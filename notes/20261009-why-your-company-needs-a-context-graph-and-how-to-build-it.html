회사에는 왜 컨텍스트 그래프가 필요한가

에이전트에 MCP 서버 몇 개를 붙인다고 회사를 이해하는 AI가 되지는 않는다. 데이터 사본, 실시간 조회, 회사의 판단 절차, 출처 기록을 한데 묶은 "회사의 두뇌"가 필요하다. 이 발표는 그 두뇌를 어떤 부품으로 짜는지 설명한다.

원본 영상: Why Your Company Needs a Context Graph (and How to Build It) 발표: Gil Feig (Merge 공동 창업자, CTO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(발표자 이름, Merge, syncing)은 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 발표자가 말하는 컨텍스트 그래프는 노드와 엣지 구조가 아니다. 외부 데이터, 정리된 문서, 메모리, 스킬을 묶은 회사의 두뇌다.
  2. MCP로 외부 서비스를 그때그때 조회하면 "지난 1년간 화난 고객은?" 같은 넓은 질문에 답하지 못한다. 티켓을 100개씩 퍼 오다 시간 초과로 끊긴다.
  3. 그래서 넓게 훑거나 뜻으로 찾을 데이터는 사본을 동기화해 자기 쪽 벡터 DB에 둔다. 고객 한 명 조회나 행동 하나는 실시간 조회로 충분하다.
  4. 가져온 데이터를 통째로 넘기지 않는다. 라우터가 길을 정하고, 요약기가 줄여서 돌려준다.
  5. "화난 고객"의 뜻은 회사마다 다르다. 그 판단 기준을 스킬로 적고, 에이전트는 스킬부터 확인한다.
  6. 컨텍스트는 네 층이다. 프롬프트·스킬·메모리, 실시간 API, 동기화 데이터, 그리고 가져오며 새로 만든 파생 컨텍스트.
  7. 모든 데이터에 출처를 남긴다. 어디서, 언제, 어떤 권한으로 가져왔고, 언제 버려야 하는지.
01

컨텍스트 그래프는 회사의 두뇌 02:10

발표자가 말하는 컨텍스트 그래프 context graph는 점(노드)과 선(엣지)으로 이은 진짜 그래프 구조가 아니다. 에이전트가 회사에 대해 알아야 할 것을 모은 "회사의 두뇌"다. 네 가지로 이뤄진다.

외부 서비스 데이터 · third-party data

회사가 쓰는 다른 시스템의 데이터다. 예로 NetSuite, Jira를 든다.

정리된 컨텍스트 · structured context

외부에서 들어온 데이터나 직접 넣어 둔 자료다. 에이전트에 늘 함께 넘길 고정 문서도 여기 들어간다.

메모리 · memory

에이전트를 쓰면서 생기는 기억이다. 사용자가 기억하라고 한 것과 에이전트가 스스로 남긴 것이 있다.

스킬 · skill

회사가 일을 처리하는 방식을 적은 것이다. 발표자는 이걸 아주 중요한 부분으로 꼽는다.

발표가 다루지 않는 것 어떤 기술 제품을 쓸지는 말하지 않는다. 발표자는 그건 에이전트에게 물어보면 된다고 한다. 대신 왜 필요한지, 어떤 부품으로 어떻게 짜는지에 집중한다.
02

MCP 몇 개로는 부족하다 03:10

MCP Model Context Protocol는 에이전트를 외부 도구와 데이터에 연결하는 표준이다. 발표자는 MCP 서버 한두 개를 연결하고 끝내면 왜 부족한지 예로 보여 준다. 에이전트는 고객 지원 티켓 서비스 Zendesk에 연결돼 있다. 같은 질문을 조금씩 넓혀 본다.

질문에이전트가 할 일결과
"고객 A는 지난주에 왜 화가 났나?"고객 A가 지난주에 낸 티켓만 찾는다답할 수 있다. 티켓 3개, 원인은 API 동기화 고장
"지난주에 화난 고객은 누구인가?"지난주 티켓을 전부 불러온다훨씬 어려워진다
"지난 1년간 화난 고객은 누구인가?"티켓을 100개씩 수천 번 불러온다시간 초과 timeout로 끝내 답하지 못한다

문제는 MCP 자체가 아니다. MCP 뒤에 있는 각 서비스의 API가 이런 대량 실시간 조회에 맞게 만들어져 있지 않다.

서비스들은 의미 검색 창구를 열 이유가 없다 04:40

Jira 같은 서비스가 "지난주 화난 고객은?"을 영어 문장으로 물어볼 수 있는 엔드포인트 endpoint를 준다면 문제는 풀린다. 발표자는 그럴 일이 없다고 본다. 이유는 두 가지다.

  • 데이터를 벡터화 vectorize하는 데 서비스 회사의 돈이 든다. 벡터화는 글을 뜻이 담긴 숫자 목록으로 바꾸는 작업이다.
  • 그런 창구가 생기면 사용자가 그 서비스에 덜 들어온다.
03

동기화 계층: 사본을 가져온다 04:50

그래서 실시간 조회 위에 동기화 계층 syncing layer이 필요하다. 외부 데이터의 사본을 가져와 자기 쪽 벡터 DB vector database에 둔다. 벡터 DB는 글자가 같은지가 아니라 뜻이 비슷한지로 찾아 주는 데이터베이스다.

모든 데이터를 동기화할 필요는 없다. 질문의 모양에 따라 나눈다.

실시간 조회 · live lookup 05:10
  • 특정 고객 한 명에 대해 묻는다
  • 행동 하나를 실행한다
  • 발표의 예: Stripe에 고객 한 명의 결제를 묻거나 결제 작업 하나를 한다

MCP로 충분하다

동기화 사본 · synced copy
  • 뜻으로 찾는다 (의미 검색 semantic lookup)
  • 큰 데이터 전체를 훑어 분석한다
  • 발표의 예: 지난 1년간 화난 고객 찾기

사본이 꼭 필요하다

벡터 DB를 만드는 일은 AI가 꽤 쉽게 도와준다. 어려운 건 어떤 구조로 저장하고 어떻게 꺼낼지 정하는 전략이다.

발표자는 외부 서비스 데이터 동기화 제품(Merge Unified)을 파는 회사의 CTO다. "MCP만으로는 부족하고 동기화가 필요하다"는 주장은 그 점을 감안해 읽자.

04

라우터와 요약기 06:00

이제 데이터는 두 곳에서 온다. 벡터 DB에서 뜻으로 찾은 데이터와 실시간으로 조회한 데이터다. 이걸 모두 에이전트에게 쏟아부을 수는 없다. 양이 너무 많다. 그래서 부품 두 개를 더한다.

부품하는 일
라우터 router프롬프트가 들어오면 어느 에이전트가 맡을지, 어디로 보낼지 정한다
요약기 summarizer동기화 데이터와 실시간 데이터를 모아 요약한다. 요약본을 프롬프트를 보낸 에이전트에게 돌려준다
05

스킬: 회사마다 기준이 다르다 06:40

메모리와 스킬은 따로 둬도 될 것 같다. 발표자는 이것도 컨텍스트 계층에 넣어야 한다고 말한다. 컨텍스트를 고르는 일 자체가 회사의 원칙과 절차이기 때문이다.

"지난주에 화난 고객"을 가려내는 방법도 회사마다 다르다.

  • 열린 티켓 수로 볼 수 있다.
  • 그런데 티켓 내용이 칭찬이라면 티켓 수는 불만의 증거가 아니다.
  • 티켓 시스템을 아예 쓰지 않는 회사도 있다. 그런 회사는 고객 만족을 볼 때 늘 설문 서비스 Qualtrics부터 확인한다.
에이전트는 스킬부터 본다 "우리 회사는 고객이 만족했는지 어떻게 판단하나" 같은 스킬이 있으면, 어디서 무슨 데이터를 가져올지가 정해진다. 그다음에 동기화 데이터와 실시간 데이터를 찾고, 요약해서 돌려준다.
06

질문 하나의 처리 흐름 07:30

  1. 라우팅: 프롬프트가 들어온다. 라우터가 맞는 에이전트로 보낸다.
  2. 스킬·메모리 확인: 에이전트는 이 질문이나 작업에 맞는 메모리나 스킬이 있는지 본다.
  3. 데이터 위치 결정: 그 결과로 동기화 캐시 DB와 실시간 MCP 조회 중 어디를 볼지 정한다.
  4. 요약과 응답: 가져온 데이터를 요약해 돌려준다.

발표자는 여기에 마법이 없다고 강조한다. 자기 사례에 맞게 계산만 잘하면 된다.

앞에서 본 "열린 티켓 수" 질문은 실시간 조회로는 불가능했다. 로컬 사본이 있으니 간단해졌다. 모든 고객의 티켓 수를 모으고, 티켓을 요약하고, 고객마다 상태를 매길 수 있다.

07

컨텍스트의 네 층 08:30

발표자는 에이전트에 들어가는 모든 것을 컨텍스트로 본다. 프롬프트, 스킬, 메모리를 컨텍스트라 부를지는 논란이 있을 수 있다. 그래도 모두 컨텍스트 계층에 넣는다.

층무엇인가언제 쓰나부담
프롬프트·스킬·메모리질문, 회사의 판단 절차, 쌓인 기억늘. 데이터를 어디서 가져올지 정한다-
실시간 API 호출질문할 때 외부 서비스를 바로 부른다단순 조회, 단순 가져오기만들기 쉽고, 덧붙이기 쉽고, 돌리는 비용이 싸다
캐시(동기화) 데이터외부 데이터의 사본을 벡터 DB에 둔다의미 검색, 복잡한 조회, 깊은 질문만들기 더 복잡하다. 벡터 DB와 계속되는 동기화 때문에 비싸다. 최신 상태를 지키기 어렵다
파생 컨텍스트 derived context데이터를 가져오면서 새로 만든 요약 같은 정보같은 질문이 반복될 때다시 찾고 다시 요약하는 일을 줄인다

파생 컨텍스트의 예 09:20: 고객 한 명의 티켓 전체를 가져올 때마다 요약을 만들어 정리된 컨텍스트 저장소에 넣어 둔다. 다음에 흔한 질문이 오면 다시 찾고 다시 요약하지 않아도 된다.

고르는 기준 단순 조회라면 실시간 API를 먼저 쓴다. 넓게 훑거나 뜻으로 찾아야 할 때만 동기화 사본을 쓴다. 사본은 강력하지만 비싸고 관리가 어렵다.
08

컨텍스트를 고르는 순서 10:00

발표자가 보여 준 순서도를 표로 옮겼다. 프롬프트가 들어오면 1단계부터 내려간다.

단계확인할 것예아니오
1맞는 스킬이나 메모리가 있나그 스킬을 실행하고 2단계로3단계로 가서 데이터를 고른다
2스킬에 외부 데이터가 필요한가3단계로바로 답을 만들어 보낸다
3동기화 데이터가 신선한가 (SLA 안인가)캐시 컨텍스트를 쓴다실시간 API를 부른다
4컨텍스트가 충분한가필요하면 알아낸 것을 메모리에 저장하고, 답을 만들어 보낸다실시간 API로 더 모은다. 충분해질 때까지 몇 번 돈다

여기서 SLA Service Level Agreement는 "이 데이터가 얼마나 최근이어야 믿고 쓸 수 있나"를 정한 신선도 기준이다.

새로 알아낸 것을 메모리로 남겨 두면, 다음 질문은 1단계에서 바로 찾을 수 있다.

09

출처를 버리지 않는다 11:30

추적 가능성 traceability과 출처 기록 provenance은 처음엔 중요해 보이지 않는다. 발표자는 데이터가 어디서 왔는지 절대 버리지 말라고 한다.

  • MCP로 가져온 데이터에는 출처가 따라온다.
  • 벡터 DB에 동기화한 데이터는 메타데이터 metadata에 출처를 함께 저장한다. 메타데이터는 데이터 자체가 아니라 데이터에 대한 정보다.

ChatGPT 같은 서비스가 답 끝에 "출처 3개"를 링크로 붙이는 것과 같은 원리다. 업무상 중요한 결정을 내릴 때는 더 중요하다. 데이터는 버전이 바뀌고 낡는다. 1년 전에 동기화한 데이터로 결정을 내리면 안 된다.

남길 항목 12:10

질문예시 값 (발표에 없음)
어디서 가져왔나Zendesk 티켓 API
언제 가져왔나2026-10-09 09:12 UTC
어떤 ID와 스코프로 가져왔나연동 계정 support-sync, 티켓 읽기 범위
누가 접근했나질문한 사용자 user-123
어떤 권한을 썼나읽기 전용
변환했나, 원래 모습은티켓 12개를 요약함. 원본 티켓 ID 목록을 함께 보관
무엇이 오면 무효인가가져온 지 한 달이 지나면 쓰지 않는다 (발표의 예)

왼쪽 질문 목록은 발표 내용이다. 오른쪽 값은 이해를 돕기 위해 만든 예시다.

이 기록은 두 곳에 쓰인다. 하나는 서비스 화면에 출처를 보여 주는 것이다. 다른 하나는 뭔가 잘못됐을 때 원인을 조사하는 것이다. 발표자는 잘못될 일은 반드시 생긴다고 덧붙인다.

10

종합 예시: Acme 상태 보고 12:40

요청은 이렇다. "고객 Acme의 상태를 한 문단으로 정리해 줘. 재계약 위험과 마지막 지원 문의도 넣어서." 이 예에서는 맞는 스킬이 없다고 가정한다.

  1. 캐시에서 Acme의 계정 요약을 찾는다.
  2. 요약이 낡았거나 없으면 CRM을 실시간 API로 조회한다.
  3. 티켓 시스템에서 마지막 지원 문의를 찾는다. 신선도 기준 안이면 캐시를, 아니면 실시간 조회를 쓴다.
  4. 실시간 조회라면 티켓은 최근 5개만 가져온다. 전체 이력을 끌어오면 시간 초과 위험이 있다.
  5. 파생 요약을 만든다. 필요하면 저장해 두고, 답으로 돌려준다.

앞에서 본 부품이 모두 들어 있다. 캐시 우선, 신선도 확인, 실시간 조회의 양 제한, 파생 컨텍스트 저장이다.

핵심 정리

  1. 컨텍스트 그래프는 외부 서비스 데이터, 정리된 컨텍스트, 메모리, 스킬을 묶은 회사의 두뇌다.
  2. 실시간 MCP 조회만으로는 넓은 질문에 답하지 못한다. 외부 API가 대량 조회에 맞지 않아 시간 초과가 난다.
  3. 서비스 회사들은 의미 검색 창구를 열 동기가 없다. 벡터화 비용이 들고 방문이 줄기 때문이다.
  4. 넓게 훑거나 뜻으로 찾을 데이터는 사본을 동기화해 벡터 DB에 둔다. 단건 조회와 단건 행동은 실시간으로 충분하다.
  5. 라우터가 요청을 맞는 곳으로 보내고, 요약기가 모은 데이터를 줄여 돌려준다.
  6. 무엇을 어디서 가져올지는 회사마다 다르다. 그 기준이 스킬이고, 에이전트는 스킬부터 본다.
  7. 컨텍스트는 네 층이다. 프롬프트·스킬·메모리, 실시간 API, 캐시 데이터, 파생 컨텍스트.
  8. 캐시가 신선도 기준(SLA) 안이면 캐시를, 아니면 실시간 API를 쓴다. 충분해질 때까지 반복한다.
  9. 모든 데이터에 출처, 시각, ID와 권한, 변환 여부, 무효 조건을 남긴다.
  10. 도구는 컨텍스트가 아니다. 데이터는 신선하고 필요한 만큼이 좋고, 모든 답은 추적할 수 있어야 한다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 컨텍스트 그래프의 네 구성 요소는?
외부 서비스 데이터, 정리된 컨텍스트, 메모리, 스킬. 노드와 엣지로 된 그래프 구조 이야기가 아니다.
Q2"고객 A는 왜 화났나"는 답하는데 "지난 1년간 화난 고객은?"은 못 하는 이유는?
실시간 조회로는 티켓을 100개씩 수천 번 불러와야 하고, 결국 시간 초과로 끊긴다. 외부 서비스의 API가 이런 대량 조회에 맞지 않는다.
Q3Jira 같은 서비스가 의미 검색 엔드포인트를 열지 않는 이유로 발표자가 든 두 가지는?
데이터를 벡터화하는 비용을 서비스 회사가 떠안아야 한다. 그리고 사용자가 그 서비스에 덜 들어오게 된다.
Q4Stripe 조회는 왜 동기화 없이 MCP 실시간 조회로 충분한가?
늘 고객 한 명에 대해 묻거나 행동 하나를 실행하기 때문이다. 큰 데이터 전체를 훑을 일이 없다.
Q5라우터와 요약기는 각각 무슨 일을 하나?
라우터는 들어온 프롬프트를 맞는 에이전트와 경로로 보낸다. 요약기는 동기화 데이터와 실시간 데이터를 모아 줄인 뒤 에이전트에 돌려준다.
Q6스킬을 컨텍스트 계층에 넣어야 하는 이유는?
컨텍스트를 고르는 일 자체가 회사의 원칙이기 때문이다. "화난 고객"을 티켓 수로 볼지, 티켓 내용으로 볼지, Qualtrics 설문으로 볼지는 회사마다 다르다.
Q7실시간 API와 캐시(동기화) 데이터를 비교하면?
실시간 API는 만들기 쉽고 싸서 단순 조회에 먼저 쓴다. 캐시 데이터는 의미 검색과 깊은 질문에 꼭 필요하지만, 만들기 복잡하고 비싸며 최신 상태를 지키기 어렵다.
Q8파생 컨텍스트란 무엇이고, 왜 저장하나?
데이터를 가져오면서 새로 만든 정보다. 예를 들어 고객 한 명의 티켓 전체 요약이다. 저장해 두면 같은 질문이 왔을 때 다시 찾고 다시 요약하지 않아도 된다.
Q9캐시를 쓸지 실시간 API를 부를지는 무엇으로 정하나?
캐시 데이터가 신선도 기준(SLA) 안에 있는지로 정한다. 안이면 캐시를 쓰고, 벗어나면 실시간 API를 부른다.
Q10출처 기록에 남겨야 할 항목은?
어디서, 언제 가져왔나. 어떤 ID와 스코프로, 누가 접근했고 어떤 권한을 썼나. 변환했나와 원래 모습. 무엇이 오면 무효가 되나(예: 한 달 경과).
Q11Acme 예시에서 티켓을 최근 5개만 가져오는 이유는?
실시간 조회로 전체 이력을 끌어오면 시간 초과 위험이 있기 때문이다. 필요한 만큼만 가져온다는 원칙과도 맞는다.
