에이전트에게 자기 샌드박스를 주는 이유

에이전트가 목표를 받아 몇 시간씩 혼자 일하려면 코드를 돌리고 파일을 남길 자기 컴퓨터가 필요하다. Google은 Gemini API 요청마다 클라우드 샌드박스를 붙이고, 에이전트 루프 전체를 서버에서 돌리는 방식으로 답한다.

원본 영상: Why AI Agents Should Have Their Own Sandbox 발표: Philipp Schmid (Google DeepMind, AI Studio·Gemini API 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 따로 확인하지 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 확실하지 않은 것에는 (추정)을 붙였다. 발표 화면의 코드는 자막에 남지 않아 옮기지 않았다. mm:ss는 영상 위치다.

제목은 "왜"를 묻지만, 발표 대부분은 Gemini의 Interactions API와 관리형 에이전트 소개다. 발표 곳곳에 흩어진 이유는 13번 섹션에 모았다. 발표자는 이 제품을 만드는 Google 쪽 사람이므로, 장점 위주의 설명은 그 점을 감안해 읽자.

3분 요약
  1. 에이전트를 쓰는 방식이 바뀌었다. 질문하고 답을 받는 대신 목표와 확인 방법을 주고 몇 시간에서 며칠을 맡긴다.
  2. Google의 새 Interactions API는 모델과 에이전트를 같은 모양으로 부른다. 대화 상태는 서버가 들고, 오래 걸리는 일은 비동기로 처리한다.
  3. 대화를 사용자·모델의 턴이 아니라 단계로 기록한다. 함수 결과는 사용자가 아니라 환경에서 오기 때문이다.
  4. environment 칸에 remote를 지정하면 에이전트가 Google이 관리하는 클라우드 샌드박스를 받는다. 코드 실행, 파일 쓰기, 패키지 설치를 거기서 한다.
  5. 샌드박스는 다음 요청에도 남고, 여러 에이전트가 같이 쓸 수 있다. 파일 시스템이 에이전트끼리 맥락을 나누는 통로가 된다.
  6. 에이전트는 파일이다. AGENTS.md와 skills 폴더는 자동으로 시스템 지시문에 들어간다. 다 꾸린 환경은 ID로 저장해 새 에이전트의 출발점으로 쓴다.
  7. 클라이언트가 함수 호출을 받아 실행하고 결과를 돌려보내던 루프가 API 호출 한 번으로 줄어든다. 인프라를 직접 다룰 필요가 없다는 것이 발표자의 주장이다.

02

Interactions API의 기본 모양 03:20

Interactions API는 Gemini 모델과 Gemini 에이전트를 부르는 새 API다. 발표자는 OpenAI의 Responses API에 대한 Google의 답이라고 소개했다.

발표자가 강조한 점은 모델을 부를 때와 에이전트를 부를 때 모양이 같다는 것이다. 이미지, 오디오 같은 다른 형식에도 같은 모양을 쓴다.

칸들어가는 것
누구에게모델(예: Gemini) 또는 에이전트(예: Antigravity 에이전트)
입력글 한 줄, 또는 이미지·오디오 같은 멀티모달 데이터
도구 또는 환경Google 검색 같은 도구, 또는 에이전트가 일할 샌드박스

위 표는 발표자의 설명을 칸별로 정리한 것이다. 실제 코드 문법은 공식 문서에서 확인해야 한다.

"Responses API보다 개발자 중심이고 단순하며 웹 개발자에게 친숙하다"는 비교는 발표자의 주장이다.

직접 써 보려면 02:40

  • ai.studio 또는 ai.dev에 들어가 API 키를 받는다. 설치할 것이 없고 Gmail 계정으로 바로 시작한다.
  • 더 큰 모델이나 더 많은 사용량이 필요하면 신용카드를 등록한다. 이제 Google Cloud로 넘어가지 않고 AI Studio 안에서 다 된다.
  • 예산 한도를 정해 비용이 넘치지 않게 할 수 있다.
03

서버가 상태를 들고 기다려 준다 04:10

Interactions API에서 새로 생긴 것은 세 가지다.

기능하는 일좋아지는 점
서버 측 상태 관리 server-side state다음 턴에는 새 입력과 이전 상호작용의 ID만 보낸다. 서버가 지금까지의 입력을 이어 붙여 모델에게 보여 준다클라이언트가 대화 기록을 들고 다니지 않아도 된다
오래 걸리는 작업 long-running operations요청을 보내면 ID를 바로 받는다. 스트리밍이나 폴링으로 끝날 때까지 기다린다영상 생성처럼 오래 걸리는 일에 HTTP 연결을 계속 열어 두지 않는다
도구 섞어 쓰기Google 검색 같은 기본 도구와 직접 만든 함수를 한 요청에 함께 넣는다어떤 도구를 먼저 쓸지 모델이 스스로 정한다

이름을 "interactions"로 지은 이유도 설명했다. 이제는 응답 하나를 받고 끝나는 게 아니라 모델, 에이전트와 계속 주고받기 때문이다.

오디오와 이미지도 같은 모양 05:20

  • 오디오: Gemini TTS 모델, 입력, 생성 설정을 넣는다. 글이 아니라 오디오를 받고 싶으니 응답 형식 response modality을 오디오로 정한다.
  • 이미지: 이미지 생성 모델 Nano Banana, 입력, 생성 설정을 넣으면 이미지가 돌아온다.

작은 CVE 탐지 에이전트 06:10

도구 사용의 예로, React에 알려진 보안 취약점(CVE)이 있는지 찾는 에이전트를 화면 한 장의 코드로 만들었다.

  1. Google 검색으로 관련 글을 찾는다.
  2. URL 컨텍스트 도구로 그 페이지들을 읽는다.
  3. 함수 호출로 결과를 정해진 구조로 정리한다. 데이터베이스에 저장하거나 나중에 찾아보기 좋게 만드는 단계다.
발표 전날 나온 모델 00:50 Nano Banana Light (추정): 새 이미지 생성 모델이다. 발표자는 아주 빠르고 싸다고 했다. 이미지 한 장에 4센트라고 한다. Omni Flash (추정): Interactions API에서 Omni로 영상을 만들고 편집할 수 있게 됐다. 발표자는 Omni 영상 생성을 오래 걸리는 작업의 예로 들었다.
04

대화 턴 대신 단계 06:40

다른 모델 제공사의 API나 오픈 모델은 사용자 턴과 모델 턴이 번갈아 오는 구조다. 사용자가 입력하고 모델이 답한다. 발표자는 이 구조가 1~2년 전까지는 잘 맞았다고 본다.

에이전트와 추론 모델이 나오면서 맞지 않게 됐다. 이유는 두 가지다.

  • 모델이 오래 생각한다. 생각을 그대로 보여 주기도 하고, 서명 signature만 남기기도 한다.
  • 함수 결과를 돌려줄 자리가 사용자 턴밖에 없었다. 그런데 그 결과는 사용자가 아니라 환경에서 온 것이다. 발표자는 이 점이 늘 어색했다고 했다. 07:20
지금까지 · 턴사용자 → 모델 → 사용자 → 모델함수 결과도 "사용자" 턴에 넣어 돌려준다
→
Interactions API · 단계일어난 순서대로 단계가 쌓인다단계마다 자기 타입이 있다. 함수 결과는 "함수 결과" 단계로 돌려준다

이렇게 하면 새 기능이 생겨도 새 단계 타입만 더하면 된다. 각 단계가 무엇인지 타입으로 드러나서 쓰기도 쉽다.

05

Antigravity 에이전트와 하네스 08:10

Google은 Google I/O에서 Gemini API용 Antigravity 에이전트를 내놓았다. 이 에이전트는 자기 샌드박스를 가지고 온다.

이 원격 에이전트는 Antigravity 제품들과 같은 하네스 harness로 돈다. Antigravity IDE, Antigravity 2.0, CLI를 써 봤다면 이미 이 하네스를 쓴 셈이다.

하네스와 에이전트는 다르다 08:30 하네스는 에이전트의 뒷단이다. 같은 하네스 위에서도 제품마다 도구와 시스템 지시문이 다를 수 있다. 예를 들어 Antigravity IDE는 코딩 에이전트라서, API에 있는 Antigravity 에이전트와 도구 구성이 조금 다르다. 하네스가 같으니 Gemini가 이 하네스에서 더 잘 일하도록 개선되면 두 쪽이 함께 좋아진다.
06

요청마다 붙는 샌드박스 09:00

새 에이전트와 함께 environment 칸이 생겼다. 여기에 remote를 지정하면, 그 API 호출에서 에이전트가 Google이 관리하는 샌드박스 sandbox를 받는다.

요청을 보내면 Google 백엔드가 클라우드 샌드박스를 띄운다. 에이전트는 그 안에서 이런 일을 한다. 09:20

  • 코드를 실행한다
  • 파일을 만들고 쓴다
  • 의존성을 설치한다
  • 필요한 도구를 직접 설치한다
  • 사용자의 API를 부른다

인프라는 Google이 관리한다. 개발자는 API 요청만 보낸다.

환경은 남고, 나눠 쓸 수 있다 09:40

첫 요청에서 "최신 기술 뉴스를 조사해서 파일로 만들어"라고 시킨다고 하자. 다음 요청에서 같은 환경을 이어 쓰면 앞에서 만든 파일이 그대로 있다.

환경은 에이전트끼리 나눠 쓸 수도 있다. 10:00 에이전트 셋이 한 환경에서 일하면 파일 시스템으로 맥락을 공유한다. 하위 에이전트 subagent가 다른 에이전트가 하던 일을 이어받을 수도 있다.

07

소스, 스킬, AGENTS.md 10:20

샌드박스만 있다고 일을 잘하지는 않는다. 모델은 그 안에서 쓸 맥락, 정보, 도구가 필요하다. 그래서 환경에 소스 sources를 넣을 수 있다.

  • Google Cloud Storage(GCS) 버킷
  • GitHub 저장소
  • 요청에 직접 담은 파일

Antigravity 에이전트는 파일 시스템을 기준으로 움직인다. 발표자는 "스킬 네이티브", "파일 시스템 네이티브"라고 표현했다. 정해진 자리에 파일을 두면 에이전트가 알아서 읽는다는 뜻이다.

파일두는 곳쓰이는 방식
스킬 skillsskills 폴더자동으로 찾아 시스템 지시문 system instruction에 넣는다
AGENTS.md환경 안시스템 지시문 뒤에 자동으로 붙는다 10:50

코딩 에이전트나 기존 에이전트에서 쓰던 AGENTS.md와 스킬을 그대로 가져올 수 있다는 뜻이다.

08

Agents API와 CLI 11:00

요청마다 설정을 다 보내는 방식은 편하지만 공유하기 어렵다. 1팀이 만든 에이전트를 2팀이 쓰고 싶을 때가 그렇다. 그래서 Agents API를 만들었다.

정하는 것뜻
기본 에이전트밑에서 도는 두뇌
지시문에이전트가 할 일과 규칙
환경소스를 넣은 새 환경, 또는 이미 만들어 둔 환경

에이전트가 자기 환경을 만든다 11:30

  1. 에이전트에게 준비 작업을 시킨다. 예: GitHub CLI 설치, 스킬 추가, 기본 점검.
  2. 작업이 끝나면 환경 ID를 받는다.
  3. 그 환경 ID로 새 에이전트를 만든다.
  4. 새 에이전트는 부를 때마다 준비가 끝난 환경에서 출발한다.

이렇게 만든 에이전트를 사용자나 고객과 나눌 수 있다. 발표자는 Terraform, Kubernetes, 마이크로서비스, Firecracker 같은 것을 고민하지 않아도 된다고 강조했다. 12:10

에이전트가 쓰는 Gemini API CLI 12:10

Gemini API를 부르는 명령줄 도구도 내놓았다. 코딩 에이전트가 아니고, Gemini CLI와도 다르다. 내 코딩 에이전트가 Gemini API를 부를 때 쓰는 도구다.

  • Nano Banana나 Omni로 이미지, 영상 같은 자료를 만든다.
  • 에이전트를 만들고, 고치고, 다듬는다.

Interactions API와 Agents API를 다루는 스킬도 따로 있다. 발표 화면의 QR 코드는 GitHub 저장소로 연결됐다.

09

데모 1: AI Talk Radio 13:00

AI Talk Radio는 AI Studio 안의 앱 applet이다. Google I/O 개발자 키노트에서도 보여 준 것으로, 관리형 에이전트 managed agents 위에 얹은 단순한 화면이다.

토크쇼 에이전트는 Gemini 모델을 모두 쓸 수 있다. 썸네일, 음성, 음악을 만들고 조사도 한다. 주제 하나를 주면 라디오 방송 한 편을 한 번에 만든다.

실행하면 일어나는 일 13:40

발표자는 "피자에 파인애플을 올려도 되나"를 주제로 넣었다.

  1. 환경을 띄운다.
  2. 모델이 할 일을 생각한다.

핵심 정리

  1. 에이전트는 이제 질문에 답하는 대신 목표를 받아 몇 시간에서 며칠 일한다.
  2. Interactions API는 모델과 에이전트를 같은 모양(누구에게, 입력, 도구 또는 환경)으로 부른다.
  3. 대화 상태는 서버가 들고, 다음 요청에는 이전 상호작용의 ID만 보낸다.
  4. 오래 걸리는 작업은 ID를 먼저 받고 스트리밍이나 폴링으로 기다린다.
  5. 함수 결과는 사용자가 아니라 환경에서 온다. 그래서 턴 대신 타입이 있는 단계로 기록한다.
  6. 하네스는 에이전트의 뒷단이다. 같은 하네스 위에서도 제품마다 도구와 지시문이 다를 수 있다.
  7. environment를 remote로 두면 에이전트가 Google이 관리하는 샌드박스에서 코드를 돌리고 파일을 쓴다.
  8. 환경은 다음 요청에도 남고, 여러 에이전트가 파일 시스템으로 맥락을 나눈다.
  9. 에이전트는 파일이다. AGENTS.md와 스킬은 자동으로 지시문에 들어가고, 다 꾸린 환경은 ID로 다시 쓴다.
  10. 클라이언트가 돌리던 함수 호출 루프가 서버로 옮겨 가, 에이전트 실행이 API 호출 한 번이 된다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말한 지금의 에이전트는 이전 단계와 무엇이 다른가?
프롬프트 대신 목표와 그 목표를 확인하는 방법을 준다. 에이전트는 몇 시간에서 며칠 동안 혼자 일하고 결과를 가져온다.
Q2Interactions API에서 모델을 부를 때와 에이전트를 부를 때 같은 것은?
부르는 모양이 같다. 누구에게(모델 또는 에이전트), 입력(글 또는 멀티모달 데이터), 도구 또는 환경.
Q3서버 측 상태 관리를 쓰면 다음 턴에 무엇을 보내나?
새 입력과 이전 상호작용의 ID. 서버가 지금까지의 입력을 이어 붙여 모델에게 보여 준다.
Q4영상 생성처럼 오래 걸리는 요청은 어떻게 처리하나?
요청하면 ID를 바로 받는다. 그다음 스트리밍이나 폴링으로 끝날 때까지 기다린다. HTTP 연결을 계속 열어 둘 필요가 없다.
Q5발표자가 사용자·모델 턴 구조를 버린 이유는?
모델이 오래 생각하고, 함수 결과는 사용자가 아니라 환경에서 온다. 그 결과를 사용자 턴에 넣는 게 어색했다. 그래서 단계마다 타입이 있는 타임라인으로 바꿨다.
Q6하네스와 에이전트는 어떻게 다른가?
하네스는 에이전트의 뒷단이다. 같은 하네스 위에서도 제품마다 도구와 시스템 지시문이 다를 수 있다. 하네스가 같으면 모델 개선이 여러 제품에 함께 반영된다.
Q7environment를 remote로 두면 에이전트가 할 수 있게 되는 일은?
Google이 관리하는 클라우드 샌드박스에서 코드를 실행하고, 파일을 만들고 쓰고, 의존성과 도구를 설치하고, 사용자의 API를 부른다.
Q8여러 에이전트가 한 환경에서 일할 때 맥락은 무엇으로 나누나?
파일 시스템. 한 에이전트가 남긴 파일을 다른 에이전트나 하위 에이전트가 읽고 이어서 일한다.
Q9Antigravity 에이전트가 환경에서 자동으로 읽는 두 가지는?
skills 폴더의 스킬과 AGENTS.md. 둘 다 시스템 지시문에 들어간다.
Q10준비가 끝난 환경에서 출발하는 에이전트는 어떤 순서로 만드나?
에이전트에게 준비 작업을 시킨다. 끝나면 환경 ID를 받는다. 그 ID로 Agents API에서 새 에이전트를 만든다. 새 에이전트는 부를 때마다 그 환경에서 출발한다.
Q11Gemini API CLI는 Gemini CLI와 무엇이 다른가?
코딩 에이전트가 아니다. 내 코딩 에이전트가 Gemini API를 부를 때 쓰는 도구다. 이미지, 영상 같은 자료를 만들고, 에이전트를 만들고 다듬는 데 쓴다.
Q12관리형 에이전트가 클라이언트에서 없애 주는 일은?
모델이 보낸 함수 호출을 해석하고, 실행하고, 결과를 다시 보내는 루프. 이 루프가 서버의 샌드박스에서 돌아 API 호출 한 번이 된다.
