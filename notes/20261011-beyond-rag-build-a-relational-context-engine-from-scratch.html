RAG 너머, 관계형 컨텍스트 엔진 만들기

벡터 검색은 "비슷한 내용"은 찾지만 "누가, 언제, 어떤 상태로"는 못 찾는다. 이 워크숍은 자연어 질문을 실제 데이터베이스 쿼리로 바꾸는 엔진을 여섯 단계로 직접 만든다. 핵심은 모델이 답을 쓰는 대신 쿼리를 쓰게 하고, 그 쿼리를 코드로 검증하고 고치게 하는 것이다.

원본 영상: Beyond RAG: Build a Relational Context Engine from Scratch 발표: Peter Werry (Unblocked)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 바로잡았고, 아닌 곳은 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 이 발표에서 RAG는 벡터 유사도 검색을 뜻한다. 그것은 검색의 절반이다. 나머지 절반은 자연어를 구조화된 쿼리로 바꾸는 것이다.
  2. 조직의 맥락은 PR, 이슈, 위키, Slack에 흩어져 있다. 모두 의미로 찾을 수 있지만 작성자, 날짜, 상태, 관계라는 구조도 있다.
  3. "지난주에 내가 머지한 PR"은 벡터 검색으로 못 푼다. 비슷한 문장은 찾아도 작성자와 머지 시점은 못 거른다.
  4. 이 방식에서 모델은 답을 쓰지 않고 쿼리를 쓴다. 그러려면 스키마 인지, 이름 매핑, 쿼리 검증, 오류 재시도가 필요하다.
  5. 스키마가 없는 문서 저장소라면 문서를 표본으로 뽑아 스키마를 추론한다. 발표 예제는 300건을 합쳐 하나의 트리로 만든다.
  6. 검증은 거부가 기본이다. 허용할 연산자와 필드를 목록으로 정하고 나머지는 막는다. 이 부분은 LLM이 아니라 코드로 한다.
  7. 검증 실패와 실행 오류를 모델에게 돌려주는 재시도 루프가 가장 중요하다. 발표자는 이것을 "가장 중요한 것 중 하나"라고 했다.
01

RAG는 검색의 절반이다 00:10

발표자 Peter Werry는 Unblocked에서 일한다. Unblocked는 조직의 맥락을 사람과 에이전트에게 전달하는 컨텍스트 엔진context engine을 만드는 회사다.

이 발표에서 RAG는 좁은 뜻으로 쓴다. 의미 유사도 검색semantic similarity search, 곧 벡터 검색이다. 발표자의 주장은 단순하다. 벡터 검색은 검색의 절반일 뿐이다. 오늘 만드는 것은 나머지 절반, 즉 자연어를 실제 데이터베이스 쿼리로 바꾸는 엔진이다.

원래 두 시간짜리 세션이 한 시간으로 줄었다. 발표자는 단계를 빨리 넘어가되, 저장소가 공개돼 있으니 나중에 따라 해도 된다고 했다. 발표 중 행사장 네트워크가 끊겨 저장소 화면은 제대로 띄우지 못했다.

발표자는 컨텍스트 엔진을 파는 회사 소속이다. "벡터 검색만으로는 부족하다"는 주장은 그 회사의 제품 방향과 맞닿아 있다. 이 점을 감안하고 읽자.

02

흩어진 맥락에는 구조가 있다 03:00

에이전트에게는 맥락이 필요하다. 그런데 엔지니어링 팀의 맥락은 팀이 쓰는 모든 도구에 흩어져 있다.

  • PR과 리뷰 댓글
  • Linear, Jira 같은 이슈와 티켓
  • Notion, Confluence 같은 문서와 위키
  • Slack, Teams 같은 대화

이 모든 것은 의미로 검색할 수 있다. 하지만 동시에 구조도 갖고 있다. 작성자, 날짜, 상태, 라벨, 서로 간의 관계가 그것이다.

발표자가 "2년 전"이라 부른 과거의 본능은 이랬다. 전부 벡터 저장소에 넣고, 꺼내서, 다시 순위를 매기면 맞는 것이 나오길 바란다. 발표자는 이 방식이 통하지 않는다고 말한다.

컨텍스트 엔진이 하는 일 03:50 왼쪽에는 코드, PR, 문서 같은 흩어진 맥락이 들어간다. 오른쪽으로는 지금 하는 일에 맞게 골라지고 서로 연결된 맥락이 나온다. 그 사이에서 의미 관계뿐 아니라 데이터를 잇는 구조적 관계까지 다뤄야 한다.
03

"지난주에 내가 머지한 PR" 04:30

벡터 검색이 빛나는 자리는 분명하다. 질문이 내용에 관한 것일 때다. "이 코드를 바꾼 PR을 찾아라", "이것을 두고 다툰 Slack 스레드를 찾아라" 같은 질문이다. 에이전트 루프로 감싸고 파일을 뒤지는 도구를 붙이면 꽤 멀리 갈 수 있다. 의미 검색이 좋은 출발점을 주고, 거기서부터 에이전트가 GitHub 파일 시스템을 직접 훑는다.

하지만 실제 엔지니어의 질문은 다르게 생겼다. "지난주에 내가 머지한 PR", "우리 팀이 지난주에 머지한 PR" 같은 질문이다. 질문하는 사람은 출발점과 관계는 알지만 도착점은 모른다.

벡터 검색으로 풀면
  • "지난주에 내가 머지한 PR"이라는 문장을 임베딩한다
  • 가장 가까운 벡터를 찾고 상위 K개를 다시 정렬한다
  • 결과: "머지"나 "지난주"를 언급한 PR이 나온다

문제: 작성자, 머지 상태, 실제 머지 시점은 걸러지지 않는다. 의미는 비슷하지만 3년 전에 머지된 PR이 나올 수 있다.

구조화된 쿼리로 풀면
  • 작성자 = 나
  • 상태 = 머지됨
  • 머지 시각 = 지난주 범위

핵심: 이 질문에는 시간이라는 구조적 조건이 있다. 그래서 검색에는 의미와 구조, 두 절반이 필요하다.

04

모델은 답 대신 쿼리를 쓴다 06:30

이 방식의 핵심은 한 문장이다. 모델이 질문에 직접 답하지 않는다. 데이터베이스에 던질 쿼리를 쓴다.

그런데 쿼리를 만드는 일만으로는 부족하다. 믿을 만하게, 그리고 안전하게 하려면 네 가지가 더 필요하다.

필요한 것이유
스키마 인지모델이 쿼리를 쓰기 전에 어떤 필드와 타입이 있는지 알아야 한다
이름 매핑"Peter의 열린 PR"이라고 물으면 모델은 "Peter"로 쿼리를 쓴다. 실제 GitHub 로그인 이름은 다를 수 있다
쿼리 검증모델 출력은 믿을 수 없다. 서버에서 JavaScript를 실행하는 연산자가 섞일 수 있다
자기 수정첫 시도가 틀렸으면 오류를 돌려주고 다시 쓰게 한다
한 번에 되길 바라는 모습 07:50 발표자의 동료 이름은 자막상 "Rashine"(추정)이고 로그인 이름은 "Rashab"(추정)이다. 엔진은 이 이름을 로그인으로 바꾸고, 상태 같은 조건을 매핑하고, 개수 제한과 정렬 같은 연산자까지 붙여 쿼리 하나를 만들어야 한다.
05

워크숍 구성: PR 6개 08:10

워크숍은 서로 쌓이는 PR 여섯 개를 차례로 따라간다. 시작점은 화면은 다 있지만 엔진은 비어 있는 상태다. 단계를 거치며 엔진을 채우고, 3단계에서 처음으로 살아난다.

  1. 스키마 발견
  2. 이름 매핑
  3. 쿼리 생성 (여기서 처음 동작한다)
  4. 허용 목록 검증
  5. 오류 재시도 루프
  6. 전문 검색

데이터는 GitHub 저장소 하나의 PR이다. 어느 저장소든 상관없다. 설정이 귀찮으면 에이전트에게 저장소를 가리키고 알아서 맞추게 해도 된다고 했다.

화면에는 두 탭이 있다. 쿼리 놀이터는 질문을 쿼리로 바꿔 결과를 보여준다. 채팅은 같은 엔진 위에서 추론까지 하는 완성된 에이전트다. 둘은 같은 엔진을 쓴다. 09:40

발표자는 데이터베이스 제품명을 말하지 않는다. 자막에 나오는 연산자 이름과 "스키마가 없다"는 설명으로 보아 MongoDB 계열 문서 저장소로 보인다(추정). 아래에서는 "문서 저장소"라고 부른다.

06

1단계: 스키마 발견 10:10

수집 스크립트는 내용을 내려받아 저장하려고 이미 스키마를 만들었다. 하지만 실제 서비스에서는 수집이 다른 곳에서 일어나 스키마를 모를 수 있다. PostgreSQL처럼 테이블 정의를 읽을 수도 없다. 저장소에 스키마가 없기 때문이다.

그래서 쓰는 요령은 하나다. 문서를 표본으로 뽑아 스키마를 거꾸로 만든다.

  • 문서 300건을 뽑는다
  • 모든 노드를 하나의 트리로 합친다
  • null은 건너뛴다. 값이 없는 필드는 타입을 좁히는 데 도움이 안 된다
  • 값의 모양을 보고 열거형enum 후보를 찾는다

결과는 PR 스키마를 설명하는 마크다운 문서다. 인덱스도 몇 개 만들어 준다. 마크다운인 이유가 있다. 이 문서를 그대로 쿼리 생성 프롬프트에 넣기 때문이다. 12:10

왜 LLM이 아니라 코드로 추출하나 11:20 LLM에게 문서를 주고 스키마를 뽑으라고 해도 된다. 하지만 결과가 매번 달라진다. 그래서 LLM이 뽑은 것을 코드로 검증하거나, 아예 코드가 추출을 맡는 틀이 항상 필요하다. 이 예제에서는 코드가 추출을 한다.

질의응답에서 발표자는 이 추출 코드가 "꽤 임시방편"이라고 인정했다. 타입 정보는 글자 수가 2~8자인지로 가르고, 열거형은 특정 패턴으로 찾는다. 32:00

07

2단계: 이름 매핑 12:40

발표자의 GitHub 로그인은 이름 "Peter"와 비슷하지만 같지 않다. "Peter가 쓴 PR을 다 찾아라"라고 물으면, 매핑 없이는 쿼리가 "Peter"라는 문자열을 찾고 아무것도 못 찾는다.

해결은 단순하다. 사람 이름과 로그인 이름을 퍼지 매칭fuzzy matching으로 잇는다. 레벤슈타인 거리Levenshtein distance 정도면 충분하다.

이 방법은 스키마에 조금 묶이는 것처럼 보인다. 발표자는 동적으로 하는 것도 가능하다고 했다. LLM에게 매핑을 만들게 할 수도 있다. 다만 이 예제는 단순한 요령으로 간다.

08

3단계: 쿼리 생성 14:30

이 단계가 LLM이 하는 부분이다. 발표자는 "아마 가장 단순한 부분"이라고 했다. 하는 일은 세 가지다.

  1. 1단계에서 만든 스키마를 프롬프트에 넣는다
  2. 이름 추출 도구를 주고, 반드시 호출하게 강제한다. 도구는 이름을 뽑고 2단계 매핑을 거친다
  3. 모델이 만든 쿼리 계획을 실행한다
시간 질문에는 현재 시각을 준다 15:00 LLM은 "지난주", "어제" 같은 시간 조건을 쿼리로 꽤 잘 바꾼다. 단, 프롬프트에 현재 날짜와 시각을 넣어 줘야 한다.

시연에서 "open PRs by Peter"라고 묻자 엔진이 살아났다. 15:50 모델은 매치 조건을 만들었고, "Peter"를 발표자의 GitHub 로그인으로 바꿔 쿼리를 생성했다.

09

4단계: 허용 목록 검증 16:20

쿼리는 되지만 안전하지 않다. 모델 출력은 믿을 수 없는 입력이다.

두 가지 위험 서버에서 코드 실행. 문서 저장소에는 조건식 안에서 JavaScript를 실행하는 연산자가 있다. 모델이 그것을 쓰면 서버가 임의 코드를 돌린다. 이 지점이 곧 프롬프트 인젝션 통로가 된다.
숨은 필드 유출. ID나 메타데이터처럼 내부용 필드가 쿼리나 결과에 드러날 수 있다.

대책은 허용 목록allow list이다. 거부 목록이 아니다. 기본은 거부이고, 허용할 연산자만 목록에 올린다. 필드도 같은 식으로 허용 목록을 둘 수 있다. 이 예제는 스키마를 동적으로 찾기 때문에 필드 허용 목록은 쓰지 않지만, 메타데이터처럼 미리 아는 필드는 막을 수 있다.

테넌트 격리에 쓰는 법 17:20

한 컬렉션에 여러 고객사tenant가 섞여 있다면 어떻게 할까. 발표자는 애초에 고객사별로 컬렉션을 나누라고 권한다. 그래도 섞여 있다면 이렇게 한다.

  • 고객사 ID가 든 메타데이터 필드를 LLM에게 숨긴다
  • 모델이 그 필드를 출력하면 지운다
  • 그 자리에 서버가 아는 고객사 ID 조건을 직접 넣는다

발표자는 이 부분이 기술적으로 어렵지 않다고 했다. 그냥 코드를 쓰면 된다. 전부 절차적 코드이고, 이 부분에 LLM을 쓰는 것은 권하지 않는다. 18:00

검증이 실패하면 지금은 오류를 그냥 출력한다. 시연에서 제목에 "authentication"이 들어간 PR을 찾자, 모델이 정규식을 썼고 정규식은 허용 목록에 없어서 쿼리가 거부됐다. 19:10

10

5단계: 오류 재시도 루프 19:30

모든 것을 하나로 묶는 단계다. 쿼리 계획은 두 곳에서 실패할 수 있다.

  • 검증 실패: 모델이 허용되지 않은 연산자를 썼다
  • 실행 실패: 쿼리가 문법상 틀렸다. 예를 들어 필드 포함과 제외를 한 투영에 섞었다

두 경우 모두 오류 메시지를 모델에게 돌려주고 "틀렸다, 다시 해 보라"고 한다. 최대 시도 횟수를 정해 둔다.

시연에서 같은 "authentication" 질문을 다시 던지자 세 번 만에 통과했다. 21:00 그런데 새 문제가 생겼다. 정규식도 전문 검색도 못 쓰니 모델이 일반 매치를 썼고, 그것은 정확히 일치하는 제목만 찾는다. 결과가 비었다. 이것이 마지막 단계로 이어진다.

11

6단계: 전문 검색과 채팅 21:40

전문 검색full text search을 붙인다. 아주 기본적인 수준이다. 텍스트 인덱스를 만들고, 작성자와 상태 조건을 같은 매치 안에서 합칠 수 있게 한다. 다시 묻자 이번에는 결과가 나왔다. 22:20

마지막 보상은 채팅 탭이다. "지난주에 인증 관련 작업을 했나?"처럼 한 단계 더 생각해야 하는 질문을 던졌다. 에이전트는 뒤에서 쿼리를 만들고, 데이터를 가져오고, 그 위에서 추론해 답했다. 22:40

쿼리 놀이터질문을 쿼리로 바꿔 결과를 보여준다엔진이 무엇을 만들었는지 확인하는 용도
→
채팅 에이전트같은 엔진으로 데이터를 가져와 추론한다둘의 차이는 추론 여부뿐이다
12

정리: 다시 쓸 수 있는 생각 23:30

상태나 시간처럼 구조에 관한 질문은 전통적인 RAG로 못 푼다. 그런 질문에 RAG를 쓰면 맞는 데이터가 나오지 않는다.

발표자가 꼽은 다시 쓸 수 있는 생각은 다섯 가지다.

  1. 스키마를 알려주는 프롬프트
  2. 동적 스키마 발견
  3. 이름 매핑
  4. 검증
  5. 오류 재시도. 발표자는 이것이 가장 중요한 것 중 하나라고 했다

만든 것은 필터, 집계, 시간 범위, 전문 검색을 지원하고, 검증되고, 스스로 고치며, 채팅 에이전트를 구동한다. 발표자는 조직에 그대로 배포해도 된다고 했다가 바로 덧붙였다. 내부에 배포하기 전에 검증 틀을 조금 더 다듬으라. 24:50

13

질의응답 25:40

청중 질문은 자막에서 대부분 들리지 않는다. 발표자가 되풀이한 질문과 답을 기준으로 정리했다.

질문발표자의 답
컬렉션이 여러 개면 스키마를 프롬프트에 어떻게 다 넣나 25:50LLM 단계를 하나 더 둔다. 컬렉션마다 짧은 설명을 두고, 질문에 맞는 스키마만 골라 싣는다. 1년 전에는 못 했지만 지금 모델은 이 일을 잘한다.
데이터 수집과 비용은 27:00Unblocked는 웹훅으로 PR 이벤트를 받아 계속 수집한다. 바뀔 때마다 받아서 저장한다. 그 뒤는 분산 시스템 확장 문제다.
가장 중요한 데이터 소스 셋은 27:40Slack이 가장 중요하다. "왜" 질문과 의사결정이 거기서 일어난다. "3주 전쯤 누구와 나눈 대화"는 구조화 쿼리에 딱 맞는다. PR 댓글에도 조직의 역사가 묻혀 있다. Unblocked는 과거 PR 댓글에서 "모범 사례 기억"을 뽑아 둔다.
MCP로 노출할 수 있나 29:20가능하다. 스키마가 바뀔 때마다 도구를 갱신할 수도 있다. 자연어를 받는 MCP 인터페이스를 둘 수도 있고, 데이터베이스를 직접 여는 인터페이스를 둘 수도 있다.
벡터 검색과 충돌하나 30:50전혀 아니다. 서로 보완한다. 전문 검색은 키워드만 맞추고, 개념이 같은 문장은 벡터 검색이 찾는다. 벡터 검색으로 출발점을 잡고, 거기서 이런 쿼리 도구를 쓰게 하면 좋다.
하이브리드 검색을 쓰나 33:00의미 검색과 어휘 검색을 합쳐 순위를 융합하는 뜻이라면, 그렇다.
표본 300건은 어떻게 정했나 33:50경험적 시행착오다. 고객이 "내가 찾던 게 빠졌다"고 하면 파고들어 원인을 찾으며 맞췄다. 항상 빠지는 문서는 있다.
도구 호출을 어떻게 강제하나 35:20두 가지 방법이 있다. 하나는 쿼리 도구가 사용자 이름을 인자로 받아 잘못된 이름이면 거기서 실패시키는 것. 다른 하나는 에이전트를 지켜보다가 추출 도구를 안 부르면 "잊었으니 지금 호출하라"는 메시지를 끼워 넣는 것.
스키마가 바뀌면 37:00이 예제는 스키마를 모르는 상황이라 일정 간격으로 다시 추론한다. Unblocked는 정적 스키마를 코드로 관리한다. GitHub가 스키마를 바꾸면 코드를 고쳐 CI로 배포한다.
발표자가 선을 그은 곳 34:00 Unblocked 제품은 정확성을 위해 정적 스키마를 많이 쓴다. 동적 스키마 발견은 데이터 탐색, 실험, 임의의 데이터베이스 연결에 좋은 기법이라서 보여준 것이다. 제품 그대로의 구조가 아니다.
14

핵심 정리

  1. 벡터 검색은 검색의 절반이다. 나머지 절반은 자연어를 구조화 쿼리로 바꾸는 것이다.
  2. 조직의 맥락에는 작성자, 날짜, 상태, 관계라는 구조가 있다. 전부 벡터에 넣는 방식은 이것을 버린다.
  3. "지난주에 내가 머지한 PR"은 시간과 작성자 조건이 있어 벡터 검색으로 못 푼다.
  4. 모델은 답이 아니라 쿼리를 쓴다. 그리고 그 쿼리는 코드가 검증한다.
  5. 스키마가 없으면 문서를 표본으로 뽑아 스키마를 추론한다. 추출은 LLM보다 코드가 낫다. 결과가 일정하기 때문이다.
  6. 사람 이름과 로그인 이름은 다르다. 퍼지 매칭으로 잇고, 이름 추출 도구 호출을 강제한다.
  7. 시간 질문을 잘 풀려면 프롬프트에 현재 시각을 넣는다.
  8. 검증은 거부가 기본, 허용 목록이다. 코드를 실행하는 연산자와 숨은 필드를 막는다. 고객사 ID 조건은 서버가 직접 넣는다.
  9. 검증 실패와 실행 오류를 모델에게 돌려주는 재시도 루프가 가장 중요하다.
  10. 벡터 검색과 구조화 쿼리는 경쟁하지 않는다. 벡터로 출발점을 잡고 구조화 쿼리로 정확히 좁힌다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1이 발표에서 RAG는 무엇을 뜻하고, 왜 "절반"이라고 하나?
의미 유사도 검색, 곧 벡터 검색이다. 내용이 비슷한 문서는 찾지만 작성자, 날짜, 상태 같은 구조적 조건은 못 거른다. 나머지 절반은 자연어를 구조화 쿼리로 바꾸는 것이다.
Q2"지난주에 내가 머지한 PR"을 벡터 검색으로 풀면 어떤 결과가 나오나?
"머지"나 "지난주"를 언급한 PR이 나온다. 작성자와 머지 시점은 걸러지지 않아 3년 전 PR이 나올 수 있다.
Q3이 방식에서 모델의 역할은?
질문에 직접 답하지 않는다. 데이터베이스에 던질 쿼리를 쓴다. 답은 그 쿼리의 결과에서 나온다.
Q4쿼리 생성 외에 필요한 네 가지는?
스키마 인지, 이름 매핑, 쿼리 검증, 자기 수정(오류 재시도).
Q5스키마가 없는 저장소에서 스키마를 어떻게 얻나?
문서를 표본으로 뽑아(예제에서는 300건) 하나의 트리로 합친다. null은 건너뛰고, 값 패턴으로 열거형을 찾는다. 결과는 프롬프트에 넣을 마크다운이다.
Q6스키마 추출을 LLM이 아니라 코드로 하는 이유는?
LLM 추출은 결과가 매번 달라진다. 그래서 LLM 결과를 코드로 검증하든 코드가 직접 추출하든, 절차적 틀이 항상 필요하다.
Q7시간 조건이 든 질문을 잘 풀기 위해 프롬프트에 넣어야 하는 것은?
현재 날짜와 시각. 이것만 주면 LLM은 "지난주" 같은 조건을 꽤 잘 쿼리로 바꾼다.
Q8검증을 거부 목록이 아니라 허용 목록으로 하는 이유는?
기본이 거부여야 모르는 위험이 새지 않는다. 서버에서 JavaScript를 실행하는 연산자나 내부 필드처럼 막아야 할 것을 하나씩 열거하는 방식은 빠뜨리기 쉽다.
Q9한 컬렉션에 여러 고객사가 섞여 있을 때 고객사 ID 필드는 어떻게 다루나?
LLM에게 숨기고, 모델이 출력하면 지우고, 서버가 아는 고객사 ID 조건을 직접 넣는다. 다만 발표자는 애초에 컬렉션을 나누라고 권한다.
Q10재시도 루프가 처리하는 두 종류의 실패는?
검증 실패(허용되지 않은 연산자 사용)와 실행 실패(문법 오류, 예를 들어 투영에서 포함과 제외를 섞음). 둘 다 오류를 모델에게 돌려주고 최대 횟수까지 다시 시도한다.
Q11시연에서 재시도 세 번 만에 통과한 쿼리가 빈 결과를 낸 이유와 해결책은?
정규식과 전문 검색이 막혀 있어 모델이 정확 일치 매치를 썼다. 해결은 텍스트 인덱스를 만들어 전문 검색을 허용하고, 작성자와 상태 조건과 같은 매치 안에서 합치는 것이다.
Q12컬렉션이 많을 때 스키마를 프롬프트에 다 넣지 않는 방법은?
컬렉션마다 짧은 설명을 두고, LLM 단계를 하나 더 둬서 질문에 맞는 스키마만 고른다.
