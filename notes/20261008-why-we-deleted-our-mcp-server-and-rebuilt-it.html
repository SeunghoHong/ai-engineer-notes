MCP 서버를 지우고 다시 만든 이유

Reducto는 API를 그대로 옮긴 MCP 서버를 팀에 풀었다가, 에이전트가 자신 있게 틀리는 모습을 보고 통째로 지웠다. 다시 만든 서버는 도구 수를 줄이고, 일의 구조와 에이전트의 불확실성을 사람이 볼 수 있게 했다.

원본 영상: Why We Deleted Our MCP Server and Rebuilt It 발표: Abhi Arya (Reducto 제품 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 사례는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 "Avi", "Cloud Code"로 들린 이름은 영상 제목과 문맥에 맞춰 Abhi Arya, Claude Code로 고쳤다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트 우선 소프트웨어는 모델을 다듬는 일이 아니라 구조의 문제다. 기준 질문은 "에이전트가 틀리면 누가 값을 치르나"다.
  2. 자동 모드는 조용히 틀리고, 사용자 우선은 채팅봇에 머문다. 이기는 쪽은 사람이 확인할 수 있는 범위에서 에이전트에게 능력을 주는 방식이다.
  3. 첫 MCP 서버는 API 엔드포인트마다 도구를 하나씩 붙인 큰 파일이었다. 데모는 잘 됐지만 팀에 풀자 자신 있게 틀렸다.
  4. 그 파일을 지우고 일의 구조를 담은 더 적은 도구로 다시 만들었다. 단계를 묶고, 다음 단계를 안내하고, 현재 상태를 한 번에 돌려준다.
  5. 실행 중 실패는 오류 없이 조용히 일어난다. 결과의 신뢰도를 모델에 돌려주고, 모호하면 추측하지 말고 묻게 했다.
  6. 세션 기록에서 사람이 고친 곳, 신뢰도가 낮던 곳, 질문한 곳을 모아 안내를 고쳤다. 쓸수록 나아졌고 영업팀이 시키지 않아도 쓰기 시작했다.
  7. 결론: 연결은 누구나 한다. 차별점은 에이전트가 자신 있게 틀렸을 때 누가, 얼마나 빨리 알아차리는가다.
01

Reducto가 푸는 문제 00:10

Reducto는 스스로를 에이전트형 문서 플랫폼 agentic document platform이라고 소개한다. 정리되지 않은 문서를 도구와 AI 에이전트가 읽을 수 있는 데이터로 바꿔 준다.

  • 지난 3년 동안 문서 30억 건 이상을 처리했다.
  • 고객으로 Harvey, Scale AI, 세계 상위 5위 안의 기술 기업, 헤지펀드를 들었다.

깨끗한 문서를 최신 모델에 넣으면 60% 정도는 그냥 된다. 어려운 건 실제 운영 환경이다. 스캔한 문서나 돌아간 페이지가 섞이면 모델이 없는 내용을 지어낸다. 이걸 환각 hallucination이라고 한다. 기업 데이터의 큰 부분이 이런 비정형 unstructured 데이터다.

Reducto는 모델과 데이터 사이에 놓이는 층이다. 복잡한 배치 분석과 후처리를 맡는다. 이런 파이프라인을 설계하다 보니 에이전트도 많이 직접 만들게 됐다.

처리량과 고객 목록은 발표자가 소개한 자사 수치다. 자사 제품 소개라는 점을 감안해 읽자.

02

"에이전트 우선"은 구조 문제 01:40

발표자는 여자친구에게서 영화 Mean Girls를 패러디한 스티커를 받았다. 문구는 "타, 루저. 우리는 에이전트 우선 소프트웨어를 만든다"였다. AI 일을 하지 않는 여자친구가 물었다. "에이전트 우선 소프트웨어 agent-first software가 뭐야?"

답이 여러 개 떠올랐다. 좋은 하네스 harness, 좋은 API, 프롬프트 다듬기. 그런데 이것들은 에이전트를 앞에 두는 일이 아니었다. 모델을 최적화하는 일에 가까웠다.

발표자의 결론은 이렇다. 에이전트 우선은 구조 architecture의 문제다. 그 구조는 질문 하나로 정해진다.

에이전트가 틀리면, 그 값은 누가 치르는가?발표의 중심 질문 02:40
03

이 질문에 따라 에이전트 제품을 세 가지로 나눌 수 있다.

방식무엇을 앞세우나어떻게 되나

04

첫 MCP 서버 04:00

Reducto는 문서 일을 처음부터 끝까지 자동화하는 파이프라인 pipeline 도구를 만든다. 순서는 이렇다.

  1. 문서를 파싱한다 parse. 글, 표, 배치를 읽어 낸다.
  2. 문서를 분류하거나 classify 구역으로 나눈다 split.
  3. 필요한 정보를 추출한다 extract.

쓰임새는 송장 처리, 계약 관리처럼 사람의 입력이 필요한 일이다.

일찍부터 문제가 보였다. 사용자, 특히 사내 영업팀이 결과보다 설정에 시간을 다 쓰고 있었다. 기존 화면이 파이프라인을 "만드는" 일에 맞춰 설계됐기 때문이다. 에이전트 시대에는 최종 결과물이 중요하다. 사용자를 거기까지 얼마나 빨리 데려가느냐가 중요하다.

그래서 MCP 서버 Model Context Protocol server를 택했다 04:50. 무거운 일은 에이전트가 맡는다. 사용자는 자기 용도를 생각하고 프롬프트만 쓰면 된다.

데모는 아무것도 말해 주지 않았다 05:00

방향을 확인하려고 Claude Code로 MVP(최소 기능 제품)를 만들었다. 앱을 움직이는 API 엔드포인트 endpoint마다 MCP 도구를 하나씩 붙였다. 전부 거대한 파일 하나에 들어 있었다.

아주 구체적인 프롬프트를 주고 Slack에 올렸다. 꽤 괜찮았다. 하지만 발표자는 자기가 무엇을 하는지 정확히 아는 사람이었다. 잘 고른 상황에서 보여 준 데모였다. 그래서 그 데모로는 아무것도 알 수 없었다.

05

팀에 풀자마자 무너졌다 05:20

진짜 시험은 MCP를 팀 전원에게 줬을 때 왔다. 바로 무너졌다.

  • 누군가 고객 통화에서 나온 어설픈 설명이나 Notion 페이지를 그대로 넣었다.
  • 에이전트는 곧장 일을 시작해 워크플로 전체를 끝까지 만들었다.
  • 그리고 모든 게 맞다고 자신 있게 말했다.
  • 하지만 사용자도 에이전트도 그 워크플로가 실제로 무엇을 하는지 설명하지 못했다.

이것이 운영 환경에서 만난 자동 모드의 실제 모습이다. 에이전트는 한 번도 "잘 모르겠다"고 하지 않았다. 가진 도구를 전부 썼다. 사람이 중간에 확인하거나 생각할 자리는 없었다.

우리 시스템과 통신하는 것은 만들었다. 하지만 우리 시스템과 함께 일하는 것은 만들지 못했다.발표자의 말을 옮김 06:00
06

파일을 통째로 지웠다 06:10

흔히 떠올리는 해결책은 시스템 프롬프트를 더 자세히 쓰거나 모델에 안내를 더 주는 것이다. 발표자는 진짜 문제가 구조라고 봤다. 그래서 MCP 도구를 담은 파일 전체를 커밋 하나로 지웠다.

새로 만든 것은 더 많은 도구가 아니었다. 오히려 도구 수는 줄었다. 대신 도구 하나하나가 실제 일의 구조를 담았다.

처음 MCPAPI 엔드포인트마다 도구 하나"만들기" 같은 단계를 에이전트가 반복 호출하고, 파이프라인이 제대로 조립되기를 빈다
→
다시 만든 MCP일의 구조를 담은 더 적은 도구제품이 실제로 어떻게 돌아가는지 아는 도구. 정답이 정해진 부분은 도구가 정한다
바꾼 것내용효과
단계 묶기 06:50분류 결과를 추출로 넘기는 흔한 조합을 classify → extract 도구 하나로 만들었다에이전트가 두 단계를 어떻게 이을지 프롬프트를 보고 추측하지 않는다
다음 단계 안내단계마다 끝나면 다음에 무엇을 할지 맥락에 맞는 안내를 준다. 일부 도구는 자동으로 다음 단계로 이어진다이미 정답이 정해진 부분을 에이전트가 마음대로 하지 않는다
상태 스냅샷 07:30한 번 호출로 파이프라인의 현재 상태를 돌려준다. 전체 흐름의 맥락부터 구체적인 오류 코드까지 담는다에이전트는 상태가 없다 stateless. 스냅샷이 있으면 변수 이름을 추측하거나 지어내지 않고, 실제로 있는 것을 참조한다
모양 제한도구는 엔지니어가 의도한 모양의 파이프라인만 만들게 한다사람이 무슨 일이 있었는지 따라갈 수 있다. 결과를 다른 사용자에게 설명할 수도 있다
핵심 맥락을 프롬프트에서 구조로 옮겼다. 그러자 에이전트는 추측을 멈추고 참조하기 시작했다.

API가 아니라 전문성을 건넨다 08:10

자동 모드를 피하려면 에이전트에게 API를 그대로 건네면 안 된다. 전문성을 담은 도구를 건네야 한다. 발표자가 꼽은 전문성은 세 가지다.

  • 올바른 패턴: 어떤 단계를 어떤 순서로 잇는지
  • 상태: 지금 무엇이 만들어져 있고 어디서 오류가 났는지
  • 검증기 validator: 결과가 맞는지 확인하는 장치

목표는 맞는 길이 가장 쉬운 길이 되게 하는 것이다.

07

실행 중의 실패는 조용하다 08:30

여기까지로 "만드는 단계"의 문제는 풀렸다. 도구가 구조를 드러냈고, 사람이 에이전트가 한 일을 따라갈 수 있었다. 이번에는 실행 단계에서 문제가 생겼다. 에이전트가 만들려는 결과 자체가 틀리면 누가 알아차릴까?

  • 추출할 항목을 정한 스키마 schema가 나쁘다.
  • 사용자가 실제 용도를 제대로 말하지 않았다.
  • 문서 100건을 돌렸는데 30쪽에 있는 스캔 이미지를 놓쳤다.
  • 어떤 종류의 문서가 들어오는지 사용자가 정하지 않았다.

이럴 때 세그폴트 seg fault 같은 눈에 보이는 오류는 나지 않는다. 파이프라인은 그대로 끝까지 돈다.

모두 같은 실패다 에이전트는 자신 있게 틀린다. 에이전트가 가진 불확실성은 전혀 보이지 않는다.
08

불확실성이 보이게 09:30

해결은 변화 하나로 모였다. 불확실성을 읽을 수 있게 만드는 것이다. 불확실성은 두 종류다.

결과의 불확실성 09:50

Reducto의 추출 결과에는 실패 정보가 붙는다.

  • 신뢰도 점수 confidence score: 이 값이 얼마나 확실한지
  • 바운딩 박스 bounding box: 문서의 어느 위치에서 읽었는지

이 정보를 모델에 다시 넣어 주는 도구를 만들었다.

결과: 추출 스키마가 시간이 갈수록 나아졌고, 문서 결과가 더 정확해졌다.

에이전트 자신의 불확실성 10:10

필드를 두 가지로 읽을 수 있거나, 처음 보는 문서 종류를 만났을 때다.

  • 추측하지 않는다.
  • 그 자리에서 그냥 멈추지도 않는다.
  • "두 가지로 읽힌다. 어느 뜻인가?"라고 사용자에게 묻는다.

평가 eval에서 근거가 약한 가정 위에 만든 결과는 실패로 처리했다. 하네스에는 Claude Code 같은 하네스가 주는 질문 도구를 쓰라고 안내했다.

원칙: 추측이 아니라 질문에 점수를 준다.

09

최종 판단은 사람에게 10:40

판단은 에이전트 혼자 하지 않는다. 파이프라인 전체는 여전히 사용자가 감독한다.

에이전트의 신뢰도와 추론 과정을 MCP의 프롬프트 안내로 내보냈다. 이제 에이전트는 무언가를 새로 만들 때마다 무엇을 왜 했는지 사용자에게 설명한다. 사용자는 그 설명을 보고 검토한다.

이 장치가 없으면 에이전트는 사용자가 원한 결과가 아니라 사용자가 적은 문장을 만족시키는 데 그친다.

11:00 전후는 자막이 중간에 끊겨 있다. 앞뒤 문장으로 뜻을 짐작해 이어 썼다.

불확실성을 드러내고 최종 판단을 책임질 수 있는 사람에게 두면, 확인 질문 하나가 세 가지 일을 한다.

  • 모델에게 맥락을 준다.
  • 모델이 할 수 있는 일을 넓힌다.
  • 사람이 루프 안에서 판단하고 확인하게 한다. 이를 사람 확인 루프 human in the loop라고 한다.

10

에이전트가 가장 쓸모 있는 자리 12:10

발표자는 에이전트의 지능이 쓰이는 곳을 구성 단계 construction로 본다.

  • 파이프라인 만들기
  • 스키마 만들기
  • 알맞은 맥락 끌어오기

이 단계에서 에이전트는 가장 강하다. 실수도 가장 싸다. 사람이 바로 옆에 있기 때문이다.

이 쓰임에 맞춰 만들자 MCP에 대한 사용자 만족도가 올랐다. 무슨 일이 일어나는지 볼 수 있었기 때문이다.

에이전트에게 맡기기 어려운 부분, 곧 정확한 파싱과 추출은 Reducto의 문서 층이 맡는다. 에이전트가 일하는 곳에서는 확인할 수 있고 정확해야 신뢰를 얻는다.

에이전트는 상자 속 지능일 뿐이다. 그 둘레의 하네스가 결과를 낸다.발표자의 표현을 옮김 12:50

사용자 만족도가 올랐다는 말에 수치는 없었다. "Reducto가 정확한 파싱과 추출을 보장한다"는 것은 자사 제품에 대한 주장이니 감안해 읽자.

기록이 다음 안내가 된다 13:10

다음으로 계측 instrumentation, 곧 사용 기록을 모으는 일에 집중했다.

  1. MCP 세션마다 모델이 보낸 프롬프트를 기록했다.
  2. 영업팀과 다른 팀원들에게 자기 Claude Code 세션을 내보내 달라고 했다.
  3. 기록에서 세 가지 신호를 찾았다: 사람이 에이전트를 뒤집은 곳, 모델의 신뢰도가 낮던 곳, 에이전트가 질문한 곳.
  4. 이 신호를 MCP가 오래 쓰는 안내에 반영했다.

그 결과 시스템은 파이프라인을 더 만들수록 파이프라인을 더 잘 만들게 됐다. 사람이 손으로 다시 쓰지 않아도 됐다. 조직별, 사용자별로 스스로 나아지는 루프가 생겼다.

바탕은 같은 결정이었다. 모델은 잘 안내되고 들여다볼 수 있게 둔다. 모델을 이끄는 일은 그 둘레의 정보가 맡는다.

12

시키지 않았는데 쓰기 시작했다 14:00

발표자는 영업팀에게 이 에이전트를 쓰라고 한 적이 없다. 회사의 Claude Enterprise(추정)에 제품 도구로 열어 두기만 했다.

영업팀과 다른 팀원들이 스스로 자기 일에 엮어 넣었다.

  1. 고객 통화 전에 Circleback이나 Slack으로 고객에 대해 알아본다.
  2. MCP에게 그 고객에 대해 묻는다.
  3. 그 고객에 맞는 파이프라인을 만든다.

사람들은 떠밀려서가 아니라 필요해서 이 도구를 찾았다. 회사 전체가 쓰는 자원이 됐다.

결과를 믿게 되자 가치가 큰 고객 앞에도 내놓았다. 데모가 그냥 돌아간 게 아니었다. 사람이 "제가 만들었어요, 와서 보세요"라고 말할 수 있었다. 이것이 영업 통화에서 효과를 냈다.

사내 사례다. 근거로 보여 준 것은 Slack 반응 화면이고, 수치로 잰 결과는 발표에 없다. 자막에서 "Cloud Enterprise"로 들린 곳을 Claude Enterprise로 추정했다.

에이전트는 먼저 가지 않는다 15:10

몇 달 전 발표자의 답가장 좋은 모델가장 빠른 추론, 가장 높은 지능
→
지금 발표자의 답책임지는 사람과 같은 루프에이전트를, 그 일의 결과를 책임지는 사람들과 함께 루프 안에 둔다

모델은 계속 좋아진다. 닫힌 모델에서 공개 모델로, 비싼 모델에서 싼 모델로 넓어진다. 그래서 에이전트 우선은 이름과 거의 반대 뜻이 됐다. 어떤 의미에서 에이전트는 먼저 가지 않는다.

"에이전트가 무엇에 연결되나"는 더 이상 차별점이 아니다. 요즘은 누구의 에이전트든 모든 것에 연결된다. Claude는 새 커넥터도 바로 만들어 준다.

14

핵심 정리

  1. 에이전트 우선은 모델 최적화가 아니라 구조 문제다. 기준 질문은 "에이전트가 틀리면 누가 값을 치르나"다.
  2. 자동 모드는 조용히 틀리고, 사용자 우선은 채팅봇에 머문다. 이기는 쪽은 사람이 확인할 수 있는 범위의 능력을 주는 방식이다.
  3. 잘 고른 데모는 아무것도 증명하지 않는다. 진짜 시험은 팀 전원에게 풀었을 때 온다.
  4. API 엔드포인트를 1:1로 옮긴 MCP는 에이전트를 자신 있게 틀리게 만들었다. 해결은 프롬프트가 아니라 구조였다.
  5. 도구는 적게, 일의 구조를 담아서. 자주 쓰는 조합은 도구 하나로 묶고 다음 단계를 안내한다.
  6. 에이전트는 상태가 없다. 현재 상태와 오류 코드를 한 번에 돌려주는 스냅샷 도구를 준다.
  7. 실행 중 실패는 오류 없이 조용히 일어난다. 결과의 신뢰도를 모델에 돌려준다.
  8. 모호하면 추측하지 말고 묻게 한다. 평가에서 근거가 약한 가정을 실패로 처리한다.
  9. 세션 기록에서 사람이 고친 곳, 신뢰도가 낮던 곳, 질문한 곳을 모아 안내를 고친다. 쓸수록 나아진다.
  10. 연결은 누구나 한다. 차별점은 자신 있게 틀렸을 때 누가, 얼마나 빨리 알아차리는가다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 에이전트 우선 소프트웨어의 기준으로 삼는 질문은?
"에이전트가 틀리면 누가 값을 치르나." 하네스, API, 프롬프트 다듬기는 모델을 최적화하는 일이고, 에이전트 우선은 구조의 문제다.
Q2자동 모드와 사용자 우선 방식은 각각 어떻게 실패하나?
자동 모드는 에이전트가 자신만만하게 틀려서 아무도 모르고, 그 피해가 고객에게 간다. 사용자 우선은 설정 손잡이만 많고 에이전트는 채팅봇 수준이라, 사용자의 이해와 에이전트의 능력이 모두 막힌다.
Q3첫 MVP는 어떻게 생겼고, 그 데모는 왜 아무것도 말해 주지 못했나?
API 엔드포인트마다 MCP 도구를 하나씩 붙인 큰 파일 하나였다. 무엇을 하는지 잘 아는 발표자가 잘 고른 상황에서 보여 준 데모라, 실제 사용자가 쓸 때 어떻게 될지는 알 수 없었다.
Q4팀 전원에게 풀었을 때 어떤 일이 벌어졌나?
어설픈 설명만 받고도 에이전트가 워크플로를 끝까지 만들고 다 맞다고 했다. 사용자도 에이전트도 그 워크플로가 무엇을 하는지 설명하지 못했다. 에이전트는 모르겠다고 하지 않았고, 사람이 확인할 자리도 없었다.
Q5다시 만든 MCP에서 도구를 어떻게 바꿨나?
도구 수를 줄이고 실제 일의 구조를 담았다. 분류에서 추출로 넘기는 흔한 조합을 도구 하나로 묶었고, 단계마다 다음에 할 일을 안내했으며, 일부 도구는 자동으로 이어지게 했다.
Q6스냅샷 도구를 만든 이유는?
에이전트는 상태가 없다. 파이프라인의 현재 상태와 구체적인 오류 코드를 한 번에 받으면, 변수 이름을 추측하거나 지어내지 않고 실제로 있는 것을 참조한다.
Q7에이전트에게 API 대신 무엇을 건네야 하나?
전문성을 담은 도구. 올바른 패턴, 상태, 검증기를 담아서 맞는 길이 가장 쉬운 길이 되게 한다.
Q8실행 중 실패가 "조용하다"는 건 무슨 뜻인가?
눈에 보이는 오류 없이 파이프라인이 끝까지 돈다. 예를 들어 문서 100건 중 30쪽의 스캔을 놓치거나, 문서 종류가 정해지지 않은 채 돌아간다. 에이전트는 자신 있게 틀리고 불확실성은 보이지 않는다.
Q9두 종류의 불확실성과 각각의 대응은?
결과의 불확실성은 신뢰도 점수와 바운딩 박스를 모델에 돌려줘 스키마를 개선한다. 에이전트 자신의 불확실성은 추측하거나 멈추지 말고 사용자에게 묻게 하고, 평가에서 근거 약한 가정을 실패로 처리한다.
Q10자동 모드, 조용한 오답, 보상 해킹의 공통 모양은?
에이전트의 자율성과 권한이 사람이 확인할 수 있는 범위보다 컸다.
Q11에이전트가 가장 강하고 실수가 가장 싼 단계는 어디이고, 왜 그런가?
파이프라인과 스키마를 만들고 맥락을 끌어오는 구성 단계다. 사람이 바로 옆에 있어서 실수를 금방 잡을 수 있다.
Q12스스로 나아지는 루프를 위해 세션 기록에서 찾은 세 가지 신호는?
사람이 에이전트를 뒤집은 곳, 모델의 신뢰도가 낮던 곳, 에이전트가 질문한 곳. 이를 MCP의 장기 안내에 반영했다.
