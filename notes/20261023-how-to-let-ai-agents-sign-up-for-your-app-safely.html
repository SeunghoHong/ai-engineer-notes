다음 사용자는 에이전트다

개인 에이전트가 사람 대신 앱을 찾고, 가입하고, 써 보는 시대가 온다. 발표자는 데모 앱 하나로 세 가지를 보여 준다. 에이전트를 앱에 들이는 법, 실제 사용자와 잇는 법, 할 수 있는 일을 제한하고 회수하는 법이다.

원본 영상: How to Let AI Agents Sign Up for Your App Safely 발표: Isabelle Williams (WorkOS 프로덕트 매니저)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 이렇게 바로잡았다. "off.md"와 "AuthMode"는 발표자가 끝에서 직접 말한 auth.md로, "Waygo"는 데모 앱 Waypoint로 적었다. 확실하지 않은 이름은 들린 대로 쓰고 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 개인 에이전트가 앱 탐색, 가입, 첫 사용을 대신하기 시작했다. 앱은 에이전트가 가입할 수 있는 길을 열어야 한다.
  2. auth.md는 앱이 함께 올려 두는 에이전트용 안내 파일이다. 접근 방법과 가입 방법을 적는다. 실제 권한 검사는 앱의 API가 한다.
  3. 첫째 연결 방법은 익명으로 먼저 써 보기다. 나중에 사용자가 링크와 일회용 코드로 결과를 넘겨받는다. 다만 손으로 할 단계가 많아 사용자를 잃기 쉽다.
  4. 둘째 방법은 ID-JAG다. 에이전트 제공자가 사용자 신원을 서명해 보증한다. 사용자는 동의만 한다. 계정과 권한은 앱이 정한다.
  5. 회사 돈처럼 위험한 일을 맡길 때는 사용자 토큰을 넘기지 않는다. 앱이 에이전트 전용 토큰을 따로 발급한다.
  6. 에이전트 토큰의 권한은 사용자 권한과 에이전트 권한 상한의 교집합이다. 그래서 기록하고, 끊고, 제한할 수 있다.
  7. 데모의 펀드 에이전트는 남은 예산 $70만 옮기고 멈췄다. 예산을 늘리는 결정은 사람에게 남았다.

다음 사용자는 에이전트다 00:50

발표자는 WorkOS의 프로덕트 매니저다. WorkOS는 로그인과 인증 기반 기술을 파는 회사다. 발표자는 OpenAI, Cursor를 포함해 고객이 3,000곳이 넘는다고 소개했다.

발표 내내 예로 쓰는 앱은 Waypoint다. 발표자가 Cursor로 직접 만든 여행 계획 앱이다. 개인 여행과 회사 출장을 둘 다 다룬다.

지금까지 앱은 사람이 빨리 가입하고 가치를 처음 느끼는 순간 aha moment에 닿게 만드는 데 공을 들였다. 이것이 제품 주도 성장 product-led growth의 핵심이다. 그런데 Muse, Instinct(추정) 같은 개인 에이전트가 늘고 있다. 이제 조사, 제품 탐색, 첫 사용까지 에이전트가 대신한다. 발표자는 여기서 세 가지 질문을 던진다.

02

auth.md: 에이전트가 읽는 안내 파일 02:10

auth.md는 에이전트가 앱 계정을 만드는 방법을 정한 공개 프로토콜이다. 앱이 자기 주소에 마크다운 파일 하나를 올려 두는 방식이다. 사람도 열어 볼 수 있지만, 읽는 대상은 에이전트다.

에이전트는 이 파일에서 앱을 시작하는 방법을 찾는다. 파일에는 세 가지를 적는다.

  • 접근 권한을 얻는 방법
  • 계정을 만드는 방법
  • 사용자 API를 부르는 방법
설명과 강제는 다르다 auth.md는 접근 방법과 할 수 있는 동작을 설명할 뿐이다. 실제로 권한을 검사하고 막는 일은 앱의 API가 한다. 파일에 적었다고 저절로 지켜지지 않는다.

Waypoint가 둔 두 가지 모드 03:10

익명 모드 · anonymous

가입 없이 제한된 동작만 허용한다.

목적: 계정을 만들기 전에 앱이 쓸 만하다는 걸 에이전트가 먼저 확인하게 한다.

사용자 대리 모드

에이전트가 실제 사용자와 연결되면 할 수 있는 동작을 넓힌다.

목적: 에이전트가 진짜 사람을 대신해 일하게 한다. 발표자가 더 원하는 쪽이다.

03

익명으로 써 보고, 사용자가 넘겨받기 03:40

첫 번째 연결 방법이다. 에이전트가 익명으로 시작하고, 나중에 사용자가 그 결과를 자기 계정으로 가져온다.

  1. 에이전트가 가입 없이 API를 부른다. 이때 두 가지를 받는다. 하나는 API를 부를 때 쓰는 액세스 토큰 access token이다. 다른 하나는 클레임 토큰 claim token이다. 나중에 사용자가 에이전트의 결과를 넘겨받을 때 쓴다.
  2. 사용자가 소유권을 가져가고 싶어지면, 에이전트가 링크와 일회용 코드 one-time code를 준다.
  3. 사용자가 Waypoint에 와서 가입하거나 로그인한다. 그리고 코드를 입력한다.
  4. 에이전트가 한 일이 사용자 계정 밑으로 옮겨진다.
  5. 앱의 인가 서버 authorization server가 OAuth로 액세스 토큰을 새로 발급한다. 이번에는 그 사용자를 대신하는 토큰이다.
  6. 에이전트는 이 토큰으로 API를 부른다.
여기서 사용자를 잃는다 04:50 링크 열기, 가입, 코드 입력, 이메일 인증까지 사용자가 손으로 할 일이 많다. 발표자는 제품 주도 성장을 아는 사람이라면 바로 이 지점에서 사용자가 떠난다는 걸 안다고 말한다.
04

에이전트 제공자가 신원을 보증한다 05:10

발표자의 질문은 이렇다. "내 에이전트는 이미 내가 누군지 알지 않나?"

Claude Code나 Muse를 쓸 때 우리는 이미 로그인해 있다. 그 서비스는 이메일 인증 같은 방법으로 우리가 실제 사람인지 확인했다. 그렇다면 에이전트 제공자가 앱에 "이 사람은 누구다"라고 알려 주면 된다. 사용자가 손댈 일이 없어진다. auth.md는 이 방식도 지원하고, 그 바탕은 ID-JAG이라는 표준이다.

흐름 한 단계씩 05:50

  1. 에이전트가 앱의 인증 방법을 찾는다. 보호 대상인 API나 MCP 서버, 그리고 OAuth 인가 서버가 어디 있는지 알아낸다. 여기까지는 OAuth의 표준 절차다.
  2. 에이전트가 사용자에게 묻는다. "이름과 이메일을 Waypoint에 알려도 될까요?"
  3. 사용자가 동의하면, 에이전트는 자기 제공자에게 ID-JAG을 달라고 한다. Claude 에이전트라면 Claude 쪽에 요청하는 식이다.
  4. 에이전트가 받은 ID-JAG을 앱의 인가 서버에 보낸다.
  5. 인가 서버는 ID-JAG이 진짜인지 확인하고 안에 든 사용자 정보를 읽는다.
  6. 앱이 결정한다. 새 계정을 만들지, 기존 계정에 연결할지, 에이전트에게 어떤 권한을 줄지.
  7. 에이전트는 앱이 준 액세스 토큰으로 사용자를 대신해 API를 부른다.
결정권은 앱에 있다 에이전트 제공자는 "이 사람이 맞다"고 보증만 한다. 계정을 어떻게 다루고 어떤 권한을 줄지는 처음부터 끝까지 앱이 정한다.

두 연결 방법 비교

사용자 확인 흐름ID-JAG
사용자가 할 일링크 열기, 가입 또는 로그인, 코드 입력동의 한 번
신원을 확인하는 쪽앱이 가입 과정에서 직접 확인에이전트 제공자가 확인하고 서명으로 보증
필요한 조건에이전트가 사용자에게 링크와 코드를 전해 주면 된다에이전트 제공자가 ID-JAG을 발급할 수 있어야 한다
약점손으로 하는 단계마다 사용자가 떠날 수 있다제공자의 보증을 얼마나 믿을지 앱이 정해야 한다
05

ID-JAG 들여다보기 07:10

ID-JAG은 Identity Assertion JWT Authorization Grant의 줄임말이다. IETF에 올라 있는 스펙이다.

한마디로 사용자 신원에 대한 서명된 주장 assertion이다. 발행자 issuer가 서명하고, 정해진 대상 audience에게 보낸다. 이 흐름에서 발행자는 에이전트 제공자이고, 대상은 Waypoint다.

자막에는 "Identity Assertion Joined Authorization Grant"로 들렸다. IETF 초안에 알려진 이름이 Identity Assertion JWT Authorization Grant라서 그 이름으로 적었다.

발표자는 다른 곳에서도 같은 스펙을 쓴다고 말한다. Anthropic이 MCP 스펙에서 다루는 기업 관리형 인가 enterprise-managed authorization, 그리고 Okta의 앱 간 접근 Cross App Access이다.

안에 든 것 08:00

부분들어 있는 것왜 들어 있나
헤더토큰 종류(ID-JAG), 서명 알고리즘, 서명 키 정보받는 쪽이 어떤 키로 서명을 확인할지 안다
발행자에이전트 제공자누가 보증했는지 안다
사용자 정보이름, 이메일, 이메일 인증 여부계정을 만들거나 기존 계정과 잇는다
대상대상 앱(Waypoint), Waypoint가 아는 클라이언트 ID이 앱을 위해 발급된 것인지 본다
유효 시간언제까지 쓸 수 있는지오래된 주장을 쓰지 못하게 한다
서명에이전트 제공자의 서명위조되지 않았는지 확인한다

예시: 발표 슬라이드 설명을 JWT 모양으로 옮겨 본 것이다. 값은 지어낸 것이고, 실제 필드 이름은 스펙을 확인한다.

// 헤더
{ "typ": "oauth-id-jag+jwt", "alg": "RS256", "kid": "provider-key-1" }

// 페이로드
{
  "iss": "https://agent-provider.example",
  "name": "Sam Rivera",
  "email": "sam@example.com",
  "email_verified": true,
  "aud": "https://auth.waypoint.example",
  "client_id": "waypoint-agent",
  "exp": 1793000000
}

// 서명: 에이전트 제공자의 비밀 키로 만든다

Waypoint의 인가 서버는 서명을 확인한다. 그다음 이 안의 무엇을 믿을지 스스로 정한다. 계정을 만들지, 에이전트에게 돌려줄 액세스 토큰에 어떤 권한 범위 scope를 넣을지도 Waypoint가 정한다.

발표에서는 "에이전트 제공자의 공개 키로 서명한다"는 식으로 말했다. 서명은 발행자의 비밀 키로 만들고, 받는 쪽이 공개 키로 확인하는 것이 맞다.

06

데모: 손대지 않고 가입에서 예약까지 09:10

발표자는 직접 만든 에이전트 하네스로 시연했다. 이 하네스는 ID-JAG을 발급할 수 있다. 발표자는 Sam Rivera라는 사용자로 로그인해 있었다. Waypoint는 이 사용자를 처음 본다.

요청은 이랬다. "뉴욕 여행 일정을 짜 줘. 동료와 공유하고 싶어. 계획하고 공유하기 쉬운 도구를 찾아 줘."

사용자가 한 일은 동의 두 번 10:20

  1. 에이전트가 묻는다. "이름과 인증된 이메일을 Waypoint와 공유해도 될까요?" 발표자는 동의했다.
  2. Waypoint의 auth.md가 추가 권한을 요구한다. 에이전트가 저녁 식당을 예약할 수 있게 해 달라는 것이다. 발표자는 여기에도 동의했다.
  3. 에이전트가 신원을 확인받고 Waypoint 계정을 만들었다. 10:50
  4. 여행 일정을 짜고 Quality Bistro에 저녁을 예약했다.
  5. 동료와 공유할 링크를 돌려줬다.

가입 화면도, 코드 입력도, 이메일 인증도 없었다. 앞 절의 사용자 확인 흐름과 비교하면 차이가 분명하다.

열린 표준이어야 한다 11:30

발표자는 이 대목에서 확신 하나를 밝힌다. 에이전트가 서비스와 대화하고, 돈을 내고, 계정을 만드는 일이 안전하고 믿을 만하려면 열린 표준 위에 지어져야 한다는 것이다. 발표 직전 한 주 동안에도 관련 표준 발표가 여럿 있었다고 덧붙였다.

07

회사 돈을 만지는 에이전트 12:00

Waypoint는 회사 출장 예약도 다룬다. 출장 담당 직원이 에이전트를 쓰게 하고 싶다. 하지만 회사 돈이 걸려 있다. 감사 audit할 수 있어야 하고, 돈이 엉뚱한 곳에 쓰이지 않아야 한다.

발표자는 예시 인물로 Jordan을 든다. Jordan은 회사의 출장 자금을 책임진다. 예산과 승인 규칙을 정할 수 있는 사람은 Jordan 하나뿐이다. Waypoint에는 Jordan을 위한 에이전트가 두 개 있다.

읽기 전용 에이전트

흔한 챗봇이다. "예산에 무슨 문제가 있어?" 같은 질문에 답한다.

할 수 없는 일: 아무것도 바꾸지 못한다.

펀드 에이전트

직원 사이에 출장 예산을 옮긴다. 예를 들어 샌프란시스코에서 비행기로 오는 직원은 비용이 크고, 보스턴에서 기차로 오는 직원은 적다. 예산과 승인 규칙 안이라면 Jordan이 직접 옮길 필요가 없다.

할 수 없어야 하는 일: 예산 총액이나 승인 규칙을 바꿔서 문제를 "해결"하는 것. 제멋대로 움직이면 go rogue 안 된다.

에이전트가 할 일을 제한한다권한을 강제하고, 회수할 수 있게 한다

앱 안에 에이전트를 넣을 때의 요점은 하나다. 사용자 토큰이나 API 키 대신, 상한을 둔 에이전트 토큰으로 일하게 한다. 그래야 기록하고, 끊고, 제한할 수 있다.

마지막 화면에는 QR 코드가 두 개 있었다. 하나는 auth.md다. 발표자는 이것을 공개 표준이라고 소개했다. 다른 하나는 데모의 에이전트 토큰을 만든 WorkOS agent auth다.

핵심 정리

  1. 개인 에이전트가 앱 탐색, 가입, 첫 사용을 대신하기 시작했다. 앱은 에이전트를 사용자로 맞을 준비를 해야 한다.
  2. auth.md는 에이전트가 읽는 접근·가입 안내 파일이다. 설명만 하고, 실제 권한 검사는 앱의 API가 한다.
  3. Waypoint는 가입 없이 써 보는 익명 모드와, 사용자와 연결된 뒤의 대리 모드를 둔다.
  4. 사용자 확인 흐름에서는 사용자가 링크를 열고 가입한 뒤 코드를 넣어 결과를 넘겨받는다. 이 손작업에서 사용자가 떠난다.
  5. ID-JAG은 에이전트 제공자가 사용자 신원을 서명해 앱에 보증하는 IETF 스펙이다. 사용자는 동의만 한다.
  6. ID-JAG에는 발행자, 사용자 이름·이메일·인증 여부, 대상과 클라이언트 ID, 유효 시간이 담긴다.
  7. 계정 생성, 기존 계정 연결, 줄 권한은 모두 앱이 정한다.
  8. 에이전트에게 사용자 토큰이나 API 키를 넘기지 않는다. 앱이 에이전트 토큰을 따로 발급한다.
  9. 에이전트 토큰의 권한은 사용자 권한과 청사진의 교집합이다. 주체가 에이전트 ID라서 누가 했는지 남는다.
  10. 데모의 펀드 에이전트는 남은 $70만 옮기고 멈췄다. 예산을 늘리는 결정은 사람에게 남았다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 던진 세 가지 질문은?
에이전트를 앱에 어떻게 들이나. 그 에이전트를 실제 고객과 어떻게 잇나. 에이전트가 할 수 있는 일을 어떻게 제한하고 회수하나.
Q2auth.md는 누가 읽는 파일이고, 무엇을 적나?
에이전트가 읽는다. 접근 권한을 얻는 법, 계정을 만드는 법, 사용자 API를 부르는 법을 적는다.
Q3auth.md에 적어 두면 그대로 지켜지나?
아니다. auth.md는 설명만 한다. 권한을 검사하고 막는 일은 앱의 API가 해야 한다.
Q4Waypoint가 둔 두 모드와 각각의 목적은?
익명 모드는 가입 없이 제한된 동작으로 앱의 가치를 먼저 확인하게 한다. 대리 모드는 실제 사용자와 연결된 뒤 할 수 있는 동작을 넓힌다.
Q5익명 모드의 에이전트가 받는 두 토큰과 쓰임새는?
액세스 토큰은 API를 부를 때 쓴다. 클레임 토큰은 나중에 사용자가 에이전트의 결과를 자기 계정으로 넘겨받을 때 쓴다.
Q6사용자 확인 흐름의 약점은?
링크 열기, 가입, 코드 입력, 이메일 인증처럼 사용자가 손으로 할 단계가 많다. 발표자는 이 단계에서 사용자를 잃는다고 말한다.
Q7ID-JAG 흐름에서 에이전트는 ID-JAG을 어디서 받아 어디로 보내나?
사용자가 동의하면 에이전트 제공자에게서 받는다. 그리고 앱의 인가 서버로 보낸다.
Q8이 흐름에서 ID-JAG의 발행자와 대상은 각각 누구인가?
발행자는 에이전트 제공자다. 대상은 Waypoint다.
Q9ID-JAG을 받은 앱이 스스로 정하는 것은?
서명을 확인한 뒤 무엇을 믿을지, 새 계정을 만들지, 기존 계정에 연결할지, 액세스 토큰에 어떤 권한을 넣을지.
Q10에이전트에게 사용자 토큰을 그대로 넘기지 않는 세 가지 이유는?
감사와 귀속, 사용자 세션을 건드리지 않는 회수, 권한 제한.
Q11에이전트 토큰의 권한은 어떻게 정해지나?
에이전트를 부른 사용자의 권한과 그 에이전트 청사진의 권한이 겹치는 부분만 들어간다.
Q12데모에서 펀드 에이전트가 Alex의 부족액 $250를 한 번에 메우지 못한 이유는?
팀 예산에 $70밖에 없었고, 예산 총액을 바꿀 권한이 에이전트 토큰에 없었다. Jordan이 직접 예산을 늘린 뒤에야 마저 채웠다.
