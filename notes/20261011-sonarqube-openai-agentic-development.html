에이전트가 쓴 코드, 누가 검증하나

코드를 만드는 일은 에이전트가 빠르게 해결했다. 이제 병목은 그 코드가 안전한지 확인하는 일이다. 이 발표는 Codex가 코드를 고치거나 새로 쓸 때마다 SonarQube가 비밀 키를 막고, 취약점을 찾고, 수정 결과를 바로 다시 검사하는 루프를 터미널 안에서 실제로 돌려 보인다.

원본 영상: SonarQube + OpenAI: Agentic Development 발표: Killian Carlsen-Phelan (Sonar 개발자 콘텐츠 엔지니어) · 도입부: OpenAI Codex 배포 엔지니어링 팀의 Tony (추정)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. 발표 후반은 워크숍 형식의 실습이라 행사장 Wi-Fi 지연으로 기다리는 구간이 많다. mm:ss는 영상 위치다.

발표자는 SonarQube를 만드는 Sonar 소속이고, 도입부 발표자는 Codex를 만드는 OpenAI 소속이다. 두 제품의 장점을 말하는 대목은 그 점을 감안해 읽자.

3분 요약
  1. OpenAI 쪽 도입부의 세 주장: "끝났다"는 증거와 함께 말해야 한다, 샌드박스로 가두는 것과 결과가 맞는 것은 다르다, 검사 규칙은 에이전트 루프 안에 들어가야 한다.
  2. Sonar의 설문에 따르면 커밋된 코드의 42%가 AI가 썼거나 도왔지만, 개발자 96%는 그 코드를 완전히 믿지 않는다. 병목은 코드 생성에서 코드 검증으로 옮겨 갔다.
  3. Sonar가 말하는 사이클은 네 단계다. 생성은 아무 도구나 쓰고, 안내(Guide) → 검증(Verify) → 해결(Solve)을 SonarQube가 맡는다.
  4. 검증은 CI(바깥 루프)까지 가기 전에 IDE와 터미널(안쪽 루프)에서 끝내야 왕복 시간을 줄인다.
  5. 실습에서는 SonarQube 플러그인을 Codex에 붙여 비밀 키 차단 훅, 이슈 목록 도구, 찾아 고치기를 돌린다.
  6. 코드를 고칠 때마다 편집 직후 훅이 서버 쪽 분석을 돌려 새 취약점이 생기지 않았는지 바로 알려 준다. 새 코드를 쓸 때는 컨텍스트 보강이 프로젝트 규칙과 구조를 먼저 넣어 준다.
  7. 비밀 키 차단은 도구 호출과 프롬프트 제출 시점에 걸린다. 에이전트가 파일을 읽는 스크립트를 따로 쓰면 우회될 수 있다고 발표자도 인정했다.
01

OpenAI 쪽의 세 가지 주장 00:00

발표는 OpenAI Codex 배포 엔지니어링 팀의 짧은 도입부로 시작한다. 에이전트 기초는 건너뛰고 더 어려운 질문으로 바로 들어간다. 에이전트가 과제를 "완료했다"는 것은 무슨 뜻인가. 신뢰 경계trust boundary는 어디에 두는가.

주장뜻
끝났다 = 증거가 있다"고쳤습니다"가 아니라 "고쳤고, 이것이 증거입니다"여야 완료다
격리 ≠ 정확성샌드박스가 에이전트의 행동 범위를 가둘 수는 있어도 결과가 옳다고 증명하지는 못한다
피드백 계약은 루프 안에검사 규칙을 사람이 나중에 따로 하는 게 아니라 에이전트가 도는 루프 안에 넣어야 한다

에이전트 루프 자체는 늘 비슷하다. 모델이 행동을 정하고, 실행하고, 로그나 출력으로 변화를 관찰하고, 계획을 고친다. 과제 하나하나에는 기대 결과, 지켜야 할 불변 조건invariant, 범위, 그리고 인수 기준acceptance criteria이 붙는다.

02

"끝났다"는 증거가 있어야 한다 01:20

도입부 발표자가 말하는 완료의 정의는 리뷰할 수 있는 diff와 도구가 남긴 증거다. 구현이 싸지면 병목은 명세와 검증으로 옮겨 가는데, 그걸 그냥 두면 안 된다는 것이다.

코딩 에이전트가 자주 빠지는 실패 01:50

  • 맥락 부족: 필요한 정보를 다 보지 못한 채 고친다.
  • 국소 수정이 전역 규칙을 깬다: 한 곳만 보면 맞는 수정이 프로젝트 전체의 불변 조건을 위반한다.
  • 검증용 테스트가 같은 실수를 되풀이한다: 에이전트가 만든 테스트가 코드와 같은 오해 위에 서 있다.
자기 비판은 독립된 심판이 아니다 에이전트가 자기 결과를 다시 보는 것은 쓸모 있지만, 독립된 검증기oracle는 아니다. 에이전트의 판단과 별도 검증기의 판단은 서로 다른 축을 본다. 그래서 완료 여부는 둘을 다 봐야 알 수 있다. 컴파일러 기준으로 끝났나, 테스트 기준으로 끝났나, 정적 분석 기준으로 끝났나를 따로 묻고, 오히려 "아직 안 끝났다"는 반증을 찾아 나서야 한다. 사람 리뷰는 이 사이클에서 빼지 못한다.
03

격리는 정답을 보장하지 않는다 02:40

에이전트 시스템에는 두 층이 있다. 두 층은 서로 다른 질문에 답한다.

실행 층 execution layer

에이전트가 무엇을 할 수 있는가를 정한다.

  • 어떤 도구에 접근하는가
  • 범위가 어디까지인가
  • 어떤 행동에 승인이 필요한가
산출물 층 artifact layer

나온 결과가 받아들일 만한가를 평가한다.

  • 어떤 테스트와 분석을 거쳤는가
  • 정책에 맞는가
  • 원래 의도에 맞는가
샌드박스는 쓰기 작업을 가둘 수는 있어도, 그 쿼리가 안전하다고 증명하지는 못한다.도입부 발표자의 말을 옮김 03:20

어떤 검증기 하나도 증명은 아니다. 그래서 경계가 다른 통제를 여러 겹 쌓는다. 흔히 말하는 심층 방어defense in depth다. 이 구조에서 사람이 쥐는 것은 세 가지다. 의도, 예외, 그리고 출시 여부 결정이다.

04

피드백 계약은 루프 안에 03:50

검사 규칙을 에이전트 루프 안에 넣는 수단으로 세 가지를 든다.

수단역할
스킬 skills특정 과제를 어떻게 수행할지 적은 절차
MCP구조화된 도구와 컨텍스트를 모델에 제공하는 연결 규약
훅 hooks생애주기의 특정 시점에 자동으로 도는 검사. 하드코딩된 비밀 키 찾기 같은 일에 잘 맞는다

이 셋 위에 CI와 사람 리뷰가 얹힌다. 사람의 역할은 그 마지막 검토가 핵심이다.

에이전트 프로세스를 만들 때 점검할 것 04:30

  • 경계: 비밀 키가 모델 입력에 들어가기 전에 가로챌 수 있는가.
  • 근거: 프로젝트의 구체적 규칙, 위치, 취약 경로를 에이전트에 줄 수 있는가.
  • 범위: 동작을 보존하면서 매개변수를 묶어 두는가.
  • 재검사: 계속 다시 확인하는가. 에이전트의 출력이 마지막 상태가 아니라고 못 박는가.

자막에서 "parameters binding while preserving behavior"로 들리는 대목은 뜻이 분명하지 않아 들린 대로 옮겼다.

07

안쪽 루프와 바깥 루프 09:40

바깥 루프 outer loop

전통적인 CI다. 코드를 쓰고, GitHub나 GitLab에 올리고, 파이프라인이 돈다. 테스트나 스캔이 실패하면 IDE로 돌아가 고치고 다시 올린다. 또 실패한다.

발표자는 이 왕복을 "많은 개발자의 골칫거리"라고 표현한다.

안쪽 루프 inner loop

IDE와 터미널이다. 코드 생성이 끝나자마자 올리지 않고 그 자리에서 검증한다.

검증을 앞당기는 것, 즉 왼쪽으로 옮기기shift left가 시간을 아낀다.

이 발표의 실습은 모두 안쪽 루프 안에서 돈다. 터미널을 떠나지 않고 안내, 검증, 해결을 끝내는 것이 목표다.

08

실습 프로젝트와 심어 둔 취약점 12:10

실습은 발표자가 공개한 저장소를 복제한 뒤 apply sonar라는 스크립트를 돌리는 것으로 시작한다. 이 스크립트는 발표자가 만든 개인 도구이고 Sonar 공식 제품이 아니다. UI를 10분씩 클릭하지 않도록 SonarQube Cloud 프로젝트 생성, 첫 스캔, CLI 설치를 한 번에 해 준다. 발표자의 환경에서는 1분이 넘은 적이 없다고 한다.

항목내용
프로젝트작은 Python 프로젝트. 파일 4개, 전체 200줄 미만
심어 둔 문제4개. 보안 취약점 3개, 코드 스멜 1개
첫 스캔 결과보안 등급 E. 가장 낮은 등급이다

문제 1: 소스 코드에 박힌 OpenAI API 키 16:30

환경 변수나 .env 파일 대신 키를 코드에 그대로 적어 두었다. 발표자는 이런 키가 실수로 프로덕션 코드에 올라가는 일이 늘 일어난다고 말한다. 발표자가 인용한 수치로, 공개 저장소에 노출된 비밀 키의 평균 수습 시간은 90일이다. 그동안 봇들이 긁어 갈 수 있다.

문제 2: SQL 인젝션 17:20

database.py 파일의 검색 함수가 인자를 f-string에 그대로 끼워 넣어 쿼리를 실행한다. 그 인자는 명령줄 인자 sys.argv에서 온다. 즉 명령줄 인자를 넣을 수 있는 사람이 데이터베이스를 마음대로 조작할 수 있다.

SonarQube가 이걸 찾는 방법 기호 실행symbolic execution과 오염 분석taint analysis으로 데이터 흐름을 추적한다. 믿을 수 없는 입력이 들어오는 지점(소스)에서 위험한 실행 지점(싱크)까지, 여러 파일과 함수를 가로질러 경로를 그려 보여 준다. 대시보드에서는 이 경로를 단계별로 볼 수 있다. 21:20

발표 중 토큰을 환경 변수로 내보내는 단계를 빠뜨려 스크립트가 멈추는 장면이 있다. 저장소 안내대로 SonarQube Cloud 관리 메뉴에서 토큰을 만들고 셸에 export해야 한다. 15:00

에이전트 분석 agentic analysis 26:10

비밀 키 차단 훅 27:00

규칙 S8702: 에이전트가 다른 에이전트에게 뚫릴 코드를 쓰지 않도록 35:10

목록에서 발표자가 고르는 것은 S8702다. Sonar가 AI 에이전트 워크플로를 위해 따로 쓴 규칙이라고 한다. 앞에서 본 명령줄 인자가 데이터베이스까지 흘러가는 흐름이 바로 이 규칙에 걸린다. Codex에게 "S8702를 고쳐 줘"라고만 말한다.

순서일어나는 일

새 기능 추가와 컨텍스트 보강 38:20

마지막 실습은 고치기가 아니라 새로 쓰기다. database.py에 "ID로 과제를 삭제하는 함수"를 추가해 달라고 한다. 이때는 컨텍스트 보강이 먼저 움직인다. 프로젝트의 규칙과 아키텍처를 가져와 에이전트에 넣은 뒤 구현이 시작된다. 구현이 끝나면 에이전트 분석 훅이 다시 검사한다. 문제가 있으면 Codex가 고쳐질 때까지 반복한다.

이 한 번의 요청 안에 안내, 검증, 해결이 모두 들어 있고, 전부 터미널 안에서 끝난다. 발표자가 말하는 "루프를 닫는다"는 것이 이것이다.

청중 질문 정리

질문발표자의 답
개발 워크플로에 부담이 늘지 않나 30:30프로비저닝 스크립트는 1분 안쪽이고, MCP는 다른 MCP와 같은 수준이다. 추가 부담은 없다고 본다
CLI와 MCP는 무슨 관계인가 32:10CLI는 설정과 프로비저닝을 맡는다. MCP는 Docker 안에서 돌고, 스킬이 필요할 때 거친다. 플러그인은 CLI 위에 얹혀 있어서, 요청에 따라 MCP 스킬로 가기도 하고 CLI 명령으로 가기도 한다
엔터프라이즈 서버에서도 되나 34:00Cloud, Server, Enterprise, 무료 요금제 모두 가능하다. 단 컨텍스트 보강과 에이전트 분석은 무료 요금제에 없다

요금제별 제공 범위는 발표 시점의 설명이다. 실제 적용 전에 Sonar 문서로 확인하자.

14

결론 40:10

  • 비밀 키는 모델에 닿기 전에 막힌다.
  • 이미 있는 이슈는 터미널에서 바로 불러와 고칠 수 있다.
  • 새로 시키는 작업에는 더 엄격한 검증 층이 감싸진다.

두 발표자의 메시지를 겹쳐 보면 이렇다. 에이전트가 "고쳤다"고 말하는 것은 완료가 아니다. 독립된 검사가 증거를 내놓아야 완료다. 그 검사는 사람이 나중에 하는 것이 아니라 에이전트가 코드를 건드리는 순간마다 자동으로 돌아야 한다. 그리고 어떤 검사도 혼자서는 증명이 아니므로, 여러 겹을 쌓고 마지막 결정은 사람이 쥔다.

15

핵심 정리

  1. 완료는 증거와 함께다. 리뷰할 수 있는 diff와 도구가 남긴 결과가 있어야 "끝났다"고 말한다.
  2. 에이전트의 자기 비판은 독립된 검증기가 아니다. 컴파일러, 테스트, 정적 분석에 따로 묻고 반증을 찾는다.
  3. 격리는 정확성이 아니다. 실행 층은 무엇을 할 수 있는지, 산출물 층은 결과가 옳은지를 본다. 둘 다 필요하다.
  4. 검사 규칙은 스킬, MCP, 훅으로 루프 안에 넣는다. 사람은 의도, 예외, 출시 결정을 쥔다.
  5. 발표자가 인용한 설문: AI가 쓴 코드 42%, 믿지 않는 개발자 96%, 완전히 검증하는 개발자 절반 미만. 병목은 검증이다.
  6. Sonar의 사이클은 생성, 안내, 검증, 해결이다. 안내는 컨텍스트 보강, 검증은 에이전트 분석이 맡는다.
  7. 검증은 CI(바깥 루프)보다 IDE와 터미널(안쪽 루프)에서 먼저 끝내야 왕복이 준다.
  8. 비밀 키 차단 훅은 도구 호출과 프롬프트 제출을 지킨다. 다른 경로로는 우회될 수 있으니 한 겹으로만 믿지 않는다.
  9. 편집 직후 훅은 바뀐 코드에서 새 문제가 생겼는지만 본다. 기존 문제까지 대신 고치려 들지 않는다.
  10. S8702처럼 에이전트 워크플로 전용 규칙이 있다. 명령줄 인자가 쿼리까지 그대로 흐르는 코드가 대표 사례다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1도입부 발표자가 말한 "완료"의 정의는?
리뷰할 수 있는 diff와 도구가 남긴 증거가 함께 있는 상태. "고쳤습니다"라는 말만으로는 완료가 아니다.
Q2코딩 에이전트의 흔한 실패 세 가지는?
맥락 부족, 국소 수정이 전역 불변 조건을 깨는 것, 검증용으로 만든 테스트가 같은 오해를 되풀이하는 것.
Q3실행 층과 산출물 층은 각각 어떤 질문에 답하나?
실행 층은 에이전트가 무엇을 할 수 있는가(도구, 범위, 승인). 산출물 층은 나온 결과가 받아들일 만한가(테스트, 분석, 정책, 의도).
Q4"샌드박스는 쓰기를 가둘 수 있어도 쿼리가 안전하다고 증명하지 못한다"는 말의 뜻은?
격리는 행동 범위를 제한할 뿐 결과의 정확성을 보장하지 않는다. 그래서 경계가 다른 검사를 여러 겹 쌓아야 한다.
Q5Sonar 설문에서 42%, 96%, 절반 미만은 각각 무엇인가?
커밋된 코드 중 AI가 썼거나 도운 비율 42%, AI 코드를 완전히 믿지 않는 개발자 96%, 머지 전에 완전히 검증하는 개발자 절반 미만. 모두 발표자가 인용한 수치다.
Q6에이전트 중심 개발 사이클의 네 단계와 SonarQube가 맡는 세 단계는?
생성, 안내, 검증, 해결. 생성은 아무 도구나 쓰고, 안내, 검증, 해결을 SonarQube가 맡는다.
Q7안쪽 루프와 바깥 루프의 차이는?
바깥 루프는 푸시 후 CI 파이프라인에서 검증한다. 안쪽 루프는 IDE와 터미널에서 생성 직후 검증한다. 안쪽에서 끝내면 실패하고 되돌아오는 왕복이 준다.
Q8실습 프로젝트의 SQL 인젝션은 왜 위험한가?
명령줄 인자가 f-string에 그대로 들어가 쿼리로 실행된다. 명령줄 인자를 넣을 수 있는 사람이 데이터베이스를 조작할 수 있다.
Q9비밀 키 차단 훅이 우회될 수 있는 경우는?
훅은 도구 호출과 프롬프트 제출 시점에 걸린다. 에이전트가 파일을 읽는 스크립트를 따로 만들어 실행하는 식으로 그 경로를 피하면 훅이 안 돌 수 있다고 발표자가 인정했다.
Q10편집 직후 훅이 기존 이슈를 발견했을 때 하는 일은?
기존 이슈가 있다고 알려 주되 대신 고치려 하지 않는다. 바뀐 코드에서 새 문제가 생겼는지만 검사한다.
Q11컨텍스트 보강과 에이전트 분석은 각각 언제 움직이나?
컨텍스트 보강은 과제를 시작하기 직전에 규칙과 아키텍처를 넣어 준다. 에이전트 분석은 파일을 쓰거나 고친 직후에 서버 쪽 분석을 돌린다. 둘 다 무료 요금제에는 없다.
