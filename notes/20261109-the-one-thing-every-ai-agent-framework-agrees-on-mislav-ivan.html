프레임워크보다 실행 경계를 먼저 정하라

에이전트 프레임워크들은 거의 모든 것에서 서로 다르다. 그런데 에이전트가 만든 코드를 격리된 샌드박스에서 돌려야 한다는 점에는 모두 동의한다. 발표자는 그래서 프레임워크보다 코드를 어디서 돌릴지를 먼저 정하라고 말한다.

원본 영상: The One Thing Every AI Agent Framework Agrees On 발표: Mislav Ivanda (Daytona 개발자 경험 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 사례와 날짜는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Claude Agent SDK, AG2, CrewAI, bubblewrap)은 알려진 이름으로 바로잡았다. 자막은 14:10 무렵 끊겨 마지막 문장을 다 담지 못했다. 발표자는 샌드박스를 파는 Daytona 소속이다. 샌드박스를 권하는 결론은 그 점을 감안해 읽자. mm:ss는 영상 위치다.

3분 요약
  1. Daytona를 여러 에이전트 프레임워크에 붙여 보니, 붙이는 모양은 달라도 속은 같은 세 줄이었다. 샌드박스를 만들고, 그 안에서 실행하고, 지운다.
  2. 이 프레임워크들은 에이전트의 정의, 구현 언어, 행동을 누가 정하는지까지 다르다. 그런데도 샌드박스에는 동의한다. 발표자는 이를 유행이 아니라 필요로 본다.
  3. 쓸모 있는 에이전트는 결국 코드나 셸 명령을 실행한다. 남는 질문은 그 코드를 어디서 돌리느냐다.
  4. 허용 목록은 모델이 무엇을 써야 하는지만 정하고, 무엇을 쓸 수 있는지는 막지 못한다.
  5. 내장 런타임은 스크립트를 가두지만, 스크립트가 부르는 도구는 런타임 밖 내 컴퓨터에서 돈다.
  6. 따로 떨어진 VM에서는 샌드박스가 뚫려도 앱은 뚫리지 않는다. 버리고 새로 띄우면 된다. 프레임워크들도 로컬 실행 같은 다른 선택지를 지우는 중이다.
  7. 프레임워크, 모델, 기능, 샌드박스 업체는 나중에 바꿀 수 있다. 실행 경계는 아키텍처 전체를 정해서 나중에 바꾸기 어렵다. 그러니 가장 먼저 고른다.
01

세 줄짜리 공통점 00:50

발표자 Mislav Ivanda는 Daytona의 개발자 경험 엔지니어다. Daytona는 샌드박스 sandbox를 제공하는 회사다. 샌드박스는 바깥과 격리된 실행 환경이다. 안에서 무슨 일이 벌어져도 밖에 영향을 주지 않게 만든 곳이다.

발표자는 지난 1년 동안 샌드박스가 필요한 곳마다 Daytona를 붙였다. 에이전트 프레임워크, 코딩 에이전트 하네스, 워크플로 도구, 개발자용 제품 등이다. 그 과정에서 같은 패턴이 계속 보였다.

이 코드는 어느 프레임워크일까

발표자는 코드 한 장을 띄우고 어느 프레임워크인지 물었다. 청중은 LangChain, LangGraph, Google ADK를 말했다. 발표자는 어느 답이든 맞는다고 했다. 프레임워크마다 Daytona를 붙인 코드가 거의 구별되지 않았기 때문이다.

겉으로 붙이는 방식은 프레임워크마다 달랐다.

  • 어떤 곳에서는 도구 tool로 붙인다.
  • 어떤 곳에서는 따로 설치하는 외부 플러그인으로 붙인다.
  • 어떤 곳에서는 프레임워크의 샌드박스 클라이언트 클래스를 확장하고 내부 API를 다룬다.

하지만 속에서 하는 일은 모두 같은 세 줄이었다. 01:50

sandbox = provider.create()   # 1. 샌드박스를 만든다
result = sandbox.run(task)    # 2. 그 안에서 코드나 작업을 실행한다
sandbox.delete()              # 3. 샌드박스를 지운다

예시: 발표 슬라이드의 코드가 아니다. 세 단계를 보여 주려고 쓴 의사 코드이고, 함수 이름은 실제 SDK와 다르다.

02

거의 모든 것이 다른 프레임워크 02:10

이 세 줄이 같다는 게 이상한 이유가 있다. 이 프레임워크들은 대부분 서로 경쟁한다. 기본 개념에서도 거의 합의하지 않는다.

질문발표자가 정리한 답
에이전트란 무엇인가LangGraph: 따라 이동할 수 있는 그래프
CrewAI: 역할을 맡아 스스로 일하는 여러 에이전트
OpenAI Agents SDK: LLM을 감싼 루프
Claude Agent SDK: 완성된 제품을 통째로 준다. 조립하지 않고 그대로 쓴다
어떤 언어로 만드나주로 Python과 TypeScript로 갈린다
행동은 누가 정하나Mastra, LangGraph: 개발자가 워크플로와 실행 경로를 직접 정한다
CrewAI: 에이전트가 목표를 이루려고 스스로 정한다
거의 모든 것에 동의하지 않는 회사들이 한 가지에 동의한다면, 그건 유행이 아니라 필요일 것이다.발표자의 말을 옮김 · 03:30
03

코드는 어디서 돌리나 03:40

왜 다들 샌드박스에 동의할까. 발표자의 답은 이렇다. 에이전트로 쓸모 있는 일을 하다 보면, 에이전트가 코드를 실행하거나 셸 shell에 접근해야 하는 때가 반드시 온다.

그다음 질문은 "그 코드를 어디서 실행하나"다. 에이전트가 만든 코드가 어디까지 닿을 수 있는지 정하는 선을 실행 경계 execution boundary라고 한다. 발표자는 격리 수준을 세 단계로 나눈다.

방식대표 수단무엇을 막나어디가 새나
1. 로컬 + 허용 목록명령 허용 목록, 승인 창, 가로채기 훅목록에 없는 명령허용한 명령 하나로 거의 모든 일을 할 수 있다
2. 내장 런타임V8, QuickJS스크립트의 네트워크·파일 접근스크립트가 부른 도구는 런타임 밖에서 실행된다
3. 분리된 VM별도 컴퓨터를 API로 제어내 인프라, 네트워크, 파일 시스템 전체새더라도 앱까지 닿지 않는다 (발표자 주장)
04

1단계: 허용 목록과 승인 창 04:10

가장 기본적인 방식이다. 로컬에서 에이전트를 개발할 때 대부분 이렇게 쓴다.

  • 허용 목록 allow list: 실행해도 되는 명령을 미리 정해 둔다.
  • 승인 창 approval prompt: Claude가 "이 명령을 실행할까요?"라고 묻는다. 발표자는 대부분 읽지도 않고 "예"를 누른다고 했다.
  • 가로채기 훅 interception hook: 명령이 실행되기 직전에 끼어들어 검사한다.

허용한 명령 하나가 전부를 연다 04:40

Claude 에이전트에게 python -c를 허용했다고 하자. 이 명령은 뒤에 붙인 Python 코드를 그대로 실행한다. 그래서 에이전트는 이 명령 하나로 다음을 모두 할 수 있다.

  • 소켓을 열어 네트워크에 접속한다.
  • 파일 시스템을 고친다.
  • 아무 코드나 실행한다.
모델이 무엇을 써야 하는지는 정했지만, 무엇을 쓸 수 있는지는 정하지 않았다.발표자의 말을 옮김 · 05:00
모델이 공격자 손에 넘어가면 내 컴퓨터에 악성 명령을 실행할 뒷문을 열어 준 셈이다.
05

2단계: 내장 런타임 05:20

한 단계 나아간 방식이다. 코드 실행을 V8이나 QuickJS 같은 내장 런타임 embedded runtime 안으로 옮긴다. 내장 런타임은 앱 안에 넣어 쓰는 작은 코드 실행 엔진이다.

1단계보다는 낫다. 네트워크와 파일 시스템이 어느 정도 격리되기 때문이다.

빈틈: 도구는 런타임 밖에서 돈다 05:40

발표자는 이 빈틈이 1단계보다 더 알아채기 어렵다고 말한다. 흐름을 따라가면 이렇다.

  1. 에이전트에게 "DB 조회", "메일 보내기" 같은 도구가 있다.
  2. 에이전트가 이 도구들을 부르는 스크립트를 만든다.
  3. 그 스크립트를 내장 런타임 안에서 실행한다.
  4. 그런데 스크립트가 부른 도구는 런타임 밖, 내 컴퓨터에서 실제로 실행된다.
런타임 안 · 격리됨에이전트가 만든 스크립트네트워크와 파일 시스템이 막혀 있다
→
런타임 밖 · 격리 안 됨스크립트가 부른 도구DB 조회, 메일 보내기가 내 컴퓨터에서 실제로 실행된다

그래서 악의적인 에이전트는 직접은 못 해도 도구를 거쳐 행동할 수 있다. 발표자의 정리로는, 에이전트가 만든 연결 코드 glue code는 격리했지만 도구 호출 자체는 격리하지 않은 것이다. 06:20

에이전트는 메일 도구나 DB 조회 도구로 나쁜 일을 할 수 있다. "DB 삭제" 도구까지 있다면 무슨 일이 생길지 짐작할 수 있다.

V8과 QuickJS는 JavaScript 엔진이다. 발표자는 에이전트가 "Python 스크립트"를 만든다고 예를 들었지만, 요점은 언어가 아니다. 런타임 안의 코드가 부른 도구가 런타임 밖에서 실행된다는 점이 핵심이다.

06

3단계: 분리된 VM 06:40

발표자가 권하는 방식이다. 코드 실행에 따로 떨어진 컴퓨터나 가상 머신 VM, virtual machine을 쓴다.

  • API로 VM과 주고받는다.
  • VM을 만들고 끄는 수명 주기 lifecycle도 API로 다룬다.
  • VM은 내 인프라, 네트워크, 파일 시스템에 닿지 않는다.

샌드박스가 뚫려도 앱은 뚫리지 않는다 07:10

샌드박스가 뚫렸다고 앱이 뚫린 것은 아니다.발표 슬라이드의 문장. 자막이 뭉개져 앞뒤 설명으로 뜻을 살려 옮겼다 (추정)
1·2단계한 단계만 잘못돼도 앱 전체가 위험하다승인한 Python 명령이나 잘못 동작한 도구 호출이 앱을 통째로 건드린다
→
3단계잘못돼도 샌드박스 하나를 버리면 된다세상에서 가장 나쁜 코드를 돌려도 앱 로직에 닿지 못한다. 새 샌드박스를 띄우면 된다

발표자는 이런 VM 방식 샌드박스를 제공하는 Daytona 소속이다. 3단계를 권하는 대목은 그 점을 감안해 읽자.

07

프레임워크가 지우는 것 07:50

발표자는 자기 주장의 근거로 프레임워크들이 움직이는 방향을 든다.

프레임워크발표자가 말한 변화
CrewAI2026년 4월, 내 컴퓨터에서 코드를 돌리던 코드 인터프리터 도구를 없앴다. 지금은 전용 샌드박스 서비스를 쓰라고 안내한다
AG2예전의 로컬 코드 실행기를 은퇴시켰다. 새 샌드박스 코드 도구 클래스는 어떤 환경에서 실행할지 명시하게 한다
Claude Agent SDK기본으로 샌드박스를 쓴다. 다만 프로세스 수준 샌드박스 process-level sandboxing다. 리눅스의 bubblewrap 같은 도구로 하는 방식이다 08:30
OpenAI Agents SDK샌드박스 에이전트가 있다. 일부 샌드박스 업체와 Docker를 기본 지원한다. 로컬 실행도 허용하지만, 그 단점을 숨기지 않고 밝혀 둔다
MastraOpenAI Agents SDK와 비슷하다
추가가 아니라 삭제 09:10 프레임워크들은 샌드박스를 새로 넣는 게 아니다. 샌드박스는 원래 있었다. 바뀐 점은 그 밖의 선택지를 지우고 있다는 것이다.

이 사례들은 발표자가 고른 것이다. 이 노트에서 각 프레임워크의 문서나 변경 기록을 확인하지는 않았다.

08

샌드박스 쓰임의 변화 09:10

프레임워크의 방향이 바뀌는 동안, 샌드박스를 쓰는 방식도 함께 바뀌었다.

시기쓰는 방식샌드박스의 역할
처음 09:30에이전트가 필요할 때 띄워 코드나 작업을 돌리고 끈다잠깐 쓰고 버리는 실행기
모델이 똑똑해진 뒤 09:50에이전트 전체를 샌드박스 안에서 돌린다. 파일 시스템, 네트워크 등 모든 것을 맡긴다에이전트의 실행 환경
최근 10:00수천 개를 동시에 띄운다강화학습 reinforcement learning, 파인튜닝 fine-tuning, 사후 학습 post-training, 벤치마크, 문제를 나눠 푸는 하위 에이전트 sub-agent
09

"어떤 프레임워크?"는 틀린 질문 10:30

발표자도 "어떤 프레임워크를 골라야 하나요?"라는 질문을 자주 받는다. 발표자는 이 질문이 틀렸다고 본다.

이유는 두 가지다. 프레임워크를 비교할 때 보는 항목은 대부분 나중에 바꿀 수 있다. 반대로 바꾸기 어려운 것은 고를 때 잘 따지지 않는다.

나중에 바꿀 수 있는 것 11:00

항목어떻게 바꾸나 (발표자 설명)
프레임워크같은 언어라면 코딩 에이전트에게 리팩터링을 맡긴다. 개발자들이 늘 하는 일이다
모델과 프롬프트특정 모델에 맞춰 시스템 프롬프트를 다듬었다면 조금 까다롭다. 다시 조정하고 회귀 테스트 regression testing를 해야 하지만 충분히 할 수 있다
없는 기능평가 evals, 추적 tracing, 메모리 같은 기능은 직접 바이브 코딩 vibe coding하거나 외부 플러그인으로 붙인다
샌드박스 업체모두 같은 말을 쓴다. 만들고, 안에서 실행하고, 지운다. 업체마다 기능과 성능 차이는 있다 12:30
예외: 내구 실행 12:10 내구 실행 durable execution은 일부 프레임워크가 주는 기능이다. 발표자는 이 기능만은 쉽게 따라 만들 수 없다고 했다. 아키텍처에 영향을 주기 때문이다. Claude에게 시켜 오후 한나절에 만들 수 있는 일이 아니다.
10

나중에 못 바꾸는 것: 실행 경계 12:40

쉽게 바꿀 수 없는 것은 실행 경계다. 에이전트의 코드를 로컬에서 돌릴지, 외부 샌드박스에서 돌릴지 정하는 일이다.

이 선택은 시스템 아키텍처 전체를 정한다. 시스템의 다른 부분을 어떻게 만들지도 이 선택을 따라간다. 13:00

도구가 좋은 예다. 모든 것을 로컬에서 돌린다고 생각하고 도구를 만들면, 도구는 호스트와 앱 프로세스의 환경을 그대로 쓰게 된다. 파일 시스템도 분리 없이 직접 쓴다. 나중에 샌드박스로 옮기려면 이 도구들을 다시 짜야 한다.

POC 그대로 프로덕션까지 13:20 대부분 POC proof of concept 단계에서 로컬 실행으로 시작한다. 그리고 다시 돌아보지 않은 채 프로덕션까지 간다. 문제가 터지면 이미 늦다. 발표자는 그 문제가 제품을 끝장낼 수도 있다고 경고한다.
11

결론 13:50

발표자의 결론은 하나다. 프레임워크를 고르기 전에 실행 경계부터 고른다.

프레임워크는 의견이다. 그리고 경계는…발표자의 마지막 문장 "Frameworks are opinions and the boundaries…" · 14:10

자막은 14:10 무렵 이 문장 중간에서 끊기고, 15:30에 같은 말의 조각만 다시 나온다. 문장의 끝은 이 노트에서 확인할 수 없다. 앞의 흐름으로 보면 "프레임워크는 바꿀 수 있지만 경계는 바꾸기 어렵다"는 대비로 보인다 (추정).

발표 내용을 순서로 옮기면 1. 에이전트가 만든 코드를 어디서 실행할지 정한다.
2. 그 경계를 전제로 도구를 만든다.
3. 프레임워크, 모델, 샌드박스 업체는 나중에 바꿀 수 있는 선택으로 다룬다.
12

핵심 정리

  1. 프레임워크마다 샌드박스를 붙이는 모양(도구, 플러그인, 클래스 확장)은 달라도 속은 만들기, 실행, 지우기 세 줄이다.
  2. 프레임워크들은 에이전트의 정의, 구현 언어, 행동을 누가 정하는지에서 서로 다르다.
  3. 그런 경쟁자들이 동의하는 것은 유행이 아니라 필요라는 것이 발표자의 논리다.
  4. 쓸모 있는 에이전트는 결국 코드 실행이나 셸 접근이 필요하다. 남는 질문은 어디서 실행하느냐다.
  5. 허용 목록, 승인 창, 훅: python -c 하나만 허용해도 사실상 모든 것을 허용한 셈이다.
  6. 내장 런타임(V8, QuickJS): 스크립트는 갇히지만 도구는 내 컴퓨터에서 실행된다.
  7. 분리된 VM: 샌드박스가 뚫려도 앱은 뚫리지 않는다. 버리고 새로 띄운다.
  8. 발표자에 따르면 CrewAI, AG2 등은 로컬 실행 도구를 없애고 샌드박스를 요구하는 쪽으로 가고 있다.
  9. 샌드박스의 쓰임은 잠깐 쓰는 실행기에서 에이전트의 실행 환경으로, 다시 수천 개 동시 실행으로 넓어졌다.
  10. 프레임워크, 모델, 기능, 샌드박스 업체는 바꿀 수 있다. 실행 경계는 아키텍처를 정하므로 프레임워크보다 먼저 고른다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 여러 프레임워크에서 본 공통 세 줄은?
샌드박스 만들기, 그 안에서 코드나 작업 실행하기, 샌드박스 지우기. 도구, 플러그인, 클래스 확장처럼 붙이는 모양만 달랐다.
Q2프레임워크들이 서로 동의하지 않는 세 가지는?
에이전트란 무엇인가, 어떤 언어로 만드나(Python과 TypeScript), 에이전트의 행동을 누가 정하나(개발자가 워크플로를 정의하는가, 에이전트가 스스로 정하는가).
Q3LangGraph, CrewAI, OpenAI Agents SDK는 각각 에이전트를 무엇으로 보나?
LangGraph는 따라 이동할 수 있는 그래프, CrewAI는 역할을 맡아 스스로 일하는 여러 에이전트, OpenAI Agents SDK는 LLM을 감싼 루프로 본다.
Q4허용 목록에 python -c를 넣으면 왜 위험한가?
이 명령 하나로 소켓 열기, 파일 수정, 임의 코드 실행이 모두 가능하다. 모델이 무엇을 써야 하는지만 정했고, 무엇을 쓸 수 있는지는 막지 못했다.
Q5내장 런타임(V8, QuickJS) 방식의 빈틈은?
스크립트는 런타임 안에서 돌지만, 스크립트가 부르는 도구(DB 조회, 메일 보내기)는 런타임 밖 내 컴퓨터에서 실행된다. 연결 코드만 격리되고 도구 호출은 격리되지 않는다.
Q6분리된 VM 방식을 가장 좋다고 하는 이유는?
샌드박스가 뚫려도 앱이 뚫린 것은 아니기 때문이다. 아주 나쁜 코드를 돌려도 앱 로직에 닿지 못하고, 샌드박스를 버리고 새로 띄우면 된다.
Q7발표자가 프레임워크의 방향을 보여 주려고 든 변화 두 가지는?
CrewAI가 2026년 4월 로컬 코드 인터프리터 도구를 없애고 샌드박스 서비스를 안내한 것. AG2가 로컬 실행기를 은퇴시키고 실행 환경을 명시하게 하는 클래스를 둔 것. Claude Agent SDK의 기본 샌드박스, OpenAI Agents SDK의 샌드박스 에이전트도 함께 들었다.
Q8"프레임워크들은 샌드박스를 추가하는 게 아니라 ○○○을 지우고 있다." 빈칸은?
다른 선택지. 샌드박스는 원래 있었고, 로컬 실행 같은 대안을 없애는 중이다.
Q9샌드박스 쓰임이 넓어진 세 단계는?
잠깐 띄웠다 끄는 실행기, 에이전트 전체를 돌리는 실행 환경, 강화학습·사후 학습·벤치마크·하위 에이전트를 위해 수천 개를 동시에 띄우는 쓰임.
Q10나중에 바꿀 수 있는 것 네 가지와, 기능 중 예외 하나는?
프레임워크(같은 언어일 때), 모델과 프롬프트, 평가·추적·메모리 같은 기능, 샌드박스 업체. 예외는 내구 실행이다. 아키텍처에 영향을 줘서 쉽게 따라 만들 수 없다.
Q11실행 경계를 나중에 바꾸기 어려운 이유는?
시스템 아키텍처 전체와 다른 부분을 만드는 방식을 정하기 때문이다. 로컬을 전제로 하면 도구가 호스트의 파일 시스템과 프로세스 환경을 분리 없이 쓰게 짜인다.
Q12발표자가 경고한 흔한 실수는?
POC 때 로컬 실행으로 시작해서 다시 돌아보지 않고 프로덕션까지 가는 것. 문제가 터진 뒤에는 늦고, 제품을 끝장낼 수도 있다.

용어 정리

용어뜻
샌드박스Sandbox. 바깥과 격리된 실행 환경. 안에서 무슨 일이 생겨도 밖에 영향을 주지 않게 만든 곳
샌드박스 업체Sandbox provider. 샌드박스를 API로 만들고 지우게 해 주는 서비스. Daytona가 여기에 속한다
에이전트 프레임워크에이전트를 만들 때 쓰는 라이브러리. LangGraph, CrewAI, OpenAI Agents SDK, Mastra 등
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀
실행 경계Execution boundary. 에이전트가 만든 코드가 어디까지 닿을 수 있는지 정하는 선. 코드를 어디서 실행하느냐로 정해진다
허용 목록Allow list. 실행해도 되는 명령을 미리 적어 둔 목록
승인 창Approval prompt. 명령을 실행하기 전에 사람에게 "실행할까요?"라고 묻는 창
가로채기 훅Interception hook. 명령이나 도구 호출이 실행되기 직전에 끼어들어 검사하는 코드
내장 런타임Embedded runtime. 앱 안에 넣어 쓰는 작은 코드 실행 엔진. V8, QuickJS 같은 JavaScript 엔진이 예다
연결 코드Glue code. 여러 도구를 이어 붙여 부르는 짧은 코드
VMVirtual machine. 한 컴퓨터 안에서 따로 돌아가는 가상의 컴퓨터
프로세스 수준 샌드박스Process-level sandboxing. 운영체제 기능으로 한 프로세스가 볼 수 있는 파일과 네트워크를 제한하는 방식. 리눅스의 bubblewrap이 예다
내구 실행Durable execution. 작업이 중간에 멈춰도 상태를 저장해 두었다가 이어서 실행하게 하는 기능
사후 학습Post-training. 이미 학습된 모델을 추가 데이터나 보상 신호로 더 다듬는 단계. 강화학습, 파인튜닝이 여기에 쓰인다
하위 에이전트Sub-agent. 큰 에이전트가 일을 나눠 맡기려고 띄우는 작은 에이전트
회귀 테스트Regression testing. 바꾼 뒤에도 원래 잘 되던 것이 그대로 되는지 확인하는 테스트
바이브 코딩Vibe coding. AI에게 말로 시켜 코드를 빠르게 만드는 방식
POCProof of concept. 아이디어가 되는지 확인하려고 빨리 만든 시제품
