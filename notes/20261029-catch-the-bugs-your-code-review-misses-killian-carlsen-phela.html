리뷰가 놓치는 버그를 잡는 법

에이전트가 쓴 코드는 테스트를 통과해도 기존 기능을 깨뜨리거나 팀 규칙을 어길 수 있다. 이 워크숍은 Sonar의 코드 변경 검증 에이전트 Gitar로 PR 세 개를 직접 검증하며, 그런 버그를 어떻게 잡고 고치는지 보여 준다.

원본 영상: Catch the Bugs Your Code Review Misses 발표: Killian Carlsen-Phelan, Taylor Luttrell-Williams (Sonar 개발자 콘텐츠 팀)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 제품 이름은 자막에서 Guitar, Git Guardian, Git Tarr, Gittar, Git Tower 등으로 뭉개졌다. 발표에 나온 설정 폴더 이름 .gitar/를 근거로 Gitar로 통일했다. 수치와 주장은 모두 발표자가 말한 것이고 따로 확인하지 않았다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트는 사람이 읽을 수 있는 것보다 많은 코드를 빠르게 낸다. 그 결과 리뷰 대기열이 쌓이고 프로덕션 장애가 늘었다고 발표자는 말한다.
  2. 정적 분석은 SQL 인젝션 같은 문제를 잘 잡는다. 하지만 코드의 의도와 비즈니스 로직이 맞는지는 판단하지 못한다. 두 층을 함께 써야 한다.
  3. 실습 1: 티켓 양도 기능은 테스트를 통과했다. 그런데 원래 구매자가 환불하면 친구의 티켓까지 무효가 되는 버그가 diff 밖 orders.py에 숨어 있었다.
  4. 실습 2: "보여 주는 가격은 항상 총액"이라는 회사 규칙을 .gitar/ 폴더의 문서와 규칙으로 알려 주면, 리뷰가 그 규칙을 어긴 변경을 찾는다.
  5. 실습 3: CI가 실패한 PR에서 Gitar가 로그를 읽고 원인을 찾고, 고친 뒤, 테스트가 통과하면 자동으로 머지한다.
  6. 그 밖에 Jira·Linear 티켓과 대조하기, 피드백에서 팀 관례 배우기, 여러 저장소·여러 PR 사이의 충돌 찾기를 소개했다.
01

누가 에이전트의 코드를 검증하나 04:10

AI 코딩 에이전트는 코드를 빠르게, 많이 쓴다. Taylor는 여기서 질문을 던진다. 에이전트가 내보내는 코드를 실제로 누가, 혹은 무엇이 검증하고 있나.

검증할 것은 보안, 유지보수성, 신뢰성만이 아니다. 기능이 돌아가는 것을 넘어 실제로 맞는 일을 하는지도 봐야 한다.

문제 1 · 리뷰 병목 05:20

팀 인원은 그대로인데 에이전트가 만든 변경은 계속 늘어난다.

  • 리뷰 대기열이 길어진다
  • 머지를 기다리는 PR이 방치된다
  • 리뷰는 아무도 맡고 싶지 않고, 맡을 시간도 없는 일이 된다
문제 2 · 프로덕션 장애 증가 05:50

장애는 변경 속도에 비례해 늘어난다.

  • 에이전트는 팀이 설계한 아키텍처를 늘 지키지는 않는다
  • 회사의 코딩 표준과 가이드라인을 모른다
  • 필요한 맥락이 없기 때문이다

Taylor의 결론은 이렇다. 해법은 사람보다 빠르고, 사람의 리뷰보다 나아야 한다. 그래야 에이전트가 들여오는 변경 속도를 따라갈 수 있다.

02

Gitar가 내세우는 것 06:40

Taylor는 Gitar를 코드 변경 검증 에이전트code change verification agent라고 소개한다. 대상은 에이전트 수준의 양과 속도로 코드를 내보내야 하는 플랫폼·엔지니어링 팀이다. 정적 분석 도구 SonarQube에 변경의 맥락과 의도를 이해하는 층을 더하는 제품이라고 설명한다.

내세운 특징내용
신호 대 잡음비거짓 경보를 줄여 실제로 고쳐지는 비율을 높이고 토큰 비용도 줄인다
CI 실패 진단진짜 고장과, 가끔 실패하는 테스트나 인프라 문제로 생긴 잡음을 구분한다
자동 수정찾은 문제를 직접 고친다. 자동화 수준과 사람의 개입 정도는 팀이 정한다
반복모든 변경이 CI를 통과할 때까지 고치고 다시 확인한다
투명성리뷰 과정과 CI를 분석 대시보드로 보여 준다

리뷰가 쓰는 맥락 08:30

  • PR의 diff, 설명, 댓글
  • CI 로그
  • 프로젝트별 지시 문서
  • 저장소에 직접 써 둔 규칙

동작 흐름 09:40

  1. PR이 열리면 리뷰 엔진이 시작된다.
  2. 위의 맥락을 모아 문제를 찾는다.
  3. 찾은 문제와 수정안을 PR 댓글로 남긴다.
  4. 사람이 댓글로 답하며 처리한다. 설정을 켜 두면 자동으로 고치고 머지한다.
모든 거짓 경보는 토큰을 쓰고, 의도치 않은 변경을 낼 위험이 있는 수정 시도 하나다.Taylor Luttrell-Williams, 09:10 (뜻을 옮김)

발표자 두 사람은 Gitar를 파는 Sonar 소속이다. "신호가 높다", "PR당 추가 비용 없이 반복한다" 같은 주장은 제품 홍보라는 점을 감안해 읽자. 워크숍 내내 수치로 된 근거는 나오지 않았다.

  1. app.gitar.ai에 로그인하고 GitHub 앱으로 설치한다.
  2. 워크숍 저장소를 포크한다. 자막상 주소는 github.com/sonarsamples/aie-new-york-workshop-guitar다(추정, 철자 확인 필요). 소유자는 Gitar 앱을 설치한 조직으로 고른다.
  3. 포크할 때 "main 브랜치만 복사"를 꼭 끈다. 실습마다 브랜치가 따로 있다.
  4. 포크한 저장소의 Actions 탭에서 워크플로를 켠다. GitHub는 포크의 워크플로를 기본으로 꺼 둔다.
  5. Gitar 대시보드의 Settings → Configurations → Repositories에서 포크가 보이는지 확인한다.

05

실습 1: diff 밖의 버그 15:40

첫 PR은 아무 설정 없이 Gitar의 기본 리뷰만 본다.

변경 내용

티켓을 산 사람이 친구에게 양도하는 기능을 더한다. 두 장을 사서 한 장을 보내면 둘 다 입장할 수 있어야 한다.

  • 없는 티켓은 양도할 수 없다
  • 이메일 주소가 올바르지 않으면 안 된다
  • 무효가 된 티켓은 양도할 수 없다
  • 테스트도 함께 넣었고, CI는 초록이다
Gitar가 찾은 것 18:00

원래 구매자가 양도한 뒤에도 환불하고 티켓을 무효로 만들 수 있다. 구매자가 주문을 취소하면 친구가 받은 티켓도 같이 취소된다.

왜 놓치기 쉬운가: "무효 티켓은 양도 못 한다"는 테스트는 있었지만, 반대 방향(양도 후 취소)은 없었다. 문제의 위치도 PR이 고친 파일이 아니라 기존 orders.py다.

diff만 보는 리뷰어는 새 코드에서 잘못을 찾을 수 없다. 기존 취소 기능이 어떻게 동작하는지 알아야 무엇이 깨지는지 보인다. Killian은 에이전트로 코드를 쓸수록 앱이 커져서, 모든 함수의 동작을 사람이 기억하기는 거의 불가능하다고 말한다. 그래서 새 기능을 기존 기능과 비교해 보는 리뷰어가 필요하다는 주장이다.

고치는 방법 20:00

  1. 리뷰 댓글의 Apply fix 버튼을 누르거나, PR에 gitar fix라고 댓글을 단다.
  2. Gitar가 PR에 새 커밋을 올린다.
  3. 새 커밋을 다시 검증한다. 워크플로에서 부작용이 생기면 초록이 될 때까지 계속 고친다.

결과 26:10: Gitar는 orders.py에 양도된 티켓을 막는 검사를 하나 더했다. 검증을 마치고 PR을 승인했다.

Killian은 이 반복이 "PR당 추가 비용 없이" 이뤄진다고 말했다. 요금 체계에 대한 제품 회사 쪽의 설명이다.

06

실습 2: 코드에 없는 규칙 22:00

팀마다 코드에 드러나지 않는 규칙이 있다. 시니어 엔지니어의 머릿속, 위키, Confluence 페이지에 있다. 이런 규칙은 코드가 올바른지와는 관계가 없다.

두 번째 PR은 티켓마다 3.50달러의 서비스 수수료를 붙인다. 50달러짜리 티켓이면 결제할 때 53.50달러가 된다. 그런데 이 가상 회사에는 "고객에게 보여 주는 가격은 모두 총액이다"라는 규칙이 있다.

규칙을 리뷰에 알려 주는 두 폴더 23:20

폴더하는 일예
.gitar/reviewMarkdown 문서로 원하는 만큼 맥락과 비즈니스 로직을 넣는다. Gitar가 이 내용에 맞춰 리뷰 방향을 잡는다"모든 가격은 총액으로 보여 준다"
.gitar/rulesPR이 어떤 조건을 만족하면 규칙이 발동해 정해진 동작을 한다가격 관련 파일이 바뀌면, 바뀐 고객 노출 필드를 나열하고 각각 총액인지 알려 준다

폴더 이름은 자막에 들린 대로 적었다. 정확한 이름은 워크숍 저장소에서 확인하자.

Killian이 즐겨 쓰는 규칙 예 24:40 동료와 Slack에서 새 기능을 논의했다고 하자. "PR 설명에 Slack 링크를 붙이면, 그 대화를 읽고 내 코드가 논의 내용과 맞는지 확인하라"는 규칙을 만들어 둘 수 있다. 링크를 붙일 때마다 규칙이 발동한다.

결과 25:10: Gitar는 규칙대로 가격 필드를 나열하고, 각 필드가 총액인지 아닌지 표시하고, 위반을 찾아냈다. Killian은 이것이 엔지니어링 버그는 아니라고 강조한다. 코드만 보면 틀린 곳이 없다. 이 회사의 규칙에 비춰 볼 때만 문제다. 이 PR은 머지하지 않고 둔다.

07

실습 3: CI 실패와 자동 머지 26:30

세 번째 실습은 PR을 연 순간부터 머지까지 전 과정을 자동으로 돌린다. 저장소 README에 같은 설정 방법이 적혀 있다.

GitHub 설정 27:00

  1. 저장소 설정에서 Allow auto-merge를 켠다. GitHub의 자동 머지 기능을 쓸 수 있게 된다.
  2. Rulesets에서 새 브랜치 규칙 묶음을 만든다. 이름은 자유롭게 짓고, 상태를 Active로 둔다.
  3. 대상은 기본 브랜치로 정한다.
  4. Require status checks to pass를 켜고 검사 항목에 test를 넣는다. 테스트가 통과해야만 자동 머지가 된다.

실패한 PR 28:30

이 PR은 티켓 스캔 방식을 리팩터링한다. 티켓이 티켓 페이지 URL을 가리키게 바꾸고 기존 로직을 조금 정리했다. 그런데 테스트 하나가 실패했다.

실패한 테스트: 티켓은 두 번 스캔할 수 없다 리팩터링 중에 이 검사가 빠졌다. 한 번 쓴 티켓을 다시 스캔해도 200(성공)이 돌아온다. 그러면 친구들이 같은 티켓으로 줄줄이 들어올 수 있다. 단순하지만 놓치기 쉬운 실수다.

Gitar의 리뷰는 CI 결과를 직접 읽는다 29:20. "CI 실패. 체크인 게이트에서 테스트 하나가 실패. 이미 쓴 티켓을 다시 스캔하면 200을 돌려줌"이라고 원인을 짚는다.

Killian은 이 과정이 개발자에게 가장 귀찮은 일 중 하나라고 말한다. 로그를 열어 무엇이 실패했는지 보고, 원인을 찾고, 로컬에서 고치고, 푸시하고, 긴 파이프라인을 기다린다. 또 실패하면 처음부터 다시 한다. 다른 엔지니어에게 리뷰를 계속 재촉해야 할 때도 있다.

자동 적용과 자동 머지 30:30

PR 댓글하는 일
gitar auto apply on사람이 매번 승인하지 않아도 Gitar가 수정을 계속 푸시한다
gitar auto merge on더 찾을 문제가 없고 파이프라인이 모두 통과하면 머지한다

이후 Gitar는 수정을 푸시하고, 검증하고, 머지까지 몇 분 안에 마친다고 Killian은 설명한다. 워크숍에서는 머지가 끝나는 장면까지 보여 주지 않았다.

댓글로 켠 것은 워크숍용이다. 다른 PR까지 자동 머지되지 않게 하려는 것이다. 실제로는 Gitar 대시보드에서 저장소별로 자동 승인과 자동 머지를 켠다. 테스트와 안전장치가 잘 갖춰진 저장소일수록 자동화를 넓게 열어도 된다는 것이 Killian의 설명이다.

PR을 그 PR이 구현하는 티켓과 대조한다. 변경이 깔끔한지만이 아니라 맞고 빠짐없는지 확인한다.

  • Slack 메시지

  • 각 리뷰 뒤에 어떤 규칙이 있고, 어디서 왔고, 왜 적용됐는지 보여 준다

혼자서는 깔끔하게 머지되지만 다른 저장소의 코드를 깨뜨리는 PR을 찾는다. Taylor는 분석하는 저장소 수에 제한이 없다고 말했다.

PR 간 분석 35:30

동시에 열려 있는 PR끼리 비교한다. 두 PR이 각각은 통과해도 함께 머지되면 프로덕션을 깨뜨릴 수 있다. 에이전트를 늘릴수록 커지는 위험이다.

대시보드에서 찾은 문제 하나를 열면 36:00 수정 방법, 문제가 생기는 위치, 그리고 왜 중요한지를 함께 보여 준다.

Taylor는 일부 기능은 엔터프라이즈 요금제에 있고 나머지는 Pro에 포함된다고 했다. 어느 기능이 어느 쪽인지는 자막에 나오지 않는다.

질의응답 37:00

질문은 자막에 잡히지 않았다. 답변으로 보아 외부 문서나 가이드라인을 리뷰에 넣는 방법을 물은 것으로 보인다.

개념답변 내용
MCP 연결Gitar는 MCP로 외부 맥락을 받아들일 수 있고, 통합을 직접 구성할 수 있다
Context아키텍처 가이드라인 같은 기준에 맞춰 코드를 리뷰하게 하는 기능
KnowledgeGitar 자신의 리뷰와 수정 방식을 조정하는 기능. "우리는 보통 이런 식으로 고친다"고 답하면 다음 수정에 반영한다

Knowledge에 외부 자료를 넣는 구체적인 방법은 발표자가 따로 확인해 알려 주겠다고 했다.

10

핵심 정리

  1. 에이전트가 코드를 쏟아내면서 리뷰 병목과 프로덕션 장애가 함께 늘었다고 발표자는 진단한다.
  2. 에이전트는 팀의 아키텍처, 코딩 표준, 가이드라인을 모른다. 맥락이 없기 때문이다.
  3. 정적 분석은 보안 문제를 잡고, 의도 검증은 비즈니스 로직의 어긋남을 잡는다. 둘은 서로를 대신하지 않는다.
  4. 테스트가 초록이어도 기존 기능과 새 기능이 부딪치는 버그는 남는다. 그 버그는 diff 밖에 있을 수 있다.
  5. 테스트는 한 방향만 덮기 쉽다. "무효 티켓은 양도 불가"는 있었지만 "양도 후 취소"는 없었다.
  6. 코드에 없는 회사 규칙은 문서(.gitar/review)와 조건부 규칙(.gitar/rules)으로 리뷰에 알려 준다.
  7. 규칙 위반은 코드 오류가 아니어도 리뷰에서 걸러야 할 문제다. 총액 표시 규칙이 그 예다.
  8. CI 실패는 로그를 읽고, 고치고, 다시 돌리는 반복이다. Gitar는 이 반복을 자동으로 돈다고 주장한다.
  9. 자동 머지는 기본 브랜치의 필수 상태 검사 위에서만 안전하다. 자동화 수준은 저장소별로 정한다.
  10. 에이전트가 늘수록 PR 하나가 아니라 PR끼리, 저장소끼리의 충돌을 봐야 한다.
11

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 꼽은, 에이전트 코드가 늘면서 생긴 두 문제는?
리뷰 병목(인원은 그대로인데 변경이 늘어 대기열이 쌓인다)과 프로덕션 장애 증가(에이전트가 아키텍처와 표준을 모른다).
Q2SonarQube 같은 정적 분석이 잘하는 것과 못하는 것은?
여러 파일을 거치는 입력 흐름을 추적해 SQL 인젝션 같은 보안 문제를 잡는다. 하지만 PR의 의도를 추론해 비즈니스 로직이 맞는지는 판단하지 못한다.
Q3실습 1에서 Gitar가 찾은 버그는?
티켓을 친구에게 양도한 뒤에도 원래 구매자가 주문을 취소·환불할 수 있었다. 그러면 친구의 티켓도 무효가 된다.
Q4그 버그를 diff만 보는 리뷰어가 놓치기 쉬운 이유는?
문제가 PR이 고친 코드가 아니라 기존 orders.py의 취소 로직에 있었다. 기존 기능의 동작을 알아야만 보인다.
Q5Gitar에게 수정을 맡기는 두 가지 방법은?
리뷰 댓글의 Apply fix 버튼을 누르거나, PR에 gitar fix 댓글을 단다.
Q6.gitar/review와 .gitar/rules는 어떻게 다른가?
review는 Markdown 문서로 맥락을 주어 리뷰 방향을 잡는다. rules는 PR이 조건을 만족할 때 발동해 정해진 동작을 한다.
Q7실습 2의 지적을 "엔지니어링 버그가 아니다"라고 한 이유는?
수수료를 더하는 코드 자체는 틀리지 않았다. "보여 주는 가격은 총액"이라는 회사 규칙에 비춰 볼 때만 문제가 된다.
Q8자동 머지를 위해 GitHub에서 켠 설정 두 가지는?
저장소의 Allow auto-merge, 그리고 기본 브랜치를 대상으로 test 상태 검사 통과를 요구하는 ruleset.
Q9auto apply와 auto merge의 차이는?
auto apply는 사람의 승인 없이 수정을 계속 푸시하게 한다. auto merge는 남은 문제가 없고 파이프라인이 통과하면 머지까지 한다.
Q10실습 3에서 리팩터링이 빠뜨린 검사는?
한 번 쓴 티켓은 다시 스캔할 수 없다는 검사. 빠지면 두 번째 스캔도 200(성공)을 돌려준다.
Q11저장소 간 분석과 PR 간 분석은 각각 무엇을 찾나?
저장소 간 분석은 혼자서는 깔끔히 머지되지만 다른 저장소를 깨뜨리는 PR을 찾는다. PR 간 분석은 동시에 열린 PR들이 함께 머지될 때의 충돌을 찾는다.
Q12왜 거짓 경보를 줄이는 것이 중요하다고 했나?
거짓 경보 하나는 토큰을 쓰고, 의도치 않은 변경을 낼 수 있는 수정 시도로 이어진다. 리뷰 과정에 잡음과 판단 부담만 더한다.
