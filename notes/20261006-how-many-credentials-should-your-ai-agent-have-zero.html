AI 에이전트에게 자격 증명은 몇 개 필요한가. 0개다.

에이전트를 오래 혼자 돌리려면 안전해야 한다. 발표자는 안전을 "작업의 의도에 맞게 샌드박스를 짓는 일"로 정의한다. 샌드박스 안에는 자격 증명을 두지 않고, 모든 도구 호출은 게이트웨이 하나를 거치게 한다.

원본 영상: How Many Credentials Should Your AI Agent Have? Zero. 발표: Jim Clark (Docker 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았고, 확실하지 않으면 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자는 Docker 소속이고, 발표 후반에 Docker의 샌드박스 제품과 명령줄 도구 sbx를 소개한다. 설계 원칙은 일반적이지만, 제품 소개 부분은 그 점을 감안해 읽자.

3분 요약
  1. 에이전트는 이제 한 시간씩 혼자 일한다. 감독을 줄이려면 먼저 안전해야 한다.
  2. 안전의 첫 질문은 "이 일에 어떤 자원과 도구가 필요한가"다. 딱 그것만 들어 있는 샌드박스를 만들면 사고가 나도 피해 범위가 작다.
  3. 하네스 자체를 가두는 게 아니다. 하네스로 흘러드는 도구와 맥락을 가둔다.
  4. 뉴스룸처럼 역할을 나눈다. 인터넷을 마음껏 읽는 조사 담당은 발행 도구가 없고, 발행 담당은 네트워크가 없다. "걸러지지 않은 입력"과 "강한 도구"가 한곳에 있지 않게 한다.
  5. 한 시간짜리 코딩 작업에서 Git 서명 키가 필요한 시간은 약 2분이다. 커밋하지 않는 순간에는 서명 키가 샌드박스에 없어야 한다.
  6. 샌드박스마다 MCP 게이트웨이 주소 하나를 넣는다. 모든 도구 호출이 그곳을 거치니 통제 지점이 생기고, 하네스를 바꿔 끼워도 설정은 그대로다.
  7. 샌드박스 안의 자격 증명 수는 항상 0개가 정답이다. 신원은 게이트웨이가 기존 SSO와 교환해 처리한다. 이것이 Docker, Anthropic, Okta(추정)가 함께 미는 XAA다.
01

감독 없이 오래 돌리고 싶다 01:10

발표자는 이 발표 자료를 Claude Code로 만들었다고 밝힌다. 슬라이드는 Marp, 도표는 Mermaid MCP가 도왔다. 주제는 MCP 게이트웨이지만, 진짜 이야기는 AI 안전이다.

지난 6개월 동안 에이전트는 예상보다 훨씬 많은 일을 하게 됐다. 발표자는 더 이상 노트북 앞에 앉아 "예, 예, 예"를 누르고 싶지 않다. 좋은 과제의 기준도 바뀌었다. 감독을 거의 안 해도 되는 과제가 에이전트에게 맞는 과제다.

여기서 모순이 생긴다 감독을 안 할수록 에이전트가 무슨 짓을 할지 걱정된다. 그래서 오래 돌리고 싶은 마음이 곧 안전에 대한 고민으로 이어진다.

신문사에서 기자는 밖에서 정보를 모아 온다. 팩트체커가 확인하고, 그다음에 기사를 쓴다. 기자가 직접 웹사이트에 발행하지는 않는다. 역할을 나누는 것은 우리가 복잡한 시스템을 만들 때 늘 하던 일이다.

슬라이드 전체에 큰 상자를 그리면, 그 "하나의 에이전트"는 발행 도구도 있고 팩트체크 도구도 있고 한때 인터넷 전체도 읽는다. 하지만 각 순간을 따로 보면 걸러지지 않은 입력을 마음껏 읽는 능력과 우리 도구로 무언가를 실행하는 능력이 한 샌드박스에 같이 있지 않다. 이 위험한 조합을 깨는 것이 목적이다.

이야기 2: 서명 키는 2분만 필요하다 08:40

두 번째 이야기는 발표자가 실제로 코딩 에이전트를 쓰는 방식이다. 에이전트에게 한 시간쯤 걸리는 긴 작업을 맡기고, 중간중간 커밋도 하게 한다.

일반화하면 에이전트가 지금 하려는 일의 의도를 안다면, 그 의도로 능력의 범위를 정한다. 이 원칙은 코딩 말고 다른 많은 작업에도 그대로 옮길 수 있다.

MCP 게이트웨이: 하나의 통제 지점 10:00

이 생각이 Docker 샌드박스 제품에서 MCP 게이트웨이를 노출하는 방식을 결정했다. 샌드박스를 만들 때 하네스를 넣고, 거기에 게이트웨이 주소 하나를 함께 넣는다. 발표자가 든 예는 내부 주소 mcp.gateway.docker.internal 같은 것이다. 모든 하네스가 같은 주소를 보고, 자원을 가져오는 요청과 도구 호출이 전부 이 한 지점을 지난다.

이렇게 하면 얻는 것

  • 통제 지점이 생긴다. 어떤 도구, 자원, 프롬프트를 어느 샌드박스에 줄지 게이트웨이가 정한다. 샌드박스 설정이 곧 "여기서 MCP로 할 수 있는 일"의 범위가 된다.
  • 하네스가 MCP 설정에서 자유로워진다. Codex에 한 방식으로, Claude Code에 다른 방식으로 MCP를 따로 설정할 필요가 없다. 하네스는 샌드박스의 매개변수 하나가 된다. 하네스를 꽂고, 필요한 MCP를 꽂고, 네트워크 규칙을 주면 끝이다.
  • 자격 증명을 관리할 자리가 생긴다. 다음 절의 주제다.

자격 증명은 몇 개? 0개 11:50

샌드박스 안에 자격 증명이 몇 개 있어야 하는가. 정답은 항상 0개다. 거기 있어서는 안 된다.발표자의 말을 옮김 11:50

자격 증명credential은 비밀번호, API 키, 토큰처럼 "나는 이 권한이 있다"를 증명하는 비밀값이다. 샌드박스 안에 자격 증명이 하나도 없으면, 에이전트가 엉뚱한 일을 해도 그 비밀값이 새어 나가거나 오용될 일이 없다. 피해 범위가 그만큼 줄어든다.

자격 증명은 샌드박스 바깥, 즉 게이트웨이 쪽에서 다룬다. 에이전트는 게이트웨이에 "이 도구를 써 달라"고만 하고, 실제 인증은 게이트웨이가 한다.

08

XAA: 기존 SSO를 에이전트에 잇는다 12:20

발표자는 Docker, Anthropic, Okta(추정)가 함께 추진하는 XAA를 소개한다. 자막에는 "cross app application"으로 들리는데, 알려진 이름은 Cross App Access로 보인다. 자격 증명을 샌드박스 밖에서 다루는 것이 왜 중요한지 보여 주는 사례다.

지금 회사의 상황

회사에는 이미 신원 관리와 SSOSingle Sign-On, 즉 한 번 로그인으로 여러 서비스를 쓰는 체계가 있다. Notion, Atlassian, GitHub, Slack 같은 자원 서버는 이미 OAuth로 연결돼 있다. 그런데 이 투자가 아직 에이전트에게는 열려 있지 않다.

XAA가 하는 일

  1. 하네스, 샌드박스, 게이트웨이가 에이전트 신원을 정의한다. 이 에이전트는 누구를 대신해 일하는가.
  2. 게이트웨이가 회사의 신원 제공자identity provider와 신원 주장을 교환한다.
  3. 그 대가로 ID-JAG라는 인가 허가authorization grant를 받는다. 발표자에 따르면 최신 MCP 명세에 들어간 새 요소다.
  4. 이 허가로 에이전트는 회사가 이미 쓰던 인가 서버들에 접근한다.
새로운 것은 없다 기존 회사 네트워크의 투자를 그대로 쓴다. 다만 "허용할까요? 예, 예, 예" 하는 동의 화면을 반복하지 않고, 에이전트가 기존 자원 서버로 무엇을 하는지 한곳에서 관리하게 된다. 발표자는 이것을 큰 단순화라고 부른다.

발표자의 회사인 Docker가 이 명세의 공동 추진자다. 명세 이름과 참여사는 자막 기준이며 따로 확인하지 않았다.

도구를 점진적으로 공개한다 14:20

점진적 공개progressive disclosure는 스킬에서 배운 말이다. 필요할 때 필요한 만큼만 보여 준다는 뜻이다. 발표자는 같은 원칙을 MCP 게이트웨이에 적용한다. 도구, 자원, MCP를 샌드박스에 필요해질 때 조금씩 공개한다.

  • 맥락 크기가 작아진다. 작업 흐름 전체에서 MCP 50개를 쓴다고 해서 샌드박스 하나하나가 50개를 다 들고 있을 필요는 없다.
  • 풀 공간은 넓게, 샌드박스는 좁게. 에이전트에게 문제를 풀 여지는 주되, 각 샌드박스는 그 작업의 의도만 담는다.

결론과 데모 안내 16:10

발표자는 이것이 결국 에이전트를 컨테이너에 담는 일이라고 정리한다. Docker가 이 이야기를 하는 이유다. 핵심은 역할 분리다.

  1. 에이전트들이 맡은 역할을 나누고, 역할마다 컨테이너로 담는다.
  2. 어떤 하네스에도 자격 증명을 두지 않는다.
  3. 능력은 필요해질 때 점진적으로 공개한다.
  4. 샌드박스가 곧 작업의 의도를 표현한다.

더 오래 돌리더라도 더 잘 가둬져 있으면 조금 더 안심할 수 있다. 발표자는 "안전은 여기서 나온다"고 맺는다.

데모와 도구 17:00 Docker의 엔지니어링 부문 EVP Tushar Jain이 같은 날 오후 4시 다른 세션에서 샌드박스를 클라우드로 옮기는 법과 오케스트레이터 만드는 법을 라이브로 보여 준다고 했다. 발표에서 말한 모든 것은 명령줄 도구 sbx로 할 수 있고, brew install sbx로 설치한다고 안내했다.

제품 소개 부분이다. 발표자가 소속된 Docker의 도구이므로 그 점을 감안해 읽자.

12

핵심 정리

  1. 에이전트를 오래 혼자 돌리고 싶다면 안전이 먼저다. 감독을 줄이는 것과 안전은 한 쌍이다.
  2. 문제는 세 조각이다. 하네스(루프), 샌드박스(일하는 장소), MCP(바깥 도구와 맥락).
  3. 하네스는 자주 바뀌는 갈아 끼우는 부품이다. 가둘 대상은 하네스가 아니라 흘러드는 도구와 맥락이다.
  4. 안전의 첫 질문은 "이 일에 무엇이 필요한가". 필요한 것만 담은 샌드박스가 피해 범위를 줄인다.
  5. 뉴스룸처럼 역할을 나눈다. 걸러지지 않은 입력과 강한 도구를 같은 샌드박스에 두지 않는다.
  6. 한 시간 작업에서 서명 키는 2분만 필요하다. 의도에 맞춰 그 순간에만 능력을 준다.
  7. 샌드박스마다 MCP 게이트웨이 주소 하나를 넣는다. 통제 지점이 생기고 하네스는 MCP 설정에서 자유로워진다.
  8. 샌드박스 안 자격 증명은 항상 0개다. 인증은 게이트웨이가 한다.
  9. XAA는 기존 SSO와 OAuth 투자를 에이전트에 연결한다. ID-JAG라는 인가 허가로 동의 화면 반복 없이 한곳에서 관리한다.
  10. 도구는 점진적으로 공개한다. 오케스트레이터는 과제마다 하네스, MCP, 네트워크, 자원을 정해 샌드박스를 짓는다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 에이전트에게 맞는 과제의 기준으로 삼은 것은?
감독을 거의 하지 않아도 되는 과제. 그래서 감독을 줄이려면 안전이 먼저 필요해진다.
Q2발표자가 말한 세 조각은 무엇이고 각각 어떤 역할인가?
하네스는 맥락을 받아 도구 호출을 내는 루프, 샌드박스는 하네스가 일하는 장소, MCP는 바깥의 도구와 맥락을 끌어오는 연결이다.
Q3샌드박스로 가둬야 하는 것은 하네스인가?
아니다. 하네스는 단순한 루프라 이미 갇혀 있다. 가둬야 할 것은 하네스로 흘러드는 도구와 맥락이다.
Q4뉴스룸 이야기에서 조사 담당 샌드박스의 네트워크와 도구 설정은?
네트워크는 인터넷 전체 허용, 도구는 거의 없고 발행 MCP는 절대 없다. 결과는 자기만 쓰는 임시 폴더에만 쓴다.
Q5뉴스룸 이야기가 깨려는 "위험한 조합"은?
걸러지지 않은 입력을 마음껏 읽는 능력과 우리 도구로 무언가를 실행하는 능력이 한 샌드박스에 같이 있는 것.
Q6한 시간짜리 코딩 작업에서 Git 서명 키가 필요한 시간은 얼마이고, 그래서 어떻게 해야 하나?
약 2분. 커밋하지 않는 동안에는 서명 키가 샌드박스 안에 없어야 한다. 샌드박스는 작업의 의도를 본떠 만든다.
Q7MCP 게이트웨이를 두면 얻는 세 가지는?
통제 지점이 생긴다, 하네스가 MCP 설정에서 자유로워진다, 자격 증명을 관리할 자리가 생긴다.
Q8샌드박스 안에 자격 증명은 몇 개 있어야 하나? 이유는?
0개. 자격 증명이 없으면 에이전트가 잘못해도 비밀값이 새거나 오용될 일이 없어 피해 범위가 줄어든다.
Q9XAA에서 게이트웨이가 신원 제공자와 교환해 받는 것은?
ID-JAG라는 인가 허가. 이걸로 에이전트는 회사가 이미 쓰던 인가 서버에 접근한다. 기존 SSO 투자를 그대로 쓴다.
Q10점진적 공개를 MCP에 적용하면 무엇이 좋아지나?
맥락 크기가 작아진다. 흐름 전체에서 MCP 50개를 써도 샌드박스 하나가 50개를 다 들고 있을 필요가 없다.
Q11오케스트레이터가 과제를 샌드박스에 넣기 전에 정해야 할 네 가지는?
어떤 하네스를 넣을지, 어떤 MCP를 허용할지, 네트워크 규칙은 무엇인지, 어떤 자원과 작업 트리를 줄지.

용어 정리

용어뜻
에이전트 하네스Agent harness. 모델을 감싸 맥락을 넣고 도구 호출을 내보내는 루프. 실행 순서와 규칙을 정하는 틀
샌드박스Sandbox. 바깥과 격리된 작업 공간. 안에서 사고가 나도 밖으로 번지지 않게 한다
MCPModel Context Protocol. 에이전트가 바깥의 도구와 맥락을 표준 방식으로 끌어오는 연결 규약
MCP 게이트웨이샌드박스 안의 모든 MCP 요청이 거치는 단일 관문. 어떤 도구를 줄지 결정하고 인증을 대신한다
피해 범위Blast radius. 무언가 잘못됐을 때 영향이 미치는 범위
자격 증명Credential. 비밀번호, API 키, 토큰처럼 권한을 증명하는 비밀값
Git 서명 키커밋이 본인 것임을 암호학적으로 증명하는 데 쓰는 비밀 키
SSOSingle Sign-On. 한 번 로그인으로 여러 서비스를 쓰는 체계
OAuth비밀번호를 넘기지 않고 다른 서비스에 권한을 위임하는 표준
신원 제공자Identity provider. 사용자가 누구인지 확인해 주는 서비스. 회사 SSO의 중심
자원 서버Resource server. Notion, GitHub, Slack처럼 실제 데이터와 기능을 가진 서비스
XAA발표자는 "cross app application"으로 말함. 알려진 이름은 Cross App Access로 보인다. 회사 SSO를 에이전트에 연결하는 방식
ID-JAG발표자가 말한 인가 허가(authorization grant)의 이름. 신원 주장을 교환해 받으며, 최신 MCP 명세에 들어갔다고 한다
점진적 공개Progressive disclosure. 필요할 때 필요한 만큼만 보여 주는 설계 원칙
오케스트레이터Orchestrator. 여러 에이전트와 샌드박스를 지휘하며 과제를 배치하는 상위 프로그램
작업 트리Work tree. Git에서 실제 파일이 놓이는 작업 폴더
sbx발표자가 소개한 Docker의 명령줄 도구. 샌드박스 컨테이너를 만든다
