학습 노트 · AI Engineer 발표 · 2026-10-28 · 14분 · 영어 발표 한글 정리

공격자보다 먼저 로직 버그를 찾는 AI

패턴으로 검사하는 도구는 코드가 맞게 돌아가지만 의도가 틀린 로직 버그를 잡지 못한다. Sonar는 저장소 전체를 읽고 이런 버그를 찾아 검증하는 AI 에이전트를 만들었고, 이 발표는 그 구조와 실제 화면을 보여 준다.

원본 영상: AI That Hunts Logic Bugs Before Attackers Do 발표: Taylor Luttrell-Williams (Sonar, 개발자 콘텐츠 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말하거나 데모 화면에서 읽어 준 것이고, 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 확실하지 않은 것은 들린 대로 적고 (추정)을 붙였다. mm:ss는 영상 위치다.

발표자는 SonarQube를 만드는 Sonar 소속이고, 이 발표는 자사 신제품 소개다. 제품의 성능과 정확도에 대한 말은 그 점을 감안해 읽자.

3분 요약
  1. 패턴 기반 정적 분석(SAST)은 "위험한 모양의 코드"를 찾는다. 코드는 맞게 도는데 의도가 틀린 로직 버그는 설계상 보지 못한다.
  2. 에이전트가 코드를 빠르고 많이 내보내는 동안 펜테스트는 1년에 몇 번뿐이다. 발표자는 이 틈을 메울 검사가 필요하다고 말한다.
  3. Hunter Agent는 저장소 전체 지도를 먼저 그리고, 범주마다 전문 에이전트 3개를 띄운다. 찾은 것은 적대적 검증과 노이즈 게이트로 한 번 더 거른다.
  4. 찾는 범주는 셋이다. 접근 제어 깨짐, 비즈니스 로직, 인증·세션.
  5. 데모에서 간단한 Python 앱을 스캔하는 데 약 1시간이 걸렸고 이슈 46개가 나왔다. 예: 사용자가 자기 role 필드를 바꿔 관리자 확인을 통과한다.
  6. 결과는 기존 SonarQube 이슈 목록에 함께 뜬다. 담당자 지정, 상태 관리, 정기 스캔, Remediation Agent의 자동 수정으로 이어진다.
  7. 발표자의 권장: SAST·SCA와 Hunter Agent를 겹쳐 쓰는 이중 구조.
01

패턴 검사기가 못 보는 버그 00:50

발표자는 지금을 에이전트 시대로 본다. 코드가 에이전트의 속도와 양으로 배포된다. 그 결과 전보다 훨씬 많은 취약점이 실제 서비스 환경까지 간다고 말한다.

많은 팀이 쓰는 도구는 정적 애플리케이션 보안 테스트SAST다. 코드를 실행하지 않고 읽어서 위험한 패턴을 찾는다. 이 도구가 원래 다루지 않는 종류의 문제가 있다.

SAST가 묻는 것이 코드가 위험한 모양인가?알려진 패턴과 맞춰 본다
→
Hunter Agent가 묻는 것이 코드가 하는 일이 규칙에 맞나?서비스의 의도와 비교한다

발표자는 이것을 의도의 문제라고 부른다. 코드는 문법도 맞고 기능도 돌아간다. 그런데 그 동작이 비즈니스 규칙과 어긋난다. 이런 것을 로직 수준 취약점logic-level vulnerability이라 한다.

어떤 모양인지 보기 (예시)

# 예시: 발표에 나온 코드가 아니다
@app.patch("/me")
def update_me():
    user = current_user()
    user.update(**request.json)   # 요청 본문에 role이 있으면 그것도 저장된다
    return user

def is_admin(user):
    return user.role == "admin"

요청 본문에 {"role": "admin"}을 넣으면 누구나 관리자가 된다. 각 줄만 보면 이상한 데가 없다. 빠진 것은 "역할은 본인이 바꿀 수 없다"는 규칙이다. 발표 후반의 데모에서 실제로 이런 종류의 이슈가 나온다(07).

02

점검 주기와 공격 속도 02:00

발표자에 따르면 많은 회사가 펜테스트penetration test를 1년에 많아야 두 번, 많으면 분기에 한 번 한다. 펜테스트는 전문가가 공격자처럼 서비스를 뚫어 보는 점검이다.

  • 공격자는 어느 때보다 좋은 모델을 쓴다.
  • 에이전트가 만든 변경은 점점 짧은 간격으로 배포된다.
  • 취약점이 발견된 뒤 실제 공격 도구로 만들어지기까지의 시간도 빠르게 줄고 있다. 04:20

그래서 사람이 몇 달에 한 번 하는 점검 사이를 메울 새로운 종류의 에이전트가 필요하다는 것이 발표자의 주장이다.

발표자는 펜테스트를 "많아야 1년에 두 번"이라고 한 뒤 "분기에 한 번일 수도 있다"고 덧붙였다. 분기에 한 번은 1년에 네 번이라 "많아야 두 번"과 맞지 않는다. 차트에는 두 값을 다 넣었다.

03

Hunter Agent의 구조 02:40

Sonar가 이 틈을 메우려고 만든 것이 SonarQube Hunter Agent다. 일은 다섯 단계로 흐른다.

단계하는 일목적
1. 전역 지도에이전트 하나가 저장소 전체를 훑어 지도를 그린다구성 요소 사이의 관계를 알아야 "여기서는 무엇이 지켜져야 하나"를 정할 수 있다
2. 전문 에이전트 3개지도를 바탕으로 범주마다 에이전트를 하나씩 띄운다각 에이전트가 자기 범주의 보안 기대치를 정하고 어긋나는 곳을 찾는다
3. 적대적 검증찾은 이슈가 진짜인지 다시 따진다 adversarial validation거짓 경보를 걸러 낸다
4. 노이즈 게이트근거가 약한 이슈와 의도된 설계를 걸러 낸다 noise gate개발자가 볼 목록을 줄인다
5. 결과심각도, 코드 전체에 미칠 영향, 고칠 정확한 위치를 붙여 내놓는다바로 개발자에게 배정할 수 있게 한다

발표자는 이 과정을 플레이북playbook이라 부른다. 저장소를 넣으면 에이전트 조율은 플레이북이 알아서 한다. 나오는 것은 개발자에게 넘길 만한 이슈 목록이다.

SonarQube를 이미 쓰고 있다면 이 이슈는 기존 SAST 이슈와 같은 목록에 함께 나온다. 03:50

04

프런티어 모델과 이중 검증 04:30

발표자는 Sonar가 OpenAI의 Daybreak Cyber Partner Program(이름은 자막에 들린 대로, 추정)에 합류한다고 발표했다. 보안 특화 최신 모델을 통제된 방식으로 SonarQube 안에서 쓰게 하는 프로그램이라고 설명했다.

  • 이유: 공격자가 좋은 모델을 쓰니 방어하는 보안 팀도 그만한 모델이 필요하다.
  • 쓰임: Hunter Agent의 플레이북마다 추론을 더 깊게 하는 데 쓴다.
  • 주장: 모든 단서를 조사하고 검증한 뒤에 보여 준다. 결과는 정확하고, 다시 돌려도 같게 나오고, 나중에 따져 볼 수 있다.

"정확하다, 반복 가능하다"는 주장에 대한 수치(거짓 경보 비율 등)는 발표에 나오지 않았다. 자사 제품 설명이라는 점을 감안해 읽자.

두 층으로 겹쳐 쓴다 05:40

1층 · SAST + SCA

위험한 코드 패턴을 찾는다. SCA는 가져다 쓴 오픈소스 라이브러리의 알려진 취약점을 찾는다.

2층 · Hunter Agent

1층이 놓친 것을 맡는다. 의도와 어긋난 로직, 권한, 세션 문제를 찾는다.

발표자는 이것을 "설계부터 겹겹인 보안"이라 부른다. 두 층은 서로 독립적이어야 하고, 어느 층도 다른 층을 믿고 넘기지 않는다(제로 트러스트zero trust). 목표는 아직 알려지지 않은 취약점(제로데이zero-day)까지 찾는 것이라고 했다.

05

데모: 스캔 한 번 돌리기 06:20

발표자는 자기가 만든 간단한 Python 앱으로 실제 화면을 보여 줬다.

  1. SonarQube Cloud 대시보드에서 Hunter Agent 메뉴로 간다.
  2. Scan now 버튼을 누르면 스캔에 필요한 사용량 단위units 추정치가 먼저 나온다. 저장소 전체를 깊게 추론하는 데 드는 양이다. 07:00
  3. 스캔을 시작한다. 규모와 복잡도에 따라 한 시간이 넘을 수 있다. 이 앱은 약 1시간 걸렸다.

SonarQube Cloud뿐 아니라 직접 설치해 쓰는 SonarQube Server에서도 된다.

스캔 안에서 일어나는 일 07:40

  1. 대상 저장소를 안전하게 복제해 AI 엔진이 소스 코드를 직접 읽게 한다.
  2. 앱 구조를 분석해 공격받을 수 있는 지점(공격 표면attack surface)을 찾고 위협 모델threat model을 만든다.
  3. 맥락을 깊게 보는 스캔으로 IDOR, 접근 제어 깨짐, 비즈니스 로직 취약점을 찾는다.
  4. 하위 에이전트들의 결과를 모으고 중복을 없애 목록 하나로 만든다.
  5. 검증된 취약점을 SonarQube 이슈 목록으로 내보낸다.
06

결과: 이슈 46개, 범주 세 개 08:30

스캔 결과에는 열린 이슈가 46개 있었다. 모두 앞에서 말한 세 범주 중 하나에 속한다.

세 범주가 다루는 것 08:50

범주발표에서 든 항목쉬운 예 (예시, 발표에 없음)
접근 제어 깨짐
Broken access control		IDOR, 권한 확인 누락·오류, 권한 상승, 민감 정보 노출, CSRF주소창의 주문 번호만 바꾸면 남의 주문이 보인다
비즈니스 로직
Business logic		필수 단계 건너뛰기, 반복 가능한 동작 악용, 속도 제한 없음결제 단계를 건너뛰고 주문 완료 요청을 바로 보낸다. 같은 쿠폰을 요청 반복으로 여러 번 쓴다
인증·세션
Authentication & session		인증 깨짐, 세션 고정, 만료되지 않는 세션, 약한 비밀번호 복구, 다중 인증 누락, 무차별 대입 방어 빈틈로그인 시도 횟수에 제한이 없어 비밀번호를 끝없이 넣어 볼 수 있다
발표에서 확인할 수 없는 것 46개 중 몇 개가 진짜 문제였는지는 나오지 않았다. 거짓 경보 비율, SAST만 돌렸을 때와의 비교도 없었다. 데모 앱은 발표자 자신의 간단한 앱이다. 도입을 검토한다면 자기 저장소에서 결과 일부를 직접 확인해 봐야 한다.

이슈 하나 열어 보기 09:40

Hunter Agent 이슈는 SonarQube의 다른 이슈와 같은 목록에 뜬다. 새 대시보드로 옮겨 갈 필요가 없다. 모든 이슈에 Hunter Agent 태그와 범주 태그가 붙는다.

접근 제어 깨짐 · 심각도 높음 10:00

로그인한 사용자라면 누구나 관리자 확인을 통과한다. 자기 계정의 role 필드를 직접 쓸 수 있기 때문이다.

01의 예시 코드와 같은 종류의 문제다.

인증·세션 · 심각도 높음 12:00

비밀번호만 입력한 사용자가 다중 인증MFA을 끝내지 않고도 보호된 경로 전부에 들어간다. 관리자 기능도 포함이다.

비밀번호 확인과 다중 인증 사이를 건너뛸 수 있다는 뜻이다.

이슈 화면에 있는 것 10:20

  • 코드의 어느 위치에서 문제가 생기는지
  • 왜 문제인지에 대한 설명
  • 어떻게 고치면 되는지
  • 이 이슈에 대한 활동 기록
  • 담당 개발자 지정

이슈 상태 정하기 11:00

모든 이슈는 열림 상태로 시작한다. 사람이 보고 셋 중 하나로 정한다. 기준은 품질 게이트quality gate에 반영되느냐다. 품질 게이트는 기준을 넘지 못한 코드가 배포되지 못하게 막는 관문이다.

상태뜻품질 게이트
Accept (수락)진짜 문제이고 거짓 경보가 아니다반영하지 않는다. 배포를 막지 않는다
Confirm (확인)진짜 문제다반영한다. 배포를 막을 수 있다
False positive (거짓 경보)문제가 아니라고 판단한다발표에서 따로 말하지 않았다
08

정기 스캔과 자동 수정 12:20

스캔은 필요할 때 바로 돌릴 수도 있고, 일정을 정해 돌릴 수도 있다.

  • 주기: 매일, 매주, 매월 중에서 고른다.
  • 브랜치: main이 아닌 특정 브랜치를 골라 스캔할 수 있다. 데모는 main을 스캔했다.
찾기에서 고치기까지 13:10 지금까지는 고치는 방법을 제안만 했다. 발표자는 발표한 주부터 이 이슈를 SonarQube Remediation Agent에 배정할 수 있다고 발표했다. 이 에이전트가 로직 수준 보안 이슈를 대신 고친다. 고치는 일도 일정을 정해 돌릴 수 있다.
사냥당하기 전에 먼저 사냥하라.발표자의 마무리 말을 옮김 13:50

핵심 정리

  1. SAST는 위험한 코드 패턴을 찾는다. 코드는 맞게 도는데 의도가 틀린 로직 버그는 설계상 보지 못한다.
  2. 로직 버그의 대표 예: 사용자가 자기 role 필드를 바꿔 관리자 확인을 통과한다.
  3. 에이전트는 코드를 빠르게 많이 내보내는데 펜테스트는 1년에 몇 번뿐이다. 발표자는 이 틈을 문제로 본다.
  4. Hunter Agent는 저장소 전체 지도를 먼저 그린 뒤 범주별 전문 에이전트 3개를 띄운다.
  5. 찾은 이슈는 적대적 검증과 노이즈 게이트로 거짓 경보와 의도된 설계를 걸러 낸다.
  6. 세 범주: 접근 제어 깨짐, 비즈니스 로직, 인증·세션.
  7. 데모에서 간단한 Python 앱 스캔에 약 1시간이 걸렸고 이슈 46개가 나왔다. 정확도 수치는 나오지 않았다.
  8. 이슈는 기존 SonarQube 목록에 함께 뜨고, 위치·이유·고치는 법이 붙는다.
  9. Confirm은 품질 게이트에 반영되고, Accept는 진짜 문제로 인정하되 배포를 막지 않는다.
  10. 발표자는 SAST·SCA와 Hunter Agent를 겹쳐 쓰라고 권한다. 정기 스캔과 Remediation Agent로 찾기부터 고치기까지 이어진다.
10

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1SAST가 로직 버그를 잘 못 잡는 이유는?
SAST는 알려진 위험 패턴과 코드를 맞춰 본다. 로직 버그는 코드 모양이 정상이고, 문제는 동작이 비즈니스 규칙과 어긋난다는 데 있다.
Q2발표자가 말하는 "의도의 취약점"이란?
기술적으로는 맞게 동작하지만, 그 동작이 서비스의 규칙이나 의도와 맞지 않아 악용될 수 있는 결함이다.
Q3Hunter Agent가 전문 에이전트를 띄우기 전에 먼저 하는 일은? 왜 필요한가?
저장소 전체 지도를 그린다. 구성 요소 사이의 관계를 알아야 각 지점에서 지켜져야 할 보안 기대치를 정할 수 있다.
Q4적대적 검증과 노이즈 게이트는 각각 무엇을 거르나?
적대적 검증은 진짜가 아닌 이슈, 즉 거짓 경보를 거른다. 노이즈 게이트는 근거가 약한 이슈와 의도된 설계를 거른다.
Q5Hunter Agent의 세 범주와 각 범주의 항목 하나씩은?
접근 제어 깨짐(예: IDOR), 비즈니스 로직(예: 필수 단계 건너뛰기), 인증·세션(예: 만료되지 않는 세션).
Q6데모의 role 필드 이슈는 왜 심각도가 높은가?
로그인한 사용자 누구나 자기 role 필드를 써서 관리자 확인을 통과할 수 있다. 일반 사용자가 관리자 권한을 얻는 권한 상승이다.
Q7Accept와 Confirm의 차이는?
둘 다 진짜 문제라는 뜻이다. Confirm은 품질 게이트에 반영돼 배포를 막을 수 있고, Accept는 품질 게이트에 반영되지 않아 배포를 막지 않는다.
Q8발표자가 SAST·SCA와 Hunter Agent를 함께 쓰라고 하는 이유는?
각 층이 보는 것이 다르기 때문이다. SAST·SCA는 패턴과 알려진 라이브러리 취약점을, Hunter Agent는 그 밖의 로직 문제를 맡는다. 서로 독립된 두 층으로 놓치는 것을 줄인다.
Q9펜테스트만으로 부족하다는 발표자의 근거 세 가지는?
펜테스트는 1년에 몇 번뿐이다. 공격자는 더 좋은 모델을 쓴다. 에이전트가 만든 변경은 더 자주 배포되고, 취약점이 발견돼 공격에 쓰이기까지의 시간도 줄고 있다.
Q10찾기부터 고치기까지 사람 손을 덜 거치게 하는 기능 두 가지는?
정기 스캔(매일·매주·매월, 브랜치 선택)과 SonarQube Remediation Agent에 이슈를 배정해 자동으로 고치는 기능이다.
Q11이 발표의 주장을 받아들이기 전에 무엇을 따로 확인해야 하나?
거짓 경보 비율과 실제로 진짜인 이슈의 비율이다. 발표는 자사 제품 소개였고, 46개 이슈의 정확도나 SAST와의 비교 수치는 보여 주지 않았다.

용어 정리

용어뜻
SASTStatic Application Security Testing. 코드를 실행하지 않고 읽어서 위험한 패턴을 찾는 보안 검사
SCASoftware Composition Analysis. 가져다 쓴 오픈소스 라이브러리의 알려진 취약점을 찾는 검사
로직 수준 취약점Logic-level vulnerability. 코드는 맞게 돌지만 서비스 규칙과 어긋나 악용될 수 있는 결함
펜테스트Penetration test. 전문가가 공격자처럼 서비스를 뚫어 보는 점검. 모의 해킹이라고도 한다
접근 제어 깨짐Broken access control. 해서는 안 되는 사람이 데이터나 기능에 접근할 수 있는 상태
IDORInsecure Direct Object Reference. 요청의 ID만 바꾸면 남의 데이터에 닿는 문제
권한 상승Privilege escalation. 일반 사용자가 관리자 같은 더 높은 권한을 얻는 것
CSRFCross-Site Request Forgery. 로그인한 사용자 몰래 다른 사이트가 요청을 보내게 만드는 공격
세션 고정Session fixation. 공격자가 미리 정한 세션 ID를 피해자가 로그인할 때 그대로 쓰게 만드는 공격
다중 인증MFA, Multi-Factor Authentication. 비밀번호 말고도 문자 코드 같은 두 번째 확인을 요구하는 것
무차별 대입Brute force. 비밀번호를 하나씩 계속 넣어 보는 공격
속도 제한Rate limit. 정해진 시간 안에 보낼 수 있는 요청 수를 제한하는 것
공격 표면Attack surface. 외부에서 공격이 들어올 수 있는 지점 전체
위협 모델Threat model. 누가 어디를 어떻게 공격할 수 있는지 정리한 것
적대적 검증Adversarial validation. 찾은 이슈를 반박하듯 다시 따져, 진짜인 것만 남기는 검증
노이즈 게이트Noise gate. 근거가 약하거나 의도된 설계인 이슈를 걸러 내는 단계
거짓 경보False positive. 문제가 아닌 것을 문제라고 잘못 알리는 것
플레이북Playbook. 이 발표에서는 Hunter Agent가 범주별로 따르는 검사 절차 전체
품질 게이트Quality gate. SonarQube에서 기준을 넘지 못한 코드가 배포되지 못하게 막는 관문
프런티어 모델Frontier model. 현재 가장 앞선 성능의 AI 모델
무기화Weaponize. 발견된 취약점을 실제 공격에 쓸 수 있는 도구로 만드는 것
제로데이Zero-day. 아직 널리 알려지지 않아 고칠 방법도 없는 취약점
제로 트러스트Zero trust. 어떤 구성 요소도 기본으로 믿지 않고 매번 확인하는 보안 원칙
