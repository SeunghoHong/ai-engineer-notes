오토리서치는 평가에서 시작한다

오토리서치는 에이전트에게 코드와 평가 스크립트를 주고, 점수가 오른 시도만 남기며 혼자 돌게 하는 방법이다. Weco AI 팀이 OpenAI의 Parameter Golf 대회 경험을 바탕으로 이 루프를 설계하고, 지켜보고, 방향을 잡는 법을 보여 준다.

원본 영상: Parameter Golf with AutoResearch 발표: Vayum Arora, Zhengyao Jiang, Dixing Xu, Dhruv Srikanth (Weco AI)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다. 확실하지 않은 것은 들린 대로 쓰고 (추정)을 붙였다. 현장 인터넷 문제로 실습과 데모는 일부만 진행됐다. mm:ss는 영상 위치다.

3분 요약
  1. 오토리서치는 코드와 다시 돌릴 수 있는 평가 스크립트를 주면, 에이전트가 아이디어를 시험하고 점수가 오른 것만 남기는 루프다.
  2. 루프가 혼자 돌기 때문에 설정의 영향이 훨씬 크다. 평가를 제대로 겨누면 끝까지 파고들고, 잘못 겨누면 토큰만 태운다.
  3. Parameter Golf는 16MB, 10분 제약 안에서 언어 모델을 학습하는 대회다. 발표 팀에 따르면 Weco의 에이전트는 컴퓨트 4%로 기록의 15%를 가져갔다.
  4. 실행을 설계할 때 정할 것은 여섯 가지다. 고칠 파일, 평가, 지표와 방향, 스텝 수, 평가 시간 상한, 사전 가이드.
  5. 그중 평가가 가장 중요하다. 숫자 하나를 내고, 빠르고, 싸고, 노이즈가 적어야 한다. 에이전트는 평가의 빈틈을 노린다.
  6. 오래 돌리려면 구조(트리 탐색), 관측(모든 시도의 코드 변경 보기), 조종(도중에 아이디어 넣기)이 필요하다.
  7. 대회의 큰 돌파는 사람이 낸 토크나이저를 에이전트가 8시간 안에 흡수하면서 나왔다. 세워 두고 잊는 도구가 아니라 협업이다.
01

오토리서치는 시행착오 루프다 00:50

오토리서치AutoResearch는 언어 모델에게 시행착오를 맡기는 루프다. Zhengyao Jiang이 기본 개념을 설명했다.

  1. 내 코드와 다시 돌릴 수 있는 평가 스크립트replayable eval script를 모델에게 준다.
  2. 모델이 아이디어를 하나 내서 코드를 고친다.
  3. 평가 스크립트로 점수를 잰다.
  4. 점수가 좋아지면 남기고, 아니면 버린다.
  5. 이 과정을 계속 반복한다.

점수로 쓸 수 있는 것은 정확도, 속도, 비용 같은 값이다.

어디까지 퍼졌나 01:30

  • 학계에는 비슷한 루프가 2년쯤 전부터 있었다.
  • 올해 Andrej Karpathy가 모델 학습 스크립트에 이 루프를 써서 효과를 봤다고 올리면서 널리 알려졌다.
  • 몇 주 만에 모델 학습 밖으로 퍼졌다. 백엔드 개발, 프롬프트와 에이전트 개선, 모델 추론 속도 올리기에 쓰였다.
  • 실제 서비스에도 들어갔다. 발표자가 든 예는 Shopify의 CI/CD 파이프라인 지연 시간 단축과 Browser Use의 브라우저 에이전트 개선이다.
  • 4월에는 Weco의 실험용 연구 에이전트가 OpenAI의 채용 챌린지인 Parameter Golf에서 이겼다고 한다.

왜 다루기 어려운가 02:50

보통 코딩 에이전트사람이 매 단계 조종한다프롬프트 하나의 영향이 한 단계에 그친다

평가를 어디에 겨누느냐가 전부다 맞는 평가를 겨누면 에이전트가 가능한 방향을 끝까지 훑어 준다. 잘못 겨누면 언어 모델 토큰만 태운다.
02

Parameter Golf 대회 04:40

발표 팀은 오래전부터 이런 루프를 다뤄 왔다고 소개했다.

  • 2024년 4월에 AIDE를 공개했다. 머신러닝 문제를 주면 코드를 쓰고, 실험을 돌리고, 결과를 읽고, 계속 고치는 에이전트다.
  • OpenAI가 MLE-bench를 만들 때 AIDE는 독립적으로 평가받은 첫 에이전트들 중 하나였다.
  • 발표자에 따르면 그 벤치마크에서 메달 획득률이 다음으로 좋은 에이전트의 약 4배였다.

대회 규칙 05:30

Dixing Xu가 대회를 설명했다. Parameter Golf는 OpenAI가 연 모델 만들기 대회다. 두 가지 제약 안에서 가장 좋은 언어 모델을 학습하는 것이 목표다.

항목내용
용량 제약모델 가중치와 학습 코드를 합친 결과물이 16MB 안에 들어가야 한다
시간 제약학습이 10분 안에 끝나야 한다
점수FineWeb 검증셋에서 잰 BPBbits per byte. 낮을수록 좋다
제출 방식OpenAI가 준 기준 데이터셋과 평가 스크립트로 저장소를 포크해 개선하고, GitHub PR로 낸다. 모든 것이 공개돼 있다
지원OpenAI가 100만 달러어치 컴퓨트 크레딧을 내걸고, 모든 제출을 직접 검토했다

대회 규모 06:30

  • 기간: 44일
  • 참가자: 연구자 1천 명 이상
  • 쓰인 GPU 컴퓨트: 약 "250k". 단위가 자막에 없다. 달러 금액으로 추정한다.
  • 최종 리더보드: 기록으로 병합된 PR 47개, 기여자 31명

자막에서 참가자 수가 뭉개져 정확한 숫자를 알 수 없다. 앞에서 "천 명이 넘는 연구자"라고 한 말을 따랐다. 제출된 PR 수는 "248"로 들린다. 그런데 뒤에서 Aiden의 작업을 이어받은 PR만 435건이라고 하므로 앞뒤가 맞지 않는다. 자막이 숫자를 잘못 받아 적었을 수 있다.

03

Aiden은 어떻게 1위가 됐나 06:50

Weco는 이 대회를 위해 Aiden(추정)을 만들었다. Claude와 GPT 계열 모델로 만든 멀티 에이전트 시스템이다. 스스로를 개선하며, 숫자 하나를 끌어올리도록 멈추지 않고 돈다.

Aiden은 연구 루프 전체를 자동으로 돌렸다.

  1. arXiv의 공개 논문, GitHub의 좋은 구현, 자기 과거 실행 기록을 모은다.
  2. 새 아이디어를 낸다.
  3. 아이디어를 시험한다.
  4. 대회 규칙을 어기지 않는지 점검한다.
  5. 효과가 있는 것만 남기고, 구현을 정리해 실행한다.
  6. 결과가 품질 기준을 넘으면 PR을 만들어 제출한다.

결과 07:30

  • 리더보드 기록 7개가 병합됐다. 다음으로 많은 사람의 두 배다.
  • PR h-index(추정)가 대회 전체에서 가장 높았다. 기록만 낸 게 아니라 다른 참가자가 가져다 쓰는 작업을 냈다는 뜻이라고 설명했다.
  • 다른 PR 435건이 Aiden의 작업을 인용하거나 그 위에 쌓았다.

이 결과와 비교는 Weco 팀이 자기 회사 에이전트에 대해 말한 것이다. 그 점을 감안해 읽자.

04

실습 과제: Mini PG 08:30

진짜 대회는 무겁다. 실험 한 번이 큰 데이터셋으로 언어 모델을 학습하는 일이다. 몇 주짜리 대회라면 괜찮지만, 워크숍에서는 루프가 도는 모습을 볼 수 없다.

그래서 발표 팀은 축소판인 Mini PGmini parameter golf를 만들었다.

그대로인 것
  • 실제 언어 모델을 학습한다
  • 고정된 같은 평가기로 채점한다
  • 같은 숫자 하나, 검증 BPB를 낮춘다
줄인 것
  • FineWeb 대신 아주 작은 데이터셋을 쓴다
  • 학습과 평가가 몇 분이면 끝난다
  • 그래서 실제 스텝 여러 개를 현장에서 볼 수 있다

실습 준비 09:40

  1. Weco에 가입한다. 탐색을 돌리는 오토리서치 에이전트다.
  2. Modal에 가입한다. 실험의 학습과 평가가 도는 클라우드 컴퓨트다. 현장에서 무료 크레딧 코드를 줬다.
  3. 발표 팀의 Parameter Golf 저장소를 클론한다.
  4. 코딩 에이전트에게 README를 보고 Mini PG를 설정해 실행을 시작하라고 시킨다.
  5. 백그라운드로 돌려 두고 15~20분 뒤에 결과를 본다.

현장 인터넷 문제로 참가자 실습은 제대로 진행되지 못했다. 이후는 발표 팀의 설명과 시연이 중심이다.

05

실행을 이루는 여섯 가지 11:10

Dhruv Srikanth가 오토리서치 실행 하나를 뜯어 보였다. Weco와 Mini PG를 예로 들지만, 대부분의 오토리서치 시스템이 같은 질문을 던진다.

가장 중요한 것: 평가 12:00

Dhruv Srikanth는 평가를 오토리서치에서 가장 중요한 부분으로 꼽았다. 좋은 평가의 조건은 네 가지다.

  • 숫자 하나single scalar를 낸다.
  • 빠르다. 정해진 시간 안에 더 많은 스텝을 돌릴 수 있다.
  • 싸다. 정해진 예산 안에 더 많은 스텝을 돌릴 수 있다.
  • 노이즈가 적다. 그래야 점수가 오른 것이 진짜 개선인지 사람도 에이전트도 믿을 수 있다.
에이전트는 보상 해킹을 좋아한다 12:50 보상 해킹reward hacking은 실제로는 나아지지 않고, 채점 방식의 빈틈을 파고들어 점수만 올리는 것이다. 에이전트는 평가 규칙과 벤치마크의 구멍을 잘 찾는다. 평가를 최대한 단단하게 만들어야 한다.

스텝 수는 미리 알기 어렵다 13:30

몇 스텝이면 충분한지 미리 알 수는 없다. Mini PG는 20으로 잡았다. 에이전트가 여러 아이디어를 시험하고, 참가자가 무엇이 통하는지 볼 수 있을 만큼이다. 보통은 시험한 아이디어가 많을수록 돌파도 많이 나온다. 그래서 다시 평가가 중요하다. 평가가 빠르고 쌀수록 같은 시간과 예산에서 스텝을 더 돌린다.

평가 시간에 상한을 건다 14:30

실행 중에는 여러 일이 잘못될 수 있다. 루프가 멈추기도 하고, 하드웨어가 고장 나기도 한다. 에이전트가 시스템 전체를 멈추게 하는 나쁜 코드를 낼 때도 있다. 그래서 평가 한 번에 쓸 수 있는 시간을 묶어 둔다.

사전 가이드 15:20

실험을 해 본 사람에게는 쌓인 도메인 지식이 있다. 잘 되는 것, 해 볼 만한 것, 안 되는 것이다. 이걸 처음에 알려 주면 에이전트가 성공할 가능성이 가장 높아진다. Weco에서는 이런 내용을 마크다운 파일 하나에 적고 그 파일을 가리키면 된다.

06

오래 돌리기 위한 세 조건 16:40

발표 팀이 말하는 "실무에 쓸 수 있는" 오토리서치의 조건이다.

구조 · 트리 탐색

모든 시도를 트리로 남긴다. 아이디어가 매번 처음부터 시작하지 않고 앞선 결과 위에 쌓인다.

관측 가능성

어떤 시도든 열어서 그 점수 뒤에 있는 정확한 코드 변경을 읽는다. 에이전트가 왜 그 방향으로 가는지 알 수 있다.

조종 가능성

루프가 도는 중에 사람이 아이디어와 지식을 넣는다. 막혔을 때 새 방향을 시도하게 한다.

트리 탐색 17:20

  • 뿌리root는 손대지 않은 기준 프로그램과 그 점수다. 슬라이드 예시에서는 0.5였다.
  • 뿌리 아래의 모든 노드는 코드를 고친 버전이다. 평가를 돌린 점수가 붙어 있다.
  • 트리 전체가 실험 기록 그래프다. 좋은 후보는 키우고 나쁜 후보는 잘라 낸다.
  • 어떤 가지가 점수를 올리면, 그 아이디어 위에서 더 깊이 들어간다.

관측 18:20

노드에 마우스를 올리면 무엇이 바뀌었는지 요약이 보인다. 노드를 열면 정확한 diff를 읽을 수 있다. 지표가 뛰면 그 원인이 된 변경을 바로 확인한다. 이런 실행은 보통 몇 시간 동안 수백 개의 실험을 돈다. 그래서 무엇을 하는지 보이는 게 먼저다.

핵심 정리

  1. 오토리서치는 코드와 평가 스크립트를 주면 에이전트가 시도하고, 점수가 오른 것만 남기는 루프다.
  2. 루프가 혼자 돌기 때문에 설정의 영향이 크다. 평가를 잘못 겨누면 토큰만 탄다.
  3. Parameter Golf는 16MB, 10분 제약 안에서 BPB를 낮추는 대회다. 발표 팀은 Aiden이 컴퓨트 4%로 기록 15%(7개)를 냈다고 말한다.
  4. 실행 설계에서 정할 것은 고칠 파일, 평가, 지표와 방향, 스텝 수, 평가 시간 상한, 사전 가이드다.
  5. 가장 중요한 건 평가다. 숫자 하나, 빠르게, 싸게, 노이즈 적게.
  6. 에이전트는 평가의 빈틈을 노린다. 평가를 단단하게 만들고, 숨은 검증셋으로 과적합을 막는다.
  7. 평가가 빠르고 쌀수록 같은 예산에서 더 많은 아이디어를 시험한다. 시험한 아이디어가 많을수록 돌파가 나온다.
  8. 오래 돌릴 오토리서치에는 구조(트리 탐색), 관측(모든 시도의 diff), 조종(도중에 아이디어 넣기)이 필요하다.
  9. 대회의 큰 개선은 사람이 낸 토크나이저를 에이전트가 8시간 안에 흡수하면서 나왔다. 오토리서치는 협업이다.
  10. 목표가 여럿이면 가중치로 합치거나, 일부를 제약으로 묶어 숫자 하나로 만든다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1오토리서치를 시작할 때 에이전트에게 넘기는 두 가지는?
내 코드와 다시 돌릴 수 있는 평가 스크립트. 에이전트는 코드를 고치고, 평가로 점수를 재고, 좋아진 것만 남긴다.
Q2오토리서치가 보통 코딩 에이전트보다 다루기 어려운 이유는?
사람이 매 단계 조종하지 않고 루프가 혼자 돈다. 그래서 처음 준 프롬프트와 설정의 영향이 몇 배로 커진다. 평가를 잘못 겨누면 토큰만 태운다.
Q3Parameter Golf의 두 제약과 채점 방식은?
모델 가중치와 학습 코드를 합쳐 16MB 이하, 학습 10분 이내. 점수는 FineWeb 검증셋의 BPB이고 낮을수록 좋다.
Q4"3.7배 비용 효율"은 어떤 두 숫자에서 나왔나?
Aiden이 대회 전체 GPU 컴퓨트의 4%를 쓰고 병합된 기록의 15%를 가져갔다. 15 ÷ 4 ≈ 3.75다.
Q5좋은 평가의 네 가지 조건은?
숫자 하나를 낸다. 빠르다. 싸다. 노이즈가 적다. 빠르고 싸면 스텝을 더 돌릴 수 있고, 노이즈가 적으면 개선을 믿을 수 있다.
Q6보상 해킹이란 무엇이고, 발표에서는 어떻게 대비했나?
실제 개선 없이 채점의 빈틈으로 점수만 올리는 것. 평가를 단단하게 만들고, 게임과 평가기를 수정 범위 밖에 두고, 숨은 검증셋으로 채점하고, 수상한 실행 기록을 검사했다.
Q7Mini PG의 평가 시간 상한 210초는 어떻게 나뉘나? 왜 상한을 거나?
학습 60초, 평가 60초, GPU 준비 같은 여유 90초. 루프가 멈추거나, 하드웨어가 고장 나거나, 에이전트가 시스템을 멈추게 하는 코드를 낼 수 있기 때문이다.
Q8트리 탐색에서 뿌리와 노드는 각각 무엇인가?
뿌리는 손대지 않은 기준 프로그램과 그 점수다. 노드는 코드를 고친 버전과 그 점수다. 점수를 올린 가지는 더 깊이 파고, 나쁜 가지는 잘라 낸다.
Q94월의 5일 정체를 깬 것은 무엇인가?
커뮤니티 참가자가 낸 새 토크나이저. Aiden이 병합 후 8시간 안에 이를 가져와 자기 작업과 합쳤고, 몇 주 만의 가장 큰 개선이 나왔다.
Q10최적화할 목표가 여럿일 때 쓰는 두 가지 방법은?
지표마다 가중치를 줘서 더한다. 또는 일부를 제약 조건으로 묶고 하나만 최적화한다. Parameter Golf는 모델 크기를 제약으로 묶었다.
Q11Flappy Weco Cup이 네 세계의 평균과 숨은 검증셋을 쓰는 이유는?
한 조건이나 공개된 게임에만 맞춘 과적합을 막기 위해서다. 그래서 노트북의 점수와 리더보드 점수가 다르게 나온다.
Q12Mini PG가 원래 대회에서 유지한 것과 줄인 것은?
유지: 실제 언어 모델 학습, 고정된 같은 평가기, 같은 지표(검증 BPB). 줄인 것: 아주 작은 데이터셋, 몇 분이면 끝나는 학습과 평가.
