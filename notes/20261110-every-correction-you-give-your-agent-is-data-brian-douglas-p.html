에이전트에게 준 교정은 데이터다

숙련자가 에이전트를 바로잡는 순간에는 에이전트가 모르는 팀의 지식이 담긴다. 발표자는 그 순간들을 세션 기록에서 골라 라벨을 붙이고, 동료처럼 리뷰하는 스킬과 작은 모델을 만든다.

원본 영상: Every Correction You Give Your Agent Is Data 발표: Brian Douglas (Paper Compute)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 바로잡았고(Claude Code, Beastie Boys, Greptile, Braintrust, Qwen 등), 확실하지 않은 것에는 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트에게 일을 넘기면 주니어가 실력을 쌓던 반복 연습도 함께 넘어간다. 발표자는 Rust를 모르는 채로 Rust 코드를 바이브 코딩한다.
  2. 그래서 에이전트 세션 기록(트레이스)을 전부 모은다. 도구는 무엇이든 된다.
  3. 기록에 라벨을 붙인다. 가장 값진 라벨은 푸시백이다. 사람이 에이전트에게 "그건 아니다"라고 되받아친 순간이다.
  4. 숙련자의 푸시백에는 에이전트가 모르는 팀의 결정과 맥락이 담긴다. 컴파일은 되지만 팀 방식과 다른 코드를 잡아낸다.
  5. 발표자는 동료 Matt의 푸시백으로 작은 모델을 후속 학습했다. 그렇게 PR을 Matt처럼 리뷰하는 트윈 리뷰어를 만들었다.
  6. 리뷰가 GitHub에서 각자의 터미널로 옮겨 가면서 지적이 공유 저장소에 남지 않는다. 세션 기록이 그 빈자리를 채운다.
  7. 순서는 스킬 → 평가 → 후속 학습이다. 지금은 스킬로 대부분의 효과를 얻을 수 있으니 스킬부터 만든다.
01

반복 연습이 에이전트에게 간다 00:40

발표자는 이 작업을 6~8개월째 하고 있다. 시작은 올해 초, 모두가 코딩 에이전트에 빠져들던 때다. 그중 Claude Code가 가장 널리 쓰이고, Codex와 ChatGPT도 있다.

Rick Rubin과 바이브 코딩

음반 프로듀서 Rick Rubin은 Beastie Boys를 비롯한 여러 아티스트의 음반을 만들었다. 발표자 말로는 Rubin은 악기를 직접 연주하지 않는다. 사람들은 이것을 바이브 코딩vibe coding에 빗댄다. 피아노를 치지 않고도 좋은 음악을 만들듯, Rust를 쓸 줄 몰라도 AI로 Rust 코드를 만들 수 있다.

발표자가 바로 그 상태다. 발표자는 Rust를 직접 쓰지 못한다.

발표자가 소개한 책: Rick Rubin, The Creative Act: A Way of Being.

주니어의 반복 연습이 사라진다 01:10

발표자는 Addy Osmani의 글을 소개했다. 발표자에 따르면 Osmani는 지금 Anthropic의 Claude Code 팀에 있다. 글의 요지는 이렇다.

  • 주니어가 시니어로 크는 길은 반복 연습reps이었다.
  • 많이 해 볼수록 실력이 늘었다.
  • 이제 그 연습을 에이전트에게 넘기고 있다.
  • 그만큼 사람이 성장할 기회도 줄어든다.
이 발표가 다루는 질문 직접 부딪혀 배울 기회가 줄었다면, 숙련자의 판단은 어디서 얻을까. 발표자의 답은 숙련자가 에이전트를 바로잡은 기록이다.
02

세션 데이터부터 모은다 01:50

발표자는 올해 초 tapes라는 오픈소스 프로젝트를 만들었다(tapes.dev, Apache 2.0 라이선스). tapes는 에이전트 세션의 트레이스trace를 모은다. 트레이스는 에이전트가 무엇을 받고 무엇을 했는지 순서대로 남긴 기록이다.

발표자는 도구가 핵심이 아니라고 강조한다. 핵심은 에이전트 세션 데이터를 모으는 일이다. 다른 길도 많다.

  • OTel 컬렉터OpenTelemetry collector로 모은다.
  • 세션 캡처 서비스를 쓴다.
  • 많은 하네스harness가 이미 기본 기능으로 세션을 저장한다. 하네스는 모델을 감싸 도구와 규칙을 정해 주는 실행 틀이다.

stereos: 에이전트 런타임 02:10

발표자 팀은 stereos도 만들었다. 에이전트가 돌아가는 실행 환경, 곧 샌드박스sandbox다. 재현할 수 있는 환경에서 세션을 기록하니, 그 환경 자체가 신호를 남긴다.

tapes, stereos, 뒤에 나오는 Paper 콘솔과 Sweeper Agent는 발표자와 발표자 회사(Paper Compute)가 만든 것이다. 발표자는 "tapes 이야기가 아니다"라고 했지만, 도구를 소개하는 부분은 그 점을 감안해 읽자.

03

병렬 에이전트로 뒷정리 02:40

발표자는 이 도구들로 자가 치유 인프라self-healing infrastructure를 만들고 있다. 그중 하나가 Sweeper Agent다. 여러 에이전트를 동시에 띄워 정해진 문제 하나를 풀게 하는 구조다.

이렇게 나눠 맡기기 좋은 일은 범위가 분명한 일이다.

  • 문서 쓰기
  • 테스트 작성
  • 코드 정리

발표자는 주로 지난 18개월 동안 바이브 코딩으로 만든 소프트웨어를 이렇게 치웠다.

그래도 남는 문제 03:20 정리는 에이전트가 해도, 발표자가 Rust를 모른다는 사실은 그대로다. 발표자는 10년 전 Rust를 배우려고 작은 개인 프로젝트를 해 봤을 뿐, 업무로 써 본 적은 없다. 그런데 발표자 회사 Paper Compute는 매일 Rust를 쓴다.
04

세션에 라벨을 붙인다 03:50

에이전트에게 험한 말을 할 거라면, 적어도 그 결과에 라벨은 붙여라.발표자가 첫머리에 밝힌 발표 주제 (00:00)

발표자는 Paper 콘솔을 데모로 보여 줬다. tapes가 모은 트레이스를 보는 화면이다.

  • 로컬에서 혼자 기록할 때와 달리, 팀 전체의 세션이 한 저장소에 모인다.
  • 세션마다 라벨을 붙일 수 있다.

데모 세션의 이름은 "paper cloud export memory limits"였다(자막 그대로). 여기에 push back이라는 라벨이 붙어 있었다. 엔지니어가 에이전트에게 "그건 아니다"라고 되받아친 순간마다 붙이는 라벨이다. 이 노트에서는 푸시백이라고 쓴다. 04:20

발표자는 "에이전트에게 무례하게 굴면 Anthropic이 계정을 막을 수 있다"는 이야기를 꺼냈다. 다만 소문일 뿐이고 근거가 있는지 모른다고 발표자 스스로 덧붙였다. 04:40

Paper 콘솔은 발표자 회사 제품이다. 발표자 말로는 지금은 대기자 명단으로만 받는다.

05

푸시백은 에이전트가 모르는 지식이다 04:50

발표자는 동료 Matt가 Rust나 Go를 다룬 세션을 찾아본다. Matt가 에이전트에게 푸시백하는 순간은 좋은 신호다. Matt는 알고 에이전트는 모르는 지식이 거기 있다는 뜻이다.

푸시백의 흔한 내용에이전트가 놓친 것
팀이 정한 API 구조컴파일은 된다. 하지만 코드를 어떻게 짜고 다른 부분과 어떻게 맞물릴지는 팀이 이미 정해 두었다.
서비스 중복맥락이 없어서 이미 있는 서비스를 또 만든다.
그 밖의 이유발표자는 "이유는 여러 가지가 더 있다"고만 했다.

요점은 컴파일러가 통과시킨 코드도 팀 기준으로는 틀릴 수 있다는 것이다. 그 기준은 코드보다 사람 머릿속에 먼저 있다.

되받아칠 지식이 없으면 05:30

발표자는 스스로를 "주니어 Rust 엔지니어"라고 부른다. 에이전트가 이상한 선택을 해도 짚어 낼 맥락이 없다. 그래서 에이전트가 쓴 Rust 코드를 보이는 그대로 믿는다.

코드를 쓸 때푸시백이 없다발표자는 에이전트 코드를 그대로 받는다. AI 리뷰 도구 Greptile이 5점 만점에 5점을 주면 그냥 넘긴다.
→
PR 리뷰 때푸시백이 몰린다PR을 열면 사람 엔지니어들이 한꺼번에 지적한다. 발표자가 Rust를 모른다는 걸 다들 안다.

그래서 발표자의 질문은 이것이다. 리뷰 때 받을 푸시백을 미리 받을 수는 없을까.

06

트윈 리뷰어: Matt처럼 리뷰하는 모델 06:00

발표자는 라벨과 트레이스를 하나도 빼지 않고 모으기 시작했다. 콘솔에는 세션마다 세부 내용이 모두 남는다. 같은 일을 하는 명령줄 도구도 있다.

  1. 트레이스를 모은다. 모든 세션을 저장한다.
  2. 데이터셋을 만든다. 라벨이 붙은 세션을 데이터셋으로 묶는다.
  3. 후속 학습post-training을 한다. Matt가 Go나 Rust 코드에서 푸시백한 순간들로 모델을 추가 학습한다. 06:40
  4. Matt처럼 코멘트하게 한다. "Matt라면 이 GitHub PR에 어떤 코멘트를 달까"를 답하게 한다.

데모에서는 twin review라는 명령줄 도구에 PR 번호(381)를 넣고 돌렸다. 도구는 그 PR을 Matt인 것처럼 리뷰했다. 06:20

학습 데이터는 트레이스뿐이다 07:00 GitHub PR 리뷰 데이터는 쓰지 않았다. 발표자는 그 데이터로도 같은 방식을 쓸 수 있을 거라고 했다. 트레이스만 쓴 이유는 다음 절에 나온다.

트윈 리뷰어는 공개하지 않았다. 민감한 데이터가 들어 있어서다. 발표자는 같은 구성을 Fireworks라는 서비스에서 후속 학습해 만들었다. 08:00

발표자는 처음에 트윈 리뷰어가 오픈소스라고 했다가 곧 바로잡았다. 이 노트는 바로잡은 말을 따른다.

07

리뷰는 GitHub에서 터미널로 옮겨 갔다 07:10

발표자 팀 대부분은 이제 명령줄에서 코드를 리뷰한다. Claude에게 맡기거나, Pi 하네스에게 맡기거나, "이 PR 리뷰해 줘"라고 시킨다. 그러면 GitHub에는 푸시백도 코멘트도 별로 남지 않는다.

예전GitHub에서 리뷰처음엔 사람이, 그다음엔 에이전트가 PR에 코멘트를 달았다. 지적이 공유 저장소에 남았다.
→
지금각자의 하네스에서 리뷰감독도 코멘트도 공유 코드베이스로 가지 않는다.

그래서 숙련자의 지적이 남는 곳은 GitHub가 아니라 세션 트레이스다. 발표자가 PR 데이터 대신 트레이스로 학습한 이유가 여기 있다.

08

골라 모을 세션 4가지 08:10

발표자는 트레이스에서 다음 종류의 세션을 찾았다.

라벨뜻
푸시백 push back사람이 에이전트의 작업을 되받아친 세션

흔한 실패: 이미 있는 것을 다시 만든다 08:20

에이전트는 이미 있는 Go 라이브러리를 새로 만들곤 한다. 원래는 푸시백해야 할 일이다. 하지만 그 라이브러리가 있다는 걸 모르면 그대로 받아들이게 된다.

발표자는 "Kubernetes를 다시 만든다"는 말이 과장으로 들린다고 인정했다. 그래도 테스트용 mock 라이브러리mock library처럼 널리 쓰이는 오픈소스를 에이전트가 다시 만드는 일은 실제로 봤다고 했다.

09

시작 순서: 스킬 → 평가 → 후속 학습 08:50

발표자의 권고는 이렇다. 리뷰에서 값진 지적을 하는 사람이 팀에 있다면, 그 사람의 트레이스를 기회로 본다. 그다음 둘 중 하나를 고른다.

  • 트레이스로 모델을 학습하거나 후속 학습한다.
  • 로컬에서 쓸 리뷰용 하네스를 직접 만든다.

발표자는 하네스를 직접 만드는 것만으로도 상당 부분을 해결할 수 있다고 본다.

발표자가 실제로 밟은 순서 09:30

단계하는 일발표자 사례
1. 트레이스 수집세션을 빠짐없이 저장한다tapes. 발표자 컴퓨터의 로컬 Postgres 데이터베이스다. Braintrust 같은 도구도 된다.
2. 스킬트레이스를 활용하는 스킬skill을 만든다tapes에 쌓인 기록을 확인하는 스킬
3. 평가스킬이 생기면 평가eval를 만들 수 있다발표에 세부 내용은 없다
4. 후속 학습평가가 생기면 Qwen 모델을 후속 학습한다Rust 코드가 조직의 작성 방식에 맞는지 판별하는 모델
모델 학습보다 스킬 먼저 10:10 발표자는 스킬 대신 모델을 학습시키는 방법에 대한 블로그 글까지 썼다. 그래도 권하는 순서는 스킬이 먼저다. 지금은 스킬로 대부분의 효과를 얻을 수 있다고 본다. 발표자 팀에는 스킬 재료로 쓸 세션이 8만 개 가까이 쌓여 있다.

발표자는 이 작업에 Qwen3 8B(자막상 "Quinn 38B", 추정)를 썼다고 했다 09:10. 뒤에서는 데모 모델을 Qwen 4B라고 했다 11:00. 두 말이 서로 다른 실험을 가리키는지는 발표에서 분명하지 않다.

10

미세조정 두 갈래: SFT와 DPO 10:30

발표자는 후속 학습 방법 두 가지를 견줬다. 하나는 SFT다(발표자 표현은 specialized fine-tuning). 다른 하나는 DPOdirect preference optimization다. DPO는 훨씬 많은 계산 자원이 필요해서, 발표자는 SFT 쪽을 권한다.

SFT · 미세조정

비유: 책 여백의 메모. 책이 사전학습된 모델이라면, 여백 메모는 그 위에 따로 얹는 가중치다. 정확히는 어댑터adapter다.

  • QLoRA(자막상 "quick Q or", 추정) 방식으로 모델을 양자화해 학습했다
  • RTX 5090 같은 비교적 작은 GPU로 했다
  • Qwen 4B 모델에서 꽤 잘 됐다 11:00

발표자 판단: 대부분은 이쪽이면 된다.

DPO · 선호 최적화

비유: 요약 학습서. 여백 메모가 SFT라면 DPO는 CliffNotes(미국의 요약 학습서)라고 했다. 발표자는 비유를 더 풀지 않았다. 11:30

  • 발표자 환경에서는 4B 같은 작은 모델로는 안 됐다
  • 70B 이상 모델이 필요했다
  • 로컬 하드웨어가 없어 Brev 서비스의 NVIDIA GPU로만 돌릴 수 있었다
  • Fireworks의 일부 기능은 끝내 쓰지 못했다
  • 큰 GPU는 미리 많은 돈을 내야 한다

발표자 판단: 하드웨어 부담이 크다.

용어: 발표자는 SFT를 "specialized fine-tuning"이라고 불렀다. 정답 예시를 보여 주며 모델을 추가 학습하는 이 방식은 보통 지도 미세조정(supervised fine-tuning)이라고 부른다.

"작은 모델에는 DPO가 안 된다"는 발표자 환경에서 겪은 결과다. DPO는 7B 이하 공개 모델에도 흔히 쓰는 방법이므로, 일반 규칙으로 받아들이지는 말자.

핵심 정리

  1. 에이전트에게 일을 넘기면 주니어가 실력을 쌓던 반복 연습도 함께 넘어간다.
  2. 핵심은 도구가 아니라 에이전트 세션 데이터(트레이스)를 모으는 일이다.
  3. 세션에 라벨을 붙인다. 가장 값진 라벨은 푸시백이다.
  4. 숙련자의 푸시백에는 팀이 정한 구조, 이미 있는 서비스와 라이브러리처럼 에이전트에게 없는 맥락이 담긴다.
  5. 컴파일된다고 맞는 코드가 아니다. 팀이 정한 방식과 맞아야 한다.
  6. 맥락이 없는 사람은 에이전트 코드를 그대로 믿고, 지적은 리뷰 때 한꺼번에 받는다.
  7. 발표자는 동료 Matt의 푸시백으로 작은 모델을 후속 학습해, Matt처럼 리뷰하는 트윈 리뷰어를 만들었다.
  8. 리뷰가 각자의 터미널로 옮겨 가면서 지적이 공유 저장소에 안 남는다. 트레이스가 그 기록을 대신한다.
  9. 순서는 스킬 → 평가 → 후속 학습이다. 지금은 스킬로 대부분의 효과를 얻는다.
  10. SFT는 작은 GPU와 4B 모델로도 됐다. DPO는 발표자 환경에서 70B 이상 모델과 큰 GPU가 필요했다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 Rick Rubin 이야기를 꺼낸 이유는?
발표자 말로는 Rubin은 악기를 연주하지 않고도 좋은 음반을 만들었다. Rust를 쓸 줄 모르면서 Rust 코드를 바이브 코딩하는 발표자의 처지와 닮았다.
Q2Addy Osmani의 글이 걱정한 것은?
주니어는 반복 연습으로 시니어가 된다. 그 연습을 에이전트에게 넘기면 사람이 성장할 기회가 줄어든다.
Q3tapes를 소개하며 발표자가 강조한 점은?
도구가 아니라 에이전트 세션 데이터를 모으는 일이 핵심이다. OTel 컬렉터, 세션 캡처 서비스, 하네스의 기본 기능 등 무엇을 써도 된다.
Q4"푸시백" 라벨은 어떤 순간에 붙고, 왜 값진가?
엔지니어가 에이전트의 작업을 되받아친 순간에 붙는다. 그 엔지니어가 에이전트에게 없는 지식을 가졌다는 신호다.
Q5컴파일이 되는 코드인데도 Matt가 푸시백한 이유 두 가지는?
첫째, 팀이 정해 둔 API 구조와 코드 사이의 연결 방식에 맞지 않았다. 둘째, 맥락이 없는 에이전트가 이미 있는 서비스를 중복으로 만들었다.
Q6발표자의 PR에 리뷰 때 지적이 몰리는 이유는?
발표자는 Rust를 몰라서 코드를 쓰는 동안 푸시백을 못 한다. 에이전트 코드를 그대로 믿고, Greptile이 5점 만점에 5점을 주면 그냥 넘긴다.
Q7트윈 리뷰어는 어떤 데이터로 만들었나?
Matt가 Go와 Rust 코드에서 푸시백한 세션 트레이스로 후속 학습했다. GitHub PR 리뷰 데이터는 쓰지 않았다.
Q8GitHub 리뷰 기록 대신 트레이스를 본 이유는?
팀 대부분이 터미널에서 Claude나 Pi 하네스로 리뷰한다. 그래서 GitHub에는 지적이 거의 남지 않는다.
Q9푸시백 말고 발표자가 골라 모은 세션 세 가지는?
사과, 골든 세션, 회귀. 흔한 실패 예는 이미 있는 Go 라이브러리나 mock 라이브러리를 에이전트가 다시 만드는 것이다.
Q10발표자가 권하는 시작 순서와 첫 단계는?
트레이스를 모은 뒤 스킬 → 평가 → 후속 학습 순서로 간다. 지금은 스킬로 대부분의 효과를 얻을 수 있으니 스킬부터 만든다.
Q11SFT와 DPO를 발표자는 어떻게 비유했고, 하드웨어 부담은 어땠나?
SFT는 책 여백의 메모(어댑터)다. 양자화해서 RTX 5090 같은 GPU와 Qwen 4B로 됐다. DPO는 요약 학습서(CliffNotes)다. 발표자 환경에서는 70B 이상 모델과 Brev의 GPU가 필요했다.

용어 정리

용어뜻
바이브 코딩Vibe coding. 코드를 직접 짜기보다 AI에게 말로 시켜 만드는 방식
반복 연습Reps. 같은 종류의 일을 여러 번 해 보며 실력을 쌓는 것
에이전트 세션에이전트와 한 번 일하는 동안 주고받은 대화와 작업 전체
트레이스Trace. 세션 동안 에이전트가 받은 입력과 한 행동을 순서대로 남긴 기록
OTel 컬렉터OpenTelemetry collector. 표준 형식의 관측 데이터를 모아 주는 수집기
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀. Claude Code, Codex, Pi 등
샌드박스Sandbox. 다른 시스템과 격리된 실행 환경
푸시백Push back. 사람이 에이전트의 작업에 "그건 아니다"라고 되받아치는 것
골든 세션Golden session. 눈여겨볼 만하다고 표시해 둔 세션
회귀Regression. 보통은 새 변경 때문에 잘 되던 것이 망가지는 것. 발표에서는 에이전트가 자주 무너지는 지점을 가리킨다
mock 라이브러리테스트에서 진짜 객체 대신 쓸 가짜 객체를 만들어 주는 라이브러리
스킬Skill. 에이전트가 필요할 때 불러 쓰는 지침과 스크립트 묶음
평가 (eval)모델이나 스킬의 결과 품질을 재는 테스트 묶음
사전학습 / 후속 학습Pre-training: 대량의 데이터로 모델의 기본 능력을 만드는 학습. Post-training: 그렇게 만든 모델을 특정 목적에 맞게 추가로 학습하는 것
SFT정답 예시를 보여 주며 모델을 추가 학습하는 미세조정. 보통 supervised fine-tuning의 약자다. 발표자는 specialized fine-tuning이라고 불렀다
어댑터Adapter. 원래 가중치는 그대로 두고 그 위에 얹어 학습하는 작은 추가 가중치
양자화Quantization. 숫자의 정밀도를 낮춰 모델을 작고 가볍게 만드는 것
QLoRA양자화한 모델 위에 어댑터를 얹어 학습하는 방법. 작은 GPU로도 미세조정을 할 수 있다
DPODirect preference optimization. 같은 질문에 대한 더 나은 답과 못한 답을 짝지어 보여 주고, 나은 쪽을 고르도록 학습하는 방법
파라미터 수 (4B, 70B)모델 크기를 나타낸다. B는 10억이다. 4B는 40억 개, 70B는 700억 개다
