에이전트를 10시간 넘게 일하게 하는 세 가지

Lovable은 2023년에 에이전트를 너무 일찍 만들다 회사가 망할 뻔했다. 지금은 기록과 실행을 나눈 런타임, 통째로 저장하고 복제하는 컴퓨터, 안팎 두 겹의 검증으로 에이전트를 상한 없이 돌린다.

원본 영상: What it takes to set intelligence free 발표: Fabian Hedin (Lovable 공동 창업자, CTO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 문맥상 확실한 것만 바로잡았다(Labbable → Lovable, V8·V2 → Vite, lab.dev → lovable.dev). mm:ss는 영상 위치다.

발표자는 Lovable CTO이고, 발표 전체가 자사 플랫폼 설명이다. 성능 수치와 "이번엔 작동한다"는 평가는 그 점을 감안해 읽자.

3분 요약
  1. 2023년, Lovable은 역할별 에이전트끼리 대화하는 정교한 구조를 만들었다. 제품이 오히려 나빠졌다. 당시 모델이 감당하지 못했다.
  2. 단순한 구조로 돌아가 살아남았다. 모델이 좋아진 지금은 에이전트를 다시 쓴다. 작업 시간 한도를 30분에서 '상한 없음'으로 풀었다.
  3. 런타임: 에이전트마다 받은편지함을 두고, 작업 기록을 Git처럼 덧붙이기만 하는 로그로 저장한다. 어느 시점에서든 갈라서 병렬 에이전트를 띄운다.
  4. 프롬프트는 기록에서 모델마다 새로 만든다. 실행 프로세스는 상태를 들고 있지 않다. 그래서 하루 700번 배포해도 10시간짜리 작업이 끊기지 않는다.
  5. 컴퓨터: 디스크, 메모리, 실행 중인 프로세스까지 통째로 체크포인트로 저장한다. 새 프로젝트는 약 230밀리초 만에 시작한다. 복제는 메모리 면에서 거의 공짜다.
  6. 개발 서버 Vite를 Rust로 다시 썼다. 발표자에 따르면 미리보기 대기가 40초에서 3초로, 메모리는 6.5분의 1로 줄었다.
  7. 검증은 두 겹이다. 턴 안에서는 빌드·타입·브라우저 검사, 턴 사이에서는 실제 사용자와 매출 지표를 에이전트에게 준다.
01

너무 일찍 만든 에이전트 00:50

발표자는 에이전트와 "복잡한 관계"라고 말하며 시작한다. 2023년, Lovable은 에이전트가 미래라고 보고 바로 만들기 시작했다. 그 판단 때문에 회사가 망할 뻔했다.

에이전트가 미래라는 건 맞았다. 틀린 건 '지금'이었다.Fabian Hedin, 01:00 부근 발언을 옮김

당시는 GPT-4 시절이었다. 복잡한 에이전트 시스템을 받칠 만큼 모델이 똑똑하지 않았다. 발표자는 지금은 다르다고 본다.

02

Lovable이 만드는 것 04:00

화면을 단순하게 보면 두 칸이다. 왼쪽 채팅에 사람이 원하는 것을 쓴다. 오른쪽 미리보기에 결과가 나온다.

2023년에는 이 방식으로 단순한 것만 만들었다. 지금은 같은 화면에서 아주 복잡한 것도 만든다. 발표자는 개발자용 도구들도 코드를 매일 들여다보지 않는 이런 화면으로 옮겨 가고 있다고 본다.

Lovable의 핵심 주장은 코드를 예전처럼 신경 쓰지 않아도 된다는 것이다. 발표자도 코딩하며 자라서 코드에 정이 들었다고 한다. 그래도 결국 중요한 건 코드가 아니라 결과라고 말한다. Lovable 사용자에게 결과란 사업을 만들고 돈을 버는 것이다.

플랫폼의 세 층 05:50

층들어 있는 것에이전트와의 관계
에이전트소프트웨어 제작에 특화된 코딩 에이전트. 브라우저로 결과를 직접 확인한다. GitHub에 연결된다쓴 코드는 사용자가 마음대로 가져다 쓸 수 있다
클라우드 06:20데이터베이스, 인증, 저장소, 백엔드 실행 환경, 보안 스캐너, 백업, 로그에이전트가 전부 들여다볼 수 있다. 여러 서비스를 따로 엮을 필요가 없다
비즈니스 07:00결제, 이메일 발송, 검색 최적화SEO, Google·Meta 광고, 분석과 전환에이전트가 이 모든 과정 안에 있다

사업에 성공하려면 코드만 써서는 안 된다. 그래서 비즈니스 층이 있다. 이 층은 뒤의 바깥 검증 루프와 이어진다.

03

30분 한도를 없앴다 07:50

예전에 Lovable은 에이전트가 한 번에 30분만 일하게 막았다. 그보다 오래 두면 믿을 수 없었기 때문이다. 지금은 시간 한도가 없다. 10시간 넘게 일하는 에이전트도 있다.

이렇게 오래 돌리려고 바꾼 것이 세 가지다. 이 노트의 나머지는 이 셋을 차례로 본다.

1 · 런타임 agent runtime

에이전트가 오래 돌아도 끊기지 않게 하는 실행 구조

2 · 컴퓨터 computer

에이전트가 개발 서버를 띄우고 결과를 확인하는 작업 공간

3 · 검증 verification

에이전트가 엉뚱한 방향으로 가지 않게 잡아 주는 피드백 루프

04

런타임 1: 받은편지함 08:50

에이전트에게 말을 거는 곳은 세 군데다. 사람, 다른 에이전트, 정해진 시각에 깨어나는 시스템이다. Lovable은 이들이 에이전트를 직접 건드리지 않게 했다.

  1. 세 출처 중 누구든 메시지를 보낸다. 예: "지금 어디까지 했어?"
  2. 메시지는 에이전트마다 따로 있는 받은편지함 inbox에 쌓인다.
  3. 에이전트는 늘 켜져 있고 하던 일을 계속한다. 요청, 도구 호출, 결과 받기까지 한 묶음을 끝낸다.
  4. 그 시점에 에이전트가 받은편지함의 메시지를 자기 작업 기록 trajectory으로 옮긴다.

누구든 메시지를 넣을 수 있다. 하지만 그 메시지가 기록에 들어가는 시점은 에이전트가 정한다. 겉보기에는 우리가 흔히 쓰는 에이전트 대화와 같다.

05

런타임 2: Git을 닮은 작업 기록 10:20

작업 기록은 지금까지 에이전트에게 일어난 일 전부다. 에이전트 기억의 바탕이기도 하다. Lovable은 이 기록을 Git을 본떠 설계했다.

  • 기록은 덧붙이기만 하는 로그 append-only log다. 고치거나 지우지 않는다.
  • 이벤트마다 바로 앞 이벤트, 곧 부모를 가리킨다.
  • 두 이벤트가 같은 부모를 가리키면 기록이 갈라진다. 이것이 포크 fork다.
  • 포크하면 기록의 어느 시점에서든 병렬 에이전트를 띄울 수 있다. 공통된 앞부분은 복사하지 않고 함께 쓴다. 10:40
  • Git과 달리 합치기 merge는 하지 않는다. 두 에이전트의 기록을 합치면 무슨 뜻이 되는지 분명하지 않기 때문이다. 대신 갈라진 에이전트끼리 대화할 수 있다.

아래 표는 구조를 보여 주려고 만든 예시다. 발표에 나온 데이터가 아니다.

이벤트 (예시)부모내용
e1없음사용자: "로그인 화면 만들어 줘"
e2e1도구 호출: 파일 쓰기
e3e2결과: 빌드 성공
e4e3에이전트 A: 디자인을 다듬는다
e5e3에이전트 B (포크): 다른 방식으로 구현해 본다

e4와 e5가 같은 부모 e3을 가리킨다. 두 에이전트는 e1~e3을 복사하지 않고 함께 쓴다.

기록과 프롬프트는 다르다 11:10

작업 기록에는 모든 것이 들어간다. 도구 호출 하나하나, 그 성공과 실패, 플랫폼에서 일어난 다른 일까지. 그중 상당수는 프롬프트에 넣을 필요가 없다.

작업 기록일어난 일 전부도구 호출, 성공·실패, 플랫폼 이벤트
→
프롬프트모델과 작업에 맞게 만든 것골라 담고, 오래된 부분은 요약한다

왜 나눌까. 기록이 길어지면 앞부분을 요약해 줄여야 한다. 이것을 컴팩션 compaction이라 한다. 언제 요약할지는 모델마다 다르다. 모델이 한 번에 읽을 수 있는 길이, 곧 컨텍스트 길이 context length가 다르기 때문이다.

기록을 따로 두면 같은 기록에서 어떤 모델, 어떤 작업에든 가장 알맞은 프롬프트를 그때그때 만들 수 있다.

어느 시점이든 다시 그린다 12:20

발표자는 내부 디버그 도구를 보여 줬다. 슬라이더를 끌면 이벤트 156개 중 고른 시점의 화면이 그대로 다시 그려진다. 기록만 있으면 어느 시점의 UI든, 플랫폼에서 일어난 다른 일이든 재현할 수 있다는 뜻이다.

06

런타임 3: 상태 없는 프로세스 13:00

에이전트를 실제로 돌리는 프로세스는 작업 기록과 분리돼 있다.

  • 프로세스는 거의 상태가 없다 stateless. 중요한 정보를 자기 안에 들고 있지 않다.
  • 호출 하나, 도구 호출 하나, 턴 하나가 끝날 때마다 결과를 작업 기록에 저장한다.
  • 그래서 프로세스는 언제든 내려가고 새로 뜰 수 있다.
왜 필요한가 13:30 Lovable은 이 시스템에 하루 700번 배포한다. 약 2분에 한 번이다. 10시간째 고객 일을 하는 에이전트를 배포 때마다 끊을 수는 없다. 그렇다고 옛 버전에 계속 둘 수도 없다. 새 기능일 수도 있고, 리눅스 커널 보안 취약점처럼 당장 고쳐야 하는 것일 수도 있다.
프로세스가 기억을 들고 있으면배포 = 작업 중단프로세스가 내려가면 진행 상황도 사라진다
→
기억을 기록에 맡기면배포 = 다른 프로세스가 이어받기에이전트 하나가 작업 하나를 계속 맡는다

정리하면 에이전트와 작업은 하나로 이어지고, 그 뒤의 계산은 여러 프로세스가 번갈아 맡는다. 10시간이든 그 이상이든 배포와 상관없이 작업이 이어진다.

07

컴퓨터 1: 통째로 저장하기 14:40

두 번째는 에이전트가 실제로 일하는 컴퓨터다. 에이전트는 여기서 개발 서버를 띄우고, 자기가 만든 것을 확인한다.

Lovable은 에이전트용 격리 환경, 곧 샌드박스 sandbox를 여러 업체 것으로 바꿔 가며 써 봤다. 지금은 직접 공들여 만든 방식에 정착했다. 컴퓨터 전체를 체크포인트 checkpoint로 저장하는 방식이다.

  1. 새 프로젝트 15:00: 모두가 같이 쓰는 골든 체크포인트 golden checkpoint를 복사한다. OS, 시스템 서비스, 자주 쓰는 도구, 바로 띄울 수 있는 개발 서버가 들어 있다. 디스크만이 아니라 메모리와 실행 중인 프로세스까지 담겨 있다. 복사에 약 230밀리초가 걸린다.
  2. 작업 중 15:40: 프로젝트의 코드와 의존성도 함께 체크포인트에 쌓인다. 에이전트가 턴을 끝낼 때마다 저장한다.
  3. 다시 쓸 때: 저장한 체크포인트에서 1초 안에 컴퓨터를 다시 띄운다.
자원을 아끼는 방법 사용자가 10분쯤 자리를 비우면 컴퓨터를 내린다. 돌아오면 사용자가 눈치채지 못할 만큼 빨리 다시 띄운다. 발표자는 오가던 중인 요청도 떨어뜨리지 않는다고 말했다.
08

컴퓨터 2: 복제와 메모리 16:10

작업 기록처럼 컴퓨터도 포크한다. 예를 들어 Lovable에는 Drafts라는 기능이 있다. 서로 다른 환경에서 따로 작업해 보는 기능이다. 이걸 하려면 지금 쓰는 컴퓨터를 복제해야 한다. 발표에서는 두 개를 보여 줬지만 수백 개도 띄운다고 했다.

수백 개를 감당하려면 최적화가 필요했다. 발표자가 소개한 것은 두 가지다.

RAM copy-on-write 16:50
  • 복제 직후에는 원본의 메모리를 같이 쓴다.
  • 그래서 복제는 메모리 면에서 거의 공짜다.
  • 어떤 프로세스가 메모리에 쓰는 순간, 그 페이지만 복사한다.
  • 새 메모리는 그때부터 든다.
메모리 스트리밍 17:20
  • 샌드박스 하나에 메모리가 수백 MB 든다.
  • 잘 안 쓰는 객체 저장소 cold object storage에서 디스크로, 다시 VM 메모리로 옮기면 몇 초가 걸린다.
  • 그래서 메모리가 다 도착하기 전에 부팅한다.
  • OS가 쓰는 메모리가 먼저 온다. 다른 프로세스는 자기 메모리가 오는 대로 일을 시작한다.

둘 다 같은 생각이다. 필요해지기 전에는 복사하지도, 기다리지도 않는다.

09

컴퓨터 3: Rust로 다시 쓴 Vite 18:00

Lovable은 더 빠르게 만들 방법을 찾다가 개발 서버까지 손댔다. 개발 서버 dev server는 코드를 고치면 바로 미리보기에 반영해 주는 서버다.

  • 대상은 Vite다. JavaScript 생태계의 메타 프레임워크 meta-framework 대부분이 쓰는 개발 서버다.
  • Lovable은 Vite를 포크해 Rust로 다시 썼다.
  • 가장 큰 변화는 Node.js를 걷어 낸 것이다. Vite는 Node.js 위에서 돈다. 이 의존을 없애고 Rust 실행 파일 하나로 만들었다.

자막에는 "V8", "V2"로 들린다. "JavaScript 메타 프레임워크 대부분이 쓰는 개발 서버"이고 Node.js 위에서 돈다는 설명으로 보아 Vite다.

콜드 스타트 "2배"와 미리보기 "40초 → 3초"(약 13배)는 같은 측정이라면 서로 맞지 않는다. 발표자는 두 숫자를 한 문장에 이어 말했지만 둘의 관계는 설명하지 않았다. 미리보기 시간에는 앞 장의 체크포인트와 메모리 최적화가 함께 반영됐을 수 있다(추측). 자막의 "code starts"는 문맥상 콜드 스타트로 읽었다.

앱을 쥐면 메모리도 쥔다 18:40

컴퓨터 안에서 도는 앱을 직접 만들면, 앱이 메모리에 쓰는 방식도 정할 수 있다. 메모리 쓰기를 통제하면 앞의 copy-on-write 복제가 더 싸진다.

그 결과 아주 많은 에이전트를 병렬로 돌릴 수 있다. 예를 들어 버그 하나를 여러 에이전트가 각기 다른 방법으로 고쳐 보게 한다. 앱 성능을 높일 방법을 동시에 여러 개 탐색하게 할 수도 있다.

10

검증: 안쪽 루프와 바깥 루프 19:10

오래 일하는 에이전트에게는 피드백 루프가 꼭 있어야 한다. 행동 하나를 할 때마다 그게 좋은 행동이었는지 알아야 엉뚱한 방향으로 가지 않는다. 앞에서 본 컴퓨터와 개발 서버가 검증의 큰 부분을 맡는다.

발표자는 피드백을 두 겹으로 나눈다. 기준은 턴 turn이다. 턴은 에이전트가 일하다가 사용자에게 차례를 넘기기까지의 한 단위다.

안쪽 루프 inner loop · 턴 안 19:40
  • 빌드가 되는가
  • lint 오류, 타입 오류가 있는가
  • 미리보기에서 런타임 오류가 나는가
  • 헤드리스 브라우저 headless browser로 만든 앱을 직접 돌아다녀 본다

에이전트가 코드가 제대로 도는지 스스로 확인한다.

바깥 루프 outer loop · 턴 사이 20:00
  • 방문자가 실제로 어떻게 행동하는가
  • 사용자가 온라인에서 뭐라고 말하는가
  • 자동 A/B 테스트: 문구를 바꿔 전환이 오르는지 본다
  • 결제 거래, 전환 같은 비즈니스 지표

에이전트가 제품이 사업으로 잘 되는지 본다.

바깥 루프는 2장의 비즈니스 기능과 이어진다. 결제와 분석을 플랫폼이 직접 쥐고 있으니 에이전트가 그 지표를 볼 수 있다. 발표자는 그래서 에이전트가 코드뿐 아니라 제품의 비즈니스 전략까지 다듬도록 도울 수 있다고 주장한다. 20:30

다시 에이전트끼리 21:00

Lovable은 런타임, 컴퓨터, 검증 세 가지를 계속 키워 갈 계획이다.

  • 지금 이 시스템은 분당 수십억 토큰을 처리한다고 발표자는 말했다.
  • 에이전트마다 컴퓨터를 띄울 수 있다. 여러 에이전트가 컴퓨터 하나를 같이 쓸 수도 있다.
  • 결국 처음에 실패했던 구조로 돌아왔다. 에이전트가 에이전트와 대화하며 일을 나눈다.
2023년 무렵에이전트끼리 대화제품이 나빠졌다
→
지금에이전트끼리 대화대규모로 작동한다 (발표자 주장)
발표자가 든 차이 모델이 복잡한 구조를 받칠 만큼 똑똑해졌다. 그리고 오래 도는 에이전트를 받치는 런타임, 컴퓨터, 검증을 만들었다. 발표자는 이번에 작동하는 이유로 이 최적화들을 든다.

3:40에는 "분당 10억 토큰 넘게", 21:20에는 "분당 수십억 토큰"이라고 했다. 정확한 값은 나오지 않았다. 또 발표에는 이번 구조가 얼마나 잘 되는지 보여 주는 성공률 같은 품질 지표가 없다. 근거는 처리 규모와 구조 설명이다.

발표자는 lovable.dev에서 직접 써 볼 수 있다고 소개하며 마쳤다. 사용자에게는 이 복잡한 구조가 보이지 않고, 단순한 화면만 보인다는 말과 함께다.

핵심 정리

  1. 에이전트가 미래라는 판단은 맞았지만 2023년에는 너무 일렀다. 당시 모델이 복잡한 구조를 감당하지 못했다.
  2. 역할별 에이전트끼리 대화하는 구조는 제품을 나쁘게 만들었다. 단순한 구조로 돌아가 살아남았다.
  3. 지금은 작업 시간 한도를 30분에서 상한 없음으로 풀었다. 10시간 넘게 일하는 에이전트도 있다.
  4. 에이전트마다 받은편지함이 있다. 사람, 에이전트, 스케줄러가 넣고, 에이전트가 한 묶음을 끝낸 시점에 기록으로 옮긴다.
  5. 작업 기록은 Git처럼 부모를 가리키는 덧붙이기만 하는 로그다. 포크는 되고 머지는 안 된다.
  6. 기록 ≠ 프롬프트. 프롬프트는 기록에서 모델마다 알맞게 만들어 낸다.
  7. 프로세스는 상태가 없다. 하루 700번 배포해도 장시간 작업이 이어진다.
  8. 컴퓨터는 디스크, 메모리, 실행 중인 프로세스까지 통째로 체크포인트한다. 새 프로젝트는 약 230밀리초, 재기동은 1초 안이다.
  9. copy-on-write, 메모리 스트리밍, Rust로 다시 쓴 Vite로 수백 개 복제와 병렬 탐색을 싸게 만든다.
  10. 검증은 두 겹이다. 턴 안의 코드 검사와 턴 사이의 실제 사용자·매출 지표.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Lovable이 2023년에 망할 뻔한 이유는?
에이전트를 너무 일찍 만들었다. GPT-4 시절 모델로는 복잡한 에이전트 시스템이 돌아가지 않았다. 역할별 에이전트끼리 대화하는 구조가 오히려 제품을 나쁘게 만들었다.
Q22024년 말에 되돌아간 단순한 구조는 어떤 모양인가?
작은 LLM 몇 개는 지식 검색만 하고, 메인 LLM 하나가 사용자 답변과 코드를 한 메시지에 쓴다. 빠르고 안정적이었다.
Q3Lovable이 보는 사용자의 "결과물"은 무엇인가? 그래서 플랫폼에 무엇을 넣었나?
코드가 아니라 제품, 곧 사업이다. 그래서 결제, 이메일, SEO, 광고, 분석 같은 비즈니스 기능을 넣고 에이전트가 모두 다루게 했다.
Q4에이전트에게 메시지를 보내는 세 출처는? 메시지는 어떻게 전달되나?
사람, 다른 에이전트, 정해진 시각에 깨어나는 시스템. 메시지는 에이전트별 받은편지함에 쌓이고, 에이전트가 요청·도구 호출·결과 한 묶음을 끝낸 시점에 자기 작업 기록으로 옮긴다.
Q5작업 기록을 Git처럼 만들어 얻는 것과 못 하는 것은?
얻는 것: 같은 부모에서 갈라(포크) 어느 시점에서든 병렬 에이전트를 띄울 수 있고, 공통 기록을 복사하지 않는다. 못 하는 것: 합치기(머지). 합친 결과가 무슨 뜻인지 분명하지 않기 때문이다.
Q6작업 기록과 프롬프트를 나눈 이유는?
컨텍스트 길이가 다른 모델마다 요약(컴팩션) 시점이 다르다. 전체 기록을 그대로 두고, 모델과 작업에 맞는 프롬프트를 그때그때 만들어 내기 위해서다.
Q7하루 700번 배포하면서 10시간짜리 작업을 끊지 않는 방법은?
프로세스가 상태를 들고 있지 않다. 호출, 도구 호출, 턴마다 결과를 작업 기록에 저장한다. 배포로 프로세스가 바뀌어도 새 프로세스가 기록을 이어받는다.
Q8골든 체크포인트에는 무엇이 들어 있고, 새 프로젝트에 복사하는 데 얼마나 걸리나?
OS, 시스템 서비스, 자주 쓰는 도구, 바로 띄울 수 있는 개발 서버. 디스크뿐 아니라 메모리와 실행 중인 프로세스까지 담겨 있다. 약 230밀리초.
Q9컴퓨터를 수백 개 복제해도 감당되게 한 두 가지 최적화는?
RAM copy-on-write: 쓰기가 일어난 메모리 페이지만 그때 복사한다. 메모리 스트리밍: 메모리가 다 도착하기 전에 부팅하고, OS 메모리부터 받는다.
Q10Vite를 Rust로 다시 써서 얻었다고 한 것은?
Node.js 의존을 없애 실행 파일 하나로 만들었다. 미리보기 대기 40초 → 3초, 메모리 6.5분의 1. 메모리 쓰기 방식을 통제하게 돼 복제도 더 싸졌다. 모두 발표자가 말한 자체 측정치다.
Q11안쪽 루프와 바깥 루프는 각각 언제, 무엇을 보나?
안쪽: 턴 안에서 빌드, lint·타입 오류, 런타임 오류, 헤드리스 브라우저 탐색. 바깥: 턴 사이에서 방문자 행동, 온라인 반응, A/B 테스트, 결제·전환 같은 비즈니스 지표.
Q12"에이전트끼리 대화" 구조가 이번에는 작동한다는 근거로 발표자가 든 것은? 빠진 것은?
든 것: 모델이 똑똑해졌고, 런타임·컴퓨터·검증 최적화를 만들었으며, 분당 수십억 토큰 규모로 돌고 있다. 빠진 것: 성공률 같은 품질 지표.
