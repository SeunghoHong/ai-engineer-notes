코딩 에이전트를 시스템처럼 엔지니어링하기

코딩 에이전트를 각자 노트북에서 말로 부리는 방식은 사람 속도에 묶인다. 발표자는 에이전트의 작업 흐름을 코드로 정의하고, 모든 실행을 기록하고 재서 스스로 나아지게 하는 "소프트웨어 팩토리"를 제안한다.

원본 영상: Engineer Your Coding Agents Like Any Other System 발표: Zach Lloyd (Warp 창업자·CEO, 전 Google 프린시펄 엔지니어, Google Docs 제품군 엔지니어링 리드)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 성과는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 발표자의 회사 Warp는 기업이 내부 소프트웨어 팩토리를 만드는 플랫폼을 판다. 자막에서 뭉개진 이름은 확실한 것만 바로잡고, 확실하지 않은 것에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 지금 대부분은 각자 로컬에서 에이전트와 대화하며 일한다. 이 방식은 사람 처리량에 묶이고, 비용 관리와 보안 통제가 어렵다.
  2. 발표자가 말하는 소프트웨어 팩토리는 자동화 몇 개나 스킬 묶음이 아니다. "클라우드 코딩 에이전트를 계속 측정하고 개선하는, 코드로 정의한 닫힌 루프 시스템"이다.
  3. 세 조건이 있다. 코드로 정의하고, 닫힌 루프로 돌리고, 모든 것을 잰다.
  4. 에이전트는 새 엔지니어링 재료다. 디버거와 프로파일러 대신 eval, 자기 개선 루프, 벤치마크, A/B 테스트가 새 도구다.
  5. 인프라는 6층이다. 아래부터 코드로 쓴 팩토리, 데이터와 맥락, 컴퓨트, 추론, 오케스트레이션, API·MCP.
  6. 모든 실행을 기록하고 다른 에이전트가 점수를 매긴다. 에이전트가 실패 패턴을 찾아 팩토리 정의에 PR을 올린다.
  7. 어떤 모델, 스킬, 하네스가 최고인지는 내 실제 데이터로 만든 벤치마크로만 답할 수 있다.
01

로컬 에이전트의 세 가지 한계 01:00

발표자가 만나는 개발자와 플랫폼 팀은 대부분 아직 이렇게 일한다. 각자 자기 컴퓨터에서 코딩 에이전트를 돌린다. 여러 개를 동시에 돌리기도 한다. 터미널에서 돌리기도 하고, 에이전트형 개발 환경agentic development environment에서 돌리기도 한다.

객석에 손을 들어 보게 했을 때도 대부분 이 방식이었다. 다만 전부는 아니었다. 발표자는 이 방식이 바뀔 것이고, 이미 바뀌기 시작했다고 본다. 이유는 셋이다.

한계무슨 뜻인가
사람 처리량 01:50에이전트마다 사람이 대화하며 지시해야 하면 자동화할 수 없다. 전체 속도가 사람 속도에 묶인다.
비용과 생산성 02:10모두가 자기 설정, 모델, 스킬을 따로 고른다. 그러면 에이전트를 비용과 생산성 면에서 효율적으로 쓰는지 확인하기 어렵다. 플랫폼 팀과 엔지니어링 리더에게서 자주 듣는 이야기다.
보안과 거버넌스 02:30모두가 자기 에이전트를 직접 설정해 돌리면 큰 보안 문제가 생긴다. 누가 무엇을 쓰게 할지 정하고 지키는 일governance도 어려워진다.
지금 대부분로컬에서 대화하며 부리는 에이전트사람 한 명이 에이전트 여러 개를 붙잡고 하나씩 지시한다

02

팩토리가 아닌 것 03:00

발표자는 다가오는 것을 느슨하게 소프트웨어 팩토리software factory라고 부른다. 객석에 물으니 팩토리를 만들고 있거나 쓰고 있는 사람도 많았다. 발표자는 대화형 에이전트 쪽보다 오히려 많아 보인다고 했다.

이 말은 사람마다 다른 뜻으로 쓴다. 그래서 발표자는 팩토리가 아닌 것부터 꼽는다.

  • 느슨하게 모은 자동화 몇 개
  • AI 팀원 모음 AI teammates
  • 함께 쓰는 스킬과 MCP 묶음
  • 개인이 돌리는 에이전트 무리 personal agent swarms

넷 다 쓸모 있는 기본 재료primitive다. 하지만 발표자는 이것들이 도착 지점은 아니라고 본다.

03

정의: 코드로 정의한 닫힌 루프 03:40

클라우드 코딩 에이전트를 계속 측정하고 개선하는, 코드로 정의한 닫힌 루프 시스템.발표자의 정의를 옮김 · "a code-defined closed loop system for continuously measuring and improving cloud coding agents"

클라우드 코딩 에이전트는 개인 노트북이 아니라 원격 실행 환경에서 도는 에이전트다. 정의에는 세 가지 요소가 들어 있다.

① 코드로 정의한다 04:00

팩토리를 키우려면 먼저 팩토리 전체를 선언형 언어declarative language로 적어야 한다. 선언형은 실행 순서가 아니라 원하는 상태를 적는 방식이다. 발표자는 Terraform처럼 코드 파일 묶음으로 적으라고 한다. 적을 것은 이렇다.

  • 어떤 코딩 에이전트를 돌리는가
  • 무엇이 에이전트를 실행시키는가 (트리거trigger)
  • 일이 들어오면 어떤 흐름을 타는가. 예를 들어 분류에서 스펙 작성까지
  • 어떤 MCP를 쓸 수 있는가
  • 에이전트가 어디서 도는가

이렇게 적는 게 왜 중요한지는 05 인프라 스택에서 나온다.

② 닫힌 루프로 돈다 04:30

전형적인 루프는 소프트웨어 개발 수명 주기SDLC 그대로다.

일의 흐름 사람이 낸 아이디어나 자동 신호 → 분류 → 구현 → 검증 → 모니터링

핵심은 루프가 닫혀 있다는 점이다. 에이전트가 많이 돌수록 이 루프를 더 효율적으로 다듬을 수 있다. 다듬는 방법은 07~09에서 나온다.

③ 모든 것을 잰다 05:10

감vibes으로 에이전트를 배치하면 세 가지를 확신할 수 없다. 가장 좋은 품질을 얻고 있는가. 가장 낮은 비용을 쓰고 있는가. 처리량을 최대로 뽑고 있는가.

그래서 재려는 태도와 잴 수 있는 도구가 둘 다 필요하다.

04

에이전트는 새 엔지니어링 재료 05:40

발표자가 이 발표에서 하나만 가져가길 바라는 생각이 있다. 지난 1년 사이 지능형 에이전트라는 새 재료가 생겼다. 이 재료를 가장 잘 쓰도록 그 주변에 시스템을 엔지니어링하는 일, 이것이 새로운 근본 문제라는 것이다.

발표자는 이 일이 정원 가꾸기나 레시피 따라 하기가 아니라고 말한다. 엔지니어는 경력 내내 엔지니어링 방식으로 문제를 풀어 왔다. 에이전트를 새 엔지니어링 재료로 보면 쓰는 방식도 자연스럽게 그쪽으로 간다.

도구도 바뀐다 06:40

손으로 만들던 시절디버거, 프로파일러, Chrome DevTools발표자가 Google에서 익힌 도구. 최고의 엔지니어와 그저 그런 엔지니어를 갈랐다
→
팩토리 엔지니어링eval, 자기 개선 루프, 벤치마크, A/B 테스트에이전트 시스템 전체를 재고 고치는 도구

발표자는 이 새 도구를 다루는 기술을 팩토리 엔지니어링factory engineering이라고 부른다. 스스로 물어볼 질문은 이렇다. eval을 세울 수 있는가. 실제로 작동하는 자기 개선 루프를 만들 수 있는가. 벤치마크를 쓸 수 있는가. 팩토리를 A/B 테스트할 수 있는가.

제품 엔지니어링은 그대로 남는다 07:40

팩토리 엔지니어링만 하게 되는 건 아니다. 내보낸 제품이 사용자와 고객의 실제 문제를 푸는지는 여전히 엔지니어가 책임진다.

다만 앞으로는 모든 엔지니어가 제품을 만드는 일에 더해, 제품을 만드는 시스템을 개선하는 법도 배워야 한다고 발표자는 본다.

05

팩토리 인프라 스택 6층 08:00

에이전트 시스템을 첫 원리부터 설계하면 대략 이런 층이 나온다고 발표자는 말한다. 꼭 이 모양일 필요는 없다. 아래층이 위층을 받친다.

  1. 6API·MCP 우선 API & MCP first 10:10사람뿐 아니라 다른 코딩 에이전트도 팩토리를 쓸 수 있게 한다. Slack, Linear, Jira, GitHub처럼 일이 일어나는 곳에 붙는다.
  2. 5오케스트레이션 orchestration 10:10일을 팩토리 안에서 다음 단계로 옮긴다. 발표자는 가장 덜 흥미롭지만 꼭 필요한 층이라고 했다.
  3. 4추론 inference 09:30모델은 고정값이 아니라 시험할 변수다. 여러 모델과 여러 하네스를 지원한다. Claude Code, Codex, Pi(추정), Warp는 하네스마다 성질이 다르다. 조직 맥락을 담은 자체 하네스도 쓸 수 있어야 한다.
  4. 3컴퓨트 compute 09:20샌드박스에서 돌린다. 보안이 좋아지고, 실행을 똑같이 되풀이할 수 있다. 여러 플랫폼을 지원하는 편이 좋다.
  5. 2데이터와 맥락 data & context 08:50에이전트가 만든 것을 전부 기록한다. 대화, 산출물, 에이전트가 만든 영상과 스크린샷까지 남긴다. 이 기록이 팩토리를 개선할 원재료다.
  6. 1코드로 쓴 팩토리 factories as code 08:20에이전트 작업 흐름 전체를 코드로 정의한다. 브랜치를 따서 다른 설정을 시험할 수 있다. 되돌릴 수도 있다. 무엇보다 에이전트가 팩토리 개선안을 직접 제안하는 자기 개선이 가능해진다.

Pi는 자막에 "Py"로 적혀 있다. 하네스 이름으로 보아 Pi 코딩 에이전트로 추정했다.

시연: 정의 파일과 실시간 기록 10:40

여기부터 벤치마크까지는 발표자 회사의 제품(Warp 팩토리) 시연이다. 발표자는 팩토리를 직접 만들어도 같은 원리가 적용된다고 했다. 제품 소개가 섞여 있으니 감안해 읽자.

팩토리 정의 파일 11:00

Terraform을 안다면 익숙한 모양의 코드다. "이것이 내 팩토리다"라고 선언하는 방식이다. 시연 화면의 정의에는 이런 것이 들어 있었다.

정의에 들어가는 것뜻
정책 policies팩토리에 걸리는 규칙
저장소팩토리가 접근하는 코드 저장소
트리거팩토리를 실행시키는 조건

팩토리를 이루는 다른 요소도 모두 코드 정의를 가진다.

팀 전체를 실시간으로 본다 11:30

Google Docs처럼 여럿이 함께 보는 화면이다. Warp 팀 엔지니어 전원의 코딩 에이전트가 지금 무엇을 하는지 실시간으로 보여 준다.

동료 한 명의 작업을 눌러 보면 그 작업을 Slack에서 시작했다는 것이 보인다. 만든 산출물도 보인다. 실제 대화 내용과 생성 결과까지 열어 볼 수 있다.

실시간 보기보다 중요한 것 실시간으로 보는 것도 좋다. 하지만 핵심은 이 정보를 전부 모은다는 점이다. 모은 기록이 있어야 팩토리를 개선할 수 있다.
07

시연: 지표와 온라인 평가 12:30

한곳에 모이면 바로 잴 수 있다 12:30

기록이 중앙에 쌓이면 모두의 노트북에 무언가를 설치하지 않아도 된다. 에이전트가 어떻게 일하는지 바로 알 수 있다.

지표예
전통적인 산출 지표DORA 지표, 사이클 타임
자동화 수준PR 하나당 사람이 개입한 횟수
처리량정해진 시간에 끝낸 일의 양
비용에이전트를 돌리는 데 드는 돈

발표자는 이 데이터가 없으면 눈을 감고 비행하는 셈이라고 말한다.

온라인 평가 13:20

eval은 결과물의 품질을 재는 시험이다. 온라인 평가online eval는 실제로 도는 모든 에이전트 세션에 걸쳐 계속 돌아가는 eval이다.

방법은 이렇다. 세션이 돌며 결과를 기록한다. 다른 에이전트가 나중에 그 기록을 다시 본다. 그리고 세션이 얼마나 잘했는지 보여 주는 기준으로 점수를 매긴다.

예: 불필요한 테스트 찾기 13:50 코딩 에이전트는 가끔 필요 없는 테스트를 쓴다. 흔한 실패 유형이다. Warp는 이것을 잡는 eval을 둔다. 잡은 뒤에는 두 가지를 묻는다. 왜 테스트를 너무 많이 쓰는가. 팩토리에서 무엇을 바꾸면 줄어드는가.

여기까지의 흐름 14:20

  1. 모든 실행을 기록한다.
  2. 실행이 따라갈 루프를 정의한다.
  3. 각 실행이 루프의 어디쯤에 있는지 본다.
  4. 실행이 만든 데이터를 모은다.
  5. 그 데이터에 온라인 평가를 건다. 점수가 개선할 곳을 알려 준다.
08

자기 개선: 에이전트가 팩토리에 PR을 낸다 15:00

평가 점수를 사람이 보는 대신 에이전트가 본다. 발표자는 이것을 자기 개선self-improvement이라고 부른다.

  1. 점수 결과를 본다.
  2. 실패한 실행 몇 건에서 공통 패턴을 찾는다.
  3. 해결책을 제안한다.
  4. 그 해결책은 팩토리 정의 파일에 대한 PR로 올라온다.

팩토리를 코드로 정의해 둔 덕분에 가능한 일이다. 코딩 에이전트가 자기들이 일하는 방식의 문제를 진단하고, 고칠 코드를 직접 낸다.

발표에서는 이 PR을 누가 검토하고 머지하는지 따로 말하지 않았다.

09

벤치마크는 내 데이터로 15:50

온라인에서는 늘 "이게 최고의 모델이다", "이게 새로 나온 최고의 스킬이다", "이게 최고의 하네스다" 같은 말이 오간다. 발표자는 이 질문에 제대로 답하는 길이 하나뿐이라고 한다. 자기 데이터로 시험하는 것이다.

  1. 실제 작업 데이터로 벤치마크 세트를 만든다.
  2. 그 과제들을 다른 설정으로 다시 돌린다replay.
  3. 모델, 하네스, 팩토리 설정을 바꿨다면 결과가 어땠을지 비교한다.

시연 화면은 새 모델이 나올 때 SWE-bench나 Terminal-Bench에서 보는 그림과 비슷하다 16:40. 모델마다 비용과 품질이 어떻게 갈리는지 보여 준다. 노릴 곳은 비용이 낮고 품질이 높은 구역이다. 발표 화면에서는 왼쪽 위였다. 다른 점은 이 그림을 자기 실제 데이터로 그린다는 것이다.

모델만 바꿔 보는 게 아니다. "이 스킬들을 빼면 팩토리가 나아지나, 나빠지나?" 같은 질문도 시험한다.

10

결론: 에이전트를 엔지니어링하라 17:10

발표자는 Warp가 이 도구들로 처리량을 크게 올리고 비용을 낮췄다고 말한다. Warp에는 비용이 중요해서 이 순환을 계속 돌린다고 한다. 성능 기준선을 잡고, 점수를 매기고, 벤치마크를 돌리고, 시험한다.

구체적인 수치는 발표에 나오지 않았다. 자기 회사 제품으로 얻었다는 성과이니 감안해 읽자.

에이전트를 엔지니어링하라. 새로운 엔지니어링 재료다.발표자의 마지막 메시지를 옮김 · "Engineer your agents. It's a new engineering primitive."

에이전트에서 최대한 뽑아낼 방법을 생각하고, 그에 맞는 시스템을 지으라는 뜻이다.

엔지니어라는 직업에 대해 17:50

요즘 엔지니어가 무슨 의미인지를 두고 불안이 많다는 것을 발표자도 안다. 발표자도 이제 코드를 직접 쓰지 않는다. 그래도 경력 내내 배운 엔지니어링 기술은 여전히 다 쓰고 있다. 그래서 발표자에게 지금은 여전히 신나는 시기다.

11

핵심 정리

  1. 로컬에서 대화하며 에이전트를 부리는 방식은 사람 처리량, 비용·생산성 관리, 보안·거버넌스에서 막힌다.
  2. 자동화 몇 개, AI 팀원, 스킬·MCP 묶음, 개인 에이전트 무리는 재료일 뿐 팩토리가 아니다.
  3. 팩토리는 클라우드 코딩 에이전트를 계속 측정하고 개선하는, 코드로 정의한 닫힌 루프 시스템이다.
  4. 에이전트, 트리거, 일의 흐름, MCP, 실행 위치를 Terraform처럼 선언형 코드로 적는다.
  5. 감이 아니라 측정으로 품질, 비용, 처리량을 판단한다.
  6. 새 도구는 eval, 자기 개선 루프, 벤치마크, A/B 테스트다. 이를 다루는 기술이 팩토리 엔지니어링이다.
  7. 스택은 아래부터 코드로 쓴 팩토리, 데이터와 맥락, 컴퓨트, 추론, 오케스트레이션, API·MCP다.
  8. 모든 실행을 기록하고, 다른 에이전트가 온라인 평가로 점수를 매긴다. 예: 불필요한 테스트 찾기.
  9. 자기 개선: 에이전트가 실패 패턴을 찾아 팩토리 정의 파일에 PR을 올린다.
  10. 최고의 모델, 스킬, 하네스는 내 데이터로 만든 벤치마크를 다시 돌려 봐야 안다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1로컬에서 대화하며 에이전트를 부리는 방식의 세 가지 한계는?
사람 처리량에 묶여 자동화가 안 된다. 각자 설정, 모델, 스킬을 골라 비용과 생산성을 관리하기 어렵다. 보안과 거버넌스 문제가 크게 생긴다.
Q2발표자가 "팩토리가 아니다"라고 한 네 가지는?
느슨한 자동화 모음, AI 팀원 모음, 함께 쓰는 스킬·MCP 묶음, 개인 에이전트 무리. 쓸모 있는 재료지만 도착 지점은 아니다.
Q3발표자의 팩토리 정의와 세 요소는?
클라우드 코딩 에이전트를 계속 측정하고 개선하는, 코드로 정의한 닫힌 루프 시스템. 세 요소는 코드로 정의, 닫힌 루프, 측정 가능이다.
Q4팩토리를 선언형 코드로 적을 때 들어가는 것은?
돌릴 에이전트, 트리거, 일의 흐름, 쓸 수 있는 MCP, 실행 위치. 시연 화면에는 정책, 저장소, 트리거, 청사진이 있었다.
Q5팩토리를 코드로 정의하면 얻는 세 가지는?
브랜치를 따서 다른 설정을 시험할 수 있다. 되돌릴 수 있다. 에이전트가 팩토리 개선안을 PR로 내는 자기 개선이 가능해진다.
Q6발표자가 Google에서 익힌 도구와 팩토리 엔지니어링의 도구는 각각 무엇인가?
예전에는 디버거, 프로파일러, Chrome DevTools. 이제는 eval, 자기 개선 루프, 벤치마크, A/B 테스트.
Q7데이터와 맥락 층에서는 무엇을 왜 기록하나?
대화, 산출물, 영상, 스크린샷까지 에이전트가 만든 것을 전부 기록한다. 팩토리를 개선할 원재료이기 때문이다.
Q8추론 층에서 모델과 하네스를 어떻게 다루라고 했나?
시험할 변수로 다룬다. 여러 모델과 여러 하네스를 지원하고, 조직 맥락을 담은 자체 하네스도 쓸 수 있게 한다.
Q9기록을 중앙에 모으면 볼 수 있는 지표 네 종류는?
DORA 지표나 사이클 타임 같은 산출 지표, PR 하나당 사람 개입 횟수(자동화 수준), 처리량, 비용.
Q10온라인 평가란 무엇이고, 발표에 나온 예는?
다른 에이전트가 세션 기록을 다시 보고 점수를 매기는 평가다. 모든 세션에 걸쳐 계속 돈다. 예는 필요 없는 테스트를 쓴 세션을 잡는 eval이다.
Q11자기 개선의 결과물은 어떤 형태인가?
실패한 실행들의 패턴을 바탕으로 한 팩토리 정의 파일의 PR. 팩토리가 코드로 정의돼 있어서 가능하다.
Q12"어느 모델이 최고인가"에 발표자가 낸 답은?
자기 실제 데이터로 벤치마크 세트를 만들고, 다른 설정으로 다시 돌려 비용과 품질을 비교해 봐야 안다. 스킬을 뺐을 때의 차이도 같은 방법으로 잰다.

용어 정리

용어뜻
코딩 에이전트코드를 읽고, 쓰고, 실행하며 개발 일을 하는 AI
대화형 프롬프팅Interactive prompting. 사람이 에이전트와 말을 주고받으며 한 단계씩 지시하는 방식
소프트웨어 팩토리발표자의 정의로는 클라우드 코딩 에이전트를 계속 측정하고 개선하는, 코드로 정의한 닫힌 루프 시스템
거버넌스누가 무엇을 어떻게 쓰게 할지 정하고 지키게 하는 관리 체계
프리미티브Primitive. 더 큰 것을 조립할 때 쓰는 기본 재료
MCPModel Context Protocol. AI가 외부 도구와 데이터에 연결하는 표준 규약
스킬에이전트가 특정 일을 할 때 불러 쓰는 지시와 자료 묶음
선언형Declarative. 실행 순서가 아니라 원하는 최종 상태를 적는 방식
Terraform인프라를 선언형 코드 파일로 정의하고 관리하는 도구
트리거에이전트 실행을 시작시키는 조건이나 사건
분류Triage. 들어온 일을 살펴 우선순위와 처리 방향을 정하는 단계
SDLCSoftware Development Life Cycle. 아이디어부터 구현, 검증, 운영까지 소프트웨어를 만드는 전체 단계
닫힌 루프Closed loop. 결과를 다시 입력으로 돌려 시스템을 계속 고치는 순환
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀. 예: Claude Code, Codex
샌드박스다른 시스템과 격리된 실행 환경
추론Inference. 학습된 모델을 실제로 돌려 답을 얻는 일
오케스트레이션Orchestration. 여러 작업과 에이전트를 순서에 맞게 다음 단계로 넘기는 일
DORA 지표DevOps Research and Assessment 연구에서 나온 소프트웨어 전달 성과 지표. 배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간
사이클 타임Cycle time. 일을 시작해서 끝낼 때까지 걸리는 시간
처리량Throughput. 정해진 시간에 끝낸 일의 양
eval / 온라인 평가eval은 결과 품질을 재는 시험이다. 온라인 평가는 실제로 도는 세션마다 계속 돌아가는 eval이다
자기 개선Self-improvement. 에이전트가 평가 결과에서 실패 패턴을 찾아 팩토리 정의를 고치는 PR을 내는 것
벤치마크 / 재생벤치마크는 같은 과제 세트로 여러 설정을 비교하는 시험이다. 재생(replay)은 과거 과제를 다른 설정으로 다시 돌리는 것이다
A/B 테스트두 설정을 나눠 돌리고 결과를 비교하는 실험
SWE-bench / Terminal-Bench공개 코딩 에이전트 벤치마크. SWE-bench는 실제 오픈소스 이슈 해결을, Terminal-Bench는 터미널 작업 수행을 잰다
