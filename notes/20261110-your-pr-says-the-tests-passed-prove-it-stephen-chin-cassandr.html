PR 설명은 증거로 써야 한다

에이전트가 쓴 PR 설명은 "테스트 통과" 같은 주장을 근거 없이 담기 쉽다. 발표자들은 작업 기록을 그래프 데이터베이스로 미리 묶어 주면, PR 품질은 조금 오르고 토큰은 절반으로 준다고 말한다.

원본 영상: Your PR Says the Tests Passed. Prove It. 발표: Stephen Chin (Neo4j), Cassandra Chin (TraceTune 제작자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 인용하거나 주장한 것이고, 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다(예: swyx, PR Bench). 확실하지 않은 이름은 들린 대로 적고 (추정)을 붙였다. 발표는 만화 이야기 형식이다. Alex, Mira, Pip 같은 이름은 만화 속 캐릭터다. mm:ss는 영상 위치다.

3분 요약
  1. AI 시대에 PR이 거절되는 건 코드가 나빠서보다 PR 설명이 틀려서인 경우가 많다고 Cassandra Chin은 본다.
  2. 원인은 에이전트가 압축된 자기 세션 기억과 diff만 보고 PR을 쓰기 때문이다. 그래서 "테스트 통과" 같은 주장이 근거 없이 들어간다.
  3. TraceTune은 컴퓨터에 남은 에이전트 작업 기록을 읽어 근거를 모으고, 작성자와 리뷰어를 따로 둔다.
  4. 첫 버전도 고쳐 쓰는 단계에서 틀렸다. 모델만 싼 걸로 바꾸면 품질이 떨어졌다.
  5. 해법은 그래프 데이터베이스 Relate다. 이유, 코드, 검사 결과를 출처와 함께 미리 묶어 "이웃 브리프"로 넘긴다. 이 단계에는 LLM 비용이 들지 않는다.
  6. 근거가 묶여 있으면 리뷰는 싼 모델 여러 개로 충분하다. 반대로 글쓰기에는 높은 등급 모델이 필요하다.
  7. 발표자들이 만든 PR Bench에서 품질은 100점 척도로 2~4점 올랐고, 토큰은 약 절반으로 줄었다.
01

PR이 거절되는 이유 00:10

풀 리퀘스트pull request, PR는 내 변경을 메인 코드에 합쳐 달라는 요청이다. 리뷰어는 코드와 함께 PR 설명을 읽고 합칠지 정한다.

Cassandra Chin은 AI 덕분에 개발 속도가 어느 때보다 빠르다고 말한다. 그런데 PR은 많이 거절된다. Cassandra Chin이 본 이유는 코드가 아니다. PR 설명에 틀린 정보가 들어 있거나, 설명이 엉성하게 쓰여 있기 때문이다.

TraceTune은 이 PR 설명을 고치려고 만든 도구다. PR 내용을 재미있게 풀어 주는 만화를 덧붙이는 기능도 있다.

발표가 다루는 세 가지 00:50 PR의 흔한 문제, PR 품질을 올리는 법, 토큰을 아끼는 법. 이 셋을 만화 주인공 Alex의 이야기로 풀어 간다. Alex의 소원은 AI Engineer 후드티를 받는 것이다. 그러려면 회사에서 PR 품질을 높인 사례로 이 행사 무대에 서야 한다.

03

에이전트의 PR 설명이 틀리는 이유 04:40

보통은 작업하던 세션에서 에이전트에게 "PR 써 줘"라고 한다. 에이전트는 자기 세션 기록을 읽고 무엇을 했는지 되짚는다. Cassandra Chin은 여기서 두 가지 문제를 짚는다.

  1. 에이전트는 잔뜩 부풀어 오른 컨텍스트 창context window으로 기록을 읽는다. 컨텍스트 창은 모델이 한 번에 붙잡고 있는 대화 내용이다.
  2. 작업이 길어지면 에이전트는 컨텍스트를 압축한다compaction. 압축할수록 세부가 빠지고, PR 설명은 점점 부정확해진다.

TraceTune은 다르게 한다. 컴퓨터에 남아 있는 여러 세션의 기록을 읽어, 실제로 무엇을 만들었고 무슨 일이 있었는지 알아낸다.

시작은 교육 연구였다 05:20

Cassandra Chin은 이 일을 Show Tell(추정) 프로젝트에서 시작했다. 한 대학 연구를 돕는 프로젝트였다.

학생들은 AI로 프로그램을 만들어 제출했다. 제출하는 건 최종 프로그램뿐이었다. 실제 노력의 대부분인 프롬프트와 그 앞의 과정은 남지 않았다. 그래서 학생이 실제로 어떤 작업을 했는지 거슬러 볼 방법이 없었다.

이 문제를 풀려고 작업 과정을 추적하는 기술을 만들었다. 그리고 같은 기록으로 PR도 나아지게 할 수 있겠다고 생각했다.

좋은 PR 설명에는 무엇이 들어가나 06:10

Stephen Chin은 작업 기록이 있으면 PR에 진짜 근거를 담을 수 있다고 말한다. 발표에 나온 예는 이렇다.

  • cd가 실행되기 전의 현재 작업 디렉터리CWD를 로그로 남겼다

  • 화면 뒤에서 실제로 무슨 일이 있었는지 적는다
흔한 AI PRdiff를 줄마다 해설한다에이전트가 diff만 보고 PR을 쓰기 때문이다

근거 기반 PR왜 바꿨고 뒤에서 무슨 일이 있었는지 적는다작업 기록에서 찾은 사실을 출처와 함께 쓴다

틀린 사실이 하나라도 섞이면 문제가 커진다. 정보가 오염되고, PR끼리 충돌하고, 결국 부정확한 결과가 돌아온다.

04

TraceTune 첫 버전 07:30

TraceTune은 오픈소스다. 하는 일은 세 가지다.

  • 에이전트 작업 기록과 코드 정보를 끌어온다
  • 서로 독립된 작성자와 리뷰어가 PR 설명을 만든다
  • 원하면 만화를 붙인다

Cassandra Chin은 반쯤 농담으로 "만화가 먼저였고, PR 품질은 나중에 챙겼다"고 말한다. 초기 만화 중에는 "매 화 새 캐릭터 쓰기"를 다룬 PR의 만화도 있다. 08:00

원래 흐름 08:20

  1. 한 브랜치에 해당하는 작업 기록trace을 모두 찾는다
  2. 기록을 조사한다
  3. PR 설명을 리뷰한다
  4. 맥락을 더 넣는다
  5. 좋은 PR에 필요한 근거가 다 모일 때까지 2~4를 되풀이한다

발표자들은 이 흐름이 이미 나았다고 말한다. 직접 봐도 나았고, PR Bench로 재도 품질과 조사가 낫고 부정확한 내용이 적었다. PR Bench는 발표자들이 만든 PR 품질 측정 틀이다.

그래도 가끔 틀렸다. Cassandra Chin은 마지막에 맥락을 더 넣어 고쳐 쓰는 단계에서 실수가 생긴다고 봤다. 08:50

05

첫 버전의 한계 09:20

"테스트 통과"라는 주장 09:30

Alex는 TraceTune으로 PR을 냈다. PR은 테스트가 통과했고 검사를 다 돌렸다고 주장했다.

실제 작업 기록은 달랐다. bun test와 bunx tsc(타입 검사)가 동시에 돌았다. Cassandra Chin의 설명으로는 이 둘은 순서대로 돌려야 테스트가 통과한다. 그러니 "통과했다"는 주장은 기록과 맞지 않았다. 코드가 실제로 한 일이 PR 설명과 달랐던 것이다.

발표 제목의 뜻 "PR이 테스트가 통과했다고 말한다면, 증명하라." PR 설명의 주장 하나하나에 그걸 뒷받침하는 실행 기록이 있어야 한다.

모델만 싸게 바꾸기 10:20

Stephen Chin은 재무팀에게 늘 듣는 말이 있다고 한다. "Opus, Sonnet, Haiku 말고 더 싼 걸 써 달라." 그래서 작성 모델을 더 싼 것으로 바꿔 봤다.

결과는 품질 하락이었다. 품질을 올리려다 오히려 떨어졌다. 비용만 줄인다고 해결되지 않는다.

이제 Alex는 막혔다. 고쳐 쓰는 데 토큰을 너무 많이 썼다. 비용을 줄일 방법도 없다. PR 결과도 여전히 나쁘다.

06

그래프가 근거를 미리 묶는다 11:00

Pip에게는 친구가 있다. Stephen Chin의 이전 발표들을 아는 사람이라면 짐작하듯 그 친구는 그래프다. 이번에는 Neo4j 데이터베이스가 아니라 새 친구 Archie다.

Archie의 정체는 Relate(자막 표기, 추정)다. 발표자들이 소개한 특징은 다음과 같다. 11:30

  • Rust로 쓴 임베디드embedded 그래프 데이터베이스다. 따로 서버를 띄우지 않고 프로그램 안에 들어가 돈다
  • 오픈소스다. 발표 주간에 NODES 컨퍼런스와 이 발표에서 공개했다
  • 무거운 구성 없이 정확도, 멀티홉 질의multi-hop query, 설명 가능한 추적을 얻는다고 한다
  • 에이전트용, 임베디드 용도에 맞춰 만들었다

Relate는 발표자들이 "우리의 새 데이터베이스"라고 소개한 제품이다. 장점은 발표자의 주장으로 감안해 읽자.

이전에이전트 루프가 매번 조사한다근거를 찾고 다시 찾는 데 LLM 토큰이 든다
→
이후그래프가 근거를 미리 묶어 준다관계를 저장하고, 연결된 것을 찾아 브리프를 만든다. 더 싼 에이전트도 좋은 정보로 초안을 쓴다

LLM 비용이 0인 단계 12:40

Archie는 LLM을 부르지 않는다. 드는 건 로컬 컴퓨터의 계산과 저장 공간뿐이다. 메모리 안에서 도는in-memory Rust 데이터베이스라 빠르다고 한다.

그래서 두 가지를 거의 공짜로 얻는다.

  • 출처 기록provenance: 제출된 변경 하나하나가 어디서 왔는지
  • 근거 그래프evidence graph: 사실과 근거가 서로 어떻게 이어지는지

이제 Alex는 사실과 출처를 다시 찾지 않아도 된다. Relate가 그 일을 하고 근거 패킷evidence packet을 만들어 TraceTune에 넘긴다. 13:00

07

이웃 브리프 13:20

근거 패킷을 더 쓸모 있게 만드는 방법이 이웃 브리프neighborhood brief다. 그래프에서 어떤 사실과 이어진 주변 정보(이웃)를 함께 꺼내 한 묶음으로 만든 요약이다.

재료뜻
이유 (why)이 변경을 왜 했는가
코드무엇이 바뀌었는가
검사 결과무엇을 돌렸고 결과가 어땠는가

세 재료마다 출처를 달고, 서로의 관계를 잇는다. 그리고 연결된 정보 한 묶음으로 돌려준다.

  • 작성자: 연결된 사실과 출처를 한곳에서 본다. 그래서 더 적은 횟수로 더 정확한 초안을 쓴다
  • 리뷰어: 대조할 근거가 이미 모여 있어 일이 훨씬 쉬워진다
08

리뷰어 일이 쉬워졌으니 비싼 리뷰어가 필요 없다. 발표자들은 모델을 이렇게 나눴다.

Cassandra Chin은 만들면서 이 배치가 직관에 반한다고 느꼈다. 작성자가 리뷰어보다 높은 등급이기 때문이다. 14:30

Stephen Chin의 설명은 이렇다. 보통은 계획자, 리뷰어, 검사자에 가장 좋은 모델을 둔다. 하지만 목표가 좋은 글이라면 사정이 다르다. 낮은 등급 모델은 반복과 피드백을 아무리 줘도 좋은 글을 못 쓴다.

낮은 모델은 글을 체크리스트로 바꿔 버린다. 아주 기계적으로.Stephen Chin의 말을 옮김 · 14:50

사람이 쓴 것 같은 글에는 높은 등급 모델이 필요하다. 오히려 리뷰와 교차 확인이 기계적인 쪽이다.

리뷰 단계가 한 일 15:20

핵심 정리

  1. PR이 거절되는 흔한 이유는 코드가 아니라 틀리거나 엉성한 PR 설명이다.
  2. 에이전트는 부풀고 압축된 자기 세션 기억과 diff로 PR을 쓴다. 그래서 설명이 diff 해설이 되고, 틀린 사실이 섞인다.
  3. TraceTune은 여러 세션의 작업 기록을 근거로 쓰고, 작성자와 리뷰어를 따로 둔다.
  4. "테스트 통과" 주장도 기록과 대조해야 한다. 실패 사례에서는 순서대로 돌려야 할 검사가 동시에 돌았다.
  5. 모델만 싼 걸로 바꾸면 비용은 줄어도 품질이 떨어졌다.
  6. 그래프 데이터베이스 Relate는 LLM 없이 출처 기록과 근거 그래프를 만든다.
  7. 이웃 브리프는 이유·코드·검사 결과를 출처·관계와 함께 한 묶음으로 넘긴다.
  8. 근거가 묶여 있으면 리뷰는 싼 모델 여러 개로 충분하다. 글쓰기는 높은 등급 모델이 해야 한다.
  9. 좋은 PR 설명은 왜, 예외, 통과한 것(어느 코드에서), 어디부터 볼지를 적는다.
  10. 발표자들의 PR Bench에서 품질은 +2, +4점, 토큰은 약 절반이었다. 모두 발표자들이 만든 도구로 잰 결과다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Cassandra Chin이 본, PR이 거절되는 주된 이유는?
코드가 나빠서가 아니다. PR 설명에 틀린 정보가 들어 있거나 설명이 엉성하게 쓰여 있어서다.
Q2작업하던 세션에서 에이전트에게 PR을 쓰게 하면 왜 점점 부정확해지나?
에이전트는 부풀어 오른 컨텍스트로 자기 세션 기록을 읽는다. 작업이 길어지면 컨텍스트를 압축하는데, 압축할수록 세부가 빠진다.
Q3TraceTune은 무엇을 근거로 PR을 쓰나?
컴퓨터에 남은 여러 에이전트 세션의 작업 기록과 코드 정보. 서로 독립된 작성자와 리뷰어가 PR 설명을 만든다.
Q4TraceTune 아이디어는 어떤 문제에서 시작했나?
교육 연구 프로젝트(Show Tell, 추정)에서 시작했다. 학생들이 AI로 만든 프로그램만 제출하고, 실제 노력인 프롬프트와 과정은 남지 않았다. 그 과정을 추적하는 기술을 PR에 옮겨 썼다.
Q5흔한 AI PR 설명은 어떤 모습이고, 왜 그렇게 되나?
diff를 줄마다 해설한다. 에이전트가 diff만 보고 PR을 쓰기 때문이다. 왜 바꿨는지, 뒤에서 무슨 일이 있었는지가 빠진다.
Q6"테스트 통과" 주장이 거짓이었던 사례에서 기록에는 무엇이 남아 있었나?
bun test와 bunx tsc가 동시에 돌았다. 발표자 설명으로는 둘은 순서대로 돌려야 테스트가 통과한다. 그래서 통과 주장은 근거가 없었다.
Q7재무팀 요청대로 작성 모델을 싼 걸로 바꾸자 어떻게 됐나?
품질이 떨어졌다. 품질을 올리려다 오히려 나빠졌다.
Q8Relate가 근거를 모으는 비용이 거의 0인 이유는?
LLM을 부르지 않는다. 로컬 계산과 저장만 쓰는 인메모리 그래프 데이터베이스다. 그래서 출처 기록과 근거 그래프를 LLM 비용에 비해 거의 공짜로 만든다.
Q9이웃 브리프란 무엇이고, 무엇이 좋아지나?
이유, 코드, 검사 결과를 출처와 관계를 달아 한 묶음으로 넘긴 것. 작성자는 더 적은 횟수로 정확한 초안을 쓰고, 리뷰어는 대조하기가 쉬워진다.
Q10작성자를 리뷰어보다 높은 등급 모델로 둔 이유는?
낮은 등급 모델은 피드백을 아무리 줘도 체크리스트 같은 기계적인 글을 쓴다. 사람이 쓴 것 같은 글에는 높은 모델이 필요하다. 반대로 근거와 대조하는 리뷰는 기계적인 일이라 싼 모델 여러 개로 된다.
Q11완성된 PR 설명의 "통과한 것" 칸에는 무엇까지 적혀 있었나?
타입 검사와 테스트 71개를 돌렸다는 것, 그리고 그 검사를 그 전 상태가 아니라 제출한 내용에서 돌렸다는 것.
Q12PR Bench 결과 수치와, 읽을 때 주의할 점은?
품질은 100점 척도로 74→76, 82→86(+2, +4). 토큰은 약 절반. TraceTune, Relate, PR Bench 모두 발표자들이 만든 것이고, 통계적 유의성은 발표에서 다루지 않았다.
