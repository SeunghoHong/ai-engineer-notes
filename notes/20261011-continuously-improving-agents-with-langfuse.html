에이전트는 배포한 뒤에 좋아진다

에이전트는 서버가 멀쩡해도 답이 틀릴 수 있다. 그래서 프로덕션의 트레이스를 보고, 우리 앱에서 실제로 잘못되는 유형을 정의하고, 그것을 자동으로 잡는 평가기를 달고, 잡힌 것을 데이터셋으로 모아 다음 변경을 검증한다. 이 과정을 계속 돌리는 것이 발표자들이 말하는 AI 엔지니어링이다.

원본 영상: Continuously Improving Agents with Langfuse 발표: Lotte Verheyden, Annabell Schäfer (Langfuse, ClickHouse)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 앞부분 개념 설명은 Lotte Verheyden, 실습 시연은 Annabell Schäfer가 맡았다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 "lenfuse"로 뭉개진 이름은 Langfuse로 바로잡았다. mm:ss는 영상 위치다.

발표자 두 사람은 Langfuse 소속이고, 이 워크숍은 Langfuse 제품을 실습하는 자리다. 도구의 장점을 말하는 대목은 그 점을 감안해 읽자. 다만 "트레이스 → 모니터링 → 데이터셋 → 실험" 이라는 흐름 자체는 특정 도구에 묶이지 않는다.

3분 요약
  1. 에이전트는 결정적이지 않다. 시스템 지표가 정상이어도 답이 틀리거나 품질이 낮을 수 있다. 이 간극을 메우는 일이 AI 엔지니어링이다.
  2. AI 엔지니어링 루프는 다섯 단계다. 프로덕션에서 돌아가는 온라인 부분(트레이싱, 모니터링)과 프로덕션 밖의 오프라인 부분(데이터셋, 실험, 평가)으로 나뉜다.
  3. 고위험 분야가 아니면 온라인 두 단계만으로 시작해도 충분히 멀리 간다. 제품이 성숙하거나 실수의 대가가 크면 오프라인 부분을 더한다.
  4. 모든 것은 트레이스에서 시작한다. 트레이스가 부실하면 모니터링에서 놓치고, 데이터셋도 나빠지고, 결정도 나빠진다.
  5. 자동 평가기는 확장은 잘 되지만 새로운 유형은 못 잡는다. 사용자 피드백과 사람의 샘플 검토가 그 빈틈을 메운다.
  6. 평가기는 템플릿을 복붙하는 것이 아니다. 우리 앱에서 실제로 잘못되는 유형을 먼저 생각한다. 시연에서는 "사용자가 반박한다", "전부 대문자로 쓴다", "범위 밖 요청"을 골랐다.
  7. 코딩 에이전트에 Langfuse 스킬을 붙이면 트레이스 전체를 훑어 평가기가 안 보던 문제까지 찾아낸다. 시연에서는 검색 도구가 조용히 실패하고 있던 것을 찾았다.
  8. 신호를 잡은 뒤에는 평가 기준을 손보고 데이터셋을 키운다. 변경할 때마다 그 데이터셋으로 실험을 돌려 회귀가 없을 때만 배포한다.
01

AI 엔지니어링이 필요한 이유 01:10

Lotte Verheyden은 먼저 전통 엔지니어링과 다른 점 하나를 짚는다. AI 에이전트는 결정적이지 않다 non-deterministic. 같은 입력에도 다른 답이 나올 수 있다.

그래서 이상한 상황이 생긴다. 서버는 살아 있고 에러도 없고 응답 시간도 정상이다. 그런데 에이전트가 사용자에게 준 답이 틀렸거나, 틀리진 않았지만 품질이 모자란다. 기존 모니터링은 이걸 보지 못한다.

AI 엔지니어링이 푸는 문제 "시스템은 건강해 보이는데 에이전트의 답이나 행동은 잘못됐다." 이 간극을 보이게 만들고 줄여 가는 일련의 과정이 AI 엔지니어링이다. 발표자는 이 과정들을 이어 붙이면 하나의 계속 돌아가는 루프가 된다고 말한다.

Langfuse는 이 과정을 실행하는 플랫폼이고 오픈소스다. 모델과 프레임워크를 가리지 않는다고 발표자가 소개했다. 제품 소개 대목이다.

02

온라인 루프와 오프라인 루프 02:40

발표자는 AI 엔지니어링 루프를 다섯 단계로 그린다. 회사마다 세부는 다르지만 큰 틀은 두 덩어리다.

온라인 · 프로덕션에서 03:20
  • 트레이싱 tracing: 앱에 계측을 넣고 배포하면, 에이전트가 무엇을 했는지 트레이스가 들어온다.
  • 모니터링 monitoring: 들어온 트레이스를 평가기와 대시보드로 자동 감시한다. 사용자 피드백과 사람의 샘플 검토도 여기 들어간다.

시작점: 고위험 분야가 아닌 팀은 이 둘만으로 시작해도 된다. 모니터링에서 본 것으로 간단히 고치고, 배포하고, 다시 트레이스를 본다. 빠르게 반복하는 좋은 첫걸음이다.

오프라인 · 프로덕션 밖에서 04:30
  • 데이터셋 datasets: 구조화된 테스트 케이스 모음. 모니터링에서 본 사례가 주 재료다.
  • 실험 experiments: 변경안을 데이터셋에 돌린다.
  • 평가 evaluation: 실험 결과를 채점한다.

언제: 제품이 성숙했거나, 실수 하나가 큰 피해를 주는 환경이면 이쪽을 더한다. 결과가 더 좋고 회귀가 없을 때만 배포한다.

이번 워크숍은 온라인 부분, 그중에서도 모니터링에 집중한다. 오프라인 부분은 마지막에 방향만 짚는다.

03

모든 것은 트레이스에서 시작한다 05:10

발표자는 트레이스 설정에 시간을 충분히 쓰라고 강조한다. 이유는 연쇄 효과다.

  1. 트레이스가 부실하면 모니터링에서 문제를 다 잡지 못한다.
  2. 모니터링에서 놓치면 데이터셋에 좋은 사례가 들어가지 않는다.
  3. 데이터셋이 나쁘면 무엇을 평가할지 제대로 결정하지 못한다.

트레이스의 구조 05:40

트레이스 trace는 관측 observation의 묶음이다. 관측은 에이전트가 답을 만들며 거친 각 단계다. LLM 호출일 수도 있고 도구 호출일 수도 있다. 관측은 중첩될 수 있다.

관측 종류붙어 있는 데이터 (예)
LLM 호출소요 시간, 토큰 사용량과 비용, 사용한 모델, 사용한 프롬프트 버전. 품질을 판단하는 데 필요한 모든 것
도구 호출종류마다 다르다. 웹 검색이면 실제로 보낸 검색어가 한 데이터 포인트다

이 데이터가 있어야 다음 단계인 모니터링이 가능하다.

04

모니터링의 세 가지 역할 06:30

  1. 집계 지표: 시간에 따른 시스템 건강을 본다. 비용뿐 아니라 품질도 포함한다. 평가기 점수가 시간이 지나며 떨어지지 않는지 확인한다.
  2. 사용자 피드백으로 신호 찾기: 앱이 커지면 트레이스를 전부 볼 수 없다. 사용자 피드백은 진짜 봐야 할 트레이스를 띄워 주는 장치다.
  3. 피드백과 평가: 자동 평가기를 두고, 사람이 직접 주석을 달기도 한다.
자동 평가기
  • 잘 확장된다. 모든 트레이스에 계속 돌릴 수 있다.
  • 내가 미리 생각하지 못한 새롭고 미묘한 경우는 잘 못 잡는다.
사용자 피드백 · 사람의 주석
  • 확장은 덜 된다.
  • 내가 생각하지 못한 것을 발견하는 곳은 여기다.

둘은 서로를 대신하지 못한다. 자동 평가기로 넓게 덮고, 사람과 사용자 피드백으로 빈틈을 찾는다.

05

예제 앱: 아빠 IT 지원 에이전트 08:30

여기서부터 Annabell Schäfer가 시연한다. 예제는 "Specs"라는 이름의 IT 지원 에이전트다. Annabell Schäfer의 아버지가 WhatsApp으로 휴대폰, 프린터, 컴퓨터 설정을 자꾸 물어와서 만든 개인 프로젝트에서 나왔다. 워크숍용은 간단한 웹 UI를 쓴다.

구성 요소역할
사용자아빠. 질문을 보낸다
지원 컨텍스트 조회 도구어떤 휴대폰, 어떤 운영체제, 어떤 앱을 쓰는지 가져온다
도움말 라이브러리 검색 도구자주 묻는 질문과 해결 방법이 담긴 문서를 검색한다
OpenAI API답을 생성한다
구현TypeScript, OpenAI Agents SDK. 이미 Langfuse 계측이 들어가 있다

이 앱으로 두 가지를 한다. 트레이스를 함께 보고, 그다음 "아빠가 원하는 지원을 받고 있는지 알려면 무엇을 봐야 하는가"를 생각한다.

06

설정과 첫 트레이스 10:10

워크숍 자료는 langfuse.com/workshop 에 있고, 저장소는 GitHub의 langfuse/langfuse-workshop 이다. 설정 순서는 이렇다.

  1. Langfuse에 가입하고 리전을 고른다. 어느 리전이든 상관없다. 프로젝트가 자동으로 만들어진다.
  2. 프로젝트 페이지에서 API 키를 만든다.
  3. 저장소를 클론하고 .env 샘플을 복사해 Langfuse 키와 OpenAI 키를 넣는다. 워크숍용 OpenAI 키는 현장에서 QR 코드로 나눠 주고 뒤에 폐기한다고 했다.
  4. 의존성을 설치하고 npm run dev로 띄운다.

첫 트레이스 읽기 13:50

"iPhone에서 Bluetooth 켜는 법"을 물으면 에이전트가 도구를 쓰고 단계별 답을 준다. Langfuse 트레이싱 화면에 첫 트레이스가 뜬다.

  • 트레이스 안의 각 행이 관측이다. 아이콘이 다르면 종류가 다르다.
  • 맨 위 뿌리는 에이전트 관측이다. 그 아래에 LLM 생성 generation 몇 개와 컨텍스트를 가져온 도구 호출들이 매달려 있다.

계측을 처음부터 손으로 넣는 단계별 가이드도 있고, 코딩 에이전트용 Langfuse 스킬로 자동으로 넣을 수도 있다고 발표자가 말했다. 이날은 계측이 끝난 상태에서 트레이스를 다루는 쪽에 집중했다.

07

무엇이 잘못될 수 있나 정하기 14:50

아빠가 앱을 쓸 때 우리는 옆에 없다. 그게 에이전트를 만든 이유다. 그래서 에이전트가 무엇을 했는지 기록하는 데서 그치지 않고, 그 기록이 무슨 뜻인지 해석해야 한다.

발표자는 "지원 앱에서 실제로 무엇이 잘못될 수 있나"를 먼저 생각했다. 그 결과가 세 가지 실패 유형이고, 각각 평가기 하나로 잡는다.

실패 유형신호평가기 방식보는 것
사용자가 반박한다"그 버튼이 없는데요", "그거 아닌데요"LLM 판사대화 전체 + 마지막 사용자 메시지
사용자가 좌절했다전부 대문자로 쓴다. 욕설도 같은 부류코드 기반마지막 사용자 메시지
범위 밖 요청휴대폰 지원 앱에 프린터나 컴퓨터를 묻는다LLM 판사시스템 프롬프트 + 마지막 사용자 메시지

실습은 git checkout으로 모니터링 체크포인트 브랜치로 옮긴 뒤 진행한다. Langfuse 평가기 화면에는 두 종류가 있다. 코드 기반 평가기는 결정적인 검사용이고, LLM 판사 LLM-as-a-judge는 대화에 숨어 있는 암묵적인 것을 끌어내는 용도다.

자막에는 "LLM as a Dutch"로 적혀 있다. 문맥상 LLM-as-a-judge다.

08

평가기 1: 사용자가 반박한다 16:30

Langfuse가 제공하는 "사용자 반박" user disagreement 템플릿을 쓴다. LLM 판사이므로 먼저 평가에 쓸 모델 연결이 필요하다. 시연에서는 같은 OpenAI 키를 연결했다. 다른 모델이나 자체 게이트웨이 프록시도 연결할 수 있다고 했다.

설정 순서 18:20

  1. 대상 관측 고르기: 생성 하나가 아니라 트레이스의 뿌리인 에이전트 관측을 고른다. 도구 호출이나 생성을 고를 수도 있다.
  2. 입력만 본다: 이 평가기는 사용자 메시지를 봐야 하므로 입력 쪽을 대상으로 한다.
  3. 변수 매핑: 평가 프롬프트 안의 중괄호 변수에 트레이스의 어느 부분을 넣을지 JSON 경로로 지정한다.
    • 대화 이력 변수에는 메시지 배열 전체를 넣는다. 미리보기에 질문, 도구 호출, 답이 한데 묶여 들어오는 것이 보인다.
    • 마지막 사용자 메시지 변수에는 사용자의 최신 메시지만 넣는다.
  4. 실행: 이제 들어오는 트레이스마다 실시간으로 돈다.
왜 이 신호가 중요한가 20:20 아빠가 "Bluetooth 어떻게 켜요"라고 묻고, 이어서 "그 버튼이 없는데요, 말한 게 틀렸어요"라고 하면 잡힌다. 발표자의 가늠으로는 질문 500개 중 500개가 실패하진 않겠지만 다섯에서 일곱 개쯤은 설명이 충분히 명확하지 않을 것이다. 그 몇 개가 어디서 무엇이 잘못되는지 알려 주는 신호다.
09

평가기 2: 전부 대문자로 쓴다 21:00

Annabell Schäfer는 자기도 Claude나 Codex에 답답해지면 대문자로 쓴다고 했다. 채팅 앱에서 전부 대문자는 사용자 좌절을 잡는 좋은 신호다. 욕설이나 평소에 안 쓰는 단어도 같은 부류의 신호다.

이건 LLM이 필요 없다. 코드 기반 평가기로 만든다.

  • 워크숍 자료의 Python 코드를 쓴다. 윗부분은 고정이고, 아래 평가 함수만 복사한다. TypeScript도 지원한다.
  • 함수는 JSON 경로로 사용자 메시지를 꺼내 전부 대문자인지 확인하고, 그러면 불리언 점수 true를 돌려준다.

  • 오른쪽의 테스트 실행으로 먼저 확인한다. Bluetooth 질문은 대문자가 아니라 false가 나온다. 결과가 마음에 들면 실행한다.
코드 기반 평가기로 할 수 있는 다른 일 23:20 특정 단어 찾기, 브랜드 이름 표기 검사 같은 결정적 규칙은 모두 여기에 맞는다. 발표자는 "Langfuse"의 f를 대문자로 쓰는 실수를 예로 들었다. 그리고 지금은 실시간 관측에 걸었지만, 같은 평가기를 오프라인 개선 과정의 실험 결과에도 돌릴 수 있다.

평가기 3: 범위 밖 요청 27:40

프로덕션에서 자주 보고 싶은 것 하나가 더 있다. 앱이 하라고 만들지 않은 일을 누가 시키고 있는가. 발표자는 이를 범위 밖 요청 out-of-scope request이라 부른다.

예제 앱의 시스템 프롬프트는 휴대폰 IT 지원만 하라고 되어 있다. 하지만 아빠는 프린터와 컴퓨터도 있다.

앞 두 평가기와 다른 점 28:20

  • 마지막 사용자 메시지만 보는 것이 아니라 시스템 프롬프트도 같이 본다. 앱이 해야 할 일과 사용자가 하려는 일을 비교하기 때문이다.
  • 그래서 대상 관측을 에이전트가 아니라 생성으로 잡는다. 시스템 프롬프트가 거기 있다.
  • 변수 매핑: 시스템 프롬프트 변수에는 대화의 첫 번째 메시지를, 다른 변수에는 마지막 사용자 메시지를 넣는다.

JSON 경로로 변수를 정의하기 때문에 트레이스의 어느 부분이든 골라 넣을 수 있다. 같은 틀로 보는 대상만 바꾸면 전혀 다른 평가기가 된다.

잡은 뒤에 내리는 결정 30:10 범위 밖 요청이 잡히면 두 갈래로 생각한다. 앱의 범위를 넓힐 것인가. 아니면 사용자에게 이 앱이 무엇을 하는지 제대로 알리지 못한 것인가. 범위가 큰 앱에서는 사용자가 시스템 용도를 완전히 오해하는 경우도 있다. 이 신호가 그걸 드러낸다.
밖에 있는 걸 복사해 붙이는 일이 아니다. 우리 앱에서 겪을 전형적인 실패 유형이 무엇인지 생각하는 일이다.Annabell Schäfer의 말을 옮김 30:50

코딩 에이전트로 트레이스 분석 31:50

이제 질문은 "이 많은 트레이스에서 무엇이 잘못되고 무엇이 잘 되고 있는지 어떻게 찾는가"다. 발표자는 코딩 에이전트를 쓴다.

Langfuse 스킬과 CLI 33:50

Codex에 시킨 것 35:20

핵심 정리

  1. 에이전트는 결정적이지 않아서 시스템이 건강해 보여도 답이 틀릴 수 있다. 기존 모니터링으로는 안 보인다.
  2. AI 엔지니어링 루프는 온라인(트레이싱, 모니터링)과 오프라인(데이터셋, 실험, 평가)으로 나뉜다.
  3. 고위험이 아니면 온라인 두 단계로 시작한다. 성숙하거나 위험이 크면 오프라인을 더한다.
  4. 트레이스 품질이 모든 하류 단계의 상한이다. 설정에 시간을 들인다.
  5. 모니터링은 집계 지표, 사용자 피드백 신호, 자동 평가와 사람 주석의 세 역할을 한다.
  6. 자동 평가기는 넓게 덮고, 사람과 사용자 피드백이 새로운 유형을 찾는다. 둘 다 필요하다.
  7. 평가기를 만들기 전에 우리 앱의 실패 유형을 정한다. 템플릿 복붙이 아니다.
  8. 결정적인 검사는 코드 기반, 암묵적인 판단은 LLM 판사. 둘 다 JSON 경로로 트레이스의 어느 부분을 볼지 지정한다.
  9. 코딩 에이전트에 트레이스 접근을 주면 평가기가 안 보던 조용한 실패를 찾고 코드까지 고친다.
  10. 신호를 잡은 뒤에는 평가 기준과 데이터셋을 계속 관리하고, 변경마다 실험으로 회귀를 확인한 뒤 배포한다.

Q1AI 엔지니어링이 전통 엔지니어링과 다른 근본 이유 하나는?

Q2AI 엔지니어링 루프의 다섯 단계를 온라인과 오프라인으로 나누면?
온라인: 트레이싱, 모니터링. 오프라인: 데이터셋, 실험, 평가.
Q3어떤 팀이 온라인 두 단계만으로 시작해도 되고, 언제 오프라인을 더하나?
고위험 분야가 아닌 팀은 트레이싱과 모니터링만으로 시작해 빠르게 반복한다. 제품이 성숙하거나 실수 하나의 피해가 큰 환경이면 데이터셋, 실험, 평가를 더한다.
Q4"모든 것은 트레이스에서 시작한다"는 말의 연쇄 논리는?
트레이스가 부실하면 모니터링에서 놓친다. 놓치면 데이터셋에 좋은 사례가 없다. 데이터셋이 나쁘면 무엇을 평가할지 제대로 결정하지 못한다.
Q5자동 평가기와 사용자 피드백·사람 주석은 각각 무엇에 강하고 약한가?
자동 평가기는 모든 트레이스에 계속 돌릴 수 있어 확장이 좋지만, 미리 생각 못 한 새 유형은 못 잡는다. 사용자 피드백과 사람 주석은 확장은 덜 되지만 생각 못 한 것을 발견한다.
Q6시연에서 고른 세 가지 실패 유형과 각각의 평가기 방식은?
사용자 반박(LLM 판사), 전부 대문자 좌절(코드 기반), 범위 밖 요청(LLM 판사).
Q7범위 밖 요청 평가기는 왜 대상 관측을 에이전트가 아니라 생성으로 잡았나?
시스템 프롬프트를 참조해야 하기 때문이다. 앱이 해야 할 일(시스템 프롬프트, 대화의 첫 메시지)과 사용자가 하려는 일(마지막 사용자 메시지)을 비교한다.
Q8평가 프롬프트의 변수에 트레이스의 어느 부분을 넣을지 어떻게 지정하나?
JSON 경로로 지정한다. 대화 이력에는 메시지 배열 전체, 마지막 사용자 메시지에는 최신 사용자 메시지처럼 부분을 골라 매핑한다.
Q9불리언 점수 평가기 이름에 "is"를 붙이라고 한 이유는?
true가 무슨 뜻인지 바로 알게 하려고. is_all_caps_frustrated가 true면 사용자가 대문자로 좌절을 표현했다는 뜻이다.
Q10코딩 에이전트가 트레이스에서 찾은 것 중 평가기로 걸지 않았던 문제는?
도움말 라이브러리 검색 도구가 조용히 실패하고 있던 것. 그 재시도가 지연과 비용도 올리고 있었다. 평가 커버리지 공백과 프롬프트 버전 불일치도 찾았다.
Q11신호를 잡은 뒤 루프를 닫기 위해 계속 관리해야 하는 두 가지는?
평가 기준(평가기 구성)과 데이터셋. 좋은 프로덕션 사례를 데이터셋에 넣고, 변경마다 실험으로 회귀를 확인한 뒤 배포한다.
Q12발표자가 "내일 시작한다면" 제안한 네 단계 순서는?
스킬로 트레이싱 넣기, 트레이스를 사람이 직접 훑기, 프로덕션 트레이스에 평가기 걸기, 그다음 오프라인 최적화.

용어뜻
AI 엔지니어링에이전트가 프로덕션에서 무엇을 하는지 보고, 평가하고, 데이터셋으로 검증해 계속 개선하는 일련의 과정. 발표자의 정의
결정적이지 않음Non-deterministic. 같은 입력에 매번 같은 출력이 나오지 않는 성질
트레이스Trace. 사용자 요청 하나를 처리하며 에이전트가 거친 모든 단계의 기록
관측Observation. 트레이스 안의 한 단계. LLM 호출, 도구 호출 등. 중첩될 수 있다
생성Generation. 관측 중 LLM 호출에 해당하는 것
에이전트 관측트레이스의 뿌리가 되는 관측. 그 아래에 생성과 도구 호출이 매달린다
온라인 / 오프라인온라인은 실제 사용자 트래픽이 흐르는 프로덕션에서 하는 일. 오프라인은 그 밖에서 데이터셋으로 하는 일
평가기Evaluator. 트레이스나 관측을 보고 점수를 매기는 자동 장치
코드 기반 평가기Python이나 TypeScript 코드로 규칙을 적어 결정적으로 채점하는 평가기
LLM 판사LLM-as-a-judge. 다른 LLM에게 프롬프트를 주어 응답이나 대화를 채점하게 하는 평가기
점수Score. 평가기가 관측에 붙이는 결과값. 불리언, 숫자 등
JSON 경로JSON 데이터 안에서 특정 위치를 가리키는 표기. 평가 프롬프트 변수에 트레이스의 어느 부분을 넣을지 지정할 때 쓴다
변수 매핑평가 프롬프트의 중괄호 변수와 트레이스 데이터의 위치를 연결하는 일
데이터셋Dataset. 구조화된 테스트 케이스 모음. 모니터링에서 본 프로덕션 사례가 주 재료
실험Experiment. 변경한 프롬프트나 코드를 데이터셋에 돌려 결과를 얻는 일
회귀새 변경 때문에 원래 잘 되던 것이 망가지는 것
범위 밖 요청Out-of-scope request. 시스템 프롬프트가 정한 앱의 용도를 벗어난 사용자 요청
체크포인트워크숍 저장소에서 특정 단계 상태로 맞춰 둔 git 브랜치
