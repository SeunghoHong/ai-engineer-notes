옵시디언 볼트를 로컬 AI 엔지니어로 만들기

옵시디언에 모아 둔 민감한 문서를 Claude Code에 그대로 열지 않는다. 내 클라우드에 둔 오픈소스 모델이 먼저 읽고 개인정보를 가린 뒤 결과만 돌려준다. 발표자는 이 설계를 MCP 서버로 만들었고, 진짜 병목은 저장이 아니라 추론 인프라였다고 말한다.

원본 영상: Turning My Obsidian Vault Into a Local AI Engineer 발표: Filip Makraduli (Superlinked)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 제품 이름이 자막에서 "Sci", "Sai"로 섞여 들려 이 노트에서는 "Sci(추정)"로 적는다. mm:ss는 영상 위치다.

발표자는 Superlinked 소속이고, 발표 내용 대부분이 자사 오픈소스 추론 엔진과 그 위에 만든 MCP 서버다. 성능과 가격 주장은 그 점을 감안해 읽는다.

3분 요약
  1. 출발점은 프라이버시와 토큰 비용이다. 옵시디언 마크다운 파일을 에이전트에 그대로 열면 허용하지 않는 기관이 있다.
  2. 해법은 무거운 전처리를 내 클라우드에 떠넘기기다. OCR과 개인정보 가리기를 내 VPC의 오픈소스 모델이 하고, Claude Code에는 가려진 결과만 돌아온다.
  3. 스킬이나 플러그인이 아니라 MCP 서버로 만들었다. 서버는 도구만 노출하고, 클라이언트 쪽으로 요청을 되돌리는 기능은 일부러 쓰지 않는다.
  4. 도구는 여섯 종류다. 문서→마크다운(OCR), 엔티티 추출, 캡션·태그, 구조화 생성, 요약, 질의응답.
  5. 데모에서 NDA 문서의 10개 구간을 가렸고, 스캔 이미지 계약서를 OCR로 읽어 마크다운으로 바꾸면서 동시에 가렸다.
  6. 뒤에서 일하는 추론 엔진이 핵심이다. 한 GPU에서 여러 모델을 핫스왑하고, 워커마다 배칭해 전체 지연 시간을 줄인다.
  7. 발표자의 결론: 겉보기에 Claude Code 친화적인 설계라도 바탕은 추론 인프라다. 인프라가 생각보다 훨씬 중요하다.
01

왜 만들었나: 프라이버시, 토큰, 적응성 00:30

발표자는 옵시디언 Obsidian에 마크다운 파일을 모아 두고 있었다. 파일끼리 연결한 그래프도 보기 좋았다. 많은 사람이 이런 지식 그래프를 에이전트의 기억으로 쓴다. 문제는 파일 정리가 아니라 그 다음이었다.

Claude Code나 Cowork 같은 에이전트에 파일을 열면 내용이 바깥으로 나간다. 어떤 기관과 사람에게는 이것이 허용되지 않는 조건이었다. 그래서 목표는 비공개로, 직접 호스팅하면서, 쓰기 편하게였다.

목표 1 · 토큰 절약 02:30

Fable 출시 초기의 API 전용 가격 정책 때문에 토큰 경제가 주목받았다고 발표자는 말한다. 특히 스캔과 이미지가 많은 민감 문서를 OCR 하면 토큰이 빠르게 쌓인다.

덤: 결과물이 작아지면 컨텍스트가 덜 차서 맥락 손실도 줄어든다.

목표 2 · 프라이버시 03:30

모든 것을 Claude Code에 붙여 넣어도 괜찮은 상황이 있다. 하지만 민감 문서는 내 VPC나 내 클라우드에서 먼저 처리하고 결과만 돌려받을 수 있어야 한다.

VPC: 가상 사설 클라우드 Virtual Private Cloud. 내가 통제하는 클라우드 안의 격리된 네트워크.

목표 3 · 적응성 03:50

여러 모델을 바꿔 가며 시험하고, 과제별로 미세 조정한 LoRA를 올릴 수 있어야 한다. 민감한 영역일수록 그 분야에 맞춘 조정이 따라붙기 때문이다.

LoRA: 큰 모델 전체 대신 작은 추가 가중치만 학습하는 저비용 미세 조정 방식.

이 세 가지를 한 번에 충족한 것이 Superlinked의 오픈소스 추론 엔진 Sci(추정)였다. 클러스터와 모델 추론을 함께 제공한다. 저장소는 GitHub에 전부 공개돼 있고, 오늘 이야기의 중심인 MCP 통합은 그 안의 하위 패키지다.

발표 제목은 "옵시디언 볼트"지만, 발표자는 슬라이드 내용이 제목과 조금 다르다고 처음에 밝혔다. 실제 내용은 옵시디언 자체보다 그 문서를 안전하게 처리하는 MCP 서버와 추론 인프라에 집중한다.

02

병목은 저장이 아니라 추론 05:10

데이터를 옵시디언에 두고 연결하는 일은 쉬웠다. API를 쓰면 더 쉬웠다. 어려워진 지점은 따로 있었다.

  • 오픈소스 모델로 규모 있게 추론을 돌리는 것
  • 여러 모델을 바꿔 가며 시험하는 것
  • 그것을 프로덕션에 배포하는 것

Sci(추정)는 클러스터와 모델을 함께 배포할 수 있다. 발표자는 이 인프라 이점이 결정적이었다고 말한다.

직접 써 보는 방법 06:10 발표자는 데모에 관리형 클러스터를 썼다. 청중은 웹사이트에서 추론 보조금 inference grant을 신청해 API 키를 받거나, Docker 컨테이너로 로컬에서 돌릴 수 있다. 로컬은 느리다. 발표자는 단계별 설명 글을 따로 낼 예정이라고 했다.
03

스킬이 아니라 MCP 서버인 이유 07:10

발표자가 원한 것은 평소 작업 흐름을 깨지 않는 것이다. Claude Code에서 일하다가 민감하거나 토큰이 많이 드는 작업만 내 클라우드로 떠넘기고 계속 일한다. 처음 떠오른 형태는 스킬이나 플러그인이었다. 그러나 결국 MCP 서버 전체를 만들었다.

플러그인만 쓰면내 노트북에서 돈다같은 경험이지만 무거운 일도 기기 안에서 한다
→
MCP 서버 + 전용 엣지내 클라우드에서 돈다무거운 일은 전용 서버가 맡고, 스킬은 그 도구를 부르기만 한다

MCP를 고른 세 가지 이유 09:00

  • 책임 분리: 전용 클러스터가 있으니 역할을 나누는 편이 낫다. 이 뼈대 위에 기능을 더 쌓을 수 있다.
  • 내가 통제하는 서버: 워커 풀과 GPU를 고르고, 어떤 모델이 어디에 고정되는지 알 수 있다.
  • 필요한 도구만 노출: 에이전트가 보는 것은 도구 목록뿐이다.

토큰 절약의 대표 예가 OCR이다. 이미지가 섞인 PDF 10쪽을 좋은 오픈소스 OCR 모델로 먼저 읽고 결과만 에이전트에 돌려주면, 맥락은 얻고 토큰은 덜 쓴다. 개인정보 PII를 가리는 도구도 핵심 쓰임새다.

04

세 층 구조와 MCP 통신 10:40

층무엇어디
MCP 클라이언트 · 호스트Claude Code, Cowork, Claude 데스크톱 등 에이전트 쪽내 기기
Sci(추정) MCP 서버도구를 노출하고 요청을 받아 클러스터에 넘긴다내 VPC
Sci(추정) 클러스터GPU와 워커 풀이 실제 추론을 한다. 큐잉 장치가 있다내 VPC

MCP의 취지는 통신 창구를 하나로 모으는 것이다. 지금 버전은 도구 호출 중심이지만, 발표자 팀은 평가 결과와 비용에 따라 모델을 고르는 모델 라우팅을 만들고 있다. 모든 모델은 오픈소스이고 내 GPU에서 돈다.

통신 방식 12:10

  • 호스트, 클라이언트, 서버가 JSON-RPC로 대화한다. 메시지는 요청, 응답, 알림 세 가지다. 초기 악수 handshake에서 인증과 도구 목록 교환이 이루어진다.
  • MCP 표준에서는 클라이언트도 샘플링 sampling이나 유도 elicitation을 열어 양방향 통신을 할 수 있다. 이 프로젝트는 프라이버시 때문에 일부러 쓰지 않는다. 서버는 악수 때 등록한 도구만 노출하고 응답만 한다.
  • 전송은 로컬 개발용 표준 입출력 stdio 대신 스트리밍 HTTP를 쓴다. 예전에는 스트리밍과 HTTP 악수를 엔드포인트 두 개로 나눴지만, 지금은 하나로 합친 표준이 있어 매끄럽다.

06

데모: NDA 가리기와 스캔 OCR 18:00

Claude Code를 패키지 디렉터리에서 연다. 옵시디언에는 받은편지함 inbox 폴더가 있고, 송장 관련 이메일과 전화번호, 사회보장번호가 든 NDA 문서가 들어 있다. 모두 합성 데이터다. 프로젝트의 계기가 된 실제 데이터는 쓰지 않았다.

  1. "NDA 문서의 데이터를 가려 줘"라고 자연어로 요청한다. 19:10
  2. 스킬이 로드되고 NDA 파일을 찾는다. 엔드포인트와 API 키는 미리 설정해 두었다. 20:10
  3. 결과: 10개 구간을 가렸고, 어떤 종류의 항목이 몇 개였는지 라벨 집계가 돌아온다. 이메일과 사람 이름 같은 항목이 마스킹된다.
  4. "스캔 문서를 전처리하고 같이 가려 줘"라고 요청한다. OCR 도구가 호출된다. 20:50
  5. 계약서 "before"는 글자가 아니라 이미지다. "after"는 글자를 추출한 마크다운이고, 개인정보는 이미 가려져 있다. 21:50
Claude Code는 무엇을 보나 모든 처리는 내 VPC에서 끝난다. Claude Code나 어떤 에이전트든 가려진 버전만 받는다. 상태 표시줄에 절약한 토큰 수가 뜨는데, 발표자는 이 계산을 더 손봐야 한다고 덧붙였다.
07

뒤에서 일하는 추론 엔진 23:00

기능만 보면 단순해 보인다. 무거운 일은 추론 엔진과 클러스터가 한다. 발표자가 꼽은 설계 포인트는 네 가지다.

핫스왑 23:20

여러 모델을 GPU 사이에서 바꿔 올린다. 세부 분야별로 미세 조정한 LoRA가 다섯 개 있다면 바꿔 가며 어느 것이 제일 나은지 시험할 수 있다.

효과가 큰 곳: GPU 하나에 들어가는 작은 모델. NER, 작은 생성 모델, 임베딩 모델을 한 GPU에서 번갈아 돌린다.

워커별 배칭 23:50

게이트웨이가 요청을 여러 워커 풀로 보낸다. 배칭은 앞단에서 한꺼번에 하지 않고 워커마다 한다.

발표자의 측정: 공유 큐 하나를 모든 워커가 끌어가는 방식보다 성능이 좋았다. 모델이 달라도 전체 지연 시간이 줄었다.

워커 풀 나누기 25:10

무거운 모델용 풀과, L4 스팟 인스턴스에서 충분히 잘 도는 모델용 풀을 따로 둔다. 비싼 하드웨어를 낭비하지 않는다.

L4 스팟: 비교적 저렴한 GPU를 중단 가능 조건으로 더 싸게 빌린 것.

오토스케일링 25:30

쓰지 않을 때는 줄어든다.

운영 자산: Helm 차트, Kubernetes 클러스터, Terraform 설정이 모두 공개돼 있다. 코드만이 아니라 배포 전체가 오픈소스다. 31:00

이 구조 위에 작업 묶음을 올릴 수 있다. 문서 파싱, 콘텐츠 임베딩, 코드 생성, 이미지 캡션, 가드레일, 정책 점검용 구조화 생성 등이다. 발표자 팀의 동료는 독일어 전용 LoRA를 싸게 미세 조정해 독일 법률 문서 같은 좁은 영역에서 성능을 올렸다. 28:40

08

성능 주장: 임베딩 가격과 품질 27:00

발표자 팀이 지금까지 벤치마크를 낸 영역은 임베딩 모델이다. 생성 모델도 있지만 수치는 아직이다.

이 수치는 발표자 소속 회사의 자체 측정이다. 비교 대상인 "프런티어 모델"이 무엇인지, 어떤 과제였는지는 발표에서 밝히지 않았다.

발표자가 얻은 깨달음 28:00 모델 하나하나의 추론이 최적화되지 않았더라도, 인프라와 구조가 잘 짜여 있으면 전체 지연 시간과 성능이 좋아진다. 프로덕션 부하에서는 이 끝에서 끝까지의 개선이 더 중요했다. 발표자 팀은 둘 다 하고 있다.
09

앞으로: 모델 라우팅과 모델 회의 31:50

추론을 작업 흐름 속의 작은 상자 하나로 풀어 두면 문서 밖으로도 넓힐 수 있다. 녹취록, 그래프 데이터, 온톨로지 생성, 구조화 생성 등이다. 아래는 아직 만들지 않은 로드맵이다.

과제에 따라 모델 고르기 32:00

  • 도구 호출이 도구 자체에 묶이지 않고, 그 밑에서 어떤 모델을 쓸지도 고른다. 예: "이 호출은 싼 OCR로".
  • 의도 파악과 에이전트 혼합 mixture of agents 방식도 실험 중이다.

따뜻한 모델을 먼저 친다 33:20

GPU에 이미 올라와 있는 모델은 바로 응답한다. 그래서 어느 모델이 올라와 있고 무엇이 방금 내려갔는지를 보고 라우팅할 수 있다. 때로는 비싸지만 이미 올라온 모델을 쓰는 편이, 싸지만 다시 올려야 하는 모델보다 저렴하다. 이 논리는 도구 수준을 넘어 비용과 사용량을 최적화한다.

판사 모델과 모델 회의 35:00

모델끼리 서로 판정하는 판사 구조나 모델 회의 council of models도 선택지다. 과제 난이도에 따라 추론 도구를 끼우거나 호출할 모델을 바꾸는 식이다.

발표자가 실제로 겪은 문제 35:30 요약 도구에 생각 토큰 thinking tokens을 쓰는 모델을 붙였더니, 요약이 아주 짧거나 아예 나오지 않았다. 출력이 생각 쪽에서 다 소진됐기 때문이다. 어떤 모델을 쓰는지, 생각 토큰을 켜는지 끄는지를 확인해야 한다.

라우터와 회의 구조의 단점도 안다. GPU가 끝없는 추론에 낭비될 수 있다. 편향된 판사 모델이 생길 수 있다. 지표를 최적화하다 보면 지표가 진짜 목표에서 멀어지고 모델이 그것을 해킹해 평가로 쓸 수 없게 된다. 발표자 팀은 그래서 먼저 평가에 힘을 쏟는다고 말한다.

10

발표자의 핵심 메시지 37:20

인프라와 추론은 생각보다 훨씬 중요하다. Claude Code와 편하게 일하는 겉모습 아래에서 바탕은 결국 추론이다.발표자의 말을 옮김

문서와 모델 카탈로그 38:00

  • 지원 파일 형식, LoRA가 들어가는 자리, 문제 해결 안내가 문서에 있다.
  • 모델 카탈로그에서 출력 형식과 아키텍처별로 고를 수 있다. 모델 계열마다 어텐션 구현이 달라 같은 방식으로 순전파를 돌릴 수 없으므로, 계열별 런타임이 따로 있다.
  • 모델은 인코딩용과 스코어링용으로 꼬리표가 붙어 있다. 스코어링 모델은 리랭킹에 쓴다. 이 MCP로 나만의 검색 파이프라인을 만들 수 있다.
  • 퀵스타트와 모델 버전 안내가 있고, OpenAI API로 만든 흐름을 옮겨 오는 방법도 있다.

런던에서 Tech Europe, DeepMind와 함께 해커톤을 열었다. 참가자들은 검색과 리랭킹, 생성 양쪽을 시험했다. 39:50

11

질의응답: 프라이버시는 정말 지켜지나 42:00

질문발표자의 답
Claude는 원본을 보나보지 않는다. 가려진 버전만 받는다. 지금 구조에서는 그 쪽만 본다.
Claude가 엉뚱하게 원본에 접근하면그런 일이 생기는지 평가할 수 있다. 발표자의 테스트에서는 MCP와 나머지를 VPC에 두었을 때 새지 않았다. 가드레일을 더 둘 수 있다. 최악의 경우 오픈소스 모델로 하네스를 직접 만들어도 된다. 그래도 토큰 절약과 맥락 개선은 유지된다.
클러스터는 꼭 Superlinked 것이어야 하나아니다. 저장소의 Terraform으로 내 클러스터를 세울 수 있다. 관리형 클러스터는 데모와 해커톤용이다. GPU가 있으면 완전히 내 것으로 운영한다.
MCP 서버가 파일을 갖고 있나파일은 메인 워커로 보내지고 거기서 처리된다.

질문자의 목소리는 자막에 거의 잡히지 않았다. 위 질문 문장은 발표자가 다시 읽어 준 내용으로 재구성한 것이다.

12

핵심 정리

  1. 출발점은 프라이버시, 토큰 비용, 적응성 세 가지다. 옵시디언 정리는 쉬웠고 오픈소스 추론을 규모 있게 돌리는 것이 어려웠다.
  2. 무거운 전처리는 내 VPC에서 하고, 에이전트에는 작고 가려진 결과만 돌려준다.
  3. 플러그인은 내 기기에서 돈다. MCP 서버 + 전용 클러스터는 같은 경험을 내 클라우드로 옮긴다.
  4. 구조는 세 층이다. MCP 클라이언트(내 기기), MCP 서버(내 VPC), GPU 클러스터(내 VPC).
  5. 서버는 도구만 노출한다. 샘플링과 유도 같은 양방향 기능은 프라이버시 때문에 쓰지 않는다. 전송은 스트리밍 HTTP다.
  6. 도구는 OCR, 엔티티 추출, 캡션·태그, 구조화 생성, 요약, 질의응답 여섯 가지다. 새 도구는 PR로 더할 수 있다.
  7. 데모에서 NDA의 10개 구간을 가렸고, 스캔 이미지는 OCR로 읽으며 동시에 가렸다. Claude Code는 가려진 버전만 본다.
  8. 추론 엔진의 핵심은 핫스왑, 워커별 배칭, 워커 풀 나누기, 오토스케일링이다. 배포 설정까지 오픈소스다.
  9. 임베딩에서 가격 약 10분의 1, 품질 99.8%라고 발표자는 주장한다. 자사 측정이다.
  10. 로드맵은 모델 라우팅과 모델 회의다. 생각 토큰을 켠 모델은 요약을 망칠 수 있다. 결론은 바탕은 추론 인프라라는 것이다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 이 프로젝트를 시작한 세 가지 목표는?
토큰 절약, 프라이버시(직접 호스팅), 적응성(여러 모델과 LoRA를 바꿔 쓰기).
Q2옵시디언 정리와 추론 중 어느 쪽이 병목이었나?
추론. 데이터를 저장하고 연결하는 것은 쉬웠고, 오픈소스 모델을 규모 있게 돌리고 여러 모델을 시험하고 프로덕션에 배포하는 것이 어려웠다.
Q3플러그인 대신 MCP 서버를 택한 이유 세 가지는?
전용 클러스터가 있으니 책임을 나누는 편이 낫다. 워커 풀과 GPU를 내가 통제한다. 에이전트에는 필요한 도구만 노출한다.
Q4세 층 구조에서 각 층은 어디에 있나?
MCP 클라이언트·호스트는 내 기기(Claude Code 등). MCP 서버와 GPU 클러스터는 내 VPC.
Q5MCP 표준의 샘플링과 유도를 이 프로젝트가 쓰지 않는 이유는?
프라이버시. 클라이언트 쪽으로 요청을 되돌리는 양방향 통신 대신, 서버는 악수 때 등록한 도구만 노출하고 응답만 한다.
Q6토큰 절약이 가장 분명하게 드러나는 작업은?
OCR. 이미지가 섞인 PDF 10쪽을 오픈소스 OCR로 먼저 읽고 텍스트만 돌려주면 토큰이 줄고 컨텍스트도 덜 찬다.
Q7데모에서 Claude Code가 받은 것은 무엇이고 받지 않은 것은 무엇인가?
가려진 마크다운과 라벨 집계를 받았다. 원본 NDA와 스캔 이미지는 받지 않았다. 처리는 VPC 안에서 끝났다.
Q8배칭을 앞단 공유 큐가 아니라 워커마다 한 이유는?
발표자 팀의 측정에서 공유 큐 하나를 모든 워커가 끌어가는 방식보다 성능이 좋았고, 모델이 달라도 전체 지연 시간이 줄었다.
Q9핫스왑이 특히 효과적인 모델 종류는?
GPU 하나에 들어가는 작은 모델. NER, 작은 생성 모델, 임베딩 모델을 한 GPU에서 번갈아 올린다.
Q10요약 도구에서 발표자가 겪은 문제와 원인은?
요약이 아주 짧거나 아예 안 나왔다. 생각 토큰을 쓰는 모델이라 출력이 생각 쪽에서 소진됐기 때문이다. 모델 선택과 생각 토큰 설정을 확인해야 한다.
Q11"따뜻한 모델"에 따른 라우팅은 무슨 뜻인가?
GPU에 이미 올라온 모델은 바로 응답하므로, 비싸지만 올라온 모델을 쓰는 편이 싸지만 다시 올려야 하는 모델보다 저렴할 수 있다는 것.
Q12발표자가 말한 단 하나의 결론은?
인프라와 추론이 생각보다 훨씬 중요하다. 에이전트 친화적인 겉모습 아래의 바탕은 추론이다.
