사람은 비동기 API다

에이전트가 사람의 답을 기다리는 일은 며칠이 걸릴 수도 있다. 발표자는 이 기다림을 함수 호출로 막아 두지 말고, 대기 조건과 시그널로 그 작업 하나만 멈춰 두라고 말한다.

원본 영상: The Human Is an Async API 발표: Melanie Warrick (Temporal)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 발표자가 소속 회사 Temporal의 기능을 데모로 보여 주는 발표다. 수치와 성능 주장은 모두 발표자가 말한 것이고 따로 확인하지 않았다. 자막에 "80K"로 찍힌 이름은 발표자가 다른 곳에서 "ADK", "Google ADK plugin"이라고 부른 Google ADK로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트 시스템에 사람이 끼면 답이 오기까지 몇 분에서 몇 주가 걸린다.
  2. 이 기다림을 평범한 함수 호출로 짜면 답이 올 때까지 막히고, 서버가 죽으면 무엇을 기다리던 중이었는지 잃는다.
  3. 발표자의 처방은 두 가지다. 대기 조건으로 그 작업 하나만 멈추고, 시그널로 사람의 답을 나중에 넣는다.
  4. Temporal은 코드를 워커·워크플로·활동으로 나눠 상태를 기록한다. 에이전트 루프는 워크플로, 모델 호출과 도구 호출은 활동이다.
  5. 데모에서 워커를 죽인 채 승인을 눌러도 승인이 저장됐다. 워커가 돌아오자 이벤트 기록을 재생해 배달까지 이어졌다.
  6. 사람이 먼저 바꾸는 경우도, 에이전트가 사람을 부르는 경우도 같은 두 가지로 처리한다. ADK와 LangGraph 어느 쪽에도 붙는다.
  7. 사람을 넣을지는 틀렸을 때의 비용으로 정한다. 너무 자주 물으면 사람은 읽지 않고 "예"만 누른다.
01

데모: 주문을 바꾸는 고객 00:20

발표는 데모로 시작한다. Temporal의 마스코트 Ziggy가 샌프란시스코 Ferry Building에서 아이스크림 가게를 한다는 설정이다.

배달은 에이전트 세 개가 나눠 맡는다. 차량 에이전트, 고객 에이전트, 배차 에이전트다. 에이전트는 Google의 ADK Agent Development Kit로 만들었다. Temporal은 그 안에 들어가 상태를 추적한다.

Temporal 화면에는 이벤트 기록 event history이 보인다. 맨 위에는 배달 활동 전체를 묶는 부모 워크플로가 있다.

사람이 끼어드는 순간 02:00

여러 에이전트가 도는 시스템에도 사람이 판단을 넣어야 할 때가 있다. 이를 사람 개입 human in the loop이라고 한다. 데모의 흐름은 이렇다.

  1. 고객이 "주문을 바꾸고 싶어요"라고 변경을 보낸다.
  2. 그 주문을 맡은 기사 A만 멈춰서 변경을 기다린다.
  3. 다른 사람이 변경을 받아들일지 정한다. 데모에서는 승인을 누른다.
  4. 변경이 처리되고, 주문은 다음 목적지인 Oracle Park로 간다.
이 데모에서 볼 것 사람의 판단을 기다리는 동안에도 다른 주문은 계속 들어오고 배달됐다. 기다림이 시스템 전체가 아니라 그 작업 하나만 멈춘다. 발표자는 잘못 만들면 변경 하나가 시스템 전체를 깨뜨릴 수 있다고 짚었다.

발표자는 이 장면을 Temporal과 ADK를 붙인 지속 실행 durable execution이라고 소개했다.

에이전트 루프와 하네스 03:40

데모 뒤에 발표 제목이 나온다. "사람은 비동기 API다."

에이전트의 뼈대는 루프다. 추론하고, 행동하고, 결과를 관찰한 뒤 다시 추론한다 reason · act · observe. 생각·행동·인지라고 부르기도 한다. 코드로는 for 루프나 while 루프 하나다.

올해 많이 나온 말은 하네스 harness다. 에이전트를 프로덕션에 올리려고 모델 둘레에 붙이는 구조를 말한다. 04:10

하네스에 무엇이 들어가는지는 아직 논쟁 중이다. 발표자가 정리한 후보는 이렇다.

  • 모델 자체
  • 도구
  • 메모리
  • 가드레일과 보안

발표자는 자신이 하네스 전문가는 아니라고 밝혔다. 조사한 범위의 지도를 보여 줄 뿐이라고 했다. 다만 한 가지는 분명히 주장한다. 그 그림에 내구성 durability도 들어가야 한다.

Temporal의 세 가지 기본 단위 05:40

Temporal은 분산 시스템의 실패 처리와 상태 관리를 표준화하는 도구다. 에이전트가 들어간 시스템도 분산 시스템이다.

Temporal은 소프트웨어이면서 서비스다. 소프트웨어는 코드에 바로 붙여 쓰는 기본 단위 primitive를 준다. 발표자는 Python, TypeScript, Rust 등을 예로 들었다.

워크플로 workflow시스템의 단계를 추적한다에이전트 루프, ADK 에이전트, 흐름 속 한 단계

발표자는 뒤에서 이 구분을 한 줄로 정리한다. 워크플로는 결정적이고, 활동은 비결정적이다. 12:30

보충 설명: 왜 이렇게 나누나 (발표에 없는 내용) 결정적 deterministic이란 같은 입력이면 늘 같은 결과를 낸다는 뜻이다. 워크플로는 나중에 기록을 다시 읽어 같은 자리로 돌아와야 한다. 그래서 매번 같은 결정을 내려야 한다. 모델 응답이나 외부 API처럼 결과가 매번 다를 수 있는 일은 활동으로 빼고, 그 결과를 기록에 남긴다.

Temporal은 오픈소스라 무료로 직접 호스팅할 수 있다. 상태 관리를 Temporal의 서비스에 맡기면 돈을 낸다. 07:10

발표자는 Temporal 소속이고, 이 발표는 Temporal과 그 연동 기능을 소개하는 자리다. "표준화한다", "수백만 개까지 확장된다" 같은 말은 제품 설명이라는 점을 감안해 읽자.

사람을 그냥 부르면 생기는 일 07:20

사람은 도구가 아니다. 하지만 에이전트 입장에서 사람은 도구처럼 쓰인다. 정보를 받아 루프에 넣어 주는 존재이기 때문이다.

"사람을 부른다"를 평범한 함수 하나로 짜면 두 가지 문제가 생긴다. 07:40

  1. 블로킹 호출 blocking call이 된다. 답이 올 때까지 그 자리에서 멈춰 있다.
  2. 서비스가 죽으면 잊는다. 사람과 무엇을 주고받던 중이었는지 기록이 남지 않는다.
함수로 부르기답이 올 때까지 막힌다서버가 죽으면 기다리던 내용을 잃는다
→
대기 조건 + 시그널그 작업 하나만 멈춘다멈춘 상태는 저장소에 남고, 답은 아무 때나 넣는다

대기 조건과 시그널 08:00

대기 조건 · wait condition
  • 사건 하나를 떼어 내고 "조건이 채워질 때까지 멈춤"을 건다
  • 이 멈춤은 워크플로, 즉 내구성 층에 저장된다
  • 시스템이 쓰러졌다 돌아와도 어디서 멈췄는지 안다
시그널 · signal
  • 사람의 답을 아무 때나 실행 중인 워크플로에 넣는다
  • 답이 들어오면 멈췄던 워크플로가 다시 움직인다
  • 그동안 시스템의 나머지는 막히지 않고 돈다

덤으로 따라오는 것 08:50

  • 스레드를 붙잡고 있지 않는다.
  • 크래시가 나도 살아남는다.
  • 타임아웃을 걸 수 있다. 사람을 얼마나 오래 기다릴지 정한다.
  • 멈춰 둔 워크플로가 수백만 개여도 시스템이 돌아간다고 발표자는 말했다.
06

코드로 보면: ADK에 붙이기 10:10

발표자가 보여 준 Python 코드는 짧았다. ADK에 Temporal을 붙이는 방법은 세 단계다.

  1. 모델을 Temporal의 모델 클래스로 감싸 ADK 에이전트에 넘긴다. 모델 호출이 활동이 된다.
  2. 도구는 Temporal의 activity tool로 감싼다. 도구 호출도 활동이 된다.
  3. 워커를 띄울 때 Google ADK 플러그인을 넣는다.

그 다음은 평소 ADK 에이전트를 돌리듯 돌리면 된다.

대기 조건과 시그널의 실제 동작 11:00

대기 조건은 Python asyncio의 await로 건다. 그러면 그 워크플로의 다음 코드는 실행되지 않고 멈춘다. 같은 워크플로의 다른 코루틴 coroutine과 다른 워크플로는 계속 돈다.

시그널은 실행 중인 워크플로에 어떤 입력이든 넣을 수 있다. 할 일 없이 기다리기만 하는 워크플로는 메모리에서 내려가 주차 parked 상태가 된다.

예시: 아래 코드는 발표 슬라이드를 옮긴 것이 아니다. 같은 구조를 Temporal Python SDK 문법으로 짧게 다시 써 본 것이다.

from datetime import timedelta
from temporalio import workflow

@workflow.defn
class OrderApprovalWorkflow:
    def __init__(self) -> None:
        self.decision: str | None = None

    @workflow.signal
    def submit_decision(self, decision: str) -> None:
        # 시그널: 사람의 답이 여기로 들어온다
        self.decision = decision

    @workflow.run
    async def run(self, order_id: str) -> str:
        # 대기 조건: 이 워크플로만 멈춘다. 다른 워크플로는 계속 돈다
        # 3일 안에 답이 없으면 타임아웃 예외가 난다
        await workflow.wait_condition(lambda: self.decision is not None, timeout=timedelta(days=3))
        return self.decision

# 승인 화면 쪽: 몇 분 뒤든 며칠 뒤든 답을 넣는다
handle = client.get_workflow_handle(workflow_id)
await handle.signal(OrderApprovalWorkflow.submit_decision, "approve")

고액 주문 13:40

워커 강제 종료 15:10

  2. 오프라인 상태에서 승인을 누른다. 승인은 내 서비스가 아니라 Temporal 쪽 저장소에 기록되고 큐에 쌓인다.
  3. 워커를 다시 띄운다.
  4. 이벤트 기록이 재생 replay된다. 이미 한 일을 다시 하는 게 아니다. 기록을 읽어 마지막으로 멈춘 위치까지 따라간다. 16:00
  5. 현재 상태를 알게 된 워크플로가 다음 단계로 간다. 승인이 반영돼 주문이 배정됐고, 배달까지 끝나 있었다.

발표자는 이를 시스템이 내려갔다가 복구되는 장면이라고 정리했다. 이런 분산 시스템은 복잡하다. 그래서 복잡한 상태를 다룰 기본 단위가 필요하다는 것이다.

사람은 언제 루프에 넣나 16:40

발표자는 이것이 진짜 질문이고 어려운 질문이라고 했다. 답은 사례마다 다르다.

틀렸을 때의 비용이 나에게 얼마인가?발표자가 던진 판단 기준을 옮김
사람을 넣는 쪽으로
  • 틀렸을 때의 비용이 크다
  • 보안이 걸려 있다
  • 모델은 확률적이라 늘 믿을 만하지는 않다
덜 넣는 쪽으로 17:10
  • 목표는 가능한 한 자율로 돌리는 것이다
  • 질문이 잦으면 경고 피로 alert fatigue가 온다
  • 사람은 읽지 않고 "예, 예, 예"를 누르게 된다

모델이 좋아지면 덜 물어도 된다. 하지만 모델이 확률적이라는 사실은 남는다. 그래서 풀려는 문제마다 이 저울을 직접 따져야 한다.

발표자의 마무리 17:40

  • 누가 시작하든 쓰는 기본 단위는 두 개다. 사람이 먼저 바꾸든, 컴퓨터가 사람을 부르든 같다.
  • 대기 조건으로 워크플로를 멈춘다.
  • 시그널로 사람이 "결과는 이거다, 계속 가라"를 넣는다.
  • 워커를 내렸다 다시 올려도 그 흐름은 이어진다.
  • ADK, LangGraph처럼 여러 프레임워크에 붙는다.
제목 풀이 "사람은 비동기 API다"는 사람을 부르는 일을 비동기 API 호출처럼 다루라는 말로 읽을 수 있다. 요청을 보내 두고 다른 일을 계속한다. 답이 오면 그때 이어 간다. 답이 언제 올지는 모른다고 가정한다.

발표자는 데모 코드가 GitHub에 있다고 했다. 슬라이드도 나중에 같은 저장소에 링크하겠다고 했다. 주소는 화면의 QR 코드로만 안내됐다. 18:20

11

핵심 정리

  1. 에이전트는 추론·행동·관찰을 반복하는 루프다. 프로덕션용 하네스에는 내구성도 들어가야 한다.
  2. 사람을 평범한 함수로 부르면 답이 올 때까지 막히고, 서버가 죽으면 기다리던 내용을 잃는다.
  3. 처방은 두 가지다. 대기 조건으로 그 작업만 멈추고, 시그널로 사람의 답을 넣는다.
  4. 멈춘 상태는 워크플로에 저장된다. 할 일이 없는 워크플로는 메모리에서 내려가 주차된다.
  5. Temporal의 기본 단위는 워커(실행), 워크플로(단계 추적, 결정적), 활동(바깥과 주고받기, 비결정적)이다.
  6. 에이전트 루프는 워크플로에, 모델 호출과 도구 호출은 활동에 둔다.
  7. 사람이 먼저 바꾸는 경우와 에이전트가 사람을 부르는 경우 모두 같은 두 단위로 처리한다.
  8. ADK는 모델·도구 감싸기와 워커 플러그인으로, LangGraph는 interrupt와 대기 조건, 시그널로 붙인다.
  9. 워커가 죽어도 승인은 저장된다. 재시작하면 이벤트 기록을 재생해 이어서 진행한다.
  10. 사람을 넣을지는 틀렸을 때의 비용과 경고 피로 사이에서 사례마다 정한다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1사람을 평범한 함수 호출로 부르면 생기는 두 가지 문제는?
답이 올 때까지 그 자리에서 막히는 블로킹 호출이 된다. 서비스가 죽으면 사람과 무엇을 주고받던 중이었는지 잃는다.
Q2대기 조건과 시그널은 각각 무슨 일을 하나?
대기 조건은 조건이 채워질 때까지 그 워크플로 하나만 멈추고, 멈춘 상태를 저장한다. 시그널은 사람의 답을 아무 때나 실행 중인 워크플로에 넣는다.
Q3첫 데모에서 고객이 주문을 바꿨을 때 무엇이 멈추고 무엇이 계속 돌았나?
그 주문을 맡은 기사 A만 멈췄다. 다른 주문은 계속 들어오고 배달됐다.
Q4Temporal의 세 가지 기본 단위와 각자의 역할은?
워커는 코드를 실행한다. 워크플로는 시스템의 단계를 추적한다. 활동은 모델 호출이나 도구 호출처럼 바깥과 주고받는 일을 맡는다.
Q5모델 호출과 도구 호출을 활동에 두는 이유는?
바깥과 주고받는 일이고 결과가 매번 다를 수 있다. 발표자 표현으로 활동은 비결정적이고 워크플로는 결정적이다.
Q6할 일 없이 사람을 기다리는 워크플로는 어떻게 되나?
메모리에서 내려가 주차 상태가 된다. 스레드를 붙잡지 않으므로 이런 워크플로가 많아도 시스템이 돈다. 발표자는 수백만 개를 말했다.
Q7ADK에 Temporal을 붙이는 세 단계는?
모델을 Temporal의 모델 클래스로 감싼다. 도구를 activity tool로 감싼다. 워커에 Google ADK 플러그인을 넣는다.
Q8LangGraph에서 에이전트가 사람을 부르는 흐름은?
노드에서 interrupt로 질문을 던진다. 워크플로는 대기 조건으로 멈춘다. 사람이 답하면 시그널이 그 답을 워크플로에 넣는다.
Q9워커를 죽인 상태에서 승인을 누르면 어떻게 되나?
승인은 Temporal 쪽 저장소에 기록되고 큐에 쌓인다. 워커가 돌아오면 이벤트 기록을 재생해 상태를 되찾고, 승인을 반영해 다음 단계로 간다.
Q10재생(replay)은 처음부터 다시 실행하는 것과 어떻게 다른가?
이미 한 일을 다시 하지 않는다. 기록을 읽어 마지막으로 멈춘 위치까지 따라가 현재 상태를 안다.
Q11사람을 루프에 넣을지 정하는 기준과, 너무 자주 넣을 때의 위험은?
기준은 틀렸을 때의 비용이다. 너무 자주 물으면 경고 피로가 와서 사람이 읽지 않고 승인만 누른다.
