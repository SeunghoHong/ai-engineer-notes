에이전트는 매번 신입으로 출근한다

코딩 에이전트는 세션을 열 때마다 프로젝트를 처음 보는 신입 직원과 같다. 발표자는 코드를 쓰기 전에 프로젝트 규칙과 코드 지도를 주고, 코드를 쓰는 동안 결정론적 검사로 계속 확인하라고 말한다.

원본 영상: Your AI Agent Starts Every Session Like a New Hire 발표: Killian Carlsen-Phelan (Sonar)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 경우에만 바로잡았다. mm:ss는 영상 위치다.

읽기 전에 이 발표는 Sonar의 새 제품을 소개하는 자리다. 효과 수치, 데모, "AI 리뷰보다 결정론적 검사가 낫다"는 주장 모두 발표자 회사의 제품과 직결된다. 그 점을 감안해 읽자. 다만 "코드를 쓰기 전에 맥락을 주고, 쓰는 동안 검사한다"는 원칙 자체는 특정 제품 없이도 적용할 수 있다.
3분 요약
  1. 코딩 에이전트는 세션마다 프로젝트 규칙을 모르는 신입으로 시작한다. 맥락을 찾느라 시간과 토큰을 쓴다.
  2. 코드베이스에 이미 있는 문제는 에이전트가 그대로 따라 한다. 새 문제까지 더해지면 품질을 지키기 어렵다.
  3. 발표자가 인용한 Sonar 설문에서 개발자 96%가 AI 코드를 완전히 믿지 않았지만, 푸시 전에 완전히 확인한 사람은 48%였다.
  4. 해법은 두 단계다. 쓰기 전에 안내(코딩 규칙, 코드 구조 지도)하고, 쓰는 동안 검증(편집마다 빠른 검사, 턴 끝에 깊은 검사)한다.
  5. 발표자는 모델 선택 다음으로 큰 성능 지렛대는 처음에 주는 맥락이라고 강조한다.
  6. 검증은 같은 입력에 늘 같은 결과를 내는 결정론적 분석이어야 한다고 주장한다. 에이전트가 자기 코드를 리뷰하는 방식은 믿기 어렵다고 본다.
  7. 데모에서 에이전트는 테스트까지 썼지만 임시 파일 권한을 명시하지 않는 보안 문제를 만들었다. 첫 수정도 통과하지 못했고, 다시 고친 뒤에야 검사를 통과했다.
01

매 세션이 신입의 첫날 00:00

Sonar는 코드 검증 플랫폼을 만드는 회사다. 발표 주제는 검증을 에이전트 코딩 루프 안으로 옮기는 방법이다.

IDE에서 에이전트 세션을 새로 열면 매번 처음부터 시작한다. 새로 뽑은 직원이 첫 출근한 것과 같다. 에이전트는 다음을 모른다.

  • 프로젝트가 지금까지 지켜 온 관례
  • 팀의 코딩 가이드라인
  • 미리 정해 둔 아키텍처 규칙

그래서 기능을 맡기면 먼저 주변을 뒤진다. 예를 들어 "새 API 엔드포인트를 만들어"라고 하면, 기존 엔드포인트가 어떻게 생겼는지부터 찾아야 한다.

이 탐색은 운에 달려 있다. 금방 찾을 수도 있고, 저장소 전체를 헤맬 수도 있다. 헤매는 만큼 시간과 토큰이 든다. 발표자는 이 문제가 충분히 고칠 수 있는 문제라고 본다.

02

나쁜 패턴은 그대로 복제된다 01:20

문제가 없는 코드베이스는 없다. 에이전트는 기존 코드를 보고 따라 쓰기 때문에, 이미 있는 문제 패턴도 그대로 복제할 가능성이 높다.

여기에 에이전트가 새로 만드는 문제가 더해진다. 발표자는 이것이 "만약"이 아니라 "언제"의 문제라고 말한다. 새 문제를 그때그때 잡지 못하면 코드 품질을 유지하기는 거의 불가능하다.

Sonar가 내놓은 답은 Sonar Vortex다. 어떤 코딩 에이전트에든 붙이는 플러그인이다. 목표는 두 가지다.

  1. 에이전트가 코드를 쓰기 전에 프로젝트를 알게 한다.
  2. 에이전트가 자기 코드를 결정론적으로 검증해, 새 문제를 들이지 않게 한다.

제품 이름은 자막에 나온 표기를 그대로 옮겼다.

03

테스트로 못 잡는 문제 02:20

발표자는 에이전트가 작은 기능을 만드는 과정을 미리 녹화했다. 에이전트는 2분도 안 돼 기능을 완성했다. 테스트 묶음도 직접 만들라고 지시했고, 실제로 만들었다.

그런데도 보안 문제가 하나 들어갔다. 기능은 로그 파일의 압축을 풀어 임시 파일에 쓰는 것이었다. 에이전트는 그 임시 파일의 권한을 명시적으로 정하지 않았다.

왜 잡기 어려운가 이런 문제는 테스트로 쓰기 어렵다. 시니어 리뷰어도 일부러 찾지 않으면 놓치기 쉽다. 리뷰에서 잡더라도 개발자나 에이전트에게 돌려보내 다시 고치고, 다시 올리고, 다시 리뷰해야 한다. 그만큼 시간과 돈이 들고 모두 지친다.
04

믿지 않으면서 확인도 안 한다 03:30

발표자는 이 불편이 개인 의견이 아니라며 Sonar의 설문을 인용했다. 개발자 1,100명 이상이 응답했다.

발표자는 48%를 "그중에서(of those)"라고 말했다. 전체 응답자 중 48%인지, 믿지 않는다는 96% 중 48%인지는 자막만으로 분명하지 않다. 어느 쪽이든 절반 미만이라는 점은 같다.

발표자는 이 숫자가 무섭다고 했다. 믿지 않는 코드를 확인도 없이 프로덕션에 내보내고 있다는 뜻이기 때문이다.

에이전트는 빨리 쓴다. 재작업rework은 속도를 늦춘다. 문제를 PR 단계에서야 발견하면 이미 늦었다는 것이 발표자의 주장이다.

05

안내하고, 검증한다 04:20

발표자는 애니메이션으로 차이를 보여 줬다. 격자는 코드베이스이고, 칸 하나가 파일 하나다. 공은 코딩 에이전트다. 아래 막대는 쓴 토큰, 곧 돈과 시간이다.

맥락 없이파일을 하나씩 뒤진다움직일 때마다 새 파일을 열어 보고, 토큰 막대가 계속 찬다. 틀린 곳은 PR 리뷰에서야 드러나고 일이 다시 에이전트에게 돌아간다.

쓰는 동안 받는 검사 06:00

시점검사보는 것
에이전트가 파일을 편집할 때마다빠른 검사방금 바꾼 파일
에이전트가 턴을 끝내기 전깊은 검사더 깊은 보안 문제, 파일을 넘나드는 데이터 흐름
문제가 나오면재검사에이전트가 고친 뒤 다시 확인

발표자에 따르면 Claude Code, Codex, Antigravity 같은 주요 에이전트에서 모두 동작한다. 직접 만든 에이전트나 오픈소스 에이전트에는 설정 가능한 MCP 클라이언트로 붙인다. 내부적으로는 Sonar가 제공하는 CLI와 MCP 도구 위에 만들어졌다.

06

발표자가 내세운 효과 07:20

토큰 사용량

평균 36% 적게 쓴다. 기존 코드베이스를 리팩터링하는 일에서 특히 효과가 크다고 했다.

프로덕션 장애

쓰는 사람들의 프로덕션 장애가 44% 줄었다.

거짓 경보

거짓 경보 비율이 매우 낮다고 했다. 구체적인 숫자는 말하지 않았다. 코딩 세션을 쓸데없는 지적으로 어지럽히지 않으려는 설계라고 설명했다.

세 주장 모두 자사 제품의 효과를 회사 사람이 발표한 것이다. 무엇과 비교한 수치인지, 어떤 표본에서 잰 것인지는 발표에서 설명하지 않았다. 36%와 44%는 서로 다른 지표라 한 차트에 나란히 그리지 않았다.

발표자는 전체를 한 줄로 요약했다. 에이전트를 안내하고, 변경을 검증한다.

07

CI의 분석 결과를 재사용 08:00

SonarQube는 20년 가까이 된 제품이다. 보통 CI 파이프라인의 한 단계로 돌린다. 보안 문제, 유지보수성 문제, 데이터 흐름 문제를 결정론적으로 분석하고, 코드의 그래프를 만들어 깊이 들여다본다.

Vortex의 아이디어는 이미 서버에 쌓인 이 지식을 에이전트에게 처음부터 넘기는 것이다.

  • CI에는 이미 SonarQube 스캔이 있다.
  • Vortex는 그 스캔이 알아낸 것을 재사용한다.
  • 그래서 에이전트가 바꾼 파일만 빠르게 검사해도, 나머지 코드에 대한 정보는 이미 알고 있다.
08

데모 1: 코드를 쓰기 전에 묻기 09:00

발표 전날 밤 녹화한 실제 작업이다. 세션이 시작되면 따로 설정하지 않아도 SonarQube가 함께 켜진다. CLI와 훅hook 시스템이 감지되고, 시크릿 감지도 켜진다.

시크릿 유출 방지 09:20 발표자는 이 부분을 깊게 다루지 않았다. 다만 시크릿 유출은 막기 가장 쉬운 문제이면서, 터지면 조직에 가장 비싼 문제 중 하나라고 했다. 플러그인은 GitHub로 가는 유출과 에이전트 컨텍스트 메모리로 들어가는 유출을 막는다고 설명했다.

프롬프트에 Sonar 관련 지시를 붙여 넣지 않았다. 모두 자동으로 불러온다.

요청은 이랬다. 로그 파일의 압축을 풀어 임시 파일에 쓰고, 같은 파일을 계속 재사용하고, 재사용됨을 증명하는 테스트를 쓴다.

에이전트가 먼저 던진 두 질문 10:10

  1. 이 클래스는 어디에 있나? 대상 GC 로그 파일 클래스의 위치, 부모·자식 구조, 기존 패턴과 가이드라인을 받는다.
  2. 이 프로젝트의 Java 코딩 가이드라인은 무엇인가? Sonar가 기본으로 정한 Java 가이드라인에, 팀이 추가한 요구 사항이 함께 들어온다.
모델 선택을 빼면, 처음에 에이전트가 받는 맥락과 방향 제시가 에이전트 성능을 움직이는 가장 큰 지렛대다.발표자의 말을 옮김 11:00

앞단에서 많이 해 둘수록 뒤에서 재작업, 방향 수정, 개입이 줄어든다.

이것이 Vortex의 안내 단계다. 애니메이션처럼 파일을 하나씩 뒤지는 대신 지도를 받는다. 에이전트는 기존 테스트를 살펴 동작 방식을 파악하고 금방 구현으로 넘어간다. 이 과정이 몇 초 걸렸다고 했다. 기능마다 다르지만, Vortex 없이 같은 기능을 돌리면 grep으로 헤매느라 더 오래 걸린다고 했다.

09

데모 2: 편집할 때마다 검사 12:00

에이전트는 구현을 하면서 자기 테스트 묶음도 추가했다. 그 안에서 임시 파일을 만드는 부분이 나중에 문제가 된다.

에이전트는 테스트 결과를 확인한 뒤, 바꾼 파일 두 개에 대해 Sonar 검사를 돌렸다.

  • 파일을 편집하거나 추가할 때마다 Vortex 분석이 돈다.
  • 사람이 강제할 필요가 없다. 신경 쓰지 않아도 자동으로 켜진다.

발표자는 자동화된 작업 흐름을 쓰는 팀, 이른바 "소프트웨어 공장"처럼 에이전트를 대량으로 돌리는 팀일수록 이런 신뢰 층이 꼭 필요하다고 말한다.

10

AI가 AI를 검사하지 않는다 13:00

발표자는 이 검사가 "AI가 AI를 검사하는 것"이 아니라고 강조한다. 에이전트가 자기 코드를 검사하는 것은 더더욱 아니다.

AI가 검사할 때 (발표자 주장)
  • 에이전트가 자기 코드를 만들 때와 리뷰할 때 생각하는 방식이 다르다
  • 다른 에이전트도 기존 코드를 리뷰하며 놓치거나 지어낼 수 있다
  • Sonar는 이것이 가장 믿기 어려운 방법 중 하나라고 봤다
결정론적 검사
  • 같은 코드를 분석하면 매번 같은 결과가 나온다
  • 그래서 믿을 수 있고, 관리할 수 있고, 규정 준수를 증명하기 좋고, 예측할 수 있다

발표자는 AI 리뷰 자체를 반대하지는 않는다. Sonar에도 AI 리뷰 도구가 있다고 했다(자막상 이름은 "Guitar"(추정)). 그림은 이렇다. AI가 코드를 쓰고, 그 위에 결정론적 검사 층이 얹히고, 그다음에 AI 리뷰가 다시 온다.

"AI 리뷰는 믿기 어렵고 결정론적 분석이 낫다"는 주장은 정적 분석 도구를 파는 회사의 관점이다. 비교 실험 결과는 발표에서 제시하지 않았다.

11

데모 3: 고쳤다는데 안 고쳐졌다 14:10

Vortex 분석에서 지적 6개가 나왔다. Claude는 그중 2개가 방금 쓴 줄에 있고, 4개는 원래 있던 코드에 있다고 정리했다.

도구가 시끄럽지 않도록 설계했다고 발표자는 말한다. 문제 하나를 찾았다고 해서 "다른 세 개도 고쳐"라고 요구하지 않는다.

  • 새로 쓴 코드의 문제는 반드시 고치게 한다.
  • 기존 코드의 문제는 사람에게 알려 두기만 한다. 나중에 고칠지는 팀이 정한다.

임시 파일 권한 문제 14:50

새 코드의 지적 중 하나가 처음 말한 보안 문제였다. Claude는 로그를 기본 임시 폴더에 두면서, 누가 그 파일을 읽을 수 있는지 정하지 않았다. 많은 서버에서 그 폴더는 여러 사용자가 함께 쓴다.

  1. 첫 수정: Claude가 고쳤다고 했다.
  2. 재검사: Vortex가 다시 돌고 "임시 파일이 여전히 공유 디렉터리에 있어서 지적이 남아 있다"고 판정했다. 15:10
  3. 원인: 첫 수정은 Java의 기본값에 기댔다. Mac과 Linux에서는 기본값이 이미 소유자 전용이다. 하지만 Sonar 규칙은 권한을 명시적으로 지정해야 한다는 높은 기준을 둔다.
  4. 두 번째 수정: Claude가 다시 고쳤고, 고칠 때마다 Vortex 분석이 다시 돌았다.
이 장면에서 배울 점 "기본값이 안전하니 괜찮다"와 "안전하다고 코드에 적혀 있다"는 다르다. 기본값은 운영체제나 설정에 따라 달라질 수 있다. 명시적으로 적어 두면 어디서 돌든 같은 결과를 보장한다.

발표자는 PR에 문제가 들어가지 않게 해야 한다고 강조한다. 빨리 잡을수록 문제의 범위가 작고, 고치는 데 드는 시간과 돈과 힘도 줄어든다.

12

정리: 얻는 것 16:20

데모에서 기억할 흐름은 세 가지다.

  1. 에이전트는 쓰기 전에 Sonar에게 먼저 물었다.
  2. Sonar가 지적하자, 에이전트는 통과할 때까지 스스로 계속 고쳤다.
  3. 마지막에 작업을 넘기기 전 데이터 흐름까지 보는 깊은 분석이 돈다.

발표자가 꼽은 효과는 이렇다.

  • 리뷰에서 주고받는 일이 줄어든다.
  • 문제를 그 자리에서 고친다.
  • 코드가 더 안전해진다.
  • 문제를 고치는 데 드는 시간과 돈이 줄어든다.
  • 에이전트 작업 흐름을 믿고 자동화할 수 있어서, 개발자 시간이 남는다.
13

핵심 정리

  1. 코딩 에이전트는 세션마다 프로젝트의 관례, 가이드라인, 아키텍처 규칙을 모르는 신입으로 시작한다.
  2. 맥락을 찾아 헤매는 탐색은 운에 달려 있고, 시간과 토큰을 쓴다.
  3. 에이전트는 코드베이스에 이미 있는 나쁜 패턴을 그대로 복제한다.
  4. 발표자가 인용한 설문에서 96%는 AI 코드를 완전히 믿지 않았고, 푸시 전 완전히 확인한 사람은 48%였다.
  5. 해법의 첫 단계는 안내다. 코딩 규칙, 허용 라이브러리, 코드 연결 지도를 먼저 준다.
  6. 둘째 단계는 검증이다. 편집마다 빠른 검사, 턴 끝에 파일을 넘나드는 깊은 검사를 돌린다.
  7. 발표자는 처음 주는 맥락이 모델 선택 다음으로 큰 성능 지렛대라고 말한다.
  8. 검증은 같은 입력에 같은 결과를 내는 결정론적 분석이어야 한다는 것이 발표자의 주장이다.
  9. 새 코드의 문제는 반드시 고치게 하고, 기존 코드의 문제는 알리기만 한다.
  10. 임시 파일 권한처럼 테스트로 잡기 어려운 문제는 기본값에 기대지 말고 명시해야 통과한다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 에이전트를 "신입 직원"에 비유한 이유는?
세션을 열 때마다 프로젝트의 관례, 코딩 가이드라인, 아키텍처 규칙을 모르는 상태로 시작하기 때문이다. 그래서 매번 맥락을 찾아 헤매야 한다.
Q2맥락 없이 일하는 에이전트가 치르는 비용 두 가지는?
탐색에 드는 시간과 토큰. 그리고 기존 코드의 나쁜 패턴을 그대로 따라 하는 품질 비용.
Q3Sonar 설문의 96%와 48%는 각각 무엇인가?
96%는 AI 생성 코드를 완전히 믿지 않는 개발자 비율, 48%는 푸시 전에 코드를 완전히 확인한 비율이다. 48%가 전체 기준인지 96% 중 기준인지는 자막만으로 분명하지 않다.
Q4에이전트가 코드를 쓰기 전에 받는 정보는?
아키텍처 가이드라인, 써도 되는 라이브러리 목록, 코딩 표준, 코드가 어떻게 연결되는지 보여 주는 지도.
Q5빠른 검사와 깊은 검사는 각각 언제 돌고 무엇을 보나?
빠른 검사는 파일을 편집할 때마다 바뀐 파일을 본다. 깊은 검사는 턴을 끝내기 전에 더 깊은 보안 문제와 파일을 넘나드는 데이터 흐름을 본다.
Q6바뀐 파일만 검사하는데도 나머지 코드를 아는 이유는?
CI에서 이미 돌고 있는 SonarQube 스캔의 결과를 재사용하기 때문이다.
Q7발표자가 꼽은 "모델 선택 다음으로 큰 성능 지렛대"는?
처음에 에이전트에게 주는 맥락과 방향 제시. 앞단에서 많이 해 둘수록 재작업과 개입이 줄어든다.
Q8발표자가 AI 리뷰 대신 결정론적 검사를 강조하는 이유는?
같은 코드를 분석하면 매번 같은 결과가 나와 믿고 관리하고 예측할 수 있다는 것이다. 에이전트의 자기 리뷰나 다른 에이전트의 리뷰는 놓치거나 지어낼 수 있다고 본다. 자사 제품과 직결된 주장이라는 점은 감안해야 한다.
Q9데모의 지적 6개를 도구는 어떻게 다뤘나?
새로 쓴 코드의 2개는 수정을 강제했다. 기존 코드의 4개는 사람에게 알리기만 하고, 고칠지는 나중에 정하게 했다.
Q10임시 파일 권한 문제에서 첫 수정이 통과하지 못한 이유는?
Java 기본값에 기댔기 때문이다. Mac과 Linux에서는 기본값이 이미 소유자 전용이지만, 규칙은 권한을 명시적으로 지정하라고 요구한다.
Q11임시 파일 권한 같은 문제가 리뷰에서 잘 안 잡히는 이유는?
테스트로 쓰기 어렵고, 시니어 리뷰어도 일부러 찾지 않으면 놓치기 쉽다. 잡더라도 다시 고치고 올리고 리뷰하는 데 시간과 돈이 든다.

용어뜻
에이전트 코딩 루프Agentic coding loop. 에이전트가 계획하고, 코드를 쓰고, 확인하고, 고치는 반복 과정
컨텍스트Context. 모델이 작업할 때 참고하도록 넣어 주는 정보 전체
토큰Token. 모델이 읽고 쓰는 글의 단위. 많이 쓸수록 비용과 시간이 든다
가드레일Guardrail. 에이전트가 정해진 범위를 벗어나지 않게 막는 장치
결정론적Deterministic. 같은 입력을 넣으면 매번 같은 결과가 나오는 성질
정적 분석Static analysis. 코드를 실행하지 않고 읽어서 문제를 찾는 방법
데이터 흐름 분석Data flow analysis. 값이 여러 함수와 파일을 거쳐 어디로 흘러가는지 추적하는 분석
CIContinuous integration. 코드를 올릴 때마다 빌드와 검사를 자동으로 돌리는 과정
훅Hook. 특정 사건(파일 편집, 턴 종료 등)이 일어날 때 자동으로 실행되는 명령
MCPModel Context Protocol. 에이전트가 외부 도구와 데이터에 연결하는 표준 방식
CLICommand-line interface. 터미널에서 명령어로 쓰는 프로그램
시크릿Secret. API 키, 비밀번호, 토큰처럼 밖으로 새면 안 되는 값
임시 파일Temp file. 작업 중 잠깐 쓰려고 만드는 파일. 기본 임시 폴더는 여러 사용자가 함께 쓰는 경우가 많다
파일 권한File permission. 누가 그 파일을 읽고 쓰고 실행할 수 있는지 정한 설정
재작업Rework. 리뷰에서 돌아온 코드를 다시 고치는 일
거짓 경보False positive. 멀쩡한 코드를 문제라고 잘못 지적하는 것
리팩터링Refactoring. 동작은 그대로 두고 코드 구조를 고치는 일
