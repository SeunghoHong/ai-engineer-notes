샌드박스를 걱정 없이 쓰는 법

AI 에이전트가 쓴 코드를 안전하게 돌리려면 샌드박스가 필요하다. 그런데 샌드박스 한두 개는 쉽고, 수백 개가 되면 문제가 따로 생긴다. 이 워크숍은 그 문제들을 레벨 8개짜리 깃발 뺏기 게임으로 직접 겪게 한다. 자원 폭주, 생명주기, 고아 프로세스, 사용자 배정, 쓰기 범위가 그 문제들이다.

원본 영상: How I Learned to Stop Worrying and Love the Sandbox 발표: Matt Brockman (E2B 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 발표자는 샌드박스 제품을 파는 E2B 소속이라, 제품 성능에 관한 말은 그 점을 감안해 읽자. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 샌드박스는 한 사용자의 코드가 다른 사용자나 내 서버를 건드리지 못하게 격리한 실행 환경이다. 에이전트가 CPU를 다 쓰거나, 파일을 지우거나, 비밀 키를 읽는 사고를 막는다.
  2. E2B는 메모리와 파일 시스템을 스냅샷으로 저장했다가 그대로 되살린다. 그래서 프로세스가 이미 켜진 상태에서 시작하고, 발표자 말로는 100밀리초 안에 뜬다.
  3. 샌드박스 한두 개는 쉽다. 수백, 수천 개가 되면 자원, 수명, 추적이 따로 문제가 된다. 워크숍은 그 문제를 8개 레벨로 쪼갰다.
  4. 레벨 1~4는 리눅스 기본기다. CPU, 메모리, 디스크를 잡아먹는 범인을 찾아 죽이거나 지운다.
  5. 레벨 5는 생명주기다. 작업 중에는 길게(1시간), 작업이 끝나면 짧게(1분) 수명을 다시 설정한다. 속도와 비용 사이의 저울질이다.
  6. 레벨 6은 고아 프로세스다. 스냅샷에서 되살리는 방식은 정리를 안 하면 지난 프로세스가 그대로 쌓인다. 발표자는 "샌드박스 관리의 상당 부분이 고아 죽이기"라고 했다.
  7. 레벨 7은 사용자별 배정이다. 샌드박스를 아무나 돌려 쓰지 말고 사용자 → 샌드박스 ID 표를 만들어 같은 사람이 같은 샌드박스로 돌아오게 한다.
  8. 레벨 8은 쓰기 범위다. 템플릿 캐시는 읽기 전용, 실행 캐시만 쓰기 허용처럼 에이전트가 쓸 수 있는 구역을 제한한다.
01

깃발 뺏기로 배우는 워크숍 01:00

이 발표는 강연이 아니라 실습이다. 참가자는 깃발 뺏기 Capture The Flag, CTF 형식의 레벨을 하나씩 푼다. 한 레벨을 풀면 코드 한 줄이 나오고, 그 코드로 다음 레벨이 열린다.

  • 모든 실습은 샌드박스 안에서 돈다. 참가자 컴퓨터에는 아무것도 설치하지 않는다. E2B 대시보드에서 샌드박스를 띄우고 브라우저로 들어간다.
  • 레벨마다 새 샌드박스가 하나씩 생긴다. 그 안에서 뭘 부숴도 처음 샌드박스는 멀쩡하다.
  • 앞 레벨들은 코드를 쓰지 않는다. 터미널 명령과 설정만으로 푼다. 레벨 7부터 Python이나 JavaScript 코드를 고친다.
  • 발표자는 "어려운 문제는 규모에서 생긴다"고 했다. 그래서 수천 개 샌드박스가 있는 상황을 시뮬레이션으로 흉내 냈다. 07:00
AI에게 풀게 해도 된다 07:40 발표자는 대부분의 코딩 에이전트가 E2B SDK를 알고 있으니, 레벨의 샌드박스 ID와 API 키를 Claude Code나 Codex에 넘겨서 풀게 해도 된다고 했다. 단, 배우는 게 목적이면 손으로 푸는 편이 낫고, 어느 쪽이든 AI가 한 일은 꼭 검토하라고 덧붙였다.
02

샌드박스가 필요한 이유 02:50

샌드박스는 사용자마다 따로 떼어 준 실행 환경이다. 한 사용자의 코드가 다른 사용자를 건드리지 못한다. 예전에는 Colab(추정) 같은 노트북이나 EC2 서버가 그 역할을 했다. 지금은 코드를 쓰는 주체가 사람이 아니라 에이전트다.

내 컴퓨터에서 에이전트를 돌리면 03:30
  • CPU를 전부 써 버린다
  • 프로세스를 잔뜩 띄운다
  • 지우면 안 되는 파일을 지운다
  • 환경 변수에 든 비밀 키를 읽는다
회사 서버에서 돌려도 03:50
  • 서버에도 비밀 키가 있다
  • 에이전트가 써야 할 도구는 전부 갖춰야 한다
  • 결국 문제가 같다

샌드박스는 이 두 문제를 한 번에 푼다. 에이전트에게 망가뜨려도 되는 전용 공간을 주고, 거기에 필요한 도구만 넣는다. 발표자는 E2B가 샌드박스 하나를 100밀리초 안에 띄우는 것을 목표로 한다고 했다. 여러 개를 동시에 돌리려면 그만큼 빨라야 한다는 이유다.

100밀리초는 E2B 자사 제품의 목표치다. 발표자가 소속된 회사의 주장으로 읽자.

03

이미 켜진 상태에서 시작한다 04:10

노트북을 덮었다가 다시 열면 하던 작업이 그대로 있다. E2B 샌드박스도 같은 방식을 노린다. 메모리와 파일 시스템을 통째로 스냅샷으로 저장하고, 다시 필요할 때 그 상태로 되살린다.

에이전트에게 이 점이 특히 중요하다. 에이전트는 다른 일을 하고 돌아왔을 때 시간이 흘렀다는 것을 모른다. 떠날 때와 똑같은 상태를 기대한다. 상태가 그대로면 오류가 줄어든다.

템플릿: 스냅샷 하나로 200개 복사 16:50

템플릿 template은 이렇게 저장한 가상 머신 스냅샷이다. 발표자는 깃발 뺏기용 프로세스를 다 띄운 뒤 그 상태를 템플릿으로 저장했다. 참가자 약 200명이 그 템플릿에서 각자 샌드박스를 띄웠다. 모두 발표자가 멈춘 지점에서 이어서 시작한 셈이다.

  • 작업 이어받기: 내가 하던 작업을 다른 사람이 그대로 이어서 한다.
  • 실험 분기: 데이터프레임을 다섯 가지로 바꿔 보고 싶으면, 샌드박스를 다섯 개로 갈라 동시에 돌린다.
  • 기본 의존성 캐시 37:40: GitHub Actions 캐시처럼 기본 패키지를 깔아 둔 템플릿을 만들고, 그 위에 작업을 쌓는다. git worktree마다 하나씩 띄우는 식이다.

그 외 사실 몇 가지다. E2B는 오픈소스다. 백엔드는 Go로 짰다. SDK는 Python과 JavaScript가 있다. 샌드박스 주소는 {포트}-{샌드박스 ID} 꼴로 만들어서, 샌드박스 안에서 띄운 서비스를 포트별로 바깥에 노출한다. 15:30

04

레벨 1~4: 자원이 터질 때 16:00

에이전트는 예상 밖의 일을 자주 한다. 발표자는 이 워크숍을 만드는 동안에도 CPU를 다 먹는 프로세스를 여러 번 만났다고 했다. 앞 네 레벨은 그런 상황에서 범인을 찾는 리눅스 기본기다.

레벨상황푸는 법
1 · 내 위치 09:40지금 들어와 있는 샌드박스 ID를 찾는다브라우저 주소창에 ID가 그대로 있다. 샌드박스로 돌아가려면 이 ID가 필요하다
2 · CPU 폭주 18:40한 프로세스가 CPU의 99.7%를 쓴다프로세스 목록에서 CPU 사용량이 큰 것을 찾아 프로세스 ID로 죽인다
3 · 메모리 폭주 20:20한 프로세스가 메모리를 다 먹는다같은 방법. 메모리 사용량으로 정렬해 찾고 죽인다
4 · 디스크 가득 22:00512MB짜리 파일 하나가 디스크를 채운다du로 큰 파일을 찾고 경로를 확인한 뒤 지운다
자원에는 저울질이 따른다 20:40 CPU를 많이 주면 빠르고, 적게 주면 느리다. 하지만 샌드박스를 여러 개 띄우는 운영 환경에서는 CPU와 RAM에 전체 한도가 있다. 하나에 많이 주면 띄울 수 있는 개수가 줄어든다. 그래서 샌드박스 하나의 메모리 사용량을 줄이는 일이 곧 비용 문제가 된다.

발표자는 레벨 4에서 파일을 지워 버리는 바람에 데모가 꼬였다. 그런데 바로 그 상황이 샌드박스의 장점을 보여 줬다. 다시 시작 버튼 하나로 템플릿 상태로 되돌아간다. 망가뜨려도 새로 띄우면 된다. 27:40

브라우저 터미널은 시연과 디버깅용이다. 실제 서비스에서는 웹 서버가 SDK로 샌드박스에 접속해 코드를 돌린다. 28:50

05

레벨 5: 얼마나 오래 살려 둘까 31:10

보통 서버는 내가 끌 때까지 켜져 있다. 샌드박스는 다르다. 사용자가 수천 명이고 각자에게 샌드박스를 주면, 얼마나 오래 살려 둘지가 곧 비용이다.

  • "접속하면 20분 주자"고 하면, 한 번 눌러 보고 떠나는 사용자 수천 명 때문에 자원을 낭비한다.
  • 반대로 데이터 분석이나 웹 스크래핑처럼 얼마나 걸릴지 모르는 작업은 도중에 끊기면 안 된다.
  • 발표자의 표현을 빌리면, 샌드박스를 붙들고 있는 시간과 "돈을 태양에 쏟아붓는 것" 사이의 저울질이다.

해법: 작업 중에는 길게, 끝나면 짧게 33:00

  1. 명령을 시작할 때 수명을 1시간으로 길게 준다. 작업이 얼마나 걸리든 끝까지 돌게 한다.
  2. 작업이 끝나면 수명을 1분으로 줄인다. 사용자가 바로 다음 명령을 보내면 그대로 쓰고, 안 보내면 스스로 꺼진다.
  3. 꺼진 자원은 다른 사용자의 샌드박스로 돌아간다.
돌고 있으면 빠르고, 멈춰 있으면 싸다 36:30 샌드박스가 돌고 있으면 응답이 빠르다. 멈춰 있으면 비용이 거의 없어서 아주 많이 둘 수 있다. Claude Code 같은 에이전트는 샌드박스 20개를 쓰다가 언제 돌아올지 모른다. 그래서 수명 설정이 곧 속도와 비용의 저울이 된다. 반대로 하루 종일 떠 있어야 하는 데몬이나 CDN 같은 정적 서비스에는 샌드박스가 가장 싼 선택이 아니라고 발표자는 말했다.
06

레벨 6: 고아 프로세스 치우기 39:00

같은 샌드박스를 멈췄다 되살리며 오래 쓰면 고아 프로세스 orphan process가 쌓인다. 어떤 작업이 띄운 자식 프로세스가 부모 작업이 끝난 뒤에도 남아 있는 것이다. 발표자는 샌드박스에서 이 문제를 유독 자주 본다고 했다.

이유는 앞 섹션의 장점과 같은 곳에 있다. 매번 새 이미지에서 시작하는 대신 지난 상태를 그대로 되살리기 때문이다. 빠르고 작업이 제자리에 있다는 장점이, 정리를 안 하면 쓰레기도 제자리에 있다는 단점이 된다.

샌드박스 관리의 상당 부분은 결국 고아 프로세스를 죽이는 일이다.발표자의 말을 옮김 40:00
  • 실습에서는 고아가 3개 있고 이름이 모두 orphan_worker라 찾기 쉽다. 하나씩 죽이면 웹 페이지가 알아채고 다음 코드를 준다.
  • 발표자는 실제 환경에서는 이름이 이렇게 친절하지 않다고 경고했다. 같은 작업에서 나온 고아는 보통 이름이 같으니 그걸로 묶어 찾는다.
  • 같은 맥락의 문제가 하나 더 있다. 샌드박스 자체를 잃어버리는 것이다. 어떤 샌드박스를 띄웠는지 추적하지 않으면, 관리 밖으로 벗어난 샌드박스를 찾아 자원을 회수해야 한다. 40:10

레벨 7을 푸는 도중 발표자의 샌드박스에도 고아가 여러 개 쌓여 테스트 결과 반영이 늦어졌다. 발표자가 이를 두고 "방금 배운 그 고아들"이라고 웃어넘겼다. 48:00

07

레벨 7: 사용자와 샌드박스 짝짓기 42:30

샌드박스를 처음 도입하면 흔히 "서버가 이만큼 있으니 오는 순서대로 나눠 주자"고 한다. 돌아가며 배정하는 round-robin 방식이다. 문제는 같은 사용자가 다시 왔을 때 지난번 샌드박스로 돌아갈 수 없다는 것이다.

이 레벨이 첫 코드 실습이다. 라우터 파일(router.py 또는 router.js)의 배정 함수를 고쳐서 사용자 → 샌드박스 ID 표를 만든다. 발표자는 실제 서비스라면 이 표를 데이터베이스에 영구 저장하라고 했다. 나중에 "샌드박스를 너무 자주 새로 배정하지 않았나" 같은 이력 분석을 할 수 있기 때문이다.

# 예시: 발표 내용을 바탕으로 다시 쓴 코드. 발표 화면의 코드 그대로는 아니다.
assignments = {}  # user_id -> sandbox_id

질문발표자의 답
로컬 코드를 여러 곳의 작은 GPU에 뿌려 돌리고 결과를 모으고 싶다 51:40E2B는 GPU를 지원하지 않는다. 흔한 방식은 샌드박스가 결과를 POST 요청으로 집에 보내는 것이다. E2B는 컨테이너가 아니라 가상 머신을 쓴다

핵심 정리

  1. 샌드박스는 에이전트가 망가뜨려도 되는 전용 공간이다. CPU 독점, 파일 삭제, 비밀 키 유출을 격리로 막는다.
  2. E2B는 메모리와 파일 시스템을 스냅샷으로 저장하고 그대로 되살린다. Docker처럼 매번 시작 명령을 돌리지 않는다.
  3. 템플릿은 그 스냅샷이다. 하나로 200개를 복사하거나, 실험 다섯 개로 가르거나, 기본 의존성 캐시로 쓴다.
  4. 한두 개는 쉽다. 규모가 커지면 자원 한도, 수명, 추적, 로그가 따로 문제가 된다.
  5. 자원 폭주는 리눅스 기본기로 잡는다. 프로세스 목록에서 CPU와 메모리 범인을 찾아 죽이고, du로 디스크 범인을 찾아 지운다.
  6. 수명은 작업 중 길게, 끝나면 짧게. 돌고 있으면 빠르고 멈춰 있으면 싸다.
  7. 지난 상태를 되살리는 방식은 고아 프로세스를 쌓는다. 샌드박스 관리의 상당 부분이 고아 치우기다.
  8. 돌아가며 배정하지 말고 사용자 → 샌드박스 ID 표를 만든다. 실제 서비스에서는 데이터베이스에 남긴다.
  9. 에이전트가 쓸 수 있는 구역을 좁힌다. 템플릿 캐시는 읽기 전용, 실행 캐시만 쓰기.
  10. 비밀 키가 있는 샌드박스는 나가는 통신을 막는다. E2B는 GPU를 지원하지 않고, Firecracker와 Nomad 위에서 돈다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1에이전트를 내 컴퓨터에서 그냥 돌리면 생기는 문제 네 가지는?
CPU를 다 쓴다, 프로세스를 잔뜩 띄운다, 지우면 안 되는 파일을 지운다, 환경 변수의 비밀 키를 읽는다.
Q2E2B 샌드박스가 Docker 컨테이너와 다른 시작 방식은?
Docker는 이미지를 쌓은 뒤 시작 명령으로 프로세스를 새로 띄운다. E2B는 프로세스를 먼저 띄운 상태를 스냅샷으로 저장하고, 되살릴 때 그 프로세스가 이미 돌고 있다.
Q3템플릿이란 무엇이고, 워크숍에서 어떻게 쓰였나?
메모리와 파일 시스템을 저장한 가상 머신 스냅샷이다. 발표자가 실습 환경을 띄운 상태를 템플릿으로 저장했고, 참가자 약 200명이 각자 그 템플릿에서 샌드박스를 띄웠다.
Q4샌드박스 하나에 CPU와 RAM을 많이 주면 왜 문제가 되나?
운영 환경에는 CPU와 RAM 전체 한도가 있다. 하나에 많이 주면 동시에 띄울 수 있는 샌드박스 수가 줄어든다. 그래서 샌드박스당 메모리를 줄이는 일이 비용 문제다.
Q5레벨 5의 수명 설정 전략을 두 단계로 말하면?
명령을 시작할 때 수명을 1시간으로 길게 줘서 작업이 끊기지 않게 한다. 작업이 끝나면 1분으로 줄여서, 사용자가 바로 안 돌아오면 스스로 꺼지게 한다.
Q6"돌고 있으면 빠르고 멈춰 있으면 싸다"는 무슨 저울질인가?
속도와 비용의 저울질이다. 돌고 있는 샌드박스는 바로 응답하지만 자원을 쓴다. 멈춘 샌드박스는 거의 공짜라 많이 둘 수 있지만 되살리는 시간이 든다.
Q7샌드박스에서 고아 프로세스가 유독 많이 쌓이는 이유는?
매번 새 이미지에서 시작하지 않고 지난 상태를 그대로 되살리기 때문이다. 정리하지 않은 프로세스가 되살릴 때마다 함께 돌아온다.
Q8돌아가며 배정하는 방식의 문제와 해법은?
같은 사용자가 다시 왔을 때 지난 샌드박스로 돌아갈 수 없다. 사용자 ID를 키로, 샌드박스 ID를 값으로 하는 표를 만들어 있으면 돌려주고 없으면 새로 만들어 표에 넣는다.
Q9레벨 8의 두 캐시와 각각의 권한은?
템플릿 캐시는 읽기 전용, 실행 캐시는 쓰기 가능. 프로세스가 템플릿 캐시에 쓰려다 죽는 오류를 캐시 경로를 바꿔서 고친다.
Q10샌드박스에 비밀 키를 넣어야 할 때 발표자가 권한 보호 방법은?
샌드박스별 네트워크 규칙으로 나가는 통신을 막는다. 개발용 키만 있으면 느슨하게 둬도 된다. 편의와 보안 사이의 선택이다.
Q11E2B가 지원하지 않는다고 밝힌 것과, 기반 기술 두 가지는?
GPU는 지원하지 않는다. 가상 머신은 Firecracker로 띄우고, 운영은 Nomad로 한다. Kubernetes는 작업 중이다.

가짜 객체Mock. 테스트에서 실제 자원 대신 쓰는 흉내 객체. 샌드박스를 진짜로 띄우지 않고 로직을 검사한다
볼륨Volume. 여러 샌드박스가 함께 붙여 쓰는 공유 저장 공간
나가는 통신Egress. 샌드박스 안에서 바깥으로 보내는 네트워크 요청. 비밀 키 유출 경로가 된다
git worktree한 저장소의 여러 브랜치를 각각 다른 디렉터리에 동시에 꺼내 두는 git 기능
