누가 소프트웨어 공장을 검증하나

코드를 쓰는 일은 이미 빨라졌다. 이제 병목은 그 코드를 믿을 근거를 만드는 검증이다. Anthropic은 에이전트가 먼저 리뷰하고 증거를 내놓게 하고, 사람은 그 증거를 확인하는 방식으로 하루 약 3만 건을 머지한다고 한다.

원본 영상: How Anthropic Merges 30,000 Code Changes a Day 진행: Manish Kapur (Sonar 제품·솔루션 개발자 관계 팀 리드) 대담: Addy Osmani (Anthropic, Claude Code 개발자 경험 담당, 전 Google 14년)

영어 대담의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳(Cloud Code → Claude Code 등)은 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 코드 작성은 거의 풀린 문제가 됐다. 이제 모자란 것은 그 코드를 믿을 근거, 곧 검증이다.
  2. 소프트웨어 공장은 루프를 대규모로 돌리는 것이다. 사람이 단계마다 판단하는 불 켜진 공장과, 사람이 예외 때만 불려 오는 불 꺼진 공장 사이에 대부분 팀이 있다.
  3. Anthropic의 하루 머지 수는 5월 약 2,500건에서 약 30,000건으로 늘었다고 한다.
  4. 방식은 이렇다. Claude가 먼저 리뷰하며 실제 사용자처럼 써 본다. 팀의 취향은 CLAUDE.md·AGENTS.md에 글로 남긴다. 사람은 에이전트가 낸 증거를 확인한다.
  5. "검증하라"만으로는 부족하다. E2E 테스트, 속성 테스트, 시각 검증처럼 테스트 종류까지 정해야 한다.
  6. Sonar는 여러 겹 검증을 권한다. 결정적 분석, 에이전트 리뷰, 공급망 보안이 각자 다른 문제를 잡는다.
  7. 에이전트가 많아지면 통제·권한·샌드박스가 핵심 걱정이 된다. 에이전트가 쓴 코드도 책임은 사람에게 남는다.
  8. 결론: 빨리 쓰는 것과 빨리 내보내는 것은 다르다. 자율은 루프마다 넣은 검증으로 얻는다.
01

빨라진 코드, 모자란 확신 00:20

Manish는 청중에게 두 가지를 묻는다. 지난 일주일 사이 코딩 에이전트가 PR을 연 사람은 거의 전부가 손을 들었다. 그중 머지한 코드를 한 줄도 빠짐없이 리뷰한 사람은 몇 명뿐이었다.

이 발표는 그 두 무리 사이의 간격을 다룬다. 리뷰 없이 머지하는 쪽과, 리뷰하고 머지하는 쪽이다.

숫자내용출처 (발표자 언급)
2,800만올해 분석한 CI 워크플로 수CircleCI
+59%처리량 throughput 증가CircleCI
10번 중 3번프로덕션으로 머지하려는 시도가 실패하는 비율CircleCI
85%이미 코딩 에이전트를 쓰는 조직. 곧 95%, 이어서 100%가 된다고 전망발표 슬라이드
76%AI로 코드를 만드는 개발자 중 "검증할 수 없는 속도로 코드가 나온다"고 답한 비율발표 슬라이드

더 많이 만들지만 더 많이 막힌다. 개발자는 리뷰에 점점 더 많은 시간을 쓴다. Manish는 Sonar가 써 온 문구를 꺼낸다. 코드에 대한 확신은 귀하다는 것이다.

리더가 지금 묻는 것 04:20

Addy가 보기에 지난 1년 동안 팀도, 모델도, 하네스 harness도 좋아졌다. 하네스는 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀이다. 그래서 리더들의 질문은 하나로 모인다. 어떻게 하면 확신을 갖고 더 빨리 내보낼 수 있나.

  • 좋은 코드를 좋다고 부를 수 있게 해 준 것은 늘 같았다. 좋은 테스트, 벤치마크, 명세다.
  • 이제 에이전트가 이런 검사 수단을 예전보다 훨씬 싸고 빠르게 만들어 준다.
  • 그러니 지금 시간을 쓸 곳은 바로 이 검사 수단이다.
Addy의 핵심 주장 05:10 에이전트에게 작업이 맞는지 스스로 검증할 방법을 줘라. 코드가 맞고 빠진 데가 없다는 것까지 확인할 수 있으면, 결과 품질이 쉽게 2~3배 좋아진다.
02

불 켜진 공장과 꺼진 공장 02:20

Manish는 Addy가 쓴 글의 한 문장을 슬라이드에 띄운다.

소프트웨어 공장은 루프를 대규모로 부리는 것이다.Addy Osmani의 글, Manish가 슬라이드로 인용 (원문: "A software factory is harnessing loops at scale.")

소프트웨어 공장 software factory은 계획하고, 만들고, 검사하고, 내보내는 루프를 끝없이 반복해 돌리는 개발 방식이다. Addy는 공장을 두 종류로 나눈다.

불 켜진 공장 · lights-on사람이 안에서 판단한다에이전트가 계획, 작성, 검사, 출시를 반복해 돕는다. 사람은 그 과정 안에서 판단과 취향을 넣는다.
→
불 꺼진 공장 · dark사람은 의도만 정한다로봇이 도는 자동차 공장처럼 범위 정하기, 작성, 검사를 계속한다. 사람은 아주 큰 예외가 있을 때만 불려 온다.

대부분 팀은 이 두 끝 사이 어딘가에 있다. 그리고 믿을 수 있는 방식으로 자동화를 한 칸씩 늘리는 방법을 찾는 중이다.

03

Anthropic의 하루 3만 건 05:40

Manish는 대담 전날 밤 읽은 Anthropic의 글을 소개한다. Anthropic은 하루에 코드 변경을 약 3만 건 머지한다고 한다. 몇 달 전에는 약 2,500건이었다.

Addy는 다른 사례도 든다. 최근 Claude.ai를 새로 손볼 때 성능을 약 3배로 올렸다. 아주 짧은 기간에 PR 약 3,000개를 머지해서 해낸 일이다. 엔지니어뿐 아니라 제품 디자이너 등 여러 직군이 함께 기여했다.

Manish는 처음에 예전 수치를 "3,000 정도"라고 했다가 "2,500 정도"로 고쳐 말했다. 3,000은 Addy가 Claude.ai 개편 때 머지했다고 한 PR 수이고, 하루 머지 수와는 다른 숫자다.

3만 건은 Anthropic이 스스로 밝힌 숫자이고, Addy도 Anthropic 소속이다. 이 노트는 원 글을 확인하지 않았다.

04

Anthropic의 리뷰 흐름 06:30

그 규모에서 코드 리뷰는 어떻게 돌아가나. Addy가 설명한 Claude Code 팀의 흐름은 다섯 단계로 정리된다.

단계하는 일
1차 리뷰Claude가 먼저 리뷰한다. 핵심은 실제 사용자처럼 직접 써 볼 수단이다. 처음부터 끝까지 이어지는 작업 돌리기, 브라우저에서 열어 보기, 도구 실행, 린트 등 확신을 쌓는 데 필요한 검사를 한다.
수정 루프 07:00버그나 기능의 빈틈이 나오면 훅 hook이 돈다. 수정이 있을 때마다 diff를 살펴 PR을 최대한 빨리 바로잡는 루프다.
자동 리뷰 도구Claude Code가 리뷰하고, Anthropic의 코드 리뷰 제품도 쓴다. 목표는 코드 리뷰를 할 수 있는 만큼 자동화하는 것이다.
기준 글로 쓰기 07:30팀이 생각하는 모범 사례와 취향을 CLAUDE.md, AGENTS.md 같은 공유 파일에 쓴다. 에이전트는 리뷰 중에 이 파일을 참고한다.
사람의 확인 07:50사람은 에이전트가 내놓은 증거를 확인한다.
어떤 증거를 받나 브라우저에서 쓰는 UI라면, 에이전트가 브라우저에서 직접 테스트하고 이리저리 클릭해 본 영상을 받는다. 모바일이나 데스크톱 화면이라면 스크린샷이나 영상을 받는다. 목표는 에이전트가 검증 증거를 최대한 많이 내놓게 만드는 것이다.

요즘 많이 말하는 "취향과 판단"도 머릿속에 두지 말고 글로 굳혀야 한다. 그래야 에이전트가 리뷰 기준으로 쓸 수 있다.

Addy는 Anthropic 소속이고, 이 대목에는 Anthropic 코드 리뷰 제품을 권하는 말("꽤 좋다")이 들어 있다. 그 점을 감안해 읽자.

05

리뷰 없이 나가는 코드 08:20

Manish는 곧 나올 Sonar의 "State of Code" 설문 보고서 숫자를 소개한다. 개발자 1,000명 넘게 답했다.

  • 84%는 AI 덕분에 기능과 수정이 더 빨리 프로덕션에 간다고 답했다.
  • PR은 점점 더 커지고 복잡해진다.
  • 그런데 리뷰 없이 프로덕션에 가는 코드가 31% 늘었다.

31% 대목은 자막이 뭉개져 있다. "31% 더 많이"로 들리지만, "31%가 리뷰 없이 간다"는 뜻일 수도 있다.

Manish는 이것이 무서운 사실이라고 말한다. 특히 규제 산업이나 멈추면 안 되는 시스템에서는 내보내는 코드를 반드시 검증하고 확신할 수 있어야 한다.

Sonar 설문은 Manish의 회사가 낸 자료이고, 발표 시점에는 아직 공개 전이었다.

06

"검증하라"를 구체적으로 09:20

다음 성장은 어디서 오나. Addy는 두 가지를 든다. 검증을 제대로 하는 것, 그리고 모델 품질이다.

모델 품질은 이미 꽤 좋은 수준에 왔다고 본다. 예로 Opus 5.5를 든다(자막에는 "Opus 55"로 들림). 그래서 남은 큰 몫은 검증 단계의 모범 사례를 서로 나누는 일이다.

"그냥 검증하세요"의 문제 사람들에게 검증하라고만 하면, 다음 질문은 "그게 대체 무슨 뜻인데요?"다. 그래서 대화는 어떤 종류의 테스트가 쓸모 있는지로 넘어가야 한다.

Anthropic이 많이 기대는 테스트는 세 가지다. 이 테스트들이 변경을 자동으로 머지해도 된다는 확신을 준다.

  • E2E 테스트 end-to-end test: 사용자처럼 처음부터 끝까지 실제 흐름을 돌려 본다.
  • 속성 테스트 property test: 입력을 많이 자동으로 만들어, 항상 지켜져야 할 규칙이 깨지지 않는지 본다.
  • 시각 검증 visual verification: 화면 결과를 스크린샷이나 영상으로 확인한다.

세 테스트의 풀이는 이 노트가 붙인 것이다. 발표에서는 이름만 나온다.

07

공장 도입은 이제 시작 10:00

Sonar 설문에서 소프트웨어 공장을 쓰는 회사는 아직 소수다.

Manish는 금융 서비스 쪽 전망이 더 높은 점을 의외라고 말한다. 청중 중에서도 지금 쓰고 있다는 사람은 몇 명뿐이었다.

검증이 불을 끄게 해 준다 10:30

Addy는 공장의 정의를 다시 짚는다. 핵심은 사람이 과정에 얼마나 끼어 있느냐다. 에이전트가 검증을 더 많이 만들어 확신을 줄수록, 불을 끌 수 있다. 대부분은 아직 그 지점에 오지 않았다.

Manish는 조립 라인에 빗댄다. 11:00 의도와 명세를 정하고, 코드를 쓰는 식으로 개발의 각 단계가 라인을 따라 이어진다. 불 켜진 공장은 사람이 모든 단계 또는 대부분 단계에 끼어 있다. 불 꺼진 공장의 목표는 불을 끄고 24시간 내내 혼자 돌게 하는 것이다.

08

여러 겹 검증 11:40

Sonar는 이날 CEO 키노트에서 검증을 여러 겹으로 해야 한다고 말했다. Manish는 그 생각을 두 원칙으로 정리한다.

  • 제로 트러스트 zero trust: 어떤 결과도 기본으로 믿지 않고 매번 확인한다.
  • 모든 루프에서 검증: 에이전트가 일하는 루프 안에서도, CI 검증 루프에서도, 코드 유지보수 중에도 에이전트가 만든 결과를 검증한다.
층잡는 문제
1. 결정적 분석 12:10같은 입력에는 늘 같은 결과를 내는 규칙 기반 검사다. 버그와 보안 문제를 잡는다. 예: SQL 인젝션, 버퍼 오버플로
2. 에이전트 리뷰 12:30에이전트가 코드를 리뷰한다. 결정적 분석이 잘 못 잡는 로직과 의도의 문제를 잡는다.
3. 공급망 보안 12:50가져다 쓰는 외부 코드를 본다. 알려진 취약점(CVE), 악성코드, 악성 패키지를 잡는다.

각 층은 특정한 종류의 문제를 잡도록 맞춰져 있다. 한 층이 다른 층을 대신하지 않는다.

Manish는 Sonar 소속이고, 여러 겹 검증은 Sonar가 키노트에서 내세운 관점이다. 그 점을 감안해 읽자.

09

에이전트를 통제하는 법 13:10

슬라이드의 숫자는 두 개다. 승인된 에이전트와 공동 통제 장치를 갖춘 회사가 28%다. 소프트웨어 공장을 자율로 운영하는 회사는 5%다.

28% 문장은 자막이 뭉개져 정확한 뜻이 분명하지 않다.

Addy가 몇 달 전 만난 많은 회사의 걱정은 이랬다. 엔지니어들이 에이전트를 자유롭게 써 보게 했더니 에이전트가 수백, 많게는 수천 개로 늘었다. 그런데 그 에이전트들이 뭘 하는지 아무도 몰랐다. 모든 시스템을 건드리고, 온갖 데이터에 접근하고, 어쩌면 프로덕션에 배포까지 하고 있었다.

그래서 기업은 에이전트 신원과 텔레메트리 telemetry를 고민한다. 텔레메트리는 실제로 무슨 일이 일어나는지 자동으로 모은 활동 기록이다.

Addy가 꼽은 세 가지묻는 것

마무리: 세 가지 교훈 17:40

Manish의 마지막 슬라이드는 "빠르게 내보내지만 눈감고 내보내지 않는 팀"을 가르는 것이 무엇인지 정리한다.

빨리 쓴다고 빨리 내보내는 게 아니다.Manish Kapur, 마지막 슬라이드 (원문: "Fast to write is not fast to ship.")
  1. 빨리 쓰는 것 ≠ 빨리 내보내는 것. 코드 작성은 가장 빠른 단계이고 이미 풀렸다. 그 속도를 유지하게 해 주는 것은 강한 리뷰와 검증이다.
  2. 모든 것을 검증한다. 무엇이 머지되는지 세고 살핀다. 프로덕션에 가기 전에 샌드박스를 벗어나는 일이 없는지 확인한다.
  3. 자율은 얻어 내는 것이다. 소프트웨어 공장은 곧 온다. 공장의 루프마다 독립적인 자동 검증을 넣어, 공장이 내놓는 결과를 믿을 수 있게 만든다.
12

핵심 정리

  1. 코드 작성은 빨라졌다. 병목은 그 코드를 믿을 근거, 곧 검증이다.
  2. CircleCI 자료에서 처리량은 59% 늘었지만, 프로덕션 머지 시도 10번 중 3번이 실패한다.
  3. 소프트웨어 공장은 루프를 대규모로 돌리는 것이다. 불 켜진 공장과 불 꺼진 공장 사이의 스펙트럼이다.
  4. 에이전트에게 스스로 검증할 수단을 주면 결과 품질이 2~3배 좋아질 수 있다고 Addy는 말한다.
  5. Anthropic의 하루 머지 수는 약 2,500건에서 약 30,000건으로 늘었다.
  6. Anthropic의 흐름: Claude가 직접 써 보며 1차 리뷰하고, 훅이 수정마다 다시 보고, 사람은 증거를 확인한다.
  7. 팀의 취향과 모범 사례는 CLAUDE.md, AGENTS.md에 글로 남겨 에이전트의 리뷰 기준으로 쓴다.
  8. "검증하라"는 E2E, 속성 테스트, 시각 검증처럼 구체적인 테스트 종류로 바꿔 말해야 한다.
  9. 검증은 여러 겹으로, 모든 루프에서 한다. 결정적 분석, 에이전트 리뷰, 공급망 보안이 각자 다른 문제를 잡는다.
  10. 에이전트가 늘면 통제·권한·샌드박스가 핵심이다. 자율은 검증으로 얻고, 책임은 사람에게 남는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1CircleCI 자료에서 서로 대비되는 두 숫자는?
처리량은 약 59% 늘었다. 그런데 프로덕션으로 머지하려는 시도는 10번 중 3번 실패한다. 더 많이 만들지만 더 많이 막힌다.
Q2불 켜진 공장과 불 꺼진 공장은 무엇이 다른가?
불 켜진 공장은 에이전트가 일을 돕고 사람이 과정 안에서 판단과 취향을 넣는다. 불 꺼진 공장은 계속 혼자 돌고, 사람은 의도만 정하다가 큰 예외 때 불려 온다.
Q3Addy가 결과 품질이 2~3배 좋아질 수 있다고 한 조건은?
에이전트에게 작업이 맞는지 스스로 검증할 방법을 주는 것. 코드가 맞고 빠진 데가 없다는 것까지 확인할 수 있어야 한다.
Q4Anthropic의 하루 머지 수는 5월과 발표 시점에 각각 얼마이고, 몇 배인가?
약 2,500건에서 약 30,000건이다. 12배다.
Q5Claude의 1차 리뷰에서 가장 중요하다고 한 것은?
실제 사용자처럼 직접 써 볼 수단. 처음부터 끝까지 이어지는 작업, 브라우저에서 열어 보기, 도구와 린트 실행 같은 검사다.
Q6팀의 취향과 모범 사례를 CLAUDE.md, AGENTS.md에 쓰는 이유는?
에이전트가 리뷰 중에 그 파일을 참고하게 하려고. 머릿속의 취향은 에이전트가 쓸 수 없다.
Q7Anthropic의 흐름에서 사람은 무엇을 확인하나?
에이전트가 내놓은 검증 증거. 브라우저 UI라면 에이전트가 클릭하며 테스트한 영상, 모바일이나 데스크톱이라면 스크린샷이나 영상이다.
Q8"그냥 검증하라"가 부족한 이유와, Addy가 꼽은 테스트 세 종류는?
그 말을 들으면 "그게 무슨 뜻이냐"는 질문이 바로 나온다. 그래서 E2E 테스트, 속성 테스트, 시각 검증 테스트처럼 종류를 정해야 한다.
Q9Sonar가 말한 검증의 세 층과 각 층이 잡는 문제는?
결정적 분석은 버그와 보안 문제(SQL 인젝션, 버퍼 오버플로)를 잡는다. 에이전트 리뷰는 로직과 의도의 문제를 잡는다. 공급망 보안은 CVE, 악성코드, 악성 패키지를 잡는다.
Q10에이전트가 수천 개로 늘어난 기업이 가장 걱정하는 세 가지는?
통제, 권한, 샌드박스. 그 밖에 에이전트 신원과 텔레메트리도 고민한다.
Q11에이전트가 쓴 코드를 PR에 표시하자는 이유는?
어떤 제약과 추가 검사를 둘지 정하는 데 도움이 된다. 감사 가능성을 높인다. 무엇보다 책임질 사람을 분명히 한다. 에이전트를 돌린 사람이 문제가 생기면 고친다.
Q12마지막 슬라이드의 세 가지 교훈은?
빨리 쓰는 것과 빨리 내보내는 것은 다르다. 모든 것을 검증한다. 자율은 루프마다 넣은 독립적인 자동 검증으로 얻는다.

용어뜻
소프트웨어 공장Software factory. 계획, 작성, 검사, 출시 루프를 대규모로 반복해 돌리는 개발 방식
불 켜진 공장Lights-on factory. 에이전트가 일하지만 사람이 모든 단계나 대부분 단계에서 판단하는 공장
불 꺼진 공장Dark factory. 사람 없이 24시간 혼자 도는 공장. 사람은 의도를 정하고 큰 예외 때만 끼어든다
루프만들고, 확인하고, 고치기를 반복하는 한 바퀴
하네스Harness. 모델을 감싸 도구, 순서, 규칙, 검사를 정해 주는 실행 틀
처리량Throughput. 일정 시간에 처리한 작업의 양
CIContinuous Integration. 코드 변경마다 빌드와 테스트를 자동으로 돌리는 장치
PR / 머지Pull request는 바꾼 코드를 합쳐 달라는 요청이다. 머지는 그 변경을 본 코드에 합치는 것이다
diff바뀐 코드 부분만 모은 것
훅Hook. 파일 수정 같은 일이 생길 때 자동으로 실행되는 스크립트
린트Lint. 코드 스타일과 흔한 실수를 자동으로 찾는 검사
CLAUDE.md / AGENTS.md저장소 안에 두는 지침 파일. 에이전트가 작업할 때 읽는다
E2E 테스트End-to-end test. 사용자처럼 처음부터 끝까지 실제 흐름을 돌려 보는 테스트
속성 테스트Property test. 입력을 많이 자동으로 만들어, 항상 지켜져야 할 규칙이 깨지지 않는지 보는 테스트
시각 검증Visual verification. 화면 결과를 스크린샷이나 영상으로 확인하는 검증
제로 트러스트Zero trust. 어떤 결과도 기본으로 믿지 않고 매번 확인하는 원칙
결정적 분석Deterministic analysis. 같은 입력에 늘 같은 결과를 내는 규칙 기반 검사
SQL 인젝션입력에 SQL 문을 끼워 넣어 데이터베이스를 조작하는 공격
버퍼 오버플로정해진 메모리 칸을 넘어 쓰는 버그. 보안 구멍이 되기 쉽다
공급망 보안Supply chain security. 가져다 쓰는 외부 패키지와 의존성의 안전을 지키는 일
CVE공개된 보안 취약점마다 붙는 고유 번호
샌드박스Sandbox. 에이전트가 정해진 범위 밖으로 나가지 못하게 막은 실행 환경
텔레메트리Telemetry. 실제로 무슨 일이 일어나는지 자동으로 모은 활동 기록
가드레일 / 가이드레일가드레일은 벗어나지 못하게 막는 울타리다. 가이드레일은 정해진 길로 이끄는 레일이다
