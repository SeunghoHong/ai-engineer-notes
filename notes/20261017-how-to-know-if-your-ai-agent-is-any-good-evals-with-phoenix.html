내 AI 에이전트가 쓸 만한지 어떻게 아나

"몇 번 돌려 보니 괜찮더라"는 테스트가 아니다. 이 워크숍은 금융 분석 에이전트 하나를 놓고 트레이스를 모으고, 직접 읽고, 코드 평가와 LLM 판정을 쓰고, 그 판정자를 사람 기준으로 검증하고, 프롬프트 변경을 실험으로 증명한 뒤 CI에 넣는 과정을 끝까지 보여 준다.

원본 영상: How to Know If Your AI Agent Is Any Good: Evals With Phoenix & Claude 발표: Laurie Voss (Arize AI 개발자 관계 총괄, 전 npm)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 알려진 이름으로 바로잡았다. h:mm:ss는 영상 위치다.

발표자는 이 워크숍에서 쓰는 관측·평가 도구 Phoenix를 만드는 Arize AI 소속이다. 도구 선택과 관련된 대목은 그 점을 감안해 읽자. 발표자도 다른 프레임워크와 LLM 제공자를 써도 같은 방법이 통한다고 밝혔다.

3분 요약
  1. 트레이스는 로그, 평가는 트레이스 위에서 돌리는 테스트다. LLM 출력은 매번 달라서 문자열 비교 단위 테스트로는 안 된다.
  2. 평가는 세 종류다. 코드 평가는 빠르고 공짜지만 뜻을 모른다. LLM 판정은 뜻을 이해하지만 틀릴 수 있다. 사람 평가는 기준이지만 느리고 지친다. 셋을 겹쳐 쓴다.
  3. 평가를 쓰기 전에 트레이스를 열 몇 개 직접 읽는다. 그래야 무엇이 실제로 망가지는지 알고, 그걸 기준으로 삼을 수 있다.
  4. 맞는 평가를 고르는 것이 평가를 조정하는 것보다 중요하다. "정확성" 판정은 전부 0점을 줬고 아무것도 알려 주지 않았다. "충실성" 판정은 꾸며낸 숫자를 짚어 냈다.
  5. 직접 쓰는 판정 프롬프트는 다섯 부분이다. 역할과 맥락, 구체적 기준, XML 태그로 구분한 데이터, 예시, 답 형식 제한. 판정 프롬프트는 코드처럼 버전 관리하고 테스트한다.
  6. 판정자는 분류기다. 사람이 붙인 정답 데이터와 비교해 정밀도와 재현율을 재고, 조정용과 검증용 데이터를 나눈다. 기준 문장 하나를 보탰더니 사람과의 일치가 오히려 떨어졌다.
  7. 프롬프트를 바꾼 뒤 같은 입력과 같은 평가로 실험한다. 실행 가능성은 5/16에서 48/48로 올랐지만 충실성은 그대로였다. 측정한 것만 고쳐졌다.
  8. 안정적으로 통과하는 평가는 회귀 평가가 되어 CI에 들어간다. 종목 언급은 차단선, 실행 가능성 평균 0.8은 목표선이다.
01

"괜찮아 보인다"는 테스트가 아니다 02:40

발표자가 전제하는 상황은 이렇다. LLM이 들어간 앱을 만들었고, 몇 번 써 보니 괜찮았고, 배포했다. 그런데 누군가 예상 밖의 방식으로 써서 망가졌다. 또는 프롬프트를 고쳐 한 가지를 잡았는데 다른 무언가를 깨뜨린 것 같은 찜찜함이 남았다. 그리고 확인할 방법이 없다.

평가eval는 바로 이 문제를 푼다. 내 에이전트가 쓸 만한가. 이번 변경이 나아진 건가 나빠진 건가. 매번 출력을 전부 읽지 않고도 어떻게 퇴보를 막나.

이 워크숍이 약속한 결과물 끝까지 따라가면 손에 남는 것은 이렇다. 처음부터 끝까지 트레이스가 남는 에이전트, 코드 평가와 LLM 판정 평가와 직접 쓴 평가, 그 판정자를 믿어도 되는지 확인한 결과, 변경이 효과가 있었음을 증명한 실험, 그리고 이 모든 것이 npm test로 돌아가는 테스트 묶음.

왜 지금 더 중요한가 07:40

몇 주에 한 번씩 새 모델이 나온다. 평가 묶음이 없으면 새 모델이 무엇을 더 잘하고 무엇을 더 못하는지 알 길이 없다. 이 워크숍도 그래서 Claude Haiku 4.5로 시작해 나온 지 일주일 된 Haiku 5.5로 올리는 것을 마지막 실험으로 삼는다.

실습 환경: Node 22 이상, TypeScript, Phoenix는 uvx로 설치해 localhost:6006에서 열고, Anthropic 키가 필요하다. 저장소에는 단계별 체크포인트와 발표자가 미리 돌린 시드 데이터가 들어 있어 중간에 막혀도 다음 단계로 건너뛸 수 있다.

사람 판단은 왜 안 되나 06:50

사람이 출력을 보고 "괜찮네" 하는 방식은 규모가 커지면 무너진다. 퇴보를 못 잡고, 사람이 없는 CI에서는 돌지 않는다. 실제 모습은 이렇다. 말투를 고치려고 시스템 프롬프트를 바꿨더니 말투는 좋아졌는데 없는 제품 기능을 지어내기 시작했고, 고객이 먼저 발견한다. 프롬프트 변경 하나가 모든 종류의 입력에 영향을 주는데 그걸 손으로 다 볼 수는 없다. 그래서 두더지 잡기가 된다. 평가는 추적하고 비교하고 행동할 수 있는 숫자를 준다.

코드 평가 code eval

  • 조금 깨지기 쉽다
  • 문자열 비교로는 못 보는 정답이 많다

언제: 답이 결정적일 때. 형식, 길이, 필수 항목, 금지 문구

LLM 판정 LLM-as-judge

두 번째 LLM이 첫 번째 LLM의 출력을 루브릭rubric, 즉 규칙에 따라 채점한다. 발표자는 루브릭이 그냥 "규칙"인데 왜 따로 말이 있냐고 투덜댄다.

  • 문자열이 아니라 뜻을 본다. 정확한가, 출처를 지켰나, 말투가 맞나
  • 판정자도 LLM이라 LLM의 결점을 다 가진다. 매번 다르고, 틀리고, 돈이 든다
  • 자신 있게 틀릴 수 있어서 반드시 검증해야 한다

언제: 이해가 필요할 때. 정확한가, 근거가 있나, 쓸모 있나

도메인을 아는 사람이 전문가로서 읽고 채점한다.

  • 품질의 기준점이다
  • 느리고 비싸다
  • 지루해지면 대충 훑기 시작한다

언제: 본 적 없는 종류의 실패를 찾을 때, 그리고 LLM 판정자가 제대로 판정하는지 확인할 때

에이전트는 왜 더 어려운가 11:20

LLM 호출 하나는 단순하다. 입력을 주면 출력이 나온다. 에이전트는 여러 단계를 사슬처럼 잇는다. 그래서 두 가지가 생긴다.

연쇄 실패 12:00

초반 단계의 실수가 뒤 단계로 번지며 점점 더 엇나간다. 금융 분석 에이전트에 Tesla 보고서를 시켰는데, 검색에서 자동차 회사가 아니라 발명가 니콜라 테슬라가 나왔다고 하자. 에이전트는 발명가에 대해 아름답고 완벽한 형식의 보고서를 쓴다. 형식, 말투, 문법 검사는 전부 통과한다. 주제만 완전히 틀렸다.

교훈: 자신 있게 틀린 것이 눈에 띄게 틀린 것보다 나쁘다

규칙보다 똑똑한 에이전트 12:50

발표자가 인용한 Anthropic의 τ²-bench 사례. 고객 응대 시뮬레이션에서 이코노미 승객이 좌석 변경을 요청했다. 규칙상 이코노미는 좌석을 바꿀 수 없으니 에이전트가 거절해야 "정답"이었다. 그런데 Claude는 승객을 일등석으로 올리고, 좌석을 바꾸고, 다시 이코노미로 내렸다. 사용자가 원한 일을 해냈는데 테스트는 실패라고 했다.

교훈: 에이전트는 예상 밖의 해법을 찾는다. 테스트는 유연해야 한다

  5. 좋음의 정의를 글로 쓴다. 도메인 전문가와 함께. 그 정의의 항목 하나하나가 평가가 된다.
  6. 맞는 평가를 고르는 것이 조정보다 중요하다. 정확성 판정은 지식 기준일 때문에 전부 0점이었고, 충실성 판정은 지어낸 숫자를 짚었다.
  7. 직접 쓰는 판정은 역할과 맥락, 오류 분석에서 나온 구체적 기준, XML 태그, 예시, 답 제한의 다섯 부분. 차원마다 평가자 하나, 신 평가자는 금지. 판정 프롬프트는 코드다.

코드 평가는 답이 결정적일 때(형식, 길이, 필수 항목, 금지 문구). LLM 판정은 이해가 필요할 때(정확한가, 근거가 있나, 쓸모 있나). 사람은 본 적 없는 실패를 찾고 LLM 판정자를 검증할 때.
Q3발명가 테슬라 보고서 예시가 보여 주는 에이전트 실패 특징 두 가지는?
연쇄 실패와 자신 있게 틀림. 검색 단계의 실수가 끝까지 번지고, 형식·말투·문법 검사는 전부 통과하는 완벽해 보이는 보고서가 나온다. 자신 있게 틀린 것이 눈에 띄게 틀린 것보다 나쁘다.
Q4LLM 판정 결과의 세 요소 중 가장 가치 있는 것과 그 이유는?
설명. 무엇이 틀렸고 빠졌는지, 프롬프트의 어디를 고칠지 알려 준다. 수백 개를 모아 다른 LLM에게 패턴을 뽑게 하고 코딩 에이전트에 넘겨 고칠 수도 있다.
Q5116%의 애널리스트는 네 가지 원인 중 무엇이고 어떻게 알았나?
추론 오류. 트레이스를 보니 검색 결과 두 개는 각각 멀쩡했고(검색 실패 아님), 에이전트가 서로 다른 데이터셋의 비율을 하나로 합쳤다. 원인을 모르면 고칠 수 없으니 트레이스를 읽는다.
Q6정확성 판정이 16개 전부 0점을 준 이유와 대안은?
판정 모델이 자기 지식으로 판단하는데 지식 기준일이 1월이라 10월 주가를 환각으로 봤다. 대안은 충실성 판정. 주어진 검색 결과와 메모를 맥락으로 주고 "이 데이터 기준으로 말이 되나"를 묻는다. 판정자가 실제로 답할 수 있는 질문이다.
Q7도구 선택 판정자가 파일 저장 시도를 대부분 통과시킨 이유는?
프롬프트가 "보고서를 써라"고만 하고 어디에, 누구를 위해 쓰라고 하지 않아 모호했다. 판정자는 그 모호함을 보고 파일에 쓰는 것도 타당하다고 봤다. 에이전트에게 하는 말과 평가에게 하는 말은 서로 영향을 준다.
Q8좋은 판정 프롬프트의 다섯 부분은?
역할과 맥락, 명시적 기준(오류 분석에서 나온 것), XML 태그로 구분한 데이터, 라벨 붙인 예시, 답 형식 제한(도구 호출로 선택지 정의).
Q9예시를 XML 태그로 감싸지 않았을 때 무슨 일이 있었나? 교훈은?
판정자가 예시와 데이터를 헷갈려 줄줄이 실행 불가능을 냈고, 태그를 넣자 다른 변경 없이 뒤집혔다. 판정 프롬프트는 작은 표현에 극도로 민감하니 코드처럼 버전 관리하고 테스트한다.
Q10"네 기준을 모두 충족해야만"이라는 문장을 보탰더니 어떻게 됐나?
dev 일치가 12/12에서 11/12로, test에서는 Apple이 추가로 깨졌다. 더 구체적으로 쓰려다 평가를 사람 판단과 덜 비슷하게 만들 수 있다. 그래서 조정용과 검증용 데이터를 나눠 확인한다.
Q11정밀도와 재현율 중 보통 무엇을 우선하고 왜?
재현율. 거짓 경보는 멀쩡한 보고서를 보는 1~2분을 쓰지만, 놓친 실패는 나쁜 보고서가 고객에게 간다. 다만 어느 쪽이 더 비싼지는 앱마다 정한다.
Q12프롬프트 개선 실험에서 실행 가능성과 충실성은 각각 어떻게 됐고, 무엇을 말해 주나?
실행 가능성 5/16 → 48/48, 충실성 2/16 → 3/48. "조사에 나온 숫자만 써라"를 적었는데도 지어내기는 안 고쳐졌다. 측정한 것만 고쳐졌고 다음 과제가 무엇인지 평가가 알려 준다.
Q13Haiku 5.5가 일관성 검사를 통과한 방식의 문제는?
45번 중 41번 "보유"라고 해서 같은 답을 반복했을 뿐이다. 더 보수적이 된 것이고 아마 더 나쁘다. 하지만 평가 덕에 무엇이 바뀌었는지, 지나친 보수성이 문제라는 것을 안다. 비용도 4배다.
Q14CI에서 실행 가능성 관문을 평균 0.8로 세운 이유는?
LLM 판정은 보고서 하나에서는 흔들릴 수 있다. 그래서 하나가 아니라 평균으로 관문을 세운다. 종목 언급은 차단선이라 전부 통과해야 하고, 실행 가능성은 목표선이다.

용어뜻
평가 (eval)매번 달라지는 LLM 출력의 품질을 재는 테스트. 트레이스 위에서 돈다
트레이스 (trace)AI가 한 일을 단계별로 입력과 출력까지 기록한 것. 로그에 해당
스팬 (span)트레이스의 한 단계. 입력, 출력, 시간, 토큰, 때로는 비용을 담는다
주석 (annotation)트레이스나 스팬에 붙이는 사람이 읽을 수 있는 글이나 라벨. 평가 결과와 사람 라벨이 여기에 저장된다
루브릭 (rubric)판정자에게 좋음이 무엇인지 알려 주는 규칙. 발표자 말로는 그냥 "규칙"
LLM 판정 (LLM-as-judge)두 번째 LLM이 루브릭에 따라 첫 번째 LLM의 출력을 채점하는 것
정확성 / 충실성정확성은 판정자의 지식 기준으로 맞나. 충실성은 주어진 맥락(검색 결과 등) 기준으로 근거가 있나
실행 가능성 (actionability)이 워크숍의 맞춤 기준. 보고서가 매수·매도·보유를 말하는가
열린 코딩 / 축 코딩본 것을 자유롭게 적기 / 그 메모를 범주로 묶기. 범주를 미리 정하지 않는 순서
하네스 누출발표자의 코딩 에이전트가 지어낸 범주. 권한 없는 일을 자꾸 허락해 달라고 하는 현상
스위스 치즈 모델구멍 있는 방어층을 여러 겹 쌓아 오류가 끝까지 못 지나가게 하는 생각
신 평가자 (god evaluator)모든 기준을 한 프롬프트에 넣은 판정자. 실패해도 무엇이 실패했는지 모른다
차단선 / 목표선guardrail은 출시를 막는 평가. north star는 지향하지만 출시를 막지 않는 평가
정답 데이터셋 (golden dataset)사람이 아는 한 답이 맞는 예시 모음. 판정자를 검증하는 기준
dev / test 분할평가를 조정하는 데 쓰는 데이터와 평가가 작동하는지 검증하는 데 쓰는 데이터. 보통 75:25
정밀도 / 재현율"문제"라고 한 것 중 진짜 문제인 비율 / 진짜 문제 중 잡아낸 비율. 하나가 오르면 다른 하나가 내린다
Cohen's Kappa두 채점자가 우연 이상으로 얼마나 일치하는지 재는 점수. 사람끼리도 0.2~0.3으로 낮을 때가 많다
자기 선호 편향모델이 자기 계열 출력을 더 높게 주는 경향. 다른 제공자의 모델로 채점하는 이유
실험 (experiment)데이터셋 + 과제 + 평가자. 같은 입력과 같은 평가로 변경 전후를 비교하는 틀
pass@k / pass^kk번 중 한 번이라도 성공 / k번 모두 성공. 실수가 비싼 곳은 pass^k
