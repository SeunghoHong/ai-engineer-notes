에이전트를 풀어 두지 말고 워크플로에 넣어라

결제 회사 Flywire는 AI 에이전트가 마음대로 돌게 두지 않는다. 정해진 순서는 코드가 맡고 모델은 판단이 필요한 단계에서만 부르는 사내 플랫폼 Orbit을 만들었다.

원본 영상: Agents in Orbit: Workflows, Not Autopilot 발표: Eduardo Simon, Javier Casal (Flywire AI Platform Experience 팀)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름 중 확실한 것(GitLab, SOC 2, Claude Agent SDK 등)은 바로잡았다. 확실하지 않은 것에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. Flywire는 규제가 강한 결제 회사다. 그래서 민감 데이터가 밖으로 나가지 않게 에이전트 플랫폼을 직접 만들었다.
  2. 플랫폼 이름은 Orbit이다. 예측 가능한 부분은 코드가 처리하고, 모델은 추론이 필요한 단계에서만 부른다.
  3. 워크플로 하나는 YAML 파일 하나다. 다른 코드처럼 머지 리퀘스트 리뷰를 거친다.
  4. 각 LLM 단계는 Claude Agent SDK를 빌려 쓴다. 대신 네트워크, 도구, 스킬, MCP 서버 권한을 단계마다 좁힌다.
  5. 모델의 답은 JSON 스키마로 강제한다. 평가는 워크플로 전체가 아니라 LLM 단계 하나씩 떼어서 한다.
  6. 지난 30일 동안 11,000회 이상 실행했고 성공률은 99%라고 한다. 그중 코드 리뷰가 9,700회 이상이다.
  7. 교훈은 세 가지다. 작게 시작하고, 모델은 가치를 더하는 곳에만 쓰고, 안전장치와 사람을 남긴다.
01

규제 속의 결제 회사 00:30

Flywire는 교육, 의료, 여행, 기업 서비스 분야의 복잡한 국제 결제를 처리한다. 발표자에 따르면 고객사는 5,000곳이 넘고, 240개가 넘는 나라에서 서비스한다.

세계의 나라 수는 200개 안팎이다. 240이라는 숫자는 국가와 지역territory을 함께 센 것으로 보인다.

금액이 큰 국제 거래를 다루기 때문에 규제 준수, 개인정보 보호, 보안은 덧붙이는 기능이 아니다. 사업의 기본 조건이다. 회사는 PCI DSS와 SOC 2 같은 기준을 지킨다. 고객 데이터, 개인 식별 정보, 결제 정보는 반드시 안전해야 한다. 그래서 민감한 맥락을 외부 서비스에 그냥 넘길 수 없다.

엔지니어링 조직 01:20

  • 엔지니어는 약 400명이고 전 세계에 흩어져 있다.
  • 언어는 Java, Ruby, Go, Python, .NET, PHP로 다양하다.
  • 거의 모든 서비스가 Victoria 위에서 돈다. Victoria는 GitLab과 AWS 위에 만든 사내 PaaS다.
  • Victoria가 빌드 파이프라인과 배포 방식을 표준화해 준다.
이 배경이 뒤의 결정을 만든다 데이터가 회사 밖으로 나가면 안 된다. 그래서 플랫폼을 직접 만들고, 이미 있는 Victoria 위에 올린다. 사람의 승인 단계도 남긴다.

  • 엔지니어들은 AI 자동화를 원한다.

팀이 생긴 뒤 사내 도구에 커밋을 1,000개 가까이 쌓았다.

업계는 더 빠르다 02:40

같은 6개월 동안 Claude Code 하나만 160번 넘게 릴리스했다. 거의 하루에 한 번이다. 주요 AI 연구소들은 새 모델을 20개 넘게 냈다. 매주 새 모델, 새 도구, 새 작업 방식이 나온다. 발표자는 빨리 만드는 것만이 아니라 따라가는 것이 과제라고 했다.

03

Orbit: 자동조종 대신 워크플로 03:00

Orbit은 엔지니어의 반복 잡무를 없애는 사내 플랫폼이다. 발표자는 "토일 킬러" toil killer라고 불렀다. 토일은 자동화할 수 있는데 사람이 반복해서 하는 일이다.

자동조종 autopilot에이전트를 열린 루프에 풀어 둔다에이전트가 처음부터 끝까지 스스로 판단하며 돈다
→
Orbit 워크플로결정적 코드에 작은 LLM 단계를 끼운다반복되는 절차는 코드로 굳히고, 추론이 필요할 때만 모델을 부른다

결정적 코드 deterministic code는 같은 입력이면 늘 같은 결과를 내는 코드다. Orbit은 이런 코드로 뼈대를 세우고, 모델은 그 사이의 작은 단계로만 쓴다.

사지 않고 만든 이유 03:30

  • 만드는 비용이 낮아졌다. 프런티어 모델 덕분에 기능 개발이 매우 빨라졌다.
  • 데이터가 밖으로 나가지 않는다. 회사는 카드 결제 정보, 개인 식별 정보PII, 건강 정보PHI를 다룬다. 실행을 기존 Victoria 안에 두면 민감 데이터가 통제된 환경을 떠나지 않는다.
  • 심사를 건너뛴다. 외부 업체를 쓸 때 필요한 긴 보안 심사와 추가 규제 대응 작업이 없다.
04

워크플로 하나 뜯어 보기 04:10

Orbit의 에이전트는 각각 YAML 파일 하나로 정의한다. 파일은 저장소에 있다. 그리고 다른 코드와 똑같이 머지 리퀘스트MR 리뷰를 거친다.

예: 코드 리뷰 에이전트 04:20

순서누가하는 일
1트리거엔지니어가 MR에서 리뷰 봇을 멘션하면 GitLab 웹훅이 워크플로를 시작한다
2코드MR 메타데이터를 가져온다
3코드변경의 위험 등급을 분류한다
4코드이전에 남긴 리뷰 지적을 불러온다
5코드저장소를 복제한다
6모델코드를 읽기만 한다. 수정 권한은 없다. 정해진 출력 스키마로만 답한다
7코드지적 사항을 MR에 다시 올린다

일곱 단계 중 모델이 맡는 건 하나뿐이다.

코드는 예측 가능한 부분을 맡고, 모델은 추론이 정말 필요한 곳에서만 부른다. 이것이 "자동조종이 아닌 워크플로"의 뜻이다.발표자의 설명을 옮김

왜 YAML과 MR 리뷰인가 05:10

  • YAML은 엔지니어들이 이미 아는 형식이다.
  • 리뷰도 매일 하던 방식 그대로다.
  • 코딩 에이전트도 워크플로 정의를 사람만큼 쉽게 읽고, 쓰고, 리뷰한다. 코드베이스가 AI 친화적으로 유지된다.

엔지니어링 팀 밖에서 나오는 요청도 있다. 이런 회사 업무용으로는 Orbit 화면에서 미리 만든 활동을 끌어다 놓아 워크플로를 만드는 도구를 검토하고 있다. YAML을 쓰지 않아도 되게 하려는 것이다.

워크플로를 시작하는 세 가지 길 05:50

방법예
직접 호출엔지니어나 다른 시스템이 Orbit 내부 API나 CLI로 부른다
웹훅GitLab, Jira, Sentry, AWS에서 일이 생기는 순간 시작한다. 새 MR, 새 프로덕션 오류 같은 일이다
일정 작업정해진 주기로 돈다. 매일 번역 동기화, 기능 플래그 정리, 지식 베이스 갱신

준비 중인 네 번째 길도 있다. Orbit용 MCP 서버다. 06:20 사내의 다른 AI 서비스와 도구가 워크플로를 직접 시작하게 하려는 것이다. 예를 들어 엔지니어가 Slack에서 Claude를 태그해 Orbit 워크플로를 돌릴 수 있다. 대화를 떠날 필요가 없다.

여러 저장소를 한 번에 07:40

발표자가 꼽은 가장 큰 이점 중 하나다. 여러 저장소에 같은 변경을 한꺼번에 할 수 있다. 마이그레이션, 라이브러리 업데이트, 지원 중단deprecation 처리에 특히 편하다. Claude doctor(추정)를 돌리거나 AI 준비도 점수표를 여러 저장소에 돌릴 때도 쓴다.

작업 단위는 여전히 MR이다 08:00 자동화가 아무리 늘어도 결과물은 MR로 나온다. MR은 사람이 루프 안에 남는 자리다. 규제 환경이라 사람이 MR을 리뷰하고 승인한다.
06

실행 구조와 안전장치 08:20

처음컨테이너 하나AWS ECS Fargate 컨테이너 하나에 오케스트레이션 계층(하네스)과 실행 환경이 함께 있었다
→
지금세 부분으로 분리오케스트레이션 계층, 에이전트 실행 환경, 세션 상태를 따로 둔다
  • 격리, 유지보수, 자원 배분이 좋아졌다.
  • 한 부분에서 오류가 나도 샌드박스까지 같이 죽지 않는다.
  • 부분마다 따로 늘리고 줄일 수 있다.

Fargate는 작업 수를 탄력적으로 늘린다. 그래서 에이전트를 아주 많이 병렬로 돌릴 수 있다. 배포도 쉬웠다. 이미 있던 Victoria가 앱 확장을 맡아 주기 때문이다.

규모에는 안전장치가 따른다 09:20

장치하는 일막는 것
타임아웃모든 에이전트는 설정한 시간이 지나면 멈춘다끝없이 도는 실행
실행 횟수 제한 rate limit기본값을 일부러 빡빡하게 잡는다고장 난 API 연동이 에이전트를 수천 개 띄워 비용이 크게 불어나는 일
동시성 제어컨트롤 플레인이 락으로 같은 작업의 중복 실행을 막는다이미 코드 리뷰가 도는데 같은 요청이 또 오면 버린다

컨테이너의 한계와 microVM 09:50

Victoria는 표준 Fargate 작업 정의를 쓴다. 그래서 컨테이너가 가볍고 제약이 많다. 기본 에이전트 컨테이너에는 흔한 언어 런타임이 들어 있다. 하지만 Bundler, Maven, Composer 같은 패키지 관리자는 일부러 뺐다. 그 결과 Jira Implementer(추정)처럼 무거운 에이전트는 컨테이너 안에서 네이티브 빌드나 단위 테스트를 쉽게 돌리지 못한다.

발표자에 따르면 4월에 Orbit을 시작할 때는 AWS Lambda microVM이 없었다. AWS가 6월에 내놓았다. 10:20 이것은 관리형 microVM이다. 멈췄다가 멈춘 자리에서 이어 가는 프로세스처럼 동작한다. 이 성질이 에이전트 실행과 잘 맞는다.

지금은 프로젝트 종류에 따라 런타임을 골라 쓴다. 기술 스택마다 자기 도구 모음을 격리된 환경에서 빠르게 얻는다.

아직 완전한 샌드박스는 아니다 목표는 Docker in Docker나 여러 microVM을 쓰는 구성이다. 어느 저장소에서든 에이전트가 테스트와 복잡한 검증을 돌릴 수 있게 하려는 것이다.
07

하네스는 빌리고 권한은 좁힌다 11:00

LLM 단계 안의 하네스harness는 직접 만들지 않았다. 하네스는 모델을 감싸 도구 호출, 순서, 규칙을 처리하는 실행 틀이다. Orbit은 Claude Agent SDK를 가져다 쓴다. Claude Code를 움직이는 것과 같은 하네스다.

도구 사용, 서브에이전트, 스킬이 처음부터 들어 있고, 이미 많이 검증됐다. 그래서 팀은 배관 공사 대신 워크플로 자체에 집중한다.

Orbit이 그 위에 더하는 것은 통제다. 단계마다 네 가지를 제한한다.

제한하는 것뜻과 예
네트워크에이전트가 접속할 수 있는 곳
도구호출할 수 있는 도구. 코드 리뷰 단계는 코드를 읽고 검색만 한다. 파일을 고치거나 변경을 푸시하지 못한다
스킬불러올 수 있는 스킬
MCP 서버쓸 수 있는 서버, 그리고 서버마다 허용된 도구. Sentry 조사 에이전트는 사내 MCP 서버로 트레이스를 조회한다. 단, 읽기 전용 도구 몇 개만 쓴다
권한도 코드처럼 리뷰된다 이 제한은 모두 YAML 파일에 적는다. 그래서 각 LLM 단계는 꼭 필요한 접근만 갖는다. 그 접근은 다른 코드처럼 눈에 보이고 리뷰된다.

발표자들은 Anthropic이 아니라 Claude Agent SDK를 쓰는 고객 쪽이다. 로드맵에는 특정 하네스에 묶이지 않게 바꾸는 계획도 있다(11번 섹션).

스킬에서 시작해 워크플로로 12:00

스킬은 한곳에서 나온다. Flywire는 중앙 스킬 저장소를 두고, 이를 사내 Claude Code 플러그인 마켓플레이스로 배포한다. Orbit은 빌드할 때 이 마켓플레이스에 연결한다.

그래서 같은 스킬이 두 곳에서 돈다. 엔지니어는 노트북의 Claude Code에서 돌린다. Orbit은 자동 워크플로 안에서 돌린다.

팀에게 하는 권고 12:30

  1. 스킬로 시작한다. 쓰기 싸고, 고치기 쉽고, 첫날부터 쓸모가 있다.
  2. 자동화할 가치가 있다고 확신이 들면 Orbit으로 옮겨 워크플로로 만든다.
  3. 예측 가능한 부분은 결정적 코드가 된다. 모델은 가치를 더하는 곳에서만 부른다.
열린 세션

  • 한 단계씩 지켜보며 이끈다

  • 백그라운드에서 돈다

출력은 스키마로, 평가는 단계별로 13:10

구조화된 출력

모든 LLM 단계는 모델의 답을 엄격한 JSON 스키마로 받는다. 이것을 구조화된 출력structured output이라고 한다.

  • 출력 형식이 묶여 있으면 다음 분기, 오류 처리, 상태 전환을 결정적인 제어 흐름이 맡는다.
  • 예측하기 어려운 문자열 파싱에 기대지 않는다.
  • 답이 스키마 검증에 실패하면 Orbit이 범위를 좁힌 재시도나 대체 경로fallback를 자동으로 돌린다. 그다음에 진행한다.

단계 하나씩 떼어 평가하기 13:50

에이전트 워크플로 전체를 합성 벤치마크 환경에서 처음부터 끝까지 평가하면 문제가 많다. 결과가 들쭉날쭉하고, 비싸고, 똑같이 재현하기 어렵다.

그래서 Orbit의 평가 하네스는 LLM 단계 하나를 떼어 낸다. 그 단계에 과거 실행의 실제 상태와 맥락을 그대로 넣는다. 이렇게 하면 출력 품질을 재고, 프롬프트를 고친 효과를 확인하고, 성능 퇴보를 빠르고 싸게 잡는다.

"충분히 좋은가"를 아는 법 14:20

  1. 바이브 체크vibe check: 지금은 새 에이전트가 이 단계를 거쳐 프로덕션에 나간다. 팀이 실제 사례 몇 개로 돌려 보고 기대대로 움직이는지 확인한다.
  2. 전 구간 추적: 프로덕션에서는 모든 실행을 OpenTelemetry로 처음부터 끝까지 추적한다. 활동, 모델 호출, 도구 호출을 하나하나 남긴다.
  3. 골든 데이터셋: 실제 실행의 트레이스를 뽑아 골든 데이터셋에 넣는다. 데이터셋은 코드 옆 저장소에서 버전 관리하고, 필요할 때 돌린다.
  4. 고치고 다시 재기: 결과를 보고 프롬프트를 고치거나 모델을 바꾼다. 데이터셋을 다시 돌려 비교한다.
평가 로드맵 15:00 아직 온라인 평가는 없고 내부에서 만들고 있다. 목표는 평가 순환 전체를 Orbit 안에서 돌리는 것이다. 화면이나 MCP 서버에서 에이전트를 배포하고, 프로덕션 실행을 지켜보며 평가하고, 다시 배포하지 않고 개선한다. 내보내고, 재고, 고치는 일을 한곳에서 한다.

프로덕션 진입 기준이 아직 바이브 체크라는 점은 발표자가 직접 밝힌 한계다.

30일 동안의 숫자 15:30

발표자가 밝힌 지난 30일의 성과다. 전체 워크플로 실행은 11,000회가 넘고 성공률은 99%다.

코드 리뷰 에이전트는 MR 하나에 평균 3분이 안 걸린다. 30일에 9,700회면 하루 평균 약 320회다(노트에서 계산).

이 숫자는 Orbit을 만든 팀이 직접 낸 것이다. 발표에서는 "성공"을 어떻게 판정하는지, 리뷰 지적이 얼마나 받아들여졌는지 밝히지 않았다. 그 점을 감안해 읽자.

배운 것과 다음 계획 16:10

  • 셀프서비스가 통했다. 발표자가 가장 잘한 결정 중 하나로 꼽았다. 표준 안전장치가 있어서 SRE, 보안, IT, 지원 팀도 자기 워크플로 단계를 쉽고 안전하게 만든다.
  • 비용 관리는 모델 고르기에서 시작한다. 모든 단계에 가장 강한 모델이 필요하지는 않다. 그래서 LLM 단계마다 자기 모델을 선언한다. 예를 들어 계획 단계와 구현 단계는 다른 모델을 쓸 수 있다.
  • 데이터 분리는 끝나지 않는 일이다. 개발 과정SDLC 데이터, 회사 운영 데이터, 민감한 결제 프로덕션 데이터를 엄격히 나눈다.
  • 집중이 필요하다. 자동화 요청이 많다. 그래서 효과가 큰 일부터 고르는 일이 중요하다.

핵심 정리

  1. 규제가 강한 결제 회사라서 민감 데이터가 밖으로 나가지 않게 에이전트 플랫폼을 직접 만들었다.
  2. Orbit의 원칙: 예측 가능한 부분은 결정적 코드, 추론이 필요한 곳만 작은 LLM 단계.
  3. 워크플로 하나는 YAML 파일 하나이고, 코드처럼 MR 리뷰를 거친다.
  4. 시작 방법은 API·CLI, 웹훅, 일정 작업 세 가지다. MCP 서버를 준비하고 있다.
  5. 실행에는 타임아웃, 실행 횟수 제한, 중복 방지 락을 건다. 결과물은 MR이고 사람이 승인한다.
  6. LLM 단계는 Claude Agent SDK를 쓰고, 네트워크·도구·스킬·MCP 권한을 단계마다 좁힌다.
  7. 스킬로 시작해, 가치가 확인되면 워크플로로 옮긴다. 같은 스킬이 노트북과 Orbit에서 돈다.
  8. 모델 출력은 JSON 스키마로 강제하고, 실패하면 재시도나 대체 경로로 간다.
  9. 평가는 LLM 단계 하나씩 떼어서 한다. 실제 트레이스로 골든 데이터셋을 만든다.
  10. 30일 동안 11,000회 넘게 실행했다(발표자 수치). 교훈은 작게 시작, 모델은 필요한 곳에만, 안전장치와 사람은 남긴다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1"자동조종이 아닌 워크플로"란 무슨 뜻인가?
에이전트를 열린 루프에서 끝까지 알아서 돌게 두지 않는다. 예측 가능한 부분은 결정적 코드가 처리하고, 추론이 필요한 단계에서만 모델을 부른다.
Q2Flywire가 플랫폼을 사지 않고 직접 만든 이유 세 가지는?
프런티어 모델 덕분에 개발이 빨라져 자체 플랫폼 비용이 낮다. 실행을 기존 Victoria 안에 두면 민감 데이터가 통제된 환경을 떠나지 않는다. 외부 업체에 필요한 긴 보안 심사와 규제 대응 작업을 건너뛴다.
Q3코드 리뷰 워크플로에서 모델이 맡는 단계와 그 제약은?
일곱 단계 중 하나다. 코드를 읽기만 할 수 있고 수정 권한이 없다. 정해진 출력 스키마로만 답한다. 나머지는 트리거와 결정적 코드다.
Q4워크플로를 YAML 파일로 정의하고 MR 리뷰를 거치게 한 이유는?
엔지니어가 이미 아는 형식이고 리뷰도 평소 방식 그대로다. 코딩 에이전트도 정의를 쉽게 읽고, 쓰고, 리뷰할 수 있다.
Q5워크플로를 시작하는 세 가지 방법과 준비 중인 네 번째는?
API나 CLI로 직접 호출, GitLab·Jira·Sentry·AWS 웹훅, 일정 작업. 준비 중인 것은 Orbit용 MCP 서버다.
Q6에이전트를 대규모로 돌릴 때 거는 세 가지 안전장치는?
타임아웃, 기본값이 빡빡한 실행 횟수 제한, 락으로 같은 작업의 중복 실행을 막는 동시성 제어.
Q7LLM 단계마다 제한하는 네 가지는?
접속할 수 있는 네트워크, 호출할 수 있는 도구, 불러올 수 있는 스킬, 쓸 수 있는 MCP 서버와 서버별 허용 도구.
Q8무거운 에이전트가 기본 컨테이너에서 빌드와 테스트를 못 돌리는 이유는?
기본 에이전트 컨테이너가 Bundler, Maven, Composer 같은 패키지 관리자를 일부러 뺐기 때문이다. 그래서 프로젝트 종류별 런타임을 microVM으로 붙이고, 완전한 샌드박스로 옮기는 중이다.
Q9발표자가 팀에게 권하는 자동화 순서는?
먼저 스킬로 만든다. 자동화할 가치가 확실해지면 Orbit 워크플로로 옮긴다. 같은 스킬이 노트북의 Claude Code와 Orbit 양쪽에서 돈다.
Q10모델 답이 JSON 스키마 검증에 실패하면 어떻게 되나?
Orbit이 범위를 좁힌 재시도나 대체 경로를 자동으로 돌린 뒤 다음으로 넘어간다.
Q11워크플로 전체 대신 LLM 단계 하나씩 평가하는 이유는?
전체를 처음부터 끝까지 평가하면 결과가 들쭉날쭉하고 비싸고 재현이 어렵다. 단계 하나에 과거 실행의 실제 상태를 넣으면 프롬프트 변경 효과와 성능 퇴보를 싸고 빠르게 잰다.
Q12비용을 관리하려고 하는 일은?
LLM 단계마다 모델을 따로 고른다. 계획과 구현에 다른 모델을 쓸 수 있다. 작업마다 비용 효율적인 모델을 고르는 자동 라우터를 로드맵에 넣었다.

OpenTelemetry실행 기록(트레이스)을 수집하는 오픈 표준
트레이스Trace. 한 번의 실행에서 일어난 단계, 모델 호출, 도구 호출을 순서대로 남긴 기록
골든 데이터셋Golden dataset. 품질을 잴 때 기준으로 삼는 사례 묶음. 무언가 바꿀 때마다 다시 돌려 비교한다
온라인 평가Online evaluation. 프로덕션에서 돌아가는 실행의 품질을 실시간으로 재는 것
모델 라우터Model router. 작업마다 어떤 모델을 쓸지 자동으로 고르는 장치
린터Linter. 코드의 규칙 위반이나 문제를 자동으로 찾아 주는 도구
