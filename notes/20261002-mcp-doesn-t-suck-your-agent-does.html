MCP가 아니라 에이전트가 문제다

MCP가 컨텍스트를 낭비한다는 비판은 프로토콜이 아니라 에이전트를 만든 방식의 문제다. 발표자는 원격 연결은 MCP에, 에이전트가 쓰는 인터페이스는 CLI에 맡기자고 제안한다. 그 둘을 잇는 도구로 Apify가 만든 mcpc를 소개한다.

원본 영상: MCP Doesn't Suck. Your Agent Does. 발표: Jan Čurn (Apify 창업자, CEO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 인용은 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. MCP는 에이전트가 도구에 접근하는 표준이다. 크게 퍼진 만큼 "MCP는 끝났다"는 비판도 쏟아졌다.
  2. 가장 큰 비판은 컨텍스트 낭비다. 발표자는 이것이 프로토콜이 아니라 하네스의 문제라고 본다. 도구를 처음부터 전부 올리는 순진한 구현 탓이다.
  3. 해결책은 이미 있다. 서브에이전트, 점진적 도구 탐색, code mode다. 하지만 대부분의 클라이언트가 아직 지원하지 않는다.
  4. CLI는 필요할 때만 부르기와 코드로 실행하기를 처음부터 갖고 있다. 모델은 셸을 학습 데이터로 이미 잘 안다.
  5. 대신 CLI는 표준 인증과 전송 방식이 없어 원격 접근에 약하다. 원격 연결은 MCP가 낫다.
  6. 제안: 원격은 MCP, 에이전트 쪽 인터페이스는 CLI. 그 다리로 Apify가 mcpc를 만들었다.
  7. Apify 자체 평가에서 mcpc는 CLI와 비슷했고, MCP를 그대로 붙인 방식은 토큰을 더 썼다. 결론은 CLI냐 MCP냐가 아니라 MCP + CLI다.
01

MCP의 짧은 역사 00:40

MCP Model Context Protocol는 에이전트가 도구와 리소스에 안전하게 접근하는 방법을 정한 표준이다. 에이전트와 도구 사이의 연결 규격이라고 보면 된다.

발표자에 따르면 Anthropic이 거의 2년 전에 내놓았다. 작년에는 AI 업계에서 가장 주목받는 기술이 됐다.

  • 발표자 추산으로 MCP 서버는 1만~1만 5천 개다. 01:00
  • Claude, ChatGPT 같은 클라이언트가 도구와 커넥터를 붙이는 표준으로 MCP를 쓴다.
  • 서버가 너무 많아 서버 목록인 레지스트리 registry가 생겼다. 레지스트리가 너무 많아지자 레지스트리의 레지스트리까지 생겼다. 01:10

03

진짜 문제는 하네스 02:30

가장 많이 나온 비판은 MCP가 컨텍스트 context window를 너무 많이 먹는다는 것이다. 컨텍스트는 모델이 한 번에 보고 기억하는 작업 공간이다. 발표자는 이 비판이 사실이라고 인정한다.

문제는 초기 에이전트가 MCP를 붙인 방식이다. MCP 서버를 연결하면 그 서버의 도구 설명을 처음부터 전부 컨텍스트에 등록했다.

  • 질문을 하나도 하기 전에 컨텍스트의 3분의 1 정도가 도구 설명으로 찰 수 있다고 발표자는 말한다.
  • 도구를 부를 때마다 그 결과도 컨텍스트에 쌓인다.
  • 컨텍스트가 길어질수록 정확도가 떨어진다. 이를 컨텍스트 부패 context rot라고 부른다.
  • 비용이 늘고 속도도 느려진다.

프로토콜이 아니라 하네스의 문제 03:20

발표자는 이것이 MCP의 문제가 아니라 하네스 harness의 문제라고 말한다. 하네스는 모델을 감싸 도구 호출과 컨텍스트 관리를 맡는 실행 틀이다.

MCP 명세는 하네스를 어떻게 만들지 아무것도 정하지 않는다. 그건 구현하는 쪽의 몫이다. MCP를 효율적으로 쓰게 만드는 건 에이전트를 만드는 사람의 일이다.

발표 제목의 뜻 "MCP Doesn't Suck. Your Agent Does." MCP가 형편없는 게 아니라, MCP를 쓰는 에이전트가 형편없다는 말이다.
04

이미 나온 해결책 세 가지 03:40

컨텍스트 문제를 푸는 방법은 이미 세 가지가 나와 있다. 뒤로 갈수록 효과가 크다.

해결책 1 · 서브에이전트 03:50

작업을 새 서브에이전트 sub-agent에게 맡긴다. 서브에이전트는 자기 컨텍스트에서 일한다. 그래서 메인 컨텍스트가 덜 어지럽다.

  • 그래도 그 토큰 값은 그대로 낸다
  • 도구가 비밀번호 같은 민감한 값을 돌려주면 컨텍스트에 남는다
  • 남은 값은 다른 도구 호출이 악용할 수 있다

한계: 컨텍스트는 민감한 값이나 큰 데이터를 넘기기에 나쁜 곳이다. 서브에이전트는 이 문제를 조금 뒤로 미룰 뿐 없애지 못한다.

해결책 2 · 점진적 도구 탐색 04:40

도구를 처음부터 다 올리지 않고 필요할 때만 올린다. 점진적 도구 탐색 progressive tool discovery이라고 부른다. 발표자에 따르면 작년 말 Anthropic이 먼저, 이어서 Cursor가 도입했다.

  • Claude에는 다른 도구를 찾아 주는 도구 tool search tool가 있다
  • 찾은 도구만 그때 컨텍스트에 올린다
  • 한 작업에 필요한 도구는 보통 한두 개라 컨텍스트를 크게 아낀다

효과: 더 정확하고, 더 싸고, 더 빠르다. 모두가 해야 할 방법인데 실제로는 그렇지 않다고 발표자는 말한다.

해결책 3 · code mode 05:40

발표자에 따르면 작년 말 Cloudflare가 내놓았다. MCP 도구를 컨텍스트에 올리는 함수 목록으로 보지 않고 코드로 다룬다. MCP 서버와 도구를 코드로 바꿔, 모델이 코드처럼 읽고 부르게 한다.

  • 모델은 코드를 쓰고 읽는 데 강하다
  • grep으로 찾고 정의를 따라가며 코드를 잘 탐색한다
  • 도구 설명도 같은 방식으로 탐색한다

왜 통하나: 도구 호출 tool calling은 사람이 만든 인위적 형식이다. 실제 세상의 데이터에는 거의 없어서 합성한 데이터로 가르쳐야 한다. 그래서 모델은 도구를 직접 부르기보다 코드를 쓰는 쪽을 더 잘한다.

그런데 대부분의 클라이언트는 아직 못 쓴다 06:50 발표자가 보기에 code mode는 기존 구현조차 쓰기 어렵고 특정 플랫폼에 묶여 있다. 그래서 실제로 쓰는 사람이 적다. 대부분의 에이전트와 MCP 클라이언트는 아직 "암흑기"에 머물러 있다. 프로토콜은 많이 발전했는데 클라이언트가 새 기능을 지원하지 않는다.
05

CLI가 에이전트와 잘 맞는 이유 07:10

사람들이 MCP와 비교하는 대상은 CLI command-line interface다. 터미널에서 명령어로 쓰는 프로그램이다. 발표자는 CLI가 앞의 해결책 두 가지를 처음부터 갖고 있다고 본다.

CLI가 기본으로 가진 것어떻게
점진적 탐색에이전트는 CLI의 명령 전체를 컨텍스트에 미리 넣지 않는다. 필요할 때만 부른다. 모르는 도구는 --help를 읽고 배운다
이미 아는 도구기본 리눅스 명령은 학습 데이터에서 오래 봐서 외우고 있다
code modeCLI를 돌리려면 샌드박스나 머신 같은 실행 환경이 있어야 한다. 거기서 실행하는 bash 명령도 코드다

CLI는 처음부터 code mode였다. MCP는 나중에야 그쪽으로 자라야 했다.

모델은 셸을 외우고 있다 08:30

Unix 계열 셸 shell은 1969년부터 있었다. Ken Thompson과 Dennis Ritchie가 만들었다.

발표에서는 두 사람이 1969년에 "Linux"를 만들었다고 말했다. 이때 만든 것은 Unix다. Linux는 1991년에 Linus Torvalds가 만들었다.

80열, 25행짜리 검은 터미널 화면은 컴퓨터에서 일어나는 일을 아주 압축해서 보여 준다. 40년 넘게 다듬어져 글자 하나하나가 중요한 정보만 전한다. 사람을 위해 다듬은 형식이지만 에이전트에게도 잘 맞는다.

  • 모델은 명령을 부르고 파이프 pipe로 잇는 법을 잘 안다. 학습 데이터에 셸이 아주 많기 때문이다.
  • AI 연구소는 셸 학습 데이터를 거의 무한히 합성할 수 있다. 명령을 이어 붙이고, 명령을 탐색하고, 매뉴얼 페이지에서 정보를 뽑으면 된다.
06

CLI의 약점: 원격 접근 09:30

CLI에도 약점이 있다. CLI는 로컬에서 도는 블랙박스다. 인증과 전송을 위한 표준 프로토콜이 없다.

  • 기업이 CLI 사용을 관측하려면 안을 직접 들여다봐야 한다. API를 쓰는지 웹소켓을 쓰는지 밖에서는 알 수 없다.
  • 자격 증명 credentials을 밖에서 넣어 줄 수도 없다.

그래서 발표자는 CLI는 로컬 인터페이스에 좋고, 원격 접근은 MCP가 낫다고 정리한다. "CLI 커넥터"를 쓰는 에이전트는 본 적이 없다고 했다. 원격 서비스를 붙이는 커넥터는 MCP다. 10:00

MCPCLI
강한 곳표준 원격 접근, 인증, 세션점진적 탐색과 코드 실행이 기본이다. 모델이 이미 잘 안다
약한 곳순진한 클라이언트는 도구를 한꺼번에 올린다. 새 기능을 지원하는 클라이언트가 적다표준 인증과 전송이 없는 블랙박스다. 기업이 관측하고 통제하기 어렵다
맞는 자리원격 서비스 연결에이전트 쪽 로컬 인터페이스

→
원격 쪽 · MCP표준 프로토콜로 서버와 통신한다세션, 인증, 비동기 작업 같은 MCP 기능 전부

이렇게 하면 MCP의 모든 기능을 에이전트가 이미 아는 도구 하나로 쓸 수 있다. 그 도구는 bash다. MCP의 복잡함은 bash 호출 하나 뒤에 숨는다. 에이전트는 세션, 인가, OAuth를 신경 쓰지 않아도 된다.

08

mcpc: MCP용 CLI 10:40

이 제안을 구현한 것이 Apify의 mcpc다. MCP 서버에 붙는 범용 CLI 클라이언트다.

  • 작년 12월 취미 프로젝트로 시작했다.
  • 발표자는 지금 나온 MCP CLI 클라이언트 중 기능이 가장 많을 것이라고 말한다.
  • npm이나 Bun으로 설치한다.

발표자는 Apify의 창업자이고 mcpc는 Apify가 만든 도구다. "기능이 가장 많다"는 말과 뒤의 비교 결과는 그 점을 감안해 읽자.

발표자는 터미널에서 mcpc를 직접 돌려 보였다. 대부분의 MCP 클라이언트가 아직 지원하지 않는 기능이 여럿 나온다.

12:40로컬 서버 연결stdio로 내 컴퓨터의 로컬 프로세스에 붙는다. 파일 시스템 서버(fs)에 연결하자 서버 이름, 프로토콜, 기능, 도구, 명령이 바로 보였다. 도구 목록은 JSON으로도 받는다
13:10원격 서버 로그인Apify MCP 서버에 로그인하면 브라우저가 열려 인증한다. 자격 증명은 OS 키체인에 안전하게 저장된다
14:00서버 안내문MCP에는 서버가 자기 역할을 설명하는 instructions가 있다. 대부분의 클라이언트는 이 기본 기능도 지원하지 않는다. mcpc는 보여 준다
14:10세션 유지열어 둔 MCP 세션 3개가 그대로 살아 있었다. 한 번 설정하면 Claude Code나 Codex가 같은 설정을 함께 쓴다
14:40grep으로 도구 찾기점진적 탐색 기능이다. "find"로 찾자 fs 서버에서 3개, Apify 서버에서 4개 도구가 나왔다
15:10비동기 작업Apify의 웹 검색 도구 RAG Web Browser를 작업(task)으로 실행했다. 서버에서 도는 동안 로컬에서 다른 일을 한다. 진행 상황을 보다가 결과를 나중에 받거나, 떼어 놓고(detach) 다른 일로 넘어간다
16:10JSON 파이프--json 출력을 파이프로 이어 셸 스크립트를 만든다. MCP 서버를 백그라운드에서 돌리므로 컨텍스트 토큰을 쓰지 않는다
16:20x402 지원로컬 지갑을 관리하는 도구가 드물어서 넣었다. 샌드박스용 프록시 같은 명령도 있지만 발표에서 자세히 다루지 않았다
10

연결 방식끼리 비교하기 16:50

보통 벤치마크는 에이전트끼리 비교한다. 예를 들어 Terminal-Bench는 Codex와 Claude Code 중 어느 쪽이 나은지 본다.

Apify는 이를 뒤집었다. 에이전트는 그대로 두고 도구를 붙이는 방식만 바꿔 비교하는 평가 틀을 만들었다. 이름은 connector evals다. CLI, MCP, mcpc 중 무엇이 더 효과적인지 본다.

결과 17:20

모든 테스트는 Claude Code와 Sonnet 5로 돌렸다. 그래프의 가로축은 작업을 끝내는 데 걸린 시간, 세로축은 토큰 비용이다.

  • 테스트 1: mcpc와 CLI의 성적이 비슷했다. MCP를 그대로 붙인 방식(raw MCP)은 더 빨리 끝났지만 토큰을 더 썼다.
  • 테스트 2: mcpc와 CLI가 비슷했다. raw MCP는 더 나빴다.
  • 테스트 3: 비슷한 결과가 나왔다.

발표자는 아직 초기 결과라고 밝혔다. 직접 확인하고 기여해 달라고 했다.

발표에서 그래프의 구체적 수치는 읽어 주지 않아 차트로 옮기지 않았다. 이 평가는 mcpc를 만든 Apify가 직접 만들고 돌린 것이다. 결과는 그 점을 감안해 읽자.

11

결론 18:10

발표자는 "CLI가 MCP보다 낫다"는 말을 그만하자며 발표를 마친다.

MCP와 CLI를 함께 쓰는 것이 가장 좋다.발표자의 마지막 말을 옮김
  • MCP가 받는 비판 대부분은 프로토콜이 아니라 순진한 하네스와 클라이언트를 향한 것이다.
  • CLI의 강점은 에이전트 쪽에 있다. 필요할 때만 부르고, 코드로 실행하고, 모델이 이미 잘 안다.
  • MCP의 강점은 원격 쪽에 있다. 표준 인증, 세션, 비동기 작업을 제공한다.
  • 그래서 하나를 고르기보다 MCP를 CLI 뒤에 두고 함께 쓰는 쪽이 낫다.
12

핵심 정리

  1. MCP는 에이전트가 도구에 접근하는 표준이다. 크게 퍼진 만큼 "MCP는 끝났다"는 비판도 컸다.
  2. 핵심 비판은 컨텍스트 낭비다. 원인은 도구를 전부 미리 올리고 결과를 계속 쌓는 순진한 하네스다.
  3. MCP 명세는 하네스 설계를 정하지 않는다. MCP를 효율적으로 쓰는 건 에이전트를 만드는 쪽의 일이다.
  4. 서브에이전트는 문제를 미룰 뿐이다. 토큰 비용과 민감한 값 노출이 그대로 남는다.
  5. 점진적 도구 탐색은 필요한 도구만 그때 올린다. code mode는 도구를 코드로 다룬다.
  6. 모델은 도구 호출보다 코드 작성을 잘한다. 도구 호출은 실제 데이터에 거의 없는 인위적 형식이다.
  7. CLI는 점진적 탐색과 code mode를 처음부터 갖고 있다. 모델은 셸을 외우고 있다.
  8. CLI는 표준 인증과 전송이 없어 원격 접근에 약하다. 원격 연결은 MCP가 낫다.
  9. 제안: 원격은 MCP, 로컬 인터페이스는 CLI. mcpc는 MCP 전체를 bash 호출 뒤에 숨긴다.
  10. Apify 자체 평가에서 mcpc는 CLI와 비슷했고 raw MCP는 토큰을 더 썼다. 결론은 MCP + CLI다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1MCP는 무엇을 위한 표준인가?
에이전트가 도구와 리소스에 안전하게 접근하는 방법을 정한 표준이다. 에이전트와 도구 사이의 연결 규격이다.
Q2MCP를 향한 가장 흔한 비판과, 발표자가 보는 실제 원인은?
컨텍스트를 너무 많이 먹는다는 비판이다. 원인은 하네스가 도구를 전부 미리 등록하고 도구 결과를 계속 쌓는 순진한 구현이다. MCP 명세는 하네스 설계를 정하지 않는다.
Q3MCP 서버 10개에 도구가 10개씩이면 어떤 일이 생기나?
질문을 하기도 전에 도구 100개가 컨텍스트에 올라간다. 발표자는 이때 컨텍스트의 3분의 1 정도가 사라질 수 있다고 했다. 실제로 필요한 도구는 보통 한두 개다.
Q4서브에이전트로 컨텍스트를 나눠도 남는 문제 두 가지는?
토큰 비용은 그대로 낸다. 비밀번호 같은 민감한 값이나 큰 데이터가 여전히 컨텍스트를 거쳐 남는다.
Q5점진적 도구 탐색은 어떻게 동작하나?
다른 도구를 찾아 주는 도구(tool search tool)로 필요한 도구를 찾는다. 찾은 도구만 그때 컨텍스트에 올린다.
Q6code mode가 효과적인 이유는?
모델은 코드를 쓰고 탐색하는 데 강하다. 반면 도구 호출은 실제 데이터에 거의 없는 인위적 형식이라 합성 데이터로 가르쳐야 한다.
Q7CLI가 처음부터 갖고 있는 두 가지 장점은?
점진적 탐색과 code mode다. 필요할 때만 부르고 모르면 --help로 배운다. 그리고 bash 명령 자체가 코드라서 코드로 실행된다.
Q8모델이 셸을 특히 잘 아는 이유는?
학습 데이터에 셸이 아주 많다. 게다가 AI 연구소는 명령을 잇고 매뉴얼을 읽는 식으로 셸 학습 데이터를 거의 무한히 합성할 수 있다.
Q9CLI가 원격 접근에 약한 이유는?
표준 인증과 전송 프로토콜이 없는 로컬 블랙박스다. 기업이 안을 들여다보거나 자격 증명을 밖에서 넣어 주기 어렵다.
Q10발표자가 제안하는 역할 분담은?
원격 접근은 MCP, 에이전트가 쓰는 로컬 인터페이스는 CLI다. MCP의 복잡함을 에이전트가 이미 아는 bash 호출 하나 뒤에 숨긴다.
Q11mcpc의 --json 옵션은 무슨 일을 하나?
MCP 명세를 따르는 순수 JSON을 돌려준다. jq와 파이프로 여러 도구 호출을 셸 스크립트로 묶을 수 있어 컨텍스트 토큰을 아낀다.
Q12connector evals는 보통 벤치마크와 무엇이 다르고, 결과는 어땠나?
에이전트 대신 연결 방식을 비교한다. mcpc와 CLI는 비슷했고, raw MCP는 토큰을 더 썼다. 첫 테스트에서는 raw MCP가 더 빨리 끝났다. Apify가 직접 만든 초기 평가라는 점을 감안해야 한다.
