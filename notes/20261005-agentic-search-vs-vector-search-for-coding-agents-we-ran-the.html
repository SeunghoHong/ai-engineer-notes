코딩 에이전트의 코드 검색, 벡터와 에이전틱 중 무엇이 나은가

평가eval는 AI 시스템에 대한 질문에 데이터로 답하는 방법이다. 발표자는 평가의 네 요소를 설명한 뒤, 코딩 에이전트가 버그 위치를 찾을 때 벡터 검색과 에이전틱 검색 중 무엇이 나은지 직접 평가한 과정을 처음부터 끝까지 보여 준다. 결과는 정확도는 같고 벡터 검색이 4배 더 비쌌다.

원본 영상: Agentic Search vs Vector Search for Coding Agents: We Ran the Eval 발표: Jess (Braintrust 개발자 관계 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. "써 봤는데 괜찮더라"로 출시하면 감으로 결정하는 것이다. "200개 케이스 중 94% 통과"처럼 숫자로 말할 수 있어야 한다.
  2. 평가는 데이터셋, 태스크, 채점, 실험 네 요소로 이뤄진다. 셋 중 하나를 바꾸면 새 실험이 된다.
  3. 운영 로그에서 데이터셋을 뽑고, 평가로 배운 것을 코드에 반영하고, 다시 로그로 확인하는 순환이 기본 흐름이다.
  4. 실제 사례: Microsoft의 TypeScript Go 저장소에서 "fix" PR 약 20개를 모아, 버그가 있던 커밋에서 에이전트가 문제 위치를 찾게 했다.
  5. 두 방식 모두 Claude Code 하네스로 돌렸다. 벡터 검색 쪽은 프롬프트 지시만으로는 부족해서 도구 금지 플래그까지 써야 했다.
  6. 결과: 정확도는 같았고 벡터 검색이 4배 더 비쌌다. 벡터 검색은 코드 조각은 잘 찾지만 import와 호출 관계 같은 "연결 조직"을 놓쳐 검색을 반복했다.
  7. 발표자 스스로 밝힌 한계: 시도 1회, 약한 벡터 검색 구현, 작은 데이터셋. 목적은 최고의 평가가 아니라 평가를 처음부터 끝까지 만드는 법을 보여 주는 것이다.
01

감이 아니라 숫자로 출시한다 00:50

발표자는 고객과 통화하다 이런 말을 자주 들었다. "엔지니어링 팀이 준비됐다고 해서 출시했다." "PM이 프롬프트 몇 개를 써 봤는데 괜찮았다." 둘 다 감으로 출시를 결정한 것이다.

듣고 싶지 않은 말"몇 번 써 봤는데 괜찮았다"근거가 사람의 인상이다
→
듣고 싶은 말"200개 케이스 중 94%가 통과했다""정확도는 5% 올랐지만 말투 점수는 5% 떨어졌다"처럼 세부까지 말할 수 있다

200개와 94%는 발표자가 든 예시 숫자다. 실제 측정값이 아니다.

02

평가는 질문에 답하는 도구다 01:30

발표자는 평가eval를 한 문장으로 정의한다. "AI 시스템에 대한 질문에 답하는 방법"이다. 평가로 답할 수 있는 질문은 이런 것들이다.

  • 모델 선택: 새 모델이 계속 나오는데, 우리 용도에는 어느 모델이 맞나.
  • 다양한 상황: 영어 입력은 잘 되는데 일본어는 어떤가. Python은 잘 되는데 TypeScript는 어떤가.
  • 비용 효율: 비용을 크게 늘리지 않고 성능을 유지하려면 어떻게 하나.
  • 브랜드 일관성: 회사의 말투와 기준을 꾸준히 지키나.
  • 피드백: 사용자에게서 배워 계속 좋아지고 있나.
  • 회귀 감지: 무언가 깨지거나 나빠졌을 때 어떻게 알아채나.
회귀 감지의 예: OpenAI의 아첨 모델 02:20 발표자가 든 사례다. 2025년 4월 OpenAI가 모델을 더 도움이 되게 바꾸려 업데이트했는데, 결과적으로 사용자에게 지나치게 동조하는 아첨sycophancy 성향이 생겨 덜 진실해졌다. AI 시스템은 복잡하고 결정적이지 않아서, 이런 변화를 잡아내려면 평가 체계가 미리 있어야 한다.
03

평가의 네 요소 03:00

요소무엇인가보통 들어가는 것
데이터셋 datasetAI 시스템에 넣을 입력 모음정답이 분명한 황금 케이스, 경계 케이스, 알려진 실패 유형
태스크 task입력을 받아 출력을 내는 방식의 정의시스템 프롬프트, 실행에 쓸 모델
채점 scoring출력이 좋은지 나쁜지 판정하는 기준결정적 채점, LLM 심판, 사람 검토. 기준은 보통 PM이나 엔지니어가 쓴다
실험 experiment데이터셋·태스크·채점의 한 조합을 돌린 결과셋 중 하나를 바꾸면 새 실험이다. 발표자는 이 단계가 가장 재미있다고 말한다

가설을 세우고 데이터셋이나 프롬프트나 채점 기준을 조금씩 바꾸면 실험이 여러 개 쌓인다. 그다음 실험끼리 비교해 무엇이 좋아졌고 무엇이 나빠졌는지 본다.

04

실험을 비교하고 흔적을 읽는다 04:30

실험 1과 실험 2를 나란히 놓으면 개선과 회귀가 보인다. 행 하나를 눌러 어느 테스트 케이스가 바뀌었는지도 볼 수 있다. 발표자는 Braintrust 화면으로 이를 보여 줬다.

  • 자연어로 질문하기: "실험을 요약해 줘", "이 실험들의 문제를 짚어 줘", "어느 실험이 가장 잘했나"처럼 트레이스와 실험 전체에 물을 수 있다.
  • 긴 대화에서 유용: 여러 턴이 오가는 대화의 트레이스에서는 환각이나 주제 이탈을 사람이 눈으로 잡기 어렵다. 이런 패턴을 찾는 데 쓴다.
  • 화면 밖에서도: 같은 일을 CLI와 MCP 서버로도 할 수 있다.
  • 관측observability: SDK로 코드를 감싸면 운영 로그가 들어온다. 대시보드를 만들고 지켜보는 전통적인 모니터링도 된다.

발표자는 평가·관측 도구를 만드는 Braintrust 소속이다. 이 절은 자사 제품 소개이니 그 점을 감안해 읽자.

05

로그에서 평가로, 다시 배포로 06:00

발표자가 든 상황은 이렇다. 문서 사이트에 AI 챗봇을 어제 붙였다. 사용자가 문서에 대해 질문을 시작한다. 그다음은 이렇게 돈다.

  1. 앱에 사용자가 들어오면 운영 로그가 쌓인다.
  2. 로그에서 10~20행쯤 뽑아 데이터셋을 만든다.
  3. 데이터셋에 태스크와 채점을 붙여 평가를 돌린다. 데이터셋, 프롬프트, 채점 기준을 바꿔 여러 번 돌린다.
  4. 가장 잘 나온 실험에서 시스템에 대해 무언가를 배운다.
  5. 배운 것을 코드나 프롬프트에 반영해 다시 배포한다.
  6. 바뀐 동작이 다시 운영 로그에 나타난다. 처음으로 돌아간다.

07

실제 사례: 두 가지 코드 검색 08:40

Braintrust CEO Ankur는 가끔 X(옛 Twitter)에서 글을 보고 발표자에게 "이거 평가해 봐"라고 보낸다. 이번에는 Cursor가 올린 글이었다. Cursor는 검색 방식을 바꿔 코딩 에이전트 성능을 크게 올렸다고 했다. 이 주제로 온라인에서 논쟁이 많아서 평가해 볼 만했다.

자막에서 발표자는 Cursor의 방식을 "시맨틱 검색, 즉 에이전틱 검색"이라고 말했다. 보통 시맨틱 검색semantic search은 임베딩 기반의 벡터 검색을 가리키므로 말실수로 보인다(추정). 이 노트는 평가의 질문을 "Cursor가 내세운 임베딩 기반 검색이 정말 에이전틱 검색보다 나은가"로 읽는다.

벡터 검색 vector search 09:30

코드나 글을 임베딩embedding으로 바꾼다. 임베딩은 그 조각의 뜻을 숫자 벡터로 표현한 것이다.

  • 뜻이 가까우면 벡터도 가깝다. 늑대·개·고양이는 서로 가깝고, 바나나·사과와는 멀다.
  • 임베딩을 Qdrant나 Pinecone 같은 벡터 데이터베이스에 저장한다.
  • "데이터베이스 로직이 어디 있나"라고 물으면, "데이터베이스"나 "로직"과 뜻이 가장 가까운 코드 조각chunk들을 돌려준다.

한 줄로: 질문과 뜻이 비슷한 조각을 찾아 준다.

에이전틱 검색 agentic search 10:40

LLM에 grep, find, ls, cat 같은 셸 도구를 준다. 사람이 코드를 뒤지듯 코드베이스를 탐색한다.

  • 함수 이름을 찾는다.
  • 파일을 열어 읽는다.
  • 그 함수의 호출을 따라 다른 파일로 간다.
  • 필요한 것을 찾을 때까지 반복한다.

한 줄로: 사람처럼 따라가며 읽는다.

08

데이터셋: 버그가 있던 순간으로 되돌린다 11:20

평가의 첫 단계는 데이터셋이다. 발표자는 Microsoft가 공개한 TypeScript Go 저장소를 썼다.

  1. 머지된 PR 중 제목에 "fix"가 들어간 것을 모았다.
  2. 각 PR의 부모 커밋을 체크아웃했다. 아직 버그가 남아 있는 시점의 코드다.
  3. 버그 코드와 수정 코드의 diff를 Claude에 주고, 이슈 트래커에 올릴 법한 버그 티켓 글을 만들게 했다.
  4. 그 티켓을 에이전트에 주고, 벡터 검색 또는 에이전틱 검색으로 버그 로직이 있는 위치를 찾게 했다.

이렇게 모은 PR은 약 20개다. 정답(실제 수정 위치)이 PR 안에 이미 있으니, 사람이 라벨을 따로 붙일 필요가 없다.

09

태스크: 같은 하네스로 두 방식을 돌린다 12:20

태스크를 만들려면 두 검색 방식을 실제로 구현해야 했다. 난이도가 크게 달랐다.

에이전틱 검색: 쉬웠다

Claude Code는 기본이 에이전틱 검색이다. 과제를 주고 그냥 돌리면 된다.

벡터 검색: 손이 더 갔다

실험 조건을 맞추려고 벡터 검색도 Claude Code 하네스 안에서 돌렸다. 문제는 Claude Code가 자꾸 기본값인 에이전틱 검색으로 돌아가려 한다는 점이다. 두 가지를 했다.

  • 프롬프트에 "에이전틱 검색을 쓰지 말라"고 명시했다.
  • 도구 금지 플래그disallowed tools로 grep 같은 탐색 도구 호출 자체를 막았다.
프롬프트만으로는 절대 충분하지 않다 발표자의 말이다. 지시문에 적는 것과 실제로 못 하게 막는 것은 다르다. 모델 행동을 통제하려면 하네스 수준의 제약을 함께 걸어야 한다.
10

끊어진 트레이스를 잇는다 13:10

Claude Code 실행을 하위 프로세스subprocess로 띄웠더니 트레이스가 고아orphaned가 됐다. 상위 트레이스에는 "Claude 에이전트 실행"이라는 한 칸만 보이고, 그 안에서 무슨 일이 일어났는지는 전혀 보이지 않았다.

해결책은 부모 스팬 ID를 환경 변수로 하위 프로세스에 넘기는 것이었다. 그러면 하위 프로세스 안의 기록이 상위 트레이스에 붙는다.

수정 전"Claude 에이전트 실행" 한 줄안에서 무엇을 했는지 알 수 없다
→
수정 후모든 턴, 모든 LLM 호출, 모든 명령grep, bash, ls, find 호출이 하나씩 보인다

발표자는 이 수정이 중요했다고 말한다. 뒤에 나오는 "왜 이런 결과가 나왔나"를 따질 때 트레이스 안이 보여야 디버깅이 된다.

11

채점과 결과: 정확도는 같고 비용은 4배 14:40

채점은 단순했다. 에이전트가 고친 결과가 TypeScript Go 저장소의 테스트 스위트를 통과하면 100점, 실패하면 0점이다. 중간은 없다.

결과를 요약하면 두 방식의 정확도는 같았다. 그런데 벡터 검색이 에이전틱 검색보다 4배 비쌌다.

12

트레이스에서 배운 세 가지 15:20

숫자만 보면 끝이 아니다. 발표자는 트레이스를 하나씩 손으로 읽으며 왜 이런 차이가 났는지 찾았다.

  1. 벡터 검색의 조각에는 맥락이 빠진다. 돌려받은 코드 조각에는 import, 도구 호출, 바로 위의 호출 코드가 자주 없다. 그래서 에이전트가 버그를 어떻게 고쳐야 할지 판단할 재료가 모자란다. 한 행에서는 벡터 검색 에이전트가 26번 검색하고도 함수 세 개가 파일 안에서 어떻게 엮이는지 끝내 맞추지 못했다.
  2. 에이전틱 검색은 연결을 따라간다. 함수 이름을 grep하고, 함수 전체를 읽고, 로직의 결함을 보고, 호출하는 쪽을 따라 다른 파일로 넘어갔다. 발표자의 표현을 빌리면 벡터 검색은 정답 코드에 가까이 데려다 주지만, 에이전틱 검색은 조각들을 잇는 연결 조직을 갖고 있었다.
  3. 비용 차이의 원인은 검색 횟수다. 벡터 검색은 조각을 받고, 부족해서 다시 검색하고, 또 조각을 받는 식으로 반복했다. 그때마다 LLM 호출이 쌓여 비용이 커졌다.
벡터 검색은 정답 코드에 가까이 가게 해 줬지만, 에이전틱 검색은 그 조각들의 로직을 잇는 연결 조직을 갖고 있었다.발표자의 표현을 옮김, 16:10
13

이 평가의 빈틈 16:50

발표자는 "이 평가에 구멍이 많다고 생각할 텐데, 맞는 지적이다"라고 먼저 말했다. 스스로 꼽은 한계는 세 가지다.

  • 시도가 1회였다. LLM은 같은 입력에도 결과가 달라진다. 과제마다 여러 번 돌려야 점수를 믿을 수 있다.
  • 벡터 검색 구현이 약했다. 더 잘 만들 수 있었다. 결과가 벡터 검색 자체의 한계인지 구현의 한계인지 가르기 어렵다.
  • 데이터셋이 작았다. 약 20행이고 저장소도 하나다. 다른 저장소로 넓혀야 한다.
결론을 어디까지 믿을까 "벡터 검색이 정확도는 같고 4배 비싸다"는 이 조건에서 나온 한 번의 결과다. 저장소 하나, 약 20개 과제, 시도 1회, 발표자가 약하다고 인정한 벡터 검색 구현이다. 일반화된 결론으로 받기보다 "이렇게 평가를 짠다"는 본보기로 읽는 것이 맞다. 발표자도 목적은 최고의 평가가 아니라 평가를 끝까지 만드는 과정을 보여 주는 것이라고 했다.
14

핵심 정리

  1. "써 봤는데 괜찮다"는 감이다. 출시 결정은 "N개 중 몇 % 통과"처럼 숫자로 말한다.
  2. 평가는 AI 시스템에 대한 질문에 답하는 방법이다. 모델 선택, 비용, 다양한 상황, 회귀 감지가 대표 질문이다.
  3. 평가의 네 요소는 데이터셋, 태스크, 채점, 실험이다. 앞의 셋 중 하나를 바꾸면 새 실험이다.
  4. 기본 흐름은 운영 로그 → 데이터셋 → 평가 → 코드 반영 → 배포 → 다시 로그의 순환이다.
  5. 평가는 팀 스포츠다. PM이 성공의 가설을 세우고, 도메인 전문가가 정답 기준을 주고, 엔지니어가 데이터를 넣는다.
  6. 데이터셋은 "fix" PR의 부모 커밋으로 만들었다. 정답이 PR 안에 있어 라벨링이 공짜다.
  7. 두 방식을 같은 하네스에서 돌려 조건을 맞췄다. 벡터 검색은 프롬프트 지시만으로 부족해 도구 금지 플래그가 필요했다.
  8. 하위 프로세스의 트레이스는 끊어진다. 부모 스팬 ID를 환경 변수로 넘겨 이어야 안에서 무슨 일이 있었는지 볼 수 있다.
  9. 결과는 정확도 같음, 벡터 검색 비용 4배. 원인은 조각에 import와 호출 관계가 빠져 검색을 반복한 것이다.
  10. 한계는 시도 1회, 약한 벡터 구현, 저장소 하나에 약 20행. 결론보다 평가를 끝까지 만드는 과정을 배운다.
15

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 "듣고 싶지 않은 말"과 "듣고 싶은 말"로 든 예는?
듣고 싶지 않은 말은 "엔지니어링 팀이 준비됐다고 했다", "PM이 몇 개 써 봤는데 괜찮았다". 듣고 싶은 말은 "200개 케이스 중 94% 통과", "정확도 5% 상승, 말투 5% 하락"처럼 숫자로 말하는 것.
Q2평가의 네 요소는 무엇이고, 실험은 어떻게 정의되나?
데이터셋, 태스크, 채점, 실험. 특정 데이터셋·태스크·채점의 한 조합을 돌린 것이 실험 하나다. 셋 중 하나를 바꾸면 새 실험이 된다.
Q3태스크에는 구체적으로 무엇이 들어가나?
시스템 프롬프트와 실행에 쓸 모델. 입력을 받아 출력을 내는 방식을 정의한다.
Q4운영 로그에서 평가로 이어지는 순환의 단계는?
앱 → 운영 로그 → 로그 10~20행으로 데이터셋 → 평가 여러 번 → 배운 것을 코드에 반영 → 배포 → 다시 운영 로그.
Q5평가에서 PM과 도메인 전문가는 각각 무엇을 맡나?
PM은 "성공이 무엇인가"라는 가설을 세우고 프롬프트를 다듬는다. 도메인 전문가는 보험·의료·법률처럼 전문 분야에서 라벨을 붙이고 잘한 답의 기준을 준다.
Q6벡터 검색과 에이전틱 검색의 동작 차이를 한 문장씩 말하면?
벡터 검색은 코드를 임베딩으로 바꿔 두고 질문과 뜻이 가까운 조각을 돌려준다. 에이전틱 검색은 LLM이 grep·cat 같은 도구로 사람처럼 파일을 열고 호출을 따라가며 찾는다.
Q7데이터셋을 만들 때 왜 PR의 부모 커밋을 체크아웃했나?
부모 커밋은 아직 버그가 남아 있는 시점이다. 그 상태에서 에이전트에게 버그 위치를 찾게 해야 평가가 된다. diff로 버그 티켓 글을 만들었고, 정답은 PR의 수정 내용이다.
Q8벡터 검색을 Claude Code 하네스에서 돌릴 때 프롬프트 외에 무엇이 더 필요했나?
도구 금지 플래그. Claude Code가 기본값인 에이전틱 검색으로 돌아가지 않도록 grep 같은 탐색 도구 호출 자체를 막아야 했다. "프롬프트만으로는 절대 충분하지 않다."
Q9하위 프로세스의 트레이스가 끊어진 문제를 어떻게 풀었나?
부모 스팬 ID를 환경 변수로 하위 프로세스에 넘겼다. 그 결과 모든 턴, LLM 호출, 터미널 명령이 상위 트레이스 안에 보이게 됐다.
Q10결과는 어땠고, 비용 차이의 원인은 무엇이었나?
정확도는 같았고 벡터 검색이 4배 비쌌다. 벡터 검색의 조각에는 import와 호출 코드가 빠져 있어 검색을 반복했고, 그때마다 LLM 호출이 쌓였다. 한 행에서는 26번 검색하고도 함수 세 개의 관계를 못 맞췄다.
Q11발표자가 스스로 꼽은 이 평가의 한계 세 가지는?
시도가 1회였다(여러 번 돌려야 한다). 벡터 검색 구현이 약했다. 데이터셋이 저장소 하나에 약 20행으로 작았다.

용어 정리

용어뜻
평가 (eval)AI 시스템의 출력 품질을 재는 테스트 묶음. 발표자의 정의는 "AI 시스템에 대한 질문에 답하는 방법"
데이터셋평가에 넣을 입력 모음. 황금 케이스, 경계 케이스, 실패 유형을 담는다
태스크입력을 받아 출력을 내는 방식의 정의. 시스템 프롬프트와 모델
채점 (scoring)출력이 좋은지 나쁜지 판정하는 기준과 방법
결정적 채점Deterministic scoring. 같은 입력에 항상 같은 점수가 나오는 규칙 기반 채점. 예: 테스트 통과 여부
LLM 심판LLM-as-a-judge. 다른 LLM이 출력을 읽고 점수를 매기는 채점
사람 검토Human in review. 사람이 직접 출력을 보고 채점
실험데이터셋·태스크·채점의 한 조합을 실행한 결과
회귀변경 뒤에 원래 잘 되던 것이 나빠지는 것
아첨 (sycophancy)모델이 사용자에게 지나치게 동조해 사실보다 듣기 좋은 말을 하는 성향
임베딩글이나 코드 조각의 뜻을 숫자 벡터로 표현한 것. 뜻이 비슷하면 벡터도 가깝다
벡터 데이터베이스임베딩을 저장하고 가까운 것을 빨리 찾아 주는 저장소. 예: Qdrant, Pinecone
벡터 검색 / RAG 검색질문을 임베딩으로 바꿔 뜻이 가까운 조각을 찾는 검색. 발표자는 RAG 검색이라고도 불렀다
에이전틱 검색LLM이 grep, find, ls, cat 같은 도구로 파일을 열고 호출을 따라가며 찾는 검색
조각 (chunk)임베딩을 만들기 위해 코드나 글을 잘라 놓은 단위
하네스모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀. 발표에서는 Claude Code
도구 금지 플래그하네스가 특정 도구를 호출하지 못하게 막는 설정. 프롬프트 지시보다 강하다
부모 커밋어떤 커밋 바로 앞의 커밋. "fix" PR의 부모 커밋은 버그가 아직 남아 있는 상태다
트레이스 / 스팬Trace는 한 실행의 전체 기록, span은 그 안의 한 단계. 스팬에 부모 ID를 주면 계층이 이어진다
고아 트레이스Orphaned trace. 부모와 연결이 끊어져 상위 기록에서 안이 보이지 않는 트레이스
하위 프로세스Subprocess. 프로그램이 별도로 띄운 다른 프로그램 실행
관측 (observability)운영 중 시스템의 로그와 지표를 모아 상태를 지켜보는 것
시도 (trial)같은 과제를 한 번 실행하는 것. LLM은 결과가 흔들려 여러 시도가 필요하다
