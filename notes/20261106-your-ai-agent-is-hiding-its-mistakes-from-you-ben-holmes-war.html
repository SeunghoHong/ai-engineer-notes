에이전트가 숨긴 실수를 찾아 고치는 루프

에이전트는 막히면 알아서 돌아가고, 끝에 "됐다"고만 말한다. 그 숨은 실패를 찾으려면 지난 대화를 모아 채점하고, 실패만 모아 스킬과 설정을 고치는 루프를 돌려야 한다.

원본 영상: Your AI Agent Is Hiding Its Mistakes From You 발표: Ben Holmes (Warp DevEx 엔지니어링 리드)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 고쳤고, 확실하지 않은 것은 "(추정)"을 붙였다. 화면의 슬라이드와 데모는 자막에 없어서, 발표자가 말로 설명한 부분만 담았다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트는 막히면 혼자 우회하고 성공했다고만 보고한다. 낡은 지시와 실패한 도구 호출은 대화 기록 속에 묻힌다.
  2. 해법은 자기 개선 루프다. 대화를 모으고, 채점하고, 실패를 모으고, 개선을 제안하고, 다시 채점한다.
  3. 모을 것은 세 가지다. 대화 원문, 도구 호출, 결과물(diff나 PR).
  4. 채점은 LLM 심판이 루브릭(채점표)으로 한다. 발표의 예시 기준은 불필요한 테스트, 장황함, 효율이다.
  5. 루브릭은 마크다운 몇 줄과 통과선이면 시작할 수 있다.
  6. PR이 머지되면 채점하고, 24시간마다 실패만 모아 개선 에이전트에게 넘긴다. 개선 에이전트는 스킬과 설정 변경을 PR로 제안한다.
  7. 점수를 시간 순으로 그려 두면 어떤 변경이 효과가 있었는지 증거가 생긴다. 메모리 방식에는 이 부분이 보이지 않는다.
01

소프트웨어 팩토리란 01:00

소프트웨어 팩토리 software factory는 소프트웨어 개발 과정 전체를 자동화한 것이다. 여러 에이전트가 일을 나눠 맡고 다음 에이전트에게 넘기는 조립 라인으로 그리기도 하고, 계속 도는 바퀴로 그리기도 한다.

  1. 할 일을 모아 둔 곳에서 출발한다. 작업 보드일 수도 있고 Slack 메시지일 수도 있다.
  2. 에이전트가 조사하고 분류한다 triage.
  3. 사람과 함께 스펙을 쓴다.
  4. 에이전트가 구현한다.
  5. 컴퓨터 사용 computer use 기능으로 스크린샷과 녹화를 남겨, 사람이 보기 좋은 PR을 만든다.
  6. 에이전트끼리 서로의 허점을 찾는 적대적 코드 리뷰 adversarial code review를 몇 번 거친다.
  7. 에이전트가 배포된 시스템을 지켜보고, 다시 1로 돌아간다.
바퀴를 돌리는 일

에이전트가 작업을 받아 PR까지 만든다.

바퀴를 고치는 일 01:50

에이전트를 움직이는 시스템 자체를 개선한다. 메타 엔지니어링, 가드닝이라고도 부르고, Warp는 팩토리 엔지니어링 factory engineering이라 부른다.

고칠 대상은 여러 가지다. 에이전트가 읽는 스킬, 코드 구조, 에이전트가 코드베이스의 맞는 곳을 건드리는지 보는 정적 분석(SonarQube 같은 도구)이 있다. 이 발표는 그중 스킬과 설정을 고치는 루프만 다룬다. 02:30

02

자기 개선 루프 02:40

자기 개선 에이전트 self-improving agent는 자기가 해 온 일을 돌아보고, 자기 설정을 어떻게 고칠지 스스로 찾는다. 루프는 다섯 단계다.

단계하는 일
1. 모으기팀 전체의 에이전트 대화를 한곳에 모은다
2. 채점하기채점 에이전트가 팀이 정한 기준(효율, 코드 품질, 테스트 커버리지 등)으로 대화마다 점수를 매긴다
3. 실패 찾기많은 대화를 채점한 뒤, 실패만 골라 왜 실패했는지 찾는다
4. 개선 제안cron으로 정해진 시각에 깨어난 에이전트가 스킬과 설정 변경을 제안한다
5. 다시 채점변경 뒤에 점수가 어떻게 바뀌는지 계속 본다

2단계의 채점 방식을 LLM 심판 LLM as a judge이라 한다. 언어 모델에게 루브릭(채점표)을 주고 대화를 평가하게 하는 방식이다.

03

1단계: 대화를 한곳에 모은다 03:20

에이전트가 팀 전체의 작업을 보고 판단하려면, 먼저 모든 대화가 한곳에 있어야 한다.

혼자 쓸 때 03:30

Claude Code, Codex, Pi(추정) 같은 로컬 에이전트는 대화를 내 컴퓨터에 파일로 남긴다. Claude Code는 .claude 폴더, Codex는 .codex 폴더에 쌓인다. 내 설정만 다듬을 거라면 이것으로 충분하다.

팀으로 쓸 때 03:50

  • 직접 모으기: 발표자가 만난 어떤 팀은 팀원 모두의 .claude 폴더를 압축해 공유 S3 버킷에 올리는 자동화를 만들었다.
  • 공용 컴퓨터에서 돌리기 04:10: 에이전트가 각자의 노트북이 아니라 팀이 함께 쓰는 컴퓨터에서 돌면, 대화가 저절로 한곳에 쌓인다. 오래 켜 두는 OpenClaw 인스턴스일 수도 있고, 작업마다 새로 뜨는 격리된 샌드박스일 수도 있다. Warp Factories는 작업마다 Docker 샌드박스를 띄운다.

무엇을 남기나 05:10

사람과 에이전트가 주고받은 말만으로는 부족하다. 세 가지를 모두 남긴다.

대화 원문 · transcript

사람이 보낸 말과 에이전트가 돌려준 말.

도구 호출 · tool calls

파일 시스템 접근, MCP 호출처럼 에이전트가 바깥과 닿은 모든 기록. 에이전트가 실제로 무엇을 했는지 보여 준다.

결과물 · output

대화 속 코드 diff, 또는 커밋을 고정해 확인한 실제 PR. 품질을 채점할 대상이다.

도구 호출이 빠지면 다음 절의 효율 채점을 할 수 없다. 에이전트의 헛걸음은 대화 원문이 아니라 도구 호출에 남기 때문이다.

04

2단계: 무엇을 채점할까 06:00

채점기 scorer는 대화 하나를 기준 하나로 평가한다. 발표자는 팀이 자주 겪는 불만에서 기준을 고르라며 세 가지 예를 든다.

불필요한 테스트 06:10

발표자가 청중에게 "에이전트가 테스트를 너무 많이 쓴다고 느끼는 사람?" 하고 손을 들게 했다.

결과는 모델과 지시에 따라 달라진다. 팀마다 E2E 테스트, 통합 테스트, 단위 테스트를 얼마나 둘지 생각도 다르다. 그래서 불필요한 테스트 redundant test 채점기를 두고, 대화마다 에이전트가 테스트를 지나치게 썼는지 본다.

장황함 07:00

두 번째 질문은 "에이전트가 주석을 너무 많이 쓴다고 느끼는 사람?"이었다. 발표자는 어느 모델 이야기인지 짐작이 간다며 이름은 밝히지 않았다.

이건 보기 싫어서만의 문제가 아니다. 지금 가장 큰 병목은 코드 리뷰다. 에이전트가 변경을 요약한 글과 코드에 남긴 주석이 리뷰 속도를 좌우한다. 그래서 대화에서든 코드에서든 말이 지나치게 많은지 보는 장황함 verbosity 채점기를 둔다.

효율 07:50

세 번째는 에이전트가 해결책까지 곧장 갔는지, 제자리에서 헛돌았는지다. 이 채점에는 도구 호출 기록이 꼭 필요하다.

에이전트가 실수를 숨기는 방식 08:10 요즘 에이전트는 끈질기다. 막히면 알아서 돌아가는 길을 찾고, 그 사실을 말하지 않는다. 끝에 "됐다"고만 보고한다. 사람 없이 오래 돌리거나 클라우드 샌드박스에서 돌리면 대화를 지켜보는 사람이 없어서, 실패한 도구 호출을 놓치기 쉽다.

발표자 팀이 실제로 겪은 일이다. 08:20

  1. 테스트 하네스용 스킬에 낡은 지시가 많았다.
  2. 에이전트는 지시대로 안 되자 포트 번호를 여기저기 찔러 보며 환경을 스스로 알아냈다.
  3. 그다음에야 코드를 쓰기 시작했고, 이 과정을 팀에 알리지 않았다.
  4. 팀이 아는 건 "생각보다 2분쯤 더 걸린다"뿐이었다.

겉으로는 사소한 지연인데, 속에는 고칠 거리가 많았다. 효율 채점기는 도구 호출을 훑어 이런 헛걸음을 잡아낸다.

05

루브릭 쓰는 법 08:50

채점기는 그냥 마크다운 파일이다. Warp에서는 스킬 정의와 비슷한 모양으로, LLM 심판에게 무엇을 어떻게 채점할지 알려 준다.

들어가는 것뜻발표에서 읽은 효율 채점기 내용
채점 대상이 채점기가 무엇을 보는가결과를 향해 일했는가, 아니면 중복 단계와 불필요한 주고받기에 힘을 낭비했는가
라벨점수마다 성공과 실패가 어떤 모습인지 09:20목록의 중간이 통과선이다. 0.4나 0.2면 실패다 10:00
정의기준의 세부 항목 10:10"cost human"(추정: 사람에게 드는 비용), 정보 수집 단계, 반복 단계의 오버헤드 routine step overhead

발표자는 고등학교 에세이 채점표에 빗댄다. "정확히 다섯 문단이고, 수동태 없이 능동태만 쓰면 잘 쓴 글" 같은 식이다. 효율처럼 꽤 분명하게 정의할 수 있는 기준은, 이렇게 채점표로 에이전트를 시험하는 게 여전히 쓸모 있다.

통과선 아래로 떨어진 대화는 무언가 잘못된 대화이니 들여다본다. 통과한 대화는 대체로 괜찮았으니 더 볼 필요가 없다.

짧게 시작해서 쓰면서 키운다. Warp가 주는 템플릿이 있지만, 글머리 기호 몇 줄과 채점표만으로도 시작할 수 있다. 발표자 말로는 "과학보다는 기예(art)에 가깝다".

06

3단계: 대화마다 채점한다 10:40

채점기가 준비되면 에이전트가 대화를 채점한다.

  • 대화 하나에 채점 에이전트를 한 번 돌린다. 11:00
  • 모든 대화를 채점해도 되고, 토큰을 아끼려고 무작위로 골라 채점해도 된다.
  • 보통 PR이 머지되면 채점이 자동으로 시작된다. 12:20

예: 인증 서비스 구현 대화 11:30

에이전트가 풀스택으로 인증 서비스(자막의 "off service", auth service로 추정)를 구현했고, PR이 머지됐다고 하자. 채점 에이전트가 기준마다 이렇게 판정한다.

기준판정이유
테스트실패팀 가이드는 E2E 테스트를 주로 쓰라고 하는데, 인증 서비스에 단위 테스트를 잔뜩 썼다
장황함통과코드 주석을 거의 안 쓰는 새 모델을 썼다. PR을 이해하기 쉬웠다
효율실패이 변경을 어떻게 테스트할지 알아내려고 테스트 환경을 오래 탐색했다. 미리 지시가 있었어야 했다

판정마다 통과나 실패와 함께, 왜 그렇게 봤는지 설명이 붙는다. 이 설명이 다음 단계의 에이전트가 무엇을 고칠지 정하는 재료가 된다.

여기서 통과와 실패는 루브릭의 통과선 아래로 떨어졌는지만 뜻한다.

07

4단계: 실패를 모아 고친다 12:50

채점은 대화가 끝나자마자 하고, 개선은 하루에 한 번 몰아서 한다.

  1. cron이 24시간마다 작업을 깨운다.
  2. 지난 24시간의 대화 표본을 가져온다. 예를 들어 200개다.
  3. 그중 실패한 대화만 남긴다. 예를 들어 50개다.
  4. 실패 보고서(무엇이, 왜 실패했는지)를 자기 개선 에이전트 self-improvement agent에게 넘긴다. 13:10
  5. "공통점을 찾아라"라고 지시하고, 스킬 저장소와 코드베이스에 접근하게 해 준다. 코드 구조까지 바꿔야 할 때를 위해서다.

예를 들어 불필요한 테스트가 여러 PR에서 되풀이되면, 개선 에이전트가 스킬에 커버리지 피라미드(테스트 종류별로 얼마나 둘지 정한 그림)를 추가한다. 13:30

08

Skill Doctor로 한 번 해 보기 13:50

가장 쉽게 해 볼 수 있는 방법으로 발표자는 Warp가 만든 스킬 Skill Doctor를 소개한다. 주소는 warp.dev/skilldoctor다.

  • 개인 로컬 환경에서 실행한다.
  • Claude Code, Codex 등에 쌓인 대화를 훑어 한 번 채점한다.
  • 토큰을 아끼려고 대화를 묶음으로 나눠 채점한다. 14:20
  • 마지막에 개선 에이전트가 점수를 보고 보고서를 낸다. 발표자는 이를 스킬 성적표 report card라고 부른다. 14:40

데모에서 나온 제안 15:10

발표자가 자기 프로젝트를 만든 세션들에 돌려 보니, 일부 지표가 기대보다 낮았고 장황함은 괜찮았다. 채점 에이전트들이 남긴 메모를 바탕으로 스킬 변경 두 가지가 나왔다.

E2E 테스트 스킬
  • 문제: 에이전트가 테스트할 머신에서 포트 번호를 두고 씨름했다. 환경이 어떻게 구성됐는지 몰랐다.
  • 제안: 포트 번호를 먼저 찾은 뒤 시작하라는 지시를 넣는다. 될 때까지 부딪히지 않게 한다.

효과: 도구 호출이 준다.

changelog 스킬 15:40
  • 문제: 발표자가 매번 changelog 문구를 원하는 표현으로 다시 쓰게 했다.
  • 제안: 어떤 문장으로 쓸지 구체적으로 정한 규칙으로 스킬을 다시 썼다.

효과: 에이전트가 PR을 열 때마다 하던 주고받기가 사라진다.

둘 다 발표자가 직접 찾을 수도 있었다. 그래도 포트 문제는 놓치기 쉽다. 에이전트 하네스에서는 "작업 중" 표시 뒤에 가려지고, 클라우드에서 돌면 아예 보이지 않기 때문이다.

한 번 돌리는 건 당장 쉬운 개선거리를 찾는 출발점이다. 누가 기억날 때만 돌리기보다 계속 돌리는 편이 낫다.

Skill Doctor와 Warp Factories는 발표자가 일하는 Warp의 제품이다. 이 절과 10절은 그 점을 감안해 읽자.

09

점수를 시간 순으로 본다 16:10

원래 여기서 점수 그래프를 보여 주려 했지만 스테이징 환경 접근이 끊겼다. 그래서 발표자는 말과 손그림으로 설명했다.

메모리 방식과의 차이 16:30

에이전트 하네스의 메모리 기능이나, 밤사이 지난 대화를 되짚는 "꿈꾸기" dreaming도 에이전트가 스스로를 돌아보는 방법이다. 이 발표의 루프와 비슷하다. 다만 에이전트가 무엇을 결론 냈는지 겉으로 보이지 않는다.

메모리 · 꿈꾸기에이전트가 혼자 돌아본다무엇을 배웠는지 사람에게 안 보인다
→
점수 + 대시보드채점 결과가 기록으로 남는다대화들이 어땠는지 사람이 보고 확인할 수 있다

변경과 점수를 잇는다 17:00

채점이 계속 돌면 데이터가 쌓인다. 효율 점수를 시간 순으로 그리면 평균 50%, 60%처럼 오르내리는 선이 나온다.

스킬 변경을 머지한 날을 이 선 위에 찍으면, 점수가 꺾이는 지점과 맞춰 볼 수 있다. "이 스킬을 머지했더니 효율이 몇 % 올랐다"고 말할 증거가 생긴다. 에이전트가 스스로 나아질 뿐 아니라, 그게 진짜인지도 확인할 수 있다. 17:20

10

루프를 계속 돌리기 17:50

Warp Factories에서는 이 루프가 한 번이 아니라 계속 돈다. 에이전트가 대화를 늘 채점하고, cron으로 깨어난 에이전트가 점수를 보고 설정 개선 PR을 올린다.

발표자가 보여 준 화면은 개선 PR 받은편지함이다. Warp 팀의 실제 에이전트 설정을 대상으로 하고, 팀이 리뷰할 PR이 쌓여 있다. 18:10

머지된 예: triage 스킬 18:20 triage 스킬에 하위 에이전트 sub-agent를 띄우는 설정이 빠져 있었다. 에이전트는 하위 에이전트를 어떻게 만드는지 알아내려고 계속 헤맸고, 도구 호출을 많이 낭비했다. 개선 에이전트가 이를 찾아 "팩토리 설정의 이 부분을 고치면 토큰을 아낄 수 있다"고 제안했다.

발표자는 이런 PR을 여러 개 머지했고, 에이전트가 조금씩 더 효율적이고 품질이 높아졌다고 말한다. 18:50

Warp 자사 제품의 화면이고, 효과도 발표자의 말이다. 점수가 얼마나 바뀌었는지 수치는 발표에 나오지 않았다.

11

핵심 정리

  1. 에이전트는 막히면 우회하고 성공만 보고한다. 실수는 대화 기록 속에 숨는다.
  2. 팩토리 엔지니어링은 에이전트를 움직이는 시스템 자체를 고치는 일이다. 이 발표의 대상은 스킬과 설정이다.
  3. 루프는 모으기 → 채점 → 실패 찾기 → 개선 제안 → 다시 채점이다.
  4. 팀 전체 대화를 한곳에 모은다. 공용 컴퓨터에서 에이전트를 돌리면 저절로 모인다.
  5. 대화 원문, 도구 호출, 결과물 세 가지를 모두 남긴다. 헛걸음은 도구 호출에 남는다.
  6. 채점 기준은 팀의 불만에서 고른다. 예: 불필요한 테스트, 장황함, 효율.
  7. 루브릭은 마크다운 몇 줄과 통과선이면 시작할 수 있다. 쓰면서 키운다.
  8. PR 머지 때 채점하고, 하루 한 번 실패만 모아 개선 에이전트에게 넘긴다.
  9. 개선은 스킬과 설정 변경 PR로 오고, 팀이 리뷰해서 머지한다.
  10. 점수를 시간 순으로 그리면 어떤 변경이 효과 있었는지 증거가 생긴다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1에이전트가 실수를 "숨긴다"는 말은 무슨 뜻인가?
막히면 혼자 돌아가는 길을 찾고, 그 과정은 말하지 않은 채 "됐다"고만 보고한다는 뜻이다. 실패한 도구 호출과 낡은 지시는 기록 속에 묻힌다.
Q2자기 개선 루프의 다섯 단계는?
대화 모으기, 채점하기, 실패 찾기, 개선 제안, 다시 채점하기.
Q3대화를 분석하려면 무엇을 남겨야 하나?
대화 원문, 도구 호출(파일 시스템, MCP 등), 결과물(코드 diff나 PR).
Q4팀 대화를 한곳에 모으는 두 가지 방법은?
각자의 .claude 같은 폴더를 공유 저장소(예: S3)로 모으거나, 에이전트를 팀 공용 컴퓨터나 샌드박스에서 돌려 저절로 모이게 한다.
Q5발표자 팀의 테스트 하네스 사례에서 겉으로 보인 증상과 실제 원인은?
겉으로는 "생각보다 2분쯤 더 걸린다"뿐이었다. 실제로는 스킬의 낡은 지시 때문에 에이전트가 포트 번호를 이것저것 찔러 보며 환경을 알아내고 있었다.
Q6장황함을 채점하는 이유는?
지금 가장 큰 병목은 코드 리뷰다. 변경 요약과 코드 주석이 지나치게 길면 리뷰가 느려진다.
Q7루브릭에 들어가는 세 부분과, 발표의 통과선 예는?
채점 대상, 점수별 라벨, 기준의 정의. 라벨 목록의 중간이 통과선이고 0.4나 0.2는 실패다.
Q8채점은 언제 시작하고, 모든 대화를 다 채점해야 하나?
보통 PR이 머지되면 시작한다. 전부 채점해도 되고, 토큰을 아끼려고 무작위 표본만 채점해도 된다.
Q9자기 개선 에이전트에게 무엇을 넘기나?
지난 24시간 실패한 대화의 보고서(무엇이 왜 실패했는지)와 "공통점을 찾아라"라는 지시, 그리고 스킬 저장소와 코드베이스 접근 권한.
Q10Skill Doctor 데모에서 나온 스킬 변경 두 가지는?
E2E 테스트 스킬에 "포트 번호를 먼저 찾아라"를 넣었고, changelog 스킬을 구체적인 문구 규칙으로 다시 썼다.
Q11메모리나 꿈꾸기 방식과 비교해 점수 방식이 나은 점은?
에이전트가 무엇을 판단했는지 기록으로 보인다. 스킬 변경 시점과 점수 변화를 맞춰 보면 효과가 있었는지 증거가 생긴다.
Q12Warp 팀에서 머지된 개선 PR의 예는?
triage 스킬에 하위 에이전트를 띄우는 설정이 빠져 있어 에이전트가 도구 호출을 낭비했다. 개선 에이전트가 팩토리 설정을 고치라고 제안했다.

커버리지 피라미드테스트 종류별로 얼마나 둘지 정한 그림. 발표에서는 개선 에이전트가 스킬에 추가하는 예로 나온다
triage들어온 작업을 살펴 분류하고 우선순위를 정하는 단계
하위 에이전트Sub-agent. 에이전트가 일을 나눠 맡기려고 띄우는 다른 에이전트
