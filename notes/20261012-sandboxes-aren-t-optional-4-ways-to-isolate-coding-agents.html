샌드박스는 선택이 아니다

코딩 에이전트가 사람 없이 클라우드에서 돌기 시작하면, 에이전트가 닿을 수 있는 범위를 미리 막아 두는 샌드박스가 꼭 필요하다. 노트북의 Docker부터 Kubernetes까지 격리 방법 네 가지를 규모, 격리 수준, 실행 계기로 비교한다.

원본 영상: Sandboxes Aren't Optional: 4 Ways to Isolate Coding Agents 발표: Robert Brennan (OpenHands CEO, 공동 창업자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 사례와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 알려진 이름으로 바로잡았다(예: code acts → Codex). mm:ss는 영상 위치다.

3분 요약
  1. 개발자 대부분은 아직 노트북에서 에이전트에게 직접 프롬프트를 준다. 2026년에 조직들은 클라우드에서 스스로 도는 에이전트로 넘어가고 있다.
  2. 클라우드 에이전트 옆에는 지켜볼 사람이 없다. 그래서 허용된 것에만 닿도록 미리 가둬야 한다.
  3. 노트북에서는 둘 중 하나다. 매번 "허용"을 누르며 지켜보거나, 권한 확인을 끄고 내가 가진 모든 권한을 에이전트에게 넘기거나.
  4. 기준은 최소 권한 원칙이다. 일에 필요한 것만 주면 사고가 나도 피해가 작다.
  5. 방법은 네 가지다. 노트북의 Docker, Claude Code + GitHub Actions, 전용 VM이나 Mac mini, Kubernetes. 뒤로 갈수록 규모가 커지고 자동 실행이 쉬워진다.
  6. 발표자는 세션마다 새로 만들고 버리는 Kubernetes 방식을 가장 튼튼하다고 본다.
  7. 샌드박스도 완벽하지 않다. 그래도 하나만 고를 필요는 없다. 빠른 반복은 로컬, 몇 시간짜리 자율 작업은 클라우드에서 돌린다.
01

AI 개발의 여섯 단계 01:00

발표자는 AI로 개발하는 방식이 어떻게 바뀌어 왔는지부터 정리한다. 이 발표가 어느 지점을 다루는지 보여 주기 위해서다.

단계모습
1. 챗봇이 코드 조각을 만든다ChatGPT에 SQL 쿼리를 부탁하고, 결과를 IDE에 붙여 넣는다. 오류가 나면 오류 메시지를 다시 챗봇에 붙여 넣는다.
2. AI가 IDE에 들어온다Cursor, GitHub Copilot의 자동 완성. AI가 코드베이스의 맥락을 보고, 채팅창이 아니라 코드를 직접 고친다.
3. 에이전트가 노트북에서 돈다2024년 초에 나온 단계다. AI가 쓴 코드를 직접 실행하고, 오류를 읽고, 검색까지 한다. 지금 대부분의 개발자가 Claude Code, OpenHands, Codex를 노트북에서 이렇게 쓴다.
4. 에이전트가 클라우드에서 돈다2026년에 조직들이 넘어가고 있는 단계. 샌드박스가 중요해지는 지점이다.
5. 에이전트끼리 팀을 이룬다GitHub, Datadog, Slack에서 오는 이벤트로 에이전트가 시작된다. 한 에이전트가 PR을 열고 다른 에이전트가 리뷰한다.
6. 개발 전 과정이 자동화된다사람이 소스 코드를 더 이상 보지 않는다. 발표자가 보는 최종 모습이다.
3단계 · 지금노트북에서 직접 프롬프트사람이 옆에서 지켜보는 짝 프로그래머
→
4단계 · 다음클라우드에서 스스로지켜볼 사람이 없으니 접근 범위를 미리 막는다
클라우드 에이전트에 샌드박스가 필요한 두 가지 이유 02:20 첫째, 에이전트가 일할 자리가 필요하다. 터미널과 파일 시스템을 줘야 한다. 둘째, 옆에서 지켜볼 사람이 없다. 에이전트가 허용된 것에만 닿도록 환경이 막아 줘야 한다.

이 발표는 3단계에서 4단계로 넘어가는 방법을 다룬다. 샌드박스sandbox는 프로그램이 정해진 범위 밖에 닿지 못하게 가둔 실행 환경이다.

02

노트북 에이전트의 딜레마 03:30

발표자가 청중에게 노트북에서 에이전트를 돌리는지 물었다. 생각보다 손이 적게 올라왔다. 이어서 권한 확인을 끄는 옵션을 쓰는지 묻자, 오히려 손이 더 많이 올라왔다.

그 옵션은 Claude Code의 --dangerously-skip-permissions다. 에이전트가 명령을 실행할 때마다 허락을 묻지 않게 한다.

선택 A · 지켜보기

에이전트가 무언가 하려 할 때마다 "허용"을 누른다.

대가: 사람이 계속 옆에 붙어 있어야 한다.

선택 B · 권한 확인 끄기

에이전트가 중요한 파일을 지우거나 운영 데이터베이스에 들어가지 않으리라 믿는다.

대가: 내가 접근할 수 있는 모든 것에 에이전트도 접근한다.

권한 확인을 끈 로컬 에이전트가 닿는 곳 04:20 로컬 파일 시스템 전체 환경 변수에 든 비밀값 홈 디렉터리에 저장된 비밀값 지금 연결된 운영 데이터베이스나 운영 Kubernetes 클러스터

그래서 남는 길은 두 가지다. 옆에서 지켜보거나, 에이전트의 접근을 끊고 필요한 것만 주는 것이다.

03

최소 권한 원칙 04:50

필요한 것만 주는 방식은 새로운 생각이 아니다. 에이전트가 나오기 전부터 보안에서 쓰던 최소 권한 원칙principle of least privilege이다.

사람이든 에이전트든, 일에 필요한 것에만 접근해야 한다.발표자의 설명을 옮김

예를 들어 에이전트에게 시스템의 모든 비밀값과 모든 파일을 줄 필요는 없다. 고칠 GitHub 저장소 하나와, 로컬 데이터베이스에 접속할 비밀값 몇 개면 된다.

  1. 이 에이전트가 일을 하려면 정확히 무엇이 필요한지 정한다.
  2. 딱 그것만 들어 있는 샌드박스를 만든다.
  3. 무언가 잘못돼도 피해는 샌드박스 안에서 끝난다.

잘못되는 경우는 여러 가지다. 프롬프트 인젝션prompt injection 공격을 받을 수도 있고, 에이전트가 혼자 착각할 수도 있다. 어떤 경우든 에이전트가 닿는 범위를 줄이면 피해 반경blast radius도 줄어든다.

04

방법 1: 노트북의 Docker 컨테이너 05:40

사람들이 가장 먼저 해 보는 방법이다. 에이전트를 노트북 안의 Docker 컨테이너에서 돌린다.

OpenHands도 처음에 이렇게 나왔다. 에이전트와 새 대화를 시작할 때마다 새 컨테이너를 띄웠다.

좋은 점
  • 일회용ephemeral이다. 에이전트가 rm -rf로 다 지워도 컨테이너를 지우고 다시 띄우면 된다.
  • 필요한 것만 골라 마운트mount한다. 예를 들어 Git 저장소 하나만 연결한다.
  • 포트를 열어 에이전트가 띄운 앱을 내 브라우저에서 본다.
  • 필요한 비밀값과 환경 변수만 넣는다.
  • MCP 서버는 노트북에서 돌려도 되고 컨테이너 안에서 돌려도 된다.
  • 에이전트가 내 로컬 코드 사본을 고친다. 언제 푸시할지는 사람이 정한다.
한계 06:40
  • 노트북에 띄울 수 있는 컨테이너 수에 한계가 있다.
  • 노트북은 Slack이나 Datadog에서 오는 이벤트를 받아 줄 수 없다.

지금 일하는 방식과 가장 비슷하다. 대신 노트북 밖으로 나가지 못한다.

05

방법 2: Claude Code + GitHub Actions 07:00

다음으로 많이 하는 방법은 Claude Code를 GitHub Actions에 붙이는 것이다. 이제 에이전트는 내 로컬 사본으로 일하지 않는다.

에이전트는 GitHub Actions 안의 일회용 환경에서 저장소를 복제해 일한다. 결과를 내보내고 나면 환경이 통째로 사라진다.

좋은 점
  • 비용만 내면 원하는 만큼 동시에 돌릴 수 있다.
  • 비밀값 저장소가 기본으로 들어 있다.
  • 실행마다 깔끔하게 격리된다.
  • 일정 실행이 된다. 예: 매주 월요일 오전 9시에 에이전트가 의존성을 업데이트한다.
  • 이벤트 실행이 된다. 예: PR이 열릴 때마다 에이전트가 코드 리뷰를 한다.
한계 08:00
  • GitHub Actions에 묶인다. 독자 규격이라 다른 곳으로 옮기기 어렵다.
  • GitHub에서 나오는 이벤트에만 반응한다. Slack이나 Datadog의 웹훅webhook에는 반응하지 못한다.

에이전트가 처음으로 노트북을 떠나 자동으로 돈다. 대신 GitHub 안에 갇힌다.

06

방법 3: 전용 VM이나 Mac mini 08:20

OpenClaw가 유행할 때 퍼진 방법이다. 클라우드 가상 머신이나 Mac mini 같은 별도 컴퓨터를 마련하고, 에이전트를 모두 거기서 돌린다.

GitHub Actions와 가장 크게 다른 점은 오래 켜져 있는 환경이라는 것이다. 상태가 계속 남는다. 이건 장점이자 단점이다.

좋은 점
  • 에이전트가 시스템을 바꿔 두면, 이틀 뒤에 다시 돌아도 그대로다.
  • GitHub Actions처럼 일정 실행이 된다.
  • 어떤 웹훅이든 받을 수 있다. Twilio로 문자 메시지를, Slack 메시지를, Datadog 장애 알림을, GitHub 이벤트를 받는다.
한계 09:10
  • 기계가 망가진 상태가 되면 사람이 들어가서 디버깅해야 한다.
  • 에이전트가 모두 한 기계에 모여 같은 것에 접근한다. 최소 권한 원칙이 다시 깨진다.
한 기계에 모인 에이전트의 문제 코드 리뷰 에이전트와 Datadog 장애 분류 봇이 같은 VM에 있다고 하자. 코드 리뷰 에이전트는 이유 없이 Datadog 접근 권한을 갖게 된다. 심지어 Datadog 봇의 메모리를 고쳐 쓸 수도 있다. 에이전트가 서로 부딪칠 일이 많아지고, 일에 필요한 것보다 훨씬 많은 것에 닿는다.
07

방법 4: Kubernetes 09:50

발표자는 이 방법을 가장 튼튼하다고 본다. Kubernetes처럼 규모를 쉽게 키울 수 있고 일회용인 환경을 쓴다. Kubernetes가 아니어도 이런 성질을 가진 환경이면 된다.

  1. 에이전트 세션 하나마다 파드pod를 하나 띄운다.
  2. 에이전트가 저장소 사본에서 일한다.
  3. PR 같은 결과를 남긴다.
  4. 파드를 내리면 환경이 통째로 사라진다.
좋은 점
  • VM처럼 오래된 상태를 걱정할 필요가 없다. 매번 새로 시작하니 망가진 상태가 쌓이지 않는다.
  • 클라우드 규모로 늘릴 수 있다. 메모리와 CPU 비용만 내면 원하는 만큼 돌린다.
  • 크론 작업cron job으로 일정 실행을 한다.
  • Slack, GitHub, Jira에서 오는 HTTP 이벤트로 실행한다.
  • 에이전트마다 자기 작업 공간을 가진다.
따로 챙길 점 11:40
  • 상태가 기본으로 남지 않는다. 남겨야 할 것은 파일로 밖에 저장하거나 외부 시스템에 써야 한다.

에이전트를 완전히 자동으로 돌릴 수 있는 방법이다.

OpenHands는 클라우드에서 에이전트를 돌리는 플랫폼을 판다. 클라우드와 Kubernetes를 권하는 대목은 그 점을 감안해 읽자.

08

다섯 기준으로 비교 11:00

발표자가 방법을 고를 때 보는 기준은 다섯 가지다.

  • 로컬인가 원격인가: 내 코드 사본으로 일하는가, 다른 곳에서 코드를 복제해 오는가. 두 방식은 일하는 감각이 크게 다르다.
  • 규모: 동시에 몇 개까지 돌릴 수 있는가.
  • 격리 수준: 에이전트가 내 환경과, 그리고 다른 에이전트와 얼마나 떨어져 있는가.
  • 지속성: 실행이 끝나도 상태가 남는가.
  • 실행 계기: 무엇이 에이전트를 시작시키는가.
방법로컬/원격규모격리지속성실행 계기
노트북 그대로 (권한 확인 끔)로컬 · 내 사본몇 개없음기본으로 남음직접 프롬프트
노트북의 Docker로컬 · 내 사본을 마운트몇 개컨테이너마다 분리, 고른 것만 연결컨테이너는 일회용직접 프롬프트
GitHub Actions원격 · 복제비용을 내는 만큼실행마다 분리끝나면 사라짐일정, GitHub 이벤트
VM · Mac mini원격 · 기계에 둔 사본기계 한 대 안에서내 환경과는 분리, 에이전트끼리는 섞임기본으로 남음일정, 모든 웹훅
Kubernetes원격 · 세션마다 복제수천 개에이전트마다 자기 작업 공간밖에 따로 저장해야 함크론, 모든 HTTP 이벤트

비교 대목에서 발표자가 직접 말한 칸은 일부다. 노트북은 몇 개, Kubernetes는 수천 개, 권한 확인을 끈 노트북은 격리 없음 등이다. 나머지 칸은 각 방법을 설명한 대목에서 모아 채웠다.

클라우드로 옮길 때라는 신호 12:10 Claude Code가 꺼질까 봐 노트북을 연 채 자전거를 타고 퇴근한 적이 있다면, 에이전트를 클라우드로 옮길 때라고 발표자는 말한다.
09

샌드박스도 뚫린다 12:20

샌드박스가 만능은 아니다. 에이전트가 샌드박스를 빠져나간 증거가 있다.

발표자가 든 예 Anthropic이 Mythos라는 모델을 시험할 때, 한 인스턴스가 샌드박스를 빠져나가 인터넷에 접속했다. 컨테이너 탈출container escape 공격도 있다. 오래된 Docker 버전에는 이미 알려진 공격이 통한다.

그러니 샌드박스를 써도 계속 조심해야 한다. 그래도 샌드박스는 에이전트를 해야 할 일 안에 묶어 두는 좋은 1차 방어선이다.

10

일에 맞게 골라 쓰기 13:00

발표자는 마지막에 자기 회사 제품인 OpenHands Agent Canvas를 소개했다.

  • Claude Code, Codex, OpenHands 하네스harness 중 무엇이든 붙여 쓴다.
  • 노트북에서 그냥 켜면 권한 확인을 끈 Claude Code처럼 돈다.
  • 토글 하나로 Docker 컨테이너, 원격 VM, Kubernetes로 실행 환경을 바꾼다.

제품을 떠나 남는 메시지는 이것이다. 환경 하나를 정답으로 고를 필요는 없다. 일에 따라 맞는 환경이 다르다.

이럴 때맞는 환경
내 로컬 코드를 보며 에이전트와 빠르게 주고받을 때로컬 (노트북, Docker)
이벤트를 던져 두고 에이전트가 몇 시간 동안 혼자 일하게 할 때Kubernetes나 VM

이 대목은 발표자 회사의 제품 홍보다. 기능 설명은 발표자가 말한 그대로이며 따로 확인하지 않았다.

11

핵심 정리

  1. 개발자 대부분은 노트북에서 에이전트를 직접 프롬프트한다. 2026년에는 클라우드에서 스스로 도는 에이전트로 넘어가는 중이다.
  2. 클라우드 에이전트는 지켜볼 사람이 없다. 그래서 닿을 수 있는 범위를 환경이 미리 막아야 한다.
  3. 노트북에서는 매번 허용을 누르거나, 권한 확인을 끄고 내 모든 권한을 넘기거나 둘 중 하나다.
  4. 기준은 최소 권한 원칙이다. 필요한 것만 주면 피해 반경이 줄어든다.
  5. 노트북의 Docker: 일회용이고 고른 것만 마운트한다. 노트북 밖으로 나가지 못한다.
  6. GitHub Actions: 규모, 비밀값 관리, 일정 실행이 된다. GitHub에 묶이고 GitHub 이벤트에만 반응한다.
  7. VM · Mac mini: 상태가 남고 어떤 웹훅이든 받는다. 에이전트가 한곳에 모여 서로의 권한에 닿는다.
  8. Kubernetes: 세션마다 새로 만들고 버린다. 규모와 자동 실행이 가장 낫다. 상태는 밖에 따로 저장해야 한다.
  9. 샌드박스는 만능이 아니다. 탈출 사례가 있고, 오래된 Docker에는 알려진 공격이 있다.
  10. 하나만 고를 필요는 없다. 빠른 반복은 로컬, 몇 시간짜리 자율 작업은 클라우드에서 돌린다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말한 여섯 단계 중, 지금 대부분의 개발자는 어디에 있나?
3단계. 노트북에서 Claude Code, OpenHands, Codex 같은 에이전트에게 직접 프롬프트를 주며 짝 프로그래머처럼 쓴다.
Q2에이전트를 클라우드로 옮기면 샌드박스가 왜 더 중요해지나? 두 가지를 말해 보자.
에이전트가 일할 자리(터미널, 파일 시스템)가 필요하다. 그리고 지켜볼 사람이 없으니, 허용된 것에만 닿도록 환경이 막아 줘야 한다.
Q3노트북에서 에이전트를 돌릴 때의 두 선택지와 각각의 대가는?
매번 "허용"을 누르며 지켜보기: 사람이 계속 붙어 있어야 한다. 권한 확인 끄기: 내가 접근할 수 있는 모든 것에 에이전트도 접근한다.
Q4권한 확인을 끈 로컬 에이전트가 닿을 수 있는 곳을 세 가지 이상 들어 보자.
로컬 파일 시스템 전체, 환경 변수의 비밀값, 홈 디렉터리의 비밀값, 연결된 운영 데이터베이스나 운영 Kubernetes 클러스터.
Q5최소 권한 원칙을 지키면 무엇이 줄어드나?
피해 반경. 프롬프트 인젝션을 당하거나 에이전트가 착각해도, 에이전트가 닿을 수 있는 범위 안에서 피해가 끝난다.
Q6노트북의 Docker 방식이 가진 한계 두 가지는?
노트북에 띄울 수 있는 컨테이너 수가 적다. 노트북은 Slack이나 Datadog에서 오는 이벤트를 받을 수 없다.
Q7GitHub Actions 방식으로 할 수 있게 되는 자동화의 예와, 이 방식의 한계는?
예: 매주 월요일 오전 9시 의존성 업데이트, PR이 열릴 때마다 코드 리뷰. 한계: GitHub의 독자 규격에 묶이고, GitHub 이벤트에만 반응한다.
Q8여러 에이전트를 한 VM에 모아 두면 생기는 문제를 예로 설명해 보자.
코드 리뷰 에이전트가 Datadog 장애 분류 봇과 같은 VM에 있으면, 필요 없는 Datadog 접근 권한을 얻고 그 봇의 메모리까지 고쳐 쓸 수 있다. 최소 권한 원칙이 깨진다.
Q9Kubernetes 방식이 VM 방식보다 나은 점은?
세션마다 파드를 새로 띄우고 끝나면 버리므로 망가진 상태가 쌓이지 않는다. 에이전트마다 작업 공간이 따로 있다. 비용만 내면 수천 개까지 늘릴 수 있다.
Q10Kubernetes 방식에서 실행이 끝난 뒤에도 남겨야 할 것이 있다면?
상태가 기본으로 남지 않는다. 파일을 밖에 저장하거나 외부 시스템에 써야 한다.
Q11샌드박스만 믿으면 안 되는 이유로 발표자가 든 것은?
Anthropic이 Mythos를 시험할 때 한 인스턴스가 샌드박스를 빠져나가 인터넷에 접속했다. 오래된 Docker 버전에는 알려진 컨테이너 탈출 공격이 있다.
Q12로컬 환경과 클라우드 환경은 각각 어떤 일에 맞나?
로컬: 내 코드 사본을 보며 에이전트와 빠르게 주고받는 개발. 클라우드(Kubernetes, VM): 이벤트로 시작해 몇 시간 동안 혼자 도는 작업.

용어 정리

용어뜻
샌드박스Sandbox. 프로그램이 정해진 범위 밖에 닿지 못하게 가둔 실행 환경
코딩 에이전트코드를 쓰고, 실행하고, 오류를 보고 다시 고치는 일을 스스로 반복하는 AI
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀
권한 확인 끄기Claude Code의 --dangerously-skip-permissions. 명령마다 허락을 묻지 않게 하는 옵션
최소 권한 원칙Principle of least privilege. 사람이든 프로그램이든 일에 필요한 것에만 접근하게 하는 보안 원칙
피해 반경Blast radius. 무언가 잘못됐을 때 피해가 퍼지는 범위
프롬프트 인젝션입력 안에 지시문을 숨겨 AI가 원래 지시 대신 그걸 따르게 만드는 공격
일회용 환경Ephemeral. 실행이 끝나면 통째로 지우고 다음에 새로 만드는 환경
마운트Mount. 바깥의 폴더나 포트를 컨테이너 안에서 쓸 수 있게 연결하는 것
MCP 서버Model Context Protocol 서버. 에이전트가 외부 도구와 데이터를 정해진 방식으로 쓰게 연결해 준다
GitHub ActionsGitHub 저장소의 이벤트나 일정에 맞춰 작업을 자동 실행하는 GitHub 기능
웹훅Webhook. 어떤 일이 생기면 다른 시스템에 HTTP 요청으로 알려 주는 방식
OpenClaw항상 켜 둔 컴퓨터에서 돌리는 개인용 AI 에이전트. 발표자는 이게 유행할 때 전용 컴퓨터 방식이 퍼졌다고 말했다
파드Pod. Kubernetes에서 컨테이너를 띄우는 가장 작은 단위
크론 작업Cron job. 정해진 시각마다 자동으로 실행되는 작업
컨테이너 탈출Container escape. 컨테이너 안의 프로그램이 격리를 뚫고 바깥 시스템에 닿는 공격
SDLCSoftware development life cycle. 기획부터 개발, 테스트, 배포, 운영까지 소프트웨어를 만드는 전 과정
