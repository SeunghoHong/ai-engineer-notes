GPU가 죽어도 학습은 이어진다

GPU 수천 개로 학습하면 고장은 반드시 난다. Crusoe 발표자들은 Slurm을 Kubernetes 위에 올려, 고장 난 GPU 노드를 자동으로 바꾸고 체크포인트에서 학습을 이어 가는 구조를 보여 준다.

원본 영상: GPU Died. Training Didn't: Self-Healing Training at Scale 발표: Connor (Crusoe 개발자 애드버킷), Nikil, Young (모두 Crusoe)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 따로 확인하지는 않았다. 발표자 이름은 자막에 나온 대로 적었다. 자막의 "SCADMD"는 Slurm 개발사 SchedMD로 바로잡았다. mm:ss는 영상 위치다.

세 발표자 모두 Crusoe 소속이고, 발표의 대부분은 자사 제품 소개다. 장점 위주의 설명이라는 점을 감안해 읽자.

3분 요약
  1. GPU 수천 개로 학습하면 고장은 반드시 난다. 사람이 매번 손으로 고치는 방식은 이 규모에서 버티지 못한다.
  2. Slurm은 AI 학습 스케줄링에 강하다. 하지만 자원 배분이 고정적이고, 고장 노드 관리가 사람 몫이며, 실패 이유를 잘 알려 주지 못한다.
  3. Kubernetes 팀과 Slurm 팀이 따로 인프라를 만들면 스택이 두 벌이 되어 운영 부담과 비용이 늘어난다.
  4. Crusoe는 Slurm을 Kubernetes 위에 올렸다. 연구자에게는 평범한 Slurm으로, 플랫폼 팀에게는 서비스 하나로 보인다.
  5. GPU 치명적 오류가 나면 작업 취소, 재큐잉, 노드 교체, 학습 재개가 사람 손 없이 이어진다.
  6. 데모에서 노드 교체는 약 5분, 학습 재개까지 전체 중단은 15분 미만이었다.
  7. 사용자가 준비할 것은 하나다. 학습 코드가 종료 신호를 받으면 체크포인트를 저장하고, 다시 시작하면 불러오게 만든다.
01

GPU 고장은 피할 수 없다 00:20

Crusoe 고객들은 GPU 수천 개에 걸친 아주 큰 학습을 돌린다. 이 규모에서는 GPU 고장이 반드시 일어난다. 고장 날 때마다 사람이 손으로 고치는 방식은 지속할 수 없다.

발표의 목표는 두 가지다. Slurm과 Kubernetes를 함께 써서 자동으로 복구하는 플랫폼을 만든다. 그러면서도 학습을 돌리는 ML 엔지니어와 클러스터를 관리하는 플랫폼 팀 모두 쓰기 쉽게 한다.

층이름하는 일
클라우드Crusoe Cloud컴퓨트, 스토리지, 네트워크, NVIDIA와 AMD의 최신 GPU를 빌려준다 (IaaS)

목표는 Slurm의 고성능 작업 스케줄링과 Kubernetes의 장애 대응력·관측 기능을 함께 얻는 것이다.

02

Slurm의 강점과 한계 02:10

Slurm은 대규모 계산 클러스터에서 작업 대기열과 자원 배분을 맡는 스케줄러다. 20여 년 전 대학과 연구소의 연구자들이 연구자를 위해 만들었다. 원래 고성능 계산(HPC) 용도였는데, 지금의 AI 학습에도 잘 맞는다.

잘하는 것 02:40

여러 노드에 걸친 학습은 각 프로세스(랭크 rank) 사이에 촘촘한 집합 통신 collective communication이 필요하다. Slurm은 이런 작업을 다루는 기능을 이미 갖고 있다.

  • 갱 스케줄링 gang scheduling: 필요한 노드를 한꺼번에 다 잡아야 시작한다
  • 토폴로지 인식 topology awareness: 네트워크상 가까운 노드에 작업을 놓는다
  • 프롤로그·에필로그 prolog / epilog: 작업 앞뒤로 스크립트를 돌려 클러스터를 검사한다
  • 연구자에게 이미 익숙한 명령과 스크립트로 작업을 돌린다
부족한 것 03:30
  • 고정된 자원 배분: 요즘 AI 작업에는 학습, 사후 학습 post-training, 평가, 추론이 섞여 있다. GPU가 모자라니 자원을 유연하게 옮겨야 한다. 그런데 Slurm의 파티션 partition은 대체로 고정돼 있다.
  • 노드 상태 관리 부담 04:20: 작업 재큐잉, 나쁜 노드 감지 기능은 있다. 하지만 나쁜 노드를 찾고, 빼내고(드레인 drain), 우회하는 일은 사람이 하거나 스크립트를 따로 짜야 한다.
  • 관측성 observability 05:00: Slurm은 작업이 실패한 건 안다. 왜 실패했는지는 다 알려 주지 못한다. GPU 고장 말고도 네트워크 플랩 network flap, 스위치 문제로 작업이 실패하거나 느려질 수 있다.
03

두 팀, 두 개의 스택 05:50

Slurm은 학습 팀에게 이점이 크다. 하지만 설치하고 운영하고 안정적으로 유지하기가 어렵다. 반대편에는 Kubernetes가 있다.

Kubernetes가 가진 것 06:10

  • 발표자는 "클라우드의 운영체제"라고 부른다. 널리 쓰여서 다룰 줄 아는 사람이 많다.
  • 생태계가 성숙했다. 관측, 네트워크, 보안 등 필요한 확장 도구가 다 있다.
  • 자체 복구 self-healing, 부하 분산, 오토스케일이 기본으로 들어 있다.

문제는 두 팀이 만날 때 06:40

고객은 흔히 Kubernetes에서 추론부터 시작하고, 나중에 학습으로 넓힌다. 반대 순서도 있다. 이때 마찰이 생긴다.

  • Kubernetes에 익숙한 팀은 Slurm 클러스터를 배포하고 운영하기 어려워한다.
  • 새로 들어온 Slurm 중심 학습 팀은 기존 Kubernetes 체계가 낯설다.
각자 익숙한 도구로 가면 인프라 스택이 두 벌이 된다. 관측 도구, 온콜 on-call 팀, 런북 runbook도 두 벌이다. 운영 부담과 비용이 그만큼 늘어난다.
04

Slurm을 Kubernetes 위에 07:30

Crusoe의 답은 Slurm을 Kubernetes 위에 올리는 것이다. 중심에는 Crusoe Slurm 오퍼레이터 operator가 있다. 이 오퍼레이터가 관리형 Kubernetes, 그리고 스토리지·네트워크 같은 Crusoe 클라우드 자원과 맞물려 움직인다.

Slurm 사용자, 파티션, 설정, 스토리지는 Crusoe가 관리한다. 하나씩 따로 맞출 필요 없이 명령 하나로 Kubernetes 클러스터 안에 Slurm 클러스터가 생긴다.

누가보이는 모습이점
연구자 (Slurm 사용자)IP 주소 하나로 SSH 접속하면 평범한 Slurm 클러스터다아래에서 Kubernetes가 돈다는 걸 몰라도 된다. 토폴로지 인식 스케줄링도 그대로 쓴다
플랫폼·인프라 팀Slurm이 기존 인프라에 붙는 서비스 하나다새 인프라 스택, 새 관측 도구, 새 온콜 팀, 새 런북이 필요 없다

학습과 추론 사이에서 GPU 옮기기 08:50

모든 GPU가 한 클러스터에 있으니 자원을 양쪽으로 옮길 수 있다.

  • 추론 사용자가 몰리면 학습 클러스터의 GPU 일부를 추론 서비스로 돌린다.
  • 사용자가 줄어 GPU가 놀면 학습을 키우거나, 더 많은 GPU로 큰 본 학습(히어로 런 hero run)을 돌린다.

발표자는 이것이 인프라 스택이 하나일 때만 가능하다고 말한다. 그리고 이 구조 덕분에 다음 절의 자동 복구(AutoClusters)를 Slurm에서도 쓸 수 있다.

"한 스택일 때만 가능하다"는 자사 제품을 소개하며 한 주장이다. 다른 방식과 비교한 근거는 발표에 없었다.

05

고장 나면 벌어지는 일 10:00

AutoClusters가 치명적인 하드웨어 오류를 감지했을 때의 흐름이다. 발표는 XID 79 오류를 예로 든다. GPU 하나를 전혀 쓸 수 없게 된 상황이다.

순서누가하는 일
1알림사용자에게 알린다. 사용자가 할 일은 없다
2Slurm 오퍼레이터해당 노드를 down 상태로 바꾸고, 돌던 작업을 취소한다
3학습 코드SIGTERM 신호를 받는다. 최대 2분 안에 체크포인트를 저장하거나 로그를 내보낸 뒤 종료된다
4Slurm취소된 작업을 자동으로 대기열에 다시 넣는다 (재큐잉 requeue)
5AutoClusters그 노드의 파드 중 자동 교체를 막는 라벨이 붙은 것이 없는지 확인한다
6AutoClusters교체해도 되면 Kubernetes 노드를 코든 cordon하고 드레인한다
7AutoClusters고장 노드를 노드 풀에서 빼고, 여유 용량 spare capacity에서 정상 노드를 가져와 채운다
8기록알림과 조치 내역을 로그로 남긴다. 사용자가 나중에 참고하는 용도다
9Slurm + 학습 코드정상 노드가 붙으면 작업이 시작된다. 학습 코드가 모델과 체크포인트를 불러와 학습을 이어 간다
사용자가 할 일은 없다. 학습 코드만 준비돼 있다면 발표는 모든 단계에서 사용자가 할 일이 없다고 강조한다. 다만 3번과 9번은 플랫폼이 아니라 사용자의 학습 코드가 하는 일이다. 종료 신호를 받으면 2분 안에 체크포인트를 저장하고, 다시 시작하면 그 체크포인트를 불러와야 한다. 이 코드가 있어야 자동 재시작이 "이어서 학습"이 된다.
06

데모: 15분 안에 재개 11:30

  1. 왼쪽 화면에서 sbatch로 PyTorch 학습 스크립트를 평소처럼 실행한다. 오른쪽은 Crusoe 콘솔이고, A100 노드 2대짜리 GPU 노드 풀이 보인다.
  2. 스크립트로 Crusoe 내부 모니터링 시스템에 "GPU 하나에서 XID 79 발생"이라고 알린다. 이 신호가 AutoClusters를 깨운다. 11:50
  3. GPU 사용률이 바로 떨어진다. 노드 교체가 곧바로 시작된다. 12:10
  4. 사용자에게 알림이 간다. 알림마다 "할 일 없음"이라고 적혀 있다. 12:30
  5. Slurm 작업이 다시 시작되고, 체크포인트를 불러와 멈춘 곳부터 학습한다. GPU 사용률이 정상으로 돌아온다. 12:50

발표자는 이 결과를 이렇게 비교한다. 엔지니어가 한밤중에 로그인해 몇 시간씩 디버깅하는 것보다 훨씬 낫다. 모든 과정이 플랫폼에서 자동으로 처리된다.

데모는 A100 노드 2대 규모였고, 오류는 실제 고장이 아니라 스크립트로 흉내 낸 것이다. 5분과 15분은 Crusoe가 자기 제품으로 보여 준 수치다. 수천 GPU 규모에서 잰 결과는 발표에 나오지 않았다.

08

핵심 메시지 세 가지 14:30

  1. 두 시스템이 맞물린다. 전통적으로 Slurm과 그 아래 인프라는 따로 노는 시스템이었다. Kubernetes와 묶으면 둘이 같은 상태를 본다. 고장 난 GPU 노드가 자동으로 코든되고, 그 신호가 Slurm 오퍼레이터까지 바로 전달된다.
  2. 두 팀 모두 하던 대로 일한다. 14:50 연구자는 같은 명령으로 Slurm 작업을 돌린다. 파드에 SSH로 들어가거나 컨테이너를 신경 쓸 일이 없다. Kubernetes 팀은 익숙한 텔레메트리와 관측 도구를 그대로 쓴다.
  3. GPU 노드는 Kubernetes 노드가 먼저다. 15:20 Slurm은 그 위에서 도는 워크로드 하나일 뿐이다. Slurm 작업이 끝나면 그 GPU는 다음 작업을 기다리며 놀지 않는다. 플랫폼 입장에서는 노드 풀의 노드일 뿐이라 추론 파드를 바로 올릴 수 있다.

09

핵심 정리

  1. GPU 수천 개 규모의 학습에서 GPU 고장은 피할 수 없다. 사람이 손으로 고치는 방식은 규모를 따라가지 못한다.
  2. Slurm은 갱 스케줄링, 토폴로지 인식, 프롤로그·에필로그 덕분에 AI 학습에 잘 맞는다.
  3. Slurm의 한계는 고정된 자원 배분, 노드 관리 부담, 부족한 관측성이다.
  4. Kubernetes 팀과 Slurm 팀이 따로 가면 인프라 스택, 관측 도구, 온콜, 런북이 모두 두 벌이 된다.
  5. Crusoe Managed Slurm은 SchedMD의 Slinky를 바탕으로 Slurm을 Kubernetes 위에서 돌린다.
  6. 연구자는 SSH로 들어가 평소처럼 Slurm을 쓰고, 플랫폼 팀은 Slurm을 서비스 하나로 다룬다.
  7. GPU가 한 클러스터에 있으니 학습과 추론 사이에서 GPU를 옮겨 쓸 수 있다.
  8. XID 79 같은 치명적 오류가 나면 작업 취소, SIGTERM 2분, 재큐잉, 코든·드레인, 노드 교체, 학습 재개가 자동으로 이어진다.
  9. 데모 기준 노드 교체는 약 5분, 전체 중단은 15분 미만이다. 나머지 시간은 주로 학습 코드가 모델과 체크포인트를 불러오는 시간이다.
  10. 설계의 핵심은 GPU 노드가 Kubernetes 노드가 먼저라는 점이다. 그래서 고장 신호가 Slurm까지 자동으로 전달된다.
10

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자들이 대규모 학습에서 수동 복구로는 안 된다고 본 이유는?
GPU가 수천 개면 고장은 반드시 일어난다. 그때마다 사람이 손으로 고치는 방식은 이 규모에서 지속할 수 없다.
Q2Slurm이 AI 학습에 잘 맞는 이유로 든 기능 세 가지는?
갱 스케줄링, 토폴로지 인식, 클러스터 검사용 프롤로그·에필로그. 연구자에게 익숙한 도구라는 점도 들었다.
Q3Slurm의 세 가지 한계는?
파티션이 고정적이라 학습·평가·추론이 섞인 동적 워크로드에 유연하지 않다. 나쁜 노드를 찾고 빼는 일이 사람이나 스크립트 몫이다. 작업이 실패한 건 알아도 왜 실패했는지는 잘 알려 주지 못한다.
Q4Kubernetes 팀과 Slurm 팀이 각자 익숙한 도구로 가면 생기는 문제는?
인프라 스택이 두 벌이 된다. 관측 도구, 온콜 팀, 런북도 두 벌이라 운영 부담과 비용이 늘어난다.
Q5Crusoe Managed Slurm은 연구자와 플랫폼 팀에게 각각 어떻게 보이나?
연구자에게는 IP 주소로 SSH 접속하는 평범한 Slurm 클러스터다. 플랫폼 팀에게는 기존 인프라에 붙는 서비스 하나다.
Q6모든 GPU를 한 클러스터에 두면 생기는 이점은?
추론 사용자가 몰리면 학습 쪽 GPU를 추론으로 돌린다. 사용자가 줄면 놀고 있는 GPU로 학습을 키우거나 큰 히어로 런을 돌린다.
Q7SIGTERM을 받은 학습 코드에게 주어지는 시간과, 그동안 할 일은?
최대 2분. 그 안에 체크포인트를 저장하거나 로그를 내보낸다.
Q8AutoClusters가 노드를 교체하기 전에 확인하는 것은?
그 노드의 파드 중 자동 교체를 막는 라벨이 붙은 것이 있는지. 없으면 코든·드레인하고 여유 용량의 정상 노드로 바꾼다.
Q9데모에서 노드 교체 시간과 전체 중단 시간은? 나머지 시간은 무엇에 쓰였나?
노드 교체 약 5분, 전체 중단 15분 미만. 나머지는 주로 학습 코드가 모델과 체크포인트를 불러오는 시간이다.
Q10"사용자가 할 일은 없다"는 말이 성립하려면 미리 갖춰야 할 것은?
학습 코드가 종료 신호를 받으면 체크포인트를 저장하고, 다시 시작하면 그 체크포인트를 불러오게 돼 있어야 한다.
Q11원클릭 Slurm의 첫 명령 하나로 만들어지는 것은?
바탕이 되는 Kubernetes 클러스터, Slurm 컨트롤러, 로그인 노드, 스토리지. GPU 노드 풀은 명령 하나를 더 쓴다. AutoClusters는 기본으로 켜져 있다.
Q12"GPU 노드는 Kubernetes 노드가 먼저"라는 말은 무슨 뜻인가?
Slurm은 Kubernetes 위에서 도는 워크로드 하나일 뿐이다. 그래서 고장 신호가 Slurm까지 자동으로 가고, Slurm 작업이 끝난 GPU에 추론 파드를 바로 올릴 수 있다.

용어 정리

용어뜻
Slurm대규모 계산 클러스터에서 작업 대기열과 자원 배분을 맡는 스케줄러
HPCHigh-Performance Computing. 많은 컴퓨터를 묶어 큰 계산을 하는 분야
Kubernetes컨테이너로 만든 서비스를 배포하고 운영을 자동화하는 플랫폼
SlinkySlurm 개발사 SchedMD의 공식 오픈소스 프로젝트. Slurm을 Kubernetes 위에서 돌린다
오퍼레이터Operator. Kubernetes에서 특정 소프트웨어의 운영을 자동으로 맡는 프로그램
랭크Rank. 분산 학습에 참여하는 각 프로세스의 번호
집합 통신Collective communication. 여러 프로세스가 한꺼번에 데이터를 주고받아 맞추는 통신
갱 스케줄링Gang scheduling. 작업에 필요한 노드를 한꺼번에 모두 잡았을 때만 시작하는 방식
토폴로지 인식Topology awareness. 네트워크 구조를 보고 서로 가까운 노드에 작업을 놓는 것
프롤로그 / 에필로그Prolog / Epilog. Slurm 작업 앞뒤에 자동으로 도는 스크립트. 노드 검사에 쓴다
파티션Partition. Slurm에서 노드를 묶어 나눈 단위
노드 풀Node pool. 같은 사양의 노드를 묶은 것
코든 / 드레인Cordon / Drain. 코든은 노드에 새 작업이 못 오게 막는 것이고, 드레인은 돌던 작업까지 빼내는 것이다
재큐잉Requeue. 취소된 작업을 대기열에 다시 넣는 것
XID 79NVIDIA GPU 드라이버가 보고하는 오류 번호 중 하나. 발표에서는 GPU를 전혀 쓸 수 없는 치명적 오류로 소개했다
SIGTERM프로그램에 "곧 끝내라"고 알리는 신호. 받은 프로그램은 정리할 시간을 갖는다
체크포인트Checkpoint. 학습 중간 상태를 저장한 파일. 여기서부터 학습을 이어 갈 수 있다
sbatchSlurm에 배치 작업을 제출하는 명령
여유 용량Spare capacity. 고장 난 노드를 바로 대신할 수 있게 비워 둔 자원
히어로 런Hero run. GPU를 가장 많이 써서 돌리는 대규모 본 학습
관측성Observability. 시스템 안에서 무슨 일이 왜 일어났는지 밖에서 알아낼 수 있는 정도
네트워크 플랩Network flap. 네트워크 연결이 짧게 끊겼다 붙었다를 반복하는 현상
온콜 / 런북On-call / Runbook. 온콜은 장애 대응 당번, 런북은 장애 때 따라 하는 대응 절차 문서
텔레메트리시스템 상태를 자동으로 모아 보내는 측정 데이터
