에이전트는 멀쩡했다. 주변이 무너졌다

Harvey의 사내 클라우드 에이전트 플랫폼에서 에이전트가 쓴 PR이 1만 개를 넘었다. 그동안 망가진 건 에이전트가 아니라, 작업을 받아 돌리고 줄 세우고 머지까지 가져가는 주변 장치였다.

원본 영상: The Agents Were Fine. Everything Around Them Broke. 발표: Joey Wang (Harvey, 사내 클라우드 에이전트 플랫폼 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. Claude Code, Codex, Cursor처럼 확실한 이름은 바로잡았고, 뭉개져서 확실하지 않은 곳에는 "(추정)"을 붙였다. 플랫폼 이름 Spectre는 자막에 가장 자주 나온 표기를 따랐다. mm:ss는 영상 위치다.

3분 요약
  1. Harvey 사내 플랫폼에서는 평균 1분에 하나 넘게 에이전트가 시작되고, 에이전트가 쓴 PR이 1만 개를 넘었다. 망가진 건 에이전트가 아니라 그 주변이었다.
  2. 플랫폼은 에이전트 도구와 경쟁하지 않는다. Claude Code든 Cursor든 사람이 고르고, 비밀값과 실제 스택, 리뷰, 머지는 플랫폼이 맡는다.
  3. 하나만 만든다면 후속 루프다. CI 실패를 읽고 다시 고쳐 올리는 반복이다. 머지된 백엔드 에이전트 PR 5개 중 4개가 이 루프를 거쳤다.
  4. 사람이 클릭할 수 있는 건 에이전트도 호출할 수 있게 했다. 터미널에서 시작된 작업이 월 1건에서 약 6,500건이 됐다.
  5. 호출이 쉬워지자 폭주가 왔다. 알림 하나가 4시간에 작업 900개를, 엔지니어 한 명이 3시간에 950개를 시작해 클러스터를 채웠다. 해법은 중복 알림 합치기와 공정한 실행 대기열이다.
  6. 실행이 풀리자 병목은 머지로 옮겨 갔다. PR이 한 달 만에 약 60% 늘고 머지 한 번이 1시간을 넘겼다. 아직 못 풀었다.
  7. 다시 해도 할 세 가지: 코드가 쓰인 뒤를 책임지고, 모든 동작을 호출할 수 있게 하고, 시작할 수 있는 양에 상한을 둔다.
01

숫자로 본 규모 00:00

발표자는 지난달 숫자 하나로 시작한다. 플랫폼에서 밤낮없이 평균 1분에 하나 넘게 에이전트가 시작됐다.

항목값
에이전트 시작평균 1분에 1개 이상, 밤낮없이 (지난달)
에이전트가 쓴 PR약 1만 개 (지금까지)
쓰는 사람Harvey 사내 약 460명 (지난달)

한 팀이 장난감처럼 만져 보는 수준이 아니다. 여름부터는 코드 밖의 일도 들어왔다.

  • Slack에 데이터 질문을 올리면 답이 돌아온다.
  • 마케팅팀의 한 사람은 시제품과 발표 대본을 Slack에 올리고, 제품 영상용 스토리보드를 요청했다.

여기서 발표자가 얻은 교훈이 있다. 하네스 harness, 곧 모델을 감싸 실행 환경과 규칙을 붙여 주는 틀이 생기면 아무도 계획하지 않은 일을 사람들이 가져온다.

이 발표의 한 줄 에이전트는 쉬운 부분이었다. PR 1만 개를 지나며 망가진 건 에이전트가 아니라 에이전트를 둘러싼 모든 것이었다.

자막에는 "The thing that broke was an agent"로 적혀 있다. 바로 다음 문장("It was everything around them")과 발표 제목을 보면 "wasn't"를 잘못 받아 적은 것이라 그렇게 고쳐 읽었다.

이 노트의 숫자는 발표자 팀이 만든 사내 플랫폼에 대해 발표자가 직접 밝힌 것이다. 그 점을 감안해 읽자.

02

하네스가 제품이 된다 01:10

발표자는 먼저 선을 긋는다. 이 발표는 모델, 평가 evals, 순위표 leaderboard 이야기가 아니다. 모델 바깥의 일 이야기다.

  • 저장소를 체크아웃한다
  • 키를 쥐고 있는다
  • PR을 연다
  • 머지까지 가져간다
어느 시점이 되면 하네스가 제품이 된다.발표자 팀이 4월에 Spectre를 처음 소개한 글의 표현. 발표에서 인용

Claude Code와 Cursor가 있는데 왜 만드나 01:40

이 말을 하면 늘 같은 질문이 돌아온다. 발표자의 답은 짧다. "우리는 그들과 경쟁하지 않는다. 그들을 돌린다."

노트북에이전트는 강력하다하지만 늘릴 수가 없다. 현실적으로 5~10개가 한계다.
→
클라우드그 이상은 클라우드가 필요하다회사 비밀값, 실제 스택, 알림과 티켓, 하나의 규칙, 아무도 굶지 않을 만큼의 용량

비밀값 secrets은 API 키나 비밀번호 같은 접속 정보다. 실제 스택 real stack은 회사가 운영하는 서비스 구성 그대로를 말한다.

이 전부를 대신 갖춰 주는 도구는 없었다. 그래서 그 층을 직접 만들었다. 그리고 망가진 곳이 바로 그 층이다.

"이 전부를 갖춘 도구는 없었다"는 자막의 "Those single two owns that for us"를 "No single tool owns that for us"로 추정해 옮긴 것이다.

세 가지 이야기 02:20

  1. 코드 작성으로 경쟁하기를 멈춘 이야기
  2. 어떤 에이전트든 플랫폼을 몰 수 있게 한 이야기
  3. 그러자 무엇이 망가졌나
03

이야기 1: 에이전트는 골라 쓴다 02:40

Cursor를 쓰는 엔지니어가 늘자 같은 질문이 쏟아졌다.

  • 회사 비밀값을 Cursor에서 어떻게 쓰나?
  • 실제 스택을 상대로 어떻게 테스트하나?

그 기능을 Cursor 안에 다시 만들 수도 있었다. 그러면 다음 도구에서도, 그다음 도구에서도 또 만들어야 한다.

답은 한 문장이 됐다 03:00 "Cursor에게 Spectre를 쓰라고 하면 된다."

사람마다 좋아하는 에이전트가 있다. 그 취향은 계속 바뀐다. 그러니 각자 고른다. Claude Code, Codex, Cursor, 아니면 직접 손으로 해도 된다(자막이 뭉개져 추정).

노트북에서 시작한 세션을 클라우드로 올렸다가 다시 내려받을 수도 있다. Spectre는 이 모든 도구 아래에 깔린다.

사람이 고르는 것
  • 코드를 쓰는 에이전트
  • 노트북에서 할지, 클라우드에서 할지
플랫폼이 맡는 것
  • 비밀값과 실제 스택
  • 하나의 리뷰 대기열과 규칙
  • 머지와 용량
04

코드가 쓰인 뒤의 일 03:30

발표자는 코드가 쓰인 다음부터가 진짜 일이라고 말한다. 하룻밤의 흐름으로 보여 준다.

  1. 새벽 2시, Slack에 알림이 뜬다.
  2. 아무도 타이핑하지 않았는데 에이전트가 그 알림을 집어 든다.
  3. 에이전트가 수정 코드를 쓴다. 실제 스택의 복사본을 띄워 확인하고, 그 증거를 PR에 올린다.
  4. CI continuous integration가 실패하면 후속 루프가 실패 내용을 읽고 다시 수정을 올린다. 모두 자는 동안이다. CI는 코드를 올릴 때마다 빌드와 테스트를 자동으로 돌리는 장치다.
  5. 아침이면 PR은 하나뿐인 리뷰 대기열에 있다. 어떤 에이전트가 썼든 다른 PR과 같은 규칙을 따른다.
  6. 담당자에게 알림이 간다. 알림은 담당자의 근무 시간이 시작된 뒤에만 간다.
  7. 승인되면 에이전트가 자동 머지 automerge한다.

하나만 만든다면 후속 루프 04:10

발표자는 위 단계 중 하나만 만들 수 있다면 후속 루프 follow-up loop를 만들라고 한다. CI 실패를 읽고 고쳐서 다시 올리는 반복이다.

10월 초에 모든 사용자에게 이 루프를 켰다. 그달 백엔드 저장소에 머지된 에이전트 PR 5개 중 4개가 이 루프를 거쳤다.

코드를 쓰는 에이전트와 일을 끝내는 에이전트의 차이가 여기서 난다.발표자의 말을 옮김
05

팀 지식을 한곳에 04:40

팀마다 꼭 한 명씩 있다. 까다로운 서비스를 어떻게 테스트하는지 아는 사람, 어떤 플래그는 절대 건드리면 안 되는지 아는 사람이다.

그 지식은 그 사람의 머리나 노트북에만 있다. 그래서 지식이 머물 곳을 만들었다. 프로젝트 projects다.

누가프로젝트에서 하는 일
사람중요한 것을 적는다
에이전트일하면서 배운 것을 적는다
팀믿을 수 있는 스킬 skills을 고정해 둔다
플랫폼누가 무엇을 돌렸는지 기록을 남긴다

프로젝트 안에서 일하는 에이전트는 무엇이든 같은 페이지를 읽는다.

발표자의 의견 어떤 에이전트를 고르든 감사 기록 audit trail과 검사는 똑같아야 한다. 감사 기록은 누가 언제 무엇을 했는지 남는 기록이다.
06

이야기 2: 클릭하면 호출도 된다 05:10

5월에 Spectre에 일을 시키려면 브라우저 탭을 열거나 Slack에서 태그해야 했다. 그달 터미널에서 시작된 작업은 정확히 1건이었다.

새 규칙 05:30 사람이 클릭할 수 있는 것은 에이전트도 호출할 수 있어야 한다.

작업 시작, 후속 루프나 자동 머지 켜기, 페이지 게시를 모두 명령줄 도구 CLI로 할 수 있게 했다. 그러자 부를 수 있는 쪽이 늘었다.

  • 노트북에서 도는 에이전트
  • 샌드박스 sandbox, 곧 작업마다 따로 떼어 놓은 실행 환경 안의 에이전트
  • CI

웹 앱 사용이 줄어든 건 아니다. 나머지가 그 주변에서 자랐다.

터미널에서 시작한 작업이 브라우저에서 시작한 작업보다 더 많이 머지됐다는 취지로 들린다(자막이 뭉개져 추정).

새로운 사용자도 나타났다. 한 달에 작업을 수백 개 시작하면서 앱은 한 번도 열지 않는 사람들이다.

07

에이전트가 에이전트를 부린다 06:20

발표자도 이렇게 일한다. 10월에 큰 일이 생기자 Claude Code 세션을 띄우고 조정자 coordinator 역할을 맡겼다.

  1. 조정자가 티켓을 마일스톤 10개로 나눴다.
  2. 하나는 발표자 몫으로 남기고, 나머지는 Spectre에 넘겼다.
  3. 작업이 수백 개 생겼다. 작업마다 자기 샌드박스에서 처음부터 끝까지 검증했다.

10월 말부터는 또 다른 에이전트에게 "Spectre를 지켜봐 줘"라고 맡긴다(이 대목은 자막이 뭉개져 도구 이름을 알 수 없다). 그 에이전트는 이렇게 일한다.

  • Spectre가 답을 기다리는 질문을 모은다.
  • 발표자 대신 답변 초안을 쓴다.
  • 발표자가 승인하면 답을 돌려보낸다.

발표자가 친구에게 보낸 메시지가 이 상황을 요약한다. "Cursor든 Claude Code든 아무거나 써서 Spectre에 일을 쏟아붓는다."

꿈이자 문제 07:10 발표자는 이것이 꿈이면서 동시에 문제라고 말한다. 그 문제는 이야기 3에서 드러난다.
08

잠깐: 가장 느린 단계는 git 07:10

작업 시간이 실제로 어디에 쓰였는지 재 봤다. 가장 느린 단계는 모델이 생각하는 시간이 아니었다(자막의 "model syncing"을 thinking으로 추정).

git이었다. 회사의 저장소를 모두 체크아웃 checkout하는 데 평균 1분이 넘게 걸렸다.

해법 모든 머신에 모든 저장소의 사본을 둔다. 작업마다 그 사본을 빌려 쓴다.

예시(발표에 없는 내용): git에는 이미 있는 로컬 저장소의 데이터를 재사용하는 git clone --reference, 저장소 하나에서 작업 폴더를 여러 개 만드는 git worktree가 있다. 발표자 팀이 어떤 방식을 썼는지는 발표에 나오지 않는다.

09

이야기 3: 알림 하나가 작업 900개로 07:30

8월 중순, 버그가 든 릴리스가 나갔다. 버그 하나가 작업 수백 개로 불어난 경로는 이렇다.

  1. 그 버그는 워크스페이스 workspace마다 한 번씩 울리는 알림을 건드렸다.
  2. 버그 하나가 알림 수백 개가 되어 Slack 채널 한 곳에 쏟아졌다.
  3. 누군가 알림마다 에이전트를 태그하는 워크플로를 만들어 둔 상태였다.
  4. 태그 하나가 작업 하나를 시작했다.

평소 이 경로로 시작되는 작업은 하루 약 50개였다. 그날은 약 4시간 만에 약 900개가 시작됐다.

에이전트 900개가 같은 버그를 쫓았다. 결국 클러스터에 노드 하나 남지 않았다.

해법 08:10 발표자 말로는 "거의 지루한" 해법이었다. 같은 알림이 다시 오면 새 작업을 만들지 않는다. 이미 열려 있는 조사에 합류한다.
10

노트북 한 대가 클러스터를 채우다 08:20

두 달 뒤 같은 일이 또 일어났다. 이번엔 봇이 아니었다.

10월, 한 엔지니어가 플랫폼 팀이 모두에게 권해 온 일을 그대로 했다. Spectre에 일을 넘긴 것이다. 명령줄로 약 3시간 동안 작업 약 950개를 시작했다.

클러스터가 꽉 찼다. 플랫폼에서 아무것도 돌아가지 않았다. 다른 모든 사람의 작업이 노트북 한 대 뒤에 줄을 섰다.

그건 사용자 문제가 아니다. 우리 문제다.발표자의 말을 옮김

공정한 실행 대기열 08:50

4일 뒤 제대로 된 해법이 나왔다. 공정 실행 대기열 fair launch queue이다.

규칙내용
줄 서기작업을 시작하면 대기열 자리를 받는다. 자리가 나면 디스패처 dispatcher가 작업을 시작한다
사람 우선키보드 앞에 앉아 기다리는 사람의 작업이 먼저다
공정한 몫모두 공정한 몫을 받는다. 클러스터가 한가할 때는 더 빌려 쓸 수 있다
순번 보기작업을 시작하면 대기열 몇 번째인지 보인다

효과가 있었나 09:30

  • 8월에는 한 주에서 가장 바쁜 날 작업이 약 2,000개 돌았다(자막이 뭉개져 추정). 10개 중 1개꼴로 끝나지 못했다.
  • 11월 4일에는 그 두 배가 넘게 돌았다. 끝까지 가는 비율도 훨씬 나아졌다.
  • 발표자는 아직 개선할 여지가 있다고 덧붙였다.

발표자는 조심스럽게 말한다. 여러 가지를 한꺼번에 바꿨기 때문에 어느 수정이 가장 중요했는지는 모른다. 다만 몰려드는 작업은 계속 커졌고, 플랫폼은 버텼다.

발표자 팀이 직접 만든 사내 플랫폼을 스스로 잰 결과다. 외부에서 확인한 숫자가 아니라는 점을 감안해 읽자.

병목은 머지로 옮겨 간다 10:00

실행 쪽이 겨우 잡히자 병목이 옮겨 갔다.

10월 말, 사내 개발 플랫폼 팀이 경보를 울렸다. 회사 전체 PR 수가 한 달 만에 약 60% 늘었다.

머지 큐 merge queue는 거듭 꺼야 했다. 머지 큐는 PR을 줄 세워 최신 main 기준으로 검사한 뒤 차례로 합치는 장치다.

그래서 지금은 PR 하나가 main 위로 리베이스 rebase하고, CI를 다시 돌리고, 통과하면 머지된다.

위험 main이 깨지면 모두의 CI가 함께 깨진다.

발표자는 이 문제를 아직 풀지 못했다고 솔직하게 말한다.

사람 없이 도는 자동화 10:40

이 문제들을 고치는 동안 다른 것이 조용히 자랐다.

지금까지 본 일은 대부분 사람이 요청해서 시작됐다. Spectre에서 가장 빨리 늘어나는 일은 그렇지 않다. 자동화 automations다.

자동화는 정해진 시간이나 이벤트에 깨어나 스스로 일하는 에이전트다. 발표에 나온 예는 이렇다.

  • 알림을 분류한다 (트리아지 triage)
  • PR을 읽는다
  • 글을 쓴다

지난달 약 110명이 자동화를 돌리고 있었다. 전체 사용자 약 460명의 4분의 1쯤이다(노트에서 계산).

첫날부터 붙이는 안전장치 11:10 5번 연속 실패하면 스스로 꺼진다. 예산을 달 수 있다. 만료일을 달 수 있다.

이유는 앞의 두 사고와 같다. 아무도 지켜보지 않을 때는 에이전트도 작업 수천 개를 시작할 수 있다.

아직 답이 없는 질문 11:30

발표자가 다음으로 쫓는 질문들이다. 발표자 스스로 아직 답이 없다고 밝힌다.

  • 모든 Slack 채널에 로그오프하지 않는 전용 에이전트가 있다면? 대화를 따라가다 스스로 일을 시작하는 에이전트다.
  • 모든 PR이 사람이 보기 전에 스스로 동작한다는 증거를 갖춘다면? 지금은 머지 20건 중 1건만 그런 증거를 갖고 있다.
  • 에이전트가 PR을 쉬지 않고 연다면, 머지는 어떻게 하나?

발표자는 "6개월 뒤에 다시 물어보면 무엇이 망가졌는지 말해 주겠다"고 정리한다.

다시 해도 할 세 가지 12:10

이런 것을 만들고 있다면, 발표자는 이 세 가지를 다시 하겠다고 한다. 세 이야기와 하나씩 짝이 맞는다.

교훈나온 이야기
코드가 쓰인 뒤의 일을 책임진다이야기 1: 실제 스택에서의 증명, 후속 루프, 하나의 리뷰 대기열, 자동 머지
모든 동작을 에이전트가 호출할 수 있게 만든다이야기 2: CLI 작업 월 1건 → 약 6,500건
에이전트, 사람, 알림이 시작할 수 있는 양에 상한을 둔다. 얼마나 시작할 수 있는지 그들이 알아채기 전에이야기 3: 작업 900개와 950개, 공정 실행 대기열
엔지니어는 어떤 에이전트로든 코드를 쓸 수 있다. 오래 남는 일은 그 코드를 돌리고, 확인하고, 머지까지 가져가는 하네스다.발표자의 마지막 말을 옮김. 자막의 "the work that's lost"는 "the work that lasts"로 추정
15

핵심 정리

  1. PR 1만 개를 지나며 망가진 건 에이전트가 아니라 주변이었다. 실행 환경, 호출 방식, 용량, 머지다.
  2. 노트북 에이전트는 5~10개가 한계다. 그 이상은 비밀값, 실제 스택, 규칙, 용량을 갖춘 클라우드 하네스가 필요하다.
  3. 플랫폼은 에이전트 도구와 경쟁하지 않고 그 도구들을 돌린다. 어떤 에이전트를 쓰든 감사 기록과 검사는 같아야 한다.
  4. 코드가 쓰인 뒤가 진짜 일이다. 실제 스택에서 증명하고, 같은 리뷰 대기열에 넣고, 근무 시간에 알리고, 승인되면 자동 머지한다.
  5. 하나만 만든다면 후속 루프다. 머지된 백엔드 에이전트 PR 5개 중 4개가 거쳤다.
  6. 팀 지식은 프로젝트에 모은다. 사람과 에이전트가 함께 적고, 모든 에이전트가 같은 페이지를 읽는다.
  7. 클릭할 수 있으면 호출할 수 있어야 한다. CLI 작업이 월 1건에서 약 6,500건이 됐다.
  8. 호출이 쉬워지면 폭주가 온다. 중복 알림은 열린 조사에 합치고, 공정 실행 대기열로 한 사람이 클러스터를 독차지하지 못하게 한다.
  9. 실행이 풀리면 병목은 머지로 간다. PR은 약 60% 늘고 머지는 1시간을 넘겼다. 아직 풀지 못했다.
  10. 사람 없이 도는 자동화에는 첫날부터 안전장치를 단다. 5번 연속 실패 시 중지, 예산, 만료일이다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표 제목의 "주변"은 무엇을 가리키나?
모델 바깥의 일이다. 저장소 체크아웃, 키 보관, PR 열기, 머지까지 가져가기, 그리고 작업을 돌릴 용량과 규칙이다.
Q2Claude Code나 Cursor가 있는데 왜 플랫폼을 직접 만들었나?
그 도구들과 경쟁하려는 게 아니라 그 도구들을 돌리려는 것이다. 노트북에서는 에이전트 5~10개가 한계다. 그 이상은 비밀값, 실제 스택, 알림과 티켓, 하나의 규칙, 충분한 용량을 갖춘 클라우드가 필요한데, 이걸 다 가진 도구는 없었다.
Q3후속 루프는 무엇이고, 하나만 만든다면 왜 이것인가?
CI 실패를 읽고 고쳐서 다시 올리는 반복이다. 코드를 쓰는 에이전트를 일을 끝내는 에이전트로 바꾼다. 10월 백엔드 저장소에 머지된 에이전트 PR 5개 중 4개가 이 루프를 거쳤다.
Q4프로젝트 기능에서 사람, 에이전트, 팀은 각각 무엇을 하나?
사람은 중요한 것을 적는다. 에이전트는 일하며 배운 것을 적는다. 팀은 믿을 수 있는 스킬을 고정해 둔다. 누가 무엇을 돌렸는지는 기록으로 남는다.
Q5"클릭할 수 있으면 호출할 수 있다" 규칙 뒤에 무엇이 바뀌었나?
터미널 작업이 월 1건에서 약 6,500건이 됐다. 노트북 에이전트, 샌드박스 안 에이전트, CI가 플랫폼을 부를 수 있게 됐다. 앱을 열지 않고 작업을 수백 개 시작하는 사용자도 생겼다.
Q6작업 시간에서 가장 느린 단계와 그 해법은?
모델이 아니라 git 체크아웃이었다. 평균 1분이 넘었다. 모든 머신에 모든 저장소 사본을 두고 작업마다 빌려 쓰게 했다.
Q78월에 버그 하나가 작업 900개로 불어난 경로와 해법은?
버그 → 워크스페이스마다 알림 → 알림마다 에이전트 태그 → 태그마다 작업. 해법은 같은 알림이 다시 오면 이미 열린 조사에 합류시키는 것이다.
Q810월 사고를 발표자가 "우리 문제"라고 한 이유는?
엔지니어는 플랫폼 팀이 권한 대로 Spectre에 일을 넘겼을 뿐이다. 한 사람이 얼마나 시작할 수 있는지 막는 장치가 플랫폼에 없었다.
Q9공정 실행 대기열의 규칙 네 가지는?
시작하면 대기열 자리를 받고 자리가 나면 시작한다. 키보드 앞에 앉은 사람이 먼저다. 모두 공정한 몫을 받고 한가할 때는 더 빌려 쓴다. 자기 순번이 보인다.
Q10발표자가 개선 효과를 조심스럽게 말한 이유는?
여러 가지를 한꺼번에 바꿔서 어느 수정이 가장 효과였는지 가릴 수 없었다. 확실한 건 몰려드는 작업이 커지는 동안 플랫폼이 버텼다는 것뿐이다.
Q11머지가 새 병목이 된 이유와 그 위험은?
PR이 한 달 만에 약 60% 늘었다. 머지 큐를 거듭 꺼야 했고, PR마다 리베이스, CI 재실행, 머지를 거친다. main이 깨지면 모두의 CI가 함께 깨진다.
Q12자동화에 첫날부터 붙인 안전장치와 그 이유는?
5번 연속 실패하면 스스로 꺼지고, 예산과 만료일을 달 수 있다. 아무도 지켜보지 않을 때는 에이전트도 작업 수천 개를 시작할 수 있기 때문이다.

용어 정리

용어뜻
하네스Harness. 모델을 감싸 실행 환경, 도구, 규칙, 검사를 붙여 주는 틀. 이 발표에서는 저장소 체크아웃, 비밀값, PR, 머지까지 포함한다
클라우드 에이전트개인 노트북이 아니라 회사 서버에서 도는 에이전트
비밀값Secrets. API 키, 비밀번호처럼 밖에 새면 안 되는 접속 정보
실제 스택Real stack. 회사가 운영하는 서비스 구성 그대로. 그 복사본을 띄워 테스트한다
체크아웃Checkout. 저장소의 코드를 작업 폴더로 내려받아 펼치는 일
CIContinuous integration. 코드를 올릴 때마다 빌드와 테스트를 자동으로 돌리는 장치
후속 루프Follow-up loop. CI 실패를 읽고 고쳐서 다시 올리는 반복
자동 머지Automerge. 승인과 검사를 통과하면 사람이 버튼을 누르지 않아도 합쳐지는 것
샌드박스Sandbox. 작업마다 따로 떼어 놓은 실행 환경
스킬Skill. 에이전트가 불러 쓰는 작업 절차와 지시 묶음
감사 기록Audit trail. 누가 언제 무엇을 했는지 남는 기록
CLICommand-line interface. 터미널에서 명령으로 쓰는 도구
조정자Coordinator. 큰 일을 쪼개 다른 에이전트에게 나눠 주는 에이전트
클러스터 / 노드Cluster / node. 작업을 돌리는 서버 묶음과, 그 안의 서버 한 대
공정 실행 대기열Fair launch queue. 작업을 줄 세워 자리가 날 때 시작하고, 한 사람이 용량을 독차지하지 못하게 몫을 나누는 장치
디스패처Dispatcher. 대기열에서 작업을 꺼내 실행 자리를 배정하는 구성 요소
부하 테스트Load test. 일부러 요청을 한꺼번에 많이 넣어 버티는지 보는 시험
머지 큐Merge queue. PR을 줄 세워 최신 main 기준으로 검사한 뒤 차례로 합치는 장치
리베이스Rebase. 내 변경을 최신 main 위로 옮겨 다시 쌓는 일
main모든 변경이 최종적으로 합쳐지는 기준 브랜치
자동화Automation. 사람이 요청하지 않아도 정해진 시간이나 이벤트에 깨어나 일하는 에이전트
트리아지Triage. 알림이나 이슈를 분류하고 우선순위를 정하는 일
