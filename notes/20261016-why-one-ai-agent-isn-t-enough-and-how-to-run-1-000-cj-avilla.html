에이전트 하나로는 왜 부족한가, 그리고 천 개는 어떻게 굴리나

에이전트 하나는 큰 일을 맡기면 게을러지고, 자기 결과를 편애하고, 목표를 잊는다. Anthropic은 Claude가 스스로 에이전트 팀을 짜서 단계별로 일하게 하는 "플로우"를 내놓았다. 최대 1,000개까지 띄울 수 있고, 안전은 선언·격리·감지 세 축으로 지킨다.

원본 영상: Why One AI Agent Isn’t Enough (And How to Run 1,000) 발표: CJ Avilla, Harrison Stall (Anthropic 기술 스태프)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다. 1시간을 넘는 곳은 h:mm:ss로 적었다. 발표 후반 약 30분과 끝부분은 청중 질의응답이다.

두 발표자는 모두 Anthropic 소속이고, 발표 내용은 Anthropic의 유료 API 제품(Claude 관리형 에이전트) 소개다. 제품의 장점과 비교 수치는 그 점을 감안해 읽자.

3분 요약
  1. 소프트웨어 역사는 한 사람의 머리에서 신뢰 계층을 가진 네트워크로 조직을 키워 온 역사다. 유닉스 한 달, OS/360 천 명, 리눅스 2,600명. 에이전트도 같은 길을 간다.
  2. 플로우flows는 Claude 관리형 에이전트 API의 새 기능이다. 리드 에이전트가 계획을 세우고, 단계마다 서브 에이전트를 스스로 띄우고 거둔다. 사람이 구조를 그려 주지 않는다.
  3. 에이전트 하나는 세 가지에 약하다. 게으름(35개 보고 "다 괜찮겠지"), 자기 편애(내가 쓴 코드는 좋다), 목표 이탈(컨텍스트가 압축되며 "프로덕션은 건드리지 마"가 사라진다). 플로우는 일을 쪼개 격리된 컨텍스트에 맡겨 이 셋을 피한다.
  4. 단계마다 자원을 다르게 쓴다. 검색 단계는 값싼 Haiku 2개, 검토 단계는 Fable 2~3개처럼 늘리고 줄인다. 플로우는 비용이 훨씬 더 들지만 훨씬 더 많이 찾는다.
  5. 플로우는 한 번에 최대 1,000개 에이전트를 쓸 수 있다. 발표자는 "유닉스 호환 운영체제를 만들라"는 한 줄 프롬프트로 85시간째 돌아가는 프로젝트를 보여 줬다.
  6. 안전은 선언·격리·감지다. 에이전트의 권한과 도구를 선언하고, 네트워크와 비밀 정보를 물리적으로 격리하고, 모든 행동을 이벤트 스트림으로 감지한다. 비밀 키는 컨테이너에 가짜 값만 있고 나가는 길목에서만 진짜로 바뀐다.
  7. 오늘 할 일: 예산을 걸고, 권한 정책을 자동 모드로 바꾸고, 비밀 키는 볼트에 넣는다. 템플릿에서 시작해 자기 일에 맞게 다듬는다.
01

유닉스 한 달, OS/360 천 명 00:00

CJ Avilla는 운영체제 세 개의 이야기로 시작한다. 셋은 "일을 몇 사람이 어떻게 나눠 맡았나"가 다르다.

  • 유닉스, 1969년. Ken Thompson은 가족이 한 달 집을 비운 사이 혼자 커널, 편집기, 어셈블러를 한 주씩 만들었다. 한 사람이 프로젝트 전체를 머리에 담고 끝까지 끌고 가는 것을 개념적 완결성conceptual integrity이라 부른다.
  • OS/360, 1960년대 IBM. 하드웨어를 바꾸면 소프트웨어를 전부 다시 쓰던 시절에 회사 명운을 걸고 만든 운영체제다. 약 5,000인년이 들 거라 보고 엔지니어 1,000명을 투입했다. 관리자였던 Fred Brooks는 교훈을 맨먼스 미신The Mythical Man-Month에 적었다. 핵심 하나가 외과 수술팀 구조다. 전체를 머리에 담은 집도의 한 명과 전문가 열 명 정도가 둘러싼다.
  • 리눅스 7.2, 2026년. 9주 동안 300여 회사의 개발자 2,600여 명이 기여했다. 처음부터 이랬던 건 아니다.

"Linus는 확장되지 않는다" 03:10

1998년 커널 메일링 리스트에서 Linus Torvalds는 지쳐 있었다. 패치를 보낸 사람들이 "세 번 보냈는데 왜 안 넣느냐"고 재촉했고, Linus는 "휴가 간다, 메일함에서 나가라"고 폭발했다. 다음 날 Larry McVoy가 글을 올렸다. "문제는 Linus가 확장되지 않는다는 것이다." 자기 버전 관리 제품 홍보도 끼어 있었다.

약 4년 뒤인 2002년 Linus는 인정했다. 모두가 자기에게 직접 보내는 별 구조를 버리고, 신뢰하는 메인테이너들이 먼저 검토하고 예외만 위로 올리는 네트워크 구조로 바꿨다. 발표 슬라이드에서 별 구조에는 행위자가 36명 모여 있었고, 네트워크 구조에서는 한 층에 많아야 4명이 보고했다.

이 이야기를 하는 이유 에이전트 여러 개를 굴리는 사람은 지금 1998년의 Linus 자리에 있다. 에이전트가 PR을 쏟아 내고 사람은 GitHub에서 승인 버튼을 누르며 병목이 된다. 해법도 같다. 신뢰 계층을 가진 조직을 만들고 자기는 꼭대기에만 남는다.

발표자는 샌프란시스코 AI Engineer 행사에서 Anthropic의 Tarek과 Gary(추정)가 "이제 무리하게 야심을 가져라, 바다를 끓여라"고 말했다고 전한다. 이 발표는 그 말을 받아 "그 큰 일을 어떻게 조직하나"를 다룬다.

플로우: Claude가 팀을 스스로 짠다 06:00

CJ Avilla와 Harrison Stall은 Anthropic 기술 스태프다. 발표 사흘 전인 금요일에 Claude 관리형 에이전트Claude managed agents에 플로우flows라는 기능이 추가됐다. 관리형 에이전트 자체는 4월에 나왔다.

플로우는 멀티 에이전트 오케스트레이션의 다음 단계다. 사람이 "에이전트 1은 이걸 하고, 에이전트 2는 1이 끝나길 기다렸다가 저걸 한다"고 구조를 그려 주지 않는다. Claude가 자기 멀티 에이전트 구조를 통째로 짜고 운영한다.

Claude Code의 동적 워크플로우가 원형이다 07:40

Claude Code에서 "ultra code를 써서 X를 하라"고 하면 Claude가 복잡한 에이전트 망을 알아서 띄운다. 내부에서는 JavaScript 엔진이 맵리듀스 같은 작업을 받친다. 분류, 분산 후 종합, 적대적 검증 같은 구조를 사람이 그리는 대신 Claude가 학습된 능력으로 고른다. 플로우는 이 방식을 API로 꺼낸 것이다.

단일 에이전트한 시간쯤 버틴다야심이 조금만 커져도 먼저 넘어진다. 발표자도 "대략적인 숫자"라고 했다

04

Claude 관리형 에이전트란 12:10

청중의 절반 정도가 들어 봤다고 손을 들었다. 관리형 에이전트는 에이전트의 생애를 Anthropic이 대신 관리해 주는 API다.

개념뜻
에이전트 agent스킬, 도구, MCP 서버 목록으로 정의한다. 상태를 가진 API 리소스다
세션 session"실제 일을 해 달라"는 요청 하나. 에이전트를 세션 안에 띄우면 알아서 일한다
환경 environmentClaude가 쓰는 컴퓨터. 컴퓨터를 주면 능력이 크게 오른다. 직접 호스팅한 샌드박스도 쓸 수 있다
이벤트 로그지속되는 로그 하나로 모든 일을 실시간으로 지켜본다

멀티 에이전트 1판에서 동적 워크플로우로 13:10

5월에 나온 1판에서는 서브 에이전트를 하나하나 정의하고, 각 에이전트가 도는 스레드thread를 모두 들어야 했다. 운영체제의 프로세스와 스레드처럼 각 스레드는 자기 컨텍스트를 갖고, 상태를 나누려면 메시지를 주고받아야 했다. 가능하긴 했지만 쉽지 않았다.

지난 금요일에 나온 동적 워크플로우는 다르다.

  1. 리드 에이전트가 일을 받는다. 예: "백만 줄짜리 모노레포를 Python에서 Rust로 옮겨라."
  2. 리드가 계획을 세우고, 스스로 서브 에이전트를 띄우고 거둔다.
  3. 여러 단계phase를 거치며 작고 검증 가능한 일 단위를 끝낸다. 1단계는 탐색 에이전트들이 파일을 읽고, 2단계는 무언가를 가려내는 식이다.
  4. 사람은 에이전트 사이의 연결을 관리하지 않는다.

도는 동안 할 수 있는 일은 셋이다. 단일 이벤트 스트림으로 에이전트별 행동을 실시간으로 본다. 세션에 예산을 걸어 토큰이 새지 않게 한다. 방향이 틀렸으면 API로 중단한다.

Claude Code와 무엇이 다른가 16:20

Claude Code 동적 워크플로우관리형 에이전트 플로우
쓰는 자리터미널에 앉아 대화하며 쓴다API다. 내 제품, 내부 프로세스, CI 어디든 붙인다
시작 방식사람이 입력한다스케줄, 웹훅(예: GitHub PR) 등으로 자동 시작한다
대표 사례지금 손에 든 코드 작업PR마다 돌아가는 버그 헌터
05

콘솔 데모: 주식 워치리스트 스캐너 17:20

Harrison Stall이 Claude 콘솔에서 플로우를 하나 띄웠다. 콘솔은 API 사용자가 Anthropic의 모든 리소스를 관리하는 곳이다.

  1. 왼쪽 메뉴 "관리형 에이전트"로 들어간다. 빠른 시작에 클릭 한 번으로 돌릴 수 있는 워크플로우들이 있고, 맨 아래에 "동적 워크플로우" 탭이 있다.
  2. 금융 쪽 청중이 많아 주식 워치리스트 스캐너 템플릿을 골랐다. 설정은 모델 Opus 5.5, 타입 multi-agent 2026-10-01, 그리고 에이전트의 성격을 정하는 시스템 프롬프트다. 템플릿을 쓰면 뒤에서 에이전트 리소스가 만들어진다.
  3. 에이전트에는 환경이 필요하다. Claude가 일할 컴퓨터다. 미리 만들어 둔 환경을 골라 세션을 시작했다.
  4. 종목으로 Apple, Nvidia, Amazon, JPM, XOM, COST를 넣고 엔터를 쳤다. 여기서 실제 멀티 에이전트 오케스트레이션이 시작된다.

세션 화면에는 피라미드 꼭대기의 리드 에이전트, 환경, 그리고 실시간 진행이 보인다. Claude가 스스로 정한 에이전트 묶음으로 단계를 밟아 가고, 컨텍스트 창 하나에 해당하는 세션 스레드들이 병렬로 떠 있다. 먼저 돌려 둔 세션은 단계마다 에이전트 6개 정도가 동시에 돌았다. 에이전트 수는 Claude가 일의 복잡도에 맞춰 늘리고 줄인다.

06

콘솔에서 코드로 23:10

CJ Avilla가 이어받는다. 보통 콘솔에서 플로우를 시험해 보고, 만족하면 자기 애플리케이션에 붙인다. 장 시작 5분 전에 매일 돌리거나, Slack에서 트리거하는 식이다.

코드는 단순하다. 에이전트를 만들 때 멀티 에이전트 설정을 켜고, 리드 에이전트에 보내는 첫 이벤트에 "워크플로우를 돌려라"고 쓴다. 이 둘로 플로우가 돈다. 기본값으로는 Claude가 필요한 서브 에이전트를 즉석에서 만든다.

더 쥐고 싶을 때

A가 B에 메시지를 보내게 하는 API는 없다. 공유 파일 시스템으로 주고받는다. 메시지 송수신 이벤트로 관찰은 할 수 있다.
Q9버그 헌터의 단계를 순서대로 말해 보라.
코드를 조각으로 나눠 조각마다 리뷰 → 다른 에이전트가 지적에 동의·반대 → 후보 선별 → 저장소를 내려받아 재현하는 증명 → PR 줄에 심각도와 함께 댓글.
Q10자격 증명이 샌드박스에서 새지 않는 원리는?
컨테이너에는 작동하지 않는 가짜 값만 있다. 요청이 나가는 출구 프록시에서만 진짜 값으로 바뀌고, 그것도 허용한 호스트로 갈 때만이다. Claude를 설득해도 꺼낼 것이 없다.
Q11선언·격리·감지는 각각 무엇인가?
선언: 에이전트의 권한·도구·스킬·인격을 적는다. 격리: 접근 도메인과 도구를 물리적으로 제한해 최악의 피해를 줄인다. 감지: 이벤트 스트림을 듣고 바로 중단한다.
Q12발표자가 "가장 쉬운 개선"이라고 한 것과 그 근거는?
권한 정책을 "항상 묻기"에서 자동 모드로 바꾸는 것. 사람은 97%를 그냥 승인하지만 Claude는 도구 호출마다 파괴적인지 끈기 있게 판단한다.
