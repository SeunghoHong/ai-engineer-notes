에이전트는 왜 내 CLI를 싫어하나

에이전트는 CLI가 불편해도 불평하지 않는다. 대신 head, grep, tail 같은 파이프로 출력을 잘라 쓴다. 같은 파이프가 반복되면 그게 버그 리포트이고, 트랜스크립트를 읽으면 무엇을 고칠지 보인다.

원본 영상: Your Agent Hates Your CLI 발표: Ayush Bhardwaj (Allos AI)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용하거나 직접 잰 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Cloud Code → Claude Code, Infraost → Infracost, Doug DB → DuckDB 등)은 알려진 이름으로 바로잡았다. 확실하지 않은 것에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트는 CLI가 불편해도 버그 리포트를 쓰지 않는다. 출력을 잘라 쓰는 파이프가 그 불편의 흔적이다.
  2. 발표자가 모은 호출 약 2만 건 중 4분의 1이 출력을 필터로 넘겼다. 읽기 위주 명령은 절반을 넘었다.
  3. 파이프는 실패를 숨길 수 있다. 실패하면 크게 알리고, 마지막 줄에 짧은 요약과 전체 로그 경로를 둔다.
  4. 같은 자르기를 매번 손으로 쓰는 것이 파이프 세금이다. 파이프의 83%는 10번 이상 반복된 패턴이었다.
  5. 기능을 넣었으면 스킬과 help로 가르친다. 에이전트는 문서를 글자 그대로 따른다. 낡은 문서는 버그다.
  6. 먼저 만들 것은 범위와 개수 제한이다. 큰 출력은 기본으로 줄이고, 더 보는 법을 출력에 적는다.
  7. 토큰만 재지 말고 턴 수와 정답 여부를 잰다. 트랜스크립트는 아직 읽지 않은 제품 분석 자료다.
01

세 번의 자르기 00:00

발표자 Ayush Bhardwaj는 에이전트가 지난 세션의 맥락을 다른 도구에서도 다시 쓰게 해 주는 CLI를 만들었다. 그 도구를 다듬다가 에이전트가 CLI를 몰래 싫어하는 이유를 알게 됐다. 발표는 세 개의 실제 호출로 시작한다.

에이전트원한 것한 일깔린 가정
Claude Code문서 페이지의 설정 하나페이지 전체를 받아 grep으로 찾고, 결과를 40줄로 잘랐다답은 검색 결과 앞쪽 40줄 안에 있다
Codex취약한 의존성의 개수JSON 보고서 전체를 받아 마지막 40줄만 남겼다합계는 보고서 끝에 있다
Cursor실패한 테스트 하나테스트 출력의 마지막 80줄만 남겼다실패 내용은 끝 80줄 안에 있다

세 번 모두 답은 남긴 부분 안에 있었다. 그래도 자르기마다 "답은 출력의 이쯤에 있다"는 가정이 들어 있다. 이 가정 때문에 도구를 만든 사람은 에이전트가 겪는 불편을 보지 못한다.

파이프pipe는 |로 한 명령의 출력을 다음 명령에 넘기는 것이다. 파이프 하나만 보면 알 수 있는 게 별로 없다. 같은 파이프가 계속 다시 쓰이면, 도구에 무언가 빠져 있다는 신호다.

세 호출은 모두 발표자의 트랜스크립트transcript에 있던 실제 기록이다. 트랜스크립트는 에이전트 세션의 대화와 도구 호출을 남긴 기록이다. Claude Code 사례는 이 발표 원고를 검토하던 에이전트가 한 일이다. 발표자는 "그런데도 참지 못했다"고 덧붙였다.

02

에이전트는 불평하지 않는다 01:00

에이전트는 불편한 도구를 만나도 버그 리포트를 쓰지 않는다. 대신 그 프로그램을 감싸는 작은 프로그램을 짜서 문제를 피해 간다. 파이프가 바로 그런 작은 프로그램이다.

Sanity의 MCP 서버 01:10 콘텐츠 플랫폼 Sanity는 6월에 자사 MCP 서버 운영기를 공개했다. MCP 서버Model Context Protocol server는 에이전트가 부를 수 있는 도구를 제공하는 서버다. 출시 이후 2만 개가 넘는 에이전트가 도구를 약 300만 번 불렀다. 버그 리포트는 한 건도 없었다. 그래서 Sanity는 "피드백 보내기" 도구를 추가했다. 불평할 곳이 생기자 에이전트들이 무엇이 문제인지 말하기 시작했다.

발표자는 피드백 도구가 없어도 시작할 수 있다고 말한다. 피드백은 이미 트랜스크립트 안에 있다.

03

2만 번의 호출 중 4분의 1 01:40

발표자는 자기 트랜스크립트에서 에이전트 호출 약 2만 건을 뽑았다. 표본에는 CLI 14개가 나왔다. git, GitHub CLI, cargo, curl, npm, docker 등이다.

그중 4분의 1은 출력을 필터로 넘겼다. 필터는 head, grep, tail, python, sort, wc처럼 출력의 일부만 남기거나 가공하는 명령이다. 읽기 위주 명령에서는 이 비율이 절반을 넘었다.

하네스harness에 따라 차이가 크다. 하네스는 모델을 감싸 도구 실행 방식과 출력 한도를 정하는 실행 틀이다. 예를 들어 Codex는 에이전트가 호출마다 출력 한도를 정할 수 있다. 그래서 파이프를 훨씬 덜 쓴다.

04

파이프가 실패를 숨길 때 02:00

파이프는 잡음만 자르는 게 아니다. 실패도 가릴 수 있다.

명령은 끝날 때 종료 코드exit code를 돌려준다. 0이면 성공이다. bash에서 pipefail 옵션을 켜지 않으면, 파이프 전체의 종료 코드는 마지막 명령의 것이 된다. 그래서 cargo test를 head로 넘기면 테스트가 실패해도 성공으로 보고될 수 있다.

발표 화면의 예는 컴파일 오류가 났는데 초록 점(성공 표시)이 뜬 경우다. 이때는 상태만 틀렸다. 에이전트는 오류 내용을 읽을 수 있었다.

더 나쁜 경우: 오류가 잘려 나간다 02:30 GitHub의 Claude Code 이슈에 올라온 사례다. 스크립트가 ReferenceError를 내고 오류 코드로 끝났다. 그런데 tail이 보여 준 마지막 세 줄은 아무 문제 없어 보였다. Claude는 성공이라고 보고했다. 오류는 모델에 닿지도 못했다.
발표자의 조언 02:50 도구가 실패하면 크게 실패한다. 출력의 맨 마지막 줄은 짧은 요약과 전체 로그의 경로로 채운다. 에이전트가 끝부분만 잘라 읽어도 실패를 놓치지 않는다.
05

파이프 세금 03:00

발표자가 만든 도구는 chat history다(이름은 들린 대로 적었다). 코딩 에이전트가 Claude Code, Codex, Cursor에서 했던 지난 세션을 검색하게 해 주는 작은 CLI다. 스킬skill이 함께 들어 있다. 스킬은 에이전트에게 도구를 언제, 어떻게 쓸지 알려 주는 문서다.

발표자는 이 도구의 사용자인 에이전트를 관찰했다. 10월 점검에서 호출 약 1,000건을 기록했다. 방법은 간단하다. 에이전트가 호출 직후에 무엇을 하는지 본다. 에이전트가 부르는 어떤 도구에도 쓸 수 있다.

80% 03:30 에이전트가 이 도구로 옛 세션을 열 때, 5번 중 4번은 출력이 곧장 grep, sed, head, tail, Python으로 들어갔다.

발표자는 이걸 파이프 세금pipe tax이라고 부른다. 파이프로 쓸데없는 내용을 컨텍스트에서 빼는 것 자체는 괜찮다. 세금은 에이전트가 같은 자르기 명령을 매번 손으로 다시 쓰는 데 있다. 한 번 한 번은 작고, 대개는 통한다. 하지만 매번 "답이 어디 있을지"를 새로 추측하는 일이다.

chat history는 발표자 자신의 도구다. 이 노트에 나오는 80%, 82% 같은 사례 수치는 발표자가 자기 도구에서 잰 것이다. 발표자는 마지막에 이 도구를 소개한다. 그 점을 감안해 읽자.

에이전트가 알아서 자르면 되지 않나 03:50

Hacker News의 "에이전트용 CLI 설계" 스레드에 나온 반론이 있다. 출력을 얼마나 읽을지는 에이전트에게 맡기라는 것이다. 에이전트는 grep이나 head를 충분히 잘 쓴다.

발표자는 반만 동의한다. 에이전트는 잘 쓰고, 한 번뿐인 일이라면 그렇게 하는 게 맞다. 하지만 일상 CLI 전체에서 파이프의 83%는 10번 이상 나온 패턴이었다. 같은 CLI 하위 명령에 같은 파이프 도구를 붙인 것이다. 인자는 달라도 에이전트가 원하는 것은 계속 같았다.

크기 상한으로는 부족하다 04:30

에이전트가 잘라 내는 출력은 대개 크다. 발표자는 긴 세션 하나를 두 가지로 열어 봤다.

하네스도 출력 크기에 상한을 둔다. 하지만 크기 상한은 어떤 메시지가 중요한지 모른다. 선택 플래그selection flag는 다르다. 에이전트가 원하는 부분을 도구에 직접 말하게 해 준다.

06

우회를 기능 요청으로 읽기 05:00

발표자는 자기 도구에서 고친 세 가지를 예로 든다. 표의 왼쪽 열을 버그 리포트로 읽으라고 했다.

에이전트가 쓴 우회우회가 하는 말발표자가 더한 기능
rg, sed(추정)로 출력 거르기"원하는 부분만 고르게 해 줘"읽기 명령이 검색어 주변만, 일치하는 메시지만, 또는 크기 상한을 둔 마지막 몇 개만 돌려준다
JSON 출력에 Python 돌리기"필드를 줄여 줘"검색에 간결 모드compact를 넣었다. 결과 하나에 한 줄이다. 같은 결과를 JSON보다 약 6배 작게 준다
inspect를 for 루프로 여러 번 호출"여러 세션을 한 번에 묻게 해 줘"한 번 호출로 여러 세션을 요약한다. inspect 호출의 약 3분의 1이 이런 손 루프였다

발표자의 말로는, 로드맵이 자기 명령을 둘러싼 명령들 안에 있었다. 무엇을 만들어야 할지는 에이전트가 앞뒤에 붙인 명령이 알려 줬다.

Infracost도 같은 것을 찾았다 06:00

클라우드 비용 도구 Infracost는 5월에 같은 발견을 글로 공개했다. 에이전트들이 JSON 덤프 위에 jq와 Python 파이프라인을 짜고 있었다. jq는 JSON을 거르고 가공하는 명령줄 도구다.

Infracost는 세 가지를 했다. 필터링을 CLI 안으로 옮겼다. 간결한 출력 형식을 넣었다. 그 사용법을 가르치는 스킬을 더했다.

그 글의 작성자는 Hacker News에서, 에이전트 로그를 읽는 일이 사용성 테스트를 지켜보는 것 같았다고 했다. 발표자도 같은 생각이다.

07

문서가 곧 인터페이스다 06:30

기능을 CLI에 넣었으면 에이전트에게 알려야 한다. 스킬 파일이나 help 플래그로 가르친다. 뻔한 이야기 같지만 함정이 있다. 에이전트는 가르친 내용을 글자 그대로 따른다.

실험: 아무 일도 안 하는 플래그 06:40
  1. 발표자는 deep 플래그(추정)를 no-op, 즉 아무 일도 하지 않는 플래그로 바꿨다.
  2. 스킬에는 그 플래그를 쓰라는 안내를 일부러 남겼다. 에이전트가 알아챌지 보려는 것이다.
  3. 검색 95번 중 95번이 여전히 그 플래그를 붙였다.
  4. 그다음 그 안내를 지운 새 스킬을 만들었다. 새 스킬을 읽은 세션 2개에서는 어떤 검색도 그 플래그를 쓰지 않았다. 두 세션 모두 첫 읽기부터 새 플래그를 썼다.

그러니 SKILL.md, help 텍스트, 오류 메시지가 곧 인터페이스다. 낡은 문서는 버그다. 에이전트가 계속 그대로 따르기 때문이다.

가르치자 파이프가 줄었다 07:10

새 플래그가 에이전트에게 전해지자 거의 모든 검색이 간결 출력을 썼다. 거의 모든 읽기도 새 플래그를 썼다.

08

트랜스크립트로 평가 만들기 07:30

도구를 매일 쓴다면 진짜 평가eval와 테스트 케이스는 이미 트랜스크립트에 있다. 평가는 결과 품질을 재는 테스트 묶음이다.

평가 재료트랜스크립트에서 찾는 곳
테스트 케이스에이전트가 실제로 실행한 명령
대략적인 답안지에이전트가 바로 다음에 한 일

이 명령들을 옛 빌드와 새 빌드에 똑같이 다시 돌린다. 무엇을 바꿨느냐에 따라 확인할 것이 다르다.

바꾼 것확인할 것
결과 순위에이전트가 실제로 가져다 쓴 결과가 여전히 맨 위에 오는가
출력 형식빠진 정보가 없는가
기본값어떤 명령의 동작이 달라졌는가
실패 사례를 찾는 신호 08:00 에이전트가 같은 호출을 인자만 바꿔 다시 했다면, 실패 사례를 찾았을 가능성이 높다.

답안지는 에이전트가 원한 것을 대충 짐작한 것일 뿐이다. 그래서 사례 몇 개는 떼어 두고held out, 고친 결과를 그 사례로 채점한다. 고칠 때 본 사례로만 채점하면 점수가 실제보다 좋게 나올 수 있다.

처음부터 다시 만든다면 08:20

핵심 정리

  1. 에이전트는 불편해도 버그 리포트를 쓰지 않는다. 출력을 잘라 쓰는 파이프가 그 불편의 흔적이다.
  2. 발표자의 호출 약 2만 건 중 4분의 1이 출력을 필터로 넘겼다. git show와 cargo test는 62%였다.
  3. pipefail이 없으면 파이프는 실패를 성공으로 바꾸거나 오류를 잘라 낸다. 실패는 크게 알리고, 마지막 줄에 요약과 로그 경로를 둔다.
  4. 같은 자르기를 매번 손으로 쓰는 것이 파이프 세금이다. 파이프의 83%는 10번 이상 반복된 패턴이었다.
  5. 출력 크기 상한은 무엇이 중요한지 모른다. 선택 플래그가 원하는 부분을 고르게 한다.
  6. 반복되는 우회를 기능으로 바꾼다. 검색어 주변만 보기, 간결 모드, 여러 개를 한 번에 묻기가 예다.
  7. 에이전트는 SKILL.md, help, 오류 메시지를 글자 그대로 따른다. 낡은 문서는 버그다.
  8. 실제 호출은 테스트 케이스, 바로 다음 행동은 답안지다. 옛 빌드와 새 빌드에 다시 돌려 비교하고, 몇 건은 채점용으로 떼어 둔다.
  9. 범위와 개수 제한부터 만든다. 기본 출력은 줄이고 더 보는 법을 알린다. 효과는 토큰보다 턴 수와 정답으로 잰다.
  10. 설계는 사람이, 실제 기록과의 대조는 에이전트가 한다. 트랜스크립트는 아직 읽지 않은 제품 분석 자료다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표 첫머리의 세 에이전트는 출력을 어떻게 잘랐고, 공통으로 깔린 가정은 무엇인가?
Claude Code는 grep 결과를 40줄로, Codex는 JSON 보고서의 마지막 40줄만, Cursor는 테스트 출력의 마지막 80줄만 남겼다. 모두 "답은 출력의 특정 위치에 있다"는 가정을 깔고 있다.
Q2Sanity가 "피드백 보내기" 도구를 만든 이유는?
2만 개가 넘는 에이전트가 약 300만 번 호출했는데 버그 리포트가 0건이었다. 에이전트는 불편해도 알리지 않고 우회한다.
Q3pipefail 없이 cargo test | head를 돌리면 생기는 문제 두 가지는?
종료 코드가 head의 것이라 테스트가 실패해도 성공으로 보인다. 더 나쁘면 잘라 낸 부분에 오류가 들어 있어 모델이 오류를 아예 보지 못한다.
Q4발표자가 권하는 실패 출력 방식은?
크게 실패한다. 출력의 맨 마지막 줄을 짧은 요약과 전체 로그 경로로 채운다. 에이전트가 끝만 읽어도 실패를 안다.
Q5"파이프 세금"이란 무엇인가?
에이전트가 같은 자르기 명령을 매번 손으로 다시 쓰는 비용이다. 한 번은 작지만, 매번 답이 어디 있을지 새로 추측하는 일이다.
Q6"grep 정도는 에이전트가 알아서 한다"는 반론에 발표자는 어떻게 답했나?
한 번뿐인 일이라면 맞다. 하지만 파이프의 83%가 10번 이상 반복된 패턴이었다. 반복되는 요구는 도구가 직접 제공해야 한다.
Q7하네스의 출력 크기 상한과 선택 플래그는 무엇이 다른가?
크기 상한은 정해진 양만 자를 뿐 어떤 메시지가 중요한지 모른다. 선택 플래그는 에이전트가 검색어 주변, 일치하는 것만, 마지막 몇 개처럼 원하는 부분을 지정하게 한다.
Q8no-op 플래그 실험이 보여 준 것은?
아무 일도 안 하는 플래그라도 스킬이 쓰라고 하면 95번 중 95번 썼다. 안내를 지우자 쓰지 않았다. 문서가 곧 인터페이스이고, 낡은 문서는 버그다.
Q9트랜스크립트로 평가를 만들 때 테스트 케이스와 답안지는 각각 무엇인가?
테스트 케이스는 에이전트가 실제로 실행한 명령, 답안지는 에이전트가 바로 다음에 한 일이다. 인자만 바꾼 재호출은 실패 사례의 신호다. 몇 건은 떼어 두고 채점에 쓴다.
Q10gh의 개수 제한 플래그(81%)와 cargo test quiet 모드(약 10%)의 차이가 주는 교훈은?
플래그는 에이전트가 집어 들 때만 도움이 된다. help와 스킬에서 가르치고, 큰 출력은 기본으로 줄이고, 더 보는 법을 출력에 적는다.
Q11DuckDB 에이전트 모드가 출력을 59% 줄였는데도 비용이 그대로였던 이유와 교훈은?
줄어든 토큰이 전체 토큰의 약 0.5%뿐이었다. 에이전트는 이미 정답을 맞히고 있었다. 토큰만 재지 말고 턴 수와 정답 여부를 잰다.
Q12에이전트에게 맡기기 어려운 일과 잘 맡길 수 있는 일은?
에이전트용 도구를 한 번에 설계하는 일은 어렵다. 사람 사용자를 떠올리고 흔한 나쁜 패턴을 따라 한다. 트랜스크립트와 실행 가능한 테스트를 주고 문제를 찾아 고치게 하는 일은 잘한다.
