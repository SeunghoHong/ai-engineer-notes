코딩 에이전트에게 API 지도를 주면

코딩 에이전트는 저장소 하나 안에서는 잘하지만, 수백 개 저장소에 흩어진 마이크로서비스 앞에서는 길을 잃는다. Postman은 모든 서비스와 API, 그 사이의 호출을 코드와 실제 트레이스에 근거한 그래프로 묶어 에이전트에게 줬다.

원본 영상: We Mapped 115 Microservices for Our Coding Agents 발표: Kamalakannan Nandagopal (Postman 스태프 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 연구 언급은 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Claude Code, Cursor Composer, RAG)은 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 코딩 에이전트는 프로젝트 하나 안에서는 잘한다. 하지만 수백 개 저장소에 흩어진 분산 시스템에서는 막힌다.
  2. 문서, 스킬·MCP, 에이전트 메모리는 모두 한계가 있다. 문서는 유지가 어렵고, 스킬·MCP는 받은 맥락만큼만 좋고, 메모리는 개인에게 묶여 있다.
  3. 마이크로서비스 구조에서는 API가 곧 맥락 층이다. API가 서비스의 책임을 정하고, API 호출이 서비스를 넘나드는 흐름을 보여 준다.
  4. Postman은 서비스, 엔드포인트, 구현 코드 위치, 호출 관계, 데이터 흐름을 API 맥락 그래프로 묶었다. 모든 항목은 코드 한 줄이나 프로덕션 트레이스에 근거해야 한다.
  5. 실제 PR로 만든 평가에서 그래프를 쓴 에이전트가 API 찾기, 입력 형태 분석, 영향 평가를 더 잘했다. 영향 평가에서는 토큰도 절반에서 3분의 1만 썼다.
  6. 그래프가 낡자 점수는 떨어지고 토큰은 늘었다. 최신 상태 유지가 그래프를 만드는 것만큼 중요하다.
  7. 효율이 오르면 같은 분석을 PR 단계와 개발자 컴퓨터까지 당겨 더 자주 돌릴 수 있다.
01

에이전트가 막히는 곳 00:40

Postman은 API를 만들고 테스트하는 플랫폼이다. 데스크톱 앱 말고도 클라우드 기능이 많다. 이 기능들 뒤에는 마이크로서비스 150개 이상과 REST API 엔드포인트 수천 개가 있다. 발표는 이 실제 환경에서 코딩 에이전트를 쓰며 배운 것을 다룬다.

영상 제목은 마이크로서비스를 115개라고 적었다. 자막에서는 "150개 이상"으로 들린다. 이 자료만으로는 어느 쪽이 맞는지 알 수 없다.

코딩 에이전트가 걸어온 길 01:00

  1. 자동 완성: 줄 단위, 함수 단위로 코드를 채운다. GitHub Copilot 시기다.
  2. 한 번에 구현: 코드베이스 전체를 리팩터링하고, 기능이나 수정을 한 번에 끝낸다. Cursor Composer와 Claude Code 시기다.
  3. 완전 자율 워크플로: 에이전트가 작업을 시작하고, 코드를 바꾸고, 확인하고, PR을 보내고, PR 검증까지 한다.
잘하는 곳 01:30
  • 처음부터 새로 만드는 프로젝트 greenfield
  • 프로젝트 하나 안의 수정과 개선
막히는 곳: 실제 프로덕션
  • 여러 마이크로서비스로 나뉜 분산 시스템
  • 여러 환경에 배포되고, 환경마다 버전이 다르다
  • 프론트엔드, CLI, API 같은 여러 앱이 백엔드와 통신한다
  • 코드가 수백 개 저장소에 흩어져 있다

03

API가 곧 맥락 층이다 03:10

같은 시기에 Postman의 GTM 팀 go-to-market도 업무용 에이전트를 만들고 있었다. 이 에이전트들은 여러 출처에서 모은 고객 데이터로 일한다. 들어오는 데이터는 구조가 없었다. 팀은 여러 번 고쳐 가며 이를 구조화된 데이터로 바꿨다.

결과물은 RAG와 GraphRAG를 합친 파이프라인이었다. 이 파이프라인이 중앙 맥락 층 context layer 역할을 했다. 그러자 개별 에이전트가 모두 잘 돌아갔다.

코딩 에이전트로 옮긴 질문 03:50 코딩 에이전트에게도 이런 중앙 맥락 층을 줄 수 있을까? 준다면 무엇으로 만들어야 할까?

분산 시스템의 맥락 층은 API 04:00

  1. 복잡한 시스템은 도메인과 모델 단위로 나뉜다.
  2. 마이크로서비스 하나는 도메인이나 모델 하나의 책임을 맡는다.
  3. 그 책임이 무엇인지 정의하는 것이 API다.
  4. 시스템 사이의 API 호출을 따라가면, 여러 서비스를 거치는 작업 흐름과 사용자 여정이 보인다.
에이전트는 받은 맥락만큼만 좋다.발표자의 표현을 옮김
04

API 맥락 그래프 만들기 04:30

Postman은 에이전트에게 줄 가장 좋은 맥락 층을 목표로 API 맥락 그래프 API context graph를 만들었다. 순서는 이렇다.

  1. 프로덕션에서 도는 마이크로서비스를 빠짐없이 목록으로 만든다.
  2. REST API 서비스마다 노출하는 엔드포인트를 모두 찾는다.
  3. 엔드포인트마다 구현된 코드 줄까지 기록한다.
  4. 서비스끼리, 엔드포인트끼리 어떻게 호출하는지 연결한다.
  5. 데이터가 DB와 캐시까지 스택 아래로 어떻게 흐르는지 추적한다.
  6. 프론트엔드, CLI, API 같은 앱이 백엔드와 어떻게 주고받는지 찾는다.
  7. 이 데이터를 모두 LLM으로 색인해 중앙 그래프로 만든다.
지킨 원칙 하나 05:30 그래프에 올라가는 데이터는 모두 확실한 근거에 묶여야 한다. 근거는 둘 중 하나다. 코드베이스에 실제로 있는 코드 한 줄, 또는 프로덕션 텔레메트리에서 나온 정확한 트레이스다.

그래프에 드러난 모습 05:50

그래프를 채우자 발표자가 "흔히 예상할 만하다"고 한 패턴이 나타났다.

  • 중앙에 핵심 서비스 묶음이 있다. 이 서비스들은 API로 강하게 얽혀 서로에게 깊이 의존한다.
  • 바깥 가장자리에 지나치게 비대해진 서비스가 한두 개 있다.
  • 중앙에 있는 서비스는 보통 티어 0이나 티어 1로 분류하는 서비스다.
05

어떻게 평가했나 06:20

그래프가 에이전트를 얼마나 낫게 하는지 재려고, 실제 기록으로 평가를 만들었다.

  • 실제 PR: Postman GitHub 조직에 올라온 PR마다 개발자가 하려던 일과 PR의 실제 결과를 정리했다.
  • 설계 논의: 중요한 프로젝트에서 나온 핵심 설계 결정과 교훈을 뽑았다.
  • eval로 변환: 각각을 평가 문항으로 바꿨다. 정답은 나중에 돌아봤을 때 실제로 내려진 결정이다.

06

시나리오 1: API 찾기 08:10

API 찾기 API discovery는 매일 생기는 질문이다. 프론트엔드든 백엔드든 다른 시스템과 연동하려면 어떤 API를 불러야 하는지 알아야 한다. 실제 시스템에는 API가 수백 개 있다. 같은 일을 하는 API가 여럿인 경우도 많다.

평가 문항 (발표자가 단순화한 예) 특정 사용자의 프로필 이름을 가져오려면 어떤 API를 불러야 하나?

순수한 검색 문제라 결과는 예상대로였다.

  • 그래프를 쓴 에이전트는 점수가 높았다.
  • 코드 검색만 쓴 에이전트는 잘 못했다.
  • Postman 에이전트와 Claude Code의 차이는 작았다. 더 파고들 만큼은 아니었다.
07

시나리오 2: API 재설계 09:00

발표자가 가장 흥미롭다고 꼽은 시나리오다. 흔히 겪는 이야기로 시작한다.

  1. 개발자가 새 기능을 위해 API를 설계한다. 요청 입력의 스키마를 정하고, 구현하고, 테스트까지 마쳤다.
  2. 출시 직전, 이 API를 쓰는 쪽에서 요청이 온다. 나중에 쓸 속성 하나를 더 보내게 해 달라는 것이다.
  3. 제대로 된 스키마를 고민할 시간이 없다. 개발자는 자유 형식 JSON 객체를 받는 필드를 하나 추가한다.
  4. 코드에 TODO를 남긴다. "2주 뒤에 다시 보고 스키마를 추가할 것."
  5. 기능은 출시되고, 모두 만족한다.
출시 때속성 하나를 받을 필드스키마 없는 자유 형식 JSON
→
2주 뒤 10:00속성이 15개로 늘었다보내는 서비스는 1곳일 수도, 5곳이나 10곳일 수도 있다

이제 개발자는 이 필드에 어떤 모양의 데이터가 들어오는지 모른다. 소비자마다 무엇을 어떻게 보내는지도 모른다. 발표자는 이 일을 "API마다 입력 형태와 그렇게 쓰는 이유를 분석하는 일"이라고 부른다.

사람이 풀기 어려운 이유 10:30
  • 실제 환경에서 API의 소비자를 모두 찾는 것은 현실적으로 힘들다.
  • 서비스 의존 관계도가 있어도, 소비자마다 보내는 정확한 입력 형태는 알기 어렵다.
  • 프로덕션 로그에는 그만큼 자세한 정보가 없는 경우가 많다. 개인정보 때문에 아예 남기지 않기도 한다.
  • 형태를 찾아내도, 소비자가 왜 그렇게 보내는지 알아내기는 더 어렵다.

결과 11:00

Postman 에이전트는 거의 정확하게 풀었다. 발표자도 놀랐다고 했다. 도움이 된 것은 두 가지다.

  • 그래프가 이 API의 소비자를 빠짐없이 알고 있었다.
  • 소비자마다 구현된 코드 위치까지 내려가 볼 수 있었다. 그 코드 주변의 맥락으로 왜 그렇게 바꿨는지도 이해했다.

에이전트는 소비자마다 보내는 고유한 입력 형태를 빠르게 찾았다. 덕분에 스키마 변경을 믿고 진행할 수 있었다.

코드 검색만 쓴 구성은 잘 못했다. 그래프를 스킬로 받은 Claude Code는 조금 나았다. 하지만 몇 턴 진행한 뒤 멈추고, 사용자가 다음 할 일을 정해 주기를 기다렸다.

08

시나리오 3: 영향 평가 11:50

또 하나의 흔한 질문은 영향 평가 impact assessment다. 변경 하나가 어디까지 영향을 주는지 알아내는 일이다.

  • 이 API를 바꾸면 어떤 사용처가 영향을 받나?
  • V2 API가 있고 V3를 새로 만들려 한다. 더 나은 V3를 설계하려면 V2가 어떻게 쓰이는지부터 알아야 한다.

그래프가 특히 효과를 낸 시나리오다. Postman 에이전트는 결과 품질이 좋았다. 토큰은 순수 코드 검색의 절반, 적게는 3분의 1만 썼다.

09

그래프가 낡으면 12:20

늘 순조롭지는 않았다. 실패한 eval도 있었다. PR 하나가 엔드포인트를 바꿨을 때, 영향을 받는 하위 서비스를 모두 찾으라는 문항이었다.

결과 그래프가 거의 뒤집혔다. Postman 에이전트는 점수가 떨어졌다. 토큰은 오히려 많이 썼다.

원인 12:50 eval을 쓴 시점과 실행한 시점 사이에 새 소비자가 생겼다. 그래프는 그 소비자를 몰랐다.

교훈 13:00

  • 그래프는 채우는 것만큼 최신으로 유지하는 것이 중요하다.
  • 실제 상태와 동기화가 늦어지면 결과에 빈틈이 생긴다.
  • 빈틈이 보이면 개발자는 바로 신뢰를 잃는다. 신뢰를 잃으면 쓰지 않는다.
  • 새 API와 새 의존성만 잡아서는 안 된다. 사라진 API와 의존성도 잡아야 한다. 놓치면 혼란과 문제가 생긴다.

입력 형태 분석거의 정확히 풀었다조금 나았지만 몇 턴 뒤 멈춤낮음

10

PR 4개 중 3개는 API를 건드린다 13:30

이런 시나리오가 우리 팀과는 상관없다고 생각할 수 있다. Postman이 상위 10개 저장소의 PR을 되짚어 봤더니, 약 75%가 API에 어떤 식으로든 영향을 줬다.

영향을 주는 방식은 두 가지다.

  • API가 바깥에 드러내는 부분 surface area을 바꾸는 변경
  • 새 API를 가져다 연동하는 변경

둘 다 하위 시스템에 연쇄적으로 큰 영향을 줄 수 있다.

11

새로 던질 수 있게 된 질문 14:00

앞의 시나리오들은 그래프가 있을 때와 없을 때를 비교하기 쉬웠다. 그런데 그래프가 생기자, 전에는 물을 수조차 없던 질문을 할 수 있게 됐다.

Postman 에이전트에게 맡긴 일 14:20 전체 생태계의 엔지니어링 분석과 처음부터 끝까지 아키텍처 리뷰를 해 달라.

발표자는 이 순간을 "불이 켜진 순간"이라고 했다. 에이전트는 약점과 취약 지점을 하나씩 짚은 21쪽짜리 보고서를 냈다.

보고서가 찾은 것왜 중요한가
의존성 순환장애가 났을 때 큰 문제가 될 수 있다
오래 끄는 위험한 마이그레이션기술 부채의 신호다
단일 장애 지점언젠가 터질 문제다
텔레메트리 사각지대구현에 있는 것이 텔레메트리에는 보이지 않는다
역할별 할 일CEO, CTO, 스태프 엔지니어가 각각 해야 할 일을 나눠 제시했다

다음에 더할 것 15:00

  • 비즈니스 의미 층: 회사가 무엇을 하는지 담은 의미 층 semantic layer을 코딩 에이전트의 맥락 층에 연결한다.
  • "왜"에 대한 추론: 이 데이터 모델은 왜 있나. 도메인은 왜 이렇게 나뉘었나. 이 API는 왜 있나. 왜 저 API 말고 이 API를 써야 하나.

발표자는 이런 정보가 이후의 코딩 결정을 돕는다고 본다. 그 결과 일상 개발에서 나오는 결과물도 좋아진다고 말한다.

12

결론: 효율은 빈도가 된다 15:40

  • API 맥락 그래프는 실제 분산 시스템에서 코딩 에이전트의 맥락 층이 된다.
  • 저장소 하나, 서비스 하나 안에서는 답할 수 없던 아키텍처 질문에 답하게 해 준다.
  • 문제를 푸는 올바른 방법을 찾는 시간을 줄인다. 품질을 지키거나, 더 효율적으로 하거나 둘 중 하나는 얻는다.
흔한 해석효율 = 비용 절감같은 일을 더 싸게 한다
→
발표자의 해석 16:10효율 = 더 자주 돌릴 수 있다같은 분석을 PR 단계, 개발자 컴퓨터까지 당긴다

결정과 문제 발견이 개발 주기의 앞쪽으로 올수록 좋다. 그러면 코드를 만드는 에이전트가 개발자에게 안심을 준다. 개발자는 더 자신 있게 프로덕션에 배포할 수 있다.

발표 끝에서 이 기능들이 Postman 플랫폼 안에 있고 얼리 액세스로 쓸 수 있다고 밝혔다. 발표자가 자기 회사 제품을 소개하는 발표이니, 평가 결과와 주장은 그 점을 감안해 읽자.

핵심 정리

  1. 코딩 에이전트는 새 프로젝트와 프로젝트 하나 안의 일은 잘하지만, 수백 개 저장소에 걸친 분산 시스템에서는 막힌다.
  2. 문서는 유지가 어렵고, LLM에게만 맡기면 품질이 급격히 떨어진다(발표자 인용). 사람이 다듬어야 한다.
  3. 스킬·MCP는 받은 맥락만큼만 좋다. 에이전트 메모리는 개인 단위라 팀이 나눠 쓰는 방법이 아직 없다.
  4. 마이크로서비스에서 API는 서비스의 책임을 정의하고, API 호출은 여러 서비스를 지나는 흐름을 드러낸다. 그래서 API가 맥락 층이다.
  5. 그래프에는 서비스, 엔드포인트, 구현 코드 줄, 호출 관계, DB·캐시까지의 데이터 흐름, 앱과 백엔드의 상호작용이 들어간다.
  6. 원칙: 모든 데이터는 코드 한 줄이나 프로덕션 트레이스라는 확실한 근거에 묶인다.
  7. 평가는 실제 PR과 설계 결정을 eval로 바꾸고, 실제로 내려진 결정을 정답으로 삼았다. 점수(0~5)와 토큰을 함께 쟀다.
  8. 그래프는 API 찾기, 입력 형태 분석, 영향 평가에서 효과가 컸다. 영향 평가에서는 토큰을 절반~3분의 1만 썼다.
  9. 그래프 동기화가 늦으면 결과에 빈틈이 생기고, 빈틈은 곧 신뢰 상실과 사용 감소로 이어진다. 삭제도 잡아야 한다.
  10. 상위 10개 저장소 PR의 약 75%가 API에 영향을 줬다. 효율이 오르면 같은 분석을 PR 단계와 개발 환경에서 더 자주 돌릴 수 있다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1코딩 에이전트가 잘하는 일과 막히는 환경은?
새로 시작하는 프로젝트와 프로젝트 하나 안의 수정은 잘한다. 여러 마이크로서비스, 여러 환경과 버전, 수백 개 저장소에 걸친 분산 시스템에서는 막힌다.
Q2발표자가 꼽은 세 가지 기존 해법과 각각의 한계는?
문서는 쓰고 유지하기 어렵고 LLM에게만 맡기면 품질이 떨어진다. 스킬·MCP는 받은 맥락만큼만 좋다. 에이전트 메모리는 개인에게 묶여 팀이 나눠 쓰기 어렵다.
Q3왜 "API가 곧 맥락 층"인가?
마이크로서비스마다 한 가지 책임을 맡는데, 그 책임을 정의하는 것이 API다. 그리고 API 호출을 따라가면 여러 서비스를 거치는 작업 흐름과 사용자 여정이 보인다.
Q4그래프에 올라가는 데이터가 지켜야 하는 원칙은?
모든 데이터가 확실한 근거에 묶여야 한다. 근거는 코드베이스의 코드 한 줄, 또는 프로덕션 텔레메트리의 정확한 트레이스다.
Q5평가의 정답은 무엇으로 정했나?
실제 PR과 설계 논의에서, 나중에 돌아봤을 때 실제로 내려진 결정을 정답으로 삼았다.
Q6비교한 세 구성은?
그래프에 연결한 Postman AI 에이전트, GitHub 코드 검색만 쓰는 Claude Code, 같은 그래프를 스킬로 받은 Claude Code.
Q7결과 그래프에서 왼쪽 위와 오른쪽 위의 차이는?
둘 다 점수는 높다. 왼쪽 위는 토큰을 적게 썼고, 오른쪽 위는 많이 썼다. 왼쪽 위가 가장 좋다.
Q8자유 형식 JSON 필드의 입력 형태를 사람이 알아내기 어려운 이유는?
소비자를 모두 찾기 힘들다. 소비자별 정확한 입력 형태를 알기 어렵다. 로그에 자세한 정보가 없거나 개인정보 때문에 남기지 않는다. 형태를 찾아도 왜 그렇게 보내는지 알기는 더 어렵다.
Q9Postman 에이전트가 입력 형태를 찾아낼 수 있었던 이유는?
그래프가 API의 소비자를 빠짐없이 알았다. 그리고 소비자마다 구현 코드 위치까지 내려가, 주변 맥락으로 왜 그렇게 보내는지도 이해했다.
Q10영향 평가 실패 사례의 원인과 교훈은?
eval을 쓴 뒤 실행하기 전에 새 소비자가 생겼는데 그래프가 몰랐다. 그래프는 최신으로 유지해야 하고, 새로 생긴 것뿐 아니라 사라진 API와 의존성도 잡아야 한다.
Q11PR 약 75%라는 숫자는 무엇을 뜻하나?
상위 10개 저장소 PR의 약 75%가 API의 바깥 부분을 바꾸거나 새 API를 연동했다. API 맥락이 필요한 일이 예외가 아니라 일상이라는 뜻이다.
Q12발표자가 말하는 효율의 진짜 가치는?
비용 절감보다 빈도다. 효율이 오르면 같은 분석을 PR 단계나 개발자 컴퓨터에서 더 자주 돌려, 문제를 더 일찍 잡을 수 있다.
