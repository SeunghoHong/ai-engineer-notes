큰 컨텍스트 창이 에이전트를 구하지 못하는 이유

도구가 큰 데이터를 돌려줄 때마다 에이전트의 컨텍스트 창은 불어난다. 창을 키워도 모델은 긴 입력의 가운데를 놓친다. 발표자는 데이터를 밖에 두고, 필요한 것만 고르고, 줄이고, 에이전트끼리 나누는 방법을 보여 준다.

원본 영상: Why Bigger Context Windows Won't Save Your Agent 발표: Elizabeth Fuentes Leone (AWS)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 주장은 모두 발표자의 것이고 따로 확인하지 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다(Strands, Amazon Bedrock, Neo4j, API Gateway, MCP). 슬라이드의 코드는 자막에 없다. 그래서 노트의 코드는 모두 같은 구조로 다시 쓴 예시다. mm:ss는 영상 위치다.

3분 요약
  1. 도구가 로그 같은 큰 데이터를 돌려줄 때마다 컨텍스트 창이 불어난다. 창이 넘치면 모델이 환각을 일으키고 필요한 정보를 잘 못 찾는다.
  2. 창을 키우는 건 답이 아니다. 모델은 긴 입력의 앞과 끝만 잘 기억하고 가운데를 놓친다.
  3. 해법은 컨텍스트 엔지니어링이다. 전략은 네 가지다. 외부화, 선택, 압축, 분리.
  4. 압축: 대화 관리자로 최근 메시지는 남기고 오래된 메시지는 요약한다. 기억은 단기, 장기, 그래프의 세 층으로 나눈다.
  5. 외부화: 큰 도구 결과는 저장소에 넣고 컨텍스트에는 포인터 ID만 남긴다. 여러 에이전트도 컨텍스트 대신 포인터를 나눈다.
  6. 같은 도구를 끝없이 부르면 호출 횟수 제한으로 막는다. 느린 외부 API는 비동기로 부른다.
  7. 피할 것: 다 넣기, 단순 요약, 컨텍스트 오염.
01

무한 컨텍스트 창은 신화다 00:30

발표자는 "무한한 컨텍스트 창은 신화"라는 말로 시작한다. 에이전트 시스템은 도구가 큰 데이터를 돌려줄 때 무너진다.

컨텍스트 창 context window은 모델이 한 번에 읽는 입력 공간이다. 지시문, 대화 기록, 도구 결과가 모두 여기에 들어간다. 이 공간이 넘치면 모델이 없는 내용을 지어내기 시작한다. 이를 환각 hallucination이라 한다. 창 안의 정보를 찾아 쓰는 능력 recall도 떨어진다.

예: 로그를 감시하는 에이전트 01:10

  1. 에이전트가 애플리케이션을 감시하려고 로그를 가져온다.
  2. 가져온 로그는 컨텍스트 창에 들어간다.
  3. 같은 세션에서 다시 부르면 앞의 기록을 모두 안고 시작한다.
  4. 그래서 창은 부를 때마다 커진다.
에이전트의 기억 = 컨텍스트 창 에이전트는 지난 대화를 컨텍스트 창에 다시 넣는 방식으로 기억한다. 기억할 것이 늘수록 창도 커진다.
02

창을 키우면 해결될까 01:50

발표자에 따르면 약 1년 전에는 "창을 키워 토큰을 더 넣으면 된다"고 봤다. 에이전트가 본격적으로 쓰이기 전 이야기다. 지금은 그게 틀렸다는 걸 안다고 발표자는 말한다.

U자 주의 곡선 02:10

데이터가 아주 크면 모델은 창의 가운데를 잊는다. 처음과 마지막에 넣은 내용만 잘 기억한다. 위치별로 기억하는 정도를 그리면 U자 모양이 된다. 그래서 U자 주의 곡선 attention U-curve이라 부른다.

창 안의 위치모델이 기억하는 정도
앞부분잘 기억한다
가운데잘 놓친다
끝부분잘 기억한다

창을 키워 더 많이 넣으면 놓치는 가운데도 같이 길어진다. 문제는 창의 크기가 아니다. 창에 무엇을 넣느냐가 문제다.

03

컨텍스트 엔지니어링 02:40

컨텍스트 엔지니어링은 모델에게 필요한 정보를, 필요한 때에 주는 일이다.발표자의 정의를 옮김

창에 모든 정보를 넣으면 안 되는 이유는 두 가지다.

  • 다 필요하지 않다. 에이전트가 매번 창 안의 모든 정보를 쓰지는 않는다.
  • 창이 모델을 오염시킬 수 있다. 창 안에 프롬프트 인젝션 prompt injection이 섞여 들어올 수 있다. 입력 속에 숨긴 지시문으로 모델을 조종하는 공격이다.

컨텍스트 엔지니어링은 창에 넣을 것을 골라 담는 일이다. 목표는 두 가지다. 결과의 품질을 높이고, 토큰 사용량을 줄인다.

05

대화 관리자로 오래된 대화 줄이기 04:00

가장 쉬운 기법부터 시작한다. 대화 관리자 conversation manager는 대화 기록이 창을 얼마나 차지할지 정하는 장치다. 발표자는 Strands Agents라는 프레임워크로 보여 줬다. AWS가 관리하는 오픈소스이고, 무료이며, 특정 모델에 묶이지 않는다고 소개했다.

발표자는 AWS 소속이고 Strands Agents는 AWS가 관리하는 프레임워크다. 기본 모델 제공자도 AWS의 Amazon Bedrock이다. 예시가 모두 자사 도구 기준이라는 점을 감안해 읽자. 네 가지 전략 자체는 프레임워크와 상관없이 쓸 수 있다.

Strands의 대화 관리 방식하는 일
슬라이딩 윈도 sliding window가장 최근 메시지만 남긴다
요약 summarization오래된 메시지를 요약해 남긴다
둘의 조합오래된 메시지는 요약하고, 최근 메시지는 그대로 둔다

자막으로는 두 번째와 세 번째의 차이가 분명하지 않다. 아래 06:00의 설정 예는 세 번째 설명과 같은 동작이다.

Strands 에이전트는 코드 한 줄 05:10

  • 코드 한 줄로 에이전트 루프 agent loop가 만들어진다. 노드나 그래프를 직접 짤 필요가 없다.
  • 넣을 것은 시스템 프롬프트와 도구 목록이다.
  • 기본으로는 Amazon Bedrock을 통해 모델을 부른다.
  • Llama, Gemini, Anthropic, OpenAI 같은 다른 모델도 쓸 수 있다. 해당 라이브러리를 불러오고 모델을 지정하는 줄 하나만 더하면 된다고 발표자는 말했다.

요약 대화 관리자 설정 06:00

대화 관리자를 붙이는 것도 한 줄이다. 발표 예에서는 두 값을 정했다.

  • 요약 비율 summary ratio: 50%
  • 그대로 남길 최근 메시지: 4개

이렇게 하면 같은 세션에서 에이전트를 부를 때마다 창이 관리된다. 최근 메시지 4개는 원문으로 남고, 나머지는 요약된다.

예시. Strands Python SDK 기준으로 다시 쓴 코드다. 인자 이름은 쓰기 전에 공식 문서로 확인한다.

from strands import Agent
from strands.agent.conversation_manager import SummarizingConversationManager

agent = Agent(
    system_prompt="애플리케이션 로그를 감시하고 이상을 알린다.",
    tools=[fetch_application_logs, summarize_logs],  # 07절 메모리 포인터 예시의 도구
    conversation_manager=SummarizingConversationManager(
        summary_ratio=0.5,           # 요약 비율 50%
        preserve_recent_messages=4,  # 최근 메시지 4개는 원문 유지
    ),
)
06

기억을 세 층으로 나누기 06:30

대화 관리자는 지금 세션 안에서만 통한다. 세션이 바뀌거나 오래 남길 기억이 많으면 층을 나눠 저장한다.

기억담는 것저장 방식
단기 기억 short-term지금 세션의 최근 대화컨텍스트 창. 대화 관리자로 크기를 관리한다
장기 기억 long-term 07:00지난 세션에서 남길 만한 내용벡터 데이터베이스. 서로 다른 프롬프트로 대화를 읽어 여러 종류의 기억을 만든다
관계 기억 relational 07:20대상끼리 어떻게 이어지는지엔티티 그래프. 연결을 따라가며 찾는다

세 가지를 함께 쓸 수 있다. 세션 안에서는 단기 기억을 쓴다. 지난 일은 장기 기억에서 꺼낸다. 관계로 남길 정보는 그래프 기억에 둔다.

발표자는 그래프 기억을 짧게 넘겼다. 자세한 내용은 행사장의 Neo4j 쪽에 물어보라고 했다.

07

메모리 포인터: 큰 데이터는 밖에 두기 08:00

로그 감시 에이전트로 돌아간다. 에이전트를 부를 때마다 로그를 창에 넣고 싶지는 않다. 그럴 때 메모리 포인터 memory pointer를 쓴다.

  1. 도구가 로그 묶음을 가져온다.
  2. 다른 도구가 그 로그를 저장소에 넣는다. 저장소는 ID를 돌려준다.
  3. Strands에서는 이 저장소로 에이전트 상태 agent state를 쓴다.
  4. 창에는 ID만 남는다. 이 ID가 메모리 포인터다.
  5. 로그를 읽는 또 다른 도구가 에이전트에게 핵심만 알려 준다. 에이전트는 원문 없이도 상황을 안다.
  6. 원문이 꼭 필요하면 에이전트가 ID를 대고 로그를 다시 꺼낸다.
전로그 원문이 창에 쌓인다부를 때마다 창이 커지고 가운데 내용은 묻힌다
→
후포인터 ID와 핵심만 남는다원문은 저장소에 있고, 필요할 때만 꺼낸다

코드로 보면 09:10

발표 슬라이드에서는 @tool 데코레이터로 도구 두 개를 만들었다. 그중 로그를 가져오는 도구(fetch application logs)가 도구 컨텍스트로 에이전트 상태에 접근한다. 거기에 로그를 저장하고 포인터 ID를 만든다. 이 ID만 창에 남는다.

예시. 슬라이드 코드를 옮긴 것이 아니라 같은 구조로 다시 쓴 것이다. read_log_store는 로그 저장소에서 읽는 함수라고 가정했다.

from strands import tool, ToolContext

@tool(context=True)
def fetch_application_logs(app_name: str, tool_context: ToolContext) -> str:
    """로그를 가져와 에이전트 상태에 저장하고 포인터 ID만 돌려준다."""
    logs = read_log_store(app_name)
    pointer_id = f"logs:{app_name}"
    tool_context.agent.state.set(pointer_id, logs)
    return f"로그 {len(logs)}줄을 저장했다. 포인터: {pointer_id}"

@tool(context=True)
def summarize_logs(pointer_id: str, tool_context: ToolContext) -> str:
    """포인터로 로그를 꺼내 핵심만 돌려준다. 원문은 창에 넣지 않는다."""
    logs = tool_context.agent.state.get(pointer_id)
    errors = [line for line in logs if "ERROR" in line]
    return f"전체 {len(logs)}줄 중 에러 {len(errors)}줄. 최근 에러: {errors[-3:]}"
08

에이전트끼리는 포인터만 나눈다 09:40

도구만으로 부족할 만큼 애플리케이션이 복잡하면 에이전트를 여러 개 쓴다. Strands에서는 Swarm으로 여러 에이전트를 묶는다.

컨텍스트 창을 통째로 나누지 않는다 발표자는 이를 다른 에이전트에게 쓰레기를 넘기는 일에 비유했다. 모든 에이전트가 서로의 정보를 다 필요로 하지는 않는다.

대신 호출 상태 invocation state를 쓴다. 한 번의 호출 동안 여러 에이전트가 함께 보는 공유 값이다.

  1. Swarm 안에서 큰 데이터를 저장하고 ID를 하나 만든다.
  2. 그 메모리 포인터를 호출 상태에 싣는다.
  3. 에이전트들은 창이 아니라 호출 상태로 포인터를 주고받는다.
  4. 원문이 필요한 에이전트만 포인터로 꺼내 쓴다.
09

도구 무한 반복 막기 10:40

에이전트가 같은 도구를 끝없이 다시 부르며 루프에서 못 빠져나올 때가 있다. 발표자가 짚은 원인은 도구가 분명한 답을 돌려주지 않는 경우다. 대책은 두 가지다.

대책 1 · 분명한 도구 응답

도구가 무엇을 했고 결과가 어떤지 분명히 돌려주게 만든다. 에이전트가 같은 도구를 다시 부를 이유가 사라진다.

예시: 검색 결과가 없을 때 빈 값 대신 "결과 없음"이라고 분명히 돌려준다.

대책 2 · 호출 횟수 제한 11:20

도구마다 최대 호출 횟수를 정한다. 발표 예에서는 항공편 검색 도구(추정)를 3번까지만 부를 수 있게 했다. 다른 도구도 3번으로 묶었다.

한도에 닿으면 에이전트는 그 도구를 더 부르지 못한다. 끝없는 내부 루프가 생기지 않는다.

"항공편 검색 도구"는 자막의 "search fly"를 보고 추정한 이름이다.

10

느린 외부 API는 비동기로 11:50

이 기법은 컨텍스트 창을 직접 줄이지 않는다. 대신 창을 쓰는 에이전트가 멈추지 않게 돕는다.

MCP 도구나 외부 API가 제때 답하지 않을 때가 있다. 예를 들어 AWS API Gateway는 응답을 기다리는 최대 시간이 정해져 있다. 그 시간을 넘기면 지연 때문에 애플리케이션이 멈춘다.

핵심 정리

  1. 도구가 큰 데이터를 돌려줄 때마다 컨텍스트 창이 불어난다. 넘치면 환각이 생기고 recall이 떨어진다.
  2. 창을 키워도 해결되지 않는다. 모델은 긴 입력의 앞과 끝만 잘 기억하고 가운데를 놓친다.
  3. 컨텍스트 엔지니어링은 필요한 정보를 필요한 때에 주는 일이다. 품질과 토큰 비용을 함께 잡는다.
  4. 전략은 네 가지다. 외부화, 선택, 압축, 분리.
  5. 가장 쉬운 출발점은 대화 관리자다. 최근 메시지는 남기고 오래된 메시지는 버리거나 요약한다.
  6. 기억은 세 층으로 나눈다. 세션 안의 단기 기억, 벡터 DB의 장기 기억, 그래프의 관계 기억.
  7. 큰 도구 결과는 저장소에 두고 창에는 포인터 ID만 남긴다. 원문은 필요할 때 ID로 꺼낸다.
  8. 여러 에이전트가 창을 통째로 나누면 쓰레기를 나누는 셈이다. 포인터를 호출 상태로 나눈다.
  9. 같은 도구를 끝없이 부르는 루프는 분명한 도구 응답과 호출 횟수 제한으로 막는다.
  10. 느린 외부 API는 비동기로 부른다. 그리고 다 넣기, 단순 요약, 컨텍스트 오염을 피한다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1로그 감시 에이전트의 컨텍스트 창은 왜 부를 때마다 커지나?
가져온 로그가 창에 들어가고, 같은 세션의 다음 호출은 앞의 기록을 모두 안고 시작하기 때문이다. 에이전트는 창에 지난 대화를 다시 넣는 방식으로 기억한다.
Q2U자 주의 곡선이란 무엇이고, 왜 창을 키워도 소용없나?
긴 입력에서 모델이 앞과 끝은 잘 기억하고 가운데는 놓치는 경향이다. 창을 키워 더 많이 넣으면 놓치는 가운데도 같이 길어진다.
Q3발표자가 말한 컨텍스트 엔지니어링의 정의는?
모델에게 필요한 정보를 필요한 때에 주는 일. 결과 품질과 토큰 사용량을 함께 최적으로 만드는 것이 목표다.
Q4창에 모든 정보를 넣으면 안 되는 이유 두 가지는?
에이전트가 매번 모든 정보를 쓰지는 않는다. 그리고 창 안에 프롬프트 인젝션이 섞여 들어와 모델을 오염시킬 수 있다.
Q5네 가지 전략의 이름과 각각이 하는 일은?
외부화: 큰 데이터를 저장소로 옮긴다. 선택: 필요한 것만 꺼낸다. 압축: 요약해 토큰을 줄인다. 분리: 에이전트마다 컨텍스트를 따로 둔다.
Q6발표의 요약 대화 관리자 설정에서 50%와 4는 무엇인가?
50%는 요약 비율이고, 4는 원문으로 남길 최근 메시지 수다. 최근 4개는 그대로 두고 나머지를 요약한다.
Q7단기, 장기, 관계 기억은 각각 어디에 두나?
단기 기억은 컨텍스트 창(대화 관리자로 관리), 장기 기억은 벡터 데이터베이스, 관계 기억은 엔티티 그래프.
Q8메모리 포인터를 쓰면 창에는 무엇이 남고, 원문은 어떻게 다시 보나?
창에는 포인터 ID와 핵심 요약만 남는다. 원문이 꼭 필요하면 에이전트가 ID를 대고 저장소(Strands에서는 에이전트 상태)에서 꺼낸다.
Q9Swarm에서 컨텍스트 창을 통째로 나누면 안 되는 이유와 대안은?
모든 에이전트가 서로의 정보를 다 필요로 하지 않아서, 쓰레기를 나누는 셈이 된다. 대신 메모리 포인터를 호출 상태에 실어 나눈다.
Q10에이전트가 같은 도구를 끝없이 부를 때 쓰는 두 가지 대책은?
도구가 분명한 답을 돌려주게 만든다. 그리고 도구마다 최대 호출 횟수를 정한다(발표 예에서는 3번).
Q11느린 외부 API를 비동기로 부를 때 필요한 도구 두 개는?
작업을 시작하고 ID를 돌려주는 도구, 그리고 ID로 상태나 결과를 확인하는 도구. 에이전트는 기다리느라 멈추지 않는다.
Q12발표자가 꼽은 피해야 할 패턴 3가지는?
다 넣기(context stuffing), 단순 요약(naive summarization), 컨텍스트 오염(context pollution).

용어 정리

용어뜻
컨텍스트 창Context window. 모델이 한 번에 읽을 수 있는 입력의 크기. 지시문, 대화 기록, 도구 결과가 모두 여기에 들어간다
토큰Token. 모델이 글을 나눠 세는 단위. 창의 크기와 비용을 이 단위로 잰다
컨텍스트 엔지니어링Context engineering. 모델에게 필요한 정보를 필요한 때에 주도록 창에 넣을 것을 설계하는 일
환각Hallucination. 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 것
recall창 안에 있는 정보를 제대로 찾아 쓰는 능력
U자 주의 곡선Attention U-curve. 긴 입력에서 앞과 끝은 잘 기억하고 가운데는 놓치는 경향
프롬프트 인젝션입력 안에 지시문을 숨겨 모델이 원래 지시 대신 그걸 따르게 만드는 공격
에이전트 루프Agent loop. 모델이 판단하고, 도구를 부르고, 결과를 읽는 과정을 반복하는 구조
대화 관리자Conversation manager. 대화 기록이 창을 얼마나 차지할지 관리하는 장치
슬라이딩 윈도Sliding window. 최근 메시지 몇 개만 남기고 오래된 것은 버리는 방식
단기 / 장기 기억단기: 지금 세션의 최근 대화. 장기: 세션이 끝나도 저장해 두었다가 다음 세션에 꺼내 쓰는 기억
벡터 데이터베이스글을 숫자 벡터로 바꿔 저장하고, 뜻이 비슷한 것을 찾아 주는 데이터베이스
엔티티 그래프Entity graph. 사람, 사물 같은 대상과 그 관계를 점과 선으로 저장한 구조
메모리 포인터Memory pointer. 저장소에 둔 데이터를 가리키는 ID. 원문 대신 이것만 창에 둔다
에이전트 상태Agent state. Strands에서 에이전트가 대화 기록과 따로 들고 다니는 키-값 저장 공간
SwarmStrands에서 여러 에이전트를 묶어 함께 일하게 하는 방식
호출 상태Invocation state. 한 번의 호출 동안 여러 에이전트가 함께 보는 공유 값. 발표에서는 여기에 포인터를 실어 나눴다
MCPModel Context Protocol. 모델이 외부 도구와 데이터에 연결하는 표준 규약
동기 / 비동기동기: 답이 올 때까지 기다린다. 비동기: 요청만 보내고 다른 일을 하다가 나중에 결과를 확인한다
API GatewayAWS의 API 관문 서비스. 응답을 기다리는 최대 시간이 정해져 있다
Amazon Bedrock여러 회사의 모델을 API로 부를 수 있는 AWS 서비스. Strands의 기본 모델 제공자
