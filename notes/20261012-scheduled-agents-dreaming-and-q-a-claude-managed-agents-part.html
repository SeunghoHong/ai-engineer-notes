에이전트를 예약하고, 지난 세션에서 배우게 하기

Claude Managed Agents 워크숍의 세 번째 영상이다. 앞부분에서는 에이전트를 정해진 일정에 돌리는 배포와, 지난 세션 기록을 읽고 메모리를 고치는 드리밍을 보여 준다. 나머지는 질의응답이다. 관측, 장기 실행, 권한, 확장에 대한 답은 대부분 한 방향으로 모인다. "API로 다 열어 뒀으니 직접 조립하고, 좋아졌는지는 eval로 확인하라."

원본 영상: Scheduled Agents, Dreaming and Q&A: Claude Managed Agents (Part 3 of 4) 발표: Anthropic의 Claude Managed Agents 팀 (자막에 이름이 나오는 발표자는 Gabe)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 고객 사례는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지 않았다. 자막에서 "cloud"로 들린 곳은 문맥상 Claude로, "Android"는 Anthropic으로, "our back"은 RBAC로 바로잡았다. 발표자들은 Anthropic 팀원이고, 자기 회사 제품을 설명하는 자리다. 4부작 워크숍의 3부라 앞 영상의 데모를 이어 간다. mm:ss는 영상 위치다.

3분 요약
  1. Managed Agents에서 작업 단위는 세션 하나다. 데모의 메인 에이전트는 커스텀 도구로 종목마다 세션을 따로 띄워 분석을 나눴다.
  2. 배포는 에이전트 하나를 일정에 맞춰 돌리는 규칙이다. 실행할 때마다 새 세션이 생긴다. 스냅샷이 아니다.
  3. 메모리 스토어는 세션과 따로 존재한다. 필요한 세션에 붙여서 실행 사이의 기억을 이어 간다.
  4. 드리밍은 지난 30일 같은 기간의 세션 기록을 서브에이전트들이 나눠 읽고, 메모리 스토어의 빈틈을 채운다. 아직 연구 미리보기다.
  5. 관측은 모든 이벤트를 API로 준다. 볼 지표를 고르고 기존 도구로 보내는 일은 사용자 몫이다.
  6. 여러 에이전트의 구조는 사람이 정하지 말고 Claude에게 맡기라고 권한다. 권한과 고객 분리의 단위는 지금 워크스페이스뿐이다.
  7. 하네스를 바꿀 때도, 스킬을 고를 때도, 드리밍 결과를 믿을지 정할 때도 답은 같았다. 내 eval로 확인한다.
01

세션을 나눠 띄우는 데모 00:00

영상은 앞 영상의 데모가 끝나 가는 지점에서 시작한다. 발표자는 메인 에이전트에게 Google과 Microsoft를 분석해 달라고 요청한다.

  1. 메인 에이전트가 이미 가진 정보로 충분한지 먼저 따진다.
  2. 앞서 만든 커스텀 도구를 부른다. 화면에는 "dispatch analysis"라는 이름으로 보인다.
  3. 이 도구를 두 종목의 티커로 한 번씩 부른다.
  4. 종목마다 세션이 하나씩 따로 뜬다.
각 세션 안에 있는 것하는 일
멀티에이전트세션 안에서 여러 에이전트가 함께 일한다
outcome 정의원하는 결과의 기준을 정해 두고, 에이전트가 스스로 점검한다
메모리 스토어세션끼리 배운 것을 나눈다

발표자는 이것을 여러 세션을 엮는 하네스라고 부른다. 세션 하나가 부품이고, 그 위에서 세션 여러 개를 조립한다. 이 생각은 하네스의 정의를 묻는 질문에서 다시 나온다.

02

배포: 일정대로 다시 돌리기 01:00

다음 주제는 반복 작업이다. 관심 있는 회사 목록이 있다고 하자. 매일 오전 9시나 매월 1일마다 그 회사들을 모두 분석하고 싶다. 이 일을 맡는 기능이 배포deployment다.

발표자는 모든 기능이 API로 열려 있다고 강조한다. 콘솔로도 다룰 수 있다. 하지만 주로 쓰라고 만든 길은 API와 SDK다. 각 기능은 조립용 부품이고, 사용자는 이걸로 자기만의 UI와 워크플로를 만든다.

배포에 넣는 것 01:40

데모에서는 Claude가 배포를 미리 하나 만들어 두었다.

일정을 기다리지 않고 콘솔에서 바로 한 번 돌릴 수도 있다. 발표자 팀은 배포 목록을 보고, 검색하고, 아무 때나 실행하는 UI도 직접 만들어 보여 줬다. 화면의 몇몇 실행은 실패 상태였다. 발표자는 원인을 나중에 Claude에게 물어보겠다며 넘어갔다.

배포는 스냅샷이 아니다 08:50

Q&A에서 한 참석자가 배포를 "모든 에이전트를 특정 시점에 찍어 둔 스냅샷"으로 이해했다. 발표자는 아니라고 답했다.

오해한 시점의 에이전트들을 얼려 둔 것버전 고정이나 스냅샷처럼 생각한다
→
실제에이전트 하나를 일정마다 새 세션으로 돌리는 규칙"리서치 데스크 에이전트가 분기마다 NVIDIA를 조사"라고 정하면 분기마다 세션이 하나 생기고 보고서가 나온다

그러면 기억은 어디에 남을까. 메모리 스토어는 세션과 따로 존재한다. 어떤 세션에 어떤 메모리 스토어를 붙일지는 사용자가 정한다. 그래서 배포가 매번 새 세션을 만들어도, 같은 메모리 스토어를 붙이면 앞 실행에서 배운 것을 이어 쓸 수 있다.

03

드리밍: 지난 기록에서 배우기 02:50

자기 개선self-improvement에 대한 질문이 앞서 여러 번 나왔다고 한다. 발표자는 Q&A 전에 드리밍dreaming의 미리보기를 보여 준다. 드리밍은 지난 세션 기록을 다시 읽고, 거기서 배운 것을 메모리에 반영하는 기능이다.

설정과 실행 03:00

  1. 메모리 스토어를 고른다. 데모에서는 지금까지 쓰던 것을 골랐다.
  2. 모델을 고른다.
  3. 지시문을 정한다. 직접 써도 되고, 데모처럼 기본 프롬프트를 써도 된다.
  4. 분석할 기간을 정한다. 데모에서는 지난 30일이었다.
  5. 시작하면 Managed Agents 세션이 하나 뜬다. 그 세션이 서브에이전트sub-agent를 여러 개 띄운다.
  6. 서브에이전트들이 이 메모리 스토어를 쓴 세션들의 기록을 나눠 읽는다.

드리밍 자체도 Managed Agents 세션으로 돈다는 점이 재미있다. 제품의 부품으로 제품의 기능을 만든 셈이다.

기록을 읽으며 묻는 것 03:40

  • 메모리 스토어가 필요한 정보를 다 담고 있었나
  • 어떤 세션이 문제를 겪었나
  • 거기서 배울 점이 있나
  • 같은 일이 여러 번 일어났나
  • 지시문을 고칠 수 있나

데모 결과 04:00

드리밍은 앞에서 만든 스킬skill에 빈틈이 있다는 걸 찾았다. 스킬을 쓴 방식에 몇 군데 구멍이 있었다. 드리밍은 스킬 파일을 직접 고치지 않았다. 대신 메모리 스토어에 이런 취지의 내용을 보탰다. "이 스킬이 있더라도, 실제로 겪으며 배운 이 내용으로 보완하라."

앞으로의 계획 지금은 메모리 스토어를 고친다. 발표자는 이를 넓혀 스킬, 에이전트 프롬프트, 서브에이전트 프롬프트까지 직접 고치게 할 생각이라고 했다.

드리밍 결과는 믿을 만한가 12:50

한 질문자가 걱정을 꺼냈다. 드리밍을 여러 번 돌리면 결과가 서로 다른 방향으로 갈 수 있다. 세션 아홉 개는 "이건 틀렸다"고 하고, 하나만 "이건 좋다"고 할 수도 있다. 다수만 따르면 그 하나에 담긴 통찰을 놓친다. 그래서 eval을 드리밍에 연결해 여러 방향 중 나은 쪽을 고르는 자동 방식이 있는지 물었다.

  • 드리밍은 정한 기간의 기록을 보고 사용자가 무엇을 하려 했는지 분석한다. 그 목적에 더 맞춘 메모리 스토어를 만든다.
  • Anthropic은 자기 쪽 eval로 드리밍이 결과를 좋게 만드는지 확인한다고 했다.
  • 일부 고객은 드리밍으로 만든 메모리 스토어를 쓰고 eval 점수가 크게 올랐다고 했다.
  • 드리밍은 연구 미리보기research preview다. 아직 초기 실험 단계라고 했다.
  • 자기만의 eval 세트를 갖추라고 권했다.

eval로 드리밍 방향을 자동으로 고르는 기능이 있는지에는 직접 답하지 않았다. 발표자는 "그냥 저를 믿으라고 하면 되겠냐"고 농담하며, 질문의 뜻은 알아들었다고 했다.

데모에서는 기존 메모리 스토어에 내용을 보탰다. 이 답에서는 "새 메모리 스토어를 만든다"고 설명했다. 자막만으로는 어느 쪽이 기본 동작인지 알 수 없다.

고객의 eval 개선은 Anthropic 발표자가 자기 제품에 대해 한 말이다. 그 점을 감안해 읽자.

04

관측: 이벤트는 전부 준다 04:40

첫 질문은 텔레메트리telemetry였다. 데모 에이전트에 따로 계측 코드를 넣지 않던데, 기본으로 들어 있느냐는 것이다.

질문답
텔레메트리가 기본인가세션에서 일어난 모든 이벤트를 볼 수 있다. 콘솔에서 실시간으로 보거나 API로 가져온다
어떤 화면이 있나트랜스크립트 화면은 읽기 좋게 정리한 것이다. 디버그 화면은 세션의 모든 이벤트를 그대로 보여 준다
지연 시간을 잴 수 있나모델 호출을 시작한 시점과 끝난 시점이 이벤트로 남는다. 그 차이로 지연 시간을 구한다
볼 항목은 누가 고르나지금은 모든 이벤트를 주고 사용자가 거른다. 빠진 이벤트가 있으면 알려 달라고 했다
기존 관측 도구로 보낼 수 있나OTEL로 내보내는 기능은 따로 없다. 모두 API 호출이라 연결 코드를 쉽게 만들 수 있다. 요구가 다 달라서 한 방식을 정해 두지 않았다고 했다
정리 원재료는 다 준다. 무엇을 지표로 삼고 어떤 대시보드로 볼지는 여전히 사용자가 정하고 만든다.
05

얼마나 오래 돌리나 05:50

질문은 이랬다. 에이전트를 끝없이 돌릴 수 있나. 저장된 상태가 계속 커지면 언젠가 따로 압축해야 하나.

  • Anthropic이 컴팩션compaction을 대신 돌린다. 컴팩션은 길어진 맥락을 요약해 줄이는 처리다. 덕분에 세션을 며칠씩 돌릴 수 있다고 했다.
  • 일부 사용자는 10시간짜리 세션을 프로덕션에서 돌린다고 했다.
  • 발표자는 "에이전트를 1년 쓰는 것"과 "세션 하나를 1년 이어 가는 것"이 다르다며 되물었다.
  • 질문자가 "매일 하는 일을 6개월 맡겨도 상태가 넘치지 않느냐"고 다시 묻자, 발표자는 괜찮다는 취지로 짧게 답했다.
시간의 단위맡는 기능근거
세션 하나컴팩션이 맥락을 줄여 며칠까지 간다06:10
반복 작업배포가 일정마다 새 세션을 만든다09:00
세션 사이의 기억메모리 스토어를 붙여 이어 간다09:20

이 표는 Q&A 여러 곳의 답을 이 노트에서 한데 묶은 것이다. 발표자가 이 표 형태로 설명하지는 않았다.

06

구조는 Claude에게 맡긴다 06:40

질문: 에이전트 A가 일을 받아 B와 C에게 나눠 주는 식의 오케스트레이션orchestration을 지원하나.

답: 지금은 서브에이전트를 쓰고, 원하는 것을 Claude에게 말하면 된다.

사람은 Claude가 일하는 방식을 묶어 두고 싶어 한다. 하지만 Claude가 똑똑해질수록 우리는 그 가드레일을 계속 걷어 냈다.발표자의 말을 옮김 06:50

예를 들어 사람은 서브에이전트 세 개가 가장 좋은 구조라고 생각할 수 있다. 발표자에 따르면 그 구조를 Claude가 정하게 두면 결과가 오히려 더 낫다. 그래프로 워크플로를 그리는 UI는 "아직 없다, 곧 생길 수도 있다"고 했다.

"Claude에게 맡기면 더 낫다"는 Anthropic 발표자의 주장이다. 내 작업에서는 고정 구조와 맡긴 구조를 eval로 직접 비교해 보자.

하네스란 무엇인가 09:40

하네스harness는 사람마다 뜻이 다르다. 발표자도 그 점을 인정하고 두 가지 뜻을 나눴다.

Managed Agents가 말하는 하네스

도구 호출 루프를 돌리는 실행부다.

  • 맥락을 관리한다
  • 세션 상태를 관리한다
  • 에이전트가 하려는 일을 해낼 수 있게 받친다
많은 개발자가 말하는 하네스

여러 에이전트와 세션을 하나의 작업 단위로 엮는 것이다.

  • 더 큰 일을 하려고 여러 세션을 조율한다
  • 일정한 연결 구조(토폴로지)로 배치한다

Managed Agents는 세션 하나를 작업 단위로 준다. 개발자는 그 세션을 부품 삼아 자기 하네스를 짓는다. 첫 데모에서 종목마다 세션을 띄운 구조가 그 예다.

핵심 정리

  1. 작업 단위는 세션 하나다. 메인 에이전트가 커스텀 도구로 세션 여러 개를 띄워 일을 나눌 수 있다.
  2. 배포는 에이전트 하나를 일정마다 새 세션으로 돌리는 규칙이다. 스냅샷이 아니다.
  3. 메모리 스토어는 세션과 따로 있다. 세션에 붙여 실행 사이의 기억을 잇는다.
  4. 드리밍은 지난 세션 기록을 서브에이전트들이 읽고 메모리 스토어의 빈틈을 채운다. 연구 미리보기다.
  5. 관측은 모든 이벤트를 API로 준다. 지표 고르기와 OTEL 연결은 사용자 몫이다.
  6. 컴팩션 덕분에 세션은 며칠도 간다. 프로덕션에서 10시간 세션 사례가 있다고 했다.
  7. 오케스트레이션은 서브에이전트로 하고, 구조는 Claude가 정하게 하라고 권한다. 그래프 UI는 아직 없다.
  8. 권한과 고객 분리의 단위는 지금 워크스페이스뿐이다. RBAC는 로드맵에 있고, BYOK는 관측을 잃어 권하지 않는다.
  9. 확장 설정은 없다. API만 부르면 된다. 모델은 Claude만 쓰고, 사내 설치는 검토 중이다.
  10. 하네스, 스킬, 드리밍 모두 좋아졌는지는 내 eval로 판단한다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1첫 데모에서 메인 에이전트는 두 종목 분석을 어떻게 나눴나?
먼저 가진 정보로 충분한지 따진 뒤, 커스텀 도구를 종목마다 불러 세션을 하나씩 따로 띄웠다. 각 세션 안에는 멀티에이전트, outcome 정의, 메모리 스토어가 있다.
Q2배포를 만들 때 넣는 네 가지는?
에이전트 정의, 일정, 첫 메시지 묶음, 그리고 선택으로 붙이는 자원(메모리 스토어, GitHub 저장소, 파일).
Q3배포는 에이전트의 스냅샷인가?
아니다. 에이전트 하나를 일정마다 새 세션으로 실행하는 규칙이다. 분기마다 돌게 하면 분기마다 세션이 하나 생긴다.
Q4매번 새 세션이 생기는데 기억은 어떻게 이어지나?
메모리 스토어는 세션과 따로 존재하는 자원이다. 사용자가 어떤 세션에 어떤 스토어를 붙일지 정한다. 같은 스토어를 붙이면 앞 실행에서 배운 것을 이어 쓴다.
Q5드리밍은 무엇을 읽고, 데모에서는 무엇을 바꿨나?
정한 기간(데모는 지난 30일) 동안 그 메모리 스토어를 쓴 세션 기록을 서브에이전트들이 나눠 읽는다. 데모에서는 스킬의 빈틈을 찾아, 메모리 스토어에 "스킬이 있어도 배운 내용으로 보완하라"는 내용을 보탰다.
Q6드리밍 결과를 믿어도 되는지 발표자는 어떻게 판단하라고 했나?
자기 eval 세트로 확인하라고 했다. Anthropic도 자기 쪽 eval로 확인하고, 드리밍은 아직 연구 미리보기라고 했다. eval로 방향을 자동으로 고르는 기능에는 직접 답하지 않았다.
Q7텔레메트리 질문에서 Managed Agents가 주는 것과 사용자 몫은?
세션의 모든 이벤트를 콘솔과 API로 준다. 모델 호출의 시작과 끝도 이벤트라 지연 시간을 구할 수 있다. 볼 지표를 거르고, OTEL 같은 기존 도구로 보내는 연결을 만드는 일은 사용자 몫이다.
Q8세션이 오래 가도 상태가 넘치지 않는 이유와, 발표자가 말한 실제 길이는?
Anthropic이 컴팩션을 대신 돌려 맥락을 줄인다. 그래서 며칠도 갈 수 있고, 프로덕션에서 10시간 세션을 돌리는 사용자가 있다고 했다.
Q9A가 B와 C에게 일을 나눠 주는 구조를 원하면 어떻게 하라고 했나? 그 이유는?
서브에이전트를 쓰고 원하는 것을 Claude에게 말하라고 했다. 사람이 구조를 정하는 것보다 Claude가 정하게 둘 때 결과가 낫다는 것이 발표자의 주장이다. 그래프형 워크플로 UI는 아직 없다.
Q10Managed Agents가 말하는 하네스와 많은 개발자가 말하는 하네스는 어떻게 다른가?
Managed Agents의 하네스는 도구 호출 루프, 맥락, 세션 상태를 관리하는 실행부다. 개발자들이 흔히 말하는 하네스는 여러 에이전트와 세션을 엮어 큰 일을 하는 구조다. Managed Agents는 세션을 부품으로 주고, 개발자가 그걸로 하네스를 짓는다.
Q11멀티테넌트 SaaS에서 BYOK를 권하지 않는 이유와, 대신 고를 수 있는 두 방식은?
고객의 API 키로 돌면 내 쪽에서 관측을 잃는다. 대신 모든 고객을 한 워크스페이스에 두고 매핑을 직접 관리하거나, 고객마다 워크스페이스를 만든다. 뒤쪽은 고객마다 에이전트를 다시 만들어야 해서 복잡하다.
Q12Claude Cowork와 Managed Agents는 언제 나눠 쓰나?
나 한 사람을 위한 에이전트는 Cowork로 충분하다. 팀, 사내 조직, 또는 내 고객이 쓸 에이전트라면 Managed Agents를 쓴다.
