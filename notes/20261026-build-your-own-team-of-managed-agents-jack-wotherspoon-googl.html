관리형 에이전트로 내 에이전트 팀 만들기

코딩 에이전트를 내 노트북이 아니라 클라우드 샌드박스에서 돌리면 어떤 점이 달라질까. Google DeepMind의 Gemini 관리형 에이전트를 예로, API 호출 한 번으로 샌드박스와 하네스를 얻고, 작업 공간을 공유하는 여러 에이전트를 이어 붙이는 방법을 설명한다.

원본 영상: Build Your Own Team of Managed Agents 발표: Jack Wotherspoon (Google DeepMind 개발자 경험 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 기능 설명과 수치는 모두 발표자가 말한 것이고 문서나 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았고, 불확실하면 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자는 Google DeepMind 소속이고 발표 내용은 자사 제품인 Gemini API의 관리형 에이전트 소개다. 장점 설명은 그 점을 감안해 읽자.

3분 요약
  1. 관리형 에이전트managed agents는 코딩 에이전트와 그 실행 틀을 내 컴퓨터가 아니라 클라우드 샌드박스에서 돌리는 방식이다.
  2. 장점은 두 가지다. 검증 작업이 내 노트북을 점령하지 않고, 개인 설정을 동료나 앱으로 확장할 수 있다.
  3. 직접 만들면 컨테이너, 하네스, 네트워크, 보안을 다 챙겨야 한다. 관리형은 이걸 API 호출 한 번으로 줄인다.
  4. 호출 방식은 Interactions API다. 모델 대신 에이전트를 지정하고 environment=remote를 켠다.
  5. 핵심 설계는 대화(interaction)와 작업 공간(environment)의 분리다. 다른 에이전트가 같은 작업 공간을 이어받아 파일을 계속 다룰 수 있다.
  6. 구성 요소는 하네스, 환경, 스킬, 자격 증명, 트리거 다섯 가지다. 비밀 토큰은 프록시가 바깥에서 끼워 넣고 샌드박스 안에는 가짜 값만 둔다.
  7. 데모에서는 SEC 공시 조사 에이전트, 정량 분석 에이전트, 보고서 에이전트 셋이 같은 환경 ID로 일을 넘겨받았다.
01

왜 내 노트북 밖에서 돌리나 00:20

관리형 에이전트는 코딩 에이전트의 실행 틀, 즉 하네스harness를 내 컴퓨터가 아니라 클라우드의 격리된 공간인 샌드박스sandbox에서 돌리는 것이다. 발표자는 그렇게 하는 이유를 두 가지로 정리한다.

이유 1 · 내 기계가 아니다

에이전트는 코드를 쓰고, 추론하고, 웹을 검색하고, 테스트를 쓰고 실행해 검증된 답을 가져온다.

노트북에서 검증을 돌리면 브라우저를 빼앗기고 팝업이 뜬다. 클라우드에서 돌리면 그 불편이 사라진다.

이유 2 · 노트북은 확장되지 않는다

개인 코딩 에이전트에 스킬이나 설정을 쌓아 두었다고 하자. 그걸 동료에게 어떻게 나누고, 내 앱에 어떻게 넣을까.

고객에게 배포하는 앱이 내 개인 구독으로 돌아가면 안 된다. 규모를 키울 방법이 필요하다.

자막에는 "cloud or managed agents"로 들리는 표현이 반복된다. 문맥상 "클라우드 에이전트 또는 관리형 에이전트"로 읽었다. 02:40 부근의 "cloud managed agents"는 다른 회사의 관리형 에이전트 제품을 가리키는 것으로 보인다(추정).

02

직접 만들기 vs API 한 번 02:10

클라우드 에이전트를 스스로 꾸리려면 할 일이 많다. 발표자는 이 과정을 "꽤 지루하다"고 표현한다.

직접 만들 때네 가지를 다 챙긴다컨테이너나 VM 띄우기 → 안에 도구 올리고 관리 → 샌드박스 안에서 하네스 설계 → 네트워크, 방화벽, 보안 설정
→
관리형 에이전트API 호출 한 번샌드박스와 Antigravity 하네스가 함께 온다. 에이전트가 더 필요하면 호출을 더 한다

인프라나 규모를 따로 관리하지 않는다는 점이 발표자가 말하는 핵심 장점이다. 오늘 발표는 Gemini API에서 제공하는 Gemini 관리형 에이전트를 다룬다.

03

모델 대신 에이전트를 부른다 03:20

호출 창구는 Interactions API다. 발표자는 이를 "에이전트 우선"으로 새로 만든 SDK라고 소개한다. 예전 방식은 모델에 입력을 주고 출력을 받는 한 번의 왕복이었다. 에이전트는 여러 단계를 거쳐 파일을 쓰고, 그 파일을 실행하고, MCP 도구를 부른다. 그래서 그 흐름을 그대로 담는 상호작용interaction 단위가 필요했다. 이 API는 올해 초 정식 출시됐고, 지금은 관리형 에이전트의 집이다.

호출할 때 바뀌는 점은 두 가지다.

  • 모델 이름 대신 에이전트를 지정한다. 기본은 Antigravity 에이전트다.
  • environment=remote를 켠다. 이 한 줄이 "클라우드에서 돌리는 관리형 에이전트를 원한다"는 신호다.
# 예시 (발표 슬라이드의 코드를 자막만 보고 재구성한 것이라 실제 SDK 문법과 다를 수 있다)
interactions.create(
    agent="antigravity",      # 모델 대신 에이전트
    environment="remote",     # 클라우드 샌드박스에서 실행
    input="엔비디아 최근 SEC 공시를 조사하고 핵심 지표를 metrics.json에 저장해",
)

발표자는 "Antigravity"를 Google의 에이전트 제품군 이름으로 쓴다. 자막에는 "anti-gravity"로 적혀 있어 알려진 표기로 고쳤다.

04

내부 구조 04:30

관리형 에이전트를 호출하면 요청이 아래 순서로 흐른다.

  1. 입력: 사용자가 작업을 적어 보낸다.
  2. Gemini API: 서버에 내장된 도구를 갖고 있다. Google 검색으로 웹을 찾고, 파일 시스템 도구로 파일을 읽고 쓴다. 여기에 사용자의 커스텀 함수나 MCP 도구를 더할 수 있다.
  3. 샌드박스: Google Cloud 인프라 위에서 돌아간다. API를 호출하면 이 샌드박스가 자동으로 만들어진다.

샌드박스에는 파일을 올릴 수 있다. 에이전트 스킬, AGENTS.md 같은 지침 파일, 시작할 때 불러올 GitHub 저장소가 그 예다.

05

다섯 가지 구성 요소 05:20

발표자는 관리형 에이전트를 이루는 뼈대를 다섯 가지로 나눈다.

구성 요소하는 일발표자의 설명
하네스 harness도구 호출을 결정하고 내장 도구를 쥔다Google의 Antigravity 제품군이 쓰는 것과 똑같은 하네스다
환경 environment샌드박스의 파일 시스템. 독립된 개체다여러 에이전트가 같은 샌드박스를 가리켜 파일을 이어서 다룰 수 있다
스킬 skills회사나 개인의 작업 절차 문서개인 에이전트에 쓰던 플레이북을 그대로 올린다
자격 증명 credentials토큰이나 MCP OAuth를 샌드박스에 넣어 외부 서비스에 접근새로 추가된 부분이다. 작동 방식은 9장에서 다룬다
트리거 triggers정해진 시각에 에이전트를 깨워 실행예: 매일 아침 8시 30분 장 시작 전에 금융 분석을 돌리고 결과를 Slack으로 보낸다
06

모델 선택과 긴 출력 07:00

하네스가 쓰는 모델은 에이전트 설정agent config의 한 줄로 바꿀 수 있다. 발표자는 작업 성격에 따라 고르라고 한다.

  • 빠르고 효율적이어야 하면 Gemini Flash.
  • 깊은 추론이나 많은 분석이 필요하면 발표 전날 출시됐다는 새 최상위 모델. 자막에는 "Gemini 4 Argon"으로 들린다(추정). 발표자는 금융 작업과 여러 문서에 걸친 데이터 분석에 특히 강하다고 말한다.

긴 출력 long decode 08:10

발표자가 강조한 기능이다. 보통 모델은 한 번에 내놓는 출력 토큰 한도가 약 6만 4천 개다. 새 모델에서는 100만 토큰 컨텍스트를 입력, 사고, 출력이 함께 나눠 쓴다. 그래서 수학 추론이나 재무 모델링처럼 결과가 수십 쪽이 되는 작업도 한 번에 쓸 수 있다고 한다.

발표자는 이 기능이 수학과 금융 벤치마크 점수를 올리고 있다고 말했다. 구체적인 벤치마크 이름이나 점수는 발표에 나오지 않았다.

07

대화와 작업 공간을 분리한다 08:50

발표자가 "두 가지 핵심 원시 요소"라고 부르는 것이다. 둘 다 서버 쪽에 상태를 저장한다.

Interaction · 대화

입력을 넣고 출력을 받는 한 턴이 하나의 interaction으로 저장된다.

  • interaction ID를 다음 호출에 넘기면 두 번째 턴이 된다
  • 즉 대화 맥락을 담당한다
Environment · 작업 공간

샌드박스의 파일 시스템 상태다. 에이전트가 쓴 파일, 만든 이미지가 여기 있다.

  • API로 파일을 내려받거나 올릴 수 있다
  • environment ID를 다른 에이전트에 넘길 수 있다

둘을 떼어 놓으면 이런 흐름이 가능하다. 첫 에이전트가 3분기 공시를 가져와 분석하고 파일로 저장한다. 두 번째 에이전트에 같은 environment ID를 넘기면, 이 에이전트는 대화 맥락은 새로 비어 있지만 파일은 그대로 물려받는다. 발표자는 이것을 멀티 에이전트 워크플로의 바탕이라고 설명한다.

왜 맥락을 비우는 게 장점인가 앞 에이전트가 조사하며 쌓은 긴 대화를 다음 에이전트가 다 들고 갈 필요가 없다. 필요한 결과는 파일에 있다. 다음 에이전트는 깨끗한 컨텍스트 윈도우로 자기 일에만 집중한다.
08

도구, 파일, 에이전트 저장 10:40

도구

샌드박스에는 코드 실행, 파일 읽기와 쓰기, Google 검색이 기본으로 들어 있다. 여기에 외부 서버를 연결해 자기가 쓰는 서비스를 붙일 수 있다. 발표자는 이것이 에이전트를 "일상 업무를 처리하는 수준"으로 끌어올린다고 말한다.

자막에는 "remote SMTP servers"로 들리지만, 문맥상 원격 MCP 서버를 말한 것으로 보인다(추정).

파일 올리기 11:10

개인 기기에서 쓰던 AGENTS.md와 스킬을 샌드박스 파일 시스템에 올린다. 같은 플레이북을 재현 가능한 환경에서 돌리게 되고, 내 컴퓨터의 파일을 덮어쓸 걱정이 없다. 발표의 코드 예시는 AGENTS.md를 올리고 GitHub 저장소를 연결해 에이전트가 코드의 버그를 살피게 했다.

에이전트 저장 11:50

워크플로가 자리를 잡으면 Agents API의 agents.create로 그 설정을 저장한다. 이후에는 agent ID만으로 같은 에이전트를 여러 번 부른다. 고치고 다시 저장하는 반복도 가능하다.

09

비밀 정보는 샌드박스에 없다 12:20

보안에서 발표자가 가장 힘주어 말한 부분이다. GitHub 토큰 같은 비밀 값은 샌드박스 안으로 들어가지 않는다.

  1. 샌드박스와 API 사이에 프록시proxy가 한 층 끼어 있다.
  2. 샌드박스 안에는 진짜 토큰 대신 자리 표시용 가짜 토큰이 놓인다.
  3. 에이전트가 GitHub API를 호출하면 프록시가 그 요청이 GitHub로 가는 것임을 알아보고 그때 진짜 토큰을 끼워 넣는다.
막으려는 상황 에이전트가 "GitHub 토큰이 있네, 다른 데도 뭐가 있는지 보자"며 엇나가는 것이다. 토큰 자체가 없으니 그런 행동이 불가능하다. 발표자의 표현을 빌리면 "에이전트는 해서는 안 될 일을 할 수 없다".
10

예약 실행과 에이전트 팀 13:10

트리거로 예약하기

트리거는 에이전트 하나를 정해진 일정으로 돌린다. 발표자가 든 예는 매일 아침 브리핑이다. 이메일을 훑어 답장할 것을 골라 주거나, 장 시작 전에 주식 시장을 점검한다. 결과는 웹훅으로 Slack에 보내거나, 팀 Jira 보드를 읽어 "오늘 누가 무엇을 하는지"를 보내는 식으로 이어진다.

에이전트가 에이전트를 부른다 13:30

관리형 에이전트는 결국 API 호출이다. 그래서 한 에이전트가 다른 관리형 에이전트를 호출해 일을 여러 갈래로 나눌fan out 수 있다. 발표자가 권하는 구성은 이렇다.

  • 에이전트마다 목적을 하나만 준다. 메모 작성, 조사 같은 좁은 일이다.
  • 결과를 파일로 저장하고, 다음 에이전트가 그 파일을 입력으로 받아 이어간다.
  • 이렇게 쪼개면 각 단계를 통제하고 측정할 수 있다. 넓은 과제를 통째로 주면 에이전트가 무엇을 하는지 가늠할 길이 없다.
11

데모: 세 에이전트가 이어받기 14:30

발표자는 금융 조사 흐름을 세 에이전트로 쪼개 실제로 돌렸다. 전부 같은 environment ID를 쓴다.

1 · SEC 공시 조사 에이전트

대상 기업은 Nvidia. 공시를 조사해 지표를 뽑는다.

핵심 정리

  1. 관리형 에이전트는 하네스를 클라우드 샌드박스에서 돌리는 방식이다. 내 노트북을 점령하지 않고, 개인 설정을 팀과 앱으로 확장한다.
  2. 직접 만들면 컨테이너, 하네스, 네트워크, 보안을 챙겨야 한다. 관리형은 이를 API 호출 한 번으로 줄인다.
  3. Interactions API에서는 모델 대신 에이전트를 지정하고 environment=remote를 켠다.
  4. 구성 요소는 하네스, 환경, 스킬, 자격 증명, 트리거 다섯 가지다.
  5. 모델은 설정 한 줄로 바꾼다. 빠른 일은 Flash, 깊은 분석은 최상위 모델.
  6. 새 모델은 출력 한도를 따로 두지 않고 100만 토큰을 입력, 사고, 출력이 공유한다고 한다. 기존 한도는 약 6만 4천이다.
  7. Interaction은 대화, Environment는 파일이다. 둘을 분리해 서버에 저장한다.
  8. environment ID를 넘기면 다음 에이전트가 깨끗한 컨텍스트로 같은 파일을 이어받는다. 이것이 멀티 에이전트의 바탕이다.
  9. 비밀 토큰은 샌드박스에 들어가지 않는다. 프록시가 바깥에서 끼워 넣고 안에는 가짜 값만 있다.
  10. 에이전트마다 목적 하나, 결과는 파일로, 다음 에이전트가 이어받기. 이렇게 쪼개야 통제하고 측정할 수 있다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 든 "클라우드에서 돌려야 하는 이유" 두 가지는?
첫째, 검증 작업이 내 노트북의 브라우저와 화면을 점령하지 않는다. 둘째, 노트북은 확장되지 않는다. 개인 설정을 동료와 나누고 앱에 넣으려면 클라우드가 필요하다.
Q2클라우드 에이전트를 직접 만들 때 챙겨야 하는 네 가지는?
컨테이너나 VM 띄우기, 그 위에 도구 올리고 관리하기, 샌드박스 안에서 하네스 설계하기, 네트워크와 방화벽과 보안 설정.
Q3Interactions API 호출에서 관리형 에이전트를 켜는 설정은?
모델 대신 에이전트를 지정하고 environment를 remote로 둔다. 이 값이 "클라우드 샌드박스에서 돌려라"는 신호다.
Q4관리형 에이전트의 다섯 구성 요소는?
하네스, 환경, 스킬, 자격 증명, 트리거.
Q5Interaction과 Environment는 각각 무엇을 담당하나?
Interaction은 대화. 입력과 출력의 한 턴이 저장되고 ID를 넘기면 다음 턴이 된다. Environment는 샌드박스의 파일 시스템. 에이전트가 쓴 파일이 여기 있고 ID를 다른 에이전트에 넘길 수 있다.
Q6두 번째 에이전트에 같은 environment ID를 넘기면 무엇이 같고 무엇이 다른가?
파일은 그대로 이어받는다. 대화 맥락, 즉 컨텍스트 윈도우는 새로 비어 있다.
Q7GitHub 토큰이 샌드박스 안에 없는데 에이전트가 GitHub API를 쓸 수 있는 이유는?
샌드박스와 API 사이의 프록시가 요청이 GitHub로 가는 것을 알아보고 그때 진짜 토큰을 끼워 넣는다. 샌드박스 안에는 가짜 토큰만 있다.
Q8발표자가 말한 기존 출력 한도와 새 모델의 방식은?
기존은 약 6만 4천 토큰. 새 모델은 100만 토큰 한도를 입력, 사고, 출력이 함께 나눠 쓴다. 그래서 수십 쪽짜리 결과도 한 번에 쓸 수 있다고 한다.
Q9멀티 에이전트를 짤 때 발표자가 권한 세 원칙은?
에이전트마다 목적을 하나만 준다. 결과를 파일로 저장한다. 다음 에이전트가 그 파일을 받아 이어간다. 이렇게 하면 각 단계를 통제하고 측정할 수 있다.
Q10데모의 세 에이전트와 각 결과물은?
SEC 공시 조사 에이전트가 metrics.json을 만든다. 정량 분석 에이전트가 그 파일을 읽어 Python을 돌리고 주가 전망 Markdown을 쓴다. 보고서 에이전트가 이를 보고서로 바꾼다.
Q11트리거는 무엇이고 발표자가 든 예는?
에이전트를 정해진 일정에 깨워 실행하는 장치. 매일 아침 장 시작 전 금융 분석, 이메일 훑어 답장 후보 고르기, Jira 보드 요약을 Slack으로 보내기.

용어 정리

용어뜻
관리형 에이전트Managed agent. 에이전트의 실행 틀과 샌드박스를 서비스 제공자가 대신 운영하는 방식. 사용자는 API로 호출만 한다
샌드박스Sandbox. 바깥과 격리된 실행 공간. 여기서 코드를 돌려도 내 컴퓨터나 다른 시스템에 영향이 없다
하네스Harness. 모델을 감싸 도구 호출, 순서, 규칙을 정해 주는 실행 틀
Interactions APIGemini API에서 에이전트의 여러 단계 상호작용을 다루는 호출 방식. 모델 대신 에이전트를 지정한다
Interaction입력 하나와 출력 하나로 이뤄진 대화의 한 턴. 서버에 저장되고 ID로 이어 붙인다
Environment샌드박스의 파일 시스템 상태. 서버에 저장되고 ID로 다른 에이전트에 넘길 수 있다
컨텍스트 윈도우Context window. 모델이 한 번에 볼 수 있는 토큰의 총량
토큰Token. 모델이 글을 처리하는 최소 단위. 영어 단어 하나가 토큰 한두 개 정도다
긴 출력Long decode. 모델이 한 번에 아주 긴 결과를 써 내는 능력
MCPModel Context Protocol. 외부 도구와 서비스를 에이전트에 연결하는 표준 규약
OAuth사용자가 비밀번호를 넘기지 않고 다른 서비스에 접근 권한을 주는 인증 방식
프록시Proxy. 두 시스템 사이에 끼어 요청을 받아 넘기는 중간 층. 여기서는 토큰을 끼워 넣는 역할
트리거Trigger. 정해진 시각이나 조건에 에이전트를 자동으로 실행시키는 장치
웹훅Webhook. 어떤 일이 끝났을 때 다른 서비스의 URL로 결과를 밀어 보내는 방식
단계 추적Step trace. 에이전트가 한 행동을 하나씩 기록한 것. 파일 쓰기, 코드 실행 같은 단계가 보인다
팬 아웃Fan out. 한 작업을 여러 에이전트에 나눠 동시에 맡기는 것
AGENTS.md에이전트에게 저장소나 작업의 규칙을 알려 주는 지침 파일
스킬Skill. 특정 작업을 어떻게 하는지 적어 둔 절차 문서. 에이전트가 읽고 따른다
