바이브에서 프로덕션으로: 에이전트 평가 입문

"돌려 보니 괜찮던데"로 배포한 AI 에이전트는 안 본 입력에서 깨진다. 이 워크숍은 트레이스를 모으고, 직접 읽고, 코드 평가와 LLM 판정자를 만들고, 판정자까지 검증한 뒤, 실패 데이터셋과 실험으로 에이전트를 고치는 전체 루프를 두 시간에 걸쳐 보여 준다.

원본 영상: From Vibes to Production: Evaluating and Shipping AI Agents That Work 101 발표: Laurie Voss (Arize AI 개발자 관계 총괄, npm 공동 창업자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 경우에만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

발표자는 관측·평가 플랫폼 Arize AX를 만드는 Arize AI 소속이고, 실습 전체가 그 제품 위에서 진행된다. 도구 선택에 관한 대목은 그 점을 감안해 읽자. 원리 자체는 다른 도구에도 그대로 적용된다.

3분 요약
  1. 평가는 AI의 테스트, 트레이스는 AI의 로그다. 트레이스는 무슨 일이 있었는지 알려주고, 평가는 그게 괜찮았는지 알려준다.
  2. 출력이 매번 달라서 단위 테스트가 안 먹힌다. 그래서 "세 번 돌려 보고 배포"가 흔한데, 세 번은 테스트 묶음이 아니다.
  3. 평가는 세 종류다. 코드 평가(결정적, 공짜), LLM 판정자(의미 이해, 비용과 오판 있음), 사람 평가(기준이지만 느리다). 셋을 겹쳐 쓴다.
  4. 에이전트는 단계마다 틀릴 기회가 늘어난다. 중간 단계도 봐야 하고, 창의적으로 맞은 답을 틀렸다고 채점하는 일도 막아야 한다.
  5. 평가를 쓰기 전에 트레이스를 읽는다. 열 몇 개를 끝까지 읽고 실패를 분류하면, 그 분류가 곧 루브릭의 기준이 된다.
  6. 실습 결과: 티커 검사는 13개 중 12개 통과, 정확성 판정은 13개 중 0개(판정자의 지식이 낡아서), 충실성 판정은 13개 중 6개 통과.
  7. 판정자도 분류기다. 사람 라벨과 비교해 일치율을 재고, 안 맞으면 루브릭의 애매한 부분을 조인다.
  8. 실패한 트레이스를 데이터셋으로 저장하고, 판정자의 설명을 코딩 에이전트에 넘겨 프롬프트를 고치고, 실험으로 전후를 비교한다. 이 루프를 프로덕션에서도 계속 돌린다.
01

평가는 테스트, 트레이스는 로그 07:30

발표자는 하나의 비유로 시작한다. 보통 코드에 테스트를 쓰듯 AI 출력에는 평가 eval를 쓴다. 서버 로그처럼 AI가 실행 중에 무엇을 했는지 기록한 것이 트레이스 trace다. 둘 다 새 이름을 붙였을 뿐 낯선 개념은 아니다.

02

세 번 돌려 보고 배포하는 문제 08:50

지금 가장 흔한 AI 기능 출시 방법은 이렇다. 기능을 만든다. 질문 몇 개를 넣어 본다. "괜찮아 보이네" 하고 배포한다. 그러면 테스트하지 않은 입력에서 깨진다. 발표자는 이것을 바이브 문제 the vibes problem라고 부른다.

단위 테스트가 안 먹히는 이유는 출력이 비결정적이기 때문이다. 같은 프롬프트가 매번 다른 문장을 만든다. 서로 다른 두 답이 모두 맞을 수 있다. 그래서 비교할 기대 문자열이 없다. 팀은 사람이 보고 넘기는 방식으로 후퇴하는데, 이 방식은 확장이 안 되고, 회귀를 못 잡고, CI에서 돌지 않는다.

평가가 없으면 못 하는 일 09:50

  • 프롬프트 고치기. 말투를 고치려고 시스템 프롬프트를 바꿨는데 제품 기능을 지어내기 시작한다. 프롬프트는 커다란 텍스트 덩어리라 한 곳을 바꾸면 전혀 다른 곳이 영향을 받는다. 평가 없이는 두더지 잡기가 된다.
  • 모델 바꾸기. 새 모델이 몇 달마다 나온다. 평가가 없으면 모델 교체는 몇 주짜리 수동 테스트다. 평가가 있으면 몇 시간 안에 점수를 비교한다.

발표자는 이것을 "감으로 나는 것과 계기판을 보고 나는 것의 차이"라고 했다. Descript, Bolt, Anthropic의 Claude Code 팀 모두 바이브로 출시했다가 평가를 세운 같은 궤적을 밟았다고 발표자는 말한다.

03

평가의 세 종류 11:20

코드 평가 code eval

결정적인 함수다. 밀리초에 끝나고 비용이 없다. JSON으로 파싱되나, 500토큰 이하인가, 물어본 것을 언급했나.

  • 장점: 빠르고 싸고 같은 입력에 같은 답
  • 단점: 단위 테스트처럼 깨지기 쉽다. 맞는 답 두 개가 전혀 다른 문장일 수 있다
LLM 판정자 LLM as a judge

두 번째 LLM이 루브릭에 따라 출력을 채점한다. 루브릭은 "무엇이 좋은 답인가"를 적은 규칙이다.

  • 장점: 의미를 이해한다. 사실인가, 출처에 충실한가, 말투가 맞나
  • 단점: 돈이 들고 판정자 자신도 비결정적이라 틀릴 수 있다. 사람 판단과 맞춰 보정해야 한다
사람 평가 human evaluation

도메인 전문가가 읽고 채점한다. 품질의 기준점이다.

  • 단점: 느리고 비싸고 지친다
  • 발표자가 인용한 수치: 사람 주석자는 피로 때문에 결함의 최대 50%를 놓친다

LLM 판정자가 가끔 놓친다고 실망하기 전에, 사람도 놓친다는 점을 기억하라는 뜻이다.

04

에이전트는 왜 더 어려운가 14:20

복잡도에는 사다리가 있다. LLM 호출 하나는 입력과 출력만 보면 된다. 에이전트는 도구 호출과 결정을 연달아 하므로 단계마다 틀릴 확률이 쌓인다. 그래서 중간 단계도 채점해야 한다. 올바른 도구를 골랐나, 인자를 제대로 넘겼나, 언제 멈출지 알았나. 루프에 갇히는 것은 실제로 흔한 실패다. 여러 에이전트가 일을 넘기는 시스템이면 인계 handoff라는 실패 층이 하나 더 생긴다.

연쇄 실패의 예 15:30

자동차 회사 Tesla를 물었다. 에이전트가 웹을 검색해 18세기 발명가 Tesla 정보를 찾는다. 그 정보로 잘 짜인 보고서를 써서 상사에게 보낸다.

어느 단계도 혼자 보면 틀리지 않았다. 입력과 출력을 직접 읽지 않으면 잡을 수 없는 실패다. 어떤 단위 테스트도 이것을 잡지 못한다.

반대 경우: 창의적으로 맞았는데 틀렸다고 채점 16:20

Anthropic이 고객 응대 벤치마크 τ²-bench를 돌렸을 때의 일이라고 발표자는 소개한다. 이코노미 항공권 일정 변경은 불가능하도록 과제를 설계했다. 에이전트는 정책상 허용된 일등석 업그레이드를 먼저 하고, 일등석은 변경이 되므로 일정을 바꿨다.

에이전트는 과제를 해냈지만 테스트는 실패로 채점했다. "창의적으로 맞음"과 "틀림"을 구분해야 한다. 이 이야기는 판정자 검증 대목에서 다시 나온다.

평가 결과에 담기는 세 가지 18:10

  • 점수. 대개 0 아니면 1이다. 이진 점수는 LLM이 가장 잘 다룬다.
  • 라벨. correct / incorrect처럼 사람이 읽는 이름.
  • 설명. LLM 판정자만 준다. 왜 그렇게 판단했는지 적는다.
설명이 평가를 점수판에서 디버깅 도구로 바꾼다 여행 계획 에이전트 예시에서 판정자는 "틀림"만 말하지 않는다. "사용자는 저예산 여행을 물었는데 비용 추정이 하나도 없다"고 적는다. 그러면 프롬프트에서 무엇을 고칠지 바로 안다. 같은 설명이 트레이스 50개에서 반복되면 한 번 생긴 예외가 아니라 구조적 문제다. 그리고 이 설명 뭉치를 코딩 에이전트에 넘기면 "이게 네가 틀린 이유들이다, 어떻게 하면 나아지겠나"라고 물을 수 있다. 이것이 오늘 실습의 마지막 단계다.

설명은 자연어라 그대로 세기 어렵다. 그래서 설명을 실패 유형으로 분류해 개수를 센다. 질적 연구에서는 이 분류 작업을 코딩 coding이라 부른다. 이것도 결국 또 다른 LLM에게 시키게 된다.

오늘 만들 전체 루프는 계측 → 트레이스 → 평가 → 반복이다. 전통 소프트웨어도 같은 루프를 도는데, AI에서는 "측정" 단계에서 대부분의 팀이 넘어진다.

05

트레이싱 설정과 에이전트 만들기 21:10

관측할 수 없는 것은 평가할 수 없다. 그래서 관측이 먼저다. 실습은 Google Colab 노트북에서 진행하고, Anthropic API 키와 Arize AX 계정이 필요하다.

두 줄로 계측하기 25:30

Arize 쪽 사람은 누구나 "두 줄만 넣으면 된다"고 말한다고 발표자는 농담한다. 그 두 줄이 하는 일은 이렇다.

  • register 호출. OpenTelemetry를 설정한다. OpenTelemetry는 애플리케이션 관측의 업계 표준이고, 그 위에 OpenInference라는 층이 프롬프트 텍스트, 완성 텍스트, 토큰 수, 호출한 모델과 도구 같은 LLM 전용 속성을 더한다. 노트북에서는 batch=False로 둬서 텔레메트리를 즉시 보낸다. 프로덕션에서는 효율을 위해 모아서 보낸다.
  • Claude Agent SDK 계측 호출. SDK가 LLM 호출이나 도구 호출을 할 때마다 스팬을 보내게 한다.

코드가 이렇게 적은 이유는 OpenTelemetry가 거의 모두가 쓰는 공개 표준이기 때문이다. Claude SDK, OpenAI SDK, LangChain 저자들이 이미 자기 SDK 안에 전송 코드를 써 두었다. 사용자는 "수집기는 여기 있다, 보내라"고만 하면 된다. CrewAI, LangChain, Mastra 같은 프레임워크도 같은 방식으로 지원된다.

발표자는 오늘 모든 것을 손으로 하지만, Arize가 공개한 스킬 묶음을 설치하면 코딩 에이전트가 계측, 평가 실행, 데이터셋 생성을 대신한다고 소개한다. 손으로 하는 이유는 원리를 이해해서 "바이브로 성공"하지 않기 위해서다.

실습용 에이전트: 금융 분석 챗봇 28:50

항목내용
입력주식 티커와 관심 주제. 예: Tesla의 재무 성과와 성장 전망
1턴: 조사웹 검색 도구로 최신 재무 정보를 모은다. 몇 번 검색할지는 에이전트가 정한다
2턴: 작성모은 자료로 읽기 좋은 보고서를 쓴다
모델Claude Haiku. 유능하지만 실수를 한다. 실수가 있어야 고칠 게 있고, 빠르고 싸다
프롬프트일부러 아주 단순하게 썼다. 나중에 평가로 잡아낼 오류를 만들기 위해서다

내장 LLM 평가: 정확성과 충실성 58:10

코드는 티커가 있는지는 보지만 분석이 좋은지는 못 본다. 재무 데이터가 정확한가, 보고서가 완전한가, 추천의 근거가 탄탄한가. 의미에 관한 질문에는 판정자가 필요하다.

LLM 판정자의 세 부품

  • 판정 모델. 채점하는 LLM. 보통 일하는 모델보다 크고 느린 모델을 고른다. 실습에서는 Haiku가 일하고 Sonnet 4.6이 판정한다.

  • 데이터. 채점할 사례들.

AX는 셋을 분리해 둔다. 같은 기준을 다른 판정 모델로, 같은 모델을 다른 기준으로 섞어 볼 수 있다. 정확성, 충실성, 도구 선택, 도구 호출 인자, 문서 관련성, 거부 감지처럼 자주 쓰는 평가는 프롬프트가 미리 만들어져 있다.

교훈은 한 평가가 다른 평가보다 낫다는 게 아니다. 사용 사례가 다르다는 것이다. 정확성 평가가 잘 맞는 경우도 많다. 실시간 조사라는 이 사례에 안 맞았을 뿐이다. 내장 평가는 프롬프트를 쓰지 않고도 바로 신호를 주는 출발점이다. 하지만 "실행 가능한 추천을 하는가"처럼 도메인에 고유한 기준은 어떤 내장 템플릿도 검사하지 않는다. 진짜 평가를 쓴다면 반드시 나만의 평가를 쓰게 된다.

판정자의 라벨은 예측이고 맞거나 틀린다. 그러니 사람 라벨을 정답으로 두고 일치율, 정밀도, 재현율로 성능을 잴 수 있다. 라벨의 75%로 루브릭을 고치고 25%는 남겨 일반화를 확인한다.
Q12판정자가 나와 가끔 다르면 어떻게 봐야 하나?
불신할 이유가 아니다. 사람끼리도 일치도가 0.2~0.3에 그치는 일이 흔하다. 늘 나와 다른 판정자가 위험 신호다. 불일치의 설명을 읽어 루브릭의 애매한 곳을 조인다.
Q13실패 트레이스를 코딩 에이전트에 넘길 때의 가드레일 두 가지는?
실패 설명만이 아니라 요구사항도 줘서 "평가 통과"가 목표가 되지 않게 한다. 안 그러면 테스트 데이터를 평가에 넣어 속인다. 그리고 개별 실패가 아니라 공통 원인인 주제를 찾게 한다.
Q14개선 투자의 우선순위는?
데이터 품질 → 프롬프트 → 모델 선택 → 하이퍼파라미터. temperature 같은 것은 손대기 쉽지만 효과가 작아 맨 마지막이다.

LLM 판정자LLM as a judge. 두 번째 LLM이 루브릭에 따라 출력을 채점하는 것

정확성 평가Correctness. 판정 모델이 아는 사실을 기준으로 출력이 맞는지 본다
충실성 평가Faithfulness. 주어진 출처 자료에 출력이 충실한지, 지어낸 것은 없는지 본다
환각Hallucination. 근거 없는 내용을 사실처럼 만들어 내는 것

오픈 코딩 / 축 코딩Open coding은 본 것을 자연어로 적기, axial coding은 그것을 원인별 카테고리로 묶기. 질적 연구 용어
스위스 치즈 모델구멍 난 방어층을 여러 겹 쌓아 한 층을 통과한 문제를 다음 층이 잡게 하는 안전공학 개념

가드레일 / 북극성Guardrail은 출시를 막는 필수 기준, north star는 있으면 좋은 지향 지표

과제 (task)실험에서 데이터셋 예시 하나를 받아 실행하고 출력을 돌려주는 함수
