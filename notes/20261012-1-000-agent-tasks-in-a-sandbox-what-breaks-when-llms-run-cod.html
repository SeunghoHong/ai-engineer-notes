에이전트 작업 1,000개로 샌드박스를 시험하다

AWS의 에이전트 호스팅 팀이 코딩 에이전트에게 테스트 1,000개를 만들게 하고, 자기 팀의 클라우드 샌드박스에서 밤새 돌렸다. 실패는 에이전트와 샌드박스를 잇는 인터페이스, 그리고 메모리와 파일 권한 같은 샌드박스의 기본 요소에서 나왔다.

원본 영상: 1,000 Agent Tasks in a Sandbox: What Breaks When LLMs Run Code 발표: Kevin Orellana (AWS, Amazon Bedrock AgentCore 팀)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 연구 결과는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(AgentCore, Kiro, Claude Code, seccomp, eBPF, SWE-bench)은 알려진 이름으로 바로잡았다. 슬라이드의 그림과 실패 건수는 자막에 나오지 않아 옮기지 못했다. mm:ss는 영상 위치다.

3분 요약
  1. 발표자는 코딩 에이전트에게 "우리 샌드박스를 부숴 봐"라고 시키고 밤새 돌렸다. 고객의 에이전트가 플랫폼을 쓰는 방식 그대로 시험하려는 것이었다.
  2. 에이전트가 샌드박스를 다룰 수 있게 MCP 서버를 만들었다. 그다음 에이전트에게 10개 도메인에 걸친 테스트 1,000개를 쓰게 했다.
  3. 결과는 마크다운 파일이 아니라 SQLite에 모았다. 서브에이전트 여러 개가 동시에 기록하기 위해서다.
  4. 실패는 두 층에서 나왔다. 인터페이스 층에서는 이미지가 깨져 돌아왔다. 샌드박스 층에서는 써 둔 파일이 사라졌다.
  5. 같은 플랫폼에서도 앱마다 실패가 달랐다. 클라우드 브라우저는 메모리 부족으로 자주 죽었고, 코드 샌드박스에서는 그런 실패가 없었다.
  6. 실패는 샌드박스 기본 요소 주변에 모인다. 메모리와 CPU, 파일 권한, 파일을 쓸 수 있는 위치, 프로세스 생성 권한, 외부 통신이 그것이다.
  7. 권고: 에이전트를 샌드박스에 올린다면 로컬 테스트로 끝내지 말고, 원격 환경에서 여러 도메인의 작업으로 퍼즈 테스트하라.
01

"부숴 봐" 실험의 출발 00:10

Kevin Orellana는 AWS의 Amazon Bedrock AgentCore 팀에서 일한다. AgentCore는 에이전트를 클라우드에 올려 돌리는 플랫폼이다. 신원 관리, 메모리, 실행 환경, 샌드박스, 게이트웨이처럼 에이전트를 만들고 띄우는 데 필요한 부품을 제공한다.

몇 달 전 발표자는 코딩 에이전트를 팀의 클라우드 샌드박스 환경에 연결했다. 그리고 "부숴 봐"라고 시킨 뒤 밤새 돌렸다. 발표자 스스로도 조금 황당한 시도였다고 말한다.

왜 이런 실험을 했나 01:00

고객이 플랫폼을 쓰는 모습을 보니, 인터넷 서비스의 부품이 점점 에이전트로 바뀌고 있었다. 그 에이전트들은 점점 더 샌드박스sandbox 안에서 돈다. 샌드박스는 바깥과 격리된 실행 환경이다.

그래서 발표자는 고객을 흉내 내기로 했다. 에이전트가 플랫폼을 쓰는 방식 그대로 서비스를 시험하는 것이다.

발표자는 이 플랫폼을 만드는 AWS 팀 소속이다. 실험 대상도, 뒤에 나오는 SSH 기능도 자기 회사 제품이라는 점을 감안해 읽자.

02

MCP 서버와 테스트 1,000개 01:40

첫 단계는 에이전트가 서비스를 자연스럽게 다룰 수 있는 접점을 만드는 것이었다. 최신 모델들은 MCPModel Context Protocol를 잘 안다. MCP는 AI 모델이 외부 도구와 데이터에 접근하는 표준 규약이다.

  1. MCP 서버 만들기: 샌드박스와 플랫폼 기능을 에이전트가 부를 수 있는 도구로 열었다. 하루이틀 걸렸다.
  2. 다듬기: 어떤 도구를 열어 줄지 정했다. 손으로 스모크 테스트smoke test도 돌렸다. 예를 들면 "Python 파일을 써서 실행해", "Python 파일을 Java로 바꿔" 같은 것이다. 02:20
  3. 넓히기: 에이전트에게 10개 도메인에 걸쳐 테스트 1,000개를 쓰라고 했다. 02:30
  4. 운영 준비: 1,000개를 돌리면 몇 시간이 걸리고 토큰도 많이 든다. 그래서 인증 정보를 관리하고 주입하는 방법을 정했다. 테스트가 실패하면 서비스 문제인지 MCP 층 문제인지 가리는 일은 에이전트에게 맡겼다. 02:50
1,000이라는 숫자 발표자 말로는 임의로 정한 숫자다. 그물을 넓게 던져 무엇이 걸리는지 보려는 것이 목적이었다.
03

결과를 모으는 구조 03:00

구조는 단순하다. 발표자는 단순하지만 강력하다고 말한다. 많은 개발자가 평소 개발하면서 이미 본 형태이기도 하다.

구성 요소하는 일
코딩 에이전트테스트를 쓰고 실행한다. 서브에이전트 여러 개가 로컬에서 동시에 돈다
MCP 서버클라우드 샌드박스 환경을 감싸서 에이전트가 도구로 쓸 수 있게 한다
SQLite 데이터베이스모든 테스트 결과를 로컬에 모은다
왜 마크다운이 아니라 SQLite인가 03:30 에이전트는 결과를 마크다운 파일로 쓰려는 경향이 있다. 테스트가 1,000개면 이 방식은 감당이 안 된다. SQLite에 모으면 서브에이전트 여러 개가 동시에 테스트를 돌리고 결과를 기록할 수 있다.
04

테스트 하나가 워크플로 하나 03:50

"테스트 1,000개"는 말로 하면 쉽다. 실제로는 슬라이드의 점 하나하나가 고객이 돌릴 만한 워크플로 하나였다. 시험한 영역은 이렇다.

  • 샌드박스 수명 주기lifecycle: 부하를 걸었을 때 얼마나 안정적인가
  • 파일 입출력: 파일을 샌드박스에 올렸다가 내려받으면 어떻게 되나
  • 성능
  • 소프트웨어 개발 과정: Python 패키지나 Java 패키지 만들기 등

작업 하나의 크기는 제각각이다. 머신러닝 학습을 처음부터 끝까지 돌리는 작업일 수도 있다. PDF 보고서를 만드는 작업일 수도 있다. 웹 페이지 하나를 여는 것처럼 단순할 수도 있다.

앱마다 중요한 테스트가 다르다 04:40

당시 플랫폼에는 큰 앱이 두 개 올라가 있었다. 코드 샌드박스와 클라우드 브라우저다. 팀은 두 앱에 중요한 테스트가 서로 다르다는 걸 금방 알았다.

코드 샌드박스
  • 코드를 쓰고 실행한다
  • Python, Java 패키지를 만든다
  • 파일을 올리고 내려받는다
클라우드 브라우저 04:50
  • 탭을 여러 개 열어 내용을 긁어 오고 요약한다
  • 스크린숏을 찍고 내려받는다
  • 폼을 채우고 로그인 과정을 자동화한다

핵심은 샌드박스에 올라간 앱마다 거치는 워크플로가 다르다는 점이다. 워크플로가 다르면 샌드박스에 요구하는 것도 다르다.

실패 사례 세 가지 05:10

발표자는 실패 가운데 패턴을 잘 보여 주는 세 가지를 골랐다.

증상원인층

널 바이트가 테스트를 망가뜨렸다널 바이트는 값 0일 수도 있고, 어떤 언어에서는 문자열이 끝났다는 표시다발표에서 밝히지 않음
샌드박스 안 특정 디렉터리에 파일을 썼는데, 다시 가져오려니 없었다 06:00샌드박스 쪽 문제샌드박스

발표에서 원인을 더 자세히 설명하지는 않았다. 일반적인 배경을 덧붙인다. MCP 메시지는 JSON 텍스트라서, 이미지 같은 바이너리는 base64 같은 텍스트 형식으로 바꿔 주고받는다. 이 변환이 한쪽에서 어긋나면 받은 파일이 원본과 달라진다. 널 바이트도 비슷하다. C 계열 언어처럼 널 바이트를 문자열 끝으로 읽는 코드를 지나면 그 뒤가 잘려 나갈 수 있다.

06

API 서비스와 무엇이 다른가 06:20

층을 나눠 보는 이유가 있다. 샌드박스에 올린 앱은 전형적인 API 서비스와 다르게 움직이기 때문이다.

지금까지오래 떠 있는 API 서비스요청을 보내면 모양이 정해진 응답이 온다. 백엔드가 무슨 일을 하는지 안다.
→
지금샌드박스 속 전문 에이전트게이트웨이로 접근한다. 할 일이 미리 정해져 있지 않아서, 컴퓨팅 환경에 요구하는 것이 크게 달라진다.

로컬에서 이미 본 장면 07:00

Kiro, Claude Code, Codex 같은 코딩 에이전트를 로컬에서 써 봤다면 익숙한 장면이 있다. 에이전트가 예상하지 못한 패키지를 내려받는다. 별 이유 없이 CSV를 JSON으로, 다시 PDF로 바꾼다.

이런 워크플로 하나하나가 환경에 다른 것을 요구한다.

  • 샌드박스의 메모리와 CPU 크기
  • 프로세스에 주어진 권한
  • 파일 시스템 권한

발표자의 요점은 이것이다. 이 제약들이 에이전트가 문제를 풀 수 있느냐를 크게 좌우한다.

07

실패가 모이는 곳 07:50

발표자는 두 앱의 실패를 나란히 놓고 비교했다. 위는 코드 샌드박스, 아래는 클라우드 브라우저였다. 빨간색은 샌드박스 자체가 죽은 경우다.

클라우드 브라우저: 메모리 부족 08:10 브라우저 탭은 메모리를 많이 쓴다. 그래서 브라우저 테스트의 상당수가 메모리 제약 때문에 실패했다. 테스트가 세션과 샌드박스의 메모리를 다 써 버렸고, 결과는 완전한 실패로 기록됐다. 코드 인터프리터 환경에서는 이런 실패가 보이지 않았다.

실패를 다른 방식으로 묶어 보면, 샌드박스 기본 요소sandbox primitives 주변으로 모인다. 기본 요소는 샌드박스를 이루는 바탕 장치다. 파일 시스템을 예로 들면 이런 것들이다. 08:20

  • 파일 시스템 권한
  • 마운트된 파일 시스템
  • 파일을 읽고, 쓰고, 실행할 권한
  • 파일 시스템이 영구적인가, 세션이 끝나면 사라지는가

테스트는 봐주지 않았다. 고객은 샌드박스에서 어떤 작업이든 만들 수 있다고 기대한다. 그러니 샌드박스의 제약이 에이전트가 일을 끝낼 수 있느냐를 크게 좌우한다는 점을 조심해야 한다.

08

샌드박스를 이루는 부품 09:10

샌드박스 컨테이너는 여러 기본 요소를 조합해 만든다. 깊게 들어가면 운영체제의 핵심인 커널 수준까지 내려간다. 발표자가 든 부품과 예는 이렇다.

부품하는 일에이전트가 막힐 수 있는 예
커널 권한 kernel capabilities관리자 권한을 잘게 나눠 프로세스에 필요한 것만 준다발표에서 구체적인 예는 들지 않았다
eBPF 프로그램커널에서 일어나는 동작을 가로채 관찰하거나 막는다외부로 나가는 호출이나 사내 API 호출을 통제할 수 있다 09:40
seccomp프로세스가 부를 수 있는 시스템 호출을 제한한다머신러닝 패키지가 새 프로세스를 띄워야 하는데, 컨테이너에 그 권한이 없을 수 있다 10:10
파일 배치무엇이 어디에 있고, 어디에 쓸 수 있는지 정한다Python 패키지가 Python 커널이 찾는 위치에 설치돼야 한다. Rust 바이너리가 실행 가능한 위치에 있어야 한다 10:30

자막상 발표자는 eBPF가 "커널 모듈을 돌리고 Python 층에서 프로그램을 가로챈다"고 말한다. 일반적으로 eBPF는 커널 모듈을 넣지 않고 커널 안에서 작은 프로그램을 돌리는 기술이다. 가로채는 대상도 시스템 호출이나 네트워크 같은 커널 수준의 동작이다.

발표자의 정리는 이렇다. 아주 작은 것들이 쌓여서, 에이전트가 업무 문제를 풀 수 있는지를 결정한다.

09

퍼즈 테스트로 찾기 11:00

요즘은 LLM으로 단위 테스트를 만드는 일이 흔하다. 발표자는 "단위 테스트를 아직 손으로 쓰는 사람이 있는지 모르겠다"고 농담했다. 한 층 위의 통합 테스트도 에이전트가 문제 영역을 이해하고 잘 쓸 거라고 기대할 수 있다.

하지만 앱이 점점 샌드박스 속 에이전트가 되면서 틈이 보인다. 아주 낮은 층의 기본 요소와 통제 장치가 에이전트의 목표 달성을 방해할 수 있다. 이런 실패는 사람 눈에 사소해 보여서 잘 드러나지 않는다. 11:20

발표자가 제안하는 방법 11:50 에이전트 샌드박스에 아주 많은 워크플로를 맡겨 보고 결과를 본다. 이번 실험에서는 1,000개였다. 발표자는 이것을 "fuzzy testing"이라고 불렀다. 보통 퍼즈 테스트fuzz testing는 예상 밖의 입력을 대량으로 넣어 버그를 찾는 방법이다. 여기서는 입력 대신 여러 도메인의 작업을 대량으로 넣는다.
10

로컬과 원격은 다르다 12:00

많은 개발자가 Codex나 Claude Code 같은 코딩 에이전트를 노트북에서 돌린다. 작업 공간이 늘면 노트북이 감당하지 못한다. 그래서 팀들은 코딩 에이전트를 원격 샌드박스로 옮긴다. 처리하는 GitHub PR 수를 늘리려는 것이다.

문제는 로컬에 있던 도구가 원격 샌드박스에는 없을 수 있다는 점이다. 로컬의 MCP 도구와 로컬에서 돌던 앱이 원격 환경과 맞지 않는다. 12:20

AgentCore의 대응: 샌드박스에 SSH로 접속 12:30

AgentCore 팀은 이 문제에 관심이 많다. 최근 고객이 자기 샌드박스에 SSH로 들어가 안에서 무슨 일이 일어나는지 볼 수 있게 했다.

발표자는 이제 SSH로 들어가는 쪽이 사람이 아니라 함께 개발하는 코딩 에이전트라고 덧붙인다. 에이전트가 샌드박스 안을 직접 살펴보며, 코딩 에이전트나 앱이 왜 매끄럽게 돌지 않는지 찾는다.

이 대목은 발표자 회사 제품의 기능 소개다. 그 점을 감안해 읽자.

11

벤치마크도 환경에 흔들린다 13:20

새 프런티어 모델이 나오면 다들 먼저 SWE-bench 점수를 본다. 발표자는 이 점수도 환경에 따라 크게 달라진다는 연구 두 개를 인용했다.

UC Berkeley 연구진 13:40

환경 통제를 맞춰 두고, 환경의 허점을 파고드는 에이전트exploit agent를 썼다. 그러자 SWE 벤치마크 점수가 최대 100%까지 나왔다.

뜻: 환경이 허술하면 점수가 실력보다 높게 나온다.

다른 연구 (발표에서 이름을 밝히지 않음) 13:50

넓은 범위의 업무 문제를 에이전트에게 주되, 도구를 고장 낸 상태로 줬다. 에이전트의 효과가 크게 떨어졌다.

뜻: 환경이 망가지면 점수가 실력보다 낮게 나온다.

두 연구는 같은 방향을 가리킨다. 에이전트의 성과는 모델만이 아니라 그 모델이 도는 환경에도 달려 있다.

자막에서 "three benchmarks"로 들리는 부분은 앞 문맥상 SWE 벤치마크로 보인다(추정). 두 연구 모두 발표자가 인용한 것이고 원 논문은 확인하지 않았다.

12

결론 14:10

앱은 점점 에이전트가 되어 간다. 고객에게 만들어 주는 것이 정해진 REST API 서비스가 아니라, 샌드박스 안에서 무엇이든 하는 에이전트가 된다.

그러면 문제가 생긴다. 샌드박스 기본 요소 때문에 에이전트가 일을 덜 잘하게 되는 지점을 모두 찾기가 아주 어렵다.

에이전트를 샌드박스에 올리려 한다면, 로컬에서 테스트하는 것도 좋다. 하지만 원격 환경에서 여러 도메인의 테스트로 퍼즈 테스트도 하라.발표자의 마지막 권고를 옮김 14:40
13

핵심 정리

  1. 발표자는 코딩 에이전트에게 자기 팀의 클라우드 샌드박스를 부숴 보라고 시키고 밤새 돌렸다. 고객의 에이전트처럼 플랫폼을 써 보는 실험이다.
  2. 에이전트와 샌드박스의 접점은 MCP 서버로 만들었다. 최신 모델이 MCP를 잘 알기 때문이다.
  3. 10개 도메인의 테스트 1,000개는 에이전트가 썼다. 숫자는 임의로 정했고, 목적은 넓게 훑는 것이다.
  4. 결과는 마크다운 대신 SQLite에 모았다. 서브에이전트 여러 개가 동시에 기록할 수 있다.
  5. 실패는 인터페이스 층(이미지 인코딩, 널 바이트)과 샌드박스 층(사라진 파일)으로 나뉜다.
  6. 같은 플랫폼이라도 앱마다 실패가 다르다. 클라우드 브라우저는 메모리 부족으로 자주 죽었다.
  7. 실패는 샌드박스 기본 요소 주변에 모인다. 메모리와 CPU, 파일 권한, 마운트, 영구 또는 임시 저장이 그것이다.
  8. 커널 권한, eBPF, seccomp, 파일 배치 같은 작은 설정이 프로세스 생성, 외부 호출, 패키지 설치를 막을 수 있다.
  9. 로컬에서 되던 에이전트도 원격 샌드박스에서는 도구가 달라 막힌다. 벤치마크 점수도 환경에 따라 크게 오르내린다.
  10. 권고: 로컬 테스트로 끝내지 말고 원격 샌드박스에서 여러 도메인의 작업으로 퍼즈 테스트하라.
14

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 이 실험을 한 이유는?
서비스의 부품이 점점 샌드박스 속 에이전트로 바뀌고 있어서다. 그래서 고객의 에이전트가 플랫폼을 쓰는 방식 그대로 서비스를 시험하려 했다.
Q2에이전트가 샌드박스를 다루는 접점으로 MCP를 고른 이유는?
최신 모델들이 MCP를 잘 알기 때문이다. 에이전트에게 익숙한 방식으로 서비스를 열어 줄 수 있고, 하루이틀이면 만들 수 있었다.
Q3테스트 1,000개라는 숫자는 어떻게 정했나?
임의로 정했다. 그물을 넓게 던져 무엇이 걸리는지 보려는 것이 목적이었다.
Q4결과를 마크다운 파일 대신 SQLite에 저장한 이유는?
테스트가 1,000개면 마크다운 파일로는 감당이 안 된다. SQLite를 쓰면 서브에이전트 여러 개가 동시에 결과를 기록할 수 있다.
Q5이미지를 올렸다 내려받았을 때 원본과 달랐던 원인은?
MCP 층의 인코딩이 잘못돼 있었다. 샌드박스가 아니라 인터페이스 층의 문제다.
Q6널 바이트가 테스트를 망가뜨릴 수 있는 이유는?
널 바이트는 값 0일 수도 있고, 어떤 언어에서는 문자열이 끝났다는 표시다. 그래서 데이터 중간에 있으면 그 뒤가 잘리거나 다르게 읽힐 수 있다.
Q7팀은 실패를 어떤 두 층으로 나눴나?
인터페이스 층과 샌드박스 층. 인터페이스 층은 에이전트와 샌드박스 사이에서 데이터를 옮기는 부분이고, 샌드박스 층은 코드가 실제로 도는 환경이다.
Q8클라우드 브라우저에서 특히 많았던 실패와 그 이유는?
메모리 부족으로 샌드박스가 죽는 실패. 브라우저 탭이 메모리를 많이 쓰기 때문이다. 코드 인터프리터 환경에서는 이런 실패가 보이지 않았다.
Q9seccomp 설정 때문에 머신러닝 작업이 막히는 예는?
머신러닝 패키지가 새 프로세스를 띄워야 하는데, 컨테이너에 프로세스를 만들 권한이 없는 경우다.
Q10로컬에서 잘 되던 코딩 에이전트가 원격 샌드박스에서 막히는 이유는?
로컬에 있던 MCP 도구나 앱이 원격 샌드박스에는 없거나 다르기 때문이다.
Q11발표자가 인용한 두 벤치마크 연구가 함께 보여 주는 것은?
에이전트의 점수가 환경에 크게 좌우된다는 것. 환경의 허점을 이용하면 최대 100%까지 오르고, 도구가 고장 나면 크게 떨어진다.
Q12발표자의 마지막 권고는?
에이전트를 샌드박스에 올린다면 로컬 테스트로 끝내지 말고, 원격 환경에서 여러 도메인의 테스트로 퍼즈 테스트하라.

용어 정리

용어뜻
샌드박스Sandbox. 바깥과 격리된 실행 환경. 에이전트가 코드를 돌려도 다른 시스템에 영향을 주지 않게 한다
Amazon Bedrock AgentCoreAWS의 에이전트 호스팅 플랫폼. 신원 관리, 메모리, 실행 환경, 샌드박스, 게이트웨이를 제공한다
MCPModel Context Protocol. AI 모델이 외부 도구와 데이터에 접근하는 표준 규약
스모크 테스트Smoke test. 기본 기능이 돌아가는지만 빠르게 확인하는 테스트
서브에이전트메인 에이전트가 일을 나눠 맡기는 하위 에이전트
SQLite파일 하나로 동작하는 가벼운 데이터베이스
널 바이트Null byte. 값이 0인 바이트. C 계열 언어에서는 문자열 끝 표시로 쓰인다
인코딩데이터를 전송이나 저장에 맞는 형식으로 바꾸는 것
샌드박스 기본 요소Sandbox primitives. 샌드박스를 이루는 바탕 장치. 메모리 한도, 파일 시스템, 권한, 커널 통제 등
마운트저장 장치나 다른 파일 시스템을 특정 경로에 붙여 쓰는 것
영구 / 임시 파일 시스템Persistent / ephemeral. 세션이 끝나도 남는 저장소와, 끝나면 사라지는 저장소
커널 권한Kernel capabilities. 관리자 권한을 잘게 나눈 단위. 프로세스에 필요한 것만 준다
eBPF커널 모듈 없이 커널 안에서 작은 프로그램을 돌려 시스템 동작을 관찰하거나 막는 기술
seccompSecure computing mode. 프로세스가 부를 수 있는 시스템 호출을 제한하는 리눅스 기능
시스템 호출System call. 프로그램이 파일 열기, 프로세스 만들기 같은 일을 운영체제에 요청하는 통로
외부 통신Egress. 샌드박스 안에서 바깥 네트워크로 나가는 요청
게이트웨이바깥 요청을 받아 안쪽 서비스나 에이전트로 넘겨 주는 입구
퍼즈 테스트Fuzz testing. 예상 밖의 입력을 대량으로 넣어 버그를 찾는 방법. 이 발표에서는 여러 도메인의 작업을 대량으로 넣는다
SWE-bench실제 오픈소스 이슈를 모델이 고치고 테스트 통과 여부로 채점하는 벤치마크
SSH원격 컴퓨터에 안전하게 접속해 명령을 실행하는 방법
