자는 동안 스스로 고치는 에이전트

에이전트의 실행 기록을 사람이 다 읽을 수는 없다. 그 일을 다른 에이전트에게 맡기고, 실패를 데이터셋으로 모으고, 평가를 만들고, 수정을 실험으로 증명하는 루프를 만든다. 사람은 수정 검증, 데이터 선별, 평가 설계처럼 판단이 필요한 자리에만 남는다.

원본 영상: Agents That Self Improve While You Sleep 발표: Fuad Ali (Arize AI 프로덕트 매니저)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 수치와 사례는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 것만 바로잡고, 나머지는 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자는 Arize AI 소속이고, 워크숍 전체가 Arize의 제품(AX, Signal, 관리형 에이전트)을 시연하는 구성이다. 제품 기능에 대한 설명은 그 점을 감안해 읽자.

3분 요약
  1. 에이전트는 결과가 매번 달라서 실패 방식을 알기 어렵다. 에이전트가 수천 개면 사람이 트레이스를 다 읽는 건 불가능하다. 읽는 일은 에이전트에게 맡긴다.
  2. 성숙도는 다섯 상자다. 트레이싱 → 평가 → 트레이스 읽기 → 실패를 테스트로 저장 → 수정을 증명. 뒤로 갈수록 하는 팀이 적다.
  3. 루프는 이렇게 돈다. 트레이스 → Signal이 읽고 이슈 묶기 → 실패 데이터셋 → 평가 제안 → 코드 수정 PR → 실험으로 증명 → 사람이 검토하고 머지 → 다시 처음.
  4. 데모의 버그는 검색 필터의 대소문자 불일치였다. 결과가 안 나와 전체를 다시 뒤지느라 지연이 14~17초까지 튀었다. Signal이 6분 만에 원인을 찾아 PR을 냈다.
  5. 실패 사례를 모은 데이터셋은 살아 있는 픽스처다. 새 실패가 생길 때마다 자라고, 수정할 때마다 회귀 테스트로 쓴다.
  6. 평가는 코드 검사, LLM 심판, 에이전트 심판, 결정 모델 네 종류다. 싸고 결정적인 것부터 쓰고, 비싼 건 샘플링한다.
  7. 사람이 남는 자리는 세 곳이다. PR 검증, 데이터셋 선별, 평가 설계. 자동화할 수 있다고 다 자동화하지 말고, 자동화로 검토자를 돕는다.
01

새벽 4시의 호출을 없애려면 01:00

에이전트는 같은 입력에도 다른 길을 간다. 이 비결정성 non-determinism 때문에 전통적인 "왜 실패했나" 문제가 열 배 어려워진다. 여기에 내부 에이전트, 코딩 에이전트, 마케팅 에이전트, 고객용 에이전트가 수천 개 겹치면 잡음이 폭발한다.

발표자가 든 그림은 새벽 4시의 PagerDuty 호출이다. 프로덕션의 쇼핑 도우미가 모든 고객에게 "보드게임은 하나도 없다"고 답하고 있다. 더 나쁜 사례로 캐나다의 자동차 딜러 챗봇이 차를 몇 달러에 팔기로 약속한 일도 언급했다. 딜러는 판매를 인정하지 않았지만, 법무팀 일이 됐다.

목표 사람의 피드백, 고객 피드백, 그리고 트레이스 같은 실제 증거를 에이전트가 스스로 읽고 고치는 데 쓰게 한다. 사람은 그 루프에서 가장 값어치 있는 지점에만 남는다.
02

우리 팀은 어느 상자에 있나 05:40

발표자는 청중에게 손을 들게 하며 다섯 단계를 짚었다. 앞 단계는 많은 팀이 하고 있었고, 뒤로 갈수록 손이 줄었다.

단계하는 일답하는 질문
1. 트레이싱에이전트가 어떤 도구를 불렀고 어떤 경로로 갔는지 트리로 기록한다에이전트가 무엇을 했나
2. 평가트레이스에 점수를 매긴다그게 맞는 행동이었나
3. 트레이스 읽기누군가 실제로 트레이스를 읽고 원인을 찾는다왜 틀렸나
4. 실패를 테스트로 저장실패 사례를 데이터셋에 넣어 회귀 테스트로 쓴다같은 실수를 두 번 하지 않나
5. 수정을 증명고친 뒤 실제로 나아졌는지 실험으로 보인다정말 고쳐졌나

3단계가 병목이다. 코딩 에이전트의 트레이스나 수백만 고객을 상대하는 챗봇의 트레이스를 사람 한 명이 다 읽을 수는 없다. 그래서 이 단계를 에이전트에게 넘기는 것이 워크숍의 핵심이다.

03

루프 한 바퀴 07:50

  1. 트레이스가 프로젝트로 들어온다.
  2. Signal이 트레이스를 읽는다. Arize가 기본 제공하는 SRE 역할의 에이전트다.
  3. 실패를 묶어 데이터셋을 만든다.
  4. 그 실패를 앞으로 잡아낼 평가를 제안한다.
  5. 저장소를 읽고 수정을 PR로 올린다.
  6. 실패 사례를 다시 돌려 수정이 맞는지 실험으로 증명한다.
  7. 사람이 PR을 검토하고 머지한다. 다시 1번으로.

매 바퀴마다 쌓인 맥락이 다음 바퀴의 입력이 된다. 발표자는 이것이 제품 로드맵뿐 아니라 엔지니어링 신뢰성 조직에도 재료가 된다고 말했다.

04

실습 에이전트와 트레이싱 09:00

실습용 에이전트는 Wonder Toys라는 채팅형 장난감 가게다. 제품을 묻고 채팅으로 살 수 있다. FastAPI, Next.js, ChromaDB와 에이전트 SDK로 만들었고 트레이스를 Arize AX로 보낸다. 데모를 위해 도구 하나에 버그를 심어 두었다. 그 도구는 필터를 잘못 건다.

따라 하려면 필요한 것 03:30

  • Arize AX 무료 계정, 스페이스 ID, API 키
  • OpenAI 또는 Anthropic 같은 LLM 제공자 API 키
  • Node와 Python
  • 코딩 에이전트가 Arize 도구를 다룰 수 있게 해 주는 스킬 설치

트레이스 트리 10:20

사용자가 "9살 아이에게 맞는 장난감 보여줘"라고 물으면 에이전트 호출, 모델 호출, 도구 호출이 트리로 기록된다. 각 노드에 시작·종료 시각, 지연, 입력, 메타데이터, 그래프 상의 단계, DB에서 가져온 결과가 붙는다. 발표자의 말대로 이걸 새벽 4시에 수천 개 읽고 싶은 사람은 없다.

계측은 AX CLI의 안내형 설정으로 한다. 제공자와 주요 에이전트 프레임워크의 자동 계측기가 오픈소스로 있고, CLI와 MCP를 감싼 스킬이 있다. 도구 호출마다 인자와 결과가 든 스팬 span이 생기고, 모델 호출과 토큰 수가 기록되며, 여러 번 주고받은 대화는 세션으로 묶인다.

05

Signal: 트레이스를 읽는 상시 에이전트 12:10

Signal은 정해진 주기로 프로젝트의 트레이스를 읽는 상시 에이전트다. 기본 주기는 6시간이다. 프로젝트를 지정하고 켜면 트레이스를 검토하고 스킬을 통해 여러 행동을 한다. 데모에서는 GitHub 저장소에 연결했다. 에이전트의 트레이스와 소스 코드를 함께 읽고 수정을 제안한다.

데모에서 Signal이 찾은 것 13:30 이슈 이름은 "불필요한 검색 재시도"다. 검색 도구 호출 뒤에 LLM 호출이 세 번 연달아 일어나고 지연이 높았다. 원인은 필터 쿼리의 대소문자였다. 제품 카테고리는 소문자에 하이픈을 쓴 슬러그 slug로 저장돼 있는데, LLM은 "Car Games"처럼 사람이 읽는 제목 형식으로 넘겼다. 정규화가 없으니 결과가 비고, 에이전트는 전체 제품을 다시 뒤졌다. 그래서 지연이 14~17초까지 올랐다.

Signal은 이슈를 묶고, 개요와 분석을 쓰고, 수정안을 쓴다. 화면에서는 이 이슈를 잡는 평가를 만들거나, 실패 사례를 데이터셋에 넣거나, GitHub 아이콘으로 PR이나 이슈를 열 수 있다. 평가를 켜 두면 같은 문제가 30일 안에 다시 생길 때 자동으로 경보가 울린다.

PR 세션을 열어 보면 에이전트가 6분 동안 일해 저장소 안에서 근본 원인을 찾았다. PR 설명에는 실제로 실패한 트레이스 다섯 개가 증거로 들어 있다.

06

직접 만드는 관리형 에이전트 16:10

Signal은 관리형 에이전트 플랫폼의 템플릿 하나다. 비용 에이전트 템플릿도 있다. 비싼 모델이 싼 일을 하는 곳을 찾아 더 싼 라우팅을 추천하고 절감액을 계산한다.

에이전트 스튜디오에서는 처음부터 만들 수 있다. 에이전트 설정을 고르고, 트레이스가 들어오는 프로젝트를 가리키고, 작업을 적고, 스킬을 붙인다.

붙일 수 있는 것예시
스킬GitHub, 권한 체계 RBAC 확인용 외부 시스템, Datadog 같은 APM. API 키가 있고 하네스에서 부를 수 있으면 무엇이든 된다
샌드박스기본은 Arize 관리형. Modal, Daytona, E2B 같은 자체 샌드박스도 된다
하네스Codex, Cursor, Claude Code, OpenCode. 더 추가될 예정
트리거시간 주기, 또는 경보. 예: 지연이 10초를 넘으면 조사 에이전트를 띄운다

SRE 조사, 비용 분석, 제품 분류 등 트레이스 위에서 돌릴 수 있는 관점은 여러 가지다.

07

이슈 정리와 살아 있는 픽스처 18:20

Signal은 리뷰어가 하듯 문제 하나에 티켓 하나만 연다. 같은 증거로 수백 개 이슈가 생기지 않는다. 해결 또는 무시로 처리하면 이후 같은 이슈는 중복 제거된다.

발표자가 가장 중요하다고 꼽은 흐름은 데이터셋에 추가다. 지속적 개선은 과거에 무엇이 실패했는지 기록이 있어야 가능하다. 코드를 내기 전에 테스트를 쓰는 건 당연하다. 여기서 새로운 건 그 테스트 묶음이 살아 있는 픽스처 living fixture라는 점이다. 새 사용 사례와 새 실패 방식이 생길 때마다 자란다. 실패의 정의를 한 시점에 고정하지 않고 프로덕션에서 실패하는 대로 키운다.

자전거를 탈 때마다 뭔가 알아채고, 그게 쌓이면 왼발을 왼쪽 페달에 올리는 걸 더는 생각하지 않게 된다.발표자의 비유. 발표자는 두 달 전 자전거에서 떨어져 발이 부러졌다고 덧붙였다.
08

평가의 네 가지 종류 20:20

픽스처가 생기면 그 위에서 기대하는 동작을 코드로 굳혀야 한다. 그게 평가 eval다.

종류맞는 일비용
코드 검사결정적 확인. 필드가 있나, 유효한 JSON인가, 필터가 적용됐나, 도구가 맞는 인자로 불렸나아주 싸다
LLM 심판 LLM as a judge질적이고 모호한 판단. 다른 모델이 트레이스 결과에 점수를 매긴다모델 호출 한 번 추가. 샘플링과 필터링으로 조절
에이전트 심판 agent as a judge무엇을 평가할지도 정해지지 않은 열린 목표. 에이전트가 기준과 점수를 스스로 고른다가장 비싸다. 모델 호출이 여러 번
결정 모델 decision model예/아니오, 선택, 점수처럼 형식이 정해진 판단일반 LLM보다 훨씬 싸다

결정 모델은 발표 시점 기준 나온 지 한 달쯤 된 종류라고 했다. Arize의 Laurie Voss(추정)가 벤치마크와 트레이드오프 자료를 많이 냈다고 한다. 자막에서 정확한 제품명은 알아들을 수 없었다.

09

사람이 가장 값어치 있는 자리 22:50

평가 점수와 트레이스가 모이면 코딩 에이전트가 수정을 구현하기에 충분한 맥락이 된다. Signal은 Arize 관리형 샌드박스에서 코딩 하네스로 이 일을 한다. 개발 중이라면 CLI로 트레이스를 바로 끌어와 로컬 에이전트에게 줄 수도 있다.

그 사이에 사람이 서는 자리는 세 곳이다.

1. 수정 검증

PR을 읽는다. 금융처럼 걸린 게 큰 분야라면 사람이 읽고 머지하는 쪽이 당연하다.

2. 데이터셋 선별

이 발견이 픽스처에 넣을 만큼 좋은가. 일부러 수동으로 남긴 단계다. 사람의 판단에 기댄다.

3. 평가 설계

평가를 써 주는 에이전트는 있다. 하지만 무엇이 좋은지에 대한 취향을 에이전트에 심는 일은 사람 몫이다.

10

평가 만들기 데모 24:50

Wonder Toys 프로젝트에서 Signal은 이슈 두 개를 찾았다. 하나는 부모 없는 스팬 orphan span인데, 발표자가 계측을 잘못한 실수였다. 그래도 잡아냈다. 다른 하나가 심어 둔 버그인 불필요한 검색 재시도다.

이슈에서 한 번의 클릭으로 새 평가기를 만들 수 있다. 그러면 Arize의 사내 에이전트 Alyx(자막 표기 Alex, 추정)가 열리고, 증거 트레이스를 바탕으로 프롬프트 템플릿을 써 준다.

만들어진 평가 프롬프트의 요지 25:50 도구 호출을 포함한 전체 궤적을 살펴본다. 불필요한 도구 호출이 있는지 본다. 제품 검색 도구가 한 번 넘게 불리면 "불필요한 재시도"로 분류하고, 점수와 분류를 트레이스에 붙인다.

이 평가를 들어오는 트레이스에 돌리면 모니터링, 그래프, 경보, 평가 비용 추적이 된다. 나중에 개발 흐름이 이 검사를 회귀 테스트로 굳히면 프로덕션에서는 토큰을 쓰지 않도록 평가를 은퇴시킬 수 있다.

11

실험으로 수정 증명하기 26:50

수정이 있고, 평가가 있고, 픽스처가 있다. 이제 그 수정이 맞는지 어떻게 아나. 에이전트가 없는 문제를 지어내서 엉성한 코드를 낸 건 아닌가. 여기가 실험 experiment의 자리다. 관심사는 둘이다. 수정이 효과가 있는가, 다른 것을 깨뜨리지 않았는가. 시스템 프롬프트를 조금 바꿔도 생각지 못한 도구가 깨질 수 있다.

  1. 실패 사례 픽스처에 수정 버전의 에이전트를 다시 돌린다.
  2. 결과에 평가를 매긴다.
  3. 직접 정한 임계값을 넘으면 통과다. 데모에서는 88.9%가 나왔고 발표자는 "배포"라고 판단했다.

이 실험도 에이전트가 AX CLI로 돌릴 수 있다. Signal이 실패 사례를 찾고 코드에 접근할 수 있으니, 그 사례를 v2 수정으로 재생하고 점수를 매긴다. 아침에 오면 PR만 있는 게 아니다. "실패했던 사례로 지연과 재시도 횟수를 다시 쟀고 더는 재시도하지 않는다. 다른 평가 세 개도 나빠지지 않았다"는 검증 결과가 함께 있다. 픽스처가 자랄수록 실험도 튼튼해진다.

에이전트 결과에 동의하지 않으면 주석 annotation을 달 수 있다. 그 주석은 다음 실행의 맥락이 된다. CI/CD에 넣을 수도 있다. 다만 에이전트 실행과 LLM 심판은 비싸니 모델, 시점, 샘플링 비율을 신중히 정한다.

자는 동안 돌아가는 것, 아침에 기다리는 것 31:00

자동으로 계속 도는 것
  • 만든 평가가 새 트레이스마다 돌고, 다음 Signal 실행의 맥락이 된다
  • 작업 시스템이 실패한 평가 결과를 데이터셋에 자동으로 넣어 픽스처를 키운다
  • Signal이 6시간마다, 또는 경보와 모니터에 맞춰 다시 돈다. 새 실패를 찾고 새 평가를 만든다
  • 주간 요약으로 읽기 쉬운 형태의 보고가 온다
사람을 기다리는 것
  • 이 이슈가 진짜인지 확인한다. 에이전트가 낸 이슈를 다 믿지 말고 출발점으로 쓴다
  • 맞는 답이 어떤 모습인지 주석으로 적는다
  • 수정을 머지한다. 자동 머지는 각자 판단이다
  • 새 버전을 배포하고 승격한다

세션을 중간에 끊거나, 모델의 추론을 들여다보거나, 세션을 이어받아 로컬 에이전트로 넘길 수도 있다. 모든 걸 Arize에 맡기고 싶지 않을 때를 위한 것이다.

확신 점수로 사람에게 보내기 32:50

결정 모델은 명시적인 확신 점수 confidence score를 돌려준다. 이 점수로 낮은 확신의 결과만 사람의 주석 대기열로 자동 전달할 수 있다. 검토자는 출력을 다 보는 대신 미리 추려진 대기열을 받는다. 발표자는 80%가 모두에게 맞는 임계값은 아니라고 했다. 임계값을 정하는 것 자체가 중요하다.

앞으로 갈 방향 34:10

발표자가 그리는 미래는 사람 개입이 거의 없이 루프 전체가 돌다가, UI를 눌러 보며 확인할 때만 사람이 들어오는 모습이다. 가장 어려운 부분은 실험 환경이다.

실험 환경에서 생각해 볼 질문 35:00 이 에이전트를 돌리려면 의존성이 몇 개인가. 가짜 DB에 붙이나. 어떤 도구는 막나. 전체를 Docker 이미지로 돌리나. 그걸 안전하게 할 수 있나. 데모 에이전트는 의존성이 없어 DB를 스스로 띄우고 전체를 재실행했다. 외부 의존성이 중요한 에이전트는 훨씬 복잡해진다.
  • 이슈에서 실험까지 한 번의 클릭. 수정안을 주면 필요한 인프라를 띄워 테스트한다.
  • 일하는 곳으로 Signal 연결. Slack에서 태그해 대화하고, API·CLI·스킬로 로컬 에이전트에게 Signal의 발견을 요약시킨다.
  • 평가 건강 점검. 99.999% 통과하는 평가는 토큰이 아까우니 은퇴시키고, 상태가 나쁜 평가는 보강한다. 심판이 내 생각과 맞는지 맞추는 평가 정렬 eval alignment 과정도 있다.
  • 어디서든 실험. 노트북이든 복잡한 인프라든 에이전트가 있는 곳에서 데이터셋을 돌린다.

발표자의 마무리 39:00

  • 방대한 데이터를 읽는 힘든 일은 에이전트가 해야 한다.
  • 이 발표의 주제는 사람이 가장 큰 지렛대를 가진 지점을 찾는 것이다.
  • 자동화할 수 있다고 자동화해야 하는 건 아니다. 자동화로 검토자에게 정보를 주라. 낮은 확신 점수를 검토 대기열로 보내는 것이 그 예다.
  • 모든 맥락이 같은 시스템으로 돌아와야 한다. 사람의 판단, 평가 점수, 트레이스 증거가 한곳에 있어야 다음 실행에 쓰이고, 그래야 버티는 대신 새 문제를 잡는다.

발표자는 "우리는 Arize에서 왔으니 Arize가 좋다고 말하지만, 어디든 맥락이 한곳에 기록되는 게 중요하다"고 스스로 덧붙였다.

질의응답 40:20

청중 질문은 자막에 거의 없어 발표자의 답에서 질문을 추정했다.

질적인 결과는 어떻게 평가하나 40:20

AI 프로덕트 매니저의 주된 일이 좋은 평가 설계라고 발표자는 말했다. 지연이나 재시도 횟수처럼 고전적인 지표는 쉽다. 데모의 대소문자 버그가 그렇다. 질적인 결과는 어렵다. "좋음"의 정의는 신호를 많이 줄수록 드러난다. 예시 하나로는 에이전트가 배우지 못한다. 그 하나에 과적합하거나 일반화가 안 된다.

발표자가 든 예는 Alyx(추정)가 필터 쿼리를 만드는 기능이다. 정답이 없다. 필터가 파싱에 성공해 결과를 돌려줘도 그게 좋은 결과인지 알 수 없다. 그래서 두 가지를 본다.

  • 세션 전체. 한 턴이 아니라 사용자가 다시 물었나, 필터를 몇 개 더 만들었나.
  • 사람의 주석. 무엇을 기대해야 하는지 아는 PM이 쿼리와 결과를 읽고 손으로 표시한다.

이 둘과 새 사용 사례를 합치면 평가 템플릿이 된다. 코딩 에이전트에게 그 맥락을 주어 프롬프트를 쓰게 하고, 가장 싼 모델에서도 잘 되도록 프롬프트를 최적화한다.

개발 단계 평가와 프로덕션 평가 44:00

평가에는 두 렌즈가 있다. CI/CD에서 회귀 검사로 도는 평가와, 실제 트레이스 위에서 도는 평가다. 후자는 비용 대비 효과의 문제다. 99.9%가 맞는데 0.1%가 치명적이라면 이야기가 달라진다.

발표자의 일반 지침 CI/CD에서 잡을 수 있는 건 거기서 잡는다. 평가가 실패했던 0.1%의 사례를 픽스처로 두고, 푸시마다 또는 PR 머지 전에 평가 점수와 함께 다시 돌린다. 필수 검사로 만들어 둔다. 프로덕션 트레이스에는 샘플링 비율을 둔 평가를 돌린다. "프로덕션 전부 평가"와 "개발에서만 테스트" 둘 다 극단이고, 답은 그 사이에 있다.

Signal은 누가 평가하나 45:50

같은 루프를 한 번 더 돌린다. 평가 자체의 트레이스를 모은 프로젝트가 있고, 그 위에서 에이전트가 평가가 좋은지 본다. Signal도 자기 트레이스를 남긴다. "당신은 Arize의 자동 리뷰어 Signal이다"로 시작하는 지시, bash 호출, 내부 MCP 호출이 다 보인다. Signal 위에 Signal을 돌릴 수도 있다.

다만 수확이 줄어드는 지점이 있다. 제품으로서 Signal은 PR 머지율, 세션 인계 여부, 데이터셋이나 평가가 만들어졌는지 같은 대리 지표로 볼 수 있다. 그 너머는 정답이 없다. 에이전트 기록만 보며 분위기로 판단하는 건 쓸모가 없다고 발표자는 말했다.

결정 모델에서 기대하는 것 48:20

  • 지연이 낮아서 실행 중 검사가 가능하다. 지금 평가는 에이전트가 끝난 뒤 사후에 보는데, 실행 도중 요청을 라우팅할 수 있다.
  • 싸니까 더 많은 사람이 평가를 쓴다. 생태계에 좋다.
  • 모델이 작아 온디바이스 활용이 열린다.
  • 멀티모달 평가에 유용하다. 생성된 이미지나 클릭 영역 해석은 질적이고 느린데, 확신 점수가 있으면 사람에게 빨리 넘길 수 있다.

다른 데이터 소스도 붙일 수 있나 50:00

된다. Datadog 스킬로 경보 주변의 지표, 로그, APM 트레이스를 끌어올 수 있고, 스킬을 직접 써도 된다. 에이전트 트레이스만이 아니라 하위 시스템의 애플리케이션 지표도 본다. 다만 필요한 것만 연결하고, 접근 범위와 키 범위를 맞추고, 맥락을 넘치게 하지 않는다. 더 많은 정보가 늘 더 나은 분류로 이어지지는 않는다.

비용은 얼마나 드나 50:50

하네스, 모델 제공자, 실행 빈도에 따라 다르고 모두 설정으로 노출된다. Signal의 비용도 Wonder Toys의 비용처럼 볼 수 있다. 발표자는 "에이전트 예산의 5%를 개선 루프에" 같은 기준은 없다고 했다. 대신 가상의 예를 들었다.

비용을 조절하는 손잡이는 셋이다. 어떤 스킬을 붙여 얼마나 많은 맥락을 주는가, 평가를 얼마나 자주 어떤 샘플링으로 돌리는가, 그리고 API로 내보내 더 싸게 쓰는 코딩 에이전트에게 같은 일을 시키는가.

핵심 정리

  1. 에이전트는 비결정적이고 수천 개다. 트레이스를 사람이 다 읽는 단계가 병목이고, 그 자리를 에이전트가 맡는다.
  2. 성숙도 다섯 상자: 트레이싱, 평가, 트레이스 읽기, 실패를 테스트로 저장, 수정 증명.
  3. 루프: 트레이스 → Signal → 실패 데이터셋 → 평가 → 수정 PR → 실험 → 사람의 검토와 머지.
  4. Signal은 6시간마다 또는 경보에 맞춰 돌고, 저장소를 읽어 PR을 낸다. 데모 버그는 필터의 대소문자 불일치였고 6분 만에 원인을 찾았다.
  5. 문제 하나에 티켓 하나. 실패 데이터셋은 살아 있는 픽스처로 계속 자란다.
  6. 평가는 코드 검사, LLM 심판, 에이전트 심판, 결정 모델 순으로 비싸진다. 싼 것부터 쓰고 비싼 건 샘플링한다.
  7. 실험은 "수정이 효과 있나"와 "다른 걸 깨뜨리지 않았나"를 동시에 본다. 임계값은 팀이 정한다.
  8. 사람이 남는 세 자리: PR 검증, 데이터셋 선별, 평가 설계.
  9. 확신 점수가 낮은 것만 사람 대기열로 보낸다. 임계값은 분야마다 다르다.
  10. CI/CD에서 잡을 수 있는 건 거기서 잡고, 프로덕션은 샘플링한다. 모든 맥락은 한곳에 모아 다음 실행에 쓴다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말한 성숙도 다섯 상자는?
트레이싱, 평가, 누군가 트레이스 읽기, 실패를 테스트로 저장, 수정을 증명. 뒤로 갈수록 하는 팀이 적다.
Q2다섯 상자 중 에이전트에게 넘기려는 단계는 어디이고 왜인가?
3단계 트레이스 읽기. 코딩 에이전트나 수백만 고객 챗봇의 트레이스를 사람이 다 읽을 수 없기 때문이다.
Q3Signal은 무엇이고 기본 실행 주기는?
프로젝트의 트레이스를 주기적으로 읽고 이슈를 묶고 수정을 제안하는 상시 에이전트. 기본 주기는 6시간이며 경보로도 띄울 수 있다.
Q4데모에 심은 버그의 근본 원인과 증상은?
제품 카테고리는 소문자 하이픈 슬러그인데 LLM이 제목 형식으로 넘겨 필터 결과가 비었다. 에이전트가 전체 제품을 다시 뒤지며 LLM 호출이 세 번 연달아 일어나고 지연이 14~17초로 올랐다.
Q5"살아 있는 픽스처"란?
실패 사례를 모은 데이터셋이 고정되지 않고, 새 실패와 새 사용 사례가 생길 때마다 자라며 회귀 테스트로 쓰이는 것.
Q6평가 네 종류를 싼 순서로 나열하면?
코드 검사 → 결정 모델 → LLM 심판 → 에이전트 심판. 결정 모델은 일반 LLM보다 훨씬 싸다고 발표자가 말했다.
Q7실험이 답해야 하는 두 질문은?
수정이 실제로 효과가 있는가, 그리고 다른 것을 깨뜨리지 않았는가. 실패 픽스처에 수정 버전을 다시 돌리고 기존 평가들도 나빠지지 않았는지 본다.
Q8사람이 가장 값어치 있는 세 자리는?
PR 검증, 데이터셋 선별, 평가 설계. 데이터셋 추가는 일부러 수동으로 남겼다.
Q9확신 점수를 어떻게 활용하나?
임계값을 정하고 낮은 확신의 결과만 사람 주석 대기열로 자동 전달한다. 스팸 예시에서는 4.6%만 사람에게 갔고 나머지는 99.5% 정확도였다.
Q10개발 단계 평가와 프로덕션 평가를 어떻게 나누라고 했나?
CI/CD에서 잡을 수 있는 건 필수 검사로 거기서 잡고, 프로덕션은 샘플링 비율을 둔 평가를 돌린다. 둘 중 한쪽만 하는 건 극단이다.
Q11Signal을 Signal로 평가할 때 한계는?
PR 머지율, 세션 인계, 데이터셋·평가 생성 같은 대리 지표 너머에는 정답이 없다. 에이전트 기록만 보고 판단하면 수확이 줄어든다.
Q12개선 루프 비용을 줄이는 세 가지 손잡이는?
붙이는 스킬과 맥락의 양, 평가 빈도와 샘플링, API로 내보내 더 싼 코딩 에이전트에게 맡기기.
