에이전트 메모리는 풀렸다, 학습은 아니다

에이전트 하나가 대화를 기억하는 일은 이미 해결됐다. 문제는 여러 에이전트와 사람이 서로의 맥락을 넘겨받으며 함께 배우는 일이다. 데이터베이스 회사가 에이전트 4개를 1년간 띄우지 못한 끝에 찾은 답은, 검증을 거쳐 승격된 공유 컨텍스트를 인프라로 만드는 것이었다.

원본 영상: Agent Memory Is Solved. Agent Learning Isn't. 발표: Karthik Ranganathan (Yugabyte 공동 창업자 겸 CEO), 데모: Heather (Yugabyte)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 제품 이름은 자막에서 Mako, Makeo, Miko 등으로 흔들려 "Mako(추정)"로 적었다. mm:ss는 영상 위치다.

3분 요약
  1. 메모리는 에이전트 하나의 문제, 학습은 여럿의 문제다. 혼자 기억하는 인프라와 여럿이 배우는 인프라는 다르다.
  2. Yugabyte는 에이전트 4개를 거의 1년간 띄우지 못했다. 원인은 모델이 아니라 데이터 문제였다.
  3. 진짜 손실은 결과물만 넘기고 추론, 막다른 길, 실패 기록을 버리는 것이다. 받는 쪽 에이전트가 토큰을 태우며 다시 도출한다.
  4. 메모리 늘리기, 파일 공유, 대화 전체 RAG, 파인튜닝, 큰 컨텍스트 창은 모두 학습이 아니다. 각각 아키텍처 구멍이다.
  5. 공유 컨텍스트에는 세 조건이 필요하다. 공유할 수 있고, 검토를 거쳐 승격되며, 출처를 추적할 수 있어야 한다.
  6. RAG 파이프라인을 하나씩 추적해 고치니 충실도가 14%에서 65%로 올랐고 청크 수는 7,000개에서 1,000개로 줄었다.
  7. Mako(추정)는 데이터 팩이라는 단위에 컨텍스트를 담고, 개인 공간에서 공유 공간으로 승격시킨다. 한 번 알아낸 것은 다음부터 MCP 도구 호출 한 번으로 꺼낸다.
01

메모리와 학습은 다르다 00:10

AI의 모든 것은 넣어 주는 데이터에 달려 있다. 나쁜 데이터를 넣으면 나쁜 결과가 나온다. 발표자는 여기서 두 문제를 가른다.

풀린 문제에이전트 메모리 agent memory대화에서 기억할 것을 뽑아 두고 같은 에이전트가 다시 쓴다. 에이전트 하나 단위로 돌아간다.
→
안 풀린 문제에이전트 학습 agent learning여러 에이전트가 함께 일하며 서로 배우고 나눈다. 혼자 있을 때는 일어나지 않는다.

발표자는 자신을 인프라를 만드는 사람이라고 소개한다. 그 관점에서 보면 에이전트 하나의 메모리를 위해 만든 인프라는 여럿이 배우는 데 필요한 인프라와 다르다. 이 발표는 그 차이를 왜, 어떻게 메웠는지에 대한 이야기다.

02

에이전트 4개, 1년의 실패 01:10

Karthik Ranganathan은 분산 데이터베이스 YugabyteDB를 만드는 회사의 공동 창업자이자 CEO다. 데이터베이스 회사가 왜 에이전트용 데이터 인프라를 만들게 됐는지, 발표자는 "어렵게 배웠다"고 말한다.

에이전트대상하는 일
Hagen (추정)사내고객 지원
Growth Vector사내영업과 마케팅을 맞춰 움직이는 시장 진입 조율
Perf Advisor고객에이전트형 데이터베이스 관리자. 고객의 데이터베이스를 운영한다
Voyager고객다른 데이터베이스에서 클라우드 네이티브 데이터베이스로 옮기고 현대화한다

네 에이전트 모두 제대로 내놓지 못했다. 거의 1년을 시도한 뒤에야 모델이 아니라 데이터 문제에서 실패하고 있다는 것을 깨달았다. 데이터베이스 회사가 데이터 문제로 막혔으니 "개인적인 일이 됐다"는 것이 발표자의 표현이다.

고객의 요구도 같은 곳을 가리켰다 02:10 고객들은 더 큰 벡터 저장소, 더 큰 그래프, 더 큰 관계형 저장소를 원했고, 늘 "더 많은 규모, 더 높은 성능, 더 적은 비용"을 요구했다. 발표자는 어느 시점부터 이것이 물리 법칙을 깨라는 요구처럼 들렸다고 말한다. 저장소를 키우는 것으로는 풀리지 않는 다른 문제가 있었다.
03

결과물만 넘기고 추론은 버린다 02:40

모든 것을 걷어내고 핵심만 보면 실패는 이렇다. 발표자의 에이전트 A가 일을 마치고 동료 Heather의 에이전트와 함께 일해야 한다. 그런데 넘길 수 있는 것은 결과물뿐이다. 마크다운 파일, PDF, 문서 같은 것들이다. 그 결과가 나오기까지의 추론은 넘길 수 없다.

이때 잃는 것은 세 가지다.

  • 추론: 왜 이 결론에 이르렀는가
  • 막다른 길: 성공하기 전에 몇 번, 어떻게 실패했는가
  • 전체 맥락: 그 일을 둘러싼 배경

그래서 Heather의 에이전트는 이 모든 것을 처음부터 다시 도출한다. 공짜가 아니다. 토큰을 태우고 모델 회사에 돈을 낸다.

사람 팀에 빗대면 03:30 새로 온 팀원에게 "우리는 X를 한다"고만 알려 주면, 그 사람은 X 대신 다른 것을 해야 할 이유 50가지를 들고 온다. 그때마다 "그건 2주 전에, 두 달 전에 이미 검토했다"고 답해야 한다. 실제 팀은 그렇게 일하지 않는다. 프로젝트의 역사와 지금까지의 방식을 먼저 알려 주고 "여기서부터 시작하자"고 한다. 에이전트에게는 바로 그 맥락이 없다.
04

다섯 가지 오해 03:50

발표자는 흔히 "이걸 하면 학습이 된다"고 믿는 다섯 가지를 빠르게 지운다. 각각이 아키텍처의 구멍이라는 것이 요지다.

오해왜 학습이 아닌가
메모리를 더 늘린다에이전트 메모리를 키우는 것은 학습이 아니라 그냥 더 많은 메모리다. 더 비싸질 뿐이다
상태를 공유한다마크다운 파일을 넘길 수 있다고 지식이 공유된 것은 아니다. 공유 상태 shared state와 공유 지식 shared knowledge은 다르다
대화 기록을 전부 RAG에 넣는다쓰레기가 잔뜩 쌓이고, 모델은 더 많은 토큰을 태워 더 나쁜 답을 낸다. 품질이 되지 않는다
파인튜닝한다에이전트가 얻은 교훈을 파인튜닝으로 저장하고 유지하는 것은 규모가 커지면 불가능하다
컨텍스트 창을 키운다가장 빠르게, 가장 비싸게 실패하는 길이다. 컨텍스트는 썩는다 context rot
05

공유 컨텍스트의 세 조건 04:50

그래서 Yugabyte가 자신들을 위해 메워야 했던 구멍은 다음 셋이다. 발표자는 많은 사용자가 이 관점을 좋아한다고 덧붙인다.

1 · 공유할 수 있다

에이전트 A의 컨텍스트를 에이전트 B가 그대로 이어받는다. 둘이 같은 컨텍스트 위에서 일하면 앞에서 본 "잃어버린 맥락" 문제가 닫힌다.

2 · 검토를 거쳐 승격된다

공유 컨텍스트는 아무나 쓰면 망가진다. 코드와 같다. 아무나 커밋할 수 없듯, 감독하에 승격 supervised promotion을 거친 것만 오래 남는 지식이 된다.

3 · 출처를 추적할 수 있다

"이 정보는 대체 어디서 왔나"를 물을 수 있어야 한다. 데이터 원본, 사람, 대화 중 어디서 뽑았는지로 거슬러 올라간다. 컨텍스트를 개선하는 첫걸음이다.

06

실패한 시도와 RAG 수치 05:40

"얼마나 어렵겠어"라는 마음으로 시작했고, 세 번 틀렸다.

시도생각결과
지식 베이스 하나전부 던져 넣으면 된다. 분산 RAG 파이프라인을 크고 탄력 있게 만들었다훌륭한 파이프라인이었지만 쓸모 있는 결과가 없었다
에이전트마다 작은 DB공유가 안 되니 각 에이전트에 작은 Postgres를 하나씩 준다반복되는 워크플로가 매번 즉석에서 다시 발명됐다
UI 없는 백엔드에이전트는 UI가 필요 없으니 처리만 하는 백엔드를 둔다무슨 일이 벌어지는지 알 수 없었다. 사람이 끼지 않으면 결과가 나쁘다

RAG 파이프라인도 형편없었다 06:40

학계에서 좋다는 구성 요소를 다 모아 넣었는데 공개 벤치마크 점수가 낮았다. 트레이스를 찍고 변수를 하나씩 바꿔 가며 고치자 수치가 올랐다.

자막에는 컨텍스트 크기가 "17분의 1"로 줄었다고 적혀 있지만, 7,000개에서 1,000개로 줄었으면 약 7분의 1이다. 발음이 뭉개진 것으로 보고 7분의 1로 적었다.

07

Mako(추정): 데이터 팩과 승격 07:30

이 모든 실패와 성공을 한 상자에 담은 것이 Mako다. 발표자는 이를 에이전트 네이티브 영속 계층 agent-native persistence layer이라고 부른다.

데이터 팩 data pack

Mako가 밖으로 드러내는 단위다. 데이터베이스 회사가 굳이 데이터베이스라고 부르지 않는 이유는, 안에 벡터, 그래프, 관계형, NoSQL 등 여러 종류의 저장소가 들어 있기 때문이다. 데이터 팩에는 컨텍스트의 여러 면이 담긴다.

  • 지식 베이스
  • 메모리
  • 대화
  • 관측 기록 observability

개인 공간에서 공유 공간으로

개인 공간에이전트가 자기 컨텍스트 조각을 밀어 넣는다아직 검증되지 않은 것들
→
공유 공간승격된 고품질 컨텍스트다른 에이전트와 사람이 여기서 빠르게 꺼내 쓴다. 사람과 에이전트를 계속 더해도 인수인계가 효율적이다

한 줄로 줄이면 "오래 가고 반복되는 워크플로를 인프라로 만든다"는 것이다.

발표자는 Mako를 만드는 회사의 CEO다. 이 섹션과 데모의 주장은 그 점을 감안해 읽자.

이 슬라이드도 그렇게 만들었다 08:30

데모에 앞서 발표자가 고백한다. 이 발표 자료 자체가 Mako를 컨텍스트 저장소로 써서 만들어졌다.

  1. Heather가 데모 개요와 거기까지 이어지는 발표 흐름을 써서 데이터 팩을 만들고, 발표자에게 공유 요청만 보냈다. 어떤 에이전트 도구를 썼는지 발표자는 모른다. 회의도 하지 않았다.
  2. 발표자는 그 데이터 팩을 Claude Desktop에 연결해 "이 개요를 쪼개 달라"고 했고, 몇 군데 고친 뒤 "이 개요로 슬라이드를 만들어 달라"고 했다.
  3. 왼쪽 다이어그램은 처음에 형편없었다. 요즘 화제라는 Claude Design(추정)으로 다시 만드니 나았다. 그림은 거기서, 나머지는 Claude Desktop에서 나왔다.
  4. Heather가 마지막으로 손봐서 데모와 이어 붙였다.
우리는 거의 대화하지 않았다. 그럴 필요가 없었다. 컨텍스트를 공유했고 에이전트들이 일을 했다.발표자의 말을 옮김 09:50
09

데모 1: 세션 이어가기 10:20

Heather가 보여 주려는 것은 집단 지식이 시간이 갈수록 자라는 모습이다. 첫 번째는 재개 가능성 resumability이다. 세션을 시작하고, 죽이고, 같은 에이전트로 다시 시작해도 이어진다.

왜 제품의 프로젝트 기능이나 메모리를 안 쓰나 10:30

  • Claude Desktop에는 프로젝트와 메모리 기능이 있다. 그러나 Heather는 두 달 전쯤 모든 IDE의 메모리를 껐다.
  • 이동 중에는 모바일 앱이나 ChatGPT처럼 다른 도구를 쓸 수 있다. 같은 계정이니 같은 주제를 이어서 작업하고 싶다.
  • 보안을 생각하면 아무 에이전트나 그 기억을 보면 안 된다. 그래서 어떤 메모리를 다른 에이전트도 꺼낼 수 있게 할지 승격해서 정한다.
비용이 줄어드는 이유 11:20 처음 뭔가를 알아낼 때는 모델과 오래 주고받으며 토큰을 많이 태운다. 다음에 다른 에이전트나 다른 세션에서 꺼낼 때는 그 과정을 반복하지 않는다. Mako 메모리를 부르는 MCP 도구 호출 한 번으로 훨씬 적은 토큰에 가져온다. 대안은 마크다운 파일에 두고 에이전트마다 모델로 다시 훑으며 토큰을 또 태우는 것이다.

녹화된 데모 12:10

  1. "early access launch"라는 데이터 팩에 대화를 저장한다. 넣는 사실은 가입 이메일이 실패했다는 것. 실제로 있었던 일로, Amazon SES의 샌드박스를 운영 환경 대신 쓰다가 한도를 넘겼다. 운영팀에 쓸모 있는 정보다.
  2. Claude에 MCP 서버를 연결했고, 언제 무엇을 저장할지 알려 주는 스킬을 만들어 두었다. 에이전트가 데이터 팩 생성을 호출하고, 사고 사실을 검색 가능한 메모리로 추가한다.
  3. 세션을 죽이고 새 채팅 창을 연다. 프로젝트도 아니고 메모리도 켜져 있지 않다. 같은 질문을 한다.
  4. 처음에는 새 대화를 만들지 않고 검색부터 하려다 실패했다. MCP 서버가 새 대화를 만들라고 지시한 뒤, Mako를 검색해 "5월에 이런 일이 있었다"는 기록을 찾아낸다.
10

데모 2: 다른 에이전트와 공유 14:20

두 번째는 공유 가능성 sharability이다. 이번에는 완전히 다른 도구인 Codex에서 묻는다. "가입 이메일이 실패하는 알려진 원인이 있나?"

  1. Codex는 찾고 또 찾지만 아무것도 보지 못한다. 새 데이터 팩이 연결된 것은 보이지만 안은 볼 수 없다.
  2. 이유는 그 메모리가 아직 Claude Desktop 쪽 개인 공간에만 있기 때문이다. 데이터 팩을 연결했지만 승격하지 않았다.
  3. 다른 계정으로 들어가 그 메모리 한 조각을 공유 지식 공간으로 승격한다.
  4. 같은 질문을 다시 하면 이제 찾는다.

승격은 아주 잘게 할 수 있다. 메모리 조각 하나만 열 수도 있고, 관리자라면 데이터 팩 전체를 열 수도 있다. 모범 사례나 진행 중인 절차처럼 골라서 주고 싶은 정보가 있을 때는 조각 단위가 더 낫다.

비용 추적과 학습 신호 16:10

정말 토큰을 아꼈는지 어떻게 아나

데이터 팩에 들어가면 저장된 대화와 그것이 어떻게 만들어졌는지 볼 수 있다. 트레이스가 기본으로 들어 있다. 결정 과정을 도구 호출 단위까지 따라가며 실제로 얼마나 호출하고 얼마나 태웠는지 확인한다.

오늘의 승격이 내일의 학습 신호다 16:40

사람이 "이건 남길 가치가 있다"고 승격할 때마다, 그것은 좋은 승격이 무엇인지 보여 주는 라벨이 붙은 예시가 된다. 나중에는 이 신호로 내 취향과 기준을 배운 에이전트를 훈련할 수도 있다. 지금은 사람이 루프 안에 있고, 그 판단은 신호로만 쌓인다. 발표자는 이것이 학습이 시작되는 방식이라고 말한다.

가장 크게 체감한 이점 17:10 장애가 났을 때를 생각해 보자. 서버 하나가 죽으면 사람들은 계속 그 서버를 두드리고, "이거 죽었나요?"가 반복되고, Slack이 터진다. 에이전트도 같다. 모두가 같은 서버를 호출하며 토큰을 낭비한다. 데이터 팩이 있으면 첫 에이전트가 한 번 겪고 기록하면 나머지 에이전트는 이미 안다.

회사 안에서 쓰는 모습 17:50

Heather는 Mako의 얼리 액세스 출시를 맡았고, 그 출시를 Mako 데이터 팩으로 운영했다. 발표자는 이를 "재귀적"이라고 표현한다.

  • 문제 해결 데이터 팩: 초기 사용자들이 데이터 팩에 접근하지 못하는 문제가 많았다. Heather는 그 문제 해결 기록을 별도 데이터 팩으로 만들어 회사 전체에 공유했다. 엔지니어는 Claude Code나 Codex 같은 코딩 에이전트에 바로 불러온다.
  • 사과 이메일: 접근하지 못한 사용자에게 보낼 이메일을 발표자는 Claude Desktop으로 설계했다.
  • 말투 데이터 팩: 발표자가 말하는 방식을 담은 데이터 팩이 따로 있다. LinkedIn 글을 자기 목소리로 계속 쓰는 일은 지치는데, 이 컨텍스트가 있으면 바로 자동화된다.
  • 새 팀원: 이 컨텍스트를 공유하면 빨리 따라잡고 기여도 한다. 본인이 모르는 사이에 하는 일에서도 패턴을 뽑아 "이걸 정식으로 만들자"고 할 수 있다.
결국 사람이 일하는 방식에 가까워지려는 것이다. 암묵지를 어떻게 붙잡고, 어떻게 나누고, 공유를 어떻게 통제하고, 무슨 일이 벌어지는지 어떻게 보는가.발표자의 말을 옮김 19:20

발표 끝에 무료 티어 가입과 Discord 참여를 권한다. 제품 홍보 구간이다.

핵심 정리

  1. 메모리는 풀렸고 학습은 안 풀렸다. 메모리는 에이전트 하나의 일, 학습은 여럿이 함께 하는 일이다.
  2. 에이전트 하나의 메모리 인프라는 여럿이 배우는 인프라와 다르다.
  3. Yugabyte는 에이전트 4개를 거의 1년간 띄우지 못했고, 원인은 데이터 문제였다.
  4. 진짜 손실은 결과물만 넘기고 추론, 막다른 길, 맥락을 버리는 것이다. 받는 쪽은 토큰을 태워 다시 도출한다.
  5. 메모리 늘리기, 파일 공유, 대화 전체 RAG, 파인튜닝, 큰 컨텍스트 창은 학습이 아니다.
  6. 공유 컨텍스트의 세 조건: 공유 가능, 검토를 거친 승격, 출처 추적.
  7. 지식 베이스 하나, 에이전트별 작은 DB, UI 없는 백엔드는 모두 실패했다. 사람이 안 보이면 결과가 나쁘다.
  8. RAG를 변수 하나씩 추적해 고치니 충실도 14%→65%, 20%→74%, 정밀도 57%→82%. 청크는 7,000개에서 1,000개로 줄었다.
  9. Mako(추정)의 데이터 팩은 개인 공간에서 공유 공간으로 승격하는 구조다. 조각 단위로 잘게 열 수 있다.
  10. 한 번 알아낸 것은 다음부터 MCP 도구 호출 한 번으로 꺼낸다. 사람의 승격 하나하나가 미래 학습의 라벨이 된다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 "메모리"와 "학습"의 차이는?
메모리는 에이전트 하나가 대화에서 기억을 뽑아 다시 쓰는 것이다. 학습은 여러 에이전트가 함께 일하며 서로 나누고 배우는 것이고, 혼자서는 일어나지 않는다.
Q2Yugabyte가 운영하는 에이전트 4개는?
사내용 고객 지원 에이전트(Hagen, 추정)와 시장 진입 조율 에이전트(Growth Vector), 고객용 데이터베이스 관리 에이전트(Perf Advisor)와 마이그레이션 에이전트(Voyager).
Q3에이전트 A가 B에게 결과물만 넘길 때 잃는 세 가지는?
추론, 막다른 길과 실패 기록, 전체 맥락. 그래서 B는 처음부터 다시 도출하며 토큰을 태운다.
Q4"상태 공유"와 "지식 공유"는 왜 다른가?
마크다운 파일을 넘길 수 있다고 상대가 그 지식을 가진 것은 아니다. 파일은 상태일 뿐, 추론과 맥락이 빠져 있다.
Q5컨텍스트 창을 키우는 것이 왜 답이 아닌가?
가장 빠르고 비싸게 실패하는 길이다. 컨텍스트가 길어질수록 품질이 썩는다.
Q6공유 컨텍스트에 필요한 세 조건은?
에이전트끼리 공유할 수 있을 것, 아무나 쓰지 못하고 검토를 거쳐 승격될 것, 어떤 데이터·사람·대화에서 왔는지 추적할 수 있을 것.
Q7"UI 없는 백엔드" 시도에서 배운 것은?
무슨 일이 벌어지는지 사람이 볼 수 없었다. 사람이 루프에 없으면 결과가 나쁘다.
Q8RAG 튜닝 전후 수치와 청크 수 변화는?
충실도 14%→65%(마크다운), 20%→74%(PDF), 컨텍스트 정밀도 57%→82%. 청크는 7,000개 이상에서 약 1,000개로 줄었다.
Q9데이터 팩을 "데이터베이스"라고 부르지 않는 이유는?
안에 벡터, 그래프, 관계형, NoSQL 등 여러 종류의 저장소가 들어 있어서다. 지식 베이스, 메모리, 대화, 관측 기록을 함께 담는다.
Q10Codex가 처음에 가입 이메일 장애 기록을 못 찾은 이유는?
그 메모리가 Claude Desktop 쪽 개인 공간에만 있었다. 데이터 팩은 연결됐지만 그 조각을 공유 공간으로 승격하지 않았기 때문이다.
Q11사람의 승격이 왜 "학습 신호"가 되나?
"남길 가치가 있다"는 판단 하나하나가 좋은 승격의 라벨 붙은 예시가 된다. 쌓이면 사용자의 기준을 배운 에이전트를 훈련할 수 있다.
Q12장애 상황에서 데이터 팩이 주는 이점은?
모든 에이전트가 죽은 서버를 반복 호출하며 토큰을 낭비하는 대신, 첫 에이전트가 한 번 겪고 기록하면 나머지는 이미 안다.
