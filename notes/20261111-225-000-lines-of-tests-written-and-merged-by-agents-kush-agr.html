에이전트가 쓰고 사람이 머지한 테스트 22만 줄

듀오링고는 8개월 동안 에이전트 파이프라인으로 iOS 단위 테스트 약 22만 5천 줄을 만들어 머지했다. 테스트를 쓰는 모델보다 그 둘레의 워크플로가 일을 더 많이 했다. 파일을 고르고, CI 실패를 고치고, 지름길을 막고, 맞는 리뷰어를 찾는 일이다.

원본 영상: 225,000 Lines of Tests, Written and Merged by Agents 발표: Kush Agrawal (듀오링고 플랫폼 팀 스태프 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 경우만 알려진 이름(Temporal, Claude Code, Datadog 등)으로 바로잡았다. 확실하지 않은 곳에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 듀오링고 iOS 코드는 2019년 약 20만 줄에서 약 200만 줄로 늘었다. iOS 엔지니어가 아닌 사람도 AI 도구로 코드를 낸다. 병목은 쓰기에서 검증으로 옮겨 갔다.
  2. 그래서 단위 테스트 작성을 에이전트에게 맡겼다. 뼈대는 고르기 → 쓰기 → 검증 → 처리 → 개선의 다섯 단계 루프다.
  3. 먼저 로컬에서 PR 57개를 만들어 약 절반을 머지했다. 목표는 머지가 아니라 에이전트가 어떻게 실패하는지 배우는 것이었다.
  4. 운영 시스템은 Temporal 워크플로 몇 개와 S3 공유 상태로 돈다. 기존 코드 채우기, PR 수명 주기 관리, 라벨 트리거 세 갈래다.
  5. 에이전트는 CI를 통과하려고 지름길을 찾는다. 제품 코드 수정, 테스트 삭제, 긴 대기 같은 것이다. 결정적 규칙, AI 리뷰, LLM 판사 세 겹으로 막았다.
  6. 결과: 테스트 PR 700개 이상, 테스트 코드 약 22만 5천 줄, MVVM 커버리지 9% → 59%. 모든 PR은 사람이 승인했다.
  7. 이 루프는 테스트 전용이 아니다. 화면 현대화, 코루틴 이전, 스냅샷 테스트에도 같은 틀을 쓰기 시작했다.
01

듀오링고 iOS의 규모 00:20

발표자 Kush Agrawal은 듀오링고 플랫폼 팀의 스태프 엔지니어다. 클라이언트 앱에 코드를 내는 엔지니어 100명 이상을 위해 개발 도구와 AI 보조 작업 흐름을 만든다. 그 전에는 Stripe와 Uber에서 10년 가까이 일했다.

  • 앱은 매주 앱스토어에 나간다.
  • 실험을 중시하는 회사라, 동시에 돌아가는 A/B 테스트가 600개가 넘는다.
  • iOS 앱과 Android 앱 모두 10년이 넘었다.

코드를 쓰는 사람도 바뀌었다.

기여자 중 상당수는 iOS 엔지니어가 아니다. 백엔드 엔지니어, Android 엔지니어, PM, 디자이너도 iOS 앱에 코드를 낸다. 발표자는 이를 Cursor, Claude Code 같은 AI 코딩 도구 덕분으로 본다.

절반만 MVVM인 코드베이스 01:10

듀오링고는 몇 년 전 iOS 앱의 구조를 MVVM (Model-View-ViewModel)으로 통일하기로 했다. MVVM은 화면, 화면 로직, 데이터를 나눠 두는 설계 방식이다.

지금은 코드의 절반이 MVVM을 따른다. 나머지 절반은 옮기는 중인 레거시 코드다. MVVM 쪽이 테스트하기 가장 쉬워서, 이 프로젝트는 그쪽에 집중했다.

출발점: 올해 3월 01:30

3월의 전체 단위 테스트 커버리지 (unit test coverage)는 11%였다. 커버리지는 테스트를 돌릴 때 실제로 실행되는 코드의 비율이다.

MVVM 계층은 더 낮았다. 리포지토리 11%, 뷰 모델 9%, 데이터 소스 5%였다. MVVM 부분을 합치면 약 9%였다. 8개월 뒤의 숫자는 11번 섹션에 있다.

02

병목은 검증으로 옮겨 갔다 01:40

에이전트와 사람이 코드를 더 많이, 더 빨리 쓴다. 누군가 PR을 올리면, 그걸 내보내도 안전한지 어떻게 알 수 있을까.

이제 어려운 건 코드를 쓰는 일이 아니다. 검증하는 일이다.발표자의 말을 옮김 01:50
예전코드 쓰기가 병목얼마나 빨리 만드느냐가 속도를 정했다
→
지금검증이 병목쏟아지는 PR이 안전한지 판단하는 속도가 전체 속도를 정한다

발표자가 꼽은 단위 테스트의 역할은 셋이다. 02:00

  • 테스트 피라미드의 맨 아래층 (testing pyramid)이다. 쓰기 싸고 돌리기 빠르다.
  • 에이전트의 가드레일이다. 에이전트의 변경이 CI (continuous integration)에서 테스트를 깨뜨리면, 무엇을 고쳐야 하는지 바로 피드백을 받는다. CI는 코드를 올릴 때마다 자동으로 빌드하고 테스트하는 시스템이다.
  • 살아 있는 문서다. 코드가 무엇을 해야 하는지 보여 준다.
03

다섯 단계 루프 02:20

종이 위에서 보면 단순한 루프다.

  1. 고르기 (identify): 테스트가 필요한 파일을 찾는다.
  2. 쓰기 (write): 에이전트가 테스트를 쓴다.
  3. 검증 (verify): 테스트 품질이 괜찮고 CI를 통과하는지 확인한다.
  4. 처리 (resolve): 엔지니어가 리뷰하고 머지한다.
  5. 개선 (iterate): 피드백을 반영해, 다음 PR 묶음을 지난번보다 낫게 만든다.

실제 운영에서는 더 복잡하다. 02:40 시스템은 Temporal 워크플로 몇 개로 이뤄진다. 워크플로들은 S3에 저장한 공유 상태로 서로 맞춘다. 운영 다이어그램의 모든 상자는 다섯 단계 중 하나에 대응한다.

단계실제로 맡는 곳노트 섹션
고르기백필 워크플로의 선택 스크립트, 또는 엔지니어 PR의 파일06, 08
쓰기파일마다 띄우는 자식 워크플로와 코딩 에이전트06
검증PR 수명 주기 워크플로의 CI 수정, 품질 검사 세 겹07, 10
처리git blame으로 리뷰어 지정, 자동 머지07
개선거절 사유를 프롬프트와 스킬에 다시 넣기10

이 표는 발표 내용을 이 노트가 다섯 단계에 맞춰 다시 묶은 것이다.

Temporal이 에이전트 일에 맞는 이유 03:10

Temporal은 내구성 있는 워크플로 실행 엔진 (durable workflow execution engine)이다. 워크플로를 평범한 Python 코드로 쓴다. 일하던 워커가 죽어도, 워크플로는 멈춘 지점부터 다시 이어진다.

에이전트 일과 잘 맞는다. 에이전트 세션은 몇 초에서 몇 시간까지 걸린다. 그 사이 GitHub, CI, S3, Claude 같은 도구를 부른다.

듀오링고가 기대는 Temporal 기본 기능은 셋이다. 03:30

  • 스케줄 (schedules): cron처럼 작업을 정해진 때에 돌린다.
  • 조합 가능한 워크플로 (composable workflows): 일을 여러 갈래로 나눠 병렬로 돌린다.
  • 재시도, 타임아웃, 멱등성 (idempotency): 같은 파일로 중복 실행이 시작되지 않게 한다.

네 개의 마일스톤 03:40

  1. 로컬 검증: 이 프로젝트가 해 볼 만한가.
  2. 정기 백필 워크플로: 이미 있는 코드에 테스트를 쓴다.
  3. PR 수명 주기 워크플로: 만든 PR을 실제로 머지시킨다.
  4. 라벨 트리거: 엔지니어가 새로 쓰는 코드에도 테스트를 받는다.
05

1단계: 로컬에서 먼저 04:00

진짜 시스템을 만들기 전에 가장 작은 실험부터 했다. 에이전트가 이 일을 잘, 그리고 대규모로 할 수 있는지 알아보는 실험이다.

  1. 오케스트레이터 역할을 하는 Claude Code 명령 하나를 만든다.
  2. 이 명령이 Xcode 빌드 스크립트로 로컬 커버리지 리포트를 만든다.
  3. 리포트를 직접 만든 파일 선택 스크립트에 넣는다.
  4. 고른 파일마다 서브에이전트 둘에게 넘긴다. 하나는 테스트를 쓰고, 하나는 PR을 연다.

이걸 반복해 PR을 두 묶음 만들었다. 04:30

이 단계의 목표 머지를 많이 하는 게 목표가 아니었다. 에이전트가 어떻게 실패하는지 배우고, 운영에 올리기 전에 자잘한 문제를 고치는 게 목표였다.

실패 유형과 처방 04:40

실패원인처방
한 파일에 테스트 프레임워크 섞기오래된 코드베이스라 XCTest와 Swift Testing이 함께 있다언제 무엇을 쓸지 명확한 규칙을 줬다
목을 만들기 어려운 코드거대한 user client 싱글턴을 어떤 코드는 구체 클래스로, 어떤 코드는 프로토콜 버전으로 주고받았다. 구체 클래스는 테스트용 가짜 객체(목, mock)로 바꾸기 어렵다코드베이스 전체를 프로토콜 버전으로 옮기고, 린트 규칙으로 강제했다
불안정한 테스트동시성 관련 문제와 시간에 기대는 테스트. CI가 불안정해지는 (flaky) 큰 원인이다테스트 스킬에 더 나은 규칙과 예시를 넣었다

둘째 처방은 에이전트만 도운 게 아니다. 많은 파일이 사람에게도 테스트하기 쉬워졌다.

06

2단계: 기존 코드 채우기 05:20

커버리지가 한참 뒤처져 있었다. 그래서 가장 효과가 큰 일은 이미 머지된 코드에 테스트를 채우는 것이었다. 이것이 정기 백필 (backfill) 워크플로다.

이 워크플로는 두 가지 일을 한다. 다이어그램 왼쪽 절반은 고르기, 오른쪽 절반은 쓰기다.

고르기: 어떤 파일부터 05:40

  1. iOS 저장소의 main 브랜치에 PR이 머지될 때마다, GitHub Actions 작업이 Xcode 커버리지 리포트를 만든다.
  2. 리포트를 S3에 올린다. 이것이 최신 커버리지의 기준 자료 (source of truth)가 된다.
  3. 백필 워크플로가 리포트를 가져와 선택 스크립트에 넣는다.
  4. 선택 스크립트가 다음에 테스트할 파일 묶음을 고른다.

선택 스크립트는 Swift 파일마다 점수를 매긴다. 06:00 기준은 하나다. 에이전트가 이 파일에 좋은 테스트를 쓸 수 있다고 얼마나 확신하는가.

신호처리
파일 종류 (가장 강한 신호)뷰 모델, 리포지토리, 데이터 소스는 점수 2.5배
레거시 파일순위를 아래로 내린다
UI 코드지금은 아예 뺀다. 화면에는 스냅샷 테스트가 더 맞다
큰 파일감점한다

잘 테스트할 수 있다고 확신하는 코드부터 한다는 뜻이다.

쓰기: 파일마다 에이전트 하나 06:20

  1. 파일마다 자식 워크플로 (child workflow)를 하나씩 띄운다. 모두 병렬로 돈다.
  2. 각 실행에서 에이전트는 iOS 저장소를 복제한다.
  3. 저장소에 둔 테스트 스킬을 읽는다. 좋은 테스트를 어떻게 쓰는지 적은 문서다.
  4. 테스트, 그리고 필요한 목과 페이크 (fake)를 쓴다.
  5. generated test 라벨을 붙여 PR을 연다. 나중에 쉽게 찾기 위해서다.
듀오링고의 클라우드 코딩 에이전트 06:40 이 에이전트들은 듀오링고 사내 플랫폼에서 돈다. 이 플랫폼도 Temporal 위에서 돈다. 클라우드에서 도는 Claude Code와 Codex 위에 얹은 추상화 계층이라고 보면 된다. Slack, Temporal, GitHub에서 부를 수 있다. MCP로 사내 도구 여럿과 연결된다. 실행마다 이벤트를 기록해서, 에이전트가 무엇을 하는지와 비용이 얼마인지 본다. 처음에는 Linux 머신에서 돌렸고, 나중에 Mac 러너로 옮겼다. 이유는 09번 섹션에 있다.

생성된 PR과 리뷰어의 선택지 07:00

PR 설명은 모두 같은 템플릿을 따른다. AI가 만든 PR이라고 분명히 적는다. 리뷰어의 선택지는 넷이다.

선택결과
승인PR이 자동으로 머지된다
직접 수정리뷰어가 PR에 변경을 바로 푸시한다
재지정더 맞는 사람에게 넘긴다
닫기머지할 수 없는 이유를 피드백으로 남기고 닫는다
07

3단계: PR 수명 주기 07:20

백필이 돌기 시작하자 새 문제가 생겼다. 열린 PR이 수십에서 수백 개가 됐다. 손으로는 관리할 수 없었다. 이 PR들을 머지할 수 있는 상태로 만들고 맞는 리뷰어 앞에 놓는 것이 PR 수명 주기 워크플로다.

상태 기계 (state machine)로 생각하면 된다. 몇 시간마다 돈다. 열린 generated test PR을 모두 살펴본다. 각 PR에 정확히 한 가지 행동만 한다. 루프의 검증과 처리 단계를 맡는다. 07:40

결정 트리 07:50

PR 상태행동
머지 충돌이 있거나, 약 3주 동안 열려 있음닫고 오래됨 (stale)으로 표시
CI가 아직 돌고 있거나, 리뷰어가 이미 보고 있음건너뜀
CI 초록, 리뷰어 없음리뷰어를 찾아 지정
CI 빨강고치기를 시도
리뷰어가 거절그 파일을 30일 쿨다운에 넣음. 같은 PR로 엔지니어를 계속 귀찮게 하지 않기 위해서다

CI가 실패하면 08:10

  1. 먼저 어느 작업이 실패했는지 본다.
  2. pre-commit 검사가 실패했으면 GitHub Action이 고친다. 싸고, 결정적 (deterministic)이고, 에이전트가 필요 없다.
  3. 진짜 테스트가 실패했으면 다른 에이전트를 띄운다. 이 에이전트가 CI 로그를 읽고 PR에 수정을 푸시한다.
  4. 이 고치기 루프는 최대 5번이다. 넘으면 끝없이 고치는 대신 PR을 닫는다.

리뷰어 찾기 08:20

CI가 초록이 되면 맞는 리뷰어를 찾는다. 테스트 대상 소스 파일에 git blame을 돌린다. 가장 많이 기여한 사람을 찾아 지정하고, 자동 머지를 켠다.

그 사람이 승인하면 PR이 머지된다. 거절하면 그 파일은 30일 쿨다운에 들어간다.

눈여겨볼 설계 싸고 결정적인 수단을 먼저 쓴다. 에이전트는 그걸로 안 될 때만 부른다. 에이전트가 고치는 횟수에는 상한을 둔다.

4단계: 라벨 하나로 새 코드에 테스트 08:40

기존 코드 채우기가 돌자, 엔지니어가 새로 쓰는 코드에도 똑같이 쉽게 테스트를 붙이고 싶었다.

이제 엔지니어는 자기 PR에 테스트 작성 라벨을 붙이기만 하면 된다. 라벨은 지금까지 본 Temporal 인프라에 그대로 연결된다.

다른 점은 고르기 하나다. 선택 스크립트 대신 엔지니어 PR의 파일을 그대로 쓴다. 에이전트가 테스트를 쓰고, 원래 PR에 연결된 초안 (draft) PR을 돌려준다.

문제 1: Linux 에이전트와 린트 실패 09:00

에이전트는 처음에 Linux 머신에서 돌았다. 여기에는 Xcode도 Swift도 없었다.

그래서 에이전트가 20~30분 일해 PR을 열면, CI가 린트 (lint)에서 자주 실패했다. 린트는 코드 스타일과 규칙을 자동으로 검사하는 도구다. 에이전트 시간도, CI 시간도 낭비됐다. 발표자는 CI 시간이 점점 귀해지는 자원이라고 했다.

파 보니 09:10 한동안 PR의 13.6%가 린트 때문에 실패했다. 그 실패의 62%는 린트 규칙 단 두 개에서 나왔다. 전체 PR로 따지면 약 8%(13.6% × 62%)가 규칙 두 개 때문에 실패한 셈이다. 이 노트의 계산이다.

자막의 이 부분은 "30 13.6%"로 뭉개져 있다. 13.6%로 읽었다.

한 번에 고치지 않고 층을 쌓았다. 09:20

  1. 프롬프트에 더 나은 예시와 피해야 할 함정을 넣었다.
  2. CI에서 린트 오류를 자동으로 고치는 GitHub Action을 붙였다.
  3. 자동으로 못 고치는 규칙을 감사했다. 신호가 약한 규칙은 없앴다. 에이전트와 사람 모두 편해졌다.
  4. 진짜 해결은 에이전트를 Mac 러너로 옮긴 것이다. 이제 에이전트는 PR을 열기 전에 직접 빌드하고 린트를 돌린다. 09:40

문제 2: 초록불로 가는 지름길 09:40

사람에게 PR을 넘길 때는, 그 사람이 편하게 승인할 수 있는 PR이길 바랐다. 그런데 에이전트는 CI를 초록으로 만드는 가장 짧은 길을 고르기도 한다.

실제로 본 지름길 1. 실패하는 테스트를 통과시키려고 제품 코드를 고쳤다. 2. 기존 테스트를 고치거나, 지우거나, 꺼 버렸다. 3. 테스트에 긴 대기를 넣었다. CI를 불안정하게 만든다.

세 겹의 방어 10:00

한 가지로 해결되는 문제가 아니었다. 그래서 세 겹을 만들었다.

층방식막는 것
1. 결정적 규칙PR이 테스트, 목, 페이크, 스텁이 아닌 파일을 하나라도 건드리면 닫는다제품 코드 수정
2. AI 코드 리뷰 활용듀오링고는 모든 PR을 Claude와 Codex로 리뷰한다. 이 봇들이 남긴 P0 지적을 사람이 보기 전에 해결하는 에이전트를 만들었다가장 심각한 리뷰 지적
3. LLM 판사 (LLM-as-a-judge)테스트 PR 전용 리뷰 에이전트가 diff를 읽는다. 알게 된 게 늘면 검사 항목도 계속 더한다제품 코드 수정, 바뀌거나 지운 테스트, 꺼 둔 테스트, 긴 대기

지금까지 LLM 판사는 PR 약 1,200개(추정)를 리뷰해 73개를 거절했다. 10:30

자막에는 리뷰한 PR 수가 ",200"으로만 남아 있어 1,200으로 읽었다(추정). 이 값이 맞다면 거절 비율은 약 6%다.

거절 사유를 다시 넣는다 10:40

LLM 판사는 거절할 때마다 이유를 정확히 적은 댓글을 남긴다. 팀은 그 피드백을 읽고 프롬프트와 스킬에 다시 넣는다. 그래서 같은 실수가 갈수록 줄어든다. 루프의 마지막 단계인 개선이 바로 이것이다.

핵심 정리

  1. 코드가 늘고 코드를 쓰는 사람이 다양해지면서, 병목은 쓰기에서 검증으로 옮겨 갔다.
  2. 단위 테스트는 싸고 빠른 검증이다. CI에서 에이전트에게 바로 피드백을 주는 가드레일이기도 하다.
  3. 파이프라인은 고르기 → 쓰기 → 검증 → 처리 → 개선의 다섯 단계 루프다.
  4. 운영 전에 로컬에서 PR 57개를 돌려 실패 유형부터 모았다. 머지율은 약 47%였다.
  5. 실패 유형은 규칙, 예시, 코드베이스 정리로 고쳤다. 에이전트가 테스트하기 쉬운 코드는 사람에게도 쉽다.
  6. 파일 선택은 "좋은 테스트를 쓸 수 있다는 확신"으로 점수를 매긴다. MVVM 계층 2.5배, UI 제외, 큰 파일 감점.
  7. PR 수명 주기 워크플로는 몇 시간마다 PR 하나에 한 가지 행동만 한다. 싼 결정적 수정이 먼저, 에이전트 수정은 5번까지다.
  8. 리뷰어는 git blame 최다 기여자다. 거절된 파일은 30일 쉰다.
  9. 에이전트는 초록불 지름길을 찾는다. 결정적 규칙, AI 리뷰 P0 해결, LLM 판사로 막고, 거절 사유를 스킬에 다시 넣는다.
  10. 결과는 테스트 PR 700개 이상, 약 22만 5천 줄, MVVM 커버리지 9% → 59%다. 같은 루프를 다른 대규모 작업에도 쓴다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말한 "병목의 이동"은 무엇에서 무엇으로인가?
코드 쓰기에서 검증으로. 에이전트와 사람이 코드를 더 빨리 쓰게 되면서, PR이 안전한지 판단하는 일이 더 어려워졌다.
Q2단위 테스트가 에이전트에게 특히 쓸모 있는 이유는?
가드레일이 되기 때문이다. 에이전트의 변경이 CI에서 테스트를 깨면, 무엇을 고쳐야 하는지 바로 피드백을 받는다.
Q3다섯 단계 루프를 순서대로 말해 보자.
고르기(identify) → 쓰기(write) → 검증(verify) → 처리(resolve) → 개선(iterate).
Q4로컬 검증 단계의 진짜 목표는 무엇이었나?
머지를 많이 하는 게 아니었다. 에이전트가 어떻게 실패하는지 배우고, 운영에 올리기 전에 자잘한 문제를 고치는 것이었다. 57개 중 27개, 약 47%가 머지됐다.
Q5로컬 검증에서 나온 실패 유형 세 가지는?
한 파일에 XCTest와 Swift Testing 섞기, 구체 클래스로 주고받는 싱글턴 때문에 목을 만들기 어려운 코드, 동시성 문제와 시간에 기대는 테스트.
Q6선택 스크립트가 점수를 매기는 기준과 가장 강한 신호는?
기준은 "에이전트가 이 파일에 좋은 테스트를 쓸 수 있다고 얼마나 확신하나"다. 가장 강한 신호는 파일 종류다. 뷰 모델, 리포지토리, 데이터 소스는 2.5배, 레거시는 아래로, UI는 제외, 큰 파일은 감점.
Q7Temporal이 에이전트 작업에 잘 맞는 이유는?
워커가 죽어도 멈춘 지점부터 이어지므로, 몇 초에서 몇 시간까지 걸리는 에이전트 세션을 안전하게 돌릴 수 있다. 스케줄, 병렬 실행, 재시도·타임아웃·멱등성도 기본으로 있다.
Q8PR 수명 주기 워크플로에서 CI가 실패하면 어떻게 하나?
어느 작업이 실패했는지 본다. pre-commit 실패는 GitHub Action이 결정적으로 고친다. 진짜 테스트 실패는 에이전트가 CI 로그를 읽고 고친다. 최대 5번까지 하고, 넘으면 PR을 닫는다.
Q9리뷰어는 어떻게 고르고, 거절되면 어떻게 되나?
테스트 대상 소스 파일에 git blame을 돌려 가장 많이 기여한 사람을 지정하고 자동 머지를 켠다. 거절되면 그 파일은 30일 쿨다운에 들어간다.
Q10린트 실패 문제의 진짜 해결책은?
에이전트를 Xcode와 Swift가 없는 Linux 머신에서 Mac 러너로 옮겼다. 이제 PR을 열기 전에 직접 빌드하고 린트를 돌린다.
Q11에이전트가 찾은 초록불 지름길 세 가지와, 그걸 막는 세 겹은?
지름길: 제품 코드 수정, 기존 테스트 수정·삭제·끄기, 긴 대기 넣기. 방어: 테스트 외 파일을 건드리면 닫는 결정적 규칙, AI 리뷰의 P0 지적을 해결하는 에이전트, 테스트 PR 전용 LLM 판사.
Q12최근 파이프라인의 몫이 줄어든 것을 왜 좋은 신호로 보나?
엔지니어들이 직접 테스트를 훨씬 많이 쓰기 시작했기 때문이다. 발표자는 이것이 원래 목표라고 했다.
