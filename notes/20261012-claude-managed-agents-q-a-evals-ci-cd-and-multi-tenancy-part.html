관리형 에이전트를 운영할 때 나오는 질문들

Claude Managed Agents 워크숍의 마지막 질의응답이다. 청중은 설정 배포, 평가, 고객별 분리, 긴 작업을 물었다. 답은 대부분 같은 방향이다. 플랫폼이 직접 해 주지 않는 일은 워크스페이스, 세션 메타데이터, 커스텀 도구, 서브에이전트 같은 기본 재료로 조립한다.

원본 영상: Claude Managed Agents Q&A: Evals, CI/CD and Multi-Tenancy (Part 4 of 4) 발표: Anthropic Claude Managed Agents 팀 (자막에 이름이 나오지 않는다)

영어 질의응답의 자동 자막을 바탕으로 한글로 정리했다. 답변은 여러 명이 나눠 했고, 이 노트는 모두 "발표자"로 적는다. 제품 동작에 대한 설명은 발표자가 말한 것이고 공식 문서로 따로 확인하지 않았다. 자막에서 뭉개진 이름은 확실한 것만 고쳤고, 나머지는 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자들은 Anthropic 소속이고, 자기 회사 제품을 설명하는 자리다. 제품이 무엇을 잘한다는 말은 그 점을 감안해 읽자.

3분 요약
  1. 에이전트 설정은 YAML로 저장소에 두고 CI에서 CLI로 반영한다. Anthropic도 내부에서 이렇게 한다.
  2. 모델이 커스텀 도구 결과를 기다리는 동안 메시지를 보내면 400 오류가 난다. 늘 말을 받아야 하면 커스텀 도구를 서브에이전트에 맡긴다.
  3. 평가의 핵심은 좋은 데이터다. 문제 정의가 엉성하면 100%가 나와도 의미가 없다. 과거 세션 기록이 좋은 재료다.
  4. 모든 리소스는 워크스페이스에 묶인다. 같은 워크스페이스의 API 키는 그 안의 리소스에 모두 접근한다.
  5. 고객을 나누는 단위는 에이전트, 워크스페이스, 조직 세 가지다. 법적으로 데이터를 나눠야 하면 워크스페이스 이상으로 나눈다.
  6. PR이 열리면 세션 여러 개를 띄워 버그를 찾게 하고, 샌드박스에서 앱을 직접 돌려 확인하게 한다. 다만 리뷰 병목은 아직 풀리지 않은 문제라고 인정했다.
  7. 기본 샌드박스는 사양이 모두 같다. GPU나 큰 메모리가 필요하면 Modal 같은 외부 샌드박스를 붙인다.
  8. 긴 작업은 종료 기준을 주면 그 기준을 채울 때까지 돈다. 진행 상황은 이벤트 API나 상태 보고용 커스텀 도구로 본다.
01

에이전트 설정을 코드로 관리하기 00:00

첫 질문은 에이전트 설정을 CI/CDcontinuous integration / continuous deployment로 어떻게 관리하느냐였다. CI/CD는 코드가 바뀔 때마다 검사와 배포를 자동으로 돌리는 흐름이다.

발표자는 Ancho CLI(들린 대로 적음, Anthropic의 ant CLI로 추정)를 소개했다. API 호출을 감싼 명령줄 도구다. YAML 파일을 넘기면 그 내용대로 리소스를 만든다. 인프라를 코드로 선언하는 Terraform과 비슷한 방식이다.

  1. 오래 유지할 리소스(에이전트 정의 같은 것)를 YAML로 써서 저장소에 넣는다.
  2. 그 YAML이 바뀌면 CI가 돌아간다.
  3. CI가 CLI로 실제 리소스를 갱신한다.

Anthropic도 내부에서 같은 방식을 쓴다. 오래 갈 리소스는 저장소에 체크인한다.

02

도구 결과를 기다릴 때는 말을 못 건다 01:00

Managed Agents에서는 에이전트가 일하는 중에도 메시지를 보낼 수 있다. 모델이 다른 일을 하는 동안 보낸 메시지는 줄을 세워 뒀다가 처리한다.

예외가 하나 있다. 모델이 커스텀 도구custom tool의 결과를 기다리는 동안이다. 커스텀 도구는 개발자 쪽에서 실행하고 결과를 돌려줘야 하는 도구다.

  • 이때 플랫폼은 실행을 멈춰 둔다.
  • 다음에 와야 할 것은 도구 결과다.
  • 순서가 꼬이지 않도록 다른 메시지는 막는다.
  • 그래도 보내면 400 오류(잘못된 요청)가 돌아온다.
언제 문제가 되나 사람의 승인을 받는 도구처럼 기다림이 길어지는 경우다. 그동안 다른 사람이 말을 걸면 거절된다. 마지막 질문에서 이 문제를 다시 다뤘다. 해법은 10장 코디네이터 패턴에 있다.
03

평가는 데이터가 먼저다 02:40

평가 하네스의 품질을 어떻게 지키는지, 그리고 사용자가 만든 에이전트는 어떻게 평가하면 되는지 물었다. 평가eval는 결과 품질을 재는 테스트 묶음이다. 하네스harness는 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀이다.

Anthropic 내부
  • 새 모델을 외부보다 먼저 받는다.
  • 관리형 서비스라서 하네스의 가정을 최대한 일찍 고친다. 새 모델에 더는 필요 없는 장치를 빼기 위해서다.
  • 내부 도구로 여러 데이터셋에 세션을 돌린다.
  • 클라우드라서 세션 1만 개를 동시에 띄울 수 있다.
  • 결과를 보고 프롬프트와 가정을 조정한다. 코딩만이 아니라 일반 용도 전반을 평가한다.
내 에이전트에 권하는 것 03:50
  • 정해진 평가 도구를 주지는 않는다. 조언은 좋은 데이터를 확보하라는 것이다.
  • Claude Code는 평가를 꽤 잘 만들어 준다. 그래도 넣은 데이터가 나쁘면 결과도 나쁘다.
  • 과거 세션과 그 결과를 채점해 데이터셋을 만든다.
100%의 함정 Anthropic이 처음 만든 평가 중에는 문제 정의가 엉성한 것이 있었다. 점수가 100%로 나와도 그게 실제 성능에서 무엇을 뜻하는지 알 수 없었다. 그래서 데이터를 고치고 문제 설정을 다시 다듬는 일을 반복했다.
Garbage in, garbage out.평가 데이터에 대한 발표자의 말 04:00

새 모델마다 하네스를 맞춘다는 설명은 Anthropic이 자기 서비스에 대해 한 말이다.

04

리소스는 워크스페이스에 묶인다 04:40

질문자의 회사는 Claude Code로 공용 스킬과 커넥터를 만들어 쓴다. 에이전트, 메모리 저장소, MCP 연결도 부서끼리 나눠 쓸 수 있는지, 일부만 공유할 수 있는지 물었다.

단위누가 정하나의미
조직 (org)회사 단위로 하나 둔다Claude 플랫폼 관리자가 이 안에서 워크스페이스를 만든다
워크스페이스관리자누가 어느 워크스페이스에 들어갈지 관리자가 정한다. 리소스는 여기에 묶인다
API 키워크스페이스 안에서 발급같은 워크스페이스의 리소스에 모두 접근한다

그래서 권한은 워크스페이스 설계로 정한다. 리소스 X에 접근해야 하는 사람들을 한 워크스페이스에 모으면 된다.

"메모리는 이 팀에만, MCP 연결은 저 팀에만" 같은 리소스 단위의 세밀한 공유 설정은 없다. 대신 그 위에 앱을 만드는 쪽이 자기 사용자에게 보여 줄 범위를 직접 세밀하게 정할 수 있다.

05

쏟아지는 PR은 누가 보나 06:30

에이전트 여럿이 코드를 대량으로 만들면 병목은 리뷰와 머지로 옮겨 간다. Anthropic은 그 많은 코드를 어떻게 리뷰하느냐는 질문이었다.

발표자에 따르면 원래 하려던 워크숍 주제가 바로 이것이었다. 방법은 Managed Agents(이하 CMA)와 연동하는 것이다.

  1. PR이 열리면 세션을 하나 이상 띄운다.
  2. 각 세션은 서브에이전트 여럿을 써서 바뀐 부분을 보고 버그를 찾는다.
  3. 리뷰하고 코멘트를 달고 다시 리뷰하는 일을 끝날 때까지 반복할 수 있다.
  4. 마지막에는 실제로 돌려 봐야 한다. 브랜치마다 환경이 있다면 배포 에이전트가 자동으로 배포해 테스트할 수 있게 한다.
  5. 샌드박스 안에서 앱을 실행하고, Claude가 브라우저로 직접 써 보며 자기 변경을 검증하게 할 수도 있다. QA 에이전트 역할이다.

지금은 터널링tunneling을 지원하지 않는다. 샌드박스 안의 화면에 사람이 직접 들어가 볼 수는 없다. 그래서 Claude가 화면을 확인하고 결과를 돌려준다. 질문자가 "영상으로 돌려받을 수도 있겠다"고 하자 발표자도 그렇다고 답했다.

아직 열린 문제 타이핑이라는 한계가 사라지면서 하루, 한 시간에 만들 수 있는 PR 수가 폭발했다. 그 속도를 어떻게 따라갈지는 Anthropic도 아직 찾는 중이라고 했다. CMA는 답의 일부라고 표현했다.

내부에서 PR당 리뷰 시간과 버그가 줄었다는 말은 Anthropic의 자체 경험이고 수치는 제시하지 않았다.

06

고객별로 나누기 08:50

고객사가 100곳인 회사가 고객마다 따로 분리된 에이전트를 둘 수 있느냐는 질문이었다. 이런 구조를 멀티테넌시multi-tenancy라고 한다. 한 시스템을 여러 고객이 서로 섞이지 않게 나눠 쓰는 것이다.

먼저 온프레미스on-prem는 지원하지 않는다. 고객 회사의 자체 서버에 설치해 쓰는 방식은 없다는 뜻이다. 그 밖에는 나누는 단위를 직접 고르면 된다.

나누는 방법분리 수준직접 관리할 것
한 에이전트 + 세션 메타데이터세션만 구분한다세션의 metadata 필드에 고객 ID를 넣어 어느 세션이 누구 것인지 기록
고객별 에이전트설정이 고객마다 따로 있다어느 고객이 어느 에이전트를 쓰는지 매핑
고객별 워크스페이스리소스가 워크스페이스마다 따로 할당된다. 데이터 분리 요구를 맞출 수 있다같은 에이전트 정의를 여러 워크스페이스에 동기화
고객별 조직가장 강한 분리. 발표자는 "true isolation"이라고 불렀다조직 여러 개를 운영

한 에이전트를 두 고객이 쓰려면 10:00

에이전트는 시스템 프롬프트, 모델 이름, 도구를 묶은 템플릿이다. 그래서 복사하기 쉽다.

고객별 워크스페이스로 갈 때

에이전트 정의를 YAML로 저장소에 둔다. CI가 그 정의를 모든 고객 워크스페이스에 한 번에 반영한다. Anthropic이 이 동기화를 돕는 도구를 준다고 했다.

한 워크스페이스에 모두 둘 때

에이전트를 고객별로 복사하거나, 에이전트 하나를 같이 쓴다. 같이 쓰면 세션 metadata의 고객 ID로 누가 쓰는 세션인지 구분한다.

법적 데이터 분리가 필요하면 11:30

질문자는 고객이 다른 고객과 데이터를 섞지 않길 원하는 경우를 물었다. 발표자의 답은 분명했다. 데이터 분리가 중요하면 고객마다 워크스페이스를 따로 둔다. 리소스가 워크스페이스 단위로 할당되기 때문이다.

발표자는 처음에 "고객별 에이전트로도 데이터가 나뉜다"고 했다. 하지만 같은 발표에서 같은 워크스페이스의 API 키는 그 안의 리소스에 모두 접근한다고 설명했다. 이 노트의 해석으로는, 분리 요구가 있다면 워크스페이스 이상을 기준으로 잡는 편이 안전하다.

07

GPU와 큰 메모리가 필요할 때 12:10

에이전트가 일할 컴퓨터 사양을 바꿀 수 있느냐는 질문이었다. 메모리를 늘리거나 GPU를 쓰고 싶은 경우다.

  • Anthropic이 제공하는 샌드박스sandbox는 지금 사양이 모두 같다. 샌드박스는 에이전트가 코드를 실행하는 격리된 작업 환경이다.
  • 사양을 바꾸려면 자체 호스팅 샌드박스self-hosted sandbox를 쓴다.
  • 예로 GPU를 제공하는 Modal을 들었다. Modal을 연결하는 쿡북cookbook과 공식 연동이 있다.
  • Modal 말고도 E2B(자막은 "EB2", 추정), Daytona 같은 곳을 쓰는 쿡북이 있다.
  • 기본 샌드박스의 사양은 문서에 나와 있다.
08

여럿이 함께 쓰는 Slack 에이전트 13:20

Claude Tag(자막은 "Cloud Tag", 추정) 같은 것을 CMA로 다른 채팅 채널에 만들 수 있느냐는 질문이었다. 문맥상 Slack 채널에서 여러 사람이 한 Claude를 함께 부르는 기능을 말한다. 질문자는 특히 여러 사람이 동시에 쓰는 멀티플레이어 방식을 물었다.

발표자는 앞 순서에서 시연한 outcomes 기능이 가장 좋은 방법이라고 답했다. 끝나는 기준을 먼저 정해 주는 기능이다.

  2. Claude는 그 기준을 채울 때까지 계속 고치고 다시 해 본다.
  3. "무엇을 다시 만들어라" 같은 아주 긴 작업도 루브릭에 맞을 때까지 반복한다.

세션을 6시간 넘게 돌리려고 따로 할 일은 없다고 했다. 그냥 계속 돈다.

코디네이터 패턴 16:30

마지막 질문은 2장의 400 오류로 돌아갔다. 사람의 승인을 기다리는 커스텀 도구가 있으면, 그동안 들어오는 메시지를 어떻게 처리하느냐는 것이다.

메인 에이전트가 직접 도구를 쓸 때도구 결과를 기다리는 동안 메시지가 막힌다그 사이에 보낸 메시지는 400으로 거절된다
→
코디네이터 패턴서브에이전트가 도구를 맡고 기다린다메인 코디네이터는 계속 메시지를 받는다
  1. 메인 코디네이터 에이전트를 정의하고, "A는 B, C와 대화할 수 있다"고 정한다.
  2. 커스텀 도구는 서브에이전트 B의 정의에 넣는다.
  3. 도구 호출은 B의 스레드에서 나온다.
  4. 사용자는 메인 스레드만 상대하면 된다. 결과를 보내면 플랫폼이 ID를 보고 맞는 곳으로 전달한다.

서브에이전트가 일하는 동안 세션은 쉬는 상태가 아니다. 대신 메인 스레드는 쉬는 상태일 수 있다. 발표자는 데모 화면에서 메인 스레드가 비어 있는 동안 서브에이전트들이 일하는 구간을 보여 줬다. 서브에이전트는 그동안 도구 결과를 기다리고 있을 수도 있다.

언제 쓰나 메인 에이전트가 늘 대화에 응할 수 있어야 할 때다. 사람의 승인이나 오래 걸리는 외부 작업을 서브에이전트에 맡기면 메인은 계속 말을 받는다.

스레드 처리 방식은 발표자들의 설명이 조금 엇갈렸다. 한 명은 B의 세션 스레드를 지켜보면 된다고 했고, 다른 한 명은 메인 스레드만 상대하면 된다고 했다. 정확한 API 동작은 문서로 확인하자.

11

핵심 정리

  1. 에이전트 정의는 오래 가는 리소스다. YAML로 저장소에 두고 CI에서 CLI로 반영한다.
  2. 커스텀 도구 결과를 기다리는 동안 보낸 메시지는 400으로 거절된다. 순서를 지키기 위해서다.
  3. 그 제약은 커스텀 도구를 서브에이전트에 맡기는 코디네이터 패턴으로 피한다.
  4. Anthropic은 새 모델마다 세션 1만 개 규모로 평가를 돌려 하네스의 가정을 고친다.
  5. 평가는 데이터 품질이 좌우한다. 100%가 나오면 문제 정의부터 의심한다. 과거 세션이 좋은 재료다.
  6. 리소스는 워크스페이스에 묶이고, 같은 워크스페이스의 API 키는 모두 접근한다. 리소스 단위 공유 설정은 없다.
  7. 고객 분리 단위는 에이전트, 워크스페이스, 조직이다. 법적 분리가 필요하면 워크스페이스 이상으로 나눈다.
  8. 기본 샌드박스는 사양이 하나다. GPU나 큰 메모리는 Modal 같은 자체 호스팅 샌드박스로 해결한다.
  9. Slack 멀티플레이어는 스레드를 세션에, 채널을 에이전트에 대응시킨다. 답장은 게시 도구로 명시적으로 하게 한다.
  10. 긴 작업은 outcomes 종료 기준으로 돌린다. PR 리뷰 병목은 Anthropic도 아직 답을 찾는 중이다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1에이전트 설정을 CI/CD로 관리하는 방법은?
에이전트 정의를 YAML로 저장소에 둔다. YAML이 바뀔 때마다 CI가 CLI로 실제 리소스를 갱신한다. Terraform과 비슷한 방식이다.
Q2모델이 커스텀 도구 결과를 기다리는 동안 메시지를 보내면? 왜 그런가?
400 오류가 난다. 플랫폼이 실행을 멈추고 도구 결과를 기다리는 중이라, 순서가 꼬이지 않게 다른 메시지를 막는다. 모델이 다른 일을 할 때는 메시지를 줄 세워 둘 수 있다.
Q3Anthropic이 새 모델마다 평가를 돌리는 목적은?
하네스의 가정을 최대한 일찍 고치고, 새 모델에 더는 필요 없는 장치를 빼기 위해서다. 클라우드라서 세션 1만 개를 동시에 돌릴 수 있다.
Q4평가 점수가 100%인데도 믿기 어려운 경우는?
문제 정의가 엉성할 때다. 그러면 100%가 실제 성능에서 무엇을 뜻하는지 알 수 없다. 데이터와 문제 설정을 다시 다듬어야 한다.
Q5내 에이전트의 평가 데이터셋을 만들 좋은 재료는?
과거 세션 기록이다. 그때 얻은 결과를 채점해 모델이 얼마나 잘하는지 본다.
Q6동료가 내 에이전트와 메모리 저장소에 접근할 수 있는지는 무엇으로 정해지나?
워크스페이스다. 같은 워크스페이스의 API 키는 그 안의 리소스에 모두 접근한다. 누가 어느 워크스페이스에 들어갈지는 관리자가 정한다. 리소스 단위로 따로 공유하는 설정은 없다.
Q7고객 데이터를 법적으로 분리해야 한다면 어떻게 나누나?
고객마다 워크스페이스를 따로 둔다. 리소스가 워크스페이스 단위로 할당되기 때문이다. 더 강한 분리가 필요하면 고객마다 조직을 둔다. 에이전트 정의는 CI로 여러 워크스페이스에 동기화한다.
Q8한 워크스페이스에서 에이전트 하나를 여러 고객이 쓸 때 고객을 어떻게 구분하나?
세션의 metadata 필드에 고객 ID를 넣는다. 어느 세션이 어느 고객 것인지는 직접 관리한다.
Q9에이전트에 GPU나 큰 메모리가 필요하면?
기본 샌드박스는 사양이 모두 같다. Modal 같은 자체 호스팅 샌드박스를 연결한다. 연결 방법은 쿡북에 있다.
Q10Slack 에이전트가 응답을 모두 채널에 올리지 않게 하려면?
Slack 게시 도구를 주고, 언제 올릴지 에이전트가 도구 호출로 정하게 한다. 응답을 그대로 옮겨 적지 않는다.
Q116시간 넘는 작업을 끝까지 돌리고 진행을 확인하려면?
outcomes 기능으로 종료 기준을 루브릭으로 준다. Claude는 기준을 채울 때까지 반복한다. 진행은 세션 events API로 보거나, 상태 보고용 커스텀 도구를 만들어 받는다.
Q12커스텀 도구를 기다리는 동안에도 메시지를 받으려면?
코디네이터 패턴을 쓴다. 커스텀 도구를 서브에이전트 정의에 넣으면 서브에이전트가 기다리는 동안에도 메인 코디네이터는 메시지를 받는다.
