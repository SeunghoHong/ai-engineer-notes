새 AI 모델을 나온 날 바로 쓰는 트레이딩 회사

Optiver는 새 AI 모델이 나오면 그날 사내 데이터로 평가해 바로 업무에 쓴다. 이를 받치는 것은 모델과 도구를 언제든 갈아 끼우고 모든 층에서 잴 수 있게 직접 만든 사내 플랫폼이다.

원본 영상: How a Trading Firm Ships New AI Models the Same Day 발표: Noyan Tokgozoglu (Optiver AI 엔지니어링 총괄)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막의 "Nayan"은 영상 제목에 따라 Noyan으로, "hotel logging"은 OTel(OpenTelemetry) 기록으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 트레이딩 회사는 변경의 효과가 몇 시간 안에 손익으로 보인다. 그래서 빨리 결정하고 빨리 잰다.
  2. 플랫폼 원칙은 갈아 끼울 수 있는 구조, 모든 층에서 측정, 셀프서비스와 좋은 기본값, 안전, 사내 운영이다.
  3. 새 프런티어 모델이 나오면 그날 트레이딩 팀의 평가 문제로 돌려 보고, 게이트웨이와 비용 관리와 하네스를 맞춰 바로 내놓는다.
  4. 모든 모델 호출은 추론 게이트웨이 하나를 지난다. 전부 기록되어 평가로 가고, 업체가 멈추면 다른 업체로 바꾼다.
  5. 셀프서비스로 두자 새 세션이 20만 토큰으로 시작했다. 도구 검색, CLI, 캐시 조정, 지식 베이스로 줄이고 팀마다 지출을 보여 줬다.
  6. 사용자가 엉성한 도구를 각자 만들고 있으면 더 나은 버전을 만들어 모두에게 준다.
  7. 남은 숙제는 지식 베이스와 도구 호출 평가의 재현이다. 에이전트는 하나로 키우지 말고 작게 나눈다.
01

Optiver는 어떤 회사인가 00:20

Optiver는 마켓 메이커market maker다. 사려는 사람과 팔려는 사람이 언제든 거래할 수 있도록 가격을 내고 거래를 받아 주는 회사다.

고객은 없다. 자기 돈으로 거래한다.

기술 회사의 눈으로 보면 하는 일은 단순하다. 데이터를 많이 모으고, 모델을 만들고, 그 모델로 결정을 내린다. 그 결정은 아주 빠르게 돌아가야 한다.

가격을 매기는 금융 상품100만 개 이상
하루 처리 데이터페타바이트 단위
사무소전 세계 10곳 이상

사무소가 여러 대륙에 흩어져 있다는 점은 뒤에서 24시간 지원과 지역별 배포 문제로 이어진다.

03

플랫폼의 원칙 02:50

이렇게 일하려고 Optiver는 사내 AI 플랫폼을 직접 만들었다. 기준이 된 원칙은 다섯 가지다.

원칙뜻
빨리 움직인다놓친 기회가 비싸므로 결정을 미루지 않는다
모듈로 만든다새 모델, 새 제품, 새 방식이 매일 나온다. 루프였다가 스웜이었다가 그래프가 된다. 부품을 갈아 끼울 수 있어야 쓸모 있는 것을 바로 들여온다
모든 층에서 잰다외부 벤치마크만 믿지 않는다. 사내 데이터는 외부 벤치마크와 분포가 달라서 내부 벤치마크가 따로 필요하다. 트레이딩에서 하던 백테스트를 AI에도 적용하는 셈이다
셀프서비스와 좋은 기본값트레이더는 똑똑하고 스스로 일을 찾아 하는 사람들이다. 다만 아무 제약 없이 열어 두면 혼란스러워지므로 기본 설정을 잘 잡아 준다
현장에 파견한다AI 엔지니어가 트레이더 옆에 앉아 함께 일한다. 거래 방식을 배우고, AI 활용법을 알려 주고, 배운 것을 플랫폼에 되돌린다. 이를 포워드 디플로이forward deploy라고 부른다

안전과 사내 운영 04:20

AI를 많이 쓸수록 안전이 중요해진다. 에이전트가 제멋대로 움직여 회사 시스템을 건드리면 피해가 클 수 있다.

발표자는 여기서 업계에 알려진 사고 이야기를 언급했다. 자막에는 "opening eye, hugging face"로 들린다(추정). 어떤 사건인지는 발표에서 설명하지 않았다.

발표자에 따르면 회사의 모든 사람이 AI를 쓴다. 쓰는 방식만 사람마다 다르다.

모든 것을 사내에 둔다 04:50 규제가 강한 업종이고, 회사의 지적 재산을 중요하게 여긴다. 그래서 GPU와 인프라를 직접 보유하고 운영한다on-prem. 밖으로 나가는 것은 외부 모델 추론뿐이다. 그 업체들과는 보낸 데이터를 저장하지 않는다는 계약zero data retention을 맺는다.
04

플랫폼 구조 한눈에 05:10

발표자가 보여 준 플랫폼 구조도는 정보가 아주 많다. 발표자가 강조한 점은 하나다. 스택의 모든 층을 플랫폼 팀이 책임진다. 아래층부터 정리하면 다음과 같다.

층하는 일
모델외부 업체의 모델, 직접 운영하는 자체 모델, 오픈소스 모델
추론 게이트웨이모든 모델 호출이 지나는 관문inference gateway. 모델 사이 라우팅, 모델별 지출 측정, 예산 배정을 맡는다
에이전트 플랫폼 06:00에이전트마다 스킬, 플러그인, 도구 같은 능력을 등록한다. 팀마다 자기 지식과 메모리 시스템을 붙인다
에이전트 게이트웨이회사의 모든 에이전트를 한 장부에 올린다agent gateway. 에이전트끼리 대화하고, 사람과 에이전트를 비슷한 신원 관리 방식으로 함께 조율한다
사용자 화면 06:30세션을 다루는 웹 화면, 팀별 사용 방식을 프로필로 만들어 공유하는 에이전트 워크벤치, 전 직원이 쓰는 개인 비서
게이트웨이를 두는 이유 모델 업체 하나가 멈춰도 다른 업체로 바로 돌릴 수 있다. 트레이딩 회사에서 멈춘 시간은 곧 벌지 못한 돈이다.

발표자는 스스로를 제품을 중시하는 사람이라고 소개했다. 플랫폼을 잘 만들어도 사람들이 쓰고 싶어 하지 않거나 쓰는 법을 모르면 소용없다. 그래서 사용자 화면을 따로 챙긴다.

05

새 모델을 출시 당일 쓰는 법 07:10

Optiver의 원칙이 하나 있다. 새 프런티어 모델frontier model이 공개되면 그날 바로 실제 업무 흐름에 쓸 수 있어야 한다. 정말 가치가 있다면 하루라도 빨리 쓰는 쪽이 이득이기 때문이다.

문제는 "정말 가치가 있나"를 그날 알아내는 것이다. 그래서 하는 일이 여러 가지다.

  1. 골든 셋으로 평가한다. 골든 셋golden set은 정답을 아는 평가용 문제 묶음이다. 이걸 돌리려면 평가 체계가 성숙해 있어야 한다.
  2. 트레이딩 팀의 벤치마크를 미리 모아 둔다. 주요 트레이딩 팀과 손잡고 그 팀의 평가 문제를 플랫폼에 올려 둔다. 새 모델이 나오면 바로 돌려 지표를 확인하고 사내에 공유한다.
  3. 게이트웨이에 올린다. 07:40 API와 인터페이스를 맞추고 비용 관리를 설정한다.
  4. 하네스를 고친다. 새 모델은 하네스harness 수정이 필요한 경우가 많다. 고친 하네스를 배포하는 일까지 플랫폼 팀이 맡는다.
  5. 24시간 지원한다. 08:00 전 세계에 사무소가 있으므로 지역마다 지원 당번을 돌려 가동률을 지킨다.
  6. 결과를 알린다. 08:10 "이 모델을 평가했다, 이 정도로 잘 된다, 이렇게 쓰면 된다, 우리는 이걸 권한다"를 사내에 꾸준히 전한다.
당일 판단이 가능한 이유 평가 문제를 모델이 나오기 전에 이미 모아 두었기 때문이다. 모델이 나온 뒤에 벤치마크를 만들기 시작하면 그날 안에 판단할 수 없다.
06

모델과 하네스에 묶이지 않기 08:30

여러 모델 중 고를 수 있으니, 가치를 더하는 모델은 무엇이든 들여온다. 그러려면 다음 상황에 흔들리지 않아야 한다.

  • 지역이나 클라우드 업체에 따라 쓸 수 있는 모델이 다르다.
  • 일부 작업은 다른 망과 완전히 분리된 사내 구역DMZ에서만 돌아야 한다. 비용 때문이기도 하고 격리 때문이기도 하다.

그래서 Optiver는 모델에도 하네스에도 묶이지 않게 플랫폼을 만든다.

모든 호출은 기록되고 평가로 간다 08:50

외부 모델도 사내 모델도 모두 추론 게이트웨이를 지난다. 모델과 주고받는 모든 상호작용이 기록된다. 이 기록은 자동으로 평가 시스템에 들어간다.

메타 하네스 09:10

플랫폼은 여러 하네스를 지원한다. 그 위에 메타 하네스meta harness라는 층을 하나 더 둔다.

  • 팀은 메타 하네스에서 자기 하네스 설정을 정의한다.
  • 그래서 아래 하네스를 바꿔도 설정을 들고 옮겨 갈 수 있다.
  • 설정은 팀의 지식 베이스에 연결된다.
  • 실행 기록trace을 살펴 지식을 자동으로 모아 쌓는다.
  • 메타 하네스를 통해 에이전트를 플랫폼에 배포해 관리할 수도 있고, 웹 포털의 IDE 화면에서 쓸 수도 있다.
07

더 쓰되 현명하게 쓰기 09:50

발표자는 숫자를 지운 AI 지출 그래프를 보여 줬다. 흐름만 옮기면 다음과 같다.

  1. 12월: Claude Code가 널리 쓰이면서 지출이 오른다. 발표자는 그래프가 꺾이는 지점이 자기 입사 시점이라고 농담했다.
  2. 여름: 큰 프런티어 모델이 연달아 나오며 지출이 급등한다.
  3. 그 뒤: 최적화를 넣어 다시 통제한다.

그래프에 숫자가 없어서 이 노트에도 차트를 그리지 않았다. 지출을 통제했다는 효과도 숫자 없이 발표자가 말한 것이다.

기조는 분명하다. 더 쓸수록 더 많은 가치를 얻는다고 본다. 다만 현명하게 써야 한다.

새 세션이 20만 토큰으로 시작했다 10:40

MCP 서버와 지식 베이스를 다들 마구 붙였다. 그 결과 아무것도 하지 않은 새 세션의 컨텍스트가 기본 20만 토큰 이상이었다. 발표자는 "말도 안 된다"고 했다.

완전한 셀프서비스의 부작용이다. 플랫폼 팀이 직접 책임을 지고 나서야 했다.

핵심 정리

  1. 트레이딩 회사는 변경의 효과가 몇 시간 안에 손익으로 보인다. 그래서 빨리 결정하고 빨리 잰다.
  2. 놓친 기회가 비싸다. 새 모델이 가치 있다면 하루라도 빨리 써야 한다.
  3. 플랫폼 원칙은 모듈 구조, 모든 층에서 측정, 셀프서비스와 좋은 기본값, 현장 파견, 안전, 사내 운영이다.
  4. 외부 벤치마크만 믿지 않는다. 사내 데이터는 분포가 달라서 트레이딩 팀의 골든 셋으로 따로 평가한다.
  5. 당일 출시는 평가만이 아니다. 게이트웨이 등록, 비용 관리, 하네스 수정, 24시간 지원, 사내 안내까지 한 묶음이다.
  6. 모든 모델 호출은 추론 게이트웨이를 지나며 기록되고 평가로 간다. 업체가 멈추면 다른 업체로 바꾼다.
  7. 셀프서비스만으로는 새 세션이 20만 토큰으로 시작했다. 도구 검색, CLI, 캐시 조정, 지식 베이스로 줄였다.
  8. 지출을 보여 주고 한도를 스스로 정하게 하면 팀은 대체로 알아서 아낀다. 목표는 같은 토큰에서 더 많은 가치다.
  9. 사용자가 엉성한 도구를 각자 만들면 더 나은 버전을 만들어 준다. 한 업체에 묶이면 그 업체의 속도로만 움직인다.
  10. 에이전트는 작게 나눠 측정할 수 있게 둔다. 도구 호출 평가의 재현과 지식 베이스는 아직 풀리지 않은 숙제다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Optiver가 일반 기술 회사와 가장 다른 점은?
변경의 효과가 몇 시간 안에 손익으로 보인다. 일반 기술 회사는 사용 지표에 몇 주, 매출 효과에 몇 달에서 몇 년이 걸린다.
Q2트레이딩 회사에서 좋은 결정 하나의 가치가 특히 큰 이유는?
한정된 고객 관심을 놓고 다투는 서비스 회사와 달리, 트레이딩은 더 많이 거래할수록 더 많이 번다. 그래서 가치의 천장이 높고, 놓친 기회도 비싸다.
Q3외부 벤치마크가 있는데도 내부 벤치마크가 필요한 이유는?
사내 데이터의 분포가 외부 벤치마크와 다르다. 외부 점수가 높아도 사내 업무에서 잘 된다는 보장이 없다.
Q4새 모델을 출시 당일 쓰려면 평가 말고 무엇이 더 필요한가?
게이트웨이 등록, API와 인터페이스, 비용 관리 설정, 하네스 수정과 배포, 지역별 24시간 지원, 평가 결과와 권장 사용법의 사내 안내.
Q5당일 판단을 가능하게 하는 준비는?
주요 트레이딩 팀의 벤치마크를 미리 모아 플랫폼에 올려 둔 것. 모델이 나오면 바로 돌려 지표를 볼 수 있다.
Q6추론 게이트웨이가 맡는 일은?
모델 사이 라우팅, 모델별 지출 측정과 예산 배정, 모든 호출 기록. 업체 하나가 멈추면 다른 업체로 돌리는 장애 대비도 된다.
Q7메타 하네스가 있으면 팀에 무엇이 좋은가?
하네스 설정을 한곳에 정의하므로 아래 하네스를 바꿔도 설정을 옮겨 갈 수 있다. 설정은 팀의 지식 베이스와 연결된다.
Q8새 세션이 20만 토큰으로 시작한 원인과 대응은?
다들 MCP 서버와 지식 베이스를 마구 붙였다. MCP 도구 검색, MCP를 감싼 CLI, 캐시 설정 조정, 시스템 프롬프트 내용을 지식 베이스로 옮기기로 줄였다.
Q9팀마다 지출을 보여 주고 한도를 직접 정하게 하자 무슨 일이 생겼나?
많은 팀이 적당한 한도를 스스로 정했다. 보이게 하고 권한을 주면 사람들은 대체로 알아서 관리한다.
Q10기성 제품 대신 직접 만드는 세 가지 이유는?
기성 도구가 사내 인프라에서 잘 돌지 않는다. 업체에 묶이면 그 업체의 속도로만 움직인다. 자기 팀이 앞서 있다고 본다.
Q11Slack 지원 봇을 다른 모델로 다시 평가하기 어려운 이유와 대응은?
도구 결과가 그때의 Slack 상태에 기대 있어 지금 돌리면 결과가 달라진다. 도구 호출마다 시점 복원 신뢰도를 기록하고, MCP 앞 프록시로 스냅샷에 연결해 다시 돌린다.
Q12에이전트를 여러 팀이 같이 쓰려 할 때 권하는 방식은?
기능을 합친 큰 에이전트 하나 대신, 잘하는 일 하나에 맞춘 작은 에이전트를 여럿 두고 에이전트 게이트웨이로 서로 부르게 한다. 그래야 측정하고 손보기 쉽다.

퀀트수학과 통계 모델로 거래 전략을 만드는 사람
백테스트과거 데이터로 전략이나 모델을 돌려 보는 검증
프런티어 모델가장 앞선 성능을 내는 최신 대형 모델
골든 셋Golden set. 정답을 알고 있는 평가용 문제 묶음
포워드 디플로이Forward deploy. 엔지니어가 사용자 팀에 직접 가서 함께 일하는 방식
온프레미스On-prem. 외부 클라우드 대신 회사가 직접 가진 서버에서 돌리는 것
무보존 계약Zero data retention. 모델 업체가 받은 데이터를 저장하지 않기로 한 약속
DMZ네트워크에서 다른 구역과 분리해 둔 구역
추론 게이트웨이Inference gateway. 모든 모델 호출이 지나는 관문. 라우팅, 비용 측정, 기록을 맡는다
에이전트 게이트웨이Agent gateway. 회사의 모든 에이전트를 한 장부에 올려 서로 찾고 부르게 하는 관문
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀
메타 하네스Meta harness. 여러 하네스 위에서 팀 설정을 한곳에 정의하는 층
MCPModel Context Protocol. AI가 외부 도구와 데이터에 접속하는 표준 규약
MCP 도구 검색도구 설명을 처음부터 다 싣지 않고, 필요할 때 찾아서 불러오는 방식
CLICommand-line interface. 명령줄에서 실행하는 도구
컨텍스트모델이 한 번에 읽는 입력 전체. 토큰 수로 잰다
프롬프트 캐시앞부분이 같은 입력을 재사용해 비용과 시간을 줄이는 장치. 앞부분이 바뀌면 깨진다
모델 라우팅Model routing. 요청마다 알맞은 모델로 보내는 것
지식 베이스Knowledge base. 에이전트가 필요할 때 찾아 읽는 정리된 자료 모음
벡터 검색글을 숫자 벡터로 바꿔 뜻이 비슷한 것을 찾는 검색
그래프 데이터베이스항목과 항목 사이의 관계를 중심으로 저장하는 데이터베이스
OpenTelemetry (OTel)프로그램의 실행 기록(로그, 트레이스)을 남기는 업계 표준
시점 조회Point in time. 과거 특정 시점의 데이터 상태로 조회하거나 되살리는 것
스냅샷특정 시점의 상태를 그대로 떠 둔 것
프록시호출을 중간에서 받아 대신 전달하거나 바꿔 주는 장치
