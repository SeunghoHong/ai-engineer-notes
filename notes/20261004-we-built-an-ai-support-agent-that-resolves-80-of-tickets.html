지원 봇을 사지 않고 직접 만들었더니

AssemblyAI에는 하루 약 1,000명이 가입하는데 이들을 맞는 엔지니어는 한 명이었다. 사서 쓴 지원 봇은 문의의 10%만 해결했다. Claude Agent SDK로 직접 만든 지원 에이전트 Joey는 첫 주에 80%를 해결했다.

원본 영상: We Built an AI Support Agent That Resolves 80% of Tickets 발표: Matt Lawler (추정) · AssemblyAI 포워드 디플로이드 엔지니어

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다. 예를 들어 FTE는 FDE로, cloud agent SDK는 Claude Agent SDK로, cloud MD는 CLAUDE.md로 고쳤다. 발표자 이름은 들린 대로 적었다. mm:ss는 영상 위치다.

3분 요약
  1. AssemblyAI에는 하루 약 1,000명이 API에 가입한다. 이들을 맞는 온보딩 엔지니어는 최근까지 한 명이었다.
  2. 사서 쓴 지원 봇은 문의의 10%만 끝까지 해결했다. 프롬프트, 도구, 검색 구조를 고칠 수 없어 개선도 못 했다.
  3. Claude Agent SDK로 Joey를 직접 만들었다. 문서를 Markdown 파일로 넣고, 임베딩 검색과 파일 탐색을 함께 쓴다.
  4. 고치는 속도가 핵심이다. 지침 파일을 고쳐 PR을 머지하면 약 30초 뒤 새 버전이 뜬다.
  5. 첫 주에 해결률이 80%가 됐다. 비용은 월 약 700달러다. 모든 문의가 Joey를 거치고 20%만 사람에게 간다.
  6. Joey가 사람에게 넘기는 일의 목록이 곧 다음에 자동화할 일의 목록이다.
  7. 오늘 할 일: FDE라면 자기 일을 자동화하고, 고객이 만드는 제품을 직접 만들어 본다. Joey의 음성 모드가 그 실천이다.
01

하루 1,000명, 담당자는 1명 01:10

AssemblyAI는 음성 AI 인프라 회사다. 음성을 글로 바꾸는 음성 인식 speech-to-text 기반 모델을 직접 학습시킨다.

  • 나중에 처리하는 용도: 회의 녹음 같은 것이다. Fireflies 같은 회의 기록 봇이 대표적이다.
  • 실시간 용도: 전화 상담 에이전트나 드라이브스루 주문 같은 음성 에이전트다.
  • 음성 에이전트 API: 음성 인식, LLM, 음성 합성을 한 번에 이어 준다.

발표자에 따르면 지금 음성 AI 수요는 폭발적이다. AssemblyAI에는 하루 약 1,000명이 API에 가입한다. 그런데 발표 이틀 전까지 온보딩 엔지니어는 발표자 한 명뿐이었다.

FDE가 하는 일 02:40

발표자의 직함은 FDE Forward Deployed Engineer다. 회사마다 뜻이 다른 넓은 직함이다. 핵심은 고객 곁에 붙어 일하는 것이다.

  • 고객의 사용 사례를 깊이 이해하고, 고객에게 꼭 필요한 것을 만든다.
  • 고객의 저장소에 코드를 직접 커밋하는 일이 많다.
  • 고객과 한 달에 여러 번, 많게는 한 주에 여러 번 만난다.
  • 기술과 영업 양쪽의 주 연락 창구다. 계약을 따내고 신뢰를 쌓는 책임도 진다.

좋은 서비스 방식이지만 규모를 늘릴 수 없다. 하루 1,000명의 가입자와 일일이 통화할 수는 없다. 고객이 늘 때마다 FDE를 계속 뽑을 수도 없다. 발표자는 사람이 직접 이끌어야 하는 계약에 시간을 쓰고 싶었다.

자기 일을 자동화해서 없애라. 그게 FDE가 매일 할 일이다.발표자의 표현을 옮김 04:00

고객 경험을 넓게 좋게 만들려면 FDE 자신이 병목이 되면 안 된다는 뜻이다.

02

기성 봇은 10%에서 멈췄다 04:10

처음 반응은 많은 팀과 같았다. "대화를 덜 받자." 그래서 기성 지원 봇 off-the-shelf support bot을 사서 문서에 연결했다. 쉬운 문서 질문은 이제 봇이 다 답할 거라고 기대했다.

결과는 끝까지 해결률 end-to-end resolution rate 약 10%였다. 하루 1,000건이면 100건은 봇이 끝냈다. 나머지 900건은 여전히 팀이 맡아야 했다.

1,000은 하루 API 가입 수다. 대화도 하루 1,000건이라는 것은 발표자가 설명하려고 같은 크기로 가정한 것이다.

고칠 수 없는 봇 05:00

더 큰 문제는 개선 속도였다. 시스템 프롬프트 system prompt에 손댈 수 없었다. 도구도, RAG 구조도 마찬가지였다. 바꾸고 싶은 게 생겨 판매사에 물으면 "로드맵에 있습니다"라는 답이 돌아왔다. 그래서 직접 만들기로 했다.

사서 쓴 봇문서에 연결만 한 기성 지원 봇프롬프트, 도구, 검색을 못 고친다. 해결률 약 10%
→
직접 만든 봇Claude Agent SDK로 만든 Joey모든 부분을 직접 고치고 30초 만에 배포한다. 해결률 약 80%
03

Joey: 뽑지 않고 만든 팀원 05:10

팀원을 한 명 더 뽑는 대신 만들었다. 이름은 Joey다.

  • 사이트 채팅 창, 영업 문의, 지원 메일 주소 중 어디로 연락하든 먼저 Joey를 만난다.
  • Joey는 AssemblyAI로 들어오는 모든 대화의 첫 창구다.
  • Joey는 지원팀의 일원이라 고객 지원 플랫폼 Pylon을 쓴다. 대화를 관리하고, 고객과 지난 대화를 기억한다.
  • 팀은 Joey의 성과 지표도 Pylon에서 본다.

발표자는 Joey를 "끝없이 늘릴 수 있는 FDE"로 만들려 했다고 말한다.

Claude Agent SDK 위에 만든 이유 05:50

Joey는 Claude Agent SDK로 만들었다. 그래서 보통 채팅봇보다 FDE에 가깝게 일한다.

  • 자기 파일 시스템이 있다.
  • 고객을 위해 코드를 쓰고 디버깅한다.
  • 도구를 부른다.
  • 자기 인프라를 다루고, 스스로 새 능력을 붙인다.
04

Joey의 구조 06:10

발표자는 Claude와 일해 봤다면 알듯 "Markdown이 친구"라고 말한다. 회사에 대한 모든 것을 Markdown 파일로 주면 Claude가 잘 이해한다. Joey의 구조는 네 부분으로 나뉜다.

부분하는 일얻는 것
1. Markdown 문서문서 사이트를 Markdown 파일로 바꿔 Joey의 파일 시스템에 둔다. 문서를 고치면 파일도 자동으로 바뀐다문서 사이트가 내려가도 최신 내용으로 답한다
2. 임베딩 검색Voyage의 임베딩으로 질문과 가장 관련 있는 문서를 먼저 가져온다오래 찾지 않고 빨리 답한다
3. 파일 탐색헷갈리거나 여러 자료를 엮어야 하면 파일 시스템을 직접 뒤진다깊이 생각해야 하는 질문에도 답한다
4. Railway 배포저장소에 변경을 머지하면 새 버전이 자동으로 뜬다서버 사양이나 EC2를 신경 쓰지 않는다

임베딩 검색과 파일 탐색을 함께 쓰는 점이 눈여겨볼 곳이다. 쉬운 질문은 임베딩으로 빨리 답한다. 어려운 질문은 에이전트가 파일을 직접 열어 보며 찾는다. 이것을 에이전트형 검색 agentic search이라고 한다.

고치는 속도가 곧 품질 07:30

  1. Slack에서 Joey가 고객과 나눈 나쁜 대화를 발견한다.
  2. 지침이나 코드를 고치는 PR을 쓴다.
  3. 머지하면 약 30초 뒤 새 버전이 뜬다.
  4. 그 뒤의 모든 대화에 고친 내용이 적용된다.

실제 대화를 지켜보다 버그를 잡고, 그 대화가 끝나기 전에 고친 버전을 배포한 적도 있다. 고객은 그 사실을 몰랐다. 기성 봇과 가장 크게 다른 점은 모든 것을 팀이 직접 제어한다는 것이다.

저장소에서 다시 본 구조 11:00

  • 문서뿐 아니라 변경 기록 changelog과 가격 페이지도 Markdown으로 바꿔 넣는다. 새 기능을 내면 Joey도 바로 안다.
  • 파일마다 원래 URL을 같이 둔다. Joey가 답에 출처 링크를 붙이고, 고객은 그걸로 답을 확인한다.
  • Joey의 행동 지침은 CLAUDE.md 한 파일에 있다. 발표자 기억으로는 약 3만 줄이다. 고객을 대하는 방법과 가드레일 guardrail이 들어 있다.
  • Joey가 틀린 답을 하면 주로 이 CLAUDE.md를 고친다.
  • 전체를 Dockerfile로 묶어 컨테이너로 Railway에 올린다. 배포를 사람이 지켜볼 필요가 없다.

Voyage는 발표자가 협력사라고 소개한 곳이다. 발표자는 Railway도 높이 칭찬했다. 다른 서비스와 비교한 내용은 발표에 없다.

05

10%에서 80%로 08:00

배포 첫 주에 끝까지 해결률이 10%에서 80%가 됐다. 발표자는 이것이 "꽤 단순한 구현"으로 낸 결과라고 말한다.

비용은 토큰과 인프라를 합쳐 월 약 700달러다.

골라서 잰 80%가 아니다 08:20

어떤 회사는 특정 유형의 티켓만 골라 해결률을 잰다. 발표자는 여기는 다르다고 강조한다.

  • 사람에게 바로 연결되는 길이 없다.
  • 사람과 이야기하려면 Joey에게 넘겨 달라고 해야 한다.
  • 그래서 Joey가 들어오는 문의의 100%를 받는다.
  • 그중 20%만 사람에게 넘긴다.

사람의 일이 900건에서 200건으로 줄면 4.5분의 1이다. 해결률이 8배 오른 것보다, 사람이 맡는 양이 얼마나 줄었는지가 팀에게는 더 와닿는 숫자다.

80%와 월 700달러는 AssemblyAI가 자기 시스템을 직접 잰 값이다. "해결"을 어떻게 판정했는지는 발표에서 자세히 밝히지 않았다. 이 점을 감안해 읽자.

06

못 하는 일이 다음 할 일 08:40

Joey가 사람에게 넘기는 20%는 "올바른 이유"로 넘긴 것이라고 발표자는 말한다. 지금은 사람이 필요하지만 언젠가 자동화할 수 있는 일들이다.

  • 요금 조정 rate change
  • 데이터 사용 거부 data opt-out
  • 계약서 서명
  • FDE나 법무팀이 꼭 끼어야 하는 요구
넘긴 목록 = 팀의 확장 계획 08:50 Joey가 아직 못 하는 일은 팀이 다음에 무엇을 해야 하는지 분명히 알려 준다. 사람에게 넘긴 문의를 모으면 그대로 자동화 순서표가 된다.
BAA 요청

Joey가 BAA(의료 정보 처리 계약서)를 보내지 못했다.

해결: BAA 링크를 참고 자료로 Joey에게 준다.

가격 상담 09:10

Joey가 가격 이야기를 하지 못했다.

해결: 이제 필요한 사용 시간을 말하면 Joey가 요율을 제시한다. 고객은 Joey와 가격을 협상할 수 있다.

발표자는 자동화할 일이 아직 많이 남았다고 덧붙인다.

07

Joey에게 목소리를 09:20

발표자가 Joey로 정말 시험하고 싶었던 것은 도그푸딩 dogfooding이다. 자기 회사 제품을 직접 써 보는 일이다.

  • 문의를 덜 받게 해 주는 봇만 만들고 싶지는 않았다.
  • 누구나 만들 수 있는 평범한 지원 봇도 원하지 않았다.
  • AssemblyAI의 고객은 음성 에이전트를 만든다. 그래서 발표자도 음성 에이전트를 만들었다.

발표가 있던 주에 Joey에 음성 에이전트 API를 붙였다. 사이트에서 음성 모드로 바꾸면 말로 Joey와 대화한다. 전화번호도 곧 연결할 계획이라고 했다.

음성 에이전트 API의 구성 10:20

항목발표자의 설명
연결웹소켓 WebSocket 연결 하나로 말이 들어가고 말이 나온다
처리 순서음성 인식 → LLM → 음성 합성. 모두 음성용으로 맞췄다
대화 처리말 사이의 멈춤, 말 끊고 들어오기 barge-in를 API가 알아서 처리한다
목소리자체 목소리를 제공한다. 음성 업체를 따로 찾지 않아도 된다
도구텍스트로 대화할 때와 같은 도구를 그대로 쓴다

음성 에이전트 API는 발표자 회사의 제품이다. 실시간, 낮은 지연 시간 같은 설명은 제품 소개로 감안해 읽자.

08

데모: BAA 질문 12:10

데모는 발표자의 컴퓨터에서 시뮬레이션으로 했다. 청중이 발표 뒤 Joey를 시험할 테니, 실제 지원팀 대기열을 늘리지 않으려는 것이다.

누가무엇을 말했나 (요약)
발표자앰비언트 의료 기록 ambient medical scribe 앱을 만들려 한다. 시험 전에 BAA에 서명해야 하는데 Joey가 해 줄 수 있나?
Joey잠깐 확인하겠다고 한 뒤 답한다. 표준 HIPAA BAA는 고객이 바로 직접 진행할 수 있다.
단, 카드가 등록된 유료 계정이 먼저 있어야 한다.
BAA에 서명하면 모델 학습 사용에서 자동으로 빠진다.
관련 문서 링크를 채팅에 붙여 준다.

앞에서 사람에게 넘기는 일로 꼽은 계약 문의를 이 데모에서는 Joey가 혼자 처리했다.

2년 전과 비교 13:40

발표자가 2년 전 지원팀에 들어왔을 때 이 질문은 사람이 답해야 했다. 지원 엔지니어가 바로 못 보면 고객은 기다렸다. 답도 정해진 문구였다. 지금은 기본 질문을 24시간 내내 물을 수 있다. 말로도 물을 수 있다.

한 겹 위의 효과 14:10 음성 에이전트 만드는 법을 Joey에게 말로 묻는 순간, 고객은 이미 그 API를 쓰고 있다. 자기가 만들 제품이 어떤 경험이 될지 질문하면서 직접 본다.
09

고객이 만드는 것을 만들어라 14:20

발표자가 남기고 싶은 말은 "Joey를 만들라"만이 아니다. FDE라면 자기 회사 제품을 늘 직접 써 봐야 한다.

  • 고객에게 시작하는 법만 가르쳐서는 부족하다.
  • 새 기능과 새 제품은 직접 만들어 본 경험으로 가르쳐야 한다.

발표자도 Joey에 음성을 붙이며 고객과 같은 벽에 부딪혔다. 지연 시간, 말할 차례 주고받기 turn-taking, 말 끊기 처리다. 고객이 쓰는 바로 그 API로 실제 서비스를 내보내 봤다. 그래서 고객의 처지를 더 잘 이해하고 더 나은 조언을 줄 수 있게 됐다.

발표자가 제안하는 오늘 할 일 15:20 고객이 도움을 청할 때까지 기다리지 않는다. 고객이 만드는 것과 똑같은 제품을 직접 만든다. 그 과정에서 Joey처럼 고객 경험까지 함께 좋아질 수 있다.

"음성 에이전트라면 AssemblyAI로 만들라"는 마지막 권유는 회사 홍보다. 도그푸딩이라는 핵심 주장은 어느 회사 제품에도 적용된다.

10

핵심 정리

  1. 하루 약 1,000명이 가입하면 사람이 하나하나 맞을 수 없다. FDE 방식은 그대로는 규모를 못 늘린다.
  2. 발표자는 FDE가 매일 할 일이 자기 일을 자동화하는 것이라고 본다.
  3. 기성 봇은 10%만 해결했고, 내부를 고칠 수 없어 개선도 막혔다.
  4. Joey는 Claude Agent SDK 위에 만든 에이전트다. 파일 시스템, 도구, 코드 실행을 쓴다.
  5. 문서는 Markdown 파일로 자동 동기화하고, URL을 함께 둬 출처를 단다.
  6. 검색은 임베딩으로 먼저 찾고, 모자라면 파일을 직접 뒤진다.
  7. 약 3만 줄의 CLAUDE.md를 고쳐 30초 만에 배포한다. 고치는 속도가 곧 품질이다.
  8. 첫 주 해결률 80%, 월 약 700달러. 모든 문의가 Joey를 거치고 20%만 사람에게 간다.
  9. 사람에게 넘긴 문의 목록이 다음 자동화 목록이다.
  10. 고객이 만드는 제품을 직접 만들어 봐야 고객을 제대로 돕는다. Joey의 음성 모드가 그 실천이다.
11

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1AssemblyAI가 지원 에이전트를 새로 만들어야 했던 배경은?
하루 약 1,000명이 API에 가입하는데 온보딩 엔지니어는 발표 이틀 전까지 한 명이었다. FDE가 고객을 하나하나 맡는 방식은 이 규모로 늘릴 수 없다.
Q2기성 지원 봇의 해결률은? 왜 개선하지 못했나?
약 10%. 시스템 프롬프트, 도구, RAG 구조에 손댈 수 없었다. 판매사는 "로드맵에 있다"고만 했다.
Q3Joey 구조의 네 부분은?
Markdown 문서, Voyage 임베딩 검색, 파일 시스템 탐색, Railway 배포.
Q4문서를 로컬 Markdown 파일로 두면 무엇이 좋은가?
문서가 바뀌면 자동으로 같이 바뀐다. 문서 사이트가 내려가도 최신 내용으로 답한다. 파일마다 URL을 둬서 답에 출처를 붙일 수 있다.
Q5임베딩 검색이 있는데 파일 탐색을 왜 또 쓰나?
임베딩은 관련 문서를 먼저 빨리 가져온다. 헷갈리거나 여러 자료를 엮어야 할 때는 에이전트가 파일을 직접 뒤져서 찾는다.
Q6Joey가 틀린 답을 하면 팀은 어떻게 고치나?
주로 CLAUDE.md(약 3만 줄의 지침)를 고치는 PR을 머지한다. Railway가 약 30초 안에 새 버전을 띄우고, 이후 모든 대화에 적용된다. 진행 중인 대화에 반영한 적도 있다.
Q780%가 골라서 잰 수치가 아니라고 말한 근거는?
사람에게 바로 가는 길이 없다. 모든 문의가 Joey를 거치고, Joey가 넘긴 20%만 사람에게 간다. 일부 유형만 골라 잰 해결률이 아니다.
Q8Joey가 지금도 사람에게 넘기는 문의는? 그 목록은 어떻게 쓰나?
요금 조정, 데이터 사용 거부, 계약서 서명, FDE나 법무가 필요한 요구. 이 목록을 다음에 자동화할 일의 순서로 쓴다. BAA 링크 제공과 가격 협상이 그 예다.
Q9Joey에 음성을 붙인 진짜 이유는?
자기 회사 제품을 직접 써 보기 위해서다. 고객이 음성 에이전트를 만드니, 같은 것을 직접 만들어 봐야 고객을 이해할 수 있다.
Q10데모에서 Joey가 알려 준 BAA 조건은?
고객이 바로 직접 진행할 수 있다. 카드가 등록된 유료 계정이 먼저 있어야 한다. 서명하면 모델 학습 사용에서 자동으로 빠진다.
Q11발표자가 음성 에이전트를 만들며 부딪힌 벽은?
지연 시간, 말할 차례 주고받기, 말 끊기 처리. 고객과 같은 벽을 겪어 봐서 더 나은 조언을 줄 수 있게 됐다.
