실행 중에 스스로 도구를 만드는 에이전트

도구가 하나도 없는 에이전트도 파일 편집, 셸, 도구 불러오기 세 가지만 주면 필요한 도구와 하위 에이전트를 실행 중에 직접 만들어 쓴다. 스스로 코드를 쓰고 지울 수 있는 만큼 평가와 가드레일이 함께 있어야 한다.

원본 영상: Agents That Write Their Own Tools at Runtime 발표: Sandhya Subramani (AWS)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 알려진 이름으로 바로잡았다(Strand → Strands Agents, claw code → Claude Code, matter tooling → meta tooling, hotel → OTel). mm:ss는 영상 위치다.

3분 요약
  1. 코딩 도구가 도구를 만드는 건 새롭지 않다. 새로운 건 운영 중인 에이전트가 멈추지 않고 필요한 도구를 직접 만들어 바로 쓰는 것이다.
  2. 이 방식을 메타 툴링이라 부른다. 시스템 프롬프트에 좋은 도구의 모양을 적고, 도구는 편집기, 셸, 도구 불러오기 세 개만 준다.
  3. 데모에서 도구가 0개인 에이전트가 계산기와 글자 수 세기 도구를 그 자리에서 만들어 썼다. 재시작은 없었다.
  4. 같은 방식으로 하위 에이전트도 만든다. 하와이 여행 요청에 항공, 활동, 일정 에이전트 셋을 만들어 불렀다.
  5. 에러가 나면 자기 도구와 에이전트를 고치는 자기 치유로 이어진다고 발표자는 말한다. 이 부분은 시연하지 않았다.
  6. 스스로 코드를 쓰고 지울 수 있으니 평가 8가지와 가드레일 4가지가 필요하다. 첫째는 생성된 코드가 도는 환경의 격리다.
  7. 발표자에 따르면 Strands는 도구 만들기, 에이전트 만들기를 거쳐 자기 소스 코드 고치기까지 왔다.
01

실행 중에 만든다는 것 00:00

Claude Code나 Cursor 같은 코딩 도구도 도구를 직접 쓴다. 발표자는 그 점을 먼저 인정하고 질문을 바꾼다. 실행 중에 자기 코드를 고치는 에이전트는 몇이나 되나.

운영 중인 서비스에서 무언가 실패하면 보통은 사람이 나선다. 발표자가 바라는 건 에이전트가 문제를 스스로 알아채고, 필요한 도구나 에이전트를 직접 써서 고치는 것이다.

지금까지개발 중에 도구를 만든다운영 중 에러가 나면 서비스를 내리고, 코딩 도구로 고친 뒤 다시 올린다

02

데모: 빈 에이전트가 도구를 만든다 01:30

발표자는 데모부터 보여 줬다. agents.py에는 시스템 프롬프트와 도구 3개만 있다. 도구를 담는 tools 폴더는 비어 있다. 이대로라면 이 에이전트가 혼자 할 수 있는 일은 없다.

  1. 에이전트를 실행해 둔다. 이후의 일은 모두 이 실행 안에서 일어난다. 02:10
  2. "복잡한 수식을 계산해 줘"라고 한다. 에이전트는 수학 계산기 math calculator 도구를 만든다. 최솟값, 최댓값 같은 기능이 여럿 들어 있다. 02:20
  3. 어떤 수의 제곱을 묻는다. 에이전트는 방금 만든 도구를 불러 답한다. 다시 실행하지 않았다. 03:10
  4. "내 단어의 글자 수를 세 줘"라고 엉뚱한 요청을 한다. 에이전트는 먼저 가진 도구로 되는지 확인한다. 맞는 게 없자 글자 수 세기 character counter 도구를 새로 만든다. 03:40
  5. 아무렇게나 친 문자열에 28자라고 답한다. 발표자는 검증하려고 세 글자를 넣어 다시 확인한다. 04:20
데모에서 볼 점 만든 도구를 재시작 없이 바로 쓴다. 새로 만들기 전에 기존 도구로 되는지 먼저 확인한다. 사용자는 "도구를 만들어"라고 말하지 않았다.
03

메타 툴링과 Strands Agents 05:00

발표자는 이 방식을 메타 툴링 meta tooling이라 부른다. 도구를 만드는 도구를 에이전트에게 준다는 뜻이다.

구현에는 Strands Agents를 썼다. AWS가 만들어 오픈소스로 공개하고 관리하는 에이전트 하네스 agentic harness다. 하네스는 모델을 감싸 도구와 실행 흐름을 정해 주는 틀이다.

발표자가 꼽은 Strands의 특징 06:10

  • 모델을 바꿔 끼운다. 더 좋은 모델이 나와도 시스템 프롬프트와 구조는 그대로 두고 모델만 바꾼다.
  • 그래서 같은 구조에서 모델끼리 성능을 비교하기 쉽다.
  • MCP와 A2A를 지원한다. 여러 모델 제공자를 쓸 수 있다.
  • AWS가 관리하는 기본 도구와 커뮤니티가 쓴 도구가 있다.

다섯 줄로 시작하기 06:40

가장 단순한 에이전트는 Agent와 shell 도구를 불러와 만든다. 셸이 첫 도구인 이유는 에이전트가 자기 위치를 알아야 하기 때문이다. 어느 폴더에서 무엇을 실행 중인지, 코드가 어디 있는지 알게 된다. 이 상태로 "무엇을 할 수 있니?"라고 물으면 자기 환경을 살펴보고 답한다.

발표자는 AWS 소속이고, Strands는 AWS가 만들어 관리하는 프레임워크다. 프레임워크의 장점에 대한 설명은 이 점을 감안해 읽자.

04

재료: 시스템 프롬프트 하나, 도구 셋 07:30

메타 툴링에 필요한 건 시스템 프롬프트 하나와 도구 세 개다. 에이전트 설정은 한 줄이면 된다.

재료하는 일
시스템 프롬프트좋은 도구가 어떻게 생겼는지, 어디에 저장하는지 알려 준다
editor도구 파일을 쓰고 고친다
shell지금 어디서 실행 중인지, 폴더에 무엇이 있는지 보여 준다
load_tool새로 생긴 도구 파일을 실행 중에 불러와 바로 쓰게 한다

실행 중에 불러오기 08:10

처음에는 에이전트 설정의 load_tools_from_directory=True가 이 일을 했다. 도구 폴더에 새로 생긴 파일을 실행 중에 바로 쓰게 하는 옵션이다. 나중에 Strands 팀은 이 기능을 도구 하나로 떼어 냈다. 그게 load_tool이다.

시스템 프롬프트에 적는 것 08:40

  • 역할: 실행 중에 직접 도구를 만들어 쓰는 메타 툴링 에이전트라고 알려 준다.
  • 도구 템플릿: 도구 파일의 생김새를 보여 준다. @tool 데코레이터 decorator를 붙여야 도구로 인식된다.
  • 도구 명세 tool spec: 도구가 갖춰야 할 형식을 적는다.
  • 규칙: 파일을 어디에 쓸지 정한다. 만들기 전에 같은 도구가 있는지 확인하고, 없을 때만 새로 쓴다.

예시 코드: 발표 설명을 바탕으로 다시 쓴 것이다. 발표 화면의 코드와 같지 않다. 실제 이름과 인자는 Strands 문서로 확인한다.

# 예시: 메타 툴링 에이전트 설정
from strands import Agent
from strands_tools import editor, shell, load_tool

SYSTEM_PROMPT = """You are a meta-tooling agent that creates and uses custom tools at runtime.
Tool template: every tool is a Python function with the @tool decorator.
Save new tools in ./tools/.
Before writing a tool, check whether one already exists. Write a new one only if it does not."""

agent = Agent(system_prompt=SYSTEM_PROMPT, tools=[editor, shell, load_tool])
# 예시: 에이전트가 써 넣을 법한 도구 파일 tools/character_counter.py
from strands import tool

@tool
def character_counter(text: str) -> int:
    """Count the number of characters in text."""
    return len(text)
05

왜 쓰나: 운영 중에 막힌 요청 09:50

발표자가 든 예는 국내선 항공권 예약 앱이다. 한 사용자가 인도에서 홍콩 가는 표를 원한다. 에이전트는 그런 일을 하도록 만들어지지 않았다.

보통의 대응
  • 에이전트가 포기하거나 에러를 낸다
  • 엔지니어링 팀에 넘긴다
  • 고쳐서 돌아오기까지 2주가 걸린다
메타 툴링
  • 에이전트가 무엇이 모자란지 알아챈다
  • 필요한 도구를 직접 만든다
  • 그 자리에서 요청을 처리한다

2주는 발표자가 든 가상의 예다.

남는 질문 즉석에서 만든 도구로 항공권을 예약해도 괜찮을까. 발표 후반의 평가와 가드레일이 이 질문에 대한 발표자의 답이다.
06

에이전트를 만드는 에이전트 10:40

도구를 쓰는 에이전트는 하위 에이전트 sub-agent도 쓸 수 있다. 하위 에이전트는 큰 일을 나눠 맡는 작은 에이전트다. 발표자는 에이전트를 엮는 패턴을 셋으로 나눈다.

패턴발표자의 설명
스웜 swarm하위 에이전트들이 병렬로 함께 일한다. 일을 나눠 각자 한 부분씩 맡는다
그래프 graph한 에이전트의 결과가 다음 에이전트로 넘어간다. 이렇게 일을 넘기는 것을 핸드오프 handoff라 한다
워크플로 workflow둘을 섞는다. 병렬 그룹, 노드, 그래프가 한 흐름 안에 함께 있다

이 구조는 사람이 짤 수도 있다. 발표자의 요점은 에이전트가 직접 짤 수도 있다는 것이다.

07

데모: 하와이 여행 계획 11:50

두 번째 데모도 구조는 같다. 도구 3개에 설정 한 줄이다. 에이전트 폴더는 거의 비어 있다. 달라진 건 시스템 프롬프트다. 도구 템플릿 자리에 에이전트 템플릿을 넣었다. 일을 하위 에이전트 2~4개로 나누라고 했고, 스웜 같은 복잡한 구조는 쓰지 않게 했다.

  1. "하와이에 가는데 일정 짜 줘"라고만 한다. 에이전트를 만들라는 말은 없다. 실제 고객도 문제만 말하고 알아서 풀어 주길 바란다. 12:40
  2. 에이전트가 항공, 활동, 일정 하위 에이전트 셋을 만든다. 편집기 도구를 세 번 부른다. 13:10
  3. 만든 에이전트들을 불러 주요 공항, 좋은 해변, 할 일을 알려 준다. 14:00
한계: 실시간 정보 13:30 이 데모는 실시간 정보를 못 가져온다. 실제 API에 접근하는 도구를 주지 않았기 때문이다. 발표자는 그런 도구가 있으면 날씨를 물었을 때 최신 날씨를 가져오는 도구를 직접 쓸 거라고 말한다.
08

고장 나면 스스로 고친다 14:20

발표자는 에이전트 시스템을 만드는 데서 멈추지 말자고 한다. 자기 치유 self-healing 코드도 생각해야 한다. 에이전트가 자기 코드를 살펴 버그를 찾고 고치는 것이다.

발표자가 긴 세션에서 겪은 일을 들려준다. 청중이 엉뚱한 요청을 하면 에이전트가 망가진다. 에러가 쏟아지고 말이 끝없이 길어진다. 발표자는 최대 토큰을 정해 둬야겠다고 덧붙였다. 14:40

그래도 에이전트는 자기가 에러를 내고 있다는 걸 알아챈다. 그리고 문제가 된 도구나 에이전트를 직접 고친다. 요구가 바뀌어도 같다. "하와이 말고 다른 곳으로"라고 하면 에이전트 정의를 고친다. 15:00

시연으로 보여 준 것
  • 빈 폴더에서 도구를 만든다
  • 만든 도구를 재시작 없이 쓴다
  • 기존 도구가 있는지 먼저 확인한다
  • 하위 에이전트 셋을 만들어 부른다
말로만 설명한 것
  • 에러를 알아채고 스스로 고친다
  • 운영 환경에 배포해 쓴다
  • 평가와 샌드박스를 적용한다
  • Python 버전이 TypeScript 버전을 썼다

발표 시간이 짧아 자기 치유는 시연하지 않았다. 이 방식이 실제로 얼마나 안정적인지는 이 발표만으로 판단하기 어렵다.

09

평가: 무엇을 확인해야 믿을 수 있나 15:20

큰 힘에는 큰 책임이, 아니 더 큰 책임이 따른다.발표자의 표현을 옮김

에이전트가 스스로 움직이니 평가 eval가 필요하다. 평가는 결과 품질을 재는 테스트 묶음이다. 발표자는 Strands에 평가가 8가지 들어 있다고 말한다. 수준별로 나누면 이렇다.

확인할 것수준발표 속 예
1. 목표를 이뤘나세션 전체"항공권 예약해 줘"라고 했으면 실제로 예약됐나
2. 도움이 되는 답인가한 번의 응답"잔액이 얼마야?"에 "500달러"처럼 기대한 형태로 답했나
3. 지어내지 않았나한 번의 응답그 500달러가 실제 잔액인가
4. 맞는 도구를 골랐나도구 사용답에 이르기까지 엉뚱한 도구를 쓰지 않았나
5. 맞는 인자를 넣었나도구 사용계좌 ID가 정말 123인가
6. 전체 결과가 원하는 대로인가멀티 에이전트최종 결과와 응답이 의도와 맞나
7. 순서가 맞나멀티 에이전트도구와 하위 에이전트를 맞는 순서로 불렀나
8. 주고받은 메시지가 괜찮나멀티 에이전트에이전트끼리 오간 메시지의 품질

이 여덟 가지를 모으면 세션 안의 대화를 처음부터 끝까지 들여다볼 수 있다. 그래야 에이전트를 믿고 권한을 줄 수 있다.

발표자는 "8가지"라고 했지만 항목을 빠르게 말로 이어 갔다. 위 번호는 정리하며 발표 설명을 여덟 개로 나눠 본 것이다.

10

가드레일: 망가뜨리지 않게 17:00

평가만으로는 부족하다. 도구와 에이전트를 만들 수 있으면 고치고 지울 수도 있다. 공들여 만든 코드와 데이터를 지우게 둘 수는 없다. 그래서 가드레일 guardrail이 필요하다. 가드레일은 에이전트가 하면 안 되는 일을 막는 제한 장치다.

가드레일내용
1. 실행 환경 격리에이전트를 컨테이너 하나에 가두는 흔한 샌드박스와 다르다. 생성된 코드가 실행되는 환경 자체를 격리한다. 그래야 다른 실행 환경을 건드리지 않고, 엉뚱한 곳에 쓰거나 지우지 않는다. 발표자에 따르면 Strands가 몇 주 전 이 기능을 냈다. 17:20
2. 도구와 권한 제한에이전트가 쓸 수 있는 도구와 권한을 좁힌다
3. 접근 제한누가 에이전트에게 물을 수 있는지, 어떤 종류의 질문을 받을지 정한다
4. 관측평가 결과, OTel, 텔레메트리 데이터를 모아 둔다. 관측 가능성 observability이 있어야 이 시스템을 믿을 수 있다고 말할 수 있다

발표자는 네 가지라고 했지만 도구, 권한, 접근, 관측을 한 문장에 이어 말했다. 위 묶음은 정리하며 나눈 것이다.

만들 수 있으면 지울 수도 있다 도구를 만드는 권한은 코드를 고치고 지우는 권한이기도 하다. 에이전트가 쓴 코드는 사람 검토 없이 바로 실행된다. 그래서 그 코드가 닿을 수 있는 범위를 먼저 좁혀야 한다.
11

Strands가 걸어온 길 18:40

발표자는 이 흐름을 자기 개선 self-improving, 자기 진화 self-evolving 에이전트의 시작으로 본다. Strands가 거쳐 온 단계는 셋이다. 19:10

  1. 에이전트가 자기 도구를 만든다
  2. 에이전트가 하위 에이전트를 만든다
  3. 에이전트가 자기 소스 코드를 고친다

발표자가 들려준 뒷이야기도 있다. Strands는 3년 전 AWS 내부용으로 시작했다. 쓸모가 커서 오픈소스로 공개했다. Python 버전을 먼저 만들었고, 그 Python 버전의 Strands가 TypeScript 버전을 스스로 썼다고 한다. 19:30

3년 전 시작과 TypeScript 버전 작성은 모두 발표자의 말이다. 사람이 얼마나 개입했는지는 발표에서 설명하지 않았다. 발표자 회사의 제품 이야기이므로 감안해 읽자.

발표자의 결론 평가, 가드레일, 관측이 갖춰지면 이런 시스템을 믿고 만들 수 있다. 고장 나면 실행 중에 고치고, 처음 배운 것보다 많은 일을 해내는 에이전트 시스템이다.
12

핵심 정리

  1. 메타 툴링은 에이전트에게 도구를 만드는 도구를 주는 방식이다.
  2. 코딩 도구와의 차이는 시점이다. 개발 중이 아니라 실행 중에 도구를 만들고 재시작 없이 쓴다.
  3. 재료는 시스템 프롬프트 하나와 도구 셋, editor, shell, load_tool이다.
  4. 시스템 프롬프트에는 도구 템플릿, 도구 명세, 저장 위치, "있으면 재사용, 없을 때만 새로" 규칙을 적는다.
  5. load_tool이 새로 생긴 도구 파일을 실행 중에 불러온다. 처음엔 load_tools_from_directory 옵션이 그 일을 했다.
  6. 템플릿을 에이전트용으로 바꾸면 하위 에이전트를 만든다. 엮는 패턴은 스웜, 그래프, 워크플로다.
  7. 쓰임새는 운영 중 처음 보는 요청이다. 2주짜리 수정 대신 에이전트가 그 자리에서 해결한다.
  8. 자기 치유는 발표자가 설명했지만 시연하지는 않았다.
  9. 평가 8가지는 세션 목표, 응답의 쓸모와 사실성, 도구 선택과 인자, 멀티 에이전트의 결과·순서·메시지를 본다.
  10. 가드레일 4가지는 실행 환경 격리, 도구·권한 제한, 접근 제한, 관측이다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 이 에이전트와 Claude Code 같은 코딩 도구의 차이는?
실행 중에 도구를 만들어 재시작 없이 쓴다. 운영 중 에러가 나도 서비스를 내리지 않고 스스로 고치는 것을 목표로 한다.
Q2메타 툴링에 쓰는 도구 세 개와 각 역할은?
editor는 도구 파일을 쓴다. shell은 실행 위치와 폴더 내용을 보여 준다. load_tool은 새 도구를 실행 중에 불러온다.
Q3시스템 프롬프트에 무엇을 적나?
메타 툴링 에이전트라는 역할, 도구 템플릿(@tool 데코레이터), 도구 명세, 저장 위치, 기존 도구를 먼저 확인하고 없을 때만 새로 쓰라는 규칙.
Q4데모에서 "글자 수를 세 줘"라고 했을 때 에이전트가 가장 먼저 한 일은?
가진 도구로 할 수 있는지 확인했다. 맞는 도구가 없어서 글자 수 세기 도구를 새로 만들었다.
Q5load_tools_from_directory=True와 load_tool은 어떤 관계인가?
둘 다 폴더에 새로 생긴 도구를 실행 중에 쓰게 한다. 처음엔 에이전트 설정 옵션이었고, 나중에 같은 기능을 도구 하나로 만든 것이 load_tool이다.
Q6국내선 예약 앱 예시가 보여 주려는 것은?
처음 보는 요청(인도에서 홍콩 가는 표)에 막혔을 때, 팀에 넘겨 2주를 기다리는 대신 에이전트가 필요한 도구를 만들어 그 자리에서 해결할 수 있다는 것.
Q7스웜, 그래프, 워크플로는 어떻게 다른가?
스웜은 하위 에이전트들이 일을 나눠 병렬로 함께 한다. 그래프는 한 에이전트의 결과를 다음 에이전트로 넘긴다. 워크플로는 둘을 섞는다.
Q8하와이 데모에서 만든 하위 에이전트와 이 데모의 한계는?
항공, 활동, 일정 에이전트 셋. 실제 API에 접근하는 도구가 없어 실시간 정보는 가져오지 못했다.
Q9"잔액이 얼마야?" 예로 설명한 두 가지 평가는?
답이 기대한 형태로 도움이 되는지, 그리고 그 값이 지어낸 게 아니라 실제 잔액인지.
Q10발표자가 말하는 실행 환경 격리는 흔한 샌드박스와 무엇이 다른가?
에이전트를 컨테이너 하나에 가두는 게 아니라, 생성된 코드가 실행되는 환경 자체를 격리한다. 그래서 다른 환경을 건드리거나 엉뚱한 곳을 지우지 못한다.
Q11이 발표에서 시연하지 않고 말로만 설명한 것은?
에러를 알아채고 스스로 고치는 자기 치유, 운영 환경 배포, 평가와 샌드박스 적용, Python 버전이 TypeScript 버전을 쓴 일.

용어뜻
메타 툴링Meta tooling. 에이전트에게 도구를 만드는 도구를 줘서 필요한 도구를 스스로 만들게 하는 방식
런타임Runtime. 프로그램이 실제로 실행 중인 때. 개발 단계와 구별한다
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀
Strands AgentsAWS가 만들어 오픈소스로 공개한 에이전트 하네스
도구Tool. 에이전트가 불러 쓸 수 있는 함수
데코레이터Decorator. Python에서 함수 위에 @이름을 붙여 기능을 덧붙이는 문법. Strands는 @tool로 도구를 표시한다
하위 에이전트Sub-agent. 큰 일을 나눠 맡는 작은 에이전트
핸드오프Handoff. 한 에이전트가 다음 에이전트에게 일을 넘기는 것
자기 치유Self-healing. 에러를 스스로 알아채고 고치는 것
MCPModel Context Protocol. 모델을 외부 도구와 데이터에 연결하는 표준 규약
A2AAgent2Agent. 에이전트끼리 통신하는 규약
평가 (eval)모델이나 에이전트의 결과 품질을 재는 테스트 묶음
트레이스Trace. 요청 하나를 처리하며 거친 단계를 기록한 것
가드레일Guardrail. 에이전트가 하면 안 되는 일을 막는 제한 장치
샌드박스Sandbox. 바깥과 격리된 실행 환경
관측 가능성Observability. 시스템 안에서 무슨 일이 일어나는지 기록으로 알 수 있는 정도
OTelOpenTelemetry. 트레이스, 지표, 로그를 모으는 오픈 표준
텔레메트리Telemetry. 실행 기록을 자동으로 모은 데이터
