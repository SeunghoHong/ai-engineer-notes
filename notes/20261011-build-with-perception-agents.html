가리키면 고치고, 눈으로 확인하는 에이전트

Amazon AGI Lab은 화면을 클릭만 하지 않고 사람처럼 이해하는 '지각 에이전트'를 만든다. 이 워크숍은 공개된 두 도구를 이어, 웹페이지에 피드백을 찍으면 코딩 에이전트가 고치고 브라우저 에이전트가 결과를 확인하는 흐름을 만든다.

원본 영상: Build with Perception Agents 발표: Emile Baizel (Amazon AGI Lab 솔루션 아키텍트 팀 리드), Shruti Arora (같은 팀 솔루션 아키텍트) Bee 연동 시연: Giovanni (Bee 팀)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 제품 이름(Nova Act, Claude Code, Bee)은 알려진 이름으로 바로잡았고, 확실하지 않은 이름에는 (추정)을 붙였다. 청중 이름은 들린 대로 적었다. mm:ss는 영상 위치다.

3분 요약
  1. Amazon AGI Lab은 에이전트를 협업, 지각, 신뢰성 세 관점으로 만든다. 기준은 "50%만 동작하는 에이전트는 동작하지 않는 것"이라는 고객의 말이다.
  2. 첫 제품 Nova Act는 자연어로 브라우저 작업을 대규모로 돌리는 AWS 서비스다. 양식 입력, 검색과 추출, 쇼핑, QA에 주로 쓰인다.
  3. 화면을 클릭하는 컴퓨터 사용은 절반이다. 나머지 절반은 화면을 사람처럼 이해하는 것이다. 이걸 하는 게 지각 에이전트다.
  4. 오픈소스로 공개한 두 도구가 있다. 비주얼 애노테이션은 화면에 찍은 피드백을 JSON과 프롬프트로 내보낸다. 비주얼 검증은 디자인 기준과 사용자 흐름대로 사이트가 동작하는지 브라우저로 확인한다.
  5. 워크숍에서는 두 도구를 에이전트 브리지로 잇는다. 버튼 한 번에 수정, 검증, 보고서까지 자동으로 돈다.
  6. 입력은 화면 표시만이 아니다. Bee 웨어러블로 회의 대화를 듣고 그대로 수정 요청으로 넘기는 시연도 있었다.
  7. 청중 데모의 공통점은 검증 단계가 "했다"는 말을 증거로 바꿔 준다는 것이다.
01

랩 소개와 세 가지 관점 01:10

Amazon AGI Lab은 연구와 제품을 함께 하는 팀이다. Emile Baizel은 "스타트업의 속도에 Amazon의 규모를 더한 팀"이라고 소개한다. 목표는 지식 노동 에이전트다. 여러 환경을 보고, 따져 보고, 행동해서 실제 업무를 끝내는 에이전트를 말한다. 사무실은 샌프란시스코와 보스턴에 있다.

Emile Baizel이 이끄는 솔루션 아키텍트 팀은 두 가지 일을 한다. 초기 고객이 이 랩의 모델과 제품을 실제 서비스에 올리도록 돕는다. 그리고 고객 현장에서 얻은 피드백을 연구팀이 학습에 쓸 평가eval로 만든다.

에이전트를 보는 세 가지 관점 01:50

협업 · collaboration

에이전트는 블랙박스가 아니라 팀원이어야 한다. 내 목표를 이해하고, 그 목표를 어떻게 이룰지 생각을 나눈다.

이 모든 걸 실제 고객 사례에 맞춰 만든다. 랩은 많은 고객과 가까이 일한다.

지각 · perception 02:30

에이전트는 자기가 일하는 환경을 이해해야 한다. 이 랩에서 환경은 화면이다.

작년에는 브라우저에서 시작했다. 앞으로 모바일 기기와 컴퓨터 전체로 넓힌다.

신뢰성 · reliability 02:50

강화학습reinforcement learning용 시뮬레이션 환경에서 모델을 학습시킨다.

환경은 외부 고객과 Amazon 내부 팀의 실제 업무를 바탕으로 만든다.

에이전트가 50%만 제대로 동작한다면, 그건 동작하지 않는 것이다.Emile Baizel이 인용한 고객의 말

이유는 간단하다. 반만 믿을 수 있는 에이전트는 아예 안 돌리게 된다. 돌리더라도 디버깅에 시간을 쏟느라 에이전트로 얻은 이득이 다 사라진다.

02

첫 제품 Nova Act 03:40

Amazon Nova Act는 이 랩이 작년에 내놓은 첫 제품이다. 브라우저 작업 흐름을 대규모로, 믿을 만하게 돌리는 AWS 정식 서비스다. 자연어로 지시하면 브라우저를 열고, 이동하고, 검색하고, 양식을 채운다.

사람이 필요한 순간에는 사람을 부른다. 경비 보고서 승인이 필요하거나 에이전트가 막혔을 때다. 이렇게 사람이 중간에 끼는 방식을 사람 참여 루프human in the loop라고 한다.

고객이 주로 쓰는 곳 04:10

사용처내용
양식 입력여러 웹사이트에 대량으로 입력한다. 사이트마다 프롬프트나 고정 스크립트를 따로 쓰지 않아도 된다
검색과 추출여러 사이트를 돌며 조사하고 데이터를 모은다
쇼핑발표에서는 이름만 언급했다
QA웹 서비스 품질 검사. 발표에서는 이름만 언급했다

제품 구성 04:50

  • AWS 콘솔: 에이전트가 한 일을 단계별 기록, 즉 궤적trajectory으로 모두 본다. 에이전트가 보고 있던 화면 요소에는 바운딩 박스bounding box가 그려진다.
  • 자체 컴퓨터 사용 모델: 화면을 보고 행동하는 추론을 뒤에서 맡는다.
  • MCP 서버와 스킬: 올해 추가됐다. 다른 에이전트가 Nova Act를 쉽게 불러 쓰게 해 준다. 워크숍에서 쓴다.
  • 사람 참여 루프와 도구 사용
  • 플레이그라운드: Nova Act 홈페이지에서 코드 없이 동작을 직접 볼 수 있다.

발표자들은 Amazon AGI Lab 소속이고 Nova Act는 이 팀의 제품이다. 제품 소개와 신뢰성에 대한 말은 그 점을 감안해 읽자.

03

왜 지각 에이전트인가 05:30

컴퓨터 사용computer use은 에이전트가 화면 위에서 행동하는 방식이다. "오른쪽 구석의 파란 버튼을 눌러"라고 시키면 그 버튼을 누른다. 업무 자동화에는 아주 중요하다.

Emile Baizel은 이게 절반일 뿐이라고 본다. 나머지 절반은 에이전트가 보이는 것을 실제로 이해하는 것이다. 화면을 그냥 클릭할 대상으로만 보지 않는다는 뜻이다.

컴퓨터 사용화면 위에서 행동한다파란 버튼을 찾아 누른다
→
지각 에이전트화면을 이해하고 행동한다이 화면이 무엇이고 어떻게 쓰는지 안다

지각 에이전트가 필요한 세 가지 이유 06:10

  1. 처음 보는 화면도 다룬다. 90년대 말 Yahoo나 Hotmail 메일 화면을 처음 본 사람도 메일 보내는 법은 금방 찾는다. 사람에게는 수천 시간 화면을 써 온 공통 감각이 있다. 에이전트도 화면을 그렇게 이해하게 만드는 게 목표다.
  2. API가 없어도 일한다. 06:50 많은 지식 노동은 API가 없는 화면에서 이뤄진다. 그래서 지금은 사람이 그 일을 한다. 에이전트도 여러 사이트에서 같은 일을 할 수 있어야 한다.
  3. 같은 화면을 보면 협업이 쉬워진다. 07:10 화면을 문단으로 설명할 필요가 없다. 가리키고, 클릭하고, "배경을 빨간색으로"처럼 바꿀 점만 말하면 된다.
04

공개한 기본 도구 두 개 07:40

랩은 지각 에이전트의 기본 부품primitive 두 개를 먼저 오픈소스로 공개했다. 기본 부품은 더 큰 기능을 쌓을 때 쓰는 가장 작은 단위다. 워크숍 전체가 이 둘을 다룬다.

비주얼 애노테이션 · visual annotation

아무 웹페이지에서나 가리키고, 클릭하고, 바꿀 점을 적는다.

  • 다 적으면 내보내기export를 누른다
  • 바꿀 점을 담은 JSON 파일과 프롬프트가 나온다
  • 둘을 코딩 에이전트에 주고 "이대로 고쳐"라고 시킨다

모델이 끼지 않는다. 추론 없이 JSON만 내보내는 결정론적 도구다. 그래서 특정 모델에 묶이지 않는다.

비주얼 검증 · visual verification 08:20

사이트가 정해 둔 기준을 지키는지 확인하는 스킬이다. 코딩 에이전트가 돌린다.

  • 디자인 기준: 지켜야 할 CSS 스타일과 디자인
  • 사용자 흐름: 결제, 로그인처럼 사이트가 지원해야 할 흐름. Gherkin 파일로 적는다
  • 에이전트가 이 둘을 기준으로 사이트를 검사한다

두 도구 모두 오픈소스로 지금 쓸 수 있다.

05

피드백 반영은 왜 느린가 10:00

Shruti Arora는 역할극으로 문제를 보여 준다. 당신은 웹 앱을 만드는 프론트엔드 엔지니어다. 디자인 팀이 준 Figma 파일을 보고 만든다. 자매 팀은 이 페이지에 자기 팀 정보를 넣고 싶어 한다. 다 만드는 데 4~5주가 걸린다.

지금의 피드백 과정 10:50

  1. 3~4주차쯤 팀에게 괜찮은지 봐 달라고 부탁한다.
  2. GitHub 같은 곳으로 코드를 공유한다.
  3. 동료가 로컬에서 서버를 띄워 페이지를 연다.
  4. "제목이 빨간색이면 안 될 것 같다" 같은 피드백을 Slack 메시지나 공유 문서로 보낸다.
  5. 하나씩 읽고 동의하거나, 반대하거나, 절충해서 반영할 목록을 정한다.
  6. 하나씩 고친다.

반영에 걸리는 시간 12:00

방식걸리는 시간
사람이 하나씩 반영약 1주
코딩 에이전트와 함께 반영며칠
피드백을 에이전트에게 바로 넘기고, 끝난 뒤에만 확인몇 시간

Shruti Arora가 말한 대략적 감각이다. 잰 값이 아니다.

핵심 아이디어 피드백을 사람이 옮겨 적지 않고 코딩 에이전트에게 그대로 넘긴다. 사람은 다 고친 뒤에만 들여다본다. 피드백을 모아 에이전트에게 보내고 커피를 마시고 오면, 변경이 다 반영돼 있는 그림이다.
06

비주얼 애노테이터 12:50

비주얼 애노테이터visual annotator는 Chrome 확장 프로그램이다. 웹페이지 위에 바로 피드백을 남긴다. 표시하는 방법은 세 가지다.

방법하는 법
그리기페이지 위에 직접 그린다
요소 고르기버튼이나 제목 같은 화면 요소를 집어서 고른다
핀 꽂기Google 지도에 핀을 꽂듯 위치를 찍고 설명을 단다

표시가 끝나면 두 가지로 쓴다. 파일로 내려받아 고칠 팀에 보낼 수 있다. 아니면 AI가 읽기 좋게 만든 프롬프트를 내 코딩 에이전트에 넘긴다. 이때 "이 코드베이스를 고쳐"라는 지시는 따로 해야 한다.

07

비주얼 검증 스킬 13:30

비주얼 검증은 스킬skill 형태다. 스킬은 코딩 에이전트에 설치하는 지시와 도구 묶음이다. Claude Code에 설치하거나, Kiro에서는 파워Kiro power(추정)로 쓴다.

검증은 디자인 스펙과 사용자 흐름을 기준으로 한다. 색이 맞는지, 글자 크기가 맞는지, 사용자 흐름이 제대로 이어지는지 본다.

스펙이 없으면? 14:10

처음 검증을 돌리면 도구가 사이트를 한 단계 깊이로 훑는다. 이걸 크롤crawl이라고 한다. 어떤 링크와 내용이 있는지 보고, 그걸 바탕으로 사용자 흐름을 Gherkin 문법으로 만든다. 다음 검증부터는 이 흐름을 쓴다.

Gherkin 키워드 (예시)뜻로그인 흐름 예시
Given시작 상태사용자가 로그인 페이지에 있다
When사용자의 행동이메일과 비밀번호를 넣고 로그인 버튼을 누른다
Then기대하는 결과대시보드가 열리고 오른쪽 위에 사용자 이름이 보인다

이 표는 Gherkin을 설명하려고 넣은 예시다. 발표에서 보여 준 파일이 아니다.

검증 데모 15:00

  1. 코딩 에이전트에서 검증 도구를 부른다.
  2. 도구가 디자인 스펙과 사용자 흐름 파일을 읽는다.
  3. 브라우저를 연다.
  4. 사용자 흐름을 하나씩 실제로 따라가 본다.
  5. 결과를 보고서로 만든다.
08

워크숍 과제 15:20

실습은 두 도구를 각각 써 본 뒤, 한 시나리오에서 둘을 이어 붙이는 순서다. Shruti Arora는 지각이 이 두 부품만으로 끝나지 않는다고 말한다. 중요한 건 특정 상황에 맞게 부품을 엮는 법이다.

  • 시나리오 과제: 게임 데이처럼 문제, 목표, 힌트가 주어진다.
  • Bee 팀 시연: 타이핑 대신 다른 방식으로 피드백을 남기는 법을 보여 준다.
  • 보너스 과제: 일찍 끝낸 사람을 위한 선택지 세 가지가 있다.
  • 상품: 무대에서 자기 활용 사례를 데모하거나, 아이디어 투표에서 뽑히면 Bee 기기를 받는다.

워크숍 자료는 GitHub에 있다. "perception agents workshop"으로 검색하면 나온다. 실습에는 Nova Act API 키가 필요하다.

말로 고치기: Bee 연동 31:40

Bee 팀의 Giovanni가 타이핑 없이 피드백을 남기는 방법을 보여 줬다. 디자인 회의에서 고칠 점을 말로 나누기만 하면, 지각 에이전트가 사이트를 고친다.

Bee는 몸에 다는 AI 비서 기기이고, Amazon 제품이다. 마이크가 있어서 버튼을 누르면 대화를 듣는다. 듣는 동안에는 LED가 켜진다. Giovanni의 설명으로는 대화가 개인 클라우드에 저장된다. Bee의 AI 에이전트는 그 대화를 바탕으로 제안을 준다.

연결하는 세 단계 33:40

  1. Bee 기기를 준비한다. 없으면 디자인 대화가 미리 들어 있는 테스트 계정을 쓴다.
  2. Bee CLI를 npm으로 설치한다. 대화 데이터를 가져오는 명령줄 도구다.
  3. 워크숍 서버를 켜고, Bee 대화를 받아 지각 에이전트로 넘기는 브리지를 켠다.

시연 34:20

LED를 켜고 "제목 색을 빨간색으로 바꾸고, 뇌 이모지를 로봇 이모지로 바꾸자"라고 말한다. 화면 오른쪽에 대화 내용과 요점이 뜬다. Bee API의 응답도 패널을 열어 볼 수 있다.

Apply를 누르면 워크숍과 같은 흐름이 돈다. 색과 이모지가 바뀌고, 이어서 Nova Act 검증이 자동으로 돈다. 실제 기기로 하면 대화가 끝나고 반영되기까지 2~3분 걸린다고 한다.

Bee도 Amazon 제품이고 이 워크숍의 상품이었다. 기기 설명은 그 점을 감안해 읽자.

핵심 정리

  1. Amazon AGI Lab은 협업, 지각, 신뢰성 세 관점으로 에이전트를 만든다.
  2. "50%만 동작하는 에이전트는 동작하지 않는 것"이다. 신뢰성이 없으면 이득이 디버깅으로 사라진다.
  3. Nova Act는 자연어로 브라우저 작업을 돌리는 AWS 서비스다. 양식 입력, 검색과 추출, 쇼핑, QA에 쓰인다.
  4. 컴퓨터 사용은 절반이다. 지각 에이전트는 화면을 사람처럼 이해한다. API가 없어도 일하고, 사람과 같은 화면을 보며 협업한다.
  5. 비주얼 애노테이션은 화면에 찍은 피드백을 JSON과 프롬프트로 내보낸다. 모델이 끼지 않는 결정론적 도구다.
  6. 비주얼 검증은 디자인 기준과 Gherkin 사용자 흐름으로 사이트를 브라우저에서 확인한다. 흐름이 없으면 첫 실행 때 크롤해서 만든다.
  7. 피드백 반영 시간은 사람이 하면 약 1주, 에이전트와 하면 며칠, 피드백을 바로 넘기면 몇 시간으로 준다(발표자 추정).
  8. 두 도구 사이엔 다리가 없다. 에이전트 브리지가 표시를 코딩 에이전트에 넘기고 검증까지 돌린다.
  9. 입력은 화면 표시만이 아니다. Bee의 대화나 Jam의 녹화도 같은 흐름에 넣을 수 있다.
  10. 검증 단계가 있으면 에이전트의 "했다"는 말을 보고서라는 증거로 확인할 수 있다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Amazon AGI Lab이 에이전트를 볼 때 쓰는 세 가지 관점은?
협업(블랙박스가 아닌 팀원), 지각(환경인 화면을 이해), 신뢰성(실제 업무 기반 시뮬레이션 환경에서 강화학습).
Q2"50%만 동작하면 동작하지 않는 것"인 이유는?
반만 믿을 수 있으면 아예 안 돌리게 된다. 돌리더라도 디버깅에 시간을 쏟느라 얻은 이득이 다 사라진다.
Q3Nova Act를 고객이 주로 쓰는 네 곳은?
여러 사이트에 대량으로 하는 양식 입력, 검색과 추출, 쇼핑, QA.
Q4컴퓨터 사용과 지각 에이전트는 무엇이 다른가?
컴퓨터 사용은 화면 위에서 행동하는 것이다. 지각 에이전트는 거기에 더해 화면이 무엇이고 어떻게 쓰는지 사람처럼 이해한다.
Q5지각 에이전트가 필요한 세 가지 이유는?
처음 보는 화면도 다룰 수 있다. API가 없는 화면에서도 일한다. 사람과 같은 화면을 보니 가리키고 말하는 것만으로 협업할 수 있다.
Q6비주얼 애노테이션은 무엇을 내보내고, 모델을 쓰나?
바꿀 점을 담은 JSON 파일과 코딩 에이전트용 프롬프트를 내보낸다. 추론을 쓰지 않는 결정론적 도구라 특정 모델에 묶이지 않는다.
Q7비주얼 검증이 확인하는 두 종류의 기준은?
CSS 스타일 같은 디자인 기준, 그리고 결제나 로그인 같은 사용자 흐름. 사용자 흐름은 Gherkin 파일로 적는다.
Q8사용자 흐름 파일이 아직 없으면 어떻게 되나?
첫 검증 때 사이트를 한 단계 깊이로 크롤해 링크와 내용을 보고, 사용자 흐름을 Gherkin으로 만든다. 다음 검증부터 그걸 쓴다.
Q9비주얼 애노테이터로 표시하는 세 가지 방법은?
페이지 위에 그리기, 화면 요소 고르기, 지도처럼 핀 꽂기.
Q10에이전트 브리지는 왜 필요하고, 무엇을 하나?
Chrome 확장에서 코딩 에이전트로 프롬프트를 보낼 길이 없기 때문이다. 브리지는 표시를 코딩 에이전트에 넘기고, 수정이 끝나면 UI 검증을 돌린다.
Q11워크숍에서 고친 두 파일은 각각 무엇을 위한 것인가?
manifest.json은 확장이 localhost와 통신하도록 권한을 연다. content.js에는 Apply changes 버튼, SDK 기반 검증, 보고서 생성 코드를 붙인다.
Q12오리 팟캐스트 데모에서 검증 보고서가 의미 있었던 이유는?
AI는 "했다"고 말해도 실제로는 안 한 경우가 많다. 검증 보고서가 변경이 정말 적용됐다는 걸 확인해 줬다.

비주얼 애노테이션Visual annotation. 웹페이지 위에 직접 표시하고 바꿀 점을 적는 것
비주얼 검증Visual verification. 디자인 기준과 사용자 흐름대로 사이트가 동작하는지 브라우저로 확인하는 것
GherkinGiven, When, Then 형식으로 사용자 흐름을 평범한 문장으로 적는 문법
결정론적Deterministic. 같은 입력이면 늘 같은 결과가 나오는 것. 모델 추론이 끼지 않는다
추론Inference. 학습된 모델을 실제로 돌려 답을 얻는 것
사람 참여 루프Human in the loop. 승인이나 막힌 곳에서 사람이 중간에 끼어드는 방식
궤적Trajectory. 에이전트가 한 단계씩 무엇을 했는지 남긴 기록
바운딩 박스Bounding box. 화면 요소를 둘러싼 사각형 표시
강화학습Reinforcement learning. 시도하고 보상을 받으며 배우는 학습 방식
MCPModel Context Protocol. 에이전트가 외부 도구에 접속하는 표준 방식
스킬Skill. 코딩 에이전트에 설치하는 지시와 도구 묶음
에이전트 브리지Agent bridge. Chrome 확장의 표시를 코딩 에이전트에 넘기고 검증까지 이어 주는 연결 프로그램
크롤Crawl. 사이트의 링크를 따라가며 페이지를 훑는 것
host_permissionsChrome 확장이 요청을 주고받을 수 있는 주소 목록
인수 조건Acceptance criteria. 기능이 완성됐다고 인정하는 기준
