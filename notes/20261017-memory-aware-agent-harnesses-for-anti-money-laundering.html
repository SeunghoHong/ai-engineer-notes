모델이 아니라 하네스를 만든다

프론티어 모델은 바꿀 수 없지만, 모델을 감싸는 하네스는 우리가 전부 설계한다. 은행의 자금세탁 감시 에이전트를 예로 삼아, 메모리 층과 에이전트 루프와 스킬 검색으로 컨텍스트 윈도우를 작게 유지하는 방법을 다룬다.

원본 영상: Memory-Aware Agent Harnesses for Anti-Money Laundering 발표: Nacho Martinez (Oracle, AI 개발자 애드보킷 · 데이터 과학자)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 앞 30분은 이론 강의, 뒤 20분은 실습 안내와 질의응답이다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 것만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 모델은 프론티어 랩이 만들고 우리는 손댈 수 없다. 같은 모델이라도 하네스가 다르면 성능이 달라진다. 그래서 하네스가 지금 가장 재미있는 주제다.
  2. 하네스는 모델이 원래 갖고 있지 않은 세 가지를 만들어 준다. 기억, 도구 사용, 인식. 사람으로 치면 데이터베이스, 손발, 감각이다.
  3. 컨텍스트 윈도우는 작을수록 문제를 잘 푼다. 광고된 한도 안에서도 토큰이 쌓일수록 정확도가 떨어진다. 요약과 압축으로 줄인다.
  4. 기억은 단기와 장기로 나눈다. 장기 기억은 다시 에피소드 기억, 절차 기억, 의미 기억으로 나눈다. 처음엔 두 구조만 두고 시작하라.
  5. 스킬 100개를 전부 컨텍스트에 넣으면 한도를 넘는다. 도구와 스킬을 벡터로 바꿔 두고 필요할 때 가장 가까운 3개만 꺼낸다.
  6. 파일과 데이터베이스는 경쟁 관계가 아니다. 여러 에이전트가 같은 파일에 쓰는 문제는 데이터베이스가 30년 전에 ACID로 해결한 일이다.
  7. 워크숍의 결과물은 은행 거래를 24시간 감시하며 의심 거래를 차단하지 않고 표시만 하는 에이전트다. 최종 판단은 사람이 한다.
01

모델이 아니라 하네스 03:50

발표자는 OpenAI가 수천 개의 에이전트를 띄워 오래 풀리지 않던 수학 문제를 풀었다는 소식을 예로 든다. 이런 에이전트는 결론에 이르기까지 사람이 전혀 끼지 않는다. 10시간, 100시간을 혼자 돌아야 한다.

그런데 큰 언어 모델 LLM 자체에는 그런 능력이 없다. 컨텍스트 윈도우는 유한하고, 기억 장치는 모델에 내장돼 있지 않다. 긴 자율 작업을 가능하게 하는 부품은 전부 우리가 모델 바깥에 만들어 붙여야 한다.

발표의 전제 프론티어 모델에 집중할 필요가 없다. 모델은 가져다 쓰면 된다. 우리가 바꿀 수 있고 점점 더 깊이 손댈 수 있는 부분은 하네스 harness다. 그래서 워크숍은 하네스를 만든다.
02

시나리오: 은행 자금세탁 감시 05:00

청중에 금융권 사람이 많다는 말을 듣고 발표자는 워크숍 소재를 은행으로 바꿨다. 중간 규모 은행에 의심스러운 거래가 자주 들어오고, 그 거래는 다섯 가지 유형으로 분류된다.

예를 들어 어떤 계좌에 100만 달러가 들어온 뒤 사흘 동안 현금 인출기에서 5만 달러씩 빠져나간다. 큰돈을 넣고 바로 잘게 흩어 뽑는 행동은 자금세탁 방지 AML, Anti-Money Laundering 관점에서 수상하다.

에이전트가 할 일은 이런 거래를 자율적으로 판단하거나 적어도 표시해 두는 것이다. 목표는 은행 직원이 거래를 들여다보는 시간을 줄이는 것이다. 사람을 대신해 계좌를 막는 것이 아니다.

AI 앱의 네 가지 모양 07:40

  1. LLM 챗봇: 가장 쉽다. 모델에 말을 걸 수 있게 한 것
  2. RAG 앱: 발표자 표현으로는 "그럴싸하게 꾸민 벡터 검색"
  3. LLM 주도 워크플로: 자동화를 준다
  4. AI 에이전트: 자율성을 준다

우리가 매일 쓰는 Claude Code, Codex, Pi, OpenClaw, Hermes Agent 같은 시스템은 3번과 4번의 결합이다. 발표자는 이를 에이전틱 시스템이라 부른다. 자동화와 자율성을 합친 것이다.

발표자가 짚은 모순 엔지니어들은 이런 에이전틱 시스템을 매일 쓴다. 그런데 자기 AI 앱을 만들 때는 챗봇이나 RAG로 끝낸다. 자기가 소비하는 방식으로 자기 앱을 만들지 않는다. 워크숍은 그 간극을 메우려 한다.

  • 모델: 어느 모델을 부를 것인가

파일인가 데이터베이스인가 13:10

최근 큰 논쟁이 있었다. 한쪽은 "전부 파일에 넣으면 한 달 뒤 에이전트가 저절로 좋아진다"고 하고, 다른 쪽은 데이터베이스 최대주의자다.

발표자가 청중에게 물었다. 여러 에이전트가 같은 파일에 동시에 쓸 때 요즘 에이전트는 어떻게 피하나. 답은 워크트리 git worktree다. 그런데 이건 우회책이다. 파일은 동시 쓰기가 들어오면 어느 쓰기가 먼저인지, 수정 전에 읽은 쪽은 어떻게 하는지 같은 일관성 문제를 안고 있다.

지금의 우회책에이전트마다 워크트리를 따로 판다파일 충돌을 피하기 위해 작업 공간을 복제한다
→
30년 전에 해결된 답ACID 쓰기원자성, 일관성, 격리성, 지속성이 보장되면 동시 쓰기 문제가 사라진다

결론은 양자택일이 아니다. 파일은 비정형 데이터를 대량으로 담는 데 훌륭하다. 데이터베이스는 다른 종류의 일에 맞다. 경우에 따라 둘을 골라 쓰고, 바퀴를 다시 발명하지 말라.

발표자는 Oracle 소속이고 스스로 "데이터베이스 사람"이라고 말한다. 워크숍도 Oracle 데이터베이스와 Oracle 클라우드 위에서 돈다. 데이터베이스를 권하는 대목은 그 점을 감안해 읽자.

단기 기억과 장기 기억 15:50

메모리 층은 에이전트가 정보를 쓰고, 다듬고, 때맞춰 불러오게 하는 모든 장치다. 어떤 종류로 나눌지는 엔지니어가 정한다. 발표자가 제안하는 구분은 이렇다.

단기 기억

컨텍스트 윈도우 자체다. 대화가 끝나면 사라진다. 새 대화는 0에서 시작한다. 용량이 작아서 모든 걸 담을 수 없다.

장기 기억 · 세 갈래
  • 에피소드 기억 episodic: 일어난 일. 지난 대화, 도구 호출 기록, 대화 요약
  • 절차 기억 procedural: 하는 법. 스킬, 그리고 스킬을 순서대로 묶은 워크플로
  • 의미 기억 semantic: 말하지 않은 것. 사용자가 누구인지, 선호, 좋아하는 프레임워크
09

컨텍스트는 작을수록 좋다 17:50

왜 전부 단기 기억에 넣지 못하나. 용량이 작기 때문만은 아니다. 어텐션 행렬이 커질수록 모델 성능이 나빠진다. 어텐션 행렬은 사실상 컨텍스트 윈도우다. 모든 모델이 그렇다.

발표자가 인용한 연구에 따르면, 컨텍스트가 0토큰일 때와 이미 25만 6천 토큰이 쌓였을 때는 같은 문제의 정답률이 크게 다르다. 지금 한도가 100만 토큰인 건 KV 캐시 덕분이다. 광고된 한도를 넘겨 계속 밀어 넣으면 성능이 "끔찍하게" 떨어진다.

컨텍스트 윈도우가 작을수록 문제를 더 잘 푼다. 사람이 생각할 수 있는 모든 종류의 문제에 적용된다.발표자의 말을 옮김 18:50

줄이는 두 가지 방법 19:00

컨텍스트 요약

모델에게 지금까지 말한 것을 짧게 요약해 달라고 한다. 다음 대화는 그 요약에서 시작한다.

압축 compaction

대화 덩어리를 데이터베이스나 파일에 ID를 붙여 저장한다. 나중에 필요하면 ID와 오프셋으로 그 부분만 다시 읽어 온다. 파일을 읽는 것과 비슷하다.

툴박스와 스킬박스 20:50

발표자는 스킬을 이미 100개쯤 설치해 두었다고 한다. 스킬 하나가 3천에서 5천 토큰이다. 전부 컨텍스트에 넣으면 광고된 한도를 금방 넘고, 실제 대화에 쓸 자리가 남지 않는다.

해법: 도구와 스킬을 벡터로 바꾼다 21:20

  1. 도구와 스킬 각각에 대해 벡터 임베딩을 만들어 벡터 저장소에 넣는다. 도구용 저장소와 스킬용 저장소를 따로 둔다
  2. 에이전트 루프가 도구나 스킬이 필요해지면 벡터 유사도 검색을 한다
  3. 가장 관련 있는 것만 꺼내 컨텍스트에 올린다
  4. 문제를 풀고 나면 다시 내려놓는다

도구 사용은 아주 흔하다. bash 명령 하나, 디렉터리 이동 하나가 모두 도구 호출이다. 발표자에 따르면 어떤 경우에는 컨텍스트 윈도우의 절반 이상이 도구와 스킬이 차지한다. 그 크기를 늘 의식하라는 것이 요점이다.

예를 들어 프런트엔드 작업에서 잘 먹힌 색 조합 선호를 스킬로 남겨 둔다. 스킬은 임베딩돼 있으니, 다음에 "그때 그 색 스타일"이라고만 말해도 에이전트가 그 스킬을 알아서 고른다. 이렇게 루프가 컨텍스트를 조립할 때 알맞은 스킬을 스스로 찾는 것을 동적 스킬 발견이라 부른다.

  2. 개발자 지시: 이 앱에 특화된 지시
  3. 사용자 요청: 우리가 채팅창에 치는 것. 세 번째다
  4. 도구와 스킬: 가장 가볍다. 요청 맨 아래에 붙는다. 꽂았다 뺐다 하는 자리로 생각하라 34:30

이 계층 덕분에 모델이 어떤 것에 더 집중할지 정할 수 있다. 질의응답에서 "에피소드 기억이 지난 대화와 혼동되지 않나"라는 질문이 나왔을 때도 발표자의 답은 같았다. 얼마나 무게를 줄지 설계자가 정하고, 중요한 기억이면 원문 대신 벡터로 저장해 꺼내라.

발표자는 이 기능을 "시맨틱 캐시"라고 불렀다. 설명한 동작, 즉 앞부분이 같은 요청을 다시 계산하지 않는 것은 보통 프롬프트 캐시 또는 프리픽스 캐시라고 부른다. 의미가 비슷한 질문의 답을 재사용하는 시맨틱 캐시와는 다른 기능이다.

  • 임베딩은 사람이 읽는 설명 뒤에 숨은 의미까지 담는다. 차원은 최소 384에서 1,000 이상이다
  • 그래서 하이브리드 검색으로 간다. 의미 검색(임베딩)과 키워드 검색을 합치는 방법으로 발표자는 RRF Reciprocal Rank Fusion를 든다. 계산은 조금 늘지만 둘 중 하나만 쓸 때보다 검색 품질이 좋다

처음부터 만들 것인가. 발표자는 그렇다고 답한다. 그래야 필요 없는 90%를 걷어낼 수 있다. 모든 것은 결국 채팅 완성 API chat completions API 위에 올라간다. 모델과 통신하는 부분을 하네스의 플러그인 하나로 보면, 작을수록 좋다는 원칙이 분명해진다. 49:30

핵심 정리

  1. 모델은 못 바꾼다. 하네스는 전부 우리가 설계한다. 같은 모델도 하네스에 따라 결과가 달라진다.
  2. 하네스가 채우는 세 가지는 기억, 도구 사용, 인식이다. 사람의 기억, 손발, 감각에 해당한다.
  3. 우리가 손댈 수 있는 곳은 데이터 층이다. 에이전트 루프, 게이트웨이와 MCP, 메모리 층, 컨텍스트 엔지니어링, 도구와 스킬.
  4. 컨텍스트는 작을수록 좋다. 한도 안에서도 토큰이 쌓이면 정확도가 떨어진다. 요약과 압축으로 줄인다.
  5. 기억은 단기(컨텍스트 윈도우)와 장기로 나누고, 장기는 에피소드·절차·의미로 나눈다. 처음엔 두 구조만.
  6. 스킬 하나가 3천~5천 토큰이다. 도구와 스킬을 임베딩해 두고 가장 가까운 3개만 꺼낸다. 리랭커로 1개까지 좁힐 수 있다.
  7. 지난 실행에서 SKILL.md를 뽑아 스킬박스에 넣는 것이 스킬 증류다. 모델을 안 건드리고 좋아지는 길이다.
  8. 지시 계층은 시스템 프롬프트, 개발자 지시, 사용자 요청, 도구·스킬 순이다. 요청의 약 80%는 도구와 문서다.
  9. 파일과 데이터베이스는 각자 맞는 일이 있다. 동시 쓰기는 ACID가 30년 전에 해결했다.
  10. 큰 하네스를 다시 만들지 말고, 문제를 작게 잘라 작은 맞춤 하네스를 만든다. 자율 작업에는 자동 압축과 긴 인내가 기본값이다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 프론티어 모델 대신 하네스에 집중하라고 한 이유는?
모델은 프론티어 랩이 만들어 우리가 손댈 수 없다. 하네스는 우리가 전부 설계할 수 있고, 같은 모델도 하네스에 따라 성능이 달라진다.
Q2하네스가 모델에 붙여 주는 세 가지와 그 사람 비유는?
기억(데이터베이스, 뇌의 기억), 도구 사용(손발), 인식(눈과 귀 같은 감각). 추론만 모델이 맡는다.
Q3LLM 챗봇, RAG, LLM 주도 워크플로, AI 에이전트 중 Claude Code 같은 도구는 어디에 속하나?
워크플로(자동화)와 에이전트(자율성)의 결합이다. 발표자는 이를 에이전틱 시스템이라 부른다.
Q4컨텍스트 윈도우를 전부 채우지 말라는 이유는 용량 때문만인가?
아니다. 어텐션 행렬이 커질수록 성능이 나빠진다. 0토큰에서 시작할 때보다 25만 6천 토큰이 쌓였을 때 정답률이 떨어지고, 광고된 한도를 넘기면 급격히 나빠진다.
Q5컨텍스트 요약과 압축의 차이는?
요약은 모델이 짧은 요약을 만들어 다음 대화의 시작점으로 쓴다. 압축은 대화 덩어리를 ID를 붙여 저장해 두고, 필요할 때 ID와 오프셋으로 그 부분만 다시 읽는다.
Q6장기 기억의 세 갈래와 각각의 예는?
에피소드 기억(지난 대화, 도구 호출 기록, 요약), 절차 기억(스킬, 워크플로), 의미 기억(사용자가 누구인지, 선호, 좋아하는 프레임워크).
Q7스킬 100개를 전부 컨텍스트에 넣으면 왜 문제인가? 해법은?
스킬 하나가 3천~5천 토큰이라 합치면 30만~50만 토큰이다. 한도를 넘거나 대화할 자리가 없다. 스킬과 도구를 임베딩해 벡터 저장소에 두고, 필요할 때 유사도 검색으로 가장 가까운 3개만 꺼낸다.
Q8여러 에이전트가 같은 파일에 쓰는 문제의 현재 우회책과 발표자가 말한 근본 해법은?
우회책은 git 워크트리다. 근본 해법은 데이터베이스가 30년 전에 해결한 ACID 트랜잭션이다. 파일과 데이터베이스는 각자 맞는 일에 쓴다.
Q9지시 계층에서 가장 무거운 것과 가장 가벼운 것은?
가장 무거운 것은 시스템 프롬프트, 가장 가벼운 것은 도구와 스킬이다. 사용자 요청은 세 번째다.
Q10요청의 80%가 도구와 스킬인데 비용이 그만큼 안 드는 이유는?
제공자가 직전 요청과 같은 앞부분을 캐시에서 꺼내 다시 계산하지 않는다. 발표자는 이를 시맨틱 캐시라 불렀지만 일반적으로 프롬프트 캐시라 부르는 기능이다. 없었다면 네다섯 배 비쌌을 것이라고 한다.
Q11메모리 층을 처음 설계할 때 발표자의 첫 권고는?
단순하게. 단기와 장기 두 구조만 두고, 남길 가치가 있는 것을 원문 텍스트로 장기 기억에 승격한 뒤 벡터로 바꾼다. 루프의 관찰과 추론 사이에 기억 떠올리기 단계를 하나 끼운다.
Q12데이터베이스 앞에 MCP를 두면 무엇이 좋아지나?
에이전트가 매번 SQL을 새로 지어내 틀리는 대신, 미리 만들어 검증한 질의만 쓰게 할 수 있다. SQL 엔진은 열다섯 가지쯤이고 문법이 미묘하게 다르다.
Q13워크숍의 자금세탁 감시 에이전트는 의심 거래를 발견하면 무엇을 하나?
계좌를 막지 않는다. 의심 거래를 목록에 표시하고 보고서를 만들어 사람이 나중에 검토하게 한다. 조사 시간을 줄이는 것이 목적이다.

컨텍스트 윈도우모델이 한 번에 읽을 수 있는 입력 전체. 발표자는 단기 기억이자 주의력에 비유한다
어텐션 행렬모델이 입력 토큰 사이의 관계를 계산하는 표. 컨텍스트가 길어질수록 커지고 성능이 떨어진다
KV 캐시이미 처리한 토큰의 중간 계산을 저장해 긴 컨텍스트를 감당하게 하는 장치
압축Compaction. 대화 덩어리를 ID와 함께 저장해 두고 필요할 때 일부만 다시 읽는 방법
에피소드 · 절차 · 의미 기억일어난 일 · 하는 법 · 말하지 않은 전제. 장기 기억의 세 갈래
의미 층Semantic layer. 명시되지 않았지만 상황이 전제하는 맥락을 모델에 주는 층
벡터 임베딩글의 의미를 수백에서 수천 개의 숫자로 바꾼 것. 거리를 재서 비슷한 것을 찾는다
리랭커Reranker. 검색으로 뽑은 후보 몇 개를 다시 정밀하게 순위 매기는 모델
하이브리드 검색 · RRF의미 검색과 키워드 검색 결과를 합치는 방법. RRF는 두 순위를 합산하는 공식
스킬 증류Skill distillation. 지난 실행에서 잘 된 방법을 뽑아 재사용 가능한 스킬로 남기는 것
지시 계층Instruction hierarchy. 시스템 프롬프트, 개발자 지시, 사용자 요청, 도구 순으로 무게가 다른 것
프롬프트 캐시앞부분이 같은 요청을 다시 계산하지 않고 재사용하는 기능. 발표자는 시맨틱 캐시라 불렀다
ACID원자성, 일관성, 격리성, 지속성. 데이터베이스 트랜잭션이 보장하는 네 성질
워크트리Git worktree. 한 저장소에서 작업 디렉터리를 여러 개 두는 기능. 에이전트 간 파일 충돌 회피에 쓰인다
MCPModel Context Protocol. 에이전트에 외부 도구와 데이터를 표준 방식으로 연결하는 규약
LoRALow-Rank Adaptation. 모델 가중치 일부만 작게 추가 학습하는 미세 조정 기법
채팅 완성 APIChat completions API. 메시지 목록을 보내고 모델의 다음 메시지를 받는 표준 호출 방식
OCIOracle Cloud Infrastructure. 워크숍의 모델과 데이터베이스가 도는 Oracle 클라우드
