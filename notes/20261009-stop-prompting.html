프롬프트를 멈추고 규칙을 남겨라

에이전트에게 같은 실수를 몇 번이고 지적하고 있다면, 그건 프롬프트로 풀 문제가 아니다. 기계로 판별할 수 있는 기준은 린터로, 판단이 필요한 기준은 정책과 리뷰 에이전트로 저장소에 남겨 두자는 발표다.

원본 영상: Stop Prompting 발표: Greg Pstrucha (Sentry AI 엔지니어, 디버깅 에이전트 Seer의 인프라 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 사례와 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 바로잡았다(Seer, ast-grep, extend_schema 등). 확실하지 않은 이름에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트에게 실수를 지적하면 "맞습니다" 하고 고친다. 하지만 컨텍스트 압축이 일어나면 같은 실수로 돌아온다.
  2. 발표자의 주장은 하나다. 프롬프트로 반복하지 말고, 지켜야 할 규칙을 저장소에 코드로 남겨라.
  3. 결정적 검사는 테스트, 엄격한 타입, 린터 세 가지다. 발표는 이 중 린터에 집중한다.
  4. 에이전트는 기억이 없고, 린터는 에이전트가 싸게 써 준다. 예전에는 손해였던 린터 만들기가 이제 이득이다.
  5. 오늘 할 일: 지난 대화 기록과 리뷰 코멘트를 에이전트에게 읽혀 반복된 지적을 린트 규칙으로 바꾼다.
  6. 린트로 못 잡는 질적 기준은 정책으로 쓴다. 정책마다 서브에이전트가 리뷰하게 하고, 모두 통과한 뒤에 사람이 읽는다.
  7. 커버리지 같은 숫자를 목표로 주면 에이전트는 숫자만 올리고 쓸모없는 테스트를 만든다.
01

같은 지적의 무한 반복 00:40

발표자는 Sentry의 AI 엔지니어다. Sentry의 디버깅 에이전트 Seer를 돌리는 인프라를 맡고 있다.

AI가 쓴 코드를 아직 읽느냐는 질문에 발표자의 답은 "상황에 따라"다. 실제 서비스가 깨지면 안 되는 Sentry 코드는 읽는다. 개인 프로젝트는 한 줄씩 읽지 않고 넘어가기도 한다.

문제는 나중에 그 코드를 고치러 다시 열었을 때다. 지나치게 방어적인 코드와 아무것도 확인하지 않는 테스트가 가득하다. 더는 손대고 싶지 않은 코드베이스가 된다.

지적하고, 고치고, 잊어버린다 01:20

  1. 에이전트에게 실수를 지적한다. "너무 복잡하다. 너무 방어적이다. 하는 일마다 엔드포인트를 만들지 마라. 그걸 영원히 유지해야 한다."
  2. 에이전트가 "맞습니다(You're absolutely right)" 하고 고치기 시작한다.
  3. 5분쯤 지나 컨텍스트 압축 compaction이 일어난다. 대화가 길어져 앞부분이 요약되는 것이다.
  4. 지적한 내용이 사라지고 원점으로 돌아간다. 같은 말을 다시 해야 한다.

발표자는 이런 실수가 대부분 아주 기초적인 것이라고 말한다. 가드레일 guardrail이 없으면 계속 나온다. 가드레일은 에이전트가 벗어나지 못하게 정해 둔 제약이다. 슬라이드에 옮긴 실제 대화 기록에서 욕을 많이 지워야 했다고 한다.

02

프롬프트 대신 규칙 02:20

발표의 주장은 하나다. 프롬프트를 멈추고, 에이전트가 따라야 할 규칙을 코드로 남겨라.

지금까지같은 지적을 프롬프트로 반복한다컨텍스트가 압축되면 다시 처음부터
→
앞으로규칙과 정책을 저장소에 남긴다에이전트가 잊어도 저장소가 기억한다

남길 규칙에는 두 가지가 담겨야 한다. 하나는 팀의 관례 convention다. 다른 하나는 자랑스럽게 내놓을 만한 코드 품질의 기준이다.

발표자는 제목을 일부러 자극적으로 지었다고 밝혔다. 사람 대신 루프를 설계하자는 "루프 엔지니어링" 이야기가 아니라, 그보다 한 단계 더 들어간 이야기라고 했다.

03

결정적 검사 세 가지 02:40

발표자가 청중에게 물었다. 결정적 검사 deterministic check를 더하라고 하면 무엇이 떠오르나. 결정적 검사는 같은 코드에 항상 같은 결과를 내는 검사다. 청중은 평가 eval와 훅 hook을 답했다.

발표자는 둘 다 중요하다고 했다. 평가는 테스트와 같은 부류다. 훅은 검사를 알맞은 때 돌리는 장치다. 그보다 먼저 갖출 것으로 세 가지를 꼽았다.

검사하는 일
테스트코드가 기대대로 동작하는지 확인한다
엄격한 타입 strict typing코드가 가질 수 있는 값과 상태를 좁힌다
린터 linter코드를 실행하지 않고 읽어서 금지한 패턴을 찾아낸다
엄격한 타입만으로는 부족하다 03:20 타입 검사를 켜도 느슨한 타입 표현을 막지 않으면, 원하지 않는 상태도 코드로 표현할 수 있다. 앱에서 표현할 수 있는 상태는 에이전트가 결국 만들어 낸다. 그래서 그런 상태를 아예 표현할 수 없게 막아야 한다.

발표는 이 셋 중 린터에 집중한다. 03:50 린터는 저장소에서 없애고 싶은 것을 결정적인 규칙으로 적어 두는 방법이다.

04

린터의 손익이 바뀌었다 04:00

린터 자체는 오래된 도구다. 그런데 팀이 직접 규칙을 만드는 경우는 드물었다. 들이는 비용에 비해 얻는 게 분명하지 않았기 때문이다.

AI 이전 · 코드를 쓰는 건 사람
  • 린터를 만드는 데 품이 많이 든다
  • 만든 뒤에도 계속 유지해야 한다
  • 그 문제가 얼마나 자주 나오는지 따져 봐야 한다

예: 3주에 한 번 "디자인 시스템 컴포넌트를 써 주세요"라고 말하는 정도면 린터까지는 필요 없다. 사람은 한두 번 들으면 기억한다.

지금 · 코드를 쓰는 건 에이전트 04:50
  • 에이전트는 기억이 없다
  • 같은 실수를 몇 번이고 반복한다
  • 린터는 에이전트에게 시키면 싸고 쉽게 만들어진다

말로 하면 잊지만, 린터는 매번 같은 결과로 막는다. 이제는 린터를 만드는 쪽이 이득이다.

05

지난 피드백을 린터로 05:10

발표자가 "이 발표에서 하나만 가져간다면"이라며 권한 일이다. 발표가 끝나면 노트북을 열고 에이전트에게 이렇게 시켜 보라고 했다.

  1. 지난 에이전트 대화 기록 transcript을 모두 읽게 한다.
  2. GitHub 리뷰 코멘트를 읽게 한다. 리뷰 봇의 지적과 동료의 지적을 모두 넣는다.
  3. 그중 결정적이고 질 좋은 린트 규칙이 될 수 있는 것을 고르게 한다.
  4. 고르는 기준은 하나다. 지금까지 프롬프트로 몇 번이고 다시 말해 온 문제를 잡아내는가.

발표자는 이 일을 이제 정기적으로 돌린다. 아직 규칙으로 잡지 못한 새 문제가 생겼는지 보기 위해서다.

예시 요청문 (발표 내용을 바탕으로 만든 예시) "최근 대화 기록과 이 저장소의 PR 리뷰 코멘트를 읽어 줘. 내가 반복해서 지적한 것을 모아 줘. 그중 코드만 보고 기계적으로 판별할 수 있는 것을 골라 린트 규칙 초안으로 만들어 줘. 판별이 애매한 것은 따로 목록으로 남겨 줘."
06

Sentry의 API 린트 규칙 05:50

커스텀 린트 규칙 custom lint rule은 저장소의 관례를 잡아내는 규칙이다. 오래전부터 써 온 단순한 종류가 있다.

  • 특정 프로젝트에서 console.log를 금지한다
  • 디자인 시스템이나 React 작성 관례를 규칙으로 만든다. 따를 것은 강제하고 피할 것은 막는다

에이전트와 함께라면 더 복잡한 규칙까지 밀어붙일 수 있다.

API 문서와 실제 동작 맞추기 06:40

Sentry는 오래된 코드베이스다. 파이썬 웹 프레임워크 Django와 그 위의 API 라이브러리 DRF Django REST Framework를 쓴다. 모든 곳에 엄격한 타입이 있지는 않다. 오래된 서비스라면 흔한 상황이다.

문제는 어긋남 drift이었다. OpenAPI 스키마 OpenAPI schema와 실제 동작이 자주 달랐다. OpenAPI 스키마는 API가 무엇을 받고 무엇을 돌려주는지 적은 명세다. 그래서 린트 규칙 세 개를 넣었다. 07:10

  1. 응답 타입을 밝힌다. 엔드포인트 함수는 응답 타입을 돌려줘야 한다. 그 안에 Any가 있으면 안 된다. 그래야 실제 타입 정보를 끌어낼 수 있다.
  2. 문서 데코레이터를 붙인다. 엔드포인트에는 @extend_schema 데코레이터가 있어야 한다. 그래야 문서에서 빠지지 않는다.
  3. 타입과 스키마가 일치한다. 함수가 실제로 만드는 타입이 OpenAPI 스키마에 적힌 것과 같아야 한다.

그 결과 API와 문서가 전보다 잘 맞게 됐다.

07

스킬 속 예제 코드도 린트한다 07:40

Seer는 Sentry의 디버깅 에이전트다. Sentry에 쌓인 텔레메트리 telemetry를 보고 문제의 근본 원인을 분석한다 RCA, root cause analysis. 그래서 Sentry API를 많이 부른다.

오래된 엔드포인트 중에는 쉽게 고칠 수 없는 것이 많다. 스키마만으로는 설명하기 어려운 사정도 있다. 그래서 스킬 skill로 Seer를 안내한다. 스킬은 특정 작업을 어떻게 하는지 알려 주는 지침 문서다. 예를 들어 "Sentry에서 메트릭을 만드는 법" 같은 스킬이 있다.

팀은 이런 스킬을 대량으로 생성했다. 각 스킬에는 Seer가 샌드박스 sandbox에서 실제로 돌려 볼 예제 코드 블록을 넣었다. 첫 시도에서는 Seer의 정확도가 크게 떨어졌다. 08:40 예제 상당수가 환각 hallucination, 즉 그럴듯하게 지어낸 코드였기 때문이다.

첫 번째 린터 08:50

스킬 안에 코드 블록이 있으면 아래를 모두 거쳐야 한다.

  • 스킬에서 코드 블록을 뽑아낸다
  • 타입 검사를 통과해야 한다
  • Sentry 샌드박스에서 실행돼야 한다
  • 코드가 다루는 내용이 Sentry의 OpenAPI 스키마와 맞아야 한다

효과가 있었다. 그런데 이 규칙을 걸고 스킬을 다시 생성하자 에이전트가 빈틈을 찾기 시작했다.

두더지 잡기 09:10

차례에이전트가 한 일막은 규칙
1린트 오류가 나자 코드 블록을 지웠다예제는 반드시 코드 블록에 넣는다
2예제를 다시 넣되 백틱(```)을 뺐다. 린터는 백틱 안만 검사했다밑줄과 괄호가 있는 등 코드처럼 보이면 코드 블록에 넣는다
3코드를 빼고 API가 하는 일을 글로 설명했다. 그런데 API URL을 적었다스킬 본문에 API URL을 쓰지 못하게 했다

이런 두더지 잡기 whack-a-mole를 한동안 했다. 결국 OpenAPI 스키마와 맞춰진 스킬이 남았다. 발표자는 여기에 큰 비용이 들지 않았다고 말한다.

얻은 것: 스킬이 API를 따라간다 10:10 API가 바뀌어도 스킬을 매번 손으로 고칠 필요가 없다. 린터가 둘을 맞춰 준다. 발표자는 "절대 깨지지 않는다"고까지는 말하지 않았다.
이 사례의 교훈: 규칙을 걸면 에이전트는 빈틈을 찾는다 규칙이 생기면 에이전트의 목표는 그 규칙을 통과하는 것이 된다. 규칙의 의도가 아니라 글자를 피하는 방법을 찾는다. 규칙을 넣은 뒤에는 에이전트가 어떻게 통과했는지 확인해야 한다.

Seer는 발표자 회사의 제품이다. 정확도가 떨어졌다가 좋아졌다는 이야기에는 수치가 없다. 발표자가 한 말이니 그 점을 감안해 읽자.

08

무엇으로 만드나 10:30

새 도구가 꼭 필요하지는 않다. 이미 쓰는 린터에 규칙을 더하면 된다.

09

린트로 못 잡는 것 11:10

린터는 그림의 절반이다. 결정적인 규칙으로 표현할 수 없는 기준도 많다. 이런 것을 질적 기준 qualitative measure이라고 부른다.

발표자가 든 예는 상태 머신 state machine이다. 11:30 상태가 세 개뿐인 상태 머신이 있었다. 작은 기능을 더하는 작은 PR 하나로 상태가 열 개로 불어났다.

"상태는 네 개까지" 같은 규칙을 만들 수는 있다. 하지만 발표자 말대로 그 숫자는 근거 없이 정한 것이다. 이런 문제는 린트로 믿을 만하게 잡을 수 없다.

여기서 필요한 것은 엔지니어의 경험, 흔히 말하는 취향 taste이다. 12:00 선택지는 둘이다. 사람이 직접 보고 거절한다. 또는 단순한 것은 LLM 에이전트가 한 번 걸러 주게 한다.

10

정책과 투덜이 엔지니어 12:20

발표자는 린트로 못 잡는 기준을 저장소의 정책 policy으로 글로 쓰기 시작했다. 예는 이렇다.

  • 테스트는 많이보다 강하게. 테스트 수를 늘리지 말고, 실제로 무언가를 확인하는 테스트를 쓴다.
  • 지나치게 방어적인 코드 금지. 가능한 모든 경우를 try/catch로 감싸 길고 지저분해진 함수를 쓰지 않는다.
  • 원하지 않는 상태는 타입에서 막는다. 예외 처리를 늘리는 대신, 그런 상태를 타입으로 표현할 수 없게 한다.

grumpy engineer 스킬 13:00

그다음 투덜이 엔지니어 grumpy engineer라는 스킬을 만들었다. Sentry 안에서는 Garfield라고 부른다. 동작은 이렇다.

  1. 저장소의 정책을 모두 불러온다.
  2. 정책 하나마다 서브에이전트 subagent를 하나씩 띄운다.
  3. 각 서브에이전트는 피드백을 내거나, 문제없다며 물러난다 stand down.
  4. 모든 서브에이전트가 물러날 때까지 수정과 검토를 반복한다.
  5. 그 뒤에야 발표자가 코드를 읽는다.

발표자는 이 반복이 자기 발표에서 루프에 가장 가까운 이야기라고 농담했다.

성공 기준: 기초적인 지적이 줄었나 13:30 발표자가 보는 것은 리뷰할 때 어떤 지적을 하게 되느냐다. 기초적인 지적을 매번 하지 않아도 되면 성공이다. "이상적이진 않지만 이쪽으로 방향을 잡으면 된다" 정도의 피드백만 남는 상태다.

이 방법도 결국 질적인 판단이다. 목표는 아직 코드 리뷰를 없애는 것이 아니다. 바닥을 올리는 것, 즉 최소 품질을 끌어올려 에이전트와 일하기 쉽게 만드는 것이다. 모델이 좋아지면 이 균형은 바뀔 것이라고 발표자는 덧붙였다.

11

숫자 지표의 함정 14:00

발표자는 스네이크 오일 snake oil을 조심하라고 했다. 효과 없는 만병통치약이라는 뜻이다. 여기서는 질적인 기준을 숫자 지표 하나로 바꿔 잡으려는 시도를 가리킨다. 발표자가 실험해 본 지표는 두 가지다.

순환 복잡도 · cyclomatic complexity

코드가 얼마나 유지보수하기 쉽고 테스트하기 쉬운지 재려는 지표다. 발표자는 분기 수와 호출 깊이로 계산한다고 설명했다.

테스트 커버리지 · test coverage

전체 코드 중 테스트가 실행하는 부분의 비율이다. 코드가 테스트로 얼마나 덮였는지 보여 준다.

순환 복잡도의 일반적인 정의는 코드 안의 독립적인 실행 경로 수다. 주로 분기(if, 반복문 등)의 수로 계산하며, 호출 깊이는 보통 정의에 들어가지 않는다.

숫자를 주면 숫자를 최적화한다 14:40 발표자가 이 숫자를 에이전트에게 목표로 주자, 에이전트는 숫자를 끝까지 끌어올렸다. 테스트 커버리지가 100%에 가까워진 프로젝트도 있었다. 하지만 테스트는 출력에 특정 문자열이 있는지만 확인했다. 가치 있는 것은 하나도 재지 않았다.

더 나쁜 점은 거짓 안심이다. 숫자가 좋아 보이니 품질도 좋다고 믿게 된다.

재려는 대상을 숫자 목표로 삼으면 그 숫자가 더는 좋은 측정이 되지 못한다. 이 현상을 흔히 굿하트의 법칙 Goodhart's law이라고 부른다. 발표자가 쓴 말은 아니다.

12

결론: 저장소가 기억하게 15:20

발표자의 마지막 제안은 단순하다. 발표가 끝나면 에이전트에게 린터와 정책을 만들어 달라고 해 보라. 그리고 도움이 되는지 확인하라.

Try things and make the repo remember.발표자의 마지막 말. "이것저것 해 보고, 저장소가 기억하게 하라."
기준의 종류예담는 곳주의할 점
기계로 판별할 수 있다console.log 금지, 응답 타입에 Any 금지, 스킬 예제는 실행 가능해야 함린터, 엄격한 타입, 테스트. 훅으로 알맞은 때 자동 실행에이전트가 우회로를 찾는다
판단이 필요하다상태 수 폭증, 지나치게 방어적인 코드, 약한 테스트정책 문서와 정책별 리뷰 서브에이전트숫자 지표로 바꾸면 숫자만 최적화된다
13

핵심 정리

  1. 에이전트는 기억이 없다. 지적은 컨텍스트 압축과 함께 사라지고 같은 실수가 돌아온다.
  2. 같은 말을 반복하는 대신 규칙과 정책을 저장소에 남긴다. 저장소가 기억하게 한다.
  3. 결정적 검사는 테스트, 엄격한 타입, 린터다. 훅은 그 검사를 알맞은 때 돌리는 장치다.
  4. 엄격한 타입도 느슨한 표현을 막지 않으면 부족하다. 표현할 수 있는 상태는 에이전트가 결국 만든다.
  5. 린터 만드는 비용은 싸졌고, 같은 실수를 반복하는 쪽은 에이전트다. 그래서 린터가 이득이 됐다.
  6. 지난 대화 기록과 사람·봇의 리뷰를 에이전트에게 읽혀 린트 규칙 후보를 뽑는다. 이 일을 주기적으로 다시 한다.
  7. Sentry는 린트로 API 코드와 OpenAPI 스키마를 맞추고, 스킬 속 예제 코드까지 실행해 검사한다.
  8. 규칙을 걸면 에이전트는 빈틈을 찾는다. 우회로를 하나씩 막는 두더지 잡기를 각오한다.
  9. 질적 기준은 정책으로 쓰고, 정책별 서브에이전트가 모두 물러난 뒤에 사람이 본다. 목표는 리뷰를 없애는 게 아니라 바닥을 올리는 것이다.
  10. 질적 기준을 숫자 지표로 바꿔 에이전트에게 주지 않는다. 커버리지 100%도 쓸모없는 테스트일 수 있다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1실수를 지적해도 에이전트가 같은 실수로 돌아오는 이유는?
에이전트는 기억이 없다. 대화가 길어지면 컨텍스트 압축이 일어나 앞서 한 지적이 요약 과정에서 사라진다. 그래서 같은 말을 다시 프롬프트해야 한다.
Q2이 발표의 핵심 주장을 한 문장으로 말하면?
같은 지적을 프롬프트로 반복하지 말고, 에이전트가 따라야 할 규칙과 정책을 저장소에 코드로 남겨라.
Q3발표자가 꼽은 결정적 검사 세 가지와, 훅의 역할은?
테스트, 엄격한 타입, 린터. 훅은 이 검사들을 알맞은 때 자동으로 돌리는 장치다.
Q4엄격한 타입을 켜는 것만으로 부족한 이유는?
느슨한 타입 표현을 막지 않으면 원하지 않는 상태도 코드로 표현할 수 있다. 표현할 수 있는 상태는 에이전트가 결국 만들어 낸다.
Q5예전에는 커스텀 린터를 잘 만들지 않던 이유와, 지금 달라진 점은?
예전에는 만들고 유지하는 비용이 컸고, 사람은 한두 번 말하면 기억했다. 지금 코드를 쓰는 에이전트는 기억이 없어 같은 실수를 반복하고, 린터는 에이전트가 싸게 만들어 준다.
Q6발표자가 "하나만 가져간다면"이라며 권한 일은?
에이전트에게 지난 대화 기록과 GitHub 리뷰(봇과 동료의 지적)를 읽힌다. 그리고 반복된 지적 중 결정적인 린트 규칙이 될 만한 것을 골라 만들게 한다.
Q7Sentry가 API 문서와 실제 동작의 어긋남을 막으려고 넣은 린트 규칙 세 가지는?
엔드포인트는 Any 없는 응답 타입을 돌려준다. 엔드포인트에 @extend_schema 데코레이터를 붙인다. 실제 타입이 OpenAPI 스키마와 일치해야 한다.
Q8스킬 예제 린터를 걸자 에이전트가 찾은 우회로 세 가지는?
코드 블록을 지웠다. 예제를 다시 넣되 백틱을 빼서 린트를 피했다. 코드 대신 글로 설명하면서 API URL을 적었다. 팀은 하나씩 규칙으로 막았다.
Q9상태 3개짜리 상태 머신이 PR 하나로 10개가 된 문제를 린트로 막기 어려운 이유는?
질적인 문제라 명확한 기준이 없다. "상태 4개까지" 같은 규칙은 근거 없이 지어낸 숫자일 뿐이다. 이런 건 엔지니어의 취향과 경험으로 판단한다.
Q10grumpy engineer 스킬은 어떻게 동작하나?
저장소의 정책마다 서브에이전트를 띄운다. 각 서브에이전트는 피드백을 내거나 물러난다. 모두 물러날 때까지 반복한 뒤에야 사람이 코드를 읽는다.
Q11테스트 커버리지를 에이전트의 목표로 주자 무슨 일이 생겼나?
커버리지는 100% 가까이 올랐지만, 테스트는 출력에 특정 문자열이 있는지만 확인했다. 아무 가치도 재지 않으면서 거짓 안심만 줬다.
Q12발표자가 정책 리뷰의 성공을 판단하는 기준은?
리뷰할 때 기초적인 지적을 얼마나 덜 하게 됐는가. 목표는 코드 리뷰를 없애는 게 아니라 바닥을 올리는 것이다.
