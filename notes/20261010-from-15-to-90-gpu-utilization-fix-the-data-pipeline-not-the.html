모델 말고 데이터 파이프라인을 고쳐라

멀티모달 모델을 학습할 때 GPU가 노는 이유는 대개 모델 쪽이 아니다. 데이터를 받고, 처리하고, 보내는 쪽이다. 발표자는 이 병목을 하나씩 풀어 GPU 사용률을 15%에서 90%로 올렸다.

원본 영상: From 15% to 90% GPU Utilization: Fix the Data Pipeline, Not the Model 발표: 자막에 발표자 이름과 소속이 나오지 않는다

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Qwen3-VL, Ray, GIL 등)은 알려진 이름으로 바로잡았다. 발표자가 읽은 원래 제목은 "Ray Actors, Vision Tokens, and the GIL: Engineering a Multimodal SFT Data Pipeline That Keeps the GPUs Busy"다. mm:ss는 영상 위치다.

3분 요약
  1. 멀티모달 학습에서 가장 어려운 일은 커널 최적화가 아니다. GPU에 데이터를 끊김 없이 대 주는 일이다.
  2. 발표자는 대기 시간 비율로 잰다. 기준선은 시간의 85%를 데이터를 기다리는 데 썼다. GPU 사용률로는 15%다.
  3. 해법 1, 동시 처리: 이미지 받기는 asyncio로, 처리는 Ray actor로 돌렸다. 배치당 데이터 시간이 100초 이상에서 약 40초로 줄었다.
  4. 해법 2, 미리 가져오기: 백그라운드 큐가 학습보다 앞서 데이터를 채운다. 배치당 데이터 시간이 거의 0초가 됐다.
  5. 해법 3, 복사 줄이기: 큰 이미지 텐서를 값 대신 참조로 넘겼다. 세 해법을 합쳐 대기 비율이 85%에서 20%로 내려갔다.
  6. 규모를 4배로 키우자 한 노드의 네트워크 카드가 막혔다. 워커를 여러 노드로 흩고 zero-copy 조회를 켜자 처리량이 50% 더 늘었다.
  7. 교훈: 병목 하나를 풀면 다음 병목이 드러난다. 규모가 바뀌면 답도 바뀐다. 먼저 기준선을 프로파일링한다.
01

GPU는 데이터를 기다린다 00:00

학습을 빠르게 하는 이야기는 보통 학습 방식이나 커널 최적화에 쏠린다. 발표자는 다른 질문을 던진다. 지금 학습 루프는 정말 GPU 때문에 멈춰 있나?

발표의 답은 이렇다. 멀티모달 학습 처리량throughput에서 가장 어려운 부분은 커널 최적화가 아니다. GPU가 계속 데이터를 받도록 하는 일이다.

멀티모달은 CPU가 바쁘다 01:50

텍스트만 다루는 학습과 달리, 멀티모달multimodal 학습은 모델에 넣기 전에 CPU에서 할 일이 많다.

  • 이미지: 불러오고, 크기를 바꾸고, 정규화한다. PIL 같은 라이브러리를 쓴다.
  • 오디오: 불러오고 잘라 낸다. numpy 배열을 쓴다.
  • 비디오: 이미지와 오디오 작업을 섞은 일이다.

학습 클러스터에는 보통 GPU보다 CPU가 훨씬 많다. 그런데도 굶는 쪽은 GPU다.

발표가 푸는 순서 01:00 단순한 기준선을 먼저 만든다. 그다음 드러나는 병목을 하나씩 푼다. 1) 동시 처리, 2) 미리 가져오기, 3) 프로세스 사이의 복사 줄이기, 4) 프레임워크 설정 조정.
02

대기 시간 비율이라는 잣대 02:40

발표자는 진행 상황을 숫자 하나로 잰다. 대기 시간 비율wait time ratio이다.

대기 시간 비율 (데이터 준비 시간 + GPU로 보내는 시간) ÷ (데이터 준비 + 전송 + 학습 시간) 분모는 파이프라인 전체 시간이다. 이 값이 클수록 GPU는 데이터를 기다리며 논다.

기준선은 시간의 85%를 데이터를 기다리는 데 썼다. 최적화를 마친 뒤에는 10% 미만이 됐다. GPU 사용률utilization로 바꾸면 15%에서 90%다.

그래서 이 발표의 목표는 GPU를 더 빠르게 만드는 게 아니다. 데이터가 절대 병목이 되지 않게 하는 것이다.

04

출발점: 하나씩 차례로 05:10

가장 단순한 기준선baseline은 이렇다. 예제마다 객체 저장소에서 이미지를 받는다. 텍스트를 토큰화한다. 이미지 크기를 바꾸고 정규화한다. 그리고 모델에 넣는다.

문제는 이 일이 하나씩 차례로 일어난다는 점이다. 이미지를 하나씩 받고, 하나씩 처리한다. 학습기가 배치 크기 256을 요청하면 이미지 256개를 줄 세워 처리해야 한다.

  • 배치 하나의 학습 시간: 15~20초
  • 배치 하나의 데이터 준비 시간: 100초 이상
  • 그 결과 GPU 사용률: 약 15%
숫자 맞춰 보기 학습 시간을 가운데 값 17.5초로 잡으면 17.5 ÷ (100 + 17.5) ≈ 15%다. 발표자가 말한 사용률과 맞는다.

플레임 그래프flame graph로 보면 시간 대부분이 S3에서 파일을 받는 데 들어갔다. 끝에는 PIL로 이미지를 여는 시간이 조금 붙어 있었다.

05

해법 1: 동시에 처리하기 06:20

예제끼리는 서로 독립이다. 그래서 그대로 나눠 동시에 돌릴 수 있다embarrassingly parallel. 차례로 처리하는 대신 워커 풀worker pool을 두고, 256개를 한꺼번에 처리한다.

줄일 비용은 두 가지다.

  • 받기: 저장소에서 이미지를 가져온다.
  • 처리하기: 디코딩, 비전 전처리, 텍스트 토큰화.

GILGlobal Interpreter Lock은 파이썬이 한 번에 한 스레드만 파이썬 코드를 실행하게 막는 잠금이다. 일부 라이브러리는 무거운 계산을 하는 동안 이 잠금을 잠시 푼다. 그런 연산에서만 스레드가 CPU 작업을 실제로 동시에 돌린다.

발표자의 원칙 예전에 통했던 방법을 그대로 고르지 않는다. 지금 병목에 맞는 방법을 고른다. 자세한 비교는 그것만으로 발표 하나가 될 만큼 길어서, 발표자는 온라인 자료를 찾아보라고 권했다.

발표자는 이미지 받기에 asyncio를, 처리에 Ray actor를 골랐다 08:10. Ray actor는 일반 프로세스와 거의 같다. 다만 워커끼리 통신하는 API를 함께 준다. 그 부분을 직접 만들 필요가 없다.

결과 08:30

파이프라인은 가장 느린 고리만큼만 빠르다. 대기 시간 비율이 내려갔고, 배치당 데이터 시간은 약 40초로 줄었다. 발표자는 이를 25% 속도 향상이라고 했다.

발표자가 말한 배치당 수치만으로 계산하면 한 스텝은 약 118초에서 약 58초로 줄어, 2배 가까이 빨라져야 한다. 학습 시간에 가운데 값 17.5초를 넣은 계산이다. 발표자는 이어서 스텝이 쌓일수록 간격이 벌어진다고 했으니, 25%는 전체 실행 기준으로 잰 값일 수 있다. 자막만으로는 어느 쪽인지 확정할 수 없다.

그래도 스텝이 쌓일수록 학습과 데이터 사이의 간격이 크게 벌어졌다. 남은 질문은 이것이다. 학습기가 요청할 때까지 기다렸다가 워커를 돌려야 하나?

06

해법 2: 미리 가져오기 09:10

답은 미리 가져오기prefetching다. 백그라운드 스레드가 큐를 미리 채운다. 생산자는 소비자보다 몇 배 빠르게 데이터를 만들어 늘 앞서 간다. 여기서 생산자는 데이터 쪽이고, 소비자는 학습기다.

그래서 학습기는 데이터를 요청하느라 멈추지 않는다. 요청하는 순간 데이터는 이미 준비돼 있다.

단점 1 · 체크포인트와 재개 09:40

모델과 데이터 로더의 체크포인트를 저장하고 이어서 학습하는 과정이 까다로워진다. 큐에 미리 받아 둔 데이터가 있기 때문이다.

단점 2 · 콜드 스타트

처음에는 큐가 찰 때까지 시간이 걸린다. 그동안은 학습을 시작할 준비가 덜 된 상태다.

발표자는 이 두 가지만 챙기면 미리 가져오기는 좋은 선택이라고 본다. 생산자를 늘 소비자보다 앞에 두면 큰 이득이 돌아온다는 것이다.

결과는 예상대로였다 10:10. 배치당 데이터 시간이 거의 0초가 됐다. 학습기가 필요로 하기 훨씬 전에 받고 처리해 뒀기 때문이다. 불러오기와 변환 병목은 이것으로 풀렸다.

07

해법 3: 복사 줄이기 10:30

두 가지를 고친 뒤 발표자 팀은 끝났다고 생각했다. 처리량은 올랐고 GPU는 데이터를 받았다. 그런데 보내기 비용이 남아 있었고, 오히려 늘었다.

샘플마다 큰 이미지 배열이 프로세스 경계를 여러 번 넘었다.

  1. 워커에서 피클링pickling한다.
  2. 코디네이터로 복사한다.
  3. 학습기로 다시 피클링한다.

샘플마다, 스텝마다 아무도 원하지 않은 메모리 복사가 일어난다. 멀티모달 텐서는 샘플당 수 MB다. 기본 동작은 결과를 값으로 돌려주는 것이라, 이 큰 배열이 프로세스마다 복사된다. 그 결과 데이터 생성기가 메모리 부족OOM으로 죽기도 한다.

바꾼 뒤 · 참조로 넘기기샘플은 객체 참조만 들고 다닌다드라이버는 포인터만 쥔다. DP 랭크가 필요할 때 저장소에서 직접 가져간다

여기에 쓴 것은 Ray가 제공하는 객체 저장소object store다. 각 샘플은 객체 참조object reference를 들고 다닌다. 참조는 데이터를 가리키는 포인터일 뿐이다. 그래서 텐서가 헤드 노드를 거쳐 왕복하지 않는다. Megatron의 데이터 병렬 랭크는 필요할 때 Ray 저장소에서 바로 데이터를 가져간다.

발표자의 경고 병렬화나 동시성 방식을 고를 때마다 늘어나는 통신 비용을 같이 따져야 한다.

Ray 저장소를 쓰면서, 미리 가져오기 구현에 있던 불필요한 put 호출 하나도 없앴다 12:00. 통신 비용이 줄었고 대기 시간 비율도 내려갔다.

규모를 키우자 다시 막혔다 12:50

그런데 같은 파이프라인의 대기 시간 비율이 다시 올랐다.

원인: 한 노드의 네트워크 카드 13:10

빠른 전송을 위해 데이터 생성기와 워커 풀을 같은 노드에 모아 뒀었다. 받기와 처리가 특정 노드에 몰리자, 그 노드의 네트워크 인터페이스 카드NIC가 학습 파이프라인의 수요를 따라가지 못했다.

쓰는 프레임워크를 파 보니 원인이 하나 더 있었다 13:40. 발표자 설명에 따르면 Ray는 기본적으로 워커를 같은 노드에 모아 배치하는 쪽을 선호한다. 그래서 다른 머신으로 넘어가기 전에 한 머신이 먼저 막히기 쉽다.

워커를 흩고, 복사 없이 읽는다 14:00

발표자 팀은 이 과정을 쪼개 흩었다disaggregate. 워커를 여러 노드에 나눠 둔다. 노드마다 자기 몫의 이미지를 처리하고 저장한다. 데이터 병렬 랭크는 필요한 순간에 필요한 만큼 가져간다lazy, just-in-time.

조정한 설정 14:20하는 일
zero-copy 조회데이터를 가져올 때 새 메모리로 복사하지 않고 저장소에 있는 것을 그대로 읽는다
spread 스케줄링워커를 한 노드에 모으지 않고 여러 노드로 퍼뜨려 배치한다

작은 규모 실험에서는 둘 다 효과가 없었다. 큰 규모에서는 둘이 함께 상승효과를 냈다. 이 두 설정만으로 큰 규모에서 처리량이 50% 더 늘었다 15:10.

같은 설정인데 판정은 정반대였다. 판정을 정한 것은 병목이었다.발표자의 표현을 옮김 15:20
규모 사다리 위에서 비교한다 작은 규모에서 성적이 나쁜 설정이 큰 규모에서는 좋을 수 있다. 그래서 설정을 하나씩 빼 보는 비교 실험ablation은 규모 사다리scaling ladder의 여러 단에서 해 봐야 한다.
10

최종 구조와 교훈 15:00

최종 파이프라인은 세 가지 성격을 갖는다. 동시에 처리한다. 미리 당겨 온다eager. 데이터를 어디서 어떻게 읽는지 고려해 일을 여러 노드에 나눈다. 이렇게 GPU를 계속 일하게 하면서 학습도 매끄럽고 안정적으로 유지한다.

발표자가 남긴 교훈 15:30

  1. 큰 싸움은 GPU 밖에서 일어난다. GPU는 비싸다. 그래서 먼저 묻는다. CPU에 묶였나, GPU에 묶였나? I/O에 묶였나, 계산에 묶였나?
  2. 병목 하나를 풀면 다른 병목이 드러난다. 이 발표에서는 처리량, 대기 시간, 메모리, 조회 비용 순으로 옮겨 갔다.
  3. 고전적인 수로 끝나지 않는다. 병렬화와 미리 가져오기는 중요하고 이미 많이 다뤄졌다. 쓰는 프레임워크의 동작 방식과 지금 처한 제약도 그만큼 중요하다.
  4. 규모가 답을 바꾼다. zero-copy와 워커 분산은 큰 규모에서만 중요해진다. 작은 규모에서는 효과가 잘 드러나지 않는다.
  5. 기준선을 프로파일링해야 숫자가 움직인다.
11

핵심 정리

  1. 멀티모달 학습에서 어려운 일은 커널 최적화보다 GPU에 데이터를 끊김 없이 대는 일이다.
  2. 이미지·오디오·비디오 전처리는 CPU에서 먼저 끝나야 한다. CPU가 많아도 GPU는 굶을 수 있다.
  3. 대기 시간 비율은 (준비 + 전송) ÷ (준비 + 전송 + 학습)이다. 기준선은 85%, GPU 사용률로는 15%였다.
  4. 기준선은 이미지를 하나씩 받고 처리했다. 배치당 학습은 15~20초, 데이터는 100초 이상이었다.
  5. 해법 1은 병목에 맞는 동시성이다. 받기는 asyncio, 처리는 Ray actor. 데이터 시간이 약 40초로 줄었다.
  6. 스레드는 GIL을 푸는 연산에서만 CPU 작업을 빠르게 한다. 어떤 연산이 그런지는 직접 확인한다.
  7. 해법 2는 백그라운드 큐로 미리 가져오기다. 데이터 시간이 거의 0초가 된다. 대신 체크포인트 재개와 콜드 스타트를 챙긴다.
  8. 해법 3은 큰 텐서를 값 대신 참조로 넘기기다. 세 해법을 합쳐 대기 비율이 85%에서 20%로 내려갔다.
  9. 규모를 4배로 키우자 한 노드의 NIC가 막혔다. spread 스케줄링과 zero-copy 조회로 처리량이 50% 더 늘었다.
  10. 병목은 하나를 풀면 다음이 드러나고, 규모가 바뀌면 답도 바뀐다. 기준선 프로파일링부터 한다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 쓰는 대기 시간 비율의 계산식은?
(데이터 준비 시간 + GPU로 보내는 시간) ÷ (데이터 준비 + 전송 + 학습 시간). 분모는 파이프라인 전체 시간이다.
Q2기준선의 GPU 사용률이 약 15%였던 이유를 숫자로 설명하면?
배치 하나의 학습은 15~20초인데 데이터 준비는 100초 이상 걸렸다. 17.5 ÷ (100 + 17.5)는 약 15%다.
Q3멀티모달 학습이 텍스트 학습보다 데이터 쪽이 무거운 이유는?
모델에 넣기 전에 CPU에서 할 일이 많다. 이미지는 불러오기, 크기 바꾸기, 정규화가 필요하고, 오디오는 불러오고 잘라야 한다. 비디오는 둘 다 필요하다.
Q4asyncio, 스레드, 프로세스는 각각 어떤 일에 맞나?
asyncio는 SQL 쿼리나 네트워크 요청 같은 I/O 작업. 스레드는 GIL을 푸는 CPU 작업. 프로세스는 무겁지만 작업을 완전히 떼어 여러 코어를 쓸 때.
Q5스레드로 CPU 작업을 빠르게 하려면 어떤 조건이 필요한가?
그 연산이 GIL을 풀어 줘야 한다. 발표자는 Hugging Face 토크나이저, PIL 변환, 일부 pandas 연산을 예로 들었다. 어떤 연산이 그런지는 직접 확인해야 한다.
Q6발표자가 이미지 받기와 처리에 각각 고른 도구는?
받기에는 asyncio, 처리에는 Ray actor. Ray actor는 일반 프로세스와 비슷하지만 워커끼리 통신하는 API를 준다.
Q7미리 가져오기의 두 가지 단점은?
모델과 데이터 로더의 체크포인트 저장과 재개가 까다로워진다. 그리고 처음에 큐가 찰 때까지 기다리는 콜드 스타트가 생긴다.
Q8미리 가져오기 뒤에도 남은 비용은 무엇이고, 왜 생겼나?
보내기 비용이다. 샘플마다 수 MB짜리 이미지 배열을 워커에서 피클링하고, 코디네이터로 복사하고, 학습기로 다시 피클링했다. 데이터 생성기가 메모리 부족으로 죽기도 했다.
Q9Ray 객체 저장소의 참조를 쓰면 무엇이 달라지나?
샘플은 데이터를 가리키는 포인터만 들고 다닌다. 텐서가 헤드 노드를 거쳐 왕복하지 않고, 데이터 병렬 랭크가 필요할 때 저장소에서 직접 가져간다.
Q10규모를 키웠을 때 대기 비율이 다시 오른 원인은?
데이터 생성기와 워커를 한 노드에 모아 둔 탓에 그 노드의 네트워크 카드가 수요를 못 따라갔다. 발표자 설명으로는 Ray가 기본적으로 워커를 같은 노드에 모으는 쪽을 선호한다.
Q11zero-copy와 spread 설정을 작은 실험 결과만 보고 버리면 안 되는 이유는?
작은 규모에서는 둘 다 효과가 없었지만, 큰 규모에서는 함께 처리량을 50% 더 올렸다. 설정 비교는 여러 규모에서 해 봐야 한다.
Q12이 발표에서 병목이 옮겨 간 순서는?
처리량, 대기 시간, 메모리, 조회 비용 순이다. 하나를 풀 때마다 다음 병목이 드러났다.
