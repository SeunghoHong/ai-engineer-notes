같은 모델인데 왜 속도가 다른가

오픈 웨이트 모델은 이제 상용 최고 모델과 같은 급에서 겨룬다. 그래서 다음 질문은 "어느 모델"이 아니라 "어디서 돌리나"가 된다. 모델 가중치가 같아도 캐시, 라우팅, 디코딩, 신뢰성에 따라 사용자가 느끼는 속도는 크게 달라진다.

원본 영상: Same Model, Different Speed: Why Your Inference Provider Matters 발표: Yun Mo (FriendliAI 창립 엔지니어, 자막 표기 기준)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

발표자는 추론 API 회사 FriendliAI 소속이다. 발표 전체가 자사 서비스 소개에 가깝고, 비교 수치는 모두 발표자 쪽에서 고른 것이다. 기술 설명은 일반적인 내용이지만 성능 비교는 그 점을 감안해 읽자.

3분 요약
  1. 오픈 웨이트 모델은 코딩, 추론, 에이전트 벤치마크에서 상용 최고 모델과 같은 급에 올라왔다. 발표자는 GLM 5.2가 Claude Opus 4.8보다 위에 있는 리더보드를 보여 줬다.
  2. 같은 타워 디펜스 게임을 만들게 했더니 결과 품질은 비슷했고 GLM 5.2가 5.6배 넘게 쌌다. 여러 번 반복하는 에이전트 작업에서는 이 차이가 누적된다.
  3. 모델이 같아도 제공자에 따라 지연, 처리량, 신뢰성이 다르다. 같은 모델, 같은 코딩 에이전트로 게임을 만들었는데 한쪽은 2분, 다른 쪽은 3분 넘게 걸렸다.
  4. 그 차이는 추론 스택 전체에서 나온다. 배칭, 스케줄링, 양자화, 추측 디코딩, 커널이 함께 맞물려야 빠르다.
  5. 에이전트 입력은 길고 50~90%가 요청 간에 반복된다. KV 캐시를 재사용하려면 캐시를 가진 복제본으로 보내는 라우팅과 GPU·CPU·디스크로 나눈 캐시 계층이 필요하다.
  6. 출력 속도는 추측 디코딩으로 올린다. 모델 기반과 모델 없는 방식을 워크로드에 따라 바꿔 쓰고, 실제 트래픽으로 초안 모델을 계속 학습시킨다.
  7. 신뢰성도 속도의 일부다. 에이전트는 호출을 여러 번 하므로 하나만 실패해도 작업 전체가 무효가 된다. 평균이 빨라도 오류율이 높으면 소용없다.
  8. 남의 벤치마크보다 내 프롬프트, 내 토큰 길이, 내 트래픽 패턴으로 직접 재는 것이 유일하게 의미 있는 벤치마크다.
01

오픈 웨이트 모델이 문턱을 넘었다 01:00

발표자는 청중에게 손을 들게 했다. GPT나 Claude 같은 닫힌 모델을 쓰는 사람은 대부분이었고, 오픈 웨이트 모델을 주로 쓰는 사람은 훨씬 적었다. 발표자 본인은 둘을 섞어 쓰다가 점점 오픈 웨이트 쪽으로 옮기는 중이라고 했다.

이유는 오픈 웨이트 모델이 문턱을 넘었기 때문이다. 코딩, 추론, 에이전트 벤치마크에서 GLM 5.2 같은 모델이 선두 상용 모델과 같은 급에서 겨룬다. 발표자가 보여 준 Code Arena(추정) 리더보드에서는 GLM 5.2가 Claude Opus 4.8보다 위, Claude Fable 5 바로 아래에 있었다. 다른 코딩, 터미널, 도구 사용 벤치마크에서도 GLM 5.2와 MiniMax M3가 좋은 결과를 냈다고 했다.

질문이 바뀐다 "오픈 웨이트 모델이 쓸 만한가"는 많은 워크로드에서 이미 답이 났다. 다음 질문은 "프로덕션에서 얼마나 빠르고 안정적으로 돌릴 수 있나"다.

오픈 웨이트 모델open-weight model은 학습된 가중치 파일을 공개해서 누구나 내려받아 돌릴 수 있는 모델이다. 반대는 닫힌 모델closed-weight model로, API로만 쓸 수 있다.

02

같은 게임, 5.6배 싼 비용 02:10

벤치마크 숫자만으로는 실제로 얼마나 잘 되는지 감이 안 온다. 그래서 발표자는 간단한 실험을 했다. GLM 5.2와 Claude Opus 4.8에게 각각 프롬프트 하나로 타워 디펜스 게임을 만들게 했다.

둘 다 돌아가는 게임을 만들었다. 맵이 있고, 포탑이 사거리 안의 적을 쏜다. 구조와 품질이 비슷했다. 그런데 비용을 보니 차이가 분명했다.

한 번 쓰고 끝나는 일이면 큰 차이가 아닐 수 있다. 하지만 에이전트 방식 작업은 같은 일을 여러 번 반복한다. 그러면 차이가 빠르게 쌓인다. 발표자의 표현을 빌리면 이제 문제는 모델 품질만이 아니라 "규모를 키웠을 때 감당할 수 있는가"다.

03

같은 모델, 다른 제공자 03:00

모델 품질과 비용 다음 질문은 제공자 품질이다. 제공자 품질은 결국 성능이다. 모델 가중치가 같아도 어디서 돌리느냐에 따라 지연, 처리량, 신뢰성이 크게 달라진다. 발표자는 OpenRouter 화면을 보여 주며 이 차이가 측정 가능한 것이라고 했다.

두 번째 실험은 이 점을 보여 준다. 같은 GLM 5.2 모델, 같은 코딩 에이전트로 캔디 크러시 스타일의 모바일 게임을 만들게 했다.

모델도 같고 에이전트 앱도 같다. 다른 것은 제공자뿐이다. 그런데 사용자가 느끼는 경험은 다르다. 발표자는 이 차이가 추론 스택 전체에서 나온다고 말한다. 모델 구조, 캐시 시스템, 라우팅 정책, 양자화 전략, GPU 커널이 다 합쳐져서 개발자가 체감하는 속도를 만든다.

이 비교는 FriendliAI가 직접 고른 조건에서 자사 서비스와 이름을 밝히지 않은 다른 제공자를 비교한 것이다. 비교 대상, 측정 시점, 반복 횟수는 발표에 나오지 않았다.

04

추론은 하나의 최적화가 아니다 04:50

발표자는 FriendliAI를 "모델 API를 그냥 노출하는 곳"이 아니라 생성형 AI 모델을 위한 풀스택 추론 엔진이라고 소개한다. 빠르고 안정적인 추론은 기술 하나로 되지 않는다는 것이 핵심 주장이다.

구성 요소하는 일
배칭 batching여러 요청을 묶어 GPU를 한 번에 돌린다
스케줄링 scheduling어떤 요청을 언제 처리할지 정한다
양자화 quantization가중치의 정밀도를 낮춰 메모리와 연산을 줄인다
추측 디코딩 speculative decoding토큰 여러 개를 미리 제안하고 한 번에 검증한다
커널 kernelGPU에서 실제 연산을 수행하는 저수준 코드

이 요소들은 함께 맞물려야 효과가 난다. 발표의 나머지는 이 중에서 캐시, 추측 디코딩, 신뢰성 세 가지를 자세히 다룬다.

05

반복되는 입력: KV 캐시 재사용 05:20

요즘 에이전트 애플리케이션의 입력은 매우 길다. 1만 토큰을 쉽게 넘긴다. 반면 출력은 비교적 짧다. 더 중요한 점은 입력의 큰 부분이 요청마다 반복된다는 것이다. 시스템 프롬프트, 도구 설명, 이전 대화가 매번 다시 들어가기 때문이다. 발표자는 실제 워크로드에서 토큰의 50%에서 많게는 80~90%가 요청 간에 동일하다고 했다.

시스템 관점에서 보면 연산 비용 대부분이 프리필prefill 단계에 있다. 모델이 입력 전체를 읽고 KV 캐시를 만드는 단계다. 같은 접두사를 매번 다시 계산하면 지연 시간과 GPU 사이클을 둘 다 낭비한다.

접두사 캐시의 원리 새 요청이 이전 요청과 같은 앞부분을 공유하면, 그 부분의 KV 캐시 텐서를 재사용하고 해당 프리필 계산을 건너뛴다. 첫 토큰까지의 시간(TTFT)이 바로 줄고, 입력의 큰 덩어리를 다시 계산하지 않아도 된다.

원리는 간단하지만 규모를 키우면 두 가지 장치가 필요하다.

1. 캐시 인식 라우팅 cache-aware routing 06:30

분산 시스템에서 KV 캐시는 한곳에 모여 있지 않다. 각 복제본replica의 메모리에 따로 산다.

라우터는 들어온 요청을 그 접두사를 이미 캐시에 가진 복제본으로 보내야 한다. 아무 데나 보내면 재사용의 이점이 사라진다.

2. 캐시 계층 cache hierarchy 06:50

KV 캐시는 메모리를 아주 많이 쓴다. 큰 모델과 긴 컨텍스트에서는 캐시 크기가 모델 가중치보다 커질 수 있다. GPU 메모리는 가장 빠르지만 아주 제한적이다.

  • 뜨거운 캐시: GPU 메모리
  • 미지근한 캐시: CPU RAM
  • 차가운 캐시: NVMe 또는 디스크

덜 쓰는 블록은 자동으로 아래 계층으로 내리고, 필요해지면 다시 올린다.

캐시 인식 라우팅과 계층 메모리 관리를 합치면 접두사 비용이 크게 줄고, TTFT가 낮아지고, 긴 컨텍스트 에이전트 워크로드가 훨씬 효율적이 된다.

06

출력 속도: 추측 디코딩 07:40

다음은 대화형 속도다. 표준 자기회귀 디코딩autoregressive decoding은 순전파 한 번에 토큰 하나를 만든다. 그래서 디코딩은 본질적으로 순차적이고, 이 동안 GPU는 놀기 일쑤다.

추측 디코딩speculative decoding은 이 문제의 모양을 바꾼다. 토큰 하나를 만들고 멈추는 대신 후보 토큰 여러 개를 미리 제안한다. 그러면 원래 모델이 그 후보들을 한 번의 순전파로 검증한다. 받아들여진 토큰은 공짜로 얻은 셈이다. 출력 품질은 바뀌지 않고 토큰당 출력 시간만 줄어든다.

후보를 만드는 두 가지 방법 08:20

방식후보를 만드는 법장점비용
모델 기반 추측작은 초안 모델draft model이 다음 토큰들을 예측한다수락률이 높다추가 연산이 든다
모델 없는 추측프롬프트나 이전 출력의 패턴을 그대로 쓴다오버헤드가 낮다출력이 기존 문맥과 닮을 때만 잘 된다
핵심은 트레이드오프 추측은 요청 하나의 지연을 줄이지만, 검증은 배치 전체에 오버헤드를 더한다. 그래서 최선의 전략은 고정돼 있지 않다.

FriendliAI는 두 방식을 섞어 쓴다. 런타임이 워크로드와 요청의 특성에 따라 모델 기반과 모델 없는 추측 사이를 동적으로 고른다. 한 걸음 더 나가서 자기 진화 추측self-evolving speculation이라는 것도 소개했다. 초안 모델이 실제 서빙 트래픽을 보고 적응해서, 프로덕션에서 실제로 돌아가는 워크로드에 대한 예측을 계속 개선한다는 뜻이다.

07

속도만으로는 부족하다 09:40

프로덕션 AI 애플리케이션에서는 신뢰성이 속도의 일부다. 평균은 빠른데 타임아웃, 5xx 서버 오류, 429 요청 제한 같은 실패가 잦으면 사용자 경험은 여전히 깨진다.

에이전트 워크로드에서는 이 점이 더 중요하다. 에이전트는 작업 하나를 끝내려고 모델을 여러 번 부른다. 중간에 호출 하나만 실패해도 작업 흐름 전체가 무효가 될 수 있다. 그래서 발표자는 지연과 처리량만 최적화하지 않고 오류율과 가동률까지 묶어서 API 경험 전체를 최적화한다고 말한다.

발표자는 GLM 5.1 Pro에 대한 제공자 비교 화면을 보여 주며 FriendliAI가 빠를 뿐 아니라 99.9%가 넘는 가동률로 신뢰성도 높다고 했다.

자막에는 이 화면의 출처가 "open AAI snapshot"으로 들린다. 앞에서 보여 준 OpenRouter 화면과 같은 종류로 추정되지만 확실하지 않다.

08

진짜 벤치마크는 내 워크로드 10:50

발표자는 솔직하게 말한다. 이 행사장에 있는 곳을 포함해 많은 추론 제공자가 자기가 빠르다고 말한다. 어떤 곳은 실제로 빠르다. 하지만 특정 벤치마크, 특정 조건에서 그렇다.

당신의 애플리케이션에 정말 중요한 유일한 벤치마크는 당신의 워크로드다.발표자의 표현을 옮김, 11:00
  • 내 프롬프트
  • 내 토큰 길이
  • 내 트래픽 패턴
  • 내가 기대하는 지연 시간

그래서 발표자의 권고는 단순하다. 워크로드를 가져와서 속도, 신뢰성, 비용, 품질을 직접 시험해 보라는 것이다. 이 발표는 행사장 부스로 오라는 초대로 이어진다.

이 권고 자체는 제공자와 무관하게 옳다. 어느 제공자를 고르든 남의 벤치마크 대신 자기 워크로드로 재는 것이 맞다.

09

고객 사례: Kilo Code 11:40

마무리는 고객 사례다. Kilo Code는 큰 코딩 에이전트 플랫폼 중 하나로, 매주 수조 토큰을 처리한다. 지난 몇 년 동안 여러 추론 제공자를 시험했고, GLM 모델에 대한 분할 테스트split test에서 FriendliAI에 특히 좋은 인상을 받았다고 한다.

Kilo Code가 보고한 결과 (발표자 인용) 다른 여러 추론 제공자와 비교해 FriendliAI가 7배 넘게 빨랐고, 오류율도 눈에 띄게 낮았다.

이 수치는 고객의 증언을 발표자가 전한 것이다. 비교 대상 제공자, 측정 조건, 기간은 발표에 나오지 않았다. 앞에서 본 "2분 대 3분" 실험과 "7배"는 다른 조건의 다른 측정이므로 서로 더하거나 비교하지 않는 것이 좋다.

10

핵심 정리

  1. 오픈 웨이트 모델은 코딩, 추론, 에이전트 벤치마크에서 상용 최고 모델과 같은 급에 올랐다.
  2. 같은 게임을 만드는 데 GLM 5.2가 Claude Opus 4.8보다 5.6배 넘게 쌌다. 반복하는 에이전트 작업에서는 차이가 누적된다.
  3. 이제 질문은 "어느 모델"에서 "어느 제공자"로 옮겨 간다. 같은 모델이라도 제공자에 따라 지연, 처리량, 신뢰성이 다르다.
  4. 그 차이는 추론 스택 전체에서 나온다. 배칭, 스케줄링, 양자화, 추측 디코딩, 커널이 함께 맞물려야 한다.
  5. 에이전트 입력은 길고 50~90%가 반복된다. 접두사 KV 캐시를 재사용하면 프리필 비용과 TTFT가 줄어든다.
  6. 캐시 재사용은 캐시 인식 라우팅과 GPU·CPU·디스크 캐시 계층이 있어야 규모에서 작동한다.
  7. 추측 디코딩은 후보 토큰을 미리 제안하고 한 번에 검증한다. 품질은 그대로, 토큰당 출력 시간만 줄어든다.
  8. 모델 기반 추측은 수락률이 높지만 비싸고, 모델 없는 추측은 싸지만 조건이 맞아야 한다. 최선의 전략은 워크로드에 따라 바뀐다.
  9. 신뢰성은 속도의 일부다. 에이전트는 호출 하나만 실패해도 작업 전체가 무효가 된다.
  10. 남의 벤치마크보다 내 워크로드로 직접 재는 것이 유일하게 의미 있는 벤치마크다.
11

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 "질문이 바뀌었다"고 말한 이유는?
오픈 웨이트 모델이 쓸 만한지는 많은 워크로드에서 이미 답이 났다. 다음 질문은 프로덕션에서 얼마나 빠르고 안정적으로 돌릴 수 있느냐다.
Q2타워 디펜스 실험에서 품질과 비용은 각각 어땠나?
두 모델 모두 비슷한 구조와 품질의 게임을 만들었다. 비용은 GLM 5.2가 Claude Opus 4.8보다 5.6배 넘게 쌌다.
Q3모델도 같고 에이전트도 같은데 결과 시간이 달랐던 실험은 무엇을 보여 주나?
제공자 자체가 사용자 경험을 바꾼다. 차이는 모델이 아니라 캐시, 라우팅, 양자화, 커널 같은 추론 스택 전체에서 나온다.
Q4에이전트 워크로드에서 연산 비용 대부분이 프리필에 있는 이유는?
입력이 1만 토큰을 넘을 만큼 길고 출력은 짧다. 프리필은 입력 전체를 읽어 KV 캐시를 만드는 단계라 비용이 몰린다.
Q5접두사 캐시 재사용이 줄이는 지표는?
첫 토큰까지의 시간(TTFT)과 GPU 연산량. 이전 요청과 같은 앞부분의 KV 캐시를 재사용해 프리필 계산을 건너뛴다.
Q6캐시 인식 라우팅이 없으면 어떤 일이 생기나?
KV 캐시는 각 복제본에 따로 있다. 요청이 캐시를 가진 복제본이 아닌 곳으로 가면 접두사를 다시 계산해야 해서 재사용의 이점이 사라진다.
Q7캐시 계층의 세 단계는?
뜨거운 캐시는 GPU 메모리, 미지근한 캐시는 CPU RAM, 차가운 캐시는 NVMe나 디스크. 덜 쓰는 블록을 아래로 내리고 필요하면 다시 올린다.
Q8추측 디코딩이 출력 품질을 바꾸지 않는 이유는?
후보 토큰은 제안일 뿐이고, 원래 목표 모델이 한 번의 순전파로 검증한다. 받아들여진 토큰만 쓰므로 결과는 원래 모델이 만들었을 것과 같다.
Q9모델 기반 추측과 모델 없는 추측의 트레이드오프는?
모델 기반은 작은 초안 모델을 써서 수락률이 높지만 추가 연산이 든다. 모델 없는 방식은 프롬프트나 이전 출력의 패턴을 써서 싸지만, 출력이 기존 문맥과 닮을 때만 잘 된다.
Q10에이전트 워크로드에서 신뢰성이 더 중요한 이유는?
작업 하나에 모델 호출이 여러 번 들어간다. 중간에 하나만 타임아웃이나 5xx, 429로 실패해도 작업 흐름 전체가 무효가 된다.
Q11발표자가 말한 "유일하게 의미 있는 벤치마크"는?
내 워크로드. 내 프롬프트, 내 토큰 길이, 내 트래픽 패턴, 내가 기대하는 지연 시간으로 직접 재야 한다.

용어 정리

용어뜻
오픈 웨이트 모델Open-weight model. 학습된 가중치를 공개해 누구나 내려받아 돌릴 수 있는 모델
추론Inference. 학습이 끝난 모델에 입력을 넣어 출력을 얻는 일
추론 제공자Inference provider. 모델을 서버에서 돌려 API로 제공하는 회사
지연 시간Latency. 요청을 보내고 응답을 받기까지 걸리는 시간
처리량Throughput. 단위 시간에 처리하는 요청이나 토큰의 양
TTFTTime To First Token. 요청 후 첫 토큰이 나올 때까지의 시간
토큰당 출력 시간Time per output token. 토큰 하나를 만드는 데 걸리는 평균 시간
프리필Prefill. 모델이 입력 전체를 읽고 KV 캐시를 만드는 단계
디코딩Decode. 출력 토큰을 하나씩 만드는 단계
KV 캐시KV cache. 앞서 읽은 토큰들의 중간 계산값(키와 값)을 저장해 두는 메모리
접두사 캐시Prefix cache. 요청 앞부분이 같을 때 그 부분의 KV 캐시를 재사용하는 것
캐시 인식 라우팅Cache-aware routing. 요청을 해당 접두사 캐시를 이미 가진 복제본으로 보내는 것
복제본Replica. 같은 모델을 돌리는 여러 서버 인스턴스 중 하나
캐시 계층Cache hierarchy. GPU 메모리, CPU RAM, 디스크 순으로 캐시를 나눠 두는 구조
자기회귀 디코딩Autoregressive decoding. 순전파 한 번에 토큰 하나를 만들고 그걸 다시 입력에 붙여 다음을 만드는 방식
추측 디코딩Speculative decoding. 후보 토큰 여러 개를 미리 제안하고 원래 모델이 한 번에 검증하는 기법
초안 모델Draft model. 추측 디코딩에서 후보 토큰을 빠르게 제안하는 작은 모델
수락률Acceptance rate. 제안된 후보 토큰 중 원래 모델이 받아들인 비율
배칭Batching. 여러 요청을 묶어 GPU에서 한 번에 처리하는 것
양자화Quantization. 가중치의 숫자 정밀도를 낮춰 메모리와 연산을 줄이는 것
커널Kernel. GPU에서 실제 행렬 연산을 수행하는 저수준 코드
5xx 오류서버 쪽 문제로 요청이 실패했음을 뜻하는 HTTP 응답 코드
429요청 제한(rate limit)에 걸려 거부됐음을 뜻하는 HTTP 응답 코드
가동률Uptime. 서비스가 정상 동작한 시간의 비율
분할 테스트Split test. 트래픽을 나눠 여러 대안을 같은 조건에서 비교하는 실험
