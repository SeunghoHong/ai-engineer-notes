버그 리포트에서 프로덕션 코드까지

에이전트를 하나씩 부리던 단계가 지나고, 에이전트를 묶은 시스템이 버그 리포트를 받아 프로덕션 코드를 내놓는 단계가 오고 있다. 발표자는 이 시스템을 소프트웨어 팩토리라 부르고, 좁은 일부터 자동화해 신뢰를 쌓고 토큰이 아니라 결과를 재라고 말한다.

원본 영상: The Software Factory: From Bug Report to Production Code 발표: Davis Palmie · Factory 기술 스태프 · Lummetric(추정) 공동 창업자

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 확실하지 않은 것에는 (추정)을 붙였다. 발표자는 에이전트 제품을 만드는 Factory 소속이고, 발표 곳곳에 자기 회사 제품 이야기가 섞여 있다. mm:ss는 영상 위치다.

3분 요약
  1. AI 엔지니어링은 자동완성, 파일 생성, 에이전트 순으로 올라왔다. 다음 단계는 에이전트를 묶은 시스템, 곧 소프트웨어 팩토리다.
  2. 팩토리는 버그 리포트나 사용자 피드백 같은 입력 신호를 받아 프로덕션 코드를 내놓는다. 엔지니어는 가드레일을 관리하고 방향을 정한다.
  3. 코드 작성은 원래 병목이 아니었다. 리뷰, 버그 재현, 문서 갱신, 테스트 관리, 팀 사이 소통이 더 오래 걸린다.
  4. 한꺼번에 다 자동화하지 않는다. 인시던트 분류처럼 좁고 확인하기 쉬운 일부터 시작해 신뢰를 쌓는다.
  5. 원칙은 세 가지다. 모델에 묶이지 않기, 배포 방식은 우리가 정하기, 개발 전 과정을 잇기. 발표자는 같은 코드 리뷰 성능을 절반 가격에 낸 사례를 들었다.
  6. 에이전트가 일하기 좋은 코드베이스는 사람에게도 좋다. 에이전트 준비도 8가지(린터, 빌드, 테스트, 문서, 개발 환경, 모듈 구조, 관측, 보안)를 점검한다.
  7. 토큰이 아니라 결과를 잰다. 신호에서 프로덕션까지 걸린 시간, 사람 개입 횟수, PR당 비용 같은 것이다.
01

AI 엔지니어링의 세 시대 00:50

발표자는 AI 엔지니어링이 세 시대를 거쳐 왔다고 본다. 시대가 바뀔 때마다 AI가 맡는 단위가 커졌다.

시대AI가 하는 일엔지니어의 자리
탭 자동완성다음 토큰을 예측해 다음 몇 글자를 채운다여전히 운전석에 앉아 직접 쓴다
파일 생성파일을 통째로 만든다결과를 골라 붙여 넣는다. 출력은 여전히 사람이 쥐고 있다
에이전트스스로 맥락을 모으고, 도구를 부르고, 자기 결과를 디버깅한다에이전트를 감독한다
다음: 팩토리에이전트들을 묶은 시스템이 입력 신호를 프로덕션 코드로 바꾼다시스템을 짓고 방향을 정한다

자동완성은 처음에 마법처럼 느껴졌다. 지금은 추억거리다. 발표자는 이 흐름을 추상화 사다리abstraction ladder로 설명한다. AI가 다루는 단위가 토큰에서 파일로, 맥락으로, 이제 시스템 전체로 올라간다.

발표자의 주장은 이렇다. 사다리를 한 칸 오를 때마다 엔지니어는 덜 중요해진 게 아니라 더 중요해졌다.

02

소프트웨어 팩토리란 02:00

발표자는 지금을 전환점으로 본다. 엔지니어는 코드를 치는 사람에서 에이전트를 다스리는 사람으로 바뀐다. 결국 그 에이전트들을 하나의 시스템으로 묶게 된다. 그 시스템이 소프트웨어 팩토리software factory다.

지금까지코드를 직접 친다AI는 옆에서 거든다
→
앞으로에이전트 시스템을 다스린다코드는 시스템이 만들고, 사람은 기준과 방향을 맡는다
시스템이 하는 일
  • 버그 리포트, 사용자 피드백 같은 입력 신호input signal를 받는다
  • 그 신호를 프로덕션 코드로 바꿔 내놓는다
엔지니어가 하는 일
  • 가드레일guardrails을 조인다. 에이전트가 벗어나지 않게 정해 둔 규칙과 검사다
  • 코드 드리프트code drift를 잡는다. 코드가 의도한 설계에서 조금씩 멀어지는 현상이다
  • 큰 우선순위와 방향을 정한다
03

모두가 묻는 네 가지 02:40

AI가 사람보다 코드를 더 많이 만들게 되면 누구나 묻는 질문이 있다. 발표자는 네 가지를 꼽고 답했다.

질문발표자의 답
비용 폭주를 어떻게 막나한 모델 회사에 묶이지 않으면 비용과 성능의 모든 조합을 고를 수 있다. 일마다 꼭 필요한 성능만 가장 싸게 쓴다.
지금 최고 모델을 어떻게 계속 쓰나어느 한 회사에 거는 것부터 잘못된 선택지다. 오픈소스 모델도 계속 좋아진다. 일마다 맞는 모델을 고르거나 자동으로 배정dynamic routing한다.
엔지니어는 어떻게 되나제품과 엔지니어링의 경계가 흐려진다. 엔지니어는 코드를 만드는 시스템을 짓고 유지한다. 팩토리의 큰 방향도 정한다.
조직은 어떻게 바뀌나팀 경계도 흐려진다. 맥락이 경계를 넘어 막힘없이 흘러야 한다. 정보가 팀마다 갇혀 있으면 사람보다 에이전트가 더 곤란하다.
아이에게 대수학 과외 선생님이 필요하다면, 아인슈타인보다 싼 사람은 얼마든지 찾을 수 있다.Factory CEO의 말이라며 발표자가 옮긴 비유 03:20

일마다 필요한 만큼의 성능만 쓰라는 뜻이다. 모든 일에 가장 비싼 모델을 쓸 필요는 없다.

비용 질문의 배경으로 발표자는 기사 두 건을 들었다. Uber CTO가 4월에 이미 그해 AI 예산을 다 썼다는 기사와, Microsoft가 비용을 줄이려 Claude Code 라이선스를 거둬들였다는 기사다. 발표자가 인용한 것이고 기사 원문은 확인하지 않았다.

비용과 모델 선택에 대한 답은 여러 모델을 고를 수 있다는 Factory 제품의 장점과 겹친다. 감안해서 읽자.

04

병목은 코딩 밖에 있다 05:00

발표자는 코딩이 쉬운 부분이었고 원래 병목이 아니었다고 말한다. 대신 실제 엔지니어링 지표를 보라고 한다.

  • PR 하나를 리뷰하는 데 걸리는 시간의 중앙값은 얼마인가?
  • 사용자 버그 리포트를 재현하는 데 얼마나 걸리나? 디버깅은?
  • PR마다 문서를 최신으로 고치는 사람은 누구인가? 전략 회의 뒤에는?
  • 테스트 스위트는 누가 관리하나?

테스트 팀, 엔지니어링 팀, 제품 팀은 흔히 서로 다른 대륙에 있는 것처럼 떨어져 일한다. 발표자는 DORA 지표DORA metrics로 코드를 쓴 시점부터 프로덕션에 나가기까지의 시간을 재 보라고 한다. 그 시간이 실제로 코드를 고치는 시간보다 훨씬 길 거라고 장담한다. 데이터를 보여 준 것은 아니고 발표자의 예상이다.

정말 필요한 것은 연결 지금은 문서가 낡고, 죽은 코드가 남고, 팀 사이에 소통 단계가 겹겹이 있다. 사람에게도 힘든 일이지만 에이전트에게는 더 힘들다. 팩토리를 지으려면 에이전트가 이 모든 곳을 오가며 조직의 미묘한 사정까지 이해해야 한다.

팩토리가 맡는 일 06:20

그래서 팩토리는 입력 신호에서 프로덕션 배포까지 이어지는 에이전트 시스템이다. 에이전트는 코딩만 하지 않는다. 고객 지원, 제품 엔지니어링, 배포 운영 같은 역할도 맡는다. 이 기둥들을 따라 에이전트가 하는 일은 이렇다.

  1. 인시던트를 분류한다
  2. 계획을 세운다
  3. 문서를 만들고 고친다
  4. 코드 작업을 실제로 한다
  5. 리뷰한다
  6. 테스트한다
  7. 배포한다
  8. 배포 뒤 릴리스를 지켜본다
05

좁게 시작해 신뢰 쌓기 07:00

이 일을 한꺼번에 자동화하려 들면 안 된다. 이유는 두 가지다.

  • 일이 너무 크다.
  • 팀이 이 시스템을 믿게 될 시간이 없다.

처음에는 좁고 결과를 확인하기 쉬운 일을 고른다. 발표자의 예는 인시던트 분류incident triage다. 들어온 장애 알림의 원인과 심각도를 먼저 가려내는 일이다.

  1. 에이전트가 Sentry 알림을 읽는다.
  2. 트레이스와 다른 맥락을 모은다.
  3. 진단 결과를 Slack에 올린다.
  4. 무엇을 할지는 엔지니어가 검토하고 정한다.

맞는 진단이 하나둘 쌓이면 팀은 이 단계를 믿고 이해하게 된다. 단계마다 책임자와 모니터링을 붙인다. 파이프라인을 루프로 돌리는 건 그다음 일이다.

루프가 닫히면 08:00 시스템이 내놓은 결과를 처음 들어온 신호와 이어 볼 수 있게 되면, 그때부터 조직이 스스로 나아질 수 있다고 발표자는 말한다.
06

세 가지 원칙 08:10

발표자는 소프트웨어 팩토리가 지켜야 할 원칙 세 가지를 든다.

원칙 1 · 모델 비종속

모델 비종속model agnostic은 한 모델 회사에 묶이지 않는 것이다. 모델마다 잘하는 일이 다르고 비용 효율도 크게 다르다.

  • 코드 리뷰에서 GPT-5.2가 최신 Opus 모델과 같은 성능을 절반 가격에 냈다
  • 오픈소스 대안은 비용을 10~30배 낮춘다
  • 묶이지 않으면 속도, 성능, 비용의 파레토 프런티어Pareto frontier 전체를 쓸 수 있다

요점: 일마다 필요한 만큼의 성능을 가장 싸게 쓴다.

원칙 2 · 배포 주권 08:50

배포 주권sovereign deployment은 보안 구조나 정책을 AI 도입에 맞춰 굽히지 않는 것이다.

  • Factory는 작업 공간과 배포 방식을 고를 수 있게 한다고 했다
  • 완전 관리형부터 자기 장비에서 돌리기, 외부망과 완전히 끊긴 환경air-gapped까지 지원한다고 했다

요점: AI가 회사 정책에 맞춘다. 반대가 아니다.

원칙 3 · SDLC 통합 09:20

소프트웨어 개발 전 과정SDLC의 단계들은 더 이상 따로 노는 문제가 아니다.

  • 문서가 바뀌면 코드에 반영되고, 코드가 바뀌면 문서에 반영된다
  • 계획 단계의 목표가 무엇을 테스트할지 정한다
  • 전략, 제품, 엔지니어링, 테스트 팀 사이의 여러 소통 단계를 거치지 않는다

요점: 기둥 하나가 약하면 시스템 전체가 약하다.

GPT-5.2와 Opus 비교는 Factory가 자체적으로 얻은 결과라고 발표자가 말한 것이다. 측정 방법은 발표에 나오지 않는다. 여러 모델을 쓸 수 있다는 점과 배포 방식 선택지는 Factory 제품이 내세우는 장점이기도 하니 감안해서 읽자.

07

AI 네이티브 조직의 모습 10:00

AI를 중심에 두고 일하는 조직AI-native org에서는 여러 하위 팀이 하나의 소프트웨어 팩토리 아래로 합쳐진다. 그리고 조금씩 자동화된다. 발표자가 자주 본다는 패턴은 이렇다.

영역에이전트가 하는 일
신호 분류Sentry 알림 같은 신호를 분류한다. 사람이 호출에 응답하기도 전에 진단을 내놓는다
보안비밀 정보 유출과 취약점을 미리 스캔한다
테스트테스트를 만들고 유지한다. 깨지기 쉽거나 필요 없어진 테스트를 찾아낸다
문서문서를 코드와 맞춘다. 여러 회의 채널에서 정한 내용과도 맞춘다
리뷰와 배포코드를 리뷰하고 PR에 코멘트를 단다. 롤아웃을 하고 릴리스를 지켜본다

에이전트가 이 일을 맡으면 엔지니어의 일이 바뀐다 11:00. 엔지니어는 판단을 내리고 AI를 바로잡는다. 바로잡을 때는 AI가 그 실수에서 배울 수 있는 방식으로 한다.

개선은 팀을 넘어 전해진다. 한 팀에서 나아진 것이 시스템 전체를 낫게 한다.

08

O(N)에서 O(1)로 11:20

회사가 크고 조각나 있을수록 관리 부담이 팀 수에 비례해 커진다. 발표자는 팩토리가 이 부담을 O(N)에서 O(1)로 바꾼다고 말한다. 여기서 N은 팀 수다.

지금까지 · O(N)팀마다 따로 관리한다가드레일, 문서, 테스트 정책이 팀 수만큼 생긴다
→
팩토리 · O(1)한 번 정의해 전체에 적용한다가드레일, 에이전트, 문서, 테스트 정책, 거버넌스를 하나의 표준으로
  • 표준은 가장 낮은 수준에 맞추지 않는다. 모두를 가장 높은 기준으로 끌어올린다.
  • 에이전트가 여러 팀을 오가며 품질 기준을 지킨다. 그래서 관리 시간을 팀 수만큼 늘릴 필요가 없다.
  • 맥락이 한곳에 모인다. 경영진은 개발 전 과정이 어떻게 돌아가는지 볼 수 있다.

발표자는 "보수적으로 잡아도" O(1)이라고 했다. 하지만 O(1)은 팀이 아무리 늘어도 관리 부담이 그대로라는 뜻이라 가장 낙관적인 표현이다. 측정 결과가 아니라 방향을 말한 비유로 읽는 편이 맞다.

어디서나 같은 에이전트 12:30

모델에 묶이지 않듯, 에이전트는 쓰는 곳에도 묶이지 않아야 한다. 발표자는 이를 surface agnostic이라 부른다. 팀은 AI 공급자에 맞추려고 자기 프로세스나 도구를 바꾸지 않아야 한다.

사람과 에이전트가 쓰는 도구는 다를 수 있다. 그래도 그 밑의 하네스harness와 맥락은 같아야 한다. 하네스는 모델을 감싸 도구, 규칙, 검사를 정해 주는 실행 틀이다.

발표자는 Factory 에이전트를 원격 머신, CLI, Slack 등 팀이 쓰는 곳 어디서나 쓸 수 있다고 소개했다. 자기 회사 제품 설명이니 감안해서 읽자.

09

에이전트 준비도 8가지 13:10

팩토리를 짓다 보면 숨어 있던 것이 드러난다. 몇몇 사람 머릿속에만 있는 지식tribal knowledge, 손으로 하는 절차, 낡은 정보다. 이걸 풀면 에이전트도 빨라지고 엔지니어 팀도 빨라진다.

Factory는 에이전트 준비도agent readiness라는 기준으로 코드베이스를 8가지 축에서 평가한다 13:30.

축점검 질문
1. 검증린터, 포매터 같은 가드레일이 있나?
2. 빌드 시스템빌드 명령과 CI가 문서로 잘 정리돼 있나?
3. 피드백 루프단위 테스트와 통합 테스트가 촘촘한가?
4. 문서README, AGENTS.md 같은 문서가 있나?
5. 개발 환경에이전트가 쓸 수 있을 만큼 깔끔하게 재현되나?
6. 코드 구조모듈 경계가 분명한가? 코드가 무질서하게 퍼지지 않게 막는 규칙이 있나?
7. 관측 가능성뭔가 잘못됐을 때 원인을 찾는 데 얼마나 걸리나?
8. 보안비밀 정보 유출과 취약점을 미리 스캔하나?
에이전트와 사람 엔지니어가 같은 길을 걷는다면, 그 길을 잘 닦는 일은 두 배로 쓸모 있다.발표자의 표현을 옮김 14:30

8개 축의 이름은 자막에서 들린 대로 나눴다. 3번(테스트)과 4번(문서)은 한 문장에 이어서 나와 경계가 분명하지 않다. 에이전트 준비도는 Factory가 내세우는 평가 방식이라는 점도 감안하자.

10

거버넌스와 사람의 자리 14:40

보이지 않는 것은 다스릴 수 없다. 에이전트에게도 사람 엔지니어에게도 마찬가지다.

  • 준비도 점검부터 시작해도 된다. 그래도 엔지니어는 에이전트의 성과를 지켜보고 행동을 통제해야 한다.
  • 발표자에 따르면 Factory에서는 모든 행동을 감사audit할 수 있다. 역할 기반 접근 제어RBAC와 최소 권한least privilege 원칙 아래 돌아간다.
  • 팩토리를 짓는 팀은 먼저 신뢰와 이해를 쌓아야 한다. 그래서 단계적으로 펼친다. 기둥 하나하나를 먼저 자동화하고, 시스템을 루프로 잇는 건 그 뒤다.

사람이 남는 자리 15:30

정확하게 실행한다고 나쁜 설계가 막아지지는 않는다. 예전에도 그랬다. 그래서 아키텍처, 전략, 방향 설정에는 여전히 사람이 있어야 한다.

엔지니어는 대체되지 않는다. 다만 중요한 능력이 바뀐다 판단과 우선순위가 손으로 구현하는 기술보다 중요해진다. 에이전트가 모든 걸 처리하지는 못한다. 조여야 할 가드레일이 생기고, 설계에서 벗어나는 코드가 생긴다. 사람은 이 팩토리의 검증 관문validation gate으로 서야 한다.

이제 펀치 카드를 기계에 넣지 않는다. 마찬가지로 코드도 손으로 쓸 필요가 없다. 팀은 전략과 감수할 위험의 범위를 정하고, 실행은 에이전트에게 맡긴다.

11

토큰 말고 결과를 잰다 16:20

에이전트가 일을 잘하는지는 무엇을 재느냐에 달려 있다. 발표자의 답은 토큰이 아니라 결과를 재라는 것이다.

재기 쉬운 것토큰 사용량, 코드 줄 수쉽게 부풀릴 수 있고 결과와 이어지지 않는다
→
재야 할 것실제 결과신호에서 프로덕션까지 걸린 시간, 사람 개입 횟수 같은 것

큰 회사의 토큰 순위표token leaderboard는 돈을 펑펑 쓰게 만들 뿐이다. 발표자는 이를 눈앞에서 벌어지는 굿하트의 법칙Goodhart's law이라 부른다 16:50. 토큰 사용량을 재기 시작하면 엔지니어는 토큰을 더 쓰는 쪽으로 움직인다. 그 순간 그 숫자는 좋은 지표가 아니게 된다.

중요한 건 누가 토큰에 가장 많이 썼느냐가 아니다. 같은 지출로 누가 가장 큰 성과를 냈느냐다.

12

결론 17:30

  • 에이전트 준비도는 효과적인 엔지니어링의 전제 조건이다. 그 자리에 에이전트가 오든 사람이 오든 같다.
  • 에이전트도 엔지니어와 똑같이 꼼꼼하게 관리한다. 도구, 접근 권한, 리뷰 체계가 모두 필요하다. 코드베이스에 그냥 풀어 놓지 않는다.
  • 토큰을 최대한 쓰는 걸 목표로 삼지 않는다token maxing. 정말 중요한 것을 잰다.
  • 사용자는 회사가 AI에 얼마를 쓰는지 관심 없다. 팩토리가 가져올 큰 개선을 체감하고 싶어 한다.
발표 내용을 시작 순서로 묶으면
  1. 에이전트 준비도 8가지로 코드베이스를 점검한다.
  2. 인시던트 분류처럼 좁고 확인하기 쉬운 일 하나를 자동화한다.
  3. 맞는 결과가 쌓이면 기둥을 하나씩 늘린다. 기둥마다 책임자와 모니터링을 둔다.
  4. 토큰이 아니라 결과 지표로 잰다.
  5. 기둥이 다 선 뒤에 결과를 입력 신호와 이어 루프를 닫는다.
발표 곳곳의 조언을 순서대로 묶은 것이다. 발표자가 이 순서를 직접 제시하지는 않았다.
13

핵심 정리

  1. AI 엔지니어링은 토큰, 파일, 맥락, 시스템 순으로 다루는 단위를 키워 왔다. 다음은 에이전트를 묶은 소프트웨어 팩토리다.
  2. 팩토리는 버그 리포트, 사용자 피드백 같은 입력 신호를 받아 프로덕션 코드를 내놓는다.
  3. 엔지니어는 가드레일을 조이고, 코드 드리프트를 잡고, 방향을 정한다.
  4. 코딩은 원래 병목이 아니었다. 리뷰, 재현, 문서, 테스트, 팀 사이 소통이 더 오래 걸린다.
  5. 한꺼번에 하지 않는다. 좁고 확인하기 쉬운 일부터 자동화해 신뢰를 쌓는다.
  6. 원칙 세 가지: 모델 비종속, 배포 주권, SDLC 통합.
  7. 발표자가 인용한 수치: 코드 리뷰에서 GPT-5.2는 최신 Opus와 같은 성능을 절반 가격에 냈다. 오픈소스는 10~30배 싸다.
  8. 기준과 거버넌스를 한 번 정의해 전체에 적용하면, 팀 수에 비례하던 관리 부담이 줄어든다.
  9. 에이전트 준비도 8가지를 닦으면 에이전트와 사람이 함께 빨라진다. 에이전트도 권한, 감사, 리뷰 아래 둔다.
  10. 토큰이 아니라 결과를 잰다. 토큰 순위표는 굿하트의 법칙에 빠진다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1AI 엔지니어링의 세 시대는 무엇이고, 다음 단계는 무엇인가?
탭 자동완성, 파일 생성, 에이전트. 다음은 에이전트들을 하나의 시스템으로 묶은 소프트웨어 팩토리다.
Q2소프트웨어 팩토리의 입력과 출력은?
입력은 버그 리포트, 사용자 피드백 같은 신호다. 출력은 프로덕션 코드다.
Q3팩토리에서 엔지니어가 맡는 세 가지 일은?
가드레일을 조이고, 코드 드리프트를 잡고, 큰 우선순위와 방향을 정한다.
Q4발표자가 "코딩은 병목이 아니었다"며 대신 짚은 것들은?
PR 리뷰 시간, 버그 재현과 디버깅, 문서 최신화, 테스트 스위트 관리, 팀 사이 소통. 코드를 쓴 뒤 프로덕션까지 가는 시간이 실제 코드 수정 시간보다 길다고 봤다.
Q5처음부터 전체 파이프라인을 자동화하지 말라는 두 가지 이유는?
일이 너무 크다. 그리고 팀이 시스템을 믿게 될 시간이 없다.
Q6첫 자동화 대상으로 든 예와 그 흐름은?
인시던트 분류. 에이전트가 Sentry 알림을 읽고, 트레이스와 맥락을 모으고, 진단을 Slack에 올린다. 무엇을 할지는 엔지니어가 정한다.
Q7소프트웨어 팩토리의 세 원칙은?
모델 비종속, 배포 주권, SDLC 통합.
Q8모델 비종속을 뒷받침하려고 든 비용 수치는?
코드 리뷰에서 GPT-5.2가 최신 Opus와 같은 성능을 절반 가격에 냈다. 오픈소스 대안은 10~30배 싸다. 둘 다 발표자가 인용한 수치다.
Q9"O(N)에서 O(1)로"는 무슨 뜻인가? 어떻게 읽어야 하나?
팀마다 따로 관리하면 부담이 팀 수만큼 커진다. 기준을 한 번 정의해 전체에 적용하면 팀 수와 거의 무관해진다는 뜻이다. 다만 측정값이 아니라 방향을 말한 비유로 읽는다.
Q10에이전트 준비도 8가지 축은?
검증(린터, 포매터), 빌드 시스템, 피드백 루프(테스트), 문서, 개발 환경, 코드 구조, 관측 가능성, 보안.
Q11토큰 사용량을 성과 지표로 삼으면 왜 안 되나?
쉽게 부풀릴 수 있고 실제 결과와 이어지지 않는다. 재기 시작하면 사람들이 그 숫자를 늘리는 쪽으로 움직인다. 굿하트의 법칙이다.
Q12대신 재라고 한 지표 5개는?
신호에서 프로덕션까지 걸린 시간, 사람 개입 횟수, 수리 시간 중앙값, 코드 수명, PR당 비용.
