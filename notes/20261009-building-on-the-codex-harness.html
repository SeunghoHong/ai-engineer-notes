Codex 하네스 위에 내 앱 짓기

Codex를 움직이는 하네스는 앱 서버라는 프로토콜로 감싸져 있고, 누구나 이 프로토콜로 자기 앱에 Codex를 넣을 수 있다. 하네스를 직접 만들지 말고 이걸 가져다 쓰되, 버전은 직접 묶어 배포하고, 지시는 덧붙이고, 도구는 필요할 때만 불러오게 하라는 것이 요지다.

원본 영상: Building on the Codex Harness 발표: Dominik Kundel (OpenAI, Codex 개발자 경험 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고(예: Cloud Code → Claude Code), 확실하지 않은 이름에는 "(추정)"을 붙였다. 발표자는 OpenAI에서 Codex를 맡고 있어서, 이 발표는 자사 제품 소개이기도 하다. mm:ss는 영상 위치다.

3분 요약
  1. 앱 서버는 Codex 하네스를 감싼 프로토콜이다. Codex 앱, IDE 확장, Xcode, JetBrains, Claude Code용 Codex 플러그인이 모두 이걸로 돈다.
  2. 하네스와 앱 서버는 Apache 2.0 오픈소스다. Responses API와 호환되면 다른 모델 제공자도 붙일 수 있다.
  3. Codex 앱의 주요 기능이 거의 다 메시지로 열려 있다. 클라이언트 메시지만 120개가 넘는다.
  4. 에이전트는 세 군데에서 맞춘다. 개발자 지시를 덧붙이고, 동적 도구를 넘기고, 스레드별 설정(모델, 샌드박스)을 바꾼다.
  5. 앱 서버는 Codex CLI와 같은 바이너리다. 프로토콜이 버전마다 바뀌니 내 앱에 묶어 배포하고, 그 버전의 타입 정의를 뽑아 쓴다.
  6. 붙이는 길은 Python SDK, 또는 문서를 주고 Codex에게 구현시키기다. 채팅 화면이 아니어도 된다. 발표자는 Doom 게임 안에 Codex를 넣어 시연했다.
  7. 세 가지 팁: 하네스 버전을 직접 실어 보낸다. 새 도구는 지연 로딩으로 연다. 시스템 프롬프트를 새로 쓰기 전에 개발자 지시부터 덧붙인다.
01

앱 서버란 무엇인가 01:10

에이전트 하네스agent harness는 모델을 감싸 도구, 지시, 실행 규칙을 정해 주는 실행 틀이다. 하네스를 처음부터 만드는 일은 부담스럽다. 발표자는 직접 만드는 대신 Codex 하네스 위에 지으라고 제안한다.

그 입구가 Codex 앱 서버Codex app server다. 앱 서버는 Codex 하네스를 감싼 프로토콜이다. 내 앱이 이 프로토콜로 하네스에 직접 붙어 깊이 연동할 수 있다. 개념은 에이전트 클라이언트 프로토콜Agent Client Protocol, ACP과 비슷하다.

클라이언트내가 만드는 앱Codex 앱, IDE 확장, 다른 회사 앱이 모두 이 자리에 있다
⇅ JSON-RPC 방식 메시지 · stdio 또는 WebSocket
서버Codex 앱 서버하네스를 감싼 프로토콜. 클라이언트 메시지 120개 이상
⇅
하네스Codex 하네스시스템 프롬프트, 도구, 샌드박스, 스레드를 다룬다
⇅ Responses API 호환 API
모델OpenAI 모델 또는 다른 제공자LM Studio, Ollama는 간편 설정이 있다

이 그림은 발표 내용을 바탕으로 이 노트에서 그린 것이다. 발표 화면을 옮긴 것이 아니다.

  • 오픈소스다. 하네스와 앱 서버 모두 공개돼 있다. 라이선스는 Apache 2.0이라 포크해서 마음대로 고쳐도 된다.
  • 속이 궁금하면 Codex에게 저장소를 읽히면 된다. 내부 동작은 다음 날 오후 별도 세션에서 더 다룬다고 했다.
  • 다른 모델도 붙는다. Responses API와 호환되는 API를 가진 제공자라면 연결할 수 있다.
02

이미 쓰고 있는 곳 02:10

앱 서버 프로토콜은 JSON-RPC 방식이다. JSON-RPC는 JSON 메시지로 상대에게 "이 기능을 실행해 달라"고 요청하는 약속이다. OpenAI는 자기 제품도 모두 이 프로토콜 위에 만든다.

구분앱 서버 위에서 도는 것

다른 에이전트 안Claude Code용 Codex 플러그인. Claude Code에서 Codex에게 코드 리뷰를 맡기거나 작업을 넘긴다. 올해 초 같은 앱 서버로 만들었다

모두 같은 하네스, 같은 앱 서버를 쓴다. 어느 화면에서 Codex를 쓰든 뒤에서 도는 엔진은 하나다.

03

실제 메시지 들여다보기 03:10

클라이언트는 내가 만드는 앱이다. 서버는 Codex 앱 서버다. 둘은 메시지를 주고받는다. 클라이언트는 동작을 요청하고, 서버는 진행 상황을 이벤트로 보낸다.

발표자는 가상의 예시 대신 실제 메시지를 보여 주려고 검사 도구inspector를 만들었다. 실제 Codex 앱과 앱 서버 사이를 오가는 이벤트를 가로채 보여 주는 도구다. 이 도구를 Codex 앱 안의 브라우저에 띄우고 메시지를 하나 보냈다. 03:50

  • 스레드 시작: 어떤 설정으로, 어느 프로젝트에서 일하는지가 담긴다
  • 설정 읽기: 클라이언트가 현재 설정을 조회한다
  • 델타 메시지: 모델의 응답이 조각조각 흘러 들어온다

처음엔 복잡해 보이지만 하나씩 보면 익숙한 내용이다. 핵심은 Codex 앱의 주요 기능이 거의 다 메시지로 열려 있다는 점이다. 응답 스트리밍도, 파일 검색도 앱 서버와 앱 사이를 메시지로 오간다. 그래서 내 앱도 같은 기능을 그대로 쓸 수 있다.

04

ACP와 다른 점, ChatGPT 로그인 06:10

ACP는 여러 에이전트에 두루 쓰도록 만든 일반 프로토콜이다. 앱 서버는 Codex 하네스 전용이다. 그래서 하네스의 개별 부분까지 프로토콜로 조정할 수 있다고 발표자는 설명한다.

ACP와의 비교는 앱 서버를 만든 쪽의 설명이다. 그 점을 감안해 읽자.

사용자가 자기 구독을 가져온다 06:30

앱 서버를 쓰면 ChatGPT로 로그인Sign in with ChatGPT 기능을 붙일 수 있다. 내 앱의 사용자가 자기 ChatGPT 구독으로 로그인한다. 사용량은 그 사용자의 Codex 사용 한도에서 빠진다. T3 Code 같은 앱이 이 방식을 쓴다.

이 노트의 해석 사용량이 사용자 쪽 한도에서 빠지므로, 앱을 만든 쪽이 사용자 몫의 모델 사용량을 따로 마련하지 않아도 되는 구조로 읽힌다.
05

에이전트를 내 앱에 맞추기 06:50

앱 서버 위에서 에이전트를 내 용도에 맞출 때 볼 곳은 세 군데다.

개발자 지시 · developer instructions

Codex의 시스템 프롬프트 뒤에 내 지시를 덧붙인다. 시스템 프롬프트 원문은 저장소에서 볼 수 있다.

  • 모델마다 다듬어 둔 기본 프롬프트를 그대로 살린다
  • 그 위에 내 앱에 필요한 지시만 얹는다

실제 사례: Codex 앱도 이렇게 한다. IDE 확장이나 CLI에는 없는 앱 전용 기능이 있어서다.

동적 도구 · dynamic tools 07:40

에이전트가 쓸 함수를 내 앱이 직접 정의해 넘긴다. MCP 같은 방법도 쓸 수 있지만, 그냥 도구를 정의해도 된다.

  • 도구를 지연 로딩deferred loading으로 표시할 수 있다
  • 표시한 도구는 시스템 프롬프트에 넣지 않는다
  • Codex가 도구 검색tool search으로 필요할 때 찾아 쓴다

효과: 도구 설명이 컨텍스트 창을 채우지 않는다. 도구 검색은 다음 날 세션에서 더 다룬다고 했다.

스레드별 설정 08:10

대화 하나, 곧 스레드 단위로 에이전트 설정을 바꿀 수 있다.

  • 모델 제공자를 바꾼다
  • 모델을 바꾼다
  • 샌드박스를 세밀하게 정한다. 어떤 네트워크에 접속할지, 어떤 파일을 고칠 수 있는지
06

앱 서버를 띄우는 법 08:40

  • Codex CLI와 같은 바이너리다. CLI가 이미 깔려 있다면 지금 바로 앱 서버를 띄울 수 있다.
  • Codex 앱은 바이너리를 앱 안에 싣는다. 설치된 Codex 앱 번들 안을 보면 들어 있다. 앱을 업데이트할 때마다 안에 든 CLI도 새 버전으로 바뀐다.
  • Windows에서는 두 개를 싣는다. Linux용과 Windows용이다. 앱을 WSL 모드로 열면 Linux용을 쓰고, 아니면 Windows 네이티브 앱 서버를 띄운다. 09:10

버전에 맞는 타입 정의 뽑기 09:30

Codex는 지금 쓰는 앱 서버 버전에 맞춰 TypeScript 바인딩이나 JSON 스키마를 생성해 준다. 이 프로토콜은 버전마다 자주 바뀐다. 그래서 이 기능이 특히 쓸모 있다.

같은 이유로 앱 서버를 내 앱에 함께 묶어 배포하라고 권한다. 그래야 내가 기대하는 버전의 기능을 내가 통제한다. Codex 앱이 바로 그렇게 한다.

전송 방식 10:00

앱 서버는 표준 입출력stdio이나 WebSocket으로 띄울 수 있다. 어느 쪽이 맞는지는 쓰임새에 따라 다르다. 발표자의 조언은 "Codex에게 물어보라"였다.

07

붙이는 두 가지 방법 10:20

방법 1 · Python SDK

최근 공개된 Python용 개발 도구 모음이다.

  • 앱 서버 프로세스를 켜고 끄는 관리를 대신 해 준다
  • ChatGPT 로그인 연동이 쉬워진다
  • 익숙한 형태의 인터페이스를 준다
방법 2 · Codex에게 시키기 10:40

발표자는 AI 엔지니어 행사이니 대부분 이쪽을 고를 거라고 했다.

  • Codex가 이 프로토콜을 아주 잘 구현한다고 한다
  • 보통 문서를 가리켜 주면 된다. 그것도 필요 없을 때가 많지만, 가끔은 문서로 방향을 잡아 주는 게 낫다
  • "macOS 앱 만들기" 같은 Codex 플러그인과 함께 쓸 수 있다

사례: 발표자는 Visual Basic으로 Windows 네이티브 클라이언트를 만들었다. 거의 한 번에 됐다고 한다.

에이전트를 만드는 세부 사항을 일일이 배우지 않고도, 짧은 시간에 쓸 만한 앱을 만들 수 있다는 것이 발표자의 주장이다.

"Codex가 이 프로토콜을 잘 구현한다", "거의 한 번에 됐다"는 Codex 담당자의 말이다. 내 환경에서 직접 확인해 보자.

08

채팅 창 밖으로: Doom 안의 Codex 11:30

  • 비디오 게임에 넣는다

한 달쯤 전 발표자는 "Codex 안에서 Doom을 돌리는 대신, Doom 안에서 Codex를 돌리면 어떨까"를 떠올렸다. 그리고 이를 무대에서 시연했다. 12:00

방식대화 없이 작업을 맡긴다메시지로 하네스를 직접 다룬다
잘 맞는 곳스크립트, CI/CD. 예: PR 자동 수정에이전트를 화면에 보여 주는 클라이언트
여러 작업 동시 실행exec 호출을 병렬로 돌리는 방법을 직접 짜야 한다새 스레드 이벤트를 여러 번 보내면 된다
제어 범위작업 단위하네스 전체

예를 들어 자체 평가 하네스를 돌리거나 /goal을 쓰려면 Codex 스레드를 여러 개 동시에 띄워야 한다. 이럴 때 앱 서버가 빛난다고 발표자는 말한다.

10

발표자의 세 가지 팁 15:50

팁 1 · 하네스를 직접 실어 보낸다 16:00

사용자가 설치한 CLI에 기대지 말고, 내 앱에 앱 서버 버전을 묶어 배포한다.

  • 깨지는 변경을 피한다. OpenAI도 줄이려 하지만, 실험 기능에 기대면 생길 수 있다
  • 사용자가 업데이트했는지 걱정할 필요가 없다
  • 업데이트하라고 재촉할 필요도 없다
팁 2 · 새 도구는 지연 로딩으로 16:30

내 앱의 기능을 도구로 적극 연다. 단, 지연 로딩으로 표시한다.

  • Codex 앱도 스레드 안에서 자기 자신을 조작하는 도구를 연다. 자동화를 띄우는 것이 그 예다
  • 지연 로딩이면 도구가 컨텍스트 창을 쓸데없이 채우지 않는다
  • 도구는 쓸 수 있게 남기면서 에이전트를 헷갈리게 하지 않는다
팁 3 · 개발자 지시부터 17:00

지시를 바꾸고 싶으면 기본 지시를 고치기 전에 개발자 지시를 덧붙여 본다.

  • 하네스 팀은 프롬프트가 모델에게 익숙한 형태in distribution로 남도록 계속 손본다
  • 그래야 에이전트가 잘 동작한다
  • 시스템 프롬프트를 새로 쓰면 그 작업을 모두 잃는다
하네스는 내 버전을 직접 실어 보내라.발표자의 말을 옮김 · "Ship your own version of the harness."
11

핵심 정리

  1. 앱 서버는 Codex 하네스를 감싼 JSON-RPC 방식 프로토콜이다. 하네스와 함께 Apache 2.0 오픈소스다.
  2. Codex 앱, IDE 확장, Xcode, JetBrains, T3 Code, Claude Code용 플러그인이 모두 같은 앱 서버 위에서 돈다.
  3. Codex 앱의 주요 기능이 거의 다 메시지로 열려 있다. 클라이언트 메시지는 120개가 넘는다.
  4. 발표자에 따르면 ACP보다 하네스를 세밀하게 조정할 수 있다. 사용자는 ChatGPT로 로그인해 자기 Codex 한도로 쓴다.
  5. 에이전트는 개발자 지시, 동적 도구, 스레드별 설정 세 군데에서 맞춘다.
  6. 앱 서버는 Codex CLI와 같은 바이너리다. stdio나 WebSocket으로 띄운다.
  7. 프로토콜은 버전마다 바뀐다. 그 버전의 타입 정의를 뽑아 쓰고, 앱 서버를 내 앱에 묶어 배포한다.
  8. 붙이는 길은 Python SDK, 또는 문서를 주고 Codex에게 구현시키기다.
  9. 채팅 창이 아니어도 된다. Doom 안의 Codex처럼 동적 도구로 내 앱을 조작하게 할 수 있다.
  10. codex exec는 스크립트와 CI용이다. 화면이 있는 클라이언트나 여러 스레드를 동시에 돌릴 때는 앱 서버를 쓴다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Codex 앱 서버는 무엇인가?
Codex 하네스를 감싼 JSON-RPC 방식 프로토콜이다. 클라이언트(내 앱)는 동작을 요청하고, 앱 서버는 진행 상황을 이벤트로 돌려준다.
Q2앱 서버 위에서 도는 제품을 세 가지 들면?
Codex 앱, VS Code 같은 IDE 확장, Xcode와 JetBrains의 Codex, T3 Code, Claude Code용 Codex 플러그인 중 세 가지.
Q3OpenAI가 아닌 모델 제공자를 붙이려면 무엇이 필요한가?
Responses API와 호환되는 API. LM Studio와 Ollama는 간편 설정이 따로 있다.
Q4발표자가 말한 앱 서버와 ACP의 차이는?
ACP는 여러 에이전트에 두루 쓰는 일반 프로토콜이다. 앱 서버는 Codex 전용이라 하네스의 개별 부분까지 조정할 수 있다. 앱 서버를 만든 쪽의 설명이라는 점은 감안한다.
Q5시스템 프롬프트를 새로 쓰기보다 개발자 지시를 덧붙이라는 이유는?
덧붙이면 모델마다 다듬어 둔 기본 프롬프트를 그대로 살린다. 새로 쓰면 프롬프트를 모델에게 익숙한 형태로 유지하려는 하네스 팀의 작업을 잃는다.
Q6동적 도구를 지연 로딩으로 표시하면 무엇이 달라지나?
도구가 시스템 프롬프트에 들어가지 않는다. Codex가 도구 검색으로 필요할 때 찾아 쓴다. 그래서 컨텍스트 창이 도구 설명으로 차지 않는다.
Q7스레드 단위로 바꿀 수 있는 설정은?
모델 제공자, 모델, 샌드박스 세부 설정(어떤 네트워크에 접속할지, 어떤 파일을 고칠 수 있는지).
Q8앱 서버를 내 앱에 묶어 배포하라는 이유는?
프로토콜이 버전마다 바뀌기 때문이다. 사용자가 설치한 CLI에 기대면 깨지는 변경, 업데이트 여부, 업데이트 재촉 문제를 떠안는다. Codex 앱도 바이너리를 앱 안에 싣는다.
Q9codex exec와 앱 서버는 각각 어디에 맞나?
codex exec는 스크립트와 CI/CD에 맞다. 앱 서버는 에이전트를 화면에 보여 주는 클라이언트나, 스레드를 여러 개 동시에 돌릴 때 맞다.
Q10Doom 시연에서 "진짜 앱 서버가 돌고 있다"는 걸 보여 준 장면은?
현재 디렉터리를 묻자 Codex가 zsh를 실행해 작업 디렉터리를 알려 준 장면. 게임 화면 뒤에서 실제 앱 서버가 발표자의 컴퓨터에서 돌고 있었다.
Q11ChatGPT 로그인을 붙이면 사용량은 어디서 빠지나?
내 앱 사용자의 Codex 사용 한도에서 빠진다. 사용자는 자기 ChatGPT 구독을 그대로 가져와 쓴다.

용어 정리

용어뜻
하네스Harness. 모델을 감싸 도구, 지시, 실행 규칙을 정해 주는 실행 틀
앱 서버App server. Codex 하네스를 감싸 바깥 앱이 메시지로 다룰 수 있게 한 프로토콜과 그 프로세스
클라이언트 / 서버요청을 보내는 쪽(내 앱)과 요청을 받아 처리하는 쪽(앱 서버)
JSON-RPCJSON 메시지로 상대에게 기능 실행을 요청하고 결과를 받는 약속
ACPAgent Client Protocol. 에디터 같은 클라이언트와 코딩 에이전트가 주고받을 메시지를 정한 공개 프로토콜
Responses APIOpenAI 모델을 부르는 API 형식. 이와 호환되면 다른 제공자의 모델도 Codex에 붙일 수 있다
스레드 / 턴스레드는 대화 하나. 턴은 그 안에서 요청과 응답이 한 차례 오가는 것
델타 메시지응답을 한꺼번에 주지 않고 조각조각 흘려보낼 때의 각 조각
시스템 프롬프트모델이 늘 먼저 읽는 기본 지시문
개발자 지시Developer instructions. 시스템 프롬프트 뒤에 덧붙이는 앱 개발자의 지시
동적 도구Dynamic tools. 내 앱이 정의해 에이전트에게 넘기는 함수
지연 로딩Deferred loading. 도구를 미리 프롬프트에 넣지 않고, 필요할 때 도구 검색으로 찾게 하는 방식
컨텍스트 창Context window. 모델이 한 번에 읽을 수 있는 입력의 범위
MCPModel Context Protocol. 외부 도구와 데이터를 AI 에이전트에 연결하는 공개 프로토콜
샌드박스에이전트가 접속할 수 있는 네트워크와 고칠 수 있는 파일을 제한하는 격리 환경
바인딩 / JSON 스키마프로토콜 메시지의 형태를 코드(TypeScript 타입)나 문서(JSON 스키마)로 적어 둔 것
stdio표준 입출력. 프로세스끼리 입력과 출력 스트림으로 메시지를 주고받는 방식
WebSocket네트워크 연결 하나를 열어 두고 양쪽이 메시지를 계속 주고받는 방식
SDK특정 기능을 쉽게 쓰도록 묶은 개발 도구 모음
WSLWindows에서 Linux 환경을 돌리는 기능
IPCInter-process communication. 같은 컴퓨터의 프로세스끼리 메시지를 주고받는 통로
WasmWebAssembly. C 같은 언어로 짠 프로그램을 웹 환경에서 돌리게 하는 형식
codex exec대화 없이 Codex에게 작업을 맡기는 Codex CLI 명령
목표 모드Goal mode, /goal. Codex에 목표를 정해 주는 기능. 발표에서는 이름만 나오고 자세한 설명은 없다
분포 안In distribution. 모델이 학습하며 익숙해진 입력 형태 안에 있다는 뜻
