인터랙션 하나면 충분하다

Google DeepMind가 모델과 에이전트를 한 창구로 부르는 Interactions API와, 샌드박스가 딸린 관리형 Antigravity 에이전트를 소개한다. 서버가 대화 맥락과 작업 환경을 기억하므로, 개발자는 ID 두 개만 넘기면 된다.

원본 영상: An Interaction Is All You Need 발표: Ivan Leo (Google DeepMind 개발자 경험 팀)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고(DeepMind, Antigravity, Nano Banana, Veo), 나머지는 들린 대로 쓰고 "(추정)"을 붙였다. 발표 화면의 코드는 자막에 없어서, 노트의 코드는 설명을 바탕으로 다시 쓴 예시다. mm:ss는 영상 위치다.

발표자는 Google DeepMind 소속이고, 이 발표는 자사 제품 소개다. 성능, 비용, "Gemini만 할 수 있다" 같은 주장은 그 점을 감안해 읽자.

3분 요약
  1. 모델을 쓰는 방식은 한 번 묻고 답하기 → 함수 호출 → 여러 도구로 오래 일하는 에이전트로 바뀌었다.
  2. 모델과 에이전트를 여러 엔드포인트로 따로 부르기 어려워졌다. Google은 이를 하나로 묶은 Interactions API를 만들었다.
  3. 서버가 대화 상태를 들고 있다. 응답의 interaction ID를 다음 요청에 넘기면 맥락이 이어진다. 중간에 모델을 바꿔도 된다.
  4. 출력마다 타입이 붙고, 과정은 steps 데이터 모델로 단계별로 남는다. 검색, URL 읽기, 직접 만든 도구를 한 호출에서 섞어 쓸 수 있다.
  5. Antigravity 에이전트를 관리형 에이전트로 쓸 수 있다. API 호출 한 번이면 계속 쓰는 샌드박스가 생기고, environment ID로 같은 샌드박스에 돌아온다.
  6. 중간 프록시가 요청 헤더에 토큰을 넣어 준다. 그래서 모델은 비밀 토큰을 보지 못한다.
  7. 설정을 굳힌 이름 붙은 에이전트를 1,000개까지 만들 수 있고 모델 사용료만 낸다고 한다. 옮겨 갈 때는 마이그레이션 스킬을 코딩 에이전트에 준다.
01

모델을 쓰는 방식의 변화 00:20

발표 제목은 유명한 논문 제목 "Attention Is All You Need"를 비튼 것이다. 발표자는 먼저 우리가 모델을 써 온 방식을 세 단계로 짚는다.

단계모습예
한 번 주고받기메시지 하나를 보내고 답 하나를 받는다"농담 하나 해 줘"에 농담 한 줄이 돌아온다
함수 호출 function calling 01:00모델이 구조가 정해진 JSON을 만든다. 앱이 그 결과를 믿고 쓸 수 있다회원가입 화면이 아이디와 비밀번호를 JSON으로 서버에 보내는 것과 같은 모양. 사용자 정보 추출, 데이터 파싱에 쓴다
에이전트 01:30도구 여러 개를 부르고, 결과를 되짚어 보고, 환경과 주고받으며 오래 일한 뒤 답한다예전 "뉴욕 날씨 알려 줘"는 날씨 도구 하나면 됐다. 이제 모델은 여러 도구를 오가며 스스로 판단한다

함수 호출이 중요했던 이유는 믿을 수 있는 결과다. 모델을 실제 앱 안에 넣으려면 결과의 모양이 매번 같아야 했다.

02

에이전트를 이루는 것 02:00

에이전트를 "루프 안에서 도는 언어 모델"로 줄여 말하는 사람이 많다. 발표자는 대부분의 경우 맞는 말이라고 본다.

모델이 좋아질수록 주변 뼈대scaffolding는 줄었다. 발표자가 든 예: 최신 Opus나 Fable 모델은 파일 읽기, 파일 편집 같은 전용 도구 대신 바로 bash 도구 하나를 쓴다.

네 가지 구성 요소

  • 언어 모델: 맥락과 사용자 의도를 이해한다
  • 함수와 자원: 모델이 쓸 수 있는 도구들
  • 단기 기억과 장기 기억: 지금까지 본 것을 기록한다
  • 실행 환경: 함수를 실제로 돌리는 곳
환경이 없으면 아무것도 못 한다 코딩 에이전트를 만들고 코드를 실행할 환경을 주지 않으면, 그 에이전트는 아무 일도 할 수 없다. 이 말은 뒤에 나오는 관리형 에이전트의 샌드박스로 이어진다.
03

AI Studio로 먼저 써 보기 03:00

Gemini 모델을 가장 쉽게 써 보는 곳으로 발표자는 AI Studio를 권한다.

  • 발표 노트 앱: 발표자는 발표자 보기presenter view를 못 쓴다는 걸 알고, 발표 2분 전에 AI Studio로 노트 화면을 만들었다. "발표 노트를 넣을 수 있는 모바일 반응형 웹사이트"라고 짧게 요청했을 뿐이다. 결과는 바로 배포돼 누구나 접속할 수 있었다.
  • 무료 사용량: 넉넉하다고 한다. 발표자는 발표 준비 대부분을 무료 범위에서 했다.
  • 써 볼 수 있는 모델: 영어로 말하면 다른 언어 음성으로 옮기는 음성 번역 모델, Gemini 3.5 Flash 같은 최신 모델.
  • 조정: 여러 매개변수를 단순한 UI 토글로 바꾼다.
04

Interactions API가 나온 이유 04:00

모델에서 에이전트로 넘어오면서, API가 받쳐야 할 작업의 모양이 크게 바뀌었다.

  • Gemini API에는 Nano Banana(이미지 모델), Gemini 3.5 Flash 같은 모델이 있다.
  • Deep Research 에이전트처럼 3분 넘게 혼자 일하는 에이전트도 있다. 연구 계획을 함께 정하면 스스로 조사해서 긴 보고서를 가져온다.
예전모델과 에이전트를 따로 부른다엔드포인트가 여러 개다. 결과는 깊게 중첩된 객체 안에 있다.
→
Interactions API한 창구로 모두 부른다모델, 에이전트, 도구를 같은 방식으로 부르고 결과에 타입이 붙는다.

Google 안에서 자사 제품에 붙일 때first-party integration도 같은 어려움이 있었다. Google이 원한 흐름은 이런 것이다.

  1. Nano Banana로 이미지를 만든다
  2. 조사를 한다
  3. 그 결과로 Veo에서 이어 만든다
  4. 여러 에이전트를 띄워 각자 일하게 한다

Interactions API는 이 모든 경우를 받치려고 만든 API다. Google도 이 위에서 Gemini를 Google 제품 전반에 넣으려 한다.

05

서버가 맥락을 기억한다 05:20

시작점은 서버 쪽 상태server-side state다. 대화 상태를 클라이언트 대신 서버가 보관한다는 뜻이다.

새 Gemini 모델은 thought signature를 돌려준다. 모델이 함수를 부르거나 답할 때 함께 오는 값이다. 사람이 읽을 수 없는 숫자열이고, 다음 요청에 그대로 돌려줘야 한다.

직접 관리하면 깨지기 쉽다 발표자가 만난 스타트업 중에는 공백 하나를 잘못 넣어 캐시를 날린 곳도 있었다. 또 thought signature를 돌려주지 않으면 모델 성능이 떨어진다고 한다.

Interactions API에서는 서버가 이 값을 대신 들고 있다.

  1. 첫 요청: "안녕, 내 이름은 Phil이야"
  2. 응답에 interaction ID가 온다 05:50
  3. 둘째 요청에서 그 ID를 previous_interaction_id 자리에 넣는다
  4. 앞 대화의 맥락이 모두 이어진다

발표에서는 이 대목을 "responses API"라고 말했다. 문맥상 Interactions API를 가리킨 말실수로 보인다.

사진 한 장에서 영상까지 06:20

팀원 Vampsy(추정)가 만든 데모다. 사진 한 장을 넣으면 Nano Banana가 여러 나라, 여러 장소에 있는 내 모습을 만든다.

  • 사진 하나하나가 interaction 하나다.
  • 첫 API 호출 하나가 여러 interaction 호출로 퍼진다.
  • 같은 interaction ID를 이어 써서, 새로 내놓은 Omni 모델(추정)로 영상을 만든다.

발표자는 이 데모가 Interactions API 없이는 어려웠다고 말한다. 이 API는 객석에 있던 동료 Philip이 만들었다고 소개했다.

코드로 보면 07:00

첫 호출은 Gemini 3.1 Flash Lite Image(추정)에게 "베네치아에 있는 내 모습"을 요청한다. 둘째 호출은 받은 interaction ID를 넘기고 모델만 Omni Flash(추정)로 바꾼다. 발표 주 수요일에 내놓은 모델이라고 했다. 같은 이미지와 맥락이 모든 호출에 이어진다.

예시: 발표 화면의 코드는 자막에 없다. 아래는 설명을 바탕으로 다시 쓴 의사 코드이고, 실제 SDK의 이름과 인자는 다를 수 있다.

first = client.interactions.create(
    model="이미지 모델",
    input="베네치아에 있는 내 모습을 만들어 줘",
)

second = client.interactions.create(
    model="영상 모델",                     # 모델을 바꿔도
    previous_interaction_id=first.id,     # 앞 맥락은 서버가 이어 준다
    input="방금 그 장면으로 짧은 영상을 만들어 줘",
)
06

결과마다 타입이 붙는다 07:30

예전 API에서 오디오를 꺼내려면 "completions 아래 audio"처럼 깊게 중첩된 객체를 파고들어야 했다. 발표자도 그 경로를 외우지 못한다고 했다.

이제는 모든 출력에 output.type이 붙는다. 타입을 보고 그에 맞게 처리하면 된다.

이미지가 필요하면 같은 메서드 client.interactions.create를 쓴다. 바꾸는 건 두 가지다.

  • 응답 형식response modality: 텍스트, 이미지, 오디오 중 무엇으로 받을지
  • 생성 설정generation config

그러면 output.type이 image로 온다.

예시: 의사 코드다. 결과의 종류를 type 하나로 가른다.

if output.type == "audio":
    play(output)
elif output.type == "image":
    show(output)
07

도구를 섞어 쓰고, 과정은 steps로 남긴다 08:20

예전에는 안 되던 조합이 된다. 내장 도구끼리, 또는 내장 도구와 직접 만든 도구를 한 요청에 섞을 수 있다.

도구종류하는 일 (예: React 앱의 최신 보안 보고서 찾기)
Google 검색내장Google과 같은 검색 색인으로 찾는다
URL context내장웹 페이지의 내용을 읽어 온다
file incident직접 만든 도구사고를 등록한다

모델은 무엇이 필요한지 스스로 판단해 도구를 고른다. 이 모든 과정이 API 호출 한 번 안에서 끝난다. 검색이 붙으니 학습 시점training cutoff 이후의 정보도 다룰 수 있다.

steps 데이터 모델 09:00

메시지 하나 보내고 답 하나 받는 구조로는 이제 부족하다. 비동기 도구 호출, 모델끼리의 협업 같은 복잡한 흐름이 생기기 때문이다.

그래서 예전의 outputs 배열을 steps 데이터 모델로 바꿨다. 단계마다 종류를 알려 주는 구분 필드discriminator가 있다. 그래서 각 단계에서 다음이 분명히 보인다.

  • 모델이 무엇을 출력했나
  • thought signature가 무엇이었나
  • 어떤 함수를 불렀나
  • 어떤 콘텐츠를 만들었나 (content.type: 오디오, 영상 등)

발표자는 이런 멀티모달 흐름을 "Gemini 모델 계열만 할 수 있는 방식"이라고 말했다. 자사 제품에 대한 주장이니 감안해서 읽자.

08

Antigravity를 원격 에이전트로 09:40

발표의 두 번째 소식은 관리형 에이전트managed agent다. Google의 Antigravity 에이전트를 원격에서 대신 돌려 준다.

  • Google은 여러 제품을 Antigravity 하네스harness로 통일했다. 하네스는 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀이다.
  • AI Studio에서 웹사이트를 만드는 것도 Antigravity 에이전트다.
  • Antigravity 앱도 같은 에이전트를 쓴다.
  • Gemini를 이 하네스와 함께 학습시켰다고 한다. 그래서 하네스를 그대로 쓰면 이득이 크다는 게 발표자의 주장이다.
예전 10:10코딩 에이전트를 직접 차린다하네스 튜닝, 샌드박스 업체 찾기, 인프라 관리, 실행 사이의 맥락 보존을 모두 직접 한다.
→
관리형 에이전트API 호출 한 번계속 쓸 수 있는 샌드박스가 바로 생긴다.

샌드박스sandbox는 바깥과 격리된 실행 환경이다. 발표자는 이 샌드박스를 따로 고치지 않고 계속 호출하며 "personal claw"처럼 쓸 수 있다고 표현했다. 개인용 에이전트를 가리키는 말로 보인다.

예: GitHub 저장소 분석 10:30

  1. API 호출로 저장소 분석을 맡긴다
  2. 에이전트가 원격 샌드박스를 띄운다
  3. 파일 목록을 확인한다
  4. 파일을 하나씩 읽는다
  5. 최종 보고서를 쓴다

사람이 끼어들지 않아도 에이전트가 조사와 추론을 스스로 해낸다.

09

같은 샌드박스로 돌아오는 두 ID 11:00

샌드박스는 여러 턴에 걸쳐 유지된다. 응답으로 받은 environment ID를 다음 요청에 넘기면 원래 샌드박스로 돌아간다.

ID이어 주는 것효과
interaction ID대화 맥락, thought signature맥락을 지키고 캐시를 깨뜨리지 않는다
environment ID샌드박스: 설치한 패키지, 만든 파일요청을 정확히 같은 샌드박스로 보낸다

발표자는 이 둘을 Google이 주는 기본 요소 두 개라고 불렀다. 상태를 직접 저장할 필요가 없고, 코드 몇 줄만 더하면 된다.

샌드박스에 자료 넣기 11:30

샌드박스에 미리 넣고 싶은 것이 있을 수 있다. 직접 만든 의존성, MD 파일(자막상 "EMD files", 추정), 보조 파일 같은 것이다. 넣는 경로는 세 가지다.

  • Google Cloud Storage(GCS) 버킷
  • GitHub 저장소
  • 요청에 직접 담는 인라인 파일

데모에서는 앞 호출에 이어 environment ID를 넘겼다. 모델은 떠난 자리 그대로의 파일을 다시 봤다. 두 ID를 계속 넘기는 동안에는 설치한 패키지와 만든 파일이 모든 턴에 남는다.

10

큰 작업, 그리고 로컬에서 클라우드로 12:10

관리형 에이전트가 간단한 작업만 하는 건 아니다. 발표자가 보여 준 실행에서는 모델이 토큰을 200만 개 넘게 쓰며 저장소 하나를 분석했다.

해커톤에서 받은 저장소였다. 누군가 강화학습reinforcement learning, RL 환경을 코딩하려고 프로그래밍 언어를 처음부터 만들었다. 발표자는 블록을 끌어다 놓아 캐릭터를 움직이는 교육용 언어 Scratch를 예로 들어 설명했다.

  • 직접 만든 DSLdomain-specific language: 특정 분야 전용의 작은 언어
  • 웹 페이지
  • 여러 스키마
  • HUD(추정) 안에서 도는 RL 학습 루프

이 전부를 API 호출 한 번으로 분석했다. 인프라를 다루거나 하네스를 튜닝하지 않고도 맞춤형 에이전트를 만들 수 있다는 게 요지다.

로컬과 클라우드가 같은 에이전트 12:50

관리형 에이전트는 Antigravity IDE에서 돌던 에이전트와 근본적으로 같다. 그래서 이런 흐름이 된다.

  1. 로컬에서 워크플로와 스킬skills을 다듬는다
  2. 스킬이 마음에 들면 폴더 하나로 묶는다
  3. sources 기능으로 agents 폴더에 올린다
  4. 같은 스킬, 같은 하네스, 같은 프롬프트가 클라우드에서도 돈다

로컬에서 충분히 믿을 만해졌을 때 올리면 그대로 동작한다고 한다.

11

모델이 토큰을 못 보게 하는 프록시 13:30

회사들이 자주 묻는 질문이 있다. "에이전트가 네트워크 자격 증명을 흘리면 어떻게 하나?"

에이전트는 외부 서비스를 자주 부른다. Gemini API를 부르거나, 비공개 GitHub 저장소를 내려받는 식이다. 그래서 Google은 중간자 프록시man-in-the-middle proxy를 뒀다.

  1. 모델이 밖으로 요청을 보낸다
  2. 프록시가 길목에서 헤더를 보고 필요한 값을 바꿔 넣는다
  3. 예: GitHub API로 가는 모든 요청에 토큰을 그때그때 넣는다 14:00
프롬프트 인젝션을 당해도 모델은 토큰을 처음부터 갖고 있지 않다. GitHub API를 부르는 코드를 실행할 뿐이다. 그래서 프롬프트 인젝션prompt injection으로 토큰을 흘리라는 공격을 받아도 흘릴 토큰이 없다.
12

이름 붙은 에이전트와 비용 14:20

에이전트가 잘 돌면 설정을 굳혀 이름 붙은 에이전트named agent로 만든다. 지금 antigravity preview 에이전트를 이름으로 부르는 것과 같은 방식이다. 만드는 방법은 두 가지다.

방법 1 · 설정으로 굳히기

정해진 파일과 네트워크 소스로 고정한다.

발표 예: antigravity preview 기본 에이전트에 기본 환경 설정과 GCS 스킬 하나를 붙여 "데이터 분석가" 에이전트를 만든다.

방법 2 · 대화로 굳히기 14:50

에이전트와 대화하며 환경을 차근차근 맞춘다. 필요한 의존성과 패키지를 설치한 뒤 그 환경을 특정 에이전트로 고정한다.

이후: 다음 호출은 모두 그 에이전트를 거친다.

규모와 비용 15:00 지금은 이름 붙은 에이전트를 1,000개까지 만들 수 있다고 한다. 저장소와 샌드박스 비용은 받지 않고 모델 사용료만 받는다고 한다.

한도와 가격은 발표 당시 발표자가 말한 것이다. 자사 제품 소개이기도 하니, 실제로 쓰기 전에 공식 문서로 확인하자.

13

CLI와 마이그레이션 스킬 15:20

  • Gemini API CLI를 오픈소스로 공개했다. 간단한 명령으로 모델을 로컬에서 시험한다.
  • 코딩 에이전트나 Antigravity 에이전트를 로컬에서 고친 뒤, 준비되면 CLI가 폴더 하나로 묶어 올리고 에이전트까지 만들어 준다.

앞으로 새 모델은 모두 Interactions API에 올라온다고 한다. 15:50 옮겨 가는 사람을 위해 Interactions API 스킬을 만들었다. 쓰던 코딩 에이전트에 이 스킬을 주면 마이그레이션을 맡길 수 있다.

왜 스킬이 필요한가 코딩 에이전트에게 Gemini 연동을 시키면 Gemini 2.5 Flash나 2.0 같은 옛 모델을 계속 쓰는 일이 흔하다. 이 스킬은 최신 모델 목록과 메서드를 계속 갱신한다. 팀이 정기적으로 평가해서 제대로 동작하는지도 확인한다고 한다.
14

핵심 정리

  1. 모델 사용은 한 번 묻고 답하기에서 함수 호출을 거쳐, 여러 도구로 오래 일하는 에이전트로 바뀌었다.
  2. 에이전트는 모델 + 도구 + 기억 + 실행 환경이다. 환경이 없으면 아무것도 못 한다.
  3. 모델이 좋아질수록 뼈대는 줄었다. 최신 모델은 전용 도구 대신 bash 하나를 쓴다.
  4. Interactions API는 모델과 에이전트를 한 창구로 부르려고 만들었다.
  5. 서버가 상태를 들고 있다. interaction ID를 previous_interaction_id로 넘기면 맥락과 thought signature가 이어진다.
  6. 모델을 바꿔도 같은 맥락으로 이어 쓸 수 있다. 이미지에서 영상으로 가는 흐름이 쉬워진다.
  7. 출력에는 output.type이, 과정에는 steps 데이터 모델이 붙어 결과를 꺼내기 쉽다.
  8. 검색, URL 읽기, 직접 만든 도구를 API 호출 한 번에서 섞어 쓴다.
  9. 관리형 Antigravity 에이전트는 계속 쓰는 샌드박스를 준다. environment ID로 같은 샌드박스에 돌아오고, 중간자 프록시 덕분에 모델은 토큰을 보지 못한다.
  10. 설정을 굳힌 이름 붙은 에이전트로 규모를 키우고, 옮길 때는 Interactions API 스킬을 코딩 에이전트에 준다.
15

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 짚은 모델 사용 방식의 세 단계는?
한 번 주고받기, 함수 호출, 에이전트. 에이전트는 도구 여러 개를 쓰고 환경과 주고받으며 오래 일한 뒤 답한다.
Q2함수 호출이 모델을 실제 앱에 넣을 수 있게 한 이유는?
모델이 구조가 정해진 JSON을 만들기 때문이다. 결과의 모양이 매번 같으니 앱이 믿고 쓸 수 있다.
Q3에이전트를 이루는 네 요소는?
맥락과 의도를 이해하는 언어 모델, 함수와 자원, 단기·장기 기억, 함수를 실제로 돌리는 실행 환경.
Q4Google이 Interactions API를 만든 이유 두 가지는?
모델과 에이전트를 여러 엔드포인트로 따로 부르기 어려웠다. 예전 API의 결과는 깊게 중첩된 객체라 다루기 힘들었다.
Q5thought signature를 직접 관리하면 생기는 문제는?
공백 하나만 잘못 넣어도 캐시가 깨질 수 있다. 돌려주지 않으면 모델 성능이 떨어진다.
Q6둘째 요청에서 앞 대화의 맥락을 잇는 방법은? 모델을 바꿔도 되나?
첫 응답의 interaction ID를 previous_interaction_id로 넘긴다. 모델을 바꿔도 된다. 발표 데모는 이미지 모델에서 Omni Flash(추정)로 바꿔 영상을 만들었다.
Q7이미지 출력을 받으려면 무엇을 바꾸나?
같은 메서드를 쓰고 응답 형식(response modality)과 생성 설정(generation config)만 바꾼다. 결과는 output.type이 image로 온다.
Q8React 보안 보고서 예시에서 섞어 쓴 도구 세 가지는?
Google 검색, URL context, 직접 만든 file incident. 이 모두를 API 호출 한 번에서 쓴다.
Q9steps 데이터 모델이 단계마다 분명히 보여 주는 것은?
모델의 출력, thought signature, 부른 함수, 만든 콘텐츠와 그 타입.
Q10관리형 에이전트가 없을 때 코딩 에이전트를 만들려면 해야 했던 일은?
하네스 튜닝, 샌드박스 업체 찾기, 인프라 관리, 실행 사이의 맥락 보존.
Q11interaction ID와 environment ID는 각각 무엇을 잇나?
interaction ID는 대화 맥락을 잇고 캐시를 지킨다. environment ID는 설치한 패키지와 만든 파일이 있는 같은 샌드박스로 요청을 보낸다.
Q12프록시 방식에서 프롬프트 인젝션을 당해도 토큰이 새지 않는 이유는?
모델은 토큰을 갖고 있지 않다. 밖으로 나가는 요청의 헤더에 프록시가 토큰을 넣는다.
