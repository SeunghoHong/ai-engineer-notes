추측 디코딩, 내 서비스에 켤 가치가 있나

큰 모델이 토큰을 하나씩 쓰는 대신, 작은 모델이 몇 개를 먼저 쓰고 큰 모델이 한 번에 확인한다. 결과는 같고 속도는 빨라진다. 하지만 메모리를 더 먹고, 작업 종류에 따라 이득이 크게 갈린다. 발표자는 vLLM과 NVIDIA Blackwell GPU 한 장으로 직접 재 본 결과를 바탕으로 판단 기준을 정리한다.

원본 영상: Is Speculative Decoding Worth It? Profiling vLLM on NVIDIA Blackwell 발표: Sheila (추정, 자막 기준) · Akamai 개발자 애드보킷

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았고, 불확실한 곳은 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. LLM 답변은 입력을 읽는 단계와 토큰을 하나씩 쓰는 단계로 나뉜다. 추측 디코딩은 뒤쪽만 빠르게 한다.
  2. 작은 초안 모델이 토큰 3~5개를 먼저 쓰고, 큰 목표 모델이 한 번의 계산으로 받아들이거나 거절한다. 거절된 자리는 목표 모델이 다시 쓴다. 출력 품질은 목표 모델과 같다.
  3. 공짜가 아니다. 모델이 둘이니 초안 모델 가중치와 두 모델의 KV 캐시만큼 GPU 메모리가 더 든다.
  4. 초안 모델은 목표 모델보다 10~50배 작고, 같은 토크나이저를 쓰고, 되도록 같은 모델 가족이어야 한다.
  5. 데모에서 구조화된 출력은 1.6배 빨라졋고 채택률이 높았다. 창의적인 글쓰기는 온도가 높아 채택률이 낮았다.
  6. RAG처럼 입력이 길고 출력이 짧은 작업은 시간이 입력 읽기에 몰려 있어 효과가 작다.
  7. 판단 기준 네 가지: 구조화된 작업인가, 남는 GPU 메모리가 있나, 창의적 작업인가, 동시 요청이 많은가. 동시 요청이 많아 GPU가 이미 바쁘면 켜지 않는다.
01

답변은 두 단계로 만들어진다 00:30

LLM에 질문을 던지면 내부에서는 두 단계가 돌아간다.

1단계 · 입력 읽기 prefill

모델이 프롬프트의 입력 토큰을 모두 처리하고 KV 캐시 KV cache를 만든다. KV 캐시는 이 요청을 처리하는 동안 모델이 쓰는 작업 기억이다.

요청마다 한 번만 일어난다.

2단계 · 토큰 생성 decode

모델이 실제로 답을 쓴다. 다음 토큰은 앞의 모든 토큰에 의존하므로 한 번에 하나씩 만든다. 이렇게 앞 결과를 보고 다음을 만드는 방식을 자기회귀 autoregressive라고 부른다.

토큰 수만큼 반복된다.

Llama 70B 같은 큰 모델을 서비스에 쓰면 답 하나에 모델 전체를 통과하는 계산, 즉 순전파 forward pass가 수백 번 필요할 수 있다. 계산 비용이 크고 사용자가 느끼는 지연도 커진다.

02

작은 모델이 먼저 쓰고, 큰 모델이 확인한다 01:30

질문은 이것이다. 토큰을 하나씩 쓰는 일을 꼭 큰 모델이 해야 하나. 작은 모델이 몇 개를 먼저 추측하게 하면 어떨까.

  1. 초안 모델 draft model이 다음 토큰을 몇 개 먼저 쓴다. 발표자는 한 번에 3~5개로 설정한다고 했다. 이것도 자기회귀지만 모델이 작아서 빠르고 싸다.
  2. 목표 모델 target model이 그 후보들을 한 번의 순전파로 검증한다. 맞으면 받아들이고 틀리면 거절한다.
  3. 거절된 자리부터는 목표 모델이 토큰을 다시 계산한다.
출력은 바뀌지 않는다 정확도를 책임지는 쪽은 여전히 목표 모델이다. 초안 모델이 무엇을 제안했든 목표 모델이 검증하므로 최종 출력은 목표 모델이 혼자 쓴 것과 같다. 빨라지기만 하고 품질은 그대로다.

이것이 추측 디코딩 speculative decoding이다. 발표자는 추론 비용을 크게 아낄 수 있다고 말한다. 다만 조건이 있다.

03

공짜가 아니다: 메모리 비용 02:40

모델을 두 개 띄우니 GPU 메모리를 더 쓴다.

  • 초안 모델의 가중치. 작은 모델이라 크지는 않다.
  • 두 모델의 KV 캐시. 초안 모델과 목표 모델이 각자 작업 기억을 가져야 하므로 추가 공간이 필요하다.

그래서 추측 디코딩은 GPU에 남는 공간이 있을 때 고려한다. 동시 요청이 많은 서비스라면 GPU가 이미 요청을 처리하느라 꽉 차 있을 것이다. 그때 모델을 하나 더 얹는 것은 맞지 않는다. 반대로 GPU가 놀고 있다면 시도할 가치가 있다.

04

초안 모델 고르는 기준 03:20

초안 모델을 고를 때 저울에 올리는 것은 두 가지다. 목표 모델과 얼마나 비슷하게 맞추는가, 그리고 얼마나 빠른가. 둘 다 좋을 수는 없으니 균형을 잡는다.

조건이유
10~50배 작다목표 모델 비용의 일부만 들어야 추측하는 의미가 있다
같은 토크나이저토큰을 자르는 단위가 같아야 초안을 바로 검증할 수 있다. 다르면 두 토크나이저 사이를 직접 변환해야 한다
되도록 같은 모델 가족같은 가족이면 토크나이저가 같고, 출력 성향도 비슷해 채택률이 오른다
비용과 정확도의 균형너무 작으면 채택률이 떨어지고, 너무 크면 속도 이득이 사라진다
05

데모 환경: Blackwell 한 장에 서버 두 개 04:00

발표자는 NVIDIA Blackwell GPU 한 장만 쓸 수 있었다. 그 한 장에 기준 서버(목표 모델만)와 추측 디코딩 서버(목표 모델 + 초안 모델)를 동시에 띄워 비교하려 했다. 그래서 두 서버가 GPU를 나눠 써도 들어갈 만큼 작은 목표 모델을 골랐다.

자막에는 두 모델의 이름이 나오지 않는다. 16비트 가중치는 파라미터 하나에 2바이트를 쓰므로 16 GB는 약 80억 파라미터, 2.5 GB는 약 12억 파라미터 규모에 해당한다. 이 환산은 노트 작성자의 계산이며 발표에는 없다.

06

이득을 보는 작업, 못 보는 작업 05:30

추측 디코딩의 목표는 작은 모델이 큰 모델의 다음 토큰을 거의 똑같이 맞추는 것이다. 그러니 다음 토큰이 예측하기 쉬운 작업일수록 이득이 크다.

이득이 큰 쪽 · 구조화된 출력
  • 코드 생성
  • JSON 쓰기
  • SQL 쿼리 만들기

문법과 형식이 정해져 있어 다음 토큰의 선택지가 좁다. 작은 모델도 잘 맞춘다.

이득이 작은 쪽 · 창의적 출력
  • 시 쓰기
  • 브레인스토밍
  • 온도를 높게 둔 자유 생성

다음 토큰이 될 수 있는 후보가 많다. 작은 모델의 추측이 자주 거절된다.

07

데모 결과: 채택률이 갈림길 09:00

데모는 두 탭으로 되어 있다. 각 탭에서 버튼을 누르면 기준 서버와 추측 디코딩 서버가 같은 요청을 동시에 처리한다. 발표 중 서버가 멈춰 vLLM 서버를 다시 띄우는 데 2분 가까이 걸렸고 07:00, 그 뒤 정상 동작했다.

구조화된 출력 09:10

발표자가 가장 눈여겨보라고 한 지표는 채택률 acceptance rate이다. 초안 모델이 만든 토큰 가운데 목표 모델이 받아들인 비율이다. 구조화된 출력에서는 이 값이 높았고, 그래서 속도 이득이 나왔다.

창의적 출력 10:00

두 번째 탭에서도 추측 디코딩 쪽이 빨랐지만 채택률이 눈에 띄게 낮았다. 이유는 두 가지다. 온도 temperature를 높게 설정했고, 작업 자체가 다음 토큰의 변화 폭이 큰 창의적 작업이었다. 초안 모델의 추측이 자주 거절되면 목표 모델이 다시 쓰는 일이 늘어 이득이 줄어든다.

채택률을 보는 이유 속도 배수는 환경에 따라 달라진다. 채택률은 "내 작업이 추측 디코딩에 맞는가"를 가장 직접 보여주는 숫자다. 채택률이 낮으면 초안 모델이 헛일을 하고 있다는 뜻이다.
08

긴 입력에서는 효과가 작다 10:50

추측 디코딩은 토큰을 쓰는 단계를 빠르게 한다. 입력을 읽는 단계는 전혀 건드리지 않는다.

그래서 모델에 긴 맥락을 넣어야 하는 작업은 이득이 작다. 검색 증강 생성 RAG이나 문서 여러 개 분석이 그렇다. 이런 작업은 KV 캐시를 만드는 데 시간을 많이 쓴다. 특히 입력은 길고 출력은 짧은 질의라면 전체 시간의 대부분이 입력 읽기에 있어 추측 디코딩이 손댈 부분이 거의 없다.

입력 읽기 (prefill)그대로KV 캐시 생성. 입력이 길수록 여기에 시간이 쏠린다
→
토큰 생성 (decode)빨라진다출력이 길고 예측하기 쉬울수록 이득이 크다

켤까 말까, 네 가지 질문 11:40

발표자가 정리한 핵심은 "내 애플리케이션이 무엇을 하는가"를 먼저 따지는 것이다.

질문켜는 쪽끄는 쪽
출력이 구조화되어 있나코드, JSON, SQL시, 브레인스토밍, 높은 온도

발표자가 직접 꼽은 질문은 구조화 여부, VRAM 여유, 창의적 작업 여부, 동시성 네 가지다. 입력과 출력의 비율은 앞 섹션의 내용을 노트에서 한 줄로 더한 것이다.

질의응답: 도구와 자료 12:40

추천 도구

발표자는 서빙 엔진 vLLM으로 구현했고, 시작하기에는 vLLM 문서가 충분히 좋다고 했다. 이 발표에서 다룬 초안 모델 방식은 추측 디코딩 가운데 가장 단순한 형태다. n-gram, Medusa, EAGLE 같은 방식은 밑에 깔린 구조가 더 복잡하다.

읽을 자료

  • 이 주제를 다룬 글이 많지 않다. 검색하면 처음에 나오는 General Compute(추정, 자막 기준) 블로그가 더 자세히 설명한다.
  • 연구 논문은 두 편이 있다. 하나는 Google이 냈고, 다른 하나의 회사 이름은 발표자가 자리에서 떠올리지 못했다.
  • 발표자는 블로그 글이나 짧은 영상을 만들 계획이라고 했다.

Akamai 자료 14:10

이 실험을 재현하는 방법은 Akamai 개발자 GitHub에 올라와 있다고 했다. 발표자는 추론 최적화를 맡고 있고, 다른 동료들은 AI 에이전트 구축, 관리형 Kubernetes, Akamai Functions 활용을 다룬다. Discord 채널도 만들고 있다.

발표자는 Akamai 소속이며 마지막 부분은 자사 GitHub와 Discord 소개다. 추측 디코딩 자체의 설명은 특정 회사 제품에 기대지 않지만, 재현 자료 안내는 그 점을 감안해 읽자.

핵심 정리

  1. LLM 답변은 입력 읽기(prefill)와 토큰 생성(decode) 두 단계다. 토큰 생성은 한 번에 하나씩이라 느리다.
  2. 추측 디코딩은 초안 모델이 3~5개를 먼저 쓰고 목표 모델이 한 번에 검증한다. 거절된 자리는 목표 모델이 다시 쓴다.
  3. 출력 품질은 목표 모델과 같다. 빨라지기만 한다.
  4. 비용은 메모리다. 초안 모델 가중치와 두 모델의 KV 캐시가 추가로 든다.
  5. 초안 모델은 10~50배 작고, 같은 토크나이저, 되도록 같은 가족이어야 한다.
  6. 데모 환경은 Blackwell 한 장. 목표 모델 가중치 약 16 GB, 초안 모델 약 2.5 GB.
  7. 구조화된 출력(코드, JSON, SQL)은 1.6배 빨라졌고 채택률이 높았다.
  8. 창의적 출력과 높은 온도는 채택률이 낮다. 채택률이 추측 디코딩 적합성을 보여주는 핵심 지표다.
  9. 입력이 길고 출력이 짧은 RAG 류 작업은 효과가 작다. 추측 디코딩은 입력 읽기를 빠르게 하지 않는다.
  10. 동시 요청이 많아 GPU가 이미 바쁘면 켜지 않는다. GPU가 남을 때, 작은 배치일 때 시도한다.

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1LLM이 답을 만드는 두 단계는 무엇이고, 각각 몇 번 일어나나?
입력 읽기(prefill)는 프롬프트를 처리해 KV 캐시를 만들며 요청마다 한 번 일어난다. 토큰 생성(decode)은 토큰을 하나씩 쓰며 출력 토큰 수만큼 반복된다.
Q2추측 디코딩에서 초안 모델과 목표 모델은 각각 무엇을 하나?
초안 모델이 다음 토큰 3~5개를 먼저 쓴다. 목표 모델이 그 후보를 한 번의 순전파로 검증해 받아들이거나 거절하고, 거절된 자리부터 다시 쓴다.
Q3추측 디코딩을 켜면 출력 품질이 떨어지나?
아니다. 최종 출력을 결정하는 쪽은 목표 모델이다. 초안 모델의 제안은 모두 목표 모델이 검증하므로 출력은 목표 모델이 혼자 쓴 것과 같다.
Q4추측 디코딩의 숨은 비용은 무엇인가?
GPU 메모리. 초안 모델의 가중치와, 초안 모델과 목표 모델 각각의 KV 캐시를 둘 공간이 추가로 필요하다.
Q5초안 모델을 고르는 세 가지 조건은?
목표 모델보다 10~50배 작아야 하고, 같은 토크나이저를 써야 하며, 되도록 같은 모델 가족이어야 한다. 그 안에서 비용과 정확도의 균형을 잡는다.
Q6데모에서 목표 모델과 초안 모델의 가중치 메모리는 각각 얼마였나?
목표 모델 약 16 GB, 초안 모델 약 2.5 GB. Blackwell GPU 한 장에 두 서버를 함께 띄우고도 KV 캐시 공간이 넉넉히 남았다.
Q7채택률이란 무엇이고 왜 중요한가?
초안 모델이 만든 토큰 가운데 목표 모델이 받아들인 비율이다. 채택률이 높아야 속도 이득이 나오고, 낮으면 초안 모델이 헛일을 하는 셈이다. 내 작업이 추측 디코딩에 맞는지 가장 직접 보여주는 지표다.
Q8구조화된 출력 데모에서 속도는 몇 배 빨라졋나? 창의적 출력에서는 무엇이 달랐나?
구조화된 출력은 1.6배 빨라졋고 채택률이 높았다. 창의적 출력은 온도가 높고 다음 토큰 후보가 많아 채택률이 눈에 띄게 낮았다.
Q9RAG처럼 입력이 긴 작업에서 추측 디코딩 효과가 작은 이유는?
추측 디코딩은 토큰 생성 단계만 빠르게 한다. 입력이 길고 출력이 짧으면 시간의 대부분이 KV 캐시를 만드는 입력 읽기 단계에 있어 손댈 부분이 거의 없다.
Q10동시 요청이 많은 서비스에서 추측 디코딩을 권하지 않는 이유는?
GPU가 이미 요청 처리로 꽉 차 있어 초안 모델과 추가 KV 캐시를 둘 공간이 없다. GPU가 남고 배치가 작을 때 이득이 있다.
Q11발표자가 쓴 서빙 엔진과, 이 발표에서 다룬 방식보다 복잡한 추측 디코딩 방식 세 가지는?
vLLM을 썼다. 초안 모델 방식은 가장 단순한 형태이고, n-gram, Medusa, EAGLE은 밑에 깔린 구조가 더 복잡하다.

용어 정리

용어뜻
추측 디코딩Speculative decoding. 작은 모델이 토큰 몇 개를 먼저 쓰고 큰 모델이 한 번에 검증해 생성 속도를 올리는 기법
입력 읽기 (prefill)프롬프트의 입력 토큰을 모두 처리해 KV 캐시를 만드는 단계. 요청마다 한 번
토큰 생성 (decode)모델이 답을 토큰 하나씩 써 나가는 단계. 출력 길이만큼 반복
KV 캐시KV cache. 앞서 처리한 토큰의 중간 계산 결과를 저장한 것. 요청을 처리하는 동안 모델의 작업 기억 역할을 한다
자기회귀Autoregressive. 앞에 만든 결과를 입력으로 삼아 다음을 만드는 방식. 그래서 토큰을 한 번에 하나씩 쓴다
순전파Forward pass. 입력이 모델 전체를 한 번 통과해 출력을 내는 계산
초안 모델Draft model. 다음 토큰 후보를 먼저 추측하는 작은 모델
목표 모델Target model. 실제로 서비스하려는 큰 모델. 초안을 검증하고 최종 출력을 결정한다
채택률Acceptance rate. 초안 모델이 만든 토큰 가운데 목표 모델이 받아들인 비율
토크나이저Tokenizer. 글을 모델이 처리하는 단위인 토큰으로 자르는 규칙
온도Temperature. 생성의 무작위성을 조절하는 값. 높을수록 다양한 토큰이 나오고 예측하기 어려워진다
동시성Concurrency. 같은 시간에 처리하는 요청의 수
배치 크기Batch size. 한 번의 계산에 묶어 처리하는 요청의 수
처리량Throughput. 단위 시간에 만들어 내는 토큰 수
VRAMGPU에 달린 메모리. 모델 가중치와 KV 캐시가 여기에 올라간다
RAG검색 증강 생성. 질문과 관련된 문서를 찾아 프롬프트에 붙여 넣는 방식. 입력이 길어진다
vLLMLLM을 서비스하기 위한 오픈소스 서빙 엔진. 추측 디코딩을 설정으로 켤 수 있다
n-gram, Medusa, EAGLE초안 모델 대신 다른 구조로 토큰을 추측하는 추측 디코딩 변형들. 발표자는 더 복잡한 방식이라고만 소개했다
