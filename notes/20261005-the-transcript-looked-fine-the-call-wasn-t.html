자막은 멀쩡했다, 통화는 아니었다

음성 에이전트의 텍스트 로그는 거짓말을 한다. 2.4초의 침묵, 사용자 말을 끊고 들어오는 응답, 14를 40으로 들은 실수는 자막에 남지 않는다. 음성 에이전트를 고치려면 오디오, 자막, 트레이스를 한 화면에서 보고, 오디오 자체를 평가해야 한다.

원본 영상: The Transcript Looked Fine. The Call Wasn't. — Debugging Voice Agents 발표: Fuad (추정, Arize 제품 매니저)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 발표자 이름은 자막 첫머리에 "Fuad", 끝에 "Ali"로 나와 확실하지 않다. mm:ss는 영상 위치다.

발표자는 관측·평가 도구를 파는 Arize 소속이다. 발표 중에 제품 홍보가 아니라고 말했지만, 도구 기능을 설명하는 대목은 그 점을 감안해 읽자.

3분 요약
  1. 음성 에이전트는 빠르게 늘고 있지만 디버깅이 가장 어려운 분야다. 지연, 말 차례 넘기기, 받아쓰기 오류는 텍스트 로그에 보이지 않는다.
  2. 환불 통화 사례: 자막만 읽으면 에이전트가 실수를 고친 것처럼 보인다. 오디오를 들으면 2.4초 침묵, 사용자 말 끊기, 14를 40으로 잘못 들음이 드러나고, 환불은 결국 40번 주문으로 처리됐다.
  3. 해법은 오디오, 자막, 트레이스를 한 화면에 두는 것이다. 여러 차례의 대화를 세션 하나로 묶고, 첫 음성까지 걸린 시간과 끼어들기 횟수 같은 지표를 같이 본다.
  4. Arize는 오디오 이벤트를 OpenInference라는 오픈소스 시맨틱 컨벤션에 매핑했다. 제공자가 달라도 질의할 수 있는 스키마 하나가 생긴다.
  5. 자막에 LLM 심판을 돌리는 것만으로는 부족하다. 감정, 지연, 끼어들기, 받아쓰기 드리프트, 과제 성공을 오디오 모델로 직접 평가한다.
  6. 평가 점수를 스팬 위에 올려 두면 질의와 필터가 가능해지고, 거기서 조사 에이전트와 자동 수정 PR까지 이어질 수 있다.
  7. 오늘 할 일: 오디오 트레이싱을 켜고, 첫 음성까지 걸린 시간과 끼어들기부터 재기 시작한다. 코딩 에이전트에 요구하는 수준을 음성 에이전트에도 요구한다.
01

빠르게 크는데 가장 보기 어렵다 01:10

발표자는 음성 에이전트 분야가 폭발하듯 커지고 있다는 근거로 최근 소식 세 가지를 들었다. OpenAI의 실시간 음성 모델 출시, LiveChat 대표의 글, Vercel의 음성 에이전트 지원이다. 발표 당일 기준 며칠 안쪽의 일들이다.

커지는 속도만큼 문제도 있다. 발표자는 음성 에이전트를 가장 디버깅하기 어려운 범주라고 부른다. 이유는 세 가지다.

  • 지연 latency: 응답이 늦으면 사용자는 끊어진 줄 안다.
  • 말 차례 넘기기 turn-taking: 누가 언제 말하는지 어긋나면 서로 말을 끊는다.
  • 받아쓰기 드리프트 transcription drift: 음성을 글자로 바꾸는 단계에서 뜻이 조금씩 어긋난다.

이 셋은 모두 텍스트 로그에 남지 않는다. 발표자의 표현을 빌리면 "로그는 거짓말을 한다."

쓰임새는 고객 지원에서 드라이브스루까지 발표자가 든 예: White Castle의 Linda(추정), Bojangles의 Bo Linda, McDonald's의 주문 봇. 새벽 2시에 치즈버거 600개가 주문되면 곤란하다는 농담으로, 겉보기에 가벼운 쓰임새에도 실패 비용이 있다는 점을 짚었다.
02

자막은 멀쩡했다, 통화는 아니었다 02:40

발표의 제목이 된 사례다. 먼저 텍스트 로그만 보자.

차례자막에 적힌 내용
사용자14번 주문 환불해 주세요.
에이전트네, 40번 주문 환불을 시작했습니다.
사용자아니요, 14번이요.
에이전트환불이 확인됐습니다.

글로만 보면 에이전트가 한 번 잘못 듣고 곧 고친 것처럼 읽힌다. 발표자가 AI로 만든 같은 통화의 오디오를 틀자 다른 그림이 나왔다.

  • 사용자의 첫 요청 뒤 에이전트가 답하기까지 2.4초의 침묵이 있었다.
  • 에이전트가 사용자 말 위에 겹쳐서 말했다. 사용자의 정정은 제대로 받아들여지지 않았다.
  • 14를 40으로 잘못 들었고, 마지막 확인은 정정 후의 것이 아니었다.
  • 목소리가 딱딱하고 기계적이었다. 자막에는 절대 안 남는 문제다.
결과 도구 호출 기록까지 보면 환불은 결국 40번 주문으로 처리됐다. 텍스트 로그만으로는 알 길이 없는 실제 손해다.
03

자막 너머를 본다는 것 03:50

발표자가 말하는 해법은 단순하다. 자막만 보지 말고 오디오, 자막, 트레이스를 한곳에서 본다. 트레이스는 에이전트가 한 일을 단계별로 기록한 것이다.

  • 세션 단위로 본다. 사용자와 에이전트가 여러 번 주고받은 대화를 하나의 화면에 묶는다.
  • 지표를 같이 본다. 첫 음성까지 걸린 시간 time to first audio, 끼어들기 횟수, 감정 분석, 오디오 토큰 비용 등.
  • 연결을 본다. 이벤트를 목록으로 나열하지 않고, 어떤 발화가 어떤 도구 호출로 이어졌는지 연결해서 본다.

발표자는 이 기능들이 이달 초 Arize AX에 추가됐다고 소개했다. 그러면서 핵심은 도구가 아니라 작업 방식이라고 강조했다. 코딩 에이전트에는 이미 하네스, 평가, 핸드오프, 하위 에이전트, 도구 호출을 추적하는 관행이 자리 잡았다. 같은 관행을 음성 에이전트에도 가져오자는 것이다.

지금까지자막을 읽는다텍스트 로그에서 문제를 찾는다. 오디오 문제는 보이지 않는다

04

오디오를 위한 공통 스키마 05:40

이 화면이 가능하려면 밑바탕에 공통 규격이 있어야 한다. Arize는 오디오 이벤트를 OpenInference에 매핑했다. OpenInference는 생성형 AI에서 일어나는 일을 OpenTelemetry 호환 형식으로 적는 시맨틱 컨벤션 semantic conventions이다. 발표자에 따르면 2023년에 Arize가 처음 내놓았고, 오픈소스이며 무료다.

발표자가 "진짜 엔지니어링 작업"이라고 부른 부분은 웹소켓 이벤트를 읽기 쉬운 규격으로 옮기는 일이다. 실시간 음성 모델은 웹소켓으로 잘게 쪼개진 이벤트를 쏟아낸다. 이를 아래처럼 정리했다.

  • 세션 생애주기
  • 오디오 입력과 자막
  • 대화 항목과 출력
  • 응답 생애주기와 토큰 수
얻는 것: 제공자와 무관한 질의 가능한 스키마 하나 OpenAI 실시간 모델이든 Google의 Gemini Live든 같은 스키마로 들어온다. 새벽 2시에 고객 통화 하나를 수천만 건의 트레이스 중에서 찾아야 할 때, 필터하고 정렬할 수 있는 공통 형식이 있느냐가 전부다. 새 모델이 나와도 제공자를 바꿔 끼우고 시스템이 계속 도는지 확인할 수 있다. 제공자마다 따로 파서를 쓰지 않고 자동 계측기 하나로 끝난다.

발표자는 이 계측기를 Grafana 같은 다른 백엔드로 보내도 된다고 말했다. "Arize를 쓰든 안 쓰든 오디오 트레이싱부터 시작하라"는 메시지다.

05

통화 전체를 다시 듣기 07:40

세션 ID가 모든 차례를 하나의 타임라인으로 꿰맨다. 웹소켓 이벤트마다 사용자인지 에이전트인지 태그가 붙고, 트레이스 화면에서 오디오를 바로 재생할 수 있다. 외부 도구나 내보내기가 필요 없다.

그러면 아래 질문에 답할 수 있다.

  • 누가 언제 말했나
  • 에이전트가 어디서 멈췄나
  • 에이전트와 사용자가 각각 어디서 끊겼나
  • 그 순간 에이전트가 어떤 도구를 불렀나

발표자는 날씨 조회 도구를 부르는 에이전트 화면을 짧게 보여 줬다. 에이전트가 도구를 호출하는 시점이 오디오와 같은 줄에 보여서, 도구 호출 실패를 세션 오디오를 들으면서 디버깅할 수 있다. 서로 떨어진 시스템의 이벤트를 따로 맞춰 보는 대신, 세션에서 일어난 모든 일을 트레이스 트리 하나로 본다.

06

사례를 다시 보면 보이는 것 09:00

세션 화면으로 환불 통화를 다시 보면 실패가 세 곳에서 드러난다.

위치보이는 문제자막에서는
1번째 차례첫 음성까지 2.4초의 침묵안 보임
3번째 차례에이전트가 사용자 말 위에 겹쳐 말함안 보임
도구 호출환불이 14번이 아니라 40번으로 처리됨"확인됐습니다"로만 남음

세 가지 모두 텍스트 로그에서는 보이지 않는다. 세션 화면에서는 오디오를 앞뒤로 움직이며 도구 호출과 에이전트 동작 안에서 실패 지점을 찾을 수 있다.

07

오디오 전용 평가 09:50

보는 것 다음은 재는 것이다. 발표자는 오디오에 특화된 평가 audio-specific evals가 따로 필요하다고 말한다. 자막에 LLM 심판을 돌리는 평가는 "거기까지만 좋다."

평가 항목왜 오디오여야 하나
어조와 감정사용자 감정을 긍정, 중립, 부정으로 분류한다. 자막은 멀쩡해 보여도 목소리는 화나 있을 수 있다. 추측이 아니라 오디오로 판단한다
지연모델은 좋아지고 있지만 고객 지원에서는 첫 음성까지의 시간에 대한 서비스 수준 약속이 여전히 중요하다. 이를 넘긴 통화를 표시한다
끼어들기누가 누구 말을 끊었는지는 오디오에만 있다
부정확성과 받아쓰기 드리프트14가 40이 된 순간은 자막 이전 단계에서 생긴다
과제 성공사용자가 원한 일이 실제로 됐는지 본다

이 평가들은 오디오 모델을 기반으로 오디오에 직접 돌린다. 발표자는 Arize가 주요 오디오 플랫폼의 새 모델이 나오는 대로 지원한다고 말했다.

LLM 심판에서 에이전트 심판으로 11:10

발표자가 보는 업계 흐름은 자막이나 오디오를 분석만 하는 LLM 심판에서, 도구와 외부 시스템에 접근해 평가 정보를 채우는 에이전트 심판 agent as a judge으로 옮겨 가는 것이다. 예로 든 것은 에이전트가 접근해야 할 시스템에만 접근했는지 확인하는 접근 권한 점검이다. 자막에서는 "RBAC 점검"으로 들렸다(추정). RBAC는 역할 기반 접근 제어다.

08

스팬 위에 점수를 올리면 11:50

평가를 만드는 방법으로 발표자는 Arize의 스킬을 소개했다. 자연어로 "GPT 오디오 모델로 감정 분석 평가를 만들고, 오디오 스팬에서 화난 사용자 어조를 잡아 달라"고 요청하면, 명령줄 도구가 뒤에서 스팬을 조회하고, 오디오 스팬만 걸러 내고, 평가를 만들어 배포한 뒤 실제 트레이스에 적용한다.

발표자가 이 부분에서 Arize의 존재 이유로 든 두 가지가 있다.

  • 수십억 개 스팬을 1초 안에 질의하는 일은 직접 만들기 어렵다.
  • 사용자가 실제로 대화하는 동안 실시간으로 점수를 매기는 평가를 배포하는 일도 그렇다.
점수를 스팬에 붙여 두는 이유 평가 점수가 스팬 자체에 있으면 데이터 전체를 놓고 복잡한 질의와 필터가 가능하다. 실패를 보고 외부 시스템에서 다시 찾는 대신, 지금 듣고 있는 오디오 바로 옆에 점수가 있다. 그러면 평가와 모니터가 조사 에이전트를 띄우는 흐름이 열린다. 어떤 도구 호출이 잘못됐나, 에이전트가 코드에 없는 제품 영역을 만났나, 새 엣지 케이스나 새 도구가 필요한가를 자동으로 파고든다.

이 섹션의 "1초 안에 수십억 개 질의"와 실시간 평가 배포는 발표자가 자사 제품을 설명하며 든 주장이다.

09

관찰, 평가, 개선 루프 13:50

코딩 에이전트를 개선할 때 쓰는 루프를 음성에도 적용하자는 것이 발표의 뼈대다. 루프는 세 단계다.

  1. 관찰 observe: 오디오와 트레이스 데이터가 손에 있다.
  2. 평가 evaluate: 관찰한 것 바로 옆에 점수가 있다.
  3. 개선 improve: 사람이든 에이전트든 수정을 시작하고, 그 수정을 검증한다.

검증 단계를 위해 Arize는 에이전트 실험 agent experiments을 내놓았다. 발표자는 "트레이싱이 붙은 Postman"에 비유했다.

발표자가 그리는 미래: SRE 에이전트 14:30

사용자 오디오가 자동으로 트레이싱되고, 실시간 평가가 점수를 매긴다. 그 위에서 SRE 에이전트가 움직인다. 사람이 고용한 엔지니어가 아니라, 트레이스를 읽고 실패 유형을 파악하고 수정을 가설로 세우는 에이전트다.

발표자가 묘사한 아침 풍경 (예시) 아침에 PR 하나가 와 있다. "지연이 높았던 이유를 찾았다. 도구 결과를 자르지 않아 에이전트에 너무 많은 정보가 들어갔고 컨텍스트가 넘쳤다. 자르는 알고리즘을 넣어 개발 환경에 올렸고, 실패했던 트레이스를 그 수정본에 다시 돌렸다. 지연이 얼마나 줄었는지 성적표를 첨부한다." 사람은 승인 또는 거절만 누른다.

발표자는 이것을 스스로 고치는 소프트웨어와 지속적 개선이 모두의 현실이 되는 미래라고 불렀다. 음성에서도 가능하게 만드는 것이 중요하다고 했다.

10

결론과 오늘 할 일 15:50

  1. 에이전트를 보기 시작한다. OpenInference 계측기를 붙인다. 오픈소스, 무료, OpenTelemetry 호환이고 어느 백엔드로든 보낼 수 있다. Arize를 쓰든 안 쓰든 오디오 트레이싱부터 시작한다.
  2. 분석을 시작한다. 첫 음성까지 걸린 시간을 재고, 끼어들기를 세고, 대화가 사용자의 목적을 실제로 이뤘는지 평가한다. 어조든 지연이든 평가 하나를 만들어 본다.
  3. 음성을 다른 스택과 같은 수준으로 끌어올린다. 코딩 에이전트나 주식을 거래하는 에이전트에서 이런 일이 일어나면 아무도 넘어가지 않는다. 치즈버거를 주문하는 에이전트라고 넘어가서는 안 된다.

발표 끝에 Arize 유료 플랜 1년 무료 코드가 안내됐다. 2단계는 발표자가 자사 도구를 권한 대목이다.

11

핵심 정리

  1. 음성 에이전트는 빠르게 늘고 있고, 디버깅은 가장 어렵다. 지연, 말 차례, 받아쓰기 드리프트가 핵심 실패 유형이다.
  2. 텍스트 로그는 거짓말을 한다. 자막이 멀쩡해도 통화는 망가져 있을 수 있다.
  3. 환불 사례에서 자막은 "고쳤다"고 보였지만 실제로는 2.4초 침묵, 말 겹침, 14를 40으로 오인, 40번 주문 환불이 있었다.
  4. 해법은 오디오, 자막, 트레이스를 한 화면에 두고, 세션 단위로 여러 차례를 묶어 보는 것이다.
  5. OpenInference는 오디오 웹소켓 이벤트를 OpenTelemetry 호환 스키마로 정리한 오픈소스 규격이다. 제공자가 달라도 질의가 같아진다.
  6. 세션 ID가 타임라인을 꿰매고, 트레이스에서 오디오를 바로 재생하면 누가 언제 말했고 어떤 도구를 불렀는지 보인다.
  7. 자막 기반 LLM 심판으로는 부족하다. 감정, 지연, 끼어들기, 드리프트, 과제 성공을 오디오 모델로 직접 평가한다.
  8. 평가는 LLM 심판에서 도구와 시스템에 접근하는 에이전트 심판으로 옮겨 가고 있다.
  9. 평가 점수를 스팬에 붙이면 질의와 필터가 가능해지고, 조사 에이전트와 자동 수정 PR로 이어진다.
  10. 오늘 할 일: 오디오 트레이싱을 켜고, 첫 음성까지 걸린 시간과 끼어들기부터 재고, 평가 하나를 만든다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 음성 에이전트를 가장 디버깅하기 어렵다고 보는 이유 세 가지는?
지연, 말 차례 넘기기, 받아쓰기 드리프트. 셋 다 텍스트 로그에 남지 않는다.
Q2환불 사례에서 자막만 읽으면 어떻게 보이나?
에이전트가 40번으로 잘못 들었다가 사용자가 정정하자 고친 것처럼 보인다.
Q3같은 통화의 오디오에서 드러난 문제 네 가지는?
2.4초 침묵, 에이전트가 사용자 말 위에 겹쳐 말함, 14를 40으로 잘못 들음, 딱딱한 기계적 어조.
Q4그 통화의 환불은 결국 몇 번 주문으로 처리됐고, 그걸 어디서 알 수 있나?
40번 주문. 도구 호출 기록에서 보인다. 자막에는 "확인됐습니다"만 남는다.
Q5"자막 너머를 본다"는 것은 구체적으로 무엇을 한 화면에 두는 것인가?
오디오, 자막, 트레이스. 거기에 세션 단위 묶음과 지표(첫 음성까지의 시간, 끼어들기, 감정, 토큰 비용)를 더한다.
Q6OpenInference는 무엇이고, 발표에서 왜 중요하다고 했나?
생성형 AI 이벤트를 OpenTelemetry 호환 형식으로 적는 오픈소스 시맨틱 컨벤션. 오디오 웹소켓 이벤트를 여기에 매핑하면 제공자가 달라도 질의할 수 있는 스키마 하나가 생긴다.
Q7세션 ID의 역할은?
여러 차례의 대화와 웹소켓 이벤트를 하나의 타임라인으로 꿰맨다. 그래서 누가 언제 말했고 어디서 끊겼는지, 그때 어떤 도구를 불렀는지 볼 수 있다.
Q8자막에 LLM 심판을 돌리는 평가로는 왜 부족한가?
어조와 감정, 지연, 끼어들기, 받아쓰기 드리프트는 자막에 없다. 오디오 모델로 오디오 자체를 평가해야 한다.
Q9LLM 심판과 에이전트 심판의 차이는?
LLM 심판은 자막이나 오디오를 분석만 한다. 에이전트 심판은 도구와 외부 시스템에 접근해 평가 정보를 채운다. 예: 접근 권한이 맞았는지 점검.
Q10평가 점수를 스팬에 붙여 두면 무엇이 가능해지나?
데이터 전체에 대한 질의와 필터. 그리고 평가와 모니터가 조사 에이전트를 띄워 원인을 파고드는 흐름.
Q11발표자가 묘사한 SRE 에이전트의 아침 PR에는 무엇이 들어 있나?
문제 설명(도구 결과를 자르지 않아 컨텍스트 초과), 수정(자르기 알고리즘), 개발 환경 배포, 실패 트레이스 재실행 결과, 지연 감소 성적표. 사람은 승인 또는 거절만 한다.
Q12발표자가 제안한 오늘 할 일 두 가지는?
OpenInference 계측기를 붙여 오디오 트레이싱을 시작하고, 첫 음성까지 걸린 시간과 끼어들기를 재며 평가 하나를 만든다.
