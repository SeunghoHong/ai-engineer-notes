에이전트 인프라는 바이브 코딩하지 마라

에이전트가 제대로 일하려면 실행 환경이 일곱 가지를 받쳐 줘야 한다. 작업 공간, 상태 보존, 출렁이는 자원, GPU, 공유 파일, 촘촘한 통제, 관측 정보다. Modal의 CTO는 이 기반이 AI에게 대충 맡겨 지을 수 있는 것이 아니라고 주장한다.

원본 영상: Don't Vibe Code Your Agent Infrastructure 발표: Akshat Bubna (Modal CTO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름 중 확실한 것(Modal, Modal Volumes, Datadog)은 바로잡았다. 확실하지 않은 것은 들린 대로 적고 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자는 샌드박스를 파는 Modal의 CTO다. 고객 사례와 "직접 만들지 말라"는 결론은 그 점을 감안해 읽자.

3분 요약
  1. 스프레드시트의 셀마다 에이전트를 하나씩 붙인 금융 분석 제품이 이미 있다. 쿼리 하나에 에이전트 수천 개가 떴다가 사라진다.
  2. 에이전트 하나는 샌드박스 하나에서 돈다. 샌드박스 안에서 에이전트 루프(하네스)와 도구가 실제로 도는 곳을 다른 컨테이너로 나눈다.
  3. 발표자가 꼽은 필요 조건은 작업 공간, 상태 보존, 자원 탄력성, 다양한 연산 장치, 공유 파일 시스템, 통제, 관측이다.
  4. 에이전트의 CPU·메모리 사용량은 크게 출렁인다. 최대치에 맞춰 미리 잡으면 샌드박스마다 15코어·15GB가 필요해 돈이 맞지 않는다.
  5. 도메인 허용 목록만으로는 부족하다. 사이드카에 직접 만든 프록시를 붙여 경로와 작업 단위까지 막는 방식이 퍼지고 있다.
  6. 샌드박스 플랫폼은 신뢰성, 보안, 규모 때문에 바이브 코딩으로 지으면 안 된다. Modal은 한 주에 스냅샷 2천만 개를 만든다고 한다.
  7. 앞으로는 두뇌(하네스)와 손(샌드박스)이 분리된다. 에이전트가 필요한 환경을 그때그때 만들고, 남기고, 버린다.
01

셀마다 에이전트 하나 00:30

발표자는 금융 쪽 청중을 위해 한 장면을 꺼낸다. 펀드의 금융 분석가가 포트폴리오에 담긴 회사를 전부 분석하려 한다.

예전며칠이 걸린다회사마다 데이터 출처를 연결한다. 회사마다 Python 코드를 돌린다.
→
지금셀마다 에이전트가 일한다스프레드시트의 셀 하나하나에 서로 다른 에이전트가 붙는다. 쿼리 하나를 던지면 모든 셀이 동시에 움직인다.

Modal의 고객사 Heavy AI(자막 표기. 금융 분석용 AI 회사 Hebbia로 추정)가 이런 제품을 이미 내놓았다. 발표자는 이런 제품을 실제로 만들려면 인프라가 무엇을 해 줘야 하는지 묻는다. 발표 전체가 그 질문에 대한 답이다.

02

에이전트를 받치는 구조 01:30

에이전트마다 Modal 샌드박스 sandbox가 하나씩 붙는다. 샌드박스는 믿을 수 없는 코드를 안전하게 돌리도록 격리한 실행 환경이다.

예전에는 샌드박스 하나가 컨테이너나 마이크로VM microVM 하나와 같았다. 이제는 샌드박스 하나 안에 여러 개를 띄울 수 있다. 셀마다 에이전트가 붙는 제품에는 이 기능이 꼭 필요하다.

부품하는 일필요한 이유
하네스 harness에이전트 루프. 모델 API를 불러 추론하고, 도구 호출을 내보내고, 이를 반복한다에이전트의 판단을 맡는다
도구 실행 컨테이너도구 호출이 실제로 돌아가는 곳하네스와 떼어 놓아야 보안과 격리가 된다
사이드카 sidecar같은 샌드박스 안에서 주 컨테이너 옆에 붙어 함께 도는 보조 컨테이너뒤의 통제 이야기에서 프록시 자리로 다시 나온다
공유 저장소에이전트끼리, 주 컨테이너와 사이드카끼리 파일을 나눈다에이전트끼리 협업해야 한다. 예를 들어 같은 행의 에이전트들이 볼륨 하나를 같이 쓰게 나눌 수 있다
빠른 기동과 종료쿼리 하나에 에이전트 수천 개를 띄우고, 끝나면 바로 내린다스프레드시트에는 셀이 많다

저장소를 행 단위로 나눌지, 다른 단위로 나눌지는 만드는 쪽이 정한다고 했다.

Modal은 무엇인가 03:10 AI 애플리케이션용 기본 부품 primitives을 모은 플랫폼이다. 발표자는 파일 시스템, 스케줄러, 런타임을 처음부터 직접 만들었다고 소개한다. 쓰임새는 추론(LLM 포함), 샌드박스, 학습, 대량 일괄 처리용 함수다. 이 발표는 그중 샌드박스가 어떻게 바뀌고 있는지를 다룬다.

04 · 필요 조건 2/7

상태 남기기 05:00

작업 공간은 오래 남아 있어야 한다. 발표자는 Basis의 회계 업무 흐름으로 설명한다.

  1. 회계 문서가 들어온다.
  2. 에이전트가 깨어나 문서를 처리한다.
  3. 에이전트가 회계사의 답을 기다린다. 며칠이 걸릴 수도 있다.
  4. 회계사가 답하면 에이전트가 다시 깨어나, 멈췄던 지점부터 이어서 일한다.

그래서 상태는 무기한 남길 수 있어야 한다. 하지만 계산 자원은 비싸다. 계산 자원은 에이전트가 실제로 일할 때만 돌아야 한다. 즉 저장은 계속, 계산은 필요할 때만이다.

05 · 필요 조건 3/7

자원은 쓸 때만 06:20

발표자는 에이전트가 자원을 매우 들쭉날쭉하게 쓴다고 말한다. 근거로 Ramp의 허락을 받아 Ramp Inspect의 사용량 데이터를 보여 준다.

  • 샌드박스끼리 비교해도 CPU·메모리 사용량 차이가 크다.
  • 한 샌드박스 안에서도 시간에 따라 사용량이 크게 바뀐다.
  • 이유는 단순하다. 무거운 컴파일을 하거나 메모리를 많이 먹는 분석을 하면 사용량이 튄다.
  • 샌드박스별 최대 사용량에도 어느 정도 경향은 있지만, 대체로 제각각이다.
최대치에 맞춰 미리 잡기 07:10샌드박스마다 CPU 15코어, 메모리 15GB발표자는 경제적으로 말이 안 된다고 본다.
→
필요할 때 받기미리 요청하지 않는다샌드박스가 필요로 할 때 자원을 안정적으로 받는다. 쓴 시간만큼만 돈을 낸다.

오른쪽은 Modal이 공들였다고 소개한 자기 제품의 기능이다. 그 점을 감안해 읽자.

06 · 필요 조건 4/7

다양한 연산 장치 07:40

에이전트가 쓰는 연산 장치도 다양해진다. 지금은 GPU가 필요하다. 앞으로는 TPU나 AMD 칩이 필요할 수도 있다.

발표자가 든 예는 Cloud Science다. 자막에는 이렇게 나오지만, 뒤에서 "Cloud가 무거운 계산이 필요할 때"라고 말하는 걸 보면 Anthropic의 Claude를 쓰는 과학용 제품으로 보인다(추정). 발표자에 따르면 이 제품에는 Modal 연동이 기본으로 들어 있다.

  • 데이터를 CPU로 전처리해야 할 때 그 계산을 Modal로 넘긴다.
  • 과학 모델을 돌리려고 GPU가 필요할 때도 Modal로 넘긴다.

게임 디자인, 영상 편집, 3D 개발, CAD도 에이전트에게 GPU를 요구한다. 08:10

모델 학습을 스스로 개선하는 에이전트 08:30

요즘 가장 주목받는 주제는 재귀적 자기 개선 recursive self-improvement, RSI이다. AI가 더 나은 AI를 만드는 일을 스스로 되풀이하는 것을 말한다. 발표자는 GPU 샌드박스가 이 일에 잘 맞고, 에이전트도 GPU 샌드박스를 잘 쓴다고 말한다.

Modal 블로그 실험 (발표자 소개) 에이전트에게 샌드박스를 주고 모델 학습 결과를 조금씩 끌어올리게 hill climbing 했다. 에이전트는 GPU 종류를 바꿔 가며 시도했다. 어블레이션 ablation을 병렬로 돌렸다. 실험을 많이 돌려 목표에 빨리 닿았다.
07 · 필요 조건 5/7

함께 쓰는 파일 09:00

에이전트끼리 함께 일하는 경우가 늘었다. 에이전트는 하위 에이전트 sub-agent와 파일 시스템을 나눠 쓴다. 사람과도 같은 파일을 놓고 함께 일한다.

그러려면 파일 시스템이 세 가지를 갖춰야 한다.

  • 빠르다.
  • 일관성 consistency이 있다. 한쪽이 쓴 내용을 다른 쪽이 읽을 때 같은 내용을 본다.
  • 동작을 이해하기 쉽다. 개발자가 결과를 예측할 수 있다.

발표자는 Modal Volumes로 이 문제를 풀고 있다고 했다.

메모리도 결국 파일이다 09:30

스스로 나아지는 에이전트도 늘고 있다. 에이전트는 메모리를 저장하고 고친다. 백그라운드 작업으로 메모리를 다듬기도 한다. 요즘은 이 작업을 dreaming이라고 부른다.

이 메모리도 파일 시스템 안의 파일일 뿐이다. 그래서 여기서도 파일 시스템 성능이 중요하다.

08 · 필요 조건 6/7

할 수 있는 일 좁히기 09:50

에이전트는 실수한다. 민감한 데이터를 엉뚱한 곳에 흘려도 스스로 모를 수 있다. 발표자는 "독일의 어느 포럼"을 농담처럼 예로 든다. 그래서 에이전트가 할 수 있는 일과 없는 일을 세밀하게 정해야 한다.

통제할 것내용
들어오는 IP어떤 IP가 에이전트에 접근할 수 있나
인증에이전트에 접근하는 쪽을 어떻게 확인하나
나가는 도메인에이전트가 어떤 도메인과 통신할 수 있나
자격 증명 credentials서비스 접속용 비밀 값을 에이전트가 볼 수 없는 방식으로 넣는다. 볼 수 있으면 나중에 다른 곳으로 빼돌릴 exfiltration 수 있다
경로와 작업 10:40Datadog이나 GitHub 같은 서비스 안에서 어떤 경로, 어떤 작업까지 허용할지

발표자가 강조한 변화는 마지막 줄이다. 도메인 단위 허용 목록 allowlist만으로는 부족하다는 걸 알게 됐다고 한다. 사용자들은 에이전트가 하는 작업 하나하나를 따져 막고 싶어 한다.

위 표는 발표에 없는 예시다. 도메인 규칙과 경로·작업 규칙의 차이를 보이려고 만들었다.

사이드카 프록시 패턴 11:00

여기서 앞의 사이드카가 다시 나온다. 사용자가 가벼운 프록시 proxy를 직접 만들어 사이드카로 붙인다. 에이전트의 바깥 통신은 이 프록시를 거친다. 프록시에는 무엇을 허용할지 자기 규칙을 넣는다. 발표자는 Ramp도 이 방식을 잘 쓰고 있다고 했다.

09 · 필요 조건 7/7

에이전트가 읽는 관측 정보 11:20

발표자가 "과소평가됐다"고 부른 마지막 항목은 관측 가능성 observability이다. 시스템 안에서 무슨 일이 일어나는지 로그와 지표로 볼 수 있는 정도를 말한다.

예는 에이전트가 모델 학습을 반복하는 자동 연구 auto research다. 학습이 실패하면 이렇게 돌아가야 한다.

  1. 에이전트가 실패 로그를 쉽게 읽는다.
  2. 무슨 일이 있었는지 따진다.
  3. 파라미터를 바꿔 다시 돌린다.

학습이 도는 동안에도 에이전트가 볼 것이 있다.

  • GPU 사용률: 학습이 멈춰 있지 않은가
  • 예산: 샌드박스에서 돈을 너무 쓰고 있지 않은가

이런 정보는 원래 사람에게 중요했다. 이제는 에이전트가 계산 자원을 점점 더 많이 움직인다. 그래서 Modal은 이 정보를 에이전트에게 직접 보여 주는 데 시간을 많이 쓰고 있다고 한다.

10

바이브 코딩하면 안 되는 이유 12:10

필요한 것을 다 알았으니 AI 도구 'Astra'(들린 대로, 추정)에게 에이전트 플랫폼을 만들라고 하면 되지 않을까. 발표자의 답은 "좋은 생각이 아니다"이다. 샌드박스 플랫폼을 바이브 코딩 vibe coding으로 만들지 말라고 한다. 바이브 코딩은 AI에게 말로 시켜 코드를 만들고, 그 코드를 깊이 따지지 않고 쓰는 방식이다.

1 · 신뢰성

매일 쓰는 웹사이트들도 자꾸 멈춘다. 드문 사건 tail event이 터졌을 때 시스템이 어떻게 무너지고 그 영향이 어떻게 되돌아오는지 따지기는 AI가 있어도 어렵다. 그래서 시스템은 아주 조심해서 지어야 한다.

2 · 보안

샌드박스 플랫폼을 바이브 코딩으로 만들 수는 있다. 하지만 모든 것이 빠르게 바뀌는 지금, 보안 경계를 계속 점검하고 방어 가능하게 지킬 사람은 누구인가.

3 · 규모

Modal은 샌드박스 100만 개까지 확장한 과정을 블로그에 썼다. 거기에는 시스템 설계에 대한 깊은 고민이 들었다고 한다. 규모가 커졌을 때 반드시 돌아가야 하는 부분은 바이브 코딩에 맡길 일이 아니다.

발표자는 바로 이 플랫폼을 파는 회사의 CTO다. "직접 짓지 말라"는 말은 "Modal을 쓰라"는 말과 이어진다. 그 점을 감안해 읽자.

11

실제 규모 13:30

발표자는 앞에서 말한 기능들이 이미 큰 규모로 쓰이고 있다며 Modal의 숫자를 밝힌다. 모두 발표자가 말한 것이고, 빠르게 늘고 있다고 했다.

개인 비서 고객의 요구 14:00

항목요구
생성 속도초당 샌드박스 1만 개
도는 수100만 개 가까이
수명2~3분 정도로 짧다
응답뜨자마자 1초 안에 바로 쓸 수 있어야 한다

자막에는 "오래 간다"로 들리지만 바로 뒤에 "2~3분 정도"라고 하므로 "오래 가지 않는다"는 뜻으로 읽었다.

참고 계산(발표에 없음): 동시에 떠 있는 수는 대략 "생성 속도 × 수명"이다. 초당 1만 개 × 120~180초 = 120만~180만 개로, 발표의 "100만 개 가까이"와 같은 규모다. 초당 1만 개가 평균이 아니라 최대 속도라면 실제 동시 개수는 이보다 작을 수 있다(추측).

클라우드 하나로는 모자란다 14:20

이 규모는 클라우드 한 곳에서 다 얻을 수 없다고 발표자는 말한다. 세계적으로 GPU뿐 아니라 CPU도 모자라지고 있다고 한다. 그래서 Modal은 여러 하이퍼스케일러 hyperscaler와 네오클라우드 neocloud의 용량을 모아 쓴다. 사용자는 필요할 때 세계 곳곳의 CPU 용량을 쓸 수 있다.

12

두뇌와 손의 분리 14:50

발표자는 하네스가 동적인 환경을 아주 잘 다룬다고 본다. 그래서 두뇌(하네스)와 손(샌드박스, 즉 실제로 일이 도는 런타임)이 갈라지고 있다고 말한다. 하네스는 이렇게 일하게 된다.

  • 지금 필요한 환경을 그 자리에서 띄운다.
  • 나중에 쓸 환경은 스냅샷으로 떠서 산출물처럼 보관한다.
  • 필요에 따라 환경을 고친다.

반려동물, 가축, 그다음 15:30

발표자는 이 변화를 서버 운영의 오래된 비유인 반려동물과 가축 pets vs cattle에 이어 설명한다.

반려동물 · 옛날

서버마다 손으로 맞춘다. 배포 하나하나를 따로 관리하고 따로 따져야 한다.

가축 · 컨테이너와 Kubernetes 이후 16:00

서버는 같은 틀에서 찍어 낸 똑같은 것이다. 늘리고 줄일 수 있다. 하나가 죽어도 시스템이 스스로 회복하니 문제가 안 된다.

발표자는 지금 에이전트를 배포하는 사람 대부분이 여기 있다고 본다.

미생물의 바다 · 앞으로 16:40

스스로 진화하며 서로 함께 일하는 수많은 생물처럼, 환경이 계속 생기고 바뀌고 사라진다.

발표자는 이 비유를 'Six'(들린 대로, 추정)에게서 빌렸다고 밝혔다.

발표자는 똑같은 환경을 찍어 내고 에이전트 수만 늘리는 방식이 한계라고 본다. 모델은 동적인 환경을 다루는 데 능하다. 스냅샷을 찍고, 필요할 때 환경을 많이 만들고, 그 사이를 오가며 일할 수 있다. 같은 틀만 주면 이 능력을 쓰지 못한다.

13

결론 17:00

계산, 저장, 네트워크에 대한 단단한 기본 부품을 주면 에이전트는 더 많은 일을 한다. 환경을 많이 띄우고, 서로 함께 일하고, 상황에 맞춰 움직인다.

좋은 기본 부품이 있어야 에이전트가 더 많은 일을 한다.발표자의 마무리 말("great primitives let your agents do more")을 옮김
14

핵심 정리

  1. 셀마다 에이전트가 붙은 스프레드시트처럼, 쿼리 하나에 에이전트 수천 개가 떴다 사라지는 제품이 이미 있다.
  2. 에이전트 하나는 샌드박스 하나에서 돈다. 샌드박스 안에서 하네스와 도구 실행 공간을 다른 컨테이너로 나눈다.
  3. 에이전트마다 저장소, 의존성, 서비스, 문서를 한곳에 모은 작업 공간이 필요하다.
  4. 상태는 무기한 남기고, 계산은 일할 때만 돌린다. 보존 방식은 전체 스냅샷, 디렉터리 스냅샷, 볼륨이다.
  5. 에이전트의 자원 사용량은 크게 출렁인다. 최대치로 미리 잡으면 샌드박스마다 15코어·15GB라 돈이 맞지 않는다.
  6. 에이전트는 GPU 같은 다양한 연산 장치를 쓰고, GPU 샌드박스로 모델 학습을 스스로 반복 개선한다.
  7. 협업과 메모리는 결국 파일이다. 빠르고 일관된 공유 파일 시스템이 필요하다.
  8. 도메인 허용 목록으로는 부족하다. 사이드카 프록시로 경로·작업 단위까지 막고, 자격 증명은 에이전트가 못 보게 넣는다.
  9. 로그, GPU 사용률, 예산을 에이전트가 직접 읽어야 다음 시도를 스스로 정한다.
  10. 샌드박스 플랫폼은 신뢰성, 보안, 규모 때문에 바이브 코딩하지 않는다. 앞으로는 두뇌와 손이 분리되고 환경은 필요할 때 만들고 버리는 것이 된다.
15

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1셀마다 에이전트가 붙은 스프레드시트를 만들 때 인프라가 감당해야 하는 것은?
쿼리 하나에 에이전트 수천 개를 빨리 띄우고 끝나면 바로 내려야 한다. 에이전트끼리 협업하도록 저장소를 나눠 줘야 한다.
Q2샌드박스 하나 안에 컨테이너를 여러 개 띄우는 이유는?
에이전트 루프인 하네스와 도구 호출이 실제로 도는 곳을 떼어 놓기 위해서다. 보안과 격리 때문이다.
Q3하네스가 하는 일 세 가지는?
모델 API를 불러 추론하고, 도구 호출을 내보내고, 이를 반복한다.
Q4Basis 사례에서 상태를 남겨야 하는 이유와, 비용을 아끼는 방법은?
회계사의 답을 며칠 기다릴 수 있고, 답이 오면 멈춘 지점부터 이어야 한다. 상태는 계속 남기고 계산 자원은 에이전트가 일할 때만 돌린다.
Q5상태를 남기는 세 가지 방식과, 디렉터리 스냅샷이 쓸모 있는 경우는?
루트 파일 시스템 스냅샷, 디렉터리 스냅샷, 볼륨. 디렉터리 스냅샷은 node_modules 같은 폴더만 남기고 기본 이미지는 새 버전으로 올리고 싶을 때 쓴다.
Q6Ramp Inspect 데이터로 본 "최대치에 맞춰 자원 잡기"의 문제는?
사용량이 샌드박스끼리도, 시간에 따라서도 크게 달라진다. 최대치에 맞추면 샌드박스마다 CPU 15코어와 메모리 15GB를 잡아야 해 경제적으로 맞지 않는다.
Q7GPU 샌드박스를 받은 에이전트가 모델 학습을 개선할 때 한 일은?
GPU 종류를 바꿔 가며 시도하고, 어블레이션을 병렬로 돌리고, 실험을 많이 돌려 목표에 빨리 닿았다.
Q8에이전트의 메모리와 dreaming이 파일 시스템 이야기인 이유는?
에이전트가 저장하고 다듬는 메모리도 결국 파일 시스템 안의 파일이다. 그래서 파일 시스템 성능이 중요하다.
Q9도메인 허용 목록만으로 부족한 이유와, 사용자들이 쓰는 대안은?
허용한 사이트 안에서도 어떤 경로, 어떤 작업을 하는지 따져야 하기 때문이다. 사용자가 규칙을 넣은 가벼운 프록시를 직접 만들어 사이드카로 붙인다.
Q10자격 증명을 에이전트가 볼 수 없게 넣어야 하는 이유는?
에이전트가 비밀 값을 볼 수 있으면 나중에 다른 곳으로 빼돌릴 수 있다.
Q11관측 정보를 에이전트에게 직접 열어 주면 무엇이 가능해지나?
학습이 실패하면 에이전트가 로그를 읽고 원인을 따져 파라미터를 바꿔 다시 돌린다. 학습 중에는 GPU 사용률과 예산을 보고 멈춤이나 과지출을 잡는다.
Q12샌드박스 플랫폼을 바이브 코딩하면 안 되는 세 가지 이유는?
신뢰성(드문 사건에서 시스템이 무너지는 방식을 따지기 어렵다), 보안(경계를 계속 지킬 사람이 필요하다), 규모(커졌을 때 반드시 돌아가야 한다).
Q13반려동물, 가축, 미생물의 바다는 각각 무엇을 가리키나?
반려동물은 서버마다 손으로 맞추던 방식이다. 가축은 같은 틀로 찍어 내 늘리고 줄이는 컨테이너·Kubernetes 방식이다. 미생물의 바다는 에이전트가 환경을 그때그때 만들고 바꾸고 버리며 서로 함께 일하는 앞으로의 모습이다.
