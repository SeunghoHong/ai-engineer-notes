언제 내 GPU가 API보다 싸지나

API 대신 오픈 웨이트 모델을 내 인프라에서 돌리면 돈을 아낄 수 있다. 하지만 그 손익은 모델 크기, 동시 사용자 수, GPU 사용률, 하네스 선택에 따라 계단처럼 크게 바뀐다. imec이 코딩 과제로 천 번 넘게 돌려 본 결과다.

원본 영상: When Running Your Own AI Models Beats Paying for APIs 발표: Steven Latré (imec AI 부문 총괄)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 확실하지 않은 것에는 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 기업의 AI 사용은 폐쇄형 API → 비용 최적화 → 오픈 웨이트 모델 직접 운영·GPU 임대 → 인프라 구매 순으로 옮겨 간다. 발표자의 회사는 지금 세 번째 단계에 있다.
  2. imec은 코딩 벤치마크 SWE-bench Pro로 하네스 3종 × 오픈 웨이트 모델 × 하드웨어를 바꿔 가며 천 번 넘게 돌렸다.
  3. 정확도는 작은 모델 32.5~40%, GLM은 Opus 수준, Kimi K3는 86%였다.
  4. 비용은 정확도에 비례하지 않는다. 성능이 같은 두 모델의 GPU 비용이 4배 차이 나기도 하고, 정확도가 20% 오르는데 비용은 15%만 오르기도 한다.
  5. 동시 사용자 수가 정확도보다 중요하다. Kimi K3는 큰 장비에서도 4명 정도만 안정적으로 받았고, Claude Code보다 3배 느렸다.
  6. 작은 장비는 GPU를 89% 돌려야 API보다 싸다. 8×B200 같은 큰 장비는 15%면 된다. GLM 급이 분기점이고, 코딩 지원 기준 약 24.5%를 아낄 수 있었다.
  7. 하네스는 정확도를 거의 바꾸지 않았다. 하지만 Codex는 토큰을 절반만 써서 GPU 사용 시간도 절반이었다. 내 GPU라면 청구서가 절반이 된다.
01

반도체 연구소가 AI를 말하는 이유 00:00

imec은 벨기에의 반도체 연구 기관이다. 40년 넘게 운영됐고, 발표자는 세계에서 가장 앞선 연구용 클린룸을 갖고 있다고 소개한다. 지금 쓰이는 트랜지스터 기술 대부분이 이곳에서 나왔다는 것이 발표자의 설명이다.

imec은 트랜지스터에서 끝나지 않고 시스템과 워크로드까지 연구한다. 워크로드workload는 하드웨어 위에서 실제로 돌아가는 일을 말한다. 발표자는 AI 워크로드와 인프라를 잇는 일을 맡고 있다.

02

AI 도입의 네 단계 01:20

imec도 사내에서 에이전트 흐름을 만들며 몇 단계를 거쳤다. 발표자는 많은 회사가 같은 길을 걷는다고 본다.

  • 2024~2025년: 최신 프런티어 모델만 쓰면 된다고 생각했다. 최고도 부족하다고 느꼈다.
  • 가격 방식이 바뀌었다: 구독형 과금에서 토큰 단위 과금으로 넘어갔다.
  • 지난 1년: 모델 라우팅model routing을 했다. 일마다 알맞은 모델을 골라 보내는 방식이다.

발표자는 모델 라우팅이 손쉬운 첫 최적화일 뿐이라고 말한다. 토큰 사용량이 계속 늘면 결국 자기 스택을 직접 쥐어야 한다.

단계하는 일
1단계폐쇄형 API를 그대로 가져다 쓴다
2단계비용을 최적화한다 (모델 라우팅 등)
3단계오픈 웨이트 모델을 직접 띄우고, GPU 인프라를 빌린다. imec이 지금 있는 단계다
4단계인프라를 사서 사내에 둔다 (온프레미스)

이 발표는 3단계와 4단계를 다룬다.

03

직접 가지면 고민이 늘어난다 03:30

API로 토큰을 사는 건 아주 쉽다. 1단계에서는 "이 일에 맞는 정확도를 내는 모델이 뭔가"만 고민하면 된다.

인프라를 직접 가지면 정해야 할 것이 한꺼번에 늘어난다.

모델과 소프트웨어
  • 어떤 모델을 쓸까
  • 그 모델을 믿을 수 있나
  • 어떤 하네스를 쓸까
  • 추론 엔진inference engine은 무엇으로 할까
하드웨어
  • 어떤 하드웨어 구조가 맞나
  • CPU와 GPU를 어떤 비율로 둘까
  • KV 캐시를 어떻게 최적화할까

발표자는 모델·하네스 쪽과 인프라 쪽 사이에 빈틈이 있다고 본다. imec은 그 빈틈을 메우는 역할을 하려 한다.

04

실험을 어떻게 했나 04:40

질문은 하나다. 같은 에이전트 과제 성능을 낼 때, API에서 내 인프라로 옮기면 비용이 얼마인가. 토큰 단가 대신 총소유비용TCO, total cost of ownership으로 따진다. 장비, 운영 등 직접 가졌을 때 드는 비용 전부다.

왜 장기 과제인가 05:20

장기 과제long-horizon task는 에이전트가 여러 단계를 오래 이어서 처리하는 일이다. 발표자는 이런 일이 인프라를 직접 가질 이유가 처음 생기는 지점이라고 본다. 사람과 짧게 주고받는 대화형 사용은 경제성이 다를 수 있다고 덧붙였다.

05

모델 정확도는 세 묶음 07:30

모델은 해결률로 크게 세 묶음으로 나뉘었다.

작은 묶음의 하한은 자막에 "32 5"로 들려 32.5%로 읽었다. "작은 모델"은 발표자 기준으로 파라미터가 수천억 개 이하인 모델이다.

  • 작은 묶음: Qwen, DeepSeek. 해결률 32.5~40%.
  • 가운데 묶음: GLM. Anthropic의 Opus와 비슷한 수준.
  • 가장 큰 묶음: 몇 달 전 나온 Kimi K3. 해결률 86%.

발표자 스스로 Kimi K3의 높은 점수에는 벤치마크 과제가 학습 데이터에 섞였을 가능성이 있다고 단서를 달았다.

발표자는 이 정확도 순위 자체는 Artificial Analysis 같은 공개 비교 사이트에서도 볼 수 있다고 말한다. 새로운 건 여기에 하드웨어를 더했을 때다.

06

비용은 계단처럼 오른다 08:40

정확도에 필요한 하드웨어를 붙여 보면, 비용이 정확도를 따라 매끄럽게 오르지 않는다.

비교정확도 변화GPU 임대 비용 변화
Qwen ↔ DeepSeek거의 같다필요한 하드웨어가 4배 차이
GLM → Kimi K3약 20% 오른다약 15%만 오른다

Qwen과 DeepSeek 중 어느 쪽이 4배 비싼지는 발표에서 말하지 않았다.

발표자가 말하는 교훈은 이렇다. 비용 곡선은 직선이 아니고 계단 함수다. 조금 더 좋은 모델이나 조금 덜 좋은 모델을 고르는 것만으로 필요한 장비 등급이 통째로 바뀔 수 있다. 그래서 오픈 웨이트 모델로 옮길 때는 정확도와 함께 하드웨어 제약과 실제 비용을 꼭 같이 봐야 한다.

07

동시 사용자 수가 더 중요하다 10:00

API를 쓰면 토큰 지연 시간과 처리량을 대략 안다. 내 인프라로 옮기면 새 질문이 생긴다. 한 장비에 몇 명이 동시에 붙어도 지연이 무너지지 않나. 이것이 동시성concurrency이다.

메모리가 먼저 찬다 10:40

대부분의 시스템은 메모리가 한계를 정한다. 메모리에는 두 가지가 들어가야 한다.

  • 모델 파라미터: 모델 크기만큼 고정으로 차지한다.
  • 사용자별 KV 캐시: 모델이 앞서 읽은 내용을 다시 계산하지 않으려고 저장해 두는 값이다. 사용자가 늘수록 커진다.

결과: 큰 모델일수록 불리하다 11:10

모델마다 가장 알맞은 장비를 썼는데도, 편하게 받을 수 있는 동시 사용자 수는 크게 떨어졌다. 장비를 키워도 마찬가지였다. 모든 경우가 기준선인 Claude Code보다 느렸다.

발표자의 결론은 동시성이 정확도보다 더 중요할 수 있다는 것이다. 정확도는 출발선일 뿐이다. 실제 비용은 장비 하나에 몇 명을 태울 수 있느냐에서 갈린다.

발표자는 발표에서 다룬 주제마다 자세한 블로그 글이 있고, 슬라이드의 QR 코드로 연결된다고 안내했다.

08

API, 임대, 구매의 손익분기 12:20

imec은 세 가지 선택지를 총소유비용으로 비교했다.

  • API를 계속 쓴다.
  • GPU 업체에서 GPU를 빌린다.
  • 장비를 사서 사내에 둔다.

보안 등 다른 이유로 옮길 수도 있지만, 여기서는 비용만 본다. 판단 기준은 GPU 사용률이다. 내 GPU가 전체 시간 중 몇 퍼센트를 일해야 API보다 싸지는지를 따진다.

슬라이드에는 "더 낮은 하드웨어"로 적혀 있었는데, 발표자가 무대에서 "더 높은 하드웨어"가 맞다고 바로잡았다. 위 차트는 바로잡은 내용을 따른다.

정리하면 장비 등급이 낮을수록 API에서 옮기는 게 손해다. 작은 모델을 작은 장비에서 돌리면 GPU를 거의 쉬지 않고 돌려야 겨우 본전이다.

분기점은 GLM 급 평균을 내 보면 GLM 급 모델이 API에서 내 인프라로 옮기는 게 유리해지는 기준선이었다. 코딩 지원 과제로 계산한 총소유비용에서 약 24.5%를 아낄 수 있었다.

절감률은 자막에 "24 5%"로 들려 24.5%로 읽었다.

09

하네스가 GPU 청구서를 바꾼다 14:30

하네스harness는 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀이다. Codex나 Claude Code가 여기에 해당한다.

처음 보기에는 하네스가 별 차이를 만들지 않았다. 어느 하네스든 어느 모델이든 이 벤치마크에서 정확도가 비슷했다. API만 쓴다면 "하네스는 상관없다"고 결론 내도 된다.

내 GPU를 쓰면 다르다. GPU가 돌아간 실제 시간wall time이 곧 비용이기 때문이다.

발표자의 결론은 하네스와 모델의 조합이 정확도에는 영향이 없어도 총소유비용에는 크게 영향을 준다는 것이다.

API를 쓸 때하네스는 정확도만 보면 된다일만 끝내면 어느 하네스든 비슷하다

10

남은 과제와 imec의 제안 16:20

발표자는 이번 연구가 첫 번째 결과일 뿐이라고 말한다. API에서 인프라로 옮기는 결정은 단순하지도 직선적이지도 않다.

  • 응용이 섞인다: 이번에는 코딩 지원 하나만 봤다. 실제 기업은 여러 응용을 함께 돌리니 더 복잡하다.
  • 세 요소가 얽힌다: 하네스, 모델, 인프라 사이의 관계가 복잡하다.
  • 다루지 못한 것: 양자화quantization, 추측 디코딩speculative decoding 같은 최적화의 영향. 추측 디코딩은 실험에 적용했지만 자세히 설정을 바꿔 보지는 않았다.
  • 표적이 계속 움직인다: 새 모델과 새 하드웨어가 계속 나온다.

imec은 지금의 벤치마크 파이프라인을 키워 전체 벤치마크 데이터셋을 공개할 계획이다. 또 소프트웨어 쪽 사람과 칩·인프라 업체를 묶는 연합alliance을 만든다고 밝혔다.

imec은 비영리 연구 기관이지만 반도체·인프라 업체를 고객으로 두고 있고, 발표 끝에서 연합 참여를 권했다. "내 인프라로 옮길 이유"를 강조하는 대목은 이 점을 감안해 읽자.

11

핵심 정리

  1. AI 사용은 폐쇄형 API → 비용 최적화 → 오픈 웨이트 직접 운영·GPU 임대 → 인프라 구매 순으로 옮겨 간다.
  2. 인프라를 직접 가지면 모델, 하네스, 추론 엔진, 하드웨어 구조, CPU·GPU 비율, KV 캐시까지 정해야 한다.
  3. 장기 과제는 인프라를 직접 가질 이유가 처음 생기는 지점이다. 그래서 SWE-bench Pro로 실험했다.
  4. 해결률은 작은 모델 32.5~40%, GLM은 Opus 수준, Kimi K3는 86%였다.
  5. 비용은 계단 함수다. 성능이 같아도 장비가 4배 차이 나고, 정확도 +20%에 비용은 +15%일 수도 있다.
  6. 메모리에는 모델 파라미터와 사용자별 KV 캐시가 함께 들어가야 한다. 사용자가 늘면 KV 캐시가 커진다.
  7. 동시성이 정확도보다 중요할 수 있다. Kimi K3는 약 4명만 안정적으로 받았고 Claude Code보다 3배 느렸다.
  8. API보다 싸지려면 작은 장비는 GPU 사용률 89%, 8×B200은 15%가 필요하다.
  9. GLM 급이 분기점이다. 코딩 지원 기준 총소유비용을 약 24.5% 아꼈다.
  10. 하네스는 비용 항목이다. GLM에서 Codex는 토큰과 GPU 시간을 절반만 썼다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말한 AI 도입의 네 단계는?
폐쇄형 API 사용, 비용 최적화(모델 라우팅 등), 오픈 웨이트 모델 직접 운영과 GPU 임대, 인프라 구매. imec은 세 번째 단계에 있다.
Q2왜 장기 과제로 실험했나?
에이전트가 오래 이어서 일하는 장기 과제가 인프라를 직접 가질 이유가 처음 생기는 지점이라고 봤다. 짧게 주고받는 대화형 사용은 경제성이 다를 수 있다.
Q3실험에서 잰 세 가지 지표는?
해결률(과제를 맞게 푼 비율), 지연 시간, 비용.
Q4"비용은 계단 함수"라는 말을 보여 주는 두 사례는?
Qwen과 DeepSeek는 성능이 비슷한데 필요한 하드웨어가 4배 차이 났다. GLM에서 Kimi K3로 가면 정확도는 약 20% 오르는데 GPU 임대 비용은 약 15%만 올랐다.
Q5Kimi K3의 86%를 그대로 믿기 어려운 이유로 발표자가 직접 든 것은?
벤치마크 과제 일부가 학습 데이터에 섞였을 가능성이 있다.
Q6동시 사용자가 늘면 메모리에서 무엇이 커지나?
사용자별 KV 캐시. 모델 파라미터는 고정이지만 KV 캐시는 사용자 수에 따라 늘어난다.
Q7Kimi K3를 직접 운영했을 때 동시 사용자 수와 지연은?
약 4명까지만 안정적으로 돌았고, 그래도 기준선인 Claude Code보다 3배 느렸다.
Q8API보다 싸지려면 필요한 GPU 사용률은 장비에 따라 어떻게 다른가?
하위 등급 장비는 89%로 사실상 불가능하다. 8×B200 같은 큰 장비는 15%로 현실적이다.
Q9API에서 내 인프라로 옮기는 게 유리해지는 분기점과 절감률은?
GLM 급 모델. 코딩 지원 과제 기준 총소유비용을 약 24.5% 아꼈다.
Q10하네스가 정확도를 거의 안 바꾸는데도 중요한 이유는?
내 GPU에서는 GPU가 돌아간 시간이 곧 비용이다. GLM에서 Codex는 다른 하네스보다 토큰을 절반만 써서 GPU 시간도 절반이었다.
Q11이번 연구가 다루지 못했다고 발표자가 밝힌 것은?
여러 응용이 섞인 실제 기업 환경, 양자화와 추측 디코딩 같은 최적화의 영향, 새 모델·하드웨어가 계속 나오는 변화.

용어 정리

용어뜻
오픈 웨이트 모델Open-weight model. 학습된 가중치를 공개해서 누구나 내려받아 직접 돌릴 수 있는 모델
폐쇄형 API모델은 공개하지 않고, 업체 서버에 요청을 보내 결과만 받는 방식
모델 라우팅Model routing. 일의 난이도에 맞춰 알맞은 모델로 요청을 나눠 보내는 것
하네스Harness. 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀. 예: Codex, Claude Code
추론 엔진Inference engine. 모델을 GPU에 올려 실제로 답을 생성하게 하는 소프트웨어
장기 과제Long-horizon task. 에이전트가 여러 단계를 오래 이어서 처리해야 하는 일
SWE-bench Pro코딩 지원 에이전트가 실제 코드 문제를 풀게 하고 해결 여부로 채점하는 벤치마크
해결률Resolve rate. 과제를 맞게 푼 비율
동시성Concurrency. 한 장비에 여러 사용자가 동시에 붙어도 버티는 정도
KV 캐시KV cache. 모델이 앞서 읽은 내용을 다시 계산하지 않으려고 메모리에 저장해 두는 값. 사용자마다 따로 필요하다
총소유비용TCO, total cost of ownership. 장비 구매·임대, 운영 등 직접 가졌을 때 드는 비용 전부
GPU 사용률GPU utilization. 전체 시간 중 GPU가 실제로 일한 시간의 비율
손익분기두 선택지의 비용이 같아지는 지점
온프레미스On-premises. 장비를 사서 회사 안에 직접 두고 운영하는 것
B200NVIDIA의 데이터센터용 GPU. 8×B200은 이 GPU 8장을 묶은 장비
wall time작업이 시작해서 끝날 때까지 실제로 흐른 시간
양자화Quantization. 모델 숫자의 정밀도를 낮춰 메모리와 계산을 줄이는 기법
추측 디코딩Speculative decoding. 작은 모델이 먼저 여러 토큰을 추측하고 큰 모델이 한 번에 검증해 생성 속도를 높이는 기법
