코딩 에이전트에게 없는 되돌리기 버튼

코딩 에이전트는 일을 끝내는 데는 능숙해졌지만, 일이 틀어진 뒤 원래 상태로 돌아가는 데는 아직 약하다. 발표자들은 두 연구로 이 차이를 재고, 변경 전 상태를 기록하고 복구까지 검증한 변경만 받아들이자고 제안한다.

원본 영상: Your Coding Agent Can't Undo Its Own Mistakes 발표: Tanmay Sah, Dolly Sah (UndoBench·EvoUndo 연구 저자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자들이 자기 연구에서 인용한 것이고, 논문 원문을 따로 확인하지는 않았다. 자막의 "agent hardness"는 agent harness로 바로잡았다. 연구 이름 UndoBench와 EvoUndo는 자막의 "Undo Bench", "Evo undo"를 붙여 쓴 것이라 정확한 표기는 추정이다. mm:ss는 영상 위치다.

3분 요약
  1. 정상 조건에서 84% 성공한 에이전트도, 중간에 실패를 넣으면 성공했던 시도의 47%만 원래대로 복구했다.
  2. 타임아웃은 응답이 안 왔다는 뜻일 뿐이다. 확인 없이 다시 보내면 54%에서 같은 작업이 두 번 일어났다.
  3. Git revert는 저장소만 되돌린다. 실행 중 설정, 배포, DB 쓰기 같은 효과는 종류에 맞는 방법으로 따로 되돌려야 한다.
  4. 에이전트가 자기 하네스를 고쳐 능력이 오른 478건 중 197건은 복구에 결함이 있었다.
  5. "고쳐 달라"고 시켜서는 한 건도 복구하지 못했다. 원인은 원래 상태 정보 부족과 되돌리기 연산 부족이었다.
  6. 되돌리기 연산을 넓히자 197건 중 180건을 복구했다. 받아들일 수 있는 개선은 600개 중 281개에서 461개로 늘었다.
  7. 결론: 변경은 능력이 오르고 복구도 검증됐을 때만 받아들인다. 복구를 검증할 수 없으면 멈추고 사람에게 넘긴다.
01

되돌리기 버튼이 없다 00:10

발표는 장면 하나로 시작한다.

  1. 코딩 에이전트가 저장소 이슈를 받아 패치를 적용한다.
  2. 테스트를 돌리고, 모두 통과한다.
  3. 릴리스 태그까지 만든다.
  4. 그런데 이 결과를 받아 쓰는 다른 시스템과의 연동이 실패한다.

질문은 하나다. 에이전트가 모든 것을 시작 전 상태로 돌려놓을 수 있을까.

Git은 저장소에서 무엇이 바뀌었는지 알려 준다. 하지만 외부 API 호출, 실행 중 설정, 이미 보낸 알림은 Git 밖에 있다. 같은 작업을 다시 시도해도 이미 일어난 일은 사라지지 않는다.

발표의 질문 에이전트가 작업을 끝낼 수 있는가가 아니다. 일이 잘못됐을 때 회복할 수 있는가다.
02

UndoBench: 끝내기와 되돌리기는 다르다 01:20

첫 연구 UndoBench는 작업을 끝내는 능력이 실패에서 회복하는 능력으로 이어지는지 확인했다.

발표자들은 쌍 비교 시도 paired trial 2,880개를 돌렸다. 같은 과제를 정상으로 한 번, 중간에 실패를 일부러 넣어 한 번 실행해 비교하는 방식이다.

작업을 잘 끝내는 에이전트라도 회복은 별개의 능력이고, 그 능력은 아직 크게 부족하다.

03

응답 실패와 작업 실패는 다르다 02:20

에이전트가 외부 시스템에 티켓을 하나 만들어 달라고 요청하는 장면이다.

  1. 에이전트가 요청을 보내고 응답을 기다린다.
  2. 서버는 요청을 받아 781번 티켓을 만든다.
  3. 서버의 확인 응답 acknowledgement이 에이전트에게 오는 길에 사라진다.
  4. 에이전트 쪽에서는 타임아웃이 난다. 티켓이 이미 만들어진 줄 모른다.
  5. 첫 요청이 반영됐는지 확인하지 않고 같은 요청을 다시 보낸다.
  6. 티켓이 두 개 생긴다. 의도한 건 하나였다.
타임아웃이 알려 주는 것 응답이 오지 않았다는 사실뿐이다. 작업이 실패했다는 뜻은 아니다.

UndoBench에서 이런 상황의 단순 재시도 naive retry는 54%에서 중복 효과를 만들었다. 그래서 응답이 실패한 것과 작업이 실패한 것을 구분해야 한다.

04

실패 시점이 답을 바꾼다 03:50

복구 방법은 실패가 언제 일어났는지에 따라 달라진다. 기준은 상태를 바꾸는 작업, 곧 변경 mutation이다.

실패 시점시스템 상태맞는 대응
변경 전아무것도 바뀌지 않았다재시도해도 대체로 안전하다
변경 중일부만 바뀌었을 수 있다재시도 전에 현재 상태부터 살펴본다
변경 후확인 응답이 사라졌어도 작업은 이미 반영됐을 수 있다그냥 재시도하면 중복이 생긴다. 앞의 티켓 사례가 이 경우다
05

Git revert로는 부족하다 04:40

Git은 저장소의 변경을 되돌릴 수 있다. 하지만 코딩 에이전트가 바꾸는 건 저장소만이 아니다.

효과 종류예git revert로 되돌려지나
저장소 파일패치, 커밋된다
런타임 상태도구 등록부, 미들웨어, 설정안 된다
외부 효과배포, 데이터베이스 쓰기, 알림, 외부 API 호출안 된다

런타임 상태 runtime state는 코드 파일이 아니라 실행 중인 시스템이 들고 있는 상태다. 외부 효과 external effect는 저장소 밖 세상에 남는 결과다.

복구 방법은 에이전트가 만든 효과의 종류에 맞아야 한다.

06

자기 하네스를 고치는 에이전트 05:20

이 문제는 코딩 에이전트가 자기 실행 환경을 고치기 시작하면 더 커진다. 발표자들은 이 실행 환경을 에이전트 하네스 agent harness라고 부른다.

  • 프롬프트
  • 도구
  • 미들웨어 middleware: 요청과 응답 사이에 끼어 처리하는 중간 계층
  • 이벤트 리스너 event listener: 특정 일이 일어나면 실행되는 코드
  • 리소스
  • 라우팅 설정: 어떤 요청을 어디로 보낼지 정하는 규칙

이런 변경은 에이전트의 성능을 올릴 수 있다. 동시에 원래대로 되돌리기는 더 어려워진다.

에이전트는 더 유능해지면서 동시에 덜 되돌릴 수 있는 상태가 될 수 있다.Tanmay Sah의 표현을 옮김
07

원래 값을 알아야 되돌린다 06:00

되돌리기는 명령을 거꾸로 실행하는 것으로 끝나지 않는다.

에이전트가 타임아웃 값을 30에서 60으로 바꿨다고 하자. 이걸 되돌리려면 원래 값이 30이었다는 걸 알아야 한다. "60으로 설정"이라는 명령만 보고는 원래 값을 알 수 없다.

두 번째 연구 EvoUndo는 변경을 적용하기 전에 사전 상태 증거 pre-state witness를 남긴다. 바꾸기 전 상태를 기록해 둔 것이다.

쓰임 1 · 복원

되돌릴 때 어떤 상태로 돌아가야 하는지 알려 준다.

쓰임 2 · 검증

되돌린 뒤, 복구가 실제로 됐는지 비교할 기준이 된다.

08

개선의 41%에 복구 결함 06:50

그렇다면 성능이 좋아진 하네스는 얼마나 자주 복구에 실패할까. EvoUndo는 진화 과제 evolution task 600개로 이를 쟀다. 에이전트가 자기 하네스를 고쳐 스스로 나아지게 하는 과제다.

발표에서는 197건이 능력이 오른 사례의 "약 42%"라고 했다. 197 ÷ 478을 직접 계산하면 약 41.2%다.

이 숫자가 말하는 것 변경 하나가 에이전트의 능력을 올리면서도, 시스템을 믿을 만하게 되돌릴 수 없는 상태로 남길 수 있다.
09

"고쳐 줘"로는 안 된다 07:30

가장 먼저 떠오르는 방법은 프롬프트다. 에이전트에게 "이 복구 실패를 고쳐 달라"고 시키는 것이다.

발표자들은 검증기의 피드백을 받아 고치는 수리 전략 verifier-guided repair 네 가지를 시험했다. 원래의 복구 언어 recovery language로는 197건 중 한 건도 복구하지 못했다. 복구 언어는 복구 계획을 쓸 때 쓸 수 있는 연산의 묶음이다.

발표자들은 문제가 꼭 에이전트의 추론 능력에 있지는 않았다고 본다. 막힌 곳은 두 군데였다.

두 병목 08:30

병목 1 · 상태 근거 state grounding

원래 상태에 대한 정확한 정보가 없었다.

무엇이 어디서 바뀌었는지 정확히 알려 주자 0건 → 48건 중 38건 복구

병목 2 · 복구 표현력 recovery expressivity

필요한 되돌리기 연산을 복구 언어로 쓸 수 없었다.

더 풍부한 되돌리기 연산을 넣자 0건 → 143건 중 142건 복구

두 결과를 함께 보면, 복구에는 정확한 상태 정보와 필요한 되돌리기를 실행할 수단이 둘 다 필요하다.

10

복구 언어를 넓히면 09:30

더 나은 되돌리기 장치를 주면, 실패한 변경을 살릴 수 있을까.

원래 복구 언어로는 복구 결함이 있는 197건을 하나도 되돌리지 못했다. 복구 언어를 확장하자 180건을 되돌렸다.

발표에서는 180 ÷ 197을 "약 92%"라고 했다. 직접 계산하면 약 91.4%다.

그 결과 받아들일 수 있는 개선 admissible improvement이 늘었다. 능력이 오르고 복구도 되는 변경을 말한다.

UndoBench와 EvoUndo는 모두 발표자들의 연구다. 성과 수치는 자기 방법을 소개하는 자리에서 나온 것이라는 점을 감안해 읽자.

11

EvoUndo의 채택 절차 10:30

여기서부터 Dolly가 EvoUndo 알고리즘을 설명한다. 핵심은 변경을 받아들이기 전에 되돌리기부터 시험해 보는 것이다.

단계하는 일
1. 제안에이전트가 변경을 내놓는다. 현재 상태, 효과 계약 effect contract, 복구 계획 recovery plan이 함께 따라온다
2. 증거 남기기변경을 적용하기 전에 원래 상태를 사전 상태 증거로 기록한다
3. 시험테스트 환경에서 변경을 적용하고, 복구 계획을 실행해 본다
4. 독립 검증별도의 검증기 verifier가 원래 상태로 정말 돌아왔는지 확인한다
5. 판정사용자가 정한 기준으로 능력이 오르고 복구 검사도 통과하면 변경을 채택한다. 아니면 에이전트가 수리를 시도하거나, 검증기가 변경을 거부한다

효과 계약이 정확히 무엇을 담는지는 발표에서 따로 설명하지 않았다.

보통의 방식배포한 뒤에 복구를 궁리한다일이 틀어지고 나서야 되돌릴 방법을 찾는다
→

예시로 따라가기: 타임아웃 30 → 60 12:00

Dolly가 앞의 타임아웃 사례를 절차에 맞춰 다시 보여 준다.

순서하는 일timeout 값
1원래 상태30
2원래 값을 읽어 사전 상태 증거로 저장한다30 (증거: 30)
3변경: 에이전트가 원하는 대로 값을 바꾼다60
4복구가 필요하면 저장한 증거로 되돌린다30
5독립 검증기가 복구된 값과 원래 값을 비교한다30 = 30

발표에서는 4단계를 "타임아웃을 60으로 복원한다"고 말했다. 흐름상 원래 값 30으로 되돌리는 것이 맞다.

복구 성공의 기준 되돌리기 명령을 실행했다고 복구가 성공한 것이 아니다. 검증기가 결과 상태를 확인해야 성공이다.
13

실패마다 다른 대응 13:30

복구 장치가 생겼다고 모든 실패에 같은 방법을 쓰면 안 된다.

상황대응
아무것도 바뀌지 않았다안전하게 재시도한다 safe retry
원래 상태를 알고 있다그 상태로 복원한다 restore
외부 작업이 이미 반영됐다보상 작업 compensating action으로 그 효과를 거꾸로 상쇄한다
복구가 안전한지 검증할 수 없다, 또는 검증기가 복구를 거부했다멈추고 사람에게 넘긴다 stop and escalate

맞는 대응은 실제로 무슨 일이 일어났는지, 그리고 무엇을 안전하게 되돌릴 수 있는지에 달려 있다.

14

결론 14:50

  1. UndoBench: 작업을 성공적으로 끝냈다고 해서 실패에서 성공적으로 회복한다는 보장은 없다.
  2. EvoUndo: 원래 상태 기록 → 변경 적용 → 복구 → 독립 검증으로 이어지는 정해진 절차를 제공한다.
  3. 채택 원칙: 자기 진화 self-evolution로 생긴 변경은 능력과 복구 가능성 요건을 둘 다 채울 때만 받아들인다.

에이전트에게 자율성을 더 줄수록, 자기 행동을 되돌릴 믿을 만한 방법도 더 줘야 한다. 발표자들은 EvoUndo를 GitHub 저장소로 공개했다고 밝혔다. 주소는 발표 화면의 QR 코드로만 안내됐다.

발표자들의 목표 복구를 AI 에이전트의 기본 능력으로 만드는 것. 에이전트가 행동을 실행하는 데서 그치지 않고, 일이 잘못됐을 때 되돌릴 수도 있게 하는 것이다.
15

핵심 정리

  1. 일을 끝내는 능력과 실패에서 회복하는 능력은 다르다. 정상 성공률은 84%, 실패 후 복구율은 47%였다.
  2. 타임아웃은 응답 실패이지 작업 실패가 아니다. 확인 없이 재시도하면 54%에서 중복이 생겼다.
  3. 실패가 변경 전, 변경 중, 변경 후 중 언제 일어났는지에 따라 복구 방법이 달라진다.
  4. Git은 저장소만 되돌린다. 런타임 상태와 외부 효과는 효과 종류에 맞는 복구가 필요하다.
  5. 에이전트가 자기 하네스를 고치면 더 유능해지면서 덜 되돌릴 수 있게 될 수 있다.
  6. 되돌리려면 원래 값을 알아야 한다. 변경 전에 사전 상태 증거를 남긴다.
  7. 능력이 오른 변경 478개 중 197개(약 41%)가 복구 결함을 가졌다.
  8. "고쳐 줘"로는 0건이었다. 막힌 곳은 상태 근거와 복구 표현력이다.
  9. 복구 언어를 넓히자 197건 중 180건이 복구됐고, 받아들일 수 있는 개선이 281개에서 461개로 늘었다.
  10. 변경은 능력과 복구 가능성을 둘 다 만족할 때만 채택한다. 검증할 수 없으면 멈추고 사람에게 넘긴다.
16

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1UndoBench의 84%와 47%는 각각 무엇이고, 왜 바로 빼서 비교하면 안 되나?
84%는 정상 실행의 작업 성공률이다. 47%는 정상일 때 성공했던 시도만 놓고, 실패를 넣었을 때 복구에 성공한 비율이다. 분모가 달라서 단순히 빼면 안 된다.
Q2티켓 생성 요청이 타임아웃됐을 때 바로 재시도하면 왜 위험한가?
타임아웃은 응답이 오지 않았다는 뜻일 뿐이다. 서버가 이미 티켓을 만들었을 수 있어서, 다시 보내면 티켓이 두 개 생긴다. UndoBench에서 단순 재시도는 54%에서 중복을 만들었다.
Q3실패가 변경 전, 변경 중, 변경 후에 일어났을 때 각각 어떻게 대응하나?
변경 전이면 재시도가 대체로 안전하다. 변경 중이면 일부만 바뀌었을 수 있으니 상태부터 살핀다. 변경 후면 이미 반영됐을 수 있어 그냥 재시도하면 중복이 생긴다.
Q4git revert로 되돌릴 수 없는 효과 두 종류와 그 예는?
런타임 상태(도구 등록부, 미들웨어, 설정)와 외부 효과(배포, 데이터베이스 쓰기, 알림, 외부 API 호출).
Q5"더 유능해지면서 덜 되돌릴 수 있게 된다"는 말은 어떤 상황을 가리키나?
에이전트가 자기 하네스(프롬프트, 도구, 미들웨어, 이벤트 리스너, 리소스, 라우팅 설정)를 고치는 상황이다. 성능은 오를 수 있지만 원래대로 되돌리기는 어려워진다.
Q6타임아웃을 30에서 60으로 바꾼 변경을 되돌리려면 무엇이 필요한가?
원래 값이 30이었다는 정보. EvoUndo는 변경 전에 이 값을 사전 상태 증거로 저장하고, 복원과 검증에 모두 쓴다.
Q7EvoUndo 600개 과제에서 능력이 오른 변경 중 복구 결함은 몇 개였나?
478개 중 197개, 약 41%. 발표에서는 "약 42%"라고 했지만 직접 계산하면 41.2%다.
Q8검증기 기반 수리 전략 4가지가 한 건도 복구하지 못한 두 원인은?
원래 상태에 대한 정확한 정보가 없었다(상태 근거). 필요한 되돌리기 연산을 복구 언어로 쓸 수 없었다(복구 표현력).
Q9복구 언어를 넓힌 뒤 바뀐 두 숫자는?
복구 결함 197건 중 180건을 복구했다. 받아들일 수 있는 개선이 600개 중 281개에서 461개로, 30%p 늘었다.
Q10EvoUndo에서 변경이 채택되려면 어떤 두 조건을 채워야 하나?
사용자가 정한 기준으로 능력이 올라야 하고, 테스트 환경에서 복구 검사를 통과해야 한다.
Q11되돌리기 명령을 실행했다는 것만으로 복구 성공이라고 보지 않는 이유는?
명령이 실행됐다고 상태가 원래대로 돌아왔다는 보장은 없다. 독립 검증기가 결과 상태를 사전 상태 증거와 비교해 같다고 확인해야 성공이다.
Q12외부 작업이 이미 반영됐을 때, 그리고 복구를 검증할 수 없을 때는 각각 어떻게 하나?
이미 반영된 외부 작업은 보상 작업으로 효과를 상쇄한다. 복구가 안전한지 검증할 수 없거나 검증기가 거부하면 멈추고 사람에게 넘긴다.
