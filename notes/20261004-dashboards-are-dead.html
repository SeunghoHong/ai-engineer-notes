대시보드는 죽었다

사람이 원한 것은 대시보드가 아니라 답이었다. 에이전트가 여러 앱에서 답을 대신 찾아 주는 지금, 제품은 사람보다 에이전트가 쓰기 쉬워야 한다.

원본 영상: Dashboards Are Dead 발표: Sarah Simionescu (Composio 소속, 발표자의 팀이 Composio 대시보드를 맡고 있음)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Data Dog, century, Enthropic, Composeio 등)은 알려진 이름으로 바로잡았고, 확실하지 않은 곳에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 발표자는 Datadog을 6개월 동안 매일 썼지만 대시보드를 한 번도 연 적이 없었다. 에이전트에게 물어서 썼기 때문이다.
  2. 도구마다 화면과 쿼리 언어가 다르다. 대시보드와 쿼리 언어는 사람과 데이터 사이의 통역기였다. 사람이 원한 건 답이다.
  3. 2023년의 스파클 버튼은 앱 안에서 쿼리를 대신 써 줬지만, 조인이 많은 질문에서는 자주 틀렸다.
  4. 2024년 11월 MCP가 나오면서 내 에이전트가 직접 쿼리를 쓰고 실행해 답을 준다. 하지만 MCP는 통로일 뿐이고, 무엇을 어떻게 건넬지는 서비스가 정한다.
  5. MCP 서버를 많이 붙이면 세 문제가 생긴다. 에이전트는 배우지 않고, 도구 정의가 컨텍스트를 채우고, 앱끼리 서로 모른다.
  6. Composio의 해법: 에이전트가 할 일을 먼저 말하면 맞는 도구와 사용 계획을 돌려준다. 큰 중간 결과는 컨텍스트에 올리지 않고 다룬다.
  7. 결론: 눈이 없는 새 사용자, 에이전트가 생겼다. 다음 시대는 에이전트가 쓰기 쉬운 제품의 것이다.
01

매일 쓰고도 열지 않은 대시보드 00:10

발표자는 고백으로 시작한다. 지난 6개월 동안 Datadog을 매일 썼다. Datadog은 서버 로그와 지표를 모니터링하는 서비스다.

어느 날 동료가 알림 하나를 같이 보자고 했다. 발표자는 Datadog을 열었는데 로그아웃 상태였다. 다시 로그인하고 대시보드 dashboard를 띄우자 그대로 얼어붙었다. 무엇이 어디 있는지 전혀 몰랐다.

Datadog 탓이 아니었다. 발표자는 대시보드를 한 번도 열어 본 적이 없었다. 매일 쓰면서도 화면은 보지 않았다.

여기서 발표자의 주장이 나온다. 대시보드는 죽었다. 01:00 처음엔 이상하게 들리지만 따져 보면 당연하다는 것이다. 발표자의 팀이 Composio 대시보드를 맡고 있어서, 발표자 자신에게만은 반갑지 않은 소식이라고 덧붙였다.

02

창 다섯 개, 쿼리 언어 여러 개 01:20

어쩌다 여기까지 왔는지 포스트모템 postmortem으로 돌아본다. 포스트모템은 일이 끝난 뒤 원인과 경과를 되짚는 글이다.

2022년, 누군가 Slack으로 "검색하면 에러가 나요"라고 알려 온다. 그때 발표자는 바로 창 다섯 개를 띄웠다.

도구한 일
Slack대화 맥락을 읽는다
Datadog쿼리를 써서 로그를 찾는다
PostHog (추정)해당 사용자의 세션을 확인한다
VS Code버그를 고친다
GitHubPR을 연다

도구 다섯 개에 화면도 다섯 개다. 도구가 화면을 새로 바꿀 때마다 다시 익혀야 한다.

도구마다 다른 쿼리 언어 01:50

화면보다 더 큰 문제는 쿼리 언어 query language다. 쿼리 언어는 데이터를 찾을 때 쓰는 전용 문법이다.

  • Datadog에는 Datadog만의 쿼리 문법이 있다.
  • Jira에는 JQL이 있다.
  • Slack에는 검색 수식어 search modifiers가 있다.
  • 같은 SQL을 쓴다는 도구끼리도 문법이 조금씩 다르다.
대시보드는 통역기였다 02:10 기계는 사람이 원하는 것을 알아듣지 못했다. 그래서 사람이 기계의 언어로 바꿔 말해야 했다. 지금까지 쓴 모든 대시보드와 쿼리 언어는 사람과 데이터 사이의 통역 장치였다.
여러분이 원한 건 대시보드도, 그 골치 아픈 쿼리 언어도 아니었다. 답을 원했다.발표자의 표현을 옮김 · 02:20
03

스파클 버튼 02:30

2023년, 반짝이 아이콘이 달린 스파클 버튼 sparkle button이 등장했다. 앱 안에 붙은 AI 기능 버튼이다. 누르면 LLM이 쿼리를 대신 써 준다.

발표자는 그 쿼리를 "가끔 맞는" 쿼리라고 표현했다. 질문에 조인 join이 두 번을 넘게 필요하면 잘 안 됐다. 조인은 두 테이블을 공통 열로 이어 붙이는 작업이다.

곧 모든 대시보드에 이 버튼이 붙었다. 대시보드가 "AI 네이티브"가 된 것이다. 하지만 발표자는 문제가 풀린 게 아니었다고 말한다.

스파클 버튼앱 안의 AI가 쿼리를 써 준다앱마다 따로 있고, 실행과 해석은 사람 몫

05

MCP 서버가 많을 때의 세 문제 03:40

MCP 서버를 열 개 넘게 붙여 본 사람은 현실이 엉망이라는 걸 안다. 발표자는 이유를 세 가지로 든다.

문제 1 03:50 에이전트는 배우지 않는다

대화는 매번 처음부터 시작한다. 에이전트는 어제 Slack 링크 형식을 틀린 걸 기억하지 못한다. 그래서 오늘도 또 틀린다.

스킬 skill로 덧대 왔지만 임시방편이다. 스킬도 컨텍스트를 차지하고, 컨텍스트가 늘수록 에이전트는 둔해진다.

문제 2 04:00 도구가 컨텍스트를 채운다

서버를 많이 붙이면 도구 정의 tool definition 수천 개가 컨텍스트 창 context window에 그대로 들어간다. Composio의 GitHub 툴킷 하나만 해도 도구가 200개가 넘는다.

모델이 엉뚱한 도구를 집는다. 도구 사이의 의존 관계를 못 풀고, 무엇을 먼저 불러야 할지 모른다.

문제 3 04:20 앱끼리 서로 모른다

MCP 서버는 자기 앱만 안다. 그런데 일은 거의 항상 앱 두 개 이상에 걸친다.

그 사이를 이어 붙이는 일은 결국 사람 몫으로 남는다.

발표자의 비유: 문은 열었지만 지도가 없다 04:40 MCP는 에이전트에게 모든 앱으로 들어가는 문을 줬다. 하지만 에이전트는 수천 개의 떨어진 방에 서 있다. 지도도 없고, 와 본 기억도 없다.

07

네이티브 MCP와의 차이 06:20

발표자는 Composio와 각 앱의 네이티브 MCP native MCP를 비교한 초기 결과를 보여 줬다. 네이티브 MCP는 앱 회사가 직접 만들어 Claude 마켓플레이스에 올린 서버다. 과제와 모델을 똑같이 두고 비교했고, 차이가 뚜렷했다고 한다.

아직 공개 전인 초기 결과이고, Composio가 직접 잰 것이다. 자막에는 구체적인 수치가 나오지 않는다. 그래서 이 노트에는 숫자와 차트를 싣지 않았다. 자사 제품에 유리한 주장이니 감안해 읽자.

이유: 에이전트를 위한 인터페이스 06:40

앱의 API는 지저분하고, 문서가 부실하고, 자주 바뀐다. Composio는 이걸 에이전트가 쓰기 좋은 형태로 바꿔 준다고 설명한다.

방식은 한 겹을 더 얹는 것이다. MCP, CLI, 각 앱의 기본 도구 위에 이 층을 올려 여러 앱을 하나처럼 다루게 한다.

아래 표는 발표에 없는 예시 정리다. 발표자가 직접 짝지은 것이 아니고, 데모에서 본 동작을 앞의 세 문제와 맞춰 본 것이다.

문제데모에서 본 대응 (예시 정리)
배우지 않는다도구와 함께 사용 계획을 돌려준다. 예: Slack은 채널 ID부터 찾는다. 에이전트가 이걸 기억할 필요가 없다
도구가 컨텍스트를 채운다할 일을 먼저 말하게 하고, 그에 맞는 도구만 돌려준다. 큰 결과는 컨텍스트에 올리지 않는다(데모 2)
앱끼리 모른다한 번의 검색으로 여러 앱의 도구를 같이 받는다. PostHog 결과로 Metabase를 조회한다(데모 2)
08

데모 2: 두 앱의 데이터 잇기 07:10

발표자가 평소에 가장 자주 하는 쪽에 가까운 예다. 사용자 데이터를 파고든다.

1단계: 앱 하나에서 답 얻기 07:20

질문은 "사용자가 온보딩에서 고른 업종의 분포"다. Claude는 Composio search를 부르고, PostHog 쿼리를 써서 실행한다. 결과가 바로 나온다. PostHog는 사용자 행동을 분석하는 도구다.

2단계: 앱 두 개를 잇기 07:40

이번엔 업종으로 이커머스를 고른 사용자만 본다. 이 사람들이 어떤 툴킷 toolkit을 즐겨 쓰는지 알고 싶다. 툴킷은 Composio에서 앱을 부르는 말이다. 사용자 ID는 PostHog에 있고, 툴킷 사용 데이터는 Metabase에 있다.

  1. Composio search로 필요한 도구를 찾는다.
  2. 08:00 PostHog에서 이커머스를 고른 사용자 ID를 조회한다. 결과 전체를 컨텍스트에 올리지 않고 따로 저장해 둔다.
  3. Metabase에서 스키마 schema를 확인하고 데이터 일부를 뽑아 본다. 데이터 구조를 파악하는 단계다.
  4. 08:20 확신이 서면 Composio Remote Workbench를 쓴다. 저장한 사용자 ID를 정규식 regex으로 묶어 SQL 쿼리를 그때그때 만든다. 이번에도 ID 목록 전체를 컨텍스트에 올리지 않는다.
  5. 08:40 몇 분 안에 이 사용자 집단이 가장 많이 쓰는 툴킷이 나온다. 두 데이터 소스를 합친 결과다.
핵심: 큰 데이터는 컨텍스트 밖에 둔다 사용자 ID 목록 같은 중간 결과를 모델이 직접 읽으면 컨텍스트가 금방 찬다. 데모에서는 결과를 저장해 두고 쿼리 안에서만 썼다. 앞에서 본 "컨텍스트가 늘수록 에이전트가 둔해진다"는 문제를 피하는 방법이다.
09

눈이 없는 새 사용자 09:00

많은 스타트업이 GEO Generative Engine Optimization를 위해 랜딩 페이지와 웹사이트를 손보고 있다. GEO는 AI 답변 엔진이 내 사이트를 잘 찾고 인용하게 만드는 일이다. 하지만 앱 자체를 에이전트가 쓸 수 있게 준비한 곳은 드물다.

Composio는 개발자를 돕는 도구로 시작했다. 09:10 사람들이 좋아하는 앱을 에이전트가 쓸 수 있는 도구로 바꿔 줬다. 발표자 말로는 지금 사람은 대시보드에 지쳤고, 에이전트는 엉성하게 설계된 MCP 서버에 지쳤다.

결론 10:10

발표자는 다시 Datadog 대시보드 앞에서 얼어붙은 장면으로 돌아간다. 그때는 자기가 뒤처지고 있다고 생각했다. 지금은 그 순간을 앞으로 올 일의 예고편으로 본다.

  • 사람이 원한 것은 처음부터 답이었다. 대시보드는 그 답에 닿기 위한 통역기였다.
  • 에이전트가 통역을 맡으면서 대시보드를 열 일이 줄어든다.
  • MCP는 통로일 뿐이다. 에이전트가 쓰기 좋은 인터페이스를 만드는 건 서비스의 몫이다.
  • 다음 시대의 제품은 에이전트가 일을 끝낼 수 있는가로 평가받는다.

"대시보드는 죽었다"는 주장의 근거는 발표자 개인의 경험과 자사 제품 데모다. 방향은 참고하되, 내 업무에서 같은 과제로 직접 시험해 보자.

11

핵심 정리

  1. 발표자는 Datadog을 6개월 동안 매일 쓰면서도 대시보드를 연 적이 없었다. 에이전트에게 물었기 때문이다.
  2. 도구마다 화면과 쿼리 언어가 달라서, 버그 하나에 창 다섯 개를 오가야 했다.
  3. 대시보드와 쿼리 언어는 사람과 데이터 사이의 통역기였다. 사람이 원한 건 답이다.
  4. 2023년 스파클 버튼은 쿼리를 대신 써 줬지만, 조인이 두 번을 넘으면 자주 틀렸다.
  5. 2024년 MCP 이후로는 내 에이전트가 쿼리를 쓰고, 실행하고, 답까지 준다.
  6. MCP는 통로일 뿐이다. 무엇을 어떻게 건넬지는 서비스가 정하고, 그게 차이를 만든다.
  7. MCP 서버를 많이 붙이면 세 문제가 생긴다. 배우지 않는다, 도구가 컨텍스트를 채운다, 앱끼리 모른다.
  8. Composio는 할 일을 먼저 받아 맞는 도구와 사용 계획만 돌려준다.
  9. 큰 중간 결과는 컨텍스트에 올리지 않고 저장해 두었다가 쿼리 안에서만 쓴다.
  10. 눈이 없는 새 사용자, 에이전트가 생겼다. 제품은 에이전트가 일을 끝낼 수 있는지로 평가받는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 동료 앞에서 Datadog 대시보드를 열고 얼어붙은 이유는?
6개월 동안 매일 Datadog을 썼지만 대시보드를 직접 연 적이 한 번도 없었다. 화면 대신 에이전트에게 물어서 썼다.
Q22022년 방식에서 버그 리포트 하나에 오간 도구 다섯 개는?
Slack, Datadog, PostHog(추정), VS Code, GitHub. 도구마다 화면과 쿼리 언어를 따로 익혀야 했다.
Q3발표자가 대시보드와 쿼리 언어를 "통역기"라고 부른 이유는?
기계가 사람이 원하는 것을 알아듣지 못해서, 사람이 기계의 언어로 바꿔 말해야 했다. 사람이 원한 건 대시보드가 아니라 답이었다.
Q4스파클 버튼의 한계로 발표자가 든 것은?
LLM이 쓴 쿼리가 가끔만 맞았다. 조인이 두 번을 넘게 필요한 질문이면 잘 안 됐다.
Q5MCP가 나왔는데도 문제가 끝나지 않은 이유는?
MCP는 통로일 뿐이다. 그 통로로 무엇을 어떻게 건넬지는 서비스가 정하고, 그 설계가 결과를 가른다.
Q6MCP 서버를 여러 개 붙이면 생기는 세 가지 문제는?
에이전트는 배우지 않는다. 도구 정의가 컨텍스트를 채운다. 앱끼리 서로 몰라서 여러 앱에 걸친 일은 사람이 이어 붙여야 한다.
Q7발표자가 스킬을 "임시방편"이라고 한 이유는?
스킬도 컨텍스트를 차지한다. 그런데 컨텍스트가 늘수록 에이전트는 둔해진다.
Q8데모 1에서 Composio search가 할 일마다 돌려준 두 가지는?
맞는 도구, 그리고 그 도구를 쓰는 계획. 예를 들어 Slack은 채널 ID를 먼저 찾아야 메시지를 조회할 수 있다.
Q9데모 2에서 사용자 ID 목록을 다룬 방식의 핵심은?
결과 전체를 컨텍스트에 올리지 않고 저장해 두었다. 그다음 Remote Workbench로 ID를 정규식으로 묶은 SQL을 만들어 Metabase에서 걸렀다.
Q10Composio와 네이티브 MCP의 비교 결과를 읽을 때 주의할 점은?
Composio가 직접 잰 미공개 초기 결과다. 자막에 구체적인 수치도 없다. 자사 제품에 유리한 주장으로 감안해 읽어야 한다.
Q11발표자가 말하는 "새로운 종의 사용자"는 무엇으로 제품을 평가하나?
일을 끝낼 수 있는가, 하나뿐이다. 눈이 없어서 화면을 보지 않고, 스파클 버튼도 누르지 않는다.
