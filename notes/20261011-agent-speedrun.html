에이전트 한 시간 만에 프로덕션까지

고객 상담 에이전트 하나를 60줄짜리 기본형에서 시작해 훅, 스킬, 스티어링으로 제어 장치를 붙이고, 마지막에 명령 몇 줄로 AWS에 배포한다. 핵심은 "LLM은 확률적이니, 꼭 지켜야 할 것은 코드로 못 박는다"는 것이다.

원본 영상: Agent Speedrun 발표: Elizabeth Fuentes Leone, Sandhya Subramani (AWS)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 라이브 워크숍이라 Wi-Fi 문제와 로그인 안내가 섞여 있는데, 이 노트는 기술 내용만 추렸다. 자막에서 이름이 뭉개진 곳은 확실한 경우만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

두 발표자는 AWS 소속이고, 발표에서 다루는 Strands Agents와 Amazon Bedrock AgentCore는 AWS 제품이다. 비용이나 편의성에 대한 평가는 그 점을 감안해 읽자.

3분 요약
  1. Strands Agents는 AWS가 만든 오픈소스 에이전트 하네스다. 모델은 아무거나 붙일 수 있고, MCP와 A2A를 지원한다.
  2. 에이전트의 기본은 루프다. 사용자 입력 → LLM이 도구 선택 → 도구 실행 → 결과를 다시 LLM에 → 답변. 도구는 @tool 데코레이터 하나로 만든다.
  3. 훅은 루프의 특정 지점에 끼워 넣는 코드다. 예: 요청 한 번에 도구 호출을 3회로 제한하는 속도 제한기. 프롬프트는 "제안"이고 훅은 "강제"다.
  4. 스킬은 마크다운으로 쓴 절차서다. 시스템 프롬프트에 다 넣지 않고, 질문 유형에 맞는 것만 그때 불러온다.
  5. 스티어링은 옆에서 지켜보는 짝 에이전트다. 응답 형식, 어조, 절차 순서를 검사하고 고치게 한다.
  6. AgentCore에 배포하려면 코드에 진입점 데코레이터 하나만 붙이면 된다. 명령 두어 개로 컨테이너, 권한, 메모리, 관측이 따라온다. 발표에서는 배포에 약 1분이 걸렸다.
  7. 관측을 켜려면 콘솔에서 Transaction Search를 켜고 OpenTelemetry 배포판을 requirements에 넣어야 한다.
01

Strands Agents란 01:20

Strands Agents는 AWS가 만들어 공개한 오픈소스 에이전트 하네스agent harness다. 하네스란 LLM을 감싸서 도구, 순서, 규칙을 정해 주는 실행 틀이다.

  • 모델은 가져다 쓴다. Amazon Bedrock과 기본으로 연결되지만, OpenAI, Hugging Face, 로컬 Llama 등 어떤 모델 제공자도 붙일 수 있다.
  • MCP와 A2A를 지원한다. MCP는 도구 연결 규약, A2A는 에이전트끼리 대화하는 규약이다.
  • 어디서나 돌린다. 로컬, AWS 관리형 서비스, 다른 호스팅 모두 가능하다.
  • 가드레일과 관측observability이 내장돼 있다.
하네스를 쓰면 좋은 점 19:00 모델을 바꿔도 시스템 프롬프트와 구조는 그대로 둘 수 있다. 같은 코드로 여러 모델의 성능을 비교하기 쉽다.
02

AgentCore: 에이전트를 배포하는 서비스 02:40

Amazon Bedrock AgentCore는 에이전트를 프로덕션에 올리는 데만 집중한 서비스다. 프레임워크를 가리지 않는다. Strands든 LangChain이든 CrewAI든 코드를 컨테이너에 넣어 CLI 한 줄로 배포한다.

구성 요소하는 일
Runtime에이전트 코드가 도는 컨테이너. 세션 단위로 돌고, 한 세션은 최대 8시간까지 이어진다. 단기 메모리와 관측이 기본으로 붙는다. 세션이 늘면 자동으로 늘어나고 줄면 줄어든다.
Gateway도구와 MCP 서버가 많을 때 하나의 엔드포인트 뒤에 모은다. 의미 기반 검색semantic search으로 지금 상황에 맞는 도구를 골라 준다.
Memory8시간을 넘는 장기 메모리. 벡터 저장소나 DB를 직접 만들 필요가 없다. 기본 제공 메모리 유형이 세 가지 있고, 자기 프롬프트로 커스텀 메모리도 만들 수 있다.
Identity에이전트의 신원과 권한. 발표에서는 이름만 언급했다.
Observability서버 자원이 아니라 에이전트 관점의 관측이다. 토큰을 얼마나 썼는지, 어떤 도구를 불렀는지, 루프 안에서 무슨 일이 있었는지를 CloudWatch에서 본다.

세션 길이에 대해 발표자는 "15분에서 8시간까지"라고 말했다. 15분이 기본값인지 다른 한계인지는 자막만으로 분명하지 않다. 메모리 유형 세 가지의 이름은 발표자가 기억나지 않는다고 했으므로 여기에도 적지 않았다.

Elizabeth Fuentes Leone은 보안과 데이터 처리도 짚었다. 고객 데이터로 모델을 학습하지 않고 데이터는 고객 계정 안에만 머문다는 설명이다. 발표자 소속을 감안해 읽을 대목이다.

04

모듈 1: 기본 에이전트와 루프 16:20

만드는 것은 고객 상담 에이전트다. 고객이 주문을 조회하거나 환불을 요청하면 처리한다.

에이전트 루프가 힘의 원천이다 17:30

  1. 사용자가 질문을 보낸다.
  2. 에이전트가 LLM을 부른다. LLM이 질문을 읽고 어떤 도구를 쓸지 정한다.
  3. 도구가 실행되고, 결과가 다시 LLM에 들어간다.
  4. 더 필요한 도구가 없으면 답변을 만든다.

LLM은 다음 토큰을 예측하는 기계다. 답을 LLM의 기억에 맡기지 말고 진실의 출처에 묶어야 한다. 그 출처가 DB든 파일이든, 도구로 감싸서 에이전트에게 준다. 언제 어떤 도구를 쓸지는 LLM의 추론에 맡긴다.

코드는 세 덩어리 19:40

  • 데이터: 고객 두 명과 주문 내역을 담은 딕셔너리. 실습용 가짜 데이터다.
  • 도구 세 개: 고객 조회, 주문 이력 조회, 환불 처리. 모양은 제각각이어도 전부 @tool 데코레이터를 붙인 함수다.
  • 에이전트: 시스템 프롬프트, 모델, 도구 목록. Bedrock 기본 모델을 쓰면 모델은 생략해도 된다.

시스템 프롬프트는 도구를 어떻게 쓸지 알려 준다. 발표에서 쓴 지침은 세 가지였다. 행동하기 전에 항상 고객 조회로 신원을 확인한다. 도구가 준 데이터로 답한다. 이미 가진 정보를 고객에게 다시 묻지 않는다.

아래는 발표 코드를 노트용으로 간추린 예시다. 실제 워크숍 코드와 이름이 다를 수 있다.

from strands import Agent, tool

@tool
def lookup_customer(customer_id: str) -> dict:
    """고객 ID로 고객 정보를 찾는다."""
    return CUSTOMERS[customer_id]

agent = Agent(
    system_prompt="You are a customer service agent. ...",
    tools=[lookup_customer, get_order_history, process_refund],
)
agent("Hi, I'm customer C001. Can you check my recent orders?")

안을 들여다보기 22:50

"에이전트가 뭘 하는지 모르겠다"는 흔한 불만에 대한 답은 메시지 목록이다. agent.messages를 찍어 보면 사용자 발화, 어시스턴트의 도구 호출 1, 2, 도구 결과, 최종 답변이 순서대로 보인다. 토큰 사용량 같은 지표도 같이 나온다. Sandhya Subramani는 이 기본 에이전트가 60줄이 안 되는 코드라고 강조했다.

05

모듈 2: 훅으로 결정론적 제어 25:50

훅hook은 에이전트 루프의 특정 지점에 내 코드를 끼워 넣는 장치다. 끼울 수 있는 자리는 여럿이다.

지점할 수 있는 일
호출 전누가 쓰는지 확인, 이런 질문을 받아도 되는지 판단
LLM 호출 후모델이 낸 결정 검사
도구 호출 전이 도구 호출을 승인할지 취소할지 결정, 호출 횟수 제한
도구 실행 후결과 검사
응답 전보내면 안 되는 답변 차단

실습: 도구 호출 속도 제한기 28:20

LLM이 폭주해서 도구를 끝없이 부르면 토큰만 태운다. 그래서 요청 한 번에 도구 호출은 최대 3회라는 하드 스톱을 만든다.

  1. strands.hooks에서 HookProvider와 HookRegistry를 가져온다.
  2. 속도 제한기 클래스를 만들고 최대 호출 수를 받는다.
  3. 레지스트리에 콜백 두 개를 등록한다. 호출 전 이벤트에서는 카운터를 0으로 되돌린다. 도구 호출 전 이벤트에서는 카운터를 올리고 한도를 넘으면 막는다.
  4. 에이전트를 만들 때 hooks=[RateLimiterHook(max_calls=3)] 한 줄을 더한다.

한도를 더 낮춰 일부러 깨뜨려 보면 "고객 조회 차단"이 찍힌다. 에이전트가 날뛸까 걱정된다면, 답은 훅이다.

프롬프트는 제안, 훅은 강제 31:20 Elizabeth Fuentes Leone이 덧붙였다. LLM은 확률적이라 프롬프트는 "이렇게 해 달라"는 제안일 뿐이다. 훅은 파이썬 코드라서 결정론적이다. 예를 들어 입력에 카드 번호가 섞여 있으면 훅이 모델에 가기 전에 막는다. 모델은 그 정보를 아예 받지 않고, 다시 부를 필요도 없으니 토큰도 아낀다. 응답 후 훅으로는 내보내면 안 되는 답변을 막는다.

질문: 도구는 막혔는데 루프는 계속 돌던데? 34:10

청중의 지적이 정확했다. 데모에서 훅은 도구 호출만 막았고, LLM은 계속 시도하다가 루프 끝까지 갔다. 발표자의 답은 이렇다. 시연을 위해 끝까지 돌게 뒀을 뿐이고, 훅 안에서 그 턴을 바로 끝내도록 만들 수도 있다.

06

모듈 3: 스킬로 맥락 주기 35:10

고객은 에이전트가 모르는 것도 묻는다. 비밀번호가 안 된다, 계정이 잠겼다, 배송은 어디쯤이냐. 그 답을 어디에 둘까.

시스템 프롬프트에 전부 넣으면 매 호출마다 입력 토큰으로 들어가 낭비된다. 대신 스킬 폴더에 마크다운 파일로 절차를 적어 두고, 질문 유형에 맞는 것만 그때 읽게 한다.

  • 워크숍의 스킬 세 개: 환불 처리, 주문 추적, 계정 문제 대응.
  • 계정 스킬에는 비밀번호 재설정 요건, 계정 잠김 처리 절차 같은 내용이 들어 있다.
  • 에이전트를 만들 때 plugins 인자에 스킬 플러그인을 넣고 스킬 폴더를 가리킨다.

"무선 헤드폰 환불해 달라"고 하면 에이전트는 먼저 스킬 목록을 훑어 맞는 것을 고르고, 그 스킬을 도구처럼 호출한 뒤 절차대로 움직인다. 흐름에 정해진 순서가 생기고, 맥락은 필요한 순간에만 들어온다.

07

모듈 4: 스티어링 39:10

에이전트는 어려운 질문은 잘 맞히면서 "이 형식으로 답해"는 자꾸 어긴다. 말도 길다. 매번 "대시 그만 써"라고 말하는 대신 결정론적으로 잡고 싶다.

스티어링steering은 짝 에이전트를 붙이는 방식이다. 짝 프로그래밍처럼, 본 에이전트가 출력을 만드는 동안 옆 에이전트가 보고 "그 형식이 아니다"라고 바로잡는다. 프로덕션에서는 형식이 조금만 틀려도 곤란하니 이런 장치가 필요하다.

스티어링 핸들러 41:10

작동 방식은 훅과 같다. LLM 호출 전후, 도구 호출 전후에 끼운다. 차이는 그 지점에서 검사하는 주체가 코드가 아니라 또 하나의 에이전트일 수 있다는 점이다. 하드코딩한 함수로도, 규칙을 받은 에이전트로도 만들 수 있고, 출력 타입 강제 같은 것도 된다.

환불 절차 핸들러

환불 전에 반드시 고객을 먼저 조회하게 한다. 정해진 절차를 건너뛰지 않도록 지킨다.

어조 가드레일 핸들러

구체적인 기한을 약속하지 않는다. 고객을 탓하지 않는다. 고객의 불만을 먼저 인정한다.

에이전트에 두 핸들러를 넘기고 "모델 뒤에서 조종" 같은 지점을 정하면, 실행 로그에 고객 조회와 주문 이력 조회 뒤에 "에이전트 응답 평가 중"이 추가로 찍힌다. 최종 답이 나가기 전에 한 번 더 검사하는 것이다.

규칙을 DB에 두기 45:00 Elizabeth Fuentes Leone이 소개한 보조 라이브러리가 있다. 자막으로는 "agent control"로 들린다(추정). 여행 예약 에이전트를 예로 들면, 훅은 6명 이상 예약을 그냥 막는다. 스티어링 규칙은 6명이면 방 두 개로 나눠 예약하게 유도한다. 이런 규칙을 DB에 두면 에이전트는 DB 주소만 알면 된다. 규칙이 바뀔 때 코드를 고치지 않고 DB만 고친다.
08

모듈 5: AgentCore에 배포 46:30

세션 관리자 모듈은 시간상 건너뛰었다. 프레임워크로 메모리를 저장하는 방법인데, AgentCore 메모리를 쓰면 프레임워크 없이도 된다고 했다. 배포는 노트북이 아니라 터미널의 CLI로 한다.

코드에서 바뀌는 것은 한 줄 48:00

노트북에서 돌던 에이전트와 프로덕션 에이전트의 유일한 차이는 진입점 데코레이터다. 런타임은 이 데코레이터를 보고 "이 뒤가 에이전트다"라고 안다. 컨테이너가 호출될 때마다 그 함수가 실행된다.

자막에서는 "MTP entry point"로 들린다. Strands와 AgentCore 문서의 @app.entrypoint를 가리키는 것으로 보인다(추정).

관측을 켜는 두 가지 준비 49:30

  1. AWS 콘솔의 AgentCore 메뉴에서 Configure → Transaction Search를 켠다. 이걸 안 켜면 CloudWatch가 정보를 못 받아서 에이전트 관측이 비어 있다.
  2. requirements에 AWS OpenTelemetry 배포판 라이브러리를 넣는다. Strands는 AWS용으로 만들어져 추가 수정이 없다. LangChain이나 CrewAI는 라이브러리가 따로 있고 코드도 조금 손봐야 한다.

배포 순서 52:00

단계내용
프로젝트 만들기이름을 정하고 "harness"가 아니라 "agent"를 고른다. 코드가 이미 있으니 "내 코드 가져오기"를 택한다. 폴더와 환경이 생긴다.
로컬 테스트로컬에서는 agentcore dev로 돌려 보고 세션과 토큰 사용량을 볼 수 있다. Workshop Studio의 가상 머신에서는 안 된다. 로컬에서 Bedrock을 쓰려면 AWS 자격 증명이 필요하다.
배포 방식 고르기코드 직접 배포 또는 컨테이너. 모델 키는 Bedrock을 쓰면 추가 입력이 없고, Anthropic이나 OpenAI 키를 가져올 수도 있다.
배포agentcore deploy 한 줄. 자격 증명을 검사하고, IAM 역할과 정책, 서비스 간 권한을 알아서 만든다. 내부적으로 CDK로 CloudFormation 스택을 만든다. 발표에서는 약 1분 걸렸다.
호출터미널에서 바로 호출하거나 boto3 SDK로 호출한다. 필요한 것은 에이전트의 ARN뿐이다.
관측Runtime 화면의 관측 대시보드에서 세션과 추적trace을 본다. 세션 하나가 컨테이너 하나다. 반영까지 1~2분 걸린다.

발표자가 터미널에서 친 명령의 정확한 이름은 자막만으로 모두 확인되지 않는다. 위 표의 명령어는 발표 흐름과 AgentCore 스타터 툴킷의 일반 명령을 바탕으로 적었다.

발표는 "AWS에서 무언가 만들 때 제일 번거로운 IAM 정책과 권한을 AgentCore가 대신 해 준다"로 마무리됐다. 마지막 QR 코드에는 슬라이드, 워크숍 링크, 소량의 크레딧이 담겨 있었다.

09

핵심 정리

  1. Strands Agents는 AWS의 오픈소스 하네스다. 모델은 아무거나, MCP와 A2A 지원, 어디서나 실행.
  2. 에이전트의 힘은 루프에서 나온다. LLM이 도구를 고르고, 결과를 다시 읽고, 답을 만든다.
  3. 답은 LLM의 기억이 아니라 도구로 감싼 진실의 출처에서 가져온다.
  4. 기본 에이전트는 시스템 프롬프트, 모델, 도구 목록 세 가지면 된다. 60줄 미만이다.
  5. agent.messages를 보면 루프 안에서 무슨 일이 있었는지 다 보인다.
  6. 훅은 루프 지점에 끼우는 코드다. 프롬프트는 제안이고 훅은 강제다. 민감 정보 차단, 호출 횟수 제한에 쓴다.
  7. 스킬은 마크다운 절차서다. 시스템 프롬프트를 부풀리지 않고 필요한 순간에만 맥락을 넣는다.
  8. 스티어링은 짝 에이전트가 형식과 어조를 검사하고 바로잡는 장치다. 규칙은 DB에 둘 수 있다.
  9. AgentCore 배포는 진입점 데코레이터 한 줄과 CLI 명령 몇 개다. 권한과 인프라는 서비스가 만든다.
  10. 관측은 공짜가 아니다. Transaction Search를 켜고 OpenTelemetry 라이브러리를 넣어야 보인다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1에이전트 하네스란 무엇이고, 왜 모델을 바꾸기 쉬운가?
LLM을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀이다. 하네스가 구조를 잡고 있으니 모델만 갈아 끼워도 시스템 프롬프트와 코드는 그대로 둘 수 있다.
Q2에이전트 루프의 네 단계는?
사용자 입력 → LLM이 도구 선택 → 도구 실행 결과를 LLM에 전달 → 더 필요한 도구가 없으면 답변 생성.
Q3왜 답을 LLM의 기억에 맡기지 말라고 하나?
LLM은 다음 토큰을 예측할 뿐이다. DB나 파일 같은 진실의 출처를 도구로 감싸 주고, 그 데이터로 답하게 해야 한다.
Q4Strands에서 도구를 만드는 가장 간단한 방법은?
함수에 @tool 데코레이터를 붙인다. 조회든 환불이든 모양은 달라도 패턴은 같다.
Q5훅과 프롬프트의 차이를 한 문장으로?
프롬프트는 확률적인 모델에게 주는 제안이고, 훅은 루프 지점에서 실행되는 결정론적 코드다.
Q6속도 제한 훅은 어느 두 이벤트에 콜백을 걸었나?
호출 전 이벤트에서 카운터를 0으로 되돌리고, 도구 호출 전 이벤트에서 카운터를 올려 한도를 넘으면 막는다.
Q7훅으로 카드 번호를 막으면 토큰이 절약되는 이유는?
모델에 가기 전에 막으니 모델이 그 정보를 받지도 않고, 다시 부를 필요도 없다.
Q8스킬을 시스템 프롬프트에 다 넣지 않는 이유는?
시스템 프롬프트는 매 호출마다 입력 토큰으로 들어간다. 스킬은 질문 유형에 맞는 것만 그때 읽어 토큰을 아끼고 흐름을 정돈한다.
Q9스티어링이 훅과 다른 점은?
끼우는 지점은 같지만, 검사하는 주체가 코드만이 아니라 또 하나의 에이전트일 수 있다. 형식, 어조, 절차 순서를 보고 바로잡는다.
Q10노트북 에이전트를 AgentCore용으로 바꿀 때 코드에서 달라지는 것은?
진입점 데코레이터 하나다. 런타임은 그 뒤의 함수를 에이전트로 보고 호출마다 실행한다.
Q11배포했는데 CloudWatch에 에이전트 관측이 안 보인다. 먼저 확인할 두 가지는?
콘솔에서 Transaction Search를 켰는지, requirements에 AWS OpenTelemetry 배포판을 넣었는지.
Q12AgentCore 배포가 IAM 작업을 줄여 준다는 말의 뜻은?
역할, 정책, 서비스 간 권한을 CLI가 CDK로 CloudFormation 스택을 만들며 알아서 생성한다. 사용자는 정책을 직접 쓰지 않는다.
