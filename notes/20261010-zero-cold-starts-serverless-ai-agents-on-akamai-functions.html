콜드 스타트 없이 MCP와 에이전트를 전 세계에 띄우기

MCP 서버와 AI 에이전트도 응답이 빨라야 한다. 발표자는 Spin으로 WebAssembly 앱을 만들고, Akamai Functions로 전 세계에 배포하는 과정을 데모로 보여 준다. 서버를 미리 띄워 두지 않아도 요청마다 순식간에 뜬다는 것이 발표의 주장이다.

원본 영상: Zero Cold Starts: Serverless AI Agents on Akamai Functions 발표: Thorsten Hans (Akamai 시니어 개발자 애드보킷)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Ecomi → Akamai, stalling monkey → StarlingMonkey 등)은 확실한 것만 바로잡았다. 발표자는 Akamai 소속이라 자사 제품에 대한 주장이 많다. mm:ss는 영상 위치다.

3분 요약
  1. 한 리전에 배포한 MCP 서버나 에이전트는 멀리 있는 사용자에게 느리다. 컨테이너와 VM은 새로 뜨는 데 수 초에서 수 분이 걸린다.
  2. 미리 넉넉히 띄워 두면 놀고 있는 서버에 돈이 나간다. 편한 고수준 플랫폼은 전용 SDK에 묶인다.
  3. 발표자의 답은 서버 쪽 WebAssembly다. Spin으로 만들고 Akamai Functions에서 전 세계에 나눠 돌린다.
  4. Akamai Functions는 요청마다 앱을 새로 띄운다. 발표자는 평균 0.5ms 미만이라 미리 띄워 둘 필요가 없다고 말한다.
  5. wasmcp를 쓰면 도구만 짜면 된다. 인증 같은 나머지는 기성 컴포넌트를 조립해 MCP 서버를 만든다.
  6. spin aka deploy 한 줄로 약 60초 만에 전 세계 리전에 배포되고 공개 URL이 나온다.
  7. 에이전트는 Vercel AI SDK로 만든다. 데모에서 LLM 왕복을 포함한 응답은 약 820~866ms였다. 시간 대부분은 LLM이 쓴다.
01

한 리전 배포의 네 가지 문제 00:40

MCP 서버와 AI 에이전트도 보통 앱과 다르지 않다. 좋은 사용자 경험을 주려면 응답이 빨라야 한다.

그런데 한 지역, 즉 리전 region에 묶인 기존 구조로는 전 세계 사용자를 고르게 상대하기 어렵다. 발표자는 이 마찰 때문에 엣지 네이티브 edge native 구조가 나왔다고 본다. 사용자 가까이 흩어진 여러 지점에서 앱을 돌리는 것을 전제로 짓는 구조다.

문제무슨 일이 생기나
지연 latency배포한 리전 근처 사용자만 빠르다. 멀리 있는 사용자는 응답이 느려 경험이 나빠진다.
콜드 스타트 cold start컨테이너나 VM이 새로 뜨는 데 수 초에서 수 분이 걸린다. 갑자기 몰린 사용자를 받으려고 빠르게 늘려야 할 때 특히 문제가 된다.
과잉 프로비저닝 overprovisioning콜드 스타트를 피하려고 서버를 미리 넉넉히 띄워 두면, 놀고 있는 서버에도 돈이 나간다. 환경 부담도 크다.
플랫폼 종속더 편한 고수준 플랫폼은 전용 SDK나 전용 배포 단위를 요구한다. 나중에 다른 클라우드로 옮기려면 복잡하고 비싸다.
02

서버에서 돌리는 WebAssembly 02:40

발표자의 해법은 서버 쪽에서 WebAssembly를 쓰는 것이다. WebAssembly Wasm는 여러 언어로 쓴 코드를 작은 이진 파일로 컴파일해, 어디서나 같은 방식으로 실행하게 하는 형식이다.

발표자의 비유 WebAssembly와 컨테이너의 관계는 컨테이너와 가상 머신(VM)의 관계와 같다. 컨테이너가 VM보다 가볍듯, Wasm은 컨테이너보다 한 단계 더 가벼운 실행 단위라는 뜻이다.
  • 파일 크기가 아주 작다.
  • 배포하기 쉽다.
  • 실행이 아주 빠르다.
  • 이식성이 좋다. 같은 파일을 여러 환경에서 그대로 돌린다.

발표자는 아래 두 가지를 묶어 엣지 네이티브 AI 스택이라 부른다. 03:10

만드는 도구

Spin. CNCF 오픈소스 프로젝트다. WebAssembly 앱을 만들고 로컬에서 돌린다.

돌리는 곳

Akamai Functions. Spin 앱을 전 세계에 나눠 실행하는 서버리스 플랫폼이다.

03

Spin: 만드는 도구 03:20

Spin은 CNCF 프로젝트다. CNCF Cloud Native Computing Foundation는 클라우드 오픈소스를 관리하는 재단이다. Spin은 특정 업체에 묶이지 않는다 vendor agnostic. 서버나 클라우드에서 돌릴 WebAssembly 앱을 만든다.

기둥 1 · CLI

개발자가 매일 쓰는 명령줄 도구다. 코드를 고치고, 빌드하고, 돌려 보는 반복을 맡는다. 이 반복을 이너 루프 inner loop라고 부른다.

기둥 2 · 런타임

Wasmtime 위에 만들었다. 로컬 PC에서도, 마이크로컨트롤러나 자원이 적은 환경에서도 앱을 돌린다.

기둥 3 · 언어별 SDK

HTTP 서비스 호출, 데이터베이스 연결 같은 일상 작업을 쉽게 해 준다.

SDK는 언어별로 있지만 Spin 자체는 언어를 가리지 않는다. WebAssembly와 WASI로 컴파일되는 언어라면 다 쓸 수 있다. WASI WebAssembly System Interface는 Wasm 앱이 파일, 네트워크 같은 시스템 기능을 쓰게 해 주는 표준 인터페이스다.

문서: spinframework.dev

04

Akamai Functions: 돌리는 곳 04:50

발표자는 Akamai Functions를 "전 세계에 분산되고 콜드 스타트가 전혀 없는 첫 진짜 서버리스 플랫폼"이라고 소개한다. 서버리스 serverless는 서버 관리를 플랫폼에 맡기고, 요청이 올 때만 코드를 실행하는 방식이다.

컨테이너 · VM미리 띄워 두고 기다린다새로 뜨는 데 수 초에서 수 분이 걸려서, 남는 서버를 넉넉히 유지한다
→
Akamai Functions요청마다 새로 띄운다발표자 주장으로 평균 0.5ms 미만이라, 미리 띄워 둘 필요가 없다

"콜드 스타트가 없다"는 말은 콜드 스타트를 안 한다는 뜻이 아니다. 모든 요청에서 콜드 스타트를 하지만, 너무 짧아서 사용자가 느낄 수 없다는 뜻이다.

특징발표 내용
운영 05:10완전 관리형이다. 만질 설정도, 쓸 Terraform도 없다. 명령 한 줄이면 전 세계에 배포되고, 그 대가로 추가 비용을 받지 않는다고 한다.
보안 05:30WebAssembly 샌드박스 안에서 돈다. 개발자가 권한을 명시적으로 주기 전에는 앱이 외부 자원에 접근하지 못한다.
저장소 05:40키-값 저장소가 내장돼 있다. 여러 고객이 함께 쓰는 멀티테넌트 구조다. 자격 증명을 따로 만들거나 교체할 필요가 없다. 앱이 쓰겠다고 하면 자동으로 연결된다.

발표자는 Akamai 소속이다. "첫 진짜 서버리스", "평균 0.5ms 미만", "추가 비용 없음"은 자사 제품에 대한 주장이니 그 점을 감안해 읽자.

05

wasmcp로 MCP 서버 조립하기 06:20

MCP Model Context Protocol 서버는 LLM 앱이 외부 도구와 데이터를 쓰게 해 주는 서버다. HTTP 위에 MCP 규격을 직접 구현해서 만들 수도 있다. 발표자는 더 나은 길로 wasmcp를 소개한다.

wasmcp는 Spin과 매끄럽게 붙는 CLI다. 개발자는 비즈니스 로직에만 집중하면 된다. MCP에서 비즈니스 로직이란 도구, 리소스, 프롬프트를 구현하는 일이다.

개발자가 짠다
  • 도구 tools
  • 리소스 resources
  • 프롬프트 prompts

템플릿 언어: Rust, TypeScript, Python

wasmcp가 맡는다
  • 비기능 요구사항. 예: OAuth 2.0과 OIDC로 사용자 인증하기
  • 미리 만든 컴포넌트를 가져와 MCP 서버 컴포넌트 하나로 조립하기

조립한 결과물은 로컬 Spin에서도, Akamai Functions에서도 그대로 돈다.

비기능 요구사항 non-functional requirements은 기능 자체가 아니라 인증, 보안, 성능처럼 시스템이 갖춰야 할 조건을 말한다.

06

데모: 로컬 hello MCP 07:30

발표자는 GitHub의 wasmcp 저장소에서 CLI를 설치해 둔 상태로 시작한다. 이름이 hello인 MCP 서버를 처음부터 만든다.

순서명령하는 일
1wasmcp new언어(Rust, TypeScript, Python)와 템플릿을 고른다. 기본 템플릿은 도구만 다룬다. 데모는 TypeScript다.
2npm install의존성을 설치한다.
3코드 수정도구의 입력 스키마, 도구 목록, 도구 실행 코드를 채운다.
4make 09:20JavaScript 코드를 Wasm 도구 컴포넌트로 컴파일한다. 아직 완전한 MCP 서버는 아니다.
5wasmcp compose필요한 컴포넌트를 내려받아 도구와 함께 MCP 서버로 조립한다. 데모에서는 인증을 뺐다.
6spin up -f server.wasm 10:00localhost:3000에서 서버를 띄운다.
7npx로 MCP Inspector 실행브라우저에서 서버에 접속하고 도구 목록을 본다. 입력에 foo를 넣어 실행하면 결과가 돌아온다.

생성된 코드에서 하는 일 08:10

  • 입력 스키마: 도구가 어떤 입력을 받는지 적는다.
  • 도구 목록: 배열 하나에 나열한다. 사람과 LLM이 둘 다 쓰는 법을 알도록 설명을 정확히 쓴다. 발표자는 이를 "좋은 시민이 되는 일"이라고 표현했다.
  • call tool 함수: 모든 요청이 이 함수 하나로 들어온다. 요청 내용을 보고 어느 도구를 실행할지 고른다.
  • 예제 도구: 들어온 입력을 검증한다. 문제가 없으면 입력 앞에 접두어를 붙여 돌려준다.

여기까지가 로컬 경험이다. 다음은 이것을 전 세계에 띄우는 일이다.

07

데모: 결정 기록 MCP 전역 배포 10:50

hello 대신 미리 만들어 둔 결정 기록 decision log MCP 서버를 쓴다. 팀이 내린 아키텍처 결정을 저장하고 찾아보는 서버다. 발표자는 배포 이름을 ADR MCP로 붙였다. ADR Architecture Decision Record은 아키텍처 결정과 그 이유를 남기는 기록이다.

이 서버는 Rust로 썼다. 구조는 TypeScript 버전과 같다. lib.rs의 call tool 함수가 요청에 따라 CRUD 도구 중 하나로 보낸다. CRUD는 만들기, 읽기, 고치기, 지우기다. 도구 정의는 decision.rs에 있다.

키-값 저장소는 설정 없이 바뀐다 11:50

환경저장소
로컬 개발Spin이 "이 앱은 키-값 저장소를 쓴다"를 알아챈다. 개발용으로 SQLite 저장소를 자동으로 만든다.
Akamai Functions전 세계에 분산된 키-값 저장소를 쓴다. 따로 설정할 것이 없다.

빌드와 배포 12:20

hello처럼 make와 compose를 따로 돌려도 된다. 발표자는 애플리케이션 매니페스트에 이 작업들을 이어 붙였다. 그러면 Spin 개발 흐름을 벗어나지 않고 spin build 한 번으로 컴파일과 조립이 끝난다.

여기에 spin aka deploy를 이어 붙이면 배포까지 한 번에 된다. 배포가 진행되는 순서는 이렇다. 13:00

  1. Wasm 파일과 매니페스트로 OCI 레이어를 만들어 Akamai Functions에 올린다.
  2. Akamai Functions는 두 파일을 받아 모든 서비스 리전에 퍼뜨린다.
  3. 리전마다 워크로드를 받았고 돌릴 수 있다고 확인해 준다.
  4. 워크로드를 한 번 띄워 내부 헬스 체크를 한다.
  5. 모든 리전이 HTTP 200으로 답하면 일반 서브도메인을 발급한다. 이제 MCP 서버가 공개 인터넷에 올라간다.
약 60초 14:10 발표자 기준으로 전 세계 배포에 걸린 시간이다. 공개 URL 앞에는 Akamai의 다른 제품(예: Property Manager)을 두어 원하는 규칙을 먼저 적용할 수 있다.

클라이언트에서 써 보기 14:20

발표자는 Z(Zed 에디터로 추정)를 클라이언트로 썼다. MCP를 지원하는 클라이언트라면 무엇이든 된다.

  1. 원격 서버를 추가하고 배포에서 받은 URL을 넣는다. CRUD 도구 5개가 보인다.
  2. 채팅으로 "OAuth 2.0을 쓰기로 한 결정을 기록해 줘"라고 보낸다.
  3. 에디터의 AI가 의도를 알아채고 insert decision 도구를 실행해도 되는지 묻는다. 도구에 넘길 원본 입력도 보여 준다.
  4. 허락하면 요청이 Akamai Functions로 가고 결정이 저장된다.
  5. "결정을 전부 보여 줘"라고 하면 list decisions 도구를 쓴다.

결과는 사용자가 어디에 있든 가장 가까운 서비스 리전으로 요청을 보내는 MCP 서버다. 15:40

08

에이전트도 같은 흐름 16:00

AI 에이전트도 흐름은 같다. 다른 점은 wasmcp 같은 전용 CLI가 없다는 것이다. 대신 널리 쓰는 SDK를 그대로 가져다 쓴다. 발표자는 Vercel AI SDK를 골랐다. TypeScript로 Spin 앱을 만들고 Vercel AI 의존성을 넣으면 된다.

게임 에이전트 16:30

데모는 시연용 게임 에이전트다. 템플릿으로 Spin 앱을 만들었다. 도구는 두 개다.

  • 동전 던지기
  • 주사위 굴리기. 주사위 면 수를 정할 수 있다.

LLM은 전용 GPU가 달린 Linode 인스턴스에 Ollama로 띄워 두었다. HTTP 핸들러가 하는 일은 이렇다.

  1. 설정을 불러온다.
  2. 에이전트를 정의하고, Linode의 Ollama 인스턴스를 가리키게 한다.
  3. 에이전트에게 정체성과 지시문을 준다. 무엇을 하려는 에이전트인지 알려 주는 것이다.
  4. 도구를 등록한다.
  5. 최대 몇 단계까지 돌 수 있는지 제한을 건다.
  6. 응답을 만들어 호출한 쪽에 돌려준다.

배포는 spin aka deploy에 확인 생략과 빌드 옵션을 붙여 한 번에 했다. 17:40

09

JavaScript가 빨리 뜨는 이유 18:00

JavaScript 같은 인터프리터 언어는 실행하려면 인터프리터가 필요하다. 발표자는 이런 언어를 Wasm으로 컴파일할 때 일을 미리 해 둔다고 설명한다.

  1. 컴파일할 때 JavaScript 인터프리터를 불러온다.
  2. 개발자가 쓴 JavaScript 코드를 불러온다.
  3. 전역 스코프를 미리 실행한다. 이때 런타임이 데워지고, 의존성도 모두 메모리에 올라간다.
  4. 그 메모리 상태를 스냅샷으로 떠서 Wasm 파일에 쓰고 디스크에 저장한다.

요청이 오면 이 준비된 상태에서 바로 시작한다. 발표자는 그래서 JavaScript로 쓴 Wasm 앱이 콜드 스타트와 실행 성능 모두에서 네이티브 JavaScript 앱보다 빠르다고 말한다.

대가 JavaScript 런타임을 사용자 코드와 함께 실어 보내야 한다. 그래서 최적화한 JavaScript 런타임인 StarlingMonkey를 쓴다. 크기는 약 10MB다.

"네이티브 JavaScript보다 빠르다"는 발표자 회사 쪽 주장이다. 발표 중에 비교 측정을 보여 주지는 않았다.

10

실제 응답 시간 18:50

배포가 끝나면 URL이 나온다. 발표자는 그 URL로 "동전 던져 줘"라고 보낸다. 응답 헤더에서 세 가지를 읽는다.

헤더에서 본 것값뜻
접속 지점 (PoP)Santa Clara요청이 Akamai 네트워크에 처음 들어온 곳
가장 가까운 서비스 리전LAX에이전트가 실제로 돈 곳
x-envoy-upstream-service-time아래 차트요청을 받아 로직을 돌리고, LLM을 거쳐 답을 돌려주기까지 걸린 시간

발표자는 처음에 33~34ms가 LLM 호출까지 포함한 시간이라고 설명했다. 그런데 곧이어 그 응답이 내부 서버 오류였다고 확인했다. LLM을 거치지 않은 오류 응답이라 실제 에이전트 응답 시간으로 보면 안 된다. 다시 보낸 요청은 866ms였고, 발표자도 LLM을 거쳐야 하니 이쪽이 현실적이라고 말했다.

계산해 보면 에이전트 응답 시간 대부분은 LLM 호출이 차지한다. 콜드 스타트가 0.5ms 미만이라는 주장이 맞다면, 약 820ms 중 0.1%도 안 된다.

11

개발 흐름과 결론 20:20

일반 업무용 앱이든, MCP 서버든, 에이전트든 개발 흐름은 늘 같다.

  1. Wasm으로 컴파일되는 언어로 구현한다. 요즘은 Rust, TypeScript, Python, Go가 대표적이다.
  2. spin CLI로 로컬에서 테스트한다.
  3. spin aka deploy 한 줄로 배포한다.
  4. 클라이언트가 MCP 서버나 에이전트를 가리키게 한다.

핵심 메시지 20:50

이식성

Spin 앱은 WASI를 따르는 런타임이면 어디서나 돈다. Akamai Functions는 그중 하나이고, 전 세계에 분산된 런타임이다.

개방형 표준

Spin은 CNCF 프로젝트다. 발표자는 WASI와 WebAssembly를 Bytecode Alliance가 관리한다고 말했다.

속도

응답이 빠르다. 인프라와 비기능 요구사항을 직접 만들지 않으니, MCP 서버와 에이전트를 출시하는 데 걸리는 시간도 줄어든다.

운영 없음

spin aka deploy면 충분하다. 지표 수집, 로그 조회, 업그레이드용 명령도 따로 있다.

WebAssembly와 WASI 표준 작업은 W3C에서 한다. Bytecode Alliance는 Wasmtime 같은 런타임과 도구를 만드는 단체다. 발표의 표현은 이 둘을 한데 묶은 것으로 보인다.

발표자는 Spin을 시작할 때부터 개발자 경험을 가장 중요한 지표로 삼았다고 말한다. 비슷한 사례와 실험은 Akamai 개발자 허브에 올라온다. 22:00

12

핵심 정리

  1. 한 리전에 배포한 MCP 서버와 에이전트는 멀리 있는 사용자에게 느리다.
  2. 컨테이너와 VM은 콜드 스타트가 수 초에서 수 분이다. 이를 피하려 미리 띄워 두면 비용이 든다.
  3. 고수준 플랫폼은 전용 SDK에 묶여 다른 클라우드로 옮기기 어렵다.
  4. 대안은 서버 쪽 WebAssembly다. 작고, 빠르고, 어디서나 돈다.
  5. Spin은 CLI, Wasmtime 기반 런타임, 언어별 SDK의 묶음이다. 언어를 가리지 않는다.
  6. Akamai Functions는 요청마다 앱을 새로 띄운다. 발표자 주장으로 평균 0.5ms 미만이다.
  7. wasmcp를 쓰면 도구만 짜고, 인증 같은 나머지는 기성 컴포넌트를 조립한다.
  8. 키-값 저장소는 로컬에서 SQLite, 배포하면 전역 저장소가 된다. 코드와 설정은 그대로다.
  9. spin aka deploy 한 줄이면 약 60초 만에 모든 리전 배포, 헬스 체크, URL 발급이 끝난다.
  10. 에이전트 응답 시간은 LLM 호출이 좌우한다. 데모 실측은 약 820~866ms였고, 33~34ms는 오류 응답이었다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 꼽은 한 리전 배포의 문제 네 가지는?
먼 사용자의 지연, 컨테이너와 VM의 느린 콜드 스타트, 미리 띄워 둔 서버에 드는 비용, 고수준 플랫폼의 전용 SDK 종속.
Q2발표자는 WebAssembly와 컨테이너의 관계를 무엇에 비유했나?
컨테이너와 VM의 관계. Wasm은 컨테이너보다 한 단계 더 작고, 빠르고, 옮기기 쉬운 실행 단위다.
Q3Spin의 세 기둥은?
개발자가 매일 쓰는 CLI, Wasmtime 기반 런타임, HTTP 호출이나 DB 연결을 돕는 언어별 SDK.
Q4"콜드 스타트가 없다"는 말은 정확히 무슨 뜻인가?
콜드 스타트를 안 한다는 뜻이 아니다. 모든 요청에서 새로 띄우지만, 발표자 주장으로 평균 0.5ms 미만이라 사용자가 느끼지 못한다는 뜻이다.
Q5WebAssembly 샌드박스가 주는 보안은?
개발자가 권한을 명시적으로 주기 전에는 앱이 외부 자원에 접근하지 못한다.
Q6wasmcp를 쓸 때 개발자가 짜는 것과 맡기는 것은?
개발자는 도구, 리소스, 프롬프트를 짠다. OAuth 2.0과 OIDC 인증 같은 비기능 요구사항은 기성 컴포넌트를 조립해 해결한다.
Q7make만 하면 왜 MCP 서버가 완성되지 않나?
make는 도구 컴포넌트만 만든다. wasmcp compose로 나머지 컴포넌트와 조립해야 완전한 MCP 서버가 된다.
Q8키-값 저장소를 쓰는 같은 코드가 로컬과 Akamai Functions에서 어떻게 다르게 동작하나?
로컬에서는 Spin이 개발용 SQLite 저장소를 자동으로 만든다. 배포하면 전 세계에 분산된 키-값 저장소를 쓴다. 따로 설정할 것은 없다.
Q9spin aka deploy 뒤 공개 URL이 생기기까지 어떤 단계를 거치나?
OCI 레이어 업로드, 모든 서비스 리전에 배포, 리전별 수신과 실행 가능 확인, 한 번 띄워 헬스 체크, 모든 리전이 HTTP 200이면 서브도메인 발급. 발표 기준 약 60초.
Q10게임 에이전트의 HTTP 핸들러가 에이전트에게 주는 것 세 가지는?
정체성과 지시문, 등록된 도구, 최대 단계 수 제한.
Q11JavaScript 앱을 Wasm으로 컴파일할 때 무엇을 미리 해 두나? 대가는?
인터프리터와 코드를 불러와 전역 스코프를 실행하고, 그 메모리 상태를 스냅샷으로 Wasm 파일에 저장한다. 대가는 약 10MB인 JavaScript 런타임 StarlingMonkey를 함께 실어야 한다는 것이다.
Q12데모의 33~34ms를 에이전트 응답 시간으로 보면 안 되는 이유는?
그 응답은 내부 서버 오류였다. LLM을 거친 실제 응답은 866ms, 반복했을 때 약 820ms였다.
