AI 코드 리뷰 에이전트, 직접 만들면 어디서 막히나

샌드박스에 에이전트를 넣고 PR 웹훅을 연결하면 리뷰 에이전트는 금방 만들어진다. 문제는 그다음이다. 버그를 놓치고, 맥락을 모르고, 비싸고, 잔소리가 많다. 발표자는 이 네 가지를 순서대로 줄이는 다섯 가지 개선을 설명한다.

원본 영상: How to Build an AI Code Review Agent 발표: Daksh Gupta (Greptile 공동 창업자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

발표자는 코드 리뷰 제품을 파는 회사의 창업자다. "직접 만들어 보라"는 조언이지만, 데이터셋 규모나 위키 같은 대목은 자사 제품의 강점을 설명하는 부분이기도 하다. 그 점을 감안해 읽자.

3분 요약
  1. 최소 구성은 간단하다. 샌드박스, 그 안의 코딩 에이전트, PR 웹훅, GitHub 리뷰 API. 이것만으로 5분 뒤 PR에 댓글이 달린다.
  2. 그런데 곧 버그를 놓치고, 맥락을 모르고, PR당 3~25달러가 들고, 잔소리 댓글이 쌓인다. 돌릴 때마다 새 버그가 나와 어디까지 믿을지도 모른다.
  3. 프롬프트는 "우리 회사가 자주 내는 버그 종류"를 적고 "잔소리가 무엇인지"를 명시하는 방향으로 고친다.
  4. 프롬프트를 조금 바꿔도 결과가 크게 흔들리므로, 과거 장애를 낸 PR을 모아 데이터셋으로 만들고 버전마다 잡는 비율을 잰다.
  5. 코드를 쓴 모델과 다른 모델로 리뷰한다. 모델마다 잘 내는 버그가 다르고, 같은 모델은 같은 방식으로 놓친다. 발표자 데이터로는 잡는 비율이 10% 오른다.
  6. grep만으로는 부족하다. 코드베이스를 미리 색인한 지식 베이스와 문서, 티켓을 함께 준다. 버그가 없어도 의도와 다른 코드를 잡으려면 이게 필요하다.
  7. 샌드박스에서 앱을 띄워 직접 눌러 본다. 코드만 읽어서는 아이폰에서 버튼이 가려지는지 알 수 없다.
  8. 비용은 작업별로 모델을 나눠 줄인다. Greptile은 토큰의 약 20%만 최상위 모델에 쓴다.
01

발표자와 Greptile 00:10

Greptile은 코드베이스 전체 맥락을 가지고 PR을 리뷰하고 테스트하는 에이전트를 만든다. 발표자에 따르면 GitHub 전체 PR의 약 1%가 Greptile을 거친다. Nvidia의 CUDA 코드베이스부터 Coinbase의 지갑 코드베이스까지 종류가 다양하다.

가끔 요구가 너무 특수해서 직접 만드는 게 나은 회사를 만난다. 그럴 때 Greptile은 무료로 돕는다. 이 발표는 그 회사들에게 해 주는 조언을 그대로 옮긴 것이다.

사람들이 Greptile에서 좋아하는 세 가지 01:20

  • 코드베이스 맥락: 코드 검증 회사가 되기 전에는 큰 코드베이스를 언어 모델에게 이해시키는 회사였다. 그래서 색인을 잘한다.
  • 코드를 실제로 돌린다: 의존성을 다 갖춘 샌드박스에 앱을 띄우고, 화면을 눌러 보고, API를 두드린다.
  • 추론 예산을 효율적으로 나눈다: 리뷰의 하위 작업마다 맞는 모델과 예산을 고른다. 그래서 달러당 성능이 높다.

이 발표는 두 종류의 청중을 위한 것이다. 직접 만들려는 사람, 그리고 리뷰 제품을 고를 때 "좋은 것"과 "아주 좋은 것"을 구분하고 싶은 사람이다.

02

5분이면 만드는 최소 구성 02:30

상황은 이렇다. 플랫폼 팀이거나 팀의 AI 열성 멤버다. 엔지니어도, 마케팅 담당자도 바이브 코딩으로 코드를 쏟아낸다. 새 병목은 리뷰와 검증이다.

구성 요소내용
샌드박스파는 회사가 많다. Firecracker 같은 것을 직접 써도 된다
에이전트Codex나 Claude Code. 발표자는 모델에 묶이지 않는 OpenCode나 Pi(추정) 같은 오픈소스 하네스를 권한다
입력GitHub이나 GitLab의 PR 웹훅. PR이 열리면 내용을 에이전트에 보낸다
프롬프트"이 PR을 리뷰하고 피드백을 보내라" 정도
출력GitHub 리뷰 API로 댓글을 단다

많은 사람이 이게 전부라고 생각한다. 실제로 PR을 열면 약 5분 뒤 피드백이 온다. 그런데 이걸 만드는 동안 이미 문제가 시작된다.

모델에 묶이지 않는 하네스를 권하는 이유는 뒤의 "모델 뒤집기"에서 나온다. 코드를 쓴 모델과 다른 모델로 리뷰해야 하기 때문이다.

03

처음 돌리면 생기는 다섯 문제 04:00

1. 버그를 놓친다

버그는 끝이 없다. 발표자는 "버그는 프랙탈처럼 무한하다"는 트윗을 인용한다. 그런데 이 시스템의 존재 이유는 최소한 큰 장애만큼은 막는 것이다.

2. 맥락을 모른다

코드베이스가 어디로 가는지, 특정 부분이 어떻게 돌아가는지, 어떤 라이브러리를 어떻게 쓰는지 모른다. 마이크로서비스 시대를 지나 저장소가 수천 개라면 더 심하다.

3. 비싸다

직접 만든 사람들은 PR 하나 리뷰에 3달러에서 25달러까지 쓴다. 토큰이 조용히, 빠르게 쌓인다.

4. 잔소리 댓글

기술적으로는 맞지만 지나치게 깐깐한 댓글이다. 두 가지가 망가진다. 사람은 "양치기 소년" 효과로 어느 댓글이 치명적인지 가려내기 힘들다. 그리고 코딩 에이전트가 그 댓글을 전부 반영해 지나치게 방어적인 코드가 된다.

5. 돌릴 때마다 새 버그

같은 PR에 다시 돌리면 또 새로운 걸 찾는다. 결과가 흔들리니 어디까지 믿을지 알 수 없다.

잔소리 댓글이 코드베이스를 망치는 경로 05:20 리뷰 에이전트가 GitHub에 댓글을 남긴다. 코딩 에이전트가 그 댓글을 집어 처리한다. 코딩 에이전트는 가려서 받지 않는다. 결과는 세 겹 방어 코드와 과한 예외 처리다. 발표자는 코딩 에이전트가 이런 코드를 특히 잘 쓴다고 말한다.
04

개선 1: 프롬프트 06:00

가장 손쉬운 개선이다. 처음 프롬프트는 "이 PR을 리뷰하고 GitHub API 형식으로 댓글을 출력하라" 정도였다. 두 방향으로 고친다.

  1. 특정 버그 종류를 찾게 한다. 과거 장애와 사고를 분석해 우리 회사가 자주 내는 버그 종류를 목록으로 만든다. 프롬프트가 그 목록을 찾게 한다.
  2. 잔소리가 무엇인지 명시하고 찾지 말라고 한다. "왜 세 겹 방어가 없냐", "예외 처리가 조금 엉성하다" 같은 것이다.

프롬프트를 바꾸면 생기는 무서운 일 06:50

프롬프트를 조금 바꿨는데 댓글 수가 크게 변한다. 이게 무서운 이유는 버그를 놓치고 있는지 알 수 없기 때문이다. 리뷰어는 버그가 있다는 건 말해 주지만, 없다는 건 말해 주지 못한다.

치명적인 버그는 아주 드물다. 발표자의 데이터로는 PR 천 건 중 한 건, 혹은 코드 천 줄 중 한 줄 정도다. 그래서 좋아 보이는 버전을 배포했는데 사실은 큰 버그를 놓치는 버전일 수 있고, 그 사실을 한참 뒤에야 알게 된다.

발표자는 "PR 천 건 중 하나"와 "천 줄 중 하나"를 둘 다 말했다. 둘은 꽤 다른 수치다. 정확한 단위는 자막만으로 확정할 수 없다.

05

개선 2: 과거 PR 데이터셋 07:40

프롬프트를 자신 있게 고치려면 채점표가 필요하다. 장애와 사고를 잘 기록해 온 회사라면 쉽다. 과거에 장애를 낸 PR 목록이 이미 있다.

  1. 장애를 낸 PR을 모아 목록으로 만든다.
  2. 리뷰 에이전트의 모든 버전을 그 목록에 돌린다.
  3. 버그를 잡는 비율을 버전마다 비교한다.

데이터셋은 계속 갱신해야 한다 08:10

버그의 종류와 모양은 시간이 지나면 바뀐다. 발표자에 따르면 버그의 80~90%는 과거 실수의 반복이지만, 코딩 에이전트가 좋아질수록 전에 없던 새로운 방식으로 실패한다. 그래서 실시간으로 갱신되는 데이터셋이 필요하다. 수백만 건의 PR이 없으면 버그 종류를 고르게 덮기 어렵다는 한계가 여기서 나온다.

발표자는 이 대목에서 Greptile이 여러 회사의 PR을 모아 큰 데이터셋을 갖고 있어 내부 도구보다 유리하다고 말한다. 자사 제품의 강점을 설명하는 부분이다. 다만 "자기 회사 데이터만으로도 꽤 멀리 갈 수 있다"고 덧붙인다.

06

개선 3: 모델 뒤집기 09:00

발표자는 올해 초 AI Engineer 샌프란시스코에서 코딩 에이전트의 실패 방식을 발표했다. 그 연구에서 발견한 것은 Claude 모델과 Codex 모델이 내는 버그 종류가 꽤 다르다는 점이다. 발표자는 이를 후처리 학습 post-training의 흔적으로 본다.

같은 모델로 쓰고 같은 모델로 리뷰하면 잡는 버그가 상대적으로 적다. 코드를 쓸 때 실패하는 방식 그대로 리뷰할 때도 실패하기 때문이다. 그래서 Claude Code로 쓴 코드는 GPT 모델이 리뷰하고, 그 반대도 마찬가지로 한다. 발표자 데이터로는 모델을 뒤집으면 잡는 비율이 10% 높다. 장애와 사고 기준으로 10%는 작은 숫자가 아니다.

어떤 모델이 썼는지 알아내기 09:50

구분방법
쉬운 80%코딩 에이전트가 남기는 지문을 본다. Codex는 브랜치 이름을 codex/로 시작한다. Claude는 PR 설명과 커밋 메시지에 Co-authored-by: Claude를 쓴다
어려운 20%브랜치를 손으로 만들었거나 다른 에이전트를 썼을 때. 모델 특유의 흔적을 찾는 휴리스틱이 필요하다. 사내에서 누가 어떤 에이전트를 쓰는지 기록한 목록이나 개발 장비의 텔레메트리가 도움이 된다
07

개선 4: 코드베이스 맥락 11:00

발표자가 가장 아끼는 주제다. 요즘은 grep이 코드베이스 맥락 문제를 사실상 해결했다고들 보지만, 발표자는 두 가지 이유로 동의하지 않는다.

  • grep은 부정확하다. 필요한 곳을 콕 집지 못하고 파일을 대량으로 읽는다.
  • grep은 비싸다. 코딩 에이전트의 실행 기록을 보면 토큰 대부분이 grep, 파일 읽기, 파일 내용 캐시 쓰기다.
발표자의 과장 섞인 계산 11:20 작년 GDP 성장의 한 자릿수 퍼센트포인트가 추론 비용이었고, 그 추론의 큰 몫이 코딩 에이전트였으며, 코딩 에이전트 토큰의 대부분이 grep과 파일 읽기다. 그러니 GDP 성장의 무시 못 할 부분이 grep이라는 것이다. 발표자는 토큰 단위로 돈을 받는 회사에게는 토큰을 더 태울 유인이 있을지도 모른다고 덧붙인다. 수치의 출처는 밝히지 않았다.

Greptile의 방법: 미리 색인한 지식 베이스 11:50

코드베이스 전체를 훑어 부분마다 목록을 만들고 색인한다. "이건 인증이다. 이렇게 동작한다. 흐름은 이렇다. 흐름 다이어그램은 이것이다. 관련 파일은 이것들이다." 이런 식이다.

맥락이 필요한 대표 예가 인증 우회다. 코드의 그 부분이 인증된 환경 안인지 밖인지를 구체적으로 알아야 우회가 일어났는지 판단할 수 있다. diff만 봐서는 알 수 없다.

08

버그가 없어도 틀린 코드 12:30

지금까지는 버그 중심이었지만, 버그가 없어도 코드는 나쁠 수 있다. 품질이 형편없거나, 작성자가 말한 의도를 채우지 못하는 경우다.

발표자는 "사람들이 점점 Slack을 IDE로 쓴다"는 글을 봤다. Slack 메시지에는 의도가 한두 문장뿐이라 지시가 모호하다. 그러면 코딩 에이전트가 지시를 잘못 읽거나, 모호해서 무엇을 할지 몰랐을 수 있다. 맞게 돌아가는 코드도 여전히 틀릴 수 있다.

가장 효과가 큰 맥락 두 가지 13:10

  • 문서와 티켓: Jira, Linear 같은 티켓 도구와 Confluence, Notion 같은 문서 도구에 접근하게 하면 놀랄 만큼 멀리 간다.
  • 코드베이스: 앞서 말한 색인기나 지식 베이스에서 온다.

사람이 좋은 코드를 쓰는 데는 무의식적으로 쓰는 부족 지식 tribal knowledge이 많이 들어간다. 에이전트에게 같은 일을 시키면 "뭘 모르는지 모르는" 느낌이 드는데, 그건 자신이 가진 지식의 깊이를 과소평가하기 때문이다.

Greptile의 방법: 살아 있는 위키 13:50 여러 맥락 출처를 하나의 위키로 모은다. 회사가 어떻게 돌아가는지에 대한 세계 모델 같은 것이다. 코드베이스, 프로덕션 텔레메트리와 로그, 문서와 티켓에서 읽은 로드맵이 들어간다. 이 위키로 에이전트가 맥락을 갖게 하고, 코드 검색도 정확하게 만든다. 필요 없는 파일은 읽지 않게 된다.
09

개선 5: 자율 테스트 14:20

UI 변경을 예로 들면, React 코드를 읽고 문제없다고 결론 내릴 수 있다. 그런데 실제로 그려 보면 아이폰에서 가려져 있을 수 있다. 기술적으로 가장 어려운 문제 중 하나다.

Greptile은 완전히 설정 가능한 가상 머신인 의존성 풍부한 샌드박스를 만들고, 고객과 함께 그 안에 고객의 스택을 띄운다. 그다음 에이전트가 컴퓨터 비전으로 끝에서 끝까지 테스트한다. 발표자는 새 세대 GPT와 Opus 모델에서 컴퓨터 비전이 크게 좋아져 끝단 QA가 거의 풀렸다고 본다.

직접 하려면 필요한 세 가지 15:20

필요한 것설명
개발 박스PR 브랜치의 의존성까지 갖춘 상태로 앱을 돌릴 수 있는 환경
단순한 빌드 스크립트에이전트가 스택을 혼자 띄울 수 있을 만큼 단순해야 한다. 발표자는 이 부분이 가장 까다로워 전담 엔지니어가 고객을 돕는다고 말한다
흐름 지도"이건 인증 코드, 이건 가입 흐름" 식으로 앱의 모든 흐름을 문서화한 것

이게 갖춰지면 에이전트가 코드를 끝에서 끝까지 테스트하고, 비전 모델로 "이 버튼이 코드상으로는 있는데 아이폰에서는 가려진다"거나 "첫 화면에 안 들어온다" 같은 것을 잡는다. 좋은 개발 박스가 이미 있다면 축하한다. 발표자 표현으로는 "Stripe에 다니시는군요"다.

10

비용: 작업마다 다른 모델 16:00

여기까지 해도 비용은 여전히 높다. PR 하나에 3달러에서 15~20달러다. 이제 풀 문제는 어떤 일에 싼 모델을 써도 되는가다. 발표자가 보기에 최상위 모델이 오픈소스 모델보다 여전히 유능하지만 격차는 좁아지고 있다.

예시 배분 16:40

작업모델
맥락 찾기작은 모델
사용자 흐름 테스트아주 가벼운 컴퓨터 사용 모델
버그 분석, 리뷰 절차 적용, 최종 제출최상위 모델

실제로 Greptile은 하위 작업이 20개이고 각각에 맞는 모델 조합이 따로 있다. 작은 연구팀이 어떤 작업에 어떤 모델을 쓸지 계속 조정한다. 하지만 단순한 작업을 단순한 모델로 바꾸는 것만으로 70~80%까지는 간다.

데이터셋 없이 모델을 바꾸면 17:10 좋은 데이터셋이 없으면 여러 하위 에이전트를 작고 빠른 모델로 신나게 바꾸고는, 버그를 잡는 능력이 꽤 떨어졌다는 걸 모를 수 있다. 장애가 나서 놓친 걸 알게 될 때까지 모른다. 개선 2의 데이터셋이 여기서 다시 필요하다.

캐시에 무엇을 넣을지 고르는 싼 모델 17:30

과도한 파일 읽기도 싼 모델로 줄일 수 있다. 싼 모델이 모든 맥락 조각을 훑고 실제로 포함할 것만 고른다. 발표자는 이론상 결정 모델이나 재순위 re-ranking API로 이걸 할 수 있다고 말한다. 최상위 모델의 캐시가 가장 비싸고 가장 귀한 자원이기 때문이다.

발표자가 이 대목에서 언급한 구체적 제품명은 자막이 불명확해 적지 않았다.

11

결론 17:50

이 다섯 가지를 다 하면 직접 만든 리뷰 에이전트로도 꽤 멀리 갈 수 있다. 발표자는 만들게 되면 알려 달라고 하고, 만들지 않기로 하면 Greptile을 쓰라고 농담으로 마무리한다. "이것들에 비하면 공짜"라는 표현이다.

최소 구성PR 내용을 넣고 댓글을 받는다샌드박스 + 에이전트 + 웹훅 + "리뷰해라"
→
완성형측정하고, 뒤집고, 맥락을 주고, 돌려 보고, 나눈다버그 목록 프롬프트, 장애 PR 데이터셋, 다른 모델로 리뷰, 지식 베이스와 문서, 샌드박스 테스트, 작업별 모델
12

핵심 정리

  1. 최소 구성은 샌드박스, 에이전트, PR 웹훅, GitHub 리뷰 API다. 5분 뒤 댓글이 달리지만 그게 끝이 아니다.
  2. 처음 생기는 문제는 다섯 가지다. 버그 누락, 맥락 부족, PR당 3~25달러, 잔소리 댓글, 돌릴 때마다 다른 결과.
  3. 잔소리 댓글은 사람을 지치게 할 뿐 아니라, 코딩 에이전트가 전부 반영해 지나치게 방어적인 코드를 만든다.
  4. 프롬프트는 우리 회사가 자주 내는 버그 종류를 찾게 하고, 잔소리의 정의를 명시해 피하게 한다.
  5. 리뷰어는 버그가 있다는 건 알려 주지만 없다는 건 알려 주지 못한다. 치명적 버그는 천 건 중 하나 수준으로 드물어 놓쳐도 한참 모른다.
  6. 장애를 낸 과거 PR 데이터셋으로 버전마다 잡는 비율을 잰다. 버그 종류는 바뀌므로 계속 갱신한다.
  7. 모델마다 잘 내는 버그가 다르다. 쓴 모델과 다른 모델로 리뷰하면 잡는 비율이 10% 오른다. 브랜치 이름과 커밋 메시지의 지문으로 80%는 구분된다.
  8. grep은 부정확하고 비싸다. 미리 색인한 지식 베이스와 문서, 티켓을 주면 인증 우회 같은 맥락 의존 버그와 의도 불일치를 잡을 수 있다.
  9. 코드만 읽어서는 UI 문제를 모른다. 샌드박스에 앱을 띄우고 비전 모델로 눌러 본다. 개발 박스, 단순한 빌드 스크립트, 흐름 지도가 필요하다.
  10. 비용은 작업별로 모델을 나눠 줄인다. 최상위 모델은 약 20%만 쓴다. 단, 데이터셋 없이 바꾸면 성능 저하를 모른다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1리뷰 에이전트의 최소 구성 네 가지는?
샌드박스, 그 안의 코딩 에이전트(또는 모델 독립 하네스), PR 웹훅, GitHub 리뷰 API로 댓글 달기.
Q2잔소리 댓글이 망치는 두 가지는?
사람이 치명적 지적과 사소한 지적을 가려내기 힘들어진다. 그리고 코딩 에이전트가 댓글을 전부 반영해 지나치게 방어적인 코드가 된다.
Q3프롬프트를 고치는 두 방향은?
과거 장애를 분석해 만든 버그 종류 목록을 찾게 하고, 잔소리가 무엇인지 명시해 찾지 말라고 한다.
Q4프롬프트를 조금 바꿨더니 댓글 수가 크게 변했다. 왜 무서운가?
버그를 놓치고 있는지 알 수 없기 때문이다. 리뷰어는 버그의 존재는 알려 주지만 부재는 알려 주지 못한다. 치명적 버그는 드물어서 놓친 걸 한참 뒤에야 안다.
Q5과거 PR 데이터셋은 어떻게 만들고 왜 계속 갱신하나?
장애를 낸 PR을 모아 모든 버전의 에이전트를 돌려 잡는 비율을 잰다. 버그의 80~90%는 반복이지만 에이전트가 좋아질수록 새로운 방식으로 실패하므로 갱신해야 한다.
Q6Claude 모델과 GPT 모델이 자주 내는 버그는 각각 무엇인가?
발표자 데이터로 Claude 모델은 off-by-one 오류를 약 3배 자주 내고, GPT 모델은 인증 우회를 훨씬 자주 낸다.
Q7모델 뒤집기란 무엇이고 효과는?
코드를 쓴 모델과 다른 모델로 리뷰하는 것. 같은 모델은 같은 방식으로 놓치기 때문이다. 발표자 데이터로 잡는 비율이 10% 오른다.
Q8어떤 코딩 에이전트가 썼는지 알아내는 지문 두 가지는?
Codex는 브랜치 이름이 codex/로 시작한다. Claude는 PR 설명과 커밋 메시지에 Co-authored-by: Claude를 남긴다. 약 80%는 이걸로 구분된다.
Q9발표자가 grep만으로는 부족하다고 보는 두 이유는?
부정확해서 파일을 대량으로 읽고, 그래서 토큰이 많이 들어 비싸다. 코딩 에이전트 토큰 대부분이 grep, 파일 읽기, 캐시 쓰기다.
Q10인증 우회를 잡으려면 왜 코드베이스 맥락이 필요한가?
그 코드가 인증된 환경 안에 있는지 밖에 있는지를 알아야 우회가 일어났는지 판단할 수 있다. diff만으로는 모른다.
Q11버그가 없어도 코드가 틀릴 수 있는 이유와, 이를 막는 맥락 두 가지는?
Slack 메시지처럼 짧은 지시는 모호해서 에이전트가 의도를 잘못 읽을 수 있다. 문서와 티켓(Jira, Linear, Confluence, Notion), 그리고 코드베이스 지식 베이스를 준다.
Q12자율 테스트를 직접 하려면 필요한 세 가지는?
PR 브랜치 의존성까지 갖춘 개발 박스, 에이전트가 혼자 띄울 수 있는 단순한 빌드 스크립트, 앱의 모든 흐름을 적은 흐름 지도.
Q13비용을 줄이는 방법과 그때의 함정은?
하위 작업마다 다른 모델을 쓴다. 최상위 모델은 약 20%만. 함정은 데이터셋 없이 바꾸면 버그 잡는 능력이 떨어진 걸 장애가 날 때까지 모른다는 것이다.

Firecracker가벼운 가상 머신을 띄우는 오픈소스 기술. 샌드박스를 직접 만들 때 쓴다
하네스모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀. 발표자는 모델을 바꿔 끼울 수 있는 오픈소스 하네스를 권한다
웹훅Webhook. 어떤 일이 생기면 정해진 주소로 자동 통보하는 방식. 여기서는 PR이 열릴 때

잔소리 댓글Nitpick. 기술적으로는 맞지만 지나치게 깐깐한 리뷰 지적
반사실Counterfactual. "이렇게 안 했으면 어땠을까". 놓친 버그는 반사실이라 알 수 없다
후처리 학습Post-training. 기본 모델을 만든 뒤 추가로 가르치는 단계. 모델마다 버그 성향이 다른 원인으로 발표자가 지목
off-by-one 오류경계를 하나 틀리는 버그. 반복 횟수나 인덱스가 하나 많거나 적다
인증 우회Auth bypass. 로그인이나 권한 확인을 거치지 않고 보호된 기능에 닿는 버그
모델 뒤집기Model inversion. 코드를 쓴 모델과 다른 모델로 리뷰하는 것
RAG필요한 문서를 먼저 찾아 모델에게 함께 주는 방식. 큰 코드베이스에 쓰기 어렵다고 발표자가 말함
부족 지식Tribal knowledge. 문서에 없고 팀원 머릿속에만 있는 지식
컴퓨터 사용 모델Computer use. 화면을 보고 클릭과 입력으로 앱을 조작하는 모델
개발 박스Dev box. 앱을 실제로 돌려 볼 수 있게 갖춰진 개발 환경
흐름 지도Flow map. 앱의 사용자 흐름(가입, 로그인 등)과 관련 코드를 적은 문서
최상위 모델Frontier model. 현재 가장 성능이 높은 상용 모델
재순위Re-ranking. 후보 여러 개를 중요도 순으로 다시 정렬하는 것. 맥락 선별에 쓴다
캐시자주 쓰는 내용을 미리 담아 두는 저장소. 최상위 모델의 캐시는 비싸고 귀한 자원
