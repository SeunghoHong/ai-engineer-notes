VS Code는 어떻게 주간 출시로 바꿨나

VS Code 팀은 10년 넘게 지켜 온 월간 출시를 AI 덕분에 주간 출시로 바꿨다. 비결은 AI를 더 많이 쓰는 데 있지 않고, 일하는 시스템 전체를 에이전트에 맞게 고친 데 있다.

원본 영상: How VS Code Went from Monthly to Weekly Releases with AI 발표: Harald Kirschner (VS Code 팀 PM)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 바로잡았다. 확실하지 않은 것은 들린 대로 적고 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. VS Code는 1.0 이후 10년 넘게 한 달에 한 번 출시했다. 몇 달 전 이를 주간 출시로 바꿨다.
  2. 에이전트가 쓴 코드가 실제 커밋까지 살아남는 비율이 55%에서 86%로 올랐다. 개발자가 AI 코드를 더 믿게 됐다는 신호다.
  3. 핵심은 AI 사용량이 아니다. 소프트웨어를 내보내는 시스템 전체를 에이전트에 맞게 바꿔야 한다.
  4. 빨리 내보내기: AGENTS.md와 스킬로 저장소를 준비하고, 빌드를 10배 빠르게 하고, 에이전트가 앱을 직접 띄워 확인하게 한다.
  5. 제대로 내보내기: 자동 코드 리뷰가 필수다. 이슈 분류와 오류 분석도 자동화해 에이전트가 수정 PR까지 연다. 사람은 바로잡고 승인한다.
  6. 한 번에 모든 사용자에게 내보내던 방식을 버리고 단계적 배포로 바꿨다. 설치형 앱은 되돌리기가 비싸기 때문이다.
  7. 더 빨리 배우기: 제품용 평가 세트를 이슈 하나로 늘리고, 프로토타입으로 매일 피드백을 주고받는다. 그리고 다음 병목을 찾는다.
01

이 발표가 다루는 것 00:00

발표자는 VS Code를 만드는 팀에서 일한다. VS Code 팀은 AI 덕분에 월간 출시를 주간 출시로 바꿨다.

이 발표는 VS Code에 에이전트 기능을 넣는 이야기가 아니다. 에이전트를 써서 VS Code라는 제품 자체를 만드는 이야기다. VS Code 본체와 Copilot 등 여러 영역이 여기에 들어간다.

AI를 많이 쓸수록 기존 방식이 여기저기서 깨진다. 그래서 일하는 방식 자체를 다시 생각해야 했다.

규모 01:00 아주 작은 팀이 5천만 명이 넘는 사용자에게 제품을 내보낸다. 목표는 그냥 빨리 내보내는 것이 아니다. 더 효과적으로 내보내는 것이다.
02

에이전트 코드가 살아남는 비율 01:10

VS Code 팀은 일찍부터 코드 생존율 code survival을 쟀다. 에이전트가 쓴 코드 중 실제로 커밋까지 간 비율이다. 개발자가 믿지 못해 버린 코드나, 읽어 보고 지운 코드는 빠진다.

숫자가 오른 이유는 두 가지다. 새 모델이 나왔다. 그리고 모델을 감싸 도구와 규칙을 정해 주는 실행 틀, 즉 하네스 harness도 계속 고쳤다.

발표자는 이 상승을 개발자의 신뢰가 늘었다는 신호로 본다. 더 많은 AI 코드를 더 빨리 내보내도 된다는 자신감이 생겼다는 뜻이다.

코드 생존율은 발표자 팀이 만드는 제품(VS Code의 에이전트 기능)의 내부 지표다. 자기 제품의 성과로 읽힐 수 있으니 그 점을 감안하자.

03

성공이 만든 새 문제 01:50

이 성공은 VS Code에 새 문제를 만들었다. VS Code는 GitHub에서 가장 큰 오픈소스 프로젝트 중 하나다.

  • 이슈가 크게 늘었다. AI가 이슈 작성을 돕기 때문이다. 좋은 이슈도 늘었지만, 자동으로 만든 질 낮은 이슈도 늘었다.
  • 열린 PR도 늘었다. 팀 내부와 커뮤니티 양쪽 모두 그렇다.
  • 뜻밖의 결과도 있다. 쓰레기 PR만 늘 거라 예상하기 쉽다. 그런데 실제로 머지된 커뮤니티 PR도 늘었다.

10년 넘게 이어 온 월간 출시를 바꾸다 02:30

VS Code는 1.0 이후 10년 넘게 매달 새 버전을 냈다. 몇 달 전 이 주기를 주간 출시로 바꿨다.

재미있는 사실: 1월 릴리스는 실제로 2월에 나왔다. 릴리스 이름이 출시 날짜가 아니라 그 달의 개발 주기를 따랐기 때문이다.

핵심은 AI 사용량이 아니다 03:10 많은 회사가 매일 AI를 더 쓰라고 밀어붙인다. 발표자는 토큰을 최대한 쓰는 것 token maxing이 답이 아니라고 말한다. 소프트웨어를 내보내는 시스템 전체를 바꿔야 AI를 과정 전체에서 제대로 쓸 수 있다. 그래야 속도가 코드 양이 아니라 실제 결과로 이어진다.
04

세 단계로 나눠 보기 03:40

발표자는 변화를 세 단계로 나눈다. 앞 단계가 풀리면 다음 단계가 병목이 된다. 이 노트의 05~14절도 이 순서를 따른다.

1단계 · 빨리 내보내기

많은 팀이 이미 겪는 쉬운 단계다. 처음에는 몇몇 사람이 스킬, MCP, 플러그인으로 자기만의 환경을 만들어 코드를 쏟아낸다. 점점 팀 전체가 같은 방식을 따라간다.

다음 병목: 코드 리뷰와 품질

2단계 · 제대로 내보내기

빨라지면 코드 리뷰에서 막힌다. 자꾸 깨지지 않는 좋은 코드를 어떻게 내보낼지가 문제다. VS Code는 사용자 컴퓨터에 설치되는 프로그램이다. 그래서 문제가 생기면 되돌리는 비용이 특히 크다.

다음 병목: 무엇을 만들지

빠르고 안정적으로 내보내게 되면 질문이 바뀐다. 지금 맞는 것을 만들고 있나? 이걸 만들어야 하나? 발표자는 코드를 더 많이 쓰는 팀이 이 제품 감각과 학습을 많이 놓친다고 본다.

목표: 더 좋은 제품

05 · 1단계 빨리 내보내기

에이전트가 일하기 좋은 저장소 04:40

이제 누구나 바이브 코딩 vibe coding으로 코드를 빨리 낼 수 있다. 바이브 코딩은 코드를 한 줄씩 짜는 대신 AI에게 말로 시키며 만드는 방식이다. 여기서 큰 부분은 코드베이스를 에이전트가 일하기 좋게 준비하는 일이다.

AGENTS.md: 에이전트에게 주는 지도 04:50

발표자는 이걸 누구나 이미 해야 하는 기본이라고 부른다.

  • AGENTS.md를 둔다. 에이전트에게 코드베이스의 지도를 주는 파일이다. 어디를 보면 되는지 알려 준다.
  • 가볍게 유지한다.
  • 처음부터 쓰지 않아도 된다. 요즘 에이전트에는 초안을 만들어 주는 슬래시 명령이 있다(/init으로 추정).
  • 살아 있는 문서로 다룬다. 에이전트가 실수할 때마다 고쳐 나간다.

개발자 경험 developer experience에 투자해 온 팀이 여기서 크게 이득을 본다. 사람을 위한 좋은 문서와 온보딩 자료는 에이전트도 읽기 때문이다.

전문가의 지식을 스킬로 05:40

스킬 skill은 특정 작업의 방법과 기준을 묶어, 에이전트가 필요할 때 불러 쓰게 한 것이다. VS Code는 오래전부터 접근성에 많이 투자해 왔다. 그래서 일찍부터 접근성 모범 사례와 팀의 접근성 관점을 담은 스킬을 만들었다.

전한 사람이 매번 불려 간다접근성을 아는 사람이 리뷰와 피드백을 직접 해야 했다
→
후모두가 스킬을 쓴다접근성 영역 담당자는 스킬을 검토하고 관리한다

발표자의 제안은 이렇다. 팀에 늘 같은 질문을 받는 몇몇 사람이 있다면, 그 지식을 스킬로 만들어 병목을 풀어라.

PM이 바이브 코딩을 해도 되나 06:20

VS Code 팀의 리트머스 시험 litmus test은 이것이다. PM인 발표자가 VS Code 저장소에서 바이브 코딩으로 제대로 기여할 수 있나? 발표자는 실제로 그렇게 한다. 그때 확인하는 질문은 다음과 같다.

  • 엔지니어들이 그 코드를 받아들이나?
  • 받아들여지게 만드는 데 일이 얼마나 드나?
  • 받자마자 바로 동작하나? 내 컴퓨터에서 돌아가나?
  • 아니면 배포하고 나서 결국 깨지나?

이런 품질 개선이 쌓이면, 결국 누구나 저장소에서 효과적으로 일할 수 있게 된다.

06 · 1단계 빨리 내보내기

느린 빌드는 에이전트 수만큼 곱해진다 07:00

빌드, 린트 lint, CI/CD가 느린 저장소는 원래도 답답하다. 그래도 사람은 피해 간다. 기다리는 동안 PR을 리뷰하거나 다른 일로 넘어간다.

에이전트는 다르다. 에이전트 10개, 20개가 같은 병목에 동시에 걸린다. 느린 단계 하나가 에이전트 수만큼 쌓인다.

TypeScript Go로 빌드 10배 VS Code는 TypeScript Go로 바꿨다. TypeScript 컴파일러를 Go 언어로 다시 만든 버전이다. 빌드가 10배 빨라졌다. 에이전트는 CI 결과를 피드백으로 받아 코드를 고친다. 그래서 자동 PR이 많은 규모에서는 이 차이가 매우 크다.

거친 PR 하나가 토론을 연다 07:50

이런 환경에서 발표자는 PM이지만 큰 PR을 직접 올린다. 올해 초에는 'ask questions' 도구를 넣는 PR을 올렸다. 발표자가 꼭 필요하다고 믿은 기능이다.

처음 PR은 아주 거칠었다. 그래도 팀은 제품 안에서 직접 써 볼 수 있었다. 몇 주 만에 잘 다듬어지고 디자인까지 갖춘 기능이 됐다.

거친 PR이 아이디어와 사용 경험을 분명히 보여 줬다. 바탕이 깔려 있으니 다른 사람들이 토론에 끼기 쉬웠다.

07 · 1단계 빨리 내보내기

에이전트가 앱을 직접 보게 하라 08:30

누구나 겪는 장면이 있다. 에이전트가 UI를 만들고 "완벽해 보인다"고 말한다. 열어 보면 다 어긋나 있다. 최신 모델도, SVG로 그려도 마찬가지다.

에이전트가 우리 앱을 직접 쓸 수 없다면, 그걸 가능하게 만드는 것이 UI 작업을 할 때마다 돌려받는 큰 투자다.발표자가 요즘 모두에게 가장 먼저 하는 말이라며 강조한 내용을 옮김

VS Code는 두 가지에 투자했다.

컴포넌트 탐색기 09:00

VS Code가 바뀔 때마다 자동 빌드가 돈다. VS Code의 모든 컴포넌트를 스크린샷으로 찍고, 이전과 달라진 곳을 짚어 준다.

  • 예: 커스터마이즈 화면에 뒤로 가기 버튼을 넣은 이슈
  • 다른 변경 때문에 엉뚱한 컴포넌트가 바뀌거나 아이콘이 사라진 것을 잡는다
  • 리뷰어는 PR이 화면에서 무엇을 바꾸는지 바로 본다

예전에는 개발자에게 영상이나 스크린샷을 붙여 달라고 했다. 이제 그 일이 자동이다.

/launch 스킬 10:00

VS Code는 Electron 위에서 도는 웹 앱이다. 결국 HTML이라 Playwright로 조작할 수 있다. /launch 스킬은 VS Code를 띄우고, 정해 준 시나리오대로 클릭해 본다.

  • 실행하면서 로그를 모아 문제를 진단한다
  • 고치기 전과 후를 사람이 클릭하지 않고 확인한다
  • launch를 걸어 두고 다른 일을 하다 돌아오면 된다

에이전트가 스스로 확인하고 고치는 자기 수정 루프다.

웹 앱이 아니어도 된다 10:50

VS Code는 웹 기술로 만든 앱이라 Playwright를 쓸 수 있었다. 다른 플랫폼에도 방법이 있다. 발표자는 따로 iOS 앱도 만든다. Xcode MCP를 쓰면 에이전트가 Xcode를 직접 다루지 않고 VS Code 안에서 iOS 앱을 만든다. 앱을 열고, 눌러 보고, 스크린샷까지 찍는다. Android용 도구도 있다.

08 · 1단계 빨리 내보내기

자동 코드 리뷰를 필수로 11:20

발표자는 코드 리뷰를 다음 큰 투자처로 꼽는다.

시점내용
처음GitHub의 자동 Copilot 코드 리뷰를 켰을 때 팀은 아직 확신하지 못했다
지금몇 달 사이 크게 좋아졌다. 이제 누가 PR을 열든 자동 리뷰가 필수로 돈다
규칙자동 리뷰의 지적이 모두 해결되기 전에는 사람이 PR을 보지도 않는다
앞으로저장소의 위험도에 맞춰 리뷰 강도를 낮음, 중간, 높음으로 고르는 기능이 나올 예정이다. 비용과 효과를 맞춰 조절할 수 있다

발표자는 VS Code 팀 소속이다. VS Code와 GitHub Copilot은 모두 Microsoft 계열 제품이다. Copilot 리뷰에 대한 평가는 이 점을 감안해 읽자.

09 · 2단계 제대로 내보내기

이슈 분류는 AI가, 바로잡기는 사람이 12:00

빨라진 만큼 품질을 지켜야 한다. VS Code는 GitHub에 있어서 이슈가 중요한 신호다.

AI 덕분에 오히려 더 좋은 이슈가 들어오기도 한다. 다른 언어를 쓰는 사람도 좋은 이슈를 쓸 수 있게 됐다. 하지만 이슈 수도 크게 늘었다.

목적은 신호 대 잡음비 signal-to-noise를 높이는 것이다. 쓸모 있는 이슈가 더 잘 보이게 한다는 뜻이다.

오류 스택에서 수정 PR까지 13:20

또 하나의 신호는 오류 스택 error stack이다. 앱에서 예외가 날 때마다 어떤 함수 호출을 거쳐 났는지 기록이 보고된다.

VS Code는 이 일에 외부 도구를 쓰지 않는다. 데이터와 도구를 모두 직접 운영하고, 대부분 이미 있던 것이다. 예전에는 그 위에서 머신러닝으로 정렬했다. 지금은 여러 기준을 섞어 쓴다.

  1. 모은다. 원시 텔레메트리를 모은다. 발표자 표현으로 하루 약 510억 건이다.
  2. 거른다. 스택 전체가 남은 오류만 남긴다.
  3. 묶는다. 같은 원인끼리 묶는다. 오류마다 지문을 뜨는 작업 fingerprinting이다.
  4. 이슈로 만든다. 영역 담당자에게 배정한다. 이 과정을 거치면 이슈가 10개 정도로 줄어든다. 기간 기준은 발표에서 밝히지 않았다.
  5. PR을 연다. 에이전트가 수정 PR을 자동으로 만든다.
  6. 승인한다. 사람이 PR을 보고 승인한다.

오류 페이지에서는 스택마다 발생 횟수와 영향받은 사용자 수를 본다. 그래서 새로 생긴 문제에 빨리 대응할 수 있다. 14:10

실제 예 14:20 이슈에는 오류 내용과 첫 진단이 들어 있었다. 에이전트는 PR을 열고 원인을 추적했다. 문제와 이어진 것은 심볼 찾기 find symbols 관련 변경이었다. 취소 요청 처리 on cancellation request가 RPC 프로토콜에 빠져 있었다. 팀은 그 PR을 그대로 머지할 수 있었다.

발표자의 말을 빌리면, 오류 하나하나에 관심을 쏟고 싶은 게 아니다. 더 안정적인 코드베이스를 원할 뿐이다.

정리하면 이렇다. 처음 분류는 에이전트와 정해진 규칙으로 도는 결정적 시스템 deterministic system이 섞여서 한다. 이슈는 여러 에이전트가 함께 일하는 시스템으로 넘어가 PR이 된다. 수정은 대부분 자동으로 들어가고, 사람은 PR 승인으로 감독한다.

웹 서비스는 원래 이렇게 배포한다. 설치형 앱은 문제가 생긴 버전을 되돌리는 롤백 rollback 비용이 훨씬 크다. 그래서 VS Code도 같은 방식을 쓰게 됐다.

12 · 3단계 더 빨리 배우기

자기 제품의 평가 세트를 쉽게 늘린다 16:00

빠르고 안정적으로 내보내게 됐다. 다음 질문은 더 빨리 배우는 법이다. 발표자는 AI 시대에 이것이 더 큰 과제라고 본다. 목표는 더 좋은 제품을 더 빨리 만드는 것이다.

VS Code는 에이전트 제품을 만든다. 그래서 자기 제품을 재는 평가 eval가 늘 가까이 있어야 하고, 쉽게 늘릴 수 있어야 한다. 그 예가 VSC Bench(추정)다. 16:10

  1. 새 시나리오를 넣고 싶으면 GitHub에 이슈를 연다.
  2. 에이전트가 템플릿을 보고 시나리오의 뼈대를 만든다.
  3. 이슈, 고객과의 대화 등 여러 경로에서 나온 개발자 시나리오가 평가 세트로 들어온다.
  4. 그 평가 점수를 보며 조금씩 끌어올린다. 이를 힐 클라이밍 hill climbing이라고 한다.
  5. 오프라인에서 나아졌는지 확인한 뒤, 실제 사용자 대상 온라인 실험으로 다시 확인한다.

발표자는 이를 전형적인 제품 개발 주기라고 부른다.

평가를 이해해야 한다: 같은 일에 토큰 70배 17:00

VS Code 팀은 평가 하네스가 처음부터 끝까지 잘 도는지 보려고 아주 단순한 과제를 줬다. "hello world"를 담은 파일 하나를 쓰는 일이다. 모델마다 어떻게 반응하는지도 함께 봤다.

결과 같은 짧은 파일을 쓰는 데 가장 비싸게 든 모델은 토큰을 70배 더 썼다. 그 모델은 깊게 추론하는 고추론 모델도 아니었다. 자세한 내용은 VS Code 블로그에 있고, 거기서도 모델 이름은 밝히지 않았다고 한다.

발표자는 이 과제를 "hello world 파일"이라고도 하고 "5글자 파일"이라고도 했다. "hello world"는 11글자라 둘이 맞지 않는다. 정확한 과제는 블로그 원문에서 확인해야 한다.

교훈은 모델 순위가 아니다. 내 하네스 안에서 모델들이 어떻게 움직이는지 아는 것이 중요하다.

PR보다 프로토타입, 월간보다 매일 17:30

발표자는 프로토타입을 많이 만든다. 작업 대부분을 VS Code PR로 넣고 싶지 않다는 걸 알게 됐기 때문이다. PR은 대화를 시작하기엔 좋다. 하지만 대개 필요한 건 빠른 대화다.

이제 팀은 매일 만난다. "이런 아이디어다", "이렇게 보일 수 있다", "이렇게 하면 어떨까"를 나눈다. 다음 날 고친 프로토타입을 들고 와 대화를 이어 간다.

피드백 주기는 월간 출시에서 주간 출시로, 다시 매일 하는 스프린트로 짧아졌다. 프로토타입은 사용 경험이 어떠해야 하는지에 대한 더 깊은 토론을 끌어낸다.

작은 팀, 오래가는 담당 18:20

팀 구조도 바뀌었다. 매일 스프린트를 돈다. 작은 스쿼드가 작은 작업 흐름을 맡는다. 각 스쿼드는 좁은 영역의 우선순위를 정하고 끌고 가서 더 빨리 움직인다. 발표자는 이를 내부 작업의 지속적인 담당 durable ownership이라고 불렀다.

핵심 정리

  1. VS Code는 10년 넘게 지킨 월간 출시를 주간 출시로 바꿨다. 핵심은 AI 사용량이 아니라 시스템 전체의 변화다.
  2. 에이전트 코드의 생존율이 55%(GPT-4.1)에서 86%(Claude Opus 4.6)로 올랐다. 모델과 하네스가 함께 좋아진 결과다.
  3. 변화는 세 단계다. 빨리 내보내기 → 제대로 내보내기 → 더 빨리 배우기. 앞이 풀리면 다음이 병목이 된다.
  4. 저장소를 에이전트용으로 준비한다. 가벼운 AGENTS.md를 두고 실수할 때마다 고친다. 전문가 지식은 스킬로 만든다.
  5. 느린 빌드는 에이전트 수만큼 곱해진다. TypeScript Go로 빌드가 10배 빨라졌다.
  6. 에이전트가 앱을 직접 띄워 보게 한다. 컴포넌트 스크린샷 비교와 /launch 스킬이 그 예다.
  7. 자동 코드 리뷰가 필수다. 지적이 모두 해결되기 전에는 사람이 PR을 보지 않는다.
  8. 이슈 분류와 오류 분석을 자동화하고, 에이전트가 수정 PR까지 연다. 사람은 바로잡고 승인한다.
  9. 설치형 앱은 되돌리기가 비싸다. 한 번에 100% 대신 단계적으로 배포한다.
  10. 자기 제품의 평가 세트를 이슈 하나로 늘리고, 프로토타입으로 매일 피드백을 주고받는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1코드 생존율은 무엇을 재나? 발표에서 어떻게 변했나?
에이전트가 쓴 코드 중 실제로 커밋까지 간 비율이다. GPT-4.1일 때 55%였고, 발표 시점 Claude Opus 4.6으로 86%다. 모델 교체와 하네스 개선이 함께 반영됐다.
Q2발표자가 "token maxing"을 답이 아니라고 한 이유는?
AI를 매일 더 쓴다고 속도가 나지 않는다. 소프트웨어를 내보내는 시스템 전체를 바꿔야 AI가 과정 전체에서 효과를 낸다.
Q3세 단계는 무엇이고, 각 단계 뒤에 어떤 병목이 오나?
빨리 내보내기 다음에는 코드 리뷰와 품질이 막힌다. 제대로 내보내기 다음에는 "맞는 걸 만들고 있나"가 문제가 된다. 마지막 단계는 더 빨리 배우기다.
Q4AGENTS.md를 다룰 때 발표자가 강조한 점은?
가볍게 유지한다. 초안은 에이전트의 슬래시 명령으로 만들 수 있다. 살아 있는 문서로 보고 에이전트가 실수할 때마다 고친다.
Q5접근성 스킬은 무엇을 바꿨나?
접근성을 아는 한 사람이 매번 불려 가던 일을, 모두가 스킬로 쓰게 바꿨다. 스킬은 접근성 영역 담당자가 검토하고 관리한다.
Q6빌드 속도가 사람보다 에이전트에게 더 중요한 이유는?
사람은 기다리는 동안 다른 일을 한다. 에이전트는 수십 개가 같은 병목에 동시에 걸리고, CI 결과를 피드백으로 받아 코드를 고친다. 그래서 TypeScript Go의 10배 개선이 크게 작용했다.
Q7에이전트가 앱을 직접 보게 하는 VS Code의 두 장치는?
컴포넌트 탐색기는 모든 컴포넌트의 스크린샷을 찍어 달라진 곳을 짚는다. /launch 스킬은 Playwright로 VS Code를 띄워 시나리오대로 클릭하고, 로그를 모으고, 수정 전후를 확인한다.
Q8자동 코드 리뷰와 사람 리뷰는 어떤 순서로 도나?
PR을 열면 자동 리뷰가 필수로 돈다. 자동 리뷰의 지적이 모두 해결된 뒤에야 사람이 PR을 본다.
Q9이슈 분류 에이전트 옆에 Chrome 확장을 둔 이유는?
에이전트는 실수한다. 사람이 중복 판정 같은 실수를 바로잡고, 그 내용을 다시 에이전트 작업에 반영하기 위해서다.
Q10오류 스택이 수정 PR이 되기까지의 단계는?
텔레메트리를 모은다(하루 약 510억 건). 스택 전체가 남은 오류만 거른다. 같은 원인끼리 묶는다. 이슈로 만들어 담당자에게 배정한다. 에이전트가 수정 PR을 연다. 사람이 승인한다.
Q11VS Code가 단계적 배포로 바꾼 이유는?
에이전트로 변경이 늘어 출시 위험을 줄이고 싶었다. 설치형 앱은 웹 서비스보다 롤백 비용이 훨씬 크다.
Q12hello world 실험이 주는 교훈은?
아주 단순한 과제에서도 가장 비싸게 든 모델은 토큰을 70배 더 썼고, 그 모델은 고추론 모델도 아니었다. 모델 순위보다 내 하네스 안에서 모델이 어떻게 움직이는지 알아야 한다.
