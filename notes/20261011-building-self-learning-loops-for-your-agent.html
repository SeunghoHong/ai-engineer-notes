에이전트에게 자기 학습 루프 달아 주기

프로덕션에서 터지는 에이전트 실패는 사람이 대시보드를 읽어서는 못 따라잡는다. 발표자는 트레이스를 사람이 아니라 에이전트가 읽게 하고, 감지·조사·수정·검증을 한 루프로 돌리는 방법을 Arize 제품을 예로 설명한다.

원본 영상: Building Self-Learning Loops for Your Agent 발표: Fuad Ali (Arize AI 프로덕트)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 경우에만 알려진 이름으로 바로잡았고, 나머지는 "(추정)"을 붙였다. 워크숍 중 실습 안내와 Wi-Fi 문제로 끊긴 부분은 뺐다. mm:ss는 영상 위치다.

발표자는 관측·평가 도구를 파는 Arize AI 소속이고, 발표 내용 대부분이 Arize의 새 기능(Signal, 스킬, 하네스 심판, 에이전트 실험) 소개다. 제품 홍보라는 점을 감안해 읽자. 다만 "에이전트가 자기 텔레메트리를 읽고 고친다"는 구조 자체는 특정 제품 없이도 적용할 수 있다.

3분 요약
  1. 관측은 사람이 읽는 대시보드에서 에이전트가 소비하는 프로그램 인터페이스로 바뀌어야 한다. 에이전트가 수천 개면 사람이 다 읽을 수 없다.
  2. 비용을 치르는 실패는 출시 때 보이지 않는다. 미리 알았다면 이미 평가를 써 뒀을 것이다. 예: "30달러 이하 선물"을 물었는데 50달러짜리를 자신 있게 추천한다.
  3. 루프는 네 단계다. 감지 → 조사 → 수정 → 검증. 트레이스(에이전트가 실제로 한 일)와 코드 저장소(에이전트가 해야 할 일)를 같이 봐야 원인을 찾는다.
  4. Signal은 백그라운드에서 트레이스를 계속 읽어 실패를 원인별로 묶고, GitHub에 연결하면 조사 보고서와 PR까지 쓴다. Arize 스킬은 Claude Code 같은 코딩 에이전트가 필요할 때 트레이스를 읽게 한다.
  5. 하네스 심판은 고정된 채점표 대신 트레이스 전체를 읽고 기준을 스스로 세운다. 외부 시스템에 물어볼 수 있어 "이 사용자가 이걸 할 권한이 있었나" 같은 검사도 된다.
  6. 에이전트 실험은 실제로 실패했던 트레이스를 데이터셋으로 만들어 고친 버전에 다시 던지고, 프로덕션과 같은 심판으로 전후를 비교한다.
  7. 끝까지 가면 에이전트가 문제를 찾고, PR을 올리고, 스스로 재배포해 실패 데이터셋으로 검증한 뒤에야 사람에게 알린다. 사람은 코드 리뷰에 남는다.
01

로켓처럼 스스로 고치는 에이전트 00:50

02

관측의 세 단계 02:10

발표자는 소프트웨어가 자기 문제를 고치는 방식을 세 단계로 나눈다. 바뀌는 것은 누가 텔레메트리를 읽느냐다.

단계누가 읽나누가 고치나
1.0앱이 Datadog 같은 관측 플랫폼에 기록을 보내고, 사람이 읽는다사람 개발자가 코드를 쓴다
2.0사람이 읽는 건 같다사람이 코드 대신 프롬프트를 써서 동작을 고친다
3.0앱이 내는 텔레메트리를 코딩 에이전트가 읽는다에이전트가 자기 코드를 보고 수정을 제안한다

Cursor, Claude Code, Datadog CLI를 쓰는 사람은 이미 3.0의 일부를 겪고 있다. 다만 아직은 사람이 "가서 Datadog 좀 읽어 봐"라고 시켜야 한다. 에이전트가 수천 개로 늘면 사람이 그 기록을 다 읽는 일 자체가 불가능해진다.

발표자가 가장 강조한 한 문장 관측은 사람이 읽는 대시보드에서 벗어나, 에이전트가 소비하고 조작하고 스스로 돌아볼 수 있는 프로그램 인터페이스로 진화해야 한다.

03

비싼 실패는 출시 때 안 보인다 05:00

정의상 그렇다. 출시 전에 잡았다면 이미 고쳤을 테니 비용을 치르지 않았을 것이다. 에이전트는 실험 단계에서 잘 돌고, 내가 만든 평가도 통과한다. 문제는 어떤 평가를 만들어야 하는지 미리 다 알 수 없다는 점이다.

  • 손님이 "30달러 이하 생일 선물"을 묻는다. 에이전트는 30달러, 50달러짜리 목록을 돌려준다.
  • 프로덕션에서는 에이전트가 그 잘못된 상품을 자신 있게 구매한다. 상품을 한 번도 확인하지 않기 때문이다.
  • 스테이징에서는 안 보인다. 사용자 불만, 지원 티켓, 새벽 3시 호출로 처음 드러난다.

"스테이징에서는 됐는데 프로덕션에서는 뭔가 이상하다"는 틈을 메우는 것이 이 발표의 목표다.

04

예제: Wonder Toys 쇼핑 도우미 06:10

워크숍 내내 쓰는 예제는 장난감 쇼핑 도우미다. 단순한 앱이고 실제 결제는 없다.

에이전트가 가진 도구
  • 상품 검색
  • 상품 상세 조회
  • 상품 구매
  • 주문 상태 확인
  • 주문 취소
구성
  • OpenAI Agents SDK
  • FastAPI 백엔드

  • 모든 실행이 Arize로 트레이스된다

실습 준비는 명령 네 개 07:30

  1. 저장소를 clone 하고 그 폴더로 들어간다.
  2. .env에 키를 넣는다. Arize API 키와 OpenAI API 키가 필요하다. Arize 무료 계정으로 충분하다.
  3. npm install 뒤 npm run dev.
  4. 웹 화면에서 상품을 묻거나 구매를 시키면 트레이스가 Arize로 자동으로 흘러 들어간다.

발표자는 키가 "세 개"라고도 말했다. 자막만으로는 세 번째 키가 무엇인지 확실하지 않다.

심어 둔 버그: 가격 조건 08:20

대부분의 질문은 잘 된다. 그런데 "30달러 이하 생일 선물"을 물으면 30달러 넘는 상품이 나온다. 특정 조건 검사price gate가 작동하지 않는 흔한 경계 사례다. 에이전트는 이걸 스스로 알리지 않고, 완전히 틀린 상품을 자신 있게 돌려준다.

아직 본 적 없는 경계 사례에 대한 평가를 어떻게 쓰나?발표자의 질문을 옮김 (09:10)

트레이스만 있는 불투명한 시스템에서는 이런 사례를 찾기 어렵다. 트레이스와 코드 저장소를 같이 봐야 원인이 보인다. 이 지점에서 Arize의 두 기능이 나온다.

05

Signal: 항상 켜진 조사 에이전트 09:10

Signal은 Arize 플랫폼 샌드박스 안에서 도는 기본 제공 에이전트다. 프로젝트 설정에서 토글 하나로 켠다.

  • 프로덕션 트레이스를 백그라운드에서 계속 읽는다.
  • 실패를 근본 원인별로 묶고, 여러 실행에 걸쳐 같은 실패는 하나로 합친다.
  • 하네스를 갖춘 에이전트라 외부 도구를 부를 수 있다. GitHub 저장소나 Datadog 같은 하류 데이터 소스에 연결한다.
  • 트레이스를 근거로 에이전트의 코드를 들여다보고, 조사 보고서와 심각도를 쓰고, 증거를 모아 PR을 열어 준다.

이것이 2절에서 말한 3.0이다. 에이전트가 관측 플랫폼에서 자기 텔레메트리를 소비하고, 자기 코드를 보고, 증거를 들어 수정을 제안한다.

데모에서 보인 화면 20:30

트레이스가 들어오기 시작하면 Signal이 돌기까지 몇 분 걸린다. 미리 켜 둔 예제 화면은 이렇게 생겼다.

화면 요소내용
군집 분석앱 전체에서 보이는 문제를 종류별로 묶은 표. 시간에 따른 추세도 보인다
예시 트레이스각 문제의 실제 사례를 열어 읽을 수 있다. 데모에서는 Python 직렬화 문제가 에이전트 입력을 망가뜨리는 사례가 나왔고, 이미 PR이 열려 있었다
조사 티켓개요(예: 주식 에이전트가 결과를 지어냄), 왜 그런지에 대한 가설, 개별 트레이스 안의 증거, 제안하는 수정
코드 리뷰는 사람 몫으로 남긴다 데모에서도 PR 머지는 사람이 결정한다. 발표자는 "어디까지 자동화할지는 마음대로지만, 사람 리뷰를 남기길 권한다"고 말했다.
06

Arize 스킬: 코딩 에이전트가 트레이스를 읽는다 11:00

Arize가 관리하는 에이전트를 쓰고 싶지 않을 수도 있다. 그럴 때는 스킬skill을 쓴다. 스킬은 Cursor, Claude Code, Codex, OpenCode, Amp(추정) 등 40개 넘는 코딩 에이전트가 Arize의 트레이스를 직접 조회하게 해 주는 묶음이다.

저장소 안에서 Claude Code에게 "내 트레이스를 읽어 봐"라고 하면, 에이전트는 트레이스 데이터와 그 에이전트의 코드를 동시에 보고 수정한다.

스킬 종류 12:10

  • 실패 사례로 데이터셋 만들기
  • 트레이스를 읽고 오류 분석하기
  • 플랫폼에서 평가기와 작업 실행하기

설치 36:50

자막으로는 아래처럼 들린다. 대화형으로 원하는 스킬만 고르거나 전부 설치할 수 있다.

발표자가 예로 든 요청은 이렇다. "내 트레이스에서 오류나 고칠 만한 것을 찾고, 이 저장소의 에이전트 코드와 대조해라. 에이전트 스킬을 써라."

07

루프 네 단계: 감지·조사·수정·검증 23:20

1 · 감지 detect

사용자가 신고하기 전에 실패를 드러낸다. 예제에서는 검색 대체 경로와 가격 조건의 실패다.

2 · 조사 investigate

실제 트레이스로 무슨 일이 있었는지 본다. 사용자가 "30달러 이하"라고 한 트레이스를, 가격 필터를 검사하는 코드 경로와 맞춰 본다.

3 · 수정 fix

Signal이나 Claude Code가 잘못된 필터를 고친 PR을 올린다. 발표자의 코드에는 실제로 가격 필터 버그가 있었다.

4 · 검증 verify

하네스 심판과 에이전트 실험으로 수정이 진짜 효과가 있는지 확인한다. 워크숍에서는 설정이 길어 설명만 했다.

루프의 두 입력은 트레이스(에이전트가 실제로 한 일의 기준 자료)와 저장소(에이전트가 해야 할 일을 정의한 코드)다. 둘을 같이 보면 규모 있게 개선할 수 있다.

Signal을 알림에 묶기 25:10

  • Signal은 내 분류 체계와 내 트레이스에 맞춰 조정된다.
  • 알림을 트리거로 쓸 수 있다. 예: 특정 평가의 실패율이 1%를 넘으면, 지연 시간이나 비용이 튀면 Signal이 조사를 시작한다.
  • PR마다 CI에서 맞춤 하네스 심판을 돌릴 수 있다.
08

하네스 심판 26:30

에이전트를 에이전트로 평가하는 방법이다. 발표자는 이걸 하네스 심판harness as a judge이라 부른다.

LLM 심판하네스 심판
채점 기준미리 정한 고정 채점표. 요약 품질, 환각 여부 같은 아는 문제를 잘 잡는다에이전트가 실제로 한 일을 보고 무엇을 검사할지 그때그때 정한다. 기준이 실행 궤적에서 나온다
보는 것입력과 출력트레이스 트리 전체. 올바른 도구를 골랐나, 인자가 유효했나, 다른 에이전트가 넘긴 맥락에 근거했나
쓰는 법컬럼 매핑, 평가 템플릿 작성채점 기준을 한 문장으로 쓴다. 샌드박스에서 실제 트레이스를 상대로 돈다
외부 접근없다. 시스템 프롬프트에 붙여 넣은 것만 안다외부 시스템을 부를 수 있다
외부 접근이 왜 중요한가: 권한 검사 28:50 LLM 심판은 이 사용자가 무엇을 할 수 있어야 하는지 모른다. 모든 사용자 정보를 프롬프트에 넣지 않는 한 그렇다. 하네스 심판은 외부 시스템에 "이 사용자가 이걸 해도 되나"를 물어보고, 트레이스가 그 권한에 맞는지 판단할 수 있다.

예제에 적용하면 29:50

채점 기준은 한 문장이다. "돌려준 모든 상품의 가격이 요청한 최소·최대 범위 안이면 통과, 하나라도 예산을 넘으면 실패." 심판은 코드까지 들어가 필터가 제대로 도는지 확인할 수 있다. 이 기준은 한 번 쓰면 이후 모든 실행에서 같은 문제를 잡는다. 미리 짜 둔 테스트 케이스 하나와 다른 점이다.

09

에이전트 실험 30:30

문제를 찾았고, 트레이스로 근거를 댔고, 왜 틀렸는지 알고, 고칠 가치가 있다고 판단했다. 배포 전에 그 수정을 여러 사례에 시험해야 한다. 지금은 대개 개발 환경에 올리고 손으로 눌러 본다. 에이전트 실험agent experiments은 이걸 CI에서 자동으로 한다.

  1. 실제로 실패한 트레이스로 데이터셋을 만든다. 예: 예산 조건 검색이 실패한 사례 25개. Arize 스킬로 만들 수 있다.
  2. 고친 에이전트를 개발 환경의 엔드포인트 뒤에 세운다.
  3. Arize에서 데이터셋 입력을 그 엔드포인트로 흘려보낸다.
  4. 프로덕션과 같은 심판 기준으로 채점한다. 예제에서는 가격 정확성 심판이다.
  5. 수정 전 프로덕션과 수정 후 개발 버전을 나란히 비교한다. 지연 시간과 비용이 늘지는 않았는지도 본다.

실험 결과는 PR에 함께 붙는다. 발표자의 예에서는 해당 평가기 점수가 36% 올랐다고 했다.

10

완전 자율 루프 한 바퀴 33:10

실험이 스킬과 API로도 열려 있어서, 에이전트는 사람에게 알리기 전에 스스로 재배포하고 검증할 수 있다. 발표자가 그린 한 바퀴는 이렇다.

  1. 에이전트가 트레이스를 보다가 "30달러 이하" 요청에 30달러 넘는 응답이 나간 것을 찾는다.
  2. 코드베이스를 참고해 왜 그런지 조사한다. 이번에는 필터 오류였다.
  3. 고친 내용을 PR로 올린다.
  4. 그 PR을 개발 환경에 올리고, 자기가 모은 실패 데이터셋으로 돌려 본다.
  5. 결과를 PR에 적어 사람에게 보고한다. "이 문제를 찾았고, 원인은 이것이고, PR을 올렸고, 실패 사례로 돌려 보니 이 평가에서 36% 좋아졌다."
루프 1감지 → 조사 → 가설 → 수정문제를 찾아 고치는 루프

시작하는 순서 35:30

  1. 트레이싱부터. 트레이스를 안 모으면 나머지가 다 안 된다. 발표자는 계측 스킬이 있어 자기 에이전트에 10분 안에 붙일 수 있고, 주요 에이전트 프레임워크와 모델 제공자를 다 지원한다고 말했다.
  2. Signal을 켜거나, Claude Code에 Arize 스킬을 붙여 조사를 시킨다.
  3. 하네스 심판으로 검증한다.
  4. 에이전트 실험으로 전후를 잰다.

발표 끝에 무료 티어는 계속 무료이고, 행사 참가자에게 Arize Pro 1년 무료 코드를 준다고 했다. 같은 날 오후 2시에 Laurie Voss가 코드 예제를 더 다루는 워크숍을 연다고도 안내했다.

12

핵심 정리

  1. 로켓이 자기 텔레메트리로 경로를 고치듯, 에이전트도 자기 트레이스를 읽고 자기를 고쳐야 한다.
  2. 관측은 1.0(사람이 읽고 코드로 고침), 2.0(사람이 읽고 프롬프트로 고침)을 지나 3.0(에이전트가 읽고 고침)으로 간다.
  3. 에이전트가 수천 개가 되면 사람이 대시보드를 읽는 방식은 성립하지 않는다.
  4. 비싼 실패는 출시 때 보이지 않는다. 미리 알았다면 평가를 써 뒀을 것이다.
  5. 원인을 찾으려면 트레이스(실제로 한 일)와 코드(해야 할 일)를 같이 봐야 한다.
  6. Signal은 항상 켜진 조사 에이전트다. 실패를 원인별로 묶고, 저장소에 연결하면 조사 보고서와 PR을 쓴다.
  7. Arize 스킬은 Claude Code 같은 코딩 에이전트가 필요할 때 트레이스를 읽게 한다. Signal과 같은 일을 다른 방식으로 한다.
  8. 하네스 심판은 고정 채점표가 아니라 트레이스 전체를 보고 기준을 세우며, 외부 시스템에도 물어본다. 채점 기준은 한 문장이다.
  9. 에이전트 실험은 실제 실패 트레이스로 데이터셋을 만들어 고친 버전을 프로덕션과 같은 심판으로 전후 비교한다.
  10. 끝까지 가면 에이전트가 찾고, 고치고, 스스로 재배포해 검증한 뒤 보고한다. 사람은 코드 리뷰에 남는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 로켓을 비유로 든 이유는?
로켓은 매 밀리초 자기 텔레메트리를 읽고 그걸로 경로를 고친다. 에이전트도 자기 트레이스를 소비해 스스로 고치게 하자는 뜻이다.
Q2관측 1.0, 2.0, 3.0에서 달라지는 것은?
누가 텔레메트리를 읽고 어떻게 고치느냐. 1.0은 사람이 읽고 코드로, 2.0은 사람이 읽고 프롬프트로, 3.0은 코딩 에이전트가 읽고 수정을 제안한다.
Q3"비용을 치르는 실패는 출시 때 보이지 않는다"가 정의상 맞는 이유는?
출시 전에 잡았다면 이미 고쳤을 것이고, 그러면 비용을 치르지 않았을 것이다. 어떤 평가를 써야 하는지 미리 다 알 수 없다.
Q4Wonder Toys에 심어 둔 버그는?
"30달러 이하 선물"을 물으면 30달러 넘는 상품이 나온다. 가격 조건 검사가 작동하지 않고, 에이전트는 이를 알리지 않고 자신 있게 답한다.
Q5Signal이 트레이스를 읽은 뒤 하는 일 네 가지는?
실패를 근본 원인별로 묶고, 실행 간 중복을 합치고, GitHub나 Datadog 같은 외부 도구를 보며 조사 보고서와 증거를 쓰고, PR을 연다.
Q6Arize 스킬과 Signal은 어떻게 다른가?
하는 일은 같다. 스킬은 엔지니어가 Claude Code 같은 코딩 에이전트에서 필요할 때 부르는 방식이고, Signal은 백그라운드에서 항상 켜져 있는 방식이다.
Q7루프 네 단계는?
감지, 조사, 수정, 검증. 검증은 하네스 심판과 에이전트 실험으로 한다.
Q8LLM 심판과 하네스 심판의 가장 큰 차이 두 가지는?
LLM 심판은 고정 채점표로 입력과 출력만 보고, 하네스 심판은 트레이스 전체를 보며 기준을 그때그때 세운다. 또 하네스 심판은 외부 시스템을 부를 수 있어 권한 검사 같은 것도 한다.
Q9예제의 하네스 심판 채점 기준 한 문장은?
돌려준 모든 상품 가격이 요청한 범위 안이면 통과, 하나라도 예산을 넘으면 실패.
Q10에이전트 실험에서 데이터셋은 어디서 오고, 채점은 무엇으로 하나?
실제로 실패한 프로덕션 트레이스에서 만든다. 채점은 프로덕션에서 쓰는 것과 같은 심판 기준으로 해서 전후를 나란히 비교한다.
Q11완전 자율 루프에서 사람에게 남는 일은?
PR을 읽고 코드를 리뷰해 배포 여부를 정하는 일. 에이전트는 그 전에 스스로 재배포하고 실패 데이터셋으로 검증까지 마친다.
Q12발표자가 가장 먼저 하라고 한 것은?
트레이싱. 트레이스를 모으지 않으면 나머지가 전부 성립하지 않는다.
