늘어난 PR은 누가 검증하나

AI 덕분에 PR은 더 많아지고 커졌다. 그런데 CI와 코드 리뷰로 이루어진 검증 단계는 그 속도를 따라가지 못한다. 발표자의 답은 검증을 맡는 에이전트다. 리뷰부터 머지까지 맡기되, 신뢰가 쌓이는 만큼 한 단계씩 연다.

원본 영상: AI Writes More PRs. Who Validates Them? 발표: Ali-Reza Adl-Tabatabai (Gitar 공동 창업자, 발표 약 한 달 전 Sonar에 인수되기 전까지 CEO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 자막에 "guitar"로 들린 회사 이름은 Gitar로, "sonar cube"는 SonarQube로, "NLM proxy"는 LLM 프록시로 바로잡았다. 발표에 비교할 만한 수치가 나오지 않아 차트는 넣지 않았다. mm:ss는 영상 위치다.

발표의 대부분은 발표자 회사의 제품 소개다. 효과에 대한 주장에는 수치나 고객 사례가 붙어 있지 않다. 그 점을 감안해 읽자.

3분 요약
  1. CI와 코드 리뷰로 이루어진 검증 단계는 모든 변경이 프로덕션으로 가는 길목이다. 팀이 커질수록 느려지고 비싸진다.
  2. 여기서 실패하면 몇 시간에서 며칠짜리 되돌이가 생긴다. 개발자의 시간과 집중이 함께 깨진다.
  3. AI는 PR을 더 많이, 더 크게 만든다. 꼼꼼히 리뷰하면 느려지고, 대충 승인하면 사고가 난다.
  4. 발표자의 답은 검증을 맡는 에이전트다. 리뷰, CI 실패 분석, 자동 수정, 자동 승인과 머지까지 한다.
  5. 사용자들은 신뢰가 쌓이는 만큼 자동화를 한 단계씩 연다. 리뷰 → 머지 차단 → 자동 수정 → 자동 머지 순서다.
  6. 모든 PR을 AI가 보니 CI 실패 유형과 PR 유형 통계가 덤으로 나온다.
  7. Sonar에 인수된 뒤에는 에이전트에 전통적인 프로그램 분석을 더하는 중이다. 발표자는 둘을 합치면 어느 한쪽보다 낫다고 본다.
01

검증 단계가 하는 일 00:40

거의 모든 소프트웨어 팀에는 변경을 한곳에서 검사하는 단계가 있다. 발표자는 이를 중앙 검증 단계centralized validation phase라고 부른다. 내용은 CI와 코드 리뷰다. CIcontinuous integration는 코드를 올릴 때마다 자동으로 빌드하고 테스트하는 장치다.

특징내용
품질 관문을 한곳에서 지킨다보안, 컴플라이언스, 코드 품질 기준을 여기서 검사한다
출시의 길목에 있다모든 변경이 이 단계를 지나야 프로덕션에 간다. 그래서 빠를수록 좋다
규모가 커지면 느려진다빌드와 작업이 길어진다. 여러 지역과 팀에 걸친 리뷰가 비동기로 늘어진다
돈이 많이 든다비싼 도구를 여러 개 붙이고, 조직이 커지는 만큼 늘린다. 모두 비싼 인프라 위에서 돈다
플랫폼 팀의 주 관심사위 이유로 플랫폼 팀이 가장 많이 신경 쓰는 영역이다

발표자는 AI 시대에 이 단계가 더 중요해진다고 강조한다.

02

실패하면 비싸다 02:00

검증 단계에서 실패가 나면 개발자는 고치고, 다시 올리고, 다시 기다린다. 이 바깥쪽 되돌이를 아우터 루프outer loop라고 한다. 발표자에 따르면 아우터 루프는 보통 몇 시간에서 며칠 단위다.

  • 개발자 시간이 사라진다. 일의 흐름이 끊기는 손해가 거기에 더해진다.
  • 고치기도 비싸다. 흩어진 시스템을 맞춤 설정과 스크립트로 이어 붙여 놓았다. 인력이 모자란 플랫폼 팀이 그걸 지킨다.
  • AI로 풀기도 복잡하다. 비동기로 오가는 상호작용, 팀의 작업 흐름, 여러 도구 연동을 함께 조율해야 한다.
03

AI가 문제를 키운다 02:50

AI 덕분에 PR이 더 많아지고 더 커졌다. 그 PR 하나하나에 결함이 있을 수 있다.

발표자는 이를 개발 비용이 오른쪽으로 옮겨 간다shifting to the right고 표현한다. 코드를 쓰는 앞쪽은 싸졌다. 대신 리뷰할 코드가 늘고 프로덕션 장애 가능성이 커져 뒤쪽이 비싸졌다.

선택 1 · 꼼꼼히 리뷰한다 03:20

개발자에게 모든 PR을 주의 깊게 보라고 한다.

결과: 느려진다.

선택 2 · 도장만 찍는다

내용을 제대로 보지 않고 형식적으로 승인한다rubber stamp.

결과: 프로덕션 사고 위험이 커진다.

어느 쪽이든 개발자는 덜 만족하고, 생산성은 기대만큼 오르지 않는다.

04

검증을 맡는 에이전트 03:40

발표자의 답은 "더 많은 AI"다. 검증 단계 전체를 에이전트가 자동으로 처리하는 에이전트 검증agentic validation이다. Gitar가 만들었고, 지금은 Sonar 제품으로도 나온다.

목표 결과물은 바로 머지할 수 있는 green PR이다. green PR은 모든 검사를 통과한 PR이다. 설정에 따라 머지까지 자동으로 끝낸다.

기능하는 일세부
리뷰 04:10PR을 리뷰하고 이슈와 인라인 코멘트를 단다목표는 노이즈 없는 리뷰다. 화면 경험과 지적 내용 모두에서 진짜 중요한 문제만 올린다. 팀 규칙, 커스텀 체크, 커스텀 자동화를 더할 수 있다
머지 차단 04:30해결 안 된 리뷰 지적이 있으면 머지를 막는다설정으로 켠다
CI 실패 분석 04:40CI 실패의 근본 원인을 요약해 올린다flaky test를 특히 잘 잡는다. flaky test를 자동으로 다시 돌리는 규칙은 발표자가 꼽은 인기 기능이다
자동 수정 05:00리뷰 지적과 CI 실패를 고친다특정 이슈만 고치게 할 수 있다. 모든 이슈가 고쳐져 PR이 green이 될 때까지 자동으로 반복하게 할 수도 있다
자동 승인·머지 05:20green PR을 승인하고 머지한다언제 자동으로 승인하고 머지할지 규칙과 조건으로 정한다

이 섹션은 발표자 회사의 제품 소개다. "노이즈가 없다", "flaky test를 잘 잡는다" 같은 주장에 정확도 수치는 나오지 않았다.

05

신뢰만큼 자동화를 연다 05:40

발표자는 사용자들에게서 뚜렷한 흐름을 본다고 말한다. AI가 정확하다는 믿음이 쌓일수록 완전 자동화된 PR 쪽으로 간다.

단계에이전트에게 맡기는 일발표자의 설명
1. 리뷰만 받는다이슈와 코멘트를 단다지적이 정확한지, 실제로 중요한 문제인지 사용자가 확인하며 신뢰를 쌓는다
2. 머지를 막게 한다해결 안 된 지적이 있으면 머지를 막는다발표자의 표현으로 에이전트에게 "이빨을 준다"
3. 자동 수정리뷰 지적과 CI 실패를 고쳐 PR을 green으로 만든다사람이 하던 수정 작업이 빠진다
4. 자동 승인·머지정해 둔 규칙에 맞으면 승인하고 머지한다발표자가 "지금 막 일어나기 시작한" 흥미로운 도약이라고 부른 단계
핵심 자동화는 한 번에 켜지 않는다. 신뢰가 쌓일 때마다 한 단계씩 연다. 발표자는 단계가 올라갈수록 시스템에서 얻는 가치도 커진다고 말한다.
06

모든 PR에서 나오는 통계 06:50

에이전트가 모든 PR을 AI로 처리하니, 새로운 종류의 통계를 뽑을 수 있다. 발표자는 두 가지 예를 들었다.

CI 실패 분류 · 플랫폼 팀용 07:00

개발자가 CI 어디에서 가장 자주 실패하는지 유형별로 묶는다.

  • flaky test 문제: 테스트의 안정성을 높여야 한다
  • 인프라 문제: 인프라를 손봐야 한다
  • 그 밖의 실패

쓰임: 무엇부터 고칠지 정한다.

PR 분류 · 리더십용 07:30

팀 전체에서 머지되는 PR이 어떤 일에 쓰이는지 나눈다.

  • 기능 개발
  • 문제 수정
  • 잡일chores
  • 리팩터링

쓰임: 엔지니어링 시간이 어디로 가는지 본다.

07

내부 구조 07:50

Gitar는 여러 구성 요소로 되어 있다. 발표자가 꼽은 흥미로운 부분은 세 가지다.

구성 요소역할
컨트롤 플레인 control planePR 작업 흐름을 지휘하고 조율하는 층
에이전트 하네스 agent runtime / harness여러 에이전트 실행, 컨텍스트 관리, 메모리 관리, 도구 호출, 외부 연동을 맡는다. 직접 만들었다
LLM 프록시 08:50요청을 여러 모델로 나눠 보낸다. 한 모델이 안 되면 다른 모델로 넘긴다
하네스를 직접 만든 이유 08:20 검증이라는 용도에 맞춰 최적화하기 위해서다. 최적화 대상은 토큰 비용, 정밀도, 커버리지 세 가지다. 발표자는 덕분에 PR당 정해진 가격으로 결과를 보장하면서도 품질을 지킬 수 있다고 말한다.

가격, 정밀도, 커버리지의 실제 수치는 발표에 나오지 않았다.

08

에이전트와 프로그램 분석 09:00

Sonar에 인수된 뒤 Gitar를 SonarQube와 합치는 중이다. SonarQube는 Sonar의 코드 품질·보안 분석 도구다.

방향은 에이전트에 전통적인 프로그램 분석program analysis을 더하는 것이다. 프로그램 분석은 코드의 구조와 값의 흐름을 알고리즘으로 따져 문제를 찾는 기법이다. 발표자가 든 예는 네 가지다.

분석보는 것

데이터 흐름 분석 data flow analysis값이 어디서 만들어져 어디로 흘러가는지
소프트웨어 구성 분석 SCA가져다 쓰는 오픈소스 라이브러리의 알려진 취약점과 라이선스
지금까지에이전트 또는 프로그램 분석각자 따로 검사한다

발표자가 보는 방향둘을 합친다정밀도와 커버리지를 함께 올리고, 가격도 좋게

Sonar의 기존 제품과 새로 인수한 제품을 합치는 이야기다. 회사 제품에 대한 주장이라는 점을 감안하자.

09

효과와 결론 09:30

발표자가 말한 효과는 다음과 같다.

  • 품질과 보안이 좋아진다. AI가 만든 코드에서 특히 그렇다.
  • PR 생성부터 승인과 머지까지 자동으로 가니 배포가 빨라진다.
  • 개발자는 리뷰와 프로덕션 걱정에 쓰는 시간이 줄고, 잡일이 줄어 만족도가 오른다.
  • 플랫폼 팀은 문제를 고치고, 맞춤 설정을 더하고, 통계를 보는 힘을 얻는다. 10:10

효과는 모두 발표자 회사 제품에 대한 주장이다. 고객 사례나 도입 전후 수치는 제시되지 않았다.

발표자의 정리 10:20

  1. PR 검증은 원래 중요했고 AI 시대에는 더 중요하다. 그런데 AI가 검증 단계를 마찰 지점으로 만든다.
  2. PR 생성부터 머지까지 검증을 완전히 자동화하면 그 마찰이 사라진다. AI가 코드를 만드는 속도도 따라갈 수 있다.
  3. 에이전트 검증과 알고리즘 기반 프로그램 분석을 합치면 어느 한쪽만 쓸 때보다 낫다.
정리자 메모: 발표가 답하지 않은 것
  • 제목은 "누가 검증하나"를 묻고, 답은 "에이전트"다. 리뷰하고 고치는 에이전트의 판단을 누가 다시 확인하는지는 다루지 않았다.
  • 자동 승인·머지 규칙에 어떤 조건을 넣는지 구체적인 예가 없다.
  • 리뷰 정확도, 거짓 경보 비율, 자동 머지 뒤 사고율 같은 수치가 없다.
10

핵심 정리

  1. 검증 단계는 CI와 코드 리뷰다. 보안, 컴플라이언스, 코드 품질 관문을 한곳에서 지킨다.
  2. 모든 변경이 지나는 길목이라 빠를수록 좋다. 하지만 조직이 커질수록 빌드는 길어지고 리뷰는 비동기로 늘어진다.
  3. 검증 실패는 몇 시간에서 며칠짜리 아우터 루프를 만든다. 개발자 시간과 집중을 함께 잃는다.
  4. 이 단계는 흩어진 도구를 설정과 스크립트로 엮어 놓은 것이라 고치기도 비싸다.
  5. AI로 PR이 많아지고 커지면서 비용이 리뷰와 프로덕션 쪽으로 옮겨 갔다.
  6. 꼼꼼히 리뷰하면 느려지고, 도장만 찍으면 사고가 난다.
  7. 에이전트 검증은 리뷰 → CI 실패 분석 → 자동 수정 반복 → 규칙에 따른 자동 승인·머지까지 맡는다.
  8. 자동화는 신뢰가 쌓이는 만큼 한 단계씩 연다.
  9. 모든 PR을 AI가 보면 CI 실패 유형, PR 유형 같은 통계가 나온다.
  10. 검증 전용 하네스로 비용·정밀도·커버리지를 맞추고, 다음은 에이전트와 프로그램 분석의 결합이다.
11

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 중앙 검증 단계는 무엇 두 가지로 이루어지나?
CI와 코드 리뷰. 보안, 컴플라이언스, 코드 품질 관문을 한곳에서 지킨다.
Q2조직이 커질수록 검증 단계가 느려지는 이유 두 가지는?
빌드와 작업이 길어진다. 여러 지역과 팀에 걸친 리뷰가 비동기로 늘어진다.
Q3검증 단계의 실패가 비싼 이유는?
몇 시간에서 며칠 단위의 아우터 루프가 생긴다. 개발자 시간을 잃고, 일의 흐름도 끊긴다.
Q4AI가 PR을 늘리면서 팀이 마주하는 두 가지 나쁜 선택은?
모든 PR을 꼼꼼히 리뷰해 느려지거나, 도장만 찍고 프로덕션 사고 위험을 지는 것. 어느 쪽이든 개발자 만족도와 생산성이 떨어진다.
Q5발표자가 리뷰 기능에서 가장 신경 썼다고 한 점은?
노이즈 없는 리뷰. 화면 경험과 지적 내용 모두에서 진짜 중요한 문제만 올리려 했다.
Q6CI 실패 분석에서 특히 잘 잡는 것과, 발표자가 꼽은 인기 기능은?
flaky test를 잘 잡는다. 인기 기능은 flaky test를 자동으로 다시 돌리는 규칙이다.
Q7자동 수정을 쓰는 두 가지 방식은?
특정 이슈만 고치게 하거나, 모든 이슈가 고쳐져 PR이 green이 될 때까지 자동으로 반복하게 한다.
Q8사용자들이 자동화를 여는 순서는?
리뷰만 받기 → 머지 차단 → 자동 수정 → 규칙에 따른 자동 승인·머지. 신뢰가 쌓일 때마다 한 단계씩 연다.
Q9AI로 모든 PR을 처리해서 얻는 통계 두 가지와, 각각 누구에게 쓸모 있나?
CI 실패 분류는 플랫폼 팀에게, PR 분류(기능 개발, 문제 수정, 잡일, 리팩터링)는 리더십에게 쓸모 있다.
Q10Gitar가 하네스를 직접 만든 이유는?
검증 용도에 맞춰 토큰 비용, 정밀도, 커버리지를 최적화하려고. 발표자는 덕분에 PR당 정해진 가격으로 결과를 보장할 수 있다고 말한다.
Q11SonarQube 통합에서 에이전트와 합치려는 프로그램 분석 네 가지는?
오염 분석, 제어 흐름 분석, 데이터 흐름 분석, 소프트웨어 구성 분석(SCA).

용어 정리

용어뜻
CIContinuous integration. 코드를 올릴 때마다 자동으로 빌드하고 테스트하는 장치
품질 관문Quality gate. 통과해야 다음 단계로 갈 수 있는 기준. 보안, 컴플라이언스, 코드 품질 등
크리티컬 패스Critical path. 전체 완료 시간을 결정하는 단계들의 줄. 여기가 느리면 전체가 느리다
아우터 루프Outer loop. 코드를 올린 뒤 CI, 리뷰, 수정, 재제출을 도는 바깥쪽 되돌이. 몇 시간에서 며칠 단위
플랫폼 팀개발 인프라, 빌드, 배포 도구를 맡아 다른 개발 팀을 지원하는 팀
러버 스탬프Rubber stamp. 내용을 제대로 보지 않고 형식적으로 승인하는 것
비용의 오른쪽 이동Shift right. 개발 비용이 코드 작성 쪽에서 리뷰와 운영 쪽으로 옮겨 가는 것
green PR모든 검사를 통과해 바로 머지할 수 있는 PR
flaky test코드가 그대로인데도 통과와 실패가 오락가락하는 테스트
근본 원인Root cause. 증상이 아니라 실패를 일으킨 진짜 원인
에이전트 검증Agentic validation. 리뷰, CI 실패 분석, 수정, 머지 같은 검증 단계를 에이전트가 자동으로 처리하는 방식
컨트롤 플레인Control plane. 작업 흐름을 지휘하고 조율하는 층
하네스모델을 감싸 실행, 컨텍스트, 메모리, 도구 호출을 맡는 실행 틀
LLM 프록시모델 요청을 여러 모델로 나눠 보내고, 한 모델이 안 되면 다른 모델로 넘기는 중간층
페일오버Failover. 한쪽이 실패하면 자동으로 다른 쪽으로 넘기는 것
정밀도 / 커버리지Precision / coverage. 정밀도는 지적 중 진짜 문제의 비율. 커버리지는 진짜 문제를 얼마나 빠짐없이 잡는가
프로그램 분석Program analysis. 코드의 구조와 값의 흐름을 알고리즘으로 따져 문제를 찾는 기법
오염 분석Taint analysis. 믿을 수 없는 입력이 위험한 곳까지 흘러가는지 추적하는 분석
SCASoftware composition analysis. 가져다 쓰는 오픈소스 라이브러리의 취약점과 라이선스를 점검하는 분석
SonarQubeSonar의 코드 품질·보안 분석 도구
