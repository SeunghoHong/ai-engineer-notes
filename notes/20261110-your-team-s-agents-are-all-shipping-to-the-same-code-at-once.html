팀의 에이전트가 한꺼번에 같은 코드로 몰려올 때

사람 여럿과 에이전트 여럿이 같은 코드와 같은 티켓 보드에서 동시에 일하면 머지 충돌과 리뷰 대기가 폭발한다. 발표자는 동시 작업을 예외가 아니라 기본으로 놓고, 일을 나누는 법과 머지하는 법과 사람이 결정하는 법을 새로 짜자고 제안한다.

원본 영상: Your Team's Agents Are All Shipping to the Same Code at Once 발표: Patrick Debois (Tessl, 'DevOps'라는 말을 처음 퍼뜨린 사람으로 알려짐)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다(Tesla → Tessl, ASD → AST). mm:ss는 영상 위치다.

3분 요약
  1. 팀 단위로 에이전트를 돌리면 PR이 10배 가까이 는다(발표자의 체감). 충돌, 재테스트, 대기, CI 비용도 함께 는다.
  2. 출발점은 생각을 뒤집는 것이다. 동시 작업을 예외가 아니라 기본으로 놓는다. 지속적 배포에서 동시 배포로 간다.
  3. 코딩 전에 일을 나누고 찜한다. 에이전트마다 작업 환경을 따로 떼어 준다.
  4. 머지는 더 똑똑해진다. 에이전트가 충돌을 풀고, 의도 충돌을 확인하고, 투기적 머지 트레인으로 줄을 빠르게 한다.
  5. 사람 쪽에서는 에이전트를 팀 대화에 불러 티켓을 함께 다듬는다. 엔지니어가 아닌 사람도 같은 파이프라인을 쓴다.
  6. 에이전트는 선택지로 묻고, 결정은 공유 장부에 남긴다. 리뷰는 작게, 증거를 붙여, 위험에 맞춰 한다.
  7. 자동화할 수 있는 건 자동화하고 예외만 사람에게 보낸다. 이 전체를 돌보는 팩토리 팀이 생긴다.
01

솔로 팩토리에서 멀티플레이어 팩토리로 00:00

소프트웨어 배포 파이프라인 delivery pipeline은 AI 이전에도 있었다. 빌드, 테스트, 릴리스 대기, main 브랜치 머지가 차례로 이어진다. 한 줄로 흐르는 직렬 흐름이다. 이 흐름 덕분에 배포가 자동화되고 튼튼해졌다.

요즘은 각자 노트북에서 코딩 에이전트로 작은 공장을 돌린다. 발표자는 이를 솔로 팩토리 solo factory라고 부른다. 소프트웨어 팩토리는 에이전트와 자동화로 코드 작성부터 배포까지 돌리는 작업 라인이다.

솔로 팩토리에서도 에이전트는 여럿이다. 하지만 결정과 머지는 여전히 사람이 한다. 무엇을 하고 있는지 기억하는 일도 사람 몫이다. 사람이 한가운데 앉아 모든 걸 붙잡고 있는 구조다.

단계모습
솔로 팩토리각자 자기 노트북에서 에이전트 여럿을 돌린다
설정 공유컨텍스트, 스킬, 루프 같은 자기 설정을 팀과 나눈다. 발표자는 지금 많은 팩토리가 이 단계라고 본다
멀티플레이어 팩토리여러 사람과 에이전트가 같은 티켓 보드, 같은 코드베이스에서 동시에 일한다

발표는 마지막 단계를 다룬다. 갈등은 두 곳에서 생긴다. 01:30

1부 · 코드

모두가 main에 머지하려 한다. 에이전트들이 같은 코드베이스에 동시에 변경을 밀어 넣는다.

2부 · 사람

여러 사람이 한 보드에 있다. 사람과 에이전트가 같은 티켓 보드에서 함께 일해야 한다.

02

PR이 10배가 되면 02:00

멀티플레이어 팩토리를 켜면 가장 먼저 PR pull request이 는다. 발표자의 체감으로는 10배 가까이다. 변경이 많이 나오니 생산성은 오른다. 동시에 긴장도 쌓인다.

  • 충돌: 머지가 많아지니 서로 겹치지 않는지 확인할 일이 는다.
  • 제자리걸음: 한 에이전트가 바꾼 걸 다른 에이전트가 되돌리고, 그걸 또 바꾼다.
  • 대기 02:40: 변경 하나가 머지되면 나머지 PR이 모두 리베이스 rebase하고 테스트를 다시 돌린다. 리베이스는 내 변경을 최신 main 위로 옮겨 다시 쌓는 일이다. 릴리스를 기다리는 시간이 길어진다.
  • CI 비용: 테스트를 계속 다시 돌리니 CI/CD 시스템이 훨씬 느려지고 비용도 는다.

PR 대기열에는 기능만 쌓이지 않는다. 03:00

대기열에 쌓이는 것내용
기능새로 만든 기능
에이전트 사고에이전트가 일으킨 문제를 고치는 변경
팩토리 유지보수팩토리에서 쓰는 스킬과 루프를 고치는 변경

이 모두를 사람이 승인해야 한다.

동시 작업을 기본값으로 03:20

발표자는 여기서 생각을 뒤집자고 한다. 지금은 동시 작업이 예외처럼 다뤄진다. 이를 일상으로 받아들이고, 처음부터 그에 맞춰 설계하자는 것이다.

03

일을 나누고 찜하기 03:50

에이전트를 그냥 병렬로 많이 돌리는 것으로는 부족하다. 사람 팀이 일을 나누듯 에이전트에게도 일을 나눠 주면 덜 부딪친다.

나누는 방법예
영역별로한 에이전트는 인증, 다른 에이전트는 결제를 맡는다
코드 구조를 보고AST abstract syntax tree를 보고 어디가 잘 떨어지는지 정한다. AST는 코드 구조를 나무 모양으로 나타낸 것이다
더 잘게파일, 함수, 심지어 같은 파일 안의 특정 편집 위치까지 나눈다

코딩을 시작하기 전에 하는 일이다. 변경을 더 잘 계획하는 방법이다.

티켓을 찜하고 변경을 알린다 04:50

계획을 실행할 때는 스크럼 보드처럼 움직인다. 에이전트가 "이 티켓은 내가 한다"고 찜 claim한다. 그러면 다른 에이전트가 같은 티켓에 끼어들지 못한다.

에이전트는 어떤 파일을 어떻게 바꿀지도 미리 알린다 announce. 다른 에이전트는 이를 보고 계획 단계와 실행 단계에서 겹치지 않게 피한다.

04

에이전트마다 따로 떼어 주기 05:20

실행 중에 서로 방해하지 않도록 많은 사람이 워크트리 worktree를 쓴다. 워크트리는 한 저장소에서 브랜치마다 작업 폴더를 따로 여는 Git 기능이다.

발표자는 이걸 더 넓게 보자고 한다. 에이전트마다 자기만의 세상을 떼어 주는 것이다.

따로 주는 것내용
머신에이전트 전용 실행 환경
컨텍스트에이전트가 볼 정보 중 자기 몫
API모킹 mock한 자기 버전. 모킹은 진짜 시스템 대신 흉내 내는 가짜를 세우는 것이다
데이터베이스자기 스냅샷과 자기 테스트 데이터
바깥 세계디지털 트윈 digital twin과 목. 디지털 트윈은 실제 외부 시스템을 본뜬 복제본이다

목표는 에이전트가 바깥 세계에 영향을 주지 않고 일하게 하는 것이다.

05

부딪쳤을 때 06:00

그래도 두 에이전트가 작업 중에 부딪칠 수 있다. 전략은 세 가지다.

전략하는 일

재협상"너는 이걸, 나는 저걸" 하고 실행 도중에 계획을 고친다 renegotiation

머지 충돌을 에이전트가 푼다 06:20

지금 Git에서 충돌이 나면 보통 다시 돌려서 이번엔 합쳐지는지 본다. 발표자는 이 일을 에이전트가 점점 더 똑똑하게 맡을 수 있다고 본다. 단계로 나누면 이렇다.

  1. 다시 돌려 본다. 지금 PR에서 흔히 하는 방식이다.
  2. 에이전트에게 맡긴다. 합쳐지는지 확인하는 일을 에이전트가 대신한다.
  3. 함수 단위로 합친다. 코드 줄이 아니라 함수 단위로 보고 합친다.
  4. 충돌을 고친다. 에이전트가 머지 충돌을 직접 고쳐서 사람이 다시 손대지 않는다.
  5. 미리 맞춘다. 다른 에이전트가 곧 바꿀 부분을 내다보고 내 코드를 먼저 맞춘다. 07:00

발표자는 이것을 변경을 직렬이 아니라 동시성으로 생각하기라고 정리한다.

06

코드는 안 부딪쳐도 의도가 부딪친다 07:20

에이전트는 코드 머지에 잘 맞춰져 있다. 그런데 두 변경이 동시에 들어오면 코드가 아닌 곳에서 문제가 생긴다. 발표자가 든 예다.

PR A

송장 합계를 계산하는 함수를 바꾼다. 이제 달러가 아니라 센트 단위로 돌려준다.

PR B

같은 때 보고서 출력을 바꾼다. 보고서는 센트 단위 값을 원하지 않는다.

두 PR은 충돌 없이 합쳐지고 테스트도 통과한다. 하지만 두 변경이 기대하는 의미가 다르다. 코드 충돌이 아니라 의도 충돌이다.

예시로 풀면 (발표에 없는 숫자) 합계가 19.99달러인 송장이 있다고 하자. PR A가 들어간 뒤 함수는 1999를 돌려준다. PR B의 보고서가 이 값을 달러로 읽으면 1,999달러가 찍힌다. 테스트가 두 변경을 함께 보지 않으면 이대로 나간다.

발표자의 제안은 이렇다. 여러 변경이 머지될 때 그 의도가 여전히 서로 맞는지 에이전트가 확인한다. 어긋나면 사람에게 경고하거나 PR을 고친다.

07

투기적 머지 트레인 08:20

머지 트레인 merge train은 머지할 PR을 줄 세워 하나씩 main에 합치는 장치다. 머지 큐 merge queue라고도 한다.

문제는 하나가 제대로 합쳐지지 않을 때다. 그러면 보통 나머지 PR이 모두 리베이스하고 일을 다시 한다.

발표자가 소개하는 개선책은 투기적 머지 트레인 speculative merge train이다. 들어오는 PR을 보고 서로 맞는 것끼리 미리 짝지어 확인해 둔다. 하나가 떨어져도 나머지 맞는 것들은 그대로 지나간다. 그래서 줄 전체가 빨라진다.

예시: PR A, B, C가 줄을 섰고 B가 실패한다흐름
보통 머지 트레인A가 들어간다. B를 합치려다 실패한다. C는 바뀐 main에 맞춰 리베이스하고 테스트를 다시 돌린 뒤에야 들어간다
투기적 머지 트레인A, B, C가 서로 맞는지 미리 짝지어 확인해 둔다. B가 떨어져도 A와 C는 이미 확인된 조합이라 바로 들어간다

위 표는 발표에 없는 예시다.

에이전트를 위한 새 인프라 층 09:10

나누기, 충돌 처리, 머지, 리뷰, 계획에 이런 새 전략이 생기고 있다. 발표자는 이를 보고 새로운 개발 인프라 층이 생긴다고 본다. 업체들도 이쪽으로 움직이고 있다.

  • 머지를 지금과 다르게 처리하는 도구
  • 분석 도구
  • 더 나은 계획 도구
  • 그 밖의 모든 단계에 맞춘 더 나은 도구

발표자가 보기에 지금 팩토리 다수는 "꾸며진 루프" glorified loops에 가깝다. 하지만 동시성은 앞으로 더 늘어난다.

08

한 보드, 한 대화 09:40

이제 반대쪽, 사람이 함께 일하는 이야기다. 멀티플레이어 팩토리에서는 모두 한 작업 보드를 쓴다. 어떤 변경이 오고 어떤 일이 진행 중인지 모두가 본다.

솔로 팩토리에서는 이걸 혼자 했다. 모두가 함께 보는 중앙 보드가 없었다.

에이전트가 많아지면 사람을 부르는 횟수도 는다. 그러니 에이전트가 사람의 주의를 덜 빼앗게 만들어야 한다. 10:00

에이전트를 대화에 부른다 10:20

흥미로운 변화는 에이전트가 팀 채팅에 들어온다는 점이다. 사람이 에이전트에게 프롬프트를 쓰는 게 아니다. 사람들이 나누는 대화에 에이전트를 끌어들인다.

프롬프트한 사람이 에이전트에게 지시한다단서는 그 한 사람에게서만 온다
→
대화에 부르기에이전트가 팀 대화에 들어온다팀원 여럿의 말에서 단서를 모은다
  • 에이전트가 모든 입력을 모아 티켓을 다듬는다.
  • 에이전트끼리의 적대적 리뷰 adversarial review에 더해, 사람 여럿의 의견이 한 티켓에 모인다. 적대적 리뷰는 일부러 흠을 찾게 시킨 에이전트의 검토다.
  • 에이전트가 먼저 질문을 던진다. 무엇을 테스트할지, 무엇을 해야 하는지, 요구사항이 무엇인지 묻는다. 사람이 매번 처음부터 설명하지 않아도 된다. 11:00

그러면 티켓은 코딩 에이전트의 플랜 모드 plan mode와 비슷해진다. 플랜 모드는 코딩 전에 에이전트가 계획을 먼저 세워 보여 주는 방식이다. 다른 점은 그 계획이 보드 위에서 팀 전체에 공유된다는 것이다.

핵심 정리

  1. 솔로 팩토리 → 설정 공유 → 멀티플레이어 팩토리. 갈등은 코드(모두 main에 머지)와 사람(한 보드에서 협업) 두 곳에서 생긴다.
  2. PR이 10배 가까이 늘면(발표자의 체감) 충돌, 되돌리기 반복, 리베이스·재테스트 대기, CI 비용이 함께 는다.
  3. 동시 배포: 동시 작업을 예외가 아니라 기본 상황으로 놓고 설계한다.
  4. 코딩 전에 일을 영역·파일·함수 단위로 나누고, 티켓을 찜하고, 바꿀 파일을 알린다.
  5. 에이전트마다 워크트리, 컨텍스트, 모킹한 API, DB 스냅샷, 디지털 트윈을 따로 준다.
  6. 작업 중 충돌은 기다리기, 재시도, 재협상으로 푼다. 머지 충돌은 에이전트가 함수 단위로 풀고, 다가올 변경을 미리 반영한다.
  7. 코드가 안 부딪쳐도 의도는 부딪칠 수 있다. 투기적 머지 트레인은 실패한 PR 하나가 줄 전체를 멈추지 않게 한다.
  8. 에이전트를 팀 대화에 불러 티켓을 다듬으면 티켓이 공유된 플랜 모드가 된다. 엔지니어가 아닌 사람도 같은 파이프라인을 쓴다.
  9. 에이전트는 선택지로 묻고, 결정은 공유 장부에 남겨 추적하고 조회한다. 에이전트가 막히면 사람이 같은 맥락으로 들어가 돕는다.
  10. 리뷰는 작게, 증거로, 위험에 맞춰 한다. 자동화하고 예외만 사람에게 보내며, 팩토리 팀이 이 전체를 돌본다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1솔로 팩토리와 멀티플레이어 팩토리는 무엇이 다른가?
솔로 팩토리는 한 사람이 자기 노트북에서 에이전트 여럿을 돌린다. 결정, 머지, 기억은 그 사람이 혼자 맡는다. 멀티플레이어 팩토리는 여러 사람과 에이전트가 같은 보드, 같은 코드베이스에서 동시에 일한다.
Q2PR이 크게 늘면 생기는 문제를 세 가지 이상 들면?
머지 충돌, 에이전트끼리 서로 되돌리기, 머지마다 다른 PR의 리베이스와 재테스트로 인한 대기, CI/CD가 느려지고 비용이 느는 것. 대기열에는 에이전트 사고 처리와 팩토리 유지보수도 쌓인다.
Q3"동시 배포"는 무엇을 뒤집는 생각인가?
동시 작업을 예외로 다루던 것을 뒤집는다. 사람과 에이전트가 같은 코드베이스에서 동시에 일하는 것을 기본 상황으로 놓고 처음부터 그에 맞춰 설계한다.
Q4작업을 시작하기 전에 겹침을 줄이는 두 방법은?
일을 영역, 파일, 함수 단위로 나눈다(AST로 잘 떨어지는 곳을 찾는다). 그리고 에이전트가 티켓을 찜하고, 바꿀 파일과 변경을 미리 알린다.
Q5워크트리 말고 에이전트마다 따로 줄 수 있는 것은?
전용 머신, 자기 몫의 컨텍스트, 모킹한 API, 데이터베이스 스냅샷과 테스트 데이터, 바깥 세계를 흉내 내는 디지털 트윈과 목.
Q6송장 합계 예에서 두 PR은 왜 문제인가?
코드 충돌도 없고 테스트도 통과한다. 하지만 한쪽은 합계를 센트로 바꿨고 다른 쪽 보고서는 센트 값을 원하지 않는다. 의도가 부딪친다. 에이전트가 머지되는 변경들의 의도가 맞는지 확인해 경고하거나 PR을 고쳐야 한다.
Q7투기적 머지 트레인은 왜 빠른가?
들어오는 PR들이 서로 맞는지 미리 짝지어 확인해 둔다. 하나가 실패해도 나머지 맞는 PR은 다시 리베이스하고 기다리지 않고 바로 지나간다.
Q8에이전트를 팀 대화에 부르면 티켓은 어떻게 바뀌나?
에이전트가 팀원 여럿의 말에서 단서를 모으고, 테스트와 요구사항을 질문으로 확인하며 티켓을 다듬는다. 티켓은 보드 위에서 공유되는 플랜 모드처럼 된다.
Q9Helix ML의 아이디어는 무엇을 해결하나?
에이전트가 막혔을 때다. 그 맥락과 파일 그대로 IDE를 열어 사람이 들어가 실험하고 결정한 뒤 다시 에이전트에게 넘긴다. 빠른 개인 작업과 팩토리 방식의 중간 지점이다.
Q10결정 장부는 무엇에 쓰나?
사람이 내린 결정을 공유 로그에 모은다. 에이전트와 사람이 찾아볼 수 있고, 누가 언제 무엇을 정했는지 추적하며, 다음 세션에서 그 맥락을 조회한다.
Q11"코드를 안 본다"는 사람에게 발표자가 되묻는 것과, 대신 내놓는 방식은?
"프로덕션에서 영향이 얼마인가?"를 묻는다. 위험에 따라 리뷰 강도를 고른다. 문서는 그대로 진행하고, 중간은 점진적 배포로 지켜보고, 인증처럼 영향이 큰 곳은 사람이 더 본다. 그리고 복원과 롤백을 싸게 만든다.
Q12팩토리 팀은 무엇을 맡나?
플랫폼 팀이 인프라를 맡았듯 코딩 에이전트의 작업 바탕을 맡는다. 스킬의 주인을 정하고, 컨텍스트를 최신으로 유지하고, 연결을 챙기고, 팩토리 자체를 유지보수하고 모니터링한다.

용어 정리

용어뜻
소프트웨어 팩토리Software factory. 에이전트와 자동화로 코드 작성부터 배포까지 돌리는 작업 라인
솔로 팩토리Solo factory. 한 사람이 자기 노트북에서 에이전트 여럿을 돌리는 팩토리. 결정과 머지는 혼자 맡는다
멀티플레이어 팩토리Multiplayer factory. 여러 사람과 에이전트가 같은 보드, 같은 코드베이스에서 동시에 일하는 팩토리
배포 파이프라인Delivery pipeline. 빌드, 테스트, 릴리스, 머지를 자동으로 잇는 흐름
PRPull request. 내 변경을 공용 브랜치에 합쳐 달라고 요청하는 단위
리베이스Rebase. 내 변경을 최신 main 위로 옮겨 다시 쌓는 일
CI/CD변경마다 자동으로 빌드·테스트하고(CI) 배포까지 하는(CD) 시스템
지속적 배포Continuous delivery. 변경을 자주, 한 줄로 차례차례 내보내는 방식
동시 배포Concurrent delivery. 사람과 에이전트가 같은 코드에서 동시에 일하는 것을 기본으로 놓고 설계하는 방식. 발표자가 쓰는 말
스킬 · 루프 · 컨텍스트스킬: 에이전트가 불러 쓰는 작업 지침 묶음. 루프: 에이전트가 반복해서 도는 작업 흐름. 컨텍스트: 에이전트가 일할 때 보는 정보
ASTAbstract syntax tree. 코드 구조를 나무 모양으로 나타낸 것
찜하기Claim. 에이전트가 티켓을 맡겠다고 표시해 다른 에이전트가 끼어들지 못하게 하는 것
워크트리Worktree. 한 저장소에서 브랜치마다 작업 폴더를 따로 여는 Git 기능
모킹Mock. 진짜 시스템 대신 흉내 내는 가짜를 세우는 것
디지털 트윈Digital twin. 실제 외부 시스템을 본뜬 복제본
재협상Renegotiation. 실행 도중에 에이전트끼리 일을 다시 나누는 것
의도 충돌코드는 충돌하지 않지만 두 변경이 기대하는 의미가 어긋나는 것
머지 트레인Merge train, merge queue. 머지할 PR을 줄 세워 하나씩 합치는 장치
투기적 머지 트레인Speculative merge train. PR 조합이 서로 맞는지 미리 확인해, 하나가 실패해도 나머지가 바로 지나가게 하는 머지 트레인
적대적 리뷰Adversarial review. 일부러 흠을 찾도록 시킨 에이전트의 검토
플랜 모드Plan mode. 코딩 전에 에이전트가 계획을 먼저 세워 보여 주는 방식
바이브 코딩Vibe coding. 코드를 자세히 보지 않고 AI에게 말로 시켜 만드는 방식
결정 장부Decision ledger, decision log. 누가 언제 무엇을 정했는지 모아 두는 공유 기록
점진적 배포Gradual release. 일부에게 먼저 내보내고 지켜보며 범위를 넓히는 배포
롤백Rollback. 문제가 생긴 배포를 이전 버전으로 되돌리는 것
플랫폼 팀개발팀이 쓰는 공용 인프라(Kubernetes, 클러스터, 클라우드)를 맡는 팀
팩토리 팀Factory team. 코딩 에이전트, 스킬, 컨텍스트, 팩토리 자체를 맡아 돌보는 팀. 발표자가 쓰는 말
개인 에이전트Personal agent. 한 사람을 대신해 보드에서 일하고, 결정하고, 다른 에이전트에 답하는 에이전트
