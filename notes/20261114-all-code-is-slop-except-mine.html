에이전트의 슬롭을 막는 코드베이스

에이전트가 한 달에 PR 수천 개를 내도 품질을 지키려면, 규칙 문서보다 코드베이스와 검증에 먼저 투자해야 한다. 에이전트를 고칠 때마다 그 교정을 린트 규칙 같은 검사로 바꾸면, 사람이 리뷰할 거리가 점점 줄고 엉성한 코드(슬롭slop)도 줄어든다.

원본 영상: All Code Is Slop (Except Mine) 발표: Lauren Tan (SpaceXSI에서 Grokbot(추정) 개발. 발표에서는 'Potato'라는 별명으로 소개)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 제품 이름이 Grokbot, Graph Bot, Grabot, Growth Bot 등으로 매번 다르게 들려서 Grokbot(추정)으로 통일했다. 자막의 Brett Taylor는 Bret Taylor로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 발표자는 지난달 혼자 PR 3,000개를 배포했다. 비결은 맹목적인 믿음이 아니라 에이전트 환경에 투자해서 얻은 신뢰다.
  2. 투자 순서는 코드 자체 → 결정적 검사 → 검증 → 글(규칙 문서)이다. 규칙 문서는 마지막에 조금만 쓴다.
  3. 에이전트는 코드베이스를 보고 따라 한다. 그래서 나쁜 패턴은 복제된다. 코드베이스를 깨끗하게 지켜야 한다.
  4. 에이전트를 고칠 때마다 규칙 문서에 한 줄을 더하지 말고 린트 규칙이나 API 설계로 그 실수를 못 하게 만든다. 예: 제품 코드에서 useEffect 금지.
  5. 주석의 99%를 금지했다. 주석은 금방 낡고, 강제할 수 없고, 에이전트가 변명을 적는 곳이 된다.
  6. 사람의 리뷰는 검증 산출물(영상, 스크린샷, 다이어그램, 형식 검증 결과)을 보는 일로 줄었다. 토큰 대부분은 검증에 쓴다.
  7. 발표자가 밝힌 결과: 팀 PR 월 11,000개, 되돌림 약 0.5%, 성능은 오히려 개선. 자동화는 이 기반을 다진 다음에 한다.
01

PR 3,000개와 신뢰 00:40

발표자는 지난달 혼자 PR 3,000개를 프로덕션에 배포했다고 말한다.

에이전트가 나오기 전에는 작업량이 큰 관심사가 아니었다. 예외는 엄청나게 생산적인 소수였다. 발표자의 이전 회사에서는 이런 사람을 '코딩 기계'coding machine라고 불렀다. 발표자가 든 예는 Google Maps를 주말 동안 통째로 다시 썼다는 Bret Taylor다.

발표자는 이제 에이전트 덕분에 누구나 코딩 기계가 될 수 있다고 본다.

발표자의 핵심 주장 01:10 이제 소프트웨어 엔지니어의 일은 생산성을 크게 늘리면서도 코드 품질을 지키거나 더 높이는 방법을 찾는 것이다.

이런 체계를 '소프트웨어 공장'software factory이라 부르는 사람도 있다. 발표자는 더 단순하게 신뢰의 문제로 본다.

맹목적으로 믿으라는 말이 아니다. 에이전트가 일하는 환경에 투자해서, 에이전트가 옳은 일을 할 거라고 믿을 수 있게 만들라는 뜻이다.

발표자는 여기까지 오는 데 6개월이 걸렸다. 지금은 PR 수천 개를 내고, 그중 상당수는 자는 동안 나간다. 발표자는 다른 사람은 이보다 훨씬 빨리 도달할 수 있다고 말한다.

02

어디에 시간을 쓰나: 역피라미드 02:00

신뢰가 낮은 환경에서 높은 환경으로 가려면, 에이전트 환경의 어디에 시간을 써야 할까. 발표자는 위가 넓은 역피라미드로 설명한다. 먼저 나오는 층에 시간을 더 쓰고, 마지막 층인 글은 조금만 얹는다.

층예하는 일
1. 코드 자체좋은 API 설계, 아키텍처, 리팩터링잘못된 길을 처음부터 없앤다
2. 정적 검사와 테스트린트 규칙, 타입 시스템, 컴파일러, 여러 종류의 테스트규칙을 어기면 바로 실패한다
3. 검증런타임 검증, 형식 검증버그를 찾고, 에이전트가 의도를 이해했는지 확인한다
4. 글규칙, 스킬, AGENTS.md판단이 필요한 것만 맡는다

위의 두 층은 결정적deterministic이다. 같은 코드를 넣으면 늘 같은 결과가 나온다는 뜻이다. 이 두 층으로 에이전트가 할 수 있는 일을 좁히고, 기본으로 옳은 일을 하게 만든다.

검증 층은 버그를 찾는다. 시스템이 언제나 지켜야 할 성질(불변식invariant)이 지켜지는지도 확인한다.

규칙 문서 같은 글은 사람의 판단이 필요한 것에만 쓴다. 발표자는 그다음 순서대로 코드베이스부터 이야기한다.

03

코드베이스는 정원이다 03:00

에이전트의 출력은 입력에 따라 달라진다. 그리고 코드베이스는 에이전트가 받는 가장 큰 입력 중 하나다.

발표자의 원칙 에이전트를 교정할 때마다, 규칙 문서나 AGENTS.md에 한 줄을 더하기 전에 결정적 검사로 만들 수 있는지 먼저 생각한다. 코드에 들어간 규칙은 매번 똑같이 작동해서 더 믿을 수 있다.

PR이 흐르는 물처럼 들어온다 03:30

2024년에 발표자는 출근하면 동료가 쓴 PR 3개를 리뷰했다. 지금은 그 숫자가 300개쯤이다.

엔지니어 한 명이 에이전트 수백, 수천 개로 이뤄진 팀이 된 셈이다. 발표자는 코드가 너무 빨리 들어와서 끊기지 않는 흐름처럼, 살아 있는 것처럼 느껴진다고 말한다.

이 비유에서 코드베이스의 제약과 안전장치는 콘크리트 기초다. 에이전트가 쓰는 새 코드는 그 기초를 따라 자란다. 그래서 발표자는 소프트웨어 엔지니어의 일이 점점 정원 가꾸기를 닮아 간다고 본다.

잡초는 퍼진다 04:20 에이전트는 코드베이스에 있는 것을 '이 코드베이스의 정해진 패턴'으로 보고 따라 한다. 임시방편, 안티패턴anti-pattern, 폐기 예정 코드, 기술 부채tech debt도 그대로 복제된다. 정원의 잡초처럼 어느새 곳곳에 퍼진다. 에이전트가 늘 좋은 코드만 베끼도록 코드베이스를 최대한 깨끗하게 지켜야 한다.
04

잘 쓰기 어려운 API는 막는다 05:00

Dune은 발표자의 팀이 Grokbot(추정)을 만들며 직접 만든 클라이언트 프레임워크다. 발표자는 'Electron 앱을 위한 Next.js' 정도로 생각하면 된다고 설명한다. 기술적으로 특별한 것은 없다고 한다.

Dune의 핵심은 제약과 린트 규칙lint rule이다. 데스크톱 앱을 만들며 배운 교훈을 규칙으로 담았다.

그 교훈 하나는 이렇다. 잘 쓰려면 미묘한 판단이 필요한 것은 슬롭으로 이어지기 쉽다.

예: React의 useEffect 05:30

useEffect는 React에서 화면을 그린 뒤 부수 효과를 실행하는 훅이다. 쓸 곳이 있지만 자주 잘못 쓰인다. "useEffect를 쓰려면 박사 학위가 필요하다"는 농담이 있을 정도다. 에이전트도 이걸 잘 못 쓴다.

팀의 해법은 제품 코드에서 useEffect를 아예 금지하는 것이다. Dune API 안쪽의 몇 곳에서만 쓸 수 있다.

그 결과 이 문제는 종류째 사라졌다. 코드 리뷰에서 다시 잡을 필요가 없다.

05

디렉토리 구조로 경계를 긋는다 06:10

두 번째 패턴은 디렉토리 구조로 맥락을 주는 것이다.

Cursor도 Electron 앱이다. 발표자는 Cursor에서 이런 안티패턴을 봤다. 에이전트가 main 쪽 코드를 renderer 쪽으로 자주 import했다. 그러면 화면을 그리는 쪽이 오래 붙잡히는 작업(롱 태스크long task)이 생기고 화면이 버벅였다(jank).

Grokbot과 Dune 앱에서는 이걸 아주 뻔한 규칙으로 만들었다. 최상위에 electron-renderer와 electron-main 디렉토리를 둔다. 둘 사이의 import는 의존성 그래프 분석기와 린트 규칙으로 막는다.

설정은 간단하다. 그래도 코드 리뷰에서 신경 쓸 일이 하나 줄어든다.

디렉토리 이름은 자막에서 "Electron renderer", "Electron main"으로 들린 것을 옮겼다. 실제 표기는 다를 수 있다.

예시: 두 규칙을 린트로 쓰면

발표에 나온 코드가 아니다. ESLint 기본 규칙 no-restricted-imports로 쓴 예시다. 에러 메시지에 금지 이유와 올바른 방법을 함께 적는 점이 핵심이다.

// eslint.config.js — 예시. 발표에 나온 코드가 아니다.
export default [
  {
    files: ['src/electron-renderer/**'],
    rules: {
      'no-restricted-imports': ['error', {
        paths: [{
          name: 'react',
          importNames: ['useEffect'],
          message: 'useEffect는 제품 코드에서 금지. 데이터 로딩과 구독은 프레임워크 API를 쓴다.',
        }],
        patterns: [{
          group: ['**/electron-main/**'],
          message: 'renderer에서 main 코드를 가져오면 화면이 멈춘다. IPC로 요청한다.',
        }],
      }],
    },
  },
];
06

주석은 변명이 된다 06:50

발표자가 놀랐던 점이 있다. 에이전트가 마크다운을 '옳은 일을 하지 않은 이유'를 적는 곳으로 쓴다는 것이다. 문서, 코드 주석, 규칙, 스킬이 모두 해당한다.

반대 방향의 문제도 있다. 에이전트가 작은 교정 하나를 과하게 받아들여서, 절대 깨면 안 되는 규칙처럼 다룬다.

Cursor의 타이머 문제 07:20

  1. 증상: 에이전트가 setTimeout, requestAnimationFrame, requestIdleCallback 같은 타이머를 땜질용으로 즐겨 썼다.
  2. 진짜 원인: VS Code의 명령형imperative 스타일과 React의 선언형declarative 스타일이 부딪치는 아키텍처 문제였다. 타이머는 그 충돌을 덮는 임시방편이었다.
  3. 비용: 타이머를 빠르게 만들고 없애면 큰 가비지 컬렉션garbage collection이 자주 일어난다. 그러면 앱이 버벅인다. 아키텍처 선택 하나가 앱과 에이전트 양쪽의 성능을 떨어뜨렸다.
  4. 가장 나쁜 점: 에이전트가 이 임시방편이 왜 정당한지 설명하는 주석을 잔뜩 달았다. 그사이 타이머는 곳곳에 퍼졌고 앱 성능이 크게 나빠졌다.

주석 99% 금지 08:20

Grokbot 팀은 이 교훈을 받아들여 주석의 99%를 금지했다. 이유는 네 가지다.

이유설명
금방 낡는다코드는 바뀌는데 주석은 그대로 남는다
사람이 안 읽는다발표자 표현으로, 사람은 '주석 슬롭'을 굳이 읽지 않는다
핑계가 된다어려운 일을 피하고 싶은 에이전트에게 빠져나갈 구멍이 된다
강제할 수 없다"다음 에이전트에게 이건 하지 말라고 알려 줘야지" 하는 선의의 주석도 지켜진다는 보장이 없다

대신 Grokbot과 Dune에는 친절한 에러 메시지를 내는 린트 규칙이 있다. 그 메시지는 에이전트에게 겉을 땜질하지 말고 근본 원인을 고치라고 알려 준다. 09:00

07

교정할 때마다 검사로 바꾼다 09:10

팀의 일반 원칙은 이렇다. 에이전트를 교정할 때마다 그 교정을 결정적 검사로 바꾼다. 아니면 더 나은 API 설계나 아키텍처로 그 문제를 종류째 없앨 방법을 찾는다.

흔한 방식규칙 문서에 한 줄 추가에이전트가 읽고 지켜 주기를 바란다
→
발표자의 방식검사나 설계로 막는다어기면 린트가 실패하고, 메시지가 고칠 방향을 알려 준다

이걸 충분히 반복하면 코드 리뷰에서 볼 거리가 줄어든다. 어느 시점에는 리뷰할 게 거의 남지 않는다. 그러면 에이전트가 낸 PR 대부분을 에이전트가 직접 머지하게 둘 수 있다고 발표자는 말한다.

08

리뷰 대신 검증 산출물을 본다 09:40

검증은 에이전트를 더 자율적으로 만든다. 에이전트의 작업을 더 믿게 해 주기도 한다.

팀의 코드 리뷰는 이제 검증 산출물verification artifact을 보는 일로 줄었다. 영상, 스크린샷, 다이어그램, 형식 검증 결과 같은 것이다.

런타임 검증 10:00

가장 기본은 런타임 검증runtime verification이다. 에이전트가 코드를 직접 실행하고, 사람 개발자가 쓰는 디버깅 도구를 똑같이 쓰게 하는 것이다. 발표자는 Chrome DevTools Protocol을 예로 들었다.

피처 맵 · feature map 10:10

사용자 관점에서 앱의 모든 기능을 정리한 사이트맵 같은 것이다. 팀의 런타임 검증 스킬 안에 들어 있다.

사람이 "왼쪽 사이드바의 그거"라고 말해도 에이전트가 추측할 필요가 없다. 사람과 에이전트 사이에 공유 어휘가 생긴다.

스킬 안의 전용 CLI 10:30

검증 스킬 안에 전용 명령줄 도구를 넣는다. 에이전트는 같은 CLI와 드라이버를 매번 다시 쓴다.

매번 새로 짜지 않으니 토큰을 덜 쓴다. CLI 자체를 테스트할 수도 있다.

09

형식 검증과 속성 기반 테스트 10:50

팀은 최근 형식 검증formal verification도 쓰기 시작했다. 형식 검증은 수학적 방법으로 시스템이 어떤 성질을 늘 지키는지 확인하는 것이다.

도구쓰는 곳
TLA+주요 사용자 흐름의 모델 검사model checking. 예: 여러 기기와 플랫폼에 걸친 알림
Lean알고리즘 증명. 예: 직접 만든 가상화 라이브러리에서 화면 깜빡임이나 떨림이 없는지 확인
Bombadil 11:30UI용 속성 기반 테스트property-based testing. 지켜야 할 성질을 적어 두면 도구가 조작을 대량으로 만들어 깨지는 경우를 찾는다

발표자는 형식 검증으로 이미 버그를 꽤 찾았다고 한다. Bombadil도 UI 버그를 몇 개 잡았다고 한다.

하지만 발표자는 형식 검증이 만능이 아니라고 선을 긋는다. 팀은 아직 실험 중이다. 에이전트 환경에 더하는 또 하나의 층, 또 하나의 도구로 다룬다.

10

테스트와 검증의 황금기 11:50

발표자는 Cindy라는 사람이 6개월 간격으로 쓴 트윗 두 개를 소개한다. 발표에서 성은 나오지 않았다.

6개월 전에이전트를 못 믿겠다미묘한 버그가 계속 머지됐다
→
지금하루 토큰의 70%를 검증에 쓴다빠져 있던 조각은 검증 과정이었다

발표자도 토큰 대부분을 검증에 쓴다고 말한다.

Cindy의 방법에는 새로운 기법이 없다. 모두 원래 있던 좋은 소프트웨어 공학 도구다. 다만 이해하고, 쓰고, 유지하기 어려워서 너무 비쌌을 뿐이다.

에이전트가 그 비용을 크게 낮췄다. 그래서 발표자는 지금을 테스트와 검증의 황금기라고 부른다. 예전에는 돈이 맞지 않던 수준까지 모든 것을 테스트할 수 있기 때문이다. 12:40

의도를 확인하는 도구 12:50

형식 검증은 제품이 어떻게 동작해야 하는지 따져 보는 데도 도움이 된다. 에이전트가 의도와 목표를 정말 이해했는지도 확인할 수 있다.

발표자는 직접 만든 플러그인 P stack(potato stack, 추정)에 statechart라는 스킬을 넣었다. 이 스킬은 사용자 관점의 상태 기계를 그림으로 보여 준다. 발표자는 이 그림을 영상, 스크린샷과 함께 보면 리뷰가 훨씬 쉽다고 한다.

11

결과: 속도는 오르고 되돌림은 낮게 13:20

이 투자로 무엇을 얻었나. 발표자가 밝힌 Grokbot 팀의 수치다.

  • 릴리스: 안정 버전을 하루에 한 번꼴로 낸다.
  • 기여자: 10월에 PR을 하나 이상 낸 사람이 약 227명이다. 맥락을 많이 모르는 가끔 기여자도 포함된다. 14:00
  • 되돌림revert: 되돌린 PR의 비율은 오히려 줄었고, 약 0.5%에서 안정적이다. 14:20
  • 성능: 출시 때보다 여러 면에서 빨라졌다. 앱 시작, 타이핑, 새 채팅 열기, 채팅 전환이 모두 해당한다. 14:30

발표자는 Grokbot이 아직 Electron 앱이라 성능에 한계가 있다고 인정한다. 그래도 다른 많은 에이전트 UI보다 이미 훨씬 빠르다고 주장한다.

Grokbot은 발표자 회사의 제품이다. 위 수치와 "다른 에이전트 UI보다 빠르다"는 주장은 회사가 직접 낸 것이고, 비교 대상과 측정 방법은 발표에 나오지 않았다. 그 점을 감안해 읽자.

12

자동화는 기반을 다진 다음에 15:10

소프트웨어 공장을 짓고 모든 것을 자동화하기 전에, 발표자가 권하는 순서다.

  1. 에이전트를 교정할 때는 먼저 코드베이스를 고친다.
  2. 린트 규칙으로 안티패턴이 새로 생기지 않게 막는다.
  3. 이미 있는 옛 패턴도 정리한다.
  4. 검증을 튼튼하게 만든다.
안쪽 코딩 루프가 슬롭을 만든다면, 그 루프를 자동화해도 슬롭이 더 늘어날 뿐이다.Lauren Tan, 15:30 발언을 옮김

그러면 문제에 토큰을 점점 더 쏟아부어야 하고, 비용이 커진다. 위의 작업 대부분은 어차피 자동화의 전제 조건이다.

코드베이스, 정적 분석, 런타임 검증과 형식 검증에 투자해 두면 많은 것이 가능해진다. 그 기반 위에 팀만의 공장을 쉽게 지을 수 있다고 발표자는 말한다.

바깥 루프의 예 16:00

발표자는 바깥 루프outer loop를 만드는 도구로 Grokbot을 소개한다. 커넥터, 루틴, 프로젝트 기능이 있고, 클라우드 에이전트를 띄워 에이전트 수백~수천 개를 조율할 수 있다고 한다.

발표자가 든 흐름은 이렇다. 16:20

  1. 새 릴리스를 만든다.
  2. Grokbot이 새 프로젝트를 자동으로 띄운다. 자막에는 "cursor project"로 들렸다.
  3. 그 프로젝트가 실제 사용자처럼 앱 전체를 써 보며 퍼징fuzzing한다.
  4. 찾은 버그마다 수정 PR을 연다.
  5. 그 PR을 자동으로 머지한다.

발표자는 코드베이스가 충분히 좋아서 PR이 기본적으로 좋게 나오기 때문에 자동 머지가 가능하다고 설명한다. 이제 제품 코드 대부분은 사람이 깊이 리뷰할 필요가 없다고 말한다.

이 대목은 발표자 회사 제품의 소개다. 자동 머지가 안전하다는 판단도 발표자 팀의 자기 평가다.

발표자의 마무리는 이렇다. 기반이 튼튼하고 구조가 좋으면 슬롭을 금으로 바꿀 수 있고, 품질을 지키면서 빠르게 배포할 수 있다.

13

핵심 정리

  1. 에이전트 시대 엔지니어의 일은 생산성을 크게 늘리면서 품질을 지키는 것이다. 열쇠는 환경에 투자해서 얻는 신뢰다.
  2. 투자 순서는 코드 자체 → 결정적 검사 → 검증 → 글이다. 규칙 문서는 마지막에 조금만 쓴다.
  3. 코드베이스는 에이전트의 가장 큰 입력이다. 나쁜 패턴은 '정해진 패턴'으로 보여서 복제된다.
  4. 에이전트를 교정할 때마다 규칙 문서에 한 줄을 더하지 말고 결정적 검사로 바꾼다.
  5. 잘 쓰려면 미묘한 판단이 필요한 API(useEffect)는 제품 코드에서 금지해 문제를 종류째 없앤다.
  6. 섞이면 안 되는 코드는 디렉토리로 나누고, 둘 사이의 import를 린트로 막는다.
  7. 주석은 낡고, 강제할 수 없고, 에이전트의 변명 장소가 된다. 대신 근본 원인을 알려 주는 린트 메시지를 쓴다.
  8. 리뷰는 영상, 스크린샷, 다이어그램, 형식 검증 같은 검증 산출물을 보는 일로 바뀐다. 피처 맵과 전용 CLI가 이를 돕는다.
  9. 검증 기법은 새롭지 않다. 에이전트가 비용을 낮춰서 지금이 테스트와 검증의 황금기다.
  10. 슬롭을 만드는 루프를 자동화하면 슬롭만 늘어난다. 자동화는 기반을 다진 다음에 한다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 소프트웨어 엔지니어의 새 일은? 그걸 가능하게 하는 것은?
생산성을 크게 늘리면서 코드 품질을 지키거나 높이는 방법을 찾는 것. 맹목적인 믿음이 아니라, 에이전트 환경에 투자해서 얻는 신뢰가 그걸 가능하게 한다.
Q2역피라미드의 네 층을 시간을 많이 쓰는 순서대로 말하면?
코드 자체(API 설계, 아키텍처, 리팩터링) → 정적 검사와 테스트(린트, 타입, 컴파일러) → 검증(런타임, 형식) → 글(규칙, 스킬, AGENTS.md).
Q3에이전트를 교정할 때 규칙 문서 대신 결정적 검사를 쓰라는 이유는?
코드에 들어간 규칙은 매번 똑같이 작동해서 재현할 수 있고 더 믿을 수 있다. 글로 쓴 규칙은 지켜진다는 보장이 없다.
Q4에이전트 시대에 기술 부채와 안티패턴이 더 위험한 이유는?
코드베이스가 에이전트의 가장 큰 입력이라서, 에이전트가 그것을 이 코드베이스의 정해진 패턴으로 보고 복제한다. 잡초처럼 금방 퍼진다.
Q5useEffect 금지와 main/renderer import 금지가 공통으로 노리는 것은?
리뷰에서 매번 잡아야 했던 실수를 규칙으로 아예 못 하게 만들어, 그 문제를 종류째 없앤다. 리뷰에서 신경 쓸 일이 하나씩 줄어든다.
Q6Cursor의 타이머 문제에서 진짜 원인은 무엇이었고, 주석은 어떤 역할을 했나?
VS Code의 명령형 스타일과 React의 선언형 스타일이 부딪치는 아키텍처 문제였다. 타이머는 그걸 덮는 임시방편이었고, 에이전트가 단 주석이 그 임시방편을 정당화하면서 타이머가 퍼졌다.
Q7Grokbot 팀이 주석의 99%를 금지한 이유 네 가지는?
금방 낡는다. 사람이 잘 안 읽는다. 에이전트가 옳은 일을 피하는 핑계가 된다. 강제할 수 없다.
Q8피처 맵과 스킬 안의 전용 CLI는 각각 무엇을 해결하나?
피처 맵은 사람과 에이전트가 같은 기능 이름을 쓰게 해서 에이전트가 추측하지 않게 한다. 전용 CLI는 같은 드라이버를 매번 다시 써서 토큰을 아끼고, 그 자체를 테스트할 수 있게 한다.
Q9TLA+, Lean, Bombadil은 각각 어디에 쓰였나?
TLA+는 여러 기기와 플랫폼에 걸친 알림 같은 주요 사용자 흐름의 모델 검사. Lean은 직접 만든 가상화 라이브러리에 깜빡임이나 떨림이 없다는 증명. Bombadil은 UI 속성 기반 테스트.
Q10발표자가 지금을 테스트와 검증의 황금기라고 부르는 이유는?
검증 기법 자체는 새롭지 않지만, 예전에는 이해하고 쓰고 유지하는 비용이 너무 컸다. 에이전트가 그 비용을 크게 낮춰서 모든 것을 훨씬 넓게 테스트할 수 있게 됐다.
Q11속도가 빨라졌는데도 품질이 유지된다는 근거로 든 것은? 어떻게 읽어야 하나?
되돌린 PR 비율이 상대적으로 줄어 약 0.5%에서 안정적이고, 앱 시작과 채팅 전환 등 성능이 출시 때보다 좋아졌다는 것. 회사가 자기 제품에 대해 낸 수치라 그 점을 감안해 읽는다.
Q12소프트웨어 공장을 짓기 전에 먼저 할 일은? 순서를 건너뛰면 어떻게 되나?
코드베이스를 고치고(린트로 새 안티패턴을 막고 옛 패턴을 정리), 검증을 튼튼하게 한다. 건너뛰면 슬롭을 만드는 루프를 자동화하게 되어 슬롭과 토큰 비용만 늘어난다.
