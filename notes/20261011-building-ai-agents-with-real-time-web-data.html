에이전트에게 실시간 웹을 열어 주기

웹 스크래핑은 사이트 수가 늘수록 사람 손으로 유지하기 어려워진다. 발표자는 그 일을 AI 에이전트에 맡기고, 에이전트가 차단 없이 웹에 닿게 하는 도구로 Bright Data의 MCP 서버를 소개한다. 마지막에는 Amazon 상품과 Reddit 반응을 모아 "살까 말까"를 판단하는 에이전트를 직접 돌려 본다.

원본 영상: Building AI Agents with Real-Time Web Data 발표: Yohan Raju (Bright Data 솔루션 아키텍트)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

발표자는 웹 데이터 수집 회사 Bright Data 소속이다. 발표 후반은 자사 제품 설명과 데모가 중심이다. "우리는 차단을 뚫는다"는 식의 주장은 그 점을 감안해 읽자.

3분 요약
  1. 스크래퍼는 사이트 하나당 3~5일이 든다. 사이트가 10개에서 100개, 1,000개로 늘면 만드는 일보다 고치는 일이 팀을 잡아먹는다.
  2. 사이트마다 화면 구조가 다르고, 모두 자기 데이터를 지키려고 봇 차단을 건다. 데이터센터 IP로 되는 곳도 있지만 Cloudflare나 Akamai가 지키는 곳은 주거용 IP와 진짜 브라우저가 필요하다.
  3. 전통 파이프라인은 트리거, 프록시, 봇 차단 우회, 파싱과 검증, 후처리, 저장으로 이어진다. 어느 한 단계가 깨지면 처음부터 다시 돌린다.
  4. AI 모델은 질문에 따라 두 길을 간다. 학습된 지식으로 답하는 비동기 경로와 지금 웹에 나가 찾는 동기 경로다. "올해"처럼 시점이 붙으면 웹에 나가야 한다.
  5. 많은 사이트가 robots.txt로 ClaudeBot과 GPTBot을 막는다. 발표자는 Bright Data의 MCP 서버가 60개 넘는 도구로 그 벽을 넘게 해 준다고 말한다.
  6. 실습 에이전트는 Amazon 상품 데이터와 Reddit 검색 결과를 받아 Gemini로 분석하고, "할인 중이고 반응이 좋으니 사라"는 판단을 내놓았다.
  7. 질문에 대한 답: 봇이 막히는 이유는 같은 IP로 아무 행동 없이 페이지만 긁기 때문이다. 이를 계속 피하려면 대규모 프록시와 매번 바뀌는 접근 방식이 필요하다.
01

발표자와 Bright Data 00:10

발표자 Yohan Raju는 Bright Data에서 약 6년간 데이터 수집과 웹 스크래핑 분야의 솔루션 아키텍트로 일했다. Bright Data는 주거용 IP 프록시 회사로 시작해 데이터 수집 플랫폼으로 넘어왔다. 발표자는 자사가 매달 페타바이트 단위 데이터를 모으며 그 규모가 Google 다음이라고 말한다.

"Google 다음"이라는 규모 비교는 발표자의 자사 소개다. 비교 기준은 발표에 나오지 않는다.

발표는 두 부분이다. 앞부분은 실시간 웹 데이터로 에이전트를 만들 때 쓰는 도구와, 미리 색인한 데이터에 기대는 RAGretrieval-augmented generation와의 차이다. 뒷부분은 따라 할 수 있는 실습이다.

02

사이트가 늘면 스크래핑이 무너진다 01:40

스크래핑은 보통 작게 시작한다. 전자상거래 데이터를 모은다면 Amazon과 Walmart 두 곳만으로도 상품 대부분의 가격과 리뷰를 얻을 수 있다. 문제는 그 다음이다. Shopee, Shopify 상점들, Etsy처럼 대상 사이트가 계속 늘어난다.

발표자는 개발자가 사이트 하나의 스크래퍼scraper를 만드는 데 3~5일이 든다고 본다. 개발만이 아니라 QA, 개발 환경 실행, 끝까지 흐르는 파이프라인 테스트를 포함한 시간이다. 10개 사이트는 참을 만하다. 100개, 1,000개가 되면 이야기가 달라진다.

만드는 비용보다 큰 문제는 유지보수다. 1,000개 사이트를 돌리는데 Amazon과 다른 두 곳이 내일 화면을 바꾸면, 무엇이 바뀌었는지 찾고 고치고 고객 SLA와 데이터 품질에 영향이 있는지 확인해야 한다. 발표자는 예전에는 이 일을 감당하려면 엔지니어를 2배, 4배로 늘려야 했다고 말한다.

발표자의 주장 AI 에이전트는 사이트를 스스로 탐색하고 스크래퍼를 만들 수 있다. 그래서 사이트 수에 비례해 엔지니어를 늘리던 병목이 사라진다.
03

셀렉터 하나가 바뀌면 04:40

스크래퍼는 보통 페이지 안에서 가격과 제목이 있는 위치를 셀렉터selector로 가리킨다. 사이트가 가격의 위치를 바꾸면 그날부터 가격이 비어 들어온다. 가격에 기대는 뒷단 분석도 함께 멈춘다.

예전에는 팀이 들어가 고치고, 빠진 기간의 데이터를 다시 채워 넣었다. 발표자는 이 과정을 에이전트가 자동으로 처리할 수 있다고 말한다.

04

사이트마다 다르고, 모두 막는다 05:20

Amazon과 Walmart는 둘 다 가격, 제목, 설명을 보여 주지만 화면 구조는 전혀 다르다. 그래서 사이트마다 다른 스크래퍼가 필요하다. 더 큰 문제는 사이트가 자기 데이터를 지키려 한다는 점이다. 경쟁자가 같은 상품 정보를 갖는 것을 원하지 않으므로 봇 차단anti-bot과 캡차CAPTCHA를 건다.

차단 수준통과에 필요한 것
기본 사이트데이터센터 IP로도 들어간다
Cloudflare, Akamai 등이 지키는 사이트주거용 IP, 진짜 브라우저, 진짜 사용자처럼 보이는 행동

"진짜 사용자처럼"의 기준은 세밀하다. 너무 빨리 클릭하거나 스크롤하거나, 이미지를 내려받지 않으면 차단이 걸릴 수 있다. 사이트가 데이터를 일부러 어렵게 숨기므로, 사람이 하던 때는 사이트별 깊은 도메인 지식이 필요했다.

자막의 "Okami"는 문맥상 봇 차단 업체 Akamai로 보고 바로잡았다.

05

전통 스크래핑 파이프라인 07:00

발표자가 그린 전통 아키텍처는 왼쪽에서 오른쪽으로 여섯 단계를 지난다.

단계하는 일발표자의 설명
1. 트리거크롤을 시작한다cron 같은 스케줄러로 매일 또는 매주 받거나, 특정 URL 설정으로 직접 시작한다
2. 프록시탐지를 피한다데이터센터나 ISP의 고정 IP, 또는 노트북·태블릿·TV에서 나오는 회전식 주거용 IP. 실제 기기에 등록된 IP라 사이트가 더 쉽게 들여보낸다
3. 봇 차단 우회차단과 재시도를 처리한다요청이 막혔는지, 재시도할지, 맞는 IP를 쓰는지 판단한다. Bright Data의 Web Unlocker와 Browser API가 이 층에 해당한다
4. 파싱과 검증데이터가 진짜인지 확인한다가격이 90%의 경우에 돌아오는지, 리뷰와 평점이 필요한지 같은 검증 규칙을 세운다
5. 후처리정제하고 적재한다중복 제거, 보강, 배치 처리. 클라우드 저장소나 내부 시스템에 넘긴다
6. 저장데이터베이스에 넣는다메달리온 구조medallion architecture의 bronze, silver를 거쳐 최종 DB로 옮긴다
약점 어느 단계가 실패하면 전체를 처음부터 다시 돌려야 한다. 봇 차단 층이 깨지거나 셀렉터가 바뀌면 다시 수집하고 빠진 데이터를 채우며 SLA를 놓칠 수 있다.
06

AI는 언제 웹에 나가나 09:50

Claude나 GPT에 질문을 던지면 가끔 "생각 중" 또는 "웹 검색 중"이라는 표시가 뜬다. 그 순간 모델은 학습된 지식만으로는 답할 수 없다고 판단하고 밖으로 나간다. 발표자는 이 둘을 두 경로로 나눈다.

비동기 경로 async

미리 학습하거나 색인한 데이터에 기대어 답한다. RAG가 여기에 속한다.

  • 질문: "샌프란시스코에 가기 좋은 때는?"
  • 답: "보통 여름이 좋다"처럼 일반 지식으로 충분하다

맞는 경우: 사전 지식으로 답해도 괜찮은 질문

동기 경로 sync

지금 웹에 나가 찾는다. 시점이나 현재 상황이 답을 바꾸는 질문이다.

  • 질문: "올해 샌프란시스코에 가기 좋은 때는?"
  • 올해 어떤 행사가 있는지 실시간으로 확인해야 한다

맞는 경우: 정말로 지금의 웹을 봐야 하는 질문

두 경로는 준비해야 할 것이 다르다. 발표자는 동기 경로를 위해 모델이 웹에 나갈 수 있게 하는 자사 도구를 다음 절에서 소개한다.

캐시할 수 있는 답 "오늘 뉴욕 날씨"를 하루에 여러 사람이 묻는다면 한 번만 웹에 나가 답을 저장해 두면 된다. 그러면 매번 토큰과 비용을 쓰지 않는다.
07

robots.txt 벽과 MCP 12:40

많은 사이트가 robots.txt로 ClaudeBot과 GPTBot을 막는다. 그래서 모델이 웹에 나가 답을 찾으려 해도 그 사이트의 데이터는 가져오지 못한다. 발표자는 바로 이 자리에 Bright Data가 들어간다고 말한다. 스크래퍼든 에이전트든 Claude나 GPT든, 차단되지 않고 웹에 닿게 하는 도구가 있다는 것이다.

Bright Data의 MCP 서버 13:30

MCPModel Context Protocol는 모델이 외부 도구와 대화하는 규약이다. Claude Code나 LangChain 같은 "두뇌"가 Bright Data의 MCP 엔드포인트에 연결하면 발표자가 말하는 60개 넘는 API를 도구로 쓸 수 있다.

도구 묶음예시
검색 엔진Google 검색 결과를 받아온다
페이지 수집페이지를 Markdown이나 HTML로 받아온다
특정 사이트Amazon, Reddit, LinkedIn, Instagram 등
브라우저 자동화클릭, 스크롤. 음식 주문이나 항공권 예약처럼 브라우저가 필요한 일
영역별 묶음 22:30전자상거래, 소셜 미디어, 금융, 리서치, 비즈니스 인텔리전스, 앱스토어, 여행

스크래퍼를 직접 고르는 사람도 있지만, MCP로 묶어 두면 에이전트가 상황에 맞는 도구를 스스로 고른다. 발표자는 이쪽이 더 간결하다고 본다.

사례: 소셜 미디어 리스너 14:20

발표 2주 전, 한 사용자가 Claude Code에서 이 MCP로 "내 이름으로 내 소셜 프로필을 모두 찾아 팔로워 수를 알려 달라"고 요청했다. 흐름은 이렇다.

  1. 검색 엔진 도구로 Instagram, TikTok, LinkedIn 프로필 페이지를 찾는다.
  2. 각 페이지에 데이터 파이프라인 API를 호출한다.
  3. 팔로워 수를 모아 답으로 돌려준다.

영상 비교: Glassdoor 15:30

같은 프롬프트 "브라우저로 이 Glassdoor 페이지 내용을 가져와"를 두 Claude에 넣었다. MCP를 붙인 쪽은 결과를 가져왔고, 붙이지 않은 쪽은 차단됐다. 발표자는 Glassdoor가 데이터 수집 업무에서도 보호가 강한 사이트로 알려져 있다고 말한다.

이 비교는 발표자가 자사 제품을 보여 주려고 고른 데모다. 어떤 조건에서 찍었는지는 발표에 나오지 않는다.

08

사용 사례: 채용 데이터 16:30

발표자가 만나는 AI 회사들은 모델 학습, 미세 조정, 에이전트의 실시간 접근, RAG 보강에 웹 데이터를 쓴다. 예로 든 것은 이력서 매칭 모델을 위한 채용 데이터다.

채용 데이터는 한 번 모아 두고 잊을 수 있는 데이터가 아니다. 어느 회사가 무엇을 뽑는지, 자리가 몇 개인지, 연봉과 위치가 어떤지 계속 바뀐다. 발표자는 네 가지 요건을 꼽는다.

요건이유
구조화되고 일관된 출력형식이 흔들리면 모델 학습과 분석이 꼬인다
성능채용 시장 패턴을 분석하려면 데이터가 끊임없이 흘러와야 한다
신뢰성중단이 생기면 전체 파이프라인이 멈춘다
과거 데이터소프트웨어 엔지니어 연봉이 왜 올랐는지 같은 추세를 보려면 지난 몇 달이나 몇 년의 데이터가 필요하다
09

실습: 살까 말까 에이전트 19:10

Google Colab 노트북으로 진행한다. 준비물은 Bright Data API 토큰과 Gemini API 키 두 개다. 설정 방법은 발표자가 Google Drive에 올려 두었다.

1단계Amazon 상품 데이터Bright Data API로 가격, 평점, 이미지, URL, 다른 판매자, 상품 특징을 받는다
→
2단계 → 3단계Reddit 검색 → AI 분석상품명으로 Reddit 게시글을 검색하고, 두 데이터를 Gemini에 넘겨 "살 만한가"를 판단한다

발표자가 고른 상품은 Stanley Quencher 텀블러다. Amazon 쪽에서는 가격, 평점, 다른 판매자, 상품 특징이 돌아왔다. Reddit 검색은 시간이 걸려 그동안 질문을 받았다.

결과 25:30

  • Reddit 게시글 몇 개가 잡혔다. "창피하다"는 반응과 "푹 빠졋다"는 반응이 섞여 있었다.
  • 최종 판단은 "사라"였다. 근거는 적당한 할인, 압도적으로 긍정적인 리뷰와 약간의 엇갈린 의견, 높은 수요에 비해 적은 Amazon 재고였다.
  • 재고 정보는 Amazon API 응답에서 그대로 읽어 낸 것이다. 모델이 API가 돌려준 데이터 항목들을 하나씩 해석해 결론을 냈다.

발표자는 이 구조가 전자상거래에 묶이지 않는다고 말한다. 페이지에 닿아 데이터를 꺼내는 도구만 있으면 어떤 용도로도 같은 흐름을 만들 수 있다. 어떤 논리로 파이프라인을 짜고 규모를 키울지는 사용자 몫이다.

자막의 "Tumblr cup"은 상품 종류인 텀블러tumbler로, "Stanley Quenter"는 Stanley Quencher로 바로잡았다.

10

질문: 왜 봇은 막히는가 24:00

청중 질문은 "왜 일반 봇은 못 가져오는 데이터를 Bright Data는 가져올 수 있나"였다. 발표자의 답은 이렇다.

  1. 처음 며칠은 데이터센터 IP로 Glassdoor 같은 사이트를 긁어도 된다.
  2. 곧 사이트가 알아챈다. 같은 데이터센터 IP가 페이지에서 아무 행동도 하지 않고 계속 접근하기 때문이다. 그때부터 봇 차단 층이 겹겹이 추가된다.
  3. 이를 계속 피하려면 스크래퍼만으로는 안 된다. 사이트가 어떤 방어를 쓰는지 파악하고 차단을 일으키지 않으면서 꾸준히 통과해야 한다.
  4. Bright Data는 세계 최대 프록시 인프라와, 사이트마다 접근 방식을 매번 바꾸는 봇 차단 우회 로직을 수년간 쌓아 왔다고 말한다.

발표자는 스크래핑을 직접 운영하는 팀에 대해 한 가지를 덧붙인다. 사이트가 무엇을 바꿨는지 알아내는 시간이 스크래퍼를 관리하는 시간보다 더 들 수 있다는 것이다.

11

핵심 정리

  1. 스크래퍼 하나에 3~5일. 사이트가 1,000개면 만드는 일보다 고치는 일이 팀을 잡아먹는다.
  2. 셀렉터 하나가 바뀌면 데이터가 비고, 뒷단 분석까지 멈춘다. 고친 뒤 빠진 기간을 다시 채워야 한다.
  3. 사이트마다 화면 구조가 다르다. 사이트별 스크래퍼와 사이트별 도메인 지식이 필요했다.
  4. 모든 사이트가 데이터를 지키려 한다. 기본 사이트는 데이터센터 IP로 되지만, Cloudflare나 Akamai 뒤의 사이트는 주거용 IP와 진짜 브라우저가 필요하다.
  5. 전통 파이프라인은 트리거, 프록시, 봇 차단 우회, 파싱과 검증, 후처리, 저장의 여섯 단계다. 하나가 깨지면 처음부터다.
  6. AI 모델은 학습 지식으로 답하는 비동기 경로와 지금 웹에 나가는 동기 경로를 택한다. "올해"처럼 시점이 붙으면 동기 경로다.
  7. 자주 묻는 실시간 질문은 한 번 가져와 캐시하면 토큰과 비용을 아낀다.
  8. 많은 사이트가 robots.txt로 ClaudeBot과 GPTBot을 막는다. 발표자는 Bright Data MCP의 60개 넘는 도구가 그 벽을 넘게 해 준다고 말한다.
  9. 실습 에이전트는 Amazon 상품 데이터와 Reddit 반응을 Gemini로 분석해 "사라"는 판단을 냈다. 같은 흐름은 어떤 용도로도 쓸 수 있다.
  10. 봇이 막히는 이유는 같은 IP로 아무 행동 없이 긁기 때문이다. 꾸준히 통과하려면 큰 프록시 인프라와 매번 바뀌는 접근 방식이 필요하다는 것이 발표자의 답이다.
12

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말한 스크래퍼 하나의 개발 기간과, 그 안에 포함되는 일은?
3~5일. 개발뿐 아니라 QA, 개발 환경 실행, 끝까지 흐르는 파이프라인 테스트가 들어간다.
Q2사이트가 1,000개가 되면 왜 "만들기"보다 "고치기"가 문제인가?
사이트 몇 곳이 동시에 화면을 바꾸면 무엇이 바뀌었는지 찾고, 고치고, SLA와 데이터 품질 영향을 확인해야 한다. 예전에는 엔지니어를 2배, 4배로 늘려야 했다.
Q3가격 셀렉터가 바뀌면 어떤 일이 연쇄로 일어나나?
가격이 비어 들어오고, 가격에 기대는 뒷단 분석이 멈춘다. 고친 뒤 빠진 기간의 데이터를 다시 채워야 한다.
Q4Cloudflare나 Akamai가 지키는 사이트에 들어가려면 무엇이 필요하다고 했나?
주거용 IP, 진짜 브라우저, 진짜 사용자처럼 보이는 행동. 너무 빠른 클릭이나 스크롤, 이미지 차단은 봇으로 의심받는다.
Q5데이터센터 IP와 주거용 IP의 차이는?
데이터센터와 ISP IP는 고정 IP다. 주거용 IP는 노트북, 태블릿, TV 같은 실제 기기에서 나오는 회전식 IP라 사이트가 더 쉽게 들여보낸다.
Q6전통 스크래핑 파이프라인의 여섯 단계와 가장 큰 약점은?
트리거, 프록시, 봇 차단 우회, 파싱과 검증, 후처리, 저장. 어느 단계가 실패하면 전체를 처음부터 다시 돌려야 한다.
Q7"샌프란시스코에 가기 좋은 때"와 "올해 샌프란시스코에 가기 좋은 때"는 어느 경로로 가나?
앞은 비동기 경로다. 학습된 일반 지식으로 "여름"이라 답할 수 있다. 뒤는 동기 경로다. 올해 행사를 실시간으로 확인해야 한다.
Q8모델이 웹에 나가도 특정 사이트의 데이터를 못 가져오는 이유로 발표자가 든 것은?
많은 사이트가 robots.txt로 ClaudeBot과 GPTBot을 막는다.
Q9소셜 미디어 리스너 사례에서 에이전트가 거친 순서는?
검색 엔진 도구로 Instagram, TikTok, LinkedIn 프로필을 찾고, 각 페이지에 데이터 API를 호출해 팔로워 수를 모아 돌려줬다.
Q10실습 에이전트의 세 단계와 필요한 두 키는?
Amazon 상품 데이터 수집, Reddit 키워드 검색, Gemini 분석. 필요한 키는 Bright Data API 토큰과 Gemini API 키다.
Q11실습 결과 "사라"의 근거 세 가지는?
적당한 할인, 압도적으로 긍정적인 리뷰에 약간의 엇갈린 의견, 높은 수요에 비해 적은 Amazon 재고.
Q12청중 질문에 발표자가 설명한, 봇이 결국 막히는 이유는?
같은 데이터센터 IP가 페이지에서 아무 행동도 하지 않고 계속 접근하면 사이트가 알아채고 봇 차단 층을 겹겹이 추가한다.
