grep이냐 임베딩이냐

코드처럼 작고 잘 정리된 데이터는 grep만으로 충분하다. 회사 문서처럼 크고 뒤섞인 데이터는 미리 인덱싱한 검색으로 방향을 잡고, grep과 read로 파고들어 근거를 확인해야 한다.

원본 영상: Grep or Embeddings? Agentic Search Over Company Documents 발표: George He (LlamaIndex 엔지니어링 총괄)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다. 예를 들어 cloud code는 Claude Code로, GP는 grep으로, CloudMD는 CLAUDE.md로 고쳤다. 확실하지 않은 이름에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. Claude Code는 벡터 DB를 시험했지만 쓰지 않았다. 코드가 계속 바뀌어 인덱스를 최신으로 유지하기 어려웠다. 코드는 작고 구조가 있어서 grep·glob·read로 충분하다.
  2. 회사 문서는 다르다. PDF, PPT, 이미지, 도면이 섞여 있고, 양이 많고, 권한 관리가 필요하다. grep할 폴더 구조가 없다.
  3. 기준은 규모다. 파일 100~1,000개면 로컬 파일 검색으로 된다. 수천~수백만 개면 어디를 볼지 알려 줄 나침반이 필요하다.
  4. 컨텍스트 창이 100만 토큰으로 커져도 문서를 매번 모델에 넣는 건 비싸다. 서브에이전트로 나눠도 토큰과 지연이 크다.
  5. 답은 하네스다. 에이전트에게 의미 검색과 목록·메타데이터·grep·read를 모두 주고 스스로 고르게 한다.
  6. 검색은 키워드와 벡터를 섞고 재순위를 붙인다. 복잡한 문서는 미리 파싱하고 페이지 스크린샷도 함께 저장한다.
  7. 실서비스에서는 멀티테넌시, 권한, 최신성이 늘 문제다. 권한은 수집할 때 벡터 저장소의 메타데이터로 넣는다.
01

grep이냐 임베딩이냐 01:10

발표자는 먼저 묻는다. 에이전트에게 벡터 검색용 맥락이 언제, 왜 필요한가.

지난 몇 년 동안 모델은 여러 단계를 스스로 조율하는 일orchestration이 크게 늘었다. 지시를 따르는 능력도 좋아졌다. 로컬 파일 시스템을 돌아다니고, 스킬과 MCP로 정보를 가져오는 솜씨도 예전보다 낫다.

그래도 검색 문제는 남는다. 큰 문서 묶음corpus이나 복잡한 문서를 다룰 때 특히 그렇다. 발표자는 이 문제를 푸는 두 갈래를 나란히 놓는다. 01:50

grep 방식

질문이 올 때마다 파일을 직접 찾고 읽는다. 발표자는 "로컬 파일 검색과 실행"이라고 부른다.

  • 미리 만들어 둘 것이 없다
  • 파일 이름, 키워드, 정규식으로 찾는다
  • 인덱스가 없으니 동기화 걱정도 없다
임베딩 방식

문서를 미리 쪼개고, 뜻을 숫자 벡터로 바꿔embedding 인덱스를 만들어 둔다. 발표자는 "사전 인덱싱, 사전 검색"이라고 부른다.

  • 질문과 뜻이 가까운 조각을 빨리 찾는다
  • 문서를 매번 다시 읽지 않는다
  • 원본이 바뀌면 인덱스도 맞춰 줘야 한다

발표의 질문은 둘 중 무엇이 이기느냐가 아니다. 언제 어느 쪽이 맞는지, 언제 둘을 섞어야 하는지다.

02

Claude Code가 벡터 검색을 뺀 이유 02:10

이 논쟁은 Claude Code가 나오면서 커졌다. Claude Code가 안에서 코드를 어떻게 찾는지 많은 사람이 궁금해했다.

Anthropic은 로컬 파일 시스템을 그대로 쓰는 쪽을 골랐다. grep으로 내용을 찾고, glob으로 파일 이름을 찾고, read로 읽는다. 코드는 로컬에서 다루기 쉽다. 간결하고, 이미 텍스트이기 때문이다.

벡터 DB를 시험하고 뺐다 02:50

발표자는 Claude Code 제작자 Boris의 트윗을 소개한다. Claude Code 팀은 벡터 데이터베이스를 시험했지만 결국 쓰지 않았다.

이유는 성능만이 아니었다. 규모를 키우고 유지보수하기가 현실적으로 어려웠다. 코드는 계속 바뀐다. 미리 만든 벡터 인덱스를 그 변화에 맞춰 최신으로 유지하기 힘들다.

코드라서 통했다 03:20

사전 인덱싱도, RAG도, 벡터 검색도 없이 잘 되는 건 코드의 성질 덕분이다.

03

회사 문서는 코드와 다르다 04:00

회사 데이터로 넘어가면 이야기가 달라진다. 이미지, PDF, 파워포인트가 섞여 있다. 코드처럼 정리돼 있지 않아서 grep할 폴더 구조가 없다.

코드는 사람이 공들여 다듬은 데이터다. 문법이 맞아야 하고, 참조도 정확해야 한다. 회사 데이터베이스나 데이터 레이크data lake에 쌓인 자료는 그렇지 않다.

코드 저장소회사 문서
정리 상태문법과 참조가 맞게 다듬어져 있다쌓인 그대로다. 따라갈 폴더 구조가 없다
형식이미 텍스트다복잡한 PDF, 회로도, 제조 도면이 섞여 있다
규모보통 작다규모가 전혀 다르다. 로컬에서 돌릴 수 없다
보안발표에서 문제로 꼽지 않았다누가 어떤 정보에 접근할 수 있는지가 중요하다
동기화디스크에 있는 것이 곧 최신이다여러 곳의 변화를 맞춰 두기가 아주 어렵다

업계가 써 본 방법들 04:50

데이터 덩어리를 어딘가에 두고, 에이전트에게 "이렇게 훑으면 된다"고 알려 주는 방법이 여럿 나왔다. 모두 데이터의 계층을 기록해 두는 방법이다.

  • MCP 서버
  • CLAUDE.md 같은 프로젝트 안내 파일
  • 스킬
  • 에이전트 파일, 지시 파일
결국 규모와 정리 노력의 문제 05:10 발표자의 핵심 메시지다. 데이터가 얼마나 큰지가 첫째다. 검색 시스템을 유지하는 데 정리 노력을 얼마나 들일지가 둘째다. 사람들은 컨텍스트 엔지니어링과 하네스를 말한다. 결국 필요한 건 알맞은 기본 도구primitives를 갖춰 두는 일이다.
04

파일 수가 길을 정한다 05:40

알맞은 도구를 고르려면 먼저 데이터의 규모를 알아야 한다. 발표자는 파일 수로 선을 긋는다.

파일 100~1,000개

로컬 파일 검색으로 충분하다. 에이전트가 컨텍스트 안에서 다룰 수 있는 양이다.

  • 파일을 하나씩 훑어도 토큰이 많이 들지 않는다
  • 파일 이름을 다루며 돌아다녀도 부담이 적다

grep과 read로 시작한다

파일 수천~수백만 개 06:00

파일을 매번 읽을 수 없다. 그만큼 토큰을 태우고 싶지도 않다.

  • 대략 어디를 봐야 하는지 알려 줄 장치가 필요하다
  • 바늘을 바로 못 찾아도, 방향은 알려 줘야 한다

미리 인덱싱한 검색으로 방향부터 잡는다

발표자는 이 장치를 나침반이라고 부른다. 정확한 답을 주지 않아도, 어느 쪽으로 가야 하는지 알려 주면 된다.

05

컨텍스트가 커져도 비용은 남는다 06:30

모델이 한 번에 받아 보는 양context window은 계속 커졌다.

중요한 건 창의 크기가 아니다. 얼마를 낼 생각이냐다.

  • 문서를 통째로 모델에 밀어 넣으면 그만큼 토큰값이 든다.
  • PDF 같은 바이너리를 보내 모델이 직접 그려 보고 내용을 뽑게 하면 더 비싸다.
  • 모델의 컨텍스트를 문서 수집과 검색에 쓰는 건 아주 비싼 방법이다.
서브에이전트로 나누면? 07:10 큰 에이전트가 작은 에이전트에게 일을 나눠 맡기는 방법이 있다. 작은 에이전트가 무거운 맥락을 처리하고 답만 돌려준다. Claude Code도 메인 세션이 더 약한 모델의 하위 세션에 일을 맡기곤 한다. 하지만 하위 에이전트도 일을 하려면 전체 맥락이 필요하다. 그래서 싼 모델을 써도 토큰과 지연이 크다.

같은 문서를 매번 다시 처리하지 않으려면 사전 인덱싱 시스템을 만들 만하다. 발표자는 여기서 하네스 이야기로 넘어간다. 07:50

06

고르는 일은 하네스에 맡긴다 08:00

규모가 커질 시스템이라면 방식을 사람이 미리 정해 두면 안 된다. "하이브리드 RAG를 쓸까, 파일을 하나씩 뒤질까"를 정해 두지 않는다.

발표자가 찾은 가장 깔끔한 방법은 하네스다. 에이전트에게 두 방식의 도구를 모두 주고, 상황에 맞게 고르게 한다.

  • 옛날식 도구: grep, cat, 파일 이름 필터, 메타데이터 필터
  • 의미 기반 필터: 뜻이 가까운 문서를 찾는 검색
1단계 · 나침반의미 검색으로 범위를 좁힌다어떤 파일들을 볼지 대략의 방향을 잡는다
→
2단계 · 근거파일 도구로 파고든다에이전트가 원래 가진 파일 탐색 능력으로 세부 내용을 읽는다

이렇게 두 장점을 다 얻는다. 검색은 방향을 준다. 파일 탐색은 답을 실제 문서에 묶어 둔다grounding. 그래야 답을 지어내지hallucination 않는다.

07

다섯 가지 도구 09:00

보험, 금융, 의료 같은 곳을 생각해 보자. 분류가 안 됐거나 라벨이 반쯤만 붙은 문서가 아주 많다. 발표자는 이런 곳의 문서 검색을 다섯 도구로 나눈다. 도구들은 세 가지 질문에 답한다.

번호도구답하는 질문
1검색 (나침반)어디를 봐야 하나?
2파일 목록 보기나침반이 가리킨 문서 묶음 안에 실제로 무엇이 있나?
3메타데이터로 파일 훑기
4grep: 원하는 키워드가 여러 개 함께 나오는 파일 찾기
5읽기: 파싱한 텍스트와 페이지 스크린샷문서에 실제로 뭐라고 쓰여 있나?

2~4번은 사전 인덱싱 파이프라인에서 미리 돌려도 되고, 질문이 올 때 바로 돌려도 된다.

발표자는 뒤에서 2~4번을 "목록, grep, read"로 묶어 부르기도 한다. 도구 번호보다 세 질문(어디를, 무엇이, 실제로 뭐라고)으로 기억하면 쉽다.

렌더링도 미리 잘라 둔다 09:50

5번에서 여러 형식이 섞인 멀티모달 문서는 미리 그려 둬야 한다.

사전 인덱싱에서 가장 중요한 일 하나는 문서를 소화하기 좋은 크기로 나누는 것chunking이다. 발표자는 이 원칙이 텍스트에만이 아니라 렌더링에도 적용된다고 본다.

자유 형식 문서에서 가장 어려운 일은 문서를 사람이 보는 모습 그대로 이미지로 그리는 것rasterize이다. 도면, PDF, 파워포인트는 기계가 아니라 사람이 보려고 만든 것이다. 원래 사람이 하던 일이기도 하다. 그래서 미리 만든 페이지 스크린샷 인덱스를 주면 에이전트의 검색에 큰 도움이 된다.

08

1번 도구: 하이브리드 검색과 재순위 10:50

나침반 역할을 하는 검색에는 방법이 많다. Graph RAG, 전통적인 RAG, 오래된 키워드 검색 방식인 BM25가 있다. 발표자는 기업용으로는 하이브리드를 권한다. 11:00

키워드 검색 (BM25)

정확한 단어를 찾는다.

  • 개발자에게 쓸모가 있다
  • 문서 묶음 안의 특정 단어를 찾는 AI 에이전트에게도 쓸모가 있다
벡터 검색

뜻이 비슷한 것을 찾는다.

  • 단어가 달라도 의미가 같으면 찾는다
  • 의미와 유사도는 검색에서 아주 중요하다
  1. 키워드 검색과 벡터 검색을 함께 돌린다.
  2. 두 결과에 가중치를 주어 합친다fusion. 한 방식의 약점에 눈이 가리지 않는다.
  3. 상위 결과를 더 깊은 방법으로 다시 줄 세운다re-ranking. 예를 들어 상위 100개를 LLM으로 다시 평가한다. 11:40

발표자는 여러 벤치마크 데이터셋에서 같은 경향이 보인다고 말한다. 키워드나 벡터 하나만 쓰면 기본 수준에 머문다. 둘을 합치고 재순위를 붙이면 훨씬 좋아진다.

발표에서는 벤치마크 이름이나 수치를 말하지 않았다.

다만 검색은 파이프라인의 한 부분일 뿐이다. 우리가 원하는 건 검색 결과가 아니라 답이다.

  2. 첫 검색에 나오지 않은 비슷한 파일까지 찾아 범위를 넓힌다.
  3. 넓힌 범위 안에서 다시 좁혀 결과를 추린다.
원격에서 쓰는 목록·grep·read 공유 파일 시스템이나 분산 파일 시스템에서는 이 세 기본 도구가 특히 중요하다. 파일을 매번 에이전트 쪽으로 내려받으면 비싸기 때문이다. 도구를 원격에서 바로 쓸 수 있으면 필요한 부분만 가져온다.

핵심 정리

  1. 에이전트 검색에는 두 길이 있다. 그때그때 파일을 찾는 grep 방식과, 미리 인덱싱해 뜻으로 찾는 임베딩 방식이다.
  2. Claude Code는 벡터 DB를 시험했지만 뺐다. 코드가 계속 바뀌어 인덱스를 최신으로 유지하기 어려웠다.
  3. 코드는 작고, 구조가 있고, import·테스트 같은 단서가 있고, 이미 로컬에 있다. 그래서 grep·glob·read로 충분하다.
  4. 회사 문서는 형식이 제각각이고, 규모가 크고, 권한 관리가 필요하다. grep할 폴더 구조가 없다.
  5. 파일 100~1,000개면 로컬 파일 검색, 수천~수백만 개면 나침반 역할의 검색부터 둔다.
  6. 컨텍스트 창이 100만 토큰이어도 문서를 매번 넣는 건 비싸다. 서브에이전트도 토큰과 지연이 크다.
  7. 하네스에 의미 검색과 목록·메타데이터·grep·read를 모두 넣는다. 검색은 방향, 파일 도구는 근거다.
  8. 검색은 키워드와 벡터를 가중치로 합치고, 상위 결과를 LLM으로 재순위한다.
  9. 복잡한 문서는 한 번 구조화 파싱해 마크다운과 페이지 스크린샷으로 저장한다. 파서는 표와 레이아웃을 제대로 담는지로 고른다.
  10. 실서비스 숙제는 멀티테넌시, 권한, 최신성이다. 권한은 수집할 때 벡터 저장소의 메타데이터로 넣는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1grep 방식과 임베딩 방식은 각각 무엇인가?
grep 방식은 질문이 올 때마다 파일을 직접 찾고 읽는다. 임베딩 방식은 문서를 미리 쪼개 벡터 인덱스로 만들어 두고, 뜻이 가까운 조각을 찾는다.
Q2Claude Code가 벡터 DB를 쓰지 않은 이유는?
성능만이 아니라 확장과 유지보수 문제였다. 코드가 계속 바뀌어서 미리 만든 인덱스를 최신으로 유지하기 어렵다.
Q3코드가 grep만으로 잘 찾아지는 성질을 세 가지 이상 들면?
저장소가 작다. 반쯤 구조화돼 있다. import와 테스트가 다음에 볼 파일의 단서를 남긴다. 폴더 계층이 있다. 이미 로컬 디스크에 있다.
Q4회사 문서에서 grep만으로는 어려운 이유는?
코드처럼 다듬어져 있지 않아 따라갈 폴더 구조가 없다. PDF, PPT, 도면처럼 형식이 제각각이다. 규모가 커서 로컬에서 돌릴 수 없다. 누가 무엇을 볼 수 있는지 권한도 관리해야 한다.
Q5발표자가 제시한 규모 기준은?
파일 100~1,000개면 로컬 파일 검색으로 충분하다. 수천~수백만 개면 매번 읽을 수 없으니, 어디를 볼지 알려 줄 나침반 역할의 검색이 필요하다.
Q6컨텍스트 창이 100만 토큰인데 왜 사전 인덱싱이 필요한가?
비용 때문이다. 문서를 매번 모델에 넣고, 바이너리를 모델이 직접 렌더링하게 하면 아주 비싸다. 서브에이전트로 나눠도 하위 에이전트마다 전체 맥락이 필요해 토큰과 지연이 크다.
Q7하네스 방식에서 의미 검색과 파일 도구는 각각 무슨 역할을 하나?
의미 검색은 나침반이다. 볼 파일의 범위를 좁힌다. 파일 도구는 그 안으로 파고들어 세부 내용을 읽고, 답을 실제 문서에 묶어 둔다.
Q8발표자가 권하는 검색 순서는?
키워드 검색과 벡터 검색을 함께 돌린다. 두 결과를 가중치로 합친다. 상위 결과(예: 100개)를 LLM 같은 더 깊은 방법으로 재순위한다.
Q9복잡한 문서를 미리 파싱하고 스크린샷까지 저장하는 이유는?
에이전트가 문서를 볼 때마다 바이너리 토큰을 태우지 않게 하려는 것이다. 표와 차트의 공간 구조를 마크다운으로 살려 둔다. 텍스트인지 아닌지 애매한 부분이 있어서 페이지 이미지도 함께 쓴다.
Q10파서를 평가할 때 볼 두 가지는?
표를 표로 잡아내는가, 그리고 원래 레이아웃을 얼마나 충실하게 담는가. 여기서 틀리면 나중에 LLM이 의미를 읽을 때 무너진다.
Q11실서비스에서 늘 나오는 세 가지 숙제는?
멀티테넌시, 권한 메타데이터, 최신성. 발표자는 최신성 때문에 여러 회사가 사전 인덱싱을 포기했다고 말한다.
Q12데모에서 grep과 read를 함께 쓰면 무엇이 좋은가?
파일을 로컬로 내려받지 않아도 된다. grep으로 위치를 찾고, 시작점과 길이를 정해 원격 저장소에서 필요한 부분만 읽는다.

용어뜻
grep파일 안에서 문자열이나 정규식 패턴을 찾는 명령
glob*.md 같은 패턴으로 파일 이름을 찾는 방식
임베딩Embedding. 글의 뜻을 숫자 벡터로 바꾼 것. 뜻이 비슷하면 벡터도 가깝다
벡터 저장소임베딩을 저장하고 가까운 것을 빠르게 찾아 주는 데이터베이스
사전 인덱싱Pre-indexing. 질문이 오기 전에 문서를 파싱하고 나누고 임베딩해 두는 일
RAGRetrieval-Augmented Generation. 관련 문서를 찾아 모델에 넣고 답하게 하는 방식
Graph RAG문서 속 대상과 관계를 그래프로 만들어 검색에 쓰는 RAG
BM25단어가 얼마나 자주, 얼마나 드물게 나오는지로 점수를 매기는 키워드 검색 방식
하이브리드 검색키워드 검색과 벡터 검색의 결과를 합치는 방식
융합Fusion. 두 검색 결과의 순위나 점수를 가중치를 두고 합치는 단계
재순위Re-ranking. 1차 검색의 상위 결과를 LLM 같은 정밀한 방법으로 다시 줄 세우는 단계
청크Chunk. 검색하기 좋게 문서를 잘게 나눈 조각
파싱Parsing. 문서를 마크다운이나 텍스트 같은 표준 형식으로 바꾸는 일
래스터화Rasterize. 문서를 사람이 보는 모습 그대로 이미지로 그리는 일
OCR이미지 속 글자를 텍스트로 읽어 내는 기술
멀티모달텍스트, 이미지, 표, 도면처럼 여러 형식이 섞인 데이터
컨텍스트 창Context window. 모델이 한 번에 받아 볼 수 있는 토큰의 양
서브에이전트큰 에이전트가 일을 나눠 맡기는 하위 에이전트
하네스모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀
그라운딩Grounding. 답을 실제 문서 내용에 묶어 지어내지 않게 하는 것
환각Hallucination. 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 것
메타데이터파일에 대한 정보. 예: 연도, 회사, 출처, 접근 권한
멀티테넌시여러 고객이 한 시스템을 함께 쓰되 서로의 데이터는 볼 수 없게 나누는 구조
최신성Freshness. 인덱스가 원본 데이터의 지금 상태를 얼마나 반영하는가
MCPModel Context Protocol. 에이전트가 외부 도구와 데이터에 접속하는 표준 방식
