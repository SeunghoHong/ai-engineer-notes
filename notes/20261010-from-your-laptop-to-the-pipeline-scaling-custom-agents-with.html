에이전트를 노트북에서 파이프라인으로

내 노트북에서 만든 에이전트를 팀에 나누고, 여러 저장소로 넓히고, 마지막에는 파이프라인에서 혼자 돌게 하는 네 단계를 GitHub Copilot 기능으로 보여 주는 발표다. 파이프라인에 올리면 비용과 실패가 보이고, 보이면 줄일 수 있다는 것이 마지막 메시지다.

원본 영상: From Your Laptop to the Pipeline: Scaling Custom Agents with GitHub Copilot 발표: Jose Palafox (GitHub 6년 반. 고객사의 도입과 확장을 돕는 현장 담당. 보안 사업을 키우다 최근 1년은 AI에 집중)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 알려진 이름으로 바로잡았다(.github-private, awesome-copilot, gh-aw, GitHub Next, OTel, SIEM). 명령 이름은 들린 대로 적었다. mm:ss는 영상 위치다.

발표자는 GitHub 직원이고, 발표 전체가 GitHub Copilot 기능 소개다. 비용과 확장성에 관한 주장은 그 점을 감안해 읽자.

3분 요약
  1. 에이전트는 결국 모델과 지시문을 담은 마크다운 파일이다. 어느 입구로 부르든 같은 하네스에서 돈다.
  2. 기본 에이전트는 일에 맞는 모델을 쓴다. 탐색은 작은 모델, 계획 검토는 다른 회사 모델이다.
  3. 1단계 만들기: /agent에 한 줄만 쓰면 Copilot이 설명, 성공 기준, 방법까지 채운다.
  4. 2단계 나누기: 마켓플레이스나 .github-private 저장소로 팀 전체에 배포한다. 모두 같은 에이전트를 쓰면 캐시 적중이 늘어 비용이 준다고 발표자는 말한다.
  5. 3단계 넓히기: orchestrate는 이슈 여러 개를 목표로 받아, 저장소마다 그 안에서 하위 에이전트를 띄운다.
  6. 4단계 옮기기: agentic workflows는 Copilot CLI를 GitHub Actions에서 돌린다. 에이전트는 내가 아니라 저장소의 이름과 예산으로 일하고, 사람은 승인 지점에서만 결정한다.
  7. 파이프라인에 올리면 실행이 보인다. 비용과 실패를 재서 고치고, 더 싼 모델을 고를 수 있다.
01

Copilot이 도는 구조 01:30

발표자는 에이전트를 두 종류로 나눈다 00:50. 하나는 내가 직접 불러 쓰는 로컬 에이전트다. 다른 하나는 파이프라인에서 혼자 도는 자율 에이전트autonomous agent다. 둘 다 이해하려면 먼저 Copilot의 데이터 흐름을 알아야 한다.

입구는 여러 개다 01:40

입구특징
IDE편집기 안에서 쓴다. 에이전트를 만드는 화면도 있다
Copilot CLI데스크톱에서 쓰는 가벼운 인터페이스다. 세션을 github.com으로 넘겨 백그라운드에서 돌릴 수 있다. /remote 명령을 쓰면 휴대폰으로 로그인해 에이전트를 이어서 조종할 수 있다
SDKSlack이나 Teams 안에 사는 에이전트를 만든다. GitHub 라이선스가 없는 동료에게 기능 일부만 열어 줄 때 쓴다
클라우드 에이전트github.com에서 플랫폼이 호스팅하는 에이전트에게 일을 맡긴다 09:00

모든 입구는 하네스를 지난다 02:40

어느 입구로 들어오든 요청은 같은 곳에 닿는다. 발표자는 이것을 Copilot API 서비스라고 했고, 내부에서는 'Cappy'라고 부른다고 했다. 다른 말로는 하네스harness다. 모델을 감싸고 귀찮은 기반 작업을 대신 맡는 실행 틀이라는 뜻이다.

  • 입력을 잘게 나눠 모델에 보낸다
  • 오픈소스 코드를 그대로 되풀이하지 않는지 확인한다
  • 인증을 처리한다
  • 지표와 감사 로그audit log를 남긴다

하네스는 요청을 모델 제공사에 넘긴다. 답이 돌아오면 걸러서 사용자에게 보여 준다.

왜 알아 두나 입구가 달라도 같은 하네스를 거친다. 그래서 같은 에이전트를 IDE, CLI, 웹에서 똑같이 부를 수 있다. 뒤에 나오는 클라우드 에이전트 예시가 그 경우다.
02

기본 에이전트에서 배우기 03:30

Copilot CLI에는 처음부터 들어 있는 에이전트가 있다. /agents를 치면 목록이 나온다. 발표자는 이것부터 보라고 권한다. 에이전트든 스킬이든 형식은 같기 때문이다.

결국 다 마크다운이다.발표자의 표현을 옮김
explore · 탐색 04:10

코드베이스를 조사하는 연구용 에이전트다. 키워드나 슬래시 명령으로 부른다.

  • 작은 모델(Haiku)로 돈다
  • 코드를 둘러보는 데 가장 큰 모델은 필요 없다

교훈: 일의 크기에 맞는 모델을 고른다.

Rubber duck · 계획 검증 04:40

이미 써 둔 계획 문서를 다른 회사의 모델이 검토한다.

  • 예: Opus가 쓴 계획을 GPT가 한 번 더 본다
  • 학습 데이터와 모델 가중치가 달라 다른 눈으로 본다

교훈: 검토는 만든 모델과 다른 모델에게 맡긴다.

기본 에이전트는 모두 쓸 모델을 파일에 적어 둔다 04:50. 커스텀 에이전트custom agent를 만들 때도 똑같이 두 가지를 정한다. 어떤 모델을 쓸지, 그리고 어떤 지시를 줄지다.

03

1단계: 직접 만들기 05:00

기본 에이전트로 안 되는 일이 있다. 이럴 때 직접 만든다.

  • 우리 팀만 하는 작업이나 리뷰
  • 꼭 지켜야 하는 컴플라이언스나 규제 요건
  • 돌려야 하는 도구나 우리만의 검사 묶음

만드는 순서 05:20

  1. CLI에서 /agent 명령을 친다. 만들기 과정이 시작된다.
  2. 저장 위치를 고른다. 지금 Git 프로젝트에만 둘 수도 있고(프로젝트 수준), 어느 프로젝트에서나 쓰게 할 수도 있다(사용자 수준).
  3. 하고 싶은 일을 한 줄로 적고 Copilot에게 만들게 한다.
  4. 만들어진 파일을 읽고 고친다.

IDE에도 같은 만들기 화면이 있다 06:10.

한 줄이 파일이 되기까지 06:20

발표자는 "GitHub 변경 기록changelog에 가서 바뀐 것을 요약해 줘" 한 줄로 에이전트를 만들었다. Copilot이 채운 것은 다음과 같다.

채운 것내용
설명에이전트가 무엇을 하는지 적는다
front matter파일 맨 위 설정 부분의 형식을 맞춘다
성공 기준언제 일이 끝난 것인지 정리한다
방법어떤 순서로 일할지 초안을 쓴다

발표자 표현으로는 "조금 게을러도 된다." 사람은 큰 방향만 쓰고 세부는 Copilot이 채운다.

물론 고칠 수 있다 06:50. 예시 에이전트는 GitHub 로드맵부터 읽도록 만들어졌다. 로드맵 항목이 섞이는 게 싫다면 변경 기록으로 바로 가게 순서를 바꾸면 된다.

결과 07:10 하네스에서 도는 내 에이전트가 생겼다. 반복하는 일이 있으면 이 에이전트를 부르면 된다.
04

2단계: 팀에 나누기 07:20

에이전트를 만들고 나면 다음 질문은 "다른 사람은 어떻게 쓰게 하나"다. 발표자는 두 길을 보여 준다.

마켓플레이스 07:30

마켓플레이스marketplace는 특별한 시스템이 아니다. 보통 저장소의 한 폴더에 "이건 마켓플레이스다"라고 알리는 JSON을 조금 넣은 것이다. 이것만으로 가벼운 패키지 관리가 생긴다.

  • 구독하면 에이전트를 한꺼번에 업데이트할 수 있다
  • 에이전트에 버전을 매긴다
  • 보안 취약점이 생기면 사용자에게 알린다
발표자가 기업에 가서 먼저 하는 일 08:00 마켓플레이스 만들기다. 팀이 에이전트나 스킬을 모을 중앙 저장소가 없는 회사가 많다. 없으면 만들라는 것이 발표자의 조언이다. 이 저장소는 각자의 기기와 동기화되고, 새 에이전트를 밀어 보낼 수 있다.

조직 전용 저장소 .github-private 08:30

조직 안에 이름이 .github-private인 저장소를 만들면, 그 안의 에이전트 파일이 조직 전체에 공개된다. GitHub가 정한 이름 규칙이라 정확히 맞춰야 한다.

데모 저장소에는 에이전트가 세 개 있었다. github.com의 클라우드 에이전트 선택 목록에 그중 compliance bot이 그대로 떴다 09:10. 같은 에이전트가 모든 사람의 IDE와 CLI에도 들어간다.

비교마켓플레이스.github-private
범위조직 사이, 조직 밖까지 가능조직 안에서만
받는 방식사용자가 구독한다관리자가 조직 전체에 밀어 준다
예예제 모음 저장소 awesome-copilot을 마켓플레이스로 등록데모의 compliance bot

재사용이 비용을 줄이는 이유 09:50

나누는 목적은 편의만이 아니다. 발표자는 표준화와 비용을 든다.

  1. 이런 제품을 가장 싸게 쓰는 길은 캐시 적중cache hit이다. 같은 데이터가 정확히 똑같이 반복될 때 생긴다.
  2. 모두가 같은 에이전트로 같은 문제를 풀면 똑같은 요청이 늘어 캐시 적중률이 오른다.
  3. 사람마다 바퀴를 새로 발명하면 그만큼 캐시를 놓치고 청구액이 커진다.

공유 에이전트가 캐시 적중률을 얼마나 올리는지 발표에 수치는 없다. 프롬프트 캐시는 보통 요청의 앞부분이 이전 요청과 똑같을 때 맞는다.

05

3단계: 여러 저장소로 10:40

컴플라이언스 에이전트 같은 공용 에이전트에는 약점이 있다. 에이전트는 자기가 사는 저장소에서 시작한다. 다른 저장소에서 일하려면 그 저장소의 권한이 필요하다. 그러려면 그 저장소에서 에이전트를 시작해야 한다.

orchestrate: 저장소를 가로질러 늘리기 11:10

발표자가 말한 Copilot 앱에는 orchestrate라는 명령이 있다. 발표자는 이것을 저장소를 가로지르는 수평 확장horizontal scaling이라고 부른다.

  1. GitHub 이슈 여러 개를 에이전트의 목표로 정한다.
  2. orchestrate가 하위 에이전트subagent를 여러 개 띄운다.
  3. 하위 에이전트는 각자 일해야 할 저장소 안에서 시작한다. 그래서 권한 문제가 없다.
쓰는 장면 11:30 한 마이크로서비스의 API를 바꾸면, 그 API를 쓰는 다른 서비스도 고쳐야 한다. orchestrate로 여러 에이전트가 여러 저장소를 동시에 고치게 한다. 마켓플레이스나 관리자가 나눠 준 기성 에이전트를 불러와 각 저장소에 보낼 수 있다. orchestrate는 각 에이전트가 맡은 일에서 벗어나지 않게 붙잡는다.

여기까지가 로컬에서 에이전트를 쓰는 세 층이다 12:00. 만들고, 나누고, 여러 저장소로 넓힌다.

06

4단계: 파이프라인으로 12:10

어떤 에이전트는 내 컴퓨터에서 돌 이유가 없다. 저장소를 관리하는 유지보수 작업이 그렇다.

  • 예산: 내 예산이 아니라 저장소의 예산으로 돌아야 한다.
  • 신원: 내 이름이 아니라 저장소의 이름으로 행동해야 한다.
모든 에이전트가 '나'로서 행동할 필요는 없다.발표자의 표현을 옮김

agentic workflows 12:40

GitHub는 이를 위해 agentic workflows라는 프레임워크를 내놓았다. 원리는 간단하다.

  1. Copilot CLI는 헤드리스 모드headless mode로 쓸 수 있다. 화면에서 대화하지 않고 명령 한 번으로 실행하는 방식이다.
  2. -p 옵션에 한 번짜리 프롬프트를 넘긴다.
  3. 이 실행을 GitHub Actions 러너나 다른 CI에서 돌린다 13:00. 그러면 파이프라인에서 도는 에이전트가 된다.

저장소에서 일어나는 일을 계기trigger로 걸 수 있다. 발표자가 든 예는 다음과 같다.

계기에이전트가 할 일
릴리스할 때문서를 갱신한다
매주컨텍스트 파일을 갱신한다
정해진 일정각종 유지보수 작업을 한다
07

사람이 승인하는 파이프라인 13:20

발표자가 드는 예는 중복 코드다. 에이전트로 개발을 많이 하는 저장소에서 지금 가장 큰 문제 중 하나라고 한다.

  • 스파게티 코드와 중복 코드가 계속 쌓인다.
  • 에이전트는 함수를 제대로 나눠 구현하는 데 게으르다.
  • 네임스페이스namespace를 정리하는 데는 더 게으르다. 그래서 같은 코드가 계속 복제된다.

그래서 코드베이스를 살펴 중복을 줄일 곳을 찾고, 그걸 이슈로 만드는 에이전트를 둔다. agentic workflows는 여기에 사람 승인 지점human in the loop을 넣어 준다 13:50. 다음 단계에 돈을 쓸지 사람이 보고 정한다.

단계누가하는 일
1 발견파이프라인 에이전트 (cron 일정)저장소를 살펴 개선할 곳 세 군데를 찾아 이슈로 만든다
2 판단개발자이슈를 읽고 고칠 가치가 있는지 정한다. 있으면 이슈 댓글에 슬래시 명령을 달아 "다음 단계로" 보낸다
3 계획PRD를 쓰는 제품 관리자 에이전트기능 범위를 정하고 계획을 쓴다
4 구현플랫폼의 Copilot넘겨받은 계획대로 구현한다

정리: 네 단계 지도 18:50

핵심 정리

  1. 에이전트는 모델과 지시문을 담은 마크다운 파일이다. 커스텀 에이전트는 둘을 직접 정한다.
  2. IDE, CLI, SDK, 웹 어느 입구든 같은 하네스를 거친다. 인증, 기록, 출력 필터를 하네스가 맡는다.
  3. 일에 맞는 모델을 고른다. 탐색은 작은 모델, 계획 검토는 만든 모델과 다른 회사 모델이다.
  4. /agent에 한 줄 설명만 주면 Copilot이 설명, front matter, 성공 기준, 방법을 채운다. 사람은 고치기만 한다.
  5. 만든 에이전트는 마켓플레이스나 .github-private로 나눈다. 버전, 일괄 업데이트, 보안 알림이 따라온다.
  6. 같은 에이전트로 같은 문제를 풀면 캐시 적중이 늘어 비용이 준다고 발표자는 말한다.
  7. 에이전트는 자기 저장소 밖에 권한이 없다. orchestrate는 이슈를 목표로 받아 각 저장소 안에서 하위 에이전트를 띄운다.
  8. 유지보수 작업은 저장소의 신원과 예산으로 파이프라인에서 돌린다. agentic workflows는 CLI 헤드리스 실행을 Actions에 올린 것이다.
  9. 사람은 매 단계가 아니라 돈이 드는 다음 단계 앞에서 슬래시 명령으로 결정한다.
  10. 파이프라인에 올리면 실행이 보인다. OTel로 비용과 실패를 재고, P90 초과를 조사하고, 더 싼 모델을 고른다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 나눈 에이전트의 두 종류는?
내가 직접 불러 쓰는 로컬 에이전트, 그리고 파이프라인에서 혼자 도는 자율 에이전트.
Q2IDE, CLI, SDK 어느 입구로 들어와도 거치는 곳은? 무슨 일을 하나?
하네스(Copilot API 서비스). 입력을 나눠 모델에 보내고, 오픈소스 코드 되풀이를 확인하고, 인증과 지표·감사 로그를 처리하고, 모델의 답을 걸러 보여 준다.
Q3explore와 Rubber duck 에이전트는 모델 선택에 대해 무엇을 보여 주나?
explore는 탐색에 큰 모델이 필요 없어 작은 모델(Haiku)을 쓴다. Rubber duck은 Opus가 쓴 계획을 GPT 같은 다른 회사 모델이 검토한다. 학습 데이터와 가중치가 달라 다른 눈으로 보기 때문이다.
Q4/agent에 한 줄 설명만 주면 Copilot이 채워 주는 것은?
설명, front matter 형식, 성공 기준, 방법 초안. 사람은 큰 방향만 쓰고, 만들어진 파일을 고친다.
Q5마켓플레이스는 무엇이고, 구독하면 무엇이 생기나?
마켓플레이스임을 알리는 JSON을 넣은 저장소다. 구독하면 에이전트를 한꺼번에 업데이트하고, 버전을 관리하고, 보안 취약점 알림을 받는다.
Q6마켓플레이스와 .github-private의 차이는?
마켓플레이스는 조직 사이, 조직 밖까지 나눌 수 있고 사용자가 구독한다. .github-private는 조직 안에서만 쓰고 관리자가 전체에 밀어 준다.
Q7발표자는 왜 재사용 에이전트가 비용을 줄인다고 하나?
같은 에이전트로 같은 문제를 풀면 똑같은 요청이 늘어 캐시 적중률이 오른다. 캐시 적중이 이런 제품을 가장 싸게 쓰는 길이다.
Q8공용 에이전트가 다른 저장소에서 일하기 어려운 이유와 orchestrate의 해법은?
에이전트는 자기가 사는 저장소에서 시작해 다른 저장소의 권한이 없다. orchestrate는 이슈 여러 개를 목표로 받아 각 저장소 안에서 하위 에이전트를 띄운다.
Q9유지보수 에이전트를 내 노트북이 아니라 파이프라인에서 돌려야 하는 이유 두 가지는?
내 예산이 아니라 저장소의 예산으로, 내 이름이 아니라 저장소의 이름으로 일해야 하기 때문이다.
Q10agentic workflows의 원리는?
Copilot CLI를 헤드리스 모드로 -p에 한 번짜리 프롬프트를 줘서 실행한다. 이걸 GitHub Actions 러너나 CI에서 릴리스, 주간 일정 같은 계기로 돌린다.
Q11중복 코드 정리 흐름에서 사람이 끼는 두 지점은?
에이전트가 만든 이슈를 읽고 슬래시 명령 댓글로 다음 단계를 허락하는 판단 단계, 그리고 구현된 코드를 받을지 정하는 수락 단계.
Q12파이프라인에서 에이전트 비용을 줄이는 방법 두 가지는?
예상 비용의 P90을 넘은 실행은 원인을 조사하게 한다. 도구 호출이 계속 실패하면 front matter나 모델을 바꿔 A/B 테스트하고, 같은 결과면 더 싼 모델로 바꾼다.
