사람이 루프에서 빠진 뒤의 Claude Code 사용법

모델이 좋아지면서 사람은 매 단계를 승인하는 자리에서 물러났다. 예전에 사람이 하던 조종, 승인, 제한, 확인, 시작은 사라지지 않았다. 모델, 하네스, 실행 환경이 나눠 맡는다. 이 발표는 그 일을 어디에 어떻게 넘기는지 차례로 보여 준다.

원본 영상: Rethinking Claude Code Best Practices 발표: Lydia Hallie (Anthropic, Claude Code 팀)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 기능 설명은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 "Cloud Code", "Opus 55"처럼 뭉개진 이름은 Claude Code, Opus 5.5 같은 알려진 이름으로 바로잡았다. 확실하지 않은 이름에는 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자는 Claude Code를 만드는 Anthropic 소속이다. 발표 전체가 자사 제품의 기능과 성과를 다루므로 그 점을 감안해 읽자.

3분 요약
  1. 예전 세션은 짧았고 사람이 계속 고쳐 주고 승인했다. 지금 Anthropic에서는 수십 개 세션이 몇 시간씩 돌고, 사람은 관리자 역할을 한다.
  2. 사람이 빠진 자리는 모델, 하네스, 실행 환경 중 하나가 맡아야 한다.
  3. 첫걸음은 쉽다. 최신 모델과 auto mode라는 기본값을 쓰고, CLAUDE.md에서 강한 경고문과 뻔한 설명을 지운다.
  4. 어려운 질문은 "사람이 없어도 괜찮은가"다. 안전은 deny 규칙 → 샌드박스 → 클라우드 세션 순서로 보장 범위를 넓힌다.
  5. 규칙으로 막을지 정하는 기준은 하나다. Claude가 한 번 틀렸을 때 되돌릴 수 있는가.
  6. 품질은 통과/실패로 답이 나오는 검증 지점으로 지킨다. 꼭 돌아야 하는 검사는 프롬프트가 아니라 훅에 넣는다.
  7. 세션이 늘어나면 CI가 공통 관문이 된다. 그다음 단계는 오케스트레이터 세션 하나가 다른 세션을 띄우고 검증하는 것이다.
01

세션의 모습이 바뀌었다 00:30

발표자는 올해 초의 세션과 지금의 세션을 나란히 놓고 시작한다. 올해 초에는 Opus 4.5 같은 모델을 썼다. 당시 기준으로는 좋은 모델이었지만 지금보다 훨씬 일찍 멈췄다.

올해 초사람이 루프 안에 있다세션이 짧다. 사람이 계속 고쳐 주고 상기시킨다. CLAUDE.md에 "important!" 같은 문구를 넣는다. 명령을 하나씩 승인하거나, 위험을 감수하고 --dangerously-skip-permissions를 쓴다. 세션은 한두 개다.
→
지금 (Anthropic)사람은 관리자다수십 개 세션이 동시에 몇 시간씩 돈다. 세션이 스스로 결과를 검증한다. 세션이 다른 세션을 지휘하기도 한다.

발표자는 Anthropic이 10월에 낸 블로그 글을 인용한다. 하루에 반영되는 변경 수가 5월의 약 2,500건에서 9월에는 3만 건 이상으로 늘었다는 내용이다.

일은 훨씬 많이 끝난다. 대신 개발자는 무엇에 집중할지 다시 정해야 한다.

02

사람이 빠진 자리를 누가 맡나 02:00

올해 초의 모범 사례는 대부분 사람이 직접 하는 일이었다. 세션을 조종하고, 명령을 승인하고, 하면 안 되는 일을 막고, 결과를 확인하고, 세션을 시작했다.

사람이 이 루프에서 한 발 빠질 때마다 다른 무언가가 그 일을 이어받아야 한다. 후보는 셋이다.

이어받는 쪽뜻
모델의도와 코드베이스를 이해하고 스스로 판단한다
하네스 harness모델을 감싸는 실행 틀이다. 여기서는 Claude Code 자체다. 권한 규칙, 훅 같은 것이 여기에 속한다
실행 환경세션이 돌아가는 기계다. 무엇을 읽고 어디에 접속할 수 있는지를 정한다
발표가 답하려는 두 질문 명령을 하나씩 승인하지 않고 세션을 여러 개 돌린다면, 코드 품질은 어떻게 보장하나. 세션이 감독 없이 몇 시간씩 돈다면, 안전은 어떻게 보장하나.
03

기본값부터 바꾼다 02:50

발표자는 옛 세션을 하나씩 고쳐 가며 설명한다. 첫 수정은 요즘의 기본값을 그대로 쓰는 것이다.

  • 모델: Opus 4.5를 Opus 5.5로 바꾼다. 발표자는 Opus 5.5가 의도와 코드베이스를 훨씬 잘 이해해서 세션 중간에 방향을 잡아 줄 일이 크게 줄었다고 말한다.
  • 권한: 수동 승인을 auto mode로 바꾼다. 발표자에 따르면 8월부터 auto mode가 기본 권한 모드가 되기 시작했다.

발표 첫머리에서 발표자는 이번 주에 Fable 5.2도 나왔다고 소개한다. 두 모델 모두 오래 걸리는 작업과 코드베이스 이해에 강하고, Fable은 자기 결과를 검증하는 일도 잘한다는 것이 발표자의 설명이다. 00:10

이 두 가지만으로 조종은 모델이, 승인은 auto mode가 맡는다. 루프에서 빠지는 것 자체는 쉽다. 어려운 것은 그다음이다.

04

CLAUDE.md를 줄인다 03:10

CLAUDE.md는 Claude Code가 세션마다 읽는 프로젝트 지침 파일이다. 모델이 의도를 더 잘 이해하게 되면 이 파일에 적을 내용도 달라진다.

지운다
  • "important", "절대 하지 마!" 같은 강한 경고 문구
  • 어떤 기술 스택을 쓰는지
  • 어디를 찾아보면 되는지

발표자에 따르면 요즘 모델에는 강한 경고문이 필요 없다. 오히려 모델이 옆길로 새서 도구 호출이 늘고 결과가 나빠질 수 있다.

남긴다
  • Claude가 코드만 봐서는 알 수 없는 것
  • 발표의 예: 어떤 서비스가 아직 옛 소스에 의존하는데, 코드에는 그 참조가 직접 나오지 않는 경우

기준: 코드에서 보이지 않는 것만 적는다.

점검 명령 03:50 발표자는 이 정리를 돕는 명령을 소개한다. 자막에는 "doctor prompt audit"로 들린다(추정). 지금 쓰는 모델을 기준으로 CLAUDE.md와 스킬을 검사해서, 새 모델에 더는 필요 없는 내용을 찾아 준다고 한다.
05

auto mode를 조정한다 04:10

auto mode는 권한 모드의 하나다. 프로젝트 안의 파일을 읽거나 고치는 일을 뺀 거의 모든 동작에 별도의 분류기 classifier를 돌린다. 분류기는 명령이 안전한지 판정하는 작은 심사 모델이다.

  • 안전하다고 아는 명령은 자동으로 허용한다. 예: 테스트 실행, 의존성 설치.
  • 안전한지 확신이 없는 명령은 막는다.

대부분은 이 동작이 맞다. 하지만 걸리는 경우가 있다. 발표의 예는 스테이징 배포다. 배포용 저장소에 푸시해야 하는데, auto mode는 기본적으로 지금 폴더와 지금 저장소만 신뢰한다. 그래서 푸시가 막히고 사람이 다시 루프로 불려 온다.

auto mode에서도 승인 요청이 잦다면 04:50 먼저 설정을 본다. auto mode는 설정 파일에 평범한 영어 문장으로 조정할 수 있다. 이 문장이 분류기에 전달되고, 분류기가 그것을 보고 허용과 거부를 정한다. 신뢰하는 저장소, 버킷, 도메인과 항상 허용할 것, 절대 하면 안 되는 것을 적는다.
06

안전 1: deny 규칙 05:30

모델을 올리고 auto mode를 켜는 것은 둘 다 모델에 기대는 방법이다. 모델은 대체로 시킨 대로 하지만, 그것이 보장은 아니다.

발표자는 Anthropic이 8월에 낸 연구를 인용한다. auto mode와 실제 사람의 승인을 비교한 실험이다.

auto mode가 사람보다 훨씬 낫다. 그래도 위험한 명령 열 개 중 하나쯤은 통과했다. 보장이 필요하면 하네스에서 강제해야 한다. 여기서 옛 모범 사례인 권한 규칙이 여전히 쓸모 있다.

deny 규칙은 분류기보다 먼저 본다 06:10

deny 규칙은 특정 도구 호출을 무조건 거부하는 권한 규칙이다. Claude Code는 auto mode 분류기보다 이 규칙을 먼저 확인한다. 도구 호출이 deny 규칙에 걸리면 분류기는 그 호출을 보지도 못한다. 그래서 Claude가 어떤 일을 절대 하지 않게 하려면 deny 규칙이 가장 확실하다.

무엇을 규칙으로 만드나 06:30

Claude가 이걸 한 번 틀리면, 되돌릴 수 있는가?발표자가 제시한 판단 기준을 옮김
상황되돌릴 수 있나맡길 곳
코드를 잘못 썼다되돌릴 수 있다모델에 맡긴다
커밋하지 않은 변경을 날렸다못 되돌린다규칙으로 막는다
비밀 키를 읽어서 대화 기록에 남았다못 되돌린다규칙으로 막는다

발표의 예는 .env 파일이다. auto mode는 기본적으로 이 파일을 읽는 것을 허용한다. 절대 읽지 못하게 하려면 deny 규칙을 추가한다. 그러면 cat 같은 명령으로도 이 파일을 열 수 없다.

// 예시: 발표에는 코드가 나오지 않는다. 정확한 문법은 공식 문서에서 확인한다.
{ "permissions": { "deny": ["Read(./.env)"] } }
07

안전 2: 샌드박스 07:10

deny 규칙만으로는 부족한 경우가 있다. 명령에 부작용이 따르는 경우다.

평범한 npm test가 위험해지는 길 npm test는 그냥 테스트라서 auto mode가 실행한다. 하지만 이 스크립트는 내가 쓰지 않은 코드, 즉 의존성을 실행한다. Claude가 잠깐 확인하려고 직접 쓴 스크립트도 마찬가지다. 그중 하나가 오염돼 있으면 .env나 SSH 키를 열어서 처음 보는 서버로 보낼 수 있다. 사람이 승인하고 있었어도 "허용"을 눌렀을 것이다. 거절할 이유가 눈에 보이지 않기 때문이다.

권한 규칙은 도구 호출을 실행할지만 정한다. 실행된 뒤 그 명령이 무엇에 닿을 수 있는지는 제한하지 못한다. 그렇다고 npm test를 막을 수는 없다. Claude가 자기 작업을 확인하는 수단이기 때문이다. 그래서 명령이 아니라 명령이 도는 환경을 제한한다.

샌드박스가 하는 일 08:10

샌드박스 sandbox는 명령을 격리된 울타리 안에서 돌리는 장치다. 자기 컴퓨터에서 Claude Code를 쓸 때 켤 수 있다.

  • 명령이 읽을 수 있는 파일, 쓸 수 있는 폴더, 접속할 수 있는 호스트를 정한다.
  • 이 제한은 운영체제가 강제한다.
  • 그 명령이 띄운 자식 프로세스에도 똑같이 적용된다.
deny 규칙만deny 규칙 + 샌드박스
누가 확인하나Claude Code가 명령 실행 전에 확인한다같은 규칙이 운영체제로 넘어간다
무엇이 보이나npm test라는 글자만 보인다. 스크립트가 여는 파일은 안 보인다의존성이 실제로 .env를 여는 순간을 운영체제가 막는다
네트워크제한하지 못한다승인하지 않은 호스트에는 접속하지 못한다

기본 설정에서 샌드박스 안의 명령은 여전히 컴퓨터의 대부분을 읽을 수 있다. SSH 키가 걱정되면 그 경로에 규칙을 하나 더 추가해야 한다.

샌드박스의 한계 09:10 샌드박스는 Claude가 실행하는 셸 명령과 그 명령이 띄운 것만 덮는다. Claude 자체의 파일 작업(자막에는 "own files"로 들림, 추정), MCP 서버, 훅은 모두 샌드박스 밖에서 돈다. 세션의 나머지는 여전히 내 컴퓨터와 그 안의 모든 것 위에서 돈다.
08

안전 3: 클라우드 세션 09:20

가장 좋은 것은 지킬 것이 처음부터 없는 곳에서 세션 전체를 돌리는 것이다. 그것이 클라우드 세션이다. 세션이 자기만의 기계와 저장소의 새 복사본을 받는다.

자막은 Claude와 cloud를 모두 "Cloud"로 적는다. 이 대목은 "자기 기계를 받는다", "노트북을 닫아도 돈다"는 설명으로 보아 클라우드 세션으로 읽었다.

  • 노트북을 닫아도 계속 돈다. 몇 시간짜리 세션에 꼭 필요한 성질이다.
  • .env 문제가 저절로 사라진다. 이 파일은 Git에 없으므로 그 기계에도 없다. SSH 키와 GitHub 토큰도 없다.
  • API 키가 필요하면 비밀 값으로 따로 넣는다. 자막에는 "network secret"으로 들린다(추정). 세션이 도중에 "API 키가 없다"고 알려 준다. 키는 모델에 전달되지 않은 채로 쓰인다.
  • 네트워크는 기본적으로 좁다. 패키지 레지스트리와 GitHub 정도만 열려 있다. 다른 호스트는 환경 설정에 도메인을 직접 추가해야 닿는다.
기계는 버려도 되지만, 밖으로 나간 것은 못 버린다 10:20 클라우드 기계는 일회용이다. 하지만 푸시한 커밋이나 커넥터로 보낸 메시지는 기계를 지워도 남는다. 그래서 클라우드에서도 auto mode를 쓰고, deny 규칙을 저장소에 커밋해서 함께 따라가게 한다. 강제 푸시나 커밋에 섞인 비밀 값 같은 것을 여기서 잡는다.

여러 세션과 CI 13:20

혼자 둬도 안심되는 세션이 하나 생겼다. 이제 몇 개 더 띄울 수 있다. 세션마다 자기 기계가 있어서 같은 폴더에서 부딪히지 않는다. 워크트리를 직접 신경 쓸 일도 줄어든다.

여기서 가장 중요한 장치는 CI다. 모든 세션은 결국 PR을 연다. CI는 세션이 어떻게 설정됐든, Claude가 도중에 무엇을 결정했든, 모든 PR에 같은 검사를 돌린다.

  • CI 자동 수정 CI auto-fix: 켜 두면 Claude가 검사 실패를 보고 돌아가서 고친다. 검사가 잡을 수 있었던 문제에 사람의 리뷰 시간을 쓰지 않는다. 14:10
  • 준비되면 병합 merge when ready: 일부 PR에 켤 수 있다. 모든 검사가 통과하면 GitHub가 PR을 병합한다. 기본값은 아니다. 변경이 얼마나 위험한지에 따라 정한다. 14:20

오케스트레이터 세션 15:10

발표자가 보는 다음 단계는 세션을 사람이 일일이 시작하지 않는 것이다. Anthropic은 이미 이쪽으로 가고 있다고 한다. 발표자는 스스로 맥락 전환에 서툴다고 말한다. 세션 여러 개를 동시에 관리하는 일이 늘 잘되지는 않는다는 것이다.

그래서 메인 세션 하나를 오케스트레이터 orchestrator, 즉 지휘자로 둔다. 발표자는 아직 베타인 Claude Code projects에서 이 모습을 볼 수 있다고 소개한다.

  1. 사람이 메인 세션에 무엇을 해야 하는지 말한다.
  2. 메인 세션이 일을 나누고, 과제마다 새 세션을 띄운다. 이 세션을 스레드 thread라고 부른다.
  3. 메인 세션이 돌아온 결과를 추적하고 검증한다.
  4. 덜 끝난 결과는 돌려보낸다. 모든 검사를 통과할 때까지 반복한다.

사람은 세션 여덟 개가 아니라 하나와만 이야기한다.

코드를 직접 쓰지 않는다. 무엇을 할지 정하고 돌아온 결과를 판단한다.

핵심 정리

  1. 세션은 "짧고 사람이 붙어 있는 것"에서 "수십 개가 몇 시간씩 도는 것"으로 바뀌었다. 사람은 관리자가 됐다.
  2. 사람이 빠진 일은 모델, 하네스, 실행 환경 중 하나가 이어받아야 한다.
  3. 최신 모델과 auto mode라는 기본값만 써도 조종과 승인은 대부분 넘어간다.
  4. CLAUDE.md에는 코드에서 보이지 않는 것만 남긴다. 강한 경고문은 요즘 모델에서 오히려 결과를 나쁘게 할 수 있다.
  5. auto mode가 자주 막으면 설정에 신뢰하는 저장소와 도메인을 평범한 문장으로 적는다.
  6. auto mode는 사람보다 위험한 명령을 훨씬 잘 막지만(89% 대 약 14%) 보장은 아니다. 보장은 하네스에서 강제한다.
  7. 규칙으로 막을지는 한 번 틀렸을 때 되돌릴 수 있는가로 정한다.
  8. 권한은 실행 여부만 정한다. 실행 중에 닿는 범위는 샌드박스와 클라우드 세션이 제한한다. 그래도 밖으로 나간 커밋과 메시지는 되돌릴 수 없다.
  9. 품질은 통과/실패로 답이 나오는 검증 지점으로 지킨다. 꼭 돌아야 하는 검사는 훅에 넣고, 실패 시 종료 코드 2로 끝낸다.
  10. 세션이 늘면 CI가 공통 관문이다. 그다음은 오케스트레이터 세션이 스레드를 띄우고 검증하는 구조다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1사람이 루프에서 빠질 때 그 일을 이어받는 세 가지는?
모델, 하네스(Claude Code 자체의 규칙과 훅), 실행 환경(세션이 도는 기계).
Q2CLAUDE.md에 남겨야 하는 내용의 기준은?
Claude가 코드만 봐서는 알 수 없는 것. 예를 들어 코드에 직접 참조가 없는 옛 소스 의존성이다. 기술 스택이나 찾아볼 위치, 강한 경고 문구는 뺀다.
Q3auto mode는 어떤 동작에 분류기를 돌리고, 기본적으로 무엇을 신뢰하나?
프로젝트 안의 파일 읽기와 수정을 뺀 거의 모든 동작에 분류기를 돌린다. 기본적으로 지금 폴더와 지금 저장소만 신뢰한다. 그래서 다른 저장소로 푸시하는 배포는 막힌다.
Q4발표자가 인용한 연구에서 사람과 auto mode의 수치는? 결론은?
사람은 약 14%만 명백히 위험한 명령을 잡아냈고, auto mode는 89%를 막았다. auto mode가 훨씬 낫지만 열 개 중 하나쯤은 통과한다. 보장이 필요하면 하네스에서 강제해야 한다.
Q5deny 규칙이 auto mode보다 확실한 이유는?
Claude Code가 분류기보다 deny 규칙을 먼저 확인한다. 규칙에 걸린 도구 호출은 분류기에 도달하지도 않는다.
Q6무엇을 deny 규칙으로 만들지 정하는 질문은?
Claude가 한 번 틀렸을 때 되돌릴 수 있는가. 잘못 쓴 코드는 되돌릴 수 있으니 모델에 맡긴다. 커밋 안 된 변경을 날리거나 비밀 키를 읽는 일은 되돌릴 수 없으니 규칙으로 막는다.
Q7.env에 deny 규칙이 있어도 npm test가 위험할 수 있는 이유는?
권한 규칙은 도구 호출을 실행할지만 정한다. Claude Code에는 "npm test"라는 글자만 보이고, 그 스크립트가 실행하는 의존성이 어떤 파일을 여는지는 보이지 않는다.
Q8샌드박스가 덮지 못하는 것은?
샌드박스는 셸 명령과 그 자식 프로세스만 덮는다. MCP 서버, 훅 등은 샌드박스 밖, 즉 내 컴퓨터 위에서 그대로 돈다. 또 기본 설정에서는 컴퓨터의 대부분을 여전히 읽을 수 있다.
Q9클라우드 세션에서도 auto mode와 deny 규칙이 필요한 이유는?
기계는 일회용이지만 밖으로 나간 것은 남는다. 푸시한 커밋, 커넥터로 보낸 메시지가 그렇다. 강제 푸시나 커밋에 섞인 비밀 값을 막으려면 규칙을 저장소에 커밋해서 함께 가져가야 한다.
Q10검증 지점이 될 수 있는 것의 조건은? 예는?
통과 또는 실패로 답이 나오는 것. 테스트, 빌드, 스크린샷 등이다. 사람은 변경 전체 대신 이 지점들을 리뷰한다.
Q11훅 스크립트가 종료 코드 2로 끝나야 하는 이유는?
발표자에 따르면 종료 코드 1이면 Claude Code가 과제를 그냥 완료로 표시한다. 2여야 Claude가 돌아가서 고친다.
Q12오케스트레이터 구조에서 메인 세션과 스레드의 역할, 그리고 발표자가 추천한 모델은?
메인 세션은 코드를 쓰지 않고 일을 나누고 결과를 판단한다(Fable). 스레드는 실제 작업을 한다(Opus 5.5). 두 모델은 따로 지정할 수 있다.

종료 코드Exit code. 프로그램이 끝나며 남기는 숫자. 0은 성공, 그 밖은 실패를 뜻한다
검증 지점작업 중간에 통과/실패로 결과를 확인하는 곳. 테스트, 빌드, 스크린샷 등
CIContinuous Integration. PR마다 같은 검사를 자동으로 돌리는 장치
워크트리Worktree. 한 저장소를 여러 폴더에 동시에 펼쳐 놓는 Git 기능
오케스트레이터Orchestrator. 일을 나눠 다른 세션에 맡기고 결과를 검증하는 메인 세션
스레드Thread. 오케스트레이터가 과제마다 띄우는 새 세션
컨텍스트 압축Compact. 길어진 대화를 요약해 모델이 볼 수 있는 분량 안으로 줄이는 것
