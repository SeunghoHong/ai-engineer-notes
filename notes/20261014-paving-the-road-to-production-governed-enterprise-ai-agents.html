에이전트를 프로덕션에 올리는 길

에이전트를 프로덕션에 올리려면 똑똑한 에이전트 하나보다 모든 에이전트가 함께 쓰는 기반이 먼저다. Credit Karma는 인증 게이트웨이, 사내 MCP 서버, 모니터링, 메모리, 평가, 비밀 차단, 토큰 절약을 저장소 템플릿에 묶어 모든 에이전트에 똑같이 깐다.

원본 영상: Paving the Road to Production: Governed Enterprise AI Agents 발표: Harish Gaggar (Intuit Credit Karma 시니어 스태프 소프트웨어 엔지니어, AI 분석 인프라 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말하거나 데모 화면으로 보여 준 것이고, 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 바로잡았다. 발표자 이름은 영상 제목의 표기를 따랐다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트가 프로덕션에서 실패하는 이유는 기반 통제가 빠져서다. 인증, 도구, 기록, 기억, 비밀 차단, 토큰 절약 장치가 없다.
  2. 새 에이전트를 등록하면 개발 포털이 저장소와 클라우드 자원을 한 번에 만든다. 메모리, 추적·평가, PII 차단, 컨텍스트 최적화가 처음부터 들어 있다.
  3. 모든 도구 호출은 MCP 게이트웨이를 지난다. 게이트웨이가 인증하고 알맞은 MCP 서버로 보낸다. 엔드포인트에 바로 붙는 길은 없다.
  4. MCP 서버는 사내에서 직접 만들고, 도구마다 보안팀 리뷰를 거친다.
  5. 에이전트는 LangGraph로 짠다. 질문을 해석하고 분류한 뒤, 쓰기·민감 작업은 사람 승인을 기다린다. 모든 결과는 감사 로그에 남는다.
  6. 에이전트마다 질문, 답, 모델, 토큰 비용, 품질 점수를 첫날부터 저장한다. 나중에 투자 효과를 물을 때 답할 근거가 된다.
  7. 컨텍스트 최적화 데모에서 같은 질문의 토큰이 24,000에서 2,400으로 줄었다. 평소 절감률은 70~78%라고 한다.
01

에이전트가 프로덕션에서 무너지는 이유 01:30

발표자는 실패의 원인을 하나로 묶는다. 기반 통제foundation controls가 빠져 있다는 것이다. 기반 통제는 어떤 에이전트든 공통으로 갖춰야 할 인증, 기록, 비용, 보안 장치를 말한다.

아래 표의 MCPModel Context Protocol는 AI가 외부 도구와 데이터를 쓰는 표준 규약이다. 발표자가 던진 질문을 표로 옮기면 이렇다.

빠지기 쉬운 것스스로 물어볼 질문
게이트웨이에이전트가 먼저 알맞은 인증 공급자로 인증받은 뒤, 알맞은 MCP 서버로 연결되나?
알맞은 도구MCP 서버에 이 질문을 처리할 도구가 있나?
추적과 평가에이전트에 보낸 모든 질문이 기록되나? 답의 품질을 평가하나?
메모리며칠에 걸쳐 대화해도 예전에 물은 것을 기억하나?
컨텍스트 최적화토큰을 아끼는 장치가 있나?
비밀 차단비밀값이 LLM, 트레이스, 메모리 DB로 새지 않게 막나?
마법 같은 에이전트는 없다 발표자는 이 발표에서 마법 같은 에이전트를 만들지 않는다고 먼저 밝힌다. 대신 위 질문 하나하나에 답하는 프레임워크를 보여 준다.
02

기반 프레임워크 여덟 가지 02:40

발표자의 해법은 핵심 네 가지와 보조 네 가지로 나뉜다.

핵심 네 가지 02:50
  • 에이전트 프레임워크: LangGraph를 쓴다. 질문에 맞춰 작업별 노드를 만든다. 마켓플레이스 플러그인, 스킬, 프롬프트를 쉽게 끼울 수 있다.
  • MCP 게이트웨이: 에이전트나 그 서비스 계정이 먼저 인증받는다. 그다음 알맞은 MCP 서버로 연결된다.
  • 직접 만든 MCP 서버: 질문을 처리할 도구를 사내에서 만든다.
  • 감사: 실제로 어떤 작업을 했는지 기록한다.
보조 네 가지 03:50
  • PII 차단: 개인정보와 비밀값을 막는다.
  • 추적과 평가: 기록과 평가 결과를 클라우드에 저장한다.
  • 메모리: 대화의 스레드와 체크포인트를 남긴다.
  • 컨텍스트 최적화: 질문 하나에 토큰을 너무 많이 쓰지 않게 줄인다.

이후 발표는 이 여덟 가지를 하나씩 설명한다. 먼저 이것들이 어떻게 모든 에이전트에 깔리는지부터 본다.

03

등록부터 배포까지 04:10

새 에이전트가 프로덕션에 가는 길은 정해져 있다. 개발자는 이 길만 따라가면 된다.

단계하는 일
1. 등록에이전트의 용도와 적용할 분야를 적는다. 시스템이 에이전트 ID를 만들어 준다.
2. 개발 포털 입력사내 개발 포털에 ID와 용도를 넣는다. 프레임워크(LangGraph나 LangChain), 언어(Python이나 TypeScript), 쓸 스킬과 프롬프트도 고른다.
3. 저장소 생성 05:10포털이 저장소를 만든다. 에이전트 프레임워크와 함께 메모리, 추적·평가, 컨텍스트 최적화, PII 차단 프레임워크가 들어 있다.
4. 로컬 테스트 06:00개발자가 저장소를 복제해 에이전트를 Docker 컨테이너로 빌드한다. 질문을 넣어 입력과 출력을 확인한다. 트레이스와 평가 결과는 SQLite나 BigQuery에 쌓아 본다.
5. PR 06:30승인 2개를 받으면 CI/CD로 넘어간다. PR은 에이전트를 중앙 에이전트 레지스트리에도 등록한다. 레지스트리에는 트레이스를 볼 수 있는 링크(Langfuse 링크로 추정)가 붙는다.
6. CI/CD로컬에서 만든 컨테이너를 프로덕션용으로 빌드한다. 이미지에 취약점이 없는지 검사한다. 보안 승인이 나면 이미지 레지스트리에 올린다.
7. 배포 07:00사내 배포 플랫폼이 쿠버네티스 클러스터의 지정된 네임스페이스에 에이전트를 올린다.

프레임워크를 저장소에 미리 넣는 이유 05:30

개발자가 이 프레임워크를 전부 챙기지는 않는다. AI 코딩 도구가 만들어 준 대로 두거나, 한두 개만 쓰는 경우가 많다. 그래서 회사 전체에 같은 프레임워크를 깐다. 그래야 방식이 일관되고, 결과를 한곳에 모아 볼 수 있다.

포털이 함께 만드는 프로덕션 자원 07:10

개발 포털은 저장소만 만들지 않는다. 다음 자원도 같이 만든다.

  • 워크로드 아이덴티티workload identity: 사람이 아니라 프로그램에 주는 클라우드 신원
  • 메모리 DB
  • 추적·평가 테이블
  • 에이전트 비밀 관리

모두 개발자가 입력한 이름을 바탕으로 만든다. 그래서 배포 시점에 에이전트는 자기가 어떤 신원으로 일할지 이미 안다. 쿠버네티스 서비스 계정과 Google Cloud 서비스 계정을 잇는 KSA-GSA 바인딩KSA-to-GSA binding도 끝나 있다. 바인딩이 되면 에이전트는 바로 이 자원들과 통신한다.

그다음 에이전트는 AI 게이트웨이, MCP 서버, 트레이싱용 Langfuse, 그 밖의 API 엔드포인트와 통신한다. 08:00

워크로드 아이덴티티, BigQuery, Cloud Spanner처럼 이 발표의 예는 대부분 Google Cloud 기준이다.

04

직접 만드는 MCP 서버 08:10

밖에 공개된 MCP 서버를 써도 된다. 하지만 폐쇄망air-gapped, 즉 외부 인터넷과 끊긴 환경에서 일한다면 직접 만들기를 강하게 권한다.

  1. FastMCP 패키지로 서버를 만든다. 그 안에 필요한 도구를 정의한다.
  2. 모든 도구는 사내 보안팀이 리뷰한다. 승인된 도구만 프로덕션에 나간다. 09:00
  3. 리뷰하면서 필터와 호출 한도를 건다. LLM에 갈 필요가 없는 필드는 막는다. 사용자가 받으면 안 되는 정보가 새지 않게 하려는 것이다.
  4. 트래픽은 MCP 클라이언트, MCP 게이트웨이, MCP 서버 순서로 흐른다. 사용자든 서비스 계정이든 게이트웨이 인증을 먼저 통과해야 도구를 쓸 수 있다.
05

MCP 게이트웨이: 인증과 연결을 한곳에서 09:40

게이트웨이도 폐쇄망이라면 사내에서 직접 만들 수 있다. 요청 하나가 흐르는 순서는 아래와 같다. 클라이언트는 로컬 코딩 도우미 도구일 수도, 에이전트일 수도 있다.

순서흐름하는 일
1클라이언트 → 게이트웨이첫 질문을 보내는 순간 한 번만 인증을 요청한다.
2게이트웨이세션 상태를 Redis에 저장한다.
3게이트웨이 → 클라이언트JWT 액세스 토큰을 돌려준다.
4 10:30클라이언트 → 게이트웨이어느 MCP 서버를 부를지 정하고 tools/call 요청을 보낸다. 경로에 서버 이름(네임스페이스)을 넣는다. 예: /github/mcp. 헤더에는 Authorization: Bearer <JWT>를 붙인다.
5게이트웨이 → MCP 서버경로를 보고 어느 서버인지 찾는다. JWT를 풀어 사용자 토큰을 요청에 붙인 뒤 그 서버로 보낸다.
6 11:00MCP 서버 → 실제 서비스서비스의 API를 부르고 ID 토큰을 교환한다. 사용자가 볼 권한이 있는 범위만 받아 온다.
7MCP 서버 → 게이트웨이 → 클라이언트받은 데이터를 게이트웨이가 받을 수 있는 형식으로 묶어 돌려준다.

경로와 헤더 모양은 발표의 설명을 옮긴 예시다. 발표자는 Artifactory와 GitHub를 예로 들었다.

핵심은 길이 하나라는 것 11:30 게이트웨이는 인증과 라우팅을 한곳에서 맡는 허브다. 코딩 도우미 도구든 에이전트든 엔드포인트에 바로 붙으면 안 된다. 반드시 게이트웨이에서 인증을 거친 뒤, MCP 서버를 통해 엔드포인트에 닿는다.
06

게이트웨이 모니터링 12:00

AI 에이전트는 지속적인 모니터링, 평가, 피드백 없이는 믿을 수 없다.발표자의 말을 옮김 · 12:10

그래서 게이트웨이에 모니터링을 붙인다. 에이전트에 호출이 들어오면 데이터가 세 갈래로 나간다.

데이터보내는 곳답하는 질문 (발표자의 예)
운영 로그로그 저장소: ELK, Loki, CloudWatch 중 하나최근 10분 동안 401 응답이 몇 번이었나? 토큰 갱신이 실패했을 때 OAuth는 무엇을 했나?
트레이스 13:00OpenTelemetry를 거쳐 Tempo이 요청에서 어느 도구가 느렸나? 호출이 에이전트에서 왔나, IDE에서 왔나? 실패한 호출의 정확한 에러는?
지표 13:30OpenTelemetry를 거쳐 Prometheus도구별 P95 지연은 얼마인가? 특정 시간에 인증 거부가 치솟았나?
시각화 13:50Grafana위 데이터를 모아 한 화면에서 본다.

트레이스trace는 요청 하나가 어떤 단계를 거쳤는지 따라간 기록이다. 지표metrics는 지연이나 에러 수처럼 시간에 따라 모은 숫자다. OpenTelemetry는 이 둘을 모아 처리한 뒤 뒤쪽 저장소로 보내는 오픈소스 도구다.

자막에는 시각화 도구가 "graph now"로 들렸다. Tempo, Prometheus, Loki와 함께 쓰는 Grafana로 바로잡았다.

07

에이전트 그래프와 사람 승인 14:00

에이전트는 대부분 LangGraph로 만든다. LangGraph는 LangChain 커뮤니티가 만든 프레임워크다. 작업 흐름을 그래프로 짜며 반복, 분기, 상태 관리를 지원한다. 여러 에이전트가 얽힌 복잡한 흐름에 맞다.

  1. 해석interpret: 어떤 종류의 질문인지, 어떤 답을 원하는지 파악한다. 그에 맞춰 계획을 세운다. 14:30
  2. 분류classify: 읽기인지, 수정인지, 삭제인지, 민감한 작업인지 가린다. 결과에 맞춰 계획을 조정한다.
  3. 계획 실행: 계획 자체가 하위 그래프다. 근거 수집 단계에서 MCP 게이트웨이로 인증받는다. 그다음 MCP 서버의 알맞은 도구로 데이터를 가져와 근거를 만든다. 15:00
  4. 검증과 정책 확인: 찾은 내용을 검증한 뒤 정책에 맞는지 확인한다. 15:40
읽기 전용 작업

바로 실행한다. 기록은 감사 로그audit log에 남긴다.

쓰기·민감 작업 15:50

사람 승인 단계HITL, human in the loop로 간다. 사람이 승인하면 실행한다.

승인이든 거절이든 결과는 감사 로그에 남는다.

합쳐 보면 16:10

에이전트가 무엇을 하든 요청이 지나는 길은 같다.

  1. 에이전트가 요청을 보낸다.
  2. MCP 게이트웨이가 인증한다.
  3. 게이트웨이가 알맞은 MCP 서버로 보낸다.
  4. MCP 서버가 알맞은 도구로 API 엔드포인트를 불러 응답을 받는다.
08

메모리: 스레드와 체크포인트 17:00

메모리 관리는 작업 흐름의 상태를 저장했다가 다시 불러오는 일이다. 질문을 여러 번 해도 흐름이 끊기지 않는다. 문제가 생겨도 저장된 지점부터 복구할 수 있다.

단위언제 생기나
스레드 thread에이전트에게 질문을 보내면 생긴다. 대화 하나에 해당한다.
실행 ID run ID스레드 안에서 질문할 때마다 하나씩 생긴다. 같은 스레드의 후속 질문도 새 실행 ID를 받는다.
체크포인트 checkpoint질문이 LangGraph의 특정 노드에서 처리될 때, 그 노드에서 상태를 저장한다.

저장소는 로컬 개발에서 SQLite를 쓴다. 프로덕션에서는 GCP라면 Cloud Spanner를 쓴다. Azure나 AWS에서는 같은 역할의 DB를 쓰면 된다. 18:00

데모: 메모리 DB에서 볼 수 있는 것 18:10

  • 처음에는 SQLite에 기록이 없다.
  • 질문을 하나 보내자 기록 한 건이 생긴다. 스레드 ID, 질문, 실행 시각이 들어 있다.
  • 한 스레드에 메시지가 몇 개 쌓였는지 조회할 수 있다.
  • 메타데이터로 호출된 도구 수, 스레드 ID, 실행 ID를 본다.
  • 어느 MCP 서버의 어떤 도구가 실행됐는지 본다.
  • LangGraph의 어느 노드를 어떤 순서로 지났는지 본다.
09

추적과 평가 19:50

게이트웨이 모니터링과 다르다 앞의 모니터링은 게이트웨이 운영을 본다. 여기서 말하는 추적은 에이전트 단위다.

에이전트 단위로 남기는 것은 이렇다.

  • 에이전트에 보낸 질문과 돌아온 답
  • 사용한 LLM 모델
  • 쓴 토큰 수와 비용
  • 평가 기준과 답의 품질

이 데이터는 첫날부터 저장해야 한다. 에이전트마다 자기 추적·평가 프로젝트와 테이블을 따로 가진다. 에이전트가 100개면 프로젝트도 100개다.

6개월 뒤 누군가 에이전트 성과와 토큰 사용량을 물을 수 있다. 그때 이 데이터를 모아 경영진용 대시보드를 만든다. 그 대시보드가 에이전트를 이렇게 많이 만든 투자 대비 효과ROI를 보여 준다. 20:40

데모: 테이블 여섯 개 21:00

테이블담는 것
작업 추적요청 ID, 세션 ID, 에이전트 이름, 질문, 답, 완료 여부, 걸린 시간, 사용 모델, 메타데이터
품질 검사 22:10실행 한 번마다 검사 8개. 성공, 지연, 비용, 도구 정확도, 안전성 등이 한 줄씩 들어간다.
평가 점수 22:30실행 한 번의 점수표. 모든 품질 항목을 0~1 점수로 한 줄에 담는다.
품질 지표 22:40실행 한 번을 깊이 본다. 답 품질, 안전성, 지연, 비용, 도구 통계를 중첩 필드로 넓은 한 줄에 담는다.
도구 호출 23:00어떤 MCP 도구가 돌았는지, 얼마나 걸렸는지, 성공했는지
실행 궤적 23:10실행을 단계별로 기록한다. LLM 호출과 그래프 상태가 계획, 요약 같은 순서대로 남는다.

테이블 이름은 발표자의 설명을 보고 붙였다. 실제 테이블 이름과 다를 수 있다.

PII 차단 23:20

PIIPersonally Identifiable Information는 특정인을 알아볼 수 있는 개인정보다. 이 발표에서는 API 키 같은 비밀값도 함께 다룬다.

에이전트를 쓰다 보면 비밀이 질문에 섞여 들어온다. 민감한 정보가 든 문서를 올리기도 하고, 입력하다가 API 키를 붙여 넣기도 한다.

  • 프레임워크가 데이터 종류별로 심각도를 정해 둔다.
  • 심각도가 90% 정도를 넘으면 즉시 막고 가린다redact. 23:50
  • 목표는 입력되는 순간, 타이핑하는 바로 그때 막는 것이다.
가린 비밀이 닿으면 안 되는 곳 24:00 LLM 모델, 메모리 DB, 추적·평가 테이블, 트레이싱 시스템. 네 곳 모두다.
11

컨텍스트 최적화 24:20

발표자가 가장 좋아한다고 밝힌 부분이다. 파일이나 데이터를 많이 올리면 질문 하나에 토큰을 많이 쓴다. 그래서 LLM에 보내기 전에 질문을 다듬고 가지치기pruning한다.

  1. 선택: 토큰 한도에 맞춰 보낼 내용을 고른다. 25:00
  2. 재정렬re-rank: 질문과 가장 관련 있는 정보가 무엇인지 순위를 다시 매긴다.
  3. 중복 제거dedupe: 겹치는 내용을 빼서 꼭 필요한 데이터만 남긴다.
  4. 압축: 남은 큰 내용을 줄인 뒤 LLM에 보낸다.

데모: 같은 질문, 최적화 전과 후 25:20

"내 JFrog Artifactory의 모든 아티팩트를 찾아 줘"라는 질문을 두 번 돌렸다. 한 번은 최적화 없이, 한 번은 최적화를 켜고 돌렸다. Slack 봇에서도 "Artifactory 전체 저장소의 내 Docker 이미지를 모두 알려 줘"로 같은 실험을 했다. 26:30

1,500은 24,000의 약 6%라서 Slack 봇 데모의 절감률은 약 94%다. 발표자는 두 데모를 모두 "약 90%"로 말했다.

발표자는 대부분의 경우 절감률이 70~78%라고 했다. 27:10 에이전트가 수천 개이고 하루에 질문이 많다면 아끼는 토큰도 그만큼 커진다.

발표자 팀이 직접 만든 사내 도구의 데모 수치다. 그 점을 감안해 읽자. 최적화 뒤에도 답의 품질이 그대로였는지는 발표에서 보여 주지 않았다.

핵심 정리

  1. 에이전트는 기반 통제가 빠져서 프로덕션에서 실패한다.
  2. 에이전트 하나가 아니라 모든 에이전트가 쓰는 엔터프라이즈 프레임워크를 먼저 만든다.
  3. 등록하면 개발 포털이 저장소, 워크로드 아이덴티티, 메모리 DB, 평가 테이블, 비밀 관리를 한 번에 만든다.
  4. 배포는 PR 승인 2개, CI/CD의 이미지 취약점 검사, 쿠버네티스 배포 순서로 진행된다.
  5. 폐쇄망이면 MCP 서버를 FastMCP로 직접 만들고, 도구마다 보안 리뷰를 거친다.
  6. MCP 게이트웨이가 JWT로 인증하고 경로의 네임스페이스로 서버를 고른다. 엔드포인트 직접 접근은 없다.
  7. 게이트웨이 운영 데이터는 로그, 트레이스, 지표로 나눠 쌓고 Grafana에서 본다.
  8. 에이전트 흐름은 해석, 분류, 근거 수집, 정책 확인 순서다. 쓰기·민감 작업은 사람이 승인하고 모든 결과는 감사 로그에 남는다.
  9. 메모리는 스레드, 실행 ID, 체크포인트로 남긴다. 평가 데이터는 에이전트마다 첫날부터 테이블에 쌓는다.
  10. 비밀은 입력되는 순간 가린다. 컨텍스트는 선택, 재정렬, 중복 제거, 압축으로 줄인다. 평소 절감률은 70~78%다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 꼽은, 에이전트가 프로덕션에서 실패하는 근본 이유는?
기반 통제가 빠져 있어서다. 게이트웨이 인증, 알맞은 도구, 추적과 평가, 메모리, 토큰 절약, 비밀 차단 장치가 없다.
Q2개발 포털이 저장소에 에이전트 프레임워크 말고 무엇을 넣나? 왜 넣나?
메모리, 추적·평가, 컨텍스트 최적화, PII 차단 프레임워크다. 개발자가 이걸 다 챙기지 않기 때문에, 회사 전체에서 일관되게 쓰고 결과를 한곳에서 보려고 넣는다.
Q3개발 포털이 저장소 말고 미리 만드는 프로덕션 자원은? 덕분에 배포 때 무엇이 쉬워지나?
워크로드 아이덴티티, 메모리 DB, 추적·평가 테이블, 비밀 관리다. 배포 시점에 에이전트가 자기 신원을 이미 알고 KSA-GSA 바인딩도 끝나 있어서, 바로 자원과 통신할 수 있다.
Q4사내 MCP 서버의 도구가 프로덕션에 나가기 전에 거치는 절차는?
사내 보안팀 리뷰다. 승인된 도구만 나간다. 리뷰하면서 필터, 호출 한도, LLM에 보낼 필요 없는 필드 차단을 정한다.
Q5MCP 게이트웨이가 첫 인증 요청을 받으면 하는 두 가지는?
세션 상태를 Redis에 저장하고, JWT 액세스 토큰을 클라이언트에 돌려준다.
Q6게이트웨이는 도구 호출을 어느 MCP 서버로 보낼지 어떻게 정하고, 보내기 전에 무엇을 하나?
요청 경로에 든 네임스페이스(예: /github/mcp)를 보고 정한다. JWT를 풀어 사용자 토큰을 요청에 붙인 뒤 보낸다. MCP 서버는 사용자가 볼 권한이 있는 범위만 돌려준다.
Q7게이트웨이 모니터링에서 로그, 트레이스, 지표는 각각 어디로 가나?
로그는 ELK, Loki, CloudWatch 같은 로그 저장소로 간다. 트레이스는 OpenTelemetry를 거쳐 Tempo로, 지표는 Prometheus로 간다. Grafana에서 모아 본다.
Q8에이전트 그래프에서 읽기 작업과 쓰기·민감 작업은 어떻게 다르게 처리되나?
읽기 작업은 바로 실행한다. 쓰기·민감 작업은 사람 승인을 기다리고, 승인되면 실행한다. 어느 쪽이든, 거절된 경우도 결과는 감사 로그에 남는다.
Q9메모리에서 스레드, 실행 ID, 체크포인트는 각각 언제 생기나?
대화를 시작하면 스레드가 생긴다. 그 안에서 질문할 때마다 실행 ID가 생긴다. 질문이 그래프의 노드에서 처리될 때 체크포인트가 저장된다.
Q10게이트웨이 모니터링과 추적·평가는 무엇이 다른가?
모니터링은 게이트웨이 운영(인증 실패, 지연, 에러)을 본다. 추적·평가는 에이전트 단위로 질문, 답, 모델, 토큰 비용, 품질 점수를 남긴다.
Q11PII 차단은 언제 막고, 막은 비밀이 가면 안 되는 곳은 어디인가?
입력되는 순간 막는다. 심각도가 90% 정도를 넘으면 가린다. LLM, 메모리 DB, 추적·평가 테이블, 트레이싱 시스템 어디에도 가면 안 된다.
Q12컨텍스트 최적화의 네 단계와 데모 결과는?
선택, 재정렬, 중복 제거, 압축이다. 데모에서 24,000 토큰이 2,400과 약 1,500으로 줄었다. 발표자는 평소 절감률을 70~78%로 말했다.
