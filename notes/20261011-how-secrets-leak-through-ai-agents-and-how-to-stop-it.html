AI 에이전트로 비밀이 새는 길, 막는 길

API 키와 비밀번호가 LLM의 입력으로 들어가는 순간, 그 비밀은 로그와 학습 데이터로 흘러갈 수 있다. 비밀 저장소를 모델이 아니라 실행 층에 묶고, 에이전트의 범위를 좁히고, 샌드박스를 과신하지 않는 것이 발표의 핵심이다.

원본 영상: How Secrets Leak Through AI Agents (and How to Stop It) 발표: Joshua Mo (Venice AI 개발자 관계 리드 엔지니어, 전 Rig 메인테이너)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실할 때만 알려진 이름으로 바로잡았고, 확실하지 않은 곳은 "(추정)"을 붙였다. mm:ss는 영상 위치다.

발표자는 프라이버시를 내세우는 AI 플랫폼 Venice AI 소속이다. Venice의 기능을 설명하는 대목은 제품 소개를 겸하므로 그 점을 감안해 읽자.

3분 요약
  1. 데이터 유출은 언젠가 일어난다. 저장하는 데이터가 적을수록 사고의 피해 범위가 줄어든다.
  2. 모델은 에이전트 시스템의 한 부분일 뿐이다. 모델을 감싼 런타임, 로그, 도구 호출이 비밀이 새는 진짜 통로다.
  3. 흔한 에이전트 구조에서는 런타임이 비밀 저장소에서 꺼낸 API 키를 LLM 추론 층에 그대로 넘긴다. 그러면 비밀이 로그와 학습 데이터로 흘러갈 수 있다.
  4. 효과가 있는 패턴: 개인정보 대신 해시, 분할 키 보관으로 암호화, 회수할 수 있는 핸들, 좁은 에이전트 범위, 프롬프트 인젝션 분류 층.
  5. 핵심 설계: 비밀 저장소를 추론 층이 아니라 실행 층에 묶는다. 그러면 LLM은 "무엇을 할지"만 정하고, 비밀은 결정적인 실행 층 안에만 머문다.
  6. 샌드박스와 VM은 보안을 크게 올리지만 만능이 아니다. 인터넷이 열려 있으면 외부 API로 데이터가 빠져나갈 수 있다. 권한을 계속 지켜봐야 한다.
  7. 하드웨어 수준에서는 신뢰 실행 환경이 추론을 격리하고 증명서를 돌려준다. 다만 도구 호출까지 기밀로 만드는 일은 아직 숙제다.
01

발표자와 Venice 00:10

발표자 Joshua Mo는 Venice AI에서 개발자 관계를 맡고 있다. 파트너십, 문서, 개발자 소통, 일부 엔지니어링을 담당한다. 그 전에는 Rust로 만든 AI 프레임워크 Rig의 리드 메인테이너였다.

Venice는 스스로를 "프라이버시를 지키고 제한이 없는 AI 플랫폼"이라고 소개한다. 발표자가 말한 특징은 이렇다.

  • 최신 오픈소스 모델을 호스팅한다.
  • OpenAI API와 완전히 호환된다.
  • 프롬프트와 대화를 저장하지 않는다.
  • 모델과 대화하는 웹 앱이 있다.
  • 영상·음성·이미지 생성과 전사를 묶은 창작자용 스튜디오가 있다.
02

왜 프라이버시인가 01:40

발표자의 출발점은 단순하다. 데이터 유출은 점점 "언젠가 일어나는 일"이 되고 있다. 그래서 평판 위험이 중요해진다.

  • 유출이 한 번만 나도 사용자는 신뢰를 거두고 다른 서비스로 옮긴다.
  • 기업 고객이라면 더 치명적이다. 발표자는 연 매출의 약 90%를 책임지는 고객 하나를 잃는 상황을 예로 들었다.
  • 민감한 데이터를 많이 갖고 있을수록 같은 사고의 피해가 커진다.
  • 반대로 사용자 데이터를 덜 저장하면 사고가 나도 피해 범위blast radius가 작아진다.

90%라는 수치는 실제 사례가 아니라 발표자가 든 가상의 예다.

03

Venice가 지금 하는 방법 02:30

발표자는 Venice가 쓰는 네 가지 장치를 소개했다. 자기 회사 제품 설명이므로 "이런 방향이 있다" 정도로 읽으면 된다.

장치내용
프롬프트 미저장대화를 서버에 남기지 않는다. 발표자는 GLM 5.2, Kimi 2.7(추정) 같은 모델을 예로 들었다. 대화는 사용자 쪽에만 남는다.
프라이버시 등급"기본 비공개" 등급에서는 OpenAI나 Claude 같은 외부 제공자로 요청을 보낼 때 사용자 흔적을 익명화한다. 프롬프트만 보고는 누구인지 알 수 없게 한다.
신뢰 실행 환경일부 모델은 하드웨어 수준의 격리 환경TEE에서 돌린다. 추론이 비공개 과정에서 실행됐음을 검증할 수 있다.
프라이버시 우선 구조영상 생성처럼 결과를 나중에 가져가야 하는 엔드포인트는 결과를 암호화해 저장한다. 키를 둘로 나눠 보관하므로 공격자도, 계정이 털린 팀원도 열 수 없다.
04

모델은 시스템의 일부일 뿐 04:10

발표자는 "모든 시스템이 똑같이 비공개는 아니다"라고 강조한다. 비공개라고 말하는 회사가 실제로는 그렇지 않을 수 있다.

더 중요한 지적은 이것이다. 모델은 에이전트 시스템에서 꼭 필요한 부분이지만, 여전히 한 부분일 뿐이다. LLM이 일을 끝내려면 그 주위에 전체 과정을 지어야 한다. 그리고 이 주변 시스템이 모델 자체보다 데이터 유출에 훨씬 취약하다.

그래서 질문은 "어떤 모델을 쓰나"가 아니라 "모델을 감싼 시스템을 어떻게 설계하나"가 된다.

기본 설정이 함정이다 로그는 개발 환경에서도 프로덕션에서도 디버깅에 아주 유용하다. 하지만 조심하지 않으면 기본 설정만으로 프롬프트와 비밀이 그대로 저장된다. 프롬프트 안에는 개인정보가 들어 있을 수 있다.

발표자는 이 대목에서 "Venice를 쓰면 걱정할 필요가 없다"고 덧붙였다. 제품 홍보에 해당하는 말이다.

06

비밀이 새는 경로 05:50

발표자는 흔한 에이전트의 요청 흐름을 따라가며 비밀이 어디서 새는지 보여 준다. 예로 든 것은 OpenClaw 같은 에이전트다.

  1. 사용자가 요청을 보낸다.
  2. 요청이 에이전트 런타임에 도착한다.
  3. 런타임이 작업에 필요한 비밀을 꺼낸다. 1Password나 HashiCorp Vault 같은 비밀 저장소에서 가져온다.
  4. 그 비밀이 LLM 추론 층으로 전달된다.
  5. 추론 층이 도구 호출로 API 요청을 만든다.
  6. 결과가 사용자에게 돌아간다.
문제는 4번이다 이 구조에서는 비밀이 LLM에 직접 입력된다. 모델에 들어간 것은 로그에 남을 수 있고, 발표자의 말대로 학습 데이터로 쓰일 수도 있다. 비밀이 새는 것은 모델이 악의적이어서가 아니라 구조가 그렇게 생겼기 때문이다.
07

효과가 있는 패턴 5가지 06:50

발표자가 Venice에서 실제로 쓰거나 권하는 패턴이다.

1 · 원본 대신 해시 06:50

식별이 필요할 때 개인정보 원본이 아니라 그것을 대표하는 해시를 저장한다.

  • 예: 속도 제한을 걸려면 사용자를 구별해야 한다.
  • 사용자 흔적을 그대로 쓰지 않고 해시로 바꿔 저장한다.
  • 개인정보 없이도 "같은 사용자인지"는 알 수 있다.
2 · 분할 키 보관 07:20

데이터를 암호화해 접근 불가능한 격리 공간에 둔다. 암호화 키는 읽기 반쪽과 쓰기 반쪽으로 나눠 보관한다.

  • 복호화에는 두 반쪽이 모두 필요하다.
  • 공격자가 한쪽을 얻어도 데이터를 열 수 없다.
3 · 회수할 수 있는 핸들 07:50

핸들handle은 무언가에 접근할 권리를 담은 객체다. 핸들이 있으면 접근할 수 있고, 없으면 접근할 수 없다.

  • 예: 데이터베이스 커넥션 풀을 핸들로 다룬다.
  • JWT나 세션 키처럼 인가 체계의 핵심인 것에 특히 중요하다.
  • 문제가 생기면 핸들만 회수하면 된다.
4 · 프라이버시를 생각한 프롬프트 08:20

Cursor나 Claude Code 같은 코딩 하네스를 쓰는 팀이라면, 에이전트가 다루는 데이터를 보호하도록 프롬프트부터 설계한다.

  • 핵심은 에이전트 범위를 좁히는 것이다. 다음 절에서 자세히 다룬다.
5 · 분류 층 09:20

에이전트 앞에 프롬프트 인젝션을 걸러내는 분류 층을 둔다. 구현 방법은 셋 중 고른다.

  • LLM이 판단하는 층
  • Qdrant, LanceDB 같은 벡터 검색을 쓰는 의미 검색 층
  • 메모리 안에서 도는 가벼운 프로세스
08

도구를 줄이면 두 가지가 좋아진다 08:40

발표자가 든 상황은 이렇다. MCP 서버 하나를 붙이면 도구가 15~20개 딸려 온다. 실제로 필요한 것은 하나뿐이다. 그런데 그 하나를 쓰려면 API 키가 필요하다.

도구가 많을수록 비밀이 빠져나갈 문이 많다 비밀 저장소에서 꺼낸 API 키를 에이전트의 일부로 넘기면, 에이전트가 도구 호출을 하는 과정에서 그 키가 악의적인 사람이 띄운 웹 서버로 유출될 수 있다. 안 쓰는 도구 열아홉 개는 쓸모는 없고 위험만 더한다.

덤으로 성능도 좋아진다 10:00

범위를 좁히면 컨텍스트 루프가 촘촘해진다. 도구가 적으니 컨텍스트 창에 들어가는 내용이 줄어든다. 발표자는 컨텍스트 창이 한계에 가까워지면 성능이 크게 떨어진다는 점은 잘 알려져 있다고 말한다. 비어 있거나 거의 빈 컨텍스트 창을 유지하면 에이전트가 가장 좋은 상태로 일한다.

09

비밀을 모델 밖에 두는 설계 10:40

이 발표의 핵심 그림이다. 사용자 요청은 추론 층으로 간다. 추론 층은 에이전트 런타임에 줄 입력을 만든다. 이 입력은 비결정적이다. 같은 요청에도 LLM은 매번 다른 답을 낼 수 있다.

흔한 구조비밀 저장소를 추론 층에 묶는다API 키와 비밀번호가 LLM 입력에 들어간다. 로그와 학습 데이터로 흘러갈 수 있다.
→
발표자의 제안비밀 저장소를 실행 층에 묶는다LLM은 "무엇을 할지"만 정한다. 비밀은 결정적인 실행 층 안에서만 쓰인다.

비밀 저장소를 런타임에 묶으면 런타임은 사실상 실행 층이 된다. 실행 층은 결정적이라고 볼 수 있다. 그러면 LLM 층에서는 프라이버시와 보안 때문에 할 수 없던 일들을 실행 층에서는 할 수 있다.

예: 로그인이 필요한 브라우저 작업 브라우저 조작 도구로 어떤 사이트에 로그인해야 한다고 하자. 비밀번호를 추론 층에 직접 먹이는 대신 실행 층이 로그인을 처리하면, "비공개이고 안전하다"고 말하기가 훨씬 떳떳해진다. 외부 API를 부르는 경우도 마찬가지다.
10

샌드박스는 만능이 아니다 12:00

Firecracker 같은 마이크로 VM이나 VPC 안의 AWS EC2처럼 샌드박스와 VM을 쓰면 에이전트 보안이 크게 올라간다. 발표자도 이를 잘 알려진 사실이라고 말한다. 하지만 치료제는 아니다.

  • 에이전트에 인터넷 접근이 열려 있으면, 샌드박스 안에서도 외부 API를 통해 데이터가 빠져나갈 수 있다.
  • 그래서 권한을 계속 지켜보는 일이 필수다.
발표자의 개인적인 제안: 런타임을 직접 만들어라 자기만의 에이전트 런타임, 즉 코딩 하네스를 직접 짓는다. 단계, 관측성, 도구를 스스로 정한다. 핵심은 실행 층과 추론 층을 모두 자기 손에 두는 것이다.
11

하드웨어 수준의 프라이버시 13:10

발표자가 기밀 컴퓨팅confidential compute이라고 부르는 접근이다. 하드웨어 수준의 신뢰 실행 환경trusted execution environment이 추론 과정을 비공개로 실행한다.

  1. 사용자가 요청을 보낸다.
  2. 응답과 함께 증명서attestation가 돌아온다.
  3. 사용자는 증명서 검증기로 그 추론이 격리된 환경에서 실행됐는지 확인한다.

이렇게 하면 추론 층의 에이전트를 암호학적으로 완전히 격리하고, 격리됐다는 사실을 증명할 수 있다.

이 절은 Venice의 기능 설명이다. 증명서 검증 자체는 다른 기밀 컴퓨팅 서비스에도 있는 일반적인 개념이다.

12

남은 과제: 비밀 도구 호출 13:50

추론은 격리할 수 있게 됐다. 그런데 도구 호출은 어떤가. 발표자는 여기에 아직 할 일이 남았다고 솔직하게 말한다.

  • 신뢰 실행 환경은 도구 호출에도 여전히 유용하다.
  • Venice는 종단간 암호화도 제공한다.
  • 그러나 쓰기 편한 API를 유지하면서 도구 호출 결과까지 완전히 암호화해 돌려주는 일은 아직 풀리지 않은 문제다.
발표자가 보는 믿을 만한 해법 도구 호출이 실행되는 컴퓨팅 층을 제공자가 직접 소유하는 것이다. 그러면 추론과 도구 호출을 같은 격리 환경 안에서 끝낼 수 있다. 발표는 이 문제가 진행 중이라는 말로 끝난다.
13

핵심 정리

  1. 데이터 유출은 언젠가 일어난다. 저장하는 데이터를 줄이면 사고의 피해 범위가 줄어든다.
  2. 모델은 에이전트 시스템의 한 부분일 뿐이다. 유출은 주로 모델을 감싼 시스템에서 일어난다.
  3. 로그는 기본 설정만으로 프롬프트와 비밀을 저장할 수 있다. 관측성 설정을 먼저 점검한다.
  4. 흔한 에이전트 구조는 비밀 저장소에서 꺼낸 키를 LLM에 그대로 넘긴다. 그 키는 로그와 학습 데이터로 흘러갈 수 있다.
  5. 식별이 필요하면 개인정보 원본 대신 해시를 저장한다.
  6. 암호화 키를 읽기·쓰기 반쪽으로 나눠 보관하면 한쪽이 털려도 데이터를 열 수 없다.
  7. 접근 권리는 회수할 수 있는 핸들로 다룬다. JWT와 세션 키처럼 인가의 핵심일수록 그렇다.
  8. 에이전트 범위를 좁힌다. 안 쓰는 도구는 유출 통로이고, 컨텍스트 창도 낭비한다.
  9. 비밀 저장소는 추론 층이 아니라 실행 층에 묶는다. LLM은 결정만 하고 비밀은 만지지 않는다.
  10. 샌드박스는 보안을 올리지만 인터넷이 열려 있으면 유출을 막지 못한다. 권한을 계속 지켜보고, 가능하면 런타임을 직접 만든다.
14

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1사용자 데이터를 덜 저장하면 무엇이 줄어드나?
보안 사고가 났을 때의 피해 범위. 발표자는 유출을 "언젠가 일어나는 일"로 보고, 갖고 있는 민감 데이터의 양이 사고의 크기를 정한다고 말한다.
Q2관측성의 세 구성 요소는? 그중 비밀이 새기 쉬운 곳은?
트레이스, 메트릭, 로그. 로그는 실제 메시지 본문을 담으므로 기본 설정만으로 프롬프트와 비밀이 저장될 수 있다.
Q3흔한 에이전트 구조에서 비밀이 새는 지점은 어디인가?
런타임이 비밀 저장소에서 꺼낸 비밀을 LLM 추론 층에 그대로 넘기는 지점. 모델에 들어간 비밀은 로그와 학습 데이터로 흘러갈 수 있다.
Q4속도 제한을 걸기 위해 사용자를 구별해야 한다. 발표자의 방법은?
사용자 정보 원본 대신 그것의 해시를 저장한다. 개인정보 없이도 같은 사용자인지는 구별할 수 있다.
Q5분할 키 보관은 어떻게 동작하나?
암호화 키를 읽기 반쪽과 쓰기 반쪽으로 나눠 따로 보관한다. 복호화에는 둘 다 필요하므로 한쪽을 얻은 공격자는 데이터를 열 수 없다.
Q6핸들이란 무엇이고 왜 쓰나?
무언가에 접근할 권리를 담은 객체. 있으면 접근할 수 있고 없으면 못 한다. 문제가 생기면 핸들만 회수하면 되므로 JWT나 세션 키 같은 인가의 핵심을 다루기 좋다.
Q7MCP 서버의 도구 20개를 다 붙이면 생기는 두 가지 문제는?
첫째, 비밀 저장소에서 꺼낸 API 키가 도구 호출을 통해 악의적인 서버로 빠져나갈 통로가 늘어난다. 둘째, 컨텍스트 창이 차서 성능이 떨어진다.
Q8프롬프트 인젝션 분류 층을 만드는 세 가지 방법은?
LLM이 판단하는 층, 벡터 검색(Qdrant, LanceDB 등)을 쓰는 의미 검색 층, 메모리 안에서 도는 가벼운 프로세스.
Q9비밀 저장소를 어디에 묶어야 하고, 그러면 런타임은 무엇이 되나?
추론 층이 아니라 에이전트 런타임에 묶는다. 그러면 런타임은 결정적인 실행 층이 되고, LLM 층에서는 할 수 없던 보안 처리를 실행 층에서 할 수 있다.
Q10샌드박스와 VM을 써도 데이터가 샐 수 있는 이유는?
에이전트에 인터넷 접근이 열려 있으면 외부 API를 통해 데이터가 빠져나갈 수 있다. 그래서 권한을 계속 지켜봐야 한다.
Q11신뢰 실행 환경에서 응답과 함께 돌아오는 것은? 무엇에 쓰나?
증명서(attestation). 검증기로 확인해 추론이 격리된 환경에서 실행됐음을 암호학적으로 증명한다.
Q12발표자가 아직 풀리지 않았다고 인정한 문제는?
도구 호출까지 기밀로 만드는 일. 쓰기 편한 API를 유지하면서 도구 호출 결과를 완전히 암호화해 돌려주는 방법이 아직 없다. 제공자가 도구 호출의 컴퓨팅 층을 직접 소유하는 것을 해법으로 본다.
