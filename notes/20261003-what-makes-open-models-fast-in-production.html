오픈 모델을 프로덕션에서 빠르게 돌리는 법

같은 오픈 모델이라도 어떻게 서빙하느냐에 따라 속도와 비용이 크게 달라진다. Nebius의 두 발표자가 캐시를 아는 라우팅, 추측 디코딩, KV 캐시, 프리필·디코드 분리, 양자화로 그 차이를 만드는 방법을 소개한다.

원본 영상: What Makes Open Models Fast in Production 발표: Dylan (Nebius Token Factory 제품 마케팅 리드), Sujee Maniyam (Nebius 개발자 애드보킷)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 불확실한 것에는 "(추정)"을 붙였다. 두 발표자 모두 Nebius 소속이고, 발표의 상당 부분이 자사 서비스 소개다. mm:ss는 영상 위치다.

3분 요약
  1. 앞 절반은 Dylan이 자사 서비스 Nebius Token Factory를 소개하고, 뒤 절반은 Sujee가 오픈 모델을 빠르게 만드는 서빙 기법을 설명한다.
  2. 닫힌 API는 튜닝이 안 되고, 직접 호스팅은 너무 무겁다. Token Factory는 그 사이의 관리형 추론을 내세운다.
  3. 모델을 띄우는 건 시작일 뿐이다. 추론 → 데이터 → 후학습 → 배포를 한 루프로 돌려야 데모가 제품이 된다.
  4. 발표자는 오픈 모델이 닫힌 모델과 격차가 좁고 더 싸다고 본다. 남은 문제는 그 모델을 빠르게 돌리는 일이다.
  5. 요청을 아무 GPU에나 보내면 캐시가 흩어진다. 캐시 위치를 아는 라우터가 요청을 맞는 GPU로 보낸다.
  6. 추측 디코딩은 작은 모델이 먼저 쓰고 큰 모델이 검증한다. KV 캐시는 발표자 경험상 5~10배 빠르게 한다.
  7. 성격이 다른 프리필과 디코드를 다른 GPU에 나누고, 양자화는 품질이 무너지기 직전까지만 한다. API 사용자는 이 작업을 보지 못하지만 속도 차이는 여기서 나온다.
01

Nebius는 어떤 회사인가 00:50

발표는 두 사람이 나눠 맡았다. 앞 절반은 Dylan이 회사와 서비스를 소개한다. 뒤 절반은 Sujee Maniyam이 서빙 최적화 기법을 설명한다.

Nebius는 스스로를 풀스택 AI 클라우드라고 소개한다. 모델 API만 파는 게 아니라, 그 밑의 데이터센터와 GPU까지 직접 운영한다는 뜻이다.

Dylan이 내세운 것내용
규모NASDAQ 상장사이고 본사는 암스테르담이다. NVIDIA가 몇 달 전 Nebius에 20억(달러로 추정)을 투자했다. 2030년 말까지 NVIDIA 시스템 5GW 확보가 목표다.
자체 운영EU와 미국에 자체 데이터센터가 있다. 여러 고객이 나눠 쓰는 클라우드가 아니라 베어메탈bare metal로 운영한다.
최신 하드웨어NVIDIA Rubin CPX(추정, 자막은 "Rubin CP like")와 BlueField 스토리지를 일찍 도입했다. 유럽 클라우드 중 처음으로 Blackwell Ultra 세대 HGX B300(추정)과 GB300을 프로덕션에 올린 곳 중 하나라고 했다.
대형 고객Microsoft, Meta와 계약을 맺었다.
수직 통합칩부터 서빙까지 한 회사가 맡는다. 발표 전체가 이 점을 바탕에 깔고 있다.

01~04는 Dylan이 자사 서비스를 소개하는 대목이다. 업계 일반론과 제품 홍보가 섞여 있으니 그 점을 감안해 읽자.

02

닫힌 API와 직접 호스팅 사이 02:40

Dylan은 오픈 모델을 쓰려는 AI 팀 대부분이 나쁜 선택지 두 개 사이에 끼어 있다고 본다.

닫힌 API · closed API
  • 시작은 쉽다
  • 금방 한계에 닿는다
  • 내 용도에 맞게 모델을 튜닝할 수 없다
  • 인프라를 모두와 나눠 써서 속이 안 보인다
  • 비용이 사용량에 정비례하고 줄일 방법이 없다
직접 호스팅 · self-hosting
  • 모델을 완전히 통제할 수 있다
  • 큰 엔지니어링 프로젝트가 된다
  • 운영을 맡을 전담 팀이 필요하다
  • 제품을 만들기도 전에 프로덕션까지 몇 달이 걸린다
관리형 추론 · Token Factory

직접 호스팅의 통제권과 성능을, 관리형 서비스의 단순함으로 얻는다는 것이 Dylan의 설명이다.

어려운 인프라 작업은 업체가 맡고 고객은 제품에 집중한다. 얻는 것은 성능, 비용, 모델 동작 조정 세 가지다.

Dylan은 오픈 모델과 닫힌 모델의 격차가 많이 좁혀졌다고 본다. 남은 문제는 그 오픈 모델을 내 프로덕션에서 실제로 돌아가게 만드는 일이다.

세 번째 길이 바로 발표자 회사의 제품이다. 앞의 두 선택지도 그 제품이 돋보이는 쪽으로 정리돼 있다.

03

네 층짜리 플랫폼 04:00

Token Factory는 추론, 데이터, 학습, 배포를 한 플랫폼에 묶었다. Dylan의 말로는 시중 플랫폼 대부분이 이 중 일부만 준다.

층하는 일발표에 나온 기능
1. 추론모델을 프로덕션에서 돌린다60개 이상 모델(GLM, Kimi, DeepSeek 등), 전용 엔드포인트, 속도 등에 따라 고르는 여러 버전, 구조화 출력, 함수 호출, 배치 API
2. Data Lab프로덕션 로그를 모아 정리한다추론 로그 가져오기, SQL 방식의 데이터셋 필터링, 데이터셋 버전 관리, 내보내기
3. 후학습모델을 내 용도에 맞게 고친다LoRA 또는 전체 미세조정, 증류, 고급 고객용 맞춤 추측 디코딩, 맞춤 양자화와 보정, GRPO(추정, 자막은 "GPO")
4. 배포고친 모델을 프로덕션에 올린다Nebius 자체 인프라에 배포

2층과 3층은 이어진다. 고객 다수가 프로덕션에서 나온 응답을 다시 들여다보고 싶어 했다. Data Lab에서 로그를 정리하고 합성 데이터셋을 만든다. 그 데이터를 후학습에 넣어 모델이 기대한 대로 동작하게 고친다.

보통 팀은 이 단계마다 다른 도구를 이어 붙인다. 도구 사이를 오갈 때마다 마찰이 생기고 반복 속도가 느려진다. Token Factory는 추론 데이터가 학습으로, 학습 결과가 다시 프로덕션으로 바로 흐르게 했다.

모델을 띄운 다음 06:20

Dylan은 프로덕션 운영에서 업체가 대신 맡는 일을 세 층으로 나눈다.

층내용
최적화지연 시간, 처리량, 비용을 엔진 수준에서 조정한다. 같은 오픈 모델도 프로바이더마다 비용이 완전히 다를 수 있다. 구체적인 방법은 뒤에서 Sujee가 설명한다.
인프라 07:00하드웨어를 직접 소유하고 운영한다. Dylan은 이 수직 통합을 다른 프로바이더 대부분에 없는 강점으로 꼽는다.
엔터프라이즈 준비 07:30보안, 규정 준수, 안정성. 큰 회사는 이것 없이는 아무것도 프로덕션에 올리지 못한다.

데모를 내는 팀과 제품을 내는 팀 08:00

많은 팀이 모델을 일단 띄운 뒤에야 그게 시작일 뿐임을 깨닫는다. 실제 환경에서 모델이 어떻게 동작하는지 알아야 한다. 계속 고쳐야 한다. 고친 모델을 아무것도 깨뜨리지 않고 다시 배포해야 한다.

모델을 돌린다띄워서 답을 받는다대부분의 팀이 여기서 시작한다
→
프로덕션 AI 시스템을 돌린다돌리고, 관찰하고, 모으고, 다시 배포한다한 바퀴 돌 때마다 더 내 용도에 맞고, 더 빠르고, 더 싸진다는 것이 Dylan의 주장

Dylan은 이 루프를 끝까지 도는지가 좋은 AI 제품을 내는 팀과 데모만 내는 팀을 가른다고 말한다. 고객에게는 모델이 어떤 칩에서, 어떤 양자화 수준으로 도는지 아는 것도 중요하다고 덧붙였다.

05

오픈 모델은 충분히 좋은가 10:20

여기서 Sujee가 이어받는다. 첫 메시지는 이렇다. 좋은 추론은 좋은 모델에서 시작한다. 하지만 그것만으로는 부족하고, 뒤에 좋은 인프라가 있어야 한다.

Sujee가 자주 받는 질문은 "오픈 모델이 정말 쓸 만한가"다. 답으로 Artificial Analysis의 벤치마크 비교표를 보여 줬다. 검은 막대가 닫힌 모델, 파란 막대가 오픈 모델이다. 오픈 모델이 닫힌 모델과 비슷하고, 몇몇 닫힌 모델보다는 낫다.

자막에는 비교표의 모델 이름과 점수가 나오지 않는다. 구체적인 값은 슬라이드를 직접 봐야 한다.

Sujee가 정리한 고객 쪽 이점은 세 가지다.

  • 똑똑한 모델을 쓰려고 닫힌 모델을 계속 쫓아다닐 필요가 없다.
  • 비슷하게 똑똑한 오픈 모델이 대개 훨씬 싸다.
  • 어느 프로바이더에서나 돌릴 수 있어 벤더 종속vendor lock-in이 없다.

선생 모델과 학생 모델 11:20

Token Factory는 큰 모델과 작은 모델을 함께 올려 둔다. Sujee는 큰 모델을 선생 모델teacher model이라 부른다. 똑똑하지만 크다. 큰 모델로 작은 학생 모델student model을 학습시킬 수 있다. 앞에서 나온 증류distillation가 이것이다.

"오픈 모델이면 충분하다"는 주장은 오픈 모델을 서빙해 돈을 버는 회사의 주장이기도 하다. 뒤에 나오는 기법들은 업계에서 널리 쓰는 것이지만, 효과 수치는 모두 Nebius 자체 경험으로 말한 것이다.

06

속도를 만드는 세 층 11:40

Sujee는 속도가 나오는 곳을 세 층으로 나눠 설명한다.

층하는 일
하드웨어최신 NVIDIA 칩을 쓰고, 커널과 런타임을 손본다
서빙모델마다 맞는 엔진을 고르고, 요청을 맞는 GPU로 보낸다
최적화추측 디코딩, KV 캐시, 프리필·디코드 분리, 양자화

하드웨어 11:50

Nebius는 NVIDIA와 가깝게 일해 최신 칩을 빨리 받는다. 칩을 들여오는 데서 끝나지 않는다. GPU에서 실제 계산을 하는 커널kernel과 런타임도 조정한다. 예로 NVIDIA의 부동소수점 형식(자막은 "Nvidia floating point", NVFP4로 추정)을 적극 받아들였다. 그 덕분에 최신 칩에서 모델 성능이 좋다고 했다.

엔진 고르기 12:20

모델을 서빙하려면 추론 엔진inference engine이 필요하다. Nebius는 오픈소스 엔진을 많이 쓴다. 그 위에 내부 포크fork를 만들어 계속 손본다.

모든 모델이 모든 엔진에서 똑같이 잘 돌지는 않는다. 그래서 모델마다 가장 잘 맞는 엔진을 찾아 그 엔진으로 배포한다. 고객은 어떤 GPU, 어떤 엔진인지 신경 쓰지 않고 API만 부르면 된다.

07

캐시를 아는 라우터 12:50

GPU가 수십만 대 규모가 되면 요청을 어디로 보낼지가 문제가 된다. 흔한 생각은 로드밸런서를 앞에 두고 요청을 아무 GPU에나 보내는 것이다. Sujee는 LLM에서는 이게 통하지 않는다고 말한다.

이유는 요청마다 모양이 다르기 때문이다. 초기 LLM은 "한 줄짜리 글을 써 줘"처럼 입력도 출력도 짧았다. 지금은 코딩 에이전트가 코드베이스 전체를 보내 리팩터링, 요약, 분석을 시킨다. 입력과 출력의 크기가 큰-작은, 큰-큰처럼 제각각이다.

무작위 분배
  • 요청이 아무 GPU에나 떨어진다
  • 그 GPU에 필요한 캐시가 있을 수도, 없을 수도 있다
  • 캐시가 여기저기 흩어져 다시 쓰는 비율이 낮다
캐시를 아는 라우터 · cache-aware router
  • 라우터가 어느 GPU에 어떤 캐시가 있는지 안다
  • 요청을 그 캐시가 있는 GPU로 보낸다
  • 캐시가 한데 모여 적중률과 속도가 올라간다

발표에 없는 보충: 여기서 말하는 캐시는 09에 나오는 KV 캐시다. 앞부분이 같은 요청이 같은 GPU로 가야 이미 계산해 둔 결과를 다시 쓸 수 있다.

08

추측 디코딩 14:20

LLM은 토큰을 하나씩 차례로 만든다. 큰 모델일수록 토큰 하나를 만드는 데 오래 걸린다. 추측 디코딩speculative decoding은 이 문제를 작은 모델과 큰 모델의 분업으로 푼다. Sujee가 특히 기대하는 기법이다.

1단계 · 작은 모델토큰을 먼저 써 둔다작은 모델은 대개 더 빠르고 싸다
→
2단계 · 큰 모델초안을 검증한다맞으면 그대로 쓴다. 틀리면 큰 모델이 다시 만든다

큰 모델이 초안을 거부해 다시 만드는 것이 최악의 경우다. 대부분은 초안이 맞아서 빨라진다. Sujee는 이 방식이 의외로 잘 확장된다고 했다. Token Factory에는 이미 들어 있는 기능이다.

Sujee의 비유 시니어 엔지니어가 주니어에게 일을 맡기는 것과 같다. 무거운 작업은 주니어가 하고, 시니어는 결과를 검토만 한다.

발표에 없는 보충: 큰 모델은 초안 토큰 여러 개를 한 번에 검사한다. 맞는 데까지는 받아들이고, 처음 틀린 자리부터는 자기가 만든 토큰으로 바꾼다. 그래서 출력 품질은 큰 모델 기준을 그대로 따른다.

초안 모델을 내 데이터로 학습한다 15:30

초안을 쓰는 작은 모델을 초안 모델draft model이라 한다. Nebius는 초안 모델을 직접 학습시키는 실험을 했다. 합성 데이터로도 학습시킬 수 있다.

일반 데이터로만 학습해도 최대 30% 개선을 봤다고 한다. 고객의 프로덕션 데이터로 학습하면 더 좋아진다. 초안이 큰 모델의 판단과 자주 맞을수록 다시 만드는 일이 줄기 때문이다.

그래서 Nebius는 프로덕션 데이터를 모아 초안 모델을 거의 클릭 한 번으로 학습시키는 기능을 내놓는다고 했다.

30%가 무엇과 비교한 개선인지는 발표에서 밝히지 않았다.

09

KV 캐시와 오프로딩 16:00

Sujee는 KV 캐시KV cache를 추론에서 투자 대비 효과가 가장 큰 최적화 중 하나로 꼽는다.

토큰을 만드는 일은 비싸다. 하나씩 차례로 만들 때는 더 그렇다. 그런데 한 번 만든 토큰은 바뀌지 않는다. 그러니 같은 계산을 매번 다시 할 필요가 없다. 계산해 둔 것을 저장하고, 다음에는 찾아 쓰기만 한다.

Sujee의 예는 "The cat sat on"이다. 다음 단어를 만들면 바로 캐시에 넣는다. 그다음 단어를 만들 때는 앞부분을 다시 계산하지 않고 캐시에서 꺼내 쓴다.

발표에 없는 보충: 정확히는 토큰 자체가 아니라, 어텐션 계산에 쓰이는 앞 토큰들의 키key와 값value 벡터를 저장한다. 그래서 이름이 KV 캐시다.

Sujee는 KV 캐시로 5~10배 빨라지는 것을 봤다고 했다. 5~10%가 아니라 5~10배라고 강조했다.

GPU 밖으로 내렸다 다시 올린다 17:00

캐시의 대가는 메모리다. 입력이 길고 컨텍스트 창이 클수록 캐시도 커진다. 그런데 GPU 메모리는 귀하다.

그래서 Token Factory는 캐시를 GPU 메모리에서 일반 메모리로 자동으로 내렸다가, 필요할 때 다시 올린다. 이를 오프로딩offloading이라 한다. 핵심은 공들여 만든 캐시를 버리지 않는 것이다. 사용자는 캐시 관리를 신경 쓸 필요가 없다.

10

프리필과 디코드 분리 17:30

LLM이 답을 만드는 과정은 성격이 다른 두 단계로 나뉜다.

프리필 · prefill

입력 전체를 읽어 컨텍스트를 채우는 단계다. 연산을 많이 쓴다.

연산 효율이 좋은 GPU 묶음 A가 맡는다

디코드 · decode

토큰을 하나씩 만들어 내는 단계다. 메모리를 많이 쓴다.

메모리 효율이 좋은 GPU 묶음 B가 맡는다

두 단계를 한 GPU에서 하면 자원을 두고 서로 다툰다. 그래서 Nebius는 두 단계를 서로 다른 GPU 묶음에 나눠 맡긴다. 프리필이 끝나면 만들어진 KV 캐시를 디코드 쪽으로 넘긴다. Sujee는 이 방식이 잘 통하고 있다고 했다.

자막에서는 이 기법 이름이 "decoding"으로만 들린다. 업계에서는 보통 프리필·디코드 분리disaggregated prefill/decode라고 부른다. 또 자막에는 프리필이 "CPU 집약"이라고 나온다. 프리필은 GPU 연산을 많이 쓰는 단계이고 발표자도 바로 뒤에서 "compute"라고 말하므로 "연산 집약"으로 옮겼다.

11

양자화의 적정선 18:10

양자화quantization는 모델이 쓰는 숫자의 정밀도를 낮추는 것이다. 정밀도를 낮추면 모델을 더 효율적으로 돌릴 수 있다. 너무 낮추면 모델 품질이 떨어진다.

그래서 Nebius는 실험을 많이 해서 효율은 챙기고 품질은 크게 잃지 않는 적정선을 찾는다. 이 작업도 플랫폼에 이미 들어 있다. 03의 후학습 층에서도 고객 요구에 맞춘 양자화와 보정calibration을 해 준다고 했다.

12

Sujee는 시간 관계상 몇 가지 기법을 더 남겨 두고, 다룬 것을 이렇게 정리했다.

  • 추측 디코딩

API만 쓰는 사람은 이런 작업이 뒤에서 돌아가는 줄 모른다. 하지만 추론 플랫폼의 품질은 여기서 나온다. 파라미터가 1조 개에 이르는 큰 모델을 서빙할 때 특히 그렇다.

마지막 안내 19:10

QR 코드로 Token Factory 크레딧을 준다고 안내했다. 최신 오픈 모델로 GLM과 Kimi를 언급했다. 자막에는 "GLM52", "kit K27s"로 나오며, GLM 5.2와 Kimi K2.7로 추정한다.

Sujee는 요즘 코딩에 이 모델들을 많이 쓴다고 했다. Cursor나 OpenCode 같은 코딩 도구에 쉽게 붙일 수 있다고 했다. 질문은 Discord 채널로 받는다.

13

핵심 정리

  1. 발표자들은 오픈 모델과 닫힌 모델의 격차가 좁아졌다고 본다. 남은 문제는 오픈 모델을 프로덕션에서 빠르고 싸게 돌리는 일이다.
  2. 닫힌 API는 튜닝이 안 되고 비용이 사용량에 정비례한다. 직접 호스팅은 전담 팀과 몇 달이 든다.
  3. 같은 오픈 모델도 누가 어떻게 돌리느냐에 따라 속도와 비용이 크게 다르다.
  4. 모델을 띄우는 건 시작이다. 돌리고, 관찰하고, 모으고, 다시 배포하는 루프가 제품과 데모를 가른다.
  5. 모델마다 잘 맞는 추론 엔진이 다르다. 모델별로 엔진을 골라 배포한다.
  6. LLM 요청은 크기가 제각각이라 무작위 분배가 맞지 않는다. 캐시 위치를 아는 라우터가 필요하다.
  7. 추측 디코딩은 작은 모델이 쓰고 큰 모델이 검증한다. 내 데이터로 학습한 초안 모델일수록 효과가 크다.
  8. KV 캐시는 발표자 경험상 5~10배 빠르게 한다. 대신 메모리를 많이 써서 GPU 밖으로 내렸다 다시 올린다.
  9. 프리필(연산 집약)과 디코드(메모리 집약)는 다른 GPU에 나눠 맡기고 KV 캐시를 넘긴다.
  10. 양자화는 품질이 무너지기 직전의 적정선을 실험으로 찾는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Dylan이 말한 두 가지 나쁜 선택지와 각각의 약점은?
닫힌 API는 시작이 쉽지만 튜닝이 안 되고, 공유 인프라라 속이 안 보이고, 비용이 사용량에 정비례한다. 직접 호스팅은 통제권이 있지만 전담 팀과 몇 달의 엔지니어링이 필요하다.
Q2Token Factory 플랫폼의 네 층은?
추론, Data Lab(로그 수집과 정리), 후학습(미세조정, 증류, 양자화 등), 배포. 추론 데이터가 학습으로, 학습 결과가 다시 프로덕션으로 흐르는 루프를 만든다.
Q3같은 오픈 모델인데 프로바이더마다 비용이 크게 다를 수 있는 이유는?
엔진 선택, 커널 조정, 캐시, 라우팅 같은 엔진 수준의 최적화가 지연 시간, 처리량, 비용을 바꾸기 때문이다.
Q4"데모를 내는 팀"과 "좋은 AI 제품을 내는 팀"을 가르는 것은?
모델을 띄우는 데서 멈추지 않고, 돌리고, 관찰하고, 데이터를 모으고, 아무것도 깨뜨리지 않고 다시 배포하는 루프를 끝까지 도는지.
Q5선생 모델과 학생 모델은 어떤 관계인가?
선생 모델은 크고 똑똑한 모델이고, 학생 모델은 작은 모델이다. 선생 모델로 학생 모델을 학습시킨다. 이것이 증류다.
Q6LLM 요청을 GPU에 무작위로 나눠 보내면 왜 안 좋은가?
요청마다 입력과 출력의 크기가 제각각이다. 필요한 캐시가 없는 GPU에 떨어지면 캐시가 흩어지고 다시 쓰는 비율이 떨어진다. 그래서 캐시 위치를 아는 라우터가 필요하다.
Q7추측 디코딩은 어떻게 동작하고, 최악의 경우는?
작은 모델이 토큰을 먼저 빠르게 만들고, 큰 모델이 검증한다. 큰 모델이 초안을 거부하고 토큰을 다시 만드는 것이 최악의 경우다.
Q8초안 모델을 내 프로덕션 데이터로 학습하면 왜 더 좋은가?
초안이 큰 모델의 판단과 자주 맞을수록 다시 만드는 일이 줄어 빨라진다. 발표자는 일반 데이터로도 최대 30% 개선을 봤고, 자기 데이터면 더 좋아진다고 했다.
Q9KV 캐시는 무엇을 아끼고, 발표자가 본 효과는 얼마인가?
이미 처리한 토큰에 대한 계산을 다시 하지 않게 한다. 정확히는 앞 토큰들의 키와 값 벡터를 저장한다. 발표자는 5~10배 빨라지는 것을 봤다고 했다.
Q10KV 캐시의 대가는 무엇이고, Token Factory는 어떻게 대응하나?
메모리를 많이 쓴다. GPU 메모리는 귀하므로 캐시를 일반 메모리로 자동으로 내렸다가 필요할 때 다시 올린다. 만든 캐시를 버리지 않는다.
Q11프리필과 디코드를 다른 GPU에 나누는 이유는?
프리필은 연산 집약, 디코드는 메모리 집약이라 한 GPU에서 하면 자원을 다툰다. 각자에 맞는 GPU 묶음에 나눠 맡기고 그 사이에 KV 캐시를 넘긴다.
Q12양자화의 적정선을 실험으로 찾는 이유는?
정밀도를 낮출수록 효율은 오르지만, 너무 낮추면 품질이 떨어진다. 효율과 품질 사이의 균형점을 찾아야 한다.
