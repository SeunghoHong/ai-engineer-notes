에이전트가 짠 코드에 내 이름을 걸려면

코딩 에이전트는 계획, 구현, 리뷰, 테스트, 배포 어디서나 품질을 떨어뜨릴 수 있다. 발표자는 결제 API 저장소를 직접 포크해, 규칙과 스킬과 계획 템플릿과 로컬 검사와 PR 리뷰를 한 줄로 이어 붙이는 과정을 보여 준다. 핵심은 같은 기준을 모든 단계에서 반복해 확인하는 것이다.

원본 영상: How to Build Quality Gates into Agentic Coding Workflows 발표: Nnenna Ndukwe (Qodo AI 개발자 관계 리드)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 "Kodto", "Codto", "COD"로 뭉개진 이름은 발표자 소속인 Qodo로, "codeex"는 Codex로, "cloud code"는 Claude Code로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 품질은 어디서나 무너진다. 계획, 구현, 리뷰, 테스트, 배포 각 단계에 에이전트를 붙잡는 장치가 필요하다.
  2. 먼저 우리 팀의 코드 품질이 무엇인지 글로 정의하고, 그 정의를 에이전트가 읽을 수 있는 곳에 둔다. 그 다음 CLI, IDE, CI 어디서든 같은 정의를 끌어다 쓴다.
  3. 워크숍 저장소에는 네 개의 게이트가 있다. 규칙 게이트, 계획과 테스트 주도 개발 게이트, 로컬 검증 게이트, PR 리뷰와 수정 게이트.
  4. 계획은 다섯 질문에 답해야 한다. 어떤 동작을 바꾸나, 어떤 규칙이 적용되나, 어떤 스킬이 안내하나, 어떤 테스트가 증명하나, 리뷰 전에 어떤 게이트를 통과해야 하나.
  5. 결정론적 도구와 AI를 섞는다. 린터, 타입 검사, 보안 검사, 정적 분석은 항상 돌리고, 그 위에 AI 리뷰를 얹는다.
  6. 다른 사람이 보기 전에 항상 로컬 코드 리뷰를 먼저 돌린다. 도구는 무엇이든 상관없다.
  7. PR 리뷰 결과는 에이전트 스킬로 자동 수정하되, 수정 뒤에 검증을 다시 돌린다. 자동화에는 반드시 재검증이 따라붙어야 한다.
01

품질은 어느 단계에서나 무너진다 02:50

발표자는 청중에게 AI로 코딩하는 사람이 누구냐고 묻는다. 거의 전원이다. 그런데 에이전트 개발 생애주기에서 품질이 깨질 수 있는 곳은 어디인가. 발표자의 답은 "어디서나"다.

  • 계획과 설계
  • 구현
  • 코드 리뷰
  • 테스트
  • 배포

그래서 지금은 코딩 에이전트를 과하다 싶을 만큼 조종해야 한다. 목표는 "이 코드에 내 이름을 걸 수 있다", "다른 개발자에게 리뷰를 맡겨도 안전하다"고 말할 수 있는 상태다.

품질 주도 시스템의 세 단계 04:00

  1. 정의한다. 나와 우리 팀에게 코드 품질이 무엇인지 글로 쓴다.
  2. 어딘가에 둔다. 저장소 안이든 별도의 맥락 관리 층이든, 에이전트가 어떤 인터페이스에서든 읽을 수 있게 한다.
  3. 배포한다. CLI, IDE, CI 워크플로 어디서든 같은 기준을 끌어다 쓴다.
이 워크숍의 한 문장 규칙과 스킬을 계획, 코드 생성, 코드 리뷰에 모두 쓴다. 품질을 일찍, 자주 확인하되, 각 단계에서 에이전트가 대조하는 기준은 같은 것이어야 한다.
02

워크숍 저장소와 전체 흐름 06:00

실습 저장소는 SignalPay라는 이름의 결제 앱이다. FastAPI로 만든 작은 결제 API이고 프론트엔드는 없다. 발표자는 이 저장소를 포크하고 클론하라고 한다. 혼자 할 때는 README의 지시를 그대로 따르면 된다.

저장소 구성역할
AGENTS.md에이전트가 가장 먼저 읽는 저장소 안내문
.plan (숨김 디렉터리)계획 템플릿과 작성된 계획이 들어가는 곳
rules결제 API에 맞춘 저장소 규칙들
skills계획, 테스트 주도 개발, 멱등성 등 구현에 쓰는 스킬
docs, api, tests문서, 실제 API 코드, 테스트
Semgrep 설정정적 분석 규칙
CI 워크플로검증 과정을 GitHub에서 자동으로 돌리는 설정

한 바퀴의 흐름 07:00

  1. 코드 변경을 계획한다.
  2. 저장소 규칙을 읽고 이 변경에 어떤 규칙이 해당되는지 고른다.
  3. 테스트 주도 개발TDD과 행동 주도 개발BDD 스킬로 테스트를 먼저 쓴다.
  4. 에이전트가 구현한다.
  5. 린터와 정적 분석 같은 로컬 게이트를 돌린다. 결정론적 검사와 AI 검사를 섞는다.
  6. PR을 열고 Qodo가 GitHub에서 리뷰한다.
  7. 리뷰에서 나온 문제를 에이전트 스킬로 자동 수정한다.

로컬 실행은 make setup 뒤 make run이다. 발표자는 앱 자체는 중요하지 않다고 여러 번 말한다. 중요한 것은 과정이다.

03

네 개의 품질 게이트 10:00

저장소에는 설정 게이트와 검증 명령이 있고, 그 위에 네 개의 품질 게이트가 있다. 게이트quality gate는 다음 단계로 넘어가기 전에 반드시 통과해야 하는 검문소다.

1. 규칙 게이트 11:00

결제 API에 맞춘 규칙들이 저장소에 들어 있다. 에이전트의 일은 요청받은 변경에 어떤 규칙이 해당되는지 스스로 판단하고 지키는 것이다.

2. 계획과 TDD 게이트 11:40

높은 수준의 계획 템플릿과 실행 중심 계획 템플릿이 있다. 계획이 자세하고 구조가 일정할수록 에이전트가 더 잘 따르고, 빠뜨린 것을 스스로 바로잡는다.

3. 로컬 검증 게이트 12:30

Ruff, Pyright, Bandit, pytest, Semgrep, 그리고 관습적 커밋conventional commits 검사. 로컬 변경이 계약을 지켰다는 결정론적 증거를 남긴다.

4. PR 리뷰와 수정 게이트 12:50

PR을 열면 Qodo가 찾은 문제를 살핀다. 고친 것과 미룬 것을 문서로 남기고, 수정 뒤 검증 명령을 다시 돌린다. 로컬 통과에서 멈추지 않고 리뷰 루프를 끝까지 닫는다.

결정론적 도구와 AI를 함께 쓰는 것을 강하게 믿는다.발표자의 말을 옮김 12:40

준비물: git, GitHub 계정과 GitHub CLI, Python과 uv, Node.js와 npm, 코딩 에이전트(발표자는 Codex나 Claude Code를 권함), Qodo 계정. Qodo는 PR 리뷰에만 써도 되고 아예 안 써도 된다고 발표자가 말했다.

04

규칙과 스킬이 사는 곳 10:30

Qodo 계정을 저장소에 연결하는 이유는 PR 리뷰 때문만이 아니다. 저장소의 규칙과 스킬을 Qodo가 읽어 들여, 코드 리뷰 단계에서도 같은 맥락을 쓰게 하려는 것이다.

개인 작업저장소 안에 둔다rules, skills 디렉터리. 혼자 쓰거나 숨겨 둘 이유가 있을 때
→
팀 작업저장소 밖의 맥락 관리 층에 둔다여러 저장소와 도구에서 언제든 끌어다 쓴다

맥락 관리 층context management layer은 규칙, 스킬, 엔지니어링 기준을 한곳에서 관리하고 어디서든 내려받는 별도의 공간이다. 발표자는 Qodo를 예로 들었지만 Unblocked(추정)도 언급했고, 마지막에는 오픈소스 대안으로 Packmind를 소개했다.

Qodo 연결 순서 13:50

  1. app.qodo.ai에 GitHub 이메일로 로그인한다.
  2. GitHub 클라우드 연결을 추가한다. 모든 저장소가 아니라 포크한 저장소 하나만 연결하라고 권한다.
  3. 프로필의 API 키 메뉴에서 키를 만들고 로컬에 저장한다.
  4. 그 키를 .qodo/config.json에 넣는다. 이 작업도 코딩 에이전트에게 시킬 수 있다.
  5. Qodo 스킬은 npx skills add로 받거나, 이미 저장소에 있는 로컬 스킬을 쓴다.

발표자는 Qodo 소속이다. Qodo 포털의 기능 설명은 그 점을 감안해 읽자. 발표자 본인도 "Qodo는 예시일 뿐이고, 어떤 도구를 쓰든 규칙과 스킬은 어딘가에 살아야 한다"고 거듭 말했다.

05

과제: 결제 워크플로 하나 16:50

실습 과제는 작은 결제 워크플로 하나를 더하는 것이다. 둘 중 하나를 고른다.

  • 환불 워크플로refund workflow
  • 결제 확정 재시도 처리capture retry handling

일부러 작은 변경이다. 하지만 결제 상태를 바꾸는 코드는 민감하다. 발표자의 표현을 빌리면, 결제 변경payment mutation은 AI가 만든 코드가 그럴듯하게 맞아 보이면서도 문제를 심기 쉬운 자리다. 그래서 품질 게이트를 시험하기 좋은 예다.

발표자는 처음에 결제 확정 재시도를 하려다, 청중과 같이 가려고 환불 워크플로를 골랐다. 어느 쪽을 할지는 에이전트가 물어보거나, 안 물으면 프롬프트에 직접 적는다.

06

설정 프롬프트와 규칙 고르기 17:50

README에 복사해 쓸 수 있는 에이전트 프롬프트가 단계별로 있다. 발표자는 Codex에서 설정 프롬프트부터 붙여 넣는다.

설정 프롬프트가 시키는 일 19:10 Qodo 스킬을 설치하거나 확인한다. AGENTS.md와 규칙을 읽는다. 이번 실습 과제에 해당하는 저장소 규칙의 ID를 고르고, 각 규칙이 왜 이 과제에 관련 있는지 설명한다. 가능하면 Qodo의 규칙 조회 스킬 결과와도 비교한다.

에이전트가 한 일은 이렇다. 저장소 지시를 먼저 읽고, 로컬 Qodo 설정과 의존성 상태를 확인한다. 저장소 로컬 스킬이 아직 설치되지 않았음을 알아채고, 커밋된 스킬 폴더를 에이전트 스킬 디렉터리로 복사하는 설치 스크립트를 돌린다. 그 다음 결제 워크플로 과제에 해당하는 규칙 목록을 내놓는다.

검증 장치가 많이 붙어 있어서 이 단계가 꽤 오래 걸린다고 발표자가 인정한다.

07

계획 모드와 두 가지 템플릿 20:50

설정이 끝나면 계획 모드로 바꾼다. 계획 프롬프트는 저장소의 계획 스킬로 README의 과제를 높은 수준의 구현 계획과 빌드 세션 실행 계획으로 바꾸라고 한다. AGENTS.md와 규칙을 읽고 관련 스킬로 제약을 정한다. 계획에는 반드시 첫 번째 구현 스킬과 그 뒤에 이어질 TDD 프롬프트를 적는다. 그리고 "아직 코드를 쓰지 말라"고 못 박는다.

에이전트는 계획 스킬과 결제 멱등성 스킬을 고른 뒤, 파일을 읽기만 하고 아무것도 쓰지 않겠다고 답한다. 그리고 현재 앱의 동작을 살펴 변경의 모양을 잡는다.

계획이 답해야 할 다섯 질문 25:20

  1. 어떤 동작을 바꾸나
  2. 어떤 규칙이 적용되나
  3. 어떤 스킬이 에이전트를 안내하나
  4. 어떤 테스트가 기대 동작을 증명하나
  5. 리뷰 전에 어떤 품질 게이트를 통과해야 하나
높은 수준 계획 템플릿 26:00
  • 요약
  • 풀려는 문제
  • 제약
  • 스킬 라우팅: 구현 중 어떤 스킬을 어떤 순서로 부를지
  • 범위
  • 동작 시나리오
  • 검증 게이트
  • 실패와 복구 규칙
  • 커밋 계획

스킬 라우팅은 사람이 끼어들지 않는 루프나 목표 실행을 쓸 때 특히 쓸모 있다. 커밋 계획은 관습적 커밋으로 정리돼 PR이 사람 팀의 작업처럼 보이게 한다.

빌드 세션 실행 템플릿 27:10
  • 시작 상태: 어느 브랜치인가, 어떤 검증 명령이 있나, 린터 기대치는 무엇인가
  • 구현 스킬 핸드오프
  • 실행 단계: 변경의 모든 단계를 에이전트가 알고 있어야 한다
  • 테스트 계획
  • 완료 정의와 완료 노트: 모든 명령을 돌렸나, 무엇을 미뤘나, 중간에 생각이 바뀐 곳은 어디인가

발표자가 가장 유용하다고 꼽은 것은 시작 상태 기록이다. 에이전트가 되돌아가 읽을 문서가 있으면 더 잘 따르고 스스로 바로잡는다.

완성된 환불 워크플로 계획에는 요약, 관련 저장소 규칙, 높은 수준 구현 계획, 빌드 세션 실행 계획, 그리고 가정 몇 가지가 들어 있었다. 발표자는 이 계획으로 구현을 시작한다 28:40.

08

스킬 계층과 로컬 리뷰 29:00

구현이 도는 동안 발표자는 자기 스킬 구성을 보여 준다. 저장소와 언어와 프레임워크에 따라 조합은 다르지만, 층은 대체로 이렇다.

층예적용 범위

  • 범위: 조직 수준과 저장소 수준. 특정 저장소에만 적용되게 좁힐 수 있다

핵심 정리

  1. 에이전트 개발의 품질은 계획, 구현, 리뷰, 테스트, 배포 어디서나 무너질 수 있다.
  2. 시작은 품질의 정의다. 글로 쓰고, 에이전트가 읽는 곳에 두고, 모든 인터페이스에 배포한다.
  3. 게이트는 네 개다. 규칙, 계획과 TDD, 로컬 검증, PR 리뷰와 수정.
  4. 각 단계에서 에이전트가 대조하는 기준은 같은 규칙과 스킬이어야 한다.
  5. 계획은 다섯 질문에 답한다. 동작, 규칙, 스킬, 테스트, 게이트. 시작 상태와 완료 정의를 문서로 남기면 에이전트가 되돌아가 스스로 바로잡는다.
  6. Ruff, Pyright, Bandit, pytest, Semgrep, 관습적 커밋 같은 결정론적 검사를 AI 리뷰와 함께 쓴다.
  7. 스킬은 일반적인 것이 위, 언어별과 감사 스킬이 아래인 계층으로 둔다.
  8. 다른 사람이 보기 전에 항상 로컬 리뷰를 돌린다. 도구는 무엇이든 좋다.
  9. 규칙은 범주와 심각도로 나누고, 심각도가 높은 것만 머지를 막는다. 코드에서 추론된 관례는 사람이 수락해야 규칙이 된다.
  10. 리뷰 결과는 스킬로 자동 수정할 수 있지만, 수정 뒤 재검증이 빠지면 자동화가 아니라 위험이다.

시작 상태 기록. 어느 브랜치인지, 어떤 검증 명령이 있는지, 린터 기대치가 무엇인지를 적어 두면 에이전트가 되돌아가 읽고 스스로 바로잡는다.
Q6실습 과제로 결제 변경 코드를 고른 이유는?
결제 변경은 AI가 만든 코드가 그럴듯하게 맞아 보이면서도 문제를 심기 쉬운 자리이기 때문이다. 작지만 민감해서 게이트를 시험하기 좋다.
Q7코드베이스에서 추론된 관례가 곧바로 규칙이 되지 않는 이유는?
추론된 관례는 제안으로만 올라온다. 사람이 좋은 예와 나쁜 예, 범주, 경고 수준을 편집하고 수락해야 활성화된다.
Q8Qodo 리뷰에서 "조치 필요"가 결정론적이라고 한 부분은 무엇인가?
어떤 규칙이 관련 있는지는 AI가 판단하지만, 심각도가 높은 문제가 머지를 막을지는 포털에서 사람이 정한 설정이 결정한다.
Q9환불 PR에서 찾은 버그 하나는 무엇이었나?
환불 멱등성 키를 프로세스 안의 딕셔너리에 저장한 것. 재시작하면 사라지는 저장소라 내구성이 없다.
Q10리뷰 문제를 자동 수정한 뒤 반드시 해야 할 일은?
검증을 다시 돌린다. 수정이 다른 것을 깨뜨릴 수 있고, 자동으로 돌지는 에이전트에 달렸으니 프롬프트로 명시하는 편이 안전하다.
Q11스킬 자체의 품질을 평가하는 도구로 발표자가 언급한 것은?
Tessl(추정). 스킬에 보안 문제가 있는지, 기대만큼 효과가 있는지 평가한다. Qodo는 스킬을 읽어 들일 뿐 평가하지 않는다.
Q12규칙과 스킬을 저장소 밖에 두라고 하는 이유와 오픈소스 대안은?
팀의 여러 저장소와 도구에서 같은 기준을 언제든 끌어다 쓰기 위해서다. 오픈소스 대안으로 Packmind를 꼽았다.

용어뜻
품질 게이트Quality gate. 다음 단계로 넘어가기 전에 반드시 통과해야 하는 검문소
SDLC소프트웨어 개발 생애주기. 계획부터 배포까지의 전체 과정
AGENTS.md코딩 에이전트가 저장소에서 가장 먼저 읽는 안내 파일
규칙Rule. 코드가 지켜야 할 기준을 적은 문서. 범주와 심각도를 가진다
스킬Skill. 에이전트가 특정 작업을 하는 방법을 적어 둔 재사용 지시문
맥락 관리 층Context management layer. 규칙과 스킬을 저장소 밖 한곳에서 관리하고 어디서든 끌어다 쓰는 공간
TDD / BDD테스트 주도 개발 / 행동 주도 개발. 테스트나 기대 행동을 먼저 쓰고 코드를 맞추는 방식
결정론적 검사같은 입력에 항상 같은 결과를 내는 검사. 린터, 타입 검사, 정적 분석 등
정적 분석코드를 실행하지 않고 패턴으로 문제를 찾는 검사. 발표에서는 Semgrep
Ruff / Pyright / BanditPython 린터 / 타입 검사기 / 보안 취약점 검사기
관습적 커밋Conventional commits. 커밋 메시지를 정해진 형식으로 쓰는 약속
멱등성Idempotency. 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 결제에서 중복 처리를 막는다
계획 모드Plan mode. 코드를 쓰지 않고 읽기와 계획만 하는 에이전트 모드
스킬 핸드오프계획에서 다음 구현 스킬과 이어질 프롬프트를 미리 지정하는 것
초안 PRDraft PR. 아직 리뷰 대상이 아니라고 표시한 PR
agentic RAG에이전트가 스스로 검색하고 걸러서 관련 맥락만 가져오는 검색 증강 생성
worktree한 저장소에서 여러 브랜치를 각각 다른 디렉터리에 동시에 체크아웃하는 git 기능
온프레미스On-premises. 외부 클라우드가 아니라 자사 서버에 설치해 쓰는 방식
