AI에게 레거시를 맡기기 전에 지도부터 그린다

오래된 금융 시스템을 AI로 옮길 때 막히는 곳은 코드 작성이 아니라 맥락이다. 발표자들은 코드 전체를 지식 그래프로 만들고, 에이전트에게 필요한 조각만 건네고, 옛 시스템과 결과가 똑같은지 테스트로 증명하는 방식을 소개한다.

원본 영상: How We Mapped a 35-Million-Line Mainframe in 4 Days 발표: Stephen Chin (Neo4j), Neeraj Deshmukh (Blitzy)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 고객 사례는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(Blitzz → Blitzy, Cobalt → COBOL, Neo for J → Neo4j)은 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 금융권의 핵심 업무는 아직 오래된 메인프레임 위에서 돈다. 한 줄만 고쳐도 전체가 깨질까 봐 아무도 손대기 싫어한다.
  2. AI가 이런 코드를 옮기다 실패하는 이유는 코드를 못 써서가 아니라 맥락을 몰라서다. 바꿀 로직이 다른 곳에서 어떻게 쓰이는지 모른다.
  3. 컨텍스트 창을 키워도 안 된다. 100만 토큰을 내세우지만 쓸 만한 양은 20만 토큰 정도라고 발표자는 말한다.
  4. 해법은 코드를 지식 그래프로 만드는 것이다. 관계마다 출처와 증거를 붙이고, 머지할 때마다 갱신한다.
  5. 에이전트는 전체 코드 대신 필요한 조각만 담은 작업 꾸러미를 받는다. 사람이 승인한 계획서대로 수천 개 에이전트가 일한다.
  6. 옛 시스템과 결과가 똑같다는 것을 테스트로 증명한다. 반올림 때문에 생기는 1센트 차이까지 잡아야 한다.
  7. 발표자가 든 사례: 3,500만 줄을 4일 만에 역공학, 은행 시스템 18일 전환, 2,500만 줄 9배 빠른 현대화. 판매사가 든 사례라는 점을 감안해 읽는다.

광고된 창과 쓸 만한 창 05:00

요즘 모델은 100만 토큰 컨텍스트 창context window을 내세운다. 컨텍스트 창은 모델이 한 번에 읽을 수 있는 입력의 양이다. 그런데 창을 채울수록 정확도가 크게 떨어진다. Stephen Chin은 연구를 들어, 실제로 쓸 만한 양은 20만 토큰 이하라고 말한다.

발표에서는 유효 컨텍스트 20~30%를 "코드 20만~30만 줄"이라고 했다. 하지만 100만의 20~30%는 줄이 아니라 토큰 20만~30만 개다. 코드 한 줄은 보통 토큰 여러 개로 나뉘므로 줄 수로는 이보다 훨씬 적다. 예를 들어 한 줄이 10토큰이면 2만~3만 줄이다(예시).

그래서 많이 주는 것보다 정확한 맥락을 골라 주는 것이 중요하다.

컨텍스트는 한 줄로 늘어서고, 정보는 서로 이어져 있다 05:40 Stephen Chin의 정리다. 컨텍스트는 글을 순서대로 이어 붙인 것이다. 반면 정보는 서로 관계를 맺고 있다. 이 관계를 살려 데이터를 정리하는 것이 핵심이라는 주장이다.

Stephen Chin은 그래프 데이터베이스 회사 Neo4j 소속이다. "그래프가 답"이라는 주장은 그 점을 감안해 읽자.

코드는 그래프다 06:00

그래프는 점(노드)과 점을 잇는 선(간선)으로 정보를 저장하는 구조다. 코드를 그래프로 바꾸면 관계가 눈에 보인다.

이자 예제라면 이자 프로그램이 한가운데 있다. 그 프로그램을 실행하는 작업, 프로그램이 불러오는 copybook, 계산 결과가 선으로 이어진다.

간선마다 붙는 정보 06:20

Neeraj Deshmukh가 강조한 부분은 간선이다. 간선 하나하나가 자기가 어디서 왔는지를 기록한다.

기록하는 것답하는 질문

그래프는 머지할 때마다 갱신된다. 코드가 바뀌면 그래프도 바뀐다. 더 이상 맞지 않는 관계는 무효로 처리한다. 그래야 그래프가 늘 최신 상태로 남는다.

Stephen Chin은 코드가 원래 그래프 모양의 문제라고 덧붙인다. 구조와 관계만 봐도 서로 얽힌 곳이 많다.

06

회사 지식의 컴파일러 07:50

Neeraj Deshmukh는 Blitzy가 회사 전체 지식을 다루는 컴파일러처럼 동작한다고 설명한다. 흐름은 여섯 단계다.

  1. 역공학 reverse engineering: 회사가 가진 소프트웨어 전체를 거꾸로 분석한다. 업무 로직, 작업 흐름, 의존 관계를 뽑아낸다.
  2. 요구사항: 사용자에게 무엇을 하고 싶은지, 어떤 규칙을 지킬지 받는다.
  3. 에이전트 실행 계획 agent action plan: 요구사항을 실행할 수 있는 계획서로 바꾼다. 앞으로 할 변경의 명세다.
  4. 사람 승인 08:20: 사람이 계획을 검토하고 승인한다. 승인 없이는 아무것도 진행되지 않는다.
  5. 생성과 검증: 에이전트가 코드를 만든다. 단계마다 검증이 들어간다.
  6. 결과물: 검증을 거친 코드가 PR로 나온다. 무엇을 했고 어떻게 검증했는지 적은 증거 문서 "프로젝트 가이드"도 함께 나온다.

1센트 차이 13:20

Stephen Chin은 Java 개발자 시절 BigDecimal과 반올림에서 실수를 많이 했다고 말한다. BigDecimal은 Java에서 소수를 정확히 다루는 숫자 타입이다. 그렇다면 AI는 더 잘할까.

Neeraj Deshmukh의 답은 이렇다. COBOL과 Java는 숫자를 다루는 방식이 다르다. 이자 공식을 Java로 옮기면 코드는 잘 컴파일된다. 결과도 그럴듯하다. 평범한 Java 코드처럼 동작하기 때문이다. 하지만 반올림 방식이 달라 1센트가 어긋난다.

처리 방식 (예시)계산값 12.345달러를 센트 단위로 맞추면
남는 자리를 잘라 낸다12.34
반올림한다12.35

예시다. 발표에 나온 숫자가 아니다.

동등성 테스트가 없으면 못 잡는다 옛 시스템 결과와 나란히 비교하지 않으면 이 차이는 보이지 않는다. 발표자는 이것이 거래 100만 건에서 일어난다고 상상해 보라고 한다. 한 건에 최대 1센트라도 100만 건이면 최대 1만 달러가 어긋난다(계산).

발표는 "Java에는 반올림이 기본으로 들어 있다"고 단순하게 말했다. 실제 결과는 Java에서 어떤 숫자 타입과 반올림 방식을 고르느냐에 따라 달라진다. COBOL도 ROUNDED를 붙이느냐에 따라 달라진다. 요점은 같다. 두 언어의 기본 처리가 다를 수 있으니, 결과를 직접 비교해야 한다.

핵심 정리

  1. 금융 시스템의 핵심은 아무도 손대기 싫어하는 오래된 메인프레임 위에서 돈다.
  2. AI가 레거시 전환에 실패하는 이유는 코드 작성 능력이 아니라 맥락이다. 바꿀 로직이 쓰이는 다른 곳을 모른다.
  3. 컨텍스트 창을 키워도 해결되지 않는다. 채울수록 정확도가 떨어져, 쓸 만한 양은 광고의 20% 남짓이다.
  4. 벡터 검색은 비슷한 것만, SQL은 한 단계 사실만 준다. 그래프는 여러 단계 관계를 따라간다.
  5. 코드를 그래프로 만들 때 간선마다 출처, 리비전, 증거를 붙이고 머지마다 갱신한다.
  6. 에이전트는 전체 코드 대신 작업 꾸러미를 받는다. 필요한 정보를 필요한 때 받는 것이 "무한 컨텍스트"다.
  7. 흐름: 역공학 → 요구사항 → 계획서 → 사람 승인 → 검증하며 생성 → PR과 증거 문서.
  8. 네 가지 통제: 시스템 수준 맥락, 지속적 검증, 명시적 가드레일, 사람이 주도.
  9. 옛 시스템과 결과가 같음을 테스트로 증명한다. 오류 경로와 1센트 반올림까지 맞아야 한다.
  10. 사례 수치(4일, 18일, 9배)는 판매사가 든 것이다. 무엇을 한 기간인지, 단위가 맞는지 따져 읽는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1AI에게 "이자 공식을 COBOL에서 Java로 바꿔"라고만 하면 무엇을 놓치나?
레코드 정밀도, 계좌 갱신, 거래 출력, 배치 계약. 결과는 공식 하나가 아니라 입력, 계산을 돌리는 작업, 계좌 갱신에 함께 달려 있다.
Q2벡터 DB, 관계형 DB, 그래프가 주는 맥락은 어떻게 다른가?
벡터 DB는 비슷한 문서를 찾는다. 관계형 DB는 SQL로 한 단계 사실을 찾는다. 그래프는 관계를 여러 단계 따라가 정확한 맥락을 준다.
Q3100만 토큰 창이 있는데 왜 코드를 다 넣으면 안 되나?
창을 채울수록 정확도가 크게 떨어진다. Stephen Chin은 쓸 만한 양이 20만 토큰 이하라고 말한다. 그래서 정확한 맥락만 골라 줘야 한다.
Q4"유효 컨텍스트 20~30% = 코드 20만~30만 줄"이라는 말에서 틀린 점은?
100만의 20~30%는 줄이 아니라 토큰 20만~30만 개다. 코드 한 줄은 토큰 여러 개라서 줄 수로는 훨씬 적다.
Q5그래프의 간선 하나가 기록하는 다섯 가지는?
출처(저장소 위치), 리비전, 건드리는 심볼, 증거(파일과 소스 범위), 추출 방법. 그래프는 머지마다 갱신되고 맞지 않는 관계는 무효 처리된다.
Q6작업 꾸러미에 담기는 여섯 가지와 "무한 코드 컨텍스트"의 뜻은?
작업 설명, 그래프 속 위치, 소스 조각, 제약, 증거, 미해결 질문. 무한 코드 컨텍스트는 전부 기억하는 게 아니라 필요한 정보를 필요한 때 필요한 자리에서 꺼내는 것이다.
Q7Blitzy 흐름에서 사람이 반드시 들어가는 곳과 최종 결과물은?
에이전트 실행 계획을 사람이 검토하고 승인한다. 결과물은 검증된 코드 PR과, 무엇을 어떻게 검증했는지 적은 프로젝트 가이드다.
Q8모든 단계에 들어가는 네 가지 통제는?
시스템 수준 맥락(지식 그래프), 지속적 검증, 명시적 가드레일(보안·거버넌스·규제 준수), 사람이 주도.
Q9동등성 테스트에서 옛 시스템과 새 시스템을 무엇으로 비교하나?
입력과 출력, 반환값, 저장된 상태, 거래 출력, 오류 결과. 정상 경로뿐 아니라 나쁜 상황까지 비교하고, 차이는 0이어야 한다.
Q101센트 반올림 차이는 왜 컴파일과 평범한 테스트로 안 잡히나?
코드는 정상으로 컴파일되고 Java답게 그럴듯한 결과를 낸다. 옛 시스템 결과와 나란히 비교해야만 차이가 드러난다.
Q113,500만 줄 사례의 "4일"은 무엇을 한 기간인가?
시스템 전체를 역공학해 지도를 그린 기간이다. 새 코드로 옮긴 기간이 아니다. 같은 고객은 SI에 약 8개월과 수백만 달러를 썼지만 결과물이 없었다.
Q122,500만 줄 사례에서 자율로 만들어져 프로덕션까지 간 코드는 전체의 몇 %쯤인가?
자율 완성 85% × 그중 약 90% ≈ 77%. 발표는 "90% 가까이"라고 했으니 조금 낮을 수 있다.
