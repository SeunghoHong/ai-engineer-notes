AI 에이전트 관측성 마스터하기

에이전트는 엄청난 양의 트레이스를 만든다. 그 소음 속에서 쓸 만한 신호를 뽑아내려면 트레이스 위에 스코어와 토픽을 자동으로 붙이고, 그 신호를 코딩 에이전트가 읽어 데이터셋과 평가를 고치게 해야 한다. 이 워크숍은 Braintrust로 그 순환 고리를 끝까지 돌려 본다.

원본 영상: Advanced Workshop: Mastering AI Observability 발표: Doug Guthrie (Braintrust 솔루션 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 것만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다. 1시간을 넘는 곳은 h:mm:ss로 적었다.

발표자는 Braintrust 직원이고 워크숍 전체가 Braintrust 제품 위에서 진행된다. 경쟁 제품 비교와 "고객들이 이렇게 쓴다"는 말은 그 점을 감안해 읽자. 다만 트레이싱, 스코어, 토픽, 플라이휠이라는 뼈대는 어느 도구를 쓰든 그대로 가져갈 수 있다.

3분 요약
  1. 트레이싱이 바닥이다. 에이전트가 거친 모든 단계와 도구의 입력·출력이 트레이스에 없으면 블랙박스다. 어디서 품질이 떨어지는지 알 수 없다.
  2. 플라이휠을 만든다. 프로덕션 관찰이 개발을 이끌어야 한다. 고치고, 평가로 회귀 여부를 확인하고, 배포하고, 다시 관찰한다.
  3. 신호는 두 가지다. 스코어는 이미 아는 실패 유형을 재고, 토픽은 아직 모르는 패턴을 찾는다.
  4. 스코어 팁: 판단 이유를 남기게 하고, 처음엔 이진 채점, 기준은 가혹하게, 평가에서 100점이 나오면 테스트가 약한 것이다.
  5. 토픽은 트레이스를 전처리해 패싯으로 요약하고, 임베딩해 지도를 만들고, 라벨을 붙인다. Braintrust가 호스팅하는 전용 모델로 돌리고 입력 100만 토큰당 6센트라고 한다.
  6. 워크숍에서는 트레이스 968개를 넣고 자동화와 토픽이 실시간으로 신호를 붙이는 것을 봤다. 커스텀 패싯이 "주문 조회 실패"라는 평가에 없던 문제를 드러냈다.
  7. 신호를 읽는 일은 UI 클릭에서 SQL을 쓰는 플랫폼 에이전트(Loop)로, 다시 CLI와 스킬을 쥔 코딩 에이전트로 옮겨 간다. 코딩 에이전트가 문제를 찾고 데이터셋에 추가하고 스코어를 만들고 평가까지 돌린다.
01

출발점은 트레이싱 05:00

관측성observability의 바닥은 트레이싱tracing이다. 에이전트가 최종 답에 이르기까지 어떤 단계를 밟았는지, 각 도구에 무엇을 넣고 무엇을 받았는지를 기록하는 일이다. 단계가 늘어나면 이 기록은 금방 커진다. 그래도 이것이 없으면 어디서 품질이 무너지는지 알 수 없고, Codex나 Claude Code 같은 코딩 에이전트에게 "여길 봐"라고 가리킬 수도 없다.

두 개의 과제 하나는 트레이스를 모아 볼 수 있는 플랫폼을 갖추는 것이다. 다른 하나는 그 많은 데이터에서 무언가 통찰을 끌어내는 것이다. 발표자는 두 번째가 진짜 어려운 쪽이라고 말한다.

어디에나 붙는다 06:40

워크숍의 예제 에이전트는 OpenAI Agents SDK로 만든 가짜 고객 지원 봇이다. 발표자는 에이전트 자체는 중요하지 않다고 말한다. Braintrust는 여러 에이전트 프레임워크, 여러 AI 제공자, Python·TypeScript·Java·Ruby·Go 같은 언어, OpenTelemetry, 직접 짠 오케스트레이션까지 연동된다고 소개한다.

02

능동 관측성과 플라이휠 04:10

발표자는 업계 대부분이 아직 데이터를 수동적으로 바라보는 단계에 있다고 본다. Braintrust가 가려는 방향은 능동 관측성active observability이다. 사용자가 플랫폼을 뒤져 의미를 캐내는 대신, 플랫폼이 바로 쓸 수 있는 통찰을 먼저 건네는 것이다.

플라이휠 08:00

발표자가 하루에 백 번은 말한다는 단어다. 핵심은 프로덕션이 개발을 이끌어야 한다는 것이다.

  1. 고친다프롬프트, 도구, 아키텍처 어디든 변경을 만든다
  2. 평가한다그 변경이 에이전트를 망쳤는지 나아지게 했는지 오프라인 평가로 확인한다
  3. 배포한다평가가 준 확신으로 프로덕션에 내보낸다
  4. 관찰한다프로덕션 트레이스를 모은다
  5. 통찰을 뽑는다사람이 다 읽을 수 없는 규모라서 그 위에 지능을 얹어야 한다. 이 단계가 다시 1번으로 이어진다

이 고리가 아주 사소한 일이 되어서 어느 팀이든 쉽게 끼워 넣을 수 있어야 한다는 것이 발표자의 바람이다.

03

신호 1: 스코어 09:50

발표자가 말하는 "신호"는 두 가지다. 첫째가 스코어score다. 에이전트의 출력을 어떤 기준으로 재는 평가기다.

종류특징예
코드 기반빠르고 싸고 만들기 쉽다. LLM을 부르지 않는다스키마 검증, 도구 A가 도구 B보다 먼저 불렸는가
LLM 심판주관적인 판단에 사람 같은 이해를 끌어온다. 기준을 글로 주면 점수를 낸다대화 전체를 보고 "문제가 해결됐는가" 채점
사람 검토와 맞춘 LLM 심판심판이 낸 점수를 사람이 검토해 보정한다. 온라인에서 실제 사용자 대화를 채점한다면 꼭 필요하다사람이 심판 결과를 수정하는 검토 화면
LLM을 부르는 코드 스코어분기 같은 복잡한 논리를 코드로 짜고, 필요한 곳에서만 LLM을 부른다워크숍 저장소에 예시가 있다

심판은 한 번 만들고 잊는 물건이 아니다. 에이전트가 바뀌면 스코어도 함께 바뀌어야 한다.

고객들에게서 들은 요령 12:10

발표자는 이 목록을 "소금 한 꼬집과 함께" 들으라고 했다. 모든 상황에 맞지는 않지만 여러 고객에서 잘 통했다는 뜻이다.

  • 판단 이유를 남기게 한다. 사람이 검토할 때 "왜 이 점수가 나왔는지" 알면 스코어를 어떻게 고칠지 보인다.
  • 처음엔 이진 채점. A·B·C·D보다 통과·실패가 낫다.
  • 가혹하게 잰다. 어려운 예시를 만든다. 평가에서 100점이 나오면 테스트 케이스가 약하거나 스코어가 물렁한 것이다.
  • 프롬프트에 예시를 넣는다.
  • 채점 모델은 생성 모델보다 강한 것을 쓴다. 사람의 주관에 조금이라도 가까워지도록. 트래픽 양에 따라 온라인에서는 달라질 수 있다.

오프라인과 온라인 13:50

오프라인 스코어

평가eval에서 돌린다. "이걸 프로덕션에 내보내도 되는가"를 묻는다. 개선인지 회귀인지 알려 준다. CI나 자동 파이프라인에 묶을 수 있다.

온라인 스코어

프로덕션에 들어오는 트래픽을 그 자리에서 채점한다. 목적은 트레이스에 신호를 붙여 두는 것이다. "라우팅 정확도가 0인 사례들에 어떤 패턴이 있나"처럼, 거대한 데이터를 작고 읽을 만한 덩어리로 줄인다.

04

신호 2: 토픽 15:10

두 번째 신호는 Braintrust의 토픽Topics 기능이다. 스코어는 이미 알아챈 실패 유형, 즉 아는 모름known unknowns을 잰다. 하지만 사용자가 에이전트를 찌르는 방식은 테스트 시나리오보다 훨씬 넓다. 사실성이나 유해성 같은 전통적인 스코어가 잡는 오류는 아주 일부다. 토픽은 그 바깥, 모르는 모름unknown unknowns과 조용한 실패를 찾는 도구다.

찾은 것이 꼭 실패일 필요는 없다. 사용자가 에이전트로 하려는 일 중 아직 지원하지 않는 것이 보이면 그게 곧 기능 요청이고 로드맵이다. 발표자는 고객들이 토픽을 로드맵 재료로 쓰기 시작했다고 말한다.

패싯 16:50

토픽은 데이터 속 패턴을 묶어 군집으로 보여 주고, 각 군집이 얼마나 자주 나오는지 알려 준다. 어떤 관점으로 패턴을 볼지 정하는 것이 패싯facet이다.

  • 기본 패싯: 작업task, 이슈issues, 감정sentiment. 사용자가 무엇을 하려 하는지, 어떤 기분인지, 어떤 문제를 겪는지. 분류 체계는 미리 주지 않아도 LLM이 만든다.
  • 커스텀 패싯: 내가 알고 싶은 것을 프롬프트로 직접 쓴다.

파이프라인 18:30

  1. 전처리거대한 트레이스를 LLM에게 줄 만한 크기로 줄인다. 기본 전처리기는 스레드 뷰처럼 사용자·어시스턴트·도구 호출의 주고받음만 남긴다. 메타데이터나 다른 스팬이 필요하면 직접 쓸 수 있다
  2. 패싯 적용전처리한 데이터를 각 패싯 프롬프트에 넣는다
  3. 요약패싯별 결과를 짧게 요약한다
  4. 임베딩요약을 벡터로 바꿔 백엔드에 저장한다
  5. 토픽 지도벡터로 군집을 만들어 산점도 같은 지도를 그린다
  6. 라벨과 분류각 트레이스에 라벨을 붙인다. 이 라벨이 있으면 사람도, 코딩 에이전트도 소음을 쉽게 걸러 낼 수 있다

요약과 임베딩 단계는 Braintrust가 직접 학습해 호스팅하는 모델만 쓴다. 발표자는 처음엔 다른 모델도 꽂을 수 있게 했지만 결과가 나빠서 막았다고 설명한다. 다른 스코어들은 사용자가 등록한 자기 모델로 돌지만 토픽만은 예외다.

왜 만들었나 20:50 Braintrust는 대량 데이터를 받아 1초 안에 조회하는 문제는 일찍 풀었다. 없던 것은 그 데이터로 무언가를 하는 능력이었다. 토픽은 규모와 비용 양쪽에서 버티도록 설계한 파이프라인이고, 고객이 플라이휠을 그 위에 짓도록 만든 기본 부품이라는 설명이다.
05

질의응답 1: 경쟁사·백엔드·호스팅 22:50

질문발표자의 답
우리 팀은 Lightstep을 쓴다. Braintrust를 써야 할 이유는?남을 깎아내리지는 않겠다고 전제했다. 꼽은 것은 두 가지다. 언어·프레임워크에 중립적인 유연성. 그리고 자체 백엔드 BrainStore. LangSmith는 LangGraph·LangChain 쪽에 기운 기능이 있다고 봤다.
BrainStore란?2024년 말 Braintrust가 직접 만든 데이터베이스다. 원래 ClickHouse를 썼는데 Netflix·Microsoft·Dropbox 같은 고객이 들어오자 규모에서 무너졌다고 한다. 당시엔 미쳤다는 소리를 들었지만 지금은 LangSmith도, Arize(추정)도 자체 DB를 만들었다며, 이 부분에서 1년쯤 앞서 있다고 주장했다. 토픽이 가능한 것도 이 백엔드 덕이라고 했다.
트레이스가 다 비슷한데 토픽이 정말 의미 있는 차이를 내나?프로덕션에서 쓰는 고객들은 그렇다고 할 것이다. 같은 도구, 같은 흐름이라도 실제 사용자가 붙으면 차이가 드러난다. 무료 계정으로 직접 넣어 보라고 권했다.
Claude Code·Codex 세션에도 토픽을 쓸 수 있나?된다. Claude Code, Codex, Cursor, OpenCode 연동이 있다. 여러 고객이 코딩 에이전트가 워크플로를 얼마나 개선하는지 보려고 토픽을 얹는 중이다.
호스팅 방식은?SaaS, BYOC, 하이브리드. 처음부터 하이브리드를 염두에 두고 설계했다. 제어 평면(웹앱·메타데이터)은 Braintrust가, 데이터 평면(트레이스·데이터셋·실험)은 고객 VPC에 둘 수 있다. 슬라이드에 나온 고객의 90%는 자체 호스팅일 것이라고 추정했다.
긴 대화는 토픽을 어떻게 처리하나?설정으로 푼다. 트레이스 단위가 아니라 그룹 단위로 묶고, 일정 시간이 지난 뒤에만 돌리게 할 수 있다. 워크숍 뒤쪽에서 실제 설정을 보여 줬다.
전처리기를 바꿀 수 있나?기본 전처리기 외에 직접 만들 수 있다. 패싯도 마찬가지다. 발표자는 이 파이프라인이 "좋은 의미로 완전히 해킹 가능하다"고 표현했다.

워크숍 준비 32:30

행사장 인터넷이 끊겨 참가자 대부분은 따라 하지 못했다. 발표자 혼자 진행했다. 저장소는 GitHub의 dpguthrie 계정에서 찾을 수 있다고 했다.

  1. 조직과 프로젝트Braintrust 조직을 만들고 프로젝트 이름을 AIE-workshop으로 짓는다. 저장소 코드가 이 이름을 가정한다
  2. AI 제공자 등록설정에서 OpenAI와 Anthropic API 키를 넣는다. 온라인 채점에 LLM 심판을 쓰려면 모델이 필요하다. 최근 주요 제공자에 워크로드 아이덴티티 연합도 추가했고, 자체 게이트웨이도 커스텀 제공자로 연결할 수 있다
  3. Braintrust API 키 생성
  4. 의존성 설치uv로 가상 환경을 만들고 개발 의존성까지 설치한다
  5. .env 작성예시 파일을 복사해 Braintrust API 키와 기본 모델을 넣는다. 기본 모델은 등록한 제공자에서 접근 가능한 것이어야 한다. 채팅 UI와 평가 실행에 쓴다
  6. Braintrust CLI임의 SQL 실행, 평가 실행, 로그 보기, 데이터셋 만들기를 터미널에서 한다. bt setup skills로 코딩 에이전트(Codex, Claude Code, OpenCode, Cursor, Qwen(추정), Gemini)에 스킬을 준다. bt init은 조직과 프로젝트를 담은 config.json을 만든다. 저장소에 올려 두면 팀 전체가 같은 설정을 쓴다
  7. 점검make ready로 CLI, API 키, 기본 모델이 다 있는지 확인한다

채점 스코어는 사용자가 등록한 모델로 돈다. 그래서 자기 API 키가 필요하다. 토픽 파이프라인만 Braintrust 호스팅 모델을 쓴다.

질의응답 2: 운영 질문 1:24:00

질문발표자의 답
하이브리드 배포 조건엔터프라이즈 플랜에서만 된다. BYOC는 데이터 평면이 고객 인프라에 있되 Braintrust가 관리한다. 하이브리드는 고객 팀이 직접 관리하고 Terraform 제공자나 Helm 차트를 준다.
고객들은 어떤 모델을 쓰나대부분 큰 제공자의 모델이다. 조금씩 바뀌어 직접 미세 조정하는 곳이 생기고 있다. 평가의 목적 하나가 회귀 없이 모델을 갈아 끼우는 것이다.
토픽에 다른 모델을 쓸 수 있나요약과 임베딩 단계는 Braintrust 호스팅 모델만 된다. 그 일에 맞춰 학습했고, 다른 모델을 꽂아 봤더니 결과가 나빴다.
토픽 결과로 대시보드를 만들 수 있나된다. 라벨은 트레이스의 메타데이터라서 꺼내 쓸 수 있다. 예시 뷰는 classifications.sentiment가 비어 있지 않은 것을 라벨로 묶어 시간에 따른 감정, 작업 상위 목록을 그렸다. 지금은 모니터 페이지가 프로젝트 단위다. 조직 전체 뷰는 직접 질의해야 하고 앞으로 바뀔 예정이다.
샘플링 비율은 어떻게 정하나새 에이전트는 높게, 성숙할수록 낮춘다. 아는 실패가 줄면 스코어가 주는 신호도 줄기 때문이다. LLM 심판이 분류나 분류 체계 성격이면 토픽으로 바꿔 보라. Dropbox는 복잡한 분류 스코어를 토픽으로 실험했다. 심판은 트레이스 100%에 돌릴 수 없었지만 토픽은 비용 때문에 가능했다.
스코어 A의 결과로 스코어 B를 돌릴 수 있나UI에는 없다. 코드 기반 스코어 하나가 안에서 A를 부르고 그 결과로 B를 불러 점수 배열을 돌려주면 된다. 또는 자동화 필터로 특정 스코어 스팬이 있을 때만 돌게 할 수 있다.
토픽이 찾아낸 뜻밖의 것어느 고객이 사용자가 에이전트로 하려는 줄 몰랐던 일을 작업 패싯에서 발견했다. 실패가 아니라 기능 요청이었다. 발표자는 이것이 가장 놀라웠다고 했다.
프로젝트는 어떻게 나누나용도나 에이전트 단위다. 한 프로젝트에 로그, 데이터셋, 스코어가 함께 산다. 곧 프로젝트 안에 일급 에이전트 객체가 생겨 다중 에이전트 시스템도 한 프로젝트에서 구분할 수 있다.
평가는 얼마나 자주 바뀌나에이전트를 바꾸는 만큼이다. 프롬프트만 고치면 데이터셋에 예시를 몇 개 보태는 정도다. 단순한 에이전트면 평가가 거의 안 바뀔 수 있다는 지적은 타당하다. 그래도 싸게 할 수 있다면 프로덕션 신호를 만드는 일 자체에 가치가 있다.
스코어를 Braintrust에서 돌릴까, 내 인프라에서 돌릴까둘 다 하는 고객이 있다. 복잡한 의존성이 있는 코드 스코어도 올릴 때 의존성을 함께 묶을 수 있는데, 이걸 모르는 고객이 있었다. 올리면 "마지막 이벤트 후 60초 기다렸다가 실행" 같은 비동기 코드를 내 쪽에서 안 짜도 된다. 스팬은 변경 가능해서 스팬 ID만 있으면 내 코드에서 점수와 지표를 나중에 붙일 수도 있다.
트레이스 접근을 막으면서 통찰은 주고 싶다트레이스는 아무도 못 보는 프로젝트에 쓰고, 서비스 계정이 플라이휠을 돌리게 한다. 사람에게는 분석 결과, 실행한 SQL, 집계 데이터, PR만 준다.
가장 저평가된 기능Braintrust CLI. 2월 말에 나왔는데 아직 안 쓰는 고객이 많다. 모두 코딩 에이전트를 쓰는 시대라 CLI와 스킬을 붙이는 것이 가장 설득력 있다. 둘째는 원격 평가remote eval. 평가를 플레이그라운드에 노출해 PM이나 도메인 전문가가 시스템 프롬프트나 도구 설명을 바꿔 보게 한다. 엔지니어가 병목이 되지 않게 한다.
원격 평가는 어떻게 동작하나평가 코드에 파라미터(각 에이전트의 프롬프트와 모델 등)를 노출한다. --dev로 개발 서버를 띄우면 플레이그라운드가 localhost 8300에서 찾는다. 자체 인프라에 올릴 수도 있다. 플레이그라운드에서 실행하면 Braintrust가 그 서버의 평가 엔드포인트에 POST를 보내고, 코드는 서버에서 돌고 결과만 스트리밍된다. 발표자의 예시 서버는 Modal에 떠 있다.
코딩 에이전트 세션 자체를 평가하나내부에서 준비 중이다. 스킬에 평가를 돌리고 Claude Code·Codex 세션을 이해하는 부품을 만들고 있다. 저장소의 커밋 두 개, 별 한 개는 중요도를 보여 주는 게 아니라고 했다.
13

핵심 정리

  1. 트레이스가 없으면 에이전트는 블랙박스다. 모든 단계와 도구 입출력을 기록하는 것이 관측성의 바닥이다.
  2. 진짜 어려운 일은 모으는 것이 아니라 그 데이터에서 신호를 뽑는 것이다. 사람이 다 읽을 규모가 아니다.
  3. 플라이휠: 고치고, 평가하고, 배포하고, 관찰하고, 통찰을 뽑아 다시 고친다. 프로덕션이 개발을 이끈다.
  4. 스코어는 아는 실패를 잰다. 코드 기반은 싸고 빠르고, LLM 심판은 주관을 다루며, 심판은 사람 검토로 보정한다.
  5. 스코어 요령: 이유 남기기, 처음엔 이진 채점, 가혹한 기준, 프롬프트에 예시, 채점 모델은 생성 모델보다 강하게. 100점은 테스트가 약하다는 신호다.
  6. 토픽은 모르는 실패와 기능 요청을 찾는다. 전처리, 패싯, 요약, 임베딩, 지도, 라벨 순서로 돌고 전용 호스팅 모델을 쓴다.
  7. 자동화 범위는 트레이스, 스팬, 그룹 셋이다. 여러 트레이스에 흩어진 대화는 대화 ID로 묶는다.
  8. 커스텀 패싯은 "문제 없음"을 정규식으로 걸러 잘못된 것만 남긴다. 토픽은 결과가 100개는 모여야 지도를 만든다.
  9. 신호를 읽는 주체가 사람의 클릭에서 SQL을 쓰는 Loop로, 다시 CLI와 스킬을 쥔 코딩 에이전트로 옮겨 간다. 코딩 에이전트는 코드베이스를 알기 때문에 실제 수정까지 한다.
  10. 평가 데이터셋은 기준선일 뿐이다. 프로덕션에서 고른 사례를 계속 보태고, 반복되는 실패는 새 스코어로 만든다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 "신호" 두 가지는 무엇이고 각각 무엇을 잡나?
스코어와 토픽. 스코어는 이미 아는 실패 유형(아는 모름)을 재고, 토픽은 아직 모르는 패턴(모르는 모름)과 조용한 실패, 기능 요청을 찾는다.
Q2평가에서 모든 케이스가 100점이면 발표자는 어떻게 해석하라고 했나?
테스트 케이스가 충분히 어렵지 않거나 스코어가 충분히 가혹하지 않다는 뜻이다. 기준을 다시 조정해야 한다.
Q3스코어 종류 네 가지는?
코드 기반, LLM 심판, 사람 검토와 맞춘 LLM 심판, 그리고 코드 안에서 LLM을 부르는 코드 기반 스코어.
Q4토픽 파이프라인의 여섯 단계를 순서대로 말해 보자.
전처리 → 패싯 적용 → 요약 → 벡터 임베딩 → 토픽 지도 → 라벨과 분류.
Q5토픽 파이프라인에서 다른 모델을 쓸 수 없는 단계와 그 이유는?
요약과 임베딩 단계. Braintrust가 그 일에 맞춰 학습한 호스팅 모델만 쓴다. 다른 모델을 꽂아 봤더니 결과가 나빴다고 한다.
Q6자동화 범위 세 가지와, 여러 트레이스로 흩어진 대화에 쓰는 것은?
트레이스, 스팬, 그룹. 흩어진 대화는 그룹 범위를 고르고 대화 ID 같은 공통 메타데이터로 묶는다.
Q7커스텀 패싯을 만들 때 발표자가 쓴 요령은?
프롬프트에서 문제가 없으면 "none"을 내게 하고, 제외 정규식으로 그 출력을 걸러 낸다. 잘못된 것만 보려는 목적이다.
Q8기본 이슈 패싯의 토픽이 생기지 않은 이유는? 발표자는 그것을 어떻게 봤나?
토픽 지도는 패싯 결과가 최소 100개 모여야 만들어지는데, 기본 이슈 프롬프트가 이 에이전트와 안 맞아 결과가 거의 없었다. 발표자는 쓸 수 없는 신호를 억지로 만들지 않는 것이 좋은 일이라고 봤다.
Q9Loop가 "최근 로그에서 무엇을 개선할까"라는 질문에 답하기 위해 한 일은?
BrainStore에 SQL을 여러 번 날려 관련 트레이스만 끌어왔다. 모든 트레이스를 읽는 대신, 붙어 있는 스코어와 토픽 라벨을 기준으로 필요한 부분만 질의했다.
Q10Braintrust는 못 하지만 CLI를 쥔 코딩 에이전트는 할 수 있는 일은?
코드베이스를 알고 실제 수정을 하는 것. Braintrust는 내 코드를 모르니 특정 함수나 아키텍처를 고치라고 권할 수 없다. 코딩 에이전트는 저장소 안에서 신호를 읽고 도구를 추가하거나 스코어를 만든다.
Q11샘플링 비율은 에이전트 성숙도에 따라 어떻게 바뀌어야 하나?
새 에이전트는 높게, 성숙할수록 낮춘다. 아는 실패가 줄면 스코어가 주는 신호도 줄기 때문이다. 분류 성격의 심판은 더 싼 토픽으로 바꾸는 것도 방법이다.
Q12원격 평가는 누구를 위한 기능인가?
PM이나 도메인 전문가처럼 코드 밖에서 플라이휠에 기여하는 사람. 평가를 플레이그라운드에 노출해 시스템 프롬프트나 도구 설명을 바꿔 보게 한다. 엔지니어가 병목이 되지 않게 하는 목적이다.
