에이전트에게 도구 대신 샌드박스를

도구를 하나씩 쥐여 주는 대신, 모델이 도구를 골라 코드로 엮어 샌드박스에서 실행하게 하자는 발표다. Arize는 이 "코드 모드"로 토큰을 43%, 비용을 31% 줄였다고 보고했고, 대신 보안과 운영에서 새로 떠안는 일도 함께 짚는다.

원본 영상: Stop Giving Your Agent Tools. Give It a Sandbox 발표: Mikyo King (Arize AI 오픈소스 그룹 총괄)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름 중 확실한 것(Arize, Claude Code, Code Mode, sed)은 바로잡았고, 불확실한 것은 들린 대로 두고 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 코딩 에이전트가 필요한 소프트웨어를 즉석에서 만들어 주면서 개발자와 비개발자의 경계가 사라지고 있다. 우리가 만드는 에이전트도 이 능력을 쓰게 하자는 것이 출발점이다.
  2. 도구를 잔뜩 준 에이전트는 일이 길어질수록 컨텍스트가 부풀고 턴이 늘어난다.
  3. 코드 모드는 모델이 필요한 도구를 검색하고, 그 도구를 부르는 코드를 써서 샌드박스에서 실행하게 한다. 한 턴에 여러 도구를 엮고, 필요한 결과만 돌려받는다.
  4. 통하는 이유는 넷이다. 점진적 공개, 조합성, 토큰 효율, 그리고 스스로 도구를 만드는 능력이다.
  5. 대가도 있다. 자원, 네트워크, 비밀 값, 권한, 디버깅, 이중 샌드박싱 같은 보안과 운영 부담이 생긴다.
  6. Arize는 같은 과제를 여러 번 돌려 평가했다. 코드 모드 뒤 토큰 43%, 비용 31%가 줄었고 지연 시간은 거의 그대로였다고 보고했다.
  7. 실행 기록과 평가 결과를 함께 모으면, 지시문의 어느 부분이 에이전트를 잘못 이끄는지 찾아 고칠 수 있다.
01

개발자와 비개발자의 경계 00:40

지난 30년의 소프트웨어는 두 종류로 나눌 수 있었다. 개발자를 위한 소프트웨어와 비개발자를 위한 소프트웨어다. 발표자는 메일함에서 송장invoice을 모두 꺼내는 일을 예로 든다.

개발자라면

50줄쯤 되는 스크립트를 쓴다. 메일마다 첨부 파일이 있는지 보고, 내려받아 폴더에 넣는다. 한 번 쓰면 계속 쓸 수 있는 도구가 생긴다.

비개발자라면

메일을 하나씩 열어 직접 내려받는다. 소프트웨어 화면이 허락하는 만큼만 할 수 있다. 필요한 기능이 있으면 그 소프트웨어를 사야 한다.

Claude Code 같은 코딩 에이전트는 이 경계를 허문다. 필요한 소프트웨어를 그 자리에서 만들어 주기 때문이다. 01:20

모델 회사들도 이 점을 안다. SWE-bench 같은 벤치마크가 보여 주듯, 모델은 코드를 쓰도록 학습되고 있다. 그렇다면 우리가 만드는 에이전트도 필요한 소프트웨어를 즉석에서 만드는 쪽으로 맞추는 게 자연스럽다. 이것이 발표의 출발점이다.

02

도구를 잔뜩 준 에이전트 01:50

흔히 만드는 에이전트는 이렇게 돈다.

  1. 에이전트에게 큰 도구 목록을 준다.
  2. 사용자 질문이 들어오면 도구를 하나 부른다.
  3. 도구 결과가 컨텍스트 윈도우에 쌓인다.
  4. 모델이 그 결과를 보고 판단한 뒤 다음 도구를 부른다.

도구가 적당히 정해져 있으면 이 방식도 잘 된다. 문제는 우리가 이제 더 많은 걸 원한다는 점이다. 미리 설계하지 않은 행동, 더 많은 컨텍스트, 더 긴 작업long horizon을 바란다. 02:30

그러면 컨텍스트가 부푼다 작업과 상관없는 도구 설명이 컨텍스트에 들어간다. 도구가 쓸모없는 내용을 잔뜩 돌려주기도 한다. 데이터를 페이지 단위로 넘겨 가며 읽어야 할 때도 있다. 그 결과 컨텍스트 부패context rot가 생기고, 턴이 늘어나고, 결국 컨텍스트를 요약해 줄이는 컴팩션compaction까지 해야 한다.
03

코드 모드란 03:00

코드 모드Code Mode는 도구 호출의 대안 구조다. 도구 메뉴를 통째로 주는 대신 두 가지 능력을 준다.

  • 도구 검색: 지금 필요한 도구를 찾아본다.
  • 도구 실행: 그냥 부르는 게 아니라, 프로그래밍 환경 안에서 코드로 부른다.

코드로 부르니 도구를 차례로 부르거나, 동시에 부르거나, 조건문으로 감쌀 수 있다. 한 턴에 여러 도구를 부르고, 모델 컨텍스트에는 꼭 필요한 결과만 돌려보낸다.

전통적인 도구 호출 03:50
  • 도구를 부를 때마다 컨텍스트가 늘어난다
  • 지연 시간과 비용이 커진다
  • 턴이 늘어 사용자가 결과를 받기까지 오래 걸린다
코드 모드 (잘 만들었을 때)
  • 한 턴에 도구를 원하는 만큼 부른다
  • 문제 풀이에 필요한 것만 컨텍스트에 넣는다
  • 턴 수가 줄어든다

예시: 아래 코드는 발표에 없다. 앞의 송장 예를 코드 모드로 옮기면 이런 모양이 된다. search_email, download_attachment는 가상의 도구다. 도구 호출 방식이었다면 메일 조회, 첨부 확인, 다운로드를 메일마다 따로 부르고, 그 결과가 모두 컨텍스트에 쌓였을 것이다.

# 예시 (발표에 없는 코드): 모델이 한 턴에 써서 샌드박스에서 실행하는 스크립트
messages = search_email(query="invoice", limit=500)
saved = [download_attachment(m.id, folder="invoices/") for m in messages if m.has_attachment]
print(len(saved), saved[:3])  # 모델 컨텍스트로 돌아가는 건 이 출력뿐

05

Arize가 열어 준 실행 환경 06:10

Arize는 오픈소스 관측 플랫폼 Phoenix 안에 자체 에이전트와 하네스를 만들었다. 에이전트에게 코드를 실행할 환경을 하나씩 늘려 줬다.

실행 환경넣은 것열린 일
Bash 06:20sed, grep 같은 리눅스 기본 명령, Arize 자체 CLI명령을 엮어 쓰고, 결과를 파일로 빼 두었다가 나중에 쓴다
Python 샌드박스 06:40REST CRUD 엔드포인트 전부. 예: 트레이스 조회, 데이터셋 수정생성, 조회, 수정, 삭제를 코드로 엮는다
SQL 07:00SQL을 직접 쓰는 능력CRUD로 안 되는 집계 질문을 푼다. 예: P95 지연 시간이 특정 값인 LLM 스팬 찾기
UI에 묶은 실행 환경 07:40웹 워커 안의 프로그래밍 환경. 브라우저 화면과 양방향 데이터 바인딩시간 범위 바꾸기, 화면의 데이터 읽기 같은 복잡한 UI 조작

SQL을 넣은 이유는 모든 일이 생성·수정·삭제 도구에 들어맞지 않기 때문이다. 집계 질문 하나에 트레이스를 페이지마다 넘겨 볼 수는 없다. 모델이 원하는 것만 정확히 집어내게 해야 한다.

UI에 묶은 환경에서는 컴퓨터 사용computer use과 비슷한 행동이 저절로 나타났다. 발표자는 에이전트가 화면을 조작하는 모습을 보는 게 꽤 재미있다고 했다.

문제내용

08

Arize의 평가 방법 11:40

Arize는 자기 플랫폼 Arize Phoenix를 직접 쓰면서dogfooding 코드 모드를 평가했다.

  1. Harbor 프레임워크로 에이전트를 샌드박스 환경에 넣는다.
  2. 명확한 지시를 주고, 네트워크는 끈다.
  3. 같은 과제를 여러 번 돌려 결과가 들쭉날쭉한 것flake을 걸러 낸다.
  4. 평가는 Harbor 검증기verifier로 만든다. 에이전트가 맞게 했는지 판정하는 코드다.
  5. 강화학습식으로 성공이면 1, 실패면 0을 준다.
  6. 여러 조합으로 돌려 보고, 과제마다 pass@k를 추적한다. 12:30
왜 여러 번 돌리나 에이전트는 결과가 매번 같지 않은 시스템이다. 같은 과제도 실행할 때마다 다른 경로를 밟는다. 한 번 성공했다고 믿을 수 없고, 한 번 실패했다고 버릴 수도 없다.
09

결과: 토큰 43% 감소 12:50

Harbor로 코드 모드 전과 후를 비교한 결과다.

Arize는 Claude Code, MCP, CLI 중 어느 경로로 써도 전보다 나아졌다고 판단했다.

토큰 감소폭(43%)과 비용 감소폭(31%)이 왜 다른지는 발표에서 설명하지 않았다.

발표자는 평가 도구를 파는 Arize AI 소속이다. 이 결과는 Arize가 자기 에이전트를 자기 도구로 잰 것이고, 과제 수, 모델, 측정 조건은 발표에 나오지 않았다. 그 점을 감안해 읽자.

10

데이터로 에이전트 고치기 13:20

실행 궤적trajectory과 평가 결과를 함께 모아 두면 큰 도움이 된다. 에이전트가 실제로 어떻게 움직였는지 보고, 어느 방향으로 고칠지 정할 수 있다.

예를 들어 새 도구를 넣으면 오히려 효율이 떨어질 때가 있다. 그러면 코딩 에이전트에게 알려 준다. 어떤 상황에서 지시문의 어느 부분이 에이전트를 잘못 이끌었는지를 짚어 준다. 이렇게 평가 점수를 조금씩 올리는 방식을 힐 클라이밍hill climbing이라 부른다.

11

결론 14:00

Arize가 코드 모드를 좋아하는 이유는 세 가지다.

  • 턴이 줄어든다.
  • 더 싸진다. 사용자가 원하는 모델을 가져다 쓸 수 있게 하고 싶다.
  • 창발적 행동과 긴 작업이 가능해진다.
에이전트에게 샌드박스를 주고, 평가는 저희 도구로 하세요.발표 마무리 발언을 옮김 14:20

마지막 문장은 Arize 제품 홍보다. 또 앞에서 작은 모델은 코드 모드를 잘 못 할 수 있다고 했으니, "원하는 모델을 쓴다"는 말은 그 한계와 함께 읽어야 한다.

12

핵심 정리

  1. 코딩 에이전트가 필요한 소프트웨어를 즉석에서 만들면서 개발자와 비개발자의 경계가 사라지고 있다.
  2. 모델은 이미 코드를 쓰도록 학습된다. 에이전트도 그 능력에 맞춰 설계하자는 것이 출발점이다.
  3. 도구를 잔뜩 준 에이전트는 일이 길어질수록 컨텍스트가 부풀고 턴이 늘어난다.
  4. 코드 모드는 모델이 도구를 검색하고, 코드로 실행하게 한다.
  5. 한 턴에 여러 도구를 차례로, 동시에, 조건에 따라 엮고 필요한 결과만 컨텍스트로 돌려보낸다.
  6. 통하는 이유는 점진적 공개, 조합성, 토큰 효율, 스스로 도구를 만드는 능력이다.
  7. Arize는 Bash, Python 샌드박스, SQL, UI에 묶은 실행 환경을 에이전트에게 줬다.
  8. 대가는 자원·네트워크·비밀 값·권한 관리, 어려운 디버깅, 도구 탐색, 이중 샌드박싱이다.
  9. 열린 문제는 중간 재개, 수학 정확도와 언어 선택, 바이너리 결과 꺼내기, 작은 모델의 능력이다.
  10. Arize는 같은 과제를 여러 번 돌려 pass@k로 쟀고, 토큰 43%, 비용 31% 감소를 보고했다. 자체 측정이다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 "사라지고 있다"고 한 경계는 무엇과 무엇의 경계인가?
개발자를 위한 소프트웨어와 비개발자를 위한 소프트웨어의 경계. 코딩 에이전트가 필요한 소프트웨어를 즉석에서 만들어 주기 때문이다.
Q2도구를 잔뜩 준 에이전트가 긴 작업을 할 때 생기는 문제는?
관련 없는 도구 설명과 쓸모없는 도구 출력이 컨텍스트를 채운다. 컨텍스트 부패가 생기고, 턴이 늘고, 컴팩션이 필요해진다.
Q3코드 모드가 모델에게 주는 두 가지 능력은?
필요한 도구를 찾는 도구 검색, 그리고 프로그래밍 환경 안에서 코드로 도구를 부르는 도구 실행.
Q4코드 모드에서 턴 수와 토큰이 줄어드는 이유는?
한 턴에 여러 도구를 코드로 엮어 실행하고, 그중 필요한 결과만 컨텍스트로 돌려보내기 때문이다.
Q5개인 식별 정보 제거 예시는 무엇을 보여 주나?
도구 호출 방식은 맞는 도구가 없으면 못 하거나, 컨텍스트 안에서 처리하다 신용카드 번호를 흘린다. 코드 모드는 필요한 도구를 스스로 짜서 쓴다.
Q6Arize가 실행 환경에 SQL을 추가한 이유는?
모든 일이 생성·조회·수정·삭제에 들어맞지 않기 때문이다. 집계 질문은 트레이스를 페이지마다 넘기지 않고 SQL로 바로 집어내는 편이 낫다.
Q7UI에 묶은 실행 환경에서 컴퓨터 사용과 비슷한 행동이 나온 이유는?
웹 워커 안의 프로그래밍 환경이 브라우저 화면과 양방향으로 연결돼 있어서다. 에이전트가 시간 범위를 바꾸고 화면 데이터를 읽는 등 UI를 직접 조작할 수 있다.
Q8코드 모드에서 도구 파라미터 정확도가 더 큰 문제가 되는 이유는?
이제 파라미터가 곧 코드이기 때문이다. 코드가 중간에 실패하면 그 뒤 처리가 어려워진다.
Q9이중 샌드박싱 문제란?
MCP와 하네스 양쪽에 코드 모드가 들어가면, 한쪽 결과를 JSON으로 직렬화하고 파싱해서 다른 코드 모드에 다시 넣는 이중 작업이 생긴다.
Q10발표자가 꼽은 열린 문제 네 가지는?
중간에 깨지면 재개할 수 없는 내구성, 수학 정확도와 언어 선택, 이미지 같은 바이너리 결과를 꺼내는 일, 작은 모델의 부족한 능력.
Q11Harbor 평가에서 같은 과제를 여러 번 돌리는 이유와 추적하는 지표는?
에이전트는 매번 다른 경로를 밟는 비결정적 시스템이라 결과가 들쭉날쭉하다. 그래서 여러 번 돌리고 과제마다 pass@k를 추적한다.
Q12Arize가 보고한 코드 모드 전후 변화는? 읽을 때 주의할 점은?
토큰 43% 감소, 비용 31% 감소, 지연 시간은 거의 그대로. Arize가 자기 도구로 잰 자체 결과이고, 측정 조건은 발표에 나오지 않았다.

용어 정리

용어뜻
코드 모드Code Mode. 도구를 하나씩 부르는 대신, 모델이 도구를 부르는 코드를 써서 샌드박스에서 실행하게 하는 에이전트 구조
도구 호출Tool calling. 모델이 함수 이름과 인자를 내면 시스템이 실행하고 결과를 돌려주는 방식
샌드박스바깥 시스템과 격리된 실행 환경. 모델이 만든 코드를 안전하게 돌리는 곳
하네스모델을 감싸 도구, 순서, 규칙, 검사를 정해 주는 실행 틀
컨텍스트 윈도우모델이 한 번에 읽을 수 있는 입력 범위
컨텍스트 부패Context rot. 쓸모없는 내용이 쌓여 모델의 판단이 흐려지는 현상
컴팩션Compaction. 대화가 길어지면 앞부분을 요약해 컨텍스트를 줄이는 일
턴모델이 한 번 응답하고 그 결과를 받는 한 주기
점진적 공개Progressive disclosure. 필요한 정보를 필요한 때에만 보여 주는 방식
조합성Composability. 작은 부품을 엮어 더 큰 동작을 만들 수 있는 성질
창발적 행동Emergent behavior. 미리 설계하지 않은 능력이 스스로 나타나는 것
개인 식별 정보PII. 이름, 카드 번호처럼 특정 개인을 알아볼 수 있는 정보
CRUD생성(Create), 조회(Read), 수정(Update), 삭제(Delete). 데이터를 다루는 기본 네 동작
트레이스 / 스팬Trace / Span. 에이전트 실행 한 번의 전체 기록 / 그 안의 한 단계
P95 지연 시간요청을 빠른 순으로 줄 세웠을 때 95번째 백분위에 해당하는 응답 시간
웹 워커Web worker. 브라우저에서 화면과 따로 도는 백그라운드 스크립트
양방향 데이터 바인딩코드 쪽 값과 화면 쪽 값이 서로 바뀌면 바로 따라 바뀌게 연결한 것
컴퓨터 사용Computer use. 모델이 화면을 보고 클릭과 입력으로 소프트웨어를 조작하는 것
이그레스Egress. 샌드박스에서 바깥으로 나가는 네트워크 통신
직렬화Serialization. 데이터를 JSON 같은 문자열로 바꾸는 것
MCPModel Context Protocol. 모델에 도구와 데이터를 연결하는 표준 규약
내구성Durability. 실행이 중간에 끊겨도 그 지점부터 이어 갈 수 있는 성질
Harbor에이전트를 샌드박스 환경에 넣어 과제를 돌리고 채점하는 평가 프레임워크
검증기Verifier. 에이전트가 과제를 맞게 했는지 판정하는 평가 코드
flake같은 조건에서도 결과가 들쭉날쭉하게 나오는 것
pass@k같은 과제를 k번 시도했을 때 한 번 이상 성공할 확률
실행 궤적Trajectory. 에이전트가 실행되며 한 단계씩 무엇을 했는지 기록한 것
힐 클라이밍Hill climbing. 평가 점수를 보며 조금씩 고쳐 올리는 반복 개선
도그푸딩Dogfooding. 자기 회사 제품을 자기가 직접 쓰는 것
