은행이 직접 만든 코딩 에이전트

디지털 은행 Monzo는 Slack에서 이모지 하나로 부르는 사내 코딩 에이전트를 만들었다. 발표자들은 성공 비결이 모델이 아니라, 이미 쌓아 둔 플랫폼 기능이 서로 곱해진 효과라고 말한다.

원본 영상: A Bank Built Its Own Coding Agent. It Took Off 발표: Felipe Felisola Caso, Francesco Galletta (Monzo)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 에이전트 이름은 자막에 Agent Chip과 Agent Ship이 섞여 나와서, 더 자주 들린 Agent Chip으로 적었다(추정). mm:ss는 영상 위치다.

3분 요약
  1. Monzo는 백엔드 서비스 3,000개 이상과 데이터 모델 약 13,000개를 운영하는 디지털 은행이다.
  2. 2026년 1월, Slack 메시지에 이모지 하나를 달면 일을 시작하는 사내 에이전트 Agent Chip이 회사 안에 퍼졌다.
  3. 발표자에 따르면 지금은 기술 조직 머지 PR의 10% 이상을 쓰고, 하루 1,800건 이상의 작업을 처리한다.
  4. 비결은 LLM이다. 단, Lots of Little Multipliers(작은 배수 여러 개)라는 뜻이다. 모니터링, 스테이징, 배포 같은 기존 플랫폼 기능이 서로 곱해졌다.
  5. 뼈대는 두 개다. 에이전트에 무엇을 보여 줄지 정하는 MCP 게이트웨이, 그리고 에이전트를 격리된 샌드박스에서 돌리는 오케스트레이션 시스템이다.
  6. 은행이라서 에이전트의 예측 불가능한 동작을 상자 안에 가둔다. 상자 안에서는 자유롭고, 밖으로는 허용한 곳으로만 나간다.
  7. Agent Chip 자체도 블록이 되어 장애 대응, 팀 간 질문, 데이터 품질 감시, 비전문가의 기여로 쓰임이 넓어졌다.
01

서비스 3,000개를 가진 은행 00:20

Monzo는 "모두를 위해 돈이 일하게 한다"를 내건 디지털 은행이다. 코딩 에이전트 coding agent가 상대할 문제의 크기는 이렇다.

데이터 웨어하우스 모델 data warehouse model은 분석용 데이터 저장소에서 데이터를 가공하는 단위다. 여기에 머신러닝 예측 모델 ML predictor도 수십 개 있다. 이 시스템들로 대출 심사, 금융 범죄 판단 같은 결정을 내린다. 앱, 백엔드, 데이터 모두에 복잡한 쓰임이 걸려 있다.

업계 분위기 01:00

요즘은 코딩 에이전트를 도입해 성공했다는 회사 이야기가 넘친다. 발표자는 몇 주 전 뉴욕의 한 콘퍼런스 뒤에 나온 2026년 업계 현황 글을 소개했다. 그 글은 X의 한 게시물을 인용했다.

자체 AI 코딩 하네스를 만들지 않는다면, 진지한 테크 회사라고 할 수 있나?X 게시물, 발표자가 인용. 발표자는 농담이길 바란다고 덧붙였다.

하네스 harness는 모델을 감싸 도구, 권한, 실행 순서를 정해 주는 틀이다.

02

이모지 하나로 부르는 동료 01:30

2026년 1월, Monzo 사내 Slack에서 한 채널이 크게 화제가 됐다. 사내 에이전트 Agent Chip(추정)의 채널이다.

쓰는 법이 아주 쉬웠다. 아무 Slack 메시지에 Agent Chip 전용 이모지로 반응하면 된다. 그러면 Agent Chip이 그 메시지를 프롬프트로 받아 일을 시작한다. 01:50

반응이 좋자 팀은 투자를 늘렸다. Agent Chip은 Slack과 사내 환경 어디서나 부를 수 있는 동료가 됐다. 02:10

  • 질문과 요청: @Agent Chip으로 부르면 일을 하거나, 질문에 답하거나, 아키텍처 정보를 찾아 준다.
  • 코드 리뷰 02:30: 리뷰도 한다. 발표자는 "아주 시니어 엔지니어처럼 LGTM 한마디만 남긴다"고 농담했다. LGTM은 "좋아 보인다"는 승인 표시다.
  • 티켓 처리 02:40: 이슈 관리 도구 Linear의 티켓을 맡기면 바로 작업에 들어간다.
03

지금의 성적표 02:50

항목발표자가 밝힌 값
머지된 PR 중 Agent Chip이 쓴 비율10% 이상. 데이터, 머신러닝, 백엔드, 앱을 아우르는 기술 조직 전체 기준
하루 작업 수1,800건 이상
쓰는 사람엔지니어뿐 아니라 비개발 직군도 쓰기 시작했다. 업무 질문에 답을 얻고, 쿼리를 쓰고, 필요한 것을 스스로 해결한다

이 수치는 Monzo가 자기 사내 도구에 대해 밝힌 것이다. "Agent Chip이 썼다"를 어떻게 셌는지, 어느 기간 기준인지는 발표에 나오지 않는다. 자기 팀의 성과 발표라는 점을 감안해 읽자.

그래서 무엇을 말하려는가 03:40

코딩 에이전트 성공담은 이미 많다. 발표자는 "Anthropic이 비슷한 제품(자막상 Claude Tag, 추정)을 내기 6개월 전에 우리가 먼저 만들었다"고 자랑할 수도 있다고 했다. 하지만 그게 오늘의 요점은 아니라고 했다.

04

비결은 다른 뜻의 LLM 03:50

발표자가 꼽은 비결은 LLM이다. 다만 여기서 LLM은 대규모 언어 모델이 아니다. Lots of Little Multipliers, 곧 "작은 배수 여러 개"의 줄임말이다.

발표자는 Agent Chip을 빠르게, 쓸모 있게 만들 수 있었던 이유를 Monzo의 튼튼한 플랫폼에서 찾는다. 겉으로는 "프롬프트 쓰고, 이모지 달고, 결과 받기"처럼 보였다. 실제로는 이미 갖춘 여러 기능 위에 서 있었다.

겉으로 보인 것Slack에서 이모지 한 번프롬프트를 쓰고, 반응을 달고, 결과를 받는다
→
실제로 받친 것 04:10이미 있던 플랫폼 기능알림, 모니터링, 외부 서비스 연동, 쉽게 테스트하는 스테이징 환경, 큐 추상화, 쉬운 배포, 데이터베이스 추상화

스테이징 환경 staging은 운영 환경과 비슷하게 꾸린 시험용 환경이다. 이런 기능 하나하나는 작다. 하지만 새로 만드는 것마다 그 위에 바로 올라탈 수 있으니 효과가 곱해진다. 발표 첫머리에 말한 "복리처럼 쌓이는 가치 compound value"가 이 뜻이다.

05

첫 블록: MCP 게이트웨이 04:50

투자는 Agent Chip보다 먼저 시작됐다. Monzo는 서버에서 도는 원격 에이전트 remote agent를 만들기 전부터, 개발자 컴퓨터에서 도는 로컬 코딩 에이전트를 지원했다.

첫 작업이 MCP 게이트웨이 MCP gateway다. 05:00 MCP는 AI 에이전트가 외부 도구와 데이터에 연결하는 표준 방식이다. 게이트웨이는 그 연결을 한곳으로 모으는 문이다.

위치무엇하는 일
안쪽사내 서비스, 내부 도구, 지식 소스에이전트에 연결할 대상
가운데MCP 게이트웨이 (Monzo가 직접 만든 MCP 서버)무엇을 에이전트에 보여 줄지 고른다. 에이전트마다 인증 authentication과 인가 authorization를 관리한다
바깥에이전트처음에는 로컬 코딩 에이전트, 나중에는 Agent Chip
문은 늘 같게 동작해야 한다 에이전트는 매번 다르게 움직인다. 그래서 에이전트가 무엇에 닿을 수 있는지는 게이트웨이가 정해진 규칙대로 정한다. 발표자는 이를 "결정적인 동작"을 얻기 위해서라고 설명했다.

이유는 단순하다. 맥락과 데이터를 안전하게 많이 줄수록 에이전트가 더 잘 일한다. 발표자는 이 말을 이번 콘퍼런스의 여러 발표에서 들었을 것이라고 했다.

06

둘째 블록: 상자 안의 상자 05:50

다음으로 에이전트 오케스트레이션 시스템 agent orchestration system을 만들었다. 에이전트 작업을 띄우고, 실행을 관리하고, 결과를 읽어 오는 시스템이다. Agent Chip은 뒤에서 이 시스템으로 돈다. 도구와 권한은 아주 엄격하게 제한한다.

앞의 MCP 게이트웨이는 이 구조에서 상자 하나로 접힌다. 원격 에이전트는 격리된 네임스페이스 namespace 안의 샌드박스 sandbox에서 돈다. 오케스트레이션 시스템이 작업을 시작하고, 거기서 결과를 받아 온다. 06:20

왜 따로 떼어 놓나 06:40

은행이라서 Monzo는 규제를 받는 은행이다. 에이전트는 같은 입력에도 다르게 움직이는 비결정성 non-determinism을 가진다. 그래서 에이전트 실행 환경을 운영 인프라와 떼어 놓는다. 동시에 에이전트가 마음껏 움직이며 개발할 공간도 필요했다. 발표자는 여러 AI 연구소와 업체도 같은 방향을 말한다고 덧붙였다.

상자를 열어 보면 07:00

이 구조 덕분에 에이전트에게 데이터를 안전하게 열어 줄 수 있다. MCP 게이트웨이가 에이전트가 닿을 곳을 정하고, 오케스트레이션 시스템이 그 둘레를 관리한다. 08:10

07

블록 위에 블록을 쌓는다 08:30

게이트웨이와 오케스트레이션이라는 두 블록이 생기자, 그 위에 새 쓰임을 붙이기가 훨씬 쉬워졌다. Slack을 붙이고, GitHub를 붙이고, Linear를 붙였다. 3,000개가 넘는 사내 서비스도 같은 방식으로 이을 수 있다.

그리고 같은 일이 한 번 더 일어난다. 플랫폼이 Agent Chip을 가능하게 했듯, 이제는 Agent Chip이 은행 곳곳의 블록이 된다. 다른 부서가 Agent Chip 위에 자기 쓰임을 만든다. 09:10

층무엇
1층 플랫폼알림, 모니터링, 연동, 스테이징, 큐, 배포, 데이터베이스 추상화
2층 에이전트 기반MCP 게이트웨이, 오케스트레이션 시스템과 샌드박스
3층 Agent ChipSlack, GitHub, Linear, 사내 서비스와 연결된 원격 에이전트
4층 사용 사례장애 대응, 팀 간 질문, 데이터 품질 감시, 비전문가의 기여

층 구분은 발표 내용을 한눈에 보도록 정리한 예시다. 발표 슬라이드에 이런 표가 나오지는 않는다.

08

실제로 달라진 일 09:20

발표자는 블록 덕분에 사내 기능만 늘어난 게 아니라 업무 성과도 났다고 말한다.

  • 엔지니어가 돌리는 작업의 폭과 양이 늘었다. 에이전트를 옆에서 계속 지켜볼 필요가 없어서다. 특정 작업은 로컬 코딩 도우미로 하고, 나머지는 원격 에이전트에 맡긴다.
  • 반복 업무를 더 잘 자동화한다. 덕분에 사람은 모호함이 큰, 가치 높은 문제에 집중한다.
장애 대응 모드 10:00

장애가 선언되면 Agent Chip이 장애 채널에 들어온다. 로그와 트레이스 trace를 읽고, 문제 서비스와 코드에 직접 닿아 원인을 조사한다.

원칙: 신호가 높은 정보만 낸다. 장애 중에 말을 많이 하거나 가설을 늘어놓지 않게 한다. Agent Chip이 얼마나 개입할지는 사람이 정한다.

ask 채널 10:40

ask 채널은 Monzo 안에서 스쿼드 squad, 곧 팀끼리 질문을 주고받는 곳이다. 백엔드 서비스, 제품 개발, 로드맵에 대한 맥락을 묻는다. Agent Chip은 지식 소스에 닿을 수 있어서 답변 초안을 쓴다.

흐름: 초안으로 충분하면 Agent Chip이 질문 티켓을 직접 닫는다. 맥락이 더 필요하면 되묻고, 담당자를 태그해 불러온다.

Agent Chip on Call 11:20

데이터 품질 경보를 분류하는 트리아지 triage를 맡는다. 문제를 일으킬 만한 백엔드 변경도 점검한다. 실패가 나면 그것을 보고 조사를 자동으로 시작한다.

성격: 일이 터진 뒤 움직이는 반응형이다. 발표자는 최근 큰 가치를 내는 쓰임이라고 했다.

선제형 감시 11:50

"오류가 애초에 안 나면 어떨까?"에서 출발했다. 백엔드 변경을 지켜보다가, 그 변경이 데이터에 어떤 결과를 낼지 미리 짚는다.

성격: 다음 배치 실행 batch으로 데이터가 처리되기 전에 움직이는 선제형이다.

09

비전문가의 문턱이 낮아졌다 12:10

발표자가 더 반긴 변화는 이것이다. 엔지니어가 아닌 사람도 Monzo의 시스템에 기여하기 쉬워졌다. Slack이라는 아주 가벼운 입구가 있기 때문이다.

  1. 제품 피드백, 아이디어, 논의를 바탕으로 Agent Chip을 부른다.
  2. Agent Chip이 실제로 동작하는 변경 초안을 만든다.
  3. 그 초안은 스테이징 환경에서 이미 테스트된 상태다.
  4. 그다음에야 엔지니어가 들어와 리뷰하고 제대로 배포한다.
엄격함은 그대로 이 방식이 Monzo의 소프트웨어 개발 기준을 낮추지는 않는다. 리뷰와 배포는 여전히 엔지니어가 맡는다. 바뀌는 건 비전문가가 팀 가까이에서 기여할 수 있게 됐다는 점이다.
10

시장이 빨라도 계속 쓰는 이유 12:50

콘퍼런스마다 새 제품과 기능이 쏟아진다. 그런데도 발표자는 2026년 이후에도 Agent Chip이 가치 있다고 본다. 이유는 세 가지다.

이유내용
조합할 수 있다 13:20Agent Chip은 이제 플랫폼의 새 블록이다. 보안, 백엔드, 플랫폼 요구 사항을 지키며 연결돼 있다. 그래서 새 에이전트 쓰임을 빨리 붙인다.
특정 업체에 묶이지 않는다 13:40플랫폼은 처음부터 업체 중립 provider agnostic으로 설계했다. 가장 안쪽 에이전트 상자는 어떤 모델로든 바꿀 수 있다. 목적에 맞는 모델을 그때그때 고른다.
개발 범위가 넓어진다 14:10지금 개발을 멈춰도 이미 가치가 있다. 앞으로는 백엔드와 앱 변경 초안, 스테이징 테스트, 데이터 테스트, 어쩌면 예측 모델까지 다룬다. 원격 에이전트가 처음부터 끝까지 맡으면 시스템을 더 잘 이해하고 통합한다.

그렇다고 Agent Chip과 끝까지 함께하겠다는 뜻은 아니라고 했다. 시장은 계속 움직인다. 다만 지금은 내부 플랫폼의 튼튼한 한 부분이라고 본다. 14:40

11

결론: 작은 배수를 찾아라 15:00

LLM에서 가치를 얻어라. 전통적인 LLM 말고, 여러분과 팀이 쓸 수 있는 작은 배수 여러 개에서.발표자의 마무리를 옮김
  • 코딩 에이전트의 성공은 모델 하나로 설명되지 않는다. 이미 쌓아 둔 플랫폼 기능이 배수로 작용했다.
  • 에이전트를 위한 기반을 만들면, 그 위의 쓰임은 빠르게 늘어난다. Monzo에서는 게이트웨이와 격리된 실행 환경이 그 기반이었다.
  • 에이전트 자체도 다시 블록이 된다. 가치가 복리처럼 쌓이는 구조다.

15분 발표라 비용, 실패나 사고 사례, 보안 검토 과정은 자세히 다루지 않았다. 이 노트도 그 부분을 따로 채우지 않았다.

12

핵심 정리

  1. Monzo는 백엔드 서비스 3,000개 이상과 데이터 모델 약 13,000개를 가진 은행이다. 에이전트가 다룰 범위가 넓다.
  2. Agent Chip은 Slack 이모지 반응 하나로 시작해, 언제든 부를 수 있는 동료가 됐다.
  3. 발표자에 따르면 기술 조직 머지 PR의 10% 이상, 하루 1,800건 이상의 작업을 맡는다. 비개발 직군도 쓴다.
  4. 비결은 LLM, 곧 작은 배수 여러 개다. 이미 있던 플랫폼 기능이 서로 곱해졌다.
  5. 첫 블록은 MCP 게이트웨이다. 에이전트에 무엇을 보여 줄지와 권한을 한곳에서 정한다.
  6. 둘째 블록은 오케스트레이션 시스템이다. 운영 인프라와 분리된 샌드박스에서 에이전트를 돌린다.
  7. 상자 안의 상자: 이미지가 도구를 정하고, 프록시가 바깥 연결을 막는다. 가장 안쪽에서만 에이전트가 자유롭다.
  8. Agent Chip도 블록이 되어 장애 대응, 팀 간 질문, 데이터 품질 감시 같은 쓰임이 빠르게 붙었다.
  9. 비전문가는 스테이징에서 검증된 초안까지 만들고, 그다음에 엔지니어가 리뷰하고 배포한다. 엄격함은 그대로다.
  10. 모델은 갈아 끼울 수 있게 설계했다. 가치는 특정 모델이 아니라 플랫폼과 조합 가능성에서 나온다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1이 발표에서 LLMs는 무엇의 줄임말로 쓰였나?
Lots of Little Multipliers, 곧 작은 배수 여러 개. 이미 있던 플랫폼 기능들이 서로 곱해져 에이전트의 가치를 키웠다는 뜻이다.
Q2Agent Chip이 사내에 퍼진 계기가 된 사용법은?
아무 Slack 메시지에 전용 이모지로 반응하면, Agent Chip이 그 메시지를 프롬프트로 받아 일을 시작한다.
Q3발표자가 밝힌 Agent Chip의 현재 수치 두 가지와, 읽을 때 주의할 점은?
기술 조직 머지 PR의 10% 이상을 쓰고, 하루 1,800건 이상의 작업을 처리한다. Monzo가 자기 도구에 대해 밝힌 수치이고, 세는 방법과 기간은 나오지 않았다.
Q4"프롬프트 쓰고, 이모지 달고, 결과 받기"를 실제로 받친 것은?
이미 있던 플랫폼 기능이다. 알림, 모니터링, 외부 서비스 연동, 스테이징 환경, 큐 추상화, 쉬운 배포, 데이터베이스 추상화.
Q5MCP 게이트웨이가 맡는 두 가지 일과, 처음 지원한 대상은?
사내 서비스와 지식 소스 중 무엇을 에이전트에 보여 줄지 고르고, 에이전트마다 인증과 인가를 관리한다. 처음에는 로컬 코딩 에이전트를 위해 만들었다.
Q6에이전트 실행 환경을 운영 인프라와 떼어 놓은 이유는?
Monzo는 규제를 받는 은행이라 에이전트의 비결정성을 통제해야 한다. 동시에 에이전트가 마음껏 움직이며 개발할 공간도 필요했다.
Q7샌드박스 안에서 에이전트 이미지와 프록시는 각각 무엇을 통제하나?
에이전트 이미지는 쓸 수 있는 도구, 실행 환경, CLI, 인증과 인가를 정한다. 프록시는 밖으로 나가는 연결을 허용한 곳으로만 열어 준다.
Q8장애 대응 모드에서 Agent Chip에 요구하는 태도는?
신호가 높은 정보만 낸다. 말을 많이 하거나 가설을 늘어놓지 않는다. 얼마나 개입할지는 사람이 정한다.
Q9Agent Chip on Call과 선제형 감시는 어떻게 다른가?
on Call은 실패가 난 뒤 그것을 보고 조사를 자동으로 시작하는 반응형이다. 선제형은 백엔드 변경을 지켜보다가 다음 배치 실행 전에 데이터에 미칠 영향을 미리 짚는다.
Q10비전문가가 변경을 제안할 때 엔지니어는 언제 들어오나?
Agent Chip이 동작하는 초안을 만들고 스테이징에서 테스트한 다음에 들어온다. 리뷰와 배포는 여전히 엔지니어가 맡아서, 개발 기준은 낮아지지 않는다.
Q11시장이 빨리 변해도 Agent Chip이 가치 있다고 보는 세 가지 이유는?
조합할 수 있는 블록이 됐다. 특정 업체에 묶이지 않아 모델을 바꿔 끼울 수 있다. 다룰 수 있는 개발 범위가 계속 넓어진다.

용어뜻
코딩 에이전트Coding agent. 코드를 읽고 쓰고 실행하며 개발 작업을 스스로 하는 AI
하네스Harness. 모델을 감싸 도구, 권한, 실행 순서를 정해 주는 틀
로컬 / 원격 에이전트로컬 에이전트는 개발자 컴퓨터에서 돈다. 원격 에이전트(remote agent)는 서버에서 돌아서, 맡겨 두고 다른 일을 할 수 있다
MCPModel Context Protocol. AI 에이전트가 외부 도구와 데이터에 연결하는 표준 방식
게이트웨이Gateway. 여러 연결을 한곳으로 모아 드나드는 것을 통제하는 문
인증 / 인가Authentication / Authorization. 인증은 누구인지 확인하는 것, 인가는 무엇을 해도 되는지 허락하는 것
결정적 / 비결정적같은 입력에 늘 같은 결과가 나오면 결정적이다. 매번 달라질 수 있으면 비결정적(non-deterministic)이다
오케스트레이션Orchestration. 여러 작업을 띄우고, 실행을 관리하고, 결과를 모으는 일
샌드박스Sandbox. 바깥에 영향을 주지 않도록 격리한 실행 공간
네임스페이스Namespace. 클러스터 안에서 자원을 따로 묶어 다른 영역과 떼어 놓는 구역
파드Pod. 컨테이너를 실행하는 가장 작은 단위. 쿠버네티스에서 쓰는 말
에이전트 이미지샌드박스를 띄울 때 쓰는 실행 환경 묶음. 어떤 도구와 CLI가 들어 있는지 여기서 정해진다
프록시 / egress프록시는 안과 밖의 연결을 중간에서 대신 잇는 서버다. egress는 안에서 밖으로 나가는 연결이다
스테이징 환경Staging. 운영 환경과 비슷하게 꾸린 시험용 환경
데이터 웨어하우스 모델Data warehouse model. 분석용 데이터 저장소에서 데이터를 가공하는 단위
트레이스Trace. 요청 하나가 여러 서비스를 거쳐 간 경로를 기록한 것
트리아지Triage. 들어온 경보나 문제를 살펴 중요도와 처리 방향을 나누는 일
배치 실행Batch. 데이터를 모아 두었다가 정해진 때 한꺼번에 처리하는 방식
스쿼드Squad. Monzo에서 팀 단위를 부르는 말
human in the loop자동화 흐름 중간에 사람이 확인하고 결정하는 단계를 두는 것
업체 중립Provider agnostic. 특정 모델 업체에 묶이지 않고 바꿔 끼울 수 있는 설계
LGTMLooks Good To Me. 리뷰에서 "좋아 보인다"며 승인할 때 쓰는 줄임말
Linear이슈와 작업 티켓을 관리하는 도구
