에이전트 고고학을 그만하자

에이전트와 일하면 결정의 이유가 각자의 대화 기록에 갇히고, 일을 넘겨받은 사람은 커밋 몇 개로 과거를 파내야 한다. 발표자는 에이전트와의 대화, 코드 변경, 동료와의 문답을 한곳에 두자고 제안하며 자기 팀의 도구 Delta를 시연한다.

원본 영상: Stop Doing Agent Archaeology on Your Team's Code 발표: Richard Feldman (Delta)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 발표 첫 슬라이드의 제목은 "From sharing code to sharing agents"다. 발표 후반부 대부분은 발표자 회사 제품 Delta의 시연이다. 시연 화면은 자막에 없어서, 말로 설명된 부분만 옮겼다. 숫자는 모두 발표자가 말한 것이다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트와 일하던 동료가 일을 넘기면 받는 것은 이슈 설명, 커밋, 에이전트 대화 기록 정도다. 무엇을 시도했다 버렸는지, 왜 그렇게 정했는지는 빠진다.
  2. 빠진 이유를 커밋 메시지 한 줄로 추측하는 일을 발표자는 에이전트 고고학이라 부른다. 그 정보는 한때 분명히 있었으므로 이 추측은 시간 낭비다.
  3. 원인은 에이전트와의 대화, 코드 변경, 동료와의 문답이 서로 다른 곳에 흩어져 있다는 데 있다.
  4. 발표자의 제안은 이 셋을 한 스레드에 모으는 것이다. 그러면 동료와 나눈 짧은 문답도 에이전트가 읽는 맥락이 된다.
  5. Delta 시연에서는 에이전트 답변에 댓글 달기, 대화 중 동료 @멘션, 줄 단위 코드 리뷰, 동료 터미널 실시간 보기, 저장소 사본 자동 생성을 보여 줬다.
  6. 새로 불려 온 사람은 위의 대화를 다 읽지 않는다. 하위 스레드에서 에이전트에게 요약을 부탁한다.
  7. Delta는 발표자 회사 제품이고 지금은 비공개 베타다. 문제 제기는 어느 팀에나 해당하지만 해법은 한 제품의 시연이라는 점을 감안해 읽는다.
01

월요일 아침의 인수인계 00:20

월요일 아침에 동료에게서 메시지가 온다. 작업을 꽤 진행했는데 휴가를 떠나야 한다는 내용이다. 브랜치 이름과 에이전트 대화 기록을 gistGitHub Gist로 남겼다고 한다. 그리고 동료는 떠난다.

받은 사람이 할 수 있는 말은 "알겠어요" 정도다. 나머지는 직접 알아내야 한다.

이런 인수인계handoff는 휴가 때만 생기지 않는다. 시간대가 다른 동료에게 일을 넘길 때도 생긴다. 진행 중인 일에 동료를 끌어들일 때도 생긴다.

02

조각이 빠진 퍼즐 01:00

인수인계 때 손에 쥐는 것과 정말 필요한 것을 나눠 보면 이렇다.

받는 것
  • 이슈 설명: 무엇을 하려 했는지는 안다
  • 코드 스냅샷: 중간중간 남긴 커밋
  • 에이전트 대화 기록: 마크다운으로 붙여 넣은 정도
받고 싶은 것
  • 코드가 변해 온 과정: 어떤 방향을 시도했고 무엇이 안 됐는지
  • 생각의 흐름: 다른 방향을 왜 버렸는지, 결정의 이유

에이전트가 "안 되니 커밋하지 않겠다"고 넘어간 시도는 커밋에도 남지 않는다.

뒤의 두 가지는 gist와 대화 기록만으로는 흐릿하다. 발표자는 이 상태를 조각이 빠진 퍼즐에 비유했다. 빠진 조각은 내 에이전트와 함께 탐정 놀이를 하며 추측할 수는 있다. 하지만 전체 그림이 없으면 쉬운 질문에도 답하기 어렵다.

개구리가 붙잡은 것 02:10

퍼즐 속 개구리가 보라색 점박이 물체를 붙잡고 있다. 조각이 빠진 상태에서는 그게 암벽인지 무엇인지 알 수 없다. 전체 그림을 보면 버섯이라는 걸 바로 안다.

지금 팀이 일하는 방식 02:30

각자 자기 에이전트와 따로 대화한다. 발표자는 이를 사일로silo라고 부른다. 동료를 끌어들이는 순간 정보가 새는 전달lossy transmission이 시작된다. 작은 스냅샷만 보내고, 빠진 조각은 받은 사람이 맞추게 둔다.

03

에이전트 고고학 02:50

최악의 경우는 과거로 거슬러 올라가야 할 때다. 6개월 전에 만든 기능 위에 새 기능을 얹는다고 하자.

  1. 기능이 어떻게 만들어졌는지는 코드를 보면 안다.
  2. 기능을 왜 그렇게 만들었는지는 안 보인다.
  3. 알고 싶은 것은 "내가 지금 하려는 방법을 그때 검토했다가 좋은 이유로 버렸나"이다.
  4. 그 답은 나에게 전달되지 않은 대화 기록 어딘가에 묻혀 있다.
  5. 커밋 메시지에는 없거나, 지나가듯 쓴 한 줄뿐이다. 그 한 줄에서 의미를 짜내며 이유를 추측한다.

발표자는 이 일을 에이전트 고고학agent archaeology이라고 부른다. 커밋 같은 작은 단서로 과거에 무슨 일이 있었는지 파내는 일이다.

왜 낭비인가 03:30 정보는 한때 분명히 있었다. 누군가 에이전트와 대화할 때, 여러 사람이 Slack에서 이야기할 때, 회의할 때 오갔다. 그 맥락이 코드 옆에 남지 않았을 뿐이다. 실제로 일어난 일을 볼 수 있는데 추측에 시간을 쓰는 것은 낭비다.
04

따로 노는 장비와 스마트폰 03:50

발표자는 스마트폰 초기에 돌던 밈을 꺼냈다. 예전에는 큰 캠코더, 유선 전화, 붐박스, CD 더미, 데스크톱 본체가 각각 따로 있었다. 각각으로도 버틸 수는 있다. 하지만 모든 기능이 한 기기 안에서 맞물려 돌아가는 경험과는 다르다. 휴대폰을 꺼내 영상을 찍고 나중에 다시 보는 데는 마찰이 거의 없다.

지금도구가 따로 논다이슈, 커밋, 각자의 에이전트 대화, Slack, 회의를 사람이 이어 붙인다

05

대화 안에서 동료에게 묻기 04:40

발표자는 이 발표의 주제를 사람-에이전트-사람 협업human-agent-human collaboration이라고 부른다. 사람끼리 협업하는데 그 사이에 에이전트가 끼어 있는 상황이다.

발표 준비 중에 실제로 있었던 일 04:50

  1. 동료가 Delta에서 발표자를 @멘션했다. "에이전트가 이걸 당신에게 확인해 보라고 하네요. 대화 중간에 되돌리는 기능conversation undo 아직 작업 중인가요?"
  2. 발표자는 오래전에 시작했지만 지금은 낡은 상태라고 답했다. 원하면 가져가라고 했다.
  3. 동료는 지금 일과는 곁가지지만 기억해 두겠다고 했다.

이 문답 자체는 Slack에서도, 말로도 할 수 있다. 차이는 위치다. 이 문답은 동료가 에이전트와 나누던 대화 한가운데에서 일어났다. 그래서 에이전트도 이 문답을 보고, 전체 흐름의 일부로 안다. 나중에 흩어진 조각을 따로 이어 붙일 필요가 없다.

대화와 코드 변경은 붙어 있다 06:20

같은 스레드 안에서 에이전트가 만든 코드 변경도 보인다. 그 동료의 diff는 약 2,000줄이었다고 한다. 발표자는 그 변경을 볼 수 있다. 원하면 자기 에이전트로 그 작업에 실시간으로 함께 참여할 수도 있다.

발표자는 5년 전만 해도 손으로 코드를 치는 데 시간이 훨씬 많이 들었다고 말한다. 지금은 에이전트와의 대화와 코드 변경을 떼어 놓을 수 없다. 둘 다 소프트웨어를 만드는 주된 방식이다. 그런데도 둘을 따로 보관하면 문제가 생기고 에이전트도 덜 유용해진다.

왜 둘을 따로 두나? 그냥 한곳에 두면 되지 않나?발표자의 질문을 옮김 07:00
06

Delta 시연: 답변에 댓글 달기 07:10

Delta는 에이전트를 쓰면서 동료와 협업하기 위한 도구다. 시연은 macOS 네이티브 앱으로 했다. Linux, Windows, 모바일 앱도 있다고 했다.

이 발표의 해법은 모두 발표자 회사 제품인 Delta다. 앞의 문제 제기는 어느 팀에나 해당하는 이야기다. 하지만 "한곳에 모으면 풀린다"는 주장과 시연 속 장점은 그 점을 감안해 읽자.

시연 작업: 시험 알림 버튼 07:20

운영체제는 앱마다 알림을 허용하거나 막을 수 있다. 그래서 버튼 하나로 시험 알림을 보내, Delta 알림이 실제로 오는지 확인하는 기능을 만들고 있었다.

답변의 아무 부분에나 댓글 07:50

  1. 에이전트가 "Delta는 첫 실제 알림이 뜰 때까지 알림 허용을 묻지 않는다"고 답했다.
  2. 발표자는 그 문장만 골라 강조하고 "피할 수 있나?"라고 댓글을 달았다.
  3. 엔터를 누르면 모델이 그 질문을 이어서 처리한다.

모델과 하네스는 골라 쓴다 08:00

시연에서는 Opus 5.5를 썼다. 발표자는 Delta가 특정 모델이나 하네스harness에 묶이지 않는다고 했다. 하네스는 모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀이다.

  • ChatGPT 구독으로 쓸 수 있다.
  • Claude Code 플러그인을 준비 중이다.
  • ACPAgent Client Protocol를 통해 Claude Code 구독으로 쓰는 기능을 내놓을 예정이다. ACP는 에디터와 코딩 에이전트를 잇는 규약이다.

발표자의 말로는 핵심이 협업이므로, 쓰던 하네스와 API 키를 그대로 가져오면 된다.

07

Delta 시연: 동료 부르기 08:20

에이전트 답을 읽다가 정할 것이 생겼다. 오류를 토스트toast로 띄울지, 화면 안 인라인 오류inline error로 보여 줄지다. 토스트는 잠깐 떴다 사라지는 알림이다. 인라인 오류는 문제가 생긴 자리 옆에 붙는 메시지다.

  1. 발표자는 그 자리에서 동료 Bennett(철자 추정)을 @멘션해 의견을 물었다.
  2. Bennett의 앱에 알림이 갔다. 09:00
  3. Bennett은 스레드에 들어와 "인라인이 더 좋아요"라고 답했다.
  4. 발표자는 그대로 하기로 했다.

결정의 무게까지 남는다 09:20

이 짧은 문답도 대화의 일부로 남는다. 발표자의 에이전트는 작업을 이어 갈 때 이 결정을 안다. 나중에 이 스레드에 접근할 수 있는 다른 사람의 에이전트도 안다.

내용뿐 아니라 무게도 전달된다 에이전트는 이 결정이 깊은 시장 조사 끝에 나온 것인지, "어때요?" "좋아요"로 끝난 것인지 구별할 수 있다. 3장의 6개월 뒤 질문, "그때 이걸 검토하고 일부러 버렸나?"에 답할 재료가 바로 이것이다.
08

코드 리뷰도 같은 자리에서 09:50

에이전트가 만든 코드 변경도 같은 스레드에서 본다. 발표자 팀은 Delta 전에 Zed 에디터를 만들었다. 그래서 코드 변경을 보여 주는 화면은 잘 만든다고 자신했다.

할 수 있는 것시연 내용
줄 단위 댓글한 줄에 "Linux에서도 동작할까?"라고 달면 에이전트에게 전달된다. 에이전트는 어느 줄을 묻는지 안다 10:10
검토 완료 표시다 본 부분을 "검토 끝"으로 표시한다
공식 리뷰 요청동료를 리뷰어로 초대하면 승인이나 거절을 누를 수 있다 10:20
직접 수정동료가 들어와 코드를 직접 고칠 수도 있다

혼자 쓸 때 10:40

발표자는 혼자 일할 때도 Delta가 쓸 만한 화면이라고 했다. 스레드 목록이 있고, 스레드 안에 하위 스레드sub thread를 만들어 일을 나눈다. 발표자가 밝힌 목표는 어떤 작업 방식이든 마찰을 줄이는 것이다.

09

실시간 동기화 11:00

발표자가 말로 Bennett에게 스레드 초대를 부탁하자 곧바로 알림이 왔다. 키보드에 손을 대지 않았는데 된 이유는 Bennett이 객석에 앉아 있었기 때문이다. 발표자도 "약간 반칙"이라며 웃었다.

기능내용
동료 터미널 보기 11:20Bennett의 스레드에서 돌던 터미널 출력이 발표자 화면에 실시간으로 그대로 보인다. 입력은 할 수 없다. 입력을 허용하면 남의 컴퓨터에서 코드를 돌릴 수 있게 되는 원격 코드 실행remote code execution 위험이 생기기 때문이다.
내 터미널 열기 12:00느낌표(!)를 누르면 발표자 자신의 터미널이 열린다. cargo run을 실행하자 Bennett도 빌드 과정을 실시간으로 봤다. 터미널마다 누구 컴퓨터에서 도는지가 이름(발표자는 rtfeldman)으로 표시된다.
저장소 사본 12:20스레드에 들어가자마자 발표자의 로컬 디스크에 Bennett의 저장소 전체 사본이 생겼다. Git 워크트리worktree가 아니라 Delta가 따로 만든 워크트리라고 했다. 더 효율적으로 만들어 스레드 사이를 쉽게 오간다는 설명이다.
각자의 에이전트 12:40발표자와 Bennett은 각자 원하는 에이전트를 쓰면서 같은 스레드에서 이야기한다.

발표자는 이 실시간 동기화를 "이 정도로 진지하게 한다"는 증거로 보여 줬다. 목표는 다른 사람이 하는 일에 마찰 없이 바로 뛰어드는 것이다.

질의응답 14:40

질문발표자의 답
동시에 몇 명까지 쓸 수 있나? 14:40큰 부하 테스트는 아직 하지 않았다. 사내 스탠드업을 스레드 하나에서 30~40명이 함께 하는데 문제가 없었다. 회사 전체가 써도 괜찮을 것이고, 한계는 스레드 하나에 몇 명이 있느냐의 문제라고 했다.
클라우드인가 로컬인가? 15:10시연한 것은 클라우드에 배포된 버전이다. 에이전트는 로컬 컴퓨터나 클라우드 러너 중 골라 실행한다. 동기화 인프라는 지금 Delta의 클라우드에서 돈다. 첫 온프레미스on-premises 시범 운영이 진행 중이다. 모든 것을 자기 하드웨어에서 돌려야 하는 규제 산업을 염두에 둔 것이다.
토큰 비용이 더 드나? 16:00비공개 베타private beta라 지금은 무료다. 가격은 아직 정하지 않았고, 정해지면 delta.dev에 올린다.
SRE 봇, 세션 포크, CI까지 이어지는 수명 주기는? 16:20 발표자 팀은 PR을 더 이상 쓰지 않고 모든 일을 Delta에서 한다. 일이 끝나면 에이전트에게 CI를 돌리라고 하고, 통과하면 반영land하라고 한다. 반영 전용 흐름이 있다 16:50. SOC 2 때문에 "누가 검토하고 승인했다"는 기록이 필요한 팀을 위한 공식 승인 흐름도 있다 17:20. 봇용 API는 공식적으로 아직 없다. @멘션 구조는 봇에도 확장할 수 있으니 관심 있으면 이야기하자고 했다 17:40.
불려 들어온 사람은 위를 다 읽어야 하나? 18:00에이전트에게 요약을 부탁한다. 발표자는 필라델피아에서 기차를 타고 오는 길에 실제로 이렇게 했다. 동료가 발표자를 대화에 불렀고, 발표자는 하위 스레드에서 "이 스레드 처음인데 접근 방식 개요를 알려 줄래?"라고 물었다. 이어서 추가 질문도 했다. 동료는 원래 스레드에서 방해받지 않고 일을 계속했다.

세 번째 질문은 추가 토큰 비용을 물었지만, 답은 Delta 이용료 이야기였다. 모델 사용료는 6장에서 말한 대로 각자의 구독이나 API 키로 내는 구조로 보인다(추론). 네 번째 질문 중 "세션을 특정 시점에서 갈라 이어 가기(포크)"에는 자막상 따로 답하지 않았다.

"PR을 쓰지 않는다"는 말은 Delta를 만드는 팀이 자기 제품으로 일하는 방식이다. 다른 팀에도 그대로 맞는다는 근거로 보지는 말자.

핵심 정리

  1. 인수인계 때 받는 것은 이슈 설명, 커밋, 에이전트 대화 기록이다. 빠지는 것은 코드가 변해 온 과정과 결정의 이유다.
  2. 에이전트가 안 된다며 커밋하지 않은 시도는 기록에서 사라진다.
  3. 에이전트 고고학은 커밋 같은 작은 단서로 과거 결정의 이유를 파내는 일이다. 정보는 한때 있었으니 낭비다.
  4. 원인은 사일로다. 각자 자기 에이전트와 따로 대화하고, 동료에게는 스냅샷만 보낸다.
  5. 에이전트와의 대화와 코드 변경은 이제 떼어 놓을 수 없다. 그러니 한곳에 둬야 한다는 것이 발표자의 주장이다.
  6. 작업 스레드 안에서 동료에게 물으면 그 문답이 에이전트의 맥락이 된다.
  7. 에이전트는 결정의 내용뿐 아니라 무게도 알게 된다. 깊이 조사한 결정인지, 가볍게 정한 결정인지다.
  8. 코드 한 줄에 단 댓글은 에이전트에게 전달되고, 에이전트는 어느 줄을 묻는지 안다.
  9. 남의 터미널은 보기만 한다. 입력까지 열면 원격 코드 실행 위험이 생긴다.
  10. 새로 합류한 사람은 하위 스레드에서 에이전트에게 요약을 받는다. 원래 대화는 방해받지 않는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1휴가 가는 동료에게 받는 세 가지와, 빠지는 두 가지는?
받는 것: 이슈 설명, 코드 스냅샷(커밋), 에이전트 대화 기록. 빠지는 것: 코드가 변해 온 과정(시도했다 버린 방향), 생각의 흐름(결정의 이유).
Q2에이전트가 시도한 방향이 커밋에도 안 남는 경우는?
에이전트가 "안 되니 커밋하지 않겠다"고 넘어간 경우. 그 시도는 기록 어디에도 남지 않는다.
Q3"에이전트 고고학"이란 무엇인가?
커밋 스냅샷이나 커밋 메시지의 한 줄 같은 작은 단서로, 과거에 왜 그런 결정을 했는지 파내는 일.
Q4발표자가 에이전트 고고학을 시간 낭비라고 하는 이유는?
정보는 한때 분명히 있었다. 에이전트와의 대화, Slack, 회의에서 오갔지만 코드 옆에 남지 않았을 뿐이다. 실제로 일어난 일을 볼 수 있는데 추측하는 것은 낭비다.
Q5스마트폰 비유가 말하려는 것은?
따로 노는 장비로도 버틸 수는 있지만, 한 기기 안에서 맞물려 돌아가는 경험과는 마찰의 정도가 다르다. 협업 도구도 대화, 코드, 동료가 한곳에 있어야 한다는 뜻이다.
Q6conversation undo 문답이 Slack에서 했을 때와 다른 점은?
문답이 동료가 에이전트와 나누던 대화 한가운데에서 일어났다. 그래서 에이전트도 그 문답을 전체 흐름의 일부로 안다. 나중에 따로 이어 붙일 필요가 없다.
Q7토스트냐 인라인이냐를 Bennett에게 물은 사례에서, 나중의 에이전트가 얻는 정보 두 가지는?
결정의 내용(인라인 오류로 한다)과 결정의 무게(깊은 조사가 아니라 짧은 문답으로 정했다).
Q8Bennett의 터미널은 보이는데 입력은 못 하는 이유는?
입력을 허용하면 남의 컴퓨터에서 코드를 실행할 수 있게 된다. 원격 코드 실행이라는 보안 위험이다.
Q9스레드에 합류하면 발표자의 컴퓨터에 무엇이 생기나?
동료 저장소 전체의 로컬 사본. Git 워크트리가 아니라 Delta가 따로 만든 워크트리다.
Q10스레드 하나에서 몇 명까지 써 봤다고 했나?
사내 스탠드업을 스레드 하나에서 30~40명이 함께 하는데 문제가 없었다고 했다. 큰 부하 테스트는 아직 하지 않았다.
Q11발표자 팀은 PR 대신 어떻게 코드를 반영하나?
에이전트에게 CI를 돌리게 하고, 통과하면 반영하라고 한다. SOC 2를 위한 공식 승인 흐름도 따로 있다.
Q12대화에 새로 불려 온 사람은 어떻게 따라잡나?
하위 스레드를 열어 에이전트에게 접근 방식의 개요를 부탁하고 추가 질문을 한다. 원래 스레드의 동료는 방해받지 않는다.
