에이전트를 다시 만들 때마다 남은 것

Arize AI는 제품 안의 에이전트 Alex를 2년 동안 여러 번 다시 만들었다. 모델이 알아서 좋아지는 동안 팀이 다시 짠 것은 모두 하네스 코드였고, 끝까지 남은 선택은 대부분 단순한 쪽이었다.

원본 영상: We Kept Rebuilding Our AI Agent. Here's What Survived 발표: Fuad Ali (Arize AI 프로덕트 담당, AI PM)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 고쳤다(Our Eyes → Arize, Aux → Arize AX). 확실하지 않은 이름에는 (추정)을 붙였다. 슬라이드에만 있고 말로 하지 않은 내용은 자막에 없어서 담지 못했다. mm:ss는 영상 위치다.

3분 요약
  1. Arize는 2년 동안 Alex를 여러 번 다시 만들었다. 다시 만든 것은 모델이 아니라 하네스 코드였다.
  2. 계획은 하네스가 들고 있는다. 모델에게 할 일 목록을 맡기니 목록을 고치는 데 호출을 낭비했다.
  3. 턴 종료는 하네스가 거는 관문이다. 명시적 종료 호출, 남은 항목이 있으면 최대 3번 되돌리기, 강제 종료로 막는다.
  4. 큰 도구 결과는 파일처럼 다룬다. 컨텍스트에 붓지 않고 위치만 남긴 뒤, 필요하면 에이전트가 코드로 찾아 읽는다.
  5. 장기 기억은 사용자당 마크다운 파일 하나(최대 8,000자)가 벡터 검색과 지식 그래프를 이겼다.
  6. 화면별 전문 에이전트 10개를 스킬을 불러 쓰는 에이전트 하나로 합쳤다. 기본 모델은 최신보다 빠르고 충분히 좋은 것을 쓴다.
  7. 운영 세션이 곧 테스트다. 에이전트 버그는 에러로 드러나지 않으니 추적으로 찾는다. 판단 기준과 속도·품질 선택은 사람이 맡는다.

에이전트가 겹겹이 00:50

발표자는 시작부터 "이 발표는 에이전트가 겹겹이 나온다"고 미리 알린다. 발표 슬라이드도 에이전트가 만들었다. 등장하는 에이전트는 셋이다.

  • 사용자의 트레이스를 읽는다.
  • 찾은 문제를 테스트로 바꾼다. 즉 평가eval를 대신 만들어 준다.

03

다시 만든 것은 하네스 05:40

팀은 모델을 직접 학습시키지 않았다. 모델은 모델 회사의 일정대로 좋아졌다. 팀이 다시 만든 것은 모두 하네스harness였다. 하네스는 모델을 감싸고 도구, 순서, 규칙, 기억을 정해 주는 코드다.

다시 만든 것은 전부 하네스 코드였다.Fuad Ali, 05:40 발언을 옮김

에이전트 프레임워크도 쓰지 않는다. 아래 네 가지를 모두 직접 짰다.

  • 루프: 모델을 부르고, 도구를 실행하고, 다시 모델을 부르는 반복
  • 계획: 무엇을 어떤 순서로 할지 (04)
  • 종료 규칙: 언제 답을 마칠지 (05)
  • 메모리: 무엇을 컨텍스트에 두고 무엇을 기억할지 (06, 07)

직접 짜면 통제할 수 있는 범위가 넓다. 만들면서 배우는 것도 많다. 발표자는 이 점에서 엔지니어링에 아직 풀 문제가 많다고 본다. 최신 모델을 그냥 돌린다고 모든 일이 되지는 않는다.

04

계획은 누가 들고 있나 06:10

발표자는 아이에게 집안일을 시키는 비유를 든다. 방법은 두 가지다.

방법 1 · 목록을 건넨다

집안일 목록을 통째로 주고, 하나 끝낼 때마다 지우라고 한다.

에이전트로 치면 모델에게 할 일 도구를 주는 것이다.

방법 2 · 목록을 내가 쥔다

목록은 부모가 들고 있다. 수시로 확인하면서 다음 일 하나만 알려 준다.

에이전트로 치면 하네스가 계획을 들고 있는 것이다.

두 방법 모두 장단점이 있다. Arize는 방법 1에서 시작해 방법 2로 옮겨 갔다.

할 일 도구를 줬더니 07:00

  • 모델이 대부분의 시간을 목록 체크에 썼다. 쓸모 있는 일 없이 목록만 고치는 LLM 호출이 많았다.
  • 도구를 여러 번 부르고 나면 집중을 잃었다.
  • 발표자는 할 일 도구에만 20번이 넘는 반복이 들어갔다고 말했다.

계획을 한 조각씩 하네스로 07:20

  1. "진행 중" 상태를 넣었다. 모델이 어디까지 했는지 잃지 않게 하려는 것이었다.
  2. 계획을 메시지로 넣었다. 하네스가 모델을 부를 때마다 계획을 그려 넣는다. 규칙이 데이터 바로 옆에 있으니 모델이 지금 위치를 읽기 쉽다.
  3. "진행 중" 표시를 다시 뺐다. 끝나지 않은 항목 중 순서상 첫 번째가 곧 다음 할 일이다. 표시를 바꾸는 호출이 따로 필요 없었다.
  4. 할 일 도구를 아예 없애 보는 중이다. 계획은 메시지 안에만 둔다.
처음모델이 목록을 들고 체크한다목록 관리에 호출이 새고, 집중을 잃는다

교훈 모델은 목록을 받으면 지나치게 열심히 관리하려 든다. 목록 관리는 하네스에 맡기고, 모델에게는 일을 시킨다.
05

턴은 언제 끝나나 08:30

턴turn은 사용자 요청 하나에 에이전트가 모델과 도구를 오가다 답을 마치는 한 단위다. 지금 Alex에서는 턴을 끝낼지 말지를 하네스가 관문처럼 정한다.

첫 규칙: 도구 호출이 없으면 끝

처음에는 모델이 도구 호출 없이 글만 내면 끝난 것으로 봤다. 이 규칙은 일부 모델에서 깨졌다. 그 모델들은 한 턴에서 "다음으로 이걸 하겠다"고 말만 하고, 실제 호출은 다음 턴에 했다. 하네스는 말만 한 그 순간을 종료로 읽었다.

모든 모델에 대비해야 하는 이유 08:50

Arize AX에서는 사용자가 모델 공급자를 직접 고른다. 팀이 모든 모델을 미리 시험해 볼 수는 없다. 회귀 테스트를 돌리고 여러 모델을 벤치마크하며, 기본 모델에 대한 의견도 있다. 그래도 Anthropic만 쓰는 고객, OpenAI만 쓰는 고객이 있다. 그래서 쓸 수 있는 모든 모델을 전제로 설계해야 했다.

06

책상 위의 책 09:40

발표자는 메모리 문제를 책상 비유로 설명한다. 책상은 컨텍스트 창context window이다. 모델이 한 번에 읽을 수 있는 입력의 범위다.

  • 두꺼운 책 한 권이 책상에 떨어진다. 너무 두꺼우면 읽느라 다른 일을 못 한다. 도구 결과 하나가 너무 큰 경우다.
  • 책이 여러 권 쌓인다. 결국 책상에 자리가 없다. 결과가 쌓여 컨텍스트가 꽉 차는 경우다.

해법은 책을 책장에 꽂고 책상에는 쪽지만 두는 것이다. 쪽지에는 책이 어디 있는지, 대략 무슨 내용인지 적는다. 필요하면 쪽지를 보고 책장에서 꺼내 온다.

문제Alex의 해법
큰 도구 결과 10:30결과는 따로 저장하고, 위치와 요약만 컨텍스트에 남긴다
큰 JSON 트레이스 11:00JSON 안쪽을 잘라서 넣는다. 전체가 필요하면 에이전트가 jq 코드를 짜서 찾는다
길어진 진행 기록 11:40하네스가 모델에게 체크포인트checkpoint를 쓰게 하고, 체크포인트가 대신한 부분은 버린다. 기록에는 고정 토큰 예산을 둔다
세션을 넘는 기억 11:50백그라운드 작업이 사용자마다 작은 파일 하나를 고친다 (07)

Alex는 다른 에이전트의 트레이스를 분석한다. 이런 트레이스에는 내용이 엄청나게 많을 수 있다. 큰 JSON 덩어리 하나가 컨텍스트 창을 다 채우면 쓸모 있는 일을 거의 못 한다.

에이전트는 코드를 쓰고, 코드 같은 도구로 정보를 찾는 일을 아주 잘한다. jq를 쓰게 한 것은 그 강점을 이용한 것이다.

교훈 12:10 큰 결과는 파일처럼 다룬다. 컨텍스트에 통째로 붓지 말고, 필요한 부분만 찾아 읽게 한다. 복잡한 장치는 필요 없다.

시도한 것복잡한 기억 장치벡터 검색, 에피소드 기억 저장소와 의미 기억 저장소, 시간 정보를 담은 지식 그래프

남은 것 12:30사용자마다 마크다운 파일 하나최대 8,000자

어떻게 돌아가나

  • 세션이 끝나면 백그라운드 작업이 이 파일을 고쳐 쓴다.
  • 파일을 쓰는 곳은 이 작업 하나뿐이다.

작은 파일이 이긴 이유 12:50

  • 작고 정확하다. 불러오기 쉽다.
  • 컨텍스트를 넘치게 하지 않는다.
  • 사람이 읽고 점검하기 쉽다. 라벨러가 파일을 보고 맞는 내용이 저장됐는지 판단한다. 필요하면 백그라운드 작업의 지시문을 고친다.
  • 쓰는 지점이 하나라 안전하게 만들기 쉽다. 다른 사용자의 기억이 섞여 들어가지 않게 막을 곳이 한 군데다.
과설계를 조심하라 발표자는 엔지니어가 만드는 일을 좋아해서 스스로 일을 키우곤 한다고 말한다. 이 사례를 "문제를 과하게 설계하지 말라"는 교훈으로 꼽는다.
08

전문 에이전트 10개에서 하나로 13:30

2025년에는 트레이스 분석만 하는 에이전트 하나로 시작했다. 그 뒤 화면마다 전문 에이전트를 두어 10개가 됐다. 예를 들어 데이터셋 화면에는 합성 데이터를 만들고 데이터셋을 살펴보는 전용 서브에이전트sub-agent가 있었다.

팀은 이 구조를 되돌렸다. 지금은 에이전트 하나가 필요할 때 스킬skill 지시문과 도구를 불러온다. 어떤 도구를 쓸지는 에이전트가 정한다.

발표자는 이 변화의 이유를 둘로 설명한다. 하나는 모델이 좋아진 것이고, 다른 하나는 구조를 단순하게 만든 것이다.

09

최신 모델이 늘 답은 아니다 14:10

팀은 최신 모델을 자동으로 기본값으로 올리지 않는다. 물론 기본 모델을 올리는 때도 있다.

"가장 좋은 모델"은 주관적인 질문이다. 범용 기준에서 가장 앞선 모델과, 내가 만드는 제품에 가장 맞는 모델은 다를 수 있다.

기본 원칙 빠르고 충분히 좋은 모델을 기본값으로 쓴다. 남는 시간은 하네스에 쓴다.

지금 살펴보는 방향 14:40

  • 자동 라우팅auto routing: 작업마다 다른 모델을 고른다.
  • 직접 만든 작은 모델: 좁은 기능에 맞춰 사후 학습post-training한 소형 언어 모델SLM을 쓴다.
  • 루프 없는 단일 호출: 어떤 기능은 에이전트 루프가 아예 필요 없다. 모델을 한 번만 부르면 된다.

예로 "AI로 필터 만들기" 기능을 든다 15:00. 예전에 SQL을 생성하던 시절과 비교하면, 이제는 아주 작은 모델로도 필터를 쉽게 만든다. 이런 곳에 루프 전체를 쓰면 또 과설계가 된다.

10

운영 세션이 테스트가 된다 15:20

팀은 모든 것을 추적한다. 사용자가 Alex에게 질문할 때마다 생기는 트레이스가 Arize 안의 한 프로젝트로 들어온다. 이 프로젝트 이름은 아직도 "Copilot prod"다.

  • 사용자 질문을 골라 회귀 데이터셋regression dataset에 넣기 쉽다. 회귀 데이터셋은 무언가를 바꾼 뒤에도 예전에 잘 되던 것이 그대로인지 확인하는 사례 묶음이다.
  • 운영 세션이 테스트 사례가 된다. 새 오류가 보일 때마다 늘고 바뀌는 "살아 있는 테스트 자료"다.
  • 세션 전체를 데이터셋으로 저장하고, 특정 턴만 다시 돌려 볼 수 있다 16:10.
  • 하네스를 바꿀 때마다 Arize의 실험 기능으로 A/B 테스트를 한다 16:20.

추적, 데이터셋, 실험은 모두 발표자 회사가 파는 기능이다. 방법 자체는 다른 도구로도 할 수 있다. "쉽다"는 주장은 그 점을 감안해 읽자.

에러 없이 생기는 버그 16:30

에이전트의 버그는 명시적인 에러로 잘 드러나지 않는다. 예전 소프트웨어와 다른 점이다. 이제는 질적인 판단이 필요하다.

상태는 "정상"인데 한 턴 안에 똑같은 도구 호출이 43번 있었다면, 고쳐야 할 문제일 가능성이 높다.

지연 시간latency도 마찬가지다 17:00. 응답에 227초가 걸리면 누구나 너무 길다고 본다. 하지만 어디서부터 너무 긴지는 쓰임새마다 다르다.

팀은 이런 이상 신호를 찾는 일을 Signal로 자동화하고 있다 17:10. Alex가 같은 시도를 되풀이하는 루프도 Signal이 찾아냈다. 사람이 트레이스를 직접 읽는 일은 점점 줄고 있다.

11

사람이 맡는 일 17:30

자동화가 늘어도 사람이 맡는 일이 남는다. 발표자는 두 가지를 꼽는다.

심사 모델의 기준은 사람이 만든다

심사 모델LLM judge은 에이전트의 결과를 채점하는 모델이다. 이 모델의 점수가 팀 엔지니어의 판단과 맞도록 맞춰야 한다. 그 기준이 되는 정답 라벨, 즉 골든 데이터셋golden dataset은 사람이 만든다.

발표자는 회귀 데이터셋도 꼭 챙기라고 강조한다.

속도와 품질의 교환은 사람이 정한다 17:50

언제 조금 빠르게 가면서 품질을 조금 낮춰도 되는지에는 하나의 정답이 없다. "모델을 바꾸면 지연 시간이 X만큼 늘고 품질이 Y만큼 오른다"는 지표가 있어도 결정은 사람이 한다.

발표자는 "모든 곳에 Astra(추정)를 쓰면 맞는 결정인가"라고 되묻는다. 지표는 판단을 돕지만 판단을 대신하지 않는다.

핵심 정리

  1. Arize는 2년 동안 Alex를 여러 번 다시 만들었다. 다시 만든 것은 모델이 아니라 하네스 코드였다.
  2. 에이전트 프레임워크 없이 루프, 계획, 종료 규칙, 메모리를 직접 짰다.
  3. 모델에게 할 일 목록을 맡기면 목록 관리에 호출을 낭비한다. 계획은 하네스가 들고 매 호출에 메시지로 넣는다.
  4. "도구 호출 없음 = 끝" 규칙은 모델에 따라 깨진다. 명시적 종료 호출, 최대 3번 되돌리기, 한도 직전 경고, 강제 종료로 막는다.
  5. 큰 도구 결과는 파일처럼 저장하고 위치만 남긴다. 필요하면 에이전트가 jq 같은 코드로 찾는다.
  6. 장기 기억은 사용자당 마크다운 파일 하나(8,000자)가 벡터 검색과 지식 그래프를 이겼다. 작고, 사람이 점검할 수 있고, 쓰는 곳이 하나다.
  7. 화면별 전문 에이전트 10개를 스킬을 불러 쓰는 에이전트 하나로 합쳤다.
  8. 기본 모델은 최신이 아니라 빠르고 충분히 좋은 것이다. 어떤 기능은 루프 없이 작은 모델 한 번 호출로 된다.
  9. 운영 세션이 회귀 테스트가 된다. 에이전트 버그는 에러가 아니라 같은 호출 43번, 응답 227초 같은 이상 신호로 나타난다.
  10. 심사 모델의 기준 라벨과 속도·품질의 선택은 사람이 맡는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Arize가 2년 동안 다시 만든 것은 무엇이고, 하지 않은 것은 무엇인가?
다시 만든 것은 하네스 코드다. 모델을 직접 학습시키지 않았고, 에이전트 프레임워크도 쓰지 않았다.
Q2모델에게 할 일 도구를 줬을 때 생긴 문제 두 가지는?
목록을 체크하는 데만 LLM 호출을 많이 썼다. 도구를 여러 번 부르고 나면 집중을 잃었다.
Q3"진행 중" 표시를 넣었다가 다시 뺀 이유는?
끝나지 않은 항목 중 순서상 첫 번째가 곧 다음 할 일이다. 표시를 바꾸는 호출은 쓸모가 없었다.
Q4"도구 호출이 없으면 끝" 규칙은 왜 깨졌나?
일부 모델은 한 턴에서 다음 단계를 말로만 알리고, 실제 호출은 다음 턴에 했다. 하네스가 그 말만 한 순간을 종료로 읽었다.
Q5Arize가 특정 모델이 아니라 모든 모델에 대비해 설계해야 했던 이유는?
Arize AX에서는 사용자가 모델 공급자를 직접 고른다. Anthropic만 쓰는 고객, OpenAI만 쓰는 고객이 있어서 팀이 모든 모델을 미리 시험할 수 없다.
Q6지금 Alex의 종료 장치 세 가지는?
명시적 종료 호출(계획에 열린 항목이 있으면 최대 3번 돌려보냄), 반복 한도 한 단계 전 경고, 강제 종료.
Q7큰 JSON 트레이스가 도구 결과로 오면 Alex는 어떻게 하나?
JSON 안쪽을 잘라서 넣고 위치만 남긴다. 전체가 필요하면 에이전트가 jq 코드를 짜서 찾는다.
Q8Alex의 장기 기억은 어떤 형태이고, 언제 쓰이고 읽히나?
사용자마다 마크다운 파일 하나, 최대 8,000자. 요청마다 통째로 불러오고, 세션이 끝난 뒤 백그라운드 작업 하나가 고쳐 쓴다.
Q9작은 파일 하나가 복잡한 기억 장치보다 나았던 이유 세 가지는?
작고 정확해서 컨텍스트를 넘치게 하지 않는다. 사람이 읽고 점검하기 쉽다. 쓰는 지점이 하나라 다른 사용자의 기억이 섞이지 않게 막기 쉽다.
Q10기본 모델을 고르는 Arize의 원칙은?
최신 모델이 늘 최선은 아니다. 빠르고 충분히 좋은 모델을 기본값으로 쓰고, 남는 시간은 하네스에 쓴다. 어떤 기능은 루프 없이 작은 모델 한 번 호출로 충분하다.
Q11에이전트 버그가 에러로 드러나지 않는다는 예 두 가지와, 자동화해도 사람이 맡는 일 두 가지는?
예: 상태는 정상인데 한 턴에 같은 도구 호출 43번, 응답에 227초. 사람이 맡는 일: 심사 모델의 기준 라벨(골든 데이터셋) 만들기, 속도와 품질 사이의 선택.
