에이전트 권한은 작업 하나만큼만

쓸모 있는 에이전트는 개인 데이터, 신뢰할 수 없는 입력, 외부 통신을 모두 갖는다. 발표자는 이 셋을 빼지 말고 권한을 좁히자고 말한다. 방법은 도구를 부를 때마다 그 작업 하나에만 쓰는 몇 분짜리 토큰을 발급하는 것이다.

원본 영상: Your Agent Is a Lethal Trifecta (And What to Do About It) 발표: Kim Maida (Keycard 창업 멤버 GTM 엔지니어, 개발자 관계 총괄)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름(OAuth, Okta, Auth0, Claude Code, Simon Willison)은 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 데모의 당직 에이전트는 정적 API 키로 고객 개인정보를 보고서에 붙이고, 운영 DB를 지우고, 서버를 재시작하고, 파드를 4개에서 40개로 늘렸다.
  2. 쓸모 있는 에이전트는 개인 데이터 접근, 신뢰할 수 없는 콘텐츠, 외부 통신을 모두 갖는다. Simon Willison은 이 조합을 치명적 삼중 조합이라고 불렀다.
  3. 사고의 원인은 사람이 필요보다 많은 권한을 준 것이다. 사람 승인을 끼워 넣으면 승인에 지친 사용자에게 책임만 넘어간다.
  4. 셋 중 하나를 빼면 에이전트가 쓸모없어진다. 기능은 두고 접근을 통제한다.
  5. OAuth, MCP 게이트웨이, 샌드박스는 합쳐도 작업 하나에 맞춘 실행 시점 자격 증명을 주지 못한다.
  6. 토큰 교환을 쓰면 도구 호출마다 STS가 사용자, 에이전트, 요청 권한을 정책에 대보고 몇 분짜리 토큰을 발급한다.
  7. 같은 데모를 다시 돌리자 정책이 개인정보 조회와 DB 삭제를 막았다. 권한 없는 사용자의 승인도 통하지 않았다.
01

데모: 권한이 너무 많은 당직 에이전트 00:00

발표는 데모로 시작한다. 주인공은 당직 분류 에이전트(on-call triage agent)다. 밤사이 들어온 장애 티켓을 읽고, 직접 해결하거나 아침 팀에게 넘긴다.

이 에이전트는 세 곳에 전체 권한을 갖고 있다. 클라우드 호스팅 API, 고객 데이터 웨어하우스, 결제 데이터베이스다. 티켓은 Incidex라는 장애 페이저 서비스에서 읽고 쓴다.

티켓에이전트가 한 일문제
결제 이상 00:50Snowflake 키로 고객 데이터 웨어하우스를 조회했다. 아침 팀 보고서에 조회한 행을 그대로 붙였다개인 식별 정보(PII)가 보고서로 퍼졌다
백업 전원 장애 01:30물리적인 문제라고 판단했다. 다른 서비스를 부르지 않고 아침 팀에게 넘겼다없음. 유일하게 문제없이 끝났다
TLS 인증서 만료 임박 01:50클라우드 호스팅 API의 인증서 갱신 엔드포인트를 API 키로 불러 해결했다결과는 맞다. 하지만 누가 키를 썼는지 기록에 남지 않는다
결제 DB 고장 02:30문서에 적힌 복구 절차대로 DB를 지우고 복원했다. 관리자 비밀번호가 든 연결 문자열을 썼다복원이 됐는지 스스로 확인할 수 없었다. 확인은 아침 팀에게 미뤘다
주문 멈춤 03:20메인 서버가 멈췄다는 티켓을 보고 정적 API 키로 서버를 재시작했다운영 서비스가 내려갔다
방문자 3명 중 1명 접속 실패 03:40서비스를 파드 4개에서 40개로 늘리고 아침 팀에게 메모를 남겼다시간당 420달러가 나가기 시작했다

발표자는 권한이 과한 에이전트가 운영 DB를 지우는 일을 여러 회사가 실제로 겪었다고 말했다.

여섯 티켓의 공통점 에이전트는 매번 오래 살아 있는 정적 자격 증명을 썼다. API 키, Snowflake 키, 관리자 비밀번호가 든 연결 문자열이다. 그래서 감사 로그로는 누가 그 키를 썼는지 알 수 없었다.
02

에이전트를 쓸모 있게 만드는 세 가지 04:10

보통 에이전트에게 바라는 최소한의 능력은 세 가지다.

1 · 사용자 데이터 읽기

사용자가 갖고 있거나 접근할 수 있는 데이터를 읽는다.

  • 이메일
  • 문서
  • 고객 CRM
2 · 스스로 조사하기

필요한 정보를 직접 찾는다.

  • 웹 검색
  • 문서 읽기
  • GitHub 이슈 가져오기
3 · 외부 도구 쓰기

바깥 서비스를 불러 일을 처리한다.

  • MCP 서버
  • API
  • SaaS 플랫폼

에이전트는 이 일을 사람의 승인을 받아 가며 하기도 한다(human in the loop). 사람 없이 뒤에서 혼자 하기도 한다.

03

치명적 삼중 조합 05:00

에이전트를 쓸모 있게 만드는 능력이 에이전트를 위험하게도 만든다. Simon Willison은 세 가지가 함께 있는 상태를 치명적 삼중 조합(lethal trifecta)이라고 불렀다.

요소당직 에이전트에서는
개인 데이터 접근고객 데이터 웨어하우스 조회, 결제 DB 조작
신뢰할 수 없는 콘텐츠 노출사용자가 올린 티켓, 다른 에이전트의 보고, 외부에 문서로 적힌 절차
외부와 통신하는 능력서드파티 API와 SaaS 서비스를 읽고 쓰기

발표자는 셋이 모이면 공격자에게 문이 활짝 열린다고 말한다.

발표에서 구체적인 공격 경로는 설명하지 않았다. 이 용어가 흔히 가리키는 위험은 이렇다. 신뢰할 수 없는 콘텐츠에 숨은 지시가 에이전트를 움직인다. 에이전트는 개인 데이터를 읽고, 외부 통신으로 그 데이터를 밖에 보낸다.

데모와 연결해 보기 첫 데모의 티켓에는 공격자가 심은 지시가 없었다. 그런데도 사고가 났다. 공격이 없어도 권한이 넓으면 에이전트 스스로 피해를 낼 수 있다는 뜻이다.
04

원인은 과한 권한 05:30

에이전트는 일을 끝내도록 설계된다. 그래서 가진 권한을 전부 써서라도 일을 끝낸다. 그 결과가 심각할 때도 있다.

이런 사고는 사람이 에이전트에게 필요보다 훨씬 많은 권한을 주기 때문에 일어난다.발표자의 말을 옮김 · 05:50

권한이 과한 에이전트(overprivileged agent)는 감독을 받아도 스스로 내린 판단대로 움직일 수 있다.

사람 승인을 끼워 넣으면? 06:00

  • 모든 행동에 사람 승인을 강제하면, 접근 통제를 동의 피로(consent fatigue)에 빠진 사용자에게 넘기는 셈이다.
  • 사람의 접근 관리는 수십 년 동안 다듬어 왔다. 그 책임을 사용자에게 미루면 보안 문제가 한 단계 위로 옮겨 갈 뿐이다.

조합을 깨지 말고 접근을 통제한다 06:20

셋 중 하나 이상을 빼면 조합은 깨진다. 하지만 에이전트가 훨씬 덜 쓸모 있어진다.

흔한 대응기능을 빼서 조합을 깬다안전해지지만 에이전트가 쓸모없어진다

05

기존 방법 셋의 한계 06:50

접근을 통제하는 흔한 방법은 셋이다. 각각 권한이나 실행을 무언가에 묶는다.

세 방법 모두 결국 상시 접근(standing access)을 남긴다. 상시 접근은 작업이 없을 때도 늘 살아 있는 권한이다.

방법무엇에 묶나얻는 것남는 구멍
OAuth 07:00권한 부여(grant)사용자가 동의한 범위 안에서만 접근한다동의가 작업보다 먼저 일어난다. 넓게 주면 상시 권한이 되고, 좁게 주면 에이전트가 무능해진다
MCP 게이트웨이 07:40경로(route)관측, 속도 제한, MCP 층의 단일 정책 결정 지점. 요청마다 정책을 적용한다게이트웨이가 상시 자격 증명을 들고 있다. 에이전트의 권한이 작업 하나보다 오래 산다
샌드박스 08:00프로세스피해 반경을 제한한다쓸모 있는 일은 샌드박스 밖에 닿아야 한다. 그때 상시 권한이 다시 생긴다. 밖에서 무엇이 허가되는지는 통제하지 못한다

OAuth에서 사용자는 작업이 생기기 전에, 에이전트가 쓸 수도 있는 모든 권한에 미리 동의한다. 그래서 읽기만 시킨 작업에서도 에이전트는 같은 실행 안에서 쓰기까지 할 수 있다.

발표자는 에이전트가 샌드박스를 빠져나간 사례도 많이 나왔다고 덧붙였다.

셋을 다 합쳐도 08:30 에이전트는 작업 하나에 맞게 범위를 줄인 실행 시점 자격 증명을 받지 못한다. 발표의 나머지는 이 빈칸을 채우는 이야기다.
06

데모에서 드러난 문제 세 가지 08:40

  1. 자격 증명이 누구의 것인지 모른다. 감사 로그(audit log)로는 어떤 사용자나 에이전트가 API 키를 썼는지 알 수 없었다.
  2. 권한에 제한이 없다. 에이전트는 API 키가 허락하는 모든 권한을 쓸 수 있었다.
  3. 사람 승인을 모든 곳에 붙일 수 없다. 사람도 실수한다. 많은 에이전트는 사람 없이 혼자 돈다.
07

토큰 교환: 먼저 사용자를 안다 09:10

발표자의 해법은 토큰 교환(token exchange)이다. 2020년에 나온 기존 표준이고, OAuth 2를 확장한다.

발표에서 표준 번호는 말하지 않았다. 이 표준의 문서 번호는 RFC 8693이다.

출발점은 사용자가 누구인지 아는 것이다.

  1. 사용자가 먼저 로그인한다. 신원을 확인하고 토큰을 발급하는 곳이 인가 서버(authorization server)다. Google, Okta, Auth0 같은 ID 제공자가 인가 서버를 제공한다.
  2. 인가 서버가 사용자에게 동의를 묻는다. 사용자 권한 중 일부를 에이전트에게 맡길지 묻는 것이다. 이 권한 단위를 스코프(scope)라고 한다.
  3. 사용자가 고른 스코프만 에이전트에게 넘어간다. 이것이 첫 번째 범위 좁히기다.
  4. 인가 서버가 토큰을 발급한다. 토큰에는 사용자가 누구인지, 어디까지 접근할 수 있는지가 담긴다.
이 단계만으로도 데모보다 낫다 이제 사용자가 누구인지 안다. 그 사용자가 무엇에 접근할 수 있는지도 안다.
08

에이전트 실행 경로 10:20

다음은 로그인한 사용자가 LLM을 통해 리소스를 다루는 경로다. 데모에서 리소스는 장애 페이저, 운영 DB, Snowflake, 클라우드 호스팅 서비스다.

구성 요소하는 일당직 에이전트에서는
에이전트LLM을 부르는 제어 루프당직 분류 에이전트
에이전트 런타임에이전트 루프를 돌리고 호출을 실행하는 프로세스Claude Code 같은 CLI일 수도 있고, 에이전트 SDK로 만든 앱일 수도 있다. 당직 에이전트는 후자다
MCP 클라이언트모델이 제안한 도구 호출을 MCP 서버로 보낸다런타임 안에서 동작한다
MCP 서버에이전트와 리소스 사이에서 정해진 도구를 제공하고 리소스 접근을 중개한다운영 인프라 도구 모음. 이번에 새로 붙인다
리소스에이전트가 실제로 다루는 서비스장애 페이저, 운영 DB, Snowflake, 클라우드 호스팅

첫 데모의 에이전트는 MCP 서버 없이 리소스를 직접 불렀다. API 키나 DB 연결 문자열 같은 오래 사는 정적 자격 증명을 썼다. 이제는 MCP 서버가 그 사이에서 접근을 중개한다.

프롬프트 하나가 지나가는 길 11:30

  1. 사용자가 런타임에 프롬프트를 낸다.
  2. 런타임이 모델을 불러 프롬프트를 보낸다.
  3. 모델이 도구 호출을 제안한다.
  4. MCP 클라이언트가 그 호출을 MCP 서버로 보낸다.
  5. MCP 서버가 도구를 실행하고 리소스 API를 부른다.
  6. 응답이 MCP 서버와 MCP 클라이언트를 거쳐 런타임으로 돌아온다.
  7. 런타임이 모델을 다시 부른다. 모델이 만족할 때까지 3~7단계를 반복하고, 끝나면 사용자에게 답한다.
09

도구 호출마다 토큰을 바꾼다 12:10

로그인한 사용자의 토큰은 주체 토큰(subject token)이 된다. 에이전트가 누구를 대신해 움직이는지 알려 주는 토큰이다.

토큰 교환은 코드를 실행할 수 있는 OAuth 클라이언트가 맡는다. 후보는 두 가지다.

  • MCP 클라이언트와 서드파티 MCP 서버 사이에 둔 게이트웨이
  • 직접 만든 앱

직접 만든 MCP 서버도 하위 리소스용 토큰을 교환할 수 있다.

교환 요청의 흐름 12:50

  1. 프롬프트와 주체 토큰이 런타임에 전달된다.
  2. 에이전트 루프가 돌고, 모델이 도구 호출을 제안한다.
  3. 런타임이 보안 토큰 서비스(security token service, STS)에 자기 신원을 증명한다. STS는 토큰 교환을 처리하는 특별한 인가 서버다. 증명에는 앱 클라이언트 자격 증명이나 워크로드 아이덴티티(workload identity)를 쓴다.
  4. 런타임이 주체 토큰도 함께 보낸다.
  5. 런타임이 토큰 교환을 요청한다. 그 도구 호출 하나, 오직 그 호출에만 MCP 서버를 쓰게 해 달라는 요청이다.
데모에 없던 정보 세 가지 13:20 1. 접근을 요청하는 에이전트의 신원 2. 에이전트가 대신하는 사용자의 신원 3. 사용자가 에이전트에게 허락한 접근 수준

토큰을 줄지 말지는 거버넌스 정책(governance policy)이 정한다. 정책은 세 가지를 본다. 어떤 리소스에 어떤 접근을 요청했는지, 에이전트가 누구인지, 사용자가 누구인지다.

10

정책은 천장일 뿐: 의도 기반 인가 14:00

정책은 천장이다. 정책이 허용하는 범위 안에서도 에이전트는 의도하지 않은 일을 할 수 있다.

그래서 나온 것이 의도 기반 인가(intent-based authorization, IBA)다. 에이전트가 움직이기 전에 사용자가 무엇을 뜻했는지 확인한다.

IBA는 아직 확정된 표준이 아니다. 지금도 제안을 받는 중이다. 발표에서 소개한 방식은 Keycard의 구현이다.

발표자는 Keycard 소속이고, 이 절의 IBA 설계가 자기 회사의 방식이라고 직접 밝혔다. 그 점을 감안해 읽자.

미션 14:30

IBA에서는 게이트웨이가 정책 집행 지점(policy enforcement point)이 된다. 프롬프트를 받은 에이전트는 먼저 미션(mission)을 제안한다. 미션에는 목표, 허용된 행동, 한도가 들어간다.

미션 A · 자동 승인

목표: 장애 2294 분류하기

  • 그 티켓만 읽는다
  • 요약하거나 사람에게 넘긴다
  • 다른 티켓은 읽지 않는다
  • 다른 서비스는 쓰지 않는다

티켓을 살펴보기만 하는 낮은 위험 작업이다. 관리자 정책에 따라 자동 승인될 수 있다.

미션 B · 사용자 승인 15:10

목표: 티켓을 읽은 뒤 사용량 급증 해결하기

  • 서비스 확장을 한 번 허용한다
  • 다른 도구나 API는 쓰지 않는다

미션을 사용자에게 보여 주고 검토와 승인을 받는다.

미션 ID로 호출을 확인한다 15:30

  1. 승인이 나면 STS가 미션에 ID를 붙여 에이전트에게 보낸다.
  2. 에이전트의 도구 호출에는 이 미션 ID가 들어간다.
  3. 게이트웨이가 호출을 중계하면서, 이 도구 호출이 미션에 맞는지 STS에 묻는다.
  4. 맞으면 게이트웨이가 그 호출 하나를 위한 토큰 교환을 요청한다.
11

토큰 발급과 하위 리소스 15:50

STS는 세 가지를 따진다. 정책, 위임 사슬(delegation chain), 요청한 접근이다. 위임 사슬은 누가 누구를 대신해 움직이는지 이어진 기록이다.

모두 문제없으면 STS가 MCP 서버용 접근 토큰을 발급한다. 발표 내용을 표로 정리하면 이렇다.

항목MCP 서버용 토큰
누구를 대신하나로그인한 사용자. 사용자 주체가 그대로 유지된다
누가 교환했나교환을 수행한 앱. 여기서는 당직 에이전트
어디에 쓰나MCP 서버의 그 도구 호출 하나
언제까지몇 분 안에 만료된다
보관저장하지 않는다. 한 번 쓰고 사라지는 일회성(ephemeral) 토큰이다
  1. STS가 토큰을 게이트웨이로 보낸다.
  2. 게이트웨이가 MCP 서버를 부른다.
  3. MCP 서버가 토큰을 검증하고 도구 호출을 허가한다.

도구가 외부 리소스를 써야 할 때 16:30

  1. MCP 서버가 방금 받은 토큰을 STS에 내고, 하위 리소스용 토큰으로 바꿔 달라고 한다.
  2. STS가 정책에 비춰 요청을 평가한다.
  3. 통과하면 그 도구 호출에만 쓰는 리소스 토큰을 새로 만든다. 사용자 주체는 그대로 둔다.
  4. STS가 토큰을 게이트웨이로 보내고, 게이트웨이를 거쳐 MCP 서버가 리소스를 부른다.
  5. 리소스가 토큰을 검증하고 접근을 허가한다.
  6. MCP 서버는 호출이 끝나면 토큰을 바로 버린다.
사용자 주체를 끝까지 유지하는 이유 위임 사슬이 리소스까지 이어진다. 그래서 모든 활동을 사용자와 에이전트 단위로 추적할 수 있다.

리소스의 응답은 거꾸로 올라간다. 모델이 답을 낼 때까지 에이전트 루프가 반복된다.

같은 데모, 다른 결과 17:30

이번에는 STS가 위임 인가(delegated authorization)로 에이전트 접근을 관리한다. MCP 서버가 도구를 정하고 리소스 접근을 중개한다.

이 데모는 작업 기반 정책(task-based policy)을 쓴다. 의도 기반 인가는 쓰지 않았다. 발표자는 IBA 데모를 이달 말 Agent Con(추정)에서 보여 주겠다고 했다.

  3. 클라우드 호스팅 플랫폼에 로그인한다. 이 플랫폼 기능 일부를 에이전트가 대신 쓰도록 허락한다. 자막에는 플랫폼 이름이 compost(추정)로 들린다.

대기열의 티켓은 같다. 에이전트도 처음처럼 행동하려 한다. 달라진 점은 하나다. 모든 요청이 STS와 정책 평가를 통과해야 토큰을 받는다.

토큰 교환은 공개 표준이다 24:20

발표자는 토큰 교환이 공개된 표준이고 충분히 연구됐다고 강조한다. 누구나 구현할 수 있다. 함께 쓸 수 있는 것으로 이런 목록을 들었다.

  • 기존 정책 엔진, 표준을 따르는 ID 제공자
  • 게이트웨이, 샌드박스, OAuth
  • 기성품 에이전트와 직접 만든 에이전트, CLI, MCP 서버
  • 소프트웨어 팩토리, 에이전트 간 통신, 앱 간 접근(cross-app access)
  • 다음 주에 새로 나올 무언가

발표자는 이 방식으로 에이전트를 쓸모 있고, 안전하고, 앞으로도 쓸 수 있게 만들자고 마무리한다.

토큰 교환 자체는 공개 표준이다. 다만 발표자는 Keycard 소속이고, 발표 속 IBA 설계는 Keycard의 방식이다. 결론의 권고도 그 점을 감안해 읽자.

핵심 정리

  1. 쓸모 있는 에이전트는 개인 데이터, 신뢰할 수 없는 콘텐츠, 외부 통신을 갖는다. 셋이 모이면 치명적 삼중 조합이다.
  2. 데모의 사고는 공격이 아니라 과한 권한에서 나왔다. 정적 키 하나로 PII 공유, DB 삭제, 서버 재시작, 파드 10배 확장이 일어났다.
  3. 사람 승인을 늘리면 동의에 지친 사용자에게 책임만 넘어간다.
  4. 기능을 빼면 쓸모가 줄어든다. 기능은 두고 접근을 통제한다.
  5. OAuth, MCP 게이트웨이, 샌드박스는 합쳐도 상시 접근을 남긴다. 작업 하나에 맞춘 실행 시점 자격 증명이 없다.
  6. 토큰 교환은 2020년에 나온 OAuth 2 확장 표준이다. 사용자 로그인과 스코프 동의가 첫 번째 범위 좁히기다.
  7. 도구 호출마다 런타임이 STS에 주체 토큰을 내고, 그 호출 하나에 쓸 토큰을 받는다.
  8. STS가 발급한 토큰은 몇 분 안에 만료되고, 저장하지 않으며, 쓰고 바로 버린다. 사용자 주체는 리소스까지 이어진다.
  9. 정책은 천장일 뿐이다. 의도 기반 인가는 미션을 먼저 정하고 호출이 미션에 맞는지 본다. 아직 표준은 아니다.
  10. 사람 승인도 정책과 사용자 역할을 넘지 못한다. 사용자가 못 하는 일은 에이전트도 못 한다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1치명적 삼중 조합의 세 요소와, 이 말을 만든 사람은?
개인 데이터 접근, 신뢰할 수 없는 콘텐츠 노출, 외부와 통신하는 능력. Simon Willison이 만든 말이다.
Q2첫 데모에서 에이전트가 쓴 자격 증명의 공통점과, 그 때문에 생긴 문제는?
API 키, Snowflake 키, 관리자 비밀번호가 든 연결 문자열처럼 오래 사는 정적 자격 증명이었다. 감사 로그로 누가 그 키를 썼는지 알 수 없었다.
Q3발표자가 꼽은 사고의 원인은? 모든 행동에 사람 승인을 붙이는 방법은 왜 답이 아닌가?
사람이 필요보다 훨씬 많은 권한을 준 것이 원인이다. 사람 승인을 강제하면 동의에 지친 사용자에게 책임이 넘어간다. 사람도 실수하고, 많은 에이전트는 사람 없이 혼자 돈다.
Q4세 요소 중 하나를 빼는 대신 발표자가 제안하는 것은?
기능은 그대로 두고 접근을 통제한다. 공격 표면을 줄이고 피해 반경을 가두면서 에이전트의 능력과 자율성은 유지한다.
Q5OAuth만으로 작업 단위 통제가 안 되는 이유는?
동의가 작업이 생기기 전에 일어난다. 넓게 주면 상시 권한이 되고, 좁게 주면 에이전트가 무능해진다. 읽기만 시킨 작업에서도 같은 실행 안에서 쓰기까지 할 수 있다.
Q6MCP 게이트웨이와 샌드박스에 공통으로 남는 구멍은?
상시 접근. 게이트웨이는 상시 자격 증명을 들고 있고, 샌드박스는 밖으로 나가는 순간 상시 권한이 다시 필요하다.
Q7토큰 교환 요청으로 STS가 알게 되는, 데모에 없던 정보 세 가지는?
접근을 요청하는 에이전트의 신원, 에이전트가 대신하는 사용자의 신원, 사용자가 에이전트에게 허락한 접근 수준.
Q8"정책은 천장"이라는 말의 뜻과, 의도 기반 인가가 더하는 것은?
정책이 허용하는 범위 안에서도 에이전트는 의도하지 않은 일을 할 수 있다. 의도 기반 인가는 목표, 허용 행동, 한도를 담은 미션을 먼저 정하고, 도구 호출이 미션에 맞을 때만 토큰을 교환한다.
Q9STS가 발급한 토큰을 다루는 규칙 세 가지는?
몇 분 안에 만료된다. 저장하지 않는다. MCP 서버는 호출이 끝나면 바로 버린다.
Q10하위 리소스용 토큰에도 사용자 주체를 유지하는 이유는?
위임 사슬이 리소스까지 이어져서, 모든 활동을 사용자와 에이전트 단위로 추적할 수 있다.
Q11두 번째 데모의 결제 이상 티켓에서 정책이 막은 것과 이유는?
고객 데이터 웨어하우스 조회용 자격 증명 발급을 막았다. 고객 PII는 에이전트 컨텍스트에도, 장애 티켓에도 들어가면 안 되기 때문이다.
Q12발표자가 서버 재시작을 승인했는데도 막힌 이유는?
발표자의 역할에 재시작 권한이 없었다. 에이전트는 사용자를 대신해 움직이므로, 사용자가 못 하는 일은 에이전트도 못 한다.

용어 정리

용어뜻
치명적 삼중 조합Lethal trifecta. 개인 데이터 접근, 신뢰할 수 없는 콘텐츠 노출, 외부 통신 능력이 한 에이전트에 모인 상태. Simon Willison이 만든 말
당직 분류 에이전트On-call triage agent. 밤사이 장애 티켓을 읽고 해결하거나 사람에게 넘기는 에이전트
에스컬레이션Escalation. 직접 처리하지 않고 다른 사람이나 팀에게 넘기는 것
PIIPersonally identifiable information. 이름, 연락처처럼 특정 개인을 알아볼 수 있는 정보
정적 자격 증명Static credential. API 키, DB 비밀번호처럼 바꾸기 전까지 계속 쓸 수 있는 비밀 값
과한 권한Overprivileged. 맡은 일에 필요한 것보다 많은 권한을 가진 상태
동의 피로Consent fatigue. 승인 요청이 너무 잦아 내용을 제대로 보지 않고 승인하게 되는 상태
공격 표면Attack surface. 공격자가 파고들 수 있는 지점 전체
피해 반경Blast radius. 사고 하나가 번질 수 있는 범위
상시 접근Standing access. 작업이 없을 때도 늘 살아 있는 권한
OAuth사용자가 비밀번호를 넘기지 않고 앱에 권한 일부를 맡기는 인가 표준
스코프Scope. OAuth에서 맡기는 권한의 단위. 예: 대기열 읽기
MCPModel Context Protocol. 에이전트가 외부 도구와 데이터에 연결하는 방식을 정한 프로토콜
MCP 게이트웨이에이전트와 MCP 서버 사이에서 요청을 중계하며 정책, 관측, 속도 제한을 거는 중간 서버
샌드박스프로그램을 격리된 환경에서 실행해 피해를 가두는 장치
인가 서버Authorization server. 신원을 확인하고 토큰을 발급하는 서버
ID 제공자Identity provider. 로그인과 신원 확인을 맡는 서비스. 예: Google, Okta, Auth0
토큰 교환Token exchange. 가진 토큰을 내고 다른 대상이나 더 좁은 범위의 토큰을 받는 OAuth 2 확장 표준. 2020년 발표, RFC 8693
주체 토큰Subject token. 에이전트가 누구를 대신하는지 나타내는 사용자 토큰
보안 토큰 서비스 (STS)Security token service. 토큰 교환 요청을 정책에 대보고 새 토큰을 발급하는 인가 서버
워크로드 아이덴티티Workload identity. 사람이 아니라 프로그램이나 서비스에 붙는 신원
위임 사슬Delegation chain. 누가 누구를 대신해 움직였는지 이어진 기록
거버넌스 정책Governance policy. 어떤 사용자와 에이전트가 어떤 리소스에 무엇을 할 수 있는지 정한 규칙
정책 결정 지점Policy decision point. 요청을 허용할지 판단하는 곳
정책 집행 지점Policy enforcement point. 판단에 따라 요청을 실제로 통과시키거나 막는 곳
의도 기반 인가 (IBA)Intent-based authorization. 에이전트가 움직이기 전에 목표, 허용 행동, 한도를 미션으로 정하고 호출이 그 안에 있는지 확인하는 방식. 아직 확정된 표준은 아니다
에이전트 런타임Agent runtime. 에이전트 루프를 돌리고 도구 호출을 실행하는 프로세스. 예: Claude Code, 에이전트 SDK로 만든 앱
감사 로그Audit log. 누가 언제 무엇을 했는지 남긴 기록
파드Pod. 서비스를 돌리는 실행 단위. 쿠버네티스에서 쓰는 말이다. 늘리면 처리량과 비용이 함께 는다
