에이전트에게 검색 가르치기

원하는 에이전트 행동을 데이터 문제로 바꾸고, 그 데이터를 합성해 모델을 학습시키는 방법. NVIDIA의 오픈소스 도구 Data Designer로 검색 수수께끼와 검색 궤적을 만들어, Nemotron 모델이 BrowseComp 벤치마크에서 0%에서 30%로 오른 과정을 따라간다.

원본 영상: Teaching Agents to Search with NVIDIA Data Designer 발표: Dhruv Nathawani (NVIDIA 연구 과학자, Nemotron 팀)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 수치와 벤치마크 결과는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 것만 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

발표자는 NVIDIA 소속이고 Data Designer는 발표자 팀이 만든 제품이다. 도구의 장점과 성과 수치는 그 점을 감안해 읽자.

3분 요약
  1. 원하는 에이전트 행동을 데이터 문제로 바꾼다. 그 행동을 보여 주는 데이터를 만들고, 그 데이터로 모델을 학습시킨다. 검색은 한 예일 뿐이고 틀은 어디에나 쓸 수 있다.
  2. LLM을 반복 호출하기만 하면 10~20번 만에 같은 답이 돈다. Data Designer는 시드, 샘플러, LLM 열을 그래프로 엮어 프롬프트마다 다른 재료를 넣는다.
  3. 모델에는 지식 마감일이 있다. 그 뒤의 일을 알려면 검색해야 한다. 진척은 BrowseComp 벤치마크로 잰다.
  4. 시드는 위키데이터 그래프를 5~8홉 무작위로 걷는 것이다. 그 경로를 수수께끼로 바꾸면 모델이 외운 답으로는 못 풀고 검색을 하게 된다.
  5. 시드 50,000개에서 출발해 고품질 레코드 7,000개만 남겼다. 그걸로 학습한 모델이 BrowseComp에서 0%에서 30%가 됐다.
  6. 가장 어려운 단계는 평가다. LLM 판정은 한 층일 뿐이고, 사람 교차 확인과 실시간 정보를 겹쳐야 데이터를 믿을 수 있다.
  7. 습관: 양보다 다양성, 가장 싼 열 타입 쓰기, 많이 만들고 걸러 내기, 데이터를 직접 보기, 데이터 만드는 과정을 코드로 남기기.
01

왜 합성 데이터인가 03:20

인터넷 데이터는 트랜스포머에게 주고 싶은 데이터가 아니다.발표자가 인용한 Andrej Karpathy의 말

인터넷에는 위키백과 같은 좋은 자료와 누군가의 트윗이 섞여 있다. 어느 것이 학습에 쓸 만한지 가려내기 어렵다. 전통적인 방법은 이 데이터를 모아서 다듬는 것이다. 발표자가 제안하는 방법은 합성 데이터synthetic data다. 처음부터 만들 수도 있고, 실제 데이터를 씨앗으로 삼아 만들 수도 있다.

씨앗을 쓰면 합성 데이터가 모델의 상상에만 기대지 않는다. 실제 세상의 분포에 뿌리를 둔다. 이 일을 하는 틀이 Data Designer다. 완전한 오픈소스이고 pip로 설치한다. 발표자에 따르면 지금까지 이 도구로 만든 학습 데이터가 6.5조 토큰이다.

LLM을 그냥 반복 호출하면 생기는 일 05:10

제품 리뷰 데이터가 필요하다고 하자. 가장 쉬운 방법은 "제품 하나, 리뷰 하나, 고객 프로필 하나"를 백만 번 묻는 것이다. 이렇게 하면 빠진 것이 많다.

빠진 것왜 문제인가
다양성같은 프롬프트를 10~20번 보내면 모델이 같은 내용을 반복한다. 발표자가 가장 중요하다고 세 번 강조한 항목이다
특성 사이의 상관관계제품, 리뷰, 고객이 서로 따로 논다. 실제 데이터에서는 서로 얽혀 있다
다중 형식텍스트만 나오고 이미지 같은 다른 형식은 못 만든다
조종 가능성어떤 데이터가 얼마나 나올지 정할 수 없다
검증만든 데이터가 맞는지 확인하는 단계가 없다
공유 가능성내가 만든 과정을 남이 그대로 다시 돌릴 수 없다
02

열을 엮어 그래프를 만든다 06:20

Data Designer의 기본 단위는 열column이다. 데이터셋을 열 하나씩 차례로 만든다. 열의 종류는 이렇다.

열 종류하는 일예
시드 열실제 데이터를 출발점으로 넣는다. 선택 사항이다. CSV, JSONL, Parquet 파일이면 된다위키백과 주제 목록, 회사 내부 데이터
샘플러 열다양성을 주입한다. 값과 비율을 정해 두고 뽑는다. 하위 샘플러로 값마다 다른 분기를 둘 수 있다난이도: 쉬움, 보통, 어려움
LLM 텍스트 열프롬프트에 앞 열들의 값을 끼워 넣어 글을 만든다질문, 답
구조화 열JSON이나 마크다운 같은 정해진 형식으로 만든다. 형식이 깨진 레코드는 버린다정답과 근거 URL을 담은 JSON
코드 열, 이미지 열코드나 이미지를 만든다. 이미지는 최근에 추가됐다
검증 열만든 값을 확인한다LLM 판정 점수

이 열들을 이어 붙이면 데이터셋이 어떤 모양이어야 하는지 설명하는 방향 그래프DAG가 된다. 그래프가 준비되면 한 번의 실행으로 데이터셋이 나온다.

2026년에 왜 코드를 보여 주나 08:10 Codex나 Claude Code 같은 도구가 코드를 대신 써 주는 시대다. 그래도 코드를 이해하고 있어야 그 도구에게 자기 데이터 워크플로를 시킬 수 있다. 노트북과 슬라이드는 발표자의 GitHub 저장소에 있다.
03

노트북 1: 질문과 답 만들기 09:00

첫 노트북의 목표는 위키백과 주제로 퀴즈 질문과 답 쌍을 만드는 것이다. 흐름은 이렇다.

  1. 모델 공급자 설정 09:30. 발표자는 NVIDIA GPU 클러스터에서 vLLM으로 gpt-oss-120b를 직접 돌렸다. 열린 모델은 보통 데이터 생성에 써도 된다. 닫힌 모델은 라이선스 때문에 그 결과로 다른 모델을 학습시키는 것을 막기도 한다.
  2. 시드 데이터셋 지정 10:10. 위키백과 주제들을 CSV로 만들어 설정 빌더에 넘긴다.
  3. 샘플러 추가 10:40. 난이도를 쉬움, 보통, 어려움으로 두고 가중치를 준다. 보통 문제를 더 많이 뽑는 식이다. 난이도마다 질문 유형을 다시 나눈다. 쉬움은 직접 찾기, 단순 사실, 정의. 어려움은 상세하거나 잘 안 알려진 내용.
  4. LLM 열 추가 11:10. "당신은 전문 퀴즈 출제자다"로 시작하는 프롬프트에 주제, 난이도, 질문 유형 자리를 비워 둔다. Jinja 템플릿 문법으로 쓴 자리는 실행 때 앞 열의 값으로 채워진다. 그래서 모델이 보는 프롬프트가 매번 다르다.
  5. 미리보기 12:40. 레코드 3개만 만들어 눈으로 본다. 예로 나온 주제는 월드와이드웹 컨소시엄이었다. "노르웨이 어느 도시의 공항 코드와 같은 세 글자 약어로 불리는 W3C 권고안은?" 같은 질문이 나왔다.
  6. LLM 판정 열 13:30. 다른 모델에게 질문의 품질을 점수 매기게 한다.
  7. 일괄 생성 14:20. 원하는 개수를 적고 실행한다. 열 순서대로 질문을 다 만든 뒤 답을 만든다. 완성된 데이터셋은 함수 하나로 Hugging Face에 올릴 수 있다.

발표자는 일부러 어려운 질문을 만든다. 모델이 외운 지식으로 답할 수 없어야 나중에 검색을 하게 되기 때문이다. 첫 노트북에서는 아직 검색 없이 모델이 답을 지어낸다.

04

노트북 2: 도구를 쓰는 데이터 15:30

MCPModel Context Protocol는 에이전트가 도구에 연결하는 표준이다. 여기서 도구는 에이전트용 검색 서비스 Tavily다. 가입하면 1,000 크레딧을 무료로 준다고 한다.

노트북 1질문을 만들고, 답을 만들어라모델이 기억으로 답한다
→
노트북 2질문을 만들고, 이 도구로 답을 찾아라답 열에 도구 별칭을 붙이면 모델이 Tavily를 부른다

시드, 샘플러, 질문 열은 첫 노트북과 같다. 답 열을 만들 때 도구 별칭 하나를 더 넘기는 것이 전부다. 그러면 모델은 답을 지어내는 대신 검색 도구를 써서 찾는다.

미리보기에서 나온 질문은 "Telefunken(추정)이 1949년에 본사를 옮긴 독일 도시는?"이었다. 모델이 만든 검색어, Tavily가 돌려준 URL과 제목과 본문, 그리고 최종 답이 한 레코드에 담긴다. 이 한 덩어리를 궤적trajectory이라 부른다.

데이터 만들기는 반복 작업이다 17:40 한 번에 끝나지 않는다. 미리보기로 몇 개를 만들고, 마음에 안 들면 프롬프트나 흐름을 고치고, 다시 본다. 만족할 때 일괄 생성으로 넘긴다.
05

왜 검색을 가르치나 19:30

발표자는 NVIDIA의 Nemotron 팀 소속이다. Nemotron은 NVIDIA가 공개한 오픈 기반 모델 모음으로, 세 가지 크기가 있고 최근 Ultra가 나왔다. 이 모델들에게 검색을 가르치는 것이 팀의 일이었다.

모델에는 지식 마감일knowledge cutoff이 있다. 학습을 시작하려면 어느 시점에 데이터 수집을 멈춰야 하기 때문이다. 2024년 1월에 학습을 시작했다면 2023년 12월 이후의 일은 모른다. "오늘 날씨"는 학습 데이터로 답할 수 없다. 현재 일을 아는 것은 과거를 아는 것만큼 중요하다. 그래서 모델은 검색을 배워야 한다.

진척을 재는 자: BrowseComp 21:40

벤치마크는 답이 공개되지 않은 표준 시험지다. 검색용 벤치마크 중 하나가 BrowseComp이고 아주 어렵다. 예로 든 문제는 이렇다. "1990년부터 1994년 사이, 브라질 심판이 봤고 양 팀에 두 장씩 경고가 나왔으며…" 같은 조건이 길게 이어진다. 답은 아일랜드 대 루마니아였다.

사람이라면 문제를 쪼개고, 어떤 검색을 할지 생각하고, 검색하고, 얻은 정보와 원래 목표를 다시 맞춰 보고, 또 검색한다. 모델에게 가르치려는 것이 바로 이 행동이다.

06

위키데이터 산책으로 수수께끼 만들기 23:20

검색 데이터의 시드는 위키백과 문서가 아니라 위키데이터Wikidata다. 위키백과 항목들이 서로 어떻게 연결되는지 적어 둔 그래프다. 이 그래프에서 항목 하나를 무작위로 고르고, 연결을 따라 몇 홉을 걷는다. 그 경로가 시드 하나다.

예시 경로 NVIDIA → 창업자 Jensen Huang → 다닌 대학 Oregon State University → 대학이 있는 Benton County → 카운티 이름의 유래 Thomas Hart Benton

이 경로를 수수께끼로 바꾸면 이렇게 된다. "Thomas Hart Benton의 이름을 딴 카운티에 있는 대학을 나온 사람이 세운 회사는?" 학습 데이터에 이 답이 그대로 있을 리 없다. 발표자의 말대로 에이전트에게 반칙할 기회를 주면 반칙한다. 답을 외우고 있으면 검색 도구를 안 쓴다. 그래서 문제를 최대한 수수께끼처럼 만든다.

홉 수는 5~8개가 좋았다고 한다. 너무 많이 걸으면 "어떤 사람 → 인간"처럼 주제에서 벗어난다. 발표자는 이 숫자를 경험으로 정한 기준이라고 했다.

발표에서 홉 수를 한 번은 "5~8", 다른 곳에서는 "4~8"이라고 말했다. 정확한 값보다 "이 범위 안에서 주제가 유지된다"는 뜻으로 읽으면 된다.

전체 흐름 26:10

  1. 위키데이터에서 무작위 경로를 만든다. 백만 번 돌리면 백만 개의 다른 경로가 나온다.
  2. 경로를 검색 수수께끼로 바꾼다.
  3. Tavily로 실제 검색을 실행해 궤적을 만든다.
  4. 만든 데이터를 평가한다.
  5. 모델을 학습시키고 벤치마크로 잰다.
청중 질문: 왜 어려운 문제여야 하나 26:50 발표자의 답은 "어려운" 문제가 아니라 인터넷에서 바로 찾을 수 없는 문제여야 한다는 것이다. BrowseComp 문제 전체를 검색창에 넣어도 답이 바로 안 나와야 한다. 그래야 여러 단계를 거치는 행동을 배운다.
07

노트북 3: 검색 궤적 만들기 27:30

세 번째 노트북은 앞의 두 개를 합친 것이다. 시드만 위키데이터 경로로 바뀐다. 발표자는 Tavily를 MCP로 부르는 함수를 따로 써 두었다.

에이전트에게 주는 시스템 프롬프트 28:40

  • 역할: 웹 검색으로 질문에 정확히 답하는 전문 검색 에이전트.
  • 출력 형식: 최종 답, 근거 URL, 짧은 이유를 담은 올바른 JSON.

핵심 정리

  1. 원하는 에이전트 행동을 데이터 문제로 바꾼다. 그 행동을 담은 데이터를 만들고, 그걸로 학습시킨다.
  2. LLM을 반복 호출하면 다양성, 상관관계, 조종, 검증, 공유가 빠진다. 열 그래프로 이걸 채운다.
  3. 열은 시드 → 샘플러 → LLM → 구조화 → 검증 순으로 엮는다. 샘플러가 프롬프트마다 다른 재료를 넣는다.
  4. 에이전트 데이터는 답 열에 도구 별칭을 붙이는 것으로 시작한다. 질문, 검색어, 검색 결과, 답이 궤적 하나가 된다.
  5. 검색이 필요한 이유는 지식 마감일이다. 진척은 BrowseComp로 잰다.
  6. 시드는 위키데이터 5~8홉 산책. 외운 답으로 못 풀어야 모델이 검색한다. 반칙할 기회를 주면 반칙한다.
  7. 시드 50,000개 중 7,000개만 남겼고, 그걸로 BrowseComp 0% → 30%.
  8. 평가는 여러 층이다. LLM 판정, 사람의 교차 확인, 실시간 정보. 시드도 낡는다 (US Steel).
  9. 습관: 양보다 다양성, 가장 싼 열 타입, 많이 만들고 걸러 내기, 데이터를 직접 보기.
  10. 데이터 만드는 과정을 코드로 남겨 버전 관리하고 공유한다. 페르소나로 실제 분포를 맞춘다.

난이도 뽑기처럼 규칙으로 되는 일에 LLM을 쓰지 않는다. 샘플러는 파이썬으로 돌리고, 글을 만들 때만 LLM을 쓴다.
Q12페르소나 데이터셋이 푸는 문제는?
합성 데이터가 실제 인구 분포를 따르게 하는 것. LLM은 숫자를 평균으로 수렴시키므로 분포를 따로 잡아 줘야 한다. 개인 정보 없이 집단에서 배울 수 있다.

용어 정리

용어뜻
합성 데이터Synthetic data. 모델이나 규칙으로 만들어 낸 학습용 데이터
시드Seed. 합성 데이터의 출발점이 되는 실제 데이터
샘플러Sampler. 정해 둔 값 중 하나를 비율대로 뽑는 열. 다양성을 주입한다
DAG방향이 있고 순환이 없는 그래프. 열들이 어떤 순서로 서로를 참조하는지 나타낸다
Jinja파이썬 템플릿 문법. 프롬프트의 빈자리를 실행 때 값으로 채운다
미리보기 / 일괄 생성Preview는 3개만 만들어 확인하는 모드, Batch는 원하는 개수를 한 번에 만드는 모드
LLM 판정LLM-as-a-judge. 다른 모델에게 결과물의 품질을 점수 매기게 하는 것
MCPModel Context Protocol. 에이전트가 외부 도구에 연결하는 표준
Tavily에이전트용 웹 검색 서비스. Exa 같은 대안도 있다
궤적Trajectory. 에이전트가 질문부터 답까지 도구를 부르고 생각한 과정 전체의 기록
지식 마감일Knowledge cutoff. 모델 학습 데이터가 멈춘 시점. 그 뒤의 일은 모른다
BrowseComp여러 단계 검색이 필요한 어려운 질문으로 모델의 검색 능력을 재는 벤치마크
위키데이터Wikidata. 위키백과 항목들을 서로 연결한 구조화된 지식 그래프
홉Hop. 그래프에서 연결을 따라 한 칸 이동하는 것
SFTSupervised fine-tuning. 정답이 있는 예시로 모델을 사후 학습시키는 방법
증류Distillation. 큰 모델의 출력으로 작은 모델을 학습시키는 것
BIRD자연어를 SQL로 바꾸는 능력을 재는 벤치마크
StructEvalJSON, YAML, XML 같은 구조화 형식을 정확히 내놓는지 재는 벤치마크
페르소나Persona. 실제 인구 분포를 따르도록 만든 가상 인물 설명. 시드로 쓴다
PGMProbabilistic graphical model. 변수 사이의 확률 관계를 그래프로 나타낸 모델
