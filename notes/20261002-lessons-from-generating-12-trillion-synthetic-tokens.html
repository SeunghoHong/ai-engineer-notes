합성 데이터 12조 토큰을 만들며 배운 것

웹 데이터만으로는 모자라서, 좋은 문서를 골라 모델에게 다시 쓰게 하는 합성 데이터로 사전학습 데이터를 채운다. 12조 토큰 규모에서 발목을 잡은 것은 메타데이터, GPU 고장, CPU와 GPU 스케줄링, 추론 설정 같은 인프라 문제였다.

원본 영상: Lessons from Generating 12 Trillion Synthetic Tokens 발표: Bogdan Gaza (DatologyAI 공동 창업자, CEO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다(예: Theology는 DatologyAI, SERM은 Slurm). 확실하지 않은 이름에는 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 모델을 조금 더 좋게 만들려면 데이터가 몇 배씩 더 필요하다. 웹 텍스트는 약 30조 토큰으로 한정돼 있어서 합성 데이터로 채운다.
  2. DatologyAI의 방식은 새로 지어내지 않고 좋은 문서를 골라 다시 쓴다. 그냥 생성하라고 하면 모델이 이미 아는 흔한 패턴만 나온다.
  3. 발표자 회사 자료로는 BeyondWeb으로 학습한 3B 모델이 다른 데이터로 학습한 8B 모델과 맞먹는다. 같은 성능을 2.7~5.3배 적은 토큰으로 낸다.
  4. 연구용 Slurm 클러스터와 제품용 Kubernetes를 Kubernetes 하나로 합쳐 큐레이션, 합성, 학습, 평가를 한 흐름으로 묶었다.
  5. 첫 병목은 메타데이터였다. S3 요청을 1,000개씩 묶어 9~11일 걸릴 일을 2시간으로 줄였다.
  6. GPU는 반드시 고장 난다. 파티션을 작게 나누고 체크포인트를 남겨, 실패해도 조금만 다시 하면 되게 했다.
  7. 여러 클러스터에 걸친 작업은 CPU와 GPU를 한꺼번에 잡는다. vLLM 설정만 탐색해도 처리량이 약 40% 올랐다.
  8. 결과: 2024년 말 300억 토큰이 한계였던 생산량이 12조 토큰(웹 7조, 수학·코드 5조)으로 늘었다.
01

데이터 벽과 합성 데이터 00:20

스케일링 법칙 scaling laws은 모델 크기, 데이터, 연산량을 늘릴 때 성능이 어떻게 오르는지 정리한 경험 법칙이다. 발표자에 따르면 지금은 성능을 한 단계 올릴 때마다 연산량과 데이터가 기하급수로 더 드는 구간이다.

그래서 사전학습 pre-training 규모가 아주 커졌다. 최고 수준의 모델을 만들려면 데이터가 많이 필요하다. 그중 상당 부분은 웹에서 구할 수 없다.

발표자는 이 한계를 데이터 벽 data wall이라고 불렀다. 인터넷의 데이터는 한정돼 있으니 질 좋은 합성 데이터 synthetic data로 보충한다. 합성 데이터는 모델이 만들어 낸 학습용 데이터다.

이 노트에서 데이터 양은 토큰 token으로 센다. 토큰은 모델이 글을 읽는 단위로, 단어보다 조금 작은 조각이다.

이 발표에서 다루는 것 01:00
  • DatologyAI의 합성 데이터 레시피 BeyondWeb
  • 조 단위 토큰을 만들며 얻은 엔지니어링 교훈 네 가지
  • 최근 끝낸 약 12조 토큰 실행: 웹, 수학, 코드
02

DatologyAI와 BeyondWeb 01:40

DatologyAI는 데이터 큐레이션 data curation 회사다. 큐레이션은 큰 데이터에서 학습에 쓸 좋은 데이터를 골라 다듬는 일이다. 발표자는 회사를 사전학습과 중간학습 mid-training 데이터의 "정유소"에 비유했다.

고객은 스타트업과 대기업이다. 고객이 가진 데이터에서 가장 질 좋은 데이터를 먼저 고른다. 그다음 합성 데이터 레시피에 넣어 훨씬 큰 데이터셋을 만든다. 이 레시피의 이름이 BeyondWeb이다.

발표자가 보여 준 결과 02:30

비교 대상은 Nemotron-Synth, Cosmopedia, QA WRAP(추정), RedPajama 같은 공개 데이터셋이다. 각 데이터셋으로 1B, 3B, 8B 크기의 모델을 학습해 정확도를 쟀다. B는 파라미터 10억 개 단위다.

BeyondWeb은 발표자 회사의 제품이고, 이 결과도 회사가 직접 낸 것이다. 그 점을 감안해 읽자. 발표자는 이 결과가 2025년 늦여름에 공개한 것이고 지금은 훨씬 좋아졌다고 말했지만, 새 수치는 보여 주지 않았다.

03

지어내지 말고 다시 쓴다 04:00

BeyondWeb의 핵심은 다시 쓰기 rephrasing다. 고객 데이터에서 가장 질 좋은 문서를 찾는다. 그 문서를 여러 방식으로 다시 쓰거나 구조를 바꾼다.

왜 그냥 생성하지 않나 04:50 모델에게 "합성 데이터를 하나 만들어"라고만 하면, 모델이 학습한 데이터에서 가장 흔한 패턴만 다시 나온다. 발표자는 이를 분포의 모드 modes of the distribution만 배우게 된다고 표현했다. 그래서 실제 문서를 씨앗으로 쓴다.

다시 쓴 문서같은 내용, 다른 형식예시: 질문과 답, 요약, 강의 노트

위 형식은 이해를 돕기 위한 예시다. 발표에서는 구체적인 다시 쓰기 형식을 밝히지 않았다.

가장 단순한 구조 05:10

  1. 대상 데이터셋: 텍스트일 수도 있고, 이미지와 텍스트 쌍일 수도 있다.
  2. 프롬프트 묶음: 골라 둔 문서 앞에 붙인다.
  3. GPU 여러 대와 여러 모델: 실제로 합성 데이터를 만든다.

계산상으로는 얼마나 걸릴지 예상할 수 있다. 하지만 실제 처리량 throughput은 들쭉날쭉하다. 처리량은 단위 시간에 처리하는 양이다. GPU가 낼 수 있는 이상적인 처리량에 맞추기는 매우 어렵다. 다음 장부터는 이 간극을 어떻게 줄였는지 다룬다.

04

두 갈래 인프라를 하나로 05:50

출발점에서 합성 데이터는 제품에 들어가 있지 않았다. 연구팀이 Slurm 클러스터에서 따로 만들었다. Slurm은 연구용 GPU 클러스터에서 작업을 줄 세워 돌리는 스케줄러다.

제품 파이프라인은 Kubernetes 위에서 돌았다. Kubernetes는 여러 서버에 프로그램을 배치하고 관리하는 시스템이다. 연구팀과 제품팀은 코드베이스도 달랐다.

처음연구와 제품이 따로합성 데이터는 Slurm, 제품은 Kubernetes. 만든 데이터는 사람이 데이터 카탈로그에 손으로 다시 채웠다
→
지금모두 Kubernetes 위에서H100 클러스터도 Kubernetes로 관리한다. 사내 스케줄러가 클러스터를 오가며 작업을 배치한다

두 갈래 방식은 느리고 실수가 잦았다. 개발 속도도 막혔다. 무엇보다 GPU를 다 쓰지 못했다. GPU 수는 정해져 있으니, 학습과 합성 데이터 작업을 한 체계에서 돌려야 GPU를 꽉 채워 쓸 수 있다.

지금의 구성 07:40

핵심 부품은 Ray, Kubernetes, vLLM이다. Ray는 Python 작업을 여러 기계에 나눠 돌리는 프레임워크다. vLLM은 언어 모델 추론을 빠르게 돌리는 엔진이다. 데이터 처리에는 Spark도 쓴다. Spark는 대용량 데이터를 처리하는 엔진이다.

구성하는 일
제어 클러스터전체 작업을 지휘한다. 데이터 카탈로그 data catalog인 asset tracker도 여기 있다. 데이터 카탈로그는 어떤 데이터가 어디 있는지 기록한 목록이다
연산 클러스터Spark 작업과 Ray 작업을 돌린다. 필요할 때 빌리는 온디맨드 CPU를 쓰고, H100까지 필요 없는 GPU 작업도 여기서 한다
H100 클러스터AWS SageMaker HyperPod 위의 EKS로 관리한다. H100이 필요한 작업은 모두 여기로 보낸다
저장소모든 데이터는 S3에 둔다. S3 호환 API를 쓰는 저장소라면 어디든 된다

HyperPod는 대규모 GPU 클러스터를 운영하는 AWS 서비스다. EKS는 AWS가 관리해 주는 Kubernetes다. 이 조합으로 같은 네트워크에 묶인 H100 클러스터 여러 개를 Kubernetes로 다룬다.

모든 것을 Kubernetes에 올린 이유도 있다. DatologyAI의 파이프라인은 AWS, GCP, 고객의 자체 서버 등 여러 환경에 배포된다. Kubernetes 위라면 어디서든 같은 방식으로 돌릴 수 있다.

얻은 것 08:40 큐레이션, 합성 데이터 생성, 학습, 평가를 차례로 이어 한 워크플로로 돌린다. 연구 흐름과 엔지니어링 흐름이 같은 인프라, 같은 코드, 같은 경로를 쓴다. 발표자는 이제 실험을 늘 돌리고, 클러스터를 넘나드는 스케줄링이 더 빠르고 안정적이라고 했다.
05

교훈 1: 메타데이터가 먼저 막힌다 09:30

조 단위 토큰 규모에서 처음 막힌 곳은 GPU가 아니었다. 데이터가 어디에 얼마나 있는지 알려 주는 정보, 즉 메타데이터 metadata였다.

규모 감각 09:40

  • 웹에서 찾을 수 있는 텍스트는 약 30조 토큰이다.
  • 이미지는 DataComp 같은 곳에 이미지와 텍스트 쌍이 약 128억 개 있다.
  • 텍스트는 보통 FineWeb 같은 공개 고품질 데이터셋을 모아 시작한다. 함께 언급된 이름은 자막에서 "dcmotron"으로 들렸다. DCLM이나 Nemotron-CC로 추정된다.

무엇이 막혔나 10:10

이 정도 데이터는 Parquet 같은 형식으로 저장된다. Parquet은 열 단위로 저장하는 데이터 파일 형식이다. 데이터는 수백만 개의 파티션 partition으로 나뉜다. 파티션은 큰 데이터를 나눠 담은 조각 파일이다.

이 파티션 정보를 S3에서 빠르게 다 가져오려 하면 요청 제한 throttling에 걸린다. S3는 AWS의 파일 저장소다. 요청 제한은 요청이 너무 많을 때 저장소가 속도를 강제로 늦추는 것이다.

Ray에서는 Ray head가 이 메타데이터를 관리한다. Ray head는 Ray 클러스터 전체를 지휘하는 노드다. 이 지점이 병목이 된다.

최악의 결과: 노는 GPU 메타데이터를 기다리는 동안 GPU는 아무 일도 하지 않는다. 발표자는 이런 작업이면 연산 비용이 수백만 달러 규모라고 했다. 그 GPU를 11일 동안 세워 둘 수는 없다.

어림 계산과 해결 11:10

요청 하나는 약 10ms 걸린다. 처음 가져오는 메타데이터 요청은 이보다 비싸다. 여기에 요청 제한까지 걸린다. 어림 계산을 해 보니 조 단위 토큰의 메타데이터를 채우는 데만 9~11일이 걸렸다.

해결책은 요청을 묶는 것이었다. S3 API는 객체 여러 개의 정보를 한 번의 목록 요청으로 돌려준다. 한 번에 받는 개수, 즉 페이지 크기를 S3가 허용하는 최대치인 약 1,000개까지 키웠다. 그러자 API 처리 시간이 약 2시간으로 줄었다.

첫 번째 교훈 메타데이터를 어떻게 관리할지부터 정한다. S3 버킷의 상태를 합성 데이터 시스템으로 어떻게 불러올지 미리 설계해야 한다. 이게 안 되면 큰 규모에서는 시작조차 못 한다.
06

교훈 2: GPU는 반드시 고장 난다 12:30

큰 규모로 돌리면 고장 난 GPU를 반드시 만난다. 머신이 꺼지기도 하고, GPU 자체가 불량이기도 하다. 규모가 크면 일어날 수 있는 일은 다 일어난다. 그 결과는 이렇다.

  • 진행한 작업을 잃는다.
  • 연산을 낭비한다.
  • 파일 절반만 처리된 불완전한 출력이 남는다.
  • 클러스터 시간이 더 필요해진다. GPU 시간은 늘 구하기 어렵다.

파이프라인 구조 13:00

DatologyAI의 파이프라인은 두 단계다. 먼저 Spark 작업이 다시 쓸 문서와 프롬프트를 이어 붙여 내보낸다. 다음으로 Ray 작업이 GPU로 실제 다시 쓰기를 한다. 입력 파티션 하나가 출력 하나로 이어지는 1:1 구조다.

큰 파티션의 위험 13:30

파티션이 크면 한 노드가 파티션 하나를 다시 쓰는 데 8시간이 걸릴 수 있다. 그 8시간 중 마지막 5분에 머신이 죽으면 거의 8시간을 날린다. 대응은 두 가지다.

방법 1 · 체크포인트 checkpoint

작업 중간중간 멈추고 지금까지의 결과를 S3에 저장한다. 머신이 죽으면 마지막 저장 지점부터 이어 간다.

방법 2 · 작은 파티션

파티션을 잃어도 괜찮을 만큼 작게 나눈다. 머신이 죽으면 그 작은 조각만 다시 한다.

DatologyAI는 둘 다 했다. 파티션 크기를 알맞게 줄이고 체크포인트도 남긴다. 이제 작업이 실패하면 다시 시도되고, 잃는 시간은 아주 적다. 며칠짜리 작업이 통째로 실패하던 상황이 복구할 수 있는 재시도로 바뀌었다.

예시 계산 8시간짜리 작업이 7시간 55분째에 죽었다고 하자. 체크포인트가 없으면 7시간 55분을 모두 잃는다. 30분마다 체크포인트를 남겼다면 잃는 시간은 25분이다. 숫자는 이해를 돕기 위해 만든 예시다.

필요한 세 가지 14:40

성질뜻
이어서 실행resumable execution 멈춘 곳부터 다시 시작할 수 있다
멱등성idempotency 같은 작업을 다시 해도 결과가 같다. 다시 실행할 때 체크포인트 파일을 덮어써도 문제가 없다

07

교훈 3: CPU와 GPU를 함께 잡는다 14:50

큐레이션 파이프라인은 한곳에서 돈다. 반면 고객의 합성 데이터 작업은 전 세계 여러 GPU 위치에서 돈다. GPU를 한곳에서 많이 구하기는 어렵기 때문이다.

합성 데이터 생성은 GPU 노드끼리 빠른 네트워크가 꼭 필요하지 않다. 그래서 여러 클러스터에 흩어진 GPU를 함께 쓴다. 여러 클러스터에 작업을 배치하고 순서를 지휘하는 일을 오케스트레이션 orchestration이라 한다.

무엇이 막히나 15:30

한 Ray 작업이 CPU 자원은 잡았는데 GPU 풀에서 GPU는 못 잡을 수 있다. 다음 작업은 반대로 GPU는 있는데 CPU가 없다. 서로 반쪽씩만 쥐고 기다리니 아무것도 돌지 않는다.

예시작업 A작업 B
잡은 자원CPUGPU
기다리는 자원GPUCPU
결과멈춤멈춤

발표자는 이를 결국 빈 패킹 bin packing 문제라고 했다. 크기가 다른 짐을 정해진 상자들에 빈틈없이 나눠 담는 문제다. 여기서 짐은 작업이고 상자는 CPU와 GPU 자원이다.

해결 16:30

  1. 자원 종류별로 전용 풀을 둔다. Spark용 CPU 풀이 따로, Ray head용 풀이 따로 있다.
  2. CPU 요구와 GPU 요구를 나눠 관리한다.
  3. 한 Ray 작업의 head와 worker는 원자적으로 잡는다. 원자적 atomic은 필요한 자원을 한꺼번에 다 잡거나, 못 잡으면 아무것도 잡지 않는다는 뜻이다.

이렇게 하자 앞의 막힘이 사라지고 작업 규모가 예상대로 늘어났다.

세 번째 교훈 여러 공급자, 여러 클라우드에서 돌린다는 전제로 설계한다. 같은 작업에 필요한 CPU와 GPU는 함께 스케줄링한다.
08

교훈 4: 추론 설정을 탐색한다 17:50

vLLM이나 SGLang을 쓸 때는 하이퍼파라미터를 신경 써야 한다. 둘 다 언어 모델 추론 엔진이다. 하이퍼파라미터는 엔진이 일하는 방식을 정하는 설정값이다.

발표자는 여기에 규율이 필요하다고 했다. 벤치마크를 하고, 최적화하고, vLLM 설정만 따로 재는 하네스 harness를 둔다. 하네스는 같은 조건으로 실험을 반복해 돌리는 실행 틀이다.

설정만 바꿔 처리량 약 40% 향상 발표자가 말한 수치다. vLLM과 SGLang의 실행 옵션(플래그)만 조정해서 얻은 결과다.

DatologyAI는 지금 vLLM을 쓰고 SGLang도 시험하고 있다. 이들의 작업은 대부분 배치 추론 batch inference이다. 쌓아 둔 입력을 한꺼번에 처리하는 방식이다. 사용자 요청에 바로 답하는 온라인 추론과는 많이 다르다.

맞춰야 할 것은 배치 크기, 추측 디코딩 speculative decoding 설정 등이다. 추측 디코딩은 가벼운 방법으로 다음 토큰 여러 개를 먼저 추측하고, 큰 모델이 한꺼번에 확인해 속도를 높이는 기법이다.

이 값들을 격자 탐색 grid search하면 처리량이 크게 오른다. 격자 탐색은 후보 값의 모든 조합을 하나씩 돌려 보는 방법이다.

예시: vLLM 설정정하는 것
--max-num-seqs한 번에 함께 처리하는 요청 수
--max-num-batched-tokens한 단계에서 처리하는 토큰 수의 상한
--gpu-memory-utilizationGPU 메모리를 얼마나 쓸지
--speculative-config추측 디코딩 방식과 한 번에 추측할 토큰 수

발표에 나온 설정 이름이 아니다. vLLM을 쓴다면 이런 값부터 탐색해 볼 수 있다는 예시다. 이름은 vLLM 버전에 따라 다를 수 있다.

09

결과: 300억에서 12조로 18:50

발표자는 네 가지 교훈을 이렇게 정리했다.

  1. 돌리는 규모를 먼저 생각한다. 메타데이터부터 막힌다.
  2. 작업이 죽어도 자동으로 복구되는 체계를 둔다.
  3. CPU와 GPU 자원을 원자적으로 함께 잡는다.
  4. vLLM 설정을 탐색한다.

무엇이 바뀌었나 19:10

2024년 말에는 Slurm 클러스터에서 제한적으로 돌려 합성 토큰 약 300억 개를 만드는 게 한계였다. 그 뒤 합성 데이터 수요가 크게 늘었다. 이 인프라로 여러 고객을 위해 웹 약 7조, 수학과 코드 약 5조, 합계 약 12조 토큰을 만들었다.

참고로 계산해 보면, 12조 토큰은 발표자가 말한 웹 텍스트 총량(약 30조 토큰)의 40% 정도다.

앞으로 19:30

더 나은 합성 레시피를 찾는 어블레이션 ablation 실험을 계속하고 있고, 결과를 더 공개할 예정이라고 했다. 어블레이션은 구성 요소를 하나씩 빼거나 바꿔 보며 효과를 재는 실험이다.

발표자는 도메인 범위도 중요하다고 덧붙였다. 웹, 다국어, 수학, 코드, 법률 데이터에서 방법이 어떻게 달라지는지는 이번 발표에서 다루지 않았다.

12조 토큰 실행도 회사가 직접 밝힌 수치다. 발표는 채용 공고로 끝났다.

10

핵심 정리

  1. 모델을 조금 더 좋게 하려면 데이터가 훨씬 많이 필요하다. 웹 텍스트(약 30조 토큰)만으로는 모자라 합성 데이터로 채운다.
  2. 좋은 합성 데이터는 지어내지 않고 좋은 문서를 골라 다시 쓴다. 그냥 생성하면 모델이 아는 흔한 패턴만 나온다.
  3. 발표자 회사 자료로는 BeyondWeb이 같은 성능을 2.7~5.3배 적은 토큰으로 내고, 3B 모델이 8B 모델과 맞먹는다.
  4. 연구용 클러스터와 제품 파이프라인을 같은 Kubernetes 위로 합쳐야 GPU를 놀리지 않고 실험을 빨리 돌린다.
  5. 조 단위 규모의 첫 병목은 메타데이터다. S3 요청을 묶어 9~11일을 2시간으로 줄였다.
  6. 가장 나쁜 결과는 GPU가 노는 것이다. 데이터 준비가 늦으면 비싼 GPU가 기다린다.
  7. GPU는 반드시 고장 난다. 작은 파티션과 체크포인트로 잃는 시간을 줄인다.
  8. 재시도가 안전하려면 멱등성이 필요하다. 같은 작업을 다시 해도 결과가 같아야 한다.
  9. 여러 클러스터에 걸친 작업은 CPU와 GPU를 한꺼번에 잡는다. 한쪽만 잡으면 서로 막힌다.
  10. 추론 엔진 설정 탐색만으로 처리량이 약 40% 오른다. 이 인프라로 생산량이 300억에서 12조 토큰으로 늘었다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 합성 데이터가 필요하다고 보는 이유는?
스케일링 법칙상 성능을 한 단계 올리려면 데이터가 기하급수로 더 필요하다. 그런데 웹에서 찾을 수 있는 텍스트는 약 30조 토큰으로 한정돼 있다.
Q2모델에게 그냥 "합성 데이터를 만들어"라고 하면 무엇이 문제인가?
모델이 학습한 데이터에서 가장 흔한 패턴(분포의 모드)만 다시 나온다. 그래서 실제 좋은 문서를 씨앗으로 골라 다시 쓰게 한다.
Q3BeyondWeb에 대해 발표자가 보여 준 두 결과는? 읽을 때 감안할 점은?
BeyondWeb으로 학습한 3B 모델이 Nemotron-Synth로 학습한 8B 모델과 맞먹는다. 같은 성능을 Nemotron-Synth보다 2.7배, Cosmopedia보다 5.3배 적은 토큰으로 낸다. 둘 다 발표자 회사가 직접 낸 결과다.
Q4처음 인프라에서 연구와 제품이 따로 놀아 생긴 문제는?
합성 데이터는 Slurm, 제품은 Kubernetes에서 돌았고 코드베이스도 달랐다. 만든 데이터를 카탈로그에 손으로 채워야 했다. 느리고 실수가 잦았으며 GPU를 다 쓰지 못했다.
Q5모든 작업을 Kubernetes로 옮긴 이유 두 가지는?
파이프라인이 AWS, GCP, 자체 서버 등 어떤 환경에도 배포돼야 한다. 그리고 큐레이션, 합성, 학습, 평가를 한 워크플로로 묶어 GPU를 꽉 채워 쓰기 위해서다.
Q6메타데이터를 채우는 데 9~11일이 걸린 원인과, 2시간으로 줄인 방법은?
수백만 개 파티션의 정보를 하나씩 요청했고 요청 제한까지 걸렸다. S3 목록 요청의 페이지 크기를 최대치(약 1,000개)까지 키워 요청을 묶었다. 이게 늦으면 비싼 GPU가 놀며 기다린다.
Q7파티션이 크면 GPU 고장 때 무엇을 잃나? DatologyAI는 어떻게 대응했나?
8시간짜리 작업이 마지막 5분에 죽으면 거의 8시간을 잃는다. 파티션 크기를 알맞게 줄이고 체크포인트도 남기는, 두 방법을 함께 썼다.
Q8체크포인트로 이어서 실행할 때 멱등성이 왜 필요한가?
재시도하면 같은 작업이 다시 돈다. 같은 파일을 덮어써도 결과가 같아야 중복되거나 깨진 출력 없이 이어 갈 수 있다.
Q9여러 클러스터에 작업을 배치할 때 생기는 막힘은?
한 작업은 CPU만 잡고 GPU를 기다리고, 다른 작업은 GPU만 잡고 CPU를 기다린다. 서로 반쪽씩만 쥐고 있어 아무것도 돌지 않는다.
Q10그 막힘을 어떻게 풀었나?
자원 종류별로 전용 풀을 두고, 한 Ray 작업의 head와 worker를 원자적으로 잡았다. 필요한 CPU와 GPU를 한꺼번에 다 잡거나 아예 잡지 않는다.
Q11vLLM 설정 탐색으로 얻은 것과, 맞춰야 할 설정은?
처리량이 약 40% 올랐다. 배치 크기, 추측 디코딩 설정 등을 격자 탐색했다. 배치 추론은 온라인 추론과 다르게 맞춰야 한다.
Q12합성 토큰 생산량은 얼마에서 얼마로 늘었나?
2024년 말 약 300억 토큰에서, 최근 실행의 약 12조 토큰(웹 7조, 수학·코드 5조)으로 늘었다. 약 400배다.
