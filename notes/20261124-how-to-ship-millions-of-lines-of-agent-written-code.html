에이전트가 쓴 수백만 줄을 믿고 내보내는 법

Jarred Sumner는 Claude Code를 가볍고 빠르게 만들려고, JavaScript를 미리 컴파일하는 컴파일러를 Bun에 넣었다. 에이전트가 쓴 수백만 줄을 믿고 내보낼 수 있었던 건, 만드는 방법을 검증하는 방법에 맞춰 골랐기 때문이다.

원본 영상: How to Ship Millions of Lines of Agent-Written Code 발표: Jarred Sumner (Bun 제작자, Anthropic)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았다(Cloud Code → Claude Code, V8 Zilly → Fuzzilli). 확실하지 않은 이름에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 목표는 Claude Code의 메모리와 속도였다. 답은 Rust로 다시 쓰기가 아니라 Bun에 넣은 AOT 컴파일러였다. 메모리는 약 4분의 1, 시작은 약 2배 빨라졌다.
  2. Rust로 옮기지 않은 이유는 테스트다. Claude Code는 코드와 테스트가 같은 언어라, 옮기려면 테스트까지 다시 써야 한다. 다시 쓴 테스트는 믿을 수 없다.
  3. 핵심 원칙: 어떻게 만들지는 어떻게 검증할지가 정한다. 심판은 프로젝트 이전부터 있던 테스트다. 에이전트가 건드렸을 리 없기 때문이다.
  4. 같은 코드를 JIT, AOT, 타입 제거 세 방식으로 돌려 결과를 맞춰 본다. Claude가 만든 코드 생성기로 대량 퍼징한다. 테스트가 정말 버그를 잡는지도 확인한다.
  5. 한 달 남짓 동안 다섯 번 다시 썼다. 1GB 메모리, 엉성한 코드, 50초 컴파일을 하나씩 넘었다. 출시 전 큰 프로젝트는 고치기보다 다시 쓰기가 쉽다.
  6. 작업 리듬: 몰아 쓸 때는 빌드를 한 번만 한다. 고칠 때는 오래 사는 서브에이전트 여럿에게 맡긴다. 매시간 점수표로 다시 잰다.
  7. 사람이 하는 일은 "계속해"와 유도 질문이다. 모델은 규칙을 지어내고 자기 능력을 낮춰 잡는다. 그래서 더 크게 해 보라고 계속 밀어줘야 한다.
01

"Claude Code를 더 가볍고 빠르게" 01:20

Bun은 JavaScript 런타임runtime이다. Claude Code가 이 위에서 돈다. Bun은 내부에서 WebKit의 JavaScript 엔진인 JavaScriptCore를 쓴다.

출발점은 Claude에게 준 프롬프트 하나였다. Claude Code가 메모리를 훨씬 덜 쓰고 더 빨라져야 한다는 것이다. 고칠 대상은 WebKit이든 Bun이든 상관없다고 했다.

그 답이 Bun에 넣은 미리 컴파일하는 컴파일러ahead-of-time compiler, AOT다. 발표자는 이 작업을 수백만 줄짜리 PR로 머지했다. 여름에 Bun을 Rust로 다시 쓴 일보다 더 큰 프로젝트라고 한다.

JIT · 지금까지실행하면서 그때그때 컴파일한다앱을 켤 때마다 컴파일 비용을 실행 중에 낸다
→
AOT · 이번 프로젝트실행 전에 미리 컴파일한다실행 중에는 컴파일 비용을 내지 않는다

왜 컴파일이 문제인가 02:50

  • 발표자에 따르면 보통 JavaScript 앱은 CPU 시간의 절반쯤을 필요할 때마다 코드를 컴파일하는 데 쓴다.
  • JavaScript 앱을 Rust나 Go로 다시 쓰는 곳이 많은 이유도 여기 있다. JIT 비용과 단일 스레드라는 한계가 겹친다.
  • Claude Code에서는 이 비용이 더 크다. 발표자는 Claude Code를 iOS 앱에서 쓰는 경우를 예로 들었다. 세션마다 컴파일까지 하면 CPU 시간이 많이 든다.
02

Rust로 다시 쓰지 않은 이유 03:50

팀은 Claude Code를 Rust로 다시 쓰는 안을 많이 논의했다. Bun 팀은 Bun을 Rust로 옮겨 본 경험이 있어서 다시 쓰기에는 자신이 있었다. 그래도 하지 않았다. 이유는 테스트다.

Bun · Zig → Rust 04:20
  • 구현: Zig에서 Rust로 바꾼다
  • 테스트: TypeScript로 쓰여 있다
  • 같은 테스트를 Zig 판과 Rust 판에 그대로 돌릴 수 있다

테스트가 심판으로 남는다. 그래서 쉬운 다시 쓰기였다.

Claude Code · TypeScript → Rust (검토만) 04:40
  • 구현: TypeScript로 쓰여 있다
  • 테스트: 역시 TypeScript로 쓰여 있다
  • 구현을 옮기면 테스트도 옮겨야 한다

테스트를 다시 쓰는 순간, 그 테스트를 믿을 수 없다. 위험이 너무 컸다.

원칙: 테스트는 바꾸는 대상과 떨어져 있어야 한다 구현과 테스트를 함께 바꾸면, 새 구현이 맞는지 판단할 기준이 사라진다. 그래서 질문을 바꿨다. "Rust로 다시 쓰지 않아도 되게, JavaScript 자체를 빠르게 만들면 어떨까?" 05:00
함께 읽기: 같은 시리즈 "코드 리뷰는 정말 죽었나" 노트 그 노트에서 Laurie Voss는 Bun의 Rust 포팅을 다른 각도로 본다. 기존 테스트는 99.8% 통과했지만 unsafe 블록이 13,044개 남았다고 지적했다. 독립된 테스트는 동작을 지켜 주지만 코드 품질까지 보증하지는 않는다. 이 발표의 2번째 판 이야기(07장)도 같은 교훈을 준다.
03

메모리 4분의 1, 시작 2배 05:20

AOT 컴파일러로 빌드한 Claude Code의 결과다. 발표 시점에는 Anthropic 내부에서 먼저 쓰는 중dogfooding이었다. 외부 공개도 곧 한다고 했다.

TypeScript 7과의 비교 05:50

  • 발표자에 따르면 TypeScript 팀은 TypeScript 7에서 컴파일러를 Go로 다시 썼다.
  • 기존 JavaScript판 TypeScript를 Bun compile로 컴파일하면, 단일 스레드 기준으로 Go 포팅판보다 빠르다고 한다.
  • AOT로 컴파일한 쪽에는 아직 멀티스레드가 없다. 이를 더하는 PR이 따로 있다.

발표자는 Bun을 만든 사람이고 Anthropic에서 일한다. Bun과 Claude Code의 성능 주장은 자기 회사 제품에 대한 것이니, 그 점을 감안해 읽자.

04

타입은 믿지 않고 예측으로 쓴다 06:30

TypeScript의 타입은 틀려도 프로그램이 돈다. 타입 표기가 실제 값과 다를 수 있다는 뜻이다.

그래서 이 컴파일러는 타입을 사실로 믿지 않는다. "아마 이 타입일 것"이라는 예측prediction으로 쓴다.

발표자는 이런 문제가 모델에게 잘 맞는다고 본다. 모델이 컴파일러를 아주 잘 쓰기 때문이라고 한다.

컴파일러가 코드를 만드는 방식 16:10

상황만드는 코드
값의 타입이 늘 같다고 확실히 증명할 수 있다 (모노모픽monomorphic)객체의 필드를 바로 읽는 코드. 빠르다
증명할 수 없다매번 타입을 확인하는 코드. 인라인 캐싱inline caching을 조금 쓰지만 많지는 않다
05

어떻게 검증할지가 어떻게 만들지를 정한다 07:00

어떤 방식으로 만들지는 전적으로, 그 코드가 정말 동작하고 버그가 없다고 어떻게 확인할지에 달려 있다.발표자의 말을 옮김 · 02:20

AOT 컴파일러는 검증하기 좋은 문제다. 돌릴 수 있는 테스트가 이미 아주 많다. 팀이 새로 쓴 테스트도 많지만, 핵심은 프로젝트 이전부터 있던 테스트다.

테스트 묶음설명
Bun 기존 테스트Bun을 Rust로 옮길 때도 심판으로 쓴 테스트
WebKit 테스트Bun이 쓰는 JavaScript 엔진 쪽 테스트
test262JavaScript 표준을 제대로 구현했는지 보는 테스트 모음
Cloudflare Code 테스트 (추정)자막에 "Cloudflare Codes tests"로 들린다. 정확한 이름은 확실하지 않다
Bun 테스트 러너Bun의 테스트 러너 자체를 AOT 모드로 돌릴 수 있게 했다

이전부터 있던 테스트가 중요한 이유는 단순하다. 에이전트가 건드렸을 리 없다. 17:10

실패하는 테스트도 일부 있다. AOT 컴파일러에는 호환을 깨는 변경breaking change이 두 가지 있고, 남은 실패는 대부분 이 때문이다. 두 변경은 주로 프로토타입 오염prototype pollution 공격을 막는 보안 조치다. 성능에도 도움이 된다.

세 방식으로 돌려 결과를 맞춰 본다 08:10

  1. JIT로 실행한다.
  2. AOT로 컴파일해서 실행한다.
  3. 타입을 지우고 실행한다.

세 결과가 같으면, 적어도 그 입력에서는 맞게 동작한다. 여러 구현의 결과를 맞춰 보는 이런 방식을 흔히 차등 테스트differential testing라고 부른다.

이 틀은 퍼징fuzzing으로 키우기 좋다. Claude에게 여러 코드 패턴을 만들어 내는 코드 생성기를 잔뜩 쓰게 한다. 생성된 코드를 세 방식으로 돌려 결과를 비교한다. 이 방법으로 버그를 많이 잡았다.

V8 팀이 쓰는 JavaScript 엔진 퍼저 Fuzzilli도 썼다. 17:30 Bun은 이미 Fuzzilli를 쓰고 있었다. 이번에는 TypeScript 타입까지 시험하도록 확장했다.

테스트가 정말 잡는지 확인한다 17:50 퍼저가 버그를 찾고 있다고 착각하기 쉽다. 실제로는 아무것도 못 찾고 있을 수 있다. 테스트 자체가 버그를 잡아내는지 따로 확인해야 한다.
06

몰아 쓰고, 그다음 고친다 08:50

발표자가 지금까지 한 일 중 코드 양이 가장 많은 프로젝트다. 대부분은 테스트 코드다. 다섯 번 다시 쓴 탓도 있다.

1단계 · 몰아 쓰기많은 코드를 한꺼번에 쓴다빌드는 한 번만 한다. 매번 빌드하면 컴파일과 빌드 에러를 기다리느라 시간을 다 쓴다.
→
2단계 · 고치기 10:00전부 고치고 확인한다컴파일되는지, 테스트를 통과하는지, 정말 동작하는지 본다. 개별 에이전트를 많이 띄워 오래 돌린다.

워크플로 대신 오래 사는 서브에이전트 15:20

Bun 런타임 작업 때는 Claude Code 워크플로workflows에 많이 기댔다. 최근 모델로는 주로 오래 사는 서브에이전트long-lived subagents를 쓴다. 처음에 몰아 쓰는 단계만 예외다.

오래 사는 서브에이전트는 관련 코드의 맥락을 컨텍스트 창에 계속 쥐고 있다. 그래서 낭비가 적다. 멈추지 않고 계속 일할 수 있다.

07

한 달 남짓, 다섯 번 다시 썼다 10:10

프로젝트는 한 달이 조금 넘게 걸렸다. 그동안 컴파일러를 다섯 번 다시 썼다. 판마다 문제를 하나씩 발견했다.

판한 일결과
1번째JavaScriptCore의 기존 코드를 최대한 재사용했다Claude Code가 메모리를 1GB 썼다. 성능 상한이 기존 코드 수준에 묶였다
2번째 10:50Bun 안에 TypeScript 타입 검사기(Bun Check)를 넣고, Claude에게 그걸 쓰게 했다시작 2배 빠름, 메모리 약 3분의 1. 하지만 코드가 엉성했다(slop)
3번째 12:20에이전트 140개를 동시에 띄워 코드를 한꺼번에 쓰고, Claude Code를 돌려 봤다전체를 빨리 뽑아내려는 시도였다. 결과는 발표에서 따로 말하지 않았다
4번째 12:50코드 품질이 좋았다. 성능은 전과 비슷했다Claude Code 컴파일에 50초. 코드가 90만 줄로 너무 컸다. 출시 직전에 접었다
5번째 14:10코드가 좋다. 빌드가 20초 미만이다출시할 만하다. 발표 다음 주 출시 예정
2번째 판이 엉성했던 예 11:20 이 판의 컴파일러는 어떤 객체든 archive라는 속성을 읽으면 Bun.archive API를 쓸 수도 있다고 가정했다. 이름만 보고 짐작하는 규칙이다. 성능 숫자는 좋았지만, 발표자는 코드를 보고 "이건 출시할 수 없다"고 판단했다.

4번째 판을 접은 이유 13:00

JavaScript 개발자는 컴파일을 기다리는 데 익숙하지 않다. Claude Code는 큰 코드베이스라 50초가 걸렸다. 다른 프로젝트도 몇 초씩 걸린다는 뜻이다. 사람들은 그만큼 기다리려 하지 않는다.

판을 거치며 얻은 교훈

마크다운 문서 1,500개 11:50 큰 계획을 세우며 설계 문서를 쓰게 하면, 모델은 마크다운 문서를 끝없이 만든다. 1,500개는 누구도 읽을 수 없는 양이다.
측정으로 스스로를 설득한다 13:40 Claude는 일을 시작하기 전에 해 볼 가치가 있는지 가늠한다. 그런데 측정이 틀렸어도 맞다고 믿기 쉽다. 발표자가 "이 아이디어 해 봐"라고 하면, Claude가 효과를 가늠하다 스스로 접는 일이 많았다. 14:40 발표자는 이렇게 접힌 아이디어 중 다시 시도할 것이 많다고 본다.
08

매시간 점수표 16:30

이 정도 규모면 무슨 일이 일어나는지 따라가기 어렵다. 그래서 에이전트가 매시간 업데이트를 올리게 했다.

  • 업데이트에는 우선순위를 둔 지표들을 비교한 점수표scorecard가 들어간다.
  • Slack에는 이전 버전과 이번 버전을 나란히 올렸다. 숫자가 올랐는지 내렸는지 바로 보인다.
계속 다시 재지 않으면 나빠진다 21:20 발표자는 결론에서도 이 점을 강조했다. 진행되는 일이 너무 많아서, 다시 재지 않으면 무엇이 나빠지는지 놓치기 쉽다.
09

대부분 빠르지만, 늘 그런 건 아니다 18:00

발표자가 보여 준 벤치마크에서 AOT 컴파일은 대부분의 프로젝트에서 JIT보다 빨랐다. 늘 그렇지는 않다.

예외 · UglifyJS 18:20

인터프리터interpreter를 많이 써야 하는 코드는 빨라지지 않는다. eval이나 new Function으로 실행 중에 코드를 만드는 경우다.

대부분의 앱은 이렇게 하지 않는다.

금지 · Object.prototype 18:50

컴파일러는 Object.prototype에 속성을 붙이는 것을 금지한다. 프로토타입 오염 공격이 주로 이 방식을 쓴다.

드문 경우지만 호환을 깨는 변경이다.

발표자는 AOT 컴파일이 "한 줄로 앱을 빠르게 만드는 것"에 가장 가깝다고 말했다. 다만 위 예외처럼 100% 그렇지는 않다고 직접 덧붙였다.

JetStream 3 20:20

JetStream 3는 JavaScript 엔진들이 주로 쓰는 벤치마크다. 발표자에 따르면 Bun AOT는 대부분의 항목에서 JavaScriptCore의 JIT와 Node.js(V8 JIT)보다 빨랐다. 발표에서 구체적인 수치는 말하지 않았다.

개발 내내 Bun compile로 컴파일한 Claude Code를 써서 Bun compile 자체를 만들었다. 20:50

벤치마크 결과도 발표자 회사 제품에 대한 주장이다. 원 자료를 확인하지 않았으니 그 점을 감안해 읽자.

결론과 지금 해 볼 것 21:00

  • Claude와 큰 프로젝트를 할 때는 테스트할 수 있느냐가 가장 중요하다. 테스트가 정말 무언가를 시험하는지도 확인한다.
  • 계속 다시 잰다. 일이 너무 많아서, 재지 않으면 나빠지는 것을 놓친다.
  • 아직 출시하지 않은 큰 프로젝트는 고치기refactor보다 다시 쓰기rewrite가 쉽다.
  • 야심 차게 움직이지 않으면 모델은 10% 개선 대신 0.1% 개선을 낸다. "더 해 볼 수 있다"고 계속 밀어줘야 한다.
지금 해 보기 22:00 Bun이 깔려 있다면 bun upgrade --canary로 카나리 버전을 받는다. 그다음 Bun compile을 쓰면 된다고 했다. 발표자는 명령을 "bun compile"이라고만 말했다. 정확한 사용법은 Bun 문서에서 확인한다.

핵심 정리

  1. 목표는 Claude Code의 메모리와 속도였다. 답은 Rust 재작성이 아니라 Bun의 AOT 컴파일러였다.
  2. 발표자 인용에 따르면 JavaScript 앱은 CPU 시간의 절반쯤을 실행 중 컴파일에 쓴다. AOT는 이 비용을 실행 전으로 옮긴다.
  3. Claude Code를 Rust로 옮기지 않은 이유는 테스트다. 구현과 같은 언어인 테스트를 옮기면 그 테스트를 믿을 수 없다.
  4. 결과는 메모리 약 4분의 1, 시작 약 2배 빠름이다.
  5. 컴파일러는 TypeScript 타입을 예측으로 쓴다. 증명되면 필드를 바로 읽고, 아니면 매번 확인한다.
  6. 프로젝트 이전부터 있던 테스트만 심판으로 믿는다. 에이전트가 건드릴 수 없기 때문이다.
  7. JIT, AOT, 타입 제거 세 방식의 결과를 비교하고, Claude가 만든 생성기로 퍼징한다. 테스트가 정말 잡는지도 확인한다.
  8. 몰아 쓸 때는 빌드를 한 번만 한다. 고칠 때는 오래 사는 서브에이전트 여럿을 쓴다. 매시간 점수표로 다시 잰다.
  9. 다섯 번 다시 썼다. 1GB 메모리, 엉성한 코드, 50초 컴파일을 넘었다. 출시 전 큰 프로젝트는 다시 쓰기가 고치기보다 쉽다.
  10. 모델은 규칙을 지어내고 능력을 낮춰 잡는다. 사람은 질문하고, 더 크게 해 보라고 밀어붙인다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1첫 프롬프트의 목표와, 손대도 된다고 한 범위는?
Claude Code가 메모리를 훨씬 덜 쓰고 더 빨라지게 하는 것. WebKit이나 Bun 중 어느 쪽을 고쳐도 된다고 했다.
Q2JIT와 AOT의 차이는?
JIT는 실행하면서 그때그때 컴파일한다. AOT는 실행 전에 미리 컴파일한다. 그래서 AOT는 실행 중 컴파일 비용이 없다.
Q3Bun은 Rust로 다시 쓸 수 있었는데, Claude Code는 왜 하지 않았나?
Bun은 테스트가 TypeScript라 Zig 판과 Rust 판에 같은 테스트를 돌릴 수 있었다. Claude Code는 코드와 테스트가 모두 TypeScript라 테스트까지 옮겨야 한다. 다시 쓴 테스트는 믿을 수 없다.
Q4AOT로 빌드한 Claude Code의 결과 수치는?
메모리는 약 4배 덜 쓰고(약 4분의 1), 시작은 약 2배 빠르다. 발표 시점에는 내부에서 먼저 쓰는 중이었다.
Q5컴파일러는 TypeScript 타입을 어떻게 다루나? 왜 그런가?
타입을 사실이 아니라 예측으로 쓴다. TypeScript 타입은 틀려도 프로그램이 돌기 때문이다. 타입이 같다고 증명되면 필드를 바로 읽고, 아니면 매번 확인한다.
Q6프로젝트 이전부터 있던 테스트가 특히 중요한 이유는?
에이전트가 건드렸을 리 없기 때문이다. 그래서 에이전트가 쓴 코드를 판정하는 심판으로 믿을 수 있다.
Q7결과를 맞춰 보는 세 가지 실행 방식은? 어떻게 키웠나?
JIT 실행, AOT 컴파일 실행, 타입을 지운 실행. 세 결과가 같으면 그 입력에서는 맞다. Claude가 쓴 코드 생성기와 Fuzzilli로 입력을 대량으로 만들어 퍼징했다.
Q8몰아 쓰는 단계에서 빌드를 한 번만 하는 이유는?
매번 빌드하면 컴파일과 빌드 에러를 기다리느라 시간을 다 쓴다. 고치는 단계는 코드를 다 쓴 뒤에 따로 한다.
Q92번째 판은 성능이 좋았는데 왜 버렸나?
코드가 엉성했다. 예를 들어 어떤 객체든 archive 속성을 읽으면 Bun.archive API를 쓸 수도 있다고 가정했다. 발표자가 코드를 보고 출시할 수 없다고 판단했다.
Q104번째 판을 접은 이유는?
Claude Code 컴파일에 50초가 걸렸다. JavaScript 개발자는 컴파일을 기다리지 않는다. 코드도 90만 줄로 너무 컸다. 5번째 판은 20초 미만이다.
Q11UglifyJS에서 AOT가 빨라지지 않는 이유는?
eval이나 new Function처럼 실행 중에 코드를 만들어 인터프리터를 많이 쓰기 때문이다. 미리 컴파일할 수 없는 코드다.
Q12모델을 계속 밀어붙여야 하는 이유는?
모델은 스스로 규칙을 지어내고 자기 능력을 낮춰 잡는다. 야심 차게 밀지 않으면 10% 개선 대신 0.1% 개선만 낸다.

용어 정리

용어뜻
런타임Runtime. JavaScript 코드를 실제로 실행하는 프로그램. Bun, Node.js가 여기에 속한다
JavaScriptCoreWebKit(Safari의 엔진)에 들어 있는 JavaScript 엔진. Bun이 내부에서 쓴다
JIT 컴파일Just-in-time. 프로그램을 실행하면서 필요한 코드를 그때그때 기계어로 바꾸는 방식
AOT 컴파일Ahead-of-time. 실행하기 전에 코드를 미리 기계어로 바꿔 두는 방식
인터프리터Interpreter. 코드를 미리 바꾸지 않고 해석하면서 바로 실행하는 방식
타입 검사기Type checker. 코드의 타입 표기가 서로 맞는지 확인하는 도구
모노모픽Monomorphic. 어떤 자리에 들어오는 값의 형태가 늘 하나뿐인 상태
인라인 캐싱Inline caching. 직전에 본 값의 형태를 기억해 두고, 같은 형태가 오면 빠른 길로 처리하는 기법
test262JavaScript 표준을 제대로 구현했는지 확인하는 테스트 모음
차등 테스트Differential testing. 같은 입력을 여러 구현에 넣고 결과가 같은지 비교하는 테스트
퍼징Fuzzing. 자동으로 만든 입력을 대량으로 넣어 버그를 찾는 방법
FuzzilliJavaScript 엔진용 퍼저. V8 팀이 쓴다
프로토타입 오염Prototype pollution. Object.prototype 같은 공용 객체에 속성을 붙여 다른 객체들의 동작을 바꾸는 공격
호환을 깨는 변경Breaking change. 기존 코드가 그대로는 동작하지 않게 되는 변경
slopAI가 대량으로 만든 엉성하고 질 낮은 결과물
서브에이전트Subagent. 메인 에이전트가 일을 나눠 맡기는 하위 에이전트
도그푸딩Dogfooding. 자기 회사 제품을 내부에서 먼저 직접 쓰는 것
JetStream 3JavaScript 엔진 성능을 비교하는 대표 벤치마크
카나리Canary. 정식 출시 전에 먼저 내놓는 실험용 빌드
