에이전트를 진짜 작업으로 시험하기

에이전트를 고쳤을 때 좋아졌는지 나빠졌는지 느낌으로 판단하던 일을 끝내자는 발표다. 작업과 채점 기준을 고정해 두고 에이전트만 바꿔 가며 돌리면, 프롬프트 한 줄을 고쳐도 증거가 남는다. Harbor가 그 틀을 제공하고, Arize의 Phoenix 팀이 실제로 어떻게 쓰는지 보여 준다.

원본 영상: How to Test Your Agents on Real Tasks With Harbor 발표: Xander Song (Arize AI 엔지니어, Phoenix 메인테이너)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 이름이 뭉개진 곳은 확실한 것만 알려진 이름으로 바로잡았고, 확실하지 않은 것은 "(추정)"을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. Harbor는 에이전트 평가 틀이다. 자연어 작업 지시, 실제 데이터가 든 격리 환경, 성공 여부를 판정하는 스크립트(검증기) 세 가지로 이루어진다.
  2. 작업과 검증기를 고정하고 에이전트만 바꾼다. 그러면 프롬프트, 도구, 스킬, 하네스를 고칠 때마다 개선인지 퇴보인지 신호가 나온다.
  3. 검증기는 에이전트가 남긴 흔적만 본다. 파일, 데이터베이스 같은 부수 효과를 검사하고 구현은 모른다. 통합 테스트와 같은 원리라 구현을 갈아엎어도 테스트가 살아남는다.
  4. 오라클(정답 스크립트)을 먼저 돌린다. 에이전트에 토큰을 쓰기 전에 데이터, 환경, 검증기가 제대로 됐는지 확인할 수 있다.
  5. 시도마다 새 Docker 컨테이너라 완전히 병렬이다. 샌드박스 서비스에서 동시 작업자 200개로 돌리면 큰 테스트 묶음도 빨리 끝난다.
  6. Phoenix 팀은 서버 전체를 컨테이너에 넣었다. SQLite 파일, API, CLI, MCP 서버, 서버 측 에이전트, 스킬까지 한 환경에 담아 "코딩 에이전트 + 우리 도구"라는 혼합 시스템을 한 단위로 평가한다.
  7. 실제 사례: 프롬프트 한 줄을 고쳐 SQL 도구 사용을 늘렸다. 정답률은 그대로였고 도구 호출 수와 턴 수가 줄었다. 느낌이 아니라 숫자로 확인했다.
  8. 가장 어려운 것은 데이터다. 데이터가 현실적일수록 현실적인 문제가 드러난다.
01

Harbor는 무엇인가 01:20

발표자는 Arize AI에서 오픈소스 관측·실험·평가 플랫폼 Phoenix를 만든다. 이 발표는 Harbor라는 오픈소스 틀을 소개한다. Harbor는 발표자가 만든 것이 아니다. 발표자는 스스로를 "열성적인 파워 유저"라고 소개했다.

발표의 주제는 한 문장이다. 느낌 vibes이 아니라 증거를 보고 배포하자.

Harbor는 세 가지로 이루어진다.

작업 task에이전트가 해내길 바라는 일을 자연어로 적은 지시문
환경 environment작업에 필요한 실제 데이터가 든, 매번 새로 만드는 격리 샌드박스
검증기 verifier에이전트가 끝난 뒤 환경을 검사해 의도한 부수 효과가 생겼는지 확인하는 스크립트

검증기는 보상 reward을 낸다. 가장 흔한 보상은 0 또는 1, 통과 또는 실패다.

왜 이 단순한 그림이 강력한가 02:10

작업과 데이터가 현실적이고, 검증기가 성공과 실패를 정확히 가른다고 하자. 그러면 작업과 검증기를 고정한 채 에이전트 구현만 바꿀 수 있다. 파이프라인을 처음부터 끝까지 한 번 돌리면 이번 변경이 개선인지 퇴보인지 신호가 나온다.

작업을 하나가 아니라 여러 개 모으면 에이전트가 할 줄 알아야 하는 능력의 넓은 범위를 덮을 수 있다. 그러면 고치고, 돌리고, 확인하는 고리가 닫힌다. 느낌만으로 배포할 때는 가질 수 없던 확신이 생긴다.

작업 하나의 구조 03:30

구성 요소형태역할
지시문마크다운 파일사용자가 에이전트에게 보내는 것과 같은 자연어 요청
환경Dockerfile작업에 필요한 데이터를 담는다. 어떤 데이터든 상관없다. SQLite 파일, 특정 커밋의 git 저장소 등

데이터셋, 시도, 잡 04:40

  • 데이터셋 dataset: 작업 여러 개를 모은 것.
  • 시도 trial: 작업 하나를 독립적으로 실행하는 단위. 작업마다 시도 횟수를 정할 수 있다. 대규모 언어 모델과 에이전트는 매번 다르게 움직이기 때문에 여러 번 돌린다.
  • 시도마다 새 Docker 컨테이너를 만들고 데이터를 채운다. 에이전트를 넣고 지시문을 준다. 에이전트는 소스 파일을 고치거나 데이터베이스를 바꾸는 식으로 환경에 흔적을 남긴다. 에이전트가 끝나면 검증기가 돌아 보상을 내고, 보상은 reward 파일에 기록된다.
  • 궤적 trajectory: 선택 사항이다. 에이전트가 내부에서 어떤 단계를 밟았는지 ATIF Agent Trajectory Interchange Format라는 JSON 형식으로 남길 수 있다. 디버깅과 기록용이다.
  • 잡 job: 데이터셋의 모든 작업을 정해진 횟수만큼 시도하고, 검증기로 보상을 내고, 궤적을 모으는 전체 실행 한 번.
하나만 기억한다면 새 환경을 만들고, 에이전트를 넣고, 끝나면 검증기가 흔적을 검사해 보상을 적는다. 발표자는 이것이 Harbor의 전부라고 말했다.
03

오라클: 에이전트 전에 파이프라인 검증 07:00

환경에는 에이전트 대신 오라클 oracle을 넣을 수도 있다. 오라클은 그 작업의 정답 스크립트다.

오라클이 쓸모 있는 이유는 에이전트를 넣기 전에 파이프라인의 문제를 모두 잡아낼 수 있기 때문이다. 데이터가 제대로 들어갔는지, 환경 설정이 맞는지, 검증기가 기대대로 도는지를 에이전트 토큰 비용을 한 푼도 쓰기 전에 확인한다.

발표자의 경험으로는 오라클이 검증기를 통과하는 것을 보면 검증기를 한 줄씩 읽지 않아도 어느 정도 믿을 수 있다. 발표자의 표현으로는 "조금 더 세게 느낌대로 가도 된다".

04

예시: 실패한 마이그레이션 고치기 07:50

코딩 에이전트를 평가한다고 하자. 특정 스킬을 붙였거나 자체 MCP 서버를 연결한 코딩 에이전트여도 좋다. 작업은 "실패하는 데이터베이스 마이그레이션을 고쳐라"다.

구성 요소이 작업에서의 내용
지시문"이 마이그레이션이 실패하는데 고쳐 줄 수 있나요?" 같은 요청
환경SQL 파일, 테이블 정의, 실패하도록 만들어 둔 상향 마이그레이션 소스 코드
검증기상향 마이그레이션을 실행해 종료 코드 0을 확인하고, 기대한 테이블·컬럼·인덱스가 있는지 검사
정답마이그레이션을 실제로 고치는 스크립트

검증기는 에이전트가 끝난 뒤에 들어온다 10:10

기본 설정인 로컬 Docker에서는 검증기가 에이전트 실행이 끝난 뒤에 컨테이너에 마운트된다. 에이전트가 실행 중에 검증기나 정답을 들여다보고 부정행위를 하지 못하게 막는 것이다.

검증기는 구현을 모른다 10:50

검증기는 에이전트에 대해 아무것도 모른다. 에이전트가 무엇을 남겼는지만 본다. 어떻게 남겼는지는 보지 않는다. ATIF 궤적을 들여다보는 검증기를 쓸 수도 있지만 그것은 표준적인 방식이 아니다.

발표자는 통합 테스트에 빗댔다. 잘 쓴 통합 테스트는 API 뒤의 구현을 모른다. 좋은 검증기도 마찬가지다. 그래서 테스트가 모두 통과하는 상태를 유지하면서 구현을 통째로 갈아엎을 수 있다. 작업을 고정한 채 에이전트를 완전히 바꾸고 파이프라인을 돌려 여전히 동작하는지 바로 안다.

Phoenix 팀이 겪은 반대 사례 13:00 발표자는 지금 여러 에이전트 경로(MCP, CLI, 서버 측 에이전트)에 흩어진 스킬을 하나로 합치는 중이다. 예전에는 테스트가 구현에 묶여 있어서 도구 하나를 바꾸면 에이전트 기능은 멀쩡한데 테스트가 깨졌다. 구현에 무관한 테스트가 필요하다는 결론은 그 고통에서 나왔다.

청중 질문에 대한 답: 환경은 그냥 Docker 컨테이너다. 어떤 프레임워크, 어떤 언어, 어떤 실행 파일이든 넣을 수 있다. Harbor는 그 위에 얹는 기본 단위다.

05

규모: 병렬 실행과 pass@k 14:20

작업과 시도는 각각 독립이고 자기 컨테이너에서 돈다. 그래서 파이프라인 전체가 가로로 늘어난다. Daytona, Modal, E2B 같은 샌드박스 서비스와 잘 맞는다. Phoenix 팀은 Daytona를 쓰고, 동시 작업자 200개로 돌리면 큰 테스트 묶음도 금방 끝난다고 했다.

발표 슬라이드의 예시 격자 14:50

  • 작업 4개 (마이그레이션 수정 작업 포함)
  • 에이전트 2개: Claude Code + Opus 5, Codex + GPT-5 (자막 기준, 모델명은 추정)
  • 시도 3회 (k = 1, 2, 3)

각 칸은 시작할 때는 똑같지만 완전히 분리된 컨테이너다. 각각에 에이전트를 따로 넣고 풀어 둔다. 같은 작업을 같은 에이전트로 세 번 독립적으로 돌리는 것이다.

여기서 pass@k 같은 집계 지표가 나온다. 세 번 시도해서 한 번이라도 통과했는가를 묻는 지표다. 예시에서는 마이그레이션 작업은 두 에이전트 모두 통과했고, 다른 작업은 하나만 통과했다. 같은 지표를 데이터셋 전체로도 계산할 수 있다. 데이터셋이 관심 있는 기능을 잘 덮고 있다면 변경이 전체적으로 어떤 영향을 줬는지 빠르게 그림이 나온다.

Harbor와 Phoenix 연결 17:00

Phoenix는 Arize의 오픈소스 AI 관측 도구다. Harbor의 기본 개념마다 Phoenix에 대응하는 개념이 있다.

ATIF 궤적OpenInference 트레이스

OpenInference 18:00

OpenInference는 OpenTelemetry 위에 얹은 의미 규약 semantic conventions이다. OpenTelemetry는 로그, 지표, 트레이스 같은 원격 측정 데이터를 다루는 오픈소스 틀이다. OpenInference는 AI 애플리케이션이 내보낼 데이터 구조를 정의하고, Phoenix 같은 소비자가 그것을 받아 전용 화면과 작업 흐름을 만든다.

발표자는 OpenInference 메인테이너이기도 하다. 이 규약을 최근 클라우드 네이티브 재단(CNCF로 추정)과 OpenTelemetry 작업 그룹에 기부했다고 했다. Arize 바깥에서도 쓰이는 근거로 들었다.

Phoenix가 더해 주는 것 19:20

  • 궤적을 LLM 호출과 도구 호출에 맞춘 전용 화면으로 보여 준다.
  • 작업과 데이터셋에 버전을 매겨, 특정 잡이 돌 때 작업이 정확히 어떤 모습이었는지 안다.
  • 실험을 추적하고 보상과 지표가 시간에 따라 바른 방향으로 가는지 그려 준다.
  • 스킬, CLI, MCP 서버가 있어 Claude, Codex, Cursor가 이 데이터에 쉽게 접근한다.
Harbor만 써도 된다 Harbor에는 로컬에서 띄우는 자체 오픈소스 UI와 호스팅 웹 서비스가 있다. Phoenix는 필수가 아니다. 위 기능이 필요할 때 써 볼 이유가 된다는 것이 발표자의 설명이다.

발표자는 Phoenix와 OpenInference의 메인테이너다. Phoenix의 장점을 말하는 대목은 그 점을 감안해 읽자. 발표자 본인도 "Harbor만 써도 된다"고 여러 번 말했다.

07

Phoenix 팀의 환경 구성 20:40

Phoenix 팀이 매일 다루는 구조는 이렇다.

  1. 사용자의 AI 앱이나 에이전트가 OpenTelemetry와 OpenInference로 계측되어 OTLP(OpenTelemetry 프로토콜)로 Phoenix 서버에 트레이스를 보낸다.
  2. Phoenix가 트레이스를 받아 SQLite 또는 Postgres에 쓴다.
  3. 트레이스, 스팬, 세션, 데이터셋, 실험, 평가 같은 핵심 서비스가 REST와 GraphQL API로 열린다.
  4. 그 위에 에이전트 경로 세 가지가 있다. 모두 테스트해야 한다.
에이전트 경로동작 방식
코딩 에이전트 + CLICLI가 REST나 GraphQL을 호출
코딩 에이전트 + MCP 서버MCP 서버가 같은 일을 함
서버 측 에이전트 Pixie(추정)팀이 직접 만든 하네스. MCP 서버와 bash 에뮬레이터를 갖춘, 서버에서 도는 코딩 에이전트

Phoenix는 Grafana처럼 단일 노드에서 도는 서버다. 그래서 Docker에 넣기 쉽다. 현실적인 데이터가 든 SQLite 파일을 넣고, 브라우저를 테스트 클라이언트로 바꾸고, 통째로 Docker에 담는다. 그러면 바로 Harbor에서 쓸 수 있다.

작업은 실제 사용자가 할 법한 요청이다. 예를 들어 "지난주 트레이스에서 환각이 있는 LLM 호출을 찾아 데이터셋에 추가해 줘". 세 경로 중 하나를 골라 환경 안에서 풀어 두고, 끝나면 검증기를 돌린다. 서버와 SQLite 파일이 컨테이너 안에 있으니 검증은 쉽다. REST 엔드포인트를 쳐서 확인하거나, SQLite 파일을 직접 조회해 데이터셋 테이블에 기대한 행이 생겼는지 보면 된다.

Harbor는 호스트에서 도는 CLI다 25:40

청중 질문에 답하며 발표자가 분명히 한 점이다. Harbor 자체는 컨테이너 안에서 돌지 않는다. 노트북이나 GitHub Actions 러너 같은 호스트에서 도는 명령줄 도구이자 조율자다. 환경은 로컬 Docker가 기본이고, 더 키우려면 Daytona 같은 샌드박스 서비스에서 돌린다.

Harbor와 환경 사이의 계약은 스크립트가 정해진 자리에 있는가다. 작업을 시작하는 스크립트, 검증기를 돌리는 스크립트, 오라클을 돌리는 스크립트가 Docker 이미지의 정해진 위치에 있어야 한다. 그 규약만 지키면 Harbor가 이미지를 돌릴 수 있다.

자유도가 크다 28:00 가장 흔한 시작점은 git 저장소 위에서 도는 코딩 에이전트다. 하지만 Phoenix 팀은 SQLite 데이터, 앱 전체, API, 서버 측 에이전트, CLI, 그리고 파일 시스템의 스킬까지 한 컨테이너에 넣었다. Docker 이미지에 들어가기만 하면 Harbor는 돌릴 수 있다.

사례: 집계 질문과 SQL 도구 33:20

문제

MCP 서버와 CLI는 REST와 GraphQL을 쓸 수 있었다. 그런데 사용자들은 그 API로 답하기 어려운 집계 질문을 던졌다. "지난 몇 달 중 가장 바쁜 날은 언제였나, 그날 트레이스가 몇 개였나", "모델별로 비용이 얼마나 드나, 어떤 모델이 가장 비싼가" 같은 것이다. 집계용 API가 없으니 에이전트는 페이지를 넘기며 직접 합산했다. 데이터가 많으면 페이지 넘김과 도구 호출이 폭증한다.

첫 번째 수정: 읽기 전용 SQL 도구 34:30

MCP 서버에 에이전트가 읽기 전용 SQL을 써서 데이터베이스에 직접 실행하는 도구를 추가했다. 그런데 새 문제가 생겼다. REST, GraphQL, SQL 중 무엇을 써야 할지 에이전트가 몰랐다.

두 번째 수정: 프롬프트 한 줄 35:30

프롬프트를 바꾸는 것은 쉽다. 문제는 정말 그렇게 하는지 어떻게 확인하느냐다. 여기서 Harbor가 들어온다.

데이터셋 만들기 36:00

  1. 팀이 제품을 직접 쓰며 모아 온 준현실적인 SQLite 파일을 환경에 넣었다.
  2. Claude에게 앱의 도메인(트레이스, 스팬, 데이터셋, 실험)을 보고 사용자 질문 목록을 만들어 달라고 했다. 집계 질문과 아닌 질문을 섞었다.
  3. 같은 에이전트에게 각 질문의 오라클 정답도 쓰게 했다. 정답은 REST 호출이나 데이터베이스 쿼리 하나다.
  4. 질문은 사람이 훑어보며 말이 되는지만 확인했다.

검증기 중 일부는 LLM 판정 LLM as a judge이고, 일부는 SQL 쿼리나 REST 호출이다. 검증기가 오라클을 통과하는 것을 봤기 때문에 검증기 자체를 어느 정도 믿을 수 있었다. 발표자가 Harbor에서 가장 신선하다고 느낀 부분이다.

결과 37:30

  • 예상대로 SQL을 더 자주, 더 적극적으로 쓰게 됐다. 발표자는 집계 질문에서 페이지를 넘기는 것보다 SQL을 과하게 쓰는 편이 낫다고 봤다.
  • 궤적당 평균 도구 호출 수가 줄었다. 애초에 이 수정을 한 이유가 도구 호출을 줄이는 것이었다.
  • 데이터셋이 작아서 페이지 넘김이 많지 않았다. 그래서 발표자는 이 완만한 감소가 실제 문제를 축소해서 보여 준다고 했다.

발표에서 구체적인 전후 수치는 말하지 않았다. 그래서 이 노트에는 막대 차트를 그리지 않았다.

Phoenix에서 결과 보기 38:30

데이터셋 화면에는 작업 예시가 버전 기록과 함께 있다. 예시 질문 하나는 "총비용 기준으로 가장 비싼 모델 세 개는 무엇이고 각각 얼마인가"다. 이 질문은 REST를 페이지 넘기기보다 SQL로 훨씬 쉽게 답한다. 화면 아래의 기대 답은 오라클이 실제 데이터에 SQL을 돌려 낸 것이라 결정적이다. 발표자는 Claude가 좋은 SQL을 썼다고 어느 정도 믿는다고 했다.

실험 화면은 Harbor의 잡 목록이다. 비용, 실행 지연, 보상, 도구 호출 수, SQL 사용 여부 같은 지표가 차트로 나온다. 이 작업의 보상은 처음부터 높았다. 시스템이 틀린 답을 내던 것이 아니라 도구 호출이 너무 많았던 것이다. 정확성 수정이 아니라 최적화였다.

보상은 어떻게 계산하나 40:30

청중 질문에 대한 답이다. 보상은 검증기에서 나오고, 검증기는 사용자가 작업마다 직접 쓴다. 이 작업에서 성공과 실패가 무엇인지 생각하고, 파일 시스템이나 데이터베이스 같은 부수 효과만 보고 그것을 어떻게 알아낼지 스크립트로 적는다. 그 스크립트가 0이나 1을 내고, 보상 이름도 직접 정한다. 잡 전체의 집계 보상을 시간에 따라 추적한다.

궤적을 들여다보는 것은 반칙인가 41:30

청중이 짚었다. 검증기는 구현에 무관하다고 했는데, "SQL을 썼는가" 같은 지표는 궤적을 들여다보는 것 아닌가. 발표자의 답은 "맞다, 반칙이다"였다. 다만 쓰임새에 따라 다르다.

정답을 맞히는지 볼 때

회귀 테스트처럼 끝에 바른 답에 도달했는지가 중요하면 검증기를 순수하게 둔다. 궤적을 보지 않고 결과만 본다.

장점: 구현을 바꿔도 테스트가 살아남는다.

특정 지표를 최적화할 때

이번 사례는 정답이 아니라 도구 호출 수를 줄이는 것이 목표였다. 그래서 궤적을 들여다보는 것이 맞았다.

대가: 테스트가 변경에 덜 튼튼해진다.

Harbor는 통합 테스트, 종단 간 테스트, CI에서의 정확성 보증에도 쓰고, "집계 질문에서 형편없는데 어떻게 고치지"라는 특정 문제를 빠르고 거칠게 확인하는 데도 쓴다. 무엇을 하려는지에 따라 검증기의 순수함을 고른다.

분산 시스템이면 어떻게 하나 29:00

S3 같은 외부 저장소에 기대는 시스템은 SQLite 파일 하나를 넣는 식으로는 안 된다. 발표자는 아직 이 문제를 겪어 보지 않았다고 솔직히 말했다. 떠오르는 방향은 에이전트를 안정된 인터페이스 뒤로 잘라 내어 "이 형식의 데이터를 받는다"는 경계를 만드는 것이다. 다만 S3 호출을 가짜로 바꾸기 시작하면 모킹의 세계로 돌아가는 셈이고, 그것이 Harbor로 벗어나려던 바로 그 세계다. Harbor가 Docker 이미지 여러 개를 띄울 수 있으니 그쪽에서 답을 찾을 수도 있다고 했다.

회귀 테스트는 어떻게 짜나 48:30

아직 초기라 정상 경로 happy path부터 잡는 중이다. 구조는 스킬 중심이다. 회귀 테스트는 에이전트와 LLM 호출이 고리 안에 든 종단 간 테스트라 Playwright와 비슷하고, 스킬은 "이러면 이렇게 한다"는 작업 흐름을 적은 것이라 그런 테스트를 쓰기 좋다. 지금은 가장 중요한 스킬의 정상 경로가 여러 모델과 공급자에서 통과하도록 다지는 단계다.

스킬이 안 켜지면 49:20

다른 스킬의 설명이 내 스킬과 겹치면 내 스킬이 더는 켜지지 않을 수 있다. 접근은 두 가지다.

  • 어느 스킬이 켜졌는지 신경 쓰지 않고, 스킬이 안 켜졌으면 어차피 못 통과할 좋은 테스트를 둔다.
  • 검증기로 궤적을 들여다보고 "이 질문에 이 스킬이 켜졌는가"를 확인한다. Phoenix 팀도 이런 테스트를 뒀다. 한 턴만 시험하면 데이터가 좋을 필요도 없다. 단점은 유지보수다. 스킬 이름을 바꾸면 테스트가 흔들린다.

구현에서 완전히 떨어진 테스트와 완전히 묶인 테스트 사이의 어딘가에 놓이는 셈이다. 그래도 쓸모가 있으니 안 쓸 이유는 없다. 중요한 것은 관심 있는 영역을 넓게 덮는 것이다.

프로덕션과 Harbor의 차이 51:40

프로덕션에서는 계측된 앱이 트레이스를 보내고 Phoenix가 데이터베이스에 쓴다. Harbor에서는 그 앞부분, 즉 OTLP 수신과 사용자 에이전트가 사라진다. 사용자 앱을 흉내 내지 않고, 그 앱이 이미 돌아서 SQLite 파일에 데이터가 쌓였다고 가정하고 데이터베이스만 채운다.

평가 단위는 코딩 에이전트가 아니다 52:20

Harbor의 표준 용도는 코딩 에이전트 평가다. Phoenix 팀은 비슷하지만 다르다. Claude Code나 Codex를 고치는 것이 아니다. 최적화 대상은 코딩 에이전트 + 팀이 만든 MCP 서버, 스킬, CLI, API라는 혼합 시스템이다. 코딩 에이전트가 제품을 더 잘 다루게 돕는 주변 기반을 팀이 유지하고, 그것들이 함께 바뀌고 함께 평가되어야 하므로 전부 한 환경에 넣었다. 이 그림에 도달하기까지 Harbor를 개념적으로 이해하는 데 시간이 조금 걸렸다.

코딩 에이전트로 Harbor 설정하기 54:30

Harbor의 계약은 정해진 디렉터리의 스크립트에 기반하는데, 그것을 검사해 주는 린터가 없다. 코딩 에이전트가 기댈 것이 없다는 뜻이다. 가장 좋은 방법은 Harbor가 제공하는 스킬을 내려받아 프로젝트를 바르게 설정하게 하는 것이다.

핵심 정리

  1. Harbor는 자연어 작업, 실제 데이터가 든 격리 환경, 부수 효과를 검사하는 검증기로 에이전트를 평가하는 오픈소스 틀이다.
  2. 작업과 검증기를 고정하고 에이전트만 바꾸면 변경마다 개선인지 퇴보인지 신호가 나온다. 느낌이 아니라 증거로 배포한다.
  3. 시도마다 새 Docker 컨테이너를 만든다. 시도를 여러 번 하는 이유는 에이전트가 매번 다르게 움직이기 때문이다.
  4. 검증기는 에이전트가 끝난 뒤 마운트돼 부정행위를 막고, 구현을 모른 채 결과만 본다. 통합 테스트처럼 구현을 갈아엎어도 살아남는다.
  5. 오라클(정답 스크립트)을 먼저 돌려 데이터, 환경, 검증기를 에이전트 토큰 비용 없이 검증한다.
  6. 모든 시도가 독립이라 샌드박스 서비스에서 완전히 병렬로 돈다. pass@k 같은 집계 지표를 작업별, 데이터셋별로 낸다.
  7. Harbor는 호스트에서 도는 CLI이고, 환경과의 계약은 정해진 자리의 스크립트다. Docker 이미지에 들어가면 무엇이든 돌릴 수 있다.
  8. Phoenix 팀은 단일 노드 서버 전체를 컨테이너에 넣어 코딩 에이전트 + 자체 도구라는 혼합 시스템을 한 단위로 평가한다.
  9. 프롬프트 한 줄을 고쳐 SQL 도구 사용을 늘린 사례에서 보상은 그대로, 도구 호출과 턴 수는 줄었다. 정답 맞히기가 목표면 검증기를 순수하게, 지표 최적화가 목표면 궤적을 봐도 된다.
  10. 데이터가 가장 어렵다. 현실적인 데이터가 현실적인 문제를 드러낸다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1Harbor를 이루는 세 요소는?
자연어 작업 지시문, 실제 데이터가 든 격리 환경(Docker), 에이전트가 끝난 뒤 부수 효과를 검사해 보상을 내는 검증기.
Q2작업과 검증기를 고정하면 무엇이 가능한가?
에이전트 구현만 바꿔 가며 파이프라인을 돌려, 각 변경이 개선인지 퇴보인지 신호를 얻는다. 작업을 여러 개 모으면 능력 전반에 대해 같은 일을 할 수 있다.
Q3시도를 여러 번 하는 이유와, 시도마다 환경은 어떻게 되나?
LLM과 에이전트가 매번 다르게 움직이기 때문이다. 시도마다 데이터를 채운 새 Docker 컨테이너를 만든다.
Q4오라클은 무엇이고 왜 먼저 돌리나?
작업의 정답 스크립트다. 에이전트에 토큰을 쓰기 전에 데이터, 환경, 검증기가 제대로 됐는지 확인할 수 있다. 검증기가 오라클을 통과하면 검증기를 한 줄씩 읽지 않아도 어느 정도 믿을 수 있다.
Q5검증기가 에이전트 실행이 끝난 뒤에 마운트되는 이유는?
에이전트가 실행 중에 검증기나 정답을 들여다보고 부정행위를 하지 못하게 막기 위해서다.
Q6검증기를 통합 테스트에 빗댄 이유는?
둘 다 구현을 모르고 결과만 본다. 그래서 구현을 통째로 바꿔도 테스트가 살아남고, 테스트가 통과하는 상태를 유지하며 리팩터링할 수 있다.
Q7Harbor는 어디에서 실행되고, 환경과의 계약은 무엇인가?
노트북이나 GitHub Actions 러너 같은 호스트에서 도는 CLI다. 계약은 작업 시작, 검증기, 오라클 스크립트가 Docker 이미지의 정해진 자리에 있는 것이다.
Q8Phoenix 팀이 Harbor 환경에 넣은 것은?
현실적인 데이터가 든 SQLite 파일, Phoenix 서버 전체, REST와 GraphQL API, CLI, MCP 서버, 서버 측 에이전트, 파일 시스템의 스킬. 단일 노드 서버라 통째로 넣기 쉬웠다.
Q9SQL 도구 사례에서 프롬프트를 고친 뒤 어떤 지표가 어떻게 움직였나?
보상은 그대로(모두 통과), GraphQL 호출과 도구 호출 수와 턴 수는 감소, SQL 호출은 증가. 정확성 수정이 아니라 최적화였다.
Q10"SQL을 썼는가"를 검증기가 보는 것은 반칙인가?
발표자는 "맞다"고 했다. 정답을 맞히는지 볼 때는 궤적을 보지 않는 순수한 검증기를, 특정 지표를 최적화할 때는 궤적을 보는 검증기를 쓴다. 대가는 테스트가 변경에 덜 튼튼해지는 것이다.
Q11Phoenix 팀이 최적화하는 단위는 코딩 에이전트인가?
아니다. Claude Code나 Codex를 고치지 않는다. 코딩 에이전트에 팀의 MCP 서버, 스킬, CLI, API를 더한 혼합 시스템이 단위다. 그래서 전부 한 환경에 넣는다.
Q12발표자가 가장 어렵다고 한 것은?
데이터를 구하는 것. 데이터가 현실적일수록 현실적인 문제가 드러난다.

용어 정리

용어뜻
Harbor자연어 작업, 격리 환경, 검증기로 에이전트를 평가하는 오픈소스 틀. 호스트에서 도는 CLI
작업 (task)에이전트가 해내길 바라는 일. 마크다운 지시문, 환경, 검증기, 선택적 정답으로 구성
검증기 (verifier)에이전트가 끝난 뒤 환경에서 돌아 의도한 부수 효과가 생겼는지 확인하는 스크립트
보상 (reward)검증기가 내는 점수. 보통 0 또는 1, 통과 또는 실패
오라클 (oracle)작업을 실제로 푸는 정답 스크립트. 에이전트 대신 환경에 넣어 파이프라인을 검증한다
데이터셋작업 여러 개를 모은 것
시도 (trial)작업 하나를 새 컨테이너에서 독립적으로 실행하는 단위
잡 (job)데이터셋 전체를 정해진 시도 횟수로 돌리고 보상과 궤적을 모으는 실행 한 번. Phoenix에서는 실험
궤적 (trajectory)에이전트가 밟은 단계(LLM 호출, 도구 호출)의 기록
ATIFAgent Trajectory Interchange Format. Harbor의 JSON 기반 궤적 형식
pass@kk번 시도해서 한 번이라도 통과했는가를 재는 지표
부수 효과 (side effect)에이전트가 환경에 남긴 변화. 수정된 파일, 데이터베이스 행 등
샌드박스 서비스격리된 실행 환경을 대량으로 띄워 주는 서비스. Daytona, Modal, E2B
PhoenixArize의 오픈소스 AI 관측·실험·평가 플랫폼
OpenTelemetry로그, 지표, 트레이스 같은 원격 측정 데이터를 다루는 오픈소스 틀
OTLPOpenTelemetry 프로토콜. 트레이스를 서버로 보내는 규약
OpenInferenceOpenTelemetry 위에 얹은 AI 앱용 의미 규약. Arize가 만들고 외부에 기부했다고 발표자가 말함
MCP 서버Model Context Protocol. 에이전트가 외부 도구와 데이터를 쓰게 해 주는 서버
스킬 (skill)에이전트가 특정 작업 흐름을 따르게 하는 지시 묶음
하네스 (harness)모델을 감싸 도구, 순서, 규칙을 정해 주는 실행 틀
LLM 판정LLM as a judge. 다른 모델이 결과의 성공 여부를 판정하는 검증 방식
정상 경로 (happy path)예외 없이 의도대로 흘러가는 가장 기본적인 시나리오
모킹 (mocking)외부 의존성을 가짜로 바꿔 테스트하는 방식. Harbor는 이것에서 벗어나려는 시도
