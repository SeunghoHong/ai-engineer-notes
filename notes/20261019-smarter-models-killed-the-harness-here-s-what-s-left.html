에이전트 하네스는 정말 죽었나

더 똑똑해진 모델이 코딩을 돕던 하네스의 보조 장치를 흡수했다. 그래도 하네스는 모델이 아직 못 하는 새 영역의 일을 열고, 모델이 대신할 수 없는 실행 환경, 보안, 비용 효율을 맡는다.

원본 영상: Smarter Models Killed the Harness. Here's What's Left 발표: Jediah Katz (SpaceXAI. Cursor에서 에이전트 하네스를 가장 오래 맡은 엔지니어)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 확실하지 않은 것은 들린 대로 적고 (추정)을 붙였다. 제품 이름 GrokBot은 자막 표기가 여러 가지라 하나로 맞췄다. mm:ss는 영상 위치다.

3분 요약
  1. 하네스는 모델의 눈과 손이다. 모델을 감싸 도구와 맥락을 주고, 컴퓨터와 외부 서비스에 이어 준다.
  2. 모델이 똑똑해지면서 코딩을 돕던 하네스 장치가 필요 없어졌다. 연구 두 개에서 하네스를 바꿔도 코딩 점수는 크게 다르지 않았다.
  3. 이유는 데이터 플라이휠이다. 하네스가 어려운 일을 가능하게 하면 데이터가 쌓이고, 모델이 그 기술을 스스로 익힌다.
  4. 그래도 하네스는 죽지 않았다. 코딩이 모델 안으로 들어가면 하네스가 다음 영역을 연다. GrokBot에서는 지웠던 프롬프트와 가드레일을 다시 넣고 있다.
  5. 모델이 흡수할 수 없는 부분이 있다. 클라우드 실행 기반, 신뢰와 보안, 비용 효율이다. 점수가 같아도 작업당 비용은 하네스마다 크게 달랐다.
  6. 앞으로 하네스는 정리되기 전에 더 지저분해진다. 안쪽을 덜 보여 주고, 기본 부품으로 짓고, 임시 땜질은 추적해서 지운다.
  7. 발표자는 6개월 안에 에이전트 작업의 90%가 노트북 밖에서 돌 것이라고 예측한다.

02

하네스 안에 무엇이 있나 01:40

에이전트 하네스 agent harness는 모델의 눈과 손이다. 모델을 감싸서 방향을 잡아 준다. 그리고 모델을 바깥 세상과 이어 준다.

연결 순서는 이렇다. 사용자는 앱을 통해 하네스에 닿는다. 하네스는 모델을 컴퓨터와 외부 서비스에 잇는다. 외부 서비스의 예로 발표자는 MCP를 든다.

두 개의 층 02:00

런타임 · runtime

하네스의 바닥이다.

  • 핵심 에이전트 루프가 어디서 도는지 정한다
  • 일을 이어서 할 수 있도록 상태를 어떻게 저장할지 정한다

만드는 방식은 전통적인 소프트웨어 공학과 비슷하다.

맥락·조율 층 · context & orchestration

사람들이 보통 "하네스"라고 할 때 가리키는 곳이다.

  • 어떤 모델을 언제 부를지 정한다
  • 모델이 무엇을 볼지 정한다: 프롬프트, 도구, 메모리, 컴팩션 compaction
  • 에이전트가 원하는 대로 움직이게 하는 여러 요령을 쓴다

발표자 표현으로는 무법지대다. 발표자가 주로 일하는 곳이기도 하다.

05

데이터 플라이휠 06:20

왜 이런 일이 생길까. 발표자는 하네스가 스스로를 쓸모없게 만든다고 설명한다. 이 과정을 데이터 플라이휠 data flywheel이라고 부른다. 플라이휠은 한 번 돌기 시작하면 계속 도는 바퀴다.

  1. 하네스가 더 어려운 코딩 작업을 해낼 수 있게 만든다.
  2. 더 많은 사용자가 에이전트로 그런 작업을 시도한다.
  3. 더 많은 코딩 데이터가 모델 회사로 간다.
  4. 모델이 그 기술을 스스로 익힌다.
  5. 하네스는 그 작업을 위해 넣었던 장치를 지운다.

그래서 "하네스는 죽었다"는 말이 나온다. 모델이 어떤 하네스에서든 코딩을 잘한다면, 하네스를 고르는 일이 아직 중요할까?

발표자의 답: 죽지 않았다 07:10 이유는 두 가지다. 첫째, 하네스는 모델이 풀 새 영역의 일을 연다. 둘째, 하네스의 일부는 모델이 흡수할 수 없다. 특히 맥락 층 바깥이 그렇다.
06

새 영역을 여는 하네스: GrokBot 07:30

발표자는 첫 번째 이유를 자기 회사 제품인 GrokBot으로 설명한다. GrokBot은 일을 대신 해 주는 자율 동료 autonomous colleague다. 코딩만 하지 않고 여러 지식 업무를 한다.

하네스 구조가 다르다. 한 번 묻고 끝나는 채팅이 아니다. 오래 살아 있는 코디네이터 coordinator 봇이 여러 워커 worker를 조율한다.

실력 좋은 변호사를 고용한 것과 비슷하다. 변호사는 의뢰인을 직접 상대하며 전략을 맡고, 세부 일은 패럴리걸 팀에 나눠 준다.발표자의 비유를 옮김

발표자는 GrokBot을 만드는 회사 소속이다. "새 범주를 만든 획기적인 제품"이라는 평가는 자기 회사 제품 이야기이니 감안해 읽자.

이유는 간단하다. 새 일하는 방식과 새 분야에는 모델이 아직 잘 못하는 일이 많다.

GrokBot이 지금 집중하는 일 09:00

과제내용
주요 웹 작업슬라이드 만들기, 여행 예약 같은 흐름
소통무엇을 했는지 알려 준다. 단, 사용자를 정보로 질리게 하지 않는다
직접 할지, 물을지동료에게 메일 보내기처럼 위험할 수 있는 일도 해야 한다. 다만 사용자가 의도한 방식으로만 해야 한다
시간이 갈수록 배우기메모리로 사용자가 일하는 방식을 익힌다

코딩 에이전트를 깊게 써 본 사람에게는 새로운 과제가 아니다. 하지만 GrokBot에서는 모든 사용자가 어떤 식으로든 이 기능을 쓰기 때문에 훨씬 중요하다. 지금 이 과제들을 가능하게 하는 것은 하네스다. 물론 모델도 큰 몫을 한다.

07

플라이휠의 마지막 화살표 10:00

GrokBot 사례로 플라이휠의 빈 화살표가 채워진다. 코딩 같은 능력이 모델 안으로 들어가 흔해지면 commoditized, 하네스가 모델이 풀 새 영역을 연다. 그러면 바퀴가 다시 돈다.

  1. 하네스가 더 어려운 작업을 해낼 수 있게 만든다.
  2. 더 많은 사용자가 에이전트로 시도한다.
  3. 더 많은 데이터가 모델 회사로 간다.
  4. 모델이 그 기술을 스스로 익힌다.
  5. 하네스가 덧대던 장치를 지운다.
  6. 하네스가 다음 영역을 연다. 다시 1번으로 돌아간다.

새 영역은 두 방향으로 열린다.

  • 코딩 밖의 일: GrokBot처럼 지식 업무 전반으로 넓어진다.
  • 개발자 일 중 코딩이 아닌 부분: 연차가 올라갈수록 코딩 비중은 줄고 다른 일이 중요해진다.

발표자는 이 플라이휠을 발표의 핵심으로 꼽는다. 모델과 하네스가 함께 바퀴를 돌린다.

소프트웨어 공장 10:50

소프트웨어 공장 software factory은 여러 에이전트가 소프트웨어 개발 전 과정을 함께 처리하는 구상이다. 아직 완성과는 거리가 멀다. 그래도 업계 곳곳의 하네스에서 새 시도가 이어진다. 발표자 회사 안에서는 이렇게 돌아간다.

  1. 누군가 채널에 버그를 올린다.
  2. 자동화가 바로 버그를 분류한다 triage.
  3. 클라우드 에이전트가 수정을 시도한다.
  4. 에이전트가 수정 전후 영상을 만들어 고쳐졌음을 보여 준다.
  5. 수정이 머지되어 배포가 시작되면, 배포 rollout 제품이 다른 에이전트를 띄워 프로덕션 문제를 지켜본다.
메타 하네스 발표자는 이 전체를 여러 에이전트를 함께 조율하는 "메타 하네스"로 보라고 한다. 에이전트 작업의 맨 앞에 서려면 맨 앞에 선 하네스가 필요하다. 이것이 하네스가 여전히 중요한 첫 번째 이유다.
08

모델이 흡수할 수 없는 것 12:00

두 번째 이유다. 하네스에는 모델이 아무리 똑똑해져도 대신할 수 없는 부분이 세 가지 있다.

실행 기반과 런타임 12:10

지난 1년 남짓 사이 에이전트 작업 하나의 길이가 몇 분에서 몇 시간, 며칠, 그 이상으로 늘었다.

노트북은 잠들 수 있다. 진짜 자율 동료라면 클라우드에서 돌아야 한다.

신뢰와 보안 12:40

셸과 API 키 파일만 준 단순한 하네스도 코딩 문제는 푼다. 하지만 모든 API 키를 모델에 넘기고 싶은 사람은 드물다. 회사의 보안 책임자라면 더 그렇다.

  • 회사에서는 권한을 특정 에이전트, 특정 사람 단위로 좁혀야 한다.
  • 개인에게도 가드레일이 필요하다. 아침에 일어나 보니 큰 사고가 나 있거나 1만 달러짜리 API 청구서가 와 있으면 안 된다.
효율 13:20

앞의 두 연구에서 점수는 비슷했다. 하지만 작업당 비용은 하네스마다 크게 달랐다.

발표자는 지난 한 달 동안 GrokBot 하네스의 효율을 다듬었다. 조정한 변수는 세 가지다.

  • 캐시 적중률 cache hit rate을 올렸다
  • 토큰 효율을 높였다
  • 모델 조합 model mix을 바꿨다

발표자에 따르면 품질은 그대로 두고 비용을 줄이고 속도를 높였다.

에이전트에게 맡기는 일이 많아질수록 효율 좋은 하네스의 가치도 커진다.

효율 개선 폭은 숫자 없이 말했다. 자기 회사 제품에 대한 주장이니 감안해 읽자.

하네스의 다음 흐름 14:20

정리되기 전에 더 지저분해진다 14:20

플라이휠이 빨라지고 있다. 제품이 다시 모델보다 빨리 움직이는 시기가 왔다. 그래서 하네스에 기능이 더 많이 붙는다. 정리는 그 뒤에 온다.

그러니 기능을 쉽게 넣고 쉽게 뺄 수 있도록 하네스를 설계해야 한다. 발표자는 이미 보이는 방법 세 가지를 든다.

안쪽을 덜 보여 준다 14:50

GrokBot 같은 제품은 하네스 안쪽 동작을 사용자에게 점점 덜 보여 준다. 배경에는 Hyrum의 법칙 Hyrum's Law이 있다. 사용자에게 보이는 것은 무엇이든 결국 누군가 의존하게 된다는 법칙이다.

얻는 것

바꿀 때 챙겨야 할 일이 줄어든다. 그래서 더 빨리 고칠 수 있다.

잃는 것

사용자가 안에서 무슨 일이 일어나는지 덜 보게 된다.

기본 부품으로 짓는다: 구독 15:20

프리미티브 primitive는 조합하고 확장해서 큰 기능을 만드는 기본 부품 인터페이스다. 프리미티브가 있으면 기능을 더해도 에이전트가 헷갈리지 않는다. 기능을 빼도 코드베이스를 크게 뜯어고칠 필요가 없다. 발표자는 "그냥 좋은 엔지니어링"이라고 말한다.

예로 든 프리미티브는 구독 subscriptions이다. 15:40 에이전트는 어떤 일이 생기면 깨어나야 한다.

하지 않는 방식이벤트마다 따로 연동Slack에 글이 올라옴, 관심 PR의 CI가 실패함, 정해진 시각이 됨
→
구독틀 하나, 도구 하나에이전트가 한 도구로 원하는 이벤트를 구독한다

임시 땜질은 추적해서 지운다 16:10

하네스에는 모델의 나쁜 행동을 정해진 규칙으로 막는 장치가 있다. 예를 들어 GrokBot이 사용자에게 답을 너무 늦게 하면 "사용자가 기다리고 있어요"라고 슬쩍 알려 준다.

발표자도 이런 장치는 꼼수라고 인정한다. 그래도 다음 모델 체크포인트를 기다리기보다 지금 고치는 편을 택한다. 대신 코드가 지저분해지지 않게 이렇게 관리한다. 이 장치를 shim(땜질)이라고 부른다.

  1. 모든 shim을 한곳에 모아 등록한다.
  2. shim이 발동할 때마다 기록을 남긴다.
  3. 봇이 발동 기록 대시보드를 지켜본다.
  4. 어떤 shim이 더 이상 발동하지 않으면, 에이전트가 "이 shim은 지워도 된다"는 PR을 올린다.

모델이 좋아져 문제 행동이 사라지면, 땜질도 자동으로 정리 대상이 된다. 앞에서 본 플라이휠의 5번 단계를 사람 손 없이 돌리는 셈이다.

발표자는 6개월 안에 에이전트 작업의 90%가 노트북 밖에서 돌 것이라고 예측한다. 이미 그쪽으로 가고 있다고 본다. 진짜 자율 에이전트와 원하는 방식으로 함께 일하려면 피할 수 없는 변화라는 것이다.

발표자 회사의 제품은 오래 살아 있는 에이전트를 운영하는 쪽이다. 클라우드 실행을 강조하는 이 예측도 그 점을 감안해 읽자.

결론 17:30

하네스는 죽었나? 발표자의 답은 둘로 나뉜다.

죽은 것

하네스를 코딩에 더 똑똑하게 만들던 부분.

플라이휠이 돌아 모델 안으로 들어갔다.

남는 것
  • 에이전트에게 다음 영역의 일을 여는 하네스
  • 신뢰와 보안
  • 효율
  • 실행 기반
어제의 하네스는 죽었을지 모른다. 그래도 내일의 에이전트 하네스는 오래 살아남는다.발표자의 마무리 말을 옮김
11

핵심 정리

  1. 하네스는 모델의 눈과 손이다. 실행 바탕인 런타임과, 모델이 무엇을 언제 보는지 정하는 맥락·조율 층으로 나뉜다.
  2. 비슷한 일의 이름이 프롬프트 엔지니어(2023), 컨텍스트 엔지니어(2025), 하네스 엔지니어링(2026)으로 바뀌었다.
  3. 모델이 똑똑해지며 Cursor는 편집 적용 모델, 코딩 지시문 같은 보조 장치를 지웠다.
  4. 연구 두 개에서 하네스를 바꿔도 코딩 점수는 크게 다르지 않았다. 하네스는 더 이상 코딩 지능을 더하지 않는다.
  5. 데이터 플라이휠: 하네스가 어려운 일을 열면 데이터가 쌓이고, 모델이 그 기술을 익히고, 하네스는 장치를 지운다.
  6. 코딩이 흔해지면 하네스가 다음 영역을 열어 바퀴를 다시 돌린다. GrokBot에서는 프롬프트와 가드레일을 다시 넣고 있다.
  7. 모델이 흡수할 수 없는 것은 클라우드 실행 기반, 신뢰와 보안, 효율이다.
  8. 점수가 같아도 작업당 비용은 하네스마다 크게 다르다. 조정 변수는 캐시 적중률, 토큰 효율, 모델 조합이다.
  9. 하네스는 더 지저분해진다. 안쪽을 덜 보여 주고, 프리미티브로 짓고, shim은 추적해서 지운다.
  10. 하네스의 부품은 LLM 호출에서 에이전트로 올라간다. 발표자는 6개월 안에 에이전트 작업의 90%가 노트북 밖에서 돌 것으로 본다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 나눈 하네스의 두 층은 각각 무엇을 맡나?
런타임은 에이전트 루프가 어디서 돌고 상태를 어떻게 저장할지 정한다. 맥락·조율 층은 어떤 모델을 언제 부르고, 모델이 무엇을 볼지 정한다.
Q2모델이 똑똑해지면서 Cursor가 지운 장치 두 가지는?
코드 편집을 파일에 적용하던 작은 전용 모델. 그리고 코드베이스 탐색법, 작업 확인법 같은 코딩 전용 지시문.
Q3UC Berkeley 연구와 Apple·EPFL 연구가 공통으로 보여 준 두 가지는?
하네스를 바꿔도 점수는 크게 달라지지 않았다. 하지만 작업당 비용은 크게 달랐다.
Q4데이터 플라이휠은 어떤 순서로 도나?
① 하네스가 어려운 작업을 가능하게 한다. ② 사용자가 늘어난다. ③ 데이터가 모델 회사로 간다. ④ 모델이 그 기술을 익힌다. ⑤ 하네스가 장치를 지운다. ⑥ 하네스가 새 영역을 열고 다시 ①로 돌아간다.
Q5Cursor는 장치를 빼는데 GrokBot은 왜 다시 넣나?
GrokBot이 다루는 새 분야와 새 일하는 방식에는 모델이 아직 잘 못하는 일이 많기 때문이다.
Q6GrokBot이 지금 집중하는 과제 네 가지는?
주요 웹 작업(슬라이드, 여행 예약), 질리지 않게 소통하기, 직접 할지 물을지 판단하기, 메모리로 사용자의 방식 배우기.
Q7소프트웨어 공장 예시에서 에이전트는 버그가 고쳐졌음을 어떻게 보여 주나? 배포 뒤에는 무슨 일이 일어나나?
수정 전후 영상을 만들어 보여 준다. 배포가 시작되면 다른 에이전트가 프로덕션에서 문제가 생기는지 지켜본다.
Q8모델이 흡수할 수 없는 하네스의 세 부분은?
실행 기반과 런타임, 신뢰와 보안, 효율.
Q9자율 동료가 클라우드에서 돌아야 한다는 근거는?
에이전트 작업 하나의 길이가 몇 분에서 며칠 이상으로 늘었다. 노트북은 잠들 수 있어서 그 시간을 버티지 못한다.
Q10발표자가 GrokBot 비용을 줄이려고 조정한 변수 세 가지는?
캐시 적중률, 토큰 효율, 모델 조합.
Q11Hyrum의 법칙은 무엇이고, 하네스 설계에 어떻게 이어지나?
사용자에게 보이는 것은 무엇이든 누군가 의존하게 된다는 법칙이다. 그래서 하네스 안쪽을 덜 보여 주면 바꿀 때 챙길 일이 줄어 더 빨리 고칠 수 있다.
Q12shim은 무엇이고, 어떻게 지우나?
모델의 나쁜 행동을 정해진 규칙으로 막는 임시 땜질이다. 한곳에 등록해 발동할 때마다 기록한다. 봇이 기록을 지켜보다가 발동이 멈추면 에이전트가 지우는 PR을 올린다.
