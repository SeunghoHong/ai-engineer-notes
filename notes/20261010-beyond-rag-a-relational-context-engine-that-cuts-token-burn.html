RAG가 못 푸는 나머지 절반

RAG는 내용 질문에는 강하지만 "지난주 내가 머지한 PR" 같은 구조 질문은 못 푼다. 발표자는 컨텍스트 엔진이 에이전트 비용을 절반으로 줄이는 데모를 보여 준 뒤, 자연어를 안전한 DB 쿼리로 바꾸는 엔진을 한 단계씩 쌓는다.

원본 영상: Beyond RAG: A Relational Context Engine That Cuts Token Burn 발표: Peter (Unblocked)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 들린 대로 쓰고 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트가 나오기 전에는 사람이 컨텍스트 층이었다. 컨텍스트 엔진은 코드, 문서, PR, Slack에 흩어진 조직 지식을 모아 작업에 맞는 묶음으로 건넨다.
  2. 발표자의 데모에서 같은 작업에 컨텍스트 엔진을 붙이자 비용은 2.60달러에서 1.29달러로, 시간은 3분에서 1분 30초로 줄었다. 발표자 회사 제품의 데모다.
  3. 검색에는 두 절반이 있다. 의미 검색(RAG)은 내용 질문을 맡는다. 구조 질의는 "지난주 내가 머지한 PR" 같은 필터, 집계, 시간 조건 질문을 맡는다.
  4. 자연어를 쿼리로 바꾸는 일 자체는 쉽다. 어려운 건 둘레다. 스키마 이해, 신원 연결, 검증, 자기 수정이 필요하다.
  5. 스키마 발견과 신원 연결은 절차적 코드로 대부분 해결된다. LLM은 애매할 때 판정만 맡긴다.
  6. 검증이 가장 중요하다. 위험한 연산자를 막는다. 테넌트 ID 같은 필드는 LLM에게 숨기고 코드가 뒤에서 붙인다.
  7. 검증에서 나온 오류는 LLM에 돌려줘 고치게 한다. 막은 기능 대신 전문 검색을 준다. 데모 엔진과 시뮬레이터는 오픈소스다.
01

사람이 컨텍스트였던 시절 01:00

AI 에이전트가 나오기 전에는 사람이 컨텍스트 층이었다. 새로 입사한 사람을 떠올리면 쉽다. 코드를 한참 읽고, 여러 문서 시스템을 뒤져야 일에 필요한 정보를 찾는다. 조직이 장애를 겪으며 쌓은 경험과 교훈도 따로 익혀야 한다.

지금까지사람이 직접 모은다코드, 문서, 장애 기록을 뒤져 맥락을 머릿속에 쌓는다

컨텍스트 엔진 context engine은 이 조직 지식 institutional knowledge을 끌어모으는 시스템이다. 흩어진 컨텍스트가 들어가고, 근거 있는 컨텍스트 grounded context가 나온다. 발표자는 좋은 컨텍스트의 성질을 네 가지로 들었다. 01:50

결국 답을 내놓는다. 발표자의 표현으로는 "알아냈다고 자신 있게 내세운다."

Claude가 Unblocked 컨텍스트 엔진을 부른다. 엔진은 이 작업에 맞춘 컨텍스트 묶음 context bundle을 돌려준다.

04

RAG가 못 푸는 질문 06:20

컨텍스트는 PR, 리뷰, 댓글, 이슈, 티켓, 문서, 대화에 흩어져 있다. 이 데이터는 의미로 검색할 수도 있고, 구조를 따라 질의할 수도 있다.

RAG retrieval-augmented generation는 질문과 의미가 가까운 자료를 찾아 모델에 붙여 주는 방식이다. 발표자는 RAG가 내용 질문을 확실하게 해낸다고 본다. 에이전트 루프에 파일 검색 도구까지 주면 아주 멀리 간다. 06:40

하지만 구조 질문은 다르다. 이건 의미 검색이 아니라 쿼리다. 07:10

의미 검색 · semantic retrieval
  • 이 기능의 코드는 어디 있나
  • 그 코드를 바꾼 PR은 무엇인가
  • 그 변경을 두고 논쟁한 Slack 스레드는

RAG, 벡터 저장소, 에이전트 루프로 푼다.

구조 질의 · structured query
  • 지난주 내가 머지한 PR
  • payments 코드를 가장 많이 리뷰한 사람
  • 지금 열려 있는 PR
  • 1월 1일부터 주별 비율을 그린 차트

이 발표가 만드는 쪽이다. 쿼리 엔진이 필요하다.

마지막 예는 앞의 데모에서 Richie가 처음 던진 질문이다. 07:20 시간 조건이 붙어 있다. 이런 정보는 벡터 저장소에 담겨 있지 않다. 그래서 벡터 검색으로는 답을 꺼낼 수 없고, 쿼리 엔진을 거쳐야 한다.

05

쿼리보다 둘레가 어렵다 08:10

목표는 자연어 질문을 구조화된 DB 쿼리로 바꾸는 것이다.

쿼리를 만드는 건 사실 쉬운 부분이다. 어려운 건 그 둘레에 세우는 비계다.발표자의 말을 옮김 · 08:20
  1. 스키마 이해: DB에 어떤 필드가 있는지 LLM에게 알려야 한다. 그래야 존재하는 필드만 쓰는 꽉 짜인 쿼리가 나온다.
  2. 신원 연결: "Rashene(추정)이 연 PR"이라고 물어도 LLM은 그 사람을 모른다. GitHub 아이디가 이름과 전혀 다를 수 있다. 이름과 계정을 이어 줘야 한다. 08:30
  3. 검증: LLM이 만든 쿼리는 믿을 수 없다. 위험한 연산이 들어 있거나 다른 고객의 데이터 경계를 넘을 수 있다. 실행 전에 맞고 안전한지 확인해야 한다. 08:50
  4. 자기 수정: 검증을 해도 오류는 난다. DB에서 실행할 때도 난다. 그때 LLM이 스스로 고치게 한다. 09:00
질문엔진이 알아야 할 것쿼리 모양 (예시)
Rashene(추정)이 연 PR 중 열린 것이 사람의 GitHub 아이디, PR 상태 필드{ state: "open", author: "<아이디>" }
내가 지난주 머지한 PR묻는 사람이 누구인지, 오늘 날짜{ author: "<내 아이디>", merged_at: { $gte: <7일 전> } }
제목에 authentication이 들어간 PR키워드로 찾는 방법{ $text: { $search: "authentication" } }

예시: 발표 화면의 쿼리를 옮긴 것이 아니다. 필드 이름은 이해를 돕기 위해 지었고 문법은 MongoDB 방식이다.

발표자는 오픈소스 저장소 document query engine을 띄워 놓고 단계를 하나씩 켠다. 09:50 처음에는 아무것도 연결되지 않아 질문을 해도 결과가 없다. 단계를 하나 올릴 때마다 같은 질문을 다시 던진다.

06

스키마 자동 발견 10:30

데모의 DB는 스키마리스 schemaless 문서 저장소다. 문서마다 필드가 달라도 되는 DB라는 뜻이다. 모든 DB가 그렇지는 않지만 같은 원리를 쓸 수 있다. 스키마를 실행 시점에 알아낸다.

  1. 저장소에서 문서를 많이 뽑아 표본을 만든다.
  2. 표본에서 필드와 타입을 추론해 스키마를 만든다.
  3. 까다로운 부분은 enum 추론이다. 어떤 필드가 정해진 몇 개 값만 갖는지 가려내는 일이다. 10:50
LLM부터 꺼내지 않는다 11:00 LLM을 만능 망치처럼 휘둘러도 결과는 꽤 괜찮다. 하지만 전통적인 절차적 방법만으로도 아주 멀리 간다. 비결정적으로 보이는 일이 실제로는 꽤 결정적인 경우가 많다.

데모에서는 GitHub PR 컬렉션의 스키마가 나왔다. 11:50 스키마와 함께 쿼리 속도를 높일 인덱스 정보도 나왔다.

발표자는 DB 이름을 말하지 않았다. "컬렉션"이라는 말과 서버에서 JavaScript를 실행하는 function 연산자 이야기로 보아 MongoDB 계열 문서 DB로 보인다(추정).

07

신원 연결과 쿼리 합성 12:00

신원 연결

신원 연결 identity resolution은 시스템마다 다른 사용자 이름을 실제 한 사람으로 묶는 일이다. 이것도 단순한 절차적 방법으로 풀린다. 발표자는 Unblocked 내부도 대체로 이렇게 한다고 했다. 12:20

  1. 여러 시스템의 사용자 이름과 신원을 모은다.
  2. 퍼지 매칭 fuzzy matching으로 비슷한 이름을 짝짓는다.
  3. 그래도 애매하면 후보 이름 목록을 LLM에 넘겨 판정만 맡긴다.

쿼리 합성 12:50

발표자는 이 단계가 사실 가장 쉽다고 했다. 재료를 모아 LLM에 넘기고 쿼리를 만들어 달라고 하면 된다.

  • 스키마: 앞에서 실행 시점에 알아낸 것
  • 현재 날짜와 시각: "지난주" 같은 말을 풀기 위해
  • 묻는 사람의 정보: "Peter의 PR"뿐 아니라 "내 PR"도 풀기 위해

이 단계를 켜자 같은 질문에 엔진이 쿼리를 만들고 문서를 가져왔다. 13:30

08

검증: 가장 중요한 단계 13:40

발표자는 검증을 가장 중요한 단계로 꼽았다. LLM이 만든 쿼리에는 무엇이든 들어 있을 수 있다.

위험한 연산자 13:50 예를 들어 function 연산자는 DB 서버에서 날 JavaScript를 실행한다. LLM이 쓴 쿼리가 이걸 그대로 실행하게 두면 안 된다.

막을 것은 연산자만이 아니다. 14:00

  • 숨은 필드: LLM에게 보여 주고 싶지 않은 필드가 있다. LLM이 그 필드를 추측해 쿼리에 넣는 것도 막아야 한다.
  • 테넌트 격리: 메타데이터에 테넌트 ID가 있고, 쿼리를 한 테넌트 안으로 묶어야 한다고 하자. 이 필드는 LLM이 아예 건드리지 못하게 한다. 대신 코드가 뒤에서 조건을 몰래 덧붙인다.

데모에서 "제목에 authentication이 들어간 PR"을 물었다. 14:50 LLM은 정규 표현식 regular expression으로 쿼리를 만들었다. 검증 엔진은 "정규 표현식은 허용되지 않는다"며 쿼리를 돌려보냈다.

이 데모 엔진이 정규 표현식을 막은 이유는 발표에서 설명하지 않았다.

09

자기 수정과 전문 검색 15:20

검증은 오류를 낸다. 그 오류를 그대로 LLM에 돌려주면 LLM이 스스로 쿼리를 고친다. 기술적으로는 이게 전부다. 최대 재시도 횟수를 둔 루프 하나다. 15:30

  1. 1차: 정규 표현식 쿼리를 만든다. 검증에서 거절된다.
  2. 재시도: 몇 번 시도한 끝에 통과하는 쿼리를 만든다. 제목이 정확히 일치하는 PR을 찾는 쿼리였다. 16:10
  3. 결과: 제목이 정확히 "authentication"인 PR은 없다. 결과가 비었다.
  4. 전문 검색 추가: 엔진에 전문 검색 full-text search을 붙인다. 제목 속 단어로 찾을 수 있게 된다. 16:20
  5. 다시 실행: 원하는 PR이 나온다. 17:00
이 흐름에서 배울 점 자기 수정 루프는 "통과하는 쿼리"를 찾을 뿐, "맞는 쿼리"를 보장하지 않는다. 검증으로 기능을 막았다면 같은 일을 안전하게 할 대안을 함께 줘야 한다.
10

완성된 엔진 17:00

처음부터 끝까지 쌓은 엔진은 RAG의 나머지 절반을 맡는다. 구조에 기댄 질문을 처리한다. 필터와 집계를 할 수 있고, 시간 범위를 다루고, 스스로 고친다. 17:10 전부 오픈소스라 구현을 직접 볼 수 있다.

단계하는 일주로 쓰는 것
스키마 발견표본 문서로 필드, 타입, enum, 인덱스를 알아낸다절차적 코드
신원 연결시스템마다 다른 이름을 한 사람으로 묶는다퍼지 매칭, 애매하면 LLM
쿼리 합성스키마, 현재 시각, 질문자 정보로 쿼리를 만든다LLM
검증위험 연산자와 숨은 필드를 막고 테넌트 조건을 붙인다절차적 코드
자기 수정오류를 LLM에 돌려주고 다시 만들게 한다LLM, 최대 재시도
전문 검색제목과 본문 속 단어로 찾는다DB의 검색 기능

표로 보면 LLM이 맡는 일은 좁다. 쿼리를 쓰고 고치는 일, 애매한 이름을 판정하는 일뿐이다. 나머지는 결정적인 코드가 한다.

채팅 에이전트 17:30

이 엔진은 채팅 에이전트의 도구로도 쓰인다. 발표자가 "지난주에 인증 관련해서 어떤 일을 했나?"라고 물었다. 에이전트는 자기가 만든 쿼리를 모두 보여 준다. 그 데이터를 받아 내용을 추론해 답한다. 18:00 발표자는 이를 "에이전트와 사람을 위한, 구조로 질의할 수 있는 컨텍스트"라고 정리했다.

11

컨텍스트 엔진 시뮬레이터 18:20

환경 제약 때문에 Unblocked를 바로 연결하기 어려운 팀을 위한 오픈소스 프로젝트다. 모든 것을 로컬에서 돌린다.

  1. 작업 하나마다 컨텍스트 묶음을 만든다.
  2. 같은 작업을 묶음이 있을 때와 없을 때로 A/B 테스트한다. 18:40
  3. 컨텍스트를 에이전트 손에 쥐여 줬을 때 얻는 이득을 보여 준다.

발표자는 화면의 QR 코드로 프로젝트를 안내했다. 19:00

자막에는 "PR code"로 나오지만 화면 안내 문맥상 QR 코드로 읽었다. 시뮬레이터는 발표자 회사가 만든 도구이고, 결과는 자기 환경에서 직접 확인하는 것이 좋다.

12

핵심 정리

  1. 에이전트 이전에는 사람이 컨텍스트 층이었다. 컨텍스트 엔진은 흩어진 조직 지식을 모아 작업별 묶음으로 건넨다.
  2. 좋은 컨텍스트는 서로 연결돼 있고, 작업 의도에 맞고, 묻는 사람에 맞고, 권한을 지킨다.
  3. 발표자의 데모에서 컨텍스트 엔진을 붙이자 비용과 시간이 약 절반으로 줄었다.
  4. 검색은 두 절반이다. 의미 검색은 내용 질문, 구조 질의는 필터, 집계, 시간 조건 질문을 맡는다.
  5. 쿼리를 만드는 건 쉽다. 어려운 건 스키마, 신원, 검증, 자기 수정이라는 둘레다.
  6. 스키마와 enum은 표본 문서에서 절차적으로 추론할 수 있다. 결정적인 일에 LLM을 먼저 꺼내지 않는다.
  7. 신원 연결은 퍼지 매칭으로 하고, 애매할 때만 LLM이 판정한다.
  8. LLM이 만든 쿼리는 믿지 않는다. 위험 연산자를 막고, 테넌트 같은 필드는 LLM에게 숨기고 코드가 붙인다.
  9. 오류는 LLM에 돌려줘 고치게 한다. 최대 재시도 횟수를 둔 루프면 충분하다.
  10. 검증으로 막은 기능에는 대안이 필요하다. 정규 표현식을 막았다면 전문 검색을 준다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1컨텍스트 엔진이 내놓는 근거 있는 컨텍스트의 네 가지 성질은?
서로 연결됨, 작업 의도에 맞춤, 묻는 사람에 맞춤(개인화), 권한 인식.
Q2컨텍스트 엔진 없이 Claude가 새 작업을 받으면 먼저 무엇을 하나?
신입 사원처럼 코드베이스를 이리저리 뒤진다. 그 탐색에 비용과 시간이 든다.
Q3데모 1에서 컨텍스트 엔진 유무에 따른 비용과 시간은?
없이: 최대 2.60달러, 3분. 사용: 1.29달러, 약 1분 30초. 둘 다 약 절반이다. 발표자 회사 제품으로 한 세션 하나의 비교다.
Q4데모 2에서 코드 리뷰 이슈가 줄어든 원인과, 수정 PR 설명에 담긴 것은?
리뷰 모델 교체로 행동 특성이 바뀐 것이 가능성 높은 원인이었다. PR 설명에는 회귀를 일으킨 PR과, 이 문제를 논의한 Slack 대화의 데이터가 담겼다.
Q5RAG가 잘하는 질문과 못하는 질문을 하나씩 들면?
잘함: "이 코드를 바꾼 PR은?" 같은 내용 질문. 못함: "지난주 내가 머지한 PR" 같은 구조 질문. 후자는 의미 검색이 아니라 쿼리다.
Q6"1월 1일부터 주별 비율 차트"를 벡터 저장소로 풀 수 없는 이유는?
시간 조건과 집계가 필요한데, 그 정보는 벡터 저장소에 담겨 있지 않다. 쿼리 엔진을 거쳐야 한다.
Q7쿼리 생성 말고 엔진에 필요한 네 가지 둘레는?
스키마 이해, 신원 연결, 검증, 자기 수정.
Q8스키마 발견과 신원 연결에서 발표자가 권한 방식은?
절차적 방법을 먼저 쓴다. 스키마는 표본 문서에서 추론하고, 신원은 퍼지 매칭으로 묶는다. LLM은 애매한 이름의 판정에만 쓴다.
Q9테넌트 ID 같은 필드는 어떻게 다루라고 했나?
LLM이 아예 건드리지 못하게 숨긴다. 쿼리를 한 테넌트로 묶는 조건은 코드가 뒤에서 덧붙인다.
Q10자기 수정 루프가 통과시킨 쿼리가 결과를 못 낸 이유와 해결책은?
정규 표현식이 막히자 제목이 정확히 일치하는 쿼리로 바꿨는데, 그런 제목의 PR이 없었다. 엔진에 전문 검색을 붙여 해결했다.
Q11컨텍스트 엔진 시뮬레이터는 무엇을 보여 주나?
작업마다 컨텍스트 묶음을 만들고, 같은 작업을 묶음이 있을 때와 없을 때로 A/B 테스트해 차이를 보여 준다. 로컬에서 돌린다.

용어뜻

조직 지식Institutional knowledge. 조직이 일하며 쌓은 결정, 경험, 장애의 교훈

벡터 저장소Vector store. 글을 의미를 담은 숫자 목록으로 바꿔 저장하고, 비슷한 것을 찾아 주는 DB
의미 검색Semantic retrieval. 뜻이 비슷한 자료를 찾는 검색
구조 질의Structured query. 필드 값, 날짜, 개수처럼 정해진 구조를 조건으로 데이터를 찾는 질의
에이전트 루프모델이 도구를 부르고 결과를 보고 다음 행동을 정하기를 반복하는 실행 방식
스키마데이터에 어떤 필드가 있고 각 필드가 어떤 타입인지 정리한 설계도
스키마리스Schemaless. 문서마다 필드 구성이 달라도 저장할 수 있는 DB 방식
enum정해진 몇 개 값만 갖는 필드. 예: PR 상태(open, closed)
인덱스DB가 데이터를 빨리 찾도록 따로 만들어 두는 목차
신원 연결Identity resolution. 시스템마다 다른 계정 이름을 실제 한 사람으로 묶는 일
퍼지 매칭Fuzzy matching. 철자가 조금 달라도 비슷한 문자열을 같은 것으로 짝짓는 방법
테넌트Tenant. 한 시스템을 같이 쓰는 고객 조직 하나하나. 서로의 데이터를 볼 수 없어야 한다
정규 표현식Regular expression. 문자열 패턴을 적는 작은 언어
전문 검색Full-text search. 글 속 단어로 문서를 찾는 검색. 미리 검색용 인덱스를 만든다
결정적Deterministic. 같은 입력이면 늘 같은 결과가 나오는 성질
A/B 테스트조건 하나만 바꾼 두 가지를 같은 일에 돌려 결과를 비교하는 실험
