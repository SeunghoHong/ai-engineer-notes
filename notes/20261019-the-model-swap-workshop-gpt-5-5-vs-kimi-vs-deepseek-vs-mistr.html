모델을 바꾸면 무엇이 달라지나

같은 코드에서 모델 이름만 바꿔 GPT-5.5, Kimi K2.6, DeepSeek V4 Flash, Mistral Large 3를 여러 시나리오로 비교한 실습이다. 차이는 바로 드러나고, 그 차이는 자동 평가와 프롬프트 자동 최적화로 줄여 나갈 수 있다.

원본 영상: The Model Swap Workshop: GPT-5.5 vs Kimi vs DeepSeek vs Mistral 발표: Pamela Fox (Microsoft)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 결과와 수치는 모두 발표자가 화면에서 보여 주거나 말한 것이고, 원 출처를 따로 확인하지는 않았다. LLM은 실행할 때마다 답이 달라질 수 있다. 여기 적힌 결과는 그날 시연 한 번의 결과다. 자막에서 뭉개진 이름(GPT-5.5, Kimi, GEPA, Ollama 등)은 알려진 이름으로 바로잡았다. mm:ss는 영상 위치다.

3분 요약
  1. 벤치마크로는 내 시나리오의 결과를 알 수 없다. 모델 이름 한 줄만 바꿔 같은 시나리오를 돌려 보면 차이가 바로 보인다.
  2. 문장 속 e 세기에서 GPT-5.5와 Kimi는 13개를 맞혔다. DeepSeek은 6개, Mistral은 8개라고 답했다. 단계별로 세라고 프롬프트를 고치자 Mistral도 맞혔다.
  3. RAG에서는 자료에 없는 것을 모른다고 하는지를 본다. Mistral은 자료에 없는 내용을 자기 지식으로 채웠고, 프롬프트를 고쳐도 일부만 나아졌다.
  4. 이미지 이해는 프롬프트로 거의 못 고친다. 실제로 받을 이미지와 실제 언어로 시험해야 한다.
  5. 도구 호출과 에이전트에서는 정답보다 효율에서 차이가 났다. 호출 횟수와 병렬 호출이다. 병렬 호출은 GPT-5.5만 했다.
  6. 실제 서비스에는 자동 평가가 필요하다. 문자열 비교 → LLM 심판 → 스펙으로 평가를 만드는 도구 순서로 보여 줬다. 기본 제공 평가 대신 맞춤 평가를 만들라고 했다.
  7. 모델마다 프롬프트를 손으로 고치는 대신 DSPy와 GEPA가 프롬프트를 찾게 하면 작은 모델로도 원하는 결과를 노릴 수 있다.
01

워크숍 준비와 목표 00:10

참가자는 발표자의 저장소를 받아 따라 했다. 발표자가 나눠 준 .env 파일에 모델 접속 정보가 들어 있다.

  • Python과 uv가 있으면 저장소를 내려받고 uv sync 한 번이면 준비가 끝난다.
  • 없으면 GitHub Codespaces를 쓴다. 브라우저 안에서 열리는 VS Code이고, 필요한 환경이 다 갖춰져 있다.
  • 배포된 모델에는 토큰 한도가 있다. 요청이 몰리면 429 오류 rate limit exceeded가 날 수 있다. 그래서 .env에 다른 프로젝트 주소도 주석으로 넣어 두었다.

왜 모델을 바꿔 봐야 하나 02:20

목표는 최상위 모델들이 실제로 어떻게 다른지 손으로 느껴 보는 것이다. 무엇을 고치면 나아지는지도 함께 본다.

발표자는 이것을 AI 엔지니어 모두가 해야 할 일로 본다. 새 모델은 끊임없이 나온다. 발표자는 "미국 정부가 언제든 어떤 모델의 접근을 끊을 수도 있다"는 예도 들었다. 앱이 다른 모델을 가리켜도 돌아가야 하고, 안 돌아가면 어떻게 고칠지 알아야 한다.

비교한 네 모델 03:10

모델이 워크숍에서의 위치
GPT-5.5발표자가 평소에 쓰는 모델. 모든 예제의 기본값이자 기준선
Kimi K2.6최근 나온 모델. 발표자는 "꽤 좋다"고 소개했다

네 모델은 모두 Microsoft Foundry 프로젝트 하나에 배포돼 있다. Anthropic 모델은 이용 조건이 달라 별도 프로젝트에 두었고, 마지막에 잠깐 다룬다.

벤치마크로는 모른다 05:00

모델은 벤치마크로도 비교할 수 있다. 품질 점수, 안전 점수, 비용, 처리량 throughput 같은 숫자다. 이걸로 대략적인 감은 잡힌다.

하지만 모델을 쓰는 방식은 너무 다양하다. 어떤 벤치마크도 내 시나리오에서 모델이 어떨지 알려 주지 않는다. 그래서 저장소에 여러 시나리오를 담고, 시나리오마다 모델을 바꿔 가며 돌린다.

실습 방식: 모델 한 줄만 바꾼다 모든 예제 파일은 맨 위의 모델 변수 하나로 시작한다. 기본값은 GPT-5.5다. 다른 모델 줄의 주석을 풀면 그 모델로 바뀐다. 연결은 OpenAI Python SDK로 Foundry 주소에 붙고, 키는 환경 변수에서 읽는다.
02

글자 세기: 한 번 호출 05:40

가장 단순한 형태부터 시작한다. LLM에 요청 한 번을 보내는 것이다. 요청은 OpenAI의 응답 API Responses API로 보냈다.

질문은 LLM이 약하기로 유명한 "세기"다. "다음 문장에 e가 몇 번 나오나? The elderly gentleman eagerly entered the elevator. 꼼꼼히 세라."

발표자는 GPT-5.5가 계산에 놀랄 만큼 강하다고 했다. 금융 벤치마크를 돌려 본 동료들이 "머릿속으로 계산을 엄청 해낸다"고 했다는 전언이다.

프롬프트를 고치면 07:40

모든 모델을 쓰고 싶다면 프롬프트 엔지니어링을 시작하게 된다. 발표자는 이렇게 덧붙였다. "문장을 단어로 나누고, 단어별로 세고, 더하고, 풀이를 보여 줘."

이렇게 답을 바로 내지 않고 풀이 과정을 거치게 하는 기법을 단계별 사고 유도 chain of thought라고 한다. Mistral은 이 프롬프트로 13개를 맞혔다.

첫 실험에서 얻는 교훈은 두 가지다. 모델마다 분명히 차이가 있다. 그리고 프롬프트를 바꾸면 결과도 바뀐다.

정답 13은 직접 세어 확인했다. The(1), elderly(2), gentleman(2), eagerly(2), entered(3), the(1), elevator(2)다. 자막에는 기본 모델이 "GPT-3.5"로 찍힌 곳이 있지만, 배포한 모델 목록과 흐름으로 보아 GPT-5.5다.

03

RAG: 모르면 모른다고 하나 08:30

RAG Retrieval-Augmented Generation는 검색한 자료를 넣어 주고 그 자료를 바탕으로 답하게 하는 방식이다. 발표자는 "에이전트도 결국 RAG"라고 할 만큼 여전히 가장 큰 쓰임새로 본다.

RAG에서 중요한 것은 근거 충실성 grounding이다. 답은 주어진 자료 안에서만 나와야 한다. 모델이 학습으로 외운 지식, 즉 가중치 weights에서 꺼낸 내용을 자료에 있던 척하면 안 된다.

발표자 관찰로는 이 점이 모델마다 크게 다르다. 작고 덜 강한 모델일수록 가중치에서 꺼내 자료에 있던 척한다.

실험 설계: 함정 질문 자료에는 목수벌 carpenter bee 정보만 있다. 질문은 "꿀벌과 목수벌이 둥지를 짓는 방식은 무엇이 다른가?"다. 좋은 답은 목수벌 내용만 말하고, 꿀벌은 자료에 없어서 모른다고 하는 것이다. 시스템 프롬프트는 "자료를 근거로 답하고 출처를 달아라"였다.
모델결과
GPT-5.5"자료에 꿀벌 둥지 정보가 없다"고 답했다. 발표자는 GPT-5.5가 자기가 모르는 것을 아는 데 아주 능하다고 했다
Kimi K2.6발표자는 "Kimi도 잘한다"고만 하고 시연은 건너뛰었다
DeepSeek V4 Flash"자료에 그 정보가 없다"고 답했다
Mistral Large 3자료에 없는 꿀벌 정보를 가중치에서 꺼내 답했다

프롬프트로 강제해 보기 11:20

발표자는 프롬프트에 이렇게 더했다. "답의 정보가 자료에 없으면 '출처 없음'이라고 써라. 지어내지 마라."

의도는 이렇다. 답의 정보 하나하나를 출처와 짝짓게 하면, 모델이 "이건 자료에 없었네" 하고 스스로 알아챌 수 있다.

결과는 절반의 성공이었다. Mistral은 꿀벌 내용에 "출처 없음"을 붙였다. 그런데 정보는 그대로 줬다. 자료에 없다는 건 알았지만 말하는 걸 멈추지는 않은 것이다.

RAG용 모델을 고를 때 볼 것은 두 가지다. 모르는 것을 인정하는가. 지어낼 가능성은 얼마나 되는가. 발표자가 가장 많이 다루는 분야가 RAG라서 특히 강조한 대목이다.

언어를 바꾸면 16:10

이 모델들은 모두 영어 중심이다. 발표자가 같은 질문을 스페인어로 "caimanes o cocodrilos?"라고 물었더니 틀린 답이 나왔다.

발표자의 해석은 이렇다. 모델은 앨리게이터와 크로커다일을 구분해야 한다. 동시에 스페인어 caimán이 무엇을 가리키는지도 풀어야 한다. 이 단어는 앨리게이터를 부르는 말로도 쓰이고, 카이만이라는 다른 동물을 뜻하기도 한다. 두 가지를 한 번에 하기엔 너무 어려운 과제가 된다.

발표자가 있는 캘리포니아에는 스페인어 사용자가 많아서 앱이 두 언어를 지원하는 경우가 흔하다. 지원할 언어마다 따로 시험해야 한다.

05

도구 호출 17:10

도구 호출 tool calling, function calling은 모든 에이전트의 바탕이다. 모델은 학습 과정에서 이 능력을 따로 훈련받는다. 함수 정의와 사용자 입력을 보고, 어떤 함수를 어떤 인자로 부를지 정한다.

함수는 JSON 스키마 JSON Schema로 정의해 모델에 보낸다. 이 예제의 함수는 create_calendar_event다. 이름, 설명, 매개변수가 들어 있다. 매개변수마다 타입과 설명이 붙는다. 예를 들어 제목은 문자열이다.

도구 정의도 프롬프트다 객체처럼 보이지만 발표자는 이것도 프롬프트 엔지니어링이라고 강조한다. 어떤 타입을 쓸지, 어떤 설명을 달지, 매개변수 이름을 뭐라 할지가 모두 모델이 함수를 어떻게 부를지 정하는 재료다.

사용자 메시지는 이렇다. "캘린더에 일정 하나 넣어 줘. 플랫폼 팀 싱크야. 나, Sarah, Marcus, 새 PM Priya. 내일 오후 1시 30분. Microsoft Teams로 온라인." 시스템 프롬프트는 "너는 캘린더 비서다. 오늘은 6월 29일 월요일이다. 도구를 써서 요청을 처리하라"였다.

모델은 함수 이름과 인자만 돌려준다. 함수를 실제로 실행하는 건 개발자 코드다. 확인할 것은 두 가지다. 맞는 도구를 불렀나. 기대한 인자를 넘겼나.

틀린 인자는 모호함의 신호 20:20

모델이 엉뚱한 인자를 넣었다면 설명이 모호했다는 뜻이다. 그럴 땐 설명을 더 구체적으로 고친다. 예를 들면 "나나 너는 빼고 이름이 나온 참석자만", "성과 이름이 있으면 둘 다" 같은 문구다. 그다음 여러 입력으로 다시 평가한다.

06

도구 호출 반복과 효율 21:00

에이전트는 목표에 닿을 때까지 도구를 반복해서 부른다. 그 전 단계로, 도구 하나를 반복해서 쓰는 예제를 봤다.

도구는 calculate 하나다. 수식을 받아 결과를 돌려준다. 문제는 쇼핑 계산이다. "가게가 세일 중이다. 셔츠 3장을 사고 세금을 내면 총액은?"

푸는 길은 두 가지다. 작은 수식을 하나씩 여러 번 계산할 수도 있다. 영리한 모델이라면 전부를 긴 수식 하나로 묶어 한 번에 끝낼 수도 있다.

여기서 재는 것은 효율이다. 반복 단계에 들어가면 모델 간 차이는 주로 여기서 난다. 같은 목표에 얼마나 빨리, 몇 번의 호출로 가는가.

시스템 프롬프트는 "머릿속으로 계산하지 마라" 한 줄이다. 자기 암산 실력을 믿고 도구를 건너뛰려는 GPT-5.5를 위해 넣은 말이다.

호출 하나하나가 네트워크 요청이다. 호출이 늘면 그만큼 시간이 늘어난다. 그래서 모델을 평가할 때는 최종 답과 함께 몇 번 만에 거기 닿았는지도 본다.

발표자가 Kimi를 자주 건너뛴 이유는 대부분 GPT-5.5와 거의 대등해서다. 다만 Kimi는 가끔 스스로 검산하다 이상한 반복에 빠진다. 전날에는 첫 시도에 정답을 내고도 확인한다며 4번쯤 더 호출했다. 이날 시연에서는 잘했다. 같은 모델도 실행마다 행동이 다를 수 있다는 뜻이다.

07

에이전트: 여행 플래너 24:10

이제 제대로 된 에이전트를 만든다. 보통은 에이전트 프레임워크를 쓴다. 저장소에는 LangChain, Pydantic AI, Agent Framework 세 가지 버전이 있다. 청중 투표로 LangChain v1을 골랐다.

예제는 여행 계획 에이전트다. 도구는 네 개다.

  • search_flights: 항공편 검색
  • search_hotels: 호텔 검색
  • check_budget: 고른 항공편과 호텔이 예산 안에 드는지 확인
  • search_activities: 도시의 즐길 거리 검색

시스템 프롬프트의 규칙은 이렇다. 항공편과 호텔을 모두 검색한다. 직항을 우선한다. 예산은 항상 확인한다. 남은 예산으로 마지막에 즐길 거리를 찾는다. 사용자는 "다음 달 샌프란시스코에서 뉴욕까지 3박, 총예산은 얼마, 직항, 즐길 거리 하나"를 요청한다. 어떤 도구가 불렸는지 보려고 미들웨어 middleware도 붙였다.

GPT-5.5의 흐름 26:00

  1. 1턴: 항공편 검색과 호텔 검색을 동시에 요청했다. 둘 사이에 의존 관계가 없다고 판단한 것이다.
  2. 2턴: 받은 항공편 가격과 호텔 가격으로 예산을 확인했다.
  3. 3턴: 남은 예산으로 즐길 거리를 검색했다.

발표자는 이것을 이 시나리오에서 가장 효율적인 에이전트라고 했다.

1턴처럼 서로 의존하지 않는 도구 여러 개를 한 턴에 함께 부르는 것을 병렬 도구 호출 parallel tool calling이라고 한다. 서버는 두 데이터베이스에 요청을 동시에 보낼 수 있어 빨라진다.

모델과 하네스를 함께 비교한다 27:30

프레임워크마다 도구 호출을 반복하는 방식이 조금씩 다르다. 이 반복 장치를 하네스 harness라고도 부른다. 그래서 모델끼리만이 아니라 모델과 하네스의 조합을 비교해야 한다.

모델병렬 호출도구 호출 수끝까지 했나메모
GPT-5.5함 (1턴)4완료3턴 만에 끝냄
Kimi K2.6안 함5완료항공편과 호텔을 두 턴에 나눠 검색. 다른 선택지를 확인하느라 예산 확인을 2번 함
DeepSeek V4 Flash안 함4완료발표자 평가: "꽤 효율적"
Mistral Large 3안 함2중단항공편과 호텔만 검색하고 멈춤

발표자는 Kimi가 "도구 호출을 2번 더 했다"고 말했다. 설명대로 세면 호출은 5번으로 GPT-5.5(4번)보다 1번 많다. Kimi는 병렬 호출을 하지 않았으니 턴 수로는 3번 대 5번이다. "2번 더"는 턴 수 기준으로 보면 맞다.

발표자는 Kimi가 병렬 호출을 지원하지 않는 건지, 이번에만 안 한 건지는 모르겠다고 했다.

에이전트 평가가 가장 어려운 이유 28:30

"에이전트는 어떻게 평가하나요?"는 발표자가 가장 많이 받는 질문이다. 에이전트는 중간에 일어나는 일이 너무 많다. 맞는 도구를 불렀나. 효율적으로 불렀나. 병렬로 불렀나. 모두 따로 봐야 한다.

Mistral은 마지막 단계를 자주 잊는다. 에이전트는 컨텍스트 창 context window이 차면 앞의 지시를 잊거나 덜 꼼꼼해진다. 그래서 중간에 "마지막 단계도 해야지" 하고 일깨워야 할 때가 있다.

멈춘 에이전트를 다시 밀어 주기 29:50 "정말 다 했나?" 하고 다시 묻는 장치를 붙인다. 발표자는 Geoffrey Huntley가 만든 Ralph 루프를 예로 들었다. 기본 반복 방식보다 에이전트를 더 끈질기게 몰아붙이는 방법이다.

다른 두 프레임워크의 코드도 거의 같다. 발표자는 요즘 에이전트 프레임워크가 다른 점보다 비슷한 점이 많다고 본다.

08

평가 1: 문자열 비교 30:20

지금까지는 손으로 돌려 보고 눈으로 확인했다. 감을 잡기엔 좋다. 실제 서비스에는 많은 사례를 자동으로, 믿을 만하게 돌리고 결과를 비교하는 평가 eval가 필요하다.

첫 단계는 문자열 비교다. 캘린더 예제처럼 모델이 인자를 돌려주면 그대로 비교하면 된다. "장소로 virtual을 줬나?" 도구 한 번 호출이라면 맞는 도구와 맞는 인자만 확인하면 된다.

사례는 많고, 늘리기 쉬워야 한다 31:30

서비스를 내보내면 사용자가 실제로 어떻게 쓰는지 보게 된다. 그러면 새 사례가 생긴다. 그 입력을 평가 세트에 계속 넣어야 평가가 실제 사용과 멀어지지 drift 않는다. 운영 중 들어온 입력을 평가 사례로 옮기는 체계가 필요하다.

발표자가 넣은 사례 종류는 이렇다.

  • 날짜 계산. 윤년이 끼면 더 어렵다
  • 애매한 기간 표현
  • 스페인어 입력. 지원할 언어마다 시험한다
  • 아주 구어체인 입력. 예: "Yo, can you book the big conference room?"
팁: 날짜 계산은 도구에 맡긴다 32:20 발표자는 LLM을 평가할 때 늘 날짜 계산을 확인한다. 대개 잘 못하기 때문이다. 날짜를 다뤄야 한다면 날짜 계산 도구를 주라고 권했다.

이날은 비교하려고 모든 모델로 돌렸다. 평소에는 한 모델로 돌리고 이전 실행 결과와 비교한다. 이전 실행은 다른 모델이었을 수도 있다.

평가는 pytest 같은 일반 테스트 묶음에 넣지 않는다. 느리고 비싸기 때문이다. 이날 결과는 발표자가 "이번엔 다들 꽤 잘했다"고 할 정도였다.

평가 프레임워크는? 33:50

청중이 문자열을 직접 비교하는 것보다 나은 도구가 있느냐고 물었다. 발표자의 답은 이렇다.

  • 관측 도구 observability 대부분이 평가 기능을 내장한다. Langfuse, LangSmith, Arize 등이다.
  • Foundry 쪽에는 Azure AI Evaluation SDK와 OpenAI 패키지의 evals가 있다. 저장소에 예제가 있다.
  • 그 밖에 DeepEval이 있고, JavaScript라면 promptfoo가 있다.

다만 문자열 비교로 충분한 경우라면 거창한 도구가 필요 없다. 병렬 호출 여부처럼 도구 호출 과정을 봐야 할 때 더 정교한 방법이 필요하다.

09

평가 2: LLM 심판 35:10

대부분의 출력은 흐릿하다. 비교할 정답 문자열이 없다. 이럴 때 다른 LLM이 판단하게 한다. 이것을 LLM 심판 LLM-as-a-judge이라고 한다. 여러 프레임워크가 이 기능을 감싸 주지만, 발표자는 원리를 보이려고 코드로 직접 썼다.

심판에게 주는 프롬프트는 세 부분이다.

  1. 역할: "너는 평가자다." 무엇을 평가하는지 알려 준다.
  2. 출력: 통과인지 실패인지 고르게 한다. 이유도 함께 쓰게 한다. 발표자는 이유가 아주 유용하다고 했다.
  3. 입력: 질문과 응답을 준다. 근거 충실성을 본다면 원래 자료도 준다.

평가할 대상에 따라 더 많은 정보가 필요하다. 도구 호출이 효율적이었는지 보려면 도구 정의와 실제 호출 기록 trace까지 줘야 한다. 좋은 심판은 입력과 출력만이 아니라 과정 전체를 본다.

이 예제는 심판 모델로 GPT-5를 쓰고, 결과를 JSON으로 받았다.

심판은 느리고 비싸다 36:50

사례 하나마다 앱이 LLM을 한 번 부르고, 심판이 또 한 번 부른다. 사례 하나가 LLM 호출 두 번이다. 심판을 다섯 개쯤 두는 경우도 흔하다. 그러면 심판마다 호출이 하나씩 더 붙는다.

발표자는 RAG를 평가할 때 사례가 최소 200개, 많게는 800개는 있어야 한다고 했다. 그래서 모든 커밋, 모든 CI에서 돌리기는 어렵다. 얼마나 자주 돌릴지 따로 정해야 한다.

예시 계산 (발표에 없는 계산) 사례 200개에 심판 5개를 둔다고 하자. 사례마다 앱 호출 1번과 심판 호출 5번이 든다. 합치면 LLM 호출 1,200번이다. 사례가 800개면 4,800번이다.

심판도 틀린다 37:50

이 예제는 앱의 질문과 답을 미리 돌려 저장해 두고 심판만 따로 돌렸다. 흔히 쓰는 방식이다. 이렇게 하면 앱과 따로 심판을 고칠 수 있어 효율적이다.

심판을 따로 고칠 일은 자주 생긴다. 심판 자체가 잘못 만들어진 경우가 많기 때문이다. 결과가 나쁘면 문제가 앱인지 심판인지부터 가려야 한다.

그래서 심판을 사람 판단에 맞춰 보정 calibration한다. 도메인 전문가가 데이터에 통과와 실패 라벨을 달고, 심판의 판단과 일치하는지 본다.

결과는 대부분의 모델이 3문제 중 2개를 통과했다. Mistral은 1개였다. 근거 충실성을 더 손봐야 한다는 뜻이다.

발표자는 평가를 더 배우려면 Hamel Husain의 Hamel.dev를 보라고 추천했다. 평가 자료와 강의가 많다고 했다. 그 자료의 핵심 메시지로 "LLM 심판을 믿으려면 보정해야 한다"를 짚었다.

10

평가 3: 스펙으로 평가 만들기 40:00

좋은 심판을 만들기는 어렵다. 모범 사례를 따로 공부해야 할 정도다. 발표자는 Microsoft Research가 지난주쯤 낸 새 도구 Assert(추정)를 소개했다. 스펙을 주면 심판을 만들어 준다.

스펙에는 세 가지를 쓴다. 어떤 에이전트를 만드는지. 대략 어떻게 동작해야 하는지. 어떤 사용자를 지원해야 하는지. 도구는 이 스펙을 실제 채점 기준 rubric으로 풀어내고, 테스트 사례를 많이 만든다. 발표자는 연구에 기반한 방법이라고 설명했다.

YAML로 쓰는 스펙 40:50

  • 설정은 YAML 파일 하나다. 발표자는 YAML이 싫지만 이 용도에는 다른 어떤 형식보다 낫다고 했다.
  • 맥락, 심판 모델, 신경 쓰는 차원을 적는다. 예를 들면 예산 압박이다. 넉넉함, 빠듯함, 불가능으로 나눈다.
  • 이렇게 조건별로 나눠 사례를 골고루 만드는 것을 계층화 stratification라고 한다. 미리 정해도 되고 도구가 정하게 둬도 된다.
  • YAML 작성을 돕는 에이전트 스킬도 있다. 아무도 직접 쓰고 싶어 하지 않으니까.
  • 평가 대상은 앞의 LangChain 여행 플래너다. 모든 도구 호출이 기록되게 해 둔다. 제대로 평가하려면 호출 하나하나를 봐야 하기 때문이다.

결과 42:20

실행 시간이 꽤 걸려서 미리 돌려 두었다. 결과는 간단한 화면에서 본다.

  1. 행동 범주: 예산으로 불가능한 요청, 직항 선호 규칙 위반, 필수 도구 사용 등. 허용되는 행동과 아닌 행동을 정리한다.
  2. 테스트 세트: 실제 사용자를 흉내 낸 시나리오들이다. 제목만 봐도 LLM이 지은 티가 나서 발표자가 재미있어했다. 출시 전에 평가 세트를 처음 만드는 일, 즉 부트스트랩 bootstrap을 도와준다.
  3. 모델 비교: DeepSeek, Kimi, GPT-5.5를 돌렸다. 숫자는 규칙 위반 수라 낮을수록 좋다. GPT-5.5가 훨씬 적었다. 발표자는 Kimi가 내내 대등해 보였기에 놀랐다고 했다. 구체적인 숫자는 자막에 나오지 않는다.

발표자도 이 도구는 나온 지 일주일이라 써 본 건 이게 전부라고 했다.

기본 평가 대신 맞춤 평가 44:30

"평가를 돌려라"라고 아무리 말해도 사람들은 안 돌린다. 돌리더라도 일관성 coherence, 유창성 fluency 같은 기본 평가만 돌린다.

그런 건 절대 돌리지 마라. LLM은 원래 일관성이 좋다. 일관성이 없다면 뭔가 아주 크게 잘못된 것이다.발표자의 말을 옮김

발표자는 RAG에 근거 충실성 groundedness과 관련성 relevance 평가를 가끔 쓴다. 하지만 대부분은 기본 평가가 원하는 것이 아니다. 에이전트가 일을 잘하는지 보려면 맞춤 평가가 필요하다. Assert는 그 맞춤 평가를 처음 만드는 일을 돕는다.

발표자는 Microsoft 소속이다. Assert는 Microsoft Research의 도구이고, 실습 환경인 Foundry도 Microsoft 제품이다. Assert에 대한 좋은 평가는 그 점을 감안해 읽자.

DSPy에 프롬프트 맡기기 45:20

모델을 바꿀 때마다 프롬프트를 손보고 평가를 다시 돌리는 건 고된 일이다. 어느 방향으로 고쳐야 할지도 모른다. 모델마다 무엇이 잘 통하는지 세세히 알 수 없기 때문이다.

발표자가 마지막으로 보여 준 방법은 DSPy다. 프로그램을 선언한다. 예를 들어 "사용자 입력을 받아 정해진 구조의 결과로 바꾼다"고 적는다. 지켜야 할 제약 조건도 선언한다. 그러면 DSPy가 평가를 돌려 보며 그 제약을 만족하는 프롬프트를 찾아 쓴다.

이때 쓰는 최적화 방법이 GEPA다. 유전 알고리즘 방식으로 다음에 시도할 더 나은 프롬프트를 만든다. 발표자는 이 과정을 지켜보는 게 정말 재미있다고 했다.

지금까지프롬프트가 코드 안에 있다모델을 바꿀 때마다 사람이 프롬프트를 고친다

예제: 단어 수와 첫 글자 맞추기 47:00

  • 검사: 결과가 제약을 지켰는지 확인하는 함수들을 둔다. 이 검사가 있어야 DSPy가 계속 고쳐 가며 점수를 올릴 수 있다. 이런 탐색을 언덕 오르기 hill climbing라고 한다.
  • 설정: 학생 모델 student model과 반성 모델 reflection model을 정하고 GEPA 최적화기를 돌린다.
  • 시간: 이 과제에서 약 6분 걸렸다.
  • 결과: 시스템 프롬프트 한 편이 나온다. Mistral에서 통하는 프롬프트다. 이날 가장 애먹인 모델이라 Mistral을 골랐다.

작은 모델로 옮겨 가기 48:10

이 방식이면 작은 모델, 가장 싼 모델로도 필요한 결과를 얻을 수 있다. 발표자는 Dropbox와 Shopify가 DSPy와 GEPA로 큰 모델에서 작은 모델로 옮겼다는 발표를 예로 들었다. 자체 인프라에 모델을 올린 경우도 있다고 했다.

프롬프트가 결과물이 되는 방식은 낯설다. 그래도 발표자는 이것이 모델 독립성을 크게 높여 준다고 본다. 더 많은 모델을 골라 쓸 수 있게 된다.

Anthropic 인용과 마무리 49:00

발표자의 정리는 간단하다. 모델 간 차이는 크다. 결과를 개선하고, 평가하고, 다시 개선하는 방법은 여러 가지다. 직접 여러 모델을 만져 보라고 권했다. 발표자 자신도 모델을 바꿔 볼 때마다 많이 배운다고 했다.

Anthropic 모델과 인용 기능 49:20

Anthropic 모델은 시연 내내 쓰지 않았다. 다른 API인 Messages API를 써야 해서 코드를 바꿔야 하기 때문이다.

그래도 발표자는 RAG에 특히 Anthropic 모델을 좋아한다. 인용 citations 기능이 모델에 내장돼 있어서다.

  1. 자료를 정해진 구조로 넣는다. 문서이고, 텍스트이고, 본문은 이것이라고 적는다.
  2. 인용 기능을 켠다.
  3. 모델은 인용이 붙은 텍스트 블록을 돌려주도록 학습돼 있다. 코드로 인용을 뽑아 화면에서 바로 링크할 수 있다.

모델을 부르는 방식 자체가 다른 것도 비교할 거리라는 뜻이다.

저장소와 로컬 모델 50:30

저장소는 계속 공개된다. 나눠 준 .env 키는 곧 교체한다. 발표자는 전날 Ollama 지원도 추가했다. 로컬 모델을 쓰려면 예제가 로컬 Ollama 서버를 가리키게 하고 모델 이름만 바꾸면 된다. 같은 API라서 대체로 그대로 돌아간다.

핵심 정리

  1. 벤치마크는 대략적인 감만 준다. 내 시나리오로 직접 돌려 봐야 모델이 어떨지 안다.
  2. 모델 이름 한 줄만 바꿔 같은 시나리오를 돌리면 차이가 바로 보인다.
  3. 단순한 세기에서도 답이 13, 13, 6, 8로 갈렸다. 단계별로 풀게 하는 프롬프트로 약한 모델을 끌어올릴 수 있다.
  4. RAG에서는 모르는 것을 모른다고 하는지 본다. 약한 모델은 자기 지식으로 빈칸을 채운다.
  5. 이미지 이해는 프롬프트로 거의 못 고친다. 실제 이미지와 실제 언어로 시험한다.
  6. 도구 정의(JSON 스키마)도 프롬프트다. 인자가 틀리면 설명의 모호함부터 고친다.
  7. 도구 반복과 에이전트에서는 호출 횟수와 병렬 호출이 차이를 만든다. 이날은 GPT-5.5만 병렬 호출을 했다.
  8. 평가는 문자열 비교, LLM 심판, 스펙 기반 생성 순으로 정교해진다. 느리고 비싸니 일반 테스트와 분리하고 실행 주기를 정한다.
  9. LLM 심판은 통과·실패와 이유를 함께 내게 하고 사람 라벨로 보정한다. 일관성·유창성 같은 기본 평가 대신 맞춤 평가를 만든다.
  10. DSPy와 GEPA로 프롬프트를 자동으로 찾으면 작은 모델로도 같은 결과를 노릴 수 있고, 특정 모델에 덜 묶인다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 모델을 바꿔 쓸 줄 알아야 한다고 본 이유 두 가지는?
새 모델이 끊임없이 나온다. 그리고 어떤 모델의 접근이 언제든 끊길 수 있다. 발표자는 미국 정부가 접근을 끊는 경우를 예로 들었다.
Q2e 세기에서 각 모델의 답과, Mistral을 정답으로 이끈 프롬프트 변화는?
GPT-5.5와 Kimi는 13, DeepSeek은 6, Mistral은 8이었다. 문장을 단어로 나누고, 단어별로 세서 더하고, 풀이를 보여 달라고 하자 Mistral도 13을 맞혔다.
Q3꿀벌·목수벌 RAG 실험에서 좋은 답은 어떤 모습인가?
자료에 있는 목수벌 내용만 답하고, 꿀벌은 자료에 없어서 모른다고 말하는 답이다.
Q4Mistral에게 '출처 없음'을 쓰게 했더니 어떻게 됐나?
꿀벌 내용에 "출처 없음"을 붙이긴 했다. 하지만 정보는 그대로 줬다. 조금 나아졌을 뿐 완전히 고쳐지지는 않았다.
Q5이미지 입력에서 프롬프트 엔지니어링의 효과가 작은 이유는?
모델은 이미지를 이해하거나 못 하거나다. 특정 분야에서 읽는 법 힌트를 주는 정도만 가능하다. 그래서 내가 보낼 종류의 이미지로 직접 시험해야 한다.
Q6도구를 정의하는 JSON 스키마가 왜 프롬프트 엔지니어링인가?
타입, 설명, 매개변수 이름이 모두 모델이 함수를 어떻게 부를지 정하는 재료이기 때문이다. 인자가 틀리게 나오면 설명이 모호하다는 신호다.
Q7계산기 문제에서 GPT-5.5와 DeepSeek은 어떻게 달랐고, 왜 중요한가?
GPT-5.5는 긴 수식 하나로 1번, DeepSeek은 4번 호출했다. 둘 다 정답이었다. 하지만 호출마다 네트워크 요청이라 시간이 늘어난다.
Q8병렬 도구 호출이란 무엇이고 왜 좋은가?
서로 의존하지 않는 도구 여러 개를 한 턴에 함께 부르는 것이다. 서버가 요청을 동시에 보낼 수 있어 빨라진다. 여행 예제에서는 항공편과 호텔 검색을 함께 불렀다.
Q9평가를 pytest 같은 일반 테스트 묶음에 넣지 말라는 이유는?
느리고 비싸기 때문이다. LLM 심판을 쓰면 사례 하나에 LLM 호출이 2번 이상 들고, RAG 평가에는 사례가 200~800개 필요하다.
Q10LLM 심판에게 무엇을 주고 무엇을 받나?
질문, 응답, 그리고 필요하면 원래 자료나 도구 정의와 호출 기록을 준다. 받는 것은 통과·실패 판정과 그 이유다.
Q11LLM 심판을 보정한다는 것은 무슨 뜻인가?
도메인 전문가가 단 통과·실패 라벨과 심판의 판단이 일치하는지 확인하는 것이다. 결과가 나쁠 때 문제가 앱인지 심판인지 가리는 데도 필요하다.
Q12DSPy를 쓰면 코드에 들어가는 것과 결과물로 나오는 것은 각각 무엇인가?
코드에는 스펙(입력·출력과 제약)과 그 제약을 확인하는 검사가 들어간다. 프롬프트는 GEPA 같은 최적화 과정이 내놓는 결과물이다.
