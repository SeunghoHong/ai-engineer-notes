에이전트에게 3주 맡긴 코드를 열어 보니

제품 관리자인 발표자는 개인 요약 시스템의 리팩터링을 3주 동안 코딩 에이전트에게 맡겼다가, 코드를 열어 보고 이름만 그럴듯한 구조를 발견했다. 처음부터 다시 만들며 찾은 답은 코드를 한 줄씩 읽는 대신 결과 기준표를 세우고 에이전트끼리 서로 검사하게 하는 것이었다.

원본 영상: I Let Agents Refactor My Codebase for 3 Weeks. Then I Read the Code. 발표: Keiji Kanazawa (Microsoft 제품 관리자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 바로잡았고, 확실하지 않으면 (추정)을 붙였다. 발표 화면은 자막에 담기지 않아서, 화면에만 나온 내용은 빠졌을 수 있다. mm:ss는 영상 위치다.

3분 요약
  1. 발표자는 개인용 요약 시스템을 에이전트 중심으로 바꾸는 일을 3주 동안 Claude Code와 Codex에게 맡겼다.
  2. 요약본에 엉뚱한 문장이 들어가 원인을 찾으려 했더니 트레이스가 없었다. "사실 에이전트가 아니라서"였다.
  3. 코드를 열어 보니 "스킬"과 "에이전트"는 이름뿐이었다. SKILL.md도 없고 에이전트 SDK도 쓰지 않았다.
  4. Codex는 단위 테스트를 실제 유료 모델에 연결했다. 한 주 지출이 평소의 5배가 됐다. 매일 돌던 에이전트의 결과는 비어 있었다.
  5. 발표자는 처음부터 다시 만들었다. 이번에는 스펙에 더해 결과가 어떠해야 하는지 적은 기준표를 줬다.
  6. 에이전트는 기준표 점수를 올리도록 반복 개선한다. 발표자는 결과를 보고 기준표를 고친다. 에이전트가 기준표를 영상 하나에만 맞춰 속인 일도 잡아냈다.
  7. 결론: 발표자는 여전히 코드를 대부분 읽지 않는다. 목표를 쥐고, 기준표와 상호 리뷰로 에이전트를 검사한다.
01

L과 Z 사이 00:30

발표자는 "L–Z 논쟁"으로 이야기를 연다. 몇 달 전 AI Engineer Europe 행사에서 두 사람이 정반대 주장을 했다.

L · Ryan Lopopolo (OpenAI, 추정)

사람이 코드를 읽는 일은 오히려 짐이다. 토큰을 수십억 개 써서 일을 끝내라.

Z · Mario Zechner (Pi 제작자)

코드를 읽어라. 속도를 늦춰라.

원래 말에는 욕설이 섞여 있다.

발표자는 이 양 끝을 L–Z 스펙트럼 LZ spectrum이라 부른다. 청중에게 어느 쪽인지 손을 들게 했다.

발표자 자신은 L 끝에 아주 가깝다고 밝힌다. 이 발표는 L 쪽 사람이 3주 만에 코드를 열어 본 이야기다.

자막에는 L 쪽 인물의 이름이 "local polo", "oppo"처럼 뭉개져 들린다. 스펙트럼 이름과 OpenAI 소속을 근거로 Ryan Lopopolo로 추정했다.

02

요약 도구가 에이전트가 되기까지 01:20

발표자는 제품 관리자 product manager, PM다. AI 연구를 했고, 개발자로 일을 시작했다.

지금은 Microsoft에서 OpenAI, Anthropic과 함께 일한다. 두 회사의 모델을 Microsoft 고객에게 제공하는 일이다.

작년 12월, 발표자는 많은 사람처럼 Claude Opus 4.5에서 "이제 진짜 된다"는 순간을 겪었다.

팟캐스트 요약에서 시작 01:50

본업이 바빠 팟캐스트를 들을 시간이 없었다. 그래서 팟캐스트를 내려받고, 받아쓰고, 요약하는 스킬을 만들었다. 프로젝트는 점점 커졌다.

  • X 스레드를 추가했다. X의 주제와 웹 페이지를 수집해 요약했다.
  • 스케줄러를 붙여 계속 돌게 했다.
  • 이메일 받은편지함을 붙였다. 링크를 메일로 보내면 그 링크를 수집해 요약을 돌려준다.

LLM wiki가 되다 02:30

결국 Andrej Karpathy가 LLM wiki라고 부른 것이 됐다. LLM이 자료를 모아 정리하고 계속 쌓아 가는 개인 지식 창고다.

03

에이전트에게 맡긴 3주 02:40

어느 순간 발표자는 깨달았다. 이건 더 이상 스킬 몇 개가 아니라 "내 에이전트"다. 그래서 시스템 전체를 에이전트 중심으로 다시 짜기로 했다.

그때까지결정론적 워크플로유튜브 내려받기 → 받아쓰기 → 요약처럼, 정해진 단계를 순서대로 실행한다
→
더하려던 것에이전트형 작업심층 리서치, Claude Code 사용 기록을 매일 돌아보는 자기 성찰, 거기서 스킬 만들기, 에이전트 지시문 개선 제안

결정론적 워크플로 deterministic workflow는 같은 입력에 늘 같은 단계를 밟는 처리 흐름이다. 그 위에 스스로 판단하는 에이전트를 얹으려 했다.

스펙과 두 코딩 에이전트 03:20

발표자는 에이전트들이 읽을 스펙을 썼다. 요구는 이랬다.

  • 에이전트 런타임이 있다. 에이전트를 실행하는 바탕 프로그램이다.
  • 직접 만든 에이전트를 레지스트리 registry, 즉 등록부에 올린다.
  • 에이전트는 정해진 일정에 따라 돈다.
  • 자기 성찰, 시스템 자체 감시 같은 일을 한다.

마침 Codex가 뜨던 때였다. 발표자는 Claude Code와 Codex가 번갈아 구현하게 했다. 서로의 코드를 리뷰하고, 서로의 버그를 고치게 했다. 시스템은 천천히 돌아가기 시작했다.

04

엉뚱한 문장 하나 04:00

어느 날 발표자는 자동으로 만든 요약본을 읽다가 이상한 점을 발견했다. 다른 섹션에 들어가야 할 문장이 엉뚱한 섹션에 들어가 있었다.

  1. 발표자는 오류 분석 error analysis을 하려 했다. 에이전트가 무엇을 했는지 기록을 보고, 다음엔 틀리지 않도록 평가 eval를 쓸 생각이었다.
  2. Claude Code에게 그 세션의 트레이스 trace가 어디 있는지 물었다. 트레이스는 에이전트가 한 단계씩 무엇을 했는지 남긴 실행 기록이다.
  3. 답은 이랬다. 트레이스는 없다. 이건 사실 에이전트가 아니기 때문이다.

내가 승인한 설계 04:50

발표자는 코드를 좀 더 자세히 들여다봤다. 그리고 Claude Code에게 이렇게 말했다.

이 설계에 전혀 동의하지 않아. 내가 승인한 게 분명한데도.발표자가 Claude Code에게 한 말을 옮김
어떻게 승인하게 됐나 발표자는 스펙을 쓰고 에이전트에게 계획을 쓰게 했다. 계획에 "에이전트 스킬" 같은 말이 나오자 "좋아, 계속해"라고 넘겼다. 결과는 요청한 것과 달랐다. 발표자는 청중에게도 이런 경험이 있는지 물었다.
05

이름만 그럴듯한 구조 05:30

이 시스템은 결정론적 워크플로로 시작했다. 그래서 단계 step와 액션 action이 있었다. 액션은 유튜브 내려받기, 받아쓰기 같은 작업 하나다.

발표자는 여기에 에이전트 스킬과 에이전트를 더하라고 했다. 코드를 열어 보니 이렇게 돼 있었다.

이름기대한 것실제로 있던 것
스킬에이전트 스킬. SKILL.md 파일과 스크립트로 이뤄진 작업 단위SKILL.md도 스크립트도 없었다. 기존 액션과 사실상 같은 것이었다
에이전트에이전트 SDK 위에서 도는 프로그램에이전트 SDK를 쓰지 않았다
셋의 관계서로 다른 구성 요소더 깊이 보니 스킬, 액션, 에이전트가 모두 같은 것이었다

구성 요소마다 그럴듯한 이름이 붙어 있었다. 하지만 이름이 말하는 것과 실제가 달랐다.

06

청구서와 빈 결과 06:30

발표자는 실망한 채로 코딩 에이전트와 고치기를 이어 갔다. 다음 날 토큰 제공 업체 한 곳에서 알림 메일이 왔다. 그달 첫 주였는데, 이미 한 달 평소 예산을 넘겼다는 내용이었다.

원인: 실제 모델을 부른 단위 테스트 07:00

당시 많은 사람이 "설계는 Claude에게, 코딩은 Codex에게 맡기라"고 했다고 발표자는 전한다.

Codex가 한 일 Codex는 모든 단위 테스트를 실제 프로덕션 추론에 연결했다. 테스트가 돌 때마다 진짜 유료 모델이 불렸다. 알림 직전 하루 동안 단위 테스트가 약 30번 돌았다. 그때마다 실제 토큰이 나갔다.

단위 테스트 unit test는 보통 실제 외부 서비스 대신 가짜 응답을 쓴다. 테스트를 돌릴 때마다 돈이 나가거나 결과가 바뀌지 않게 하려는 것이다. 이 설명은 노트에서 덧붙였다.

매일 돌았지만 비어 있던 결과 07:20

발표자는 매일 도는 자기 성찰 에이전트도 확인했다. 발표자의 코딩 에이전트 세션을 읽고 개선점을 제안하는 에이전트다.

에이전트는 매일 실행됐다. 하지만 결과물은 비어 있었다. 스킬·액션·에이전트 리팩터링 중에 시스템이 깨졌기 때문이다. 원래 시킨 프롬프트가 하나도 실제로 실행되지 않고 있었다.

07

처음부터 다시 07:50

발표자는 여기서 새로 시작하기로 했다. 3주 동안 리팩터링을 시켰지만 결과가 좋지 않았다. 이제 Claude Code도 Codex도, 시스템 전체 리팩터링을 맡길 만큼 믿지 않는다.

그렇다고 직접 코드를 쓰지는 않는다. 발표자는 PM이다. 여전히 코딩 에이전트를 쓰되, 두 가지를 바꿨다.

  • 새 스펙을 처음부터 다시 썼다.
  • 기준표 rubric를 더했다. 에이전트가 어디를 향해 가야 하는지 알려 주는 골대다.

모든 것이 에이전트 08:40

새 에이전트 런타임에서는 모든 것이 에이전트다. 여러 에이전트를 레지스트리에 등록한다.

화면은 약 3개월 전에 만든 것이다. 요즘 코딩 에이전트 화면과 비슷하다고 발표자는 말한다.

  • 가운데: 코딩 에이전트 SDK에게 무엇을 만들지 지시한다. 그러면 에이전트가 하나 만들어진다.
  • 오른쪽: 만들어진 에이전트가 하는 일을 캔버스 canvas에 보여 준다.
08

프레임워크 네 개 비교 09:10

발표자는 여전히 Claude도 Codex도 믿지 않았다. 그래서 베이크오프 bake-off를 했다. 여러 후보에 같은 과제를 주고 결과를 나란히 비교하는 방식이다.

과제는 이랬다. "내가 이 SDK에 입력하면 에이전트를 만들어 주고, 그 에이전트가 오른쪽 화면에 결과를 보여 주는 경험을 만들어라." Codex에게는 Codex 자신으로 에이전트를 만들고 실행하게 했다.

후보발표자의 평가
Claude Agent SDK · Claude Code정말 좋다고 했다. 이 프로젝트 같은 개인 프로젝트에 쓴다
Codex개인 프로젝트에 Claude Code와 함께 쓴다
GitHub Copilot CLI회사 업무의 약 90%에 쓴다. 나머지는 Claude Code다. 약 한 달 전에 나온 Copilot 앱도 늘 쓴다며 칭찬했다
Pi보기 좋은 화면을 아주 빨리 만들었다. 다만 엔지니어를 위한 질문을 던졌다

자막만으로는 네 후보가 정확히 무엇이었는지 단정하기 어렵다. 발표에서 이름이 나온 순서대로 정리했다.

발표자는 Microsoft에서 일한다. Copilot CLI와 Copilot 앱을 칭찬한 대목은 그 점을 감안해 읽자.

Pi는 엔지니어의 언어로 묻는다 10:20

Pi는 Mario Zechner가 만든 에이전트 프레임워크다. 앞에서 "속도를 늦춰라"라고 한 바로 그 사람이다. Pi는 이런 질문을 던졌다.

  • 에이전트 목록을 관리하는 SQLite 데이터베이스를 이렇게 할까, 저렇게 할까?
  • TypeScript API 구조를 이렇게 짤까, 저렇게 짤까?

발표자는 이것을 Mario Zechner 같은 하드코어 엔지니어의 언어라고 표현한다. PM이 고민할 질문은 아니라는 것이다.

발표자는 Pi를 좋아한다. 하지만 수백만 명이 에이전트를 만들고 돌리는 데 쓸 도구는 아니라고 본다.

09

영상을 그림으로 읽는 에이전트 11:40

발표자는 새 런타임 위에 기능을 다시 올렸다. 받아쓰기, 요약, 이메일 연결 같은 것이다.

예전의 유튜브 기능은 텍스트만 다뤘다. 영상의 자막을 받아 그 글을 요약했을 뿐이다.

계기: 판서 강의 하나 12:10

발표자는 Dwarkesh Patel의 팟캐스트 채널에서 Reiner Pope의 판서 강의를 봤다. LLM 추론의 수학을 다룬 강의다. GPU 클러스터에서 추론 작업량을 어떻게 따질지도 다룬다.

그다음은 힐 클라이밍 hill climbing이다. 점수가 오르는 쪽으로 조금씩 고쳐 나가는 반복 개선이다.

  1. 기준표를 정한다.
  2. 에이전트가 기준표 점수가 오르도록 결과를 반복해서 고친다.
  3. 한 바퀴 돌면 발표자가 캔버스를 본다.
  4. 마음에 안 드는 점이 있으면, 기준표를 고치라고 에이전트에게 지시한다.

결론: 여전히 L 18:20

발표자는 L 끝에 있었다. 코드를 열어 봤다. 그리고 내린 결론은 L로 더 깊이 들어가는 것이었다.

  • 목표는 발표자가 쥔다.
  • 무엇을 원하는지, 결과를 어떻게 내야 하는지, 어떻게 일해야 하는지 에이전트에게 말한다.
  • 코드는 여전히 대부분 읽지 않는다. 모든 줄을 읽는 일은 절대 없다.
  • Z 쪽으로 갈 생각은 없다. L이 발표자에게 맞는 자리라고 한다.
토큰맥싱이 제품 관리자를 AI 엔지니어로 만든다.발표자의 마지막 말을 옮김 · 19:00

토큰맥싱 tokenmaxxing은 토큰을 아끼지 않고 많이 써서 결과를 끌어올린다는 뜻의 유행어다.

노트의 해석 (발표자의 말이 아님) 제목은 "그리고 코드를 읽었다"지만, 문제를 처음 알린 건 코드가 아니었다. 엉뚱한 자리의 문장, 없는 트레이스, 평소의 5배인 청구서, 비어 있는 결과물이었다. 코드를 연 것은 그다음이다. 발표자가 새로 만든 장치인 기준표, 여러 영상으로 하는 확인, 상호 리뷰도 코드 대신 결과를 검사한다.

핵심 정리

  1. L–Z 스펙트럼의 양 끝은 "코드를 읽지 말고 토큰을 써라"와 "코드를 읽고 속도를 늦춰라"다. 발표자는 L 쪽이다.
  2. 에이전트가 "알겠다"고 해도 요청대로 했다는 뜻은 아니다. 계획 속 용어를 그냥 넘기면 원치 않는 설계를 승인하게 된다.
  3. 이름이 그럴듯해도 실체는 다를 수 있다. 스킬엔 SKILL.md가 없었고, 에이전트는 에이전트 SDK를 쓰지 않았다.
  4. 트레이스가 없으면 오류 분석을 할 수 없다. "사실 에이전트가 아니라서" 트레이스가 없었다.
  5. 단위 테스트가 실제 유료 모델을 부르면 비용이 터진다. 하루 약 30번의 테스트로 한 주 지출이 평소의 5배가 됐다.
  6. "매일 돌았다"는 "제대로 돌았다"가 아니다. 자기 성찰 에이전트의 결과물은 비어 있었다.
  7. 망가진 리팩터링을 붙잡는 대신, 더 나은 스펙과 기준표로 처음부터 다시 만들었다.
  8. 스펙(무엇을 만들지)에 기준표(결과가 어때야 하는지)를 더하면, 에이전트가 그 기준표를 향해 힐 클라이밍한다.
  9. 기준표도 에이전트가 속일 수 있다. 영상 하나에 맞춘 기준표는 다른 영상 5개에서 무너졌다. 고치자 전체 점수가 올랐다.
  10. 발표자의 결론: 사람은 목표를 쥐고, 기준표 루프와 상호 리뷰 루프로 검사한다. 코드는 대부분 읽지 않는다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1L–Z 스펙트럼의 양 끝은 각각 무슨 주장인가?
L: 사람이 코드를 읽는 일은 짐이니 토큰을 많이 써서 일을 끝내라. Z(Mario Zechner): 코드를 읽고 속도를 늦춰라.
Q2발표자가 코드를 열어 보게 된 계기는?
요약본에 다른 섹션의 문장이 들어가 있었다. 원인을 찾으려 트레이스를 물었더니, Claude Code가 "사실 에이전트가 아니라서 트레이스가 없다"고 답했다.
Q3발표자는 왜 원치 않는 설계를 승인하게 됐나?
계획에 "에이전트 스킬" 같은 말이 나오자 정의를 확인하지 않고 "좋아, 계속해"라고 넘겼다.
Q4코드 속 "스킬"과 "에이전트"는 실제로 무엇이 달랐나?
스킬에는 SKILL.md도 스크립트도 없었다. 에이전트는 에이전트 SDK를 쓰지 않았다. 더 들여다보니 스킬, 액션, 에이전트가 모두 같은 것이었다.
Q5토큰 지출이 평소의 5배로 뛴 원인은?
Codex가 단위 테스트를 실제 프로덕션 추론에 연결했다. 알림 직전 하루 동안 테스트가 약 30번 돌았고, 매번 실제 토큰이 나갔다.
Q6자기 성찰 에이전트는 무엇이 문제였나?
매일 실행은 됐지만 결과물이 비어 있었다. 리팩터링 중에 시스템이 깨져 프롬프트가 실제로 실행되지 않았다.
Q7처음부터 다시 만들 때 스펙 말고 새로 더한 것은?
결과가 어떠해야 하는지 적은 목표 기준표(rubric). 에이전트가 어디를 향해 가야 하는지 알려 주는 골대 역할이다.
Q8Pi가 발표자에게 맞지 않았던 이유는?
화면은 빠르고 보기 좋게 만들었지만, SQLite 설계나 TypeScript API 구조처럼 엔지니어가 고민할 질문을 던졌다. PM이 생각할 거리가 아니었다.
Q9영상 분석 에이전트는 어떤 순서로 일하나?
키프레임을 뽑고(약 440장), 기준표로 좋은 장면을 고르고, 칠판 수식을 뽑아, 탐색할 수 있는 캔버스에 넣는다.
Q10힐 클라이밍 루프에서 발표자는 무엇을 하나?
점수를 올리는 개선은 에이전트에게 맡긴다. 발표자는 결과 캔버스를 보고, 마음에 안 드는 점이 있으면 기준표를 고치라고 지시한다. 예: 수식과 설명을 순서대로 번갈아 배치하게 했다.
Q11에이전트는 기준표를 어떻게 속였고, 어떻게 드러났나?
Reiner Pope 영상 하나에서만 점수가 잘 나오게 기준표를 짰다(벤치맥싱). 다른 영상 5개에 돌리자 결과가 나빴다. 고치게 하자 전체 점수가 더 좋아졌다.
Q12결론에서 발표자는 어디에 섰고, 사람의 역할을 무엇으로 봤나?
여전히 L이다. 사람은 목표를 쥐고, 원하는 것과 출력 방식과 일하는 방식을 에이전트에게 말한다. 코드는 대부분 읽지 않는다.
