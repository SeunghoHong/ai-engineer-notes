에이전트에게 API 키 대신 신원을 준다

에이전트에게 API 키를 주면 누가 무엇을 했는지 알 수 없고 권한도 줄일 수 없다. 이 워크숍은 도구 호출마다 토큰을 교환해 짧게 쓰고 버리는 권한을 주는 법(Keycard), 그리고 그 에이전트가 중간에 죽어도 이어서 실행되게 하는 법(Temporal)을 실습으로 보여 준다.

원본 영상: Stop Giving Your AI Agents API Keys 발표: Kim Maida (Keycard), Mason Egger (Temporal 솔루션 아키텍트)

영어 워크숍의 자동 자막을 바탕으로 한글로 정리했다. 화면을 따라 하는 실습이라 화면에만 나온 내용은 담지 못했다. 수치는 모두 발표자가 말한 것이다. 자막에 "Keycloak"으로 잡힌 곳은 문맥상 모두 Keycard라서 바로잡았다. 두 발표자 모두 자기 회사 제품으로 실습하므로 제품 장점에 대한 말은 감안해 읽자. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트에게 API 키를 주면 누가 했는지 모르고, 권한을 줄일 수 없고, 사람 승인으로도 다 막지 못한다.
  2. 대안은 OAuth 2를 확장한 토큰 교환 표준이다. 사용자의 로그인 토큰을 내고, 다음 단계에서만 쓰는 토큰을 받는다.
  3. 도구 호출 하나마다 토큰을 새로 받는다. 몇 분 안에 만료되고, 저장하지 않고, 쓰고 나면 버린다.
  4. 발급 여부는 정책이 정한다. 어떤 에이전트가, 누구를 대신해, 어떤 리소스에 무엇을 원하는지 본다.
  5. 목표는 사칭이 아니라 위임이다. 기록에는 "Kim이 했다"가 아니라 "에이전트가 Kim을 대신해, Kim의 권한으로 했다"가 남는다.
  6. 신원이 생기자 규칙이 작동했다. 에이전트는 약 50달러 미만만 혼자 승인하고, 누구도 자기 경비를 승인하지 못한다.
  7. Temporal로 에이전트 루프를 짜면 워커가 죽어도 LLM을 다시 부르지 않고 이어서 돈다. 토큰은 실행 이력에 남지 않는다.
01

API 키를 주면 생기는 문제 01:20

요즘 에이전트에게 리소스 접근 권한을 줄 때 가장 흔한 방법은 API 키를 건네는 것이다. Kim Maida는 이 방식에 세 가지 문제가 있다고 본다.

문제무슨 뜻인가
주인을 모른다크리덴셜(접근 자격 증명 credential)이 사용자 신원에도, 에이전트 신원에도 묶여 있지 않다. 나중에 누가 했는지 알 수 없다.
권한을 줄일 수 없다에이전트는 키에 담긴 모든 권한을 제한 없이 쓴다.
사람 승인으로 다 막을 수 없다사람 승인 단계(human in the loop)를 모든 곳에 넣을 수는 없다. 사람도 실수하고, 많은 에이전트는 사람 없이 혼자 돈다.

Keycard가 내놓는 답은 토큰 교환 token exchange이라는 공개 표준이다. 발표자는 2020년부터 있던 표준이고 OAuth 2를 확장한 것이라고 소개했다.

Kim Maida는 Keycard 소속이고, 이 워크숍의 앞부분 전체가 Keycard 제품 실습이다. 토큰 교환 자체는 공개 표준이지만, 그 구현 방법으로 Keycard를 보여 준다는 점을 감안해 읽자.

02

시작은 사용자 로그인 02:10

에이전트와 그 뒤의 사용자에게 신원을 주려면, 먼저 사용자가 누구인지 알아야 한다.

  1. 권한 부여 서버 authorization server가 신원을 확인하고 토큰을 발급한다. Google, Okta, Auth0 같은 신원 제공자 identity provider가 이런 서버를 제공한다.
  2. 사용자가 로그인한다. 에이전트 실행 경로에 신원을 이어 붙이려면 이 단계가 먼저다.
  3. 서버가 동의 consent를 묻는다. 사용자는 자기 권한 중 일부만 에이전트에게 맡긴다. 이 일부를 스코프 scope라고 한다.
  4. 서버가 토큰을 발급한다. 토큰에는 사용자가 누구이고 어디까지 접근할 수 있는지 담긴다.
첫 번째 좁히기 02:50 동의 단계에서 접근이 이미 한 번 좁아진다. 에이전트는 사용자 권한 전체가 아니라, 사용자가 허락한 일부만 받는다.

한 바퀴 도는 순서 04:10

  1. 사용자가 런타임에 프롬프트를 낸다.
  2. 런타임이 LLM을 부른다.
  3. 모델이 도구 호출을 제안한다.

  7. 모델이 만족할 때까지 반복한다. 마지막에 사용자에게 답한다.
04

두 번의 토큰 교환 04:50

로그인 때 받은 사용자 토큰은 이제 subject token이 된다. 에이전트가 누구를 대신해 일하는지 밝히는 토큰이다.

토큰 교환을 하려면 코드를 실행할 수 있는 OAuth 클라이언트가 필요하다. 발표자는 세 가지 형태를 든다.

  • MCP 클라이언트와 외부 MCP 서버 사이에 둔 게이트웨이
  • 직접 만든 에이전트 앱. 이 워크숍의 Expense Desk가 여기에 해당한다
  • 기성 코딩 에이전트를 감싸는 CLI

첫 번째 홉: 에이전트 → MCP 서버 05:40

  1. 모델이 도구 호출을 제안한다.
  2. 에이전트 앱이 Keycard의 보안 토큰 서비스 STS, security token service에 자기를 인증한다. 클라이언트 자격 증명이나 워크로드 신원 workload identity을 쓴다.
  3. 사용자의 subject token을 함께 보낸다.
  4. "이 MCP 서버에, 이 도구 호출 하나만" 접근하게 해 달라고 교환을 요청한다.
발급을 판단하는 정보 06:20 요청한 에이전트가 누구인가. 에이전트가 누구를 대신하는가. 사용자가 에이전트에게 허락한 접근이 어디까지인가. 여기에 "어떤 리소스에 어떤 접근을 원하는가"를 더해 정책 policy으로 평가한다.

위임 사슬과 요청한 접근이 모두 정책 안에 들어오면 Keycard가 액세스 토큰을 발급한다. 이 토큰은 그 MCP 서버에서만 쓸 수 있다. 보통 몇 분 안에 만료되고, 저장하면 안 된다.

에이전트는 이 토큰을 bearer 크리덴셜로 붙여 MCP 서버를 부른다. MCP 서버는 토큰을 검증하고, 그걸 근거로 도구 호출을 허가한다.

두 번째 홉: MCP 서버 → Ledger API 07:30

도구가 일하려면 Ledger API에 접근해야 한다. 이번에는 MCP 서버가 자기 이름으로 Keycard에 교환을 요청한다. 에이전트에게서 받은 토큰을 내고 Ledger API용 토큰을 받는다.

Keycard는 다시 정책을 평가한다. 새 토큰에는 그 도구 호출에 필요한 접근만 담긴다. MCP 서버는 이 토큰으로 Ledger API를 부르고, 호출이 끝나면 바로 버린다.

홉요청하는 쪽내는 토큰받는 토큰쓰는 곳
1Expense Desk 에이전트 앱사용자의 subject tokenMCP 서버 전용 토큰Expense MCP 서버
2Expense MCP 서버에이전트에게서 받은 토큰Ledger API 전용 토큰Ledger API
권한이 좁아지는 세 번 동의 단계에서 사용자 권한 중 일부(스코프)만 넘어간다. 첫 홉에서 그 MCP 서버, 그 도구 호출 하나로 좁아진다. 둘째 홉에서 그 호출에 필요한 Ledger 접근만 남는다. 모든 토큰은 몇 분 안에 만료되고 어디에도 저장하지 않는다.
05

출발점: 모두가 API 키를 쓴다 09:40

실습은 브라우저 안의 샌드박스에서 진행한다. 참가자는 미리 만든 Keycard 조직 하나를 함께 쓴다. 그래서 다른 사람이 한 일도 서로 보인다. 수업마다 체크포인트 checkpoint가 있어, 그 단계가 끝난 상태의 코드를 바로 불러올 수 있다.

처음 상태의 Expense Desk에는 로그인이 없다. 모두 같은 MCP 서버를 쓰고 에이전트는 각자 돌린다. 모두 API 키를 쓰는데, 같은 키인지 다른 키인지도 알 길이 없다. 경비를 내면 승인되거나 거절되고, 그 다음 지급되는 흐름이다. 모든 조작은 에이전트를 거친다.

  1. 11:10 Kim Maida가 에이전트에게 워크숍 간식비 75달러를 제출하라고 한다. 경비는 대기 상태로 들어간다.
  2. 활동 기록에는 "API 키로 받은 권한으로 생성됨"만 남는다. 사용자에게도, 에이전트에게도 신원이 없다.
  3. 12:00 다른 사람의 경비를 승인한다. 승인 버튼은 사실상 에이전트에게 프롬프트를 보내는 것이다.
  4. 기록에는 누가 만들었는지도, 누가 승인했는지도 없다. 남는 건 API 키뿐이다.
이 상태의 구멍 누가 냈는지, 누가 승인했는지 기록이 없다. 신원을 모르니 자기 경비를 자기가 승인해도 막을 수 없다. 발표자는 뒤에서 이 점을 다시 짚는다 36:30.
06

콘솔에서 에이전트 등록하기 12:50

다음 목표는 에이전트에게 신원을 줘서 자기 이름으로 일하게 하는 것이다. 참가자는 GitHub 계정으로 공유 조직에 들어간다. 들어갈 때 동의 화면이 몇 번 뜬다. 앞에서 본, 자기 권한의 일부를 에이전트에게 맡기는 단계다.

application과 resource 14:10

Application 등록

토큰을 요청하는 쪽이다. 토큰 교환을 요청해 아래쪽 리소스에 접근한다.

Resource 등록

토큰을 받는 쪽이다. 토큰이 향하는 대상이다.

하나가 둘 다일 수 있다. Expense Desk 에이전트는 사용자의 로그인 토큰을 받고(resource), 그 토큰으로 교환을 요청한다(application). Expense MCP 서버도 마찬가지다.

설정 순서

단계한 일이유
1. Application 만들기 14:50"agent app"이라는 이름에 자기 GitHub 핸들을 붙인다. 식별자는 조직 안에서 고유해야 한다. 동의 방식은 implicit consent로 고른다. 샌드박스 터미널에서 리다이렉트 URL을 받아 넣는다.모두 한 조직을 쓰니 자기 것을 찾을 수 있어야 한다. 리다이렉트 URL은 로그인을 마친 사용자가 돌아올 주소다.
2. Resource 만들기 16:40"agent resource"를 만든다. 크리덴셜 제공자는 zone provider로 둔다. "이 리소스는 agent app이 제공한다"고 연결한다.에이전트가 사용자 로그인 토큰을 받는 대상이 되어야 한다. zone provider는 Keycard가 이 리소스의 교환과 발급을 맡는다는 뜻이다.
3. 의존성 연결 18:40agent resource, Expense MCP 서버, LLM API, 사용자 정보 엔드포인트를 고른다.Expense MCP 서버는 모두가 함께 쓰도록 미리 만들어 둔 리소스다. LLM API 키는 Keycard 볼트에 있어서 디스크에 두지 않는다. 사용자 정보 엔드포인트는 로그인한 사람이 누구인지 알려 준다.
4. 크리덴셜 추가 20:10클라이언트 ID와 시크릿을 만들어 에이전트 폴더의 .env 파일에 넣는다. agent resource의 식별자도 넣는다.에이전트가 스스로 로그인할 수단이다.
연결을 빠뜨리면 교환이 거절된다 18:10 2단계의 "agent app이 제공한다" 연결은, 이 앱이 이 리소스로 온 로그인 토큰을 교환해도 된다고 Keycard에 알려 준다. 이 연결이 없으면 교환 요청은 거절된다.

시크릿을 .env에 넣은 건 샌드박스라서다. 발표자는 실제 서비스라면 워크로드 신원을 쓰거나, 시크릿을 디스크에 두지 않고 그때그때 채워 주는 Keycard CLI를 쓰라고 했다.

07

코드에서 바뀌는 곳 22:00

콘솔 설정이 끝나면 Expense Desk 앱이 실제로 교환을 할 수 있어야 한다. 실습에서는 체크포인트 코드를 열어 두 군데를 확인한다.

  • MCP 도구 묶음 MCP toolset 23:20: Keycard SDK의 인증 객체를 넘긴다. 이제 에이전트가 MCP 도구를 부를 때마다 토큰을 새로 요청한다. 토큰은 그 도구 호출 하나에 맞춰진다.
  • 토큰 발급 함수 24:30: 발표에서는 mint 함수라고 부른다. 상황에 따라 두 길로 갈린다.

핵심 정리

  1. 에이전트에게 API 키를 주면 누가 했는지 모르고, 권한을 줄일 수 없고, 사람 승인으로도 다 막지 못한다.
  2. 대안은 OAuth 2를 확장한 토큰 교환이다. 사용자 토큰(subject token)을 내고 다음 단계 전용 토큰을 받는다.
  3. 시작은 사용자 로그인과 동의다. 사용자는 권한 일부(스코프)만 에이전트에게 맡긴다.
  4. 도구 호출 하나마다 토큰을 새로 받는다. 몇 분 안에 만료되고, 저장하지 않고, 쓰고 나면 버린다.
  5. 발급 여부는 정책이 정한다. 에이전트가 누구인지, 누구를 대신하는지, 어떤 리소스에 무엇을 원하는지 본다.
  6. MCP 서버도 아래쪽 API로 갈 때 다시 교환한다. 홉마다 권한이 좁아지고, 같은 세션 번호로 이어 볼 수 있다.
  7. Keycard에서 application은 토큰을 요청하는 쪽, resource는 받는 쪽이다. 에이전트와 MCP 서버는 둘 다다.
  8. 프롬프트에 쓴 "Kim 대신"은 증거가 아니다. 로그인한 신원만 기록에 남는다. 목표는 사칭이 아니라 위임이다.
  9. 신원이 생기면 규칙이 작동한다. 에이전트는 약 50달러 미만만 혼자 승인하고, 누구도 자기 경비를 승인하지 못한다.
  10. Temporal로 루프를 워크플로, 도구 호출을 액티비티로 짜면 워커가 죽어도 LLM 재호출 없이 이어 간다. 토큰은 이벤트 이력에 남지 않는다.

Q1에이전트에게 API 키를 줄 때 발표자가 꼽은 세 가지 문제는?
크리덴셜이 사용자나 에이전트 신원에 묶여 있지 않아 누가 했는지 모른다. 에이전트가 키의 모든 권한을 제한 없이 쓴다. 사람 승인을 모든 곳에 넣을 수 없다.
Q2스코프란 무엇이고, 왜 "첫 번째 좁히기"인가?
사용자가 동의 단계에서 에이전트에게 맡기는 권한의 일부다. 에이전트는 사용자 권한 전체가 아니라 이 일부만 받으므로, 여기서 접근이 처음 좁아진다.
Q3subject token은 무엇을 밝히는 토큰인가?
에이전트가 누구를 대신해 일하는지. 이 워크숍에서는 사용자가 로그인할 때 받은 토큰이다.
Q4Keycard가 토큰 발급을 판단할 때 정책으로 보는 것은?
요청한 에이전트가 누구인지, 에이전트가 누구를 대신하는지, 사용자가 허락한 접근이 어디까지인지, 어떤 리소스에 어떤 접근을 요청하는지.
Q5교환으로 받은 토큰을 다루는 규칙은?
그 대상(MCP 서버나 Ledger API)에서만 쓸 수 있다. 그 도구 호출 하나에 필요한 접근만 담긴다. 보통 몇 분 안에 만료된다. 저장하지 않고, 호출이 끝나면 버린다.
Q6Keycard의 application 등록과 resource 등록은 어떻게 다른가? 에이전트는 왜 둘 다 필요한가?
application은 토큰을 요청하는 쪽, resource는 토큰을 받는 쪽이다. 에이전트는 사용자 로그인 토큰을 받고(resource), 그 토큰으로 교환을 요청하므로(application) 둘 다 필요하다.
Q7agent resource를 만들 때 빠뜨리면 교환이 거절되는 설정은?
"이 리소스는 agent app이 제공한다"는 연결. 이 연결이 있어야 Keycard가 agent app이 그 리소스로 온 로그인 토큰을 교환해도 된다고 판단한다.
Q8로그인한 사용자가 없을 때 에이전트는 어떻게 인증하고, 기록에는 무엇이 남나?
클라이언트 ID와 시크릿으로 client credentials grant를 써서 자기를 인증한다. 감사 로그에는 행위자가 에이전트 application 자신으로 남는다.
Q9"내 대신 제출해"라고 했는데 기록에는 에이전트가 낸 것으로 남은 이유는?
"Kim 대신"은 프롬프트에 쓴 말일 뿐이다. 사용자가 로그인하지 않아 에이전트가 확인할 방법이 없었다. 그래서 자기 신원으로 경비를 만들었다.
Q10승인 한도가 100달러인 Kim이 자기의 75달러 경비를 승인할 수 없었던 이유는?
자기 경비는 승인도 거절도 할 수 없다는 규칙 때문이다. 75달러는 에이전트 혼자 승인 한도(약 50달러)도 넘으므로 다른 검토자가 처리해야 한다. 신원이 있어서 이 규칙이 작동한다.
Q11Temporal의 워크플로와 액티비티는 에이전트의 무엇에 대응하나?
워크플로는 에이전트 루프 전체(부모 함수), 액티비티는 도구 호출 하나하나(자식 함수)다. 액티비티는 실패할 수 있다고 보고, 실패하면 재시도하거나 상태를 다시 세운다.
Q12워커를 강제로 껐다가 다시 띄웠을 때 다시 일어나지 않은 일은? 토큰이 이력에 남지 않게 하는 두 방법은?
LLM 호출과 이미 끝난 액티비티를 다시 실행하지 않았다. 이벤트 이력을 재생해 상태만 되찾았다. 토큰은 인터셉터로 실행할 때만 끼워 넣거나, 페이로드 인코더로 데이터를 자기 키로 암호화해 막는다.

용어 정리

용어뜻
크리덴셜Credential. 접근할 자격이 있음을 증명하는 값. API 키, 토큰, 시크릿 등
신원Identity. 요청을 보낸 주체가 누구인지. 사람일 수도, 에이전트일 수도 있다
권한 부여 서버Authorization server. 신원을 확인하고 토큰을 발급하는 서버
신원 제공자Identity provider. Google, Okta, Auth0처럼 로그인과 권한 부여 서버를 제공하는 곳
동의Consent. 사용자가 자기 권한의 일부를 앱에 맡겨도 된다고 허락하는 단계
스코프Scope. 토큰이 허락하는 권한의 범위
OAuth 2비밀번호를 넘기지 않고 앱에 접근 권한을 위임하는 표준
토큰 교환Token exchange. 가진 토큰을 내고 다른 대상용 토큰을 받는 OAuth 2 확장 표준. 흔히 RFC 8693으로 알려져 있다. 발표에서는 번호 없이 "2020년부터 있던 표준"이라고만 소개했다
subject token에이전트가 누구를 대신해 일하는지 밝히는 토큰. 여기서는 사용자의 로그인 토큰
액세스 토큰Access token. 특정 리소스에 접근할 때 내는 토큰
bearer 크리덴셜들고 있는 쪽이 내기만 하면 통하는 크리덴셜
보안 토큰 서비스STS, security token service. 교환 요청을 받아 새 토큰을 발급하는 서버. 이 워크숍에서는 Keycard
client credentials grant사용자 없이 앱이 자기 클라이언트 ID와 시크릿으로 토큰을 받는 OAuth 방식
워크로드 신원Workload identity. 실행 중인 프로그램에 플랫폼이 붙여 주는 신원. 시크릿을 파일로 두지 않아도 된다
정책Policy. 토큰을 발급할지 정하는 규칙
홉Hop. 요청이 한 부품에서 다음 부품으로 넘어가는 한 구간
위임 사슬Delegation chain. 누가 누구를 대신해 무엇에 접근했는지 이어진 기록
사칭Impersonation. 에이전트가 사용자인 척 사용자 이름으로 행동하는 것. 위임과 다르다
MCPModel Context Protocol. 에이전트가 외부 도구와 데이터에 접근하는 표준 방식
런타임에이전트 루프와 함께 돌며 호출을 실행하는 프로세스
감사 로그Audit log. 누가 언제 무엇을 했는지 남기는 기록
리다이렉트 URLRedirect URL. 로그인을 마친 사용자를 돌려보낼 주소
볼트Vault. 비밀값을 안전하게 보관하는 저장소
내구성 있는 실행Durable execution. 실행 상태를 보관해, 실패해도 그 지점부터 이어서 실행하는 방식
워크플로 / 액티비티Temporal에서 전체 흐름(부모 함수)과, 그 안의 실패할 수 있는 단계(자식 함수)
워커Worker. 워크플로와 액티비티 코드를 실제로 실행하는 프로세스
이벤트 이력Event history. Temporal이 워크플로마다 남기는 실행 기록. 상태를 다시 세울 때 쓴다
재생Replay. 이벤트 이력을 다시 돌려 이전 상태를 되찾는 것
인터셉터Interceptor. 코드의 정해진 지점에 끼워 넣는 훅
페이로드 인코더발표자의 표현. Temporal로 가는 데이터를 사용자 키로 암호화하는 장치. Temporal 문서에서는 Payload Codec이라는 이름으로 나온다
JWTJSON Web Token. 서명된 JSON 형태의 토큰
just-in-time 크리덴셜필요한 순간에만 받아 쓰고 버리는 크리덴셜
