AI 해커는 펜테스트보다 빠르다

AI 덕분에 코드는 쏟아지고, 공격자도 같은 AI로 몇 분 만에 시스템을 뚫는다. 1년에 두어 번 하는 펜테스트로는 따라갈 수 없다. 발표자는 LLM 에이전트로 펜테스트를 코드가 바뀔 때마다 돌리자고 제안한다.

원본 영상: AI Hackers Are Faster Than Your Pen Test 발표: Eli Cohen (Snyk 초대 필드 CTO, 전 Helios 공동 창업자·CEO)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치는 모두 발표자가 인용한 것이고 원 출처를 따로 확인하지는 않았다. 자막의 'sneak'은 Snyk로, 'cloud code'는 Claude Code로 바로잡았다. 확실하지 않은 이름과 숫자에는 (추정)을 붙였다. 발표는 Snyk의 새 보안 제품 Evo 소개를 겸한다. mm:ss는 영상 위치다.

3분 요약
  1. AI로 코드는 더 많이(개발자 1인당 +218%), 덜 안전하게(LLM 결과물의 62%가 안전하지 않거나 깨짐) 만들어진다. 보안 백로그가 고치는 속도보다 빨리 쌓인다.
  2. 공격자도 같은 AI를 쓴다. 발표자가 인용한 가장 빠른 AI 공격은 4분 만에 성공했다.
  3. 정적 분석은 코드 패턴을, 동적 분석은 실행 중 권한 문제를 찾는다. 둘 다 비즈니스 로직의 빈틈은 잘 못 찾는다.
  4. 비즈니스 로직은 사람 펜테스트가 표준이다. 하지만 비싸서 1년에 1~3번뿐이고, 나머지 날은 아무도 시험하지 않는다.
  5. 해법은 지속적 공격 보안이다. LLM으로 펜테스트를 PR마다 돌리고, 에이전트 레드팀과 동적 테스트를 함께 묶는다.
  6. 핵심은 맥락과 증명이다. 기존 스캐너 결과를 LLM에 맥락으로 넣고, 찾은 취약점이 실제로 공격 가능한지 증명해 거짓 경보를 줄인다.
  7. 도구를 고를 때 네 가지를 묻는다. 계속 도는가, 앱 맥락을 이해하나, 맥락을 더 받아들이나, 공격 가능성을 증명하나.
01

코드는 늘고 보안은 약해졌다 01:40

발표자는 AI가 만드는 코드의 양부터 짚는다. Snyk가 가진 데이터로는 개발자 한 명이 쓰는 코드 줄 수가 전보다 218% 늘었다.

  • 개발자의 85% 이상이 코딩 에이전트를 쓴다. 발표자는 이 행사 청중이라면 Claude Code나 Codex 세션을 여러 개 동시에 돌리고 있을 거라고 농담했다.
  • LLM이 만든 결과물의 62%는 안전하지 않거나 제대로 동작하지 않는다.

둘을 합치면 그림이 나온다. 전보다 훨씬 많은 코드가 전보다 덜 안전한 상태로 프로덕션에 들어간다. 그래서 보안 백로그security backlog가 고치는 속도보다 빨리 길어진다. 보안 백로그는 찾았지만 아직 고치지 못한 보안 문제 목록이다.

02

공격자도 AI를 쓴다 03:00

AI는 방어하는 쪽만 돕지 않는다. 공격자도 최신 모델을 쓴다.

  • 취약점 엮기: 심각도가 낮은 취약점 여러 개를 이어 붙여 치명적인 취약점 하나로 만든다.
  • 맥락이 필요한 곳 노리기 03:20: 공격자는 애플리케이션 맥락application context을 알아야 하는 곳을 노린다. 이 앱이 무슨 일을 하고 누가 무엇을 해도 되는지 같은 정보다. LLM이 코드를 만들 때 가장 약한 곳이라 취약점도 가장 많이 생긴다.

발표자가 든 숫자 03:50

한 AI 공격 작전은 방화벽 600개 이상을 뚫었다. 피해는 55개국(추정)에 걸쳤다.

자막에는 "555개국"으로 들린다. 세계의 나라는 200개 남짓이라 이 숫자는 그대로일 수 없다. 55개국을 잘못 들은 것으로 보고 옮겼다.

발표자가 이 숫자를 말한 시점은 영상 4분 20초쯤이다. 발표자는 "제가 말을 시작한 뒤로 어딘가에서 AI 공격 하나가 프로덕션 시스템을 뚫었을 것"이라고 말했다.

AI 에이전트가 외부 도구와 데이터에 접속하는 통로인 MCP 서버Model Context Protocol server는 43%에 취약점이 있다. 04:30

네 가지가 한꺼번에 겹친다 04:40 코드는 전보다 많다. 그 코드는 덜 안전하다. 공격자는 같은 도구로 더 빨리 움직인다. 백로그는 쌓이기만 한다. 발표자는 그래서 방어하는 쪽도 공격 보안offensive security을 써야 한다고 본다. 공격자 입장에서 내 시스템을 직접 공격해 약점을 먼저 찾는 일이다.

청중에 개발자와 보안 담당자가 섞여 있어서, 발표자는 기본 개념부터 정리한다.

04

펜테스트의 한계 07:10

펜테스트는 사람이 공격자처럼 앱을 깨 보는 모의 해킹이다. 앱의 업무 규칙을 이해하는 사람이 하기 때문에 애플리케이션 보안 테스트의 표준으로 꼽힌다. 문제는 세 가지다.

  1. 비싸다. 보안 연구자가 처음부터 끝까지 직접 테스트한다. 사람이 옆에서 거드는 정도가 아니다.
  2. 드물다. 비싸고 느려서 회사는 1년에 한두 번, 많아야 세 번 한다. 1년에 두 번이면 나머지 350일가량은 아무도 앱을 시험하지 않는다. AI 공격자는 그동안에도 쉬지 않는다.
  3. 결과가 늦게 쓰인다. 08:20 결과는 두툼한 PDF 보고서로 온다. 개발자는 무엇이 진짜인지 가려내고, 고치고, 다시 테스트를 받아야 한다. 발표자는 이 과정을 "90년대 영화 같다"고 했다.

그래도 발표자는 펜테스트가 비즈니스 로직을 시험하는 가장 좋은 방법이라고 인정한다. 그래서 질문은 이 방법을 싸고 자주 할 수 있느냐로 바뀐다.

05

지속적 공격 보안 08:50

달라진 것은 기술이다. LLM과 최신 모델로 펜테스트를 쉬지 않고, 큰 규모로 돌릴 수 있게 됐다. 발표자는 이것을 지속적 공격 보안continuous offensive security이라고 부른다.

Snyk는 이 개념을 자사 제품 Evo로 내놓았고, 발표 전체가 그 소개를 겸한다. 발표자는 원칙 자체는 일반적이라 어느 업체에든 확인해 볼 수 있다고 했다. 그래도 제품 설명이 섞여 있다는 점을 감안해 읽자.

06

AI 펜테스트는 무엇이 다른가 10:40

사람 펜테스트의 장점은 사람이 비즈니스 맥락을 이해한다는 점이었다. 발표자는 LLM이 바로 그 일을 잘한다고 본다. 이 장점을 LLM으로 옮기면 세 가지가 바뀐다.

  • 코드가 바뀔 때마다 돈다. 1년에 두세 번이 아니다. PR마다, 바뀐 부분마다 펜테스트를 돌린다. 개발자에게 무엇을 어떻게 고칠지도 알려 준다.
  • 공격할 수 있는지 증명한다. 11:30 보안 업계의 큰 문제는 거짓 경보false positive다. 멀쩡한 것을 문제라고 지적하는 것이다. 그래서 버그라고 표시만 하지 않고, 실제로 공격이 통한다는 것을 보여 준다.
  • 여러 곳의 맥락을 모은다. 여러 머신과 환경에서 모은 정보를 합쳐 LLM이 어디를 볼지 안내한다.
지금까지사람이 1년에 1~3번 한다결과는 PDF 보고서다. 진짜인지 가리는 일은 개발자 몫이다

07

에이전트 여섯이 나눠 맡는다 12:10

발표자는 기존 정적·동적 스캐너에 LLM을 덧붙인 것이 아니라고 강조한다. 처음부터 LLM으로 다시 만들었다는 것이다. 안에서는 에이전트 여러 개가 차례로 일을 넘긴다.

에이전트발표자의 비유하는 일
1. 오케스트레이터
LLM orchestrator 12:40		두뇌상황에 따라 바뀌는 계획을 따르며 아래 에이전트들을 부린다
2. 정찰
recon 12:50		정예 정보부대네트워크 엔드포인트, API, 서버 종류를 알려 주는 단서(핑거프린트)를 모은다. 이걸로 앱의 구조도를 그려 다음 단계에 넘긴다
3. 취약점 테스트
vulnerability testing 13:10		—여러 전문 에이전트로 이뤄진다. 일부는 잘 알려진 취약점 종류를 노린다. 일부는 앱을 직접 깨 보며 공격자가 어디서 들어올 수 있는지 찾는다
4. 공격 검증
exploit validation 13:30		판사앞 단계가 찾은 취약점이 진짜인지, 실제로 공격할 수 있는지 판정한다
5. 수정
remediation 14:00		—개발자가 바로 고칠 수 있게 수정 방법을 만든다
6. 보고
reporting 14:20		—결과를 정리해 보고한다

공격 검증 단계를 따로 두는 이유는 두 가지다. 사람이 진위를 가리는 판단 부담cognitive load을 줄인다. 시스템이 내보내는 거짓 경보도 줄인다. 수정 단계를 두는 이유는 개발자가 받아도 무엇을 할지 모르는 보고를 만들지 않기 위해서다.

이 구조는 발표자가 자사 제품 Evo의 내부를 설명한 것이다. 실제로 이렇게 동작하는지는 발표만으로 확인할 수 없다.

08

맥락이 결과를 정한다 14:30

AI 펜테스트는 지금 큰 시장이다. 발표자는 업체 제품을 고르든 사내에서 직접 만들든 아래 점을 확인하라고 한다.

LLM은 넣어 준 맥락만큼만 좋다.발표자의 말을 옮김 14:50

그래서 AI 펜테스트를 따로 떼어 돌리지 않는다. 정적 스캐너, 동적 스캐너, 다른 검사 엔진의 결과를 모두 AI 펜테스트에 넣는다. 그러면 LLM에게 어디를 찾아볼지 알려 줄 수 있다. 발표자는 Mythos나 Fable(추정) 같은 최신 모델도 어디를 볼지 알 때 결과가 훨씬 좋다고 덧붙였다.

자막에는 두 번째 모델 이름이 "frame"으로 들린다. Fable로 읽었지만 확실하지 않다.

도구 하나로는 부족하다 15:40

발표자에 따르면 실험실 데이터와 고객 데이터 모두 여러 도구를 함께 쓸 때 결과가 가장 좋았다. 취약점 종류마다 잘 맞는 도구가 다르기 때문이다. 예를 들어 크로스 사이트 스크립팅은 동적 분석이 가장 잘 찾는다. 보낼 수 있는 페이로드 목록이 아주 방대해서다. 비즈니스 로직은 펜테스트를 함께 써야 한다.

비즈니스 로직펜테스트 (사람 또는 AI)16:30

09

도구를 고를 때 물을 네 가지 16:40

예전에는 몇 달에 한 번 테스트해도 괜찮았다. 코드가 천천히 바뀌었고, 마지막에 사람이 앱과 변경을 따져 봤기 때문이다. 이제 코드는 24시간 프로덕션에 올라간다. 공격하는 LLM도 앱 맥락을 추론하며 쉬지 않고 깨 보려 한다. 빠르면 4분이면 된다. 이 발표 길이(19분 28초)의 5분의 1쯤이다.

네 가지 질문 17:20

질문왜 묻나
1. 계속 도는가, 가끔 한 번 돌리는가?공격은 24시간 계속된다. 발표자는 이것을 가장 큰 차이로 꼽았다
2. 앱 맥락을 정말 추론하나?LLM이 만든 코드의 새 취약점은 앱 맥락에서 나온다
3. 맥락을 얼마나 더 받아들이나?데이터가 풍부할수록 결과가 좋다. 발표자는 LLM을 돌리는 비용도 싸진다고 했다
4. 공격 가능성을 증명하나, 버그라고 표시만 하나?증명 없는 지적은 거짓 경보일 수 있고, 가려내는 데 개발자 시간이 든다
발표자가 말한 목표 18:20 버그를 더 빨리 찾는 데서 끝나지 않는다. 더 정확하고 더 싸게 찾는다. 그래서 개발자와 보안 담당자가 가장 중요한 일에 집중하게 한다.
10

핵심 정리

  1. 코드는 개발자 1인당 218% 늘었고, LLM 결과물의 62%는 안전하지 않거나 깨져 있다. 보안 백로그가 쌓인다.
  2. 공격자도 AI로 낮은 심각도 취약점을 엮어 치명적인 공격을 만든다. 가장 빠른 사례는 4분이다.
  3. 공격자는 앱 맥락이 필요한 곳을 노린다. LLM이 만든 코드가 가장 약한 곳이다.
  4. 정적 분석은 코드 패턴을 싸게 찾지만, 실행해야 드러나는 권한·설정 문제는 못 찾는다.
  5. 동적 분석은 실행 중인 앱에 페이로드를 보내 BOLA 같은 권한 문제를 찾는다. 비즈니스 로직에는 약하다.
  6. 사람 펜테스트는 비즈니스 로직 검사의 표준이지만, 비싸서 1년에 1~3번뿐이다.
  7. 지속적 공격 보안은 LLM으로 펜테스트를 PR마다 돌리고, 에이전트 레드팀과 동적 테스트를 함께 묶는다.
  8. 핵심 장치는 공격 검증이다. 실제로 공격할 수 있는지 증명해 거짓 경보를 줄인다.
  9. LLM은 받은 맥락만큼만 좋다. 기존 스캐너 결과를 넣고, 도구 하나에 기대지 않는다.
  10. 도구를 고를 때 네 가지를 묻는다. 계속 도는가, 앱 맥락을 추론하나, 맥락을 더 받나, 공격 가능성을 증명하나.
11

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 인용한 코드량과 코드 품질 숫자는? 둘을 합치면 무슨 일이 생기나?
개발자 1인당 코드 줄 수가 218% 늘었고, LLM 결과물의 62%가 안전하지 않거나 깨져 있다. 덜 안전한 코드가 더 많이 프로덕션에 들어가 보안 백로그가 쌓인다.
Q2공격자는 AI로 낮은 심각도 취약점을 어떻게 쓰나?
여러 개를 엮어 치명적인 취약점 하나로 만든다.
Q3공격자가 특히 노리는 곳은 어디이고, 왜 그곳인가?
애플리케이션 맥락을 알아야 하는 곳이다. LLM이 코드를 만들 때 가장 약한 곳이라 취약점이 가장 많이 생긴다.
Q4정적 분석(SAST)이 잘 찾는 것과 못 찾는 것은?
SQL 인젝션, 크로스 사이트 스크립팅 같은 코드 패턴은 싸게 찾는다. 실행해야 드러나는 권한 문제와 설정 문제는 못 찾는다.
Q5BOLA는 무엇이고, 어떻게 찾아야 하나?
사용자 A가 사용자 B의 데이터를 볼 수 있는 권한 결함이다. 코드만 읽어서는 못 찾는다. 실행 중인 앱에 요청을 보내 보는 동적 분석이 필요하다.
Q6사람 펜테스트가 표준인데도 부족한 이유 세 가지는?
비싸다. 그래서 1년에 1~3번뿐이라 나머지 기간은 아무도 시험하지 않는다. 결과가 PDF 보고서로 와서 진위 가리기, 수정, 재테스트에 오래 걸린다.
Q7에이전트 레드팀이 흉내 내는 공격 세 가지는?
프롬프트 인젝션, 데이터 유출, 목표 탈취(추정). 모두 여러 단계에 걸친 공격이다.
Q8AI 펜테스트 안에서 에이전트들이 일을 넘기는 순서는?
오케스트레이터, 정찰, 취약점 테스트, 공격 검증, 수정, 보고 순이다. 오케스트레이터는 전체를 지휘한다.
Q9공격 검증(판사) 에이전트를 따로 두는 이유는?
찾은 취약점이 실제로 공격 가능한지 판정해 거짓 경보를 줄인다. 사람이 진위를 가리는 판단 부담도 줄인다.
Q10AI 펜테스트에 기존 스캐너 결과를 넣는 이유는?
LLM은 받은 맥락만큼만 좋다. 어디를 볼지 알면 결과가 훨씬 좋아진다. 발표자는 비용도 줄어든다고 했다.
Q11크로스 사이트 스크립팅에 발표자가 가장 좋다고 꼽은 도구와 그 이유는?
동적 분석(DAST)이다. 보낼 수 있는 페이로드 목록이 아주 방대하기 때문이다.
Q12보안 도구를 고를 때 물을 네 가지 질문은?
계속 도는가, 앱 맥락을 정말 추론하나, 맥락을 얼마나 더 받아들이나, 공격 가능성을 증명하나.

용어 정리

용어뜻
공격 보안Offensive security. 공격자 입장에서 내 시스템을 직접 공격해 약점을 먼저 찾는 보안 활동
지속적 공격 보안Continuous offensive security. 공격 테스트를 정기 행사가 아니라 코드가 바뀔 때마다 계속 돌리는 방식
펜테스트Penetration test. 모의 해킹. 사람(또는 AI)이 공격자처럼 시스템을 깨 보며 취약점을 찾는다
보안 백로그찾았지만 아직 고치지 못한 보안 문제 목록
정적 분석 (SAST)Static Application Security Testing. 코드를 실행하지 않고 읽어서 취약한 패턴을 찾는다
동적 분석 (DAST)Dynamic Application Security Testing. 실행 중인 앱에 공격 입력을 보내고 반응을 본다
페이로드Payload. 테스트나 공격을 위해 보내는 입력값
SQL 인젝션입력값에 SQL 문을 섞어 데이터베이스 질의를 조작하는 공격
크로스 사이트 스크립팅XSS. 웹 페이지에 악성 스크립트를 심어 다른 사용자의 브라우저에서 실행되게 하는 공격
BOLABroken Object Level Authorization. 사용자 A가 사용자 B의 데이터에 접근할 수 있는 권한 결함
비즈니스 로직서비스가 지켜야 할 업무 규칙. 코드 문법은 멀쩡해도 이 규칙의 빈틈이 취약점이 된다
애플리케이션 맥락Application context. 앱이 무슨 일을 하고, 누가 무엇을 해도 되는지 같은 정보
레드팀Red teaming. 실제 공격자처럼 여러 단계 공격을 흉내 내 방어를 시험하는 활동
프롬프트 인젝션입력 안에 지시문을 숨겨 AI가 원래 지시 대신 그걸 따르게 만드는 공격
데이터 유출Data exfiltration. 시스템 안의 데이터를 공격자가 밖으로 빼내는 것
목표 탈취Goal hijacking (추정). AI 에이전트가 원래 목표 대신 공격자의 목표를 따르게 만드는 공격
거짓 경보False positive. 멀쩡한 것을 문제라고 잘못 지적하는 것
공격 가능성Exploitability. 찾은 취약점을 실제로 악용할 수 있는지 여부
오케스트레이터여러 에이전트에게 일을 나눠 주고 순서를 정하는 상위 에이전트
정찰Recon. 공격 전에 대상의 엔드포인트, API, 서버 정보를 모으는 단계
핑거프린트Fingerprint. 서버나 프레임워크의 종류와 버전을 알려 주는 단서
MCP 서버Model Context Protocol 서버. AI 에이전트가 외부 도구와 데이터에 접속하게 해 주는 서버
존재조차 모르는 위험Unknown unknowns. 있는지도 모르기 때문에 대비하지 못한 위험
