에이전트에게 가입 문을 여는 auth.md

에이전트는 이미 코드를 쓰고 쓸 서비스도 고르지만, 회원가입 단계에서 막힌다. WorkOS는 서비스가 에이전트에게 가입 방법을 알려 주는 문서 auth.md를 제안한다.

원본 영상: Auth for Agents: Let AI Sign Up for Your Product with auth.md 발표: Michael Grinich (WorkOS 창업자)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 바로잡았고, 확실하지 않은 것에는 (추정)을 붙였다. mm:ss는 영상 위치다.

3분 요약
  1. 코딩 에이전트는 한 번 지시로 몇 시간, 며칠씩 혼자 일한다. 이 방식이 개발 밖의 분야로도 퍼진다.
  2. 에이전트는 이제 쓸 서비스를 직접 고른다. "사람이 원하는 것"과 함께 "에이전트가 원하는 것"도 만들어야 한다.
  3. 그런데 웹의 가입 절차는 사람용이다. 이메일 인증, CAPTCHA, 카드 등록, API 키 복사가 에이전트를 막는다.
  4. 빠진 것은 에이전트 가입이라는 기본 요소다. MCP는 연결을 해 주지만 가입에는 여전히 사람이 필요하다.
  5. auth.md는 서비스가 "에이전트는 이렇게 가입하면 된다"고 적어 두는 문서다. 기존 표준 위에서 가입 단계만 다룬다.
  6. 데모: 에이전트가 auth.md를 보고 Cloudflare를 골랐다. 신원 증명을 보내 계정을 받았고, 사람의 클릭 없이 앱을 배포했다.
  7. 결제는 나중이다. 먼저 쓰게 하고, 서비스가 정한 조건으로 돈을 받는다. 발표자는 스펙이 공개돼 있고 WorkOS가 소유하지 않는다고 말한다.

발표자는 자동차에 빗댄다. 최근 5~10년 사이의 차에는 큰 디스플레이가 달렸다. 그래도 운전은 사람이 한다. 크루즈 컨트롤이 있어도 사람은 여전히 루프 안에 있다.

에이전트 덕분에 사람은 계획과 실행에서 한 걸음 물러나, 더 높은 수준의 판단에 집중한다.

03

에이전트가 벤더를 고른다 05:20

에이전트에게 무언가를 만들라고 하면, 에이전트는 필요한 것을 스스로 정리한다. 데이터베이스, 배포 시스템, 이미지 크기 조절, 동영상 변환, 이메일 발송 같은 것들이다. 그리고 어느 회사의 서비스를 쓸지도 직접 조사해 고른다.

발표자에 따르면 급성장 그래프를 자랑하는 서비스 회사 중에는 에이전트가 골라 줘서 큰 곳들이 있다. 이메일 발송, 코드 배포, 데이터 저장 분야다. 발표자는 지금은 사람보다 에이전트를 위해 만드는 게 더 중요할 수도 있다고 말한다.

04

에이전트 앞에서 닫힌 문 06:50

사람은 웹과 모바일로 서비스에 들어간다. 에이전트는 그러지 못한다. 대부분의 서비스는 에이전트에게 문을 열어 두지 않았다.

발표자는 빠진 기본 요소 primitive가 있다고 본다. 바로 에이전트 가입 agent registration이다. 07:10 에이전트가 시스템에 연결해 맥락을 가져오는 도구는 이미 많다. 하지만 맨 첫 단계인 가입은 아직 아무도 풀지 못했다. 이것이 에이전트 도입을 크게 막는다.

왜 닫혀 있나 07:20

지난 20~30년 동안 웹에서 자동화된 트래픽은 나쁜 것이었다. 그래서 막는 장치를 겹겹이 쌓았다.

  • DoS 방어: 요청을 쏟아부어 서비스를 멈추게 하는 공격을 막는다
  • 크리덴셜 스터핑 방어 credential stuffing: 유출된 아이디와 비밀번호를 대량으로 넣어 보는 공격을 막는다
  • 로그인 화면 강화: 자동화된 접근을 탐지하고 바로 끊는다

로그인 화면이 일부러 에이전트를 막으려던 건 아니다. 옛날에 만든 방식 그대로라서 막힌다. 진짜 문제는 좋은 자동화와 나쁜 자동화를 구분하기 어렵다는 점이다.

CAPTCHA는 이미 무너졌다 08:00 클라우드 브라우저 실행 환경 중에는 CAPTCHA 뚫기를 장점으로 내세우는 곳도 있다. 남용과 토큰 사기 token fraud도 흔하다. 필요한 건 좋은 에이전트는 들이고 나쁜 에이전트는 막는 새 방법이다.
05

가입 절차는 사람을 전제한다 08:30

지금의 가입 절차는 다음을 사람이 한다고 가정한다.

  • 랜딩 페이지를 읽는다

에이전트는 대개 이메일 주소가 없다 이메일 인증 하나만으로도 막힌다. 대시보드도 사람용 화면이다. 지금의 가입은 사람을 위한 인터페이스이지, 에이전트를 위한 인터페이스가 아니다.

MCP Model Context Protocol는 에이전트를 도구, 스킬, 맥락에 연결해 준다. 발표자는 스스로 MCP의 큰 팬이라고 말한다. WorkOS는 샌프란시스코에서 MCP 행사를 여러 번 열었다.

하지만 MCP는 가입 단계를 풀지 않는다. 지금 MCP로 인증하려면 사람이 끼어야 한다.

07

auth.md란 무엇인가 11:00

WorkOS의 제안은 auth.md라는 새 스펙이다. 마크다운 파일 이름을 붙인 이유를 발표자는 "마크다운 파일이 미래니까"라고 농담처럼 말한다.

auth.md는 서비스가 에이전트에게 "이렇게 하면 정식 사용자가 될 수 있다"고 알려 주는 안내문이다. 목표는 서비스 제공자에게 에이전트용 가입 경험을 주는 것이다. 새롭고 복잡한 체계를 발명하지 않고, 이미 있는 표준 위에 짓는다.

범위를 일부러 좁게 잡았다 11:50 에이전트 신원 전체, 권한, 오래 유지되는 연결 같은 큰 문제는 다루지 않는다. 가입 단계 하나만 다룬다. 가장 큰 걸림돌이라서 작게 시작해 넓혀 가겠다는 것이다.

auth.md는 발표자의 회사 WorkOS가 제안한 스펙이다. WorkOS는 인증 제품을 판다. 이 점을 감안해 읽자.

08

데모: 혼자 가입하고 배포하기 13:00

발표자가 보여 준 짧은 데모다. Cloudflare와 함께 만들었고, 실제로 작동해 누구나 해 볼 수 있다고 했다.

  1. 사용자가 코딩 하네스(Pi나 Claude 등)에서 만들던 앱을 친구들과 공유하고 싶다고 말한다.
  2. 에이전트가 설명한다. localhost는 내 컴퓨터에서만 열린다. 공유하려면 실제 서버에 배포해야 한다. 가입을 에이전트가 대신 할 수 있는 서비스가 있으니 찾아볼지 묻는다.
  3. 에이전트가 auth.md를 내건 서비스를 찾는다. Cloudflare에 auth.md가 있다. 직접 가입하고 쓸 수 있으니 Cloudflare를 고른다. 13:50
  4. 가입한다. 에이전트가 신원 주장 identity assertion을 만들어 Cloudflare에 보낸다. Cloudflare는 이를 확인할 수도 있고, 다른 경로로 따로 확인할 수도 있다. 14:10
  5. Cloudflare는 예를 들어 72시간 정도 배포를 허락한다. 신원 주장은 ID-JAG라는 표준으로 주고받는다. Cloudflare 계정이 생겼다는 응답이 온다. 14:50
  6. 에이전트는 Cloudflare 배포 도구 Wrangler를 쓸 줄 안다. 설정을 쓰고 배포까지 마친다. 앱이 공개된다. 15:10
사람이 한 일 클릭도, 가입 양식도 없었다. 사람은 "응, 해 줘"라고 승인만 했다. 발표자는 이 과정이 한 번의 지시로 끝날 수 있어야 한다고 말한다.

서비스마다 다이얼을 다르게 14:30

auth.md는 유연하다. 서비스마다 제약이 다르기 때문이다. 발표자가 든 예는 이렇다.

이메일 발송 서비스무료로 주지 않을 수도 있다
물리 세계에 닿는 서비스무료로 주지 않는 편이 낫다
데모의 Cloudflare72시간 정도의 배포 허용
09

구조로 다시 보기 15:50

발표자는 같은 흐름을 그림으로 다시 설명한다.

단계무엇이 일어나나
1. 출발점에이전트 하네스(예: Pi) 안에 LLM, 메모리, 맥락 층이 있다. 하네스는 사용자 신원을 맡은 신원 서비스에 연결돼 있다
2. 발견에이전트가 Cloudflare 같은 서비스에 auth.md를 찾는 요청을 보낸다
3. 신원 증명ID-JAG를 보낸다. 사용자를 대표하는 서명된 자격 증명이다
4. 토큰 수령서비스가 실제 API에 쓸 액세스 토큰을 돌려준다
5. 평소대로 사용일반 API 요청과 MCP 호출이 그대로 된다

auth.md는 가입 단계에만 쓰인다. 기존 API는 그대로 동작하고, 나머지 문서도 바꿀 필요가 없다. 발표자에 따르면 Firecrawl(추정)과도 같은 흐름을 돌려 봤다.

발표자는 ID-JAG를 "identity JSON access grant"라고 풀어 말했다. IETF OAuth 작업 그룹 초안에서 ID-JAG는 Identity Assertion JWT Authorization Grant의 줄임말이다.

10

성장과 결제 16:50

구조는 단순하지만 효과는 크다고 발표자는 말한다. 에이전트가 처음부터 끝까지 일을 끝낼 수 있게 되기 때문이다.

발표자는 계획 단계를 싫어한다. 긴 계획서와 "가입해야 할 서비스 목록"을 받고 싶지 않다. 돌아가는 시제품을 받고 싶다. 특히 새 시제품은 어딘가에 무료로 배포돼서 바로 눌러 볼 수 있으면 된다.

서비스 제공자 입장 17:20

에이전트도 고객이 된다. 고객이 들어오는 깔때기 growth funnel가 사람에서 사람과 에이전트로 넓어진다.

발표자는 에이전트가 만든 것이 모두 쓸모 있지는 않을 거라고 인정한다. 전부 프로덕션까지 가거나 오래 남지는 않는다. 그래도 일부는 남는다. PLG나 그 전의 프리미엄 freemium처럼, 이것이 다음 성장 방식이라는 주장이다.

"제품에 바로 성장 효과가 난다"는 말은 발표자의 전망이다. WorkOS는 이 가입 기능을 제품으로 제공한다.

결제는 나중에 18:10

발표자는 사용이 있으면 돈을 낼 의도도 있다고 본다. 에이전트가 돈을 내는 방법은 여러 곳에서 만들고 있다. x402 같은 암호화폐 기반 프로토콜도 있고, 결제 회사들의 시도도 있다.

하지만 결제는 가입 뒤에 와야 한다. 에이전트에게 처음부터 카드 등록을 강요하는 건 거꾸로다. SaaS도 이미 그 방식에서 벗어났다.

카드 먼저카드 등록 → 가입 → 사용에이전트에게는 첫 단계부터 벽이다
→
auth.md 방식가입 → 사용 → 결제서비스가 정한 요금과 조건으로 나중에 받는다
11

API가 곧 UI 18:40

발표자는 화면 없이 API로 쓰는 제품 쪽으로 가는 흐름의 예로 Salesforce를 든다.

우리의 API가 곧 UI다.Marc Benioff (Salesforce 창업자, CEO)의 말. 발표자가 인용

발표자가 소개한 내용에 따르면 Salesforce, Agentforce, Slack 플랫폼 전체를 API, MCP, CLI로 열었다. 흔히 오래된 SaaS 회사로 여겨지지만, SaaS라는 분야를 사실상 만든 회사다. 그런 회사가 에이전트 우선으로 간다.

화면을 없앤다는 뜻은 아니다. 에이전트가 미래라고 믿는다는 뜻이다. 발표자는 아직 이 문제를 생각해 보지 않았다면 시제품을 만들고 사용자와 이야기해 보라고 권한다.

지금 쓸 수 있나 19:20

  • 공개 스펙이 있고 GitHub 저장소도 있다.
  • 에이전트에게 구현을 시킬 수도 있다. 발표자도 "좀 메타하다"고 말한다.
  • 발표자는 WorkOS가 이 스펙을 통제하지 않는다고 말한다.
  • WorkOS가 호스팅하는 버전이 있다. 직접 만들어 기존 시스템에서 돌려도 된다.
  • WorkOS 제품을 쓰면 클릭 한 번으로 켤 수 있다.
발표자가 강조한 점 이 일은 너무 중요해서 어느 한 회사가 소유하면 안 된다. 원하는 플랫폼 어디에든 만들 수 있어야 한다.

발표자는 인증 제품을 파는 WorkOS의 창업자이고, 호스팅 버전도 WorkOS가 제공한다. 이 대목은 그 점을 감안해 읽자.

결론: 다음 플랫폼 19:50

발표자는 2007년 1월 Steve Jobs의 iPhone 발표로 마무리한다. 발표자 말로는 바로 이 발표장인 Moscone 센터에서였다. 발표자는 그때 대학 1학년이었다.

스마트폰은 새로운 소프트웨어 플랫폼이었다. 그 위에서 수많은 회사가 생겼다. 발표자는 B2B SaaS와 클라우드도 좋았지만 그만한 순간은 없었다고 본다. 그리고 에이전트가 그다음 큰 물결이라고 말한다. 20:30

발표자의 요청 auth.md로 직접 만들어 보고, 막히는 곳을 알려 달라. 함께 에이전트 시대의 소프트웨어를 만들자는 것이다.
14

핵심 정리

  1. 코딩 에이전트는 한 번 지시로 몇 시간, 며칠씩 혼자 일한다. 병목은 사람의 머리다.
  2. LLM은 엔진이다. 실행 환경, 도구, 맥락, 피드백, 사람의 검토를 갖춘 하네스가 있어야 일을 한다.
  3. 에이전트가 직접 벤더를 고른다. "에이전트가 원하는 것"도 만들어야 한다.
  4. 웹은 20~30년 동안 자동화 트래픽을 막아 왔다. 그래서 좋은 에이전트도 문 앞에서 막힌다.
  5. 지금 가입 절차는 이메일, CAPTCHA, 카드, API 키 복사처럼 사람을 전제한다.
  6. MCP는 연결을 풀어 주지만 가입에는 여전히 사람이 필요하다.
  7. auth.md는 서비스가 에이전트에게 가입 방법을 알려 주는 문서다. 가입 단계만 다루고 기존 표준을 쓴다.
  8. 흐름은 auth.md 발견 → ID-JAG로 신원 증명 → 액세스 토큰 → 평소처럼 API 사용이다.
  9. 무료 범위와 확인 방식은 서비스가 위험도에 맞춰 정한다. 결제는 가입 뒤로 미룬다.
  10. 스펙은 공개돼 있다. 발표자는 에이전트를 iPhone 이후 첫 새 플랫폼으로 본다.

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1에이전트를 여러 개 동시에 돌릴 때 병목은 무엇인가?
사람의 머리다. 몇 개의 작업 맥락을 한꺼번에 쥐고 있을 수 있느냐가 한계다.
Q2에이전트가 일을 잘하려면 필요한 다섯 가지는?
실행 환경(샌드박스), 도구, 맥락, 피드백, 사람의 검토.
Q3엔진 비유에서 하네스는 무엇에 해당하나?
엔진(LLM)을 뺀 나머지인 차체, 변속기, 구동계, 바퀴. 모델이 좋아도 하네스가 나쁘면 효과가 없다.
Q4발표자는 Y Combinator 구호를 어떻게 고쳤고, 왜 그랬나?
"에이전트가 원하는 것을 만들어라." 에이전트가 벤더를 직접 고르고, 사람보다 많아지며, 우리 대신 결정하기 때문이다.
Q5로그인 화면이 에이전트를 막게 된 이유는?
일부러 막은 게 아니다. 20~30년 동안 자동화 트래픽을 나쁜 것으로 보고 DoS, 크리덴셜 스터핑을 막는 장치를 쌓았기 때문이다. 좋은 자동화와 나쁜 자동화를 구분하기 어렵다.
Q6지금 가입 절차에서 에이전트에게 어려운 단계를 세 가지 이상 들면?
이메일과 비밀번호 입력, CAPTCHA 풀기, 메일함의 인증 링크 누르기, 요금제 선택과 결제, API 키 복사, 대시보드 관리. 에이전트는 대개 이메일 주소부터 없다.
Q7MCP가 가입 문제를 풀지 못하는 이유는?
MCP 인증은 사람이 로그인하고 동의해야 한다. 예를 들어 PostHog MCP 서버를 Claude에 붙이려면 사람이 PostHog 계정으로 로그인한다.
Q8auth.md가 일부러 다루지 않는 것은?
에이전트 신원 전체, 권한, 오래 유지되는 연결 같은 큰 문제. 가입 단계 하나만 다룬다.
Q9데모에서 에이전트는 왜 Cloudflare를 골랐고, 어떻게 가입했나?
Cloudflare에 auth.md가 있어 에이전트가 직접 가입할 수 있었다. 신원 주장을 만들어 ID-JAG 표준으로 보냈고, 계정과 토큰을 받았다.
Q10데이터베이스 서비스와 이메일 발송 서비스의 무료 정책이 다를 수 있는 이유는?
위험이 다르다. 이메일 발송이나 물리 세계에 닿는 서비스는 남용 피해가 커서 무료로 아무것도 주지 않을 수 있다.
Q11발표자가 결제를 가입 뒤로 미루자고 한 이유는?
카드부터 받는 건 거꾸로다. SaaS도 이미 그 방식에서 벗어났다. 먼저 쓰게 하고, 서비스가 정한 요금과 조건으로 나중에 받으면 된다.
Q12auth.md를 도입하면 기존 API와 문서는 어떻게 되나?
그대로 둔다. 가입 단계만 더해지고, 토큰을 받은 뒤에는 일반 API 요청과 MCP 호출이 평소처럼 된다.
