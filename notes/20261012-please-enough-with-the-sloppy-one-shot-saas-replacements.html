한 번에 뽑은 SaaS 대체품은 이제 그만

에이전트에게 한 번 시켜 만든 SaaS 대체품은 돌아가기는 해도 매일 쓰고 싶은 물건은 아니다. 발표자가 Railway의 사내 마케팅 도구를 직접 만들며 그 간극을 메운 원칙을 정리한다.

원본 영상: Please… Enough with the Sloppy, One-Shot SaaS Replacements 발표: Mahmoud Abdelwahab (Railway)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 따로 확인하지 않았다. 자막에서 뭉개진 말은 앞뒤 맥락으로 바로잡았다. 예를 들어 "Asian skills"는 agent skills로, "tan stack"은 TanStack으로 고쳤다. mm:ss는 영상 위치다.

3분 요약
  1. 에이전트가 한 번에 뽑은 소프트웨어는 돌아가지만 매일 쓰고 싶지는 않다. 발표자는 이 간극이 잘 이야기되지 않는다고 본다.
  2. 발표자는 Railway 마케팅팀이 쓰던 SaaS 여러 개를 에이전트로 만든 올인원 사내 도구 하나로 바꿨다.
  3. 스택보다 구조가 중요하다. 추상화가 탄탄한 코드베이스를 주면 에이전트는 기존 패턴을 따라 일관된 기능을 만든다.
  4. 에이전트는 시키지 않으면 잘 안 하는 패턴이 있다. 자동 저장, 낙관적 업데이트, 되돌리기, 보관, URL 상태, 무한 스크롤이다.
  5. 새 기능을 시킬 때는 기존 페이지를 기준으로 지정한다. 반복되는 취향은 에이전트 스킬로 묶는다.
  6. 가장 중요한 건 검증이다. "빌드·테스트 통과"에서 멈추지 말고, 에이전트가 기능을 실제로 끝까지 써 보게 한다.
01

돌아가는 것과 쓰고 싶은 것 00:00

"SaaS는 끝났다"는 말은 이제 새롭지도 않다. 에이전트에게 시키면 되는데 왜 남이 만든 도구에 돈을 내느냐는 주장이다.

발표자는 여기서 잘 언급되지 않는 조각 하나를 짚는다. 한 번에 뽑아서 돌아가는 소프트웨어와 실제로 쓰고 싶은 소프트웨어 사이에는 큰 간극이 있다. 쓰고 싶은 쪽은 다듬어져 있고, 쓰는 느낌이 좋다. 발표자의 표현으로는 "기쁨을 주는sparks joy" 소프트웨어다.

02

스택보다 구조 02:20

흔히 이런 말을 한다. 어떤 언어나 프레임워크를 쓰든 상관없다. 에이전트에게 시키면 뭐든 만든다.

발표자는 일부만 동의한다. 실제로 쓸 도구를 만든다면 차이가 생긴다. 추상화abstraction가 탄탄한 코드베이스를 주면, 새 기능을 만들 때마다 기존 것과 비슷하고 일관된 결과가 나온다.

  • 에이전트가 같은 바퀴를 매번 다시 만들 필요가 없다.
  • 새 패턴을 들여오지 않는다.
  • 이미 있는 패턴을 그대로 따른다.

그래서 무엇을 고르느냐는 크게 중요하지 않다. 코드베이스의 구조가 제대로 잡혀 있느냐가 중요하다.

발표자의 선택 03:20 웹에서 무언가를 만들 때는 TanStack 라이브러리를 쓴다. 콘텐츠를 다루는 일이라면 Payload를 권한다. 경험이 좋고 추상화가 훌륭하다는 이유다. 발표자는 CMS를 한참 비교해 봤다. 직접 만들 수는 있지만 그래야 한다고는 보지 않는다. 미래에는 바뀔 수도 있다고 덧붙인다.

자막에는 이 항목 이름이 "texts don't matter"로 들린다. 앞뒤가 언어와 프레임워크 이야기라 "stacks don't matter"(추정)로 읽었다.

03

에이전트가 알아서 안 하는 것 04:00

매일 쓰는 SaaS를 쓸 때는 잘 못 느낀다. 막상 그 경험을 따라 만들어 보면, 흐름 하나하나에 얼마나 많은 공이 들었는지 금방 알게 된다.

이메일 보내기나 글 게시 같은 기능은 단순하다. 서버에서 그린 페이지에 폼을 제출하는 방식으로도 충분히 된다. 하지만 매일 손이 가는 도구라면 "이런 느낌이면 안 되는데" 싶어진다.

발표자는 에이전트가 명시적으로 요청받지 않으면 보통 하지 않는 패턴을 목록으로 정리했다.

04

자동 저장과 실시간 편집 04:50

문서 편집기 같은 화면이라면 자동 저장autosave은 있어야 할 기본 기능이다. 발표자는 이를 세 겹으로 쌓는다.

  1. 뒤에서 자동 저장한다. 저장 버튼을 누르지 않아도 진행 상황이 저장된다. 저장이 타이핑을 막지 않아야 한다. 이를 비차단non-blocking 동작이라고 한다.
  2. 탭 닫기를 막는다. 저장 안 된 변경이 있으면 브라우저 탭이 닫히지 않게 한다. 05:30
  3. 실시간 공동 편집을 더한다. 여러 사람이 동시에 고칠 수 있다. 꼭 필요하지는 않은 한 걸음 더다. 05:40

앞의 두 겹만으로도 작업한 내용이 사라지지 않는다는 보장이 생긴다.

실시간 편집은 에이전트가 전혀 어려워하지 않았다고 한다. 에이전트에게 물어보고, 어떻게 동작할지 검토한 뒤 맡겼다. 발표자는 여기에 "토큰 7억 개 뒤에" 실시간 편집이 생겼다고 농담처럼 덧붙인다.

발표자는 자동 저장 같은 제품 경험을 에이전트가 잘 못 챙기는 첫 번째 예로 든다.

05

낙관적 업데이트 06:10

에이전트가 자주 빠뜨리는 또 하나는 낙관적 업데이트optimistic update다. 사용자가 무언가 할 때마다 로딩 스피너를 보여 주지 않는다. 성공한 화면을 먼저 보여 주고, 실제 반영은 뒤에서 한다.

기본 흐름
  1. 사용자가 버튼을 누른다
  2. 로딩 스피너가 돈다
  3. 서버 응답이 온다
  4. 화면이 바뀐다

누를 때마다 기다린다.

낙관적 업데이트
  1. 사용자가 버튼을 누른다
  2. 화면이 바로 성공 상태로 바뀐다
  3. 뒤에서 서버와 맞춘다
  4. 실패하면 원래대로 되돌리고 실패했다고 알린다

앱이 훨씬 빠르고 즉각적으로 느껴진다.

모든 곳에 쓰지는 않는다 06:40 결과가 제대로 됐는지 확인한 뒤에 보여 줘야 하는 경우가 있다. 그런 곳은 스피너를 보여 주고 기다리는 게 맞다.

요청하는 법 07:00: 발표자는 에이전트에게 이렇게 말하면 된다고 한다. "말이 되는 곳에 낙관적 업데이트를 넣고 싶다. 계획부터 세우자." 그러면 에이전트가 적용할 만한 곳을 짚어 준다.

06

되돌리기와 보관 07:20

발표자는 되돌리기undo를 낙관적 업데이트의 연장으로 본다. 삭제 기능을 예로 든다.

에이전트가 보통 만드는 것삭제 → 확인창 → 확인 → 삭제삭제 버튼을 누르면 확인 대화상자가 뜨고, 확인을 눌러야 지워진다
→
더 나은 방식삭제 → 바로 사라짐 → 몇 초 유예화면에서 바로 빼고 몇 초 동안 되돌릴 기회를 준다. 아무것도 안 하면 그때 실제로 지운다

되돌리기를 누르면 항목을 다시 살린다. 실제 삭제는 뒤에서, 조금 늦춰서 실행하는 셈이다.

보관 08:10

지연 실행은 다음 항목인 보관archive으로 이어진다. 에이전트에게 레코드를 보관하고 보관 해제하는 기능을 요청하라고 한다.

  • 어떤 항목은 화면이나 검색 결과에서 완전히 숨기고만 싶다.
  • "안 보고 싶으면 지워라"를 사용자에게 강요하면 안 된다.
  • 보관할 수 있으면 지우지 않고도 숨길 수 있다.
07

URL 상태와 무한 스크롤 08:40

발표자가 크게 꼽는 것은 URL 상태URL state다. 말이 되는 곳이라면 화면 상태를 URL에 남기라고 에이전트에게 요청한다.

레코드 목록에 필터와 정렬 조건이 여러 개 걸려 있다고 하자. 이 조건이 URL에 있으면 링크 하나만 보내면 된다. 받은 동료는 보낸 사람이 보여 주려던 화면을 그대로 본다.

예시: /posts?status=draft&sort=updated 같은 주소를 보내면 받는 사람도 "초안만, 최근 수정순"으로 걸러진 목록을 바로 본다. 발표에 나온 주소는 아니다.

무한 스크롤 09:10

에이전트가 기본으로 안 해 주는 작은 것이 하나 더 있다. 무한 스크롤infinite scroll이다.

  • "더 보기"나 "다음 페이지" 버튼을 계속 누르게 하지 않는다.
  • 스크롤하면 데이터가 이어서 들어온다.
  • 끝에 닿으면 끝이라고 보여 준다.

아주 사소하다. 하지만 매일 쓰는 도구에서는 큰 차이를 만든다고 발표자는 말한다.

08

기존 페이지를 기준으로 09:30

결과를 크게 좋게 만든 방법이 하나 있다. 기존 페이지를 참고하라고 에이전트에게 명시적으로 말하는 것이다.

  • UI를 맞춘다.
  • 데이터를 가져오는 방식과 동작을 맞춘다.
  • 전체 구조를 맞춘다.

이렇게 하면 "좋은 모습"을 한 번만 정의하면 된다. 그다음 기능부터는 그 정의를 재사용한다.

솔직한 단서 10:00 "X 페이지를 참고하라"고 해도 안 따를 때가 있다. 발표자는 모델이 가끔 멍청해지는 건지 모르겠다고 말한다. 그래도 기준 페이지를 지정하면 성공률이 더 높다.

일관성도 따라온다. 10:20 앱을 쓰다 보면 "이건 저쪽 화면이랑 똑같네" 하고 느낀다. 같은 개념을 공유하는 두 화면은 거의 같아야 한다. 예를 들어 둘 다 레코드를 만들고, 고치고, 지우고, 목록으로 보는 화면이라면 거의 똑같이 생겨야 한다.

2장의 "탄탄한 구조"와 같은 이야기다. 에이전트가 따라갈 본보기가 있으면 결과가 일관된다.

09

취향은 에이전트 스킬로 10:40

지금까지 본 목록처럼 무언가에 대한 의견이 있다면 에이전트 스킬agent skills로 묶으라고 한다. 에이전트 스킬은 에이전트가 작업할 때 읽고 따르는 지침 묶음이다. 묶어 두면 에이전트는 무언가를 만들 때 그 스킬을 꽤 충실히 따른다.

발표자가 사내 도구를 만들며 손이 간 스킬은 세 가지다. 11:00

발표자는 Railway 소속이다. 모든 것을 Railway에서 돌린다는 대목과 Railway 스킬 추천은 그 점을 감안해 읽자. 디자인 엔지니어링 스킬 두 개는 이름이 나오지 않았다.

10

가장 중요한 단계: 검증 11:40

스킬까지 갖췄다면 마지막 단계가 남는다. 발표자는 이 단계가 가장 중요하다고 말한다.

에이전트는 무언가를 만들고 나면 보통 이렇게 보고한다. "기능 구현했습니다. 빌드 통과, 테스트 통과, 다 됐습니다." 막상 써 보면 경험이 완전히 망가져 있을 때가 있다.

검증 루프verification loop를 두면 밤과 낮만큼 달라진다. 에이전트가 스스로 이렇게 움직이는 게 보인다.

  1. 기능을 만든다.
  2. 직접 써 본다.
  3. 실패하면 고친다.
  4. 다시 써 본다. 될 때까지 반복한다.
  5. "끝까지 다 테스트했다"고 보고한다.

발표자가 이 돌파구를 느낀 건 컴퓨터 사용computer use이 정말 좋아졌을 때다. 12:20 컴퓨터 사용은 AI가 화면을 보고 클릭과 입력을 하며 프로그램을 직접 조작하는 기능이다.

발표자가 새 기능마다 마지막에 붙이는 지시 이 기능이 처음부터 끝까지end to end 동작하는지 검증해라. 실제 인프라를 띄워서 직접 써 보고 확인해라.

에이전트는 이 일을 충분히 해낸다. 말해 주기만 하면 된다.

11

회사의 SaaS 층이 되기 12:50

이 조각들이 다 모이면 빨리 만들 수 있고, 제대로 동작하고, 일관된 사내 도구가 나온다. 발표의 원칙을 순서대로 이으면 이렇다.

  1. 구조: 추상화가 탄탄한 코드베이스를 준다.
  2. 패턴: 에이전트가 알아서 안 하는 UX 패턴을 콕 집어 요청한다.
  3. 기준: 기존 페이지를 본보기로 지정한다.
  4. 스킬: 반복되는 취향과 배포 방법을 스킬로 묶는다.
  5. 검증: 실제로 끝까지 써 보게 한다.

발표자의 바람은 각자 쓰기 좋고 다듬어진 사내 도구를 직접 만드는 것이다. 발표자는 이를 "회사의 SaaS 층SaaS layer이 되라"는 말로 맺는다. 13:10

12

핵심 정리

  1. 에이전트가 한 번에 만든 소프트웨어는 돌아가지만, 매일 쓰고 싶은 수준과는 거리가 있다.
  2. 발표자는 Railway 마케팅팀이 쓰던 SaaS 여러 개를 에이전트로 만든 올인원 도구 하나로 바꿨다.
  3. 스택보다 구조가 중요하다. 탄탄한 추상화가 있으면 에이전트는 기존 패턴을 따른다.
  4. 좋은 SaaS의 흐름에는 사용자가 못 느끼는 공이 많이 들어 있다. 에이전트는 시키지 않으면 그걸 하지 않는다.
  5. 자동 저장과 탭 닫기 경고로 작업 유실을 막는다.
  6. 낙관적 업데이트로 앱을 즉각적으로 느끼게 하되, 필요한 곳에만 쓴다.
  7. 삭제는 확인창 대신 되돌리기로 바꾸고, 삭제와 별개로 보관을 둔다.
  8. 필터와 정렬은 URL에 담고, 페이지 넘김은 무한 스크롤로 바꾼다.
  9. 새 기능은 기존 페이지를 기준으로 만들게 하고, 반복되는 취향은 에이전트 스킬로 묶는다.
  10. 가장 중요한 건 검증이다. 에이전트가 실제 인프라에서 기능을 끝까지 써 보게 한다.
13

점검 퀴즈

답을 먼저 떠올린 뒤 눌러서 확인한다.

Q1발표자가 말하는 "빈틈"은 무엇과 무엇 사이인가?
한 번에 뽑아서 돌아가는 소프트웨어와, 다듬어져 있어 실제로 매일 쓰고 싶은 소프트웨어 사이다.
Q2스택 선택에 대해 발표자는 어떤 입장인가?
무엇을 고르느냐는 크게 중요하지 않다. 대신 추상화가 탄탄한 코드베이스가 중요하다. 그래야 에이전트가 기존 패턴을 따라 일관된 결과를 낸다.
Q3작업 유실을 막는 자동 저장의 두 겹은?
타이핑을 막지 않고 뒤에서 자동 저장하기. 그리고 저장 안 된 변경이 있으면 브라우저 탭 닫기를 막기.
Q4낙관적 업데이트는 어떻게 동작하고, 실패하면 어떻게 하나?
성공한 화면을 먼저 보여 주고 실제 반영은 뒤에서 한다. 실패하면 원래대로 되돌리고 사용자에게 실패했다고 알린다.
Q5낙관적 업데이트를 모든 곳에 쓰지 않는 이유와, 에이전트에게 요청하는 법은?
결과를 확인한 뒤 보여 줘야 하는 경우가 있어서다. 그런 곳은 스피너를 보여 주고 기다린다. 에이전트에게는 "말이 되는 곳에 넣고 싶다, 계획부터 세우자"고 요청한다.
Q6되돌리기를 쓰면 삭제 흐름이 어떻게 바뀌나?
확인창 없이 항목을 화면에서 바로 뺀다. 몇 초 동안 되돌릴 기회를 주고, 아무것도 안 하면 그때 실제로 지운다.
Q7삭제가 있는데도 보관 기능이 필요한 이유는?
화면이나 검색 결과에서 숨기고만 싶을 때가 있다. 안 보고 싶으면 지우라고 사용자에게 강요하면 안 된다.
Q8필터와 정렬을 URL에 담으면 무엇이 좋은가?
링크 하나만 보내면 동료가 같은 조건으로 걸러진 화면을 그대로 본다.
Q9기존 페이지를 기준으로 지정하면 얻는 것 두 가지는?
에이전트의 성공률이 올라간다. 그리고 같은 개념을 가진 화면들이 거의 똑같아져 앱 전체가 일관된다.
Q10발표자가 쓴 에이전트 스킬 세 가지는?
UI·글꼴·레이아웃·에러 메시지를 돕는 디자인 엔지니어링 스킬, 애니메이션을 돕는 디자인 엔지니어링 스킬, 배포를 돕는 Railway 에이전트 스킬.
Q11"빌드 통과, 테스트 통과"로 부족한 이유와 해결책은?
실제로 써 보면 경험이 망가져 있을 때가 있다. 에이전트가 실제 인프라를 띄워 기능을 끝까지 써 보고, 실패하면 고치기를 반복하게 한다. 컴퓨터 사용이 좋아지면서 가능해졌다.

용어 정리

용어뜻
SaaSSoftware as a Service. 설치하지 않고 구독해서 웹으로 쓰는 소프트웨어
원샷One-shot. 요청 한 번으로 결과물을 통째로 뽑는 것
스택Stack. 프로젝트에 쓰는 언어, 프레임워크, 라이브러리의 조합
코드베이스Codebase. 한 프로젝트의 소스 코드 전체
추상화Abstraction. 반복되는 코드를 공통 틀로 묶어, 세부를 몰라도 쓸 수 있게 한 것
TanStack웹 개발용 오픈소스 라이브러리 모음. Query, Router, Table 등이 있다
CMSContent Management System. 웹사이트의 글과 이미지를 관리하는 시스템
PayloadTypeScript로 만든 오픈소스 CMS
CRMCustomer Relationship Management. 연락하는 사람과 진행 상황을 기록하는 도구
서버 사이드 렌더링Server-side rendering. 서버가 완성된 페이지를 만들어 보내는 방식. 폼을 제출하면 페이지가 새로 뜬다
비차단Non-blocking. 작업이 도는 동안 사용자가 기다리지 않고 계속 쓸 수 있는 것
낙관적 업데이트Optimistic update. 성공할 거라 보고 화면을 먼저 바꾸고, 서버 반영은 뒤에서 하는 방식
롤백Rollback. 실패한 변경을 원래 상태로 되돌리는 것
보관Archive. 지우지 않고 목록과 검색에서 숨기는 것. 다시 꺼낼 수 있다
URL 상태URL state. 필터, 정렬 같은 화면 상태를 주소에 담는 것
무한 스크롤Infinite scroll. 스크롤이 끝에 가까워지면 다음 데이터를 자동으로 불러오는 방식
에이전트 스킬Agent skills. 에이전트가 특정 작업을 할 때 읽고 따르는 지침 묶음
디자인 엔지니어링Design engineering. 디자인 감각과 프런트엔드 구현을 함께 다루는 일
버킷Bucket. 파일을 올려 두는 클라우드 저장 공간
검증 루프Verification loop. 만들고, 써 보고, 고치기를 될 때까지 반복하는 흐름
컴퓨터 사용Computer use. AI가 화면을 보고 클릭과 입력으로 프로그램을 직접 조작하는 기능
엔드 투 엔드End to end. 사용자가 쓰는 처음부터 끝까지의 전체 흐름을 실제처럼 확인하는 것
토큰Token. AI 모델이 글을 처리하는 단위. 사용량과 비용의 기준이 된다
