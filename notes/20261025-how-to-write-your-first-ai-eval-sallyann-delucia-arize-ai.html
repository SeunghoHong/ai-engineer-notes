첫 AI 평가를 쓰는 법

AI 에이전트가 잘 동작하는지 감으로 판단하면 금방 한계가 온다. 이 워크숍은 "좋은 답"을 구체적인 기준으로 적고, 그 기준을 LLM 판정 프롬프트로 바꿔 첫 평가를 만드는 과정을 따라간다.

원본 영상: How to Write Your First AI Eval 발표: SallyAnn DeLucia (Arize AI 제품 총괄, Arize의 AI 에이전트 Alex 개발 담당)

영어 발표의 자동 자막을 바탕으로 한글로 정리했다. 수치와 주장은 모두 발표자가 말한 것이고 원 출처를 따로 확인하지는 않았다. 자막에서 뭉개진 이름은 확실한 것만 알려진 이름으로 고쳤다(LangGraph, OpenInference, GPT-4.1 mini, ROUGE·BLEU, app.arize.com). 슬라이드 화면은 자막에 없어서, 화면에만 있던 내용은 빠져 있을 수 있다. 실습은 발표자 회사의 제품인 Arize 위에서 진행됐다. mm:ss는 영상 위치다.

3분 요약
  1. 프롬프트를 고치고 "나아진 것 같다"는 감으로 배포하면, 무엇이 고쳐지고 무엇이 깨졌는지 아무도 증명하지 못한다.
  2. AI 평가는 단위 테스트와 다르다. 맞는 답이 여러 개이고, 에이전트의 로직은 실행이 끝난 뒤 트레이스로만 보인다.
  3. 평가 방식은 여러 가지다. 이 워크숍은 LLM 판정자를 다룬다. 다른 LLM에게 결과를 채점하게 하는 방식이다.
  4. 첫 단계는 "좋다"를 구체적으로 적는 것이다. "도움이 된다" 대신 "요청한 날 수와 같다", "예산 안에 있다"처럼 쓴다.
  5. 평가 하나에는 품질 하나만 맡긴다. 몇 개로 시작해 실제 데이터를 보며 늘린다. 발표자 팀의 에이전트 Alex에는 지금 평가 32개가 돈다.
  6. 만드는 순서는 셋이다. 판정할 스팬을 데이터셋에 담고, 기준을 판정 프롬프트로 옮기고, 플레이그라운드에서 돌려 보며 고친다.
  7. 그다음은 사람의 판정과 맞춰 보기와 운영 중에 계속 돌리기다. 시작은 트레이스 20개, 판정자 하나면 된다.
01

감으로는 확인할 수 없다 02:10

발표자는 이 문제를 "바이브 문제" vibes problem라고 부른다. 결과 몇 개를 훑어보고 느낌으로 좋고 나쁨을 정하는 방식이다. 이 방식은 규모가 커지면 버티지 못한다.

시점일어나는 일
월요일프롬프트를 고쳐 배포한다. 전체적으로 나아진 느낌이다
화요일또 고쳐 배포한다. 확인할 방법은 없지만 괜찮아 보인다
일주일 뒤고쳤다고 생각한 사용 사례가 다시 깨져 있다
그다음 주문제가 점점 커진다. 고쳐졌는지 깨졌는지 증명할 근거가 없다. 남은 건 느낌뿐이다

평가가 없으면 못 하는 일 02:40

  • 프롬프트를 바꿨을 때 회귀 regression를 잡는다. 회귀는 원래 되던 것이 새 변경 때문에 망가지는 것이다.
  • 프롬프트끼리, 모델 버전끼리 객관적으로 비교한다.
  • 새 모델이 내 사용 사례에서 정말 나은지 안다.
  • CI에 품질 관문 quality gate을 둔다. CI는 코드를 합칠 때마다 자동으로 검사하는 과정이다. 품질 관문은 기준을 못 넘으면 배포를 막는 장치다.
02

평가는 단위 테스트와 다르다 03:00

발표자가 자주 받는 질문은 "평가는 그냥 단위 테스트 아닌가"이다. 발표자의 답은 "비슷해 보여도 다르다"이다.

단위 테스트AI 평가
정답입력 하나에 맞는 출력 하나맞는 출력이 여러 개
로직코드를 읽으면 다 보인다미리 읽을 수 없다. 실행 뒤 트레이스로 드러난다
판단 기준값이 기대와 같은가여러 기준을 함께 본다. 예: 하루 단위 일정, 예산 내역
트레이스는 AI의 로그이고, 평가는 실제 테스트다.발표자의 표현을 옮김

에이전트는 더 어렵다 04:10

트레이스 trace는 에이전트가 답을 내기까지 거친 모든 단계를 모은 기록이다. 그 안의 단계 하나하나를 스팬 span이라고 부른다.

발표의 예시 트레이스에는 여러 단계가 섞여 있다. 조사 에이전트가 도구를 부르고, 다른 에이전트가 지식 베이스에서 자료를 찾는다. LLM 호출도 여러 번 얽혀 있다. 단위 테스트 하나로는 이 복잡함을 담을 수 없다.

그래서 발표자는 평가를 하려면 먼저 트레이스가 있어야 한다고 말한다. 다른 말로 관측성 observability이 먼저다. 관측성은 시스템 안에서 무슨 일이 일어났는지 밖에서 볼 수 있게 기록해 두는 능력이다.

발표자는 관측·평가 도구를 파는 Arize의 제품 총괄이다. "평가에는 관측성이 먼저 필요하다"는 주장은 그 점을 감안해 읽자.

03

평가의 종류 05:10

이 워크숍은 LLM 판정자 LLM as a judge를 다룬다. 별도의 LLM에게 에이전트 결과의 한 측면을 채점하게 하는 방식이다. 질문 답변의 정확성, 요약 품질, 관련성 같은 것을 본다.

LLM 판정자는 레이블과 설명을 함께 돌려준다. 레이블 label은 "맞음", "틀림" 같은 판정 결과다. 설명 explanation은 그 판정을 내린 이유다. 설명이 있으면 레이블을 그대로 믿지 않고 판단 과정을 확인할 수 있다.

종류방식잘 맞는 곳주로 쓰는 단계
LLM 판정자다른 LLM이 채점한다. 레이블과 설명을 준다질문 답변, 요약, 관련성개발·운영
결정 모델 decision model질문 하나에 확률과 레이블(참/거짓 등)만 준다. 설명은 없다. 싸고 빠르다 05:40예/아니오로 답할 수 있는 판정개발·운영
코드프로그램으로 정해진 규칙을 검사한다. 같은 입력이면 늘 같은 결과다 06:10특정 단어 포함 여부, JSON 형식, ROUGE·BLEU 점수개발·운영
어노테이션 annotation사람이 정답을 붙인 골든 데이터셋과 비교한다. 정답을 합성해 만들 때도 있다 06:30기준 정답이 필요한 비교개발·운영
에이전트 판정자 agent as a judge에이전트 하나가 다른 에이전트를 평가한다. 발표자 말로는 최근 6개월 사이에 나왔다 06:40아주 복잡한 성공 기준주로 운영
사용자 피드백실제 사용자의 반응을 모은다운영 중 체감 품질주로 운영
비즈니스 지표매출, 전환 같은 사업 숫자를 본다운영 중 성과주로 운영

단계 구분은 발표자가 "앞의 네 가지"는 개발과 운영 모두에, "끝의 세 가지"는 주로 운영에 쓴다고 한 말을, 말한 순서대로 나눈 것이다. 슬라이드를 볼 수 없어 이 나눔은 확인하지 못했다. 결정 모델은 발표자가 "아주 새로운 것"이라고 소개했다. 발표자는 OpenAI가 지난주 결정 모델 API를 냈다고 말했는데, 이 노트에서 확인하지는 않았다.

개발에서 쓴 평가를 운영까지 가져간다 07:00 앞의 네 가지는 개발과 운영 모두에 쓸 수 있다. 개발 단계에서만 쓰고 버릴 평가에 공을 들이지 말라는 뜻이다. 같은 평가가 사용 사례와 함께 자라야 품질을 일관되게 잴 수 있다.
04

실습 준비와 데이터 둘러보기 07:30

실습은 Arize의 데모 프로젝트에서 한다. 발표자는 진행 방법을 Notion 한 장짜리 문서로 정리해 QR 코드로 나눠 줬다.

  1. app.arize.com에서 Arize AX에 로그인한다. 계정이 없으면 무료로 만든다.
  2. Settings의 AI Providers에 모델 제공자의 API 키를 넣는다. Anthropic, OpenAI, Gemini 중 아무거나 된다. 직접 운영하는 엔드포인트도 된다. 08:10
  3. Test integration 버튼으로 키가 동작하는지 확인한다.
  4. Traces 메뉴에서 데모 프로젝트를 연다. 예전 데모가 보여도 실습에는 문제없다. 시간 범위를 넓히면 데이터가 더 보인다. 09:30

데모: 여행 계획 에이전트 10:10

이 에이전트는 사용자의 여행 요청을 받는다. 필요하면 후속 질문을 하고, 도구를 부르고, 여행 계획을 돌려준다. 사용자 요청에는 목적지, 기간, 예산, 여행 스타일이 들어 있다.

제품 관점에서 "좋은 답" 사용자가 한 후속 질문에 답하고, 여행 날 수와 예산을 지킨다. 발표자가 이 에이전트에 대해 내린 정의다.

트레이스를 보며 적어 볼 것 10:50

  • 사용자는 무엇을 요청했나
  • 에이전트는 무엇을 했고, 어떤 도구를 불렀나
  • 최종 답은 무엇이었나
  • 이 답을 실제 사용자에게 보여 줄 수 있나

이때 제품 담당자나 엔지니어처럼 이 에이전트에 이해관계가 있는 사람의 눈으로 본다. 그리고 무엇을 재고 싶은지 메모해 둔다. 13:30

발표자가 연 트레이스 하나 11:20
  • 요청: 체코 프라하, 3일, 예산 800달러
  • 추가 요청: 관광지 느낌이 덜한 현지 분위기
  • 결과: 1일 차부터 3일 차까지 자세한 일정
  • 추가 데이터는 attributes 탭에 있다
  • 특정 단계의 데이터는 그 스팬을 눌러 입력과 출력으로 본다. 예: OpenAI에 보낸 요청

발표자는 이때 데이터가 어디에 있는지 봐 두라고 했다. 평가에 어떤 데이터가 필요한지 나중에 정해야 하기 때문이다.

05

트레이스 읽는 법 14:00

스팬하는 일여행 에이전트에서

에이전트 스팬큰 에이전트를 대신해 일부 일을 맡은 하위 에이전트조사 에이전트

현장 질문 3가지 16:20

질문발표자의 답
LLM 스팬이 왜 두 개인가첫 번째 LLM 호출이 쓸 도구를 골랐다. 두 번째 호출은 도구가 가져온 기온, 목적지 정보를 요약했다. 계측 방식 때문에 이렇게 나뉘어 보이기도 한다. 트레이스를 내려갔다 다시 올라와야 이해되는 경우가 있다.
루트가 모든 결정을 내리나 17:30에이전트 구조에 따라 다르다. 감독 에이전트 supervisor가 하위 에이전트에게 계획을 주는 구조가 있다. LLM 하나가 도구를 들고 한 단계씩 나아가는 구조도 있다. 이 데모는 LangGraph로 만들었고, 감독 없이 역할별 에이전트 몇 개로 나뉘어 있다.
어떤 프레임워크를 지원하나 18:10특정 프레임워크를 가리지 않는다. Arize의 트레이싱 패키지 OpenInference에 프레임워크별 자동 계측기 auto-instrumentor가 여러 개 있다.
06

"좋다"를 구체적으로 적기 19:00

평가를 만드는 첫 단계는 "좋다"가 무슨 뜻인지 정하는 것이다. 발표자는 이 단계를 많은 사람이 어려워한다고 했다. 요령은 좋은 답의 모습을 아주 구체적인 기준으로 적는 것이다.

모호한 기준도움이 된다, 정확하다, 좋은 답이다무엇을 보고 판정할지 알 수 없다
→
구체적인 기준후속 질문에 답한다, 요청한 날 수와 같다, 합계가 예산 안이다답 하나를 보고 바로 맞다 틀리다를 정할 수 있다

평가 하나에 품질 하나 19:50

LLM 판정자는 한 번에 기준 하나만 볼 때 잘한다. 발표자는 이를 보여 주는 연구가 많다고 했다.

예외도 있다. 결정 모델과 에이전트 판정자는 평가 하나에 기준 여러 개를 담아도 비교적 잘 버틴다.

그래서 LLM 판정자는 기준 하나로 평가 하나를 만든다. 필요한 기준이 더 있으면 평가를 하나씩 늘린다.

작게 시작해 실제 데이터로 늘린다 20:30

평가는 한 번 만들고 끝나는 게 아니다. 계속 고쳐 가는 일이다. 처음엔 몇 개만 적어서 만들고, 시간이 지나며 더한다.

발표자가 Arize의 AI 에이전트 Alex에 처음 붙인 평가는 단순했다. 질문 답변 정확성, 사용자 불만, 그리고 탈옥과 유해성 같은 안전 평가였다. 지금 Alex에는 평가 32개가 돈다.

사용자가 늘면 실제 운영 데이터가 쌓인다. 그 데이터를 근거로 성공을 정의하는 데 무엇이 더 필요한지 보고 평가를 더한다.

범용 평가냐, 맞춤 평가냐 21:10

대체로 내 사용 사례에 맞춘 평가가 낫다. 하지만 평가가 아예 없는 것보다는 범용 평가라도 있는 게 낫다.

Arize의 평가 허브 eval hub에는 기본 템플릿이 있다. 질문 답변 정확성, 환각, 세션 일관성 session coherence 같은 것이다. 환각 hallucination은 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 것이다. 이런 템플릿은 시작용으로 좋고, 조직 안에서 함께 쓰기에도 좋다. 핵심은 템플릿을 내 사용 사례에 맞게 고치고, 점점 더 구체적인 평가를 만드는 것이다.

평가 기준 6가지 적기 22:00

발표자는 옆 사람과 짝을 지어 아래 여섯 가지를 적게 했다. 이 메모가 다음 단계에서 판정 프롬프트가 된다. 구체적일수록 평가가 좋아진다.

항목적을 내용
1. 과제이 평가가 어떤 상황을 보는가
2. 성공성공은 어떤 모습인가 (한 줄)
3. 실패실패는 어떤 모습인가 (한 줄)
4. 판정 대상판정자가 정확히 무엇을 보고 판단하는가
5. 합격 조건합격하는 답의 모습을 bullet 세 개로
6. 불합격 조건불합격하는 답의 모습을 bullet 세 개로
발표 슬라이드의 예 24:00
  • 과제: 사용자가 여행에 대해 후속 질문을 보낸다
  • 성공: 이 여행의 정보를 써서 후속 질문에 바로 답한다
  • 실패: 일반적인 예산 이야기로 빠진다

합격·불합격 bullet은 슬라이드에만 있었고 자막에는 없다.

예시: 합격·불합격 bullet

합격

  • 후속 질문에 첫 문장부터 직접 답한다
  • 답에 이 여행의 목적지, 기간, 예산을 쓴다
  • 질문 범위를 벗어난 내용을 늘어놓지 않는다

불합격

  • 질문과 상관없는 일반적인 예산 조언으로 빠진다
  • 어느 여행에나 맞는 답을 한다
  • 질문에 답하지 않고 일정 전체를 다시 보여 준다

이 노트가 만든 예시다. 모두 "후속 질문에 답하는가"라는 품질 하나만 본다.

한 줄짜리 성공·실패만으로는 부족하다. 이 메모로 LLM 판정 프롬프트를 쓰기 때문이다. LLM이 기준을 이해하려면 bullet 수준으로 구체적이어야 한다.

동료에게 설명하듯 쓴다 발표자는 기준을 쓸 때 동료나 이해관계자에게 "성공은 이런 모습이다"라고 설명하듯 쓰라고 했다.

현장 질문: 트레이스의 데이터는 직접 만들어야 하나 23:00

계측 instrumentation은 실행 기록이 남도록 코드에 장치를 다는 일이다. Arize의 기본 계측은 트레이싱 모범 사례를 미리 담고 있다. input.value나 LLM에 보낸 입력 메시지 같은 공통 속성은 자동으로 남는다.

내 사용 사례에 맞는 정보가 더 필요하면 수동 계측으로 바꾼다. 자동과 수동을 섞는 하이브리드 방식도 있다.

발표자는 직접 트레이스를 보낼 때 코딩 에이전트에게 계측을 맡기라고 권했다. 시작 페이지의 명령 하나가 Arize의 스킬 skills을 불러온다(자막에는 "MPX evals"로 들림, npx 명령으로 추정). 에이전트가 계측 방법을 찾고, 사람은 방향만 잡아 준다.

플레이그라운드에서 판정자 만들기 27:20

만드는 순서

  2. 평가 허브에서 만든 평가가 있으면 드롭다운에서 불러온다. 처음이면 빈 평가 blank eval로 시작한다. 28:00

핵심 정리

  1. 감으로 배포하면 회귀를 잡지 못하고, 무엇이 나아졌는지 증명하지 못한다.
  2. AI 평가는 단위 테스트와 다르다. 맞는 답이 여럿이고, 로직은 실행 뒤 트레이스로 드러난다.
  3. 트레이스는 에이전트가 거친 모든 단계의 기록이다. 스팬은 그 안의 작업 단위이고, 루트 스팬에 보통 입력과 최종 출력이 있다.
  4. 평가 방식에는 LLM 판정자, 결정 모델, 코드, 어노테이션, 에이전트 판정자, 사용자 피드백, 비즈니스 지표가 있다.
  5. LLM 판정자는 레이블과 설명을 준다. 설명을 읽어야 판정을 믿을지 정할 수 있다.
  6. "도움이 된다" 대신 "요청한 날 수와 같다"처럼 구체적으로 쓴다.
  7. LLM 판정자 하나에는 품질 하나만 맡긴다. 작게 시작해 실제 데이터를 보며 늘린다. Alex는 지금 32개다.
  8. 과제, 성공, 실패, 판정 대상, 합격 bullet 3개, 불합격 bullet 3개를 적으면 그게 판정 프롬프트가 된다.
  9. 판정할 스팬을 데이터셋에 담고, 플레이그라운드에서 돌려 보며 프롬프트를 고친다. 이름 차이는 변수 매핑으로 맞춘다.
  10. 다음은 정렬과 온라인 평가다. 지표는 고장 신호를, 평가는 실패 유형을 알려 준다.

점검 퀴즈

Q1평가가 없으면 못 하는 일 네 가지는?
프롬프트를 바꿨을 때 회귀를 잡는 일, 프롬프트와 모델을 객관적으로 비교하는 일, 새 모델이 내 사용 사례에 나은지 아는 일, CI에 품질 관문을 두는 일.
Q2AI 평가가 단위 테스트와 다른 점 두 가지는?
맞는 출력이 여러 개다. 그리고 로직을 미리 읽을 수 없고, 실행 뒤 트레이스로만 볼 수 있다.
Q3루트 스팬은 어떻게 알아보고, 보통 무엇이 들어 있나?
위에 다른 스팬이 없는 맨 위 스팬이다(parent ID가 null). 보통 사용자 입력과 최종 출력이 들어 있다.
Q4LLM 판정자와 결정 모델의 차이는?
LLM 판정자는 레이블과 설명을 준다. 결정 모델은 확률과 레이블만 주고 설명이 없다. 대신 싸고 빠르다.
Q5코드 기반 평가가 잘 맞는 경우의 예는?
결과가 늘 같은 규칙 검사다. 출력에 특정 단어가 있는지, JSON 형식인지 보는 것. ROUGE·BLEU 점수도 여기에 든다.
Q6여행 에이전트에서 "좋은 답"을 구체적인 기준으로 바꾸면?
사용자의 후속 질문에 답한다. 요청한 날 수와 일정이 같다. 비용 합계가 말한 예산 안에 있다.
Q7LLM 판정자에게 품질 하나만 맡기라는 이유와 그 예외는?
LLM 판정자는 한 번에 기준 하나를 볼 때 잘한다(발표자가 인용한 연구). 결정 모델과 에이전트 판정자는 기준 여러 개를 담아도 비교적 잘 버틴다.
Q8판정자를 만들기 전에 적어야 할 여섯 가지는?
과제, 성공, 실패, 판정 대상, 합격 조건 bullet 세 개, 불합격 조건 bullet 세 개.
Q9"요청이 일정에 반영됐나"와 "도구가 맞는 정보를 가져왔나"를 평가할 때, 데이터셋에 각각 무엇을 담나?
앞의 것은 루트 스팬, 뒤의 것은 도구 스팬을 담는다.
Q10변수 매핑을 쓰면 무엇이 좋은가?
프롬프트에 데이터의 정확한 이름을 쓰지 않아도 된다. 데이터셋과 트레이스가 같은 값을 다른 이름으로 불러도, 평가를 고치지 않고 연결만 바꾸면 된다.
Q11정렬과 온라인 평가는 각각 무엇인가?
정렬은 사람이 붙인 판정과 판정자의 결과가 맞는지 비교하는 일이다. 온라인 평가는 판정자를 운영 트레이스에 계속 돌려 애플리케이션을 지켜보는 일이다.
Q12지표와 평가는 각각 무엇을 알려 주나?
지표는 뭔가 고장 났을 수도 있다고 알려 준다. 평가는 어떤 식으로 실패했는지, 곧 실패 유형을 알려 준다. 둘 다 쓴다.

회귀Regression. 새 변경 때문에 원래 되던 기능이 망가지는 것
품질 관문Quality gate. 기준을 못 넘으면 배포를 막는 장치
CIContinuous integration. 코드를 합칠 때마다 자동으로 빌드하고 검사하는 과정
관측성Observability. 시스템 안에서 일어난 일을 밖에서 볼 수 있게 기록해 두는 능력
트레이스Trace. 에이전트가 답을 내기까지 거친 모든 단계의 기록
스팬Span. 트레이스 안의 작업 단위 하나

계측Instrumentation. 실행 기록이 남도록 코드에 장치를 다는 일
LLM 판정자LLM as a judge. 다른 LLM에게 결과를 채점하게 하는 평가 방식
결정 모델Decision model. 질문 하나에 확률과 레이블만 주는 판정 모델. 설명은 없다
에이전트 판정자Agent as a judge. 에이전트 하나가 다른 에이전트를 평가하는 방식
어노테이션Annotation. 사람이 데이터에 정답이나 판정을 붙이는 일
골든 데이터셋Golden dataset. 정답이 붙어 있어 기준으로 쓰는 데이터 묶음
ROUGE · BLEU모델 출력과 기준 문장이 단어를 얼마나 겹치게 쓰는지 재는 점수
레이블Label. 판정자가 내는 판정 값. 예: correct, incorrect
멀티 에이전트 시스템여러 에이전트가 일을 나눠 맡는 구조
감독 에이전트Supervisor. 하위 에이전트에게 계획을 주고 지휘하는 에이전트
프롬프트 플레이그라운드프롬프트를 쓰고 데이터에 바로 돌려 보는 화면
변수 매핑Variable mapping. 프롬프트의 변수를 실제 데이터 필드에 연결하는 것
정렬Alignment. 판정자의 결과가 사람의 판정과 맞는지 맞춰 보는 일
온라인 평가Online eval. 운영 중 들어오는 트레이스에 평가를 계속 돌리는 것
실패 유형Failure mode. 시스템이 실패하는 구체적인 방식
